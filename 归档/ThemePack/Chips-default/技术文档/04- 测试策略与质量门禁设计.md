# 测试策略与质量门禁设计（Chips-default）

> 文档状态：实现对齐稿  
> 适用范围：`ThemePack/Chips-default` 默认主题包的本地与 CI 验证

---

## 1. 目标与原则

- 为默认主题包提供**可重复、可自动化**的质量门禁。
- 覆盖 token 结构、关键组件契约、构建产物完整性。
- 不依赖临时实现或手工检查，所有检查均可通过脚本与测试用例执行。

---

## 2. 可用命令一览

在 `ThemePack/Chips-default` 目录下：

- `npm run build`
  - 执行 `build:tokens`、`build:contracts` 与 `build:css`；
  - 生成 `dist/tokens.json`、主题 contract 产物与 `dist/theme.css`。
- `npm run build:tokens`
  - `src/build-tokens.ts`；构建五层 token。
- `npm run build:contracts`
  - `src/build-contracts.ts`；从组件库正式 contract 生成本主题包 contract 产物。
- `npm run build:css`
  - `src/build-css.ts`；拼接所有 CSS 文件。
- `npm run validate:theme`
  - `src/validate-theme.ts`；验证 token 结构与完整组件 contract 覆盖。
- `npm test`
  - 使用 Vitest 运行 `tests/*.spec.ts`，作为本主题包的基础测试集。

---

## 3. 构建与产物校验

### 3.1 Token 构建（build:tokens）

- 输入：
  - `tokens/ref.json`
  - `tokens/sys.json`
  - `tokens/motion.json`
  - `tokens/layout.json`
  - `tokens/comp/*.json`
- 输出：

```json
{
  "ref": { ... },
  "sys": { ... },
  "comp": { ... },
  "motion": { ... },
  "layout": { ... }
}
```

- 校验要点：
  - 所有 JSON 文件必须存在且可解析；
  - 合并后的 `comp` 层包含所有组件的 `chips.comp.*` token。

### 3.2 CSS 构建（build:css）

- 输入：
  - `styles/base.css`
  - `styles/components/*.css`
  - `styles/motions.css`
- 输出：`dist/theme.css`
- 校验要点：
  - 构建过程无错误或异常输出；
  - 最终 CSS 中不包含占位样式或 `TODO` 标记。
  - 视觉升级后，CSS 还应保持以下质量基线：
    - `data-scope` 契约选择器仍完整覆盖组件库正式 contract；
    - 浮层、菜单、表格、树、反馈组件只通过主题 token 与本主题内部派生变量表达层级；
    - 焦点样式统一消费 `chips.comp.*.focus.outline`、`chips.layout.focus.*` 与 `--chips-base-focus-ring`；
    - reduced motion 下关闭骨架屏 shimmer、Spinner、Progress indeterminate 等非必要动画。

## 4. 主题验证脚本（validate:theme）

入口：`src/validate-theme.ts`，通过 `npm run validate:theme` 执行。

### 4.1 结构校验

步骤：

1. 读取 `dist/tokens.json` 并解析为 `ThemeTokenLayers`：

```ts
interface ThemeTokenLayers {
  ref: Record<string, unknown>;
  sys: Record<string, unknown>;
  comp: Record<string, unknown>;
  motion: Record<string, unknown>;
  layout: Record<string, unknown>;
}
```

2. 检查 `ref/sys/comp/motion/layout` 五层均为对象，否则退出并输出错误信息。
3. 将五层合并为组件库 validator 可消费的 contract token tree，并保持 Host Theme Runtime 的正式扁平键名：
   - 示例键名：
     - `chips.ref.color.gray-0`
     - `chips.sys.color.primary`
     - `chips.comp.button.root.surface.idle`

### 4.2 完整组件 contract 校验

校验脚本不再维护本地硬编码 token 白名单。正式来源为：

- `Chips-ComponentLibrary/packages/theme-contracts/contracts/components/*.contract.json`：组件库正式 contract 来源；
- `contracts/theme-interface.contract.json`：由组件库正式 contract 生成、随主题包发布给 Host 读取的 contract 产物；
- `contracts/theme-min-functional-set.json`：由组件库正式 contract 生成的最小功能集产物；
- `@chips/theme-contracts`：统一生成 `ThemeContractView`、`ThemeDiagnostic` 与 `ThemeDiagnosticSummary`，并比较主题包 contract 是否漂移。

校验逻辑：

- `src/validate-theme.ts` 读取 `manifest.yaml` 中的 `themeId/version`；
- 读取组件库正式 contract，比较本包 `theme-interface.contract.json` 与 `theme-min-functional-set.json` 是否为生成等值产物；
- 调用组件库 validator 生成 `ThemeContractView`；
- 若 `summary.blocking > 0`，输出 JSON 形式的 `summary/diagnostics` 并设置 `process.exitCode = 1`；
- 所有 required token 覆盖完整时输出组件数与 required token 数。

## 5. Vitest 用例设计

### 5.1 `tests/tokens.spec.ts`

- 目的：验证构建后的 token 文件结构。
- 行为：
  - 读取 `dist/tokens.json`；
  - 断言 `ref/sys/comp/motion/layout` 字段均存在且为对象。

### 5.2 `tests/contract.spec.ts`

- 目的：验证完整组件库 contract 基线与诊断 schema。
- 行为：
  - 调用 `validateTheme()`；
  - 断言 contract 覆盖数量等于组件库正式 contract 数量；
  - 断言 `summary.status=complete`、required 覆盖率为 1；
  - 断言 `theme-min-functional-set.json` 与组件库正式组件集合等值；
  - 断言 `buildContracts()` 可以从组件库来源重新生成当前 contract 产物；
  - 构造缺失 button token 的场景，断言 `THEME_REQUIRED_TOKEN_MISSING` 可定位到 `component/part/state/tokenKey/layer`。
- 说明：
  - 与 `validate:theme` 使用同一 contract 与 validator，避免本地白名单漂移；
  - 后续新增组件 contract 时，应先更新组件库正式 contract 与主题包 contract，再由本测试暴露覆盖缺口。

### 5.3 `tests/build.spec.ts`

- 目的：验证构建流水线可在 CI 环境顺利执行。
- 行为：
  - 在测试中执行 `npm run build`；
  - 检查 Material Symbols 三套字体进入 `dist/icons/variablefont/`；
  - 检查 `dist/theme.css` 覆盖每个 component contract scope，避免出现 contract token 完整但无 CSS 选择器的空主题组件。

### 5.4 `tests/theme-matrix.spec.ts`

- 目的：验证浅色主题矩阵快照可被设置面板、CLI 或测试报告复用。
- 行为：
  - 读取 `preview/theme-matrix.json`；
  - 断言矩阵覆盖应用插件窗口、基础卡片 iframe、箱子布局 iframe 和模块配置面板四类运行场景；
  - 断言每个场景引用的 contract scope 都存在于组件库正式 contract view。

## 6. 建议的 CI 门禁

在集成到统一 CI 流水线时，建议按以下顺序执行：

1. `npm run build`
2. `npm run validate:theme`
3. `npm test`

所有步骤均通过才允许将默认主题包作为可发布版本：

- 若 `build` 失败：视为主题包结构或脚本错误；
- 若 `validate:theme` 失败：视为 token 契约不满足当前正式组件 contract 基线；
- 若 `npm test` 失败：视为基础保障用例不通过。

---

## 7. 后续扩展方向

- 当组件库侧新增或修改正式组件 contract 时，主题包必须重新运行 `npm run build:contracts`，同步 `theme-interface.contract.json`、`theme-min-functional-set.json` 与对应 `tokens/comp/*.json`、CSS 和测试；
- 完整视觉质量仍需要在 Host、设置面板和典型插件窗口中做人工视觉巡检；自动化门禁负责阻断契约漂移、构建失败、资源缺失和明显的 CSS 覆盖缺口。
