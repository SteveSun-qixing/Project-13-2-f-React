# 主题包插件脚手架技术架构与模板设计

> 文档状态：vNext 实现收口稿  
> 适用范围：`Chips-Scaffold/chips-scaffold-theme` 仓库的总体技术方案、模板结构与集成方式

---

## 1. 总体定位与上下游关系

### 1.1 在生态中的位置

主题包插件脚手架是薯片生态“开发工具”侧的一层薄封装，位于：

- **上游**：开发者与 `chipsdev create theme` 命令：
  - 开发者通过命令行选择「主题插件」类型与具体模板；
  - `chipsdev` 根据配置从本仓库读取模板元数据与文件，生成新的主题插件工程。
- **下游**：Host Theme Runtime / SDK / 组件库：
  - 生成的主题插件工程打包为 `.cpk` 后由 Host `plugin.install` / `theme.apply` 等动作加载；
  - 主题 tokens 由 L11 Theme Runtime 解析，并通过 `theme.resolve/getAllCss/contract.get` 等接口向 L9/L10 暴露；
  - 组件库通过 `chips.comp.*` token 与 CSS 变量消费主题。

脚手架自身 **不参与运行时链路**，只承担：

- 标准化主题插件工程目录结构与配置；
- 严格对齐 `生态共用技术文档` 的主题系统设计与契约；
- 为主题开发者提供最小可用、可测试、可扩展的项目起步模板。

### 1.2 与其他脚手架仓库的关系

- 与 `Chips-Scaffold/chips-scaffold-app`、`chips-scaffold-basecard` 等仓库共同构成统一的脚手架体系；
- 顶层目录结构保持一致，`templates/` 下仅包含各主题模板资产（manifest、tokens、scripts、styles、resources、测试等），而 `需求文档`、`技术文档`、`开发计划` 等目录仅属于脚手架自身的内部文档体系，用于说明设计与演进，不会同步出现在生成的主题项目中；
- 仅在模板内容与生成工程结构上体现“主题插件”的专有差异。

## 2. 模板目录结构设计

主题脚手架内部以模板目录承载可选的工程基线。命名约定：

- 顶层使用 `templates/` 目录收纳所有模板；
- 主题模板使用前缀 `theme-`，例如：
  - `theme-standard`：标准官方主题模板（覆盖核心组件集与 Host UI）；
  - `theme-derived`：基于父主题的差异化派生模板；
  - 后续如需更多变体（高对比度主题、实验型主题等），可在后续阶段补充。

当前 `theme-standard` 以 `ThemePack/Chips-default` 的正式工程结构为来源基线，复制后对插件身份、主题身份和文档文本进行参数化。模板目录结构如下：

│  │  ├─ README.md.tpl

约束：

- 需要参数化的模板文件使用 `.tpl` 后缀；`.json`、`.ts`、`.css`、`.md`、`.yaml` 等文本文件也会经过占位符渲染，二进制资源使用原样复制；
- `manifest.yaml.tpl` 必须符合《Manifest配置规范》与《主题包开发指南》中 `type: theme` 的字段要求；
- token 源文件模板必须与 Theme Runtime 的五层结构一致（详见第 4 节）。

## 3. 生成工程目录结构约定

以 `theme-standard` 模板生成的主题插件工程为例，初始化完成后的目录结构如下（略去部分细节文件）：

```text
my-theme/
├─ manifest.yaml
├─ package.json
├─ tsconfig.json
├─ chips.config.mjs
├─ README.md
├─ contracts/
│  ├─ theme-interface.contract.json
│  └─ theme-min-functional-set.json
├─ fonts/
│  └─ README.md
├─ icons/
│  ├─ README.md
│  ├─ SOURCE.md
│  └─ variablefont/*.woff2
├─ preview/
│  ├─ README.md
│  └─ theme-matrix.json
├─ tokens/                    # 设计 token 源文件（五层结构输入）
│  ├─ ref.json
│  ├─ sys.json
│  ├─ layout.json
│  ├─ motion.json
│  └─ comp/
│     ├─ button.json
│     ├─ input.json
│     └─ ...
├─ src/
│  ├─ build-tokens.ts        # 合并五层 token 源为 dist/tokens.json
│  ├─ build-contracts.ts     # 从 @chips/theme-contracts 生成主题 contract
│  ├─ build-css.ts           # 输出 CSS 与图标字体运行时资源
│  └─ validate-theme.ts      # 执行主题 contract 与 token 覆盖校验
├─ styles/
│  ├─ base.css               # 全局与语义层 CSS 变量注入
│  ├─ components/
│  │  ├─ button.css
│  │  └─ input.css
│  └─ motions.css
└─ tests/
   ├─ tokens.spec.ts
   ├─ contract.spec.ts
   ├─ layout-primitives.spec.ts
   ├─ theme-matrix.spec.ts
   └─ build.spec.ts
```

其中 `dist/` 仅在执行 `npm run build` 后生成，用于承载 `dist/tokens.json`、`dist/theme.css` 等运行时产物；初始化项目默认不会预创建该目录，也不会创建 `需求文档/`、`技术文档/`（或“技术手册”）与 `开发计划/` 目录。

关键约束：

- `manifest.yaml`：
  - 必须位于工程根目录；
  - `type: theme`、`themeId`、`version`、`parentTheme`、`entry.tokens`、`entry.themeCss` 等字段符合《主题包开发指南》《Manifest配置规范》；
  - 权限声明默认使用最小集（通常只需要主题相关只读能力），由脚手架模板提供基线。
  - `.cpk` 打包后包根 manifest 必须继续指向 `dist/tokens.json` 与 `dist/theme.css`。
- `tokens/`：
  - 作为设计 token 源文件目录，遵循《主题包开发指南》中 `ref/sys/comp/motion/layout` 五层分层；
  - 不直接暴露给 Theme Runtime，需经 `src/build-tokens.ts` 构建为 `dist/tokens.json`。
- `dist/tokens.json`：
  - 输出为 Theme Runtime 所需的五层结构：
    - `ref/sys/comp/motion/layout`；
  - 结构必须通过 `Chips-Host` 侧 `asThemeTokenLayers` 校验。
- `styles/` 与 `icons/`：
  - 通过 CSS 变量对接 token，命名遵循 `--chips-*` 与 `chips.comp.*` 的约定；
  - 图标与字体资源使用《图标与字体系统设计规范》中的资产来源与回退链。
- `tests/`：
  - 至少覆盖 token 完整性与契约映射、构建脚本关键路径、基础颜色对比度规则。

## 4. token 构建链路与五层结构映射

### 4.1 设计 token 源与目标结构

根据《主题包开发指南》和《主题系统设计》，脚手架采用“两层模型”：

- **源层（工程视角）**：面向主题开发者的五层 token 源目录：
  - `tokens/ref.json`：原始值层；
  - `tokens/sys.json`：语义值层；
  - `tokens/motion.json`：动效值层；
  - `tokens/layout.json`：布局密度、间距、安全区和断点；
  - `tokens/comp/*.json`：组件级 token。
- **目标层（运行时视角）**：Theme Runtime 消费的五层结构：
  - `ref`：原始值层；
  - `sys`：语义值层；
  - `comp`：组件值层；
  - `motion`：动效值层；
  - `layout`：布局密度层。

脚手架提供默认构建脚本（`src/build-tokens.ts`）完成从**源层 JSON**到**目标层 JSON**的合并：

- 不引入新的第三方 token 构建库，保持与正式默认主题包一致；
- `tokens/comp/*.json` 按文件名排序深度合并，避免不同组件 token 互相覆盖；
- 生成的 `dist/tokens.json` 必须可以被 `Theme Runtime` 的 `mergeThemeLayers/resolveThemeFromLayers` 正常消费。

### 4.2 token 命名与组件对接

- 所有组件级 token 必须遵循《Token 与主题对接标准》中的前缀：
  - `chips.comp.button.*`、`chips.comp.input.*` 等；
  - 组件 token 文件直接保存 `chips.comp.*` 层级结构，构建脚本只负责合并，不改写公共 token key；
- `ref/sys` 层的键名设计应避免业务语义，保持通用性（例如 `color.blue.500` 而非 `todo-card-bg`）；
- `layout` 层建议集中管理列表密度、间距、容器高度等参数，后续可与 L8/L9 的布局策略联动。

## 5. 门禁与自测集成设计

主题脚手架需要为生成工程提供可直接运行的最小门禁链路，建议默认支持：

1. **本地构建与打包**
   - `npm run build`：
     - 依次调用 `build-tokens`、`build-contracts` 与 `build-css`；
     - 产出 `dist/tokens.json`、`contracts/theme-interface.contract.json`、`contracts/theme-min-functional-set.json`、`dist/theme.css` 与 `dist/icons/variablefont/*.woff2`。
   - `npm run package`：
     - 调用 `chipsdev package` 生成 `.cpk`；
     - 保证包根保留 `manifest.yaml`、运行产物位于 `dist/`、压缩方式为 ZIP Store。
2. **主题契约与 token 完整性校验**
   - `npm run validate:theme`：
     - 加载 `dist/tokens.json`、`contracts/theme-interface.contract.json` 与 `contracts/theme-min-functional-set.json`；
     - 通过 `@chips/theme-contracts` 的 `compareThemeInterfaceContract`、`compareThemeMinFunctionalSet` 与 `buildThemeContractView` 校验生成主题覆盖组件库正式 contract；
     - 若出现 required token 缺失，输出阻断级诊断并失败。
3. **单元测试与集成测试**
   - 基础单元测试：
     - token 映射逻辑（`build-tokens`）；
     - 契约映射逻辑（从 `@chips/theme-contracts` 到主题 contract）；
     - CSS 对所有 component contract scope 的公开 `data-scope` 覆盖；
     - preview matrix 引用的 scope 与真实 contract 一致；
   - 脚手架级 E2E：
     - 在临时生态工作区中执行 `chipsdev create theme`；
     - 执行生成工程 `npm run verify`；
     - 通过 Host Runtime 安装、启用、切换生成的 `.cpk`，并读取 `theme.getAllCss`、`theme.resolve` 与 `theme.contract.get`。

门禁脚本与测试文件本身只在生成工程中存在，脚手架仓库负责提供模板与约定，不直接维护具体主题。

## 6. 与其他脚手架的对齐要求

为保证薯片生态脚手架体系的一致性，主题脚手架在以下方面需与其他脚手架仓库对齐：

- 顶层目录结构：`templates/` 仅包含可导出的主题模板资产（manifest、tokens、scripts、styles、contracts、tests、资源等），`需求文档`/`技术文档`/`开发计划` 这些目录属于脚手架自身的内部文档体系，不会随模板导出到用户项目；
- 模板文件约定：统一使用 `.tpl` 后缀与一致的占位符语法；
- 生成工程约定：
  - 尽可能复用 `src/`、`tests/`、`config/` 等目录约定，仅在主题场景需要时新增 `tokens/`、`styles/`、`icons/` 等；
  - NPM 脚本命名优先与应用/卡片/模块脚手架保持一致（如 `dev/build/test/validate`）。

本技术文档作为主题包插件脚手架的架构与模板设计基线，后续实现与调整必须与本设计保持一致。如需重大变更，必须先更新本文件与相关需求/开发计划文档，再进行实现。
