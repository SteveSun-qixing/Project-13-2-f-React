# 模块插件开发

## 1. 概述

模块插件是安装到 Host 中的无界面能力插件。模块插件不创建窗口，不承载页面渲染，不以 DOM 挂载和前端插槽为正式能力边界。

模块插件对外提供的是正式能力契约，用于被 Host、应用插件、卡片插件、布局插件以及其他模块插件复用。

## 2. 正式定位

模块插件与其他插件类型的边界如下：

- 应用插件负责用户界面和业务流程；
- 卡片插件负责基础卡片渲染和编辑；
- 布局插件负责箱子布局呈现；
- 模块插件负责无界面能力提供；
- 主题插件负责视觉样式。

模块之间允许相互调用，但必须继续经过 Host 的正式模块服务。

## 3. 正式调用模型

模块插件正式使用 capability + method 模型，而不是 `slot + mount` 模型。

调用方通过正式模块服务完成：

- 查询 provider：`module.listProviders`
- 解析 capability：`module.resolve`
- 调用方法：`module.invoke`
- 查询任务：`module.job.get`
- 取消任务：`module.job.cancel`

Host 负责：

- provider 注册；
- capability 解析；
- 权限校验；
- schema 校验；
- 模块 runtime 激活；
- 同步调用和异步任务调度；
- 日志和审计。

调用责任划分：

- Host 管理统一调用治理框架；
- 模块开发者定义 capability / method / schema 等业务契约；
- 调用方开发时对照正式契约接入，运行时由 Host 解析 provider 并转发请求。

默认 provider 解析规则：

- Host 按 capability、语义化版本降序、pluginId 排序 provider；
- `module.resolve` 和未指定 `pluginId` 的 `module.invoke` 会选择 `enabled` 或 `running` 且版本范围匹配的最高语义化版本；
- `module.listProviders` 可按 `status: "enabled" | "running" | "disabled" | "error"` 与 `versionRange` 过滤。
- 按需激活前 provider 状态为 `enabled`，首次真实调用后状态变为 `running`。

## 4. Manifest 规范

模块插件必须提供根目录 `manifest.yaml`，并满足以下正式要求：

```yaml
id: chips.module.example
name: Example Module
version: 0.1.0
type: module
entry: dist/index.mjs
permissions:
  - file.read
runtime:
  targets:
    desktop:
      supported: true
    web:
      supported: false
    mobile:
      supported: false
    headless:
      supported: true
module:
  apiVersion: 1
  runtime: worker
  activation: onDemand
  provides:
    - capability: example.process
      version: 1.0.0
      methods:
        - name: run
          mode: sync
          inputSchema: contracts/run.input.schema.json
          outputSchema: contracts/run.output.schema.json
  consumes:
    - capability: example.normalize
      versionRange: ^1.0.0
```

补充约束：

- `type` 必须为 `module`；
- `entry` 指向 Host 加载的正式模块运行时代码；
- 模块正式能力声明位于 `module.provides`；
- 模块正式依赖声明位于 `module.consumes`；
- 模块通过 `ctx.module.invoke(...)` 调用其他模块 capability 时，目标 capability 必须预先声明在 `module.consumes` 中；调用自身提供的 capability 不需要额外声明；
- 不再把 `capabilities: ["module.xxx"]` 作为模块正式能力契约主入口。

## 5. 工程结构

推荐结构如下：

```text
src/
└─ index.ts
contracts/
├─ <method>.input.schema.json
└─ <method>.output.schema.json
tests/
├─ unit/
└─ integration/
```

官方模块脚手架默认不得生成：

- React 运行时模板；
- `runtime.tsx`；
- 主题 CSS 注入逻辑；
- i18n UI 词典模板；
- `mountModule(container)` 之类页面挂载入口。

生成工程 README 的正式口径必须包含：

- `npm run verify` 与 `chipsdev-r package` 产出 `.cpk` 的打包路径；
- `chipsdev-r module invoke` 作为真实 Host 联调入口；
- `timeoutMs`、`MODULE_TIMEOUT`、`MODULE_SCHEMA_INVALID`、`MODULE_JOB_CANCELLED` 等调用治理语义；
- `module.consumes` 只声明依赖，不自动安装下游 provider，运行期由 Host 校验；
- 禁止创建应用窗口、跨目录 import 模块源码或绕过 Host 直接访问应用私有资源。

## 6. 模块入口设计

模块入口应导出 Host 可加载的模块定义对象，例如：

```ts
export default {
  async activate(ctx) {},
  async deactivate(ctx) {},
  providers: [
    {
      capability: "example.process",
      methods: {
        async run(ctx, input) {
          return { ok: true, input };
        },
      },
    },
  ],
};
```

说明：

- 模块运行时上下文由 Host 注入；
- 模块不得自行构造第二套 Host 通信通道；
- 模块访问 Host 正式服务动作时，应使用 `ctx.host.invoke(...)`；
- 模块调用其他模块时，应继续使用 Host 提供的 `ctx.module.invoke(...)`。

## 6.1 模块运行时上下文

Host 注入给模块方法的正式运行时上下文至少包括以下能力：

- `ctx.host.invoke(action, payload?)`：调用 Host 正式公开的非模块服务动作；
- `ctx.module.invoke(...)`：调用其他模块能力；
- `ctx.module.job.get(jobId)`：查询子模块异步任务状态；
- `ctx.module.job.cancel(jobId)`：取消子模块异步任务；
- `ctx.job.reportProgress(...)`：向 Host 汇报当前模块任务进度；
- `ctx.job.isCancelled()` 与 `ctx.job.signal`：感知上游任务取消。

约束：

- 模块只能使用 Host 注入的正式上下文能力，不得自行 `import` Host 内部实现；
- 需要中间目录、临时文件、子任务轮询或取消联动时，仍然必须走上述正式上下文；
- 模块不得通过 `ctx.host.invoke(...)` 调用 `module.*`，模块能力调用必须继续使用 `ctx.module.*`；
- Host 不再向模块注入 `ctx.services.*` 手写 wrapper；
- 是否具备调用资格仍由 `manifest.yaml` 中的 `permissions` 和 Host 路由权限校验共同决定。
- 模块间 capability 依赖还必须写入 `manifest.yaml` 的 `module.consumes`，Host 会在运行期校验该声明。

转换模块示例：

```ts
const pdf = await ctx.host.invoke("platform.renderHtmlToPdf", {
  htmlDir: htmlOutputDir,
  outputFile: pdfFile,
});

const image = await ctx.host.invoke("platform.renderHtmlToImage", {
  htmlDir: htmlOutputDir,
  outputFile: imageFile,
  options: {
    format: "png",
  },
});
```

说明：

- 目录态 HTML 导出能力由 Host `platform.*` 正式动作承载；
- 模块插件不得直接 `import("electron")` 或私自创建 `BrowserWindow`。

## 6.2 命令行入口声明

模块插件可以在 `manifest.yaml` 中声明 `cli.commands`，用于为 capability + method 提供友好的命令行入口。声明只负责登记命令、参数和目标；真实执行仍必须走 Host `module.invoke / module.job.*`。

```yaml
cli:
  commands:
    - commandPath: icon generate
      target:
        type: module
        capability: converter.icon.generate
        method: generate
        timeoutMs: 60000
      titleKey: icon.cli.generate.title
      descriptionKey: icon.cli.generate.description
      permissions:
        - file.read
        - file.write
      arguments:
        - name: input
          position: 0
          type: path
          required: true
          mapsTo: inputPath
      options:
        - name: formats
          short: f
          type: stringList
          default: [png, ico]
          mapsTo: formats
      job:
        wait: true
        cancelOnInterrupt: true
```

约束：

- `target.type` 必须是 `module`。
- `target.capability` 和 `target.method` 必须指向模块插件正式声明的能力与方法。
- `target.pluginId` 可省略；若写入，必须等于当前插件 `id`。
- `permissions` 中的权限必须已经出现在插件顶层 `permissions` 中。
- CLI 执行器会把参数映射结果作为 `module.invoke.input`，Host 继续负责 provider 解析、schema 校验、权限校验、timeout 和 job 治理。

官方模块脚手架默认在各模板 `manifest.yaml` 中生成 `cli.commands` 示例。命令路径第一段由项目名派生为只含字母、数字和连字符的安全根段，并避开 Host 固定命令根；后续段按模板能力使用 `run / run-async / convert / render / process / colors / execute` 等稳定动作词。模板会按输入 schema 生成位置参数、选项、`mapsTo`、路径/JSON/枚举/布尔/整数校验和 TUI 控件提示，安装启用后由 Host 动态发现，并进入传统 CLI、TUI 和 shell completion 候选，执行仍走 `module.invoke / module.job.*`。

## 6.3 转换链路补充

文件转换系统中的“编排模块”和“原子转换模块”都只是普通模块插件：

- `Chips-FileConversion-Plugin` 属于编排模块；
- `Chips-CardtoHTML-Plugin`、`Chips-HtmltoPDF-Plugin`、`Chips-HtmltoImage-Plugin` 属于原子转换模块；
- 它们统一通过 capability + method 契约接入 Host；
- 编排关系只体现在模块之间的能力调用，不新增新的插件类别或 Host 路由类别。

## 7. SDK 调用示例

```ts
import { createClient } from "chips-sdk";

const client = createClient();

const result = await client.module.invoke({
  capability: "example.process",
  method: "run",
  input: {
    sourcePath: "/workspace/demo.txt",
  },
  timeoutMs: 30000,
});

if (result.mode === "sync") {
  console.log(result.output);
}
```

异步任务示例：

```ts
const started = await client.module.invoke({
  capability: "converter.card.export",
  method: "convert",
  input: {
    cardFile: "/workspace/demo.card",
    targetFormat: "html",
  },
});

if (started.mode === "job") {
  const snapshot = await client.module.job.get(started.jobId);
  console.log(snapshot.job.status);
}
```

补充语义：

- `timeoutMs` 会传给 Host 模块服务，sync 方法超时返回 `MODULE_TIMEOUT`；
- job 方法返回 `jobId` 后仍受该值治理，超时后 job 进入 `failed`，错误码为 `MODULE_TIMEOUT`；
- `client.module.job.cancel(jobId)` 取消运行中 job 后，job 进入 `cancelled`，错误码为 `MODULE_JOB_CANCELLED`。

## 8. 测试策略

模块插件至少应覆盖以下测试层次：

- 单元测试：method 行为、schema 约束、错误归一；
- 集成测试：Host provider 注册、能力调用、任务取消；
- 脚手架测试：生成工程 build/test/validate/package；
- 跨模块调用测试：验证模块依赖和组合路径。

重点门禁：

- 不得留下 TODO、占位实现或未使用的临时代码；
- `manifest.yaml`、`contracts/`、`README`、测试和脚手架模板必须同步更新；
- 模块禁用和卸载必须具备可验证的回收行为。

## 9. 推荐工作流

```bash
chipsdev-r create module Chips-ModulePlugin/my-module
cd Chips-ModulePlugin/my-module
npm install
npm run build
npm test
npm run validate
chipsdev-r package
```

若模块能力依赖真实 Electron 宿主，例如：

- `platform.renderHtmlToPdf`
- `platform.renderHtmlToImage`

则正式联调命令应为：

```bash
chipsdev-r module invoke \
  --capability <capability> \
  --method <method> \
  --input '<json>'
```

约束：

- `chipsdev-r module invoke` 在安装模块前会先执行正式构建；若工程在 `package.json` 中定义了正式 `build` 脚本，则优先以该脚本为准；
- 不要把 `chipsdev-r start` 视为模块 Electron 联调入口；
- `chipsdev-r start/plugin/theme/...` 负责开发工作区管理，不直接替代 capability 调用；
- 依赖 `BrowserWindow` 的模块能力，必须通过 `chipsdev-r module invoke` 收口。

## 10. 最佳实践

- capability 和 method 命名保持稳定；
- 把业务能力 schema 作为正式契约提交到仓库；
- 把外部依赖显式写入 `module.consumes`；
- 模块间调用统一走 Host；
- 每次功能迭代同步更新 README 与测试、契约等运维资料；不再把 `需求文档/`、`技术文档/`（或“技术手册”）与 `开发计划/` 目录当作脚手架的默认产物，而是由各业务仓按需维护，确保模板只输出必要的运行时代码与配置。
