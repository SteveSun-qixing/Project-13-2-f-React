# 资源打开契约

**版本**：1.3.0
**更新时间**：2026-08-29
**状态**：正式版

---

## 1. 文档定位

本文档定义整个生态统一使用的资源打开动作 `resource.open`，用于让应用插件、查看器、复合卡片容器等，把“打开某个资源”的复杂路由统一委托给 Host。

核心原则：

1. 资源打开必须统一走 Host `resource.open`；
2. 调用方不得直接硬编码目标应用插件 ID；
3. 资源处理器发现、优先级匹配、启动参数组装与回退策略都由 Host 负责；
4. 应用开发者只声明能力并处理自己的启动上下文，不处理跨应用路由底层细节。

---

## 2. `resource.open`

### 2.1 请求

```ts
interface ResourceOpenRequest {
  intent?: string;
  resource: {
    resourceId: string;
    mimeType?: string;
    title?: string;
    fileName?: string;
    payload?: Record<string, unknown>;
  };
}
```

字段说明：

1. `intent` 表示打开意图，当前未提供时 Host 默认按 `view` 处理；
2. `resource.resourceId` 是正式资源标识，可为本地文件路径、`file://` URL、Host 托管资源 URL，或其他正式资源 ID；
3. `mimeType`、`title`、`fileName` 是帮助 Host 做更精确路由和更友好展示的可选提示字段。
4. `payload` 是可选的结构化上下文；Host 不解释其业务语义，只在命中正式应用处理器后继续透传。

### 2.2 响应

```ts
interface ResourceOpenResult {
  mode: 'plugin' | 'shell' | 'external';
  pluginId?: string;
  windowId?: string;
  matchedCapability?: string;
  resolved: {
    resourceId: string;
    filePath?: string;
    mimeType?: string;
    extension?: string;
    fileName?: string;
  };
}
```

字段说明：

1. `mode = 'plugin'` 表示 Host 已经找到正式应用插件处理器并完成启动；
2. `mode = 'shell'` 表示没有命中应用插件，Host 回退为系统默认本地路径打开；
3. `mode = 'external'` 表示资源是外部 URL，Host 回退为系统外链打开；
4. `matchedCapability` 仅在 `plugin` 模式下返回，表示最终命中的能力声明；
5. `resolved` 是 Host 已完成归一后的资源视图，供调用方记录日志、调试与诊断。

### 2.3 错误语义

1. 当请求结构不合法时，Host 返回 `SCHEMA_VALIDATION_FAILED` 或 `INVALID_ARGUMENT`；
2. 当资源既没有命中应用处理器，又不能按本地路径或外部链接回退时，Host 返回 `RESOURCE_HANDLER_MISSING`。

## 3. 处理器能力声明

应用插件如果要作为资源处理器，必须在 `manifest.yaml` 的 `capabilities` 中声明：

```yaml
capabilities:
  - resource-handler:view:image/*
```

正式格式：

```txt
resource-handler:<intent>:<mime>[@tier]
file-handler:<ext>[@tier]
```

层级后缀（tier）：

1. 省略后缀表示 `primary`（专用处理器层级）：图片查看器、视频播放器、书籍阅读器等专用查看器使用该层级；
2. `@fallback` 表示 `fallback`（通用兜底层级）：通用文件查看器等兜底应用使用该层级，声明「我也能处理，但优先让专用处理器接管」；
3. 除 `@fallback` 外不允许其他 `@` 后缀，携带未知后缀的声明视为非法能力串，Host 解析时直接忽略。

匹配规则（`resolveHandlerFromRecords` 统一口径，`resource.open`、`association.openPath`、系统文件关联共用）：

1. **用户默认处理器偏好优先**：若 Host 配置 `fileOpen.defaults` 中存在当前请求命中的偏好键（依次检查 `mime:<精确MIME>`、`mime:<主类型>/*`、`ext:<扩展名>`），且偏好指向的插件已启用并声明了任一候选能力，则直接命中该插件；
2. 未命中偏好时，按候选链顺序匹配：精确 MIME 能力（`resource-handler:view:image/png`）→ 主类型通配能力（`resource-handler:view:image/*`）→ 扩展名能力（`file-handler:<ext>`）；
3. 同一候选内，`primary` 层级声明先于 `fallback` 层级声明；同层级内保持插件安装顺序；
4. 偏好指向已停用、已卸载或未声明任何候选能力的插件时，偏好被忽略并进入常规匹配；
5. 当前 `resource.open` 只会把 `type: app` 插件作为正式处理器候选。

Host 对常见资源扩展名会进行 MIME 推断，统一复用 Host/SDK MIME 表。正式内置推断包括图片、媒体、压缩包、电子书，以及 Word/Slide/Sheet/PDF 等办公格式（如 `.doc/.docx/.ppt/.pptx/.xls/.xlsx`）。调用方已知 MIME 时仍应显式传入 `resource.mimeType`，以减少歧义。

补充约束：

1. `resource-handler:*` 主要用于跨应用资源转交；
2. `file-handler:<ext>` 主要用于本地文件扩展名匹配与系统文件关联；
3. 两者可以同时声明，Host 会优先采用 `resource-handler`；
4. `plugin.query({ capability })` 的能力过滤按归一化能力串匹配（剥离层级后缀），因此 `file-handler:.png` 与 `file-handler:.png@fallback` 都能被 `capability: 'file-handler:.png'` 查询命中。

## 4. Host 启动上下文注入

当 Host 通过 `resource.open` 命中应用插件时，启动上下文会统一补充：

```ts
interface ResourceOpenLaunchParams {
  trigger: 'resource-open-service';
  targetPath?: string;
  resourceOpen: {
    intent: string;
    resourceId: string;
    filePath?: string;
    mimeType?: string;
    extension?: string;
    fileName?: string;
    title?: string;
    matchedCapability?: string;
    payload?: Record<string, unknown>;
  };
}
```

正式要求：

1. `resourceOpen` 是当前生态资源打开路由的正式启动参数；
2. 当 Host 能解析出真实本地文件路径时，会继续补充 `targetPath`，用于兼容文件查看器类应用的既有启动恢复逻辑；
3. 资源处理器应用应优先读取 `launchParams.resourceOpen`，并允许把 `targetPath` 作为本地文件查看场景下的兼容回退。
4. 若上游通过 `resource.payload` 传入结构化上下文，Host 必须继续把它透传为 `launchParams.resourceOpen.payload`，不得在 Host 内部裁剪或改写其业务字段。

## 4.5 默认查看器治理（文件打开方式）

生态从架构上支持「像桌面系统一样选择文件的打开方式」：同一文件类型可以有多个已安装的处理器应用，Host 维护每个文件类型的默认处理器，用户平时无需选择，默认处理器自动生效；需要时可在生态设置面板「文件打开方式」页调整。

### 4.5.1 偏好存储

- 配置键：`fileOpen.defaults`（Host 配置服务，user 作用域，`config.get / config.set / config.reset` 直接读写）；
- 值结构：`Record<preferenceKey, pluginId>`；
- `preferenceKey` 两种形式：
  1. `mime:<mime>`：精确 MIME（如 `mime:image/png`）或主类型通配（如 `mime:image/*`）；
  2. `ext:<ext>`：小写带点扩展名（如 `ext:.png`）；
- 解析顺序与第 3 节匹配规则一致：精确 MIME 偏好 → 通配 MIME 偏好 → 扩展名偏好。

### 4.5.2 处理器槽位查询：`plugin.listHandlers`

- 动作：`plugin.listHandlers`；权限：`plugin.read`；幂等；超时 3s；
- 请求：`{}`（无参数）；
- 响应：

```ts
interface FileHandlerSlot {
  capability: string;            // 归一化能力串（无层级后缀）
  kind: 'resource-handler' | 'file-handler';
  intent?: string;               // 仅 resource-handler
  mimeType?: string;             // 仅 resource-handler
  extension?: string;            // 仅 file-handler
  preferenceKey: string;         // 该槽位写入 fileOpen.defaults 的偏好键
  preferencePluginId: string | null;  // 偏好键上的原始偏好（可能指向已停用插件）
  defaultPluginId: string | null;     // 当前生效默认：有效偏好优先，否则按层级与安装序
  plugins: Array<{
    pluginId: string;
    name?: string;
    tier: 'primary' | 'fallback';
    isPreferred: boolean;
  }>;
}
```

- `plugins` 顺序：用户首选在前，`primary` 先于 `fallback`，同级按安装顺序；
- 生态设置面板「文件打开方式」页是该接口的正式治理 UI，可修改/清除偏好并整体恢复默认。

## 5. 复合卡片与查看器容器

涉及卡片、复合 iframe 或其他嵌入式资源容器时，正式要求如下：

1. 基础卡片节点只表达“我想打开一个资源”的意图，不直接启动其他应用；
2. 容器应用在收到资源打开事件后，应调用 `client.resource.open(...)` 或 `window.chips.invoke('resource.open', ...)`；
3. 卡片查看器、箱子查看器、未来的富媒体查看器都必须复用同一条资源打开路由，不得各自硬编码图片查看器、PDF 查看器等目标插件。
4. Host 注入的单卡查看态运行时负责基于当前资源基准 URL 归一基础卡片传入的相对资源标识；导出的社区 Web HTML 即使把卡片根资源基准改写为相对 URL，也必须在单卡文档运行时按当前文档 URL 得到可访问的绝对 `resource.resourceId`。

编辑引擎编辑态本地基础卡片运行时同样遵守该规则：

1. `BasecardFrameHost` 注入基础卡片查看态 `openResource(...)` 可选回调；
2. 若基础卡片传入相对资源标识，编辑引擎先基于当前 `.card` 根目录运行时 URL 归一为正式 `resource.resourceId`；
3. `CompositeCardAssembler` 只补充 `cardId/baseCardId/cardType` 等容器上下文；
4. `CardWindow` 统一调用 `client.resource.open({ intent: "view", resource })`；
5. 编辑引擎不得在基础卡片 iframe 内暴露 Host Bridge，也不得按卡片类型硬编码目标应用插件。

## 6. 典型链路示例

“卡片查看器点击图片 -> 图片查看器打开”的正式链路如下：

1. 基础卡片节点发出资源打开意图；
2. 卡片查看器接收到该意图后调用 `resource.open`；
3. Host 根据 `resource-handler:view:image/*` 解析出图片查看器；
4. Host 启动图片查看器，并通过 `launchParams.resourceOpen` / `targetPath` 传入资源；
5. 图片查看器恢复到对应图片查看状态。

补充：

1. 当上游不仅要“打开某个资源”，还要让目标应用恢复结构化业务上下文时，应把该上下文放入 `resource.payload`；
2. 当前“音乐基础卡片 -> 音乐播放器”正式使用该能力，把音乐卡片配置、已解析的音频/封面/歌词资源描述符一并透传到 `launchParams.resourceOpen.payload`；
3. 当前“视频基础卡片 -> 视频播放器”正式使用 `chips.video-card` payload，把视频、封面、字幕与播放入口参数作为结构化上下文透传；
4. 当前“电子书基础卡片 -> 书籍阅读器/图片查看器”正式使用 `chips.book-card` payload；
5. 当前“文件基础卡片 -> 任意资源处理器 / 系统打开”以无 payload 的 `resource.open` 表达纯打开意图：`resourceId` 为卡片根目录相对文件路径，`mimeType` 由插件按后缀推断，`fileName` 为含后缀的完整文件名；Host 负责按资源处理器能力与扩展名推断路由，未命中应用处理器时回退系统默认打开方式；
6. “通用文件查看器兜底链路”是本契约的正式组成部分：万能文件查看器（`com.chips.universal-file-viewer`）以 `@fallback` 层级声明全部其引擎支持的格式，专用查看器已安装且启用时优先接管，未安装或被停用时由万能文件查看器兜底预览；用户也可通过 `fileOpen.defaults` 强制指定任一处理器为默认；
7. Host 负责路由与透传，不负责解释这类业务级 payload 的内部语义。

## 7. 音乐基础卡片 Payload

音乐基础卡片通过 `resource.open` 向音乐播放器传递结构化上下文。Host 只透传该对象，不参与业务解释。

```ts
interface MusicCardOpenTeamRole {
  id: string;
  role: string;
  people: string[];
}

interface MusicCardOpenResource {
  resourceId: string;
  relativePath: string;
  fileName?: string;
  mimeType?: string;
}

interface MusicCardOpenPayload {
  kind: 'chips.music-card';
  version: '1.0.0';
  cardType: 'base.music';
  config: {
    card_type: 'MusicCard';
    theme?: string;
    audio_file: string;
    music_name: string;
    album_cover: string;
    lyrics_file: string;
    production_team: MusicCardOpenTeamRole[];
    release_date: string;
    album_name: string;
    language: string;
    genre: string;
  };
  resources: {
    audio: MusicCardOpenResource;
    cover?: MusicCardOpenResource;
    lyrics?: MusicCardOpenResource;
  };
  display: {
    title: string;
    artist: string;
  };
}
```

正式消费规则：

1. `resources.audio.resourceId` 是音乐播放器实际读取的主音频资源；调用 `resource.open` 时，主资源也必须指向同一音频资源。
2. `resources.cover` 与 `resources.lyrics` 是可选补充资源；音乐播放器应优先使用 payload 中的封面、歌词和展示标题，再回退到嵌入元数据与伴生文件发现。
3. `relativePath` 是卡片内部相对路径，目标应用可用于日志、匹配和用户可读文件名恢复。
4. `display.title / display.artist` 是播放器首屏展示上下文；若缺少嵌入元数据，不应丢失音乐基础卡片中已填写的标题和歌手。
5. 目标应用不得要求上游硬编码自身插件 ID，也不得绕过 `resource.open` 私传音乐卡片上下文。

## 8. 电子书基础卡片 Payload

电子书基础卡片通过 `resource.open` 向阅读器或图片查看器传递结构化上下文。Host 只透传该对象，不参与业务解释。

```ts
interface BookCardOpenResource {
  resourceId: string;
  relativePath: string;
  fileName?: string;
  mimeType?: string;
}

interface BookCardOpenPayload {
  kind: 'chips.book-card';
  version: '1.0.0';
  cardType: 'base.book';
  mode: 'ebook' | 'image-sequence';
  resources: {
    book?: BookCardOpenResource;
    images?: BookCardOpenResource[];
  };
  display: {
    title: string;
    author?: string;
  };
}
```

正式消费规则：

1. `mode = 'ebook'` 时，书籍阅读器应使用顶层 `launchParams.resourceOpen.filePath/resourceId` 作为实际读取入口，并用 `resources.book` 与 `display.title/author` 恢复书籍上下文；
2. `mode = 'image-sequence'` 时，图片查看器应按 `resources.images[]` 的顺序建立图片队列，并用当前 `resourceOpen.resourceId` 或首项作为初始索引；
3. 基础卡片发起打开意图时，`resources.*.resourceId` 与 `relativePath` 应保存卡片根目录相对资源路径；Host 或外层容器会把顶层 `resourceOpen.resourceId` 归一为目标应用可实际读取的正式资源标识。目标应用不得只依赖 payload 内的主资源 `resourceId` 读取文件。
4. 电子书基础卡片点击图片包时，主资源必须是序列中的第一张图片；完整序列必须放在 `payload.resources.images[]` 中；
5. 目标应用不得要求上游硬编码自身插件 ID，也不得绕过 `resource.open` 私传图包或书籍上下文。

## 9. 视频基础卡片 Payload

视频基础卡片通过 `resource.open` 向视频播放器或其他视频资源处理器传递结构化上下文。Host 只透传该对象，不参与业务解释。

```ts
interface VideoCardOpenResource {
  resourceId: string;
  relativePath: string;
  fileName?: string;
  mimeType?: string;
}

interface VideoCardOpenSubtitleResource extends VideoCardOpenResource {
  id: string;
  label?: string;
  language?: string;
  kind: 'subtitles' | 'captions';
  default?: boolean;
}

interface VideoCardOpenPayload {
  kind: 'chips.video-card';
  version: '1.0.0';
  cardType: 'base.video';
  config: {
    card_type: 'VideoCard';
    theme?: string;
    video_file: string;
    cover_image: string;
    subtitles: Array<{
      id: string;
      label: string;
      language: string;
      kind: 'subtitles' | 'captions';
      file_path: string;
      default: boolean;
    }>;
    playback: {
      autoplay: boolean;
      loop: boolean;
      muted: boolean;
      playback_rate: number;
      start_time: number;
    };
    video_title: string;
    publish_time: string;
    creator: string;
  };
  resources: {
    video: VideoCardOpenResource;
    cover?: VideoCardOpenResource;
    subtitles?: VideoCardOpenSubtitleResource[];
  };
  display: {
    title: string;
    creator?: string;
    publishTime?: string;
  };
  playback: {
    autoplay: boolean;
    loop: boolean;
    muted: boolean;
    playbackRate: number;
    startTime: number;
  };
}
```

正式消费规则：

1. `resources.video.resourceId` 是视频播放器实际读取的主视频资源；调用 `resource.open` 时，主资源也必须指向同一视频资源；
2. `resources.cover` 与 `resources.subtitles` 是可选补充资源；视频播放器可优先使用 payload 中的标题、封面、字幕和播放入口参数，再回退到视频文件自身元数据；
3. `relativePath` 是卡片内部相对路径，目标应用可用于日志、匹配和用户可读文件名恢复；
4. `playback.startTime`、`playback.playbackRate`、`autoplay`、`loop`、`muted` 只是打开入口期望，目标应用应按自身能力和用户策略安全消费；
5. 目标应用不得要求上游硬编码自身插件 ID，也不得绕过 `resource.open` 私传视频卡片上下文。

## 10. 与万能文件处理链路的关系

### 10.1 链路定位

`resource.open` 与万能文件处理链路（`file.*`）是互补关系：

| 链路 | 定位 | 核心场景 |
|---|---|---|
| `resource.open` | 资源打开路由 | 跨应用资源转交、文件关联、系统默认打开 |
| `file.session.*` | 文件会话管理 | 文件的完整生命周期管理、编辑、版本控制 |
| `file.preview.*` | 文件预览生成 | 生成预览图、缩略图 |
| `file.convert.*` | 格式转换 | 文件格式互转、批量转换 |

### 10.2 能力声明对应

万能文件处理链路使用扩展的 `file-handler` 能力声明格式：

```yaml
# 资源打开路由（使用 resource-handler）
capabilities:
  - resource-handler:view:image/*

# 万能文件处理链路（使用扩展 file-handler）
capabilities:
  - file-handler:view:image/*
  - file-handler:edit:image/*
  - file-handler:preview:image/*
  - file-handler:convert:image/*->image/png
```

详细协议定义见《15-万能文件处理协议.md》。

### 10.3 选择原则

1. **资源打开**：使用 `resource.open`，由 Host 统一路由到合适的应用处理器
2. **文件编辑**：使用 `file.session.*`，获得完整的会话管理和版本控制能力
3. **格式转换**：使用 `file.convert.*`，获得统一的转换编排能力
4. **预览生成**：使用 `file.preview.*`，获得统一的预览生成能力
