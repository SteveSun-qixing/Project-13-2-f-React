# 模块插件脚手架功能需求规格

> 文档状态：已按模块插件重构实现更新

## 1. 模板管理

- 脚手架必须支持枚举可用模板。
- 每个模板必须声明 `id/name/description/version`。
- 模板可声明 `extends`、`excludeFiles` 与 `moduleShape`，用于复用公共工程骨架并覆盖形态差异。
- 模板可声明是否集成 SDK，以及是否仍依赖 React、主题系统、多语言系统。
- 模板缺少 `template.json` 或元数据非法时，必须阻断创建。

## 2. 工程创建

- 创建参数至少包含 `projectName/targetDir/templateId/pluginId/moduleCapability/displayName/version`。
- 创建参数可包含 `moduleConsumes`，用于渲染 `manifest.module.consumes`。
- 目标目录已存在且非空时必须拒绝覆盖。
- 文本模板文件按占位符渲染，非文本文件按原样复制。
- 父模板文件先进入渲染集合，子模板可通过 `excludeFiles` 移除父模板文件，并用同路径文件覆盖父模板。
- `template.json` 只作为模板元数据，不得进入生成工程。
- 创建结果必须返回工程目录、模板 ID 和生成文件数。

## 3. 标准模板 `module-standard`

- 必须生成：
  - `.eslintrc.cjs`
  - `.gitignore`
  - `README.md`
  - `chips.config.mjs`
  - `manifest.yaml`
  - `package.json`
  - `tsconfig.json`
  - `vitest.config.mts`
  - `contracts/run.input.schema.json`
  - `contracts/run.output.schema.json`
  - `contracts/runAsync.input.schema.json`
  - `contracts/runAsync.output.schema.json`
  - `src/index.ts`
  - `tests/unit/module-definition.test.ts`
- 模板生成的 `manifest.yaml` 必须默认符合 `type: module`、`entry: dist/index.mjs`、`module.apiVersion/runtime/activation/provides/consumes`。
- 模板必须默认提供一个 capability。
- 模板必须默认提供一个同步方法示例和一个异步 job 方法示例。
- 模板必须让方法实现和 schema 文件一一对应。
- 模板不得再生成 React 运行时、页面挂载逻辑、主题/i18n UI 示例。

## 4. 模板矩阵

脚手架必须至少提供以下模块模板：

- `module-standard`：通用 capability 模块，提供 `run` 同步方法与 `runAsync` job 方法。
- `module-pure-function`：纯函数同步处理模板，适合文本、配置和元数据归一。
- `module-file-conversion`：文件输入输出 job 模板，默认声明 `file.read/file.write` 并通过 Host 文件动作治理输入、输出和覆盖。
- `module-html-rendering`：目录态 HTML 渲染导出 job 模板，默认声明 `platform.read/file.read/file.write`，通过 `platform.renderHtmlToPdf/renderHtmlToImage` 调用 Host 渲染能力。
- `module-image-processing`：图像读取与轻量分析同步模板，默认只依赖 Host 文件读取能力。
- `module-color-extraction`：颜色提取同步模板，输出 `backgroundColor/accentColor`。
- `module-orchestration`：模块编排 job 模板，默认声明 `module.read/module.invoke`，通过 `ctx.module.invoke/job.*` 调用下游能力。

各模板必须生成与自身方法匹配的 schema、manifest、源码和单测。

## 5. CLI 集成

- `chipsdev-r create module <targetDir>` 必须可用。
- CLI 必须自动推导 `projectName/pluginId/moduleCapability`。
- CLI 必须默认选择 `module-standard`。
- CLI 必须支持 `--template <id>` 或 `--template=<id>` 选择模块模板。
- CLI 必须支持 `--plugin-id <id>`、`--capability <capability>` 覆盖默认推导值。
- CLI 必须支持一个或多个 `--consumes <capability>` / `--consumes <capability>@<versionRange>`，写入 `manifest.module.consumes`。
- 当目标位于生态工作区中时，CLI 必须自动注册 workspace 并写入 `volta.extends`。
- 模板或脚手架无效时，CLI 必须输出可诊断错误。

## 6. 生成工程验证

- 默认生成工程必须通过：
  - `npm run lint`
  - `npm run typecheck`
  - `npm test`
  - `npm run build`
  - `npm run validate`
  - `npm run package`
  - `npm run verify`
- 生成出的 `.cpk` 必须能够被 Host 安装、启用并通过 `module.invoke` 正常调用。
- 生成工程 README 必须提供 `chipsdev-r module invoke` 联调示例，并说明 CLI 会先构建、安装、启用 `.cpk`，再通过 Host `module.invoke` 调用能力。
- 生成工程 README 必须说明 `timeoutMs`、`MODULE_TIMEOUT`、`MODULE_SCHEMA_INVALID`、`MODULE_JOB_CANCELLED` 与 `module.consumes` 运行期校验。

## 7. 文档要求

- 模板 README 必须说明工程定位、目录结构、capability/method/schema 用法和正式约束。
- 所有模板 README 必须说明 `.cpk` 打包、Host 联调命令和禁止跨目录 import 模块源码。
- `module-orchestration` README 必须说明 `--consumes` 只写入依赖声明，不自动安装下游 provider；运行期由 Host 校验 `module.consumes`。
- 根 README 必须作为脚手架维护入口，说明模板矩阵、创建命令、生成工程验证、Host 联调和维护门禁。
- 若模板目录结构、CLI 行为或验证链路发生变化，必须同步更新本仓文档。
