# 05-完整下载与文件回收链路

## 当前状态

当前社区服务端已经保存 source.card，但公共 API 契约明确说明“社区内 .card 回下载”不在当前范围内。

也就是说：

- 存储层已经有可用于下载或重建缓存的对象：chips-card-files/{userId}/{cardId}/source.card；
- 数据库也有源文件 bucket/key/hash；
- 但还没有正式的下载 HTTP API；
- 前台也没有稳定的“下载完整卡片”入口；
- CardViewer Web chrome 里的下载动作还没有和社区源文件下载闭环绑定。

## 下载应该返回什么

下载不能返回网页查看缓存。理想情况下，下载应该返回用户原始完整 .card；如果当前数据只有 source.card，就必须先确认它是原始完整包还是发布处理包。

原因：

- 原始完整 .card 保留 metadata、structure、content、封面和内部资源；
- 发布处理 .card 也保留卡片结构，但资源可能已经改成 CDN/publicUrl；
- 网页 HTML 缓存只是消费产物，丢失了很多编辑语义；
- 从 HTML 反向合成 .card 会制造第二套转换标准，非常危险；
- source.card 的 SHA-256 已经在 sourceCardSha256 中记录，适合作为该对象的完整性依据，但不等于证明它是原始完整离线包。

## 推荐下载接口

建议新增：

    GET /api/v1/cards/:cardId/source-card

行为：

- 先走 CardService.getAccessible(cardId, requesterId)；
- 检查下载权限策略；
- 找到 sourceCardBucket/sourceCardKey；
- 流式读取对象存储；
- 返回：

    Content-Type: application/vnd.chips.card+zip
    Content-Disposition: attachment; filename*=UTF-8''<safe-title>.card
    Accept-Ranges: bytes
    ETag: "<sourceCardSha256 或对象 etag>"

如果文件比较大，需要支持 Range 或者返回短期签名下载 URL，避免 API 进程长时间中转。

## 公开卡片和私有卡片的差异

公开卡片：

- 可以允许匿名下载，前提是作者允许下载；
- 也可以只允许登录下载，这属于产品策略；
- 大文件最好直接 302 到对象存储短期签名 URL，主站不承担流量。

私有卡片：

- 必须鉴权；
- 不应该暴露永久公开 URL；
- 推荐 API 鉴权后生成短期签名 GET URL，或由 API 流式代理；
- 如果对象存储不方便签名 GET，就通过 API 代理，但要限制并发和速率。

## 是否需要重新整合资源

有两种情况。

### 情况 A：下载保存的 source.card

这是首选。无需重新整合，直接下载即可。

只要上传阶段保存的是“原始完整 .card”，下载回来的文件就是完整离线卡片。

如果上传阶段保存的是“发布处理 .card”，下载回来仍可能是正式 .card，但它依赖外部资源 URL，不应该被宣传成原始完整离线包。

### 情况 B：上传时把资源外置到 CDN

桌面社区上传模块当前会把资源上传到 chips-card-resources，然后把卡片里的资源路径改成 publicUrl，再删除内部资源并重新打包 processed.card。服务器保存的就是这个 processed.card。

这种文件下载回来仍然是一个正式 .card，但它不一定是“全填充卡片”：资源可能依赖公网 URL。

如果用户期待“离线也完整”，那还需要一个额外能力：

    下载离线完整包
      -> 服务器或本地软件读取 source.card
      -> 把外部资源抓回卡片内部
      -> 改写 URL 为内部相对路径
      -> 重新 pack

这个能力比较重，不建议放在弱服务器热路径里。更好的方式是本地软件提供“下载并离线化”或“另存为全填充卡片”。

## 删除和资源回收

当前 CardService.delete(...) 已经会删除：

- chips-card-resources 里相关资源；
- resourceManifest 里记录的外置资源；
- chips-card-files 源 .card；
- view/cover 公开与私有缓存；
- 旧 covers 路径；
- 数据库记录。

这说明删除链路已经考虑到源文件和缓存分离。后续补下载时不要把下载链接设计成永久可访问的公开源文件 URL，否则删除和权限变更会失控。

## 体验上的下载入口

建议至少有三个入口：

1. 卡片详情页按钮：下载完整卡片；
2. CardViewer Web chrome 动作：下载；
3. 作者管理列表：下载 / 重新生成缓存 / 删除。

用户不需要知道源文件、缓存、CDN。按钮文案就叫“下载卡片”或“保存卡片文件”。
