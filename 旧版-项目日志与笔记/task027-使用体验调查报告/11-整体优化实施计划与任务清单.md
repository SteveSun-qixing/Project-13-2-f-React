# 卡片上传、网页查看与客户端下载开发计划

> 修订时间：2026-08-05  
> 文档性质：task027 的全生态开发计划。本文按最新决策重写：浏览器只负责网页查看；上传和下载必须在薯片客户端中完成；网络资源卡片是正式卡片类型，不是社区内部临时产物。  
> 目标体验：用户在电脑或手机客户端中制作卡片，上传到社区后网页可以直接查看；需要下载完整卡片时，必须在安装了薯片生态相关插件的客户端里完成下载、资源恢复和打包。

## 1. 最新决策

- [x] 浏览器没有上传 .card 的功能。
- [x] 浏览器没有下载 .card 的功能。
- [x] 浏览器只有查看能力：打开社区页面，查看已经发布好的卡片内容。
- [x] 上传、下载、客户端查看入口统一由用户设备上的客户端模块负责。
- [x] 客户端中的各种应用插件都通过这个统一模块调用上传、查看和下载能力，不各自实现一套社区文件链路。
- [x] “空壳卡片”改名并正式定义为“网络资源卡片”：它是正常 .card 文件类型，不是社区内部发布产物。
- [x] 网络资源卡片内部保留 .card/metadata.yaml、.card/structure.yaml、.card/cover.html 和 content/*.yaml 等配置与封面文件；除配置和封面本体外，所有资源都以对象存储或 CDN URL 形式写在卡片配置中，不再保存本地资源文件。
- [x] 用户上传到社区时，客户端把原始卡片中的本地相对资源路径改写为对象存储 URL。
- [x] 用户从客户端下载安装到本地时，客户端必须根据恢复清单把对象存储 URL 还原为原始卡片根相对路径，并把资源重新放回原路径。
- [x] 最终下载得到的卡片应尽可能与用户上传前的卡片完全一致：路径、配置内容、资源字节、ZIP Store 条目顺序、条目时间和修改时间都不能改变。
- [x] .card ZIP 使用 Store 模式，只打包不压缩。
- [x] 不设置人为的“最大卡片安全上限”；只保留真实技术边界、平台能力边界、对象存储限制和反恶意文件保护。
- [x] 卡片文件本身不实现权限管理；公开、私有、身份、授权等属于社区身份和内容管理系统，当前文件链路计划不处理。
- [x] 可以适当使用第三方库，但必须经过技术选型、许可证、维护状态、包体、安全和跨端兼容性评估。

## 2. 最终用户体验

### 2.1 客户端上传

1. 用户在电脑或手机上的薯片客户端中制作并保存完整 .card。
2. 用户点击“发布到社区”，或由某个应用插件调用统一上传模块。
3. 客户端读取完整 .card，枚举内部资源。
4. 客户端把资源直接上传到对象存储。
5. 客户端把卡片配置中的本地相对资源路径改写成对象存储 URL，生成网络资源卡片。
6. 客户端把网络资源卡片上传到对象存储，并向社区 API 提交卡片信息、对象位置和可逆恢复清单。
7. 社区后台生成网页查看缓存。
8. 用户得到社区卡片页面地址。

用户看到的体验仍然是“选择卡片 -> 发布 -> 得到网页地址”，不接触对象存储、恢复清单、URL 改写和缓存生成。

### 2.2 浏览器查看

1. 用户打开社区网页。
2. 网页加载已经生成好的查看缓存，或用 Web CardViewer 查看网络资源卡片。
3. 图片、音频、视频、书籍等资源通过卡片中的对象存储/CDN URL 加载。
4. 浏览器页面不提供上传入口。
5. 浏览器页面不提供下载 .card 文件入口。
6. 如果用户想保存完整卡片，网页只提示“请在薯片客户端中打开并下载”或提供客户端深链。

### 2.3 客户端下载

1. 用户在薯片客户端的卡片查看器或其他正式插件中打开社区卡片。
2. 用户点击“下载卡片”。
3. 客户端向社区 API 获取下载计划和恢复清单。
4. 客户端下载网络资源卡片和所有对象存储资源。
5. 客户端把卡片配置中的对象存储 URL 还原为上传前的卡片根相对路径。
6. 客户端按原路径恢复资源文件。
7. 客户端按原 ZIP Store 条目信息重新打包为完整 .card。
8. 下载得到的 .card 可以离线打开、继续编辑，并尽量保持和上传前一致。

## 3. 核心架构

目标链路：

用户设备完整 .card
-> 统一卡片传输模块
-> 资源直传对象存储
-> 生成网络资源卡片
-> 生成可逆恢复清单
-> 网络资源卡片和资源保存到对象存储/CDN
-> 社区 API 保存元数据和恢复清单
-> Worker 生成网页查看缓存
-> 浏览器只查看
-> 客户端按恢复清单下载并恢复完整 .card

关键边界：

- 浏览器只消费社区页面和查看缓存，不承担上传、下载、打包、解包。
- 客户端统一模块是上传、下载和客户端查看入口的唯一正式文件链路。
- API 服务器只做控制面：鉴权、会话、签名、元数据、恢复清单、状态和任务调度。
- 文件字节全部走对象存储/CDN，弱服务器不做长期文件保存，也不承担大文件转发。
- 网络资源卡片是正式 .card 类型，里面写 URL；完整离线卡片也是正式 .card 类型，里面写相对路径和内置资源。

## 4. 卡片类型定义

### 4.1 完整离线卡片

完整离线卡片是用户制作、编辑、备份和本地保存时最常见的卡片形态。

特征：

- 资源文件保存在 .card ZIP 内部；
- 配置文件里记录卡片根相对路径；
- 不依赖网络即可查看和编辑；
- 适合本地备份、离线分享和继续编辑。

### 4.2 网络资源卡片

网络资源卡片是正常 .card 文件类型，不是社区临时产物。

特征：

- .card 中保留配置文件、结构文件、元数据和封面 HTML；
- 资源文件不放在 ZIP 内；
- 配置文件中的资源字段记录对象存储/CDN URL；
- 必须依赖网络资源才能完整查看；
- 适合社区发布、网页查看和弱服务器分发。

### 4.3 可逆恢复要求

因为上传会把相对路径改写成 URL，下载时又要还原为原始路径，所以必须保存“可逆恢复清单”。

恢复清单至少需要记录：

- 原始卡片版本 ID；
- 网络资源卡片对象位置；
- 每个资源的原始相对路径；
- 每个资源上传后的对象键；
- 每个资源写入网络资源卡片后的 URL；
- 每个配置文件中发生过的路径替换位置或可验证替换规则；
- 原始 ZIP 条目顺序；
- 原始 ZIP 条目 Store 模式；
- 原始 ZIP 条目修改时间；
- 原始 ZIP 条目外部属性、注释和必要 extra fields；
- 原始资源文件名、大小和 MIME；
- 封面资源的原始引用和 URL 替换关系。

如果要求下载后的 ZIP 包在归档层面也尽量保持一致，不能只保存“文件名”。必须保存足够的 ZIP 条目元数据，让客户端重新打包时复原条目顺序、时间和 Store 模式。

## 5. 对象存储与数据库模型

### 5.1 对象存储布局

建议每张卡片、每个版本独立目录：

- cards/{cardId}/versions/{versionId}/network-card/card.card
- cards/{cardId}/versions/{versionId}/resources/{resourceObjectName}
- cards/{cardId}/versions/{versionId}/render/{renderProfileId}/index.html
- cards/{cardId}/versions/{versionId}/cover/{renderProfileId}/index.html

说明：

- network-card/card.card 是网络资源卡片，内部资源字段已经改写为对象存储/CDN URL。
- resources/ 保存从原始完整卡片中拆出来的资源文件。
- render/ 保存网页查看缓存。
- cover/ 保存封面查看缓存。
- 对象存储保存全部文件，API 服务器不保存任何长期文件。

### 5.2 数据库职责

数据库只保存索引、状态和恢复信息。

建议表：

cards：

- id
- ownerId
- activeVersionId
- 标题、简介、社区展示信息
- 创建时间、更新时间

card_versions：

- id
- cardId
- status
- networkCardBucket
- networkCardObjectKey
- networkCardSizeBytes
- resourceCount
- totalResourceBytes
- createdAt
- readyAt
- failedReason

card_version_resources：

- cardVersionId
- originalRelativePath
- networkUrl
- bucket
- objectKey
- sizeBytes
- mimeType
- originalEntryModifiedTime
- originalEntryExternalAttributes
- originalEntryExtraFields
- originalEntryComment
- 唯一约束：cardVersionId + originalRelativePath

card_restore_manifests：

- cardVersionId
- 原始 ZIP 条目顺序；
- 原始 ZIP 条目元数据；
- 配置文件路径替换映射；
- URL 到原始相对路径的恢复映射；
- 封面引用恢复映射；
- 恢复清单版本。

恢复清单可以放数据库，也可以作为小型 JSON 文件放对象存储、数据库保存 object key。选择时以事务一致性、查询频率和大小为准。

### 5.3 不保存的内容

不要保存：

- 用户本机绝对路径；
- 临时签名 URL；
- 浏览器 blob URL；
- Host 临时文件 URL；
- 可过期的本地缓存路径；
- 卡片文件内部权限字段；
- 只为旧链路保留的 source.card 双重语义。

- [x] P0-03 明确完整离线卡片使用相对路径和内置资源；网络资源卡片使用对象存储/CDN URL 和外部资源。

### 阶段 1：建设客户端统一卡片传输模块

目标：所有客户端应用插件都接入同一个模块，不再各自处理上传、下载、查看。

建议能力：

- community.card.transfer.upload(cardFile)
- community.card.transfer.openRemote(cardId 或 url)
- community.card.transfer.download(cardId 或 versionId, outputPath)
- community.card.transfer.getStatus(taskId)
- community.card.transfer.cancel(taskId)

任务：

- [x] P1-01 定义模块 manifest、能力名、输入输出 schema、错误码和任务事件。
- [x] P1-02 支持 Desktop Host。
- [x] P1-03 支持 Mobile Host/PAL。
- [x] P1-04 不支持 Web 浏览器运行时；浏览器不加载该模块。
- [x] P1-05 SDK 只提供类型化封装和调用入口，不承载上传下载主实现。
- [x] P1-06 CardViewer、EditingEngine 和其他应用插件通过该模块调用发布、打开社区卡片和下载。
- [x] P1-07 模块统一处理进度、取消、重试、断网恢复、对象签名刷新和错误状态。
- [x] P1-08 模块统一处理对象存储 URL 改写和下载恢复，禁止插件自行替换 YAML 或 HTML。
- [x] P1-09 模块所有 UI 文案走多语言系统，界面走主题系统和组件库。
- [x] P1-10 对第三方库建立依赖评审记录：用途、替代方案、许可证、维护状态、包体、安全风险和跨端支持。

阶段完成标准：客户端中任何需要上传、查看社区卡片、下载卡片的插件，都只依赖统一模块，不直接写社区上传下载逻辑。

### 阶段 2：实现无压缩归档读取、改写和恢复核心

目标：客户端可以从完整离线卡片生成网络资源卡片，也可以从网络资源卡片恢复完整离线卡片。

- [x] P2-01 读取 .card ZIP Store 条目，保留条目顺序、路径、修改时间、extra fields、注释和外部属性。
- [x] P2-02 校验 .card 是否使用 Store 模式；发现压缩条目时按规范转换或提示格式不符合要求。
- [x] P2-03 枚举需要外置的资源文件，包括根目录资源和封面资源。
- [x] P2-04 保留 .card/metadata.yaml、.card/structure.yaml、.card/cover.html 和 content/*.yaml。
- [x] P2-05 将配置文件中的相对资源路径精确替换为对象存储 URL。
- [x] P2-06 为每个替换写入恢复清单，确保下载时可以把 URL 还原为原始相对路径。
- [x] P2-07 生成网络资源卡片时不压缩，只使用 ZIP Store 模式。
- [x] P2-08 恢复完整离线卡片时，把资源文件写回原始相对路径。
- [x] P2-09 恢复完整离线卡片时，把配置文件中的 URL 改回原始相对路径。
- [x] P2-10 恢复 ZIP 时尽量复原原始条目顺序、条目时间、Store 模式和可保存的 ZIP 元数据。
- [x] P2-11 不为了业务一致性强制计算 SHA-256；ZIP 格式自身需要的 CRC32 正常保留。
- [x] P2-12 支持大文件流式处理，不把整张卡片或全部资源一次性放进内存。
- [x] P2-13 允许适当引入成熟 ZIP/流式处理第三方库，但必须通过阶段 1 的依赖评审。
- [x] P2-14 建立黄金回环测试：完整离线卡片 -> 网络资源卡片 + 资源 + 恢复清单 -> 完整离线卡片。
- [x] P2-15 黄金回环至少比较文件路径、配置内容、资源字节、条目顺序和条目时间。

阶段完成标准：同一张完整离线卡片经过上传转换和下载恢复后，能通过正式 Host 打开、渲染和继续编辑，并满足恢复一致性测试。

- GET /api/v1/cards/:cardId/open-view
- GET /api/v1/cards/:cardId/render-status
- POST /api/v1/card-transfer/download-sessions
- GET /api/v1/card-transfer/download-sessions/:id/plan
- POST /api/v1/card-transfer/download-sessions/:id/refresh

- [x] P3-03 complete 接口提交网络资源卡片对象位置、资源对象位置和恢复清单。
- [x] P3-04 API 校验对象键归属、卡片版本、资源数量和恢复清单结构。
- [x] P3-05 API 不接收 multipart .card。
- [x] P3-06 API 不代理资源、网络资源卡片、查看缓存或下载文件字节。

- [x] P3-09 下载计划返回网络资源卡片对象位置、资源对象位置和恢复清单。
- [x] P3-10 卡片文件本身不处理公开/私有/权限字段；接口只保留社区系统基本登录和内容归属所需的外层控制。

阶段完成标准：只有客户端模块能完成上传和下载；网页端没有上传下载 API 调用路径。

- [x] P4-06 客户端生成网络资源卡片并直传对象存储。

## 8. 关键技术风险

### 8.1 URL 改写必须可逆

上传时把相对路径改写成对象存储 URL，会改变配置文件内容。若下载要完全恢复，必须保存精确的替换映射。只保存文件名不够，因为多个目录可能有同名文件，配置中也可能有相同字符串出现在非资源字段。

### 8.2 ZIP 时间和条目元数据需要专门保存

如果要求下载后连 ZIP 条目修改时间都不变，归档核心必须读取并保存原始 ZIP 条目元数据。普通“重新打包目录”的方法会改变时间、顺序或 extra fields，不能满足本目标。

### 8.3 网络资源卡片是正式格式，不是缓存

网络资源卡片可以长期保存和被查看器直接打开。因此所有基础卡片插件必须正式支持 URL 资源，不应该把 URL 当作社区临时补丁。

### 8.4 浏览器不能偷偷补上传下载

网页端一旦保留隐藏上传、下载或打包能力，体验和架构又会分叉。浏览器只查看这一条必须从 UI、API 调用、SDK 能力声明和测试中同时约束。

### 8.5 不设置人为上限不等于不做安全校验

不设置最大卡片安全上限，意思是不把格式人为限制为 500MB 或某个固定值。但实现仍必须防 ZIP bomb、路径穿越、磁盘写满、对象存储滥用和异常条目。限制应来自真实平台能力和安全防护，而不是产品上的随意上限。

## 9. 现在应先做什么

第一批只做这几件事：

1. 修订公共规范：确认完整离线卡片、网络资源卡片、恢复清单、浏览器只查看、客户端上传下载的正式口径。
2. 修改 AGENTS 规则：允许在充分评估后适当使用第三方库。
3. 设计统一客户端卡片传输模块：明确能力名、调用方、Desktop/Mobile 支持和 Web 不支持。
4. 做一个黄金回环原型：完整离线卡片 -> 网络资源卡片 + 对象资源 + 恢复清单 -> 完整离线卡片。
5. 用黄金回环验证 ZIP Store 条目顺序、修改时间、配置内容和资源字节是否能恢复。
6. 再改社区 API 和对象存储模型，让服务端只保存控制面数据。
7. 最后接入 CardViewer Web 查看和客户端 CardViewer 下载。

只要黄金回环没有证明“改 URL 后仍能恢复原始卡片”，就不要大规模改 UI。这个回环是整个新方案最核心的技术前提。
