# 07-用户交互逻辑逐步推敲

## 用户心智

用户最好只理解一个东西：卡片文件。

不要让用户理解这些词：

- 资源外置；
- 预签名 URL；
- render cache；
- Headless Host；
- Web 插件宿主；
- bucket；
- CDN；
- source.card；
- processed.card。

用户看到的应该是：

    制作卡片
      -> 保存卡片文件
      -> 上传到社区
      -> 生成网页
      -> 分享链接
      -> 下载卡片文件

底层再复杂，也要包装成“像发图片一样发布”的体验。

## 本地软件里的发布入口

本地软件可以有两个入口：

- 保存：保存到本机 .card；
- 发布到社区：把当前卡片上传到社区。

“发布到社区”里不要出现太多选项。最多是：

- 标题；
- 简短描述；
- 标签；
- 公开 / 私密；
- 是否允许下载；
- 发布按钮。

真正的复杂动作由 CommunityUploader 模块做：

    读取 .card
      -> 检查卡片信息
      -> 扫描资源
      -> 上传大资源
      -> 重新打包发布态 .card
      -> 提交社区
      -> 等待网页生成

进度条文案可以很生活化：

- 正在检查卡片；
- 正在整理资源；
- 正在上传资源；
- 正在生成发布文件；
- 正在提交到社区；
- 正在生成网页查看；
- 发布完成。

不要显示“正在 presign resources”“正在 rewrite YAML”这类技术文案。

## 网页拖拽上传入口

网页端也应该支持拖 .card 上传，因为这是最接近“发微博/发图片”的入口。

推荐流程：

    用户拖入 .card
      -> 前端检查扩展名和大小
      -> 创建上传会话
      -> 上传文件
      -> 服务端检查结构
      -> 显示卡片封面/标题
      -> 后台生成网页查看
      -> 自动跳到卡片详情页

网页端可以不做完整资源外置，因为这会让浏览器链路复杂很多。第一版网页上传只要能稳定处理“完整自包含 .card”即可。

但用户看不懂“自包含”这个词，所以错误提示要换成人话：

- 这个卡片里有缺失的本地资源，请回到薯片客户端重新保存后再上传；
- 这个卡片太大，建议使用薯片客户端发布；
- 这个卡片使用了网页暂不支持的插件，已上传但暂时不能在线查看；
- 文件不是有效的卡片文件。

## 上传后的状态页

上传成功后，不要让用户留在一个空白等待页。

卡片详情页应该立即出现：

- 封面或占位封面；
- 标题；
- 作者；
- 上传时间；
- 当前状态；
- 分享链接；
- 下载按钮状态；
- 如果网页查看未生成，显示“网页查看正在生成”；
- 如果生成失败，显示“重新生成网页查看”。

这很重要。用户上传后最怕的是“我到底发出去没有”。哪怕网页查看还在排队，也要先告诉用户“卡片已经保存成功”。

## 网页查看入口

用户点击“查看”时，应该有三种体验：

### 已生成

直接打开 CardViewer Web 页面。

用户不应该感知到 open-view、plugin session、iframe、viewUrl。地址栏可以是社区卡片 URL 或专门查看 URL，但体验上就是“打开卡片”。

### 生成中

显示轻量状态：

    卡片网页查看正在生成
    通常需要几秒钟，文件较大时会更久
    [稍后自动刷新] [返回详情] [下载卡片文件]

这里可以继续提供下载，因为源 .card 已保存，不一定要等 HTML 缓存生成。

### 生成失败

不要只显示失败。至少告诉用户是哪一类：

- 卡片文件损坏；
- 缺少基础卡片插件；
- 某个资源无法读取；
- 渲染超时；
- 服务器繁忙；
- 权限策略阻止。

作者本人可以看到更详细的诊断；普通访客只看到简洁失败提示。

## 资源点击体验

卡片里可能包含图片、音乐、视频、书籍、网页等资源。网页查看时点击资源，用户预期是“继续在网页里打开”，而不是下载一堆不明文件。

目标体验：

- 图片打开 PhotoViewer Web；
- 音乐打开 MusicPlayer Web；
- 视频打开 VideoPlayer Web；
- 电子书打开 BookReader Web；
- 网页链接打开新标签；
- 不支持的资源给出下载或复制链接。

这里的关键不是 UI，而是 Web 插件宿主能力要完整。资源打开链路需要从基础卡片 iframe 一直传到 HostedPluginSurface，再创建对应应用插件 session。

## 下载完整卡片的交互

下载按钮应该很直白：

- 下载卡片文件；
- 文件名是卡片标题.card；
- 浏览器按普通文件下载；
- 下载后可以用薯片客户端打开或继续编辑。

几个状态要处理好：

- 作者允许下载：按钮可用；
- 作者禁止下载：显示“作者未开放下载”；
- 私有卡片无权限：显示“没有下载权限”；
- 源文件还在保存：显示“文件准备中”；
- 源文件丢失：显示“源文件异常，无法下载”；
- 网页查看失败但源文件存在：仍然可以下载；
- 网页查看成功但源文件异常：必须提示不能下载，不能从 HTML 缓存临时拼。

从体验上，下载和查看应该是两个独立按钮：

- 查看：打开网页体验；
- 下载：拿回完整 .card。

不要把“打开网页查看”误叫成下载，也不要把“下载 HTML”误叫成下载卡片。

这里还要决定一个用户可见口径：如果下载的是发布处理包，而不是原始离线完整包，页面是否仍叫“完整卡片文件”。我更倾向最终同时保存原始完整包和发布处理包，下载默认返回原始完整包；如果历史卡片只有处理包，就要显示为“下载发布版卡片文件”，不要偷换概念。

## 编辑体验边界

用户提出“网页端可以实现所有查看体验，但是编辑还是需要安装软件”，这个边界非常正确。

网页端不要承诺完整编辑。否则会引出大量问题：

- 浏览器文件系统权限不稳定；
- 大资源导入和本地持久化复杂；
- 基础卡片编辑器运行时能力不一定齐全；
- 离线编辑、增量保存、资源清理都要重做；
- 手机浏览器上编辑复杂卡片体验也不一定好。

网页端可以提供：

- 查看；
- 播放；
- 打开资源；
- 下载；
- 分享；
- 收藏；
- 评论；
- 举报；
- 复制链接。

编辑入口可以显示为：

    用薯片客户端打开编辑
    未安装？下载客户端

如果未来做轻量网页编辑，也应该是另一个明确项目，不要混进当前“查看 + 下载”闭环里。

## 移动端体验

手机上重点是“能打开、能看、能保存”。

需要注意：

- CardViewer Web 必须适配窄屏；
- 资源播放器必须适配触摸；
- 大图/视频不要一次性撑爆内存；
- 下载 .card 后，iOS/Android 的文件打开方式要有引导；
- 如果移动端没有薯片客户端，就提示“已保存文件，可在电脑或安装客户端后打开”；
- 分享链接打开时不要强制跳 App。

移动端编辑暂时不要承诺。移动端只要能顺滑查看和下载，就已经满足大部分分享场景。

## 零感知的关键

用户零感知不是底层没规则，而是规则不让用户背。

可以让系统自动做：

- 自动判断走桌面发布链路还是网页直传链路；
- 自动外置大资源；
- 自动生成网页缓存；
- 自动选择公开 CDN 或私有代理；
- 自动在失败时给出可理解原因；
- 自动保留源 .card；
- 自动给下载文件命名。

不要让用户手动做：

- 选择资源是否外置；
- 选择上传到哪个 bucket；
- 选择是否生成 HTML；
- 选择是否重新打包；
- 选择渲染版本；
- 复制技术 URL。

用户只做内容决策：发什么、给谁看、让不让下载。
