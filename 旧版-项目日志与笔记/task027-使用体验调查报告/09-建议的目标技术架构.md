# 09-建议的目标技术架构

## 一句话架构

建议把社区卡片平台拆成五层：

    本地创作层
      -> 发布上传层
      -> 源文件保存层
      -> 异步网页生成层
      -> Web 查看与下载层

其中 .card 是完整文件真相，网页 HTML 是派生产物。

更准确一点，后续最好区分两种 .card：

- original.card：用户原始完整包，服务于回下载、备份、迁移和离线编辑；
- publish.card：发布处理包，资源可外置，服务于网页查看缓存生成和公开访问性能。

如果只保存一份，就必须先决定它到底是哪一种，不能同时假装两者都是。

## 目标链路

理想链路是：

    用户在客户端制作卡片
      -> 导出或保存 .card
      -> 点击发布到社区
      -> 客户端整理资源并上传
      -> 社区保存 original.card
      -> 社区保存或生成 publish.card
      -> 社区 worker 生成 view/cover 缓存
      -> 浏览器通过 CardViewer Web 查看
      -> 用户从网页下载 original.card
      -> 本地客户端重新打开编辑

网页上传作为补充入口：

    用户拖 .card 到网页
      -> 网页基础检查
      -> 直接上传 original.card
      -> 社区保存源文件
      -> 必要时生成 publish.card
      -> worker 生成缓存
      -> 浏览器查看和下载

这两条链路在用户心智上都叫“上传卡片”，只是技术实现不同。

## 不建议的架构

不建议浏览器直接承担完整 .card 解析和渲染。

原因：

- 浏览器端解包、校验、插件分发、资源路径重写都要重做；
- 复杂卡片会占用大量内存；
- 基础卡片插件和 Host 运行时能力不一定完整；
- 手机浏览器体验难控制；
- 安全边界更复杂。

也不建议服务器请求时实时渲染。

原因：

- 弱服务器扛不住；
- 用户每次打开都触发重计算；
- Host 启动和插件渲染容易导致延迟抖动；
- 失败会直接变成页面不可用。

最稳的是：服务器异步生成静态查看缓存，浏览器加载缓存，CardViewer Web 提供统一查看壳。

## 核心组件分工

### 本地客户端 / 编辑器

职责：

- 创建和编辑目录态 .card；
- 管理资源导入、删除和路径；
- 导出归档态 .card；
- 调用 CommunityUploader 发布；
- 对大资源做外置和发布态重新打包；
- 给用户显示简单发布进度。

不应该做：

- 让用户手工管理 bucket；
- 让用户手工改资源 URL；
- 让用户理解 source.card 和 processed.card。

### CommunityUploader 模块

职责：

- 读取正式 .card；
- 使用 Host/SDK 的 card.readInfo、card.unpack、card.pack；
- 扫描资源；
- 调社区创建 upload session；
- 申请资源预签名 URL；
- 直传资源；
- 改写资源引用；
- 提交发布态 .card；
- 返回社区 cardId 和 URL。

这是弱服务器体验的关键模块。

但如果目标强调“完整回下载”，CommunityUploader 还需要配合新契约：上传 original.card 到私有源文件仓库，同时提交 publish.card 给网页发布链路，或者由服务端/worker 基于 original.card 生成 publish.card。否则回下载的语义会一直模糊。

### 社区 API

职责：

- 用户鉴权；
- 上传会话；
- 预签名上传；
- 提交 original.card / publish.card；
- 保存元数据和源文件位置；
- 入队 view/cover render；
- 提供 open-view、render-status；
- 提供 source-card 下载入口；
- 提供 resource-open-plan 和 Web 插件 session；
- 控制公开、私有、下载权限。

API 不应该实时渲染卡片，也不应该长期承载公开静态文件流量。

### 对象存储 / CDN

职责：

- 保存 original.card；
- 保存 publish.card；
- 保存外置资源；
- 保存 view HTML 缓存；
- 保存 cover 缓存；
- 承载公开访问流量；
- 支持签名下载；
- 支持 Range 和正确 MIME。

对象存储是文件层，数据库是索引层，API 是权限层。

### Render Worker

职责：

- 从队列拿任务；
- 下载 publish.card 或 original.card；
- 调 Headless Host 和 CardtoHTML；
- 上传 view cache；
- 生成 cover cache；
- 更新 render 状态；
- 重试失败任务；
- 记录可读失败原因。

Worker 可以很慢，但必须稳定、可重试、可观测。

### Web 插件宿主

职责：

- 创建 com.chips.card-viewer session；
- 注入 theme.css、bootstrap.js；
- 提供 window.chips Web 实现；
- 处理 resource.open；
- 打开 PhotoViewer、MusicPlayer、VideoPlayer、BookReader 等插件；
- 控制 iframe sandbox。

它是“网页看起来像本地查看器”的关键。

## 建议补齐的 API

### 源文件下载

建议新增：

    GET /api/v1/cards/:cardId/source-card

行为：

- 鉴权和权限判断；
- 检查 originalCardBucket/originalCardKey，或当前阶段的 sourceCardBucket/sourceCardKey；
- 检查作者是否允许下载；
- 记录下载事件；
- 返回短期签名 URL 或流式响应；
- 设置正确文件名和 MIME。

这是工单121的核心之一。

### 源文件直传

建议上传会话扩展出 source-card 预签名能力：

    POST /api/v1/upload-sessions/:uploadId/source-card/presign
      -> 客户端 PUT original.card
      -> POST /api/v1/upload-sessions/:uploadId/source-card/complete

这样弱服务器不需要通过 multipart 接收大 .card，再转存对象存储。

如果还要提交 publish.card，可以有两种设计：

- 客户端同时直传 original.card 和 publish.card；
- 客户端只直传 original.card，worker 负责生成 publish.card 和 view cache。

第一种更省服务器计算，第二种更统一但更吃 worker。

### 下载策略字段

卡片记录或发布配置里建议有：

- allowDownload：是否允许下载；
- downloadVisibility：匿名、登录、仅自己、按分享链接；
- originalCardBucket；
- originalCardKey；
- originalCardSha256；
- originalCardSizeBytes；
- publishCardBucket；
- publishCardKey；
- publishCardSha256；
- sourceCardFilename；
- sourceCardContentType；
- sourceCardStoredAt。

部分字段已有类似信息，后续实现时应以现有 schema 为准，不要重复散落。

### 渲染重建

建议有：

    POST /api/v1/cards/:cardId/render-cache/rebuild

仅作者或管理员可用。

用于：

- renderer 升级后重建；
- 主题升级后重建；
- 上次渲染失败后重试；
- 对象存储缓存丢失后恢复。

### 私有资源访问

如果支持私有卡片外置资源，需要正式契约：

- 资源对象是否有 visibility；
- 私有资源是否走 signed URL；
- HTML 缓存中如何引用私有资源；
- 签名 URL 过期后 viewer 如何刷新；
- resource.readBinary 如何走权限。

第一版可以先避免私有外置资源，但不能误把公开资源 bucket 当作所有场景通用方案。

## 数据保存建议

每张社区卡片至少分三类数据：

### 1. 源文件数据

- originalCardBucket；
- originalCardKey；
- originalCardSha256；
- originalCardSizeBytes；
- originalCardStoredAt；
- originalCardFilename；
- originalCardContentType。

这是下载和完整离线回收的基础。

### 2. 发布和展示缓存数据

- publishCardBucket；
- publishCardKey；
- publishCardSha256；
- viewCacheBucket；
- viewCacheKeyPrefix；
- viewEntryUrl；
- viewStatus；
- viewCacheVersion；
- coverCacheBucket；
- coverEntryUrl；
- renderErrorCode；
- renderErrorMessage；
- renderedAt。

这是网页查看的基础。

### 3. 产品权限数据

- visibility；
- allowDownload；
- ownerId；
- sharePolicy；
- moderationState；
- deletedAt；
- downloadCount。

这是社区体验和安全的基础。

## 公开卡片资源策略

公开卡片可以走最高性能路径：

    资源 public bucket
      + view cache public bucket
      + cover cache public bucket
      + CDN

这样打开体验最好，服务器压力最低。

下载原始完整 .card 仍建议从 API 入口走一次权限策略，再签名到对象存储，因为下载行为是产品行为，不只是静态资源访问。

## 私有卡片资源策略

私有卡片建议不要把内容资源写到永久 publicUrl。

可选方案：

1. 私有卡片不做资源外置，original.card 自包含，view cache 进入 private bucket；
2. 私有资源上传到 private resource bucket，网页访问走短期签名 URL；
3. 私有资源统一由 API 代理，但只适合低并发；
4. 私有 CDN + 签名 Cookie，适合以后规模变大。

第一版如果选择 1，要在桌面发布模块和网页上传中明确限制，不要让私有卡片无声变成公开资源。

## 缓存版本策略

view cache 的版本建议至少包含：

- publishCardSha256 或 originalCardSha256；
- renderer version；
- CardtoHTML plugin version；
- Host render profile；
- themeId；
- locale；
- 可能影响输出的插件版本摘要。

这样同一张卡片内容不变时可以复用缓存，内容或渲染环境变化时能生成新路径。

缓存 key 最好版本化，而不是覆盖固定路径：

    cards/{cardId}/view/{cacheVersion}/index.html

这样 CDN 不需要立即全局刷新，旧链接也不容易突然坏。

## 用户侧最简规则

最终给用户的规则应该只有：

- 上传 .card；
- 等待网页生成；
- 分享链接；
- 网页可以查看；
- 下载 .card 后用客户端编辑。

所有技术规则都藏在系统里。

如果一个规则必须让用户理解，它很可能还没设计好。
