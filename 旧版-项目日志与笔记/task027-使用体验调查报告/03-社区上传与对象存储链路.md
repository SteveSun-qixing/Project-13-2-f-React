# 03-社区上传与对象存储链路

## 现在社区有两条上传链路

当前代码里能看到两条卡片上传路径。

第一条是正式主链路：上传会话。

    POST /api/v1/upload-sessions
      -> POST /api/v1/upload-sessions/:uploadId/resources/presign
      -> 客户端 PUT 资源到对象存储
      -> POST /api/v1/upload-sessions/:uploadId/card

第二条是过渡链路：

    POST /api/v1/upload/card
      -> multipart 直接提交 .card

公共 API 契约已经明确：正式主链路是上传会话；旧浏览器直传入口只是过渡 API。

## 桌面社区上传模块做了什么

Chips-CommunityUploader-Plugin 是一个模块插件，能力是 community.card.publish。它只支持 desktop/headless，不支持 web。

它的链路很明确：

    读取本地 .card
      -> card.readInfo
      -> card.unpack
      -> 扫描非结构文件资源
      -> 创建 upload session
      -> 为资源申请预签名 URL
      -> 直接 PUT 资源到对象存储
      -> 把 content/*.yaml 和 cover.html 里的资源路径改成 publicUrl
      -> 删除已外置资源
      -> card.pack 重新打包 processed.card
      -> 提交 processed.card 到社区

这条链路对弱服务器非常友好，因为最重的“扫描、改写、重新打包”和大资源上传都在用户设备上完成。服务器只做会话、校验、保存发布处理包、排队渲染。

但这也带来一个回下载语义问题：processed.card 已经把部分资源改成 publicUrl，并删除了内部资源。它适合网页发布和缓存生成，但不一定等同于用户最初保存的完整离线 .card。这个缺口已在工单121里登记。

## 网页上传现在做了什么

社区网页 cardsApi.uploadCard(...) 当前会：

    创建 upload session
      -> FormData 直接提交原始 .card
      -> manifest 里 resources: []

也就是说，网页端当前没有执行桌面模块插件那套“资源外置、URL 改写、重新打包”。它更像一个用户方便入口：拖 .card 上去，服务器接住源文件并生成查看缓存。

这不是坏事，但要承认边界：

- 如果 .card 内部本来包含所有资源，网页上传可以正常形成完整源文件；
- 如果 .card 里引用了本地绝对路径或缺资源，服务器不可能凭空找到用户电脑里的资源；
- 如果卡片很大，网页直传会压服务器 API 流量；正式大文件体验还是应该由桌面模块插件走预签名直传。

## 服务端提交阶段做了什么

POST /api/v1/upload-sessions/:uploadId/card 会：

1. 校验上传会话归属、过期时间、内容类型；
2. verifyResources 对已预签名资源做对象存储 Head 校验；
3. inspectCardSourceFile 检查 .card 源文件，读取标题、卡片 ID、封面比例、metadata、structure、内容与资源；
4. 如果存在外置资源，会检查处理后的 .card 不再包含这些资源文件，并且全部引用对应 publicUrl；
5. 创建数据库卡片记录；
6. 把 .card 上传到私有 bucket chips-card-files，key 是 {userId}/{cardId}/source.card；
7. 写入 sourceCardBucket/sourceCardKey/sourceCardSha256/sourceCardStoredAt；
8. 入队生成 view 缓存和 cover 缓存。

这条链路是目标体验的基础，因为它至少保留了一份可追溯 .card。但后续要实现“完整离线回下载”，还需要确认 source.card 是原始完整包，还是发布处理包；如果是后者，应新增 original.card 保存位。

## 对象存储 bucket 分工

当前 bucket 设计是：

    chips-card-resources              公开读，外置资源
    chips-card-files                  私有，永久 .card 源文件
    chips-card-render-cache           公开读，公开卡片查看 HTML 缓存
    chips-card-render-cache-private   私有，私有卡片查看 HTML 缓存
    chips-card-cover-cache            公开读，公开封面缓存
    chips-card-cover-cache-private    私有，私有封面缓存

这个分工是合理的：

- 源 .card 不能默认公开，避免绕过权限和下载策略；
- 公开卡片的网页查看缓存可以公开读/CDN 化；
- 私有卡片的缓存必须走 API 权限代理；
- 外置资源如果进入 chips-card-resources，当前设计是公开读，因此私有卡片若要严格保护资源，就不能把敏感资源放到公开资源 bucket，或者必须增加私有资源 bucket/签名 URL 策略。

## CDN / 图床应该谁来上传

推荐策略：

- 桌面软件正式发布：用户设备向社区请求预签名 URL，然后用户设备直接 PUT 到对象存储/CDN 源站；
- 网页上传小文件：可以直接上传 .card 到 API，让服务器保存源文件；
- 网页上传大资源：不要走 API 中转，应该未来补一个 Web 侧资源预签名链路，浏览器直传对象存储；
- 服务端只在生成渲染缓存时上传 HTML/CSS/JS/封面缓存到对象存储。

也就是说，不建议“用户直接上传到第三方图床”。用户不应该感知图床、bucket、URL 改写这些概念。应由社区服务器签发上传计划，用户设备按计划上传，最后服务器校验和登记。
