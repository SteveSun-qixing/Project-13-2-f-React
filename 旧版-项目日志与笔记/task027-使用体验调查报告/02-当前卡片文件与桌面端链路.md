# 02-当前卡片文件与桌面端链路

## .card 文件现在是什么

当前正式定义里，.card 是一个 ZIP Store 归档文件。Store 的意思是零压缩，优先访问速度和实现简单度，不把已经压缩过的图片/视频/音频再压一遍。

目录结构大概是：

    Some.card
    ├── .card/
    │   ├── metadata.yaml
    │   ├── structure.yaml
    │   ├── cover.html
    │   └── cardcover/
    ├── content/
    │   └── <baseCardId>.yaml
    └── 资源文件

几个关键点：

- .card/metadata.yaml 保存卡片 ID、名称、主题、封面比例、标签等；
- .card/structure.yaml 保存基础卡片顺序和资源 manifest；
- .card/cover.html 是封面正式入口；
- content/*.yaml 是每个基础卡片自己的内容配置；
- 内部资源路径必须从卡片根目录开始记相对路径；
- 不能把 /Users/...、C:\\...、file://、blob:、Host 临时 URL 写进正式卡片配置。

## 目录态与归档态

现在有两个形态：

1. 目录态：编辑引擎工作时直接读写的 Some.card/ 文件夹；
2. 归档态：导出、分享、上传、下载时使用的单个 .card 文件。

这个设计很适合目标体验：编辑时保持可修改，发布时变成一个用户能理解的文件。

## 桌面编辑链路

编辑引擎的正式链路大致是：

    创建/打开目录态 .card
      -> CardService 读取 metadata/structure/content
      -> 基础卡片编辑器通过 renderBasecardEditor 输出配置
      -> 编辑引擎资源桥 import/resolve/delete/release 管理资源
      -> CardService.persistCard 写回 content/*.yaml 和资源
      -> 导出时 Host/SDK card.pack 生成归档态 .card

这条链路里的关键是：资源生命周期由宿主统一管，基础卡片插件不应该自己拼文件系统路径。这样导出的 .card 才能跨电脑、跨平台、跨网页环境继续使用。

## 桌面查看链路

通用查看态正式走 Host 托管渲染：

    应用传入 .card 文件
      -> Host card.render 校验和解析
      -> Host 按 structure[].type 找基础卡片插件
      -> Host 给每个基础卡片生成 iframe 文档
      -> Host 拼成复合卡片文档
      -> SDK compositeWindow.render 把 documentUrl 挂进 iframe
      -> session 结束后 releaseRenderSession

封面是另一条独立链路：

    Host card.renderCover
      -> 读取 .card/cover.html
      -> 返回受控 coverUrl
      -> SDK coverFrame.render 挂载 iframe

这对社区网页很重要：网页端要么复用 Host 产出的显示结果，要么复用 CardtoHTML 转换出来的显示缓存。不能让社区前台自己重写一套基础卡片分发器。

## 当前已实现的 Host/SDK 能力

代码里已经有这些 API：

- card.pack(cardDir, outputPath)
- card.unpack(cardFile, outputDir)
- card.readMetadata(cardFile)
- card.readInfo(cardFile, fields?)
- card.parse(cardFile)
- card.validate(cardFile)
- card.render(cardFile, options?)
- card.renderCover(cardFile)
- card.releaseRenderSession(sessionId)
- card.compositeWindow.render(...)
- card.coverFrame.render(...)

这些能力已经能支撑“本地软件编辑/导出/查看”的核心闭环。

## 对网页端的启发

网页端不应该直接把 .card 解包后到处拼 DOM。更好的策略是：

- 网页查看读的是社区已经生成好的 community-web HTML 缓存；
- 原版 CardViewer Web 插件负责外层查看器体验；
- .card 源文件必须单独保存，用于下载、重新渲染、未来迁移；如果发布链路会生成 processed.card，还要区分原始完整包和发布处理包；
- 如果未来要网页端轻量预览上传文件，可以只做本地结构预检和封面预览，不做完整编辑。
