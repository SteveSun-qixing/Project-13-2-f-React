# 08-漏洞与风险清单

## 先说最大的漏洞

当前最大漏洞不是技术上不能网页查看，而是体验闭环没有完整契约。

上传源 .card 已经保存，网页查看缓存也已经有主链路，但“从网页下载完整 .card”还没有正式 API、权限策略和前端入口。这个缺口已登记为工单121-社区卡片完整回下载与源文件直传契约缺口。

更细一点说，工单121还指出另一个关键语义：当前桌面发布模块保存到服务器的 source.card 可能是资源已外置、URL 已改写的发布处理包，不一定是用户最初本地保存的完整离线包。如果目标是“像 Word 文档一样下载回来仍完整离线可编辑”，就要同时设计原始完整包和发布处理包的边界。

## 源文件与网页缓存混淆风险

风险等级：高。

网页查看缓存是 HTML 消费产物，源 .card 是正式文件。两者不能混用。

容易出错的做法：

- 让下载按钮下载 render-cache/index.html；
- 从 HTML 缓存反向拼装 .card；
- 上传后只保留 HTML，不保留源 .card；
- 删除源文件时还让详情页显示“可下载”。

正确做法：

- source.card 或 original.card 才是下载依据；
- render-cache 只用于网页查看；
- 数据库里分清 sourceCard 状态和 renderCache 状态；
- 前端分别显示“查看状态”和“下载状态”。

## 原始完整包与发布处理包混淆风险

风险等级：高。

这点是本轮最容易被忽略的技术细节。

桌面 CommunityUploader 当前会：

    解包用户 .card
      -> 上传资源到对象存储
      -> 把资源路径改成 publicUrl
      -> 删除已外置资源
      -> 重新打包 processed.card
      -> 提交到社区

所以服务器保存的 source.card 更像“发布处理包”。它可以用于网页渲染，也可能可以被客户端打开，但它不一定是完整离线包。

如果用户下载后断网打开，卡片里的 CDN 资源可能不可用。那就和“像 Word 文档一样完整保存”不完全一致。

建议最终明确两份文件：

- original.card：用户原始完整包，用于回下载、备份、迁移、离线编辑；
- publish.card：资源外置后的发布包，用于网页查看缓存生成和公开访问优化。

第一版如果暂时只保存一份，也必须在产品文案和技术契约里说清楚它是哪一种。

## 私有卡片资源公开风险

风险等级：高。

当前桌面发布模块会把扫描到的大资源上传到 chips-card-resources，并拿到 publicUrl，再把卡片内容里的资源路径改写成公开 URL。这对公开卡片很合理，但对私有卡片可能有风险。

如果一个私有卡片的图片、音频、视频资源被外置到公开 bucket，卡片详情本身虽然有权限控制，但资源 URL 可能被直接访问。

需要补清楚：

- 公开卡片可以用公开资源 bucket；
- 私有卡片是否禁止资源外置到公开 bucket；
- 私有卡片是否应该使用 private resources bucket；
- 私有资源在网页查看缓存里如何签名或代理；
- 从私有改公开、从公开改私有时资源权限如何迁移；
- 删除卡片时外置资源如何回收。

如果第一版不处理私有资源外置，至少要限制：私有卡片只能上传自包含 .card，或明确禁止外置资源公开化。

## 网页上传缺少资源整理风险

风险等级：中高。

桌面发布模块会扫描、外置、改写、重新打包。网页上传当前只是提交原始 .card，manifest 里 resources 为空。

这会带来几种情况：

- 自包含 .card：可以正常；
- 内部缺资源：服务器无法补；
- 引用了本地绝对路径：服务器无法访问；
- 大文件 .card：API 压力变大；
- 资源数量很多：服务端检查和 worker 渲染压力变大。

建议：

- 网页上传先定位为中小型自包含 .card 上传；
- 上传前做基础大小检查；
- 服务端检查发现本地路径、file://、blob:、缺资源时直接给清晰错误；
- 大卡片提示使用桌面客户端发布；
- 以后再考虑浏览器端解包检查，但不要把完整发布处理强塞进第一版网页上传。

## 渲染缓存失败后的用户体验风险

风险等级：中高。

当前链路有 render_pending、cache_ready、render_failed 一类状态基础，但用户体验需要继续细化。

必须避免：

- 上传后只显示转圈；
- render 失败后详情页死掉；
- 公开页打不开但没有下载入口；
- 作者看不到失败原因；
- 普通访客看到内部错误堆栈。

更稳的策略：

- 源文件保存成功和网页查看生成成功分开显示；
- 查看失败不影响下载源 .card；
- 作者有“重新生成网页查看”；
- 失败原因分级展示；
- 缓存生成慢时显示排队状态。

## Web 插件宿主能力不完整风险

风险等级：中高。

网页端要实现“本地查看器一样的查看体验”，核心是 CardViewer 和各类资源应用插件能在 Web Host Runtime 里跑。

已处理过的相关缺口包括：

- 工单119：Web 插件宿主辅助资源读取能力缺口；
- 工单120：Web 插件宿主缺少主题 CSS 与图标字体注入。

后续仍要小心：

- resource.open 是否覆盖所有资源类型；
- resource.readBinary/readMetadata 是否处理远端和缓存资源；
- theme/i18n 是否和桌面一致；
- plugin session 生命周期是否能回收；
- iframe sandbox 是否既安全又不阻断插件需要的能力；
- 移动浏览器上音视频自动播放、文件下载、弹窗策略是否会拦。

如果这些不稳定，用户会觉得“网页能打开，但不像本地查看器”。

## 服务器热路径过重风险

风险等级：高。

弱服务器最怕三件事：

- 上传大文件都经过 API；
- 每次查看都实时渲染；
- 每次下载都由 API 整包中转。

当前渲染缓存方向是对的，但还要继续守住边界：

- 查看只读缓存，不实时 render；
- worker 并发有限；
- 大资源直传对象存储；
- 下载源 .card 用签名 URL 或流式代理；
- API 不把大对象读进内存。

如果后续为了快临时把“打开页面时生成 HTML”写进路由，就会直接破坏低性能部署目标。

## 插件版本与缓存版本漂移风险

风险等级：中。

网页查看缓存是用某个 renderer version、主题、locale、源文件 hash 生成的。如果插件升级或主题升级，旧缓存可能和最新运行时不一致。

需要明确：

- cacheVersion 里包含哪些因素；
- 插件升级后是否批量重建缓存；
- 主题升级后是否重建；
- 用户看到的是发布时效果还是最新渲染效果；
- 私有卡片是否也自动重建；
- 重建失败时是否保留旧缓存。

从用户角度，最好是“已经发布的卡片稳定可看”，后台可以按需重建，但不要因为插件升级让旧链接突然坏掉。

## 源文件完整性风险

风险等级：高。

下载回来的 .card 必须还能打开编辑，否则整个文件体验会崩。

需要检查：

- sourceCardSha256 是否在保存后校验；
- 下载时 ETag/hash 是否可对上；
- 保存 source.card 失败时是否禁止创建可见卡片；
- 数据库有 sourceCardKey 但对象存储丢失时如何显示；
- 删除卡片是否删除 source.card；
- 重新发布同一卡片时旧 source.card 如何归档或覆盖；
- 下载的是原始上传文件还是 processed.card，这个口径必须明确。

这里还有一个产品问题：如果桌面发布模块外置资源并重新打包 processed.card，那么保存为 source.card 的其实是“发布态 .card”，不是用户最初本地那份原始文件。这个没问题，但文案要叫“下载发布版卡片文件”；如果文案叫“完整离线卡片文件”，就必须另存原始完整包。

## 安全风险

风险等级：高。

.card 内包含 cover.html，网页查看缓存也包含 HTML。必须小心：

- cover.html 是否能执行脚本；
- HTML 缓存里是否有恶意内联脚本；
- iframe sandbox 是否限制足够；
- 资源 URL 是否可能 SSRF 或读取内网；
- 卡片里是否能写 file://、blob:、本地绝对路径；
- 外部 URL 是否需要白名单或安全策略；
- 下载文件名是否会注入响应头；
- 私有资源 URL 是否泄漏给匿名用户；
- 插件入口和主题资源是否只能从受控目录读取。

原则是：.card 是用户上传内容，不应该被当成可信代码。

## 对象存储和 CDN 配置风险

风险等级：中高。

对象存储配置如果不稳，问题会很隐蔽：

- HTML 被设置成 attachment，导致 iframe 下载而不是渲染；
- MIME 类型错误；
- CORS 不允许 Web 插件读取资源；
- Range 不支持，音视频拖动失败；
- CDN 缓存旧版本；
- 私有缓存被公开；
- 公开缓存没有 cache purge 或版本化路径。

建议所有缓存都使用带版本的 key，不依赖覆盖同一个 index.html 后立刻全网刷新。

## 下载权限策略风险

风险等级：中高。

“公开可看”不一定等于“公开可下载”。

需要早一点决定：

- 作者能否禁止下载；
- 禁止下载是否还允许网页查看；
- 匿名用户能否下载公开卡片；
- 私有卡片分享链接是否允许下载；
- 下载是否需要登录；
- 下载是否计数；
- 下载是否进入审计；
- 被举报或下架卡片是否还能下载。

如果这些不先抽象成正式字段和统一检查，后面会散落在页面按钮、API 路由和对象存储签名逻辑里。

## 删除与回收风险

风险等级：中。

一个社区卡片至少可能关联：

- original.card 或 source.card；
- publish.card；
- 外置资源；
- view render cache；
- cover cache；
- 私有缓存；
- 数据库记录；
- 评论/收藏/统计；
- 下载日志。

删除时需要明确：

- 软删除还是硬删除；
- 源文件是否立即删除；
- CDN 缓存是否失效；
- 外置资源是否有引用计数；
- 多张卡片引用同一资源时能否删除；
- 删除失败是否重试。

弱服务器下，删除也应该异步化：先标记不可见，再后台清理对象存储。

## 需要避免的错误方向

- 不要把网页端完整编辑当成第一阶段目标；
- 不要从 HTML 缓存反向生成 .card；
- 不要让 API 每次打开都实时渲染；
- 不要把私有资源上传到永久公开 URL；
- 不要让用户选择技术性上传规则；
- 不要把下载按钮接到缓存 HTML；
- 不要把 render_failed 当作源文件上传失败；
- 不要为了低并发省事跳过权限和安全模型。
