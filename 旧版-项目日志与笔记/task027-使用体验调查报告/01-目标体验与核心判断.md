# 01-目标体验与核心判断

## 用户想要的体验

用户视角可以概括成一句话：

> 我在电脑/手机上的薯片软件里制作一张卡片，保存成 .card 文件，像发微博/发图片一样上传到社区；别人点开网页就能直接看；需要收藏或二次编辑时，再从网页下载完整 .card 文件，用本地软件继续打开和编辑。

这个体验里其实有三件事要同时成立：

1. .card 必须继续是“完整内容文件”，不能因为上传到网页就被拆散成只剩 HTML；
2. 网页查看必须足够接近本地查看器，而不是只展示一张截图或一个静态封面；
3. 下载必须能拿回完整 .card，并且拿回来的文件仍然能被 Host / 查看器 / 编辑器正式识别。

## 核心判断

我倾向的目标架构是：

    本地编辑软件
      -> 导出正式 .card
      -> 上传到社区
      -> 社区保存原始完整 .card / 发布处理 .card
      -> 异步生成网页查看缓存
      -> 网页打开缓存 + CardViewer Web 宿主
      -> 下载时返回原始完整 .card，或明确标注的发布版 .card

不要把“网页查看”理解成“服务器每次实时渲染卡片”。弱服务器扛不住，也没有必要。更合理的是上传后或首次访问时生成静态查看产物，后续浏览器大部分流量直接走对象存储/CDN。

也不要把“下载完整卡片”理解成“从已经渲染好的网页 HTML 重新合成 .card”。网页缓存是消费产物，.card 是源文件，两者应该并行保存，源文件才是下载与再编辑的真实依据。

这里要特别小心一个语义：当前桌面社区上传模块会把资源外置到对象存储、改写 URL、删除已外置资源并重新打包 processed.card。服务器保存的 source.card 可能是“发布处理包”，不一定是用户最初保存的“完整离线原始包”。如果目标体验承诺像 Word 一样下载回来仍完整离线可编辑，后续需要区分 original.card 和 publish.card。

## 现在已经接近目标的地方

- .card 格式本身已经是 ZIP Store 归档态，设计上就接近 Word / 图片这种“单文件可携带内容”的体验；当前格式规范明确 .card 是 ZIP 包，包含 .card/metadata.yaml、.card/structure.yaml、.card/cover.html、content/ 和资源文件。
- Host / SDK 已经有正式 card.pack、card.unpack、card.readInfo、card.render、card.renderCover、card.compositeWindow.render、card.coverFrame.render 链路。
- 社区服务端当前上传后会保存一份 source.card 到私有 bucket chips-card-files/{userId}/{cardId}/source.card，并把 sourceCardBucket/sourceCardKey/sourceCardSha256 写进数据库。需要继续确认这份 source.card 在不同上传链路下是原始完整包还是发布处理包。
- 社区端有异步渲染缓存：community-web 生成完整查看 HTML，community-cover 生成封面 HTML。公开卡片缓存可以进入公开对象存储/CDN，私有卡片缓存走受控 API 代理。
- 社区网页当前会创建 com.chips.card-viewer Web 插件会话，把 /api/v1/cards/:cardId/view 作为文档源交给 CardViewer，而不是在社区页面里临时手写查看器。

## 最大闭环缺口

当前公共社区 API 契约明确写着“社区内 .card 回下载”不在当前范围内。也就是说：上传、网页查看、渲染缓存已经有主要链路；但“用户从网页下载完整卡片”这个体验还没有正式 HTTP 契约和前端入口。

这不是一个从零开始的工程缺口，因为服务器已经保存了 source.card；但它是体验闭环和语义闭环缺口。要补的是：

- 权限判断：公开卡片谁能下载，私有卡片谁能下载；
- 下载接口：例如 GET /api/v1/cards/:cardId/source-card；
- 文件名和响应头：Content-Disposition: attachment; filename*=UTF-8''xxx.card；
- Range/大文件支持：大卡片不要让 API 进程整包读入内存；
- 下载按钮：Card detail / CardViewer chrome 里都要有稳定入口；
- 下载行为记录：下载计数、审计、作者可选禁止下载等策略如果要做，必须进入正式字段和 API 契约。
- 原始完整包和发布处理包的边界：如果下载入口承诺离线完整，就不能直接把带 CDN URL 的处理包当作原始完整包。

## 我对“用户设备解析还是服务器解析”的判断

最好分两条链路：

1. 本地软件正式发布链路：用户设备解析 .card、外置大资源、改写 URL、重新打包，然后上传处理后的 .card。这能极大减少服务器压力。
2. 网页过渡上传链路：浏览器直接上传 .card，服务器只做结构检查、保存源文件、排队渲染。不要要求普通用户在网页端理解资源外置规则。

从用户体验上，这两条链路都应该表现为“拖进去，点上传，等一下就能看”。技术差异不应该暴露给用户。

## 最重要的产品原则

- 用户只理解一个东西：.card 文件。
- 网页只需要查看，不承诺完整编辑。
- 本地软件负责创作、编辑、导出、复杂资源整理。
- 社区负责保存、展示、分享、下载。
- 弱服务器不做重计算热点请求；计算尽量提前、异步、可失败重试。
