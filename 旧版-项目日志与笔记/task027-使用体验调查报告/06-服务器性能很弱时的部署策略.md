# 06-服务器性能很弱时的部署策略

## 总原则

如果社区服务器性能很弱，最重要的原则是：服务器只做控制面，不做大流量和大计算的热路径。

控制面包括：

- 登录、鉴权、权限判断；
- 创建上传会话；
- 生成对象存储预签名 URL；
- 保存卡片元数据；
- 入队渲染任务；
- 查询渲染状态；
- 必要时代理私有缓存或私有下载。

真正重的东西应该尽量挪走：

- 大资源上传：用户设备直传对象存储；
- 公开查看流量：对象存储/CDN 承载；
- 公开封面流量：对象存储/CDN 承载；
- 大文件下载：对象存储签名 URL 或 CDN；
- 渲染计算：异步 worker 慢慢跑，不在用户请求里实时跑。

换句话说，弱服务器不能当“文件服务器 + 渲染服务器 + CDN + API”全包。它应该只是调度员。

## 上传阶段怎么省服务器

桌面发布模块现在的方向是对的：在用户设备上解包、扫描资源、申请预签名 URL、把资源直接 PUT 到对象存储、改写资源 URL、重新打包 processed.card，再提交到社区。

这条链路对服务器最友好：

    用户设备
      -> 直接上传资源到对象存储
      -> 只把发布态 .card 提交给社区 API
      -> 社区 API 保存源文件和元数据

服务器不需要接收每张大图、每首歌、每个视频的原始上传流量，也不需要自己做资源改写。

网页上传现在更像方便入口：用户拖一个 .card，前端创建 upload session，然后把 .card 直接提交给 API，manifest 里 resources 是空数组。这种体验简单，但对弱服务器压力更大，因为整个 .card 会经过 API。可以保留它，但最好加几条边界：

- 网页直传只适合中小卡片；
- 超过大小阈值时提示“建议使用桌面客户端发布”；
- API 不把文件整包读入内存，必须落临时文件或流式处理；
- 上传完成后立即返回“处理中”，不要同步生成查看页面；
- 失败原因尽量转换成人话，例如“文件太大”“卡片缺少资源”“当前服务器繁忙，已排队”。

如果未来要进一步省服务器，可以把 source.card 本身也改成预签名直传：API 只创建 source-card 上传地址，浏览器或桌面端直接 PUT 到对象存储，最后调用 complete 接口提交元数据和 hash。这样 API 连 .card 文件流量都不用扛。

## 渲染阶段怎么省服务器

网页查看不要做请求时实时渲染。

不推荐：

    用户打开 /cards/abc
      -> API 下载 .card
      -> API 启动 Host
      -> API 实时生成 HTML
      -> API 返回页面

这会把最重的动作放在用户等待时刻，而且打开一次算一次，服务器会被反复打爆。

推荐：

    上传完成
      -> 写入 render_pending
      -> worker 慢慢生成 HTML 缓存
      -> 上传到 render-cache bucket
      -> 用户打开时直接跳转缓存

worker 可以非常保守：

- 单进程；
- 并发 1；
- 每个任务有超时；
- 失败后有限重试；
- 支持手动重建缓存；
- 队列堆积时前端显示“排队中”，不假装马上能打开。

这对用户也不一定差。用户的心理预期可以是“发布后生成网页预览需要几秒到几十秒”，类似视频平台上传后转码。

## 查看阶段怎么省服务器

公开卡片的查看页应该尽量变成静态资源访问：

    浏览器
      -> 社区 API 只拿一次 open-view 元信息
      -> CardViewer Web 插件加载 viewUrl
      -> viewUrl 指向对象存储/CDN 上的 index.html
      -> 后续 HTML、图片、CSS、JS 全走对象存储/CDN

API 只在这些场景被访问：

- 打开前检查卡片是否存在、是否可见；
- 查询 render-status；
- 私有卡片查看时代理或签发短期 URL；
- Web 插件 session bootstrap；
- resource.open 计划查询。

对公开卡片来说，越少经过 API 越好。

私有卡片比较麻烦。当前已有私有 render cache bucket 和私有 cache proxy 思路，这能保证权限，但也会让 API 扛流量。弱服务器下可以分两档：

- 低并发阶段：API 代理私有缓存，简单可控；
- 稍高并发阶段：API 鉴权后签发短期 GET URL，让对象存储承载流量；
- 更高并发阶段：私有 CDN + 签名 URL 或签名 Cookie。

第一版低并发可以先做 API 代理，但必须限速、限并发、支持缓存头和 Range，不能无限制地把大 HTML 包和大资源都压到 API 上。

## 下载阶段怎么省服务器

完整 .card 下载最不能让 API 整包读入内存。

推荐优先级：

1. 公开卡片：API 判断权限后 302 到对象存储短期签名 GET URL；
2. 私有卡片：API 判断权限后 302 到更短时效的签名 GET URL；
3. 如果对象存储签名 GET 暂时不好接，再做 API 流式代理；
4. API 流式代理必须支持限速、Range、超时和并发限制。

不推荐：

- 从 render-cache HTML 反向打包 .card；
- 下载时重新整合资源；
- 读取对象存储完整 buffer 后再 res.send；
- 每次下载都启动 Host 或重新 pack。

正确口径是：上传阶段保存 source.card，下载阶段直接返回 source.card。

但这里要结合工单121再确认一个语义：当前 source.card 可能是桌面发布模块生成的“发布处理包”，里面部分资源已经改成 CDN URL。它适合网页发布和重建缓存，但不一定等同于用户最初保存的“完整离线原始包”。如果产品要求“下载后完全离线可编辑”，就要额外保存原始完整包，不能只暴露处理包。

## CDN 和对象存储的分工

可以这样理解：

- chips-card-files：私有源文件仓库，保存 .card；
- chips-card-resources：公开资源仓库，适合公开卡片外置资源；
- chips-card-render-cache：公开查看 HTML 缓存；
- chips-card-cover-cache：公开封面缓存；
- private render / cover cache：私有卡片查看缓存，不直接公开。

公开资源和公开缓存都应该配置 CDN，因为它们是浏览器会高频访问的东西。

源 .card 不应该默认公开。即使是公开卡片，下载也最好从 API 入口走一次权限和策略判断，再签发短期 URL。这样以后要做“作者允许查看但禁止下载”“登录后下载”“下载统计”时不会推翻架构。

## 队列与降级策略

弱服务器一定要接受“不是所有任务都马上完成”。

建议状态至少分成：

- uploaded：文件已收到；
- validating：检查中；
- render_pending：等待生成网页查看；
- render_running：正在生成；
- cache_ready：可以查看；
- render_failed：生成失败；
- source_missing：源文件丢失或不可读；
- unsupported_plugin：依赖插件缺失；
- blocked_by_policy：权限或安全策略阻止。

前端不要只显示一个转圈。用户应该知道现在是“排队中”“生成中”“失败可重试”，而不是误以为网页坏了。

队列还需要几个保护：

- 每个用户每天上传数量限制；
- 单卡片大小限制；
- 单卡片资源数量限制；
- 单资源大小限制；
- 渲染任务超时；
- 同一卡片同一 hash 不重复渲染；
- 失败任务指数退避；
- 管理后台能看到积压和失败原因。

## 最小可行部署形态

如果服务器真的很弱，我建议第一阶段这样部署：

    API 进程：只跑鉴权、元数据、上传会话、状态接口
    Worker 进程：单并发，异步生成 view/cover 缓存
    对象存储：保存源文件、资源、缓存
    CDN：只挂公开资源和公开缓存
    数据库：保存卡片记录、源文件 key、渲染状态

用户体验上表现为：

- 上传很快进入“处理中”；
- 小卡片几秒生成；
- 大卡片慢慢排队；
- 分享页能显示封面、状态和重试；
- 查看成功后基本不占 API；
- 下载完整卡片从对象存储出流量。

这比把所有事情堆给服务器稳定得多。
