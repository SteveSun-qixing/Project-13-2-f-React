## 一、任务背景与目标

### 1.1 用户新需求

1. **箱子与卡片不区分上传**，大部分时候尽可能共用同一条上传链路；
2. **箱子文件支持内嵌卡片**：卡片实体直接保存在 `.box` 文件根目录中；
3. **支持混合模式**：一部分条目保存 URL 引用，一部分条目直接内嵌卡片实体，无限制；
4. **上传箱子时自动收集关联卡片**：箱子内很多卡片通常不在箱子文件内部，而是散落在用户设备各处（本地 `.card` 文件），上传器需要把这些关联卡片一并上传到社区；
5. **已是网络资源保存的卡片不需要重新上传**（如条目 URL 已是 http/https 网络地址、或资源已全部网络化的卡片）。

### 1.2 本清单范围

- 全面梳理箱子从"本地保存 → 引用/内嵌 → 编辑 → 上传 → 社区存储 → 网页/客户端查看 → 下载"的完整链路；
- 找出所有已断链、未打通、口径漂移的问题点；
- 输出分阶段开发任务清单与验收口径。

## 二、当前箱子链路全景（调查结论）

### 2.1 本地保存与格式

- `.box` 是 ZIP Store 零压缩包，内含 `.box/metadata.yaml`、`.box/structure.yaml`、`.box/content.yaml`、`.box/cover.html`（必需）+ `assets/`（可选）。
- **当前格式明确禁止**在箱子内保存 `.card` 实体（规范 `生态共用技术文档/文件格式规范/02-箱子文件格式规范.md` §4.4、§11.3；Host 校验 `Chips-Host/packages/box-service/src/box-service.ts:1613`）。
- 条目统一用 URL 定位（`file://` / `http://` / `https://` / `webdav://`），凭证不入文件。

### 2.2 本地消费链路（Host 负责）

```
box.openView（解包到临时目录，建会话）
  → listEntries / readEntryDetail / renderEntryCover / resolveEntryResource / readBoxAsset
  → box.renderLayoutFrame（装载布局插件，生成受控文档 chips-render://）
  → 布局插件渲染摘要页 → 点击条目 → box.openEntry
      file:// 卡片 → card.open 新窗口
      file:// 箱子 → 递归打开嵌套箱子
      http(s) → openExternal
```

- SDK 封装：`Chips-SDK/src/api/box.ts:574` `client.box.documentWindow.render`。

### 2.3 上传链路（现状：卡片与箱子两条完全不同链路）

| 维度 | 卡片（已打通） | 箱子（缺口） |
|---|---|---|
| 客户端入口 | WorkspacePage 选择 `.card` 批量上传 | **无任何入口**（`POST /api/v1/upload/box` 无调用方） |
| 字节路径 | 客户端模块直传对象存储（预签名 PUT），API 只做控制面 | multipart 直传 API 服务器进程（`routes/upload.ts:62`） |
| 协议 | 3 段控制面（session/presign/complete）+ 对象存储 | 单 POST multipart |
| 会话模型 | `upload-sessions` 表（contentType 枚举已含 `box` 但控制面硬编码 `card`，`card-transfer.ts:194`） | 无 |
| 上传后 | 网络资源卡片保留对象存储，可在线查看/回下载 | 服务端解包后**删除原始 .box**（`box.service.ts:199`） |

### 2.4 社区服务器存储

- `boxes` 表：`boxFileId / title / coverUrl / coverRatio / documentUrl / metadata / structure / layoutPlugin / visibility / fileSizeBytes`（`db/schema/boxes.ts`）。
- 上传时解包 `.box` → 解析 metadata/structure → 写入 JSONB → **删除临时 .box 文件**（`services/box.service.ts:168-201`）。
- **对象存储中没有箱子本体**：bucket 清单（`storage/buckets.ts`）只有卡片资源/源文件/渲染缓存/封面缓存/头像/房间封面，没有 box 相关 bucket。
- 卡片引用匹配：`enrichCardRefs`（`box.service.ts:252`）用 `structure.cards[].card_id` 去 `cards.cardFileId` 匹配，返回 `communityCardId / communityViewUrl / communityRenderStatusUrl`。

### 2.5 查看链路

- **本地**：Host + 布局插件 + 查看器，已闭环（见 2.2）。
- **社区 Web**：`BoxDetailPage`（`packages/web/src/pages/BoxDetailPage.tsx`）→ `DocumentPluginRoutePage` → 起 `com.chips.card-viewer` 插件 iframe 承载，需要 `box.documentUrl`；**但 documentUrl 恒为 null**（`BoxService.create` 从不写入），页面实际停在"未就绪"挂起态（`box.notReady`）。
- **社区桌面客户端**：`Chips-CommunityClient/src/community/pages/BoxDetailPage.tsx` 只做只读展示（metadata + 引用卡片列表，引用卡片可 `openInLocalViewer` 本地打开），无布局渲染。
- 社区契约明确"箱子在线布局运行时"不在当前范围（`协议与契约/09-社区平台API契约.md` §8）。

## 三、问题清单（详细问题情况）

### 问题 1：箱子格式禁止内嵌卡片（核心需求冲突）

- **位置**：`生态共用技术文档/文件格式规范/02-箱子文件格式规范.md` §4.4/§11.3；`Chips-Host/packages/box-service/src/box-service.ts:1613`（`validateZipEntries` 拒绝 `.card`/`.box` 条目）；`生态设计原稿/06-箱子文件格式.md` 全文口径"不保存卡片实体"。
- **现状**：箱子打开校验直接抛 `BOX_FORMAT_INVALID`，内嵌卡片文件根本进不了箱子。
- **需求**：允许 `.card` 放入箱子根目录（任意层级），支持"全部内嵌 / 全部引用 / 混合"三种形态。
- **影响**：文件格式规范、设计原稿、Host 校验、SDK 类型、编辑引擎、服务器解析全部需要同步放开与扩展。

### 问题 2：条目引用模型无法表达"箱内条目"

- **位置**：`Chips-Host/packages/box-service/src/box-service.ts:1799`（`assertSupportedUrl` 只认绝对 URL 白名单 `file:/http:/https:/webdav:`）、`:1769-1814`（`normalizeEntries`）、`:2063`（`resolveEntryLocator`）。
- **现状**：`structure.yaml` 的条目 `url` 必须是绝对 URL，无法引用"箱子内部根目录的卡片文件"；`normalizeEntrySnapshot` 还拒绝旧 `card_id` 字段（`:1830`）。
- **需求**：需要定义"箱内引用"的正式表达（例如相对路径 `url: "cards/foo.card"` 或新增 `location: "embedded"` 字段，需设计冻结），Host 解析/摘要/封面/打开链路都要支持。
- **连带影响**：`renderEntryCover`（`:1357`）、`openEntry`（`:1415`）、`resolveEntryResource`（`:1258`）都只按本地 file 或远程 URL 分流，需增加"箱内条目"分支。

### 问题 3：社区服务器解析模型与 Host/规范完全漂移（严重）

- **位置**：`Chips-CommunityPlatformServer/packages/server/src/types/box.ts`（`id` / `layout_plugin` / `updated_at` / `structure.cards`——全部是旧格式）；`services/box.service.ts:185-190`（`metadata.id`、`metadata.layout_plugin`）。
- **现状**：
  - 正式格式字段是 `box_id` / `active_layout_type` / `modified_at` / `structure.entries`，服务器读的全是旧字段名；
  - 结果：`boxFileId` 恒为 null（`metadata.id` 不存在）、`layoutPlugin` 恒为 null（`metadata.layout_plugin` 不存在）；
  - `enrichCardRefs` 读 `structure.cards`（Host 明确禁止该字段），社区 `box.cards` 引用匹配恒为空列表；
  - 服务器 `unpackBox` 只读 metadata/structure 两个文件，不校验 content.yaml/cover.html，与 Host 的 4 必需文件校验口径不一致。
- **需求**：服务器解析模型全面对齐正式格式（entries + snapshot + document_id 匹配卡片）。

### 问题 4：上传链路不统一，客户端无箱子上传

- **位置**：`Chips-CommunityClient/src/community/pages/WorkspacePage.tsx:63-69`（文件过滤器只允许 `.card`）；`routes/upload.ts:62`（multipart 箱子上传无人调用）；`card-transfer.ts:194`（控制面硬编码 `contentType: 'card'`）。
- **现状**：卡片走 card-transfer 控制面 + 对象存储直传；箱子走 multipart 经 API 进程。两条链路并存且箱子链路无人用。
- **需求**：按用户要求"箱子与卡片共用链路"——把箱子上传接入 card-transfer 会话模型（`uploadSessionContentTypeEnum` 已预留 `box`），客户端选择器同时接受 `.card` 与 `.box`。

### 问题 5：上传器不会收集散落卡片（核心需求）

- **位置**：`Chips-ModulePlugin/Chips-CommunityUploader-Plugin/src/publisher.ts:995`（`uploadCommunityCard` 只处理单个 `.card`）；`index.ts:28-46`（capability `community.card.transfer` 只有 upload/download/openRemote）。
- **现状**：上传箱子时，`structure.yaml` 里 `file://` 指向用户设备上其他位置的卡片不会被发现、不会被上传，社区中的箱子引用会失效。
- **需求**：
  1. 上传箱子前先解析 `structure.yaml` 条目；
  2. 内嵌卡片 → 从箱子内提取；
  3. `file://` 本地卡片 → 收集并复用现有卡片上传链路逐个上传；
  4. `http(s)` 网络卡片/已网络化卡片 → 跳过（判定标准需定义：URL 协议为 http/https 即跳过；或提供"卡片资源是否已全部网络化"的检查能力）；
  5. 上传完成后把箱子内条目的 URL 改写为社区网络地址（或用 `document_id` 关联匹配社区卡片），再提交箱子本体。

### 问题 6：服务器删除原始 .box，箱子本体无法重建/下载

- **位置**：`box.service.ts:199`（上传后 `rmSync(boxFilePath)`）；`boxes` 表无对象存储字段（无 `sourceBoxBucket/Key/Url`）。
- **现状**：社区只有 metadata/structure JSONB，没有正式 `.box` 文件；无法下载、无法交给 Host `box.openView` 渲染、无法重建（工单097 的核心证据之一）。
- **需求**：箱子本体（含内嵌卡片）应保留到对象存储（新增 bucket 或复用卡片文件 bucket），作为社区箱子的正式源文件。

### 问题 7：社区箱子无法正式查看（documentUrl 恒 null）

- **位置**：`packages/web/src/pages/BoxDetailPage.tsx:47-61`（依赖 `box.documentUrl`）；`BoxService.create` 从不写 `documentUrl`；契约 §8 声明"箱子在线布局运行时"不在范围。
- **现状**：网页箱子详情卡在"未就绪"挂起态；工单097 处理中（暂行：服务端用 metadata/structure 生成只读文档源），但 `documentUrl` 仍未落地。
- **需求**：短期至少落地只读文档源并写入 `documentUrl`；长期由 Host render session Web 导出能力提供正式布局渲染。

### 问题 8：箱子无渲染缓存 / 封面缓存 / Worker 队列

- **位置**：`card-render-cache.service.ts`、`storage/buckets.ts`（卡片有 view/cover 缓存 bucket 与 worker 队列；箱子无对应 bucket、无渲染任务、无私有代理路由）。
- **现状**：社区箱子的封面 `coverUrl` 在 `BoxService.create` 中也没有生成（`coverUrl` 列恒 null，需外部上传 `POST /api/v1/boxes/:boxId/cover` 之类能力——当前不存在）。
- **需求**：按卡片同等标准补齐箱子封面产物生成、view/cover 缓存与私有代理（`/api/v1/boxes/:boxId/render-cache/...`）。

### 问题 9：内嵌卡片与摘要封面的渲染链路缺失

- **位置**：`box-service.ts` `renderEntryCover`/`readEntryDetail`/`readBoxAsset`（资源都从解包目录或卡片文件读取，无"箱内卡片"分支）；`Chips-EditingEngine/src/services/box-document-service.ts:209`（`serializeEntry` 只序列化 URL 条目）。
- **现状**：编辑引擎创建箱子时没有"添加内嵌卡片"的能力（`structure.yaml` 只能写 URL）；`card.pack` 与 `box.pack` 是两条独立打包器，未做"箱内嵌卡片的资源完整性"处理。
- **需求**：编辑引擎支持把本地卡片打包进箱子根目录并在 `structure.yaml` 登记箱内引用；Host 消费时按箱内路径解析封面/摘要/打开。

### 问题 10：文档契约大面积未更新

- `生态共用技术文档/文件格式规范/02-箱子文件格式规范.md`（禁内嵌、URL-only）
- `生态设计原稿/06-箱子文件格式.md`（不保存卡片实体）
- `生态共用技术文档/02-箱子业务.md`（格式/上传动作面）
- `生态共用技术文档/协议与契约/08-箱子布局运行时契约.md`（条目模型、箱内引用）
- `生态共用技术文档/协议与契约/09-社区平台API契约.md`（箱子上传方式、DTO、下载、渲染缓存）
- **需求**：需求方案冻结后，以上文档按"格式层（可内嵌）→ Host 层（箱内解析）→ 传输层（共用链路 + 收集卡片）→ 社区层（源文件保留 + 渲染 + 查看）"整体更新，避免口径再次漂移。

### 问题 11：下载/回链缺口（关联工单 121）

- 社区箱子无下载入口；下载应返回正式 `.box`（含内嵌卡片）。
- 箱子下载回来后的条目 URL 指向社区网络地址——需要定义"回还原"策略（类似卡片 restoreManifest）或保留原始引用视图。
- 关联工单：工单121（卡片完整回下载与源文件直传契约缺口，待处理）——箱子下载应与其一起收口。

## 六、风险与依赖

1. **格式变更影响面大**：内嵌卡片改动涉及 Host 校验/解析/渲染、SDK、编辑引擎、服务器解析、布局插件条目模型——P0 契约冻结必须先行，避免各仓各自实现造成二次漂移。
2. **收集散落卡片的语义**：`file://` 条目指向的卡片可能属于其他箱子或用户私有目录，收集策略（复制进箱 / 仅引用）、去重（同 card_id 已上传过）与失败处理需要产品口径确认。
3. **"已是网络资源保存的卡片"判定标准**：建议以条目 URL 协议（http/https）为第一判据；若需要识别"资源已全部网络化的本地卡片"，需在 Host 增加 `card.readInfo` 的资源形态查询能力（当前 `card-info-service` 无此字段，需扩展）。
4. **工单097 的 Host Web 导出能力**是社区箱子正式查看的长期正解，本任务不替代它，只在 P1 保证箱子本体可保留、可重建。

### 修复记录（2026-08-06 第二轮联调）

1. **箱子预签名下载 URL 签名不匹配（HTTP 403）**：
   - 根因：`storage/s3.ts` 的 SigV4 canonical query 用 `localeCompare` 排序（locale 排序把小写 `response-content-disposition` 排在大写 `X-Amz-*` 前），且最终 URL 用 `URLSearchParams.toString()`（空格→`+`）与签名编码（`%20`）不一致；
   - 修复：新增 `serializeSignedQuery`（ASCII 字节序排序 + `encodeURIComponent` 编码），签名计算与最终 URL 统一复用；GET/PUT 预签名均生效；
   - 验证：boto3 对照、真实对象下载 200 OK，服务器 85 测试通过。

2. **下载回来的箱子卡片封面无法显示**：
   - 根因：`uploadCommunityBox` 上传时把散落卡片的 `file://` 条目 URL 改写为社区 URL（`http://localhost/cards/{uuid}`），服务器保存的 `.box` 源文件即改写版；客户端下载后卡片查看器按远程 URL 解析，`renderEntryCover` 无法渲染封面；
   - 修复：上传时 `structure.yaml` 保持原始引用不变（file:// / 内嵌相对路径 / 网络 URL 均原样），社区匹配由服务器 `enrichCardRefs` 按 `snapshot.document_id` 动态提供；
   - 验证：重新上传后服务器存储原始引用且 communityCardId 匹配正常；下载箱子经 Host `readEntryDetail` 返回 `kind: card / status: ready`，封面渲染链路可用。
