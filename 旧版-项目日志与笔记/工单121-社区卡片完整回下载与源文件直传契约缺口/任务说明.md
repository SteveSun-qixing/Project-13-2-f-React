# 工单121：社区卡片完整回下载与源文件直传契约缺口

## 背景

目标社区体验要求用户把本地制作完成的 `.card` 像 Word 文档、图片一样上传到社区，网页可以直接查看，之后也可以从网页下载保存完整卡片文件。

当前卡片上传与查看主链路已经具备上传会话、资源预签名、源 `.card` 私有保存、view/cover 渲染缓存和网页插件宿主。但核对现有代码与契约后发现，完整回下载与低性能服务器友好的源文件直传还没有形成正式闭环。

## 证据

1. 公共 API 契约明确把“社区内 `.card` 回下载”列为当前不在契约范围内的内容：`生态共用技术文档/协议与契约/09-社区平台API契约.md`。
2. 当前 `cards` 表保存了 `source_card_bucket`、`source_card_key`、`source_card_sha256`，但 `CardService.toDTO` 只暴露 `sourceCardSha256`、`viewUrl` 和 `renderStatusUrl`，没有源文件下载入口：`Chips-CommunityPlatformServer/packages/server/src/db/schema/cards.ts`、`Chips-CommunityPlatformServer/packages/server/src/services/card.service.ts`。
3. `cards.ts` 只有详情、open-view、status、render-status、view、cover、私有缓存代理、更新、删除和列表路由，没有 `download` / `source` / attachment 响应路由：`Chips-CommunityPlatformServer/packages/server/src/routes/cards.ts`。
4. 当前上传会话只给资源文件预签名，处理后的 `.card` 仍通过 `POST /api/v1/upload-sessions/:uploadId/card` multipart 进入 API 进程，再由服务器上传到 `chips-card-files`：`Chips-CommunityPlatformServer/packages/server/src/routes/upload.ts`、`Chips-CommunityPlatformServer/packages/server/src/services/upload-session.service.ts`。
5. `Chips-CommunityUploader-Plugin` 会在用户设备上把资源外置、改写 URL、删除已外置资源并重新打包处理后的 `.card`，因此服务器当前保存的发布源文件可能是“网页发布态处理包”，不是用户最初上传的全填充离线原始包：`Chips-ModulePlugin/Chips-CommunityUploader-Plugin/src/publisher.ts`。

## 影响范围

- 社区网页“下载完整卡片文件”的用户体验；
- 公开卡片和私有卡片的下载权限、签名 URL、审计和限流；
- 上传链路的数据面流量，尤其弱服务器处理大 `.card` 的压力；
- CommunityUploader、社区 API、对象存储 bucket 结构、数据库模型与公共 API 契约；
- “网页查看态处理包”和“用户原始完整包”之间的长期语义边界。

## 复现步骤

1. 上传一个包含本地图片、音频或视频资源的 `.card`；
2. 使用 CommunityUploader 正式发布链路时，观察上传模块会把资源 PUT 到预签名 URL，并把 `.card` 内部引用改成公开 URL 后重新打包；
3. 查看社区服务端 `cards` 记录，确认只保存一组 `source_card_bucket/key/sha256`；
4. 查看 `GET /api/v1/cards/:cardId` 与 `GET /api/v1/cards/:cardId/view`，确认只有查看缓存入口，没有源 `.card` 下载入口；
5. 若直接把当前 `source.card` 暴露为下载文件，用户拿到的可能是带 CDN URL 的处理包，而不是原始完整离线包。

## 期望行为

- 社区应区分至少两种卡片源：
  - 原始完整包：用户本地保存/上传的完整 `.card`，用于回下载、备份、迁移和离线打开；
  - 发布处理包：资源已外置、URL 已改写、面向网页渲染和缓存生成的 `.card`。
- 上传会话应支持源 `.card` 预签名直传到私有对象存储，API 只负责签发、提交、Head 校验、记录元数据和排队校验/渲染，不承担大文件数据面中转。
- 下载接口应返回用户期望的“完整卡片文件”，并按权限、作者设置、未来授权策略和审计要求控制访问。
- 对旧的仅保存处理包的记录，应有明确迁移或重新上传策略，不把处理包伪装成完整离线包。

## 暂行处理

本轮只登记缺口，并在上传链路调查笔记与 task-027-使用体验调查报告中给出推荐方案，不改动生产接口和数据结构。后续实施前需要先冻结公共契约，再同步修改 CommunityUploader、社区服务端、数据库迁移、网页端下载入口和验证用例。
