## 2. 总体结论

社区服务器当前已经具备第一版社区站点所需的主链路：

1. 用户注册、登录、刷新、登出；
2. 用户主页、公开作品列表、工作区上传；
3. `.card` / `.box` 上传；
4. 卡片异步转换为 HTML 并发布到对象存储；
5. Web 插件宿主链路承载原版 CardViewer / PhotoViewer；
6. 管理后台的用户与内容基础治理；
7. 生产域名、HTTPS、对象存储公开域名与 Docker 部署基础。

但如果目标提升到“稳定生产社区 + 本地上传器 + 长期生态平台”，还需要系统性优化。最需要优先处理的不是单个页面细节，而是以下基础能力：

1. 上传任务正式化；
2. 本地客户端会话与设备授权；
3. 任务队列与失败恢复；
4. 用户级限流、配额和安全治理；
5. 数据库分页、索引和查询性能；
6. 统一 API schema / OpenAPI 契约；
7. 生产可观测性、审计和运维能力；
8. 测试覆盖从单元测试扩展到上传、认证、流水线、部署烟测。

## 3. 优先级定义

- P0：上线前或本地上传器前置必须解决，否则会造成数据重复、任务丢失、安全风险或生产不可控。
- P1：第一版生产稳定运行强烈建议解决，会明显影响可靠性、维护效率或扩展能力。
- P2：中期平台化优化，解决规模、体验、治理和长期演进问题。
- P3：锦上添花或高级能力，适合基础稳定后推进。

## 4. 上传与本地上传器相关优化

### O-001 本地客户端会话体系

- 优先级：P0
- 当前现状：
  - `POST /api/v1/auth/login` 返回 `accessToken`；
  - refresh token 主要通过 `chips_refresh_token` HttpOnly Cookie 写给网页端；
  - `POST /api/v1/auth/refresh` 支持请求体中的 `refreshToken`；
  - `POST /api/v1/auth/logout` 当前只读取 Cookie 中的 refresh token。
- 问题：
  - 本地上传器可以登录并上传，但还不是一等客户端；
  - 本地工具长期保存用户名密码不安全；
  - 无设备列表、设备吊销、客户端名称、客户端版本、scope 权限；
  - 如果本地上传器通过请求体 refresh token 续期，退出时缺少正式吊销入口。
- 优化建议：
  1. 新增本地客户端设备会话模型；
  2. 支持浏览器确认式设备登录或一次性授权码登录；
  3. 每个本地客户端会话记录设备名、系统、客户端版本、创建时间、最后使用时间；
  4. refresh / logout 同时支持 Cookie 与请求体 token，并能精确吊销当前设备；
  5. token 增加 scope，例如 `upload:card`、`upload:box`、`content:read-own`；
  6. 用户设置页和管理后台可查看、吊销设备。
- 需要同步文档：
  - 若作为正式对外能力，需要同步到 `生态共用技术文档/协议与契约/09-社区平台API契约.md`。

### O-002 上传任务模型

- 优先级：P0
- 当前现状：
  - 卡片上传返回 `{ cardId, status: "pending" }`；
  - 前端用 `GET /api/v1/cards/:cardId/status` 轮询；
  - 箱子上传成功后直接返回 `{ boxId, title }`；
  - 没有独立的 `uploadId` 或上传任务表。
- 问题：
  - 本地上传器批量上传时无法稳定追踪“上传请求”和“最终内容”的关系；
  - 失败阶段不够细，客户端只能看到最终错误信息；
  - 无上传文件名、sha256、客户端来源、耗时、阶段事件；
  - 服务器重启时进程内任务状态容易断裂。
- 优化建议：
  1. 新增 `uploads` 表；
  2. 上传接口统一返回 `uploadId`，并关联 `cardId` / `boxId`；
  3. 状态拆分为 `receiving`、`validating`、`queued`、`processing`、`publishing`、`ready`、`error`、`cancelled`；
  4. 记录原始文件名、文件大小、sha256、客户端类型、客户端版本、IP、User-Agent；
  5. 新增 `GET /api/v1/uploads/:uploadId`；
  6. 新增 `GET /api/v1/users/me/uploads`，供本地上传器恢复任务列表；
  7. 上传任务状态与卡片状态联动，但不要把“上传任务”完全等同于“卡片实体”。

### O-003 幂等键与重复上传治理

- 优先级：P0
- 当前现状：
  - 卡片流水线中只检查同用户同 `cardFileId` 且状态为 `pending/processing` 的重复；
  - 上传入口没有 `Idempotency-Key`；
  - `sha256File` 工具已存在，但上传路由未使用。
- 问题：
  - 本地工具网络中断后重试可能创建重复数据库记录；
  - 同一个文件多次上传的正式行为没有冻结；
  - 卡片处理到后期失败时，重复请求可能造成多份对象存储资源。
- 优化建议：
  1. 支持 `Idempotency-Key` 请求头；
  2. 服务端计算并记录文件 sha256；
  3. 对同用户同 sha256 上传提供明确策略：
     - 返回已有上传任务；
     - 创建新版；
     - 或要求客户端显式传 `duplicatePolicy`；
  4. 重复卡片 ID 检查从流水线后置检查前移到校验阶段；
  5. 错误码新增 `UPLOAD_DUPLICATE`、`UPLOAD_IDEMPOTENCY_CONFLICT`。

### O-004 上传队列持久化与 Worker 化

- 优先级：P0
- 当前现状：
  - `routes/upload.ts` 里用 `setImmediate()` 触发 `runCardPipeline()`；
  - 流水线运行在 API 进程内；
  - 任务没有持久化队列。
- 问题：
  - API 进程重启会中断正在处理的卡片；
  - 多实例部署时任务调度不可控；
  - 批量上传可能和普通 API 请求争抢 CPU、内存、IO；
  - 失败重试策略不可配置。
- 优化建议：
  1. 把卡片处理改为持久化任务队列；
  2. API 只负责接收文件、写入任务、快速返回；
  3. Worker 进程负责解包、上传资源、转换 HTML、发布对象存储；
  4. 支持任务重试、最大重试次数、退避、死信队列；
  5. Worker 并发通过环境变量治理；
  6. 管理后台可查看队列积压、失败任务、重试按钮。

### O-005 上传校验细化

- 优先级：P0
- 当前现状：
  - `.card` / `.box` 上传入口检查扩展名和大小；
  - `unpackCard()` / `BoxService.create()` 检查 ZIP 魔数与关键文件；
  - `.card` 结构校验集中在流水线阶段；
  - `.box` 解析缺少更细的结构与布局插件校验。
- 问题：
  - 错误码多归为 `FILE_CORRUPT`；
  - 客户端难以给用户展示“缺 metadata”“结构字段错误”“资源缺失”等精确原因；
  - ZIP 解压没有统一的总解压大小、文件数量、压缩比限制；
  - YAML schema 未与共用文件格式规范形成完整自动校验。
- 优化建议：
  1. 建立 `.card` / `.box` 服务端正式校验器；
  2. 拆分错误码：`CARD_METADATA_INVALID`、`CARD_STRUCTURE_INVALID`、`BOX_METADATA_INVALID`、`ZIP_ENTRY_FORBIDDEN` 等；
  3. 校验 ZIP 文件数量、单文件大小、总解压大小、压缩比；
  4. 校验资源引用是否全部存在；
  5. 校验布局插件、基础卡片插件 ID 是否在服务器可处理范围内；
  6. 本地上传器可调用 `POST /api/v1/upload/validate` 先做预检。

### O-006 断点续传与大文件体验

- 优先级：P1
- 当前现状：
  - 上传使用一次性 `multipart/form-data`；
  - Nginx `client_max_body_size` 当前为 520M；
  - 卡片最大值默认 500MB。
- 问题：
  - 500MB 文件在弱网下失败成本高；
  - 本地上传器无法恢复中断上传；
  - 服务器端无法复用已经成功传输的部分。
- 优化建议：
  1. 新增分片上传初始化接口；
  2. 分片上传带 index、size、sha256；
  3. 完成后服务端校验并合并；
  4. 支持查询已上传分片；
  5. 定期清理过期分片；
  6. 第一阶段可以先只给本地上传器开放分片上传，网页端继续使用普通 multipart。

### O-007 用户上传限流、配额和并发上限

- 优先级：P0
- 当前现状：
  - 只有限制单个文件最大尺寸；
  - 没有用户级、IP 级、客户端级限流；
  - 没有总存储配额。
- 问题：
  - 本地上传器可以批量上传，容易打满 API、Worker、对象存储；
  - 恶意用户可以注册后大量占用存储；
  - 管理后台无法看用户配额与超限情况。
- 优化建议：
  1. 增加用户级上传并发上限；
  2. 增加每日上传数量和大小限制；
  3. 增加账号总存储配额；
  4. 限流响应返回 `429` 与 `Retry-After`；
  5. 管理后台可配置用户配额；
  6. 首页/工作区/本地上传器可展示剩余额度。

## 5. 认证、账号与安全优化

### O-008 登录与注册防滥用

- 优先级：P0
- 当前现状：
  - 登录失败计数按用户名存在 Redis；
  - 达到 5 次失败后锁 15 分钟；
  - 注册接口无额外防滥用策略。
- 问题：
  - 可枚举用户名并触发账号锁定；
  - 没有 IP 维度、设备维度、注册频率限制；
  - 没有验证码、邮箱验证或邀请机制。
- 优化建议：
  1. 登录失败计数加入 IP / 用户名组合维度；
  2. 注册加入 IP 级频率限制；
  3. 对异常登录返回统一口径，减少账号枚举；
  4. 第一版可先实现 Redis 限流，不引入新第三方服务；
  5. 后续再评估邮箱验证、邀请注册等产品策略。

### O-009 密码策略与会话吊销

- 优先级：P1
- 当前现状：
  - 密码 schema 未在本轮完整核对到高强度策略；
  - 修改密码只更新密码哈希；
  - refresh token 黑名单只在 refresh rotation 和 logout 中处理。
- 问题：
  - 修改密码后旧设备会话可能仍可恢复；
  - 用户无法主动“退出所有设备”；
  - 没有密码更新时间、会话版本号。
- 优化建议：
  1. 用户表增加 `passwordChangedAt` 或 `sessionVersion`；
  2. access / refresh token payload 带 session version；
  3. 修改密码后吊销所有旧 refresh token；
  4. 增加 `POST /api/v1/auth/logout-all`；
  5. 增加设备会话管理后，允许用户按设备吊销。

### O-010 CSRF 与 Cookie 策略核对

- 优先级：P1
- 当前现状：
  - refresh token Cookie 为 HttpOnly、SameSite strict；
  - access token 存在内存中，通过 Bearer 发送；
  - 生产 CORS 只允许 `BASE_URL` 同源。
- 问题：
  - 当前策略对网页第一方场景基本稳妥，但本地客户端引入后需要重新定义 Cookie 与 body refresh token 的边界；
  - 管理后台也依赖同源 Cookie refresh。
- 优化建议：
  1. 明确网页端 refresh token 只走 Cookie；
  2. 本地客户端 refresh token 走设备会话接口和请求体；
  3. 对 Cookie refresh 保持 SameSite strict；
  4. 若未来出现跨域前端，必须增加 CSRF token 或等价方案；
  5. 管理后台敏感操作可引入二次确认或短期操作 token。

### O-011 Web 插件宿主安全边界

- 优先级：P1
- 当前现状：
  - `host-runtime.ts` 允许创建 Web 插件 session；
  - 当前使用 `optionalAuthenticate`；
  - 插件资源通过服务端读取本地插件资产；
  - bootstrap 通过 `postMessage` 与外层通信。
- 问题：
  - 插件 session 创建未细分哪些插件可公开访问、哪些必须登录；
  - session 生命周期、最大数量、超时清理不明确；
  - 错误多为普通 `Error`，会落到 500；
  - launchParams 的 schema 校验不足。
- 优化建议：
  1. Web 插件 session 增加 ACL；
  2. 限制单 IP / 单用户并发 session 数；
  3. 增加 session TTL 和后台清理；
  4. 对 `pluginId`、`launchParams`、`resource-open-plan` 使用 zod schema；
  5. 统一错误码，例如 `HOST_PLUGIN_NOT_FOUND`、`HOST_PLUGIN_FORBIDDEN`、`HOST_RESOURCE_UNSUPPORTED`；
  6. 审查 iframe sandbox、CSP 与对象存储 HTML CSP 的组合策略。

## 6. API 契约与接口工程化优化

### O-012 OpenAPI schema 完整化

- 优先级：P1
- 当前现状：
  - 已接入 Swagger；
  - 只有健康检查等少量路由带 schema；
  - 多数路由依赖 zod 手动 parse 或 `request.body as ...`。
- 问题：
  - `/api/docs` 不能完整表达真实 API；
  - 本地上传器或外部工具无法稳定按 OpenAPI 生成客户端；
  - 文档、前端类型、服务端校验容易漂移。
- 优化建议：
  1. 为所有公开 API 补 Fastify schema 或统一 zod-to-json-schema 生成流程；
  2. 上传 multipart 也要在 OpenAPI 中表达字段；
  3. 错误响应统一 schema；
  4. CI 中导出 OpenAPI JSON 并做契约快照；
  5. 后续本地上传器优先消费这个契约。

### O-013 错误码体系扩展

- 优先级：P1
- 当前现状：
  - 已有基础错误码；
  - 上传、Host Runtime、流水线很多错误仍是普通 `Error`；
  - 卡片处理失败把原始 error message 写入 `cards.errorMessage`。
- 问题：
  - 客户端难以区分可重试、不可重试、用户文件错误、服务器错误；
  - 可能把内部路径、插件错误细节暴露给用户；
  - 管理后台难以按错误类型统计。
- 优化建议：
  1. 错误码按领域扩展：`UPLOAD_*`、`PIPELINE_*`、`HOST_RUNTIME_*`、`STORAGE_*`；
  2. 错误对象增加 `retryable`；
  3. 内部日志记录完整错误，用户响应返回安全摘要；
  4. pipeline 记录 `errorCode`、`errorStage`、`errorMessage`；
  5. 本地上传器根据错误码决定重试或提示用户修复文件。

### O-014 API 版本治理

- 优先级：P2
- 当前现状：
  - 前台 API 使用 `/api/v1`；
  - 目前没有明确的版本变更策略。
- 问题：
  - 本地上传器发布后，接口变更会影响已安装客户端；
  - 当前项目虽未发布第一版，但一旦本地工具落地，就需要版本治理。
- 优化建议：
  1. 冻结 `v1` 上传、认证、状态接口；
  2. 破坏性调整在未发布阶段可以直接收口，但发布前要完成文档同步；
  3. API 返回服务端能力版本，例如 `GET /api/v1/capabilities`；
  4. 本地上传器启动时检查最小服务器版本。

## 7. 数据库与查询性能优化

### O-015 数据库索引补齐

- 优先级：P1
- 当前现状：
  - schema 中定义了主键和部分 unique；
  - 迁移里未看到针对常用查询的复合索引。
- 问题：
  - 大量查询按 `userId`、`visibility`、`status`、`createdAt` 排序；
  - 搜索使用 `ilike`；
  - 房间内容和用户主页随着数据增长会退化。
- 优化建议：
  1. 为 `cards(user_id, visibility, status, created_at desc)` 建索引；
  2. 为 `cards(room_id, visibility, status, created_at desc)` 建索引；
  3. 为 `boxes(user_id, visibility, created_at desc)` 建索引；
  4. 为 `boxes(room_id, visibility, created_at desc)` 建索引；
  5. 为 `rooms(user_id, visibility, created_at desc)` 建索引；
  6. 为 `cards(card_file_id)` 和 `boxes(box_file_id)` 建索引；
  7. 搜索后续考虑 PostgreSQL trigram 或全文索引，技术选型需先确认。

### O-016 分页查询下推到数据库

- 优先级：P1
- 当前现状：
  - 多处使用 `findMany()` 拉出全部数据后在内存中 `slice()`；
  - 涉及 `CardService.listByUser`、`BoxService.listByUser`、discover、admin 列表等。
- 问题：
  - 数据量增长后内存和响应时间不可控；
  - 管理后台搜索和公开发现页尤其明显；
  - total 计算与分页 items 应拆成数据库 count + limit/offset。
- 优化建议：
  1. 所有分页接口改为数据库 `limit` / `offset`；
  2. total 使用 `count()`；
  3. 复杂列表按服务层提供统一分页工具；
  4. 搜索接口分别返回各类型 total 或明确只返回当前页摘要；
  5. 长期可考虑 cursor pagination。

### O-017 房间 slug 唯一约束

- 优先级：P1
- 当前现状：
  - `ensureUniqueSlug()` 在应用层循环检查；
  - 数据库没有 `rooms(user_id, slug)` 唯一约束。
- 问题：
  - 并发创建同名房间可能产生重复 slug；
  - 后续如果增加 slug 路由，会有不确定行为。
- 优化建议：
  1. 数据库增加 `unique(user_id, slug)`；
  2. 创建和重命名房间时捕获唯一约束冲突并重试；
  3. 如果当前前端不暴露房间，也应先把数据层约束补齐。

### O-018 内容删除一致性

- 优先级：P1
- 当前现状：
  - 用户删除卡片会删除资源、HTML、封面；
  - 管理员删除卡片删除资源和 HTML，但未看到删除卡片封面对象；
  - 箱子当前主要删除数据库记录。
- 问题：
  - 不同入口删除同一类内容的对象存储清理口径不一致；
  - 可能产生孤儿对象；
  - 箱子未来如果有封面资源，也需要正式清理。
- 优化建议：
  1. 抽出 `ContentDeletionService`；
  2. 用户删除和管理员删除复用同一路径；
  3. 删除卡片时统一删除 `CARD_RESOURCES`、`CARD_HTML`、`COVERS/cards/...`；
  4. 删除房间封面、头像更新旧头像时也应考虑旧对象清理；
  5. 增加对象存储孤儿扫描工具。

## 8. 卡片/箱子处理流水线优化

### O-019 卡片流水线阶段化记录

- 优先级：P0
- 当前现状：
  - 卡片只有 `pending`、`processing`、`ready`、`error`；
  - 详细阶段只写 console 日志；

- 问题：
  - 上传器和网页端无法准确展示处理进度；
  - 运维无法知道大量失败集中在哪个阶段；
  - 失败恢复只能靠人工重新上传。
- 优化建议：
  1. 数据库记录 `pipelineStage`；
  2. 阶段包括 unpack、inline-richtext、upload-assets、rewrite、pack、convert-html、upload-html、commit-db；

  4. 失败写入 `errorCode`、`errorStage`、`retryable`；
  5. 管理后台展示阶段分布。

### O-020 Host 集成层生产化

- 优先级：P1
- 当前现状：
  - API 启动时初始化 `HeadlessHostShell`；
  - 工作区启动前会清空 `.chips-server-host`；
  - 默认插件来自生态仓库路径或 dist cpk；
  - 缺少 Host 集成健康检查接口。
- 问题：
  - API 服务启动强依赖 Host 与插件安装成功；
  - 生产镜像内插件构建/复制链路较重；
  - 插件缺失时错误对业务用户不友好；
  - Host 运行状态无法被健康检查区分。
- 优化建议：
  1. 增加 `GET /api/v1/health/ready` 检查 DB、Redis、S3、Host、插件；
  2. Host 插件清单和版本写入启动快照；
  3. 生产镜像中只放正式构建产物，减少源码复制范围；
  4. Host 初始化失败应让 readiness 失败，普通 liveness 仍可返回；
  5. Worker 化后由 Worker 初始化 Host，API 进程可不承载重型转换能力。

### O-021 卡片 HTML 与封面发布一致性

- 优先级：P1
- 当前现状：
  - 内容 HTML 和封面 HTML 分别上传；
  - 数据库最后统一写 ready；
  - 若对象存储部分成功后后续失败，可能留下部分对象。
- 问题：
  - 失败重试可能覆盖或遗留对象；
  - 没有发布事务或清理补偿。
- 优化建议：
  1. 发布使用临时 key 前缀；
  2. 全部成功后再切换为正式 key；
  3. 失败时清理临时前缀；
  4. 数据库记录发布版本或 revision；
  5. 对象存储写入后记录 manifest，便于清理和审计。

### O-022 箱子上传处理补齐

- 优先级：P1
- 当前现状：
  - `.box` 上传同步解包并写入数据库；
  - 当前没有像卡片一样的资源发布流水线；
  - 封面 URL 字段存在，但上传 `.box` 未看到正式封面资源处理。
- 问题：
  - 箱子如果包含自有资源、封面或布局配置资源，服务器端处理不完整；
  - 箱子引用卡片只在读取时做社区匹配；
  - 本地上传器无法获知箱子资源是否被完整发布。
- 优化建议：
  1. 按箱子文件格式规范重新核对 `.box` 资源目录；
  2. 为箱子建立与卡片类似但更轻的处理任务；
  3. 上传箱子自有资源到对象存储；
  4. 解析并发布封面；
  5. 记录引用卡片匹配结果和未匹配原因；
  6. 后续箱子在线运行时需要 session 化加载条目和资源。

## 9. 对象存储与资源治理优化

### O-023 私有内容资源访问控制

- 优先级：P1
- 当前现状：
  - bucket 当前统一公开读；
  - 内容层通过 API 控制私有卡片/箱子的详情可见性；
  - 但卡片 HTML / 资源 URL 一旦获得，可直接访问对象存储公开 URL。
- 问题：
  - `visibility = private` 对已发布对象资源不构成真正访问控制；
  - 私有卡片如果完成 HTML 发布，资源 URL 可能被分享访问。
- 优化建议：
  1. 明确当前 `private` 是否只是社区列表隐藏，还是资源层私有；
  2. 如果要真正私有，私有资源不能放公开 bucket；
  3. 使用签名 URL、代理鉴权或私有 bucket；
  4. visibility 变更时需要迁移或重新发布资源访问策略；
  5. 该项属于正式权限契约，落地前必须同步共用 API 契约。

### O-024 对象存储清理与审计

- 优先级：P1
- 当前现状：
  - 删除部分内容时会按前缀删除对象；
  - 没有对象 manifest；
  - 没有孤儿对象巡检。
- 问题：
  - 流水线失败、管理删除口径不一致、重复上传都可能留下对象；
  - 存储成本不可见。
- 优化建议：
  1. 每个上传任务记录对象清单；
  2. 删除内容按清单删除，前缀删除作为兜底；
  3. 定期扫描 DB 与对象存储，输出孤儿对象报告；
  4. 管理后台展示用户存储占用明细；
  5. 支持按用户、内容、任务维度导出审计。

### O-025 资源缓存与 CDN 头治理

- 优先级：P2
- 当前现状：
  - 对象存储上传时设置 Content-Type；
  - 没有看到 Cache-Control、ETag 口径由业务统一治理。
- 问题：
  - HTML、JS、CSS、图片缓存策略应不同；
  - 重新发布同 key 时浏览器/CDN 可能缓存旧内容；
  - 公开资源长期缓存可提升性能，但需要版本化 key。
- 优化建议：
  1. HTML 使用短缓存或 no-cache；
  2. 内容资源使用 hash key 和长缓存；
  3. 卡片发布输出使用 revision 目录；
  4. 数据库记录当前 revision 的入口 URL；
  5. 对象存储 metadata 统一由上传服务设置。

  2. mock S3 或使用本地测试 bucket；
  3. 跑 `runCardPipeline()` 并断言数据库状态；
  4. 校验 htmlUrl、coverUrl、metadata、structure；
  5. 失败样本覆盖缺 metadata、缺资源、转换失败。

### O-040 前后台 E2E 烟测

- 优先级：P1
- 当前现状：
  - web/admin 只有 build 脚本，未看到 E2E；
  - 工作区上传体验靠人工验证。
- 问题：
  - 登录、上传、个人页查看、后台删除这些主链路容易回归；
  - Web 插件宿主涉及 iframe/postMessage，尤其需要浏览器测试。
- 优化建议：
  1. 增加 Playwright E2E；
  2. 覆盖注册/登录/上传/轮询/打开卡片；
  3. 覆盖后台登录、用户禁用、内容删除；
  4. 覆盖 `/cards/:cardId` Web 插件宿主不空白；
  5. CI 中至少跑 smoke 套件。

## 14. 文档与契约治理优化

### O-041 本地上传器 API 专章

- 优先级：P0
- 当前现状：
  - 共用 API 契约列出了上传接口；
  - 没有本地上传器登录、refresh、幂等、任务状态、错误处理完整专章。
- 问题：
  - 本地上传器如果直接读网页端代码，很容易形成非正式口径；
  - 后续客户端多语言实现会漂移。
- 优化建议：
  1. 当前先在项目日志中设计；
  2. 服务器实现落地后同步到共用 API 契约；
  3. 提供 curl 示例、Node 示例、错误码表；
  4. 明确 token 保存、安全建议、重试策略；
  5. 明确 upload capabilities 与最小服务器版本。

### O-042 内部技术文档与代码同步机制

- 优先级：P1
- 当前现状：
  - 社区服务器技术文档较完整；
  - 代码已有不少新能力和生产部署补丁；
  - git 状态显示当前已有多处未提交修改。
- 问题：
  - 文档“最后核对时间”可能落后于当前代码；
  - 生产部署、对象存储、上传并发等能力需要持续同步。
- 优化建议：
  1. 每次改 server 路由或 env 时同步 `技术文档/07-启动与运行说明.md`；
  2. 每次改公开 API 时同步共用契约；
  3. 每次改上传页或上传流程时同步 `技术文档/04-工作区上传页技术方案.md`；
  4. 文档中记录核对日期和真实代码路径；
  5. CI 或脚本检查 OpenAPI 快照与文档中的接口清单。

## 16. 需要进一步确认的问题

1. 私有内容是否必须做到对象存储层真正不可公开访问，还是第一版只做社区页面隐藏；
2. 本地上传器是否面向用户个人使用，还是也允许服务端自动化/CI 上传；
3. 本地上传器登录方式优先采用设备码、浏览器跳转、还是账号密码登录增强版；
4. 上传重复策略是默认覆盖、创建新版、返回已有内容，还是由用户选择；
5. `.box` 文件是否在第一版需要完整发布自有资源和封面；
6. 社区服务器是否准备多实例部署；如果是，Worker 队列和对象存储临时区需要更早落地；
7. 是否需要保留“社区内 `.card` 回下载”能力；当前共用契约明确不在范围内，但本地上传器后续可能自然需要同步下载/备份。

## 17. 当前不建议做的事

1. 不建议直接在本地上传器里长期保存用户明文密码；
2. 不建议继续扩大 `setImmediate()` 进程内 pipeline 的职责；
3. 不建议让本地上传器绕过服务器正式校验直接写对象存储；
4. 不建议在没有幂等键的情况下支持大规模批量上传；
5. 不建议把私有内容继续定义含糊，必须尽早明确“列表隐藏”还是“资源不可访问”；
6. 不建议只改前端上传体验而不补服务器任务模型；
7. 不建议新增第三方限流、队列、搜索依赖前不先冻结生态技术选型。
