## 3. 本轮目标与结果概览

本轮围绕四个性能问题落地：

| 优先级 | 优化项 | 实施结果 |
| --- | --- | --- |
| P0 | 修正静态资源缓存头冲突 | 已在外层 Nginx 拆出 `/assets/` 与 `/admin/assets/` 长缓存 location，HTML fallback 保持 `no-cache` |

- 卡片详情页切换“查看封面”后白屏，是因为长正文 iframe 高度被封面态继承，封面被垂直居中到可视区外。本轮已在 CardViewer 封面态和社区 Web 宿主层修复高度同步与滚动复位。

## 4. 静态资源缓存头优化

### 4.1 原问题

生产入口存在缓存头冲突：

1. 内层前端静态服务对 hash 静态资源设置长缓存；
2. 外层 `deploy/nginx/nginx.conf` 的 `location /` 又统一追加 `Cache-Control: no-cache`；
3. 浏览器和中间缓存收到多个缓存语义，可能保守回源，影响重复访问速度。

### 4.2 技术方案

在外层 Nginx 中按资源类型拆分 location：

1. `/assets/`
   - 代理到 `ccps_web/assets/`；
   - `proxy_hide_header Cache-Control`；
   - 只保留 `Cache-Control: public, max-age=31536000, immutable`。
2. `/admin/assets/`
   - 代理到 `ccps_admin/assets/`；
   - 同样只保留长缓存。
3. `/`
   - 继续作为前台 SPA HTML fallback；
   - 保持 `Cache-Control: no-cache`。
4. `/admin/`
   - 继续作为后台 HTML fallback；
   - 不再和 `/admin/assets/` 混用缓存语义。
5. `/api/` 与 `/admin/api/`
   - 继续走 server upstream；
   - 不对 API 增加静态资源长缓存。

### 4.3 修改文件

- `Chips-CommunityPlatformServer/deploy/nginx/nginx.conf`
- `Chips-CommunityPlatformServer/技术文档/09-生产域名与对象存储部署说明.md`

### 4.4 设计取舍

本轮不改变 Vite 构建产物命名，也不改内层 web/admin Nginx 配置。原因是 hash 静态资源本身已适合 immutable 缓存，问题主要出在外层反代把 HTML fallback 策略套到了静态资源路径上。

## 5. 卡片打开页轻量化与预取

### 5.1 原问题

`/cards/:cardId` 原先先请求完整详情接口：

- `GET /api/v1/cards/:cardId`

该接口会返回：

- `cardMetadata`
- `cardStructure`
- `fileSizeBytes`
- 其他详情字段

但卡片打开页只需要决定：

1. 卡片是否 ready；
2. 标题是什么；
3. 正文 HTML URL 是什么；
4. 封面 URL 和比例是什么；
5. 当前用户是否有访问权限。

完整详情接口会把 JSONB 带入打开热路径，卡片越复杂，首个接口越重。

### 5.2 服务端技术方案

新增轻量接口：

```http
GET /api/v1/cards/:cardId/open-view
```

响应字段：

```ts
{
  id: string;
  title: string;
  status: "pending" | "processing" | "ready" | "error";
  htmlUrl: string | null;
  coverUrl: string | null;
  coverRatio: string | null;
  visibility: "public" | "private";
  createdAt: string;
  updatedAt: string;
  user: PublicUserProfile | null;
}
```

实现要点：

1. `CardService.getOpenViewAccessible()` 只选取打开页需要的列；
2. `CardService.toOpenViewDTO()` 不返回 `cardMetadata`、`cardStructure`、`fileSizeBytes`；
3. 权限口径和详情接口一致：
   - 公开卡片可匿名访问；
   - 私有卡片只允许所有者访问；
   - 无权访问按 `CARD_NOT_FOUND` 处理，不暴露存在性。

### 5.3 前端技术方案

前端新增内存 Promise 缓存：

- `packages/web/src/lib/card-open-view-prefetch.ts`

核心行为：

1. `prefetchCardOpenView(cardId)` 以 cardId 为 key 保存请求 Promise；
2. 多次 hover/focus/近视口命中同一卡片时复用同一个 Promise；
3. 请求失败后删除缓存，避免缓存错误状态；
4. `CardDetailPage` 优先读取预取缓存，未命中才发起接口请求。

个人页作品卡预取入口：

- `WorkTile` 在非管理模式下，只对 `type = card` 的作品启用预取；
- 触发条件：
  1. hover；
  2. focus；
  3. IntersectionObserver 接近视口，`rootMargin: 360px 0px`。

前端启动时还增加资源预连接：

- `packages/web/src/lib/resource-hints.ts`
- 默认预连接 `https://file.chipscard.space`
- 若配置 `VITE_CCPS_RESOURCE_ORIGIN`，则使用配置来源
- 若资源来源与当前页面同源，则不写入额外 hint

### 5.4 保留的正式链路

本轮没有绕开 CardViewer：

1. `/cards/:cardId` 仍创建 `com.chips.card-viewer` Web 插件会话；
2. `htmlUrl` 仍作为 `webDocumentUrl` 传入 CardViewer；
3. CardViewer 内部仍用正式托管文档 iframe 承载对象存储 HTML；
4. 图片打开仍通过 `resource.open` 进入 `com.chips.photo-viewer`。

## 6. 数据库分页、DTO 瘦身与索引

### 6.1 原问题

多处列表存在增长风险：

1. 服务层先 `findMany` 查询全量，再在内存 `slice`；
2. 列表 DTO 可能读取完整 JSONB；
3. 缺少面向用户页、房间页、发现页的复合索引；
4. 管理后台用户列表还会对每个用户重复计算存储量。

这些问题在数据少时不明显，但会让接口耗时随总内容量增长，而不是随 pageSize 保持稳定。

### 6.2 技术方案

统一改为数据库分页：

```ts
limit: pageSize
offset: (page - 1) * pageSize
```

分页总数使用独立 `count()`：

```ts
db.select({ count: count() }).from(table).where(where)
```

DTO 分层：

1. `CardSummaryRecord`
   - 只包含列表需要字段；
   - 不读取 `cardMetadata` / `cardStructure`。
2. `CardOpenViewRecord`
   - 只包含卡片打开页字段；
   - 不读取详情 JSONB。
3. `BoxSummaryRecord`
   - 只包含箱子列表字段；
   - 不读取完整 `metadata` / `structure`。

### 6.3 已调整的查询区域

服务层：

- `CardService.listByUser`
- `CardService.listByRoom`
- `CardService.listRootByUser`
- `BoxService.listByUser`
- `BoxService.listByRoom`
- `BoxService.listRootByUser`

路由：

- `GET /api/v1/discover/cards`
- `GET /api/v1/discover/boxes`
- `GET /api/v1/search`
- `GET /admin/api/v1/users`
- `GET /admin/api/v1/content`
- `GET /api/v1/users/:username/space`
- `GET /api/v1/rooms/:roomId/contents`

N+1 收口：

- `BoxService.enrichCardRefs` 收集 `card_id` 后使用 `inArray(cards.cardFileId, ids)` 一次查询，再用 Map 匹配引用。
- 管理后台用户列表按当前页用户 ID 聚合卡片/箱子存储量，避免每个用户单独查询。

### 6.4 新增普通列

目的：

## 7. 上传流水线队列化

### 7.1 原问题

原上传流程：

1. API 接收 `.card`；
2. 创建卡片记录；
3. 用 `setImmediate()` 在 API 进程里调用 `runCardPipeline()`；
4. 转换、资源上传、HTML 生成和封面导出都发生在 API 进程。

风险：

1. API 进程被 CPU、磁盘 IO、对象存储上传拖慢；
2. 批量上传会影响普通接口响应；
3. 进程重启会丢失进程内任务；
4. 缺少统一重试、锁定、失败记录和 worker 并发治理。

### 7.2 数据模型

新增表：

- `card_pipeline_jobs`

关键字段：

| 字段 | 含义 |
| --- | --- |
| `id` | 任务 ID |
| `card_id` | 对应社区卡片 ID |
| `user_id` | 上传用户 |
| `source_bucket` | 原始 `.card` 内部任务对象 bucket |
| `source_key` | 原始 `.card` 内部任务对象 key |
| `status` | `queued` / `processing` / `succeeded` / `failed` |
| `retry_count` | 当前重试次数 |
| `max_retries` | 最大重试次数 |
| `last_error` | 最近错误 |
| `locked_by` | 当前 worker ID |
| `locked_at` | 锁定时间 |
| `finished_at` | 完成时间 |

约束与索引：

1. `card_id` 唯一，避免同一张卡重复入队；
2. `(status, created_at)` 索引用于队列状态巡检；
3. 外键级联删除到 `cards` 和 `users`。

### 7.3 对象存储分层

新增私有逻辑 bucket：

- `chips-card-pipeline-inputs`

用途：

1. API 上传后，把原始 `.card` 保存为内部任务对象；
2. worker 从该对象下载到专属临时目录；
3. 转换成功后删除该内部对象；
4. 该 bucket 不加入公开读 bucket 列表。

`S3_BUCKET_NAME` 单物理 bucket 模式下：

1. 公开 bucket 仍映射进共享物理 bucket；
2. `chips-card-pipeline-inputs` 始终保持独立私有 bucket；
3. 公开 URL 仍使用逻辑 bucket 路径，前端不感知物理 bucket 合并。

### 7.4 API 入队流程

`POST /api/v1/upload/card` 新流程：

1. 校验登录；
2. 以流式方式写入临时文件，同时限制最大尺寸；
3. 校验 `.card` 扩展名；
4. 校验 room 权限和 visibility；
5. 创建 `cards` 记录，状态为 `pending`；
6. 上传原始 `.card` 到 `chips-card-pipeline-inputs/{userId}/{cardId}/source.card`；
7. 插入 `card_pipeline_jobs`；
8. 把 jobId `LPUSH` 到 Redis 队列 `ccps:card-pipeline:queue`；
9. 删除 API 本地临时文件；
10. 返回 `202`：

```json
{
  "data": {
    "cardId": "...",
    "status": "pending"
  }
}
```

若入队失败：

1. 卡片状态置为 `error`；
2. 清理已上传的内部任务对象；
3. 返回 `CARD_PIPELINE_ERROR`。

### 7.5 Worker 流程

新增入口：

- `packages/server/src/worker.ts`

启动顺序：

1. 运行数据库迁移；
2. 连接 Redis；
3. 初始化对象存储 bucket；
4. 初始化 Host 集成层；
5. 重排超时 `processing` 任务；
6. 按 `CARD_PIPELINE_WORKER_CONCURRENCY` 启动消费循环。

消费流程：

1. `BRPOP ccps:card-pipeline:queue` 取 jobId；
2. 通过数据库条件更新把 `queued` 任务锁定为 `processing`；
3. 下载 `source.card` 到专属临时目录；
4. 调用既有 `runCardPipeline()`；
5. 校验卡片最终状态必须为 `ready`；
6. 成功：
   - job 标记为 `succeeded`；
   - 删除内部任务对象。
7. 失败：
   - `retry_count + 1`；
   - 未超过 `max_retries` 时重新置为 `queued` 并延迟重入 Redis；
   - 超过最大重试后 job 标记为 `failed`，卡片状态置为 `error`。
8. 最终清理 worker 本地临时目录。

### 7.6 环境变量

新增：

- `CARD_PIPELINE_WORKER_CONCURRENCY`
  - 默认 `1`
  - 控制 worker 消费循环数量
- `CARD_PIPELINE_JOB_MAX_RETRIES`
  - 默认 `2`
  - 控制最大失败重试次数
- `CARD_PIPELINE_RETRY_DELAY_MS`
  - 默认 `5000`
  - 控制失败重试前等待时间
- `CARD_PIPELINE_QUEUE_POLL_TIMEOUT_SEC`
  - 默认 `5`
  - 控制 `BRPOP` 阻塞等待时间

## 8. Host 集成层运行目录拆分

### 8.1 原问题

API 与 worker 都会初始化 Host 集成层。如果两者复用同一个 Host 运行目录，可能在插件安装、启用、缓存文件上互相抢占。

### 8.2 技术方案

`host-integration.ts` 为不同进程使用不同运行目录：

- API：`.chips-server-host-server`
- Worker：`.chips-server-host-worker`

这样 API 与 worker 可以各自初始化 Host 插件运行环境，避免同目录竞争。

### 8.3 修改文件

- `packages/server/src/services/host-integration.ts`
- `Chips-CommunityPlatformServer/技术文档/07-启动与运行说明.md`

## 10. CardViewer 封面切换白屏修复

### 10.1 现象

在社区卡片查看页中：

1. 打开一张长正文卡片；
2. 滚动到正文中段；
3. 点击右上角“查看封面”；
4. 按钮变为“查看内容”，说明事件已经送达 CardViewer；
5. 但浏览器可视区域显示空白，看不到封面。

### 10.2 排查结论

封面资源正常：

1. `GET /api/v1/cards/:cardId/open-view` 正常返回 `coverUrl`；
2. 对象存储中的 `cover.html` 正常 `200`；
3. CardViewer 启动参数中包含 `coverUrl` 和 `coverRatio`；
4. 点击后 CardViewer 状态已切换到 cover。

真正原因：

1. 长正文通过 `plugin.surface.resize` 把外层插件 iframe 撑到 2844px；
2. 切换到封面时，外层 iframe 仍保留这个旧高度；
3. CardViewer 封面态使用 `100vh` 居中；
4. iframe 内部的 `vh` 以 2844px 为基准；
5. 封面被垂直居中到浏览器可视区下方，用户看到空白。

### 10.3 技术方案

CardViewer 侧：

1. `ViewerCoverSurface` 挂载后发布 `plugin.surface.resize`；
2. 封面 iframe ready/error 后补发稳定高度；
3. resize / visualViewport resize 时重新发布；
4. 社区 document surface 下封面态 `min-height: 0`，不再使用旧正文高度做垂直居中基准。

社区 Web 宿主侧：

1. `HostedPluginSurface.dispatchChromeAction()` 在 document surface 下先把 iframe 高度重置到当前浏览器视口；
2. 同时 `scrollIntoView({ block: "start" })` 回到 surface 顶部；
3. 再发送 `plugin.chrome.action` 给插件。

### 10.4 修改文件

- `Chips-CardViewer/src/components/ViewerCoverSurface.tsx`
- `Chips-CardViewer/src/components/ViewerCoverSurface.css`
- `Chips-CardViewer/tests/unit/viewer-cover-surface.test.tsx`
- `Chips-CommunityPlatformServer/packages/web/src/components/HostedPluginSurface.tsx`
- `Chips-CommunityPlatformServer/技术文档/08-社区Web插件宿主链路.md`

## 14. 当前风险与后续建议

### 14.1 Nginx 生产验证

本轮已更新 Nginx 配置，但本地没有在 Docker Nginx 容器内完成最终 `nginx -t` 和线上 curl 头部验证。部署前建议执行：

```bash
docker compose -f Chips-CommunityPlatformServer/deploy/docker-compose.yml config
nginx -t
curl -I https://www.chipscard.space/assets/<hash>.js
curl -I https://www.chipscard.space/
curl -I https://www.chipscard.space/admin/assets/<hash>.js
```

期望：

1. `/assets/*` 只有长缓存；
2. `/admin/assets/*` 只有长缓存；
3. `/` HTML fallback 是 `no-cache`；
4. API 不被静态资源长缓存影响。

### 14.2 队列可观测性

当前队列表和日志已经具备基础追踪能力，但还缺少管理后台视图。后续建议：

1. 增加队列积压数量；
2. 增加失败任务列表；
3. 增加手动重试；
4. 增加 worker 心跳与最后处理时间；
5. 增加转换阶段耗时统计。

### 14.3 数据库分页模式

本轮使用 `limit/offset`，适合第一阶段快速稳定落地。后续内容量进一步增长时建议评估游标分页：

1. 个人页作品流；
2. 发现页；
3. 管理后台内容列表；
4. 搜索结果。

### 14.4 封面 iframe 成本

当前个人页仍使用卡片封面 HTML iframe。虽然打开页预取已经降低进入详情等待，但作品网格大量 iframe 仍有成本。后续建议上传流水线生成封面快照图片：

1. 列表默认展示快照；
2. 详情和正式查看态继续使用 `cover.html`；
3. 管理后台可查看封面快照生成失败任务。
