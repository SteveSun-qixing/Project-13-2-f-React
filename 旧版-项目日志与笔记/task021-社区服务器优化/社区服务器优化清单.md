## 1. 文档定位

## 2. 总体判断

当前社区服务器已经打通正式 Web 插件宿主、对象存储公开资源、卡片上传转换和生产域名链路。主要优化空间不在单一功能错误，而在多层延迟叠加：

1. 卡片网页打开链路层级偏多，存在多个串行请求与双层 iframe。
2. 前台、插件、卡片 HTML、对象存储资源的缓存策略没有形成统一分层。
3. 列表接口与个人页存在“查询全量再分页 / 前端拉全量”的增长风险。
4. 数据库迁移目前缺少面向核心列表查询的二级索引。
5. 上传流水线仍运行在 API 进程内，缺少队列化、并发治理、失败重试和可观测性。
6. Nginx、Docker、Redis、PostgreSQL、对象存储、监控告警还有生产化强化空间。

## 3. 优先级总览

| 优先级 | 优化项 | 预期收益 |
| --- | --- | --- |
| P0 | 修正静态资源缓存头冲突 | 立即改善重复访问与浏览器缓存命中 |
| P0 | 卡片打开页减少串行等待与预取 | 明显改善打开卡片网页的体感速度 |
| P0 | 数据库分页与索引 | 避免内容增长后接口越来越慢 |
| P1 | 封面 iframe 替换为缩略图或封面快照 | 改善个人页/作品列表滚动和首屏资源压力 |
| P1 | 上传流水线队列化 | 避免转换任务拖垮 API 进程 |
| P1 | 对象存储资源分层缓存与压缩策略 | 降低资源加载成本和回源压力 |
| P1 | API 响应瘦身 | 降低卡片详情和列表接口传输与序列化成本 |
| P2 | Docker 镜像瘦身与构建缓存 | 降低部署时间、镜像体积和回滚成本 |
| P2 | 可观测性与告警 | 缩短性能问题定位时间 |
| P2 | 安全、限流、备份和运维自动化 | 提升生产稳定性 |

## 4. 前台与卡片打开链路优化

### 4.1 `/cards/:cardId` 打开链路过长

现状：

- `packages/web/src/pages/CardDetailPage.tsx` 先请求 `GET /api/v1/cards/:cardId`。
- 卡片 ready 后再请求 `POST /api/v1/host/plugin-sessions` 创建 `com.chips.card-viewer` 会话。
- `HostedPluginSurface` 再加载 `/api/v1/host/plugin-sessions/:sessionId/entry`。
- `CardViewer` 启动后，`HostedDocumentWindow` 再用内部 iframe 加载对象存储 `htmlUrl`。

影响：

- 首次打开一张卡至少经历社区 SPA、卡片详情 API、插件会话 API、插件入口 HTML、插件 JS/CSS、卡片 HTML、卡片内部资源等多段请求。
- 任一环节 300ms-800ms，串起来就会形成明显“打开慢”。

建议：

1. 保留正式插件宿主链路，但为社区 Web 增加“卡片文档直达轻量宿主”能力：入口仍由 Host 会话授权与 bridge 约束，但页面层少启动一整个 CardViewer React 应用。
2. 在 `CardDetailPage` 中把创建会话与详情加载做更激进的早启动。拿到卡片基础状态和 `htmlUrl` 后立即创建会话，不等待额外 UI 状态稳定。
3. 从个人页作品卡 hover、focus、触达视口时预取 `GET /api/v1/cards/:cardId`，并预连接 `https://file.chipscard.space`。
4. 对 `CardViewer` Web 场景做专门入口拆分，只加载托管文档窗口所需代码，避免把本地文件打开、拖拽区等桌面场景代码一起进入卡片网页首屏。

### 4.2 插件入口缓存过保守

现状：

- `packages/server/src/routes/host-runtime.ts` 对插件入口 `entry` 和 `bootstrap.js` 设置 `Cache-Control: no-store`。
- 插件静态资源只设置 `public, max-age=300`。

影响：

- 每次打开卡片都会重新请求插件入口和 bootstrap。
- CardViewer / PhotoViewer 产物带 hash 文件名，理论上适合长缓存，但当前服务端只给 5 分钟缓存。

建议：

1. `entry` 可以保持短缓存或 `no-cache`，因为它注入 sessionId。
2. `bootstrap.js` 包含 sessionId 和 launchParams，不适合跨会话长缓存，但可以考虑内联到 entry，减少一次请求。
3. `/assets/*` 这类 hash 产物改为 `Cache-Control: public, max-age=31536000, immutable`。
4. 插件入口 HTML 中只注入极小 bootstrap，桥接通用逻辑改成可长缓存静态脚本，session 数据通过内联 JSON 或短接口提供。

### 4.3 前台生产静态资源缓存头冲突

现状：

- `deploy/nginx/web.conf` 对 `/assets/` 设置长缓存。
- 外层 `deploy/nginx/nginx.conf` 的 `location /` 统一追加 `Cache-Control: no-cache`。
- 线上静态 JS/CSS 出现两个 `Cache-Control` 响应头：一个长缓存，一个 `no-cache`。

影响：

- 缓存语义不清晰，部分浏览器或中间缓存可能保守回源。

建议：

1. 在外层 Nginx 增加单独 `location /assets/` 代理到 `ccps_web`，只保留长缓存。
2. `location /` 仅用于 SPA HTML，并设置 `no-cache` 或较短缓存。
3. 对 admin 前端同样处理 `/admin/assets/` 的长缓存策略。

### 4.4 个人页作品封面 iframe 成本偏高

现状：

- `WorkTile` 对卡片封面使用 iframe 加载 `coverUrl`。
- 多个作品卡同时出现在页面中时，会创建多个 iframe 文档上下文。

影响：

- iframe 自身创建成本高。
- 封面 HTML 若包含脚本、字体、图片，会拖慢作品网格。
- 手机端滚动时容易产生内存与合成层压力。

建议：

1. 上传流水线增加封面缩略图生成产物，例如 `cover.webp` 或 `cover.avif`。
2. 列表页优先展示图片缩略图；只有用户打开详情或需要交互封面时再加载 HTML 封面。
3. 若短期必须保留 iframe，至少限制首屏外 iframe 的挂载数量，使用 IntersectionObserver 到近视口再挂载。
4. 给封面 iframe 固定尺寸、禁止不必要脚本，并审查封面 HTML 的资源体积。

## 5. API 与数据模型优化

### 5.1 列表接口使用“查全量再 slice”

现状：

- `CardService.listByUser/listByRoom/listRootByUser`、`BoxService.listByUser/listByRoom/listRootByUser`、`discoverRoutes`、`search` 中多处先 `findMany` 取全量，再在内存中 `slice`。

影响：

- 当前数据少时不明显；内容一多，数据库、Node 内存、JSON 序列化都会增长。
- 分页接口的响应时间会随总量增长，而不是随 pageSize 保持稳定。

建议：

1. 使用数据库 `limit` / `offset` 或游标分页。
2. `total` 使用单独 `count()` 查询。
3. 对发现页、个人页和房间页优先使用 `(visibility, status, created_at)`、`(user_id, visibility, status, created_at)` 等复合索引。
4. 搜索接口若继续用 `ilike`，需要明确数据规模边界；数据增长后引入 PostgreSQL trigram 索引或专门搜索服务。

### 5.2 前端个人页默认拉全量作品

现状：

- `packages/web/src/api/content.ts` 的 `fetchAllPages` 会按 `totalPages` 拉完所有页。
- `ProfilePage` 同时拉用户、所有卡片、所有箱子，再统一混排。

影响：

- 用户作品越多，个人页越慢。
- 多页并发请求可能挤占 API 与浏览器连接。

建议：

1. 增加服务端统一作品流接口，例如 `GET /api/v1/users/:username/works?page&pageSize`，服务端直接混排卡片和箱子。
2. 首屏只取首批作品，滚动加载下一页。
3. 管理模式需要全量选择时再按需分页拉取，不阻塞普通访问。

### 5.3 卡片详情响应过重

现状：

- `GET /api/v1/cards/:cardId` 返回 `cardMetadata`、`cardStructure`、`user` 等完整 detail。
- 打开卡片网页实际只需要 `id/title/status/htmlUrl/visibility` 等轻量字段。

影响：

- 传输体积和 JSON 序列化不必要增大。
- metadata/structure 随卡片复杂度增长后会影响首屏打开。

建议：

1. 增加轻量打开接口，例如 `GET /api/v1/cards/:cardId/open-view`。
2. 保留详情接口给资料页、后台或调试用。
3. 列表 DTO 不返回不参与首屏的字段。

### 5.4 房间计数存在 N+1 查询风险

现状：

- `GET /api/v1/users/:username/rooms` 对每个房间调用 `RoomService.getContentCounts`。

影响：

- 房间数量增加后，会产生 1 + 2N 次查询。

建议：

1. 用聚合 SQL 一次性取所有房间的可见卡片数和箱子数。
2. 或在房间列表接口中允许不返回计数，进入房间详情时再取。
3. 后续可以维护计数缓存字段，但要谨慎处理公开/私有可见口径。

### 5.5 箱子引用卡片 enrichment 存在 N+1 查询风险

现状：

- `BoxService.enrichCardRefs` 对 `structure.cards` 逐条查询社区卡片。

影响：

- 大箱子打开会变慢。

建议：

1. 收集所有 `card_id` 后使用 `inArray(cards.cardFileId, ids)` 一次查询。
2. 用 Map 在内存中匹配引用。
3. 给 `cards.card_file_id` 建索引。

## 6. 数据库优化

### 6.1 缺少核心查询索引

现状：

- 初始迁移只创建主键、唯一约束和外键，未看到面向列表查询的二级索引。
- 高频查询包括按 user、room、visibility、status、created_at 排序。

建议新增索引：

1. `cards(user_id, visibility, status, created_at DESC)`
2. `cards(room_id, visibility, status, created_at DESC)`
3. `cards(visibility, status, created_at DESC)`
4. `cards(card_file_id)`，用于箱子引用匹配
5. `boxes(user_id, visibility, created_at DESC)`
6. `boxes(room_id, visibility, created_at DESC)`
7. `boxes(visibility, created_at DESC)`
8. `rooms(user_id, visibility, created_at DESC)`
9. `rooms(user_id, slug)` 唯一索引，配合 slug 唯一逻辑
10. `users(username_lower)` 已唯一，继续保持

### 6.2 JSONB 字段不应进入普通列表热路径

现状：

- `cards.card_metadata/card_structure` 和 `boxes.metadata/structure` 是 JSONB。
- 当前 DTO 容易把完整 JSONB 带出去。

建议：

1. 列表和打开页只读必要列。
2. 若需要封面比例、描述、标签等热字段，考虑冗余为独立列。
3. JSONB 仅在详情、后台审核、调试和导入导出场景返回。

### 6.3 数据库连接池与慢查询基线

现状：

- 当前文档中未看到连接池参数、慢查询日志和执行计划基线。

建议：

1. 明确 `pg` 连接池最大连接数、空闲超时、连接超时。
2. 生产开启慢查询记录，先以 300ms 或 500ms 为阈值。
3. 对核心接口保存 `EXPLAIN ANALYZE` 基线。
4. 定期 `VACUUM/ANALYZE`，尤其是上传、删除频繁后。

## 7. 上传与转换流水线优化

### 7.1 卡片转换任务运行在 API 进程内

现状：

- `upload.ts` 接收 `.card` 后用 `setImmediate` 启动 `runCardPipeline`。
- 转换、打包、上传对象存储都在同一个 server 进程内执行。

影响：

- 高并发上传会抢占 API CPU、内存和 IO。
- 进程重启会丢失正在执行的任务。
- 缺少统一重试、暂停、恢复和并发控制。

建议：

1. 引入正式后台任务队列。可以基于现有 Redis 做队列，但若新增第三方库需要先决策。
2. API 只负责落库和入队；worker 负责转换。
3. 任务表记录 `queued/processing/succeeded/failed/retry_count/last_error`。
4. 转换 worker 设置全局并发，例如卡片转换 1-2 并发，资源上传按对象存储限流配置。

### 7.2 流水线缺少阶段耗时指标

现状：

- `runCardPipeline` 有阶段日志，但没有结构化指标和 traceId。

建议：

1. 每个阶段记录耗时：解包、资源上传、URL 替换、重新打包、HTML 转换、HTML 上传、封面导出、DB 更新。
2. 将 `cardDbId`、`userId`、`traceId` 写入结构化日志。
3. 统计失败原因分布，用于定位插件转换、对象存储、卡片格式三类问题。

### 7.3 临时目录和大文件治理

现状：

- 上传与转换大量使用 `os.tmpdir()`。
- 异常退出时可能残留临时文件。

建议：

1. 使用社区服务器专属临时根目录，例如 `.ccps-runtime/tmp`，便于巡检与清理。
2. 启动时扫描并清理过期临时目录。
3. 对转换工作目录设置磁盘水位保护，超过阈值暂停新上传。
4. 记录每次转换产生的临时目录大小与最终清理结果。

### 7.4 头像与房间封面上传使用内存拼接

现状：

- 头像和房间封面上传把文件流拼接成 Buffer 后调用 `uploadBuffer`。

影响：

- 当前 5MB 限制问题不大，但模式不适合未来扩展到更大媒体。

建议：

1. 小图可以保留 Buffer 模式。
2. 若未来支持大封面、视频封面或批量资源，应统一改成流式临时文件上传。
3. 上传图片前补充尺寸、像素数量、实际文件头校验，避免只信任 MIME。

## 8. 对象存储与 CDN 优化

### 8.1 写入时缺少业务化 Cache-Control 配置

现状：

- `uploadFile` / `uploadBuffer` 只设置 `ContentType`，未按资源类型设置缓存策略。
- 线上七牛资源当前返回了较长缓存，但这是对象存储/CDN侧策略，不由应用显式表达。

建议：

1. 应用上传时按 bucket 和扩展名设置 Cache-Control。
2. 不变 hash 资源：`public, max-age=31536000, immutable`。
3. 卡片 HTML 和封面 HTML：如果上传后不再覆盖同 key，可长缓存；如果同 key 会覆盖，则改成带版本 key 或短缓存。
4. 头像、房间封面这类固定 key 覆盖资源建议改成版本化 key，避免缓存旧图。

### 8.2 HTML 与资源 key 缺少版本化策略

现状：

- 卡片 HTML key 为 `${userId}/${cardId}/index.html`。
- 同一 cardId 若未来允许重新处理或更新，旧缓存可能难以失效。

建议：

1. 以内容 hash 或处理版本加入 key，例如 `${userId}/${cardId}/${version}/index.html`。
2. 数据库保存当前 active htmlUrl。
3. 旧版本资源通过异步清理任务删除。

### 8.3 图片体积与格式优化

现状：

- 示例卡片文件大小约 3.7MB，包含大图资源。
- 当前上传流水线替换 URL，但没有看到图片压缩、缩略图、多尺寸产物策略。

建议：

1. 生成列表缩略图、详情预览图、原图三档资源。
2. 优先输出 WebP/AVIF，保留原图作为查看器高质量资源。
3. 富图片卡片首屏先加载低清预览，再按需加载原图。
4. 对过大图片设置像素与文件体积提示。

## 9. Nginx 与网络入口优化

### 9.1 API 与前端缓存位置需要拆分

建议：

1. `location /assets/`、`/admin/assets/` 独立长缓存。
2. `location /` 和 `/admin/` 的 HTML fallback 保持 `no-cache`。
3. API 默认 `no-store` 或按具体接口设置短缓存。
4. 公开发现、公开用户资料等可短缓存 10-60 秒，并用用户态差异避免缓存私有数据。

### 9.2 HTTP/2 已启用，后续可评估 HTTP/3

现状：

- Nginx 使用 `listen 443 ssl http2`。

建议：

1. 先优化缓存和链路串行，再评估 HTTP/3。
2. 若目标用户跨地域访问明显，HTTP/3 + CDN 对资源域名更有价值。

### 9.3 TLS 与地理延迟

现象：

- 从当前网络环境轻量测试，`www.chipscard.space` 和 `file.chipscard.space` 首次 TLS/TTFB 有数百毫秒到 1 秒级波动。

建议：

1. 静态资源尽量走 CDN 边缘缓存。
2. 主站 API 如果用户集中在国内，应确认服务器地域、DNS、证书链和 CDN 接入策略。
3. 对 `file.chipscard.space` 开启 HTTP/2、Brotli/Gzip、边缘缓存命中率监控。

### 9.4 安全响应头重复

现象：

- Fastify Helmet 与 Nginx 都设置部分安全头，线上可见重复的 `X-Frame-Options`、`X-Content-Type-Options` 等。

建议：

1. 明确安全头由 Nginx 还是应用层负责。
2. 对插件 iframe 和远端卡片 HTML 的 CSP 单独治理，避免为了 Web 插件全局放宽。
3. 统一响应头后纳入部署验证脚本。

## 10. Docker 与部署优化

### 10.1 Server 镜像构建上下文大

现状：

- `Dockerfile.server` 复制多个生态仓库并构建 Host、CardViewer、PhotoViewer、基础卡片、布局、模块、主题。

影响：

- 构建时间长，镜像体积大。
- 任一生态仓库变动可能导致缓存失效。

建议：

1. 将插件构建产物作为发布前 artifact，server 镜像只复制已验证产物。
2. 区分运行时必需文件和源码、测试、文档、node_modules。
3. 使用 `.dockerignore` 明确排除 `node_modules`、测试结果、输出目录、日志、归档大文件。
4. 给 Host 插件安装源建立最小运行时目录。

### 10.2 生产容器缺少资源限制

现状：

- `docker-compose.yml` 未配置 CPU、内存限制和日志滚动。

建议：

1. 为 server、web、admin、postgres、redis、nginx 设置内存上限和 restart 策略。
2. 配置 Docker logging max-size/max-file，避免日志撑满磁盘。
3. 对转换 worker 独立容器设置更严格的 CPU/内存限制。

### 10.3 MinIO 在外部对象存储模式下仍默认启动

现状：

- Compose 总是定义并启动 MinIO。

建议：

1. 使用 profile 区分本地 MinIO 与生产外部对象存储。
2. 生产模式不启动 MinIO，减少资源占用和误用风险。
3. 文档中明确本地、生产两套 compose 启动命令。

## 11. Redis、认证与限流优化

### 11.1 可选认证接口仍会查 Redis 黑名单

现状：

- `optionalAuthenticate` 如果带 Bearer token，会验证 JWT 并查 Redis 黑名单。

建议：

1. 公开静态/匿名接口避免不必要地携带 Authorization。
2. 前端对公开页面可延迟恢复登录态，不阻塞内容展示。
3. 对访问频繁的公开接口评估是否需要 optional auth，或拆分公开版与本人版接口。

### 11.2 登录、上传、创建会话需要限流

现状：

- 登录失败有 Redis 计数。
- 但上传、插件会话创建、资源打开 plan 等接口未看到统一限流。

建议：

1. 增加 IP + 用户维度限流。
2. 上传接口限制并发、频率和每日总量。
3. `POST /api/v1/host/plugin-sessions` 防止被刷出大量 runtime sessions。
4. resource open plan 设置轻量缓存，减少重复解析。

### 11.3 Refresh 恢复不应阻塞公开内容直达页

现状：

- `AuthProvider` 在应用启动时立即请求 `/api/v1/auth/refresh`。
- `/cards/:id` 这类公开内容页也会进入同一个 App provider。

建议：

1. 公开内容直达页先渲染内容，登录态恢复异步完成。
2. 只有需要本人权限的页面或操作才阻塞等待 auth restore。
3. 减少访客访问公开卡片时的额外 API 请求。

## 12. Host Runtime 与插件会话优化

### 12.1 会话生命周期和数量需要治理

现状：

- 生产环境 `HostedPluginSurface` 卸载时删除会话。
- 页面异常关闭、网络中断、浏览器崩溃时可能无法发出 delete。

建议：

1. 服务端为 Web plugin session 设置 TTL。
2. 定时清理长时间无心跳会话。
3. 前端定期 heartbeat，后台用最后活跃时间判断。
4. 记录当前 session 数、按插件维度统计。

### 12.2 插件入口每次读磁盘

现状：

- `GET /entry` 每次 `fs.readFile(entry.entryPath, 'utf-8')`。

建议：

1. 对插件入口原始 HTML 做进程内缓存，按文件 mtime 或启动版本失效。
2. 注入 session 内容仍按请求生成。
3. 静态资源读取可交给 Fastify 静态插件或 Nginx/X-Accel，但需保持插件目录安全边界。

### 12.3 Bridge 本地能力可以拆分冷热路径

现状：

- bootstrap 中包含文件选择、对象 URL、本地文件 token 等能力。
- 卡片网页查看常用能力主要是 theme/i18n/resource.open/surface resize。

建议：

1. 为 document 查看场景生成更小 bootstrap。
2. 文件选择、保存、通知等低频能力延迟注入或按 action 动态加载。
3. bridge 消息加上耗时日志，定位插件内调用慢点。

## 13. 前端 bundle 与渲染优化

### 13.1 社区 Web 主 bundle 可以按路由拆分

现状：

- `packages/web` 构建输出单个 JS 约 240KB 未压缩。
- 首页、个人页、工作区、卡片详情、插件宿主页在同一 bundle。

建议：

1. 使用 `React.lazy` / route-level dynamic import 拆分页面。
2. `/cards/:id` 内容直达页只加载卡片打开所需代码。
3. 工作区上传、资料设置、后台跳转等低频页面独立 chunk。

### 13.2 CardViewer bundle 面向 Web 文档查看可继续瘦身

现状：

- `Chips-CardViewer` dist JS 约 276KB 未压缩。
- Web 文档查看只需要 HostedDocumentWindow，但 bundle 还包含 DropZone、文件打开、本地 CardWindow 等逻辑。

建议：

1. CardViewer 增加 web-document 专用入口。
2. 本地文件打开、拖拽、桌面专用能力单独 chunk。
3. 主题/多语言读取复用 bootstrap 快照，避免启动后再走 bridge 查询。

### 13.3 个人页背景动效需关注低端设备

现状：

- ProfilePage 有大量背景 stream/orb 样式配置和动效。

建议：

1. 已有 `prefers-reduced-motion` 的原则应落实到所有动效。
2. 移动端减少背景层数量和 blur 半径。
3. 首屏作品区域优先保证滚动性能。

## 14. 可观测性与性能测试

### 14.1 缺少端到端性能指标

建议建立指标：

1. 前端：FCP、LCP、INP、卡片详情页从 route start 到 iframe load、到 `chips.composite:ready`。
2. API：p50/p90/p99、错误率、每接口吞吐。
3. 数据库：慢查询、连接池等待、锁等待。
4. Redis：延迟、错误、内存、key 数。
5. 对象存储：上传耗时、下载 TTFB、CDN 命中率、失败率。
6. Host Runtime：启动耗时、插件安装耗时、会话创建耗时、活跃会话数。
7. 转换流水线：各阶段耗时、失败原因、队列等待时长。

### 14.2 增加自动性能检查脚本

建议脚本：

1. `curl` 检查首页、API health、卡片详情、卡片 HTML、静态 JS/CSS 的响应头和耗时。
2. Playwright 检查公开个人页、公开卡片页的加载完成时间和截图。
3. 数据库脚本检查核心索引是否存在。
4. 对象存储脚本检查新上传资源不包含错误 `content-encoding: aws-chunked`。

### 14.3 日志结构化

建议：

1. 所有请求日志带 requestId。
2. 上传流水线、Host session、resource open plan 使用同一 traceId 贯穿。
3. 生产日志输出 JSON，交给日志平台采集。
4. 错误日志保留 code、message、details、userId、resource id，但避免记录敏感 token。

## 15. 安全与稳定性优化

### 15.1 Swagger 生产默认关闭

现状：

- `.env.example` 中 `ENABLE_SWAGGER=true`。

建议：

1. 生产环境默认关闭 Swagger。
2. 如需开启，仅允许内网或管理员认证访问。

### 15.2 上传文件内容校验强化

建议：

1. `.card` 和 `.box` 不只校验扩展名，还校验 ZIP 魔数、目录结构和最大解压后体积。
2. 防 ZIP bomb：限制文件数量、单文件大小、总解压大小、目录深度。
3. YAML 解析限制体积和对象复杂度。
4. 图片、头像、封面校验真实文件头和像素尺寸。

### 15.3 备份与恢复演练

建议：

1. PostgreSQL 定时备份，并测试恢复。
2. Redis 持久化策略按 token 黑名单和登录失败计数重要性决定。
3. 对象存储开启版本控制或生命周期策略。
4. 数据库记录与对象存储资源建立定期一致性巡检：孤儿对象、断链 URL、缺失 HTML。

### 15.4 删除操作异步化与可恢复

现状：

- 删除卡片时同步删除对象存储前缀后删除数据库。

建议：

1. 先标记删除，再异步清理对象存储。
2. 清理失败可重试，避免删除接口长时间阻塞。
3. 关键删除操作记录审计日志。

## 19. 可拆分落地任务

### 19.1 P0-01 修正生产静态资源缓存头

目标：

- 让主站和后台 hash 静态资源只返回长缓存头。
- HTML fallback 继续保持可更新。

涉及文件：

- `Chips-CommunityPlatformServer/deploy/nginx/nginx.conf`
- `Chips-CommunityPlatformServer/deploy/nginx/web.conf`
- `Chips-CommunityPlatformServer/deploy/nginx/admin.conf`
- `Chips-CommunityPlatformServer/技术文档/09-生产域名与对象存储部署说明.md`

建议做法：

1. 外层 Nginx 增加 `/assets/` 专用 location。
2. `/admin/assets/` 增加专用 location。
3. 根 `location /` 不再覆盖静态资源缓存头。
4. 部署验证脚本中固定检查 `Cache-Control` 是否只出现一次。

验收：

1. `curl -I https://www.chipscard.space/assets/index-*.js` 返回 `public, max-age=31536000, immutable`。
2. `curl -I https://www.chipscard.space/` 返回 `no-cache`。
3. 不出现同一响应里同时有 `immutable` 和 `no-cache`。

风险：

- Nginx location 顺序写错会导致 SPA 路由 404，需要同时验证 `/cards/:id`、`/@:username`、`/admin/`。

### 19.2 P0-02 增加卡片打开轻量接口

目标：

- 打开卡片网页时不再读取和返回完整 `cardMetadata/cardStructure/user`。
- 降低首个 API 的响应体积和序列化成本。

涉及文件：

- `Chips-CommunityPlatformServer/packages/server/src/routes/cards.ts`
- `Chips-CommunityPlatformServer/packages/server/src/services/card.service.ts`
- `Chips-CommunityPlatformServer/packages/web/src/api/content.ts`
- `Chips-CommunityPlatformServer/packages/web/src/pages/CardDetailPage.tsx`
- `生态共用技术文档/协议与契约/09-社区平台API契约.md`

建议做法：

1. 新增 `CardService.toOpenViewDTO(card)`。
2. 新增 `GET /api/v1/cards/:cardId/open-view`。
3. 响应只包含 `id/title/status/htmlUrl/visibility/updatedAt` 和必要错误信息。
4. `CardDetailPage` 使用 open-view 接口。
5. 公共契约同步补充该接口，因为它是社区平台对外 HTTP API。

验收：

1. ready 卡片可以正常打开。
2. pending/error/private/not found 口径与原详情接口一致。
3. 响应体不包含 `cardMetadata`、`cardStructure`。

风险：

- 公共契约变更需要同步文档；不能只改项目内部代码。

### 19.3 P0-03 插件静态资源长缓存

目标：

- CardViewer / PhotoViewer 的 hash JS/CSS 走长期缓存。
- 减少重复打开卡片或图片查看器时的静态资源下载。

涉及文件：

- `Chips-CommunityPlatformServer/packages/server/src/routes/host-runtime.ts`
- `Chips-CommunityPlatformServer/packages/server/src/services/host-integration.ts`
- `Chips-CommunityPlatformServer/技术文档/08-社区Web插件宿主链路.md`

建议做法：

1. `assets/*` 响应改成 `public, max-age=31536000, immutable`。
2. 非 hash 文件或入口 HTML 继续短缓存。
3. 若无法判断 hash，先按插件构建产物路径 `/assets/` 长缓存，entry/bootstrap 不长缓存。
4. 后续把 bootstrap 通用逻辑拆成长缓存脚本，session 数据单独注入。

验收：

1. `/api/v1/host/plugin-sessions/:id/assets/index-*.js` 返回长缓存。
2. `/entry` 不被长缓存。
3. `/bootstrap.js` 不跨会话错误复用。

风险：

- 若插件构建产物文件名不是内容 hash，长缓存会导致升级后旧资源残留；需确认 Vite 产物命名稳定带 hash。

### 19.4 P0-04 数据库核心索引迁移

目标：

- 支撑个人页、发现页、房间内容、箱子引用卡片等高频查询。

涉及文件：

- `Chips-CommunityPlatformServer/packages/server/src/services/card.service.ts`
- `Chips-CommunityPlatformServer/packages/server/src/services/box.service.ts`
- `Chips-CommunityPlatformServer/packages/server/src/services/room.service.ts`

建议索引：

1. `cards(user_id, visibility, status, created_at DESC)`
2. `cards(room_id, visibility, status, created_at DESC)`
3. `cards(visibility, status, created_at DESC)`
4. `cards(card_file_id)`
5. `boxes(user_id, visibility, created_at DESC)`
6. `boxes(room_id, visibility, created_at DESC)`
7. `boxes(visibility, created_at DESC)`
8. `rooms(user_id, visibility, created_at DESC)`

验收：

2. 迁移可在空库和已有库执行。
3. 核心列表 SQL 使用索引，执行计划无全表扫描热路径。

风险：

### 19.5 P0-05 列表接口改数据库分页

目标：

- 避免查全量再 `slice`。
- 让接口耗时随 pageSize 稳定。

涉及文件：

- `Chips-CommunityPlatformServer/packages/server/src/services/card.service.ts`
- `Chips-CommunityPlatformServer/packages/server/src/services/box.service.ts`
- `Chips-CommunityPlatformServer/packages/server/src/routes/discover.ts`
- `Chips-CommunityPlatformServer/packages/server/src/routes/rooms.ts`

建议做法：

1. findMany 加 `limit` 和 `offset`。
2. total 使用 `select count()`。
3. 返回 DTO 只选必要列。
4. 搜索接口暂时也先分页，后续再做 trigram 或搜索服务。

验收：

1. page/pageSize 返回结果与旧接口一致。
2. total/totalPages 正确。
3. 数据量扩大时接口耗时不随总量线性增长。

风险：

- Drizzle 查询写法需要统一封装，避免每个 service 自己拼一套导致口径漂移。

### 19.6 P1-01 个人页作品流接口

### 19.7 P1-02 封面缩略图产物

目标：

### 19.8 P1-03 卡片打开预取与预连接

### 19.9 P1-04 Host Web Session TTL 与清理

目标：

- 防止异常关闭页面后 session 长期残留。

涉及文件：

- `Chips-CommunityPlatformServer/packages/server/src/services/host-integration.ts`
- `Chips-CommunityPlatformServer/packages/server/src/routes/host-runtime.ts`
- `Chips-CommunityPlatformServer/packages/web/src/components/HostedPluginSurface.tsx`

建议做法：

1. session 记录最后活跃时间。
2. bootstrap 或 HostedPluginSurface 周期 heartbeat。
3. 服务端定时清理超时 session。
4. 暴露基础 session 指标日志。

验收：

1. 正常打开页面 session 保持。
2. 关闭页面后 session 被删除。
3. 异常断开后超时清理。

风险：

- TTL 过短会误杀长时间阅读中的卡片页面。

### 19.10 P1-05 上传流水线阶段指标

目标：

- 先不拆 worker，也能明确每一步慢在哪里。

涉及文件：

- `Chips-CommunityPlatformServer/packages/server/src/pipeline/card-pipeline.ts`
- `Chips-CommunityPlatformServer/packages/server/src/routes/upload.ts`
- `Chips-CommunityPlatformServer/packages/server/src/app.ts`

建议做法：

1. 为每次上传生成 traceId。
2. 每个 pipeline step 用统一计时器记录耗时。
3. 成功/失败日志输出结构化 JSON。
4. status 接口可选返回最近阶段信息。

验收：

1. 上传一张卡后日志能看到每阶段耗时。
2. 失败时能看到失败阶段和错误类型。
3. 不泄露敏感路径或 token。

风险：

- 日志过多会影响性能，需要控制级别和字段。

### 19.11 P2-01 上传转换 worker 队列化

目标：

- API 与重型转换任务分离。

涉及文件：

- `Chips-CommunityPlatformServer/packages/server/src/routes/upload.ts`
- `Chips-CommunityPlatformServer/packages/server/src/pipeline/card-pipeline.ts`
- `Chips-CommunityPlatformServer/packages/server/src/db/schema/*`
- `Chips-CommunityPlatformServer/deploy/docker-compose.yml`
- `Chips-CommunityPlatformServer/deploy/Dockerfile.server`

建议做法：

1. 建立任务表或 Redis 队列。
2. 新增 worker 入口。
3. API 只创建任务并返回。
4. worker 按并发限制处理任务。
5. 支持失败重试和人工重跑。

验收：

1. API 上传响应不受转换耗时影响。
2. worker 重启后任务可恢复。
3. 多用户上传时不会拖垮 API。

风险：

- 若选择新增队列库，需先做技术选型确认。

### 19.12 P2-02 Docker 生产镜像瘦身

目标：

- 缩短构建和部署时间，降低镜像体积。

涉及文件：

- `Chips-CommunityPlatformServer/deploy/Dockerfile.server`
- `Chips-CommunityPlatformServer/deploy/Dockerfile.web`
- `Chips-CommunityPlatformServer/deploy/Dockerfile.admin`
- `.dockerignore`
- 发布构建脚本

建议做法：

1. 把生态插件产物作为独立 release artifact。
2. server 镜像不再复制完整源码。
3. 排除 node_modules、测试、日志、归档、output。
4. 运行时只保留 dist、manifest、assets、必要 CPK 和迁移文件。

验收：

1. 镜像体积下降。
2. 构建时间下降。
3. Host 集成层仍可正常安装插件。

风险：

- 运行时漏复制插件资源会导致 `PLUGIN_ENTRY_NOT_FOUND`，需要完整自动验证。

## 23. 是否需要登记工单

本文件列出的是优化规划，不等同于已经发现“阻断开发的架构缺陷”。以下情况需要另行登记正式工单：

1. 要做封面缩略图，但现有 Host / 模块 / SDK 缺少正式 HTML 转图或图片转换能力。
2. 要做 Web 文档直达轻量宿主，但 Host 侧没有可复用的正式 WebHostShell 抽象。
3. 要做队列化，但现有技术选型没有明确队列方案，需要新增第三方依赖。
4. 公共 API 新增后，生态共用契约与实际代码无法同步收口。
5. 生产部署脚本、Docker 镜像或插件产物链路与文档再次出现漂移。
