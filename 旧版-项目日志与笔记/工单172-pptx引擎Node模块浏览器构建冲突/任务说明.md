# 工单172：pptx 引擎 Node.js 内置模块与浏览器构建冲突

> 状态：已闭环（2026-09-03）。处理结果与关键验证见文末「处理结果」章节。

## 背景

Chips-Office 完成 4 件套移植与单元测试后，在执行 `chipsdev-r build` 时遇到引擎层模块包含 Node.js 内置模块（`node:crypto`、`node:fs`、`node:stream/promises`、`node:module`、`node:path`、`node:zlib`），导致 Rollup 在浏览器构建阶段报错。

## 证据

`pnpm run build` 产生以下错误：

```
src/engine/pptx-engine/src/zip.ts (10:9): "createHash" is not exported by "__vite-browser-external"
src/engine/pptx-engine/src/sections.ts: "node:crypto"
src/engine/pptx-engine/src/media-insert.ts: "node:zlib"
src/engine/pptx-engine/src/index.ts: "node:fs", "node:stream/promises"
src/engine/file-parse/src/pdf.ts: "node:module", "node:path"
```

## 影响范围

- Chips-Office 整个浏览器构建链路阻塞
- 任何依赖 pptx-engine 的应用插件都无法完成浏览器打包
- 需要拆分"浏览器端"与"服务端/工具端"两份引擎入口，或将 Node.js 依赖下沉到 SDK 测试工具内

## 复现步骤

1. `cd Chips-Office`
2. `pnpm install`
3. `pnpm run build`
4. 浏览器构建阶段报错：`createHash is not exported by __vite-browser-external`

## 期望行为

- `chipsdev-r build` 在 Chips-Office 仓库成功完成，输出可分发的桌面端插件包
- 不在浏览器侧入口中保留 `node:` 内置模块引用
- 引擎层区分浏览器侧 API 与服务端 API，提供清晰的导出分层

## 暂行处理

- 本次任务中：Chips-Office 单元测试已全部通过（88 / 88），lint 通过
- 在 `usePdf.tsx` 中将 `pdfToText` 改为动态 `import()`，避免静态依赖 Node 端代码
- 在 `manifest.yaml` 中补充 `commands` 块、`chips-sdk` 链接与 `pdfjs-dist` 复制以跑通测试
- 浏览器构建阻塞问题需要引擎层重构后才能最终解决，详见本工单

## 建议方向

1. 在 `src/engine/pptx-engine/src/index.ts` 中拆出 `browser.ts` 与 `node.ts` 两个入口
2. `file-parse/src/pdf.ts` 拆分为 `pdf.browser.ts`（纯 JSZ + pdfjs 浏览器构建）与 `pdf.node.ts`（含 DOMMatrix polyfill）
3. 使用 `process.env` 守卫或 Vite alias 切换实现
4. 与 SDK 团队协商统一抽象，避免在引擎内部直接 `require('node:...')`

## 处理结果（2026-09-03 闭环）

实际收口采用比原建议方向更彻底的方案：不引入 bundler alias 切换魔法，而是把浏览器可达代码全部改造为 Web 标准 API 实现，Node 专属能力收敛到独立入口，使分层在源码层面显式可见。

### 架构收口

1. **新增引擎共享字节工具层** `Chips-Office/src/engine/shared/bytes.ts`
   - `encodeUtf8 / decodeUtf8 / bytesToBase64 / base64ToBytes / concatBytes / bytesEqual / sha256Hex`
   - 全部基于 Web 标准 API（TextEncoder / TextDecoder / btoa / atob / Web Crypto），浏览器与 Node 通用；
   - 定位为引擎各包唯一字节操作入口：引擎代码禁止再引用 Buffer 或 `node:*` 内置模块。

2. **pptx-engine 全量浏览器安全改造（13 个文件）**
   - `zip.ts`：`node:crypto` 的 `createHash('sha256')` → `sha256Hex`（Web Crypto）；
   - `sections.ts`：`node:crypto` 的 `randomUUID` → `globalThis.crypto.randomUUID()`（与引擎既有模式一致）；
   - `media-insert.ts`：`node:zlib` 的 `deflateSync` → 纯 JS 实现 RFC 1950 zlib（`0x78 0x01` 头 + RFC 1951 stored 块 + 大端 Adler-32），同步零依赖；`solidPng/pngChunk` 以 `Uint8Array + DataView` 重写，字节布局与原实现一致；
   - `index.ts`、`slide-transfer.ts`、`insert.ts`、`chart-insert.ts`、`layout.ts`、`builtin-layouts.ts`、`notes.ts`、`theme-apply.ts`、`comments.ts`、`hyperlink.ts`、`resource-cleanup.ts`：全部 `Buffer.from(...,'utf8')`、base64 编解码、字节比较替换为共享字节工具；
   - `index.ts` 中 Node 专属的流式写盘 `savePptxToFile`（node:fs / node:stream/promises）整体迁出到独立入口 `pptx-engine/src/node-io.ts`（Node 侧/CLI 专用，浏览器代码禁止引用），`buildZip` 以 `@internal` 导出供其使用。

3. **统一导出入口分层** `engine/index.ts`
   - 仅重导出浏览器安全面：`docxEngine`、`pptxEngine`（不含 node-io）、`pptxRender` 命名空间与 `file-parse` 的 `pdfToText`；
   - `font-metrics`（node:fs 扫描系统字体）与 `file-parse` 的 Node 侧文本抽取管线（parse/doc/ppt/pptx/xlsx/vendor，依赖 word-extractor、ppt-to-text）保留原目录、不进入浏览器导出面，并在入口注释中写明分层边界。

4. **file-parse 浏览器入口重写** `file-parse/src/pdf.ts`
   - 删除 `node:module` / `node:path` 与 `require.resolve` 文件系统路径解析；
   - 改用 pdfjs-dist 浏览器构建（`pdfjs-dist` + `pdfjs-dist/build/pdf.worker.mjs`），`standardFontDataUrl` 走 `new URL('pdfjs-dist/standard_fonts/', import.meta.url)` Vite 资产化（与 `usePdf.tsx` DOC_OPTIONS 同构）；
   - DOMMatrix polyfill 保留（浏览器原生存在时自动跳过，Node 测试环境兜底）。

5. **PDF 应用侧 worker 注册** `apps/pdf/hooks/usePdf.tsx`
   - 补齐 `import "pdfjs-dist/build/pdf.worker.mjs"` 副作用导入（顶层注册 `globalThis.pdfjsWorker`），使浏览器端 fake worker 回退可用，解决未设置 workerSrc 时 `getDocument` 直接失败的问题。
