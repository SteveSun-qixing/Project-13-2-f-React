# 生态命令行架构问题与目标

## 1. 任务定位

薯片生态命令行需要从“开发工具与 Host 管理入口”升级为“生态插件能力的统一命令入口”。应用插件和功能模块插件都应能够登记命令行指令，用户安装并启用插件后，可以通过 `chips` 或 `chipsdev` 发现并执行这些指令。

命令行指令不应只服务模块插件，也不应只停留在通用 `module invoke` 调试入口。应用插件也可以声明 CLI 指令，并完成一些功能。

功能模块插件则继续以 capability + method 为核心，通过 CLI 指令把用户友好的命令参数映射到 `module.invoke`。应用插件与模块插件可以独立登记 CLI 指令，也可以协同：应用插件负责交互和配置，模块插件负责无界面批处理能力。

## 2. 当前架构已有能力

### 2.1 `chipsdev` 开发者命令行

当前 `chipsdev` 已承担开发工作区能力：

- 创建 app/card/layout/module/theme 工程；
- 构建、测试、校验、打包插件；
- 管理开发工作区 Host；
- 安装、启用、查询开发工作区插件；
- 通过 `chipsdev module invoke` 调用模块插件 capability/method。

`chipsdev module invoke` 当前是模块插件真实 Host 联调入口，支持：

- `--capability`；
- `--method`；
- `--input` / `--input-file`；
- `--manifest`；
- `--timeout-ms`；
- 同步返回与异步 job 等待。

### 2.2 模块插件能力模型

模块插件已经具备正式能力契约：

- `manifest.yaml` 中声明 `module.provides`；
- 每项 capability 下声明 method；
- method 声明输入输出 schema；
- Host 负责 provider 发现、默认 provider 解析、权限校验、schema 校验、异步 job、取消、超时、日志和审计；
- 调用方通过 `module.listProviders / module.resolve / module.invoke / module.job.*` 使用能力。

### 2.3 应用插件命令系统

应用插件已经具备 Host command registry 接入方式：

- 应用内菜单；
- 工具栏；
- 命令面板；
- surface 内快捷键；
- 命令文案走 i18n key；
- 命令元数据可序列化。

这套命令系统当前主要解决 Host surface 内部交互，还没有与操作系统 CLI 子命令形成统一登记、发现和调度关系。

## 3. 当前架构问题

### 3.1 用户态 CLI 与开发态 CLI 边界还不完整

当前文档明确 `chipsdev` 操作开发工作区，`chips` 操作用户工作区。但现有命令行能力主要偏开发工具和 Host 管理，尚未形成用户态插件能力调用体验。

问题表现：

- 用户安装应用插件或功能模块插件后，CLI 不能自动出现该插件声明的友好命令；
- 用户态 `chips` 与开发态 `chipsdev` 在“插件扩展 CLI 命令”上的职责未冻结；
- 插件能力调用更多停留在 `module invoke` 这种通用调试口径，而不是面向用户的稳定命令口径。

### 3.2 缺少应用插件和模块插件统一的 CLI 命令扩展声明

模块插件 manifest 当前能声明 capability/method，但不能声明“这些 method 如何暴露为 CLI 命令”。应用插件当前能声明应用内 command metadata，但不能声明“哪些应用命令或启动场景可以暴露为 CLI 命令”。

缺少的信息包括：

- 命令路径，例如 `icon generate`；
- 插件类型：app 或 module；
- 模块插件对应 capability/method；
- 应用插件对应 commandId、handlerId、sceneId 或 launchParams；
- 参数列表、短参数、默认值、必填规则；
- 参数到 module input payload 或 app command payload 的映射规则；
- help 文案、多语言 key 和示例；
- 权限需求；
- 输出格式和退出码语义；
- 是否需要打开/聚焦应用 surface；
- 是否支持异步 job、进度显示和取消。

### 3.3 CLI 缺少动态发现插件命令的机制

理想状态是插件安装和启用后，CLI 下次运行即可发现新命令，不需要重新安装 CLI，也不需要用户手工写配置。

当前缺口：

- Host 插件注册表未明确索引 app/module 插件的 CLI command extension；
- CLI 未定义从 Host/工作区读取命令扩展的标准流程；
- CLI 缓存、缓存失效、插件启停后的热更新策略未定义；
- shell completion 如果存在静态缓存，缺少刷新策略。

### 3.4 缺少命令参数到插件 payload 的标准映射

友好 CLI 命令需要把命令参数转换成模块输入或应用命令输入。例如：

```bash
chips icon generate app.svg --formats png,ico --out ./dist
```

需要转换为：

```json
{
  "input": "app.svg",
  "formats": ["png", "ico"],
  "outputDir": "./dist"
}
```

应用插件命令也需要把 CLI 参数转换为 launchParams 或 command payload。例如：

```bash
chips editor open demo.card --scene card-edit --readonly
```

可以转换为：

```json
{
  "commandId": "chips.editor.open",
  "payload": {
    "path": "demo.card",
    "scene": "card-edit",
    "readonly": true
  },
  "surface": {
    "open": true,
    "focus": true
  }
}
```

当前缺少统一规则处理：

- 位置参数；
- 多值参数；
- 布尔参数；
- 数字参数；
- JSON 参数；
- 文件路径规范化；
- 相对路径基准；
- 输出目录创建策略；
- 覆盖与冲突策略；
- dry-run；
- 错误消息与退出码。

### 3.5 文件路径、权限和 surface 治理需要 CLI 口径

GUI 应用插件通常通过 Host 对话框或浏览器 File API 获取输入；CLI 则天然接收本地路径。模块插件和应用插件处理命令行路径时都必须明确走 Host 能力和权限治理，不能让插件私下绕过 Host 边界。

需要澄清：

- CLI 传入路径如何归一为 Host 可审计输入；
- 应用插件与模块插件分别需要哪些 `permissions`；
- 用户态和开发态工作区如何解析路径；
- 输出文件如何确认覆盖；
- 批量输入如何报告部分失败；
- 文件系统错误如何归一为标准错误。
- CLI 触发应用插件时如何选择打开新 surface、复用现有 surface 或只投递 command；
- 应用未运行、正在运行、被禁用或权限不足时的标准行为。

### 3.6 插件能力复用与专用 CLI 命令之间缺少治理层

如果每个插件都在 CLI 里写死专用命令，会导致 CLI 本体膨胀、插件热更新困难、能力重复实现。

当前缺口是中间治理层：

- CLI 本体只提供扩展运行框架；
- 插件声明命令；
- Host/工作区注册表索引命令；
- CLI 动态解析并转发到 `module.invoke`、`surface.open`、`plugin.launch` 或 `command.invoke`；
- CLI 不直接 import 插件源码；
- CLI 不复制插件业务逻辑。

### 3.7 异步任务、进度和取消体验未产品化

模块能力契约已经有 job，应用插件也可能通过 command 触发长任务，但友好 CLI 如何展示任务状态还未形成标准：

- 进度条或结构化 JSON 输出；
- `Ctrl+C` 是否映射为 `module.job.cancel`；
- 应用插件命令触发的长任务是否需要统一进入 Host job；
- 超时策略；
- job 失败后的错误展示；
- 批量 job 的聚合状态；
- CI 场景下的纯 JSON 输出。

### 3.8 命令冲突与命名空间治理缺失

如果多个插件都声明同一个命令，例如 `image convert`，CLI 必须有冲突处理规则。

需要定义：

- 命令路径命名规范；
- 官方插件优先级；
- 第三方插件命名空间；
- 多 provider 冲突时的选择和提示；
- 禁用或卸载插件后的命令消失行为；
- 命令别名与废弃策略。

## 4. 需要达到的目标

### 4.1 建立应用插件与模块插件统一的 CLI 扩展模型

目标是在插件 manifest 或配套契约文件中支持声明 CLI 命令扩展。声明内容至少包括：

- `commandPath`：例如 `icon generate`；
- `target.type`：`module` 或 `app`；
- 模块目标：`capability`、`method`；
- 应用目标：`pluginId`、`commandId`、`handlerId`、`sceneId`、`launchParams`、surface 策略；
- 参数 schema；
- 参数到 input payload、command payload 或 launchParams 的映射；
- 输出模式；
- help/i18n key；
- 权限需求；
- job 支持策略。

示例方向：

```yaml
cli:
  commands:
    - commandPath: icon generate
      target:
        type: module
        capability: icon.generate
        method: generate
      titleKey: icon.cli.generate.title
      descriptionKey: icon.cli.generate.description
      arguments:
        - name: input
          position: 0
          required: true
          type: path
      options:
        - name: formats
          type: stringList
          default: [png, ico, icns]
        - name: out
          type: path
          mapsTo: outputDir
      output:
        mode: human
      job:
        wait: true
        cancelOnInterrupt: true
    - commandPath: editor open
      target:
        type: app
        pluginId: chips.app.editor
        commandId: chips.editor.open
        surface:
          open: true
          focus: true
          reuse: preferred
      titleKey: editor.cli.open.title
      descriptionKey: editor.cli.open.description
      arguments:
        - name: path
          position: 0
          required: true
          type: path
      options:
        - name: readonly
          type: boolean
          mapsTo: readonly
```

具体字段需要后续正式设计冻结，不能在单个插件中私造不可复用口径。

### 4.2 实现安装即发现、启停即更新

目标体验：

- 应用插件或功能模块插件安装并启用后，用户下次执行 `chips` 即可看到插件声明的 CLI 命令；
- 插件禁用后，命令自动不可用；
- 插件升级后，命令声明自动更新；
- 不需要重新安装 CLI；
- 不需要重新安装 Host；
- 不需要用户手动编辑命令映射配置。

### 4.3 支持热更新与缓存失效

目标机制：

- Host 插件注册表索引 CLI command extension；
- 插件 install/enable/disable/update/uninstall 时更新命令索引版本；
- CLI 每次运行读取索引版本；
- CLI 可使用本地缓存，但必须能根据索引版本失效；
- shell completion 可单独刷新，但真实命令执行不能依赖静态 completion。

### 4.4 统一用户态 `chips` 与开发态 `chipsdev` 体验

目标区分：

- `chips`：用户工作区命令，面向已安装插件的日常能力调用；
- `chipsdev`：开发工作区命令，面向插件开发、联调、测试、打包；
- 两者使用同一套 CLI 扩展声明模型；
- 两者读取各自工作区的插件注册表和命令索引；
- 同一插件在用户态和开发态互不污染。

### 4.5 支持应用命令与模块能力两类正式执行路径

目标架构：

```text
CLI 友好命令
  -> module target -> Host module.invoke -> 模块插件 capability/method
  -> app target    -> Host surface/plugin/command -> 应用插件 scene/command
```

要求：

- 适合无界面批处理的能力优先由模块插件承载；
- 需要界面状态、用户交互、工作台上下文或应用场景的能力可以由应用插件登记 CLI 指令；
- CLI 可以打开/聚焦应用，也可以向已运行应用投递 command；
- 应用插件登记的 CLI 指令必须走 Host surface/plugin/command 正式链路；
- 模块插件登记的 CLI 指令必须走 Host module 正式链路；
- CLI 不复制模块业务逻辑；
- 应用插件和模块插件都不直接实现独立操作系统命令行程序；
- Host 继续负责权限、schema、job、审计和 provider 解析。

### 4.6 完善参数、路径、输出与错误标准

目标形成统一 CLI 参数治理规范：

- 位置参数和选项参数规则；
- 类型解析和 schema 校验；
- 文件路径归一与工作目录规则；
- 输出目录创建、覆盖和冲突策略；
- 批量输入的部分成功报告；
- human / json 两类输出；
- 标准退出码；
- 标准错误对象到 CLI 文本的映射；
- CI 场景下的稳定 JSON 输出。

### 4.7 支持 job 进度、取消和结构化输出

目标：

- 异步 method 返回 job 时，CLI 默认等待并展示进度；
- 应用插件 command 若触发 Host 托管任务，也应能返回可追踪任务状态；
- `--no-wait` 可只输出 jobId；
- `--json` 输出结构化进度或最终结果；
- `Ctrl+C` 可按策略映射为 `module.job.cancel` 或应用命令声明的取消入口；
- 超时和取消使用模块契约标准错误码；
- 批量任务输出可被脚本稳定消费。

### 4.8 建立命令命名与冲突治理

目标：

- 官方插件可声明短命令，如 `icon generate`；
- 第三方插件默认建议带命名空间，避免占用通用命令；
- 冲突时 CLI 明确提示冲突插件、命令来源和解决方式；
- 支持用户禁用某个插件的 CLI 命令扩展；
- 支持命令别名，但别名必须可追踪来源。

## 5. 分阶段建议

### 阶段一：问题冻结与契约草案

- 梳理 `chips` 与 `chipsdev` 当前命令边界；
- 设计 `cli.commands` 声明草案；
- 设计 Host 插件注册表命令索引草案；
- 设计参数映射、路径治理、输出和错误码草案。

### 阶段二：Host/SDK/CLI 最小闭环

- Host 安装插件时读取 CLI 扩展声明；
- 工作区插件注册表写入命令索引；
- CLI 读取命令索引并动态解析命令；
- CLI 将模块目标转换为 `module.invoke`；
- CLI 将应用目标转换为 `surface.open`、`plugin.launch` 或 `command.invoke`；
- 支持 `--json` 与基本错误输出。

### 阶段三：热更新、completion 与 job 体验

- 插件启停更新索引版本；
- CLI 缓存失效；
- shell completion 刷新命令；
- job 进度、取消、超时、批量输出。

### 阶段四：真实插件样板验证

- 以功能模块插件作为无界面批处理样板：
  - `chips icon generate`;
  - `chips icon inspect`;
  - `chips icon presets`;
- 以应用插件作为界面场景和应用命令样板：
  - `chips editor open demo.card`;
  - `chips viewer open demo.box`;
  - `chips iconmaker open --preset app-store`;
- 图形应用插件可以调用模块能力，也可以登记需要打开 surface 的应用命令；
- 开发态通过 `chipsdev icon generate` 或 `chipsdev module invoke` 验证；
- 用户态通过 `chips icon generate`、`chips editor open` 等命令验证。
