# 生态命令行扩展架构设计方案

## 1. 设计定位

本文是 task024 的阶段性架构方案，保存命令行完善任务的设计决策、模块划分和实施路径。本文不作为生态最终公共契约发布位置；待方案实现并验证后，需要把稳定口径同步到 `生态共用技术文档/命令行工具/`、`生态共用技术文档/插件开发/` 和 `生态共用技术文档/协议与契约/`。

本方案基于以下现状核对：

- 生态设计原稿确认 Host 是唯一运行时承载，插件能力必须走 Host / Bridge / SDK / 模块服务正式链路。
- `Chips-Host/src/main/cli/index.ts` 当前只承载 Host 管理命令、插件管理、主题管理、文件打开等入口。
- `Chips-SDK/cli/index.js` 当前承载 `chipsdev` 开发者 CLI，并将 Host 管理命令转发到开发工作区。
- `Chips-Host/src/runtime/plugin-runtime.ts` 已负责解析 `manifest.yaml`、安装插件、持久化 `plugin-runtime.json`。
- Host 已有 `plugin.query`、`plugin.launch`、`surface.open`、`command.*`、`module.invoke`、`module.job.*` 路由，可作为 CLI 扩展执行层。
- 模块插件契约已冻结为 `module.provides / module.consumes`、capability、method、job、cancel 等模型。

## 2. 总体目标

命令行体系从“Host 管理与开发工具”升级为“生态插件能力统一命令入口”：

- 应用插件和模块插件都可以通过 `manifest.yaml` 的 `cli.commands` 声明命令。
- `chips` 读取用户工作区已启用插件命令，`chipsdev` 读取开发工作区已启用插件命令。
- 插件安装、启用、禁用、升级后，CLI 命令自动发现并按索引版本失效缓存。
- CLI 不直接 import 插件源码，不复制业务逻辑，只负责参数解析、权限预检、路径规范化、输出治理和转发。
- 模块目标走 `module.invoke / module.job.*`。
- 应用目标走 `plugin.launch / surface.open / command.invoke`。
- 空命令进入键盘优先 TUI，可逐级浏览命令树、填写参数、执行命令、查看进度。
- 保留现有 `module.invoke` 与 `chipsdev module invoke` 作为低层调试入口，不要求插件开发者迁移已有模块能力契约。

## 3. 架构原则

1. Host 唯一承载：插件 CLI 命令不是独立 OS 程序，执行必须回到 Host。
2. 声明驱动：插件只声明命令、参数和目标，不在 CLI 本体注册硬编码分支。
3. 运行时薄入口：`chips` / `chipsdev` 负责解析和调度，业务能力仍由 app/module 插件完成。
4. 工作区隔离：`chips` 使用用户工作区，`chipsdev` 使用开发工作区，两者命令索引互不污染。
5. 契约优先：参数、路径、输出、错误码、job 进度、取消、冲突处理都进入统一模型。
6. 键盘优先：TUI 与传统命令行共享同一命令索引和解析器，不建立第二套命令模型。
7. 无临时口径：新增字段先形成统一模型，再进入 Host/SDK/Scaffold，不在单个插件私造命令格式。

## 4. 分层架构

```text
用户输入
  chips / chipsdev
    ├─ 传统命令解析器
    ├─ TUI 命令构建器
    └─ CLI 扩展运行器
          ↓
Host CLI 命令索引读取
          ↓
Host 插件运行时 / 工作区插件注册表
          ↓
已启用插件 manifest.cli.commands
          ↓
执行目标
    ├─ module target -> module.invoke -> module.job.*
    └─ app target    -> plugin.launch / surface.open / command.invoke
```

### 4.1 Host 层职责

Host 是 CLI 扩展的事实来源：

- 在安装插件时解析 `manifest.cli.commands`。
- 校验命令声明结构、目标类型、权限字段、参数字段和 i18n key 字段。
- 在 `plugin-runtime.json` 或独立命令索引文件中持久化已安装插件的 CLI 声明快照。
- 在 `plugin.install / plugin.enable / plugin.disable / plugin.uninstall` 后更新命令索引版本。
- 提供 `cli.command.list / cli.command.get / cli.command.resolve` 等只读路由，供 `chips`、`chipsdev` 和后续 shell completion 使用。
- 执行 app/module 目标时继续走现有正式路由，不新增绕过内核路由的专用通道。

### 4.2 CLI 层职责

`chips` 与 `chipsdev` 共享 CLI 扩展运行器：

- 读取当前工作区命令索引和版本号。
- 解析用户输入的命令路径、位置参数和选项。
- 按命令声明完成类型转换、默认值填充、必填检查、路径规范化、输出目录和覆盖策略预检。
- 将命令转换为 Host 路由调用。
- 统一输出 human / json 两种模式。
- 处理 job 进度、超时、取消和退出码。
- 空命令时进入 TUI；非 TTY 或 CI 环境下输出 help/错误，不阻塞脚本。

### 4.3 SDK 层职责

SDK 只做类型化封装和开发工具接入：

- 提供 `client.cliCommands.list/resolve/execute` 类型封装，底层仍调用 Host 路由。
- 为 `chipsdev validate` 增加 `manifest.cli.commands` 校验。
- 为脚手架模板生成正式 `cli.commands` 示例和测试。
- 不在 SDK 中实现 Host 命令索引或插件运行时主逻辑。

## 5. Manifest 声明模型

新增公共字段：

```yaml
cli:
  commands:
    - commandPath: icon generate
      target:
        type: module
        capability: converter.icon.generate
        method: generate
      titleKey: icon.cli.generate.title
      descriptionKey: icon.cli.generate.description
      arguments:
        - name: input
          position: 0
          type: path
          required: true
          mapsTo: inputPath
      options:
        - name: formats
          short: f
          type: stringList
          default: [png, ico]
          mapsTo: formats
          ui:
            control: multiSelect
            choices: [png, ico, icns]
        - name: out
          type: path
          mapsTo: outputDir
          path:
            kind: directory
            create: true
      output:
        mode: human
        json: supported
      job:
        wait: true
        cancelOnInterrupt: true
```

应用插件示例：

```yaml
cli:
  commands:
    - commandPath: editor open
      target:
        type: app
        pluginId: chips.app.editor
        commandId: chips.editor.open
        surface:
          open: true
          focus: true
          reuse: preferred
      titleKey: editor.cli.open.title
      descriptionKey: editor.cli.open.description
      arguments:
        - name: path
          position: 0
          type: path
          required: true
          mapsTo: path
      options:
        - name: scene
          type: string
          mapsTo: scene
        - name: readonly
          type: boolean
          mapsTo: readonly
      output:
        mode: human
```

### 5.1 顶层字段

| 字段 | 必填 | 说明 |
|---|---:|---|
| `commandPath` | 是 | 用户输入的命令路径，空格分隔，例如 `icon generate`。 |
| `target` | 是 | 执行目标，支持 `module` 和 `app`。 |
| `titleKey` | 是 | 命令标题 i18n key。 |
| `descriptionKey` | 否 | 命令说明 i18n key。 |
| `arguments` | 否 | 位置参数声明。 |
| `options` | 否 | 选项参数声明。 |
| `examples` | 否 | 示例命令，文案用 i18n key 或稳定命令字符串。 |
| `permissions` | 否 | 命令执行所需权限补充，必须包含在插件 `permissions` 中。 |
| `output` | 否 | 输出模式、文件结果、结构化输出策略。 |
| `job` | 否 | 异步任务等待、进度和取消策略。 |
| `conflict` | 否 | 插件主动声明的优先级或命名空间提示。 |

### 5.2 目标模型

模块目标：

```yaml
target:
  type: module
  capability: converter.file.convert
  method: convert
  pluginId: chips.module.file.convert # 可选，通常不写，交给 Host provider 解析
  timeoutMs: 60000
```

规则：

- `capability` 和 `method` 必填。
- `pluginId` 可选；不写时由 Host 模块服务按正式 provider 规则解析。
- 参数映射结果作为 `module.invoke.input`。
- `job.mode` 为 `wait` 时，CLI 调用 `module.job.get` 等待终态。

应用目标：

```yaml
target:
  type: app
  pluginId: chips.app.viewer
  commandId: chips.viewer.open
  launchParams:
    source: cli
  surface:
    open: true
    focus: true
    reuse: preferred
```

规则：

- `pluginId` 必填，默认必须等于声明该命令的插件 ID。
- `commandId` 可选；不写时只执行 `plugin.launch` 或 `surface.open`。
- `surface.open=true` 时先打开或聚焦应用 surface，再按需要投递 command。
- `commandId` 存在时，CLI 将 payload 传给 `command.invoke`，source 固定为 `api` 或后续新增 `cli`。
- 应用命令只返回 dispatch ack；若需要长期进度，应由应用命令创建 Host 托管 job 或委托模块目标。

## 6. 参数与控件模型

参数类型统一为：

- `string`
- `stringList`
- `number`
- `integer`
- `boolean`
- `enum`
- `path`
- `json`
- `jsonFile`
- `text`
- `textFile`

参数字段：

| 字段 | 说明 |
|---|---|
| `name` | 参数名，CLI 选项使用 `--name`。 |
| `short` | 单字符短参数，如 `-o`。 |
| `position` | 位置参数序号，仅 `arguments` 使用。 |
| `type` | 参数类型。 |
| `required` | 是否必填。 |
| `default` | 默认值。 |
| `mapsTo` | 写入 payload 的字段路径，默认等于 `name`。 |
| `choices` | 枚举或多选候选。 |
| `multiple` | 是否可重复传入。 |
| `validation` | 最小值、最大值、正则、长度等校验。 |
| `path` | 路径类型的存在性、文件/目录、创建、扩展名策略。 |
| `ui` | TUI 控件建议。 |

TUI 控件建议：

- `select`
- `multiSelect`
- `toggle`
- `stepper`
- `slider`
- `pathInput`
- `pasteBox`
- `textarea`

## 7. 路径、输出与覆盖策略

路径处理必须由 CLI 和 Host 共同治理：

- 相对路径默认基于当前 shell 工作目录解析。
- `chipsdev` 在开发工作区执行插件命令时，路径仍基于用户执行 `chipsdev` 的项目目录解析，不基于 `.chips-host-dev`。
- CLI 传给 Host 的路径一律规范化为绝对路径，并保留 `original` 与 `cwd` 供审计。
- `type: path` 可声明 `kind: file | directory | any`、`exists`、`create`、`extensions`。
- 输出目录默认不隐式覆盖同名文件，除非命令声明或用户传入 `--overwrite`。
- 批量输入必须返回 `items[]`，每项包含 `input / ok / output / error`，允许部分成功。
- `--dry-run` 由 CLI 扩展运行器统一支持；插件声明 `dryRun: supported` 后才会传入目标 payload。

标准覆盖策略：

- `fail`：默认，存在冲突时报错。
- `overwrite`：覆盖目标。
- `rename`：自动生成不冲突文件名。
- `skip`：跳过冲突项并返回部分成功。

## 8. 输出、错误码与退出码

输出模式：

- human：默认，人读摘要、进度条、生成路径、下一步动作。
- json：机器可读，所有错误和进度都输出结构化 JSON。

通用成功输出：

```json
{
  "ok": true,
  "commandPath": "icon generate",
  "target": { "type": "module", "capability": "converter.icon.generate", "method": "generate" },
  "output": {},
  "artifacts": []
}
```

通用错误输出：

```json
{
  "ok": false,
  "code": "CLI_ARGUMENT_INVALID",
  "message": "缺少必填参数 input",
  "details": {
    "commandPath": "icon generate",
    "argument": "input"
  },
  "retryable": false
}
```

退出码建议：

| 退出码 | 含义 |
|---:|---|
| 0 | 成功。 |
| 1 | 通用失败。 |
| 2 | 参数解析或校验失败。 |
| 3 | 命令不存在或命令冲突。 |
| 4 | 权限不足。 |
| 5 | 输入/输出文件错误。 |
| 6 | 插件未安装、未启用或目标不可用。 |
| 7 | 任务失败。 |
| 8 | 任务取消。 |
| 9 | 超时。 |

错误码命名建议：

- `CLI_COMMAND_NOT_FOUND`
- `CLI_COMMAND_CONFLICT`
- `CLI_ARGUMENT_INVALID`
- `CLI_PATH_NOT_FOUND`
- `CLI_OUTPUT_CONFLICT`
- `CLI_PERMISSION_DENIED`
- `CLI_PLUGIN_DISABLED`
- `CLI_TARGET_UNAVAILABLE`
- `CLI_JOB_CANCELLED`
- `CLI_TIMEOUT`

Host 原有错误码如 `PLUGIN_NOT_FOUND`、`PERMISSION_DENIED`、`MODULE_TIMEOUT`、`MODULE_JOB_CANCELLED` 继续透传，并在 CLI 层映射为稳定退出码。

## 9. 动态发现、缓存与热更新

### 9.1 命令索引

Host 在工作区维护命令索引：

```json
{
  "schemaVersion": 1,
  "workspaceKind": "user",
  "version": 12,
  "updatedAt": "2026-05-28T00:00:00.000Z",
  "commands": [
    {
      "commandId": "chips.module.icon.cli.generate",
      "commandPath": ["icon", "generate"],
      "ownerPluginId": "chips.module.icon",
      "ownerPluginType": "module",
      "enabled": true,
      "declaration": {}
    }
  ]
}
```

命令索引可独立保存为 `cli-command-index.json`，也可以从 `plugin-runtime.json` 即时派生。最终实现建议使用独立索引文件，原因是：

- shell completion 可快速读取。
- 缓存版本号清晰。
- 安装、启停、卸载时可审计索引变更。
- CLI 不需要读取完整插件运行时记录。

### 9.2 版本失效

- `plugin.install`：解析新 manifest，更新索引版本。
- `plugin.enable`：将对应命令标记为 enabled，更新索引版本。
- `plugin.disable`：将对应命令标记为 disabled 或从可执行视图移除，更新索引版本。
- `plugin.uninstall`：移除命令，更新索引版本。
- `plugin.update` 或重复安装同 ID 插件：替换命令声明，更新索引版本。

CLI 每次运行先读取索引版本；如果本地解析缓存版本不一致，重建命令树。真实执行不得依赖静态 shell completion。

### 9.3 冲突处理

命令路径冲突定义：两个 enabled 命令拥有完全相同 `commandPath`。

默认规则：

1. Host 内置命令优先于插件命令。
2. 官方插件可占用短命令。
3. 第三方插件建议使用命名空间，如 `vendor image convert`。
4. 同优先级冲突时，CLI 不自动选择，返回 `CLI_COMMAND_CONFLICT`。
5. 用户可用完整限定形式执行：`chips --plugin <pluginId> <commandPath>`。
6. 禁用或卸载插件后冲突自动重新解析。

命令索引应保留冲突组，TUI 中展示来源插件、版本和启用状态。

## 10. 执行链路

### 10.1 模块目标执行链路

```text
chips icon generate app.svg --out dist
  -> 解析 commandPath = icon generate
  -> 校验参数和路径
  -> payload = { inputPath, outputDir }
  -> runtime.invoke("module.invoke", { capability, method, input, timeoutMs })
  -> sync: 输出结果
  -> job: 轮询 module.job.get，Ctrl+C 调 module.job.cancel
```

模块目标要求：

- 模块插件必须已安装且启用。
- `capability/method` 必须存在于模块 provider 中。
- Host 继续执行 provider 解析、schema 校验、权限校验、超时和审计。
- CLI 不读取模块源码，不绕过 Host 调用模块能力。

### 10.2 应用目标执行链路

```text
chips editor open demo.card --readonly
  -> 解析 commandPath = editor open
  -> 校验参数和路径
  -> launchParams / command payload
  -> plugin.launch 或 surface.open 打开/复用/聚焦应用
  -> command.invoke 投递应用命令
  -> 输出 dispatch ack 或应用返回的标准结果
```

应用目标要求：

- 应用插件必须已安装且启用。
- `surface.open` 与 `plugin.launch` 继续由 Host 负责 session、Bridge、权限和 surface context。
- 若 `commandId` 存在，应用侧必须已在 Host command registry 注册对应命令。
- 如果应用未运行且命令要求注册后才能调用，CLI 先启动应用并等待 ready，再执行 `command.invoke`。
- 长任务优先由应用委托模块目标；如果应用自己创建任务，后续需要统一 Host job 抽象后再纳入进度治理。

## 11. TUI 交互工具设计

TUI 与传统 CLI 共用命令索引、参数模型和执行器。

入口：

```bash
chips
chipsdev
```

布局：

```text
┌────────────────────────────────────────────────────────────┐
│ chips icon generate --formats png,ico                      │
├────────────────────────────────────────────────────────────┤
│ › generate   生成图标资源          chips.module.icon       │
│   inspect    检查图标源文件        chips.module.icon       │
│   open       打开图标制作器        chips.app.iconmaker     │
└────────────────────────────────────────────────────────────┘
```

核心交互：

- `↑ / ↓`：移动候选。
- `Enter`：命令未完整时补全候选，命令完整时执行。
- `Tab`：补全当前高置信候选。
- `Backspace`：删除片段。
- `Esc`：返回上一级或退出。
- `Ctrl+L`：清空当前命令。
- `Ctrl+C`：退出界面或取消正在执行的 job。

当前正式口径补充：TUI 不维护历史命令搜索或回放文件；CLI / TUI 的执行、补全和错误结果统一写入 Host 操作日志。

TUI 状态机：

```text
loadingIndex
  -> browsingCommandTree
  -> editingArgument
  -> readyToExecute
  -> executing
  -> showingResult
  -> browsingCommandTree
```

非交互环境：

- 如果 `process.stdin.isTTY !== true`，空命令输出 help。
- 如果声明了 `CI=true`，空命令不进入 TUI。
- 传统命令执行永远不依赖 TUI。

实现策略：

- 初版优先使用 Node 标准 `readline` 和 ANSI 控制序列，不引入新第三方 TUI 库。
- 若后续确需更强控件框架，先登记技术选型工单，再进入依赖决策。

## 12. Scaffold 与示例策略

应用插件脚手架：

- `manifest.yaml.tpl` 增加一个禁用或最小可用的 app target CLI 示例。
- README 增加“如何声明 CLI 命令”章节。
- 生成的 i18n 文件包含 CLI title/description key。
- 测试覆盖 `cli.commands` 字段渲染和 `chipsdev validate`。

模块插件脚手架：

- `manifest.yaml.tpl` 为默认 `run` 或模板特定 method 增加 module target CLI 示例。
- 文件转换、HTML 渲染、图像处理模板给出更贴近场景的命令路径。
- README 明确真实联调可用两条路径：
  - 低层：`chipsdev module invoke`
  - 友好：插件声明后的 `chipsdev <commandPath>`

示例命令建议：

- `chips icon generate <input> --formats png,ico --out <dir>`
- `chips file convert <input> --to pdf --out <dir>`
- `chips editor open <card> --readonly`
- `chips viewer open <box>`

## 13. 测试与验收

Host 测试：

- `PluginRuntime` 可解析并持久化 `cli.commands`。

## 14. 分阶段实施路径

### 阶段一：契约与索引闭环

- 在 task024 中冻结字段草案。
- Host `PluginManifest` 增加 `cli` 类型和解析。
- Host 新增命令索引生成与版本号。
- Host 新增 `cli.command.list / cli.command.resolve` 只读路由。
- `chips help` 展示动态命令摘要。

### 阶段二：传统 CLI 动态执行

- CLI 扩展运行器接入 `chips`。
- `chipsdev` 对非内置工程命令转发到开发工作区动态命令。
- 实现参数解析、路径规范化、payload 映射。
- 模块 target 执行闭环。
- 应用 target 最小执行闭环：launch/open + command dispatch。

### 阶段三：job、输出与错误标准

- `--json`、human 输出、退出码映射。
- job 轮询、进度展示、Ctrl+C cancel。
- 输出目录、覆盖策略、批量输入结果。
- shell completion 读取命令索引版本。

### 阶段四：TUI

- 空命令进入 TUI。
- 命令树浏览、补全、参数填写、执行状态。
- 单选、多选、开关、数字、滑块、路径粘贴、多行输入控件。
- 执行结果、错误定位、最终命令复制。

### 阶段五：脚手架、示例与公共文档

- 应用脚手架和模块脚手架同步。
- 官方样板插件声明真实 CLI 命令。
- 共享技术文档同步正式口径。
- 全量验证 Host / SDK / Scaffold / 示例插件。

## 15. 需要进一步确认的问题

1. `command.invoke` 的 `source` 是否新增 `cli`，还是先复用 `api` 并在 payload/context 中标记 `source: "cli"`。
2. 应用 target 是否需要 Host 统一提供“启动并等待 command registry ready”的路由，避免 CLI 自己轮询 `command.list`。
3. 应用长任务是否统一扩展 Host job 模型，还是第一阶段只要求应用委托模块 target。
4. `cli.commands` 是否允许 card/layout/theme 插件声明。当前建议第一阶段只允许 app/module，避免把无界面或嵌入式插件混入 OS 命令入口。
5. 是否允许用户为冲突命令设置偏好 provider。当前建议第一阶段只支持 `--plugin <pluginId>` 显式选择。

## 16. 当前结论

本方案建议把 CLI 扩展做成 Host 托管的插件声明索引，而不是把命令硬编码到 `chips` 或 `chipsdev`。这样可以满足安装即发现、启停即生效、用户态/开发态隔离、应用/模块双目标和 TUI 共用命令树，同时不破坏现有 Host 运行时边界。

下一步应先冻结 `cli.commands` 字段和 Host 命令索引格式，再进入 Host/SDK/Scaffold 实现。
