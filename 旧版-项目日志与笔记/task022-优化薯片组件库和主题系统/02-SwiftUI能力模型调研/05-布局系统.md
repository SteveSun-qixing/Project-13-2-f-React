# SwiftUI 调研：布局系统

## 1. 这一层解决什么问题

SwiftUI 的布局系统不是几个容器组件，而是一套覆盖基础堆叠、滚动、列表、表格、表单、安全区、测量、自定义布局和 layout modifier 的完整体系。

布局系统的价值是：开发者能用一致方式表达界面结构，系统根据容器、平台、尺寸和上下文完成布局。

薯片还需要让统一布局系统自然覆盖网页式结构。很多生态页面会像网页：长滚动、分区组织、图文混排、卡片网格、详情页、文档页、市场页、社区页。这些不应该由每个应用重新写 CSS，而应由同一套布局系统表达。

## 2. 核心布局能力

| 能力 | 作用 |
|---|---|
| `HStack` | 横向排列子视图 |
| `VStack` | 纵向排列子视图 |
| `ZStack` | 叠放子视图 |
| `Grid` | 二维布局 |
| `List` | 单列数据行容器，可带选择等行为 |
| `Table` | 单列或多列表格 |
| `Form` | 设置页、检查器等数据录入分组 |
| `ScrollView` | 滚动区域 |
| `GeometryReader` | 基于容器尺寸和坐标系生成内容 |
| `Layout` | 自定义布局协议 |

## 3. Layout Modifier 能力

SwiftUI 使用 modifier 处理布局细节：

- size：宽度、高度、最小/最大尺寸。
- position：位置与偏移。
- alignment：对齐。
- padding and spacing：内边距与间距。
- safe area and margins：安全区和边距。
- grid configuration：网格配置。
- layer order：层级顺序。
- layout direction：布局方向。

## 4. 设计价值

### 4.1 容器和修饰能力分层

容器负责结构，modifier 负责局部布局约束。这样布局 API 能组合，而不是每个容器都膨胀出一堆特殊属性。

### 4.2 列表、表格、表单是布局也是交互

`List/Table/Form` 不只是视觉容器，还带有选择、分组、输入、平台样式和辅助语义。这一点很重要：高质量应用里的布局常常同时承载行为。

### 4.3 自定义布局有统一协议

复杂应用不可能只靠内置布局。SwiftUI 用 `Layout` 给自定义布局留下正式入口。

## 5. 对薯片的直接启发

薯片布局系统应包含：

- 基础容器：`ChipsBox`、`ChipsInline`、`ChipsStack`、`ChipsLayerStack`、`ChipsGrid`。
- 信息容器：`ChipsList`、`ChipsTable`、`ChipsForm`、`ChipsSection`。
- 网页式结构可以由 `ChipsSection`、`ChipsStack`、`ChipsGrid`、`ChipsList`、`ChipsScrollView`、`ChipsText`、`ChipsImage`、`ChipsMedia` 等统一原语组合表达；不单列特殊组件族。
- 滚动容器：`ChipsScrollView`、虚拟列表、滚动阴影、滚动恢复。
- 尺寸系统：生态统一 `cpx`、容器换算、断点、密度。
- 安全区域：窗口边界、工具栏、状态栏、浮层遮挡。
- 测量能力：`ChipsMeasure` / `ChipsGeometry`。
- 自定义布局：声明式 layout contract，而不是业务页面临时计算。
- 主题联动：间距、半径、边框、阴影、密度都来自 token。

薯片的布局目标不是做成网页 CSS 工具类，而是形成生态应用统一、可测试、可预览的布局语言。
