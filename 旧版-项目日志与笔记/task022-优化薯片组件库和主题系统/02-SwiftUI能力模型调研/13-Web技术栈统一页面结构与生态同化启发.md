# 调研补充：Web 技术栈、统一页面结构与生态同化启发

## 1. 为什么要补充这一章

薯片生态不是 Apple 原生平台，也不是普通 Web 站点集合。它的底层技术栈应统一建立在 Web 技术栈之上：HTML、CSS、JavaScript、TypeScript、React、Chromium/Electron、Bridge、Host 服务、插件 manifest、主题 token、多语言和组件契约。

因此，薯片对标 SwiftUI 时需要做一次转译：

- SwiftUI 的 `View` 是 Apple 平台的声明式 UI 单元。
- 薯片的 `View` 应是 Web 技术栈上的统一声明式界面单元。
- SwiftUI 的系统能力由 Apple 平台提供。
- 薯片的系统能力由 Host 大底座提供。
- SwiftUI 的平台统一风格来自系统控件。
- 薯片的统一风格来自主题系统、无头组件库、交互规范和 Host 注入环境。

## 2. View 不只是应用 UI，也要承载网页式结构

薯片未来不只做设置面板、资源管理器、编辑器、播放器这类工具界面，也会出现大量类似网页的页面结构：

- 插件市场详情页。
- 主题展示页。
- 文档阅读页。
- 帮助中心。
- 账户与社区页面。
- 内容展示型卡片和箱子页面。
- 官网式介绍页。
- 教程、公告、活动、作品集页面。

正确方向是：同一套 `View/Stack/Grid/Form/List` 声明式模型自然覆盖这些页面结构，并统一沉淀到常规组件组合和生态规范中。

- `View`：页面或区域语义根。
- `Stack`：纵向/横向内容流。
- `Grid`：响应式网格和卡片墙。
- `Form`：设置、登录、配置、反馈。
- `List`：文章列表、资源列表、条目列表。
- `Section`：内容分区。
- `ScrollView`：内容阅读与长页面。
- `Text/Image/Media`：内容表达。
- `Header/Footer/Aside/Main`：可作为普通页面区域语义，而不是新的应用类型。

这使薯片框架既能做生产力软件，也能处理网页式页面结构，而且仍然只有一套统一前端框架。

## 3. Web 技术栈底座的优势

以 Web 技术栈作为底层，薯片可以获得：

- Chromium 统一渲染能力。
- React 统一官方前端工程模型。
- CSS 变量与主题 token 的天然适配。
- HTML 语义与 a11y 基础。
- 现有 Web 项目的迁移和吸收可能。
- 浏览器开发工具、Playwright、视觉回归、性能指标等成熟工具。
- Electron Desktop、未来 Web Host Shell、未来 Mobile WebView/Capacitor 的统一基础。

这和薯片“一个 Host 大底座承载很多软件”的目标天然匹配。

## 4. 外部 Web 项目同化的启发

薯片未来如果要快速重做大量软件，不能每个软件都从零写。框架需要允许把外部 Web 项目快速吸收进生态，然后逐步同化：

1. 识别项目类型：React、Vite、静态 HTML、传统 SPA、组件库型项目。
2. 生成插件 manifest：补齐 `type: app`、`runtime.targets`、`ui.surface`、权限和入口。
3. 接入 Host：替换直接 Node/Electron/API 调用为 `window.chips.*` / SDK。
4. 接入主题：把硬编码颜色、字号、阴影、圆角逐步映射为 token。
5. 接入 i18n：抽取用户可见文案为 key。
6. 接入组件库：将高频基础控件替换为 Chips 组件。
7. 接入导航和命令：将路由、菜单、快捷键、工具栏纳入生态命令系统。
8. 接入质量门禁：a11y、性能、主题矩阵、视觉回归。

“同化”不是简单包一层 iframe，而是让外部 Web 项目逐步成为薯片生态应用。

## 5. 底层厚、上层薄的启发

薯片要重做大量软件，不能让每个应用都重复实现基础能力。常用模块应沉淀到底层：

- 文件、资源、配置、主题、多语言、插件、模块、卡片、箱子、日志、凭证、surface、transfer、association 由 Host 服务域提供。
- 表单、列表、表格、导航、命令、弹层、焦点、a11y、预览、性能工具由前端框架提供。
- 组件只负责结构、状态和 a11y。
- 应用插件只写业务流程、页面组合和少量特有逻辑。

这就是薯片版 SwiftUI 的核心：复杂性留在系统底座，上层应用写得短、清楚、统一。

## 6. 对薯片野心的定位

薯片前端框架的目标不是组件库，不只是开发体验，而是软件生态级应用框架：

- 能支撑生产力软件。
- 能用同一套页面结构表达工具界面、展示页面、文档页面、市场页面等不同场景。
- 能支撑插件市场和社区。
- 能支撑编辑器、播放器、阅读器、资源管理器。
- 能快速吸收外部 Web 项目。
- 能让所有应用拥有统一交互和视觉质量。
- 能把常用模块沉淀到底座，逐步形成可以重做大量软件的生态基础设施。
