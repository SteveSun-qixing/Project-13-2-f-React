# SwiftUI 调研：控件与样式系统

## 1. 这一层解决什么问题

SwiftUI 的控件系统覆盖动作、输入、选择、指标和分组；样式系统让控件在不同平台和上下文中保持一致，同时允许开发者按语义调整外观。

这说明高质量组件库不能只提供按钮和输入框，而要覆盖真实应用中大量常用操作，并且每个控件都应有状态、样式、可访问性和平台语义。

## 2. 控件覆盖面

| 能力 | 作用 |
|---|---|
| `Button` | 触发动作 |
| `Link` | 打开 URL 或导航到外部内容 |
| `Toggle` | 布尔开关 |
| `TextField` | 单行文本输入 |
| `SecureField` | 私密文本输入 |
| `TextEditor` | 长文本编辑 |
| `Picker` | 从互斥选项中选择 |
| `DatePicker` | 日期选择 |
| `ColorPicker` | 颜色选择 |
| `Slider` | 有界范围数值选择 |
| `Stepper` | 递增/递减 |
| `Menu` | 展示动作菜单 |
| `DisclosureGroup` | 展开或收起内容 |
| `Gauge` | 范围值指标 |
| `ProgressView` | 任务进度 |

## 3. 样式系统

SwiftUI 控件不只是固定外观，而是通过 style、tint、foreground/background、control size 等机制适应不同场景。样式和控件行为是分离的：控件表达语义和行为，样式决定外观。

这和薯片的“无头组件 + 主题 token”方向高度一致。

## 4. 设计价值

### 4.1 控件必须覆盖真实应用场景

设置页、编辑器、资源管理器、插件市场、主题编辑器、播放器、阅读器需要的控件远多于基础表单。

### 4.2 控件质量来自状态完整

一个控件至少要处理默认、hover、focus、active、disabled、loading、error、selected、invalid、readonly 等状态，并保证键盘和屏幕阅读器行为正确。

### 4.3 样式不是业务页面的责任

如果样式散落在应用页面里，生态一致性会迅速崩掉。SwiftUI 的样式体系启发薯片：组件结构与视觉主题必须严格解耦。

## 5. 对薯片的直接启发

薯片组件库的最低目标是覆盖 SwiftUI 基础控件，并补充 Web/Electron 生态常见高级控件：

- 基础输入：PasswordInput、Textarea、TextEditor、NumberInput、Slider、RangeSlider、Stepper。
- 选择输入：Picker、Combobox、Autocomplete、MultiSelect、TagInput、ColorPicker、DateRangePicker。
- 动作与菜单：Link、Menu、ContextMenu、CommandMenu、ToolbarItem。
- 展开与分组：Disclosure、Accordion、Section。
- 指标反馈：Progress、Gauge、Badge、Status、TaskProgress。
- 文件与系统：FileInput、DirectoryInput、HotkeyInput、ResourcePicker。

样式系统则由 `data-scope/data-part/data-state`、token、主题包、图标描述符、density 和 motion token 共同构成。
