# 任务029.03：统一文档窗口与 surface 生命周期收口

## 1. 任务目标

收口 `Chips-CardViewer` 的 `.card/.box` 显示链路、托管文档 iframe、surface resize、资源打开和 cleanup 逻辑，确保查看器只消费 Host/SDK 正式文档窗口接口。

## 2. 背景

当前 `CardWindow` 已通过 `client.document.window.render({ filePath, locale, mode: "view" })` 消费统一文档窗口。任务029必须保留这条正式链路：`.card` 内部分发到 Host card render，`.box` 内部分发到 Host box runtime 和布局插件。查看器不得重写基础卡片分发、iframe 拼接或箱子布局运行时。

## 3. 开发内容

1. 保留并强化 `client.document.window.render(...)` 作为 `.card/.box` 主入口。
2. 复核 `client.document.detectType(...)`、`onReady`、`onError`、`onResourceOpen`、`dispose` 的使用边界。
3. 将文档窗口生命周期接入 AppRuntime/Document Scene，避免业务组件分散管理 iframe 资源。
4. 复核 `HostedDocumentWindow` 的 `webDocumentUrl`、message 监听、`plugin.surface.resize` 和资源打开转发。
5. 若托管文档属于正式复合/箱子文档，按公共 sandbox/origin 标准收口；若属于独立 web route 文档，记录项目内部边界。
6. 资源打开继续走 `client.resource.open(...)`；不得私建卡片内部资源打开协议。
7. 确保 cleanup 释放 SDK/Host render session、box view session 和 DOM iframe。

## 4. 验收标准

- `.card/.box` 文件显示仍统一走 `client.document.window.render(...)`。
- 查看器不 import 基础卡片插件或布局插件源码。
- 托管文档 iframe 的 sandbox、message 过滤和 surface resize 路径有明确契约依据。
- 资源打开失败有可诊断错误态，且不破坏原有用户流程。
- 文档窗口卸载后不遗留 render session、box session 或 iframe 节点。

