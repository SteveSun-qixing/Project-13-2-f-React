### 3.4 运行时调用链

#### 3.4.1 `.card/.box` 文件渲染

`src/components/CardWindow.tsx` 当前主渲染链路：

- 调用 `client.document.detectType(filePath)` 识别 `.card/.box`。
- 调用 `client.document.window.render({ filePath, locale, mode: "view" })`。
- 将 SDK 返回的 iframe 挂载到容器。
- 监听：
  - `client.document.window.onReady(...)`
  - `client.document.window.onError(...)`
  - `client.document.window.onResourceOpen(...)`
- 资源打开请求调用 `client.resource.open(...)`。
- cleanup 时调用 `result.dispose()` 并移除 iframe。

`Chips-SDK/src/api/document.ts` 当前实现：

- `.card` 分发到 `cardApi.compositeWindow.render(...)`。
- `.box` 分发到 `boxApi.documentWindow.render(...)`。
- ready 事件覆盖 `chips.composite:ready` 与 `chips.box-layout:ready`。
- error 事件覆盖 `chips.composite:fatal-error` 与 `chips.box-layout:error`。
- `onResourceOpen` 当前代理 `cardApi.compositeWindow.onResourceOpen(...)`。

启动前判断：

- 主文件渲染路径已经基本符合“查看器只消费 SDK/Host 正式文档窗口链路”的要求。
- `.box` 通过 SDK 分发到 Host box runtime，当前查看器没有重写箱子布局逻辑，这是重要一致点。
- `onResourceOpen` 对箱子布局文档没有额外事件代理；按当前 box runtime 契约，布局内部 `openEntry` 等请求由 runtime bridge 处理。若查看器未来需要监听箱子资源打开外抛事件，需要先澄清契约。

#### 3.4.3 托管文档模式

`src/components/HostedDocumentWindow.tsx` 当前链路：

- 直接创建 `<iframe src={documentUrl}>`。
- 手写监听 `window.message` 中的 `chips.composite:ready`、`chips.composite:resize`、`chips.composite:fatal-error`、`chips.composite:resource-open`。
- 手写 `plugin.surface.resize` bridge emit。
- sandbox 为 `allow-scripts allow-same-origin allow-popups`。
- iframe title 为硬编码英文 `Hosted Card Document`。

启动前判断：

- 这条链路与正式复合卡片窗口标准存在明显漂移：正式复合 iframe sandbox 不应包含 `allow-same-origin`，应用层也应优先通过 SDK 事件接口消费 iframe 事件。
- 该模式可能是 web route 或托管复合文档的过渡入口；如果仍需保留，应在 vNext 迁移中映射为正式 Document scene/surface 模式，并尽量复用 SDK/组件库的 `EmbeddedDocumentFrame` / `CompositeCardWindow` 或正式事件订阅能力，而不是继续扩展私有 iframe 协议。

### 3.5 主题、多语言与组件库使用

当前状态：

- `src/App.tsx` 使用 `ChipsThemeProvider`。
- 当前主题从 `client.theme.getCurrent()` 和文档 `data-chips-theme-*` 快照读取。

- UI 文案大部分通过 `src/i18n/messages.ts`、本地 messages 与 `formatMessage(...)` 注入组件。
- `DropZone` 使用 `ChipsButton`，其余布局主要是自有 CSS/inline style。
- `CardWindow` 使用 `useThemeRuntime()` 触发主题 cacheKey 变化后重渲染文档窗口。

启动前判断：

- 已有主题/语言基础接线，且用户可见文案大部分没有直接硬编码在主 UI 中。
- 与 vNext 官方入口相比，当前没有使用 `ChipsEnvironmentProvider`、`useChipsTheme`、`useChipsI18n`、`useChipsSurface`、`useChipsPermissions` 等统一环境 hooks。
- `HostedDocumentWindow` 的 iframe title 仍是硬编码英文，需纳入 i18n。
- `DropZone` 和部分 CSS 存在大量 inline style、硬编码半径/尺寸/阴影和 token fallback 色值，应迁移到组件库/主题 token 体系；迁移时不能改变空态功能和交互含义。

### 3.6 文件选择与拖拽

当前状态：

- 点击打开走 `client.platform.openFile(...)`。
- 拖拽文件路径解析先查 `window.chips.platform.getPathForFile(file)`，回退到 Electron 常见 `file.path`。
- SDK 公共文档中已有 `client.platform.getPathForFile(file: unknown): string` 说明，底层会复用 `window.chips.platform.getPathForFile`。

启动前判断：

- 点击打开路径符合 SDK 正式链路。
- 拖拽路径解析建议迁移到 `client.platform.getPathForFile(file)`，减少直接访问 `window.chips` 与 `file.path`。
- Web target 已声明 supported，但拖拽本地文件路径、平台文件对话框和 `.card/.box` 本地路径语义在 Web route 下需要真实验证；不能只凭 desktop 行为判断 web target 已闭环。

### 3.7 测试与验证现状

当前测试文件：

- `tests/unit/app.test.tsx`
- `tests/unit/hosted-document-window.test.tsx`
- `tests/e2e/basic-flow.test.tsx`

复核判断：

- 已有基础渲染、托管文档 surface resize、基础 e2e mock 流程。
- 当前 e2e 主要是 mock `document.window.render` 的组件级流程，不等同于真实 Host + 真实 `.card/.box` 素材回归。
- 未见覆盖：
  - `manifest.yaml` command 权限断言。
  - `.card` 与 `.box` 从 Host 启动上下文进入查看器的真实链路。
  - 缺失基础卡片插件/布局插件时的错误诊断。
  - 主题切换与语言切换同步到壳层和内容 iframe。
  - command registry、菜单、工具栏、快捷键、命令面板。
  - 复合 iframe sandbox 不含 `allow-same-origin`。
  - 多文档/切换文件时 render session dispose 与事件 cleanup 的系统覆盖。

## 4. 已一致点

1. `manifest.yaml` 已声明 `file-handler:.card` 与 `file-handler:.box`，应用身份、入口和 surface 基础字段存在。
2. 主文档渲染已经通过 `client.document.window.render({ filePath })` 进入 SDK 统一文档窗口，而不是在查看器内手写 `.card/.box` 解析和 iframe 拼接。
3. `.box` 当前由 SDK 分发到 `boxApi.documentWindow.render(...)`，查看器没有重写箱子布局运行时。
4. 资源打开已通过 `client.resource.open(...)` 转发，方向符合 `resource.open` 公共契约。
5. cleanup 已调用 SDK 返回的 `dispose()`，对 render session 释放有基本意识。
6. 主题和语言已有基础接线，壳层能读取当前主题/语言并响应变化。
7. UI 主文案大多通过本地 i18n key 注入，没有大面积直接写死中文/英文文案。
8. 当前项目没有引入任务范围外的新第三方库，技术选型仍保持 React + component-library + chips-sdk。

## 6. 可能需登记工单

以下仅为启动前识别的候选项；按用户要求，本轮不登记、不创建工单目录。

1. `resource.open` 权限口径澄清：CardViewer 当前 manifest 只有 `resource.read`，但运行时调用 `client.resource.open(...)`。需要确认 Host route manifest 与 Manifest 配置规范是否要求独立声明资源打开权限。
2. `webDocumentUrl` 托管文档入口正式化：当前 `HostedDocumentWindow` 是真实存在的用户路径，但其 sandbox 与事件链路不符合正式复合窗口标准。需要确定它是正式 web document surface，还是历史过渡入口。
3. 拖拽 `File` 到本地路径的 SDK/Host 行为边界：公共 SDK 已提供 `client.platform.getPathForFile(file)`，但 web target 或无法暴露真实路径时的 `.card/.box` 打开策略需要明确。
4. 箱子文档资源打开事件是否需要统一外抛：当前 `document.window.onResourceOpen` 只代理 card composite resource-open；box layout runtime 多数资源动作在 runtime bridge 内部处理。如果查看器要统一诊断资源打开，需要补契约。
5. 组件库 `card-runtime` 与公共文档 sandbox 口径可能存在历史差异：公共文档要求复合 iframe 不含 `allow-same-origin`，但组件库部分 card-runtime 默认/测试仍可见 `allow-same-origin`。任务029应以公共契约和 SDK 正式渲染链路为准；若迁移用到该组件需先澄清。

## 7. 建议实施顺序

1. 冻结当前行为清单与测试基线

   先用现有代码提炼“空启动、打开文件、拖拽、launch targetPath、launch webDocumentUrl、loading/error/resource-open/cleanup”的行为断言。不要先改视觉或产品结构。

2. 调整 manifest 与包脚本基线

   复核 `.card/.box` file-handler、surface、runtime targets、资源与命令权限。按 vNext 应用基线补齐质量脚本，但脚本必须对应真实检查，不放空实现。

3. 建立 vNext 应用骨架

   将入口迁为 `src/app/AppRoot.tsx`、`AppProviders.tsx`、`AppRuntimeProvider.tsx`、`AppShell.tsx`、`scene-registry.ts`。`src/App.tsx` 保持 re-export。先保持 UI 行为不变。

4. 拆分 scene 与 document surface

   建议最少拆为：

   - `EmptyLaunchScene`：当前 DropZone 空态。
   - `CardDocumentScene` 或统一 `DocumentScene`：`.card` 文件查看。
   - `BoxDocumentScene` 或统一 `DocumentScene`：`.box` 文件查看。
   - `HostedDocumentScene`：仅在确认 `webDocumentUrl` 保留时迁移。

   文件类型分发仍以 `client.document.detectType` 和 `client.document.window.render` 为准，不写二套协议。

5. 收敛 SDK 与 Environment 使用

   将自有 `useChipsClient`、`useChipsBridge` 的业务消费迁到官方 Environment hooks。若某些 bridge 能力尚无 hook，限定在 runtime adapter 层，并记录为可能需工单的正式 API 缺口。

6. 接入 command registry

   以当前已有“打开文件”为第一条命令，保持按钮点击、菜单、快捷键、命令面板都触发同一个 command handler。若当前没有“最近打开/导出/诊断”可见入口，不要扩写产品行为；可等主代理确认后按既有设计接入。

7. 迁移 UI 到组件库与主题 token

   在行为测试通过后，再替换 DropZone、loading、error、path/status 等 UI 表达。目标是消除 inline style、硬编码颜色、硬编码标题和非 token 视觉值，同时保持当前交互路径不变。

8. 处理 `HostedDocumentWindow`

   这是迁移中最需要先决策的部分。建议先验证 `webDocumentUrl` 是否由 Host/测试空间正式使用；若使用，迁入正式 Document surface，并将 iframe sandbox、message 事件、resize、resource-open 向 SDK/组件库正式能力收敛。

9. 补真实 `.card/.box` 回归

   覆盖基础卡片组合、嵌套箱子、缺失插件、主题切换、语言切换、iframe ready/error/resize/resource-open/cleanup。真实素材可以落在成品测试空间或测试 fixtures，避免把测试只停在 mock render。

10. 最后同步项目内部文档

   任务完成后再根据真实代码更新 `Chips-CardViewer/README.md` 或项目内部技术文档。涉及生态公共契约变化时，另行进入正式公共文档收口，不在实现中夹带未核准的新规范。

## 9. 启动结论

`Chips-CardViewer` 当前并非从零开始：`.card/.box` manifest、主文档 `client.document.window.render(...)`、资源打开和基础主题/语言接线已经具备较好的正式链路基础。任务029的主要风险不在卡片或箱子底层渲染，而在应用壳层仍停留在旧结构：缺少 vNext App/Scene/Document surface 模型、官方 Environment Provider、command registry、完整质量脚本和真实 `.card/.box` 回归。

启动实现时应先保持现有用户可见行为不变，把结构迁到 vNext，再收敛主题/多语言/组件库/命令/测试。尤其不要把“工具栏、路径栏、最近打开、导出入口、诊断面板”理解成可自由新增的产品重设计；只有确认它们是既有或已冻结需求后，才应按命令系统和组件库标准迁移。
