## 2. 目标、范围与验收摘录

## 3. 相关设计理念与硬性约束

应用迁移总原则：所有 `type: app` 应用迁移统一使用 SDK/hooks、App/Scene/surface、统一布局、组件库、主题、多语言、命令、a11y 与质量门禁；应用清单包含 `Chips-EcoSettingsPanel` 等 8 个现有应用插件（`05-开发任务方案/任务20-现有应用插件全量迁移.md:3-20`）。迁移中应先读项目规则、manifest、package、源码入口、i18n、主题、测试，再做 manifest、运行时调用、UI、文案、命令导航和质量迁移（`任务20-现有应用插件全量迁移.md:30-72`）。

生态设置面板设计定位：它是整个生态配置管理入口，以应用插件运行，负责插件安装更新、主题切换、偏好配置和外部集成；插件管理、主题管理、服务状态、全局设置、快捷方式等都是其设计范围（`生态设计原稿/17-生态设置面板设计.md:3-8`、`17-生态设置面板设计.md:21-41`、`17-生态设置面板设计.md:45-55`）。设置面板与安装器边界明确，运行时配置由设置面板负责，系统级安装升级由安装器负责（`17-生态设置面板设计.md:57-65`）。

App/Scene/surface 设计理念：SwiftUI 调研强调应用结构应由 App 和 Scene 声明，设置、菜单、命令也纳入框架，而不是各应用临时拼接（`02-SwiftUI能力模型调研/03-App-Scene-Window-Document应用结构.md:3-8`、`:32-48`）。薯片重构方案要求 Host 是唯一运行时承载，`surface` 是跨平台界面容器主语义，Desktop 才映射 BrowserWindow；插件只能通过 `window.chips.*`、Runtime Client 或 SDK 正式链路访问能力（`04-薯片前端框架开发重构方案/01-薯片前端框架开发重构方案.md:23-37`）。

命令系统约束：菜单、工具栏、快捷键、命令面板、上下文菜单必须消费同一条 command 记录；命令 metadata 只能写 i18n key，不得写原始文案，图标必须是 `IconDescriptor`，真实调度走 Host command service（`生态共用技术文档/协议与契约/13-命令系统契约.md:3-8`、`:35-43`、`:148-177`）。

主题与多语言约束：主题治理必须走 `plugin.query({ type: 'theme' })`、`theme.list()`、`theme.getCurrent()`、`plugin.install/enable/uninstall`、`theme.apply` 等正式接口，安装/卸载/切换后不能只靠前端本地猜测（`生态共用技术文档/协议与接口标准/07-运行时设置治理接口标准.md:13-58`）。语言治理固定使用 `i18n.getCurrent()`、`i18n.listLocales()`、`i18n.setCurrent({ locale })` 和 `language.changed` 事件，语言切换后重渲染，不重启应用（`07-运行时设置治理接口标准.md:59-69`；`生态共用技术文档/协议与接口标准/03-多语言规范.md:7-25`）。

插件与快捷方式治理约束：应用插件治理必须以 `plugin.query({ type: 'app' })` 为列表基线，快捷方式状态必须由 Host 检查，治理类应用只能调用 Host 正式接口创建/删除快捷方式，不得自行创建 `.lnk`、`.app` 或平台文件（`07-运行时设置治理接口标准.md:70-156`）。

Manifest 约束：`type: app` 插件必须声明完整 `runtime.targets` 与 `ui.surface`，Host、SDK CLI 和脚手架校验都应把缺失这些字段视为无效 manifest（`生态共用技术文档/插件开发/06-Manifest配置规范.md:50-122`）。

组件库约束：应用插件可以直接使用 `@chips/component-library`，但业务页面不得硬编码组件视觉值、不得改写组件契约字段语义；组件库已提供布局原语、命令消费组件、复杂 Compound、Workbench、System UX 等正式导出（`生态共用技术文档/组件库/01-组件库对外使用总览.md:29-51`、`:137-168`、`:230-239`）。

## 6. 建议执行顺序

1. 冻结现有行为清单：从 `Chips-EcoSettingsPanel/需求文档`、`技术文档`、当前页面和测试中提取现有主题、语言、插件、快捷方式、组件展示行为，先写迁移对照表。迁移过程中只搬架构，不重设计产品行为。
2. 补齐入口架构：按 vNext 应用基线引入 `AppRoot/AppProviders/AppRuntimeProvider/scene-registry/commands`，把现有 `RuntimeProvider/I18nProvider/ChipsThemeProvider` 合并或迁移为正式 App Runtime，但保持现有用户路径和默认菜单顺序。
3. 命令优先：先为现有七类菜单和关键动作建立 command metadata、handlerId、i18n key、权限声明，再让导航、工具栏、快捷键和命令面板消费同一套 command。
4. SDK 正式接口收口：把 `platform.*` 裸 invoke 替换为 SDK Domain API；主题、语言、插件状态继续以 Host 返回为唯一事实来源。
5. UI 结构迁移：逐页把私有壳层迁移到组件库布局原语、Form/List/NavigationSplitView/Toolbar/MenuBar/CommandPalette 等正式组件，保留原有功能、状态和数据语义。
6. 新增治理入口：在不改变既有行为的前提下新增主题矩阵、组件 contract、主题 contract、缺失 token、诊断、预览/性能入口；如果 Host/SDK 没有正式接口，登记工单，不在前端伪造状态。
7. 测试分层补强：先单元测试 command metadata、runtime service、i18n adapter、组件矩阵；再补 Host mock/smoke、主题切换、语言切换、权限不足、快捷方式状态刷新。
8. 最后运行 `npm run verify`，必要时联动运行 SDK、Host、组件库、主题包相关验证。

## 7. 应避免的误区

## 9. 任务028内解决与后续工单建议

### 应在任务028内解决

- `Chips-EcoSettingsPanel` 自身 App/Scene/surface/commands 结构迁移。
- 现有功能行为保持前提下的 UI 布局原语/组件库替换。
- 现有裸 `client.invoke("platform.*")` 到 SDK platform Domain API 的收口。
- 现有七类治理页面的 i18n、主题 token、a11y、错误态、加载态、空态、权限不足测试补齐。
- command metadata、handlerId、权限、菜单/工具栏/快捷键/命令面板消费链路。
- 新增组件矩阵、主题矩阵、contract 状态、缺失 token 诊断和预览入口的前端承载，只消费正式 Host/SDK 数据。
- 同步 `Chips-EcoSettingsPanel` 内部 README/技术文档/需求文档中只属于本项目的实现说明，但本轮预研报告不应替代正式任务执行时的文档更新。

### 发现后应登记后续工单

- Host 或 SDK 缺少正式诊断接口，例如无法通过公开 API 获取组件 contract、主题 contract、缺失 token、L8/L9 诊断、质量报告或性能报告。
- `client.command.*`、组件库 command consumer 或 Host command registry 在真实设置面板迁移中无法满足菜单/工具栏/快捷键统一消费。
- 组件库正式导出与公共文档漂移，例如 `ChipsFormField/ChipsFormGroup` 仍被展示矩阵依赖但公共文档已将其归档。
- 主题包 contract 与组件库 contract 无法支撑设置面板新增矩阵或诊断入口。
- `chipsdev validate` 与公共 manifest 规范或当前应用 manifest 真实字段出现不一致。
- 开发工作区与用户工作区状态无法通过 Host 正式治理接口清晰区分，导致设置面板必须在前端猜测路径或状态。

## 10. 启动结论

任务028存在且与应用迁移对应，当前应以 `Chips-EcoSettingsPanel` 作为第一批应用迁移样板。当前工程已有正式 manifest、SDK/组件库依赖、运行时治理服务和基础页面，但距离任务028验收仍有明显差距：入口架构、commands、统一布局、诊断/矩阵/预览入口、测试覆盖是主线。建议主代理完成任务027后，先冻结现有行为清单，再按 App Runtime 与 command registry 迁移入口，最后补诊断矩阵与验证闭环。
