## 1. 复核结论

`Chips-MusicPlayer` 当前已经具备可用的首版音乐播放器能力：音频资源启动、文件关联、手动选择、拖放打开、同目录封面/歌词发现、MP3/FLAC/MP4/Ogg/Opus 常见嵌入元数据解析、嵌入封面转 PNG/缓存、HTML5 `<audio>` 播放控制、滚动歌词、移动端双页滑动和保存副本链路。当前 `npm run lint` 与 `npm test` 均通过，现有 14 个测试文件、56 个测试通过。

但它仍停留在旧式应用插件结构：`src/App.tsx` 同时承担 SDK client、Bridge 订阅、主题/语言、启动上下文、资源解析、元数据/封面/歌词、保存副本和反馈状态；`MusicPlayerStage` 直接持有 `<audio>` 控制器、键盘处理、移动端分页、歌词动画和画布背景；没有 `src/app/`、`src/runtime/`、`src/scenes/`、`src/commands/`，没有 `ChipsEnvironmentProvider/AppRuntimeProvider/scene-registry`，没有 Host command registry，manifest 也缺 `command.read/write/invoke`。e2e 仍是 `1 + 1` 占位，`app.test.tsx` 只验证 `App` 是函数。

任务032建议拆成 5 个中等颗粒度子任务，按“先冻结现状 -> 再迁 AppRuntime/DocumentScene -> 再拆播放会话与命令 -> 再收口壳层主题/i18n/焦点/A11y -> 最后真实素材和文档闭环”执行。不要把“播放队列”扩成媒体库产品；基于当前需求文档，032 中的队列应定义为启动批次/卡片上下文/多文件选择的轻量播放队列与上一首/下一首命令，不引入媒体库、随机播放或长期播放列表。

## 3. 当前行为冻结建议

任务032正式启动前，主代理应先把以下行为作为迁移对照基线冻结：

1. 输入入口：`launchParams.resourceOpen.filePath`、`launchParams.resourceOpen.resourceId`、`launchParams.resourceOpen.payload.kind = "chips.music-card"`、`launchParams.targetPath`、手动多文件选择、拖放多文件。
2. 支持格式：`.mp3/.flac/.wav/.ogg/.oga/.m4a/.aac/.opus/.webm`，`mimeType` 以 `audio/` 开头时判为支持。
3. 单曲播放：播放/暂停、进度拖动、前后 10 秒、音量、静音、单曲循环、buffering、媒体错误反馈。
4. 资源优先级：标题 `launch title > music-card display/config > embedded > lyrics metadata > filename`；歌词 `music-card lyrics > 显式/伴生 > embedded timed/plain > empty`；封面 `music-card/伴生 > embedded > default`。
5. 音乐基础卡片链路：`music-BCP` 查看态通过 `openResource(...)` 上抛音频资源意图和 `chips.music-card` payload，播放器从 payload 恢复封面、歌词、标题、歌手、专辑。
6. 视觉交互：左封面右歌词，封面主色生成背景/控制色，歌词时间轴滚动高亮，空态保留完整骨架，小屏纵向切成播放器页/歌词页双页滑动。
7. 保存副本：本地源走 `platform.saveFile + file.copy`，Web/远端/无稳定路径走下载 fallback，同路径保存给提示。
8. 清理：切换曲目和卸载时释放运行时 `blob:` 封面 URL；嵌入封面优先落盘到 Host 工作区临时 PNG。

## 4. 主要差距

1. `src/App.tsx` 是单体运行时入口，没有 vNext App/Scene/surface/Environment 结构。
2. `useChipsBridge` 直接读取 `window.chips` 并订阅 `language.changed`，应收口到 SDK/Environment 事件源；业务组件不应自行初始化 Host Bridge。
3. manifest 缺 `command.read`、`command.write`、`command.invoke`，也没有命令注册目录。
4. 播放/暂停、快进、音量、循环、保存、打开等动作只存在于 Stage/controller 回调和本地键盘处理，没有 Host command registry、菜单、工具栏、命令面板统一事实来源。
5. “播放队列”尚未建模。当前需求文档明确不做媒体库/播放列表，032 应只支持打开批次中的轻量队列和上一首/下一首，不改变产品定位。
6. 主题与多语言已有本地 JSON 和 `ChipsThemeProvider`，但未使用应用模板的 `ChipsEnvironmentProvider`、同步 i18n adapter 和 runtime `setLocale` 入口。
7. Stage 使用私有按钮/滑块/tooltip/CSS，部分 ARIA 已有，但未系统接入组件库命令消费、FocusScope、焦点恢复、A11y 测试 helper 与 reduced motion。
8. 嵌入封面 TIFF 当前在播放器工具里有应用内 baseline 解码回退；文档写了优先走 Host `resource.convertTiffToPng`，032 应复核是否仍允许保留该回退。若架构红线认定播放器不应承载图像转换基础设施，应由主代理登记/拆后续 Host/模块能力工单。
9. README 和需求文档仍含原工作区路径 `/Project-13-2-f`，迁移闭环阶段要改为当前 worktree 友好的相对口径。
10. `tests/e2e/basic-flow.test.ts` 是占位，`tests/unit/app.test.tsx` 覆盖不足，缺 AppRuntime/Scene/Command/Host launch/真实素材/清理回归。

## 6. 需要主代理判断的问题

1. **播放器内 TIFF/PNG 工具边界**  
   当前播放器有 `src/utils/tiff.ts`、`src/utils/png.ts` 和 `artwork-runtime.ts` 的应用内 baseline 解码/编码回退。任务032要求“音频资源读取、封面解析、格式转换、TIFF 转 PNG 等能力优先走 Host/模块正式接口”。主代理应判断：这是可接受的浏览器展示回退，还是应登记“媒体封面图像转换能力下沉 Host/模块”的后续工单。

2. **播放队列边界**  
   任务032总文档提到“播放队列”，但 `Chips-MusicPlayer` 需求文档明确不做播放列表/媒体库。建议本轮只做打开批次轻量队列、上一首/下一首、队列状态，不做随机播放、媒体库、持久播放列表。

3. **媒体键能力**  
   任务032提到媒体键，但当前公共文档里未看到已冻结的 Host 媒体键服务。若 Host/SDK 当前没有正式媒体键事件入口，不应在播放器里直接监听 OS 私有能力，建议登记后续 Host `mediaSession`/platform media key 工单。
