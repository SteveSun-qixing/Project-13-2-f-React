## 3. 真实 e2e 推荐设计

### 3.1 临时生态根

建议在 `run-generated-e2e.cjs` 中建立临时生态根：

- `sandboxRoot = fs.mkdtemp(os.tmpdir()/chips-module-scaffold-e2e-)`；
- symlink 当前 worktree 的 `Chips-SDK`、`Chips-Scaffold`、`Chips-ComponentLibrary`，必要时也 symlink `Chips-Host`、`ThemePack`；
- 写入临时根 `package.json`：
  - `name: "chips-ecosystem-workspace"`；
  - `private: true`；
  - `volta.node = process.versions.node`；
  - `volta.npm = "10.9.3"`，与 SDK 测试当前口径一致；
  - `workspaces` 采用现有生态根常用模式；
  - `overrides` 可沿用 SDK create-module 测试中的 `tldts/tldts-core` 锁定，避免 npm 解析漂移。
- env 设置：
  - `CHIPS_ECOSYSTEM_ROOT=sandboxRoot`；
  - `NPM_CONFIG_CACHE=sandboxRoot/.npm-cache` 与 `npm_config_cache`；
  - 需要 CLI 入口时用 `node ${ecosystemRoot}/Chips-SDK/cli/index.js ...`，避免依赖全局 bin。

### 3.2 workspace 注册与生成工程

在 `sandboxRoot` 下执行：

```bash
node Chips-SDK/cli/index.js create module validation-projects/module-smoke
```

必须断言：

- 临时根 `package.json.workspaces` 包含 `validation-projects/module-smoke`；
- 生成工程 `package.json.volta.extends` 指向临时生态根 `package.json` 的相对路径；
- `chips.config.mjs` 为 `type: "module"`；
- `manifest.yaml` 中：
  - `id: chips.module.module.smoke` 或当前 CLI slug 规则对应值；
  - `type: module`；
  - `entry: dist/index.mjs`；
  - `runtime.targets.desktop.supported: true`；
  - `runtime.targets.headless.supported: true`；
  - `runtime.targets.web/mobile.supported: false`；
  - `module.apiVersion: 1`；
  - `module.runtime: worker`；
  - `module.activation: onDemand`；
  - `module.provides[].capability` 与生成能力一致；
  - `run` mode 为 `sync`，`runAsync` mode 为 `job`；
  - 每个 method 都有 `inputSchema/outputSchema`；
  - `module.consumes: []` 存在且合法。

### 3.3 生成工程安装与质量门禁

在临时生态根执行一次：

```bash

```

随后在生成工程目录执行：

```bash
npm run verify
```

- `lint`: `chipsdev lint`
- `typecheck`: `tsc -p tsconfig.json --noEmit`
- `test`: `chipsdev test`
- `build`: `chipsdev build`
- `validate`: `chipsdev validate`
- `package`: `chipsdev package`
- `verify`: 串联 `lint`、`typecheck`、`test`、`build`、`validate`、`package`

建议把 `verify` 排在生成工程 README 的首选命令中，`build/test/validate/package` 仍作为拆分命令说明。

### 3.4 `.cpk` 唯一输出

`npm run verify` 后断言：

- `dist/index.mjs` 存在；
- `dist/*.cpk` 只有一个；
- `.cpk` 文件名等于 `${safeManifestId}-${version}.cpk`，当前 `chipsdev package` 规则是把 manifest id 中非 `[a-zA-Z0-9_.-]` 替换为 `_`；
- `.cpk` 可作为 `plugin.install` 的 `manifestPath` 输入；
- 包内不应包含二次嵌套的 `.cpk` 或重复 manifest。

如需检查包内容，可参考 SDK `chipsdev package` 逻辑使用现有 `StoreZipService` 或 Host 安装链路间接证明，不建议在脚手架 e2e 里复制打包实现。

### 3.5 Host 构建与临时 Host 工作区

建议在 e2e 中执行：

```bash
npm run build
```

目录为真实工作区 `Chips-Host`，确保 `dist/src/main/core/host-application.js`、`dist/src/renderer/runtime-client.js`、`dist/src/runtime/plugin-runtime.js`、`dist/src/main/electron/dev-invoke-module.js` 可用。

临时 Host 工作区：

- `hostWorkspace = fs.mkdtemp(os.tmpdir()/chips-module-host-workspace-)`；
- 用 `PluginRuntime(hostWorkspace, { locale: "zh-CN", themeId: "chips-official.default-theme" })` 加载；
- 安装并启用 `ThemePack/Chips-default/manifest.yaml`；
- 再创建 `HostApplication({ workspacePath: hostWorkspace })` 并 `start()`；
- 用 `RuntimeClient(app.createBridge(), ...)` 作为调用端。

这部分可以直接参考 SDK create-module 测试，但主代理应考虑抽出小的 e2e helper 函数以降低脚本长度。

### 3.6 模块 `.cpk` 安装启用与 Provider 发现

通过 RuntimeClient 走正式 Host 路由：

```js
const installed = await runtimeClient.invoke("plugin.install", { manifestPath: packagedModulePath });
await runtimeClient.invoke("plugin.enable", { pluginId: installed.pluginId });
const providers = await runtimeClient.invoke("module.listProviders", { capability: moduleCapability });
```

断言：

- `installed.pluginId` 等于生成工程 `package.json.name` / manifest id；
- `module.listProviders` 返回的 providers 至少包含该 `pluginId`；
- provider 状态应先是 `enabled`，sync/job invoke 后可变为 `running`；
- provider methods 包含 `run`、`runAsync`，模式分别为 `sync`、`job`；
- `module.resolve({ capability })` 可返回同一 provider，建议纳入断言。

### 3.7 `module.invoke` 同步调用

通过 RuntimeClient 调：

```js
await runtimeClient.invoke("module.invoke", {
  capability: moduleCapability,
  method: "run",
  input: {
    sourceText: "hello from scaffold",
    uppercase: true,
    prefix: "[host] "
  }
});
```

断言：

- result.mode 为 `sync`；
- output 为模板实现的真实输出；
- `handledBy` 等于生成模块插件 id；
- schema 校验生效：传入额外字段或缺少 `sourceText` 时应抛出 `MODULE_SCHEMA_INVALID`。

### 3.8 `module.invoke` job 调用与轮询

通过 RuntimeClient 调：

```js
const started = await runtimeClient.invoke("module.invoke", {
  capability: moduleCapability,
  method: "runAsync",
  input: { sourceText: "async scaffold", delayMs: 1 }
});
```

断言：

- started.mode 为 `job`；
- `module.job.get({ jobId })` 可轮询到 `completed`；
- completed job output 与同步方法输出结构一致；
- progress 最终应有 `{ stage: "completed", percent: 100 }` 或至少存在 progress 字段。

### 3.9 取消与错误路径是否纳入

建议纳入，但分层处理：

- 错误路径：优先纳入，成本低。用无效输入触发 Host schema 校验即可，不需要改模板新增“失败方法”。断言错误 code/message 包含 `MODULE_SCHEMA_INVALID`。
- 取消路径：建议在 RuntimeClient 黑盒链路中纳入，不建议通过当前 `chipsdev module invoke` CLI 纳入。当前 CLI 的 `dev-invoke-module.ts` 会等待 job 终态，并在非 `completed` 时以失败退出；它没有“启动后取消”的参数。脚手架 e2e 可直接：
  1. 启动 `runAsync`，`delayMs` 设为 200-500；
  2. 立即 `module.job.cancel({ jobId })`；
  3. 断言返回 `{ ack: true }`；
  4. `module.job.get` 看到 `cancelled`，error code 为 `MODULE_JOB_CANCELLED`。
- cleanup 基线：无论断言成功失败，必须在 `finally` 中 `app.stop()` 并删除临时 Host workspace 与临时生态根。

如果 026.02 改造模板后 `runAsync` 开始主动读取 `ctx.job.isCancelled()` 或 `ctx.job.signal`，取消断言可以更强；若仍保持当前模板，Host 已会在 `module.job.cancel` 时把 job 标记为 `cancelled`，模板 sleep 结束后也不会覆盖为 completed。

### 3.10 CLI `chipsdev module invoke` 是否也要跑

建议至少纳入一条轻量 CLI 验证：

```bash
node Chips-SDK/cli/index.js module invoke --capability <capability> --method run --input '{"sourceText":"cli"}'
```

用途：

- 证明 README 推荐的正式 CLI 入口可用；
- 覆盖 `ensureDevWorkspaceThemeBootstrap`、`dev-invoke-module.ts`、Electron runner 输出 JSON。

但完整 sync/job/cancel/error 仍建议使用 `RuntimeClient`，避免 e2e 过慢、重复启动 Electron runner 太多次。若采用 CLI 测试，需要参考 SDK `run-cli-module-invoke-tests.cjs` 的 mock electron loader，避免真实 GUI 依赖。

### 6.6 Host 模块调用

- `module.listProviders({ capability })` 返回生成模块 provider；
- `module.resolve({ capability })` 返回同一 provider；
- 同步 `module.invoke` 返回 `{ mode: "sync", output }`；
- 输出 schema 与模板逻辑一致；
- 异步 `module.invoke` 返回 `{ mode: "job", jobId }`；
- `module.job.get` 轮询到 `completed`；
- job output 与模板逻辑一致；
- 无效输入触发 `MODULE_SCHEMA_INVALID`；
- `module.job.cancel` 对长延迟 job 返回 `{ ack: true }`，后续 `module.job.get` 为 `cancelled`。

## 7. 预计风险

- e2e 时间会明显增加，尤其是 `npm install`、Host build、Electron runner；建议脚本输出清晰阶段日志，便于定位失败阶段。
- `npm install` 容易受网络与 npm cache 影响。SDK 测试已有独立 cache 与 overrides，026.03 应沿用，不新增依赖。
- `chipsdev module invoke` 每次都会拉起 Electron Host，重复调用会慢；完整矩阵建议用单个 `HostApplication` 进程内 RuntimeClient 完成。
- 当前 `chipsdev module invoke` CLI 无取消参数，取消路径不要强行塞进 CLI，应走 RuntimeClient。
- `module.job.cancel` 标记取消后，模板实现如果不主动检查 signal，仍会执行到结束；Host 当前会保持 cancelled，不会写 completed output。断言应以 Host job 状态为准。
- 026.02 可能调整模板形态矩阵，026.03 开始前要重新核对最终模板文件名、method 名、schema 名与 README 文案，避免报告中的 `run/runAsync` 名称过期。
