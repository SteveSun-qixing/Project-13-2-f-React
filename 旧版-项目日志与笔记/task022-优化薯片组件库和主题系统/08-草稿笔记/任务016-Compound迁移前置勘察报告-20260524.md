## 2. 总体结论

当前 10 个目标组件中，组件库已有大部分“单体 props API + data-part contract + a11y helper + 少量测试”，但基本没有任务016要求的 Compound 静态子组件导出。搜索 `Dialog.Root`、`Object.assign`、`Compound` 等未发现组件库运行时存在正式 Compound API。

Host L8 的 `StandardCompoundSlotSchemas` 只覆盖 `Dialog / Tabs / Menu / Form / DataGrid` 五个组件，且公共文档也只冻结这五个。缺少 `Popover / Select / Tree / CommandPalette / NavigationSplitView`。Host 单测覆盖 Dialog 的缺失/重复/未声明/类型错误诊断，以及 Tabs/Menu/Form/DataGrid 的最小 schema 校验；缺少另外五个 schema 的测试。

主题 contract 覆盖了当前单体运行时 parts，但与任务016目标存在明显差距：Dialog 缺 `header/body/footer/actions`，Menu 缺 `group/separator`，DataGrid 缺 `toolbar/pagination`，Tree 当前是 `node/toggle/label/children` 而不是 `item/branch/leaf/disclosure`，CommandPalette 当前是 `search` 且 token 使用 `result.*`，NavigationSplitView 当前不存在独立 contract，仅有布局原语 `split-view`。

建议任务016按“垂直切片”拆分：每个子工单在同一轮完成某个组件或组件簇的运行时 Compound API、类型、测试、theme contract、Host L8 schema、公共文档同步。不要先导出半套 `X.Root`，也不要只改类型或只改 Host schema。

## 3. 10 个组件现状矩阵

### 3.1 Dialog

- 目标 API：`Dialog.Root/Trigger/Content/Header/Body/Footer/Actions/Close`。
- 运行时现状：`ChipsDialog` 是单体 `React.forwardRef`。props 包含 `open/defaultOpen/triggerContent/title/description/children/closeButton* / closeOnBackdrop / closeOnEscape / modal`。运行时输出 parts：`root / trigger / backdrop / content / title / description / close / status`。缺少 Compound 子组件，缺少 `header/body/footer/actions` part。
- 类型现状：`DialogProps` 是单体 props，`ChipsDialog` 类型为 `React.ForwardRefExoticComponent<DialogProps & RefAttributes<HTMLDivElement>>`；没有 `Dialog.Root` 等静态成员类型。
- 测试现状：`index.test.mjs` 只验证导出存在、a11y helper、buildComponentContract tokens；`a11y-stage9.test.mjs` 校验 trigger button 语义；Host 单测覆盖 `StandardCompoundSlotSchemas.Dialog` 的 slot 诊断。
- 主题 contract：`dialog.contract.json` parts 为 `root/trigger/backdrop/content/title/description/close/status`，tokens 覆盖 backdrop/content/title/close/focus。未覆盖任务016目标的 header/body/footer/actions。
- 风险：如果任务016将 `title/description` 提升为 `Header/Body` 语义，需要同步 contract 与 ThemePack CSS/token；否则 Host schema 的 `header/body/footer/actions` 与组件库 contract 不一致。

### 3.2 Popover

- 目标 API：`Popover.Root/Trigger/Content/Arrow`。
- 运行时现状：`ChipsPopover` 是单体 `React.forwardRef`。props 包含 `open/defaultOpen/triggerContent/children/closeOnEscape`。运行时输出 parts：`root / trigger / positioner / content / arrow / status`。目标 parts 基本存在，但没有 Compound 子组件。
- 类型现状：`PopoverProps` 是单体 props，`ChipsPopover` 无静态子组件类型。
- 测试现状：组件库测试覆盖导出、a11y helper、contract；Host 没有 `StandardCompoundSlotSchemas.Popover`。
- 主题 contract：`popover.contract.json` 覆盖 `root/trigger/positioner/content/arrow/status`，与目标 `Trigger/Content/Arrow` 方向基本一致。
- 风险：Popover 是较适合优先迁移的组件，主题包通常不需要纯主题前置任务；只有当 `positioner/status` 是否纳入 Compound 公开 part 发生变化时才需要同步 contract/CSS。

### 3.3 Tabs

- 目标 API：`Tabs.Root/List/Trigger/Panel`。
- 运行时现状：`ChipsTabs` 是基于 `items[]` 的单体 API。运行时输出 parts：`root / list / trigger / panel / status`，role 为 `tablist/tab/tabpanel`，支持方向键/Home/End。
- 类型现状：`TabsItem` 与 `TabsProps` 仍以 `items` 描述 tab label/content；没有 `Tabs.List/Trigger/Panel` 类型。
- 测试现状：组件库测试覆盖导出、a11y helper、contract；Host `StandardCompoundSlotSchemas.Tabs` 已存在，Host 单测覆盖 trigger 类型不匹配诊断。
- 主题 contract：`tabs.contract.json` 覆盖 `root/list/trigger/panel/status`，与目标 parts 基本一致。
- 风险：迁移时需要把 `items[]` 数据模式转为显式子组件组合，同时保留可访问关联：trigger id、panel id、`aria-controls/aria-labelledby`。当前未发布第一版，不建议为了兼容保留双 API 长期并存。

### 3.4 Menu

- 目标 API：`Menu.Root/Trigger/Content/Item/Group/Separator`。
- 运行时现状：`ChipsMenu` 是基于 `items[]` 的单体 API。运行时输出 parts：`root / trigger / content / item / status`，支持 Arrow/Home/End/Escape 与 `menu/menuitem`。没有 group/separator。
- 类型现状：`MenuItem` 与 `MenuProps` 是数据驱动；无 `Menu.Group/Separator` 类型。
- 测试现状：组件库测试覆盖导出、a11y helper、contract；Host `StandardCompoundSlotSchemas.Menu` 已存在并包含 `group/separator`，Host 单测覆盖一个合法 Menu compose。
- 主题 contract：`menu.contract.json` 仅覆盖 `root/trigger/content/item/status`。缺 `group/separator` parts 和 tokens。
- 风险：Host schema 已比组件库 contract 更完整。任务016必须同轮补齐 runtime/type/contract，否则会继续出现 L8 可声明但 L10 无主题挂点的错位。

### 3.5 Select

- 目标 API：`Select.Root/Trigger/Content/Option/Value`。
- 运行时现状：`ChipsSelect` 是基于 `options[]` 的单体 API。运行时输出 parts：`root / trigger / value / icon / list / option / status`，role 为 trigger button + listbox/option。没有 `Content` part，当前弹层 part 名为 `list`。
- 类型现状：`SelectOption` 与 `SelectProps` 是数据驱动；无 `Select.Root/Option/Value` 类型。
- 测试现状：组件库测试覆盖导出、a11y helper、contract；Host 没有 `StandardCompoundSlotSchemas.Select`。
- 主题 contract：`select.contract.json` 覆盖 `root/trigger/value/icon/list/option/status`。目标 `Content` 与当前 `list` 命名不一致。
- 风险：需要先确定公共命名：若任务016按 `Content` 冻结，则 contract/token/CSS 需从 `list` 迁移或明确 `Content` 对应 `data-part="list"`。在“不做兼容性包袱”的前提下，建议一次性统一公开 part 名称，避免 `Content/list` 双口径长期存在。

### 3.6 Form

- 目标 API：`Form.Root/Section/Field/Label/Control/Error/Hint`。
- 运行时现状：组件库没有独立 `ChipsForm` 导出；当前是 `ChipsFormField` 和 `ChipsFormGroup` 两个单体组件。`ChipsFormField` parts 为 `root / label / control / helper / error / status`；`ChipsFormGroup` parts 为 `root / legend / description / content / status`。
- 类型现状：只有 `FormFieldProps` 与 `FormGroupProps`；无 `Form.Root/Section/Field/...` 类型。
- 测试现状：组件库测试覆盖 `ChipsFormField/ChipsFormGroup` 导出、a11y helper、contract。Host `StandardCompoundSlotSchemas.Form` 已存在，slot 为 `section/field/label/control/error/hint`，但其中 `field` 的 type 是 L8 `Form`，这与组件库 `form-field` 命名并不直接对齐。
- 主题 contract：只有 `form-field.contract.json` 与 `form-group.contract.json`，没有 `form.contract.json`。`form-field` 使用 `helper`，目标 slot 是 `Hint`。
- 风险：这是任务016里最大的一处命名/职责收口点。需要决定 `Form` 是新 root 组件，还是由 `Form.Root` 聚合 `Form.Field` 并继续复用 `form-field` scope。公共文档、Host schema、组件库 contract 必须同轮统一，不能让 `Form`、`form-field`、`form-group` 三套语义继续漂移。

### 3.7 DataGrid

- 目标 API：`DataGrid.Root/Toolbar/Header/Row/Cell/Pagination`。
- 运行时现状：`ChipsDataGrid` 是基于 `columns[]/rows[]` 的单体 API。运行时输出 parts：`root / table / header / row / cell / status`，role 为 `grid/row/gridcell`，支持排序、行选择和键盘上下/Home/End。没有 toolbar/pagination。
- 类型现状：`DataGridColumn`、`DataGridRow`、`DataGridProps` 是数据驱动；无 `DataGrid.Toolbar/Header/Row/Cell/Pagination` 类型。
- 测试现状：组件库测试覆盖导出、a11y helper、`applyDataGridSort` 纯函数、contract。Host `StandardCompoundSlotSchemas.DataGrid` 已存在，并要求 `header/row/cell` 为 `Table` 类型，`toolbar/pagination` 为 optional Toolbar。
- 主题 contract：`data-grid.contract.json` 覆盖 `root/table/header/row/cell/status`。缺 `toolbar/pagination` parts 和 tokens。
- 风险：Host schema 已包含 toolbar/pagination，但组件库 contract/runtime 未覆盖。迁移时还要考虑 `table` part 是否保留为内部结构，避免把 Compound slot 与实际 table DOM 混成一层。

### 3.8 Tree

- 目标 API：`Tree.Root/Item/Branch/Leaf/Disclosure`。
- 运行时现状：`ChipsTree` 是基于 `nodes[]` 的单体 API。运行时输出 parts：`root / node / toggle / label / children / status`，role 为 `tree/treeitem`，支持展开、选择、方向键和层级 `aria-level`。没有 `item/branch/leaf/disclosure` 命名。
- 类型现状：`TreeNode` 与 `TreeProps` 是数据驱动；无 `Tree.Item/Branch/Leaf/Disclosure` 类型。
- 测试现状：组件库测试覆盖导出、a11y helper、`flattenTreeNodes/findTreeParentId` 纯函数、contract；Host 没有 `StandardCompoundSlotSchemas.Tree`。
- 主题 contract：`tree.contract.json` 覆盖 `root/node/toggle/label/children/status`。目标 part 命名整体不一致。
- 风险：若按任务016目标重命名为 `item/branch/leaf/disclosure`，这是 contract/token/CSS 变更，必须同步 ThemePack。建议不要保留 `node/toggle` 兼容别名；当前未发布第一版，应一次性收口。

### 3.9 CommandPalette

- 目标 API：`CommandPalette.Root/Input/List/Item/Group`。
- 运行时现状：`ChipsCommandPalette` 是单体 API，已接入 command provider/adapter。运行时输出 parts：`root / trigger / search / list / item / shortcut / status`。没有 `input` 和 `group`，当前输入 part 叫 `search`。
- 类型现状：`CommandPaletteProps` 支持 `items/commands/adapter/i18n/commandQuery/payload/invocationContext` 等；无 `CommandPalette.Root/Input/List/Item/Group` 类型。
- 测试现状：组件库测试覆盖导出、a11y helper、`filterCommandPaletteItems` 和 command helper；Host 没有 `StandardCompoundSlotSchemas.CommandPalette`。
- 主题 contract：`command-palette.contract.json` parts 为 `root/trigger/search/list/item/shortcut/status`，但 tokens 使用 `chips.comp.command-palette.result.surface.active` 与 `chips.comp.command-palette.result.text.color`。这里已经存在 `part=item` 与 `token=result` 的口径不一致。
- 风险：迁移前应先把 `search/input` 与 `item/result` 命名统一。若引入 `Group`，contract 与 ThemePack CSS/token 必须同轮更新。CommandPalette 还与任务007 command registry 相关，不应在组件库内直接绑定业务动作。

### 3.10 NavigationSplitView

- 目标 API：`NavigationSplitView.Root/Sidebar/Content/Detail`。
- 运行时现状：组件库没有 `ChipsNavigationSplitView`。当前接近能力是布局原语 `ChipsSplitView`，从 `layout-primitives.js` 经 `index.js` 导出，parts 为 `root / primary / secondary / detail / divider / status`，props 为 `primary/secondary/detail/variant`，variant 支持 `two-column/three-column/sidebar-detail`。
- 类型现状：`ChipsSplitViewProps` 定义在 `layout-primitives.d.ts`；无 `NavigationSplitView` 类型。
- 测试现状：`index.test.mjs` 和 `layout-primitives.test.mjs` 覆盖 `ChipsSplitView` 导出、data-part、a11y helper；Host 没有 `StandardCompoundSlotSchemas.NavigationSplitView`。
- 主题 contract：只有 `split-view.contract.json`，覆盖 `root/primary/secondary/detail/divider/status`。没有 `navigation-split-view.contract.json`，没有 `sidebar/content/detail` 命名。
- 风险：`SplitView` 是通用布局原语，`NavigationSplitView` 带导航语义。建议任务016不要把两者混写：要么明确新增 `navigation-split-view` scope 和 contract，要么正式把任务目标改为 `SplitView.Root/Sidebar/Content/Detail`。按当前任务文本，倾向新增 NavigationSplitView 垂直切片，并保留 `ChipsSplitView` 的布局原语职责。

## 4. Host StandardCompoundSlotSchemas 覆盖情况

当前 `Chips-Host/src/renderer/declarative-ui/composition.ts` 中 `StandardCompoundSlotSchemas` 覆盖：

- `Dialog`：`trigger/content/header/body/footer/actions/close`。
- `Tabs`：`list/trigger/panel`。
- `Menu`：`trigger/content/item/group/separator`。
- `Form`：`section/field/label/control/error/hint`。
- `DataGrid`：`toolbar/header/row/cell/pagination`。

缺少：

- `Popover`：任务目标 `trigger/content/arrow`。
- `Select`：任务目标 `trigger/content/option/value`。
- `Tree`：任务目标 `item/branch/leaf/disclosure`。
- `CommandPalette`：任务目标 `input/list/item/group`。
- `NavigationSplitView`：任务目标 `sidebar/content/detail`。

现有 Host 测试覆盖：

- `createCompoundComponent` 的显式 slot compose。
- Dialog 的 required、type mismatch、multiple forbidden、undefined slot 结构化诊断。
- Tabs/Menu/Form/DataGrid 的标准 schema 最小校验。
- boolean mode prop 阻断。

现有 Host 测试未覆盖：

- Popover/Select/Tree/CommandPalette/NavigationSplitView schema。
- 每个标准 schema 的完整合法 compose 输出顺序。
- schema 的 `part/role` 与组件库 contract parts 的一致性。
- `StandardCompoundSlotSchemas.Form` 中 `field` 使用 L8 `Form` 类型是否符合组件库 `Form.Field` 设计。

## 5. 建议拆分子工单

拆分原则：

- 每个子工单只要导出某个组件的 Compound API，就必须同时完成运行时、类型、测试、contract、Host schema、公共文档同步，避免半套 API。
- 主题包不单独提前做纯主题任务；只有当该子工单改变 `data-part`、token 或 CSS selector 时，才在同一子工单同步 ThemePack 默认与暗色主题。
- 公共生态规则落入 `生态共用技术文档/`；过程记录留在 `项目日志与笔记/`。

## 6. 主题包介入判断

不建议提前开纯主题包任务。主题包应只在对应组件子工单实际改变 contract/token/CSS 时同步介入。

当前明确可能需要 ThemePack 同步的点：

- Dialog：若新增 `header/body/footer/actions` parts 和 tokens。
- Menu：若新增 `group/separator` parts 和 tokens。
- Select：若将 `list` 收口为 `content`，或新增 `content` token。
- Form：若新增 `form` root scope，或把 `helper` 统一为 `hint`。
- DataGrid：若新增 `toolbar/pagination` parts 和 tokens。
- Tree：若从 `node/toggle` 迁移到 `item/branch/leaf/disclosure`。
- CommandPalette：若统一 `search/input` 或 `result/item` token 命名，且新增 `group`。
- NavigationSplitView：若新增 `navigation-split-view` scope/token/CSS，或重命名 `split-view` parts。

当前不一定需要 ThemePack 前置介入的点：

- Popover：现有 contract 已覆盖 `trigger/content/arrow`，只要 part 不改名，主题包可不变。
- Tabs：现有 contract 已覆盖 `root/list/trigger/panel/status`，只要只是 API 迁移且 part 不改名，主题包可不变。
- Host schema-only 补齐：如果没有改变组件库 contract 和 CSS selector，不需要 ThemePack。

## 7. 风险与建议

1. 最大风险不是缺组件，而是命名漂移：`Content/list`、`Hint/helper`、`Item/result`、`Tree node/item`、`SplitView primary/sidebar` 需要在公共文档、Host schema、组件库 contract、ThemePack CSS 中一次性统一。
2. 当前组件库 `index.js` 体量很大，任务016如果继续全部堆在单文件里会提高维护风险；但是否拆文件属于架构动作，应由主代理结合现有组件库结构决策，不应在子代理报告里先行改动。
3. Host `StandardCompoundSlotSchemas.Form.field` 当前 type 为 `Form`，后续若组件库正式引入 `Form.Field`，需要复核 L8 语义原语是否要新增更精确的 `Field` 类型，或者通过 `Slot`/`Section` 表达，避免 `Form` 嵌套 `Form` 的误解。
4. DataGrid 和 Tree 的 Compound 迁移不能只改 JSX 组合，还要保留当前排序、选择、展开、键盘导航、ARIA 行列/层级语义测试。
5. CommandPalette 必须继续走 command adapter/registry 正式链路，不能把业务命令函数直接塞进组件库。
6. NavigationSplitView 不应简单等同于布局原语 `SplitView`；如果它是导航语义组件，应有独立 scope/contract/schema。
