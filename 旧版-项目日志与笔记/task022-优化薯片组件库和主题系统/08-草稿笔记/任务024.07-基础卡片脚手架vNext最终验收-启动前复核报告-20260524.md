## 验收风险清单

1. 024.06 完成状态需要先确认。

   当前 `07-工作日志` 只有 024.01-024.05，未看到 `任务024.06-基础卡片脚手架公共文档收口` 完成日志。公共文档 `03-卡片插件开发.md` 当前已经包含脚手架默认结构、`resource_path`、资源桥、cleanup、组件库、`verify` 等内容，但最终验收前应确认这些改动确实属于 024.06 收口结果，并补写 024.06 工作日志。

2. `template.json` 仍会复制到生成工程。

   `template-engine.ts` 会遍历模板目录全部文件；当前 `template.json` 会生成到目标工程，测试也读取生成后的 `template.json`。如果“模板身份泄露”定义为不得出现 `card-standard` 或模板元数据文件，则这是风险；如果 `template.json` 被定义为正式生成工程元数据，则需要在 024.07 日志中明确说明并让门禁只禁止 `chips-scaffold-basecard/app-standard/旧命令` 等泄露项。

3. 资源打开 payload 仍是通用示例形状，验收时需确认是否足够正式。

   `view.tsx.tpl` 的 `openResource` payload 当前为 `{ cardType, resourcePath }`，没有 `kind/version/relativePath` 这类更稳定的业务上下文 envelope。公共文档只要求业务上下文放入 `payload` 且 Host 透传，并未冻结通用样板 payload 形状；因此不阻断 024.07，但后续业务卡片迁移时不应照抄为唯一正式协议。

4. 资源桥测试存在覆盖空白。

   已覆盖查看态 `resolve/release/openResource` 和编辑态 `import/delete` 的基本路径，但建议验收时确认是否需要补充：
   - `resolveResourceUrl` reject 的错误态；
   - 缺少 `importResource` 时的用户错误态；
   - 替换已有资源时是否先/后删除旧资源的期望；
   - `importResource` 返回非法路径时 schema 是否阻断 `onChange`；
   - `importArchiveBundle/convertTiffToPng` 是否至少有类型透传或生成工程断言。

5. cleanup 验收应重点看真实执行结果。

   模板 runtime 已有同容器重复挂载时先调用上一次 cleanup 的机制，编辑态会恢复 `html/body/container` 样式；测试也覆盖了部分重复挂载。但集成测试第一段仍在 `onChange` 中重复 `mountBasecardView`，没有保存并最终调用 view/editor dispose。024.07 可将此作为建议补断言，不一定阻断最终验收。

6. `check-templates.cjs` 的门禁仍偏静态关键词。

   当前门禁能阻断旧 `chips dev`、TODO/FIXME、脚手架包名、硬编码视觉、Bridge/fs 直连、组件库缺失、资源桥缺失等。但未直接渲染模板后检查所有生成文件；这部分由 `template-engine.test.ts` 与 `run-generated-e2e.cjs` 补位。024.07 需要依赖完整验证命令，而不能只跑 `test:templates`。

7. 内部历史技术文档仍有旧口径。

   `rg` 显示 `Chips-Scaffold/chips-scaffold-basecard/技术文档/03-模板参数化与渲染引擎设计.md`、`04-命令行集成与工作流设计.md` 等内部文档仍含旧 `chips dev` 或旧 `card-standard` 模板说明。024.07 范围是最终验收，不建议扩大修内部历史文档；但若用户要求“脚手架所有文档最终一致”，应转给后续文档工单或在 024.06/024.07 工作日志中说明已知范围。
