## 当前 module 脚手架真实状态摘要

`Chips-Scaffold/chips-scaffold-module` 当前是一个独立脚手架包，提供 `module-standard` 模板、本体单元测试、模板检查和生成工程 e2e。`package.json` 的正式脚本为 `build/test/test:templates/test:e2e`。

模板结构：

- 模板目录包含 `.eslintrc.cjs.tpl`、`README.md.tpl`、`chips.config.mjs.tpl`、`manifest.yaml.tpl`、`package.json.tpl`、`tsconfig.json.tpl`、`vitest.config.mts.tpl`、`src/index.ts.tpl`、四个 schema 文件和 `tests/unit/module-definition.test.ts.tpl`。
- 默认不会生成 `需求文档/`、`技术文档/`、`技术手册/`、`开发计划/` 目录；`tests/core/template-engine.test.ts` 已断言这些目录不存在。
- 当前会把模板根 `template.json` 复制到生成工程。证据：`src/core/template-engine.ts` 第 206-219 行遍历 `templateFiles` 后直接写入所有文件，没有跳过 `template.json`；相邻 `chips-scaffold-boxlayout/src/core/template-engine.ts` 第 211-214 行已经显式跳过。`module` 测试也没有断言生成工程不含 `template.json`。

Manifest：

- `manifest.yaml.tpl` 已是 `type: module`、`entry: dist/index.mjs`、完整 `runtime.targets`，其中 `headless.supported: true`。
- 已声明 `module.apiVersion: 1`、`runtime: worker`、`activation: onDemand`、`module.provides` 和 `module.consumes: []`。
- 默认权限为 `permissions: []`；这适合纯函数样板，但不适合文件转换、HTML 渲染、颜色提取等形态，需要模板选项按形态生成 `file.read/file.write/platform.read/module.read/module.invoke/zip.manage` 等最小权限。

module provider / definition / export：

- `src/index.ts.tpl` 默认导出 `moduleDefinition = { providers: [...] }`，provider capability 来自 `{{ MODULE_CAPABILITY }}`，方法为 `run` 和 `runAsync`。
- Host `module-runtime.ts` 第 264-283 行支持 `providers` 数组导出，第 286-299 行还兼容 `capability + methods` 形态。因此当前模板能被 Host 加载。
- 但公共文档示例推荐 `defineModule(...)` 风格，当前 SDK 未见正式 `defineModule` 辅助导出；任务026不应凭空引入新 helper，除非先在 SDK/公共文档/Host 形成一致口径。保守做法是沿用 Host 已支持的 `providers` 对象，并在 README 说明这是当前正式导出形态。

Host context：

- Host 注入的 `ctx.host.invoke`、`ctx.module.invoke/job.get/job.cancel`、`ctx.job.reportProgress/isCancelled/signal` 已落地。
- `register-host-services.ts` 第 2560-2570 行禁止模块通过 `ctx.host.invoke("module.*")` 调用模块服务，要求使用 `ctx.module.*`。
- `register-host-services.ts` 第 3234-3264 行会按 manifest 中的 input/output schema 路径校验请求和输出。
- 当前模板只演示 `ctx.job.reportProgress`，没有演示 `ctx.host.invoke`、`ctx.module.invoke`、取消感知、错误码归一或 cleanup。

测试脚本：

- 生成工程 `package.json.tpl` 只有 `dev/build/test/lint/validate`，缺少 `typecheck/package/verify`。
- `scripts/check-templates.cjs` 只检查模板元数据和必要文件，不检查 `template.json` 泄露、未替换占位符、旧 `mountModule/runtime.tsx`、React/UI 依赖、TODO/FIXME、缺少质量脚本、`module.provides` schema 资产、manifest `runtime.targets` 等。
- `scripts/run-generated-e2e.cjs` 只直接调用 `renderTemplateToTarget()` 并检查 5 个文件存在，不安装依赖、不运行生成工程 `lint/build/test/validate/package/verify`，也不通过 Host 调用能力。
- `Chips-SDK/tests/run-cli-create-module-workspace-tests.cjs` 已提供更强的真实链路：第 89 行执行 `node cli/index.js create module`，第 126-131 行运行生成工程 `lint/build/test/validate/package`，第 186-224 行安装 `.cpk` 后通过 Host `module.listProviders`、`module.invoke(run)`、`module.invoke(runAsync)` 验证。任务026可把这条模式迁入脚手架本体 e2e。

已有模块插件工程：

- 五个真实模块均已使用 `type: module`、`entry: dist/index.mjs`、`runtime.targets`、`module.provides`。
- `Chips-ColorPicker` 提供 `image.color.pick/pick`，`mode: sync`，权限 `file.read`，内部使用 `sharp`，这属于既有依赖，不能作为新模板默认依赖随意扩散。
- `Chips-CardtoHTML-Plugin` 提供 `converter.card.to-html/convert`，`mode: job`，权限 `card.read/file.read/file.write/zip.manage`。
- `Chips-FileConversion-Plugin` 提供 `converter.file.convert/convert`，`mode: job`，权限 `file.read/file.write/module.read/module.invoke`，并在 `module.consumes` 声明三个原子转换能力。
- `Chips-HtmltoImage-Plugin` 与 `Chips-HtmltoPDF-Plugin` 通过 `ctx.host.invoke("platform.renderHtmlToImage")` / `ctx.host.invoke("platform.renderHtmlToPdf")` 调 Host 正式导出能力，且带打包级 e2e。

## 与公共文档/设计原稿的一致性

一致部分：

- 设计原稿明确模块插件是 Host 托管的无界面能力模块，不创建窗口，不以 DOM 挂载为正式边界；当前模板没有 React、`runtime.tsx`、`mountModule(container)` 或主题/i18n UI 入口。
- 公共契约要求 `module.provides/module.consumes`，当前模板和五个真实模块均已采用该结构。
- Manifest 规范要求 module 插件声明 `runtime.targets`，当前模板和真实模块均已声明。
- SDK CLI 已接入 `chipsdev create module`，并默认使用 `chips-scaffold-module` 的 `module-standard`；`chipsdev module invoke` 已是正式 Electron Host 联调入口。
- Host 已统一负责 provider 发现、schema 校验、sync/job 调度、事件和审计，模块 runtime 上下文与公共契约一致。

不一致或漂移证据：

- 公共手册要求 `chipsdev create` 生成工程默认只输出 README 与运行时、测试、契约等必要目录；模板元数据 `template.json` 不属于生成工程必要目录，但当前 module 渲染器会复制它。相邻 boxlayout 已跳过该文件。
- 任务024/025 已形成的 vNext 模式要求生成工程具备 `typecheck/package/verify` 和真实 `chipsdev create` e2e；当前 module 生成工程缺少这些脚本，本体 e2e 也弱于 SDK 已有真实测试。
- 任务026要求“常见模块形态拆成模板选项：纯函数转换、文件转换、图像处理、颜色提取、HTML 渲染”；当前 `CreateModuleProjectOptions` 只有 `moduleCapability`，`template.json` 也只有一个 `module-standard`，未表达模板形态。
- 公共文档要求模块开发至少覆盖单元、集成、脚手架、跨模块调用测试；当前模板只生成 `tests/unit/module-definition.test.ts`。
- 当前模板 README 仍说默认提供“单元测试、构建、校验与打包脚本”，但生成 `package.json.tpl` 没有 `package` 脚本，文案与真实模板不一致。
- 真实模块普遍已经替换 `run/runAsync` 为业务 `convert/pick`；脚手架仍只生成演示型 `run/runAsync`，不阻断启动，但不足以完成任务026验收。

## 建议任务026拆分与实施顺序

建议按 P0/P1/P2/P3 推进，先修会扩散的模板基线，再扩展能力形态。

1. P0：脚手架基线与质量门禁收口。
   - `renderTemplateToTarget()` 跳过 `template.json`，并在单元测试中断言生成工程不含 `template.json`、不含 `{{ ... }}` 占位符、不含 `module-standard/chips-scaffold-module` 这类模板身份泄露。
   - 生成工程补齐 `typecheck`、`package`、`verify` 脚本，`verify` 串联 `lint/typecheck/test/build/validate/package`。
   - 修 README 与脚本口径，让“打包脚本”“正式质量门禁”与 `package.json.tpl` 一致。
   - 强化 `check-templates.cjs`：检查禁止 `runtime.tsx/mountModule/React UI`，检查 `manifest.module.provides`、schema 文件存在、`runtime.targets` 完整、非 app 无 `ui.surface`、无 TODO/FIXME。

2. P1：真实 `chipsdev create module` e2e 内化。
   - 将 `scripts/run-generated-e2e.cjs` 改为临时生态根或复用 SDK 测试模式，真实执行 `chipsdev create module <targetDir>`。
   - 在生成工程内运行 `npm run verify`，或至少覆盖 `lint/typecheck/test/build/validate/package`。
   - 安装生成 `.cpk` 到临时 Host workspace，验证 `module.listProviders`、sync 方法、job 方法、schema 错误路径、取消/cleanup 基线。
   - 同步或复用 `Chips-SDK/tests/run-cli-create-module-workspace-tests.cjs` 断言，避免 SDK 和脚手架两套 e2e 漂移。

3. P2：模块形态选项与模板参数扩展。
   - 扩展 `CreateModuleProjectOptions`，加入稳定的 `moduleKind` 或 `capabilityPreset`，但不要写死某个现有业务模块的私有实现。
   - 建议至少形成五种预设：
     - `function`：纯函数同步能力，`permissions: []`，演示 schema 错误路径。
     - `file-conversion`：文件读写/zip/错误码/job/cleanup 样板。
     - `image-processing`：本地资源输入、`ctx.host.invoke("file.*" | "resource.*")`、输出文件样板，不默认引入新图像库。
     - `color-pick`：对齐 `image.color.pick/pick` 契约，可作为轻量 schema 和错误码模板；如涉及 `sharp` 只能作为可选业务参考，不能默认新依赖。
     - `html-render`：演示 `platform.renderHtmlToPdf` 或 `platform.renderHtmlToImage` 的 Host 正式导出调用、job 进度、取消和输出校验。
   - 每种预设都必须同步 manifest 权限、`module.provides/methods`、contracts、src、tests、README 示例命令。

4. P3：公共文档和既有模块对照。
   - 更新 `生态共用技术文档/插件开发/05-模块插件开发.md` 与 `命令行工具/02-Chips-Dev开发者命令行手册.md`，只沉淀稳定的生成工程结构、预设形态、验证命令、`chipsdev module invoke` 调用方式。
   - 若模板正式新增预设参数，也同步 SDK CLI `create module` 文档和测试。
   - 只把通用规范写入公共文档；五个业务模块的实现细节仍留在各自仓库 README/技术文档。

不能提前做的内容：

- 不要在任务026中迁移五个现有模块插件业务实现；它们对应任务046-050。
- 不要为了模板选项引入新第三方库，尤其不要把 `sharp`、浏览器运行时或 Electron 直接塞进默认模板。
- 不要新增 Host 模块类型或 `conversion.*` 服务域；文件转换系统仍是普通 module capability。
- 不要让模块模板生成窗口、页面、React、主题 CSS、i18n UI 词典或 `ui.surface`。
- 不要把 `ctx.services.*`、直接 `import` Host 内部实现、直接调用 Electron/BrowserWindow 写进模板。
- 不要把 `chipsdev start` 写成模块能力联调入口；依赖 Electron Host 的模块必须用 `chipsdev module invoke`。
