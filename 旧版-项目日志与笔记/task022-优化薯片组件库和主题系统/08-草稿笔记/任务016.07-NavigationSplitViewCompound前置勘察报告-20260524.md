## 1. 任务目标与设计约束

016.07 的正式目标不是增强现有 `ChipsSplitView`，而是把 `NavigationSplitView` 作为导航语义组件迁移为 Compound API，并明确它与布局原语 `ChipsSplitView` 的职责边界。

关键约束：

- `ChipsSplitView` 是布局原语，当前 scope 为 `split-view`，parts 为 `root / primary / secondary / detail / divider / status`，默认 `role="group"`。它适合主从或三栏视图容器，不承担导航状态、选中路径、Sidebar/Content/Detail 导航语义。
- `NavigationSplitView` 应是导航语义组件，建议使用独立 scope `navigation-split-view`，正式 Compound API 至少为 `Root / Sidebar / Content / Detail`。任务文档提到 `Toolbar`，建议作为可选子组件补入本轮决策，因为框架示例把 `ChipsToolbar` 放在 detail 内，Host L8 schema 也天然已有 `Toolbar` primitive。
- 当前仍未发布第一版，不应保留长期兼容包袱。如果新增 `navigation-split-view`，应一次性补 runtime、类型、contract、token、ThemePack、Host L8 schema、测试与公共文档，不做临时 alias 或只改类型。
- 组件库 L10 只负责结构、状态机、a11y 和主题 contract，不直接访问 Host 服务或命令运行时。
- Host L8 只校验声明树 slot schema，不渲染 DOM、不处理主题 token。
- ThemePack 只消费组件 contract 与 token，不发明协议；默认主题和暗色主题必须同步。
- 用户可见文案和 aria label fallback 应走 i18n adapter 或由调用方显式提供，不在组件内部写死中文/英文。

## 3. 建议冻结的正式 Compound API

建议新增并冻结：

```tsx
<ChipsNavigationSplitView.Root aria-label="Library navigation" defaultColumnVisibility="automatic">
  <ChipsNavigationSplitView.Sidebar aria-label="Collections">
    ...
  </ChipsNavigationSplitView.Sidebar>
  <ChipsNavigationSplitView.Content aria-label="Items">
    ...
  </ChipsNavigationSplitView.Content>
  <ChipsNavigationSplitView.Detail aria-label="Detail">
    <ChipsNavigationSplitView.Toolbar>
      <ChipsToolbar toolbarId="main" ariaLabel="Detail toolbar" />
    </ChipsNavigationSplitView.Toolbar>
    ...
  </ChipsNavigationSplitView.Detail>
</ChipsNavigationSplitView.Root>
```

导出形态建议沿用 016.01-016.04 已有 Compound 习惯：

- `ChipsNavigationSplitView` 等同 `ChipsNavigationSplitView.Root`
- `Object.assign(NavigationSplitViewRoot, { Root, Sidebar, Content, Detail, Toolbar })`
- displayName：
  - `ChipsNavigationSplitView`
  - `ChipsNavigationSplitView.Sidebar`
  - `ChipsNavigationSplitView.Content`
  - `ChipsNavigationSplitView.Detail`
  - `ChipsNavigationSplitView.Toolbar`

最小静态子组件：

- `Root`：导航分栏容器，管理列可见性、响应式状态、禁用/加载/错误状态和上下文。
- `Sidebar`：导航源栏，承载列表/树/导航链接等导航项。
- `Content`：中间内容栏。两栏模式下可选；三栏模式下用于列表/二级内容。
- `Detail`：详情栏，承载最终内容区域，建议必填。

建议本轮同时纳入的静态子组件：

- `Toolbar`：可选工具栏槽位，主要放在 `Detail` 或 `Content` 内部。任务文档验收提到 Host schema 与 toolbar，框架示例也把 `ChipsToolbar` 放在 detail 内；如果不纳入静态 API，至少要把 `toolbar` 作为公开 part 和 L8 slot。

不建议本轮新增的子组件：

- `NavigationLink`：任务016.07 没要求，且属于导航系统更大能力，应该留给任务11或后续导航栈工单。
- `Column` / `Primary` / `Secondary`：这些会把导航语义退回 `split-view` 布局原语口径，不利于边界清晰。
- `Divider`：建议 divider 是内部公开 part，而非可组合子组件。若未来需要 resizable divider，应优先评估与 `ChipsSplitPane` 的职责边界。
- `SidebarToggle` / `CollapseButton`：当前任务不要求；如果为了响应式必须提供折叠入口，可通过 Root props + 外部 Command/Toolbar 完成，不建议在 016.07 扩大为导航系统任务。

建议 props 口径：

| 子组件 | 建议 props | 说明 |
|---|---|---|
| `Root` | `children`, `columnVisibility`, `defaultColumnVisibility`, `onColumnVisibilityChange`, `variant`, `collapseBreakpoint`, `disabled`, `loading`, `error`, `ariaLabel`, `ariaLabelledBy`, `onStateChange` | 避免 `showSidebar/showDetail/withToolbar` 等 boolean 模式。`columnVisibility` 用枚举承载状态。 |
| `Sidebar` | `children`, `ariaLabel`, `ariaLabelledBy`, `collapsible`, `defaultCollapsed`, `collapsed`, `onCollapsedChange` | `collapsible` 是基础能力布尔值可接受，但不应引入业务模式布尔。若主代理想更严格，可把折叠状态统一提升到 Root。 |
| `Content` | `children`, `ariaLabel`, `ariaLabelledBy` | 中间栏可选。 |
| `Detail` | `children`, `ariaLabel`, `ariaLabelledBy` | 详情栏建议必填。 |
| `Toolbar` | `children`, `ariaLabel`, `ariaLabelledBy` | wrapper 输出 `role="toolbar"` 或承载内部 `ChipsToolbar`；需避免 nested toolbar role 冲突。 |

建议枚举：

- `variant`: `two-column | three-column | sidebar-detail`
- `columnVisibility`: `automatic | all | detailOnly | sidebarOnly | sidebarContent | contentDetail`

如果担心本轮过大，可先只冻结 `variant`，响应式状态通过 `data-layout` / CSS 自动表达；但任务文档要求响应式行为，建议至少留 `data-collapsed` / `data-column-visibility` 的可测口径。

与 `ChipsSplitView` 的职责边界建议写入公共文档：

- `ChipsSplitView`：布局原语，只表达泛用分栏容器，parts 使用 `primary/secondary/detail`，无导航语义。
- `ChipsNavigationSplitView`：导航容器，parts 使用 `sidebar/content/detail/toolbar/divider`，可包含导航 landmark、导航项列表、详情区域、响应式列可见性，不承担具体路由或 Host command 执行。

## 5. 建议 ARIA / role / keyboard / responsive 行为

### 5.1 Root

建议 root 使用：

- DOM：`div`
- `role="group"` 或 `role="region"`
- 必须通过 `aria-label` 或 `aria-labelledby` 提供名称
- `aria-disabled="true"`：disabled/loading 时输出
- `aria-busy="true"`：loading 时输出

role 决策建议：

- 如果 Root 只是一个复合导航容器，默认 `role="group"` 与 `ChipsSplitView` 保持一致即可。
- 如果 Root 在页面中承担 landmark，允许调用方传 `role="region"`，但必须提供可访问名称。
- 不建议 Root 默认使用 `role="navigation"`，因为 Sidebar 本身更适合作为 navigation landmark；一个页面中多个 navigation landmark 需要各自 label，Root 再加 navigation 容易语义重复。

### 5.2 Sidebar

建议 Sidebar 使用：

- DOM：`nav` 或 `aside`
- 默认 `role="navigation"`；如果 `as="aside"`，仍可显式 `role="navigation"`
- 必须通过 `aria-label` 或 `aria-labelledby` 提供名称
- 承载导航列表、Tree、List、NavigationLink 等子内容

如果 Sidebar 内有 `ChipsTree` 或 `ChipsList`，焦点与键盘由内部组件负责；NavigationSplitView 不应吞掉方向键。

### 5.3 Content

建议 Content 使用：

- DOM：`section`
- 默认 `role="region"`
- 建议提供 `aria-label` 或 `aria-labelledby`，但如果仅作为中间列表容器且内部已有独立可访问名称，可允许不强制
- 用于二级列表、内容集合、搜索结果等

### 5.4 Detail

建议 Detail 使用：

- DOM：`main` 或 `section`
- 默认 `role="main"` 的风险：同一页面只能有一个 main，组件内部默认 main 可能与 App Shell 冲突。
- 更稳妥默认：`role="region"`，由调用方在顶层页面决定是否传 `role="main"`。
- 建议 Detail 必须有可访问名称，尤其在三栏布局中。

### 5.5 Toolbar

如果提供 `ChipsNavigationSplitView.Toolbar`：

- 默认 `div role="toolbar"`
- 必须有 `aria-label` 或 `aria-labelledby`
- 如果 children 已经是 `ChipsToolbar`，需要避免双层 `role="toolbar"`。建议 wrapper 默认只输出 part，不强制 role；或者约定 `Toolbar` 子组件本身就是 toolbar role，内部不要再嵌套 `ChipsToolbar`。

更推荐做法：

- `NavigationSplitView.Toolbar` 自身输出 `role="toolbar"`，适合直接放按钮/命令。
- 如果使用 `ChipsToolbar`，则不要包 `NavigationSplitView.Toolbar`，而是把 `ChipsToolbar` 放在 `Detail` 内；主题可以靠 `toolbar` slot schema 而非 DOM wrapper 表达。

需要主代理决策。

### 5.6 Divider

当前 `ChipsSplitView` divider 是装饰结构 `aria-hidden="true"`。016.07 建议延续装饰 divider：

- `data-part="divider"`
- `aria-hidden="true"`
- 不作为可拖拽 splitter

不要在 016.07 里顺手实现 resize splitter；若要 resizable，应评估是否复用 `ChipsSplitPane` 或另立后续工单。

### 5.7 键盘行为

建议 016.07 最小键盘承诺：

- Tab 顺序按 DOM 顺序进入 Sidebar、Content、Detail、Toolbar 内部可聚焦元素。
- NavigationSplitView Root 不抢占方向键；方向键由内部 Tree/List/DataGrid/Menu 等组件处理。
- 如果支持 Sidebar 折叠：
  - 折叠/展开按钮必须是真实 `button` 或外部 `Command`。
  - Enter/Space 触发折叠/展开。
  - 折叠后焦点不得丢失；如果当前焦点位于被隐藏栏，需转移到 Detail 或触发按钮。
- 如果支持列切换快捷键，应通过 Host command/shortcut 链路，不在组件内部硬编码。

不建议在本轮实现复杂焦点域、导航链接 selection 或路由状态；这些属于 NavigationStack/NavigationLink 或 App routing 后续能力。

### 5.8 响应式行为

建议 CSS/DOM 基线：

- expanded regular：三栏或两栏 grid，显示 sidebar/content/detail。
- compact：可收敛为 `detailOnly` 或 overlay/sidebar-hidden，但不要在组件 runtime 用窗口宽度硬编码判断。
- 组件 runtime 可输出 `data-column-visibility`，ThemePack CSS 基于该属性和容器查询/媒体查询处理布局。
- 主题 CSS 尽量使用 `chips.layout.breakpoint.*`、`chips.layout.size.navigation-primary-min`、`chips.layout.size.split-secondary-min`、`chips.layout.divider.thickness`。

当前 ThemePack CSS 中 `split-view` 三栏已经引用 `navigation-primary-min`，可作为新组件 CSS 的基础，但不要直接把 `split-view` selector 改成导航语义。

## 7. Host L8 声明式 UI slot schema 同步点

建议新增：

```ts
NavigationSplitView: {
  sidebar: {
    type: ['Navigation', 'List', 'Section'],
    required: true,
    multiple: false,
    part: 'sidebar',
    role: 'navigation'
  },
  content: {
    type: ['View', 'Stack', 'List', 'Section', 'Table'],
    required: false,
    multiple: false,
    part: 'content',
    role: 'region'
  },
  detail: {
    type: ['View', 'Stack', 'Section', 'ScrollView'],
    required: true,
    multiple: false,
    part: 'detail',
    role: 'region'
  },
  toolbar: {
    type: 'Toolbar',
    required: false,
    multiple: false,
    part: 'toolbar',
    role: 'toolbar'
  }
}
```

rootType 建议：

- `Navigation`：最贴近导航语义，也符合 Host 现有 primitive。

建议 Host 测试：

- `StandardCompoundSlotSchemas.NavigationSplitView` 合法结构：
  - `sidebar: Navigation(...)`
  - `content: List(...)` 或 `Section(...)`
  - `detail: Section(...)`
  - `toolbar: Toolbar(...)`
  - validate 返回 `[]`
- 缺少 `sidebar` 产生 `DECLARATIVE_UI_SLOT_REQUIRED`
- 缺少 `detail` 产生 `DECLARATIVE_UI_SLOT_REQUIRED`
- `sidebar: View(...)` 如果 schema 不允许 View，应产生 `DECLARATIVE_UI_SLOT_TYPE_MISMATCH`
- `toolbar: View(...)` 产生 `DECLARATIVE_UI_SLOT_TYPE_MISMATCH`
- `primary/secondary` 或 `divider` 作为 slots 传入，产生 `DECLARATIVE_UI_SLOT_UNDEFINED`
- `content` 多个节点产生 `DECLARATIVE_UI_SLOT_MULTIPLE_FORBIDDEN`
- `root.props` 里 `showSidebar / showDetail / withToolbar / isCompact` 被 `guardAgainstBooleanModeProps` 拦截；如需要允许 `disabled/loading`，这些不匹配 `is|has|show|with` 前缀，不会误伤

需要主代理决策：

- L8 schema 是否允许 `Content` 缺省。如果目标覆盖两栏 sidebar-detail，`content` 应为 optional；如果要强制三栏，则 required。结合任务文档“两栏/三栏结构”验收，建议 `content` optional，测试覆盖有 content 和无 content 两种合法形态。
- `Toolbar` 是否进入 NavigationSplitView schema。建议进入 optional slot，理由是任务背景与示例都将工具栏视为导航分栏常见组成。

## 9. 风险点与需要主代理决策的问题

### 9.1 关键风险

1. 误把 `ChipsSplitView` 直接改名或扩展成导航组件。这样会污染布局原语 contract，导致 `primary/secondary/detail` 与 `sidebar/content/detail` 长期混用。
2. 只新增 runtime/types，不新增 contract/token/ThemePack。主题 apply/contract guard 后续会因 required token 缺失阻断。
3. 只补 ThemePack CSS，不补 `theme-interface.contract.json` 和 `theme-min-functional-set.json`。主题包本地测试和 Host `theme.contract.get` 口径会漂移。
4. Toolbar 子组件和 `ChipsToolbar` 嵌套 role 冲突。需要先决定 `NavigationSplitView.Toolbar` 是否是真 toolbar，还是只作为 slot wrapper。
5. 响应式行为如果写进 runtime 的窗口宽度判断，会绕开 layout token/cpx 和页面自治原则。建议通过 props/data 属性 + CSS/container queries 处理。
6. Sidebar/Detail 默认 role 如果过强，可能和 App Shell landmark 冲突。默认 `group/region/navigation` 要可覆盖。
7. L8 slot schema 当前不能表达“两栏或三栏”的联合约束，只能用 `content optional` 近似。不要为 016.07 临时扩展复杂 schema 语法，除非主代理明确要做。
8. 当前 016.05/016.06 可能仍在迁移中；不要在 016.07 中顺手修 Tree/CommandPalette 未收口口径。

### 9.2 需要决策

- 是否正式新增独立 scope `navigation-split-view`。建议：是。
- `Toolbar` 是否作为正式静态子组件。建议：是，但需避免与 `ChipsToolbar` role 嵌套；也可只作为 L8 optional slot。
- Root 默认 role 用 `group` 还是 `region`。建议：`group`，允许调用方传 `role="region"`。
- Detail 默认 role 用 `region` 还是 `main`。建议：`region`，避免页面多 main。
- Sidebar DOM 用 `nav` 还是 `aside role="navigation"`。建议：默认 `nav`。
- Content 是否必填。建议：可选，以支持两栏 sidebar-detail；三栏时显式传入。
- 是否在本轮实现 collapsible/responsive state。建议：至少输出 `data-column-visibility` 和 `variant`，不要实现复杂动画/overlay。
- 是否把 NavigationSplitView 放进 `STAGE7_WORKBENCH_COMPONENTS`、新建 `STAGE7_NAVIGATION_COMPONENTS`，还是归入 layout primitive。建议：新建或使用导航分组；不要归入 `layout-primitives.js`，以免继续模糊边界。

## 10. 候选工单

以下不是本轮正式工单；仅供主代理判断是否需要登记。

1. 生态公共文档已出现 `ChipsNavigationSplitView` 愿景和任务要求，但正式组件库文档、L8 schema 文档、token 文档尚无对应 API。当前不阻断 016.07，因为本任务本身就是补齐该缺口；正式执行时同步文档即可。
2. Host L8 `StandardCompoundSlotSchemas` 暂不能表达“slot 联合必填”或“每个父 slot 内子 slot 数量限制”。NavigationSplitView 可用 `sidebar/detail required + content optional` 绕开，不阻断；如果后续 Tree/CommandPalette 需要更复杂约束，可能要单独工单增强 slot schema。
3. `ChipsSplitView` 当前 CSS 的三栏 variant 已引用 `navigation-primary-min`，名称上容易让后续开发误会它就是导航分栏。建议在公共文档或代码注释中说明这是布局尺寸 token，不代表 `split-view` 拥有导航语义；不阻断 016.07。

## 14. 总结结论

当前代码没有 `ChipsNavigationSplitView`。唯一可用的是布局原语 `ChipsSplitView`，其 scope、parts、contract、ThemePack CSS 和公共文档都稳定指向 `split-view`。016.07 应新增独立 `navigation-split-view` Compound 组件，而不是改造 `split-view`。

建议正式 API 冻结为：

- `ChipsNavigationSplitView.Root`
- `ChipsNavigationSplitView.Sidebar`
- `ChipsNavigationSplitView.Content`
- `ChipsNavigationSplitView.Detail`
- `ChipsNavigationSplitView.Toolbar`（建议纳入可选）

建议正式公开 parts：

- `root / sidebar / content / detail / toolbar / divider / status`

建议 Host L8 schema：

- rootType: `Navigation`
- slots: `sidebar` 必填、`detail` 必填、`content` 可选、`toolbar` 可选
- 旧 `primary/secondary/divider` 不作为 L8 slot，传入应报 `DECLARATIVE_UI_SLOT_UNDEFINED`

016.07 的最大风险是边界混淆。只要坚持“`split-view` 是布局原语，`navigation-split-view` 是导航语义组件”，后续 runtime、contract、ThemePack、Host schema 和公共文档都能顺序收口。
