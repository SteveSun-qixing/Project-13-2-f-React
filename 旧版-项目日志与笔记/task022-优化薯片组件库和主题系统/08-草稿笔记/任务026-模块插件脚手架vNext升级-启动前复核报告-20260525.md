## 2. 与 023/024/025 vNext 模式的差距清单

| 优先级 | 差距 | 证据 | 影响 |
|---|---|---|---|
| P0 | 生成工程 e2e  هنوز只做文件存在性检查，没有复刻 023/024/025 那种真实 `verify`、`package`、Host 安装与 `module.invoke` 闭环 | `Chips-Scaffold/chips-scaffold-module/scripts/run-generated-e2e.cjs` 只检查关键文件；`Chips-Scaffold/chips-scaffold-module/scripts/check-templates.cjs` 也只是文件完整性检查；对照 `Chips-SDK/tests/run-cli-create-module-workspace-tests.cjs` 才有真实安装与调用链 | 不能证明新生成的模块工程真能被 Host 安装、启用并调用 |
| P0 | 模板测试没有覆盖错误路径、清理路径和 Host mock 调用链，和任务026要求的“错误码 + 权限 + 质量门禁”还差一层 | `templates/module-standard/tests/unit/module-definition.test.ts.tpl` 只有 `run` / `runAsync` 的正向样例；没有 `ctx.host.invoke`、`ctx.module.invoke`、取消、失败、清理、错误码断言 | 026 的错误模型和治理边界很容易只停留在 README 上 |
| P1 | 当前只有一个 `module-standard` 模板，没有把常见模块形态拆成模板选项 | `templates/module-standard/**`、`template.json`、需求/技术文档都还是单模板单示例 | 真实模块家族太多，后续会逼出业务仓自己改模板 |
| P1 | 生成工程没有形成 023/024/025 那种 vNext 质量脚本心智，缺少 `verify` / 门禁级联语义 | `package.json.tpl` 只有 `build/test/lint/validate`，README 只写 `chipsdev package`，没有一个统一的工程级 `verify` 叙述 | 生成工程质量闭环不够硬，容易退回成“能跑就行” |

| P2 | 模板检查还没有像 023/024/025 那样做旧身份、旧文本、占位符和生成产物洁净度扫描 | `scripts/check-templates.cjs` 只做最小文件存在校验 | 旧口径有机会悄悄混进新模板 |
