## 2. 当前状态摘要

`Chips-CardViewer` 不是从零开始。当前已经具备这些正式链路基础：

- `manifest.yaml` 已声明 `type: app`、`file-handler:.card`、`file-handler:.box`、`ui.surface`、`ui.launcher`。
- `CardWindow` 当前通过 `client.document.window.render({ filePath, locale, mode: "view" })` 打开 `.card/.box`。
- SDK 源码确认 `client.document.window.render(...)` 是正式统一文档窗口入口：`.card` 内部分发到 `client.card.compositeWindow.render(...)`，`.box` 内部分发到 `client.box.documentWindow.render(...)`。
- `client.box.documentWindow.render(...)` 源码确认箱子链路由 SDK 串接 Host `box.inspect -> box.readLayoutDescriptor -> box.normalizeLayoutConfig -> box.getLayoutInitialQuery -> box.openView -> box.renderLayoutFrame`，并在 `dispose()` 时释放 render session 与关闭 view session。
- `CardWindow` 当前通过 `client.document.window.onReady/onError/onResourceOpen(...)` 消费统一文档窗口事件，并通过 `client.resource.open(...)` 打开卡片内部资源。
- 主题初始读取、`theme.changed` 订阅、`language.changed` 订阅和本地 i18n bundle 已有基础实现。

主要差距不在底层渲染链路，而在应用框架基线：

- 当前 `src/App.tsx` 同时承担启动上下文、主题、语言、目标文档、打开文件、场景分发等职责，尚未迁入 vNext `AppRoot/AppProviders/AppRuntimeProvider/AppShell/Scene` 分层。
- 当前使用私有 `useChipsClient()` 在多个组件内创建 client，没有统一 `ChipsEnvironmentProvider` 注入的单例 SDK client。
- 当前使用私有 `useChipsBridge(): any` 直接读 `window.chips`，应收口到 SDK client、`ChipsEnvironmentProvider` 与必要的正式 Bridge 事件订阅。
- 空态/错误态/加载态仍有大量 inline style 和私有结构，未完全使用组件库 layout primitives、`ChipsErrorState`、`ChipsLoadingBoundary`、`ChipsEmptyState` 等正式组件。
- 当前没有 commands/menu/toolbar/diagnostics 结构，manifest 也未声明 `command.*` 权限。
- README 仍写“统一卡片显示接口：`client.card.compositeWindow.render({ cardFile, mode: 'view' })`”，但当前真实主路径是 `client.document.window.render({ filePath, locale, mode: "view" })`；任务029完成后需要同步更新项目文档。

## 4. 关键迁移路径

建议主路径：

1. 保留正式显示核心，不重写卡片或箱子渲染。
   - `.card/.box` 文件统一继续走 `client.document.window.render(...)`。
   - 明确 `.card` 内部分发到 Host `card.render` / SDK `card.compositeWindow.render`。
   - 明确 `.box` 内部分发到 Host box runtime / SDK `box.documentWindow.render`。
   - 不直接 import 基础卡片插件、布局插件源码，不扫描 `.card/.box` 内部资源。

2. 先迁应用运行时骨架，再迁页面 UI。
   - 新建 `src/runtime/chips-client.ts`，导出单例 `chipsClient`。
   - 新建 `src/runtime/launch-context.ts`，封装 `platform.getLaunchContext()` 与 fallback surface。
   - 新建 `src/app/AppRoot.tsx`，由 `main.tsx` 渲染 `AppRoot`。
   - 新建 `AppProviders`，用 `ChipsEnvironmentProvider` 注入 client、launchContext、surface、theme、locale、permissions、diagnostics。
   - 新建 `AppRuntimeProvider`，把当前 target、documentType、locale、theme、权限、诊断、打开动作收敛成可测试上下文。

3. 将当前 `App.tsx` 的行为迁到 Scene。
   - 空启动 scene：保留拖拽与打开文件按钮，不新增营销页或说明页。
   - document file scene：保留当前 `CardWindow` 主流程。
   - hosted document scene：保留 `webDocumentUrl` 启动路径与 `HostedDocumentWindow` surface resize。
   - 文件选择仍用 `client.platform.openFile({ mode: "file", allowMultiple: false, mustExist: true })`；建议增加 `.card/.box` filter，但不要破坏现有可选路径。

4. UI 替换时保持视觉和交互语义。
   - 当前测试明确首屏不应出现额外“卡片查看器”品牌标题；迁移时不要把 app-standard 的三栏样板照搬成产品重设计。
   - 工具栏、路径栏、诊断面板可以作为查看器壳层能力接入，但默认首屏和文档沉浸式查看逻辑应保持。
   - 加载、错误、空态优先使用组件库正式组件；视觉值走主题 token，不继续扩大 inline style。

5. 主题与语言链路统一化。
   - 主题由 `ChipsEnvironmentProvider/useChipsTheme` 和 `ChipsThemeProvider` 驱动。
   - i18n 文案用 `useChipsI18nText({ bundles, fallbackLocale, defaultLocale })`，不在 React render 中等待异步翻译。
   - `language.changed` 后只重渲染，不重启应用。
   - 内容 iframe 的重新渲染继续依赖 `themeRuntime.cacheKey` 或 SDK/组件库正式主题缓存键。

6. 安全与生命周期收口。
   - `CardWindow` 当前使用 SDK 创建的 iframe，sandbox 来自 SDK：卡片与箱子当前均为 `allow-scripts allow-forms`。
   - `HostedDocumentWindow` 当前手写 iframe sandbox 为 `allow-scripts allow-same-origin allow-popups`，与复合卡片窗口公共标准“不得加入 `allow-same-origin`”存在冲突风险；后续应确认 `webDocumentUrl` 是何类文档。如果它承载正式复合文档，应移除 `allow-same-origin` 或改走 SDK 受控入口。
   - `HostedDocumentWindow` 当前直接监听 `window.message` 并只校验 `event.source`，未复用 SDK origin 过滤；若保留该路径，应补齐 origin/null-origin 策略或登记协议缺口。

## 7. 风险与阻塞点

1. `HostedDocumentWindow` 的 sandbox 与公共标准存在潜在冲突。
   - 证据：当前 `HostedDocumentWindow` 使用 `sandbox="allow-scripts allow-same-origin allow-popups"`。
   - 公共标准要求正式复合文档和基础卡片 iframe 不加入 `allow-same-origin`。
   - 建议：若 `webDocumentUrl` 是正式复合/箱子文档，应在任务029收口；若是普通 web route surface 文档，则需在项目内部文档明确其边界。

2. `HostedDocumentWindow` 手写消息监听未复用 SDK origin 过滤。
   - 证据：SDK `document.window` / `card.compositeWindow` / `box.documentWindow` 事件订阅都有 `event.source` 与 origin/null-origin 过滤；当前 `HostedDocumentWindow` 只检查 `event.source`。
   - 建议：优先改用 SDK 事件接口；若 SDK 缺少 hosted-document resize/resource 入口，再判断是否需要登记工单。

3. 组件库 `CompositeCardWindow` 当前默认 sandbox 与公共标准有漂移迹象。
   - 证据：`Chips-ComponentLibrary/packages/card-runtime/src/composite-card-window.js` 默认 `sandbox = "allow-scripts allow-same-origin"`。
   - 公共标准要求复合顶层 iframe 当前为 `allow-scripts allow-forms` 且不得加入 `allow-same-origin`。
   - 影响：如果任务029直接使用组件库 `CompositeCardWindow` 包装 SDK iframe，需要显式传入正式 sandbox，或先推动组件库默认值收口。
   - 建议：任务029里不要悄悄依赖该默认值；是否登记工单由主代理在实现前确认。

4. `client.document.window.onResourceOpen(...)` 只订阅卡片复合资源事件。
   - 证据：`Chips-SDK/src/api/document.ts` 中 `onResourceOpen` 直接返回 `cardApi.compositeWindow.onResourceOpen(frame, handler)`。
   - 箱子布局资源打开目前看起来通过 SDK 的 box runtime bridge 处理 `box.openEntry/resolveEntryResource/readBoxAsset`，不是同一个 `chips.composite:resource-open`。
   - 建议：不要在 CardViewer 内自造箱子资源打开协议；若需要统一箱子资源打开事件，先补 SDK/公共契约并登记工单。

5. README 与当前实现不同步。
   - 证据：README 仍强调 `client.card.compositeWindow.render({ cardFile, mode: 'view' })`，当前 `CardWindow` 实际用 `client.document.window.render({ filePath, locale, mode: "view" })`。
   - 建议：任务029完成后更新 README；本轮只在报告中标明，不改文档。

6. Commands 接入会改变权限面。
   - 当前 manifest 没有 `command.read/write/invoke`。
   - Host `command.register` 代码存在 `command.manage` 权限检查，同时 route manifest 中暴露 `command.register`；需要主代理复核当前应用模板到底要求 `command.write` 还是 `command.manage`。
   - 建议：以当前 Host/SDK 真实权限校验为准，必要时先登记权限文档漂移工单，不要只照抄模板权限。

7. Web target 边界不清。
   - manifest 声明 `web.supported: true`，但当前主流程依赖本地文件路径与 `platform.dialogOpenFile`。
   - 现有 `webDocumentUrl` 可能是 web route 的特殊恢复路径，但公共文档中未看到明确独立契约。
   - 建议：029.01 先确认 web target 是正式支持还是仅托管文档 surface；不清楚时不要扩大 web 功能承诺。
