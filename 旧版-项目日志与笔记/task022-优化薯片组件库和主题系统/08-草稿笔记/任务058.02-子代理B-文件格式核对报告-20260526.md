## 发现的问题

### 1. `03-CPK打包格式规范.md` 的包结构示例与 `chipsdev package` 真实产物不一致

具体口径：

- 文档示例把 `.cpk` 内部写成 `app/`、`card/`、`layout/`、`module/`、`theme/` 这类类型包裹目录；
- 主题插件示例中还出现了两个 `manifest.yaml`；
- 当前 `chipsdev package` 真实产物不是这类 wrapper 结构，而是包根直接存在 `manifest.yaml`，构建产物和 manifest 声明资源按原相对路径进入包内。

建议：

- 将 CPK 标准结构统一改为：

```text
<plugin>.cpk
├── manifest.yaml
├── dist/
└── <manifest 声明的正式资源目录或文件>
```

- 五类插件差异应放到 manifest 字段、运行目标、入口和导出契约说明里，不应通过 `.cpk` 顶层 wrapper 目录表达。

### 2. `03-CPK打包格式规范.md` 将签名和热插拔流水线写成已落地事实，需改成当前实现边界

具体口径：

- “CPK支持数字签名”“系统使用公钥验证签名有效性”“下载新版本 CPK、验证签名、停止旧版本、加载新版本”等内容像是在描述已完成发布流水线；
- 当前 Host 实现里，本地开发和本地 `.cpk` 安装是 `source=local` 主链路；非 local 来源主要校验 `signature` 字段是否存在，未见该文档所述完整公钥验证、远端下载、热更新发布流水线；
- `04-打包与安装路径手册.md` 已经把该边界写得更准确：本地开发打包链路不要求先生成签名，未来远端来源校验需要单独补充。

建议：

- CPK 规范中保留“签名/来源治理属于发布安全能力”的方向；
- 明确当前第一版本地开发和本地安装主链路不以签名、公证或远端更新为前置条件；
- 不把尚未落地的远端热插拔流程写成当前正式能力。

### 3. `03-文件格式协议.md` 对 `.cpk` Store 约束的错误描述需要修正

具体口径：

- 文档写“Host 当前安装器按 Store 模式解析本地文件头；若插件包使用 Deflate 等压缩方法，安装阶段会报 `PLUGIN_PACKAGE_INVALID`”。
- 当前 `StoreZipService.readEntryFromBuffer` 能读取 compressionMethod `0` 和 `8`；`PluginRuntime.install(.cpk)` 通过 `StoreZipService.extract` 解包，不会仅因为 Deflate 直接报错。
- 但 `chipsdev package` 的正式产物和兼容测试要求所有 `.cpk` 条目使用 Store，且公共规范应要求 Store。

建议：

- 改为：“正式 `.cpk` 产物必须由 `chipsdev package` 生成并使用 ZIP Store；Host 解包器目前可读取部分 Deflate ZIP，但这不是 `.cpk` 正式生产口径，也不作为第三方包兼容承诺。”

### 4. `.box` 双链路措辞需更精确：目录态是打包输入，正式消费入口是 `.box` 文件

具体口径：

- 任务要求核对 `.card/.box/.cpk` 是否均为 ZIP Store / 目录态双链路。
- `.card` 的 `readMetadata` 与 `validate` 都直接支持目录态和 ZIP 态；`.box` 的 `pack` 支持目录态输入，但 `inspect/validate/readMetadata/renderCover/openView` 当前读取的是 `.box` 文件。
- `02-箱子文件格式规范.md` 已正确强调正式形态是单个 `.box` 文件，但 `04-打包与安装路径手册.md` 可进一步说明目录态箱子只是编辑/打包工作目录，不是 Host 正式消费形态。

建议：

- `.card`：可以写“目录态工作目录与 `.card` 打包态均被 Host 服务部分读取能力支持”；
- `.box`：写“目录态用于编辑器保存与 `box.pack` 输入；正式分发和运行时消费是单个 `.box` 文件”；
- 避免把 `.box` 目录态描述成与 `.card` 完全对等的正式消费形态。

### 5. `01-卡片文件格式规范.md` 有旧资源模型残留，需按第一版资源链路收口

具体口径：

- 附录 B 仍写“支持相对路径、绝对路径、URL”；
- 文档中仍保留“半空壳卡片”等历史资源模式描述；
- 当前正式约束已在同文档前文和设计原稿中强调：内部资源路径以卡片根目录相对路径记录，不得把运行时 `blob:`、`data:`、系统绝对路径写回正式内容配置；外部 URL 只应由具体基础卡片插件契约声明。

建议：

- 把检查清单改成“内部资源必须是卡片根目录相对路径；外部 URL 只在对应基础卡片插件显式支持时允许；系统绝对路径、`file://`、`blob:`、运行时临时 URL 不得作为内部资源写回”；
- 若保留空壳/半空壳等历史说明，应明确它们不是第一版默认保存链路，或移到历史背景/非正式设计区。

### 6. `02-箱子文件格式规范.md` 文件级校验漏列 `.box/cover.html`

具体口径：

- 文档第 4.2 节已把 `.box/cover.html` 列为必需文件；
- Host `BoxService.validateZipEntries` 和 `loadDirectoryPackage` 都要求 `.box/cover.html`；
- 但第 11.1 文件级校验只列了 `.box/metadata.yaml`、`.box/structure.yaml`、`.box/content.yaml`。

建议：

- 在第 11.1 增加 `.box/cover.html` 必须存在；
- 与 `BoxService` 的 required path 列表保持一致。

### 7. `09-卡片信息与打开契约.md` 响应示例多包了一层 `info`

具体口径：

- 文档示例为 `CardReadInfoResponse { info: { cardFile, info: {...} } }`；
- Host route `card.readInfo` 返回 `{ info }`，其中 `info` 是 `CardInfoService.readInfo(...)` 的结果；
- SDK `CardReadInfoResult` 是 `{ cardFile, info: CardInfoPayload }`，`client.card.readInfo()` 返回该对象。

建议：

- 文档保留路由响应层时应明确：

```ts
interface CardReadInfoRouteResponse {
  info: CardReadInfoResult;
}

interface CardReadInfoResult {
  cardFile: string;
  info: CardInfoPayload;
}
```

- 避免读者误以为业务 payload 本身需要手写双层 `info.info`。

## 证据摘要

### Host route 与服务实现

- `register-host-services.ts` 注册了 `card.pack/unpack/readMetadata/readInfo/parse/render/renderCover/renderEditor/validate/open`、`box.pack/unpack/inspect/validate/readMetadata/renderCover/openView/listEntries/readEntryDetail/renderEntryCover/renderLayoutFrame/renderLayoutEditor/openEntry/readBoxAsset`、`zip.compress/extract/list`。
- `CardPacker.pack()` 从目录态卡片工作目录创建 `.card`，最终调用 `StoreZipService.compress()`；`CardPacker.readMetadata()` 同时支持目录态和 `.card` 文件。
- `CardService.validate()` 对目录态和 `.card` 文件都检查 `.card/metadata.yaml`、`.card/structure.yaml`、`.card/cover.html`；`renderCover()` 以 `.card/cover.html` 生成 `coverUrl`。
- `BoxService.pack()` 先 `loadDirectoryPackage(boxDir)` 再压缩；`loadDirectoryPackage()` 要求 `.box/metadata.yaml`、`.box/structure.yaml`、`.box/content.yaml`、`.box/cover.html`。
- `BoxService.validate()/inspect/readMetadata/renderCover/openView()` 通过 `loadArchivePackage(boxFile)` 消费 `.box` 文件；`validateZipEntries()` 要求 Store，并拒绝 `.card/.box` 嵌入。
- `BoxService.normalizeEntries()` 拒绝旧 `cards` 字段和 `internal/external/location/path` 旧位置字段；正式条目基于 `entry_id + url`。
- `StoreZipService.compress()` 写入 `compressionMethod=0`、`compressedSize=size`；`readEntryFromBuffer()` 当前可读取 Store 与 Deflate，但 Store 是正式生产口径。

### SDK 与 CLI

- `Chips-SDK/src/api/card.ts` 暴露 `pack/unpack/readMetadata/readInfo/parse/validate/open/render/coverFrame/compositeWindow/editorPanel`。
- `Chips-SDK/src/api/box.ts` 暴露 `pack/unpack/inspect/validate/readMetadata/renderCover/openView/listEntries/readEntryDetail/renderEntryCover/openEntry/resolveEntryResource/readBoxAsset/documentWindow/editorPanel`。
- `Chips-SDK/src/api/zip.ts` 只封装通用 `zip.compress/extract/list`，不把 `.card/.box/.cpk` 混成同一种业务对象。
- `Chips-SDK/cli/index.js` 的 `zipDirectoryToCpk()` 使用 `archiver('zip', { store: true })`，把工程根 manifest 写到包根 `manifest.yaml`，并排除重复 manifest、`publish-meta.json` 和旧 `.cpk`。
- `run-cli-package-compatibility-tests.cjs` 断言 `.cpk` 只包含 `assets/icons/app-icon.ico`、`dist/main.js`、`manifest.yaml`，且所有条目 `compressionMethod=0`。

### Host 插件安装链路

- `PluginRuntime.install(.cpk)` 会先把 `.cpk` 解包到临时目录，再查找 manifest 并复制到 workspace `plugins/<pluginId>/`。
- `findManifestPath()` 当前兼容 `manifest.yaml`、`manifest.yml`、`manifest.json` 和 `*.plugin.json`，排序优先级以 `manifest.yaml` 最高。
- 这说明公共规范可把工程根 `manifest.yaml` 定为唯一正式清单源，同时补充 Host 兼容读取历史/辅助 manifest 名称；不要反过来把兼容输入写成推荐生产口径。
