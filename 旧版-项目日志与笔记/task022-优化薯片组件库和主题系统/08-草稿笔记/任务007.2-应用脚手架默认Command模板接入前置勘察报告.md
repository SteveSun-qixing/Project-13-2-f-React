## 3. 当前 app 模板已有和缺失能力

### 3.1 chips-sdk / client

已有：

- `templates/app-standard/package.json.tpl` 已声明 `chips-sdk`，但在 `devDependencies` 中。
- `Chips-SDK/src/core/client.ts` 已提供 `createClient()`。
- `Chips-SDK/src/api/command.ts` 已提供 `client.command.register/unregister/get/list/invoke/setState/onRegistered/onUnregistered/onChanged/onInvoked`。
- `Chips-SDK/src/types/client.ts` 已把 `command` 挂到 `Client`。
- `Chips-SDK/src/index.ts` 已导出 command 相关类型。

缺失或不一致：

- 当前 `templates/app-standard/src/App.tsx.tpl` 未 import `createClient`，没有 `client.command.*` 示例。
- 当前 `templates/app-standard/template.json` 中 `supports.sdk` 为 `false`，但模板已经声明 `chips-sdk` 依赖；007.2 应改为 `true`，否则模板元数据与生成工程不一致。
- `chips-sdk` 当前放在 devDependencies；因为模板运行时代码将 import `createClient`，正式实施时建议评估是否移入 `dependencies`。同一生态内其他模板也把 `chips-sdk` 放 devDependencies，但它们主要用于类型或工具；app 模板若运行时代码直接导入，放 `dependencies` 更准确。若不调整，需要确认 `chipsdev build` 和发布包依赖解析不会丢运行时 SDK。

### 3.2 Bridge

已有：

- 当前模板有 `src/hooks/useChipsBridge.ts.tpl`，直接读取 `(window as any).chips`。
- 当前 `App.tsx.tpl` 通过 `(window as any).chips.invoke("theme.getCurrent", {})` 读取主题信息。
- Host Bridge 已暴露 `window.chips.command`，公共文档也已冻结 `command.register/unregister/get/list/setState/invoke`。

缺失或需要替换：

- 任务007.2 目标要求默认模板使用 `client.command.*`；因此 command 示例应优先走 SDK，不应继续以 `window.chips.invoke("command.*")` 私造薄封装。
- `useChipsBridge.ts.tpl` 可保留为 Bridge 可用性检查或非 SDK 场景示例，但 command 接线不应依赖它。
- 现有 `App.tsx.tpl` 中 `any` Bridge 直接调用和中文错误文本不符合“所有界面文案走多语言系统”的目标，007.2 至少应避免新增类似写法，最好顺手把 command 相关错误/状态展示全部用 i18n key。

### 3.3 主题

已有：

- `App.tsx.tpl` 使用 `ChipsThemeProvider`。
- `themeEventSource` 使用 `(window as any).chips` 并监听 `theme.changed`。
- UI 样式多处使用 CSS 变量，例如 `var(--chips-sys-color-surface, #ffffff)`。

### 4.3 必改：新增 commands 集中声明

建议新增路径：

- `Chips-Scaffold/chips-scaffold-app/templates/app-standard/src/commands/app-commands.ts.tpl`

建议内容职责：

- 集中导出 command id、handler id 和 `CommandDefinitionInput[]`。
- 从 `chips-sdk` import 类型，例如 `import type { CommandDefinitionInput, CommandInvokedEvent, CommandView } from "chips-sdk";`。
- commandId 使用模板插件 ID 前缀，例如 `{{ PLUGIN_ID }}.show-welcome`，满足全生态唯一。
- scope 使用 `{ kind: "app", appId: "{{ PLUGIN_ID }}" }`。
- title/description/aria label 只写 key，例如：
  - `app-standard.commands.showWelcome.title`
  - `app-standard.commands.showWelcome.description`
  - `app-standard.commands.showWelcome.ariaLabel`
- icon 使用运行时 `IconDescriptor`，例如 `{ name: "waving_hand", style: "rounded" }` 或 `settings`；不要使用 `assets/icons/app-icon.*`。
- handlerId 使用稳定字符串，例如 `show-welcome`。
- placements 覆盖三类消费：
  - `menuPlacement: [{ menuId: "app", groupId: "primary", order: 10 }]`
  - `toolbarPlacement: [{ toolbarId: "main", groupId: "primary", order: 10 }]`
  - `paletteKeywords: ["welcome", "demo"]`
- shortcut 可选；如添加 `shortcut: { accelerator: "CommandOrControl+Shift+P", platform: "desktop" }`，要确认不会与通用命令面板入口冲突。更保守是示例不默认注册全局快捷键，只在 UI 中展示菜单/工具栏/命令面板；但任务目标提到快捷键/Command 模板接入，建议至少有一个无冲突示例快捷键，并由测试断言所有触发走 `client.command.invoke()`。
- `state` 初始值建议 `{ enabled: true, visible: true }`。
- 不要导出业务函数给 Host；Host 只接收可序列化 metadata 和 handlerId。

### 4.4 必改：新增 command 注册和本地 handler hook

建议新增路径：

- `Chips-Scaffold/chips-scaffold-app/templates/app-standard/src/commands/useAppCommands.ts.tpl`

建议内容职责：

- 创建并复用 SDK client：`const client = createClient();`。
- 启动时调用 `client.command.register()` 注册 `appCommandDefinitions`。
- 卸载时调用 `client.command.unregister(commandId)` 清理示例命令。
- 调用 `client.command.list({ source: "toolbar", includeDisabled: true })`、`client.command.list({ source: "menu", includeDisabled: true })`、`client.command.list({ source: "palette", includeDisabled: true })` 读取列表。
- 订阅 `client.command.onChanged()` 重新拉取命令列表。
- 订阅 `client.command.onInvoked()`，根据 `handlerId` 和 `ownerPluginId/ownerSessionId` 执行本地 handler。最小 handler 可以只更新本地状态，例如记录最近一次触发来源；不要传函数给 Host。
- 暴露 `invokeCommand(commandId, source)`，内部统一调用 `client.command.invoke(commandId, {}, { source })`。
- 错误状态使用标准错误对象形态，UI 只展示 i18n key 对应文案或错误 code，不写硬编码中文。
- 如果模板内要显示 command 标题，提供一个同步 i18n adapter：从本地 `i18n/zh-CN.json` / `en-US.json` 导入或维护一个小型 `translateLocalKey(key)`。更理想是通过 `client.i18n.translate(key)`，但 React render 中需要异步缓存；为模板简单可靠，可做本地字典 adapter，同时不影响 command definition 的公共契约。

注意：

- `createClient()` 在非 Host 环境且无 transport 时调用 `client.command.*` 会抛 `BRIDGE_UNAVAILABLE`。模板测试应使用 mock transport 或只测试纯函数，不应要求 Vitest 在普通 Node 环境直连 Host。
- `React.StrictMode` 会让 effect 在开发下重复执行。注册逻辑应能承受重复 mount/unmount，或通过 `registeredRef` 控制；Host 对同 owner 同 commandId 重复 register 会覆盖，所以逻辑可以保持幂等。

## 6. 与任务007.1的依赖边界和风险点

### 6.1 不要抢跑组件库实现

任务007.1目标是让组件库 Toolbar、Menu、CommandPalette、ContextMenu、Shortcut 相关组件消费 Host command registry。当前 worktree 中已有 `Chips-ComponentLibrary/packages/components/src/index.js` 未提交改动，疑似 007.1 进行中：

- 增加 `createCommandAdapter`、`resolveCommandToolbarItems`、`resolveCommandMenuGroups`、`resolveCommandPaletteItems`、`useChipsCommands`。
- 增加 Toolbar/MenuBar/ContextMenu/Shortcut 相关 token 和 metadata。
- 但当前未看到 `index.d.ts` 同步导出，也未看到实际 `ChipsToolbar` 等组件实现导出。

007.2 正式实施应遵循：

- 如果 007.1 已合入并正式导出 command 消费 helper/组件，app 模板应直接消费组件库正式 API。
- 如果 007.1 尚未完成，不应在 app 模板里私造长期 Toolbar/MenuBar/ContextMenu/Shortcut 组件。
- app 模板可以保留最小组合 UI，但数据必须来自 `client.command.list()`，触发必须走 `client.command.invoke()`，并在测试里证明没有独立动作模型。

### 6.2 不要把业务 handler 传给 Host

公共命令系统契约明确：Host 不接收函数，只保存可序列化 metadata、owner、scope、permission、placement 与状态。SDK/插件侧根据 `handlerId` 和 `command.invoked` 事件执行本地 handler。

模板中禁止：

- `client.command.register({ ..., handler: () => ... })`
- 在菜单/工具栏/命令面板 item 中直接挂业务函数并绕过 `command.invoke`
- 把 `onClick` 视作 command 事实源

### 6.3 command 权限和业务权限必须一致

Host 当前 `ensurePluginOwnsCommandPermissions()` 会检查 command 的 `permission` 是否声明在 owner 插件 manifest permissions 中。模板若定义 command-specific permission，manifest 必须同步声明。

推荐模板首轮只演示 command 服务级权限，避免额外业务权限造成新手困惑。若示例确需业务权限，必须写清并测试。

### 6.4 `chipsdev validate` 当前不会替模板查 command 语义

SDK CLI `validateManifestShape()` 当前只校验基础字段、permissions 数组、runtime targets、capabilityFallbacks、app ui.surface、module 等；不会校验：

- command 权限是否与源码 command 注册匹配。
- command definition 是否有 raw title。
- `src/commands/` 是否存在。

因此 007.2 的质量门禁不能只依赖 `chipsdev validate`，必须补脚手架模板测试和生成工程测试。

### 6.5 i18n 和 UI 文案风险

当前模板本身已有硬编码中文。007.2 如果只新增 command 区域，至少要保证新增命令相关文案完全走 i18n key；若重构范围允许，建议顺带把 `App.tsx.tpl`/`ExamplePanel.tsx.tpl` 的新增或触碰文案收口到 i18n。

不建议为了快速通过验收把 command title 翻译结果硬编码进 `label` 字段，因为命令契约禁止 raw `label/title/description/ariaLabel` 字段。

### 6.6 SDK 运行时依赖位置风险

当前 app 模板把 `chips-sdk` 放在 `devDependencies`，但 007.2 会让生成的 React 应用运行时代码 import `createClient`。如果打包后的 JS 已把 SDK 打入 bundle，构建期解析即可；如果发布或独立安装环境需要运行时依赖，devDependency 可能不准确。

建议正式实施时做一次生成工程 `npm run build` 和 `npm run validate` 后，再检查构建产物是否稳定；如决定移动到 `dependencies`，同步更新脚手架测试和 SDK CLI create workspace 测试。

### 6.7 不要引入未冻结库或新路由方案

不要新增 React Router、状态管理库、快捷键库、菜单库或命令面板库。当前组件库和 SDK 足够完成最小示例。

### 6.8 公共文档是否需要补充

公共命令契约 `生态共用技术文档/协议与契约/13-命令系统契约.md` 已明确：
