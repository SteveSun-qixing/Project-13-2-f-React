## 2. 当前 `module-standard` 模板能力与缺口

### 2.1 已支持能力

当前模板目录：`Chips-Scaffold/chips-scaffold-module/templates/module-standard/`

已支持：

- Manifest 基线：
  - `id/name/version/type/entry/description/author/permissions/runtime.targets/engines/os/module`。
  - `type: module`。
  - `entry: dist/index.mjs`。
  - `runtime.targets.desktop/headless = true`，`web/mobile = false`。
  - `module.apiVersion = 1`、`module.runtime = worker`、`module.activation = onDemand`。
  - `module.provides` 默认声明一个 capability。
  - `module.consumes: []`。
- 方法基线：
  - `run`，`mode: sync`，输入输出 schema 分别为 `contracts/run.*.schema.json`。
  - `runAsync`，`mode: job`，输入输出 schema 分别为 `contracts/runAsync.*.schema.json`。
  - `runAsync` 演示 `ctx.job.reportProgress(...)`。
- 工程基线：
  - `.eslintrc.cjs` 禁止 `TODO/FIXME`。
  - `chips.config.mjs` 指向 `./src/index.ts`、`./dist`、`./tests`、`./manifest.yaml`。
  - `package.json` 脚本含 `dev/build/test/lint/validate`。
  - `tsconfig.json` 严格 TypeScript 基线。
  - `README.md` 说明模块无界面、`module.provides`、`ctx.host.invoke`、`ctx.module.invoke`、不使用 `ctx.services.*`。
- 脚手架能力：
  - `listAvailableTemplates()` 按模板目录枚举。
  - `loadTemplateMeta(templateId)` 校验 `template.json`。
  - `renderTemplateToTarget(options)` 做字符串占位符替换、跳过 `归档/`、拒绝非空目标目录。
  - `createModuleProject(options)` 对外给 `chipsdev create module` 使用。

## 4. 建议的 vNext 模板矩阵

### 4.1 总体原则

- 模板以“形态”命名，不以现有业务模块 ID 命名。
- 模板只提供正式骨架、契约和最小可运行测试，不复制五个样本的业务算法、卡片资源重写细节或 PDF/图片导出完整逻辑。
- 模板默认不新增第三方依赖；只有图像处理模板如需沿用颜色提取样本的 `sharp/esbuild`，应把它明确标为“依赖现有官方样本技术选型”的模板，并在 026.02 内谨慎决定是否默认启用。
- 每个模板都应生成：
  - `manifest.yaml`
  - `contracts/*.schema.json`
  - `src/index.ts`
  - `src/types.ts`
  - `src/errors.ts`
  - 至少一个业务分层文件
  - `tests/unit/module-definition.test.ts`
  - README
  - `package.json` 中 `lint/typecheck/test/build/validate/package/verify`

### 4.2 模板一：`module-function`

适用场景：

- 纯函数转换、文本处理、元数据归一、无文件写入或少量 Host 查询的轻量模块。

默认 Manifest：

```yaml
type: module
entry: dist/index.mjs
permissions: []
runtime:
  targets:
    desktop: { supported: true }
    web: { supported: false }
    mobile: { supported: false }
    headless: { supported: true }
module:
  apiVersion: 1
  runtime: worker
  activation: onDemand
  provides:
    - capability: {{ MODULE_CAPABILITY }}
      version: "1.0.0"
      methods:
        - name: transform
          mode: sync
          inputSchema: contracts/transform.input.schema.json
          outputSchema: contracts/transform.output.schema.json
  consumes: []
```

默认 contract/schema：

- 输入：`{ value: string, options?: { uppercase?: boolean, prefix?: string } }`
- 输出：`{ value: string, handledBy: string }`
- 错误：`MODULE_INPUT_INVALID` 或 `{{ ERROR_PREFIX }}_INPUT_INVALID`，建议模板变量支持默认错误前缀。

默认测试：

- provider capability 与 method 暴露。
- 正常转换。
- 输入非法时抛结构化错误。
- 生成文件不含未渲染占位符、旧 `run/runAsync` 身份、`chips dev` 文本。

README 要点：

- 适用于无界面同步能力。
- 不访问文件/平台能力时 `permissions: []`。
- 调用方使用 `client.module.invoke({ capability, method: "transform" })`。

验证命令：

- `npm run verify`
- `chipsdev module invoke --capability <capability> --method transform --input '{"value":"hello"}'`

### 4.3 模板二：`module-file-converter`

适用场景：

- 输入文件到输出文件/目录的转换模块。
- 适合 `card -> html` 这类原子转换骨架，也适合未来 `doc -> html`、`markdown -> html` 等文件转换。

默认 Manifest：

```yaml
permissions:
  - file.read
  - file.write
module:
  provides:
    - capability: {{ MODULE_CAPABILITY }}
      version: "1.0.0"
      methods:
        - name: convert
          mode: job
          inputSchema: contracts/convert.input.schema.json
          outputSchema: contracts/convert.output.schema.json
  consumes: []
```

默认 contract/schema：

- 输入：`{ sourceFile: string, output: { path: string, overwrite?: boolean }, options?: Record<string, unknown> }`
- 输出：`{ outputPath: string, artifacts: [{ type: string, path: string, mimeType?: string }], warnings?: [...] }`
- 错误前缀：`CONVERTER_INPUT_*`、`CONVERTER_OUTPUT_*`、`CONVERTER_PIPELINE_*`。

默认测试：

- `file.stat` 校验输入存在。
- 输出已存在且 `overwrite=false` 报 `CONVERTER_OUTPUT_EXISTS`。
- `overwrite=true` 时调用 `file.delete`。
- job 进度 `prepare/completed`。
- 失败时对部分输出做 best-effort 清理。

README 要点：

- 通过 `ctx.host.invoke("file.*")` 访问文件能力。
- 不直接使用 Node 文件系统作为正式 Host 能力替代。
- 输出目录/文件治理、overwrite、清理策略必须测试。

验证命令：

- `npm run verify`
- `chipsdev module invoke --capability <capability> --method convert --input-file /绝对路径/input.json`

### 4.4 模板三：`module-html-renderer`

适用场景：

- 消费目录态 HTML，调用 Host `platform.renderHtmlToPdf` 或 `platform.renderHtmlToImage` 输出文件。
- 对应 HTML 转 PDF、HTML 转图片这类 Electron 宿主能力模块。

默认 Manifest：

```yaml
permissions:
  - file.read
  - file.write
  - platform.read
module:
  provides:
    - capability: {{ MODULE_CAPABILITY }}
      version: "1.0.0"
      methods:
        - name: convert
          mode: job
          inputSchema: contracts/convert.input.schema.json
          outputSchema: contracts/convert.output.schema.json
  consumes: []
```

默认 contract/schema：

- 输入：`{ htmlDir: string, entryFile?: string, outputFile: string, options?: { format?: string } }`
- 输出：`{ outputFile: string, warnings?: [...] }`
- 可通过模板元数据区分默认 renderer target：
  - `renderTarget: "pdf"`：README 示例使用 `platform.renderHtmlToPdf`，输出可含 `pageCount`。
  - `renderTarget: "image"`：README 示例使用 `platform.renderHtmlToImage`，输出含 `format/width/height`。

默认测试：

- 校验 `entryFile` 不能越出 `htmlDir`。
- 校验 `htmlDir` 与 entry file 存在。
- 调用 `ctx.host.invoke("platform.renderHtmlToPdf" | "platform.renderHtmlToImage", payload)`。
- Host 返回缺失 `outputFile` 时映射为结构化错误。
- job 取消时在调用前停止。

README 要点：

- 模块不得直接 `import("electron")`、不得创建 `BrowserWindow`。
- 依赖 Electron 的真实联调用 `chipsdev module invoke`，不是 `chipsdev start`。
- `platform.renderHtmlToPdf/Image` 是 Host 正式动作，不是模块可复制的浏览器运行时。

验证命令：

- `npm run verify`
- `chipsdev module invoke --capability <capability> --method convert --input-file /绝对路径/html-render-input.json`

### 4.5 模板四：`module-image-processor`

适用场景：

- 本地图片读取、图像采样、图像元数据提取、颜色提取等模块。

默认 Manifest：

```yaml
permissions:
  - file.read
module:
  provides:
    - capability: {{ MODULE_CAPABILITY }}
      version: "1.0.0"
      methods:
        - name: process
          mode: sync
          inputSchema: contracts/process.input.schema.json
          outputSchema: contracts/process.output.schema.json
  consumes: []
```

默认 contract/schema：

- 输入：`{ imagePath: string, options?: { sampleSize?: number } }`
- 输出：`{ summary: string, handledBy: string }` 或若选择颜色提取模板则 `{ backgroundColor: string, accentColor: string }`。
- 错误前缀：通用模板可用 `IMAGE_PROCESSOR_*`；颜色提取专用模板可用公共契约已冻结的 `COLOR_PICKER_*`。

默认测试：

- `file.stat`、`file.read` 调用。
- 拒绝空路径/远程 URL。
- 处理 Host `file.read` 非二进制返回。
- 结构化错误断言。

README 要点：

- 若不引入图像解码库，模板只能给出“文件读取 + 处理函数边界”的正式骨架，不能伪造图像分析。
- 若提供 `module-color-extractor` 专用模板并默认使用 `sharp/esbuild`，必须明确这是沿用现有官方 `Chips-ColorPicker` 样本已批准技术选型，不属于 026.02 新增技术选型。

验证命令：

- `npm run verify`
- `chipsdev module invoke --capability <capability> --method process --input '{"imagePath":"/absolute/path/image.png"}'`

### 4.6 模板五：`module-orchestrator`

适用场景：

- 编排多个模块能力，统一对外暴露一个入口。
- 对应 `Chips-FileConversion-Plugin` 的 `converter.file.convert` 形态。

默认 Manifest：

```yaml
permissions:
  - file.read
  - file.write
  - module.read
  - module.invoke
module:
  provides:
    - capability: {{ MODULE_CAPABILITY }}
      version: "1.0.0"
      methods:
        - name: execute
          mode: job
          inputSchema: contracts/execute.input.schema.json
          outputSchema: contracts/execute.output.schema.json
  consumes:
    - capability: {{ CONSUMED_CAPABILITY }}
      versionRange: ^1.0.0
```

默认 contract/schema：

- 输入：`{ source: { type: string, path: string }, target: { type: string }, output: { path: string, overwrite?: boolean }, options?: Record<string, unknown> }`
- 输出：`{ outputPath: string, pipeline: [{ capability: string, method: string }], artifacts: [...] }`
- 错误前缀：`ORCHESTRATOR_*` 或对文件转换模板使用 `CONVERTER_PIPELINE_*`。

默认测试：

- 正常调用 `ctx.module.invoke({ capability, method, input })`。
- 子模块返回 `mode: sync`。
- 子模块返回 `mode: job` 后轮询 `ctx.module.job.get(jobId)`。
- 父 job 取消时调用 `ctx.module.job.cancel(jobId)`。
- 子模块失败时错误归一。
- 临时目录创建/清理，如果模板包含文件中间产物。

README 要点：

- `module.consumes` 是正式依赖声明。
- 编排不是新的插件类型，只是普通模块调用其他模块。
- 不直接 import 下游模块源码，不复制下游 schema。

验证命令：

- `npm run verify`
- `chipsdev module invoke --capability <capability> --method execute --input-file /绝对路径/input.json`

## 5. 模板选择 API / CLI 参数建议

### 5.1 脚手架内部 API

当前 API 已经有 `templateId`：

```ts
interface CreateModuleProjectOptions {
  projectName: string;
  targetDir: string;
  templateId: string;
  pluginId: string;
  moduleCapability: string;
  displayName: string;
  version: string;
  authorName?: string;
  authorEmail?: string;

```

026.02 最小改动建议：

- 保持 `templateId` 为主选择字段，不新增“模板 registry 类”或第二套选择 API。
- 给 `ModuleScaffoldTemplateMeta` 增加可选描述字段即可：
  - `category?: "function" | "file-converter" | "html-renderer" | "image-processor" | "orchestrator"`
  - `defaultMethod?: string`
  - `defaultMode?: "sync" | "job"`
  - `requiresPermissions?: string[]`
  - `consumesTemplate?: Array<{ capabilityPlaceholder: string; versionRange: string }>`
- 如果 026.02 需要 `module-orchestrator` 默认写入 consumed capability，可保守新增可选参数：
  - `consumedCapability?: string`
  - `methodName?: string`
  - `errorPrefix?: string`
- 不建议新增复杂 `shape` 对象、插件业务类型枚举或自动 schema 生成 DSL；模板目录本身已经是稳定边界。

### 5.2 `chipsdev create module` CLI

当前 CLI 注释写了通用格式 `chipsdev create <type> <targetDir> [--template id] [...]`，但 `handleCreate` 对 `module` 分支当前没有解析 `--template`，始终使用 `module-standard`。

建议实现：

```bash
chipsdev create module <targetDir>
chipsdev create module <targetDir> --template module-file-converter
chipsdev create module <targetDir> --template module-html-renderer
chipsdev create module <targetDir> --template module-orchestrator --consumes converter.card.to-html
chipsdev create module <targetDir> --capability converter.example.convert --plugin-id chips.module.example
```

参数建议：

- `--template <id>`：选择模板目录，默认仍为 `module-standard` 或将其作为 `module-function` 的别名。
- `--capability <capability>`：覆盖默认 `module.${slug}` 推导。
- `--plugin-id <id>`：覆盖默认 `chips.module.${slug}` 推导。
- `--method <name>`：可选，覆盖模板默认方法名；若不做此项，模板各自固定 `transform/convert/process/execute`。
- `--consumes <capability>`：仅对编排模板有效，可重复；初版也可只支持一个。

不建议：

- 不建议把 `--kind html-to-pdf` 直接写成业务模块名；应通过 `--template module-html-renderer` 加 README 指引完成。
- 不建议默认生成五个现有官方模块 ID、capability 或 README 文案。
- 不建议为 `ColorPicker` 默认新增 `sharp` 依赖，除非 026.02 明确把 `module-color-extractor` 作为“官方样本模板”并同步说明技术选型来源。
