## 2. 总体现状

当前任务015后续控件可以分为三类：

- 已有正式组件闭环：`Button`、`Checkbox`、`RadioGroup`、`Switch`、`Select`、`Tooltip`、`Skeleton`、`EmptyState`，以及相邻但名称不完全匹配的 `Input`、`DateTime`、`ErrorBoundary`、`LoadingBoundary`。
- 有相近能力但没有任务015独立 scope：`ToggleButton` 可由 `ChipsButton toggleable/pressed` 表达一部分状态；`TextField` 可由 `ChipsInput` 表达单行输入；`DatePicker/TimePicker` 可由 `ChipsDateTime` 的日期时间输入覆盖一部分；`ErrorState` 可由 `ErrorBoundary/EmptyState` 组合覆盖一部分。但这些都没有独立 `data-scope`、contract、comp token、主题 token/CSS 或类型导出。
- 完全缺口：`Image`、`Media`、`IconButton`、`TextArea`、`SearchField`、`SecureField`、`SegmentedControl`、`ComboBox`、`Slider`、`Stepper`、`NumberInput`、`DatePicker`、`TimePicker`、`Badge`、`Tag`、`Avatar`、`Progress`、`Spinner`、`ErrorState`。

两套官方主题当前 `theme-interface.contract.json` 与 `theme-min-functional-set.json` 均只列出现有 46 个组件 scope：`box/button/.../virtual-list`，未包含上述新增 scope。新增任意组件都必须同步默认主题与暗色主题，否则后续 contract guard 会出现缺口。

## 5. 建议后续批次拆分

原则：每批都形成“实现 + 类型 + contract + 组件 token + 默认主题 token/CSS/contract + 暗色主题 token/CSS/contract + 测试 + 公共文档同步”的独立闭环；不要只加空导出。

### 批次 B：按钮派生与轻量展示/反馈

建议控件：

- `IconButton`
- `ToggleButton`
- `Badge`
- `Tag`
- `Avatar`
- `Spinner`
- `Progress`

理由：

- 写集小，交互复杂度低到中，适合继主代理 `Icon` 后立即利用统一图标入口。
- `IconButton` 可验证 `ChipsIcon` 与按钮 a11y 的组合规范；`Spinner/Progress` 可补齐任务015反馈类闭环，避免应用层私造加载控件。
- `Badge/Tag/Avatar` 多为展示控件，可以稳定 contract/token 命名模板。

建议 scope：

- `icon-button`
- `toggle-button`
- `badge`
- `tag`
- `avatar`
- `spinner`
- `progress`

注意：

- `ToggleButton` 不建议只靠 `ChipsButton toggleable` 默默复用；至少需要正式导出、scope/token/contract 或在公共文档明确 `ToggleButton` 是 `ChipsButton` 的正式模式并补独立测试。为了任务015矩阵清晰，推荐补独立 `ChipsToggleButton`。
- `IconButton` 必须强制可访问名称，图标装饰/功能语义需和 `ChipsIcon` 保持一致。

### 批次 C：文本输入派生

建议控件：

- `TextField`
- `TextArea`
- `SearchField`
- `SecureField`

理由：

- 可复用 `ChipsInput` 当前状态模型、错误归一、`useInteractiveState`、`createAriaStatusProps`。
- 对后续应用迁移价值高：任务031/036/043 等迁移任务都将依赖标准文本输入与错误态。

建议 scope：

- `text-field`
- `text-area`
- `search-field`
- `secure-field`

注意：

- 不要把四种模式塞入一个 `ChipsInput` 的多 boolean API；设计稿要求避免 boolean 模式膨胀，建议独立组件或显式 compound/slot。
- `SearchField` 至少需要输入、搜索图标槽、清空按钮槽、`onSearch`/Enter 行为、`aria-label`/`aria-describedby`。
- `SecureField` 至少需要密码输入、可见性切换按钮槽、`aria-pressed`、键盘激活与可访问名称。

### 批次 D：选择扩展

建议控件：

- `SegmentedControl`
- `ComboBox`

理由：

- 和已有 `RadioGroup`、`Select` 相邻，但键盘语义更复杂，适合单独一批。

建议 scope：

- `segmented-control`
- `combo-box`

注意：

- `SegmentedControl` 应明确单选/多选边界。若只做单选，使用 roving focus + `aria-pressed` 或 `radiogroup/radio` 需要先冻结口径。
- `ComboBox` 应按 combobox/listbox 语义补 `aria-expanded`、`aria-controls`、`aria-activedescendant`、Escape/Arrow/Enter 路径，不建议用当前 `Select` 简单包一层。

### 批次 E：数值输入

建议控件：

- `NumberInput`
- `Stepper`
- `Slider`

理由：

- 三者共享数值解析、min/max/step/clamp、键盘增减逻辑，可在一批建立公共 helper，但需要分别有正式 scope。

建议 scope：

- `number-input`
- `stepper`
- `slider`

注意：

- `Slider` 需要明确单滑块还是范围滑块。本任务建议先做单值 slider，范围滑块后续作为扩展。
- `Stepper` 与 `NumberInput` 是否组合使用需要写清；可以让 `NumberInput` 内部使用 stepper part，但 `Stepper` 作为独立控件仍需导出和测试。

### 批次 F：日期时间拆分

建议控件：

- `DatePicker`
- `TimePicker`

理由：

- 当前已有 `ChipsDateTime`，但任务015明确要求 `DatePicker/TimePicker`。需要决定是新增两个正式控件，还是把 `ChipsDateTime` 降为内部/高级组合。

建议 scope：

- `date-picker`
- `time-picker`

注意：

- 当前 `ChipsDateTime` 的 `label` 使用了 `data-part="icon"`，这在语义上不够清晰；新增拆分时建议使用 `label/input/icon/status`。
- 如暂不做弹出日历/时间列表，也应明确这是原生输入型 picker，并为后续弹层能力保留公开 part，不做临时占位。

### 批次 G：媒体与错误展示

建议控件：

- `Image`
- `Media`
- `ErrorState`

理由：

- `Image/Media` 涉及加载、错误、替代文本、尺寸适配、媒体类型边界，和文本/按钮/输入不是同一类问题。
- `ErrorState` 应与 `ErrorBoundary` 区分：前者是静态错误展示组件，后者捕获渲染错误。

建议 scope：

- `image`
- `media`
- `error-state`

注意：

- `Image` 必须严格处理 `alt`、装饰图、加载失败、占位、`objectFit` 等语义；不要在组件库中引入业务图片处理逻辑。
- `Media` 建议先定义为通用媒体壳层/受控 `<video>/<audio>` 容器还是仅内容卡槽。若涉及复杂播放器控制，可能跨入基础卡片/媒体应用能力，需要先冻结边界。
- `ErrorState` 可复用 `EmptyState` 的结构思路，但应有独立 error token、role/aria-live 策略和 action 槽。

### 6.1 新增 scope 契约缺口

除已有 `button/input/checkbox/radio/switch/select/tooltip/skeleton/empty-state/date-time/error-boundary/loading-boundary` 外，本任务清单的大部分控件没有：

- `COMPONENT_TOKEN_MAP` 条目
- `buildComponentContract` 条目

- `P0_BASE_INTERACTIVE_COMPONENTS` 或新的任务015基础控件元数据集合
- `packages/theme-contracts/contracts/components/*.contract.json`
- `packages/tokens/tokens/comp/*.json`
- 默认/暗色主题 `tokens/comp/*.json`
- 默认/暗色主题 CSS selector
- 默认/暗色主题 `theme-interface.contract.json` 与 `theme-min-functional-set.json` 覆盖

这不是阻断当前勘察的工单，但后续实现批次必须完整补齐。

### 6.2 文档与代码漂移风险

公共文档当前“常见接口”列的是已交付组件，但任务015要求的基础控件清单显著大于当前实现。后续每批完成后应同步：

- `生态共用技术文档/组件库/01-组件库对外使用总览.md`
- `生态共用技术文档/组件库/02-组件契约标准.md`
- `生态共用技术文档/组件库/03-Token与主题对接标准.md`
- `生态共用技术文档/组件库/05-可访问性与质量基线.md`（如新增测试/质量基线口径）
- 必要时补 `生态共用技术文档/组件库/00-组件库文档索引.md`

本报告不修改正式文档，只提示主代理在各批次完成时同步。

### 6.3 类型声明漂移风险

发现至少一个现有类型与实现不完全一致：

- `ChipsSkeleton` 实现接收 `animated`、`shape`、`ariaLabelKey`，但 `SkeletonProps` 当前只声明 `lines/loading/disabled/error/ariaLabel/i18n/onStateChange/onDiagnostic` 等字段。

这类漂移会影响后续新控件类型冒烟测试。建议下一批开始前先让主代理决定是否顺手修复同范围类型漂移；如果认为超出任务015基础控件批次，应单独记录工单。

### 6.4 组件库技术栈历史漂移

`生态共用技术文档/组件库/01-组件库对外使用总览.md` 仍写有 `React + Ark UI + Style Dictionary + Tamagui (Core)`，而当前组件库实现主要是自研 React 结构与 helper。历史上已有 `工单094-组件库冻结技术栈与质量门禁覆盖漂移`，本报告不重复创建工单；后续新增控件应沿用当前仓库实际模式，除非用户另行要求技术栈迁移。

### 6.5 主题 CSS 中存在固定视觉值

现有主题 CSS 有 `font-size: 14px`、`padding-block: 6px`、`outline: 2px` 等固定值。后续新增组件若继续复制，可能扩大 token 约束漂移。是否要把这些结构尺寸全面 token 化属于主题系统治理范围；若后续实现中遇到必须新增固定视觉值且无现成 token，建议先记录工单，而不是在组件库中硬编码。

## 8. 结论

任务015剩余范围很大，但可以稳定拆成 B-G 六个批次。下一批最推荐从 `IconButton / ToggleButton / Badge / Tag / Avatar / Spinner / Progress` 开始，因为它们能最快建立“新增正式 scope + 两套主题包 + contract + 测试”的重复模板，同时避开输入、组合框、日期时间、媒体这些更容易牵扯交互语义的复杂区。

后续每批开始前都应重新读取 `index.js`、`index.d.ts`、contract/token/theme contract 最新状态，尤其主代理当前正在并行收口 `Text / Label / Icon`，这些变更可能影响 `IconButton` 与展示控件的最终写法。
