## 当前代码事实

1. `chipsdev` 当前命令集合在 `Chips-SDK/cli/index.js:29` 定义，包含 `init/create/start/stop/status/config/logs/plugin/theme/update/doctor/open/module/preview/component/quality/assimilate/diagnostics/server/debug/build/test/lint/e2e/package/validate/login/publish/version/run`。Host 托管命令集合在 `Chips-SDK/cli/index.js:63`，包括 `start/stop/status/config/logs/plugin/theme/update/doctor/open`。

2. `chipsdev init` 默认模板仍在注释中写 `type: app | card | layout | module | theme | i18n`，见 `Chips-SDK/cli/index.js:671`。从当前 CLI 的 `create` 实现看，正式支持的工程类型是 `app/card/layout/module/theme`，见 `Chips-SDK/cli/index.js:1757` 后续分支和错误提示。

3. `chipsdev package` 在 `Chips-SDK/cli/index.js:1055` 实现：读取工程根 `chips.config.mjs` 与 `manifest.yaml`，要求 `config.outDir` 存在，包名为 `<safePluginId>-<version>.cpk`，输出到工程根 `dist/`，包根写入 `manifest.yaml`，再按构建产物与 manifest 显式资源根收集文件。`zipDirectoryToCpk` 使用 `archiver('zip', { store: true })`，并排除嵌套 manifest、`publish-meta.json` 与历史 `.cpk`。

4. `chipsdev validate` 在 `Chips-SDK/cli/index.js:1092` 起实现，当前校验 `id/name/version/type`、`permissions` 必填数组、完整 `runtime.targets.desktop/web/mobile/headless`、app 的 `ui.surface`、非 app 禁止 `ui.surface`、`capabilityFallbacks`、模块插件 `module` 字段、构建输出目录非空、manifest 引用资源存在。

5. `chipsdev theme inspect` 是 SDK 工具命令，见 `Chips-SDK/cli/index.js:2105`，读取主题包 manifest/contracts/tokens/dist 并输出诊断报告。`chipsdev theme validate` 不是 SDK 本地主题包静态校验命令，而是被转发到 Host CLI 的 `chips theme validate`。

6. Host 托管命令由 `delegateHostManagedCommand` 执行，见 `Chips-SDK/cli/index.js:1551`。它先解析开发工作区，再用 `runHostCliCommand` 调用 Host 编译产物 `dist/src/main/cli/index.js`，并设置 `CHIPS_HOME=<workspacePath>`、`CHIPS_WORKSPACE_KIND=dev`。开发工作区解析规则见 `Chips-SDK/cli/index.js:707`：优先 `CHIPS_HOME`，再向上找 `.chips-host-dev`，找不到则在当前项目根创建。

7. `chipsdev theme/run/open` 会触发默认主题引导，见 `Chips-SDK/cli/index.js:1509` 和 `Chips-SDK/cli/index.js:1555`。当前默认主题以 `ThemePack/Chips-default/manifest.yaml` 安装，通过 Host CLI `plugin install`、`plugin enable`、`theme apply` 进入开发工作区。

8. `chipsdev run` 在 `Chips-SDK/cli/index.js:2346` 实现，只支持 `manifest.type === "app"`；它先构建当前应用，再引导开发工作区主题，拉起 Electron 执行 `Chips-Host/dist/src/main/electron/dev-run-app.js`，传入 `--workspace` 与工程根 `manifest.yaml`。Host 端 `dev-run-app.ts` 会同步 `plugins.json` 中已配置插件，再安装启用当前应用并调用 `plugin.launch`。

9. `chipsdev module invoke` 在 `Chips-SDK/cli/index.js:2499` 与 `Chips-SDK/cli/index.js:2531` 实现。它支持 `--capability`、`--method`、`--input`、`--input-file`、`--manifest`、`--timeout-ms`，未知参数报错。若当前目录或显式 manifest 是 module 工程，会先构建，再拉起 Electron 执行 `dev-invoke-module.js`。Host 端会安装启用模块并调用 `module.invoke`，job 模式轮询到终态。

10. Host CLI 的正式入口是 `chips` 直连命令，不再使用 `chips host` 二级命令。`Chips-Host/src/main/cli/index.ts:76` 实现 `runCli`，`host` 二级命令直接返回错误，帮助文本见 `Chips-Host/src/main/cli/index.ts:92`。

11. Host CLI `theme validate` 存在，见 `Chips-Host/src/main/cli/index.ts:208`。真实语义是列出当前工作区主题，逐个执行 `theme.apply` 与 `theme.resolve`，返回每个已安装主题的校验结果；它不接收 `<theme-cpk>`，也没有 `--tokens`、`--components` 参数。

12. Host CLI `plugin install` 支持插件目录、`.cpk` 文件、manifest 文件路径，CLI 层见 `Chips-Host/src/main/cli/index.ts:241`，运行时安装核心见 `Chips-Host/src/runtime/plugin-runtime.ts:320` 与 `Chips-Host/src/runtime/plugin-runtime.ts:685`。`.cpk` 输入会先解压到临时目录，再查找 manifest、读取、校验资源、复制到 `<workspace>/plugins/<pluginId>/`。

13. Host 运行时安装时会校验插件 ID 反向域名、语义化版本、权限命名、资源路径安全，以及非 `source: local` 时必须有 `signature`，见 `Chips-Host/src/runtime/plugin-runtime.ts:605` 与 `Chips-Host/src/runtime/plugin-runtime.ts:635`。当前本地 `.cpk` 打包链路没有签名生成步骤。

14. Host 服务路由中 `plugin.install/enable/disable/uninstall/query` 已注册，见 `Chips-Host/src/main/services/register-host-services.ts:4892`、`:4912`、`:4933`、`:4959`、`:5044`。主题服务 `theme.list/apply/resolve/contract.get` 见 `:3979`、`:4003`、`:4074`、`:4087`。卡片、箱子、zip 打包服务分别见 `card.pack` `:5984`、`box.pack` `:6201`、`zip.compress/extract/list` `:6621` 起。

15. Host 安装器 CLI 只有 `macos` 命令，见 `Chips-Host/src/main/installer/cli.ts`。安装器会组装 `Chips.app` 与 `.pkg`，默认内置插件包含默认主题、生态设置面板、可选图片查看器，见 `Chips-Host/src/main/installer/macos-installer.ts`。

## 需要修正文档处

1. `生态共用技术文档/文件格式规范/03-CPK打包格式规范.md` 的目录结构仍写成包内 `app/`、`card/`、`layout/`、`module/`、`theme/` 包裹目录。当前 `chipsdev package` 与 Host 安装事实是 `.cpk` 包根直接放 `manifest.yaml`，构建产物通常位于 `dist/`，manifest 显式资源按相对路径进入包内，不存在强制的类型包裹根目录。

2. 同一文档主题插件目录示例重复写了两次 `manifest.yaml`，并以 `tokens/`、`components/`、`global.css` 作为包内主结构。当前主题脚手架和测试体现的是工程源目录可以有 tokens/styles/contracts 等，但 `.cpk` 正式入口以 `manifest.entry.tokens`、`manifest.entry.themeCss` 指向 `dist/tokens.json`、`dist/theme.css`，并携带 `contracts` 等显式资源。

3. 同一文档权限示例仍是旧权限名 `file-access`、`network-request`、`clipboard-access`。当前 Host 权限命名校验要求点分段 kebab/lowercase，如 `file.read`、`theme.read`、`plugin.manage`、`platform.read`、`zip.manage`。

4. 同一文档写“应用/卡片/布局/模块入口分别是 HTML/渲染组件/布局算法/模块代码，主题入口是 CSS 文件”。当前 manifest 模型允许 `entry` 是字符串或对象，主题入口是对象形式 `tokens/themeCss`，模块还需要 `module.provides[].methods[].inputSchema/outputSchema` 等可执行契约资源。建议按 `Manifest配置规范` 与 `chipsdev validate` 真实字段重写。

5. 同一文档“签名机制”写得像所有 CPK 都必须签名并验证。当前代码只在 `manifest.source !== 'local'` 时要求 `signature` 字段存在，本地打包安装不生成也不验证数字签名。应改为“当前实现边界”，避免把未落地发布链路写成开发前置要求。

6. 同一文档“热插拔支持”包含“差异包更新、签名完整性验证、unload/load 生命周期、增量更新支持”等当前代码未完整验证的能力。当前已落地的是同 `pluginId` 安装替换、保留启用状态、关闭相关会话、同步主题/模块状态；不能把差分升级或完整热更新流水线写成已实现标准。

7. 同一文档“主题契约校验工具”列出 `chips theme validate <theme-cpk>`、`chips theme validate --tokens <theme-dir>`、`chips theme validate --components <theme-dir>`。当前 Host CLI 没有这些参数。真实可用命令是 `chips theme validate` / `chipsdev theme validate` 对当前工作区已启用主题逐个 `theme.apply + theme.resolve`；静态检查是 `chipsdev theme inspect` 生成诊断报告，主题工程自己的 `validate:theme` 才是工程级主题校验脚本。

8. `Chips-SDK/cli/index.js` 的 `defaultConfigTemplate` 注释仍残留 `i18n` 第六类工程类型。这是代码口径问题，不属于本报告可修改范围，但正式文档不应引用 `i18n` 作为当前插件类型。

9. `chipsdev login/publish` 的帮助与输出仍写“可对接后续市场服务/线上市场服务”。用户已明确当前薯片生态不需要应用市场。若正式公共文档出现“应用市场/市场服务”口径，应移除或改为中性“外部分发服务/发布系统”并由后续任务决定；代码中的提示文案也建议单独修正。

10. `生态共用技术文档/开发与运维/04-打包与安装路径手册.md` 和 `生态共用技术文档/命令行工具/02-Chips-Dev开发者命令行手册.md` 整体较新，但示例命令有的使用 `chipsdev theme validate`，应在上下文中继续明确其真实语义是“运行时工作区已启用主题校验”，不是“校验某个主题包文件”。这一点在部分段落已经说明，建议统一加一句避免误读。
