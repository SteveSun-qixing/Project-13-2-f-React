## 1. 复核结论

`Chips-BookReader` 当前已经是一个功能较完整的阅读器应用插件，具备 EPUB/EPUB3、PDF、TXT、Markdown、FB2、RTF 的内部阅读链路，也能识别 MOBI/AZW/AZW3/DJVU/DOC/DOCX 并给出解码器缺失错误。它已经使用 React、`chips-sdk`、`@chips/component-library` 的 `ChipsThemeProvider`、本地双语词典、Host `platform/resource/file/config/theme/i18n` 能力，并有较多阅读引擎单测。

但它还没有完成任务031要求的新前端框架迁移：入口仍是单体 `src/App.tsx`，没有 `src/app/AppRoot/AppProviders/AppRuntimeProvider/AppShell/scene-registry` 结构；没有正式 `ChipsEnvironmentProvider`；没有 command registry；启动上下文、主题、语言、事件订阅仍由根组件手写；UI 组件多数是阅读器私有控件和 CSS 类，而不是组件库/声明式 View 模型沉淀出的应用壳层。README 还残留原工作区路径，并且 README 的“当前正式支持 EPUB/EPUB3”与 manifest/需求/实现中声明的多格式范围不完全一致。

任务031建议拆成 5 个中等颗粒度子任务，不宜像 030 那样继续过细拆分：先冻结现状与任务拆分，再迁移 AppRuntime/Scene，再接入 Commands 与组件库壳层，再收口主题/i18n/a11y/焦点/键盘，再做真实素材、文档与闭环。

### 2.2 任务031工单

`任务031-阅读器应用迁移.md` 要求把 `Chips-BookReader` 迁移到新前端框架基线，使它成为电子书、PDF、Markdown、文本和文档类资源的统一阅读应用插件。关键验收点包括：

- 重新核对 resource-handler、file-handler、网络权限、配置权限和 surface。
- 改造成 App/Scene/Document surface 结构，支持空启动、资源启动和文件启动。
- 阅读视图、目录、书签、搜索、进度、字体、分页/滚动、缩放、设置改为统一 View/Modifier 模型。
- 格式解析优先走 Host/模块插件正式能力，缺失能力登记工单，不在应用内复制底层解析基础设施。
- 使用组件库实现工具栏、侧栏、目录、搜索、弹层、阅读设置和错误状态。
- 接入主题、阅读安全区、焦点、键盘翻页、a11y、减少动效和多语言。
- 增加 EPUB/PDF/TXT/Markdown/DOCX 等启动和回归样本。
- 增加阅读进度、配置保存、窗口恢复、资源释放和错误诊断测试。

### 2.3 生态设计与公共规范

- `生态设计原稿/01-生态概述.md`：薯片生态以 Host 为唯一入口，所有上层应用是插件；12 层架构中 L1-L9 由 Host 承载，组件库负责 L10 无头组件，SDK 只是开发工具包。
- `生态设计原稿/06-前端多样化和主题系统.md`：应用层可以有不同 UI，但业务调用必须走 Host/Bridge/SDK；视觉统一由主题系统提供，不允许应用层硬编码独立皮肤体系。
- `生态设计原稿/07-插件系统架构.md`：应用插件是 surface 语义下的跨平台界面插件；模块插件承担解析、转换、索引等无界面能力。
- `生态设计原稿/15-查看器设计.md`：文档查看器、电子书阅读器应通过统一资源打开链路接收资源和显示上下文；查看器/阅读器不应拼接文件系统绝对路径或绕开 Host 资源解析。
- `生态共用技术文档/插件开发/02-应用插件开发.md`：官方应用模板要求 `ChipsEnvironmentProvider`、`AppRuntimeProvider/useAppRuntime()`、scene registry、SDK client 单例、命令目录、同步 i18n adapter、Host surface context。
- `生态共用技术文档/插件开发/06-Manifest配置规范.md`：`type: app` 必须声明 `runtime.targets` 和 `ui.surface`；`capabilityFallbacks` 必须明确 unsupported 策略。
- `生态共用技术文档/协议与契约/13-命令系统契约.md`：菜单、工具栏、快捷键、命令面板、上下文菜单必须消费同一 command registry；command 文案只能使用 i18n key；图标使用 `IconDescriptor`。

- `生态共用技术文档/组件库/11-焦点键盘与A11y交互模型.md`：复合列表、树、菜单、面板等应使用公共键盘模型、roving tabindex、FocusScope、ARIA 校验和测试 helper。

## 5. 迁移差距清单

### 5.1 必修差距

1. **应用结构差距**  
   当前缺少 vNext 应用模板的 `src/app/`、`src/runtime/`、`src/commands/`、`src/scenes/` 目录心智，根组件过重。

2. **命令系统差距**  
   目录、搜索、书签、偏好、打开文件、打开 URL、翻页、上一章/下一章等用户动作没有注册到 Host command registry，也没有菜单/工具栏/快捷键统一事实来源。

3. **权限差距**  
   manifest 未声明 `command.read/write/invoke`；若后续通过 Host/模块插件调用文档解析或转换，可能还需要补模块能力相关权限，但不能预先乱加。

4. **Document surface 差距**  
   阅读器能处理 `launchParams.resourceOpen/targetPath`，但没有把“空启动、文件启动、资源启动、文档上下文、错误上下文”明确建模为 Scene/Document Scene。

5. **解析能力边界差距**  
   当前 EPUB ZIP/OPF/HTML、TXT/Markdown/FB2/RTF、PDF iframe 包装都在应用内部。任务031要求解析优先走 Host/模块插件正式能力，缺能力要登记工单。需要主代理确认哪些内部能力允许作为阅读器领域能力保留，哪些应迁到模块插件。

6. **组件库差距**  
   `ReaderChrome/ControlButton/PanelShell/NavigationTree/SearchPanel/PreferencesPanel/FeedbackToast` 多数是私有组件。任务031要求工具栏、侧栏、目录、搜索、弹层、设置、错误状态尽量使用组件库。

7. **A11y/焦点差距**  
   阅读器交互层有键盘逻辑，但没有统一使用 `@chips/a11y` 的 keyboard map、FocusScope、roving tabindex 和 ARIA 测试。目录树、搜索结果、书签列表、偏好面板、抽屉关闭/焦点恢复需要专项收口。

8. **测试差距**  
   缺 AppRuntime/Environment/Command/Host launch 测试；e2e 仍是占位；缺真实素材回归样本路径、暗色主题/默认主题回归、资源释放与窗口恢复测试。

9. **文档差距**  
   README 与当前实现范围不完全一致，快速开始路径不属于当前 worktree；迁移后需要同步 README 和 `技术文档/02-书籍阅读器实现说明.md`。

### 5.2 不建议立刻处理为代码的风险点

- 不建议在任务031启动前直接改格式解析架构。模块插件能力缺口需要主代理结合 Host/SDK/ModulePlugin 当前能力判断，必要时登记问题工单或新增后续任务。
- 不建议为了“组件库化”重做阅读产品交互。用户明确要求应用迁移时最终功能、交互、使用逻辑不变；阅读器的沉浸式控制层应保持，只替换运行时与组件/主题/i18n/a11y底座。
- 不建议在任务031一开始就引入第三方 PDF/EPUB/DOCX 库。AGENTS 明确禁止未列入技术选型的第三方库；DOCX/MOBI/DJVU 等缺解码器应走模块能力工单。

   候选处理：031.01 或 031.05 统一修正文档。

3. **阅读器 e2e 门禁占位**  
   证据：`tests/e2e/basic-flow.test.ts` 仅断言 `1 + 1`。  
   候选处理：031.05 增加真实启动/导入/阅读面板/错误路径 e2e 或 Host smoke。

   候选处理：031.01 核对 Host/SDK 网络契约后决定。
