# 差距分析：Web 技术栈、统一页面结构与生态同化

## 1. 对标目标

薯片前端框架必须以 Web 技术栈作为底层，既能做复杂应用，也能表达网页式页面结构，还能快速吸收外部 Web 项目并同化为薯片生态应用。

这里的“同化”不是把外部网页简单放进 iframe，而是让项目逐步接入：

- 插件 manifest。
- Host surface。
- Bridge / SDK。
- 主题 token。
- 多语言 key。
- Chips 组件和布局系统。
- 命令、导航、权限、资源和配置。
- 质量门禁。

## 2. 当前薯片已有基础

根据重新核对：

- 官方产品统一使用 React。
- 应用插件本质是 Host 托管的 Web 前端入口。
- Desktop 由 Electron/Chromium 承载。
- 未来 Web/Mobile/Headless 已在 `runtime.targets` 和 `ui.surface` 中预留。
- Host 已有 surface、file、resource、config、theme、i18n、plugin、module、card、box 等服务域。
- SDK 已有 surface、resource、theme、plugin、document、card、box 等封装。
- Scaffold 已有应用插件脚手架方向。
- L8 已公开 `View/Stack/Grid/Form/List` 语义原语。

## 3. 当前主要差距

### 3.1 统一页面结构能力不足

当前组件库更偏应用工具和工作台基础。当前缺口集中在统一页面结构能力还不够完整：

- `View/Stack/Grid/Form/List` 需要成为脚手架默认页面结构。
- `Section/ScrollView/Text/Image/Media` 等基础页面表达能力需要补齐或规范化。
- 插件市场、主题展示、帮助文档、教程、社区等页面应复用同一套布局和组件规则。
- 普通页面结构应继续归入标准 app 插件和统一 View 模型。

影响：

- 插件市场、主题展示、帮助文档、社区页面、教程页面会各自写布局。
- 视觉和交互难以统一。
- 网页式页面结构难以直接享受主题、i18n、a11y 和性能门禁。

### 3.2 外部 Web 项目同化工具缺失

当前没有正式工具链来快速分析并改造外部 Web 项目。

缺少：

- 项目类型识别。
- 依赖与构建方式扫描。
- manifest 生成。
- 权限推断。
- 硬编码视觉扫描。
- i18n 文案抽取。
- 组件替换建议。
- 路由到 surface 的映射。
- Bridge/SDK 适配报告。
- 同化进度门禁。

### 3.3 常用功能模块前端封装还不够厚

Host 服务域已经厚，但上层前端消费还不够“少代码”。

例如，应用常见需求应该只有几行代码：

- 打开资源。
- 选择文件。
- 保存配置。
- 读取当前主题。
- 切换语言。
- 打开插件。
- 展示文档窗口。
- 调用模块能力。
- 记录日志。
- 发起导入/导出。

当前虽然 SDK 有基础封装，但还需要更高层的 hooks、组件、场景 API 和模板。

### 3.4 脚手架还不能承担“软件帝国级批量造应用”

现有脚手架定位是生成标准插件工程。未来还需要：

- 新建标准应用。
- 包装外部 Web 项目。
- 生成迁移报告。
- 自动替换基础组件。
- 注入主题和 i18n。
- 创建 preview 和测试矩阵。
- 生成 Host mock 和真实 Host 调试配置。

## 4. 差距等级

严重等级：高。

原因：如果没有 Web 项目同化能力和统一页面结构能力，薯片很难快速吸收、重做和统一大量软件。生态会变成“每个应用慢慢手写”，而不是形成高复用、高质量、快速复制的软件生产体系。

## 5. 后续判断

需要把“Web 同化工具链”列为前端框架 vNext 的正式方向，但优先作为 SDK/Scaffold CLI 和质量报告能力落地。App/Scene、View/Modifier、预览矩阵、主题治理等方向也应先归入 Host、SDK、组件库、脚手架、主题包和生态设置面板这些现有边界。

最终只有在某个能力域需要独立发布、独立版本、独立测试、独立维护时，才开工单评估是否新建项目。
