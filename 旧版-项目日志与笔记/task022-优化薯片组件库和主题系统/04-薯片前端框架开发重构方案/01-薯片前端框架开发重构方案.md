# 薯片前端框架开发重构方案

> 方案日期：2026-05-21  
> 文档性质：项目日志与重构方案，不是生态正式公共契约。  
> 目标：让薯片生态开发应用像 SwiftUI 一样简单、统一、高质量，同时遵守薯片 Host/Bridge/SDK、React、组件库、主题系统、多语言系统和 Electron 框架定位。

## 1. 北极星目标

薯片前端框架的目标不是“做一套组件库”，也不只是提供一套完整开发体验，而是提供一套最高质量的生态级应用框架。

它要服务薯片生态更大的目标：以 Host 大底座和 Web 技术栈为基础，长期重做大量软件，建立一套统一、高质量、好用、可扩展的软件生态。换句话说，它要支撑的是“软件帝国级”的应用生产能力。

开发者写一个薯片应用时，默认拥有：

- 应用入口、窗口场景、文档场景、设置页、菜单、工具栏和命令系统。
- 声明式 UI、布局、导航、弹层、表单、列表、表格、工作台和系统 UX。
- 主题、密度、动效、图标、多语言和可访问性的一致体验。
- Host 能力调用、权限、资源、卡片、箱子、文件、配置和日志的标准入口。
- 预览、组件矩阵、主题矩阵、测试、性能和发布门禁。
- 统一页面结构能力：用同一套 View/Stack/Grid/Form/List 表达文档、市场、教程、社区、主题展示、详情页、图文混排等普通页面结构。
- 外部 Web 项目同化能力：快速包装、接线、主题化、i18n、组件替换和质量门禁。

最终效果应该是：开发者主要思考产品结构和业务流程，不需要重复处理窗口、主题、i18n、Bridge、权限、键盘、焦点、错误态、空态、加载态、虚拟化、弹层栈和基础交互。

本方案的底座口径是 Electron + Host + 插件结构。Host 是大底座，常用模块优先沉淀为 Host 服务域；插件通过 `window.chips.*` / Runtime Client / SDK 使用能力；`surface` 是跨平台界面容器主语义，Desktop 才落为 Electron BrowserWindow。后续所有 App/Scene/Window/Document、View/Modifier、组件、主题、预览和性能工具都必须沿这条主链路设计。

本方案的技术栈口径是 Web 技术栈。官方前端使用 React；渲染基础来自 Chromium/Electron；主题来自 CSS 变量和 token；未来 Web/Mobile 也应围绕 Web runtime 与 surface 映射推进。

## 2. 基本原则

1. Host 是唯一运行时承载，插件访问系统能力只能通过 `window.chips.*` / Bridge / Runtime Client / SDK 正式链路。
2. 官方前端统一使用 React 技术栈。
3. 组件库保持 L10 Component Headless 定位，只负责结构、状态机、可访问性和主题契约点。
4. 主题系统保持 L11 Theme Runtime 定位，视觉必须由 token、contract、主题包和 Host 注入链路决定。
5. SDK 只承担开发期封装、类型、脚手架和测试辅助，不承载 Host 主运行时实现。
6. 不为了短期兼容保留旧口径；当前尚未发布第一版，应优先选择长期清晰的架构。
7. 不引入未在技术选型中明确使用的新第三方库；若需要引入，先形成决策文档和工单。
8. 所有新组件都必须有 contract、token、a11y、i18n、测试和文档。

## 3. 目标架构

### 3.1 分层位置

重构后的前端框架仍遵守现有 12 层架构：

| 层级 | 名称 | 本方案中的强化目标 |
|---|---|---|
| L1-L5 | PAL / Kernel / Services / Plugin Runtime / Bridge | 保持 Host 唯一运行时和系统能力边界 |
| L6 | Runtime Client | 成为 UI 能力调用的唯一协议封装层 |
| L7 | UI Hooks | 提供 React 开发者可用的主题、i18n、窗口、资源、配置、权限等 hook |
| L8 | Declarative UI | 成为应用 UI 的声明式入口，对标 SwiftUI `View` |
| L9 | Unified Rendering | 负责声明树归一、校验、主题解析、布局计算、提交和 effect 调度 |
| L10 | Component Headless | 提供无头组件、状态机、结构、a11y、contract |
| L11 | Theme Runtime | 提供 token、作用域链、变量注入、主题切换和主题契约 |
| L12 | App/Page Domain | 只写业务状态和业务编排，不直接碰 Host 内部细节 |

### 3.2 前端框架能力域与现有落点

以下不是新增独立项目清单，而是前端框架需要具备的能力域。当前阶段优先落在已经存在、开发者已经熟悉的 Host、SDK、组件库、脚手架、主题包和插件体系中。

| 能力域 | 优先落点 | 职责 |
|---|---|---|
| App / Scene / surface / commands | Host + SDK + `chips-scaffold-app` | 应用入口、场景声明、surface 映射、命令注册、生命周期 |
| Runtime Client / UI Hooks | SDK + Host Bridge | Bridge 协议、错误归一、权限、超时、React hooks |
| View / Modifier / Layout / State / Navigation | Host L8/L9 + SDK + 组件库 + 脚手架 | 声明式 UI、布局原语、状态环境、导航呈现、默认模板 |
| Component Headless | `Chips-ComponentLibrary` | 无头组件、状态机、结构、a11y、contract、测试基线 |
| Theme Runtime / Design Token | Host theme service + ThemePack + 组件库主题契约 | token 解析、作用域链、变量注入、主题诊断、组件接口点 |
| Preview / Gallery / Performance / A11y | SDK `chipsdev` + 组件库质量脚本 + 生态设置面板 | 预览、组件矩阵、主题矩阵、性能和可访问性检查 |
| Testing / Quality Gate | SDK + 组件库 testing 包 + 脚手架模板 | Host mock、Bridge mock、组件测试、应用测试、视觉和 E2E 辅助 |
| Web 项目同化 | SDK/Scaffold CLI 能力优先 | 外部 Web 项目识别、manifest 生成、Bridge 接线、token/i18n/组件替换报告 |

只有当某个能力域达到独立发布、独立版本、独立测试和独立维护的规模时，才考虑拆成新项目。否则它应作为现有项目中的模块、脚手架命令、Host 服务或开发工具能力存在。

## 4. 开发者 API 目标形态

### 4.1 应用入口

目标是让应用入口具备 SwiftUI `App` 的清晰度，同时遵守薯片 manifest 和 Host 运行时。

这里的窗口声明应编译或映射到 Host `surface` 语义，而不是让应用插件直接操作 Electron BrowserWindow。

示意：

```tsx
createChipsApp({
  manifest,
  scenes: (
    <ChipsApp>
      <ChipsWindowGroup id="main" titleKey="app.title">
        <MainPage />
      </ChipsWindowGroup>

      <ChipsSettingsScene>
        <SettingsPage />
      </ChipsSettingsScene>

      <ChipsCommands>
        <ChipsCommand id="file.open" titleKey="command.file.open" shortcut="mod+o" />
      </ChipsCommands>
    </ChipsApp>
  )
});
```

这不是要求照搬 Swift 语法，而是要形成“应用结构由框架声明，运行时由 Host 接管”的体验。

### 4.2 视图与布局

目标是让页面使用统一布局原语和主题语义：

```tsx
<ChipsView titleKey="page.library.title">
  <ChipsNavigationSplitView>
    <ChipsSidebar>
      <ChipsList items={boxes} selection={selectedBoxBinding} />
    </ChipsSidebar>

    <ChipsDetail>
      <ChipsToolbar>
        <ChipsToolbarItem command="box.import" />
        <ChipsToolbarItem command="box.search" />
      </ChipsToolbar>
      <ChipsDataGrid rows={entries} columns={columns} />
    </ChipsDetail>
  </ChipsNavigationSplitView>
</ChipsView>
```

同一套模型也必须适用于网页式普通页面结构：

```tsx
<ChipsView titleKey="market.plugin.title">
  <ChipsStack>
    <ChipsText i18nKey="plugin.name" />
    <ChipsText i18nKey="plugin.summary" />
    <ChipsGrid items={screenshots} />
    <ChipsText content={description} />
  </ChipsStack>
</ChipsView>
```

### 4.3 状态、绑定和环境

目标是明确本地状态、业务状态、Host 服务状态和环境值边界：

- `useChipsState`：页面本地 UI 状态。
- `useChipsBinding`：表单、选择、导航、焦点双向绑定。
- `useChipsEnvironment`：theme、locale、density、workspace、pluginId、permissions。
- `useChipsStorage`：app/scene/workspace 作用域持久状态。
- `useChipsFocusState`：焦点状态。
- `useChipsServiceState`：Host 服务状态只读或受控写入入口。

这些 API 不能绕过 Runtime Client。

## 5. 组件库扩展路线

### 5.1 P0：架构收口与地基

优先级最高，因为后续所有组件都依赖这些口径。

1. 处理技术栈漂移：在 Ark/Zag/Tamagui 与自研状态机之间做正式路线决策。
2. 修正 contract validator 分层：普通组件契约和 iframe 高级组件契约分离。
3. 拆分 `packages/components/src/index.js` 的集中实现，按组件族模块化。
4. 建立每个组件独立目录：实现、类型、contract、token、tests、README。
5. 建立 direct import 路径，聚合入口只做开发便利，不影响按需导入和包体。
6. 组件 API 规范升级为组合优先：Root、Trigger、Content、Item、Panel、Provider。
7. 建立组件默认 i18n key 规则。
8. 建立真实 DOM、浏览器交互、a11y、视觉回归和性能门禁。
9. 建立主题切换 E2E，覆盖应用、复合卡片 iframe、基础卡片 iframe、箱子封面 iframe。

## 6. 主题系统重构重点

主题系统要从“token 能构建”升级为“全生态视觉运行时”。

需要强化：

1. token 层级：`ref/sys/comp/motion/layout` 保持，补齐 density、z-index、overlay、focus-ring、selection、scrollbar、drag、drop、chart、media、editor。
2. 作用域链：继续使用 `global -> app -> box -> composite-card -> base-card -> component`。
3. 组件状态：覆盖 idle、hover、focus、active、disabled、loading、error、selected、expanded、collapsed、dragging、drop-target、invalid、readonly、checked、indeterminate。
4. 主题包：一个主题包只承载一种外观，不在包内混合 light/dark。
5. 图标：运行时 UI 图标统一收口到 `ChipsIcon + IconDescriptor`。
6. 预览：主题包必须能生成所有组件、所有状态、所有密度、所有语言方向的矩阵预览。
7. 门禁：token 完整性、contract 匹配、对比度、动效安全、图标资产、变量注入、iframe 刷新都必须校验。

## 7. 多语言系统重构重点

组件库和前端框架需要默认接入 i18n：

1. 所有用户可见文案都使用 key。
2. 组件内系统文案使用组件级默认 key。
3. aria label 也走 i18n。
4. 命令、菜单、工具栏、弹层、空态、错误态、进度、分页都要声明 key。
5. 语言切换触发局部重渲染，不重启应用。
6. 缺失 key 进入质量门禁。

- 示例应用：设置页、资源管理器、插件市场、编辑器、卡片查看器。

### 阶段 5：Web 项目同化与生态规模化

目标：

- 支持外部 React/Vite/静态 Web 项目快速包装为薯片 app 插件。
- 输出主题、i18n、组件替换、权限和 Host 接线报告。
- 让生态具备批量吸收和改造软件的能力。
- 网页式普通页面仍归入统一 app 插件与统一 View 模型，不能另起应用分类。

交付物：

- Web 项目扫描器。
- manifest 生成器。
- Bridge/SDK 接线检查。
- token 迁移报告。
- i18n 抽取报告。
- Chips 组件替换建议。
- 同化质量门禁。

## 11. 关键风险与需要决策的问题

1. 技术栈路线：Ark/Zag/Tamagui 是否继续作为正式底座，还是自研状态机升格为正式路线。
2. L8 Declarative UI 的真实形态：React JSX 组合为主，还是增加可序列化 UI 声明树为主，或两者共存但边界清晰。
3. 组件库与 App Framework 的包边界：哪些能力放 Host，哪些放 SDK，哪些放组件库。
4. 预览工具使用方式：纯浏览器、Host mock、还是启动真实 Host 开发工作区。
5. 视觉回归基线存储：快照保存位置、主题矩阵规模、CI 成本。
6. 组件数量扩展后的包体和导入性能：必须支持 direct import 和按需加载。
7. 多窗口与多插件状态同步：需要 Host 场景状态和权限模型支撑。

## 12. 验收标准

重构完成后，至少达到：

1. SwiftUI 官方基础控件和容器，薯片都有对应正式组件或框架能力。
2. 每个组件都有 contract、token、i18n、a11y、测试和预览。
3. 应用入口能通过 `ChipsApp/Scene/Window/Commands` 统一声明。
4. 主题切换覆盖应用窗口、卡片、箱子、iframe 和原生窗口背景。
5. 多语言切换覆盖组件默认文案和 aria label。
6. 复杂组件支持键盘和焦点管理。
7. 大列表、表格、树、资源网格具备性能预算。
8. 开发者可以用脚手架生成符合规范的应用，并在预览工具中检查主题、语言、状态和窗口尺寸。
9. 所有正式门禁脚本通过。
10. 生态内应用不再需要私有基础控件和私有主题适配。

## 13. 最终目标表达

薯片前端框架 vNext 应该让开发者获得这样的体验：

- 想做一个设置页：直接用 `ChipsSettingsScene + ChipsForm + ChipsSection + ChipsField`。
- 想做一个资源管理器：直接用 `ChipsNavigationSplitView + ChipsResourceList + ChipsResourcePreview + ChipsToolbar`。
- 想做一个编辑器：直接用 `ChipsWorkbench + ChipsDockLayout + ChipsInspector + ChipsCommandRegistry`。
- 想做一个插件市场：直接用 `ChipsPluginCard + ChipsPermissionRequest + ChipsInstallButton`。
- 想做一个卡片/箱子应用：直接用 `ChipsCardCoverFrame + ChipsBoxEntryCover + ChipsResourcePicker`。

开发者仍然使用 React，但不再孤零零地面对 Electron、Bridge、主题、i18n、可访问性和组件细节。框架把这些系统能力托住，应用只需要专注业务。这才是薯片生态对标 SwiftUI 的真正方向。
