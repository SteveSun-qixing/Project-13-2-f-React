# 薯片组件库与主题系统优化审查

## 1. 结论

当前 `Chips-ComponentLibrary` 不能称为完美状态。

它已经具备阶段性可用基础：P0/P1/P2 的一批核心组件已经导出，主题 token、contract、类型入口、单元测试、a11y 基线和性能门禁可以跑通。本轮已执行：

- `cd Chips-ComponentLibrary && npm run verify`：通过。
- `cd Chips-ComponentLibrary && npm run quality:gate`：通过。
- 当前组件契约约 32 个，质量门禁报告显示 passed。

但如果按“全生态应用组件库”的定位来判断，组件种类数量还不够，组件深度也还不够。它目前更像“第一批生态通用组件基线”，可以支撑设置面板、简单表单、基础列表、基础工作台、卡片封面和复合卡片窗口等场景；但还不足以覆盖编辑引擎、资源管理器、社区平台、阅读器、播放器、富文本编辑器、主题编辑器、插件市场、安装器、可视化工作流等未来全部软件。

判断标准不是“有没有按钮、输入框和表格”，而是能否让生态内各种应用少写私有 UI、少写私有交互、少写私有主题适配。目前还做不到。

## 3. 当前不能称为完美的原因

### 3.1 冻结技术栈与真实实现不一致

生态文档和组件库技术文档冻结的是 `React + Ark UI + Style Dictionary + Tamagui Core`。当前真实依赖里没有 Ark UI、Zag.js、Tamagui Core，组件行为主要由自研状态和键盘逻辑实现。

优化方向：

1. 决定正式路线：继续按文档补齐 Ark UI / Zag.js / Tamagui Core，或把当前自研实现升格为正式路线。
2. 如果采用 Ark/Zag，需要为每个复杂交互组件建立状态机封装层。
3. 如果采用自研，需要更新生态共用文档，补齐状态机设计、键盘规则和 a11y 证明。
4. 不应长期保留“文档冻结一套，代码实现另一套”的状态。

### 3.2 contract 分层不干净

当前 contract validator 强制所有组件都存在 `iframe.requiredSandbox`，导致普通组件也带 iframe 字段。这与“iframe 高级组件附加契约只适用于 CardCoverFrame / CompositeCardWindow”的设计不一致。

优化方向：

1. 将普通组件 contract 与 iframe 高级组件 contract 分层。
2. 普通组件只校验 `component/scope/parts/states/tokens/a11y`。
3. iframe 组件额外校验 `sandbox/allow/lifecycleEvents/messageBoundary/degradedState`。
4. 更新 contract validator，让普通组件不再伪装成 iframe 组件。

### 3.3 测试门禁还偏浅

当前测试可以证明很多纯函数和导出可用，但还没有完整证明真实浏览器交互可用。

优化方向：

1. 增加真实 DOM 级组件测试。
2. 增加 Playwright 浏览器交互测试。
3. 每个交互组件至少覆盖键盘操作、焦点顺序、disabled/loading/error、受控/非受控模式。
4. Dialog 必须覆盖 focus trap、Escape 关闭、关闭后焦点恢复、aria-modal。
5. Menu/Select/CommandPalette 必须覆盖 roving focus、方向键、Home/End、搜索、禁用项跳过。
6. SplitPane 必须覆盖 pointer 事件、拖拽清理、键盘调节、卸载时监听器释放。
7. DataGrid/Tree/VirtualList 必须覆盖大数据量、可访问性、选择状态、排序、展开折叠和滚动行为。

### 3.4 组件实现过于集中

大量组件集中在 `packages/components/src/index.js`，长期会影响维护、测试、按需导入和职责边界。

优化方向：

1. 按组件族拆目录：`base-interactive/`、`data-form/`、`workbench/`、`system-ux/`、`media/`、`navigation/`。
2. 每个组件独立 `component.tsx`、`contract.json`、`tokens.json`、`tests`、`README`。
3. 聚合入口只做导出，不承载实现。
4. 增加按组件导入路径，减少全量 barrel 带来的包体和依赖耦合。

### 3.5 API 组合能力不足

部分组件还是单体 props 模型，离“组合优先、显式子组件、避免 boolean props 爆炸”的目标还有距离。

优化方向：

1. Dialog 改为 compound API：`Dialog.Root`、`Dialog.Trigger`、`Dialog.Content`、`Dialog.Close`。
2. Tabs 改为 `Tabs.Root/List/Trigger/Panel`。
3. Menu 改为 `Menu.Root/Trigger/Content/Item/Separator/Group`。
4. DataGrid 改为可组合列、行、单元格、工具栏、空态、分页。
5. Workbench 组件改为布局容器 + 面板注册 + 命令插槽。

### 3.6 i18n 接入不完整

组件库原则上不硬编码用户可见文案。当前部分组件依赖外部传入 label，但系统级组件还需要更完整的 i18n 适配。

优化方向：

1. 建立组件级默认文案 key，而不是直接给英文 fallback。
2. 所有 close、expand、collapse、loading、empty、error、retry 等系统文案走 i18n adapter。
3. 组件 contract 中声明需要的 i18n key。
4. 测试覆盖语言切换后的文案和 aria label。

### 3.7 主题 token 覆盖不够细

当前 token 能覆盖基础视觉，但对于复杂软件，组件状态和密度还需要更细。

优化方向：

1. 所有组件 token 覆盖 idle/hover/focus/active/disabled/loading/error。
2. 增加 selected、expanded、collapsed、dragging、drop-target、invalid、readonly、checked、indeterminate 等状态 token。
3. 增加密度 token：compact / normal / spacious。
4. 增加尺寸 token：xs / sm / md / lg。
5. 增加 z-index、overlay、scrim、focus-ring、selection、scrollbar、resize-handle token。
6. 增加数据可视化 token：chart palette、series color、grid line、axis、legend。
7. 增加媒体 token：player controls、timeline、waveform、caption、thumbnail overlay。

### 3.8 主题运行时还缺真实生态闭环验证

组件库侧有 token resolver 和变量注入工具，但全链路仍要证明 Host 主题服务、preload 注入、应用 provider、组件消费、iframe 内容刷新全部一致。

优化方向：

1. 建立主题切换 E2E：Host 当前主题 -> preload 注入 -> 应用根节点 -> 组件渲染。
2. 覆盖应用窗口、原生窗口背景、复合卡片 iframe、基础卡片 iframe。
3. 覆盖默认主题和暗色主题两个独立 themeId。
4. 覆盖工作区隔离：`chips` 和 `chipsdev` 当前主题互不污染。
5. 覆盖主题禁用/卸载后的回退。
6. 主题包 contract 失败时必须阻断应用主题，而不是静默回退。

## 5. 主题系统优化清单

1. 明确主题包“一包一种外观”的强约束，并让设置面板只按 themeId 切换。
2. 补齐默认浅色主题与默认暗色主题的完整视觉验收。
3. 建立主题 contract schema 版本化。
4. 建立 token 命名自动校验，禁止业务名 token 混入 comp 层。
5. 建立 token 引用图，检测循环、孤儿 token、未使用 token。
6. 建立主题覆盖矩阵，覆盖 global/app/box/composite-card/base-card/component。
7. 建立主题包预览基准页，展示所有组件全部状态。
8. 建立主题包截图回归，防止样式漂移。
9. 建立 contrast 自动报告，覆盖文本、图标、边框、焦点环。
10. 建立 motion 安全门禁，限制时长、曲线和高频动画。
11. 建立 reduced-motion 支持。
12. 建立 high-contrast 高对比度主题策略。
13. 建立 density token 与组件尺寸的统一映射。
14. 建立图标 token 与 `ChipsIcon` 的完整映射。
15. 建立字体资产加载、回退和缺失诊断。
16. 建立主题切换性能预算：组件树不重建，优先变量更新。
17. 建立 iframe 主题变量注入一致性测试。
18. 建立原生窗口背景 token 推导测试。
19. 建立主题禁用、卸载、契约失败的回退策略测试。
20. 建立主题包开发者文档中的真实示例工程。

## 7. 架构与包结构优化清单

1. 拆分 `packages/components/src/index.js` 的巨型文件。
2. 每个组件建立独立目录。
3. 每个组件绑定同名 contract、token、docs、tests。
4. 聚合包只导出，不承载实现。
5. 增加子路径导出，例如 `@chips/components/button`。
6. 类型定义从源码生成，避免手写声明漂移。
7. contract 由组件元信息生成或双向校验。
8. tokens 由 contract 反向检查完整性。
9. 组件族按依赖层级拆包，避免高级组件污染基础组件。
10. `card-runtime` 与普通组件 contract validator 分离。
11. `theme-contracts` 提供 schema 和 CLI，不只提供 JSON 文件。
12. `testing` 包提供真实组件测试工具。
13. `a11y` 包提供可运行测试工具，而不只是 props 断言。
14. `hooks` 包明确哪些是内部 hook，哪些是对外正式 API。
15. 建立弃用策略，但当前第一版未发布前不保留兼容包袱。

## 9. 总体判断

当前组件数量对“第一批生态应用”基本够用，对“全生态长期平台”不够。

当前组件质量对“阶段性开发和内部验证”可用，对“完美状态、正式生态标准、第三方开发者长期依赖”还不够。

真正的完美状态应该满足：

1. 冻结技术栈与真实实现一致。
2. 所有组件契约分层干净。
3. 所有组件真实交互、a11y、主题、多语言、性能均有门禁。
4. 组件种类覆盖通用应用、专业编辑器、媒体工具、资源管理、社区平台、插件市场、主题编辑和系统治理。
5. 应用插件不再需要重复造基础 UI。
6. 主题包可以无侵入接管所有视觉状态。
7. Host、SDK、组件库、主题包、应用之间的边界稳定可验证。

在这些完成前，建议把当前状态定义为：

**组件库阶段性基线可用，但还不是全生态完美组件平台。**
