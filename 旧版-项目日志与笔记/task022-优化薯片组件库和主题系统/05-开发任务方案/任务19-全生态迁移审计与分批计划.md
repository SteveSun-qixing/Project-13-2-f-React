# 任务19：全生态迁移审计与分批计划

## 1. 任务目标

在框架底座、脚手架、组件库、主题包和样板应用验证完成后，对整个生态做一次全量迁移审计，形成可执行的分批迁移计划。

这一步是“从新框架可用”走向“整个生态完成重构”的转折点。它不直接改业务代码，而是明确每个项目需要迁移什么、风险在哪里、先后顺序如何、验收命令是什么。

## 2. 当前范围

需要纳入审计：

- Host：`Chips-Host`
- SDK：`Chips-SDK`
- 组件库：`Chips-ComponentLibrary`
- 脚手架：`Chips-Scaffold/*`
- 主题包：`ThemePack/Chips-default`、`ThemePack/Chips-theme-default-dark`
- 应用插件：`Chips-EcoSettingsPanel`、`Chips-CardViewer`、`Chips-EditingEngine`、`Chips-BookReader`、`Chips-MusicPlayer`、`Chips-PhotoViewer`、`Chips-RichTextEditor`、`Chips-VideoPlayer`
- 基础卡片插件：`Chips-BaseCardPlugin/*`
- 箱子布局插件：`Chips-BoxLayoutPlugin/*`
- 模块插件：`Chips-ModulePlugin/*`
- 社区平台：`Chips-CommunityPlatformServer`
- 开放项目处理空间：`OpenSourceProjectHandlingFolder`
- 成品测试空间：`ProductFinishedProductTestingSpace`

## 4. 开发内容

1. 生成项目清单。
   - 项目路径。
   - 项目类型。
   - 是否有 `manifest.yaml`。
   - 是否有 `package.json`。
   - 是否有 `AGENTS.md`。
   - 当前验证脚本。

2. 迁移项扫描。
   - 是否直接使用 `window.chips.invoke`。
   - 是否绕开 `chips-sdk`。
   - 是否直接访问 Electron/Node。
   - 是否硬编码可见文案。
   - 是否硬编码颜色、圆角、阴影、字体、动效。
   - 是否使用组件库旧 API。
   - 是否缺少 `runtime.targets`、`ui.surface`。
   - 是否缺少主题 contract。
   - 是否缺少 i18n。
   - 是否缺少 a11y 和键盘测试。

3. 风险分级。
   - P0：阻断新框架或全生态运行。
   - P1：阻断某类插件迁移。
   - P2：影响质量但可分批修复。
   - P3：文档或体验改进。

4. 批次划分。
   - 第一批：治理和样板应用。
   - 第二批：核心应用插件。
   - 第三批：基础卡片插件。
   - 第四批：箱子布局插件。
   - 第五批：模块插件。
   - 第六批：社区平台和开放项目样本。
   - 第七批：成品测试空间和发布验收。

5. 输出迁移矩阵。
   - 每个项目一行。
   - 当前状态。
   - 目标状态。
   - 依赖任务。
   - 负责人或后续处理。
   - 验证命令。
   - 阻断工单。

## 6. 验收标准

- 全生态项目清单完整。
- 每个项目都有迁移等级和验证命令。
- 每个阻断问题都有工单或明确归属。
- 后续任务 20-29 能直接根据审计矩阵推进。

## 7. 验证方式

建议执行：

```bash
find . -maxdepth 3 -name manifest.yaml -print | sort
find . -maxdepth 3 -name package.json -print | sort
rg -n "window\\.chips\\.invoke|electron|BrowserWindow|require\\('fs'\\)|from 'fs'|TODO|占位|临时版|简化版" Chips-* ThemePack ProductFinishedProductTestingSpace OpenSourceProjectHandlingFolder
```

仅文档审计时不需要跑构建；如果审计中修改脚本或检测工具，需要运行对应项目测试。

## 9. 风险与注意事项

- 不要跳过“审计”直接全量迁移，否则容易在多个项目同时卡住。
- 不要把某个应用的私有做法变成公共规则。
- 发现架构缺口先登记工单，再推进可继续的部分。
