# 04 下载与回导链路分析

> 用户问题：之后直接从网页上下载保存完整卡片。现在是怎样？要做到需要什么？这一节是目标体验里缺口最明确的一环。

## 1. 现状：网页端没有任何下载能力

全仓库检索结论：
- **服务端没有任何返回源 .card 的下载接口**。`cards.ts` / `upload.ts` / `host-runtime.ts` 等所有路由里搜 `download`，只有对象存储内部工具函数 `downloadFile`（`storage/s3.ts:139`，Worker 下载源文件用，非对外接口）。
- **网页前端没有任何下载按钮/入口**。`packages/web/src` 全目录搜 `download|导出|保存|下载|save|export`：只命中个人资料表单的"保存"、iframe sandbox 的 `allow-downloads` token，没有任何面向卡片的下载动作（`UploadQueueItem` 成功态只有「打开结果 / 前往主页」两个链接）。
- 生态共用文档 `09-社区平台API契约.md` 第 651 行明确把「社区内 .card 回下载」列在**当前不在契约范围内**的能力里。

## 2. 但好消息：源文件其实一直在

上传时源 .card 已经**永久**存进了对象存储 `chips-card-files/{userId}/{cardId}/source.card`（`upload.ts:419-425`），并记录了 bucket/key/sha256。所以「下载完整卡片」在数据层面**早就有了**，缺的只是：

1. 一个对外暴露源文件的 GET 接口；
2. 权限控制（下载权、公开/私有、downloadable 标记）；
3. 网页前端一个下载按钮。

## 3. "重新整合"其实是伪命题

用户担心"从服务器下载后如何再整合"——因为资源内嵌在 .card 里，**源 .card 就是完整自包含的卡片**，下载下来就是一个文件，不需要任何再整合。这与「资源外置 + URL 引用」的路径 B 不同：

- 路径 A（现在网页在用）：资源全内嵌 → 下载=源 .card 原样给用户，**零成本**。
- 路径 B（预签名直传外置资源）：.card 是壳、资源在 `chips-card-resources` 里 → 下载时要么**重新打包**（把外置资源取回塞进 .card），要么把资源一并给用户。这会让"下载"变成"重新组装"。

**结论**：在当前"资源全内嵌"的模型下，下载体验天然最简单。若未来引入资源外置，下载回导就要认真设计"打包回导"逻辑。

## 4. 要做到"网页下载"需要什么（方向性，不写实现）

- **服务端**：新增一个鉴权接口 `GET /api/v1/cards/:cardId/file`（或类似），校验 `downloadable` 与可见性后，把源 .card 流式吐给浏览器（Content-Disposition: attachment；支持私有卡片鉴权；大文件直接代理对象存储 GET，不让 Node 缓冲）。
- **权限语义**：`metadata.yaml` 里有 `downloadable` 字段（默认 true），社区数据库 cards 表目前没存这个字段的列 → 要么从 metadata 里读，要么同步到库。
- **前端**：卡片详情页/作品卡加「下载」按钮。由于源文件是"处理中"（pending）后才就绪，下载入口要在卡片 status=ready 后出现。
- **一致性**：`downloadable=false` 时隐藏下载按钮；私有卡片仅 owner 可见下载。

## 5. 下载与"像图片一样"体验的差距

图片（jpg）下载 = 右键保存，浏览器原生支持。卡片要接近这个体验，本质只需一个 URL + 浏览器原生下载行为。现在缺的就是这个 URL 接口 + 按钮。

## 6. 顺带：本地卡片查看器打开社区卡片的入口也不存在

网页端没有「用本地应用打开此卡片」的深链（无 app:// 协议、无 custom scheme、无 open-in-app）。现在网页查看全部在网页内完成。若想"网页看到 → 一键在本机查看器打开"，需要自定义协议/关联处理，当前没有，也超出本报告主线。

## 7. 小结

> 下载是目标体验最大的洞，但补全成本其实不高：源文件已有，只缺「鉴权下载接口 + 前端按钮 + downloadable 语义入库」。而"重新整合"在当前资源全内嵌模型下不存在。
