# 02 网页渲染机制分析

> 用户问题：网页端能否直接加载渲染，还是服务器渲染好页面再传送到浏览器？这一节把现状和取舍讲透。

## 1. 现状：服务器渲染好，浏览器只负责显示

当前答案是明确的：**服务器渲染好静态 HTML，浏览器用 iframe 加载，浏览器不参与卡片解析**。

流程回顾（详细代码见 01 节）：
1. 用户上传 .card，服务器存源文件；
2. 后台 Worker 启动一套完整 Host 运行时，把 .card 渲染成「静态 HTML 目录」（index.html + 每张基础卡一个 html + assets/content/ 资源树）；
3. 这个目录整体上传到对象存储；
4. 网页 `GET /api/v1/cards/:id/view` 命中缓存时直接 302 到对象存储/CDN 的静态入口，浏览器 iframe 加载。

## 2. 为什么服务器渲染而不是浏览器渲染

**浏览器直接渲染的候选方案**：把 .card 下载到浏览器，前端解 ZIP + 解析 yaml + 用 CardViewer 插件渲染。理论上可行（Host 有 web target），但现在**没这么做**。原因：

1. **要保证「网页看到的 = 本地看到的」**：只有用同一套渲染器（Host + 基础卡片插件）渲染，网页端和本地端看到的内容才可能一致。服务器端跑的就是同一套 Host，天然保证一致性。
2. **弱服务器反而受益**：渲染是重计算，但一次渲染、长期缓存。热门卡片只被第一次访问的 1 张请求拖累一次，之后的千万次访问全部由 CDN/对象存储扛静态文件。服务器不参与高频访问。
3. **浏览器渲染要求把整套渲染器 JS 发给浏览器**，包体大、且需要打通前端资源访问（私有资源、大文件、权限），复杂度高很多。
4. **覆盖"零依赖查看"**：服务器渲染后的纯静态 HTML 甚至不依赖 Chips 生态运行时也能显示（HTML 本身自包含），这是"像看图片一样看卡片"的基础。

## 3. 服务器端渲染的关键机制

### 3.1 用真实 Host 渲染，不是写死模板

`host-integration.ts` 里装的是完整插件集（CardViewer、全部基础卡片 BCP、布局、主题、转换模块），然后走 `card.render → target: offscreen-render`，导出器把渲染结果离线化成静态文件。

这意味着：**新加一个基础卡片类型，只要 Host/插件生态支持，服务器渲染自动就能出这个卡片**。渲染器和本地查看器是同一个东西，不会出现"本地能看、网页看不了"的漂移（前提是插件集保持同步）。

### 3.2 渲染缓存有版本键与生命周期

- 缓存版本键：`rendererVersion + renderProfile + themeId + locale + sourceCardSha256`（`card-render-cache.service.ts:40-52`）
- 版本键里**没有插件版本**（pluginVersionManifest 字段预留但当前不参与版本键，见 task023 方案第 8 节）。**风险**：如果服务器端安装的某个插件升级了渲染行为，缓存不会自动失效，会一直用旧渲染结果到缓存过期/手动重渲染。
- 生命周期：命中后 touch 续期到「最后访问 + 30 天」，过期由清理任务删除（`deleteExpiredCaches`）。所以 30 天内有人看就一直在，没人看就清理掉重新按需渲染。
- 任务去重：同一版本键只有 1 个活跃 job（`enqueueForCard` 检查 queued/processing 的已有 job），避免并发渲染风暴。

### 3.3 查看热路径

```
GET /cards/:id            → open-view（轻量，不读大 JSONB）
GET /api/v1/cards/:id/view → 权限校验 → 缓存 hit → touch 续期 → 302 到静态入口
```

静态流量走对象存储/CDN，API 服务器只做校验 + 302。这对弱服务器非常关键。

### 3.4 私有卡片

- 私有卡片的渲染缓存放私有 bucket，通过受控 API 代理 `GET /api/v1/cards/:id/render-cache/:cacheVersion/*` 流式返回（`routes/cards.ts:293`），带 Range 支持（断点/视频拖动）。这保证私有内容不暴露公网 URL，代价是**私有卡片的静态流量也要过 API 服务器**，弱服务器上私有高频访问会打回服务器。

## 4. 渲染的内容到底是什么——离线化细节

CardtoHTML 导出器（`exporter.ts`）做的是"把 Host 实时渲染的 HTML 离线化"：

1. 调 `card.render(...)` 拿复合卡片 HTML（`offscreen-render` target），render session 目录里有每张基础卡的子文档；
2. 解析子文档里的 `base href`（`file://` 或受控渲染协议）推导卡片资源根；
3. 把资源根整树复制到 `assets/content/`（注意：**图片、视频、音频全部复制**，见 03 节分析）；
4. 把 HTML 里的 `file://`/受控协议资源地址全部改写为相对路径 `./assets/content/...`；
5. 每张基础卡 iframe 子文档外置成 sibling HTML；
6. 包一层导出展示壳层（背景/居中/响应式宽度）；
7. 释放 render session。

## 5. 网页端三层 iframe（感受一下）

```
社区网页 (React)
 └─ HostedPluginSurface iframe
     src = /api/v1/host/plugin-sessions/<id>/entry   ← 服务端注入 base/theme.css/bootstrap
     sandbox="allow-scripts allow-same-origin allow-forms allow-downloads allow-modals allow-popups"
      └─ CardViewer 插件（运行在服务端托管会话里的 React 应用）
          └─ HostedDocumentWindow iframe
              src = documentUrl（渲染缓存入口）
              sandbox="allow-scripts allow-forms"
```

三层 iframe 确实有点深，但每一层的职责是清晰的：
- 最外层 = 社区网页自己的沙箱，加载"服务端托管的 CardViewer 插件会话"；
- 中间层 = CardViewer 应用本身（在 web target 下以 `route` surface 运行）；
- 最内层 = 卡片渲染结果静态 HTML。

## 6. 对「弱服务器」的意义

- ✅ 渲染一次缓存多次：渲染重活只有一次，且并发默认 1（`CARD_RENDER_WORKER_CONCURRENCY=1`）。
- ✅ 高频静态流量由 CDN/对象存储扛，不走 Node。
- ⚠️ 但渲染本身极重（一套 Host + 插件 + 解压 + 复制资源 + 上传目录），单卡渲染的耗时/内存/磁盘都要心里有数。见 05 节。
- ⚠️ 私有卡片静态流量过 API，是弱服务器的一个隐藏压力点。

## 7. 结论

**网页端渲染链路的选择是正确的**——服务器预渲染 + 静态缓存 + CDN 承载，是最适合"弱服务器 + 统一体验"的方案。它牺牲了"浏览器端实时交互渲染"，但换来了一致性、零依赖、低服务器负载。

**值得继续追问的两个点**：
1. 插件版本不进缓存版本键，将来插件升级后的缓存失效策略要设计；
2. 私有卡片的受控代理流量，在弱服务器上要算进容量规划。
