# 07 漏洞清单与建议

> 这一节把所有发现的问题汇总，给出严重程度和建议方向。只给方向，不给实现方案。每条都标了证据位置。

## 图例

- 🔴 高：影响目标体验成立/会压垮弱服务器
- 🟡 中：明显缺陷，影响体验或健壮性
- 🟢 低：打磨项 / 观察项

---

## A. 链路断裂类（直接影响"像图片一样"目标体验）

### A1. 🔴 网页端没有下载卡片的能力
- 现象：无下载接口、无下载按钮；源 .card 存在对象存储但无读取路由。见 04 节。
- 证据：`routes/cards.ts`、`packages/web/src` 无 download；`09-社区平台API契约.md:651` 明示不在契约范围。
- 影响：用户"从网页下载保存完整卡片"的目标完全无法达成。
- 建议方向：新增鉴权下载接口（公开卡流式吐源 .card；私有卡鉴权；`downloadable` 语义入库）；前端详情页/作品卡加下载按钮。

### A2. 🔴 编辑器 ↔ 社区上传没有衔接（无一键发布）
- 现象：编辑引擎内没有任何"发布/上传到社区"入口；官方上传器插件 `Chips-CommunityUploader-Plugin` 存在但没有任何 UI/入口调用它。
- 证据：`EditingEngine` 全仓无 publish/community/upload UI（子代理调查结论）；`ExportPanel.tsx:391` 只走转换插件；上传插件 `community.card.publish` capability 未接入。
- 影响：用户要在"导出文件 → 打开网页 → 拖拽"之间手动搬运，不符合"发微博"心智。
- 建议方向：打通"保存/导出即发布"链路——编辑器内提供发布动作，走上传插件/上传会话正式链路；或至少提供清晰的"导出后去社区上传"指引。

### A3. 🟡 无 remix / 二次创作闭环（下载→本地改→重新上传）
- 现象：没有"下载社区卡片→本地打开→修改→重新上传"的平滑衔接。
- 证据：下载缺失（A1）+ 无重新上传/替换源文件接口（A5）+ 网页无编辑入口。
- 影响：`remixable` 元数据存在但没有对应产品闭环。
- 建议方向：先补齐下载 + 本地打开 .card + 上传，链路自然闭环；remix 的版权/署名规则后续单独设计。

## B. 弱服务器性能风险类

### B1. 🔴 大资源全量过 Node 服务器（预签名直传链路闲置）
- 现象：网页上传 `manifest.resources=[]`，资源整个塞在 .card 里 multipart 过服务器；`chips-card-resources` 预签名直传链路服务端已完整但无人用。
- 证据：`content.ts:208`；`upload-session.service.ts:100`；task023 方案第 7 节。
- 影响：弱服务器带宽/磁盘/内存被大文件上传吃满。
- 建议方向：网页端或官方上传器接入预签名资源直传；大资源客户端直传对象存储，服务器只收壳 + 校验。

### B2. 🔴 渲染结果重复存储 + 重复传输（源文件一份、渲染缓存一份）
- 现象：资源既在 `chips-card-files` 源 .card 里，又在 `chips-card-render-cache/assets/content/` 复制了一份；每次重渲染都要重新复制+上传整棵资源树。
- 证据：`exporter.ts:698-706` copyAssetTree；渲染缓存整体上传 `card-render-cache.service.ts:480`。
- 影响：存储翻倍；500MB 卡渲染时服务器要再搬 500MB。
- 建议方向：对"资源内嵌卡片"模型，评估渲染时资源是否必须复制进缓存，还是可引用源文件/复用资源存储；或对超大资源提供外置 + 引用模式。需产品/架构决策。

### B3. 🟡 私有卡片静态流量全过 Node
- 现象：私有卡 view/cover 缓存走受控 API 代理流式返回，带 Range。
- 证据：`routes/cards.ts:293` streamPrivateCache。
- 影响：私有高频查看时 Node 成为带宽瓶颈。
- 建议方向：评估对象存储短时签名 GET 直连（Node 只签发 URL）。

### B4. 🟡 每次查看都写库续期（touch 写放大）
- 现象：`view`/`cover` 命中缓存即 `touchCache` 写 PostgreSQL（lastAccessedAt/expiresAt）。
- 证据：`card-render-cache.service.ts:237`；task023 方案第 6 节已预留 Redis 合并写方案。
- 影响：热门卡片访问量大时数据库写放大。
- 建议方向：按 task023 预留方案，改 Redis 记录访问时间 + 后台合并 flush。

### B5. 🟡 渲染队列无全局限速（只有并发=1 隐式限速）
- 现象：并发默认 1，但过期卡片同时被访问、或批量上传多卡时，队列会堆积，后端排队。
- 证据：`worker.ts` + `enqueueForCard`（有去重、有优先级，无速率限制）。
- 影响：弱服务器上大量排队渲染时延迟变长，用户等更久。
- 建议方向：队列按 priority 排序消费；后台批量/上传类任务优先级低于用户触发的 miss；可加每任务超时/内存上限。

### B6. 🟢 渲染缓存上传是 Node 逐文件 PUT
- 现象：`uploadDirectory` 并发 8 逐文件上传。
- 证据：`card-render-cache.service.ts:120-142`。
- 建议方向：大文件可考虑对象存储服务端复制/分片；上传失败重试。

## C. 数据与权限语义类

### C1. 🟡 `downloadable` 元数据未入库、未被使用
- 现象：卡片文件规范有 `downloadable`（默认 true），但社区 cards 表无此列，下载权限无从实现。
- 证据：`card.service.ts` create 参数无 downloadable；`metadata.yaml` 规范有该字段。
- 建议方向：上传时解析 metadata 的 downloadable 入库；下载接口按它控制。

### C2. 🟡 网页上传可见性硬编码 public，无私有选项 UI
- 现象：工作区页 `visibility: "public"` 硬编码；API 支持 private 但无 UI。
- 证据：`WorkspacePage.tsx`；`content.ts:198`。
- 影响：用户无法上传"仅自己可见"的卡片。
- 建议方向：上传 UI 提供 公开/私有 选项；后续再扩展 unlisted。

### C3. 🟢 PATCH 可见性有 API 无 UI
- 现象：PATCH /cards/:id 支持改 visibility/roomId，但 ProfilePage 管理态只支持删除。
- 证据：`routes/cards.ts:343`；ProfilePage 调查结论。
- 建议方向：管理态加"设为公开/私有/删除"操作。

### C4. 🟡 无"重新上传/替换源文件"能力，卡片内容一经发布不可改
- 现象：上传会话一次性，无替换源 .card 的接口；卡片内容无法更新。
- 证据：`upload.ts` 无 replace；PATCH 仅 roomId/visibility。
- 影响：创作者无法修正或更新已发布卡片。
- 建议方向：设计"重新提交新版本源 .card"接口（复用上传会话 + 更新 source + 重渲染 + 缓存版本切换）。注意这涉及版本语义（保留旧缓存还是直接覆盖）。

## D. 渲染一致性 / 缓存生命周期类

### D1. 🟡 插件版本不进渲染缓存版本键
- 现象：缓存版本键 = rendererVersion+renderProfile+themeId+locale+sha256，无插件版本；`pluginVersionManifest` 字段预留未参与。
- 证据：`card-render-cache.service.ts:40-52`；task023 方案第 8 节。
- 影响：服务器端插件渲染行为升级后，旧缓存不自动失效。
- 建议方向：将参与渲染的插件版本集纳入版本键（或提供管理后台强制重渲染入口）。

### D2. 🟢 无管理后台强制重渲染/重构建入口
- 现象：API 有 delete/重排队逻辑，但未发现 admin 端"重新渲染某卡" UI。
- 证据：admin 包未细查；`enqueueForCard` 有 `manual` 来源。
- 建议方向：确认/补齐 admin 重渲染入口。

### D3. 🟢 渲染失败态展示
- 现象：网页有 render_error 态文案（`card.errorState`/`card.notReady`），失败原因透出 latestJob.lastError。
- 证据：`cards.ts` render-status；`CardDetailPage.tsx`。
- 建议方向：失败原因对普通用户要友好化（现在是原始错误消息）。

## E. 文档/规范与代码一致性

### E1. 🟡 生态共用文档 09-社区平台API契约 与代码基本一致，但把"下载"等列为不在契约范围——需要在新能力补齐后同步更新
- 证据：`09-社区平台API契约.md:643-653`。
- 建议方向：实现下载/可见性等新能力后，契约文档同步收口。

### E2. 🟢 孤儿 i18n 文案与归档遗留
- 现象：`card.openRawHtml`、`imageViewer.*`、`box.communityCard` 等键在字典里无引用；旧 CardViewerPageShell 已归档。
- 证据：web 调查结论（zh-CN.ts:145-168）。
- 建议方向：清理或复用（不影响功能，仅卫生）。

### E3. 🟡 文档与代码存在口径漂移风险
- 现象：多份文档（设计原稿/共用文档/任务日志）对"资源外置/空壳卡片/上传器"的表述不一致：设计原稿 05 提到空壳/半空壳；文件格式规范 7.1 明确不属于第一版默认；API 契约 7.1 描述上传器做资源外置。而代码当前默认全内嵌。
- 证据：`生态设计原稿/05-卡片文件格式.md:69-83` vs `文件格式规范/01:1316-1331` vs `API契约/09:467-469`。
- 影响：未来实现资源外置时口径不一容易踩坑。
- 建议方向：统一为一份正式口径（全内嵌为第一版默认，外置为可扩展方向），在共用文档收敛。

## F. 其他观察

### F1. 🟢 三层 iframe 的查看链路
- 现象：社区网页 → CardViewer 插件会话 iframe → 卡片渲染缓存 iframe。
- 证据：`HostedPluginSurface` + `HostedDocumentWindow`。
- 建议方向：无功能问题，仅注意安全与调试；sandbox 配置合理（最内层只 allow-scripts allow-forms）。

### F2. 🟢 上传后去向
- 现象：上传成功给"打开结果/前往主页"两个链接。
- 建议方向：可考虑上传完成后自动跳详情页（发帖心智）。

### F3. 🟢 手机查看/上传
- 现象：手机上传可用（点击选择），查看可用（响应式），编辑不可用（与目标一致）。
- 建议方向：在引导文案明确"网页可看可传，编辑需安装软件"。

## G. 优先级建议排序

**第一优先（目标体验成立 + 弱服务器续命）：**
1. A1 网页下载接口 + 按钮（最明确的硬缺口）
2. B1 接上预签名资源直传（弱服务器最大的性能解药）
3. A2 编辑器内一键发布衔接（"发微博"心智核心）

**第二优先（体验闭环 + 稳健性）：**
4. C1 downloadable 入库 + C2 可见性 UI + C3 管理操作（权限语义补齐）
5. B2 渲染缓存资源重复问题（存储/带宽翻倍，需架构决策）
6. A3 remix 闭环（依赖 A1/A5）
7. C4 重新上传/替换源文件能力

**第三优先（打磨与维护）：**
8. B4 touch 合并写、B5 队列限速、B3 私有签名直连
9. D1 插件版本进缓存键、D2 admin 重渲染
10. E 系列文档收敛与清理

## 结语

> 结论一句话：**"查看"已经通了，"上传"动作本身也够简单，但"下载"和"一键发布"两个缺口必须补，弱服务器的大资源与渲染成本必须通过"直传 + 缓存复用 + 队列治理"来化解。** 整个架构方向（服务器预渲染 + 静态缓存 + CDN）是对的，剩下的工作是补齐闭环和治理重活。
