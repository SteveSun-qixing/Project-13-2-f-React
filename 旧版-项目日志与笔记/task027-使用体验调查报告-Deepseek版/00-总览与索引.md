# 薯片卡片全链路使用体验调查报告（Deepseek 版）

> 笔记风格调查报告，非正式文档。按节拆分，一节一个文件。
> 调查日期：2026-08-03
> 调查范围：从「用户在本机编辑卡片 → 保存 .card → 上传社区 → 网页查看 → 网页下载回本地」的完整链路，覆盖 Chips-Host / Chips-EditingEngine / Chips-CardViewer / Chips-CommunityPlatformServer / Chips-ModulePlugin / Chips-SDK。

## 为什么写这份报告

目标体验很朴素：像 Word 或图片一样，用户在自己设备上把卡片做好、保存成一个文件，然后把这个文件丢到社区网页上，大家就能直接在网页上看。想下载的时候，点一下就能把完整卡片下回来。

这个体验看起来很简单，但背后牵扯一整条链路：文件格式、本机保存、上传协议、服务器解析、网页渲染、资源存储、CDN、下载回导、以及一台性能很弱的服务器的生死问题。

这份报告把现状一条条查出来，把每条链路上真实存在的代码/接口/文件位置都标出来，然后对照「像发微博一样简单」的目标体验，找出漏洞和缺口。

## 核心结论速览（先说结论）

1. **查看体验已基本成立**：卡片是「服务器渲染成静态 HTML + 资源拷贝 → 上传对象存储 → 浏览器 iframe 加载」的模式，弱服务器上这一步的架构是对的（一次性渲染、长期缓存、静态由 CDN 扛流量）。
2. **上传体验基本成立但有割裂**：网页拖拽 .card 上传已经能跑通，但上传前要用户先在自己电脑上"导出"出 .card 文件——这一步编辑器和社区之间没有打通，存在"编辑器导出 → 手动拖到网页"的断点。
3. **下载回导完全不成立**：全仓库没有任何下载接口，没有下载按钮，`.card` 源文件存在对象存储里但没有任何公开读取路由。这是目标体验最大的洞。
4. **服务器端渲染 = 把整套 Host + 插件装到了服务器上**：弱服务器上每张卡片渲染都要启动一次完整的 Host 运行时，非常重；并发 1 的 worker 是瓶颈，需要认真设计队列、优先级、超时和限流。
5. **资源大文件策略需要明确**：现在 .card 内部资源在上传时全部整体进入源文件，渲染时又整体复制进渲染缓存，一份视频在对象存储里可能存两遍，弱服务器的存储和带宽是真实压力点。
