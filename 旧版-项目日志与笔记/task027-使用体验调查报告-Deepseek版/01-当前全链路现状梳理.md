# 01 当前全链路现状梳理

> 这一节把「现在真实跑通的链路」从用户触发到最终呈现，一步步写清楚。所有结论都标了文件和行号，方便核对。

## 1. 链路全景

```
[用户本机: Chips-Host + EditingEngine]
   创建编辑卡片（内存 CompositeCard / 工作区目录态）
   ↓ 保存（目录态落盘）
   ↓ 导出（card.pack 打包成 .card ZIP）
   ↓ （手动）把 .card 文件带到网页
[社区网页: 上传拖拽区]
   POST /upload-sessions（建会话）
   POST /upload-sessions/:id/card（multipart 提交 .card）
   ↓
[社区服务器 API] 解析 .card、存元数据、源 .card 存对象存储、入队渲染
   ↓
[后台 Worker] 下载源 .card → 用"服务器端 Host 运行时"渲染成静态 HTML → 上传渲染缓存
   ↓
[网页查看] iframe 加载渲染缓存 HTML / 封面
```

## 2. 第一步：用户在本机编辑与保存

**编辑引擎**（`Chips-EditingEngine`）在 **工作区目录态** 下工作——它不是直接操作 .card 压缩包，而是操作一个解开的目录。

- 创建卡片时建目录结构：`Chips-EditingEngine/src/core/card-initializer.ts:70-71`，文件夹名就叫 `${cardId}.card/`，内含 `.card/metadata.yaml`、`.card/structure.yaml`。
- 保存卡片直接写目录：`Chips-EditingEngine/src/core/card-service.ts` 的 `saveCard`(582) → `queuePersist` → `persistCard`(894)，写 `.card/metadata.yaml`(915)、`.card/cover.html`(916)、`content/<nodeId>.yaml`(925)、资源文件(929-942)、`.card/structure.yaml`(968)。
- 打开卡片从目录反解：`openCard`(482-565)。

## 3. 导出 .card 文件（用户得到“文件”的那一步）

导出面板：`Chips-EditingEngine/src/components/CardSettings/panels/ExportPanel.tsx`

- `client.platform.saveFile`(362) 弹「另存为」对话框
- `saveCard(cardId)`(379) 先把当前内存态落盘成目录态
- `client.card.pack(card.path, finalOutputPath)`(387) —— **这就是 .card 文件正式产出的唯一通道**

Host 侧打包实现：`Chips-Host/packages/card-packer/src/card-packer.ts`
- `pack(cardDir, outputPath)`(98)：暂存 → `packUntilSizeStabilizes`(124，等 `metadata.file_info.total_size` 稳定) → 写回 metadata。
- 必需文件 `REQUIRED_CARD_FILES = ['.card/metadata.yaml', '.card/structure.yaml', '.card/cover.html']`(22)（注意：规范里 cover.html 是必需的）。

## 4. .card 文件长什么样

卡片文件本质是 **ZIP 压缩包，零压缩率（store 模式）**，扩展名 `.card`。改了后缀 zip 就能解开看。

内部：
```
card.card
├─ .card/                    # 核心配置
│  ├─ metadata.yaml          # 卡片元数据（ID/名称/主题/tags/cover_ratio...）
│  ├─ structure.yaml         # 结构（基础卡片列表 + manifest 资源清单）
│  ├─ cover.html             # 封面 HTML
│  └─ cardcover/             # 封面资源（可选，图片封面上传时才有）
├─ content/                  # 每个基础卡片一个 {10位62进制ID}.yaml
│  ├─ a1B2c3D4e5.yaml
│  └─ ...
└─ 资源文件直接放根目录         video.mp4 / image.jpg / audio.mp3 ...
```

真实样例：
- `ProductFinishedProductTestingSpace/富文本基础卡片.card`（16.5MB）
- `ProductFinishedProductTestingSpace/视频音乐卡片.card`
- 解开的目录态样例：`.chips-host-dev/WyuXzrM5PP.card/`

## 5. 上传：网页端拖拽

网页端唯一上传入口：`Chips-CommunityPlatformServer/packages/web/src/pages/WorkspacePage.tsx`

- 支持多文件拖拽/点选：`components/UploadDropzone.tsx`（`accept=".card,.box"`，`multiple`，支持 drop）
- 上传并发 3：`WorkspacePage.tsx:15 WORKSPACE_UPLOAD_CONCURRENCY = 3`
- 按 `.card`/`.box` 分类入队：`handleFiles`(167-196)

卡片上传两次请求（`api/content.ts` `cardsApi.uploadCard` 187-218）：
1. `POST /api/v1/upload-sessions`（JSON，带 contentType="card"、fileName、visibility、client）
2. `POST /api/v1/upload-sessions/:uploadId/card`（multipart，字段 `file`=.card，`manifest`=JSON 字符串）：web 端这里 `manifest.resources` **恒为 `[]`**（`content.ts:208`），也就是说**网页上传不走「外置资源直传」链路**，是把资源整个塞在 .card 里整体交上去。

## 6. 服务器收到 .card 后

服务器：`Chips-CommunityPlatformServer/packages/server/src/routes/upload.ts`

流程 `receiveProcessedCardUpload`(316) → `persistProcessedCard`(384)：
1. `inspectCardSourceFile` 解包 .card、读 metadata/structure/封面、算 SHA256（`utils/card-file.ts`）
2. `CardService.create` 建卡片记录（status 先 pending），表 `cards`
3. 源 .card 上传到对象存储公开/私有 bucket：`chips-card-files` 的 `{userId}/{cardId}/source.card`，记 `sourceCardBucket/Key/SHA256`（`card.service.ts:420-438`）
4. 入队两个渲染任务：`viewRenderProfile('community-web')`(priority 100) + `coverRenderProfile('community-cover')`(priority 90)（`upload.ts:440-451`）

然后 API 返回 202。

## 4. 后台渲染（服务器端渲染，关键）

Worker：`packages/server/src/worker.ts`

- 从 Redis 队列消费（`CardRenderCacheService.takeNextJobId`，BRPOP）
- 处理 `renderViewJob`(card-render-cache.service.ts:411)：下载源 .card → 调用 `hostIntegration.convertCardToHtml` → 得到 HTML 目录 → 上传到渲染缓存 bucket → 更新库。

**重点：这个转换不是随便写的，是正儿八经启动了整套 Chips Host 运行时。**

`services/host-integration.ts`：
- `init()` 里 `new HeadlessHostShell({...})`(239)，start 后**把整套插件装进服务器进程**：
  - app 插件：CardViewer、PhotoViewer、MusicPlayer、VideoPlayer、BookReader（`resolvePluginSources` 589-610）
  - card 插件：richtext/image/webpage/music/video/score/book/hyperlink 的 BCP（595-603）
  - layout 插件：grid-BLP
  - theme：Chips-default
  - module：CardtoHTML、FileConversion
- 然后 `convertCardToHtml`(297) 调 module capability `converter.file.convert`（FileConversion 插件把它编排到 `converter.card.to-html` = CardtoHTML 模块）。

于是服务器端 = 一台跑着完整 Chips Host 的数据。渲染一结束，工作目录的临时代码（`ccps-card-render-*`）被 rm 掉。

### 渲染产物结构（CardtoHTML 模块产出，见 `Chips-ModulePlugin/Chips-CardtoHTML-Plugin/技术文档/01-卡片转HTML模块技术方案.md`）

```
<output>/
├─ index.html                    # 复合卡片壳层 + iframe[nodes] 引用
├─ <node-id>.html                # 每张基础卡片一个 sibling HTML（离线）
├─ assets/
│  ├─ content/                   # 卡片资源根（图片/视频/音频，includeAssets=true 时）
│  └─ theme/                     # Host 主题 CSS 引用的文件资源
└─ conversion-manifest.json (可选)
```

资源会被导出器 `rewrite HtmlAssetUrls` 重写成相对路径 `./assets/content/...`，并**整树复制**资源（`exporter.ts:698-706 copyAssetTree`）。

## 5. 网页查看

自定义渲染的**不实时**，网页拿到的是上面渲染好的静态缓存。

- 详情页取状态 → 轮询到 `cache_ready`：`pages/CardDetailPage.tsx`
- 渲染到底是怎么回事：
  - `GET /api/v1/cards/:cardId/view`（`routes/cards.ts:226`）：命中缓存 → touch 续期 → **302 重定向**到渲染缓存入口（公开=S3 公共 URL / 私有=受控 API 代理）；未命中 → 202 + 入队 + `websocket轮询 render-status`。
  - 公开卡片的 view/cover 缓存放在公开 bucket（`chips-card-render-cache` / `chips-card-cover-cache`），走 CDN/对象存储直连。
  - 私有卡片走受控代理 `GET /api/v1/cards/:cardId/render-cache/:cacheVersion/*`（需要鉴权，从私有 bucket 流式返回）。
- 网页端真正看到卡片是通过 **Double iframe**：
  - 外层：`components/HostedPluginSurface` 加载服务端托管的 CardViewer 插件会话 html
  - 内层：CardViewer 的 `HostedDocumentWindow` 里 iframe 加载 `documentUrl`（即渲染缓存入口），`sandbox="allow-scripts allow-forms"`

## 6. 封面

渲染封面缓存在 `routes/cards.ts` 同样 302 到 `cover-cache` 或私有代理。列表页 `WorkGrid` 里的卡片封面是 `<iframe src={coverUrl} sandbox="allow-scripts" loading="lazy">`。

## 7. 箱子（box）：暂时不在本报告主线，但顺带记录

- box 上传走的是**旧接口** `POST /api/v1/upload/box`（multipart），上传成功即 success，**不做渲染轮询**（`WorkspacePage.tsx`）。
- box 现在只写 metadata/structure 摘要到库，不上传源 .box；和正式箱子规范没有完全收口（有工单 097 覆盖）。

## 中篇小结：链路现状一句话

> **编辑→导出→上传→服务器用整套 Host 渲染成静态 HTML→CDN 缓存→网页 iframe 查看** 已经跑通了。但**下载回导**、**编辑边界**、**上传前体验**三个环节有真实缺口，见各节。
