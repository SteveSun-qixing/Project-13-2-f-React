# 03 资源文件处理与存储分析

> 用户问题：资源是用户上传到服务器，再让服务器传到 CDN/图床，还是用户直接传图床？资源文件怎么保存，下载时怎么再整合？这一节把资源的来龙去脉讲透。

## 1. 资源从哪里进卡片：本机编辑时

用户在编辑器里加图片/视频/音频时，资源被**复制进卡片目录态根目录**（`persistCard` 里写资源文件，`EditingEngine/src/core/card-service.ts:929-942`；`file-service.ts` / `resource-service.ts` 管理）。规范要求：内部资源路径相对于卡片根目录，不得写回 blob:/data:/绝对路径（文件格式规范第 7.2 节）。

所以 `.card` 文件 = 配置 + 资源**全部内嵌**在一个 ZIP 里。这是「全填充卡片」模式，也是现在正式链路的默认模式（规范里"空壳/半空壳卡片"已明确不属于第一版默认保存链路，见文件格式规范 7.1）。

## 2. 资源怎么上传：现在两条路，但网页只走一条

### 路径 A：网页上传（当前实际在用）——资源包在 .card 里整体传

- 网页端 `manifest.resources = []`（`content.ts:208`），**不拆资源**，整个 .card 一次 multipart 上传（上限 `MAX_CARD_SIZE_MB=500`）。
- 服务器 `inspectCardSourceFile` 解包读取（包括看所有资源文件列表），源 .card 存 `chips-card-files`。
- **没有把任何资源单独拆出来**存到 `chips-card-resources`。

### 路径 B：上传会话 + 预签名资源直传（服务端能力已完整，但网页/官方客户端没接）

服务端有完整的一套：`POST /api/v1/upload-sessions/:id/resources/presign`（`upload-session.service.ts:100` presignResources）→ 客户端用预签名 URL **直接 PUT 到对象存储** → 提交 .card 时服务器 `verifyResources`（headObject 校验大小/`chips-sha256` 元数据）→ `assertResourcesMatchCard`（校验 .card 不再包含这些资源、且全部被引用）。

- **这套就是为「大资源不经过弱服务器」设计的正式链路**（task023 方案第 7 节：大资源直传对象存储，.card 只提交处理后的壳）。
- 但网页端没用它，官方上传器插件（`Chips-CommunityUploader-Plugin`）存在但**编辑引擎没有调用入口**，也没有 Host 侧 UI 触发它。

### 现状结论

**现在是"资源全塞进 .card 一起过服务器"**。500MB 的 .card 要完整经过 Node 服务器（multipart 写入磁盘 → 解包 → 重新上传对象存储 → Worker 再下载 → 渲染 → 再上传），弱服务器上这是最大的带宽/IO 压力点。预签名直传链路是现成的解药，但没接上。

## 3. 资源怎么存储：对象存储（S3 兼容）里的 bucket 布局

`storage/buckets.ts`：

| bucket | 用途 | 读权限 |
|---|---|---|
| `chips-card-files` | **永久**源 .card（`{userId}/{cardId}/source.card`） | 私有 |
| `chips-card-resources` | 外置资源（预签名直传目标，当前网页未使用） | 公开 |
| `chips-card-render-cache` | 完整查看静态缓存 `{cardId}/{cacheVersion}/` | 公开 |
| `chips-card-render-cache-private` | 私有卡片查看缓存 | 私有 |
| `chips-card-cover-cache` | 封面静态缓存 | 公开 |
| `chips-card-cover-cache-private` | 私有卡片封面缓存 | 私有 |
| `chips-avatars` / `chips-covers` | 头像/封面杂项 | 公开 |

存储实现：`storage/s3.ts`，S3 兼容（开发 MinIO、生产可切七牛云，`S3_FORCE_PATH_STYLE`、自定义 `S3_PUBLIC_URL` 指向 `file.chipscard.space`，nginx `/cdn/` 跳转）。

## 4. 资源怎么从网页加载：被复制进渲染缓存，随 HTML 一起

关键点：**网页上卡片里的资源，是"渲染时被复制到渲染缓存 assets/content/ 里"的那一份，不是源 .card 里的那一份。**

`CardtoHTML` 导出器：
- 解析卡片资源根 → `copyAssetTree` 整树复制到 `assets/content/`（`exporter.ts:698-706`）
- HTML 里的资源地址全部改写为 `./assets/content/...` 相对路径

所以浏览器加载 `index.html` 时，图片/视频/音频都以相对路径从**同一个渲染缓存目录**（对象存储/CDN）加载。一张卡片的查看流量 = 渲染缓存的流量，全部由 CDN 扛。

### 结果：一份资源可能存两份

```
chips-card-files/{userId}/{cardId}/source.card   ← 永久源（里面含资源）
chips-card-render-cache/{cardId}/{version}/assets/content/xxx.mp4  ← 渲染缓存（资源副本）
```

对于 500MB 的视频卡片：源里一份 + 缓存里一份 = 1GB 存储，且每次重新渲染（缓存过期/换主题/插件升级）都要把视频再复制+再上传一遍。**这是弱服务器存储/带宽的显性成本**，要纳入设计。

## 5. CDN / 图床的真实位置

- 没有"用户直接上传到第三方图床"这一步。对象存储本身就是公开读 + 自定义 HTTPS 域名（`file.chipscard.space`），承担 CDN 的职能；若要真 CDN 加速，对象存储前再挂一层即可。
- nginx 是 API/网页的反代 + `/cdn/` 旧入口跳转，**不做静态缓存回源缓存**——静态流量直接命中对象存储公开域名，不经过 Node，也不经过 nginx 服务器本身。

## 6. 私有卡片的资源访问

- 私有卡片的渲染缓存走受控 API 代理（`/api/v1/cards/:id/render-cache/:version/*`），图片/视频也从这个代理出，带 Range 支持。所有静态流量过 Node，弱服务器压力点。

## 7. 与「下载回导」的关系

如果要下载完整卡片：**源 .card 就是完整卡片**（资源全在里面）。所以下载链路不需要"重新整合"——只要把 `chips-card-files` 里的源文件吐出来即可。详见 04 节。

## 8. 资源处理的关键问题清单（详见 07 节）

1. 大资源全量过服务器，预签名直传链路闲置 → 弱服务器带宽瓶颈；
2. 资源在源 .card 和渲染缓存里各存一份 → 存储翻倍、重渲染时重复复制上传；
3. 渲染缓存上传用 Node 流式逐文件 PUT（`CARD_RENDER_CACHE_UPLOAD_CONCURRENCY=8`），大资源多时耗时；
4. 无 CDN 层面缓存（如 Range/缓存头在对象存储直连下的行为要确认）；
5. 私有卡片静态流量过 API。
