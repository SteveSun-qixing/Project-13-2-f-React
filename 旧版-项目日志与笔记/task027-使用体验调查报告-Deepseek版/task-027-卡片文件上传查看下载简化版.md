# 卡片文件上传、网页查看、完整下载：简化方案

## 目标体验

用户在本地软件制作并保存 .card，像上传图片一样发到社区。别人直接在网页查看，需要保存或继续编辑时再下载 .card。网页只查看，编辑仍用本地软件。

## 推荐链路

    本地保存 .card
      -> 直传对象存储
      -> 后台生成静态网页
      -> CardViewer Web 查看
      -> 下载完整 .card

技术上建议这样分工：

- 用户设备负责检查卡片和上传文件；
- 对象存储保存文件并承担上传、查看、下载流量；
- Worker 异步生成一次网页缓存；
- CDN 提供公开网页和资源；
- 弱服务器只负责登录、权限、文件登记、任务排队和状态查询。

不要让浏览器完整解析 .card，也不要在用户每次打开网页时实时渲染。

## 文件保存

最好保存两份：

- original.card：包含全部资源，用于下载、备份和离线编辑；
- publish.card：资源可以外置，用于生成网页。

当前 source.card 可能是资源已经外置的发布处理包，不能直接当成“完整离线卡片”下载。网页 HTML 也只是查看缓存，不能反向拼装 .card。

## 当前主要漏洞

1. 没有正式的 .card 下载 API 和网页下载按钮；
2. 原始完整包与发布处理包没有分开；
3. 私有卡片资源可能进入公开存储；
4. 网页上传让整个 .card 经过 API，对弱服务器不友好；
5. CardViewer Web、资源查看器和安全沙箱仍需完整验证。

前两项是最关键的体验缺口，已登记在工单121。

## 用户交互

用户只需要看到：上传中、检查中、网页生成中、已发布、生成失败可重试、下载卡片。

用户不需要理解资源外置、对象存储、CDN、缓存和签名 URL。

## 实施顺序

1. 分开保存 original.card 和 publish.card；
2. 让 .card 通过预签名地址直传对象存储；
3. 增加下载 API、权限判断和下载按钮；
4. 补齐私有资源方案；
5. 完善生成状态、失败重试和移动端查看。

## 结论

这个体验可以实现。最合适的方案是：本地软件负责创作，对象存储负责文件，Worker 负责一次性网页生成，浏览器负责查看，社区服务器只负责权限和调度。
