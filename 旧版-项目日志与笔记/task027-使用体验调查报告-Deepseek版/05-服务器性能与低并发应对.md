# 05 服务器性能与低并发应对

> 用户问题：服务器性能非常弱，如何尽可能满足低性能要求、低并发？这一节把当前架构里"谁是重活、谁扛流量、哪里会压垮弱服务器"拆开讲。

## 1. 先说结论

当前架构的整体设计对弱服务器是**友好的**：重计算（渲染）只做一次并缓存，高频静态流量全部交给 CDN/对象存储，Node 服务器在热路径上只做「鉴权 + 302」。真正的压力点集中在**上传、渲染、私有卡片代理**三块。逐项分析。

## 2. 好消息：热路径（查看）不重

```
GET /cards/:id           → open-view：轻量查询（不读大 JSONB）
GET /api/v1/cards/:id/view → 鉴权 → 缓存 hit → touch → 302
```

- 热门卡片的静态流量 = 对象存储/CDN 直接扛，不经过 Node。
- 每次命中缓存会 `touchCache`（写库续期）。**潜在隐患**：热门卡片每看一次写一次数据库（lastAccessedAt/expiresAt），弱服务器 + 高访问会有写放大。task023 方案已预留"Redis 合并写 + 后台 flush"的升级路径，但**当前实现是直接写库**（`card-render-cache.service.ts:237 touchCache`）。
- 302 重定向到静态 URL 之前，`open-view` 会做一次缓存查询（`findReadyCache`），这个查询带 `sourceCardSha256` 等条件，有索引支撑。

## 3. 压力点一：上传（大文件过 Node）

现状（网页路径）：整个 .card（最大 500MB）multipart 进 Node → 写临时文件 → 解包 → 重新上传对象存储。弱服务器：
- 带宽上限决定上传速度；
- 临时文件占用磁盘（`ccps-upload-*`，用后删除）；
- `inspectCardSourceFile` 会解包整个 ZIP（`card-unpack.ts`），大卡解包 CPU/内存开销大。

**预签名直传链路是现成的解决方案但没接**（见 03 节路径 B）：大资源客户端直接 PUT 对象存储，服务器只收壳 + 校验，彻底绕开 Node 带宽。对弱服务器是刚需级别的重要优化。

## 4. 压力点二：渲染（最重的单次操作）

### 4.1 渲染本身极重

`host-integration.ts` 里，Worker 进程要：
1. `HeadlessHostShell.start()`：启动完整 Host 运行时；
2. 安装全部插件（CardViewer + 8 个基础卡片 BCP + 布局 + 主题 + 2 个转换模块），逐个 `plugin.install` + `plugin.enable`；
3. 对每张卡：下载源 .card → 解包 → `card.render(offscreen-render)` → 导出器解析子文档/复制资源树/改写 URL → 生成目录 → **逐文件上传到对象存储**（并发 `CARD_RENDER_CACHE_UPLOAD_CONCURRENCY=8`）。

这意味着**每渲染一张卡，都要跑一遍完整的 Host + 插件**。虽然 Host 是常驻的（init 一次），但每张卡的内容解析/资源复制/上传都是实打实的工作。弱服务器上：
- **CPU**：yaml 解析、HTML 生成、模板渲染；
- **内存**：Host 运行时 + 插件 + 大资源文件流；
- **磁盘**：`/tmp` 下解包目录 + 渲染目录 + 上传临时，大卡几百 MB；
- **网络**：渲染缓存整体上传 = 卡片体积再传一遍。

### 4.2 并发默认 1，是保护也是瓶颈

- `CARD_RENDER_WORKER_CONCURRENCY=1`：Worker 一次只处理一个 job（`worker.ts` 循环单线程，多 worker loop 由该值控制，默认 1）。
- 好处：不会并发把服务器打爆；坏处：**上传队列长时，后面的卡片要等**。网页端上传后靠轮询 render-status，等待期间用户看到"准备中"。

### 4.3 队列入队时机与去重

- 上传时入队 view+cover 两个 job；
- `view`/`cover` 未命中时也会触发入队（`view_miss`/`cover_miss`，优先级 10/20，高于上传任务 100/90 的数值——注意：**priority 数值越小越优先**，这里 miss 用 10/20 更优先是对的）；
- 同版本键去重：已有 queued/processing job 时不会重复建（`enqueueForCard`），避免风暴；
- 失败重试 `maxAttempts=2`，超时 job 30 分钟会被 requeue（`requeueStaleProcessingJobs`）。

### 4.4 缓存过期 → 按需重渲染

缓存过期（最后访问 + 30 天）后，再被访问会重新入队渲染。弱服务器上，如果一堆过期卡片同时被访问（比如老卡片突然上热门），会一下子排很多渲染 job。有去重 + 优先级保护，但**没有全局渲染限速**（只有并发=1 的隐式限速）。可以考虑渲染队列按 priority 排序，或后台批量渲染优先级低于用户触发。

## 5. 压力点三：私有卡片的静态流量

- 私有卡片的 view/cover 缓存走受控 API 代理（`/api/v1/cards/:id/render-cache/:version/*`），**每个字节都过 Node**。
- 带 Range 支持（视频拖动、断点续传），但大文件流经 Node 会占用连接和内存。
- 弱服务器上私有高频查看是真实压力点；备选方案是短时签名 URL（对象存储预签名 GET）让客户端直连私有对象，Node 只签发 URL。

## 6. 数据库/Redis 相关

- Redis：渲染队列 + 锁 + 认证状态。低并发下负载很小，但 **Redis 挂了队列就断**——队列持久化依赖其 rdb（docker-compose 里 `--save 60 1`）。
- PostgreSQL：热路径查询有索引建议（task023 方案第 9 节），当前 `cards` 表是否有全部索引需要核对，但低并发问题不大。
- 写放大：touchCache 每次访问写库（见 2 节）。

## 7. 给弱服务器的建议方向（详见 07 节汇总）

1. **接上预签名资源直传**：大资源不经过 Node（最优先）。
2. **渲染结果直接用对象存储/S3 的拷贝能力**（如 `COPY` 或服务器端复制）代替 Node 逐文件下载+上传：现在 Worker 是「下载源 .card → 本地解包 → 渲染 → 本地目录 → 上传」，如果源 .card 里资源已经在对象存储有一份，渲染时可以考虑复用/引用而不是重新复制（需要小心与"资源内嵌 .card"模型的矛盾，见 03 节第 4 点）。
3. **渲染缓存上传可考虑分段/分片 + 更高并发**，或异步化。
4. **touchCache 改 Redis 合并写**。
5. **私有卡片可考虑短时签名直连**。
6. **渲染队列限速 + 优先级排序**（用户触发的 miss 优先于后台/上传）。
7. **上传大小上限、每用户并发、会话 TTL 已有**（`MAX_CARD_SIZE_MB`、`UPLOAD_SESSION_TTL_MINUTES`、上传并发3），可继续收紧。

## 8. 容量粗略估算（一张 500MB 视频卡片）

```
上传：500MB 过 Node（网页路径）→ 如果直传：0 过 Node
源文件：500MB 存 chips-card-files
渲染：解包 500MB + 渲染 + 复制 500MB 到缓存 + 上传 500MB 到对象存储
缓存：500MB 存 chips-card-render-cache
```

弱服务器上，单张 500MB 卡的渲染过程会短暂吃掉服务器全部磁盘 IO 和大量带宽。这是设计时必须正视的数字。
