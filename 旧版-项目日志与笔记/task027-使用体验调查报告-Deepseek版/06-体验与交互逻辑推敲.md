# 06 体验与交互逻辑推敲

> 这一节对照用户想要的目标体验——「像发微博/推特一样简单」——逐条推敲每个交互环节。不写方案，只把交互逻辑想清楚、把断点找出来。

## 1. 目标体验拆解

```
1. 在自己电脑/手机上编辑制作卡片          ← 本地软件（编辑器）负责
2. 保存为卡片文件 (.card)                ← 本地软件负责
3. 把卡片文件上传到社区服务器              ← 用户操作：上传
4. 直接在网页上查看卡片                    ← 网页查看
5. 从网页下载保存完整卡片                  ← 网页下载
6. 查看体验在网页端完整可还原              ← 渲染一致性
7. 编辑仍需要安装软件                      ← 编辑边界：网页只读
```

用户想要的感受是：「一个文件，传上去，大家能看，还能下回来。」就像贴一张图、发一条微博。

## 2. 逐环节推敲

### 环节 1+2：制作与保存

- 现状：编辑器「保存」是目录态落盘，**导出 .card 才得到文件**。用户心智里"保存"和"导出成文件"是两件事，这正是和 Word/图片体验的第一个差一点——Word 的"保存"就是文件的保存。
- 推敲：对普通用户，"我在编辑器里做完了、随手保存" → 应该天然就有 .card 文件。现在的编辑器工作区目录态 + 导出面板是"工程向"的模型，用户要理解「导出」概念。理想是保存即产出 .card（或至少"发布/分享"一键同时导出）。
- **断点①**：保存 ≠ 得到文件，用户要多一步"导出"。

### 环节 3：上传

- 现状：网页拖拽 .card 上传，已支持多文件、并发 3、进度条、失败提示。这是当前唯一正式入口。
- 但用户必须先"导出"出文件，再拖进浏览器。中间隔着文件系统。
- 推敲：微博式体验是"选图→发"，这里对应"选 .card 文件→传"。**对上传这个动作本身，网页拖拽已经够简单**。真正的问题是：本地编辑器和社区上传是两个产品，中间没有任何衔接（编辑器里没有"发布到社区"按钮，上传插件存在但没接 UI）。
- **断点②**：编辑 → 上传之间的衔接断层。用户要"导出文件 + 打开网页 + 拖拽"，而非编辑器内一键发布。

### 环节 4：网页查看

- 现状：服务器渲染成静态 HTML，网页 iframe 加载。多基础卡片类型、视频、音乐、图片、富文本都能看（取决于渲染器支持）。封面在列表页用 iframe 显示。
- 推敲：
  - 查看一致性：服务器和本地用同一套 Host 渲染，一致性有基础。但**插件版本差异**会带来渲染差异（见 02 节 3.2）。
  - 未就绪态：上传后要等渲染，网页显示"准备中"并轮询。微博式体验希望"传完马上能看"，但弱服务器下渲染要时间。需要设计好的中间态（比如先显示封面 + 标题，正文渐进出现）。
  - 查看体验细节：详情页三层 iframe；视频资源走渲染缓存（支持 Range 拖动）；音乐卡片点击资源会走 resource.open（打开到独立播放器视图）。
- **观察③**：查看能力是完整的，但"渲染等待"和"三层 iframe"是体验上的两个观感问题（后者用户无感知，前者有感知）。

### 环节 5：网页下载

- 现状：完全不存在（见 04 节）。
- 推敲：这是目标体验里**最明确的硬缺口**。微博/图床天然支持下载，这里卡片也必须支持。由于资源全内嵌，下载=源 .card 原样给出，简单。
- **断点④**：无下载接口 + 无下载按钮。

### 环节 6：编辑边界

- 现状：网页端没有任何编辑入口；服务端 PATCH 只能改 roomId/visibility，不能改内容；也没有"重新上传替换源文件"的接口（上传会话是一次性的，源文件已固化）。
- 推敲：用户期望"网页只读，编辑回本地软件"。但有一个体验细节要想清楚：**用户想在别人卡片基础上改**（二次创作 remixable），怎么办？现在没有"把社区卡片下载下来→本地打开→改→再传回去"的平滑衔接，全靠手动下载 + 本地打开 + 手动上传。
- **断点⑤**：没有 remix 流程闭环（下载→本地编辑→重新上传）。这也是"像图片一样"体验的一个大缺口——图片可以另存再改，卡片因为需要安装软件，门槛更高。

### 环节 7：跨设备（手机）

- 用户提到"电脑/手机"。手机上编辑目前不支持（编辑需要安装软件，Host 是桌面端）。手机上**查看**呢？
  - 网页查看理论可行（渲染缓存是静态 HTML），但要看移动端适配（导出壳层有响应式宽度，`exporter.ts` 里 `.chips-export-stage` 移动端全宽）。
  - 手机上传：网页拖拽在手机上不可用（没有文件拖拽），需要上传按钮/文件选择器。当前 `UploadDropzone` 也有点击选择（`<input type=file>`），手机可用。
  - **观察⑥**：手机场景的"上传"和"查看"基本可行，"编辑"明确不可行（与目标一致）。

## 3. 五个断点总结（重要）

| # | 断点 | 影响 | 程度 |
|---|---|---|---|
| ① | 保存 ≠ 得到 .card 文件，用户要多一步"导出" | 心智摩擦 | 中 |
| ② | 编辑器 ↔ 社区上传没有衔接，无一键发布 | 不符合"发微博"心智 | 高 |
| ③ | 上传后渲染等待，中间态体验 | 观感，可优化 | 低-中 |
| ④ | 网页无下载接口和按钮 | 目标体验硬缺口 | 高 |
| ⑤ | 无 remix 闭环（下载→本地改→重新上传） | 二次创作体验断层 | 中-高 |
| ⑥ | 手机编辑不可行（与目标一致，但需在文案/指引中明确） | 预期管理 | 低 |

## 4. "像发微博一样简单"还差什么（软件层心智）

微博式的"简单"背后是：
1. 发帖 = 一个入口、一次操作；
2. 别人的内容点开即看、即存；
3. 不需要理解文件格式、协议、目录。

对薯片卡片：
- 上传=一次拖拽，已经接近"一个入口"（但缺编辑器内的一键发布来达到"一次操作"）；
- 查看=点开即看，已成立（但缺渲染中的即时反馈优化）；
- 下载=需要补齐（缺口④）；
- 用户不需要懂 .card 格式，这部分已做到（上传拖拽文件即可）。

**最大的一块缺口其实是 ②④⑤ 三点组成的"闭环"**：从"本地制作"到"社区分享"到"社区回本地"的整条路径，目前只有"上传→查看"是通的，前后两个方向都没接全。

## 5. 交互细节补充推敲

- **上传后去向**：当前上传成功给「打开结果 / 前往主页」两个链接。微博式体验通常是"上传后直接进详情页"。可推敲。
- **可见性/权限**：网页上传硬编码 `visibility: public`（工作区页）。用户没有"私有/仅自己可见"的 UI（API 支持 private，但工作区写死 public）。对"发微博"心智，通常默认公开 + 可选私有，现在的缺口是**没有私有选项 UI**。
- **下载权限**：`metadata.yaml` 有 `downloadable`，但库表没同步、网页也没用。下载按钮出现条件要想清楚。
- **删除**：已有（ProfilePage 管理态批量删除），删除会清源文件和渲染缓存（`CardService.delete`）。
- **改可见性**：API 有 PATCH visibility，但无 UI（ProfilePage 只支持删除）。用户把公开卡改私有或反之，目前做不到。
- **重新上传/更新版本**：无能力。卡片一经上传内容不可改。这对"持续编辑发布"的创作流是限制，但和"第一版像图片一样"的目标不算冲突（图片上传后也不能改）。可列为后续。

## 6. 小结

> 目标体验在"查看"环节已经基本达标；"上传"环节动作本身简单，但缺编辑器内一键发布的衔接；"下载"环节完全缺失；"编辑"边界与"remix 闭环"需要产品决策。最优先补的是 ④下载、②一键发布衔接、⑤remix 闭环，其次是 ①保存即文件、③上传后即时反馈、以及私有/可见性的 UI。
