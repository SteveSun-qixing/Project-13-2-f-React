## B-1 SwiftUI 哲学（声明式、语义化、自适应的平台抽象）

**（Declarative, Semantic, Adaptive Platform Abstraction）**

如果只挑一个词，叫 平台抽象（Platform Abstraction）；如果从苹果文档语境，叫 自适应 UI / Adaptive UI；从架构角度，叫 控制反转 + 接口与实现分离。

SwiftUI 的哲学不是单一原则，而是一组相互支撑的技术与设计信念。它把界面开发从"命令式地创建、配置、同步、绘制和适配视图"，转为"声明意图、持有状态、组合语义、交给系统实现"。其核心可以这样阐述：

- **声明式与意图优先**：开发者描述在给定状态下界面应该具有的结构、层次、语义和关系，不描述创建、布局、绘制、更新、销毁的具体过程。框架负责把声明转换为实际渲染树，并在状态变化时计算差异、执行更新。
- **状态是唯一事实来源，视图是状态的函数**：界面不是被手动修改出来的，而是状态在某一时刻的投影。状态变化是界面变化的根本驱动力。框架追踪依赖、重新求值、比较差异，并以最小代价更新界面。开发者不再维护"视图与数据一致"这件事。
- **单向数据流与显式依赖**：状态向下传递，事件向上反馈。绑定、观察、环境等机制形成显式依赖图。数据流方向明确，状态所有权清晰，减少隐式耦合、竞态和不可追踪的副作用。
- **组合优于继承，值语义优先**：视图是轻量、可组合、可替换的声明单元。复杂界面由简单视图组合、修饰、包装而成。修饰符是变换，不是属性设置。值类型带来可预测性、隔离性、可测试性和更低的状态共享风险。
- **语义化 API 与契约稳定**：API 表达角色、意图、层级、关系、材质、颜色、字体、间距等语义，不暴露具体像素、坐标和平台控件实现。开发者依赖的是接口契约，不是某一种实现细节。系统可以在契约不变的前提下替换实现。
- **自适应与平台托管**：布局、外观、行为由系统结合设备形态、窗口尺寸、方向、尺寸类、安全区、输入方式、环境特征、可访问性、本地化、主题等因素决定。开发者声明关系与意图，系统计算几何、位置、样式和适配结果。
- **控制反转与关注点分离**：框架控制生命周期、渲染、布局、动画、事件分发和资源管理；开发者控制状态与业务意图。内容、状态、布局、外观、动画、平台适配、可访问性彼此分离。框架调用开发者，而不是开发者手动驱动框架的每一步。
- **外观、行为与实现分离**：标准控件、导航、标签、工具栏、材质、转场和视觉语言由系统设计系统提供。系统更新可以替换外观与行为的实现，而不改变应用依赖的接口。动态链接与稳定的运行时契约使旧应用也能获得新平台行为。自定义越多，自动适配越少；语义化标准越多，平台托管越多。
- **动画与交互内建**：动画与状态变化绑定。开发者声明状态目标，系统负责插值、时间、曲线、转场、共享元素和中断处理。交互连续性和视觉一致性由框架统一保证，而不是由每个应用各自实现。
- **类型安全与声明式 DSL**：Swift 的类型系统、结果构建器、属性包装器、不透明返回类型、泛型、协议、并发和观察机制，使声明式语法保持编译期检查、可组合、可扩展，同时隐藏复杂类型和实现细节。
- **跨平台与原生体验**：同一套声明可以在不同平台和设备形态下由系统适配为符合平台惯例的原生体验。可访问性、本地化、动态字体、主题等作为环境语义参与，不是事后补丁。
- **即时反馈与迭代**：预览、实时重载和编译期检查缩短反馈循环，使声明式开发可探索、可验证、可快速调整。开发者在描述意图的同时，能立即看到系统如何解释这些意图。
- **性能与一致性由框架保证**：框架通过依赖追踪、差异计算、按需更新和渲染优化，减少手动同步带来的错误与性能负担。开发者不再维护视图树一致性，框架保证状态与界面一致。

**哲学本质**：应用表达"应该是什么"和"为什么"，系统负责"怎么做"和"长什么样"。平台适配、外观实现、布局计算、动画过程和运行时行为被收回到系统层。应用依赖接口而非实现，依赖语义而非像素，依赖状态而非命令。因此，系统演进时可以统一替换实现，而符合语义化、自适应和平台托管原则的应用无需重写。

**总结**：意图优先、状态驱动、组合构建、语义表达、控制反转、平台托管、契约稳定、系统实现。它不只是一个 UI 框架，而是苹果平台抽象哲学在界面层的体现。

拆开看，它是好几种技术设计的组合：

| 维度 | 技术名称 | 含义 |
|---|---|---|
| UI 范式 | 声明式 UI | 开发者描述"界面是什么"，不描述"怎么画" |
| API 设计 | 语义化 API | 用角色、意图表达，如 .primary、.regularMaterial，而不是具体颜色和坐标 |
| 布局 | 自适应布局 / 响应式布局 | 用 Size Class、Safe Area、Trait 等让系统决定位置和尺寸 |
| 架构 | 控制反转 IoC | 框架调用你的代码，而不是你手动控制所有流程 |
| 架构 | 关注点分离 | 内容、状态、表现、平台适配分开 |
| 渲染 | 系统控件 + 设计系统 | 导航栏、标签栏、按钮、材质由系统统一绘制 |
| 视觉 | 主题化 / Skinning | 液态玻璃这类外观由系统替换，App 使用语义材质即可跟随 |
| 运行时 | 动态链接 + ABI 稳定 | App 运行时调用系统框架，系统更新替换实现，旧 App 仍能工作 |
| 设计理念 | 平台一致性 / 原生体验 | 遵循 HIG，系统保证不同设备形态下的统一体验 |

苹果能做到"系统一更新，很多 App 自动变"，本质不是远程改代码，而是：**开发者依赖的是接口契约，不是具体实现。系统更新替换了框架实现，但接口没变，所以 App 自动获得新行为。**

例如：TabView 是语义："我要一个标签容器"，不是"在底部画一个栏"；`.regularMaterial` 是语义："我要一种常规材质"，不是"画一层半透明灰色"；Auto Layout / SwiftUI 布局是语义："放在安全区底部"，不是 y = 700。

这些都属于 面向意图编程（Intent-based Programming）和 平台抽象。

**一句话总结**：这叫"把平台适配和外观实现收进系统框架，开发者只描述意图"的设计。核心术语是：声明式 UI、语义化 API、自适应布局、控制反转、动态链接与平台抽象。

## B-2 DeepSeek Harness（一切皆插件、自进化的 Agent 运行时）

DeepSeek Harness 的设计哲学、架构特点与技术方法，共同指向一个核心目标：构建一个能够自我进化（Self-Evolving）的 Agent 运行时。其核心主张是 "一切皆插件"（Everything is a Plugin），旨在将传统 Harness 的固定结构彻底解耦，实现极致的灵活性与可扩展性。

**设计哲学：一切皆插件**

设计哲学是对传统 Agent 框架的一次根本性重塑。它不满足于仅将工具作为插件，而是将模型适配器、工具注册表、会话日志，乃至 Agent 主循环（Agent Loop）本身全部设计为可插拔的组件。这意味着框架中不存在一个"不可修改的特权核心"，整个 Harness 就是由插件拼装而成，为 Agent 在运行过程中生成、替换自己的组件（即"自进化"）奠定了基础。

这一哲学的背后，是解决一个被忽视的根本问题：动态组合的可靠性。如果 Agent 要修改自己的运行时，那么修改后必须能够安全地"撤销"和"重组"。为此，DeepSeek 与北京大学合作发表了论文《一套处理时空可组合性的编程范式》，其核心正是 Cordis 元框架，它解决了两个关键难题：

- **时间可组合性（Temporal Composability）**：确保插件卸载时，其产生的所有副作用（如事件监听、资源占用）能被完整撤销，如同"后悔药"一般。
- **空间可组合性（Spatial Composability）**：解决组件间的动态依赖问题，当某个服务被替换或消失时，依赖它的组件能自动协调生命周期。

**架构设计特点：基于 Cordis 的插件树**

架构建立在 Cordis 插件系统之上，形成了一棵可动态配置的"插件树"。

*分层装配架构*：运行实例并非写死的模块，而是通过 Profile、Bundle 和 Patch 逐层合成：

- Profile：具名部署组合（如 Web、Headless），声明需要加载的 Bundle。
- Bundle：可分发的配置层，包含配置行和对应的插件代码，提供通用能力（模型、工具、会话等）。
- Patch：允许在部署时替换、插入或修改配置行，实现无需 Fork 源码的灵活定制。

*三大核心机制*：

- **可逆副作用（Reversible Effects）**：这是 Cordis 的纪律性要求。插件对系统的任何修改（服务注册、事件监听）都会被记录，卸载时可逐层撤销，解决了传统插件框架常见的状态残留与"系统变脏"问题。
- **服务/事件协作（Service/Event Collaboration）**：插件间通过声明式的服务进行能力依赖，通过类型化事件进行跨插件协作和策略拦截。所有生命周期事件都是可监听的扩展点，为干预 Agent 行为提供了明确入口。
- **作用域与预设复用（Scope & Preset）**：通过 Scope 作用域隔离，同一进程内可以运行多个拥有不同人格、提示词和工具集的 Agent。Agent 的插件挂载在自己的 agent.ctx 中，实现了能力的精细化隔离与复用。

**技术设计方法：面向长任务的可靠性**

- **可替换的 Loop 机制**：基础 Agent Loop / Goal Round / Ralph Run（多个独立子 Agent 轮次，不继承父级对话历史，通过共享工作区和结构化交接报告传递信息）。
- **事件驱动的持久化状态**：会话状态通过仅追加的、类型化的 SessionEvent 日志来管理，这是系统唯一的真源。事件溯源（Event Sourcing）设计使会话完全可回放，为长任务审计、调试和从崩溃中恢复提供基础。
- **按需暴露的工具 Schema**：模型理解的"外部世界"完全由 Harness 暴露的工具 Schema 定义；可按需动态暴露工具，而非一次性加载全部工具，有助于在长任务中控制上下文长度和保持模型焦点。
- **分层权限控制与多维验证**：分层权限控制（如"自动批准"结合 LLM 分类器作为工具调用关口）；多维验证体系，明确将"测试全部通过且应用正常启动"等客观标准作为任务完成的依据，而非仅依赖 Agent 的自我声明，以解决"验收失真"问题。

**总结**：DeepSeek Harness 的设计是一场围绕 "动态可组合性" 的深度工程实践。它以 Cordis 元框架为基石，通过可逆副作用和作用域隔离确保了"一切皆插件"架构的可靠性；再以事件溯源日志和可替换的 Loop 机制等方法，将这种架构优势转化为面向长任务的实际工程能力。其最终愿景，是让 Agent 能够像飞机在空中更换零件一样，在不停止服务的情况下，安全地修改和进化自身的运行时。
