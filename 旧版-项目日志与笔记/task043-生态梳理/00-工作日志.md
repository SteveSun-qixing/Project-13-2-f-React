### 1.4 初步理解（待与所有者校准）

**生态定位**：
薯片平台是一个运行在操作系统之上的**软件级统一平台**，目标是在 Windows / macOS / Linux / Android / iOS 五端只写一份代码，承载所有领域软件（笔记、Office、浏览器、开发工具、Agent、媒体创作、游戏等）。对标"像微信小程序那样，但是是跨全平台的、全领域的软件平台"。

**核心理念**：
- 让复杂内容像打开图片一样简单（双击 `.card` 即开）
- 一切皆插件、一切皆卡片
- 平台提供运行时，开发者只写业务
- 内容属于用户，信息脱离程序保存

**架构哲学（三大支柱）**：
1. **厚而无感**：底层无所不包（API/模块/库/框架/服务全在平台），上层无所限制（插件自由组合），用户感受无形（不感知底层复杂度）
2. **平台抽象**：声明式（描述意图而非过程）、语义化（用角色而非像素）、自适应（平台托管适配）
3. **动态可组合**：一切皆插件、可逆副作用（卸载完全撤销）、作用域隔离（多实例互不影响）、事件溯源（状态可回放）

**技术架构现状**：
- 十二层架构：PAL → Host Kernel → Host Services → Plugin Runtime → Bridge Transport → Runtime Client → UI Hooks → Declarative UI → Unified Rendering → Component Headless → Theme Runtime → App/Page Domain
- task030 后：L10/L11（无头组件库 + 主题系统）废弃，插件侧视觉统一由 antd（唯一组件库）+ `@chips/ui` 共享层承接（单一苹果风格）
- task030 后：多语言系统废弃，界面文案一律简体中文直写
- task037 提出：跨端目标为 Rust 核心 + 五端壳（可移植核心 + 多壳），但 task037 最终判断是"当前仓库不存在可安装到 Android 的 APK 产生链路，处于契约预研阶段而非 Android 可运行阶段"

**内容体系**：
基础卡片（原子内容） → 复合卡片（`.card` 文件） → 箱子（`.box` 文件，卡片容器 + 布局插件） → 社区（网络平台）

**产品族**：
- 薯片主机（唯一底座，Electron/未来跨端）
- 卡片编辑引擎（做卡片的工具）
- 卡片查看器（消费卡片内容）
- 资源管理器（标签文件系统）
- 生态设置面板（插件管理 + 运行治理）
- 社区服务器（存储 + 平台）
- 各种应用插件（视频播放器、图片查看器、电子书阅读器等）

### 2.2 DeepSeek Harness 与 Cordis 哲学研究（2026-09-19 00:08）

已读取 DeepSeek Harness 完整文档。以下是核心哲学提炼：

**Cordis 元框架的核心能力**：

1. **时间可组合性（Temporal Composability）**：
   - 插件卸载时，所有副作用（事件监听、服务注册、资源占用）完整撤销
   - 像"后悔药"一样，系统不会"变脏"

2. **空间可组合性（Spatial Composability）**：
   - 组件间动态依赖自动协调
   - 某服务被替换/消失时，依赖它的组件自动调整生命周期

3. **可逆副作用（Reversible Effects）**：
   - 所有注册都有对应的 disposer
   - 插件的任何修改都被记录，卸载时逐层撤销

4. **服务/事件协作**：
   - 插件通过声明式"服务"进行能力依赖
   - 通过类型化事件进行跨插件协作
   - 5 种事件分发模式：emit / waterfall / parallel / serial / bail

5. **作用域隔离（Scope）**：
   - 同一进程可运行多个隔离实例（不同配置、不同能力集）
   - 每个实例有自己的 `ctx`，能力精细化隔离

**对薯片生态的启示**：

您说的"原子化模块"问题，Cordis 提供了一个非常好的解决方案：

**当前问题**：
- 模块插件是"大应用级别"，太重
- 无法灵活组合
- 依赖关系难管理

**Cordis 解决方案**：
- 每个能力都是独立"服务"（Service）
- 通过 `ctx.<key>` 访问（如 `ctx.tools`、`ctx.llm`、`ctx.fs`）
- 通过 `inject: ['tools', 'fs']` 声明依赖
- 框架自动处理加载顺序、生命周期、依赖协调
- 卸载时自动撤销所有副作用

**应用到薯片生态**：

```typescript
// 图片处理模块的 Cordis 风格
class ImageProcessingService extends Service {
  // 声明依赖：需要文件系统和资源访问
  static inject = ['file', 'resource']
  
  // 注册能力
  apply(ctx) {
    // 注册解码能力
    ctx.imageProcessing.registerDecoder('jpg', ...)
    ctx.imageProcessing.registerDecoder('png', ...)
    
    // 注册变换能力
    ctx.imageProcessing.registerTransform('resize', ...)
    ctx.imageProcessing.registerTransform('crop', ...)
    
    // 注册滤镜能力
    ctx.imageProcessing.registerFilter('blur', ...)
    
    // 卸载时自动撤销所有注册
  }
}

// 另一个插件使用图片处理能力
class PhotoViewerPlugin extends Service {
  static inject = ['imageProcessing'] // 声明依赖
  
  apply(ctx) {
    // 直接使用 ctx.imageProcessing.decode(...)
    // 框架保证 imageProcessing 先加载
  }
}
```

**核心优势**：
1. 模块可以很细（一个算法）也可以很粗（一套功能），通过服务注册灵活组合
2. 依赖关系显式声明，框架自动解决加载顺序
3. 卸载干净，无状态残留
4. 同一模块可以有多个实现，通过替换提供方改变整个系统行为

## 【核心决策待确认】插件分类的全新方案

基于对 Cordis 哲学的理解和您对卡片/箱子统一链路的澄清，我提出以下插件分类方案：

### 方案：基于 Cordis 的三层插件体系

**第一层：应用插件（Application Plugin）**
- 定义：拥有独立窗口的完整应用
- 特征：完整的用户交互界面、独立的业务逻辑、可独立启动
- 例子：编辑引擎、查看器、资源管理器、设置面板
- 对应 Cordis：是"消费者"角色，使用各种服务

**第二层：能力插件（Capability Plugin）**
- 定义：向平台注册能力的服务提供方
- 特征：通过 `ctx.<key>` 暴露服务、可被其他插件依赖、可替换实现
- 子类：
  - **渲染能力插件**：渲染各种文档类型（卡片内容、箱子布局、未来的表格、幻灯片...）
  - **处理能力插件**：提供原子化处理能力（图像、视频、音频、文档转换...）
  - **基础设施插件**：提供基础服务（存储、网络、认证、日志...）
- 对应 Cordis：是"服务提供方"角色

**第三层：扩展插件（Extension Plugin）**
- 定义：监听事件、拦截流程、扩展行为的策略插件
- 特征：通过事件系统工作、可插可拔、影响全局行为
- 例子：权限策略、审计日志、性能监控、主题定制
- 对应 Cordis：是"事件监听者"角色

### 关键变化：

**1. 卡片插件和布局插件统一为"渲染能力插件"**

### 问题 1：系统原生 WebView 的一致性问题

这是一个非常关键的问题。让我诚实地回答：

**系统原生 WebView 的现实**：

❌ **不能完全保证一致性**。原因：
- macOS WebKit、Windows WebView2 (Chromium)、Linux WebKitGTK 是**不同的渲染引擎**
- 即使都是基于 WebKit/Chromium，版本也不同
- CSS 渲染细节、JavaScript API 支持会有差异
- 字体渲染、滚动行为、动画效果都可能不同

**Electron 的优势**：
✅ 打包同一个 Chromium 版本，跨平台完全一致
✅ 开发时看到的就是用户看到的

**这是一个重大权衡**：
- Tauri：体积小（~5MB）、性能好、但渲染有差异
- Electron：体积大（~150MB）、资源重、但渲染一致

### 重新评估：桌面端应该选 Electron

基于您的关切点（融合吸收 Electron 项目、界面一致性），我改变推荐：

**桌面端（macOS/Windows/Linux）**：
- **核心**：Rust（性能关键路径、跨平台逻辑）
- **壳**：Electron（渲染一致性、生态兼容性）
- **架构**：Rust 核心以 Node.js Native Module 形式集成到 Electron

**移动端（Android/iOS）**：
- 单独平台，后续设计

**这样的优势**：
- ✅ 界面完全一致（同一个 Chromium）
- ✅ Electron 项目可以直接集成
- ✅ 开发体验好（调试工具、生态成熟）

- ❌ 体积较大（但桌面端可接受）

### 问题 2：Bridge 重新设计

您说现在的 Bridge 设计不够好。让我分析问题并提出新方案。

**当前 Bridge 的问题**（推测）：

可能的问题点：
1. **不够类型安全**：JavaScript 调用 Rust/Node 时缺少类型检查
2. **不够语义化**：API 设计不够清晰，难以理解
3. **性能问题**：IPC 开销大，序列化/反序列化慢
4. **扩展性差**：新增能力需要修改 Bridge 核心
5. **调试困难**：跨进程调用难以追踪

**我的新 Bridge 设计提案**：

#### 核心理念：**能力导向的声明式 Bridge**

不再是"调用函数"的思维，而是"请求能力"的思维。

```typescript
// 传统 Bridge（不好的设计）
window.chips.invoke('file', 'read', { path: '/a.txt' })

// 新 Bridge（能力导向）
const capability = await chips.request('file:read')
const content = await capability.execute({ path: '/a.txt' })
```

#### 完整设计：

```typescript
// ============ Bridge 核心接口 ============

interface ChipsBridge {
  // 1. 能力请求（带权限检查）
  request<T extends Capability>(
    capabilityId: string,
    options?: RequestOptions
  ): Promise<T>
  
  // 2. 事件订阅（类型化）
  subscribe<E extends Event>(
    eventId: string,
    handler: EventHandler<E>
  ): Subscription
  
  // 3. 资源访问（统一句柄）
  resource(uri: string): ResourceHandle
  
  // 4. 上下文访问（插件隔离）
  context(): PluginContext
}

// ============ 能力接口 ============

// 所有能力都实现这个接口
interface Capability {
  readonly id: string
  readonly permissions: Permission[]
  readonly schema: Schema  // 参数和返回值的 JSON Schema
  
  execute(params: unknown): Promise<unknown>
}

// 例子：文件读取能力
interface FileReadCapability extends Capability {
  id: 'file:read'
  permissions: ['file:read']
  
  execute(params: {
    path: string,
    encoding?: 'utf8' | 'binary'
  }): Promise<string | Uint8Array>
}

// ============ 资源句柄 ============

interface ResourceHandle {
  readonly uri: string
  readonly type: ResourceType
  
  read(): Promise<Uint8Array>
  stream(): ReadableStream
  metadata(): Promise<ResourceMetadata>
  dispose(): void
}

// ============ 使用示例 ============

// 插件请求能力
class PhotoViewerPlugin {
  async init() {
    // 请求需要的能力
    this.fileRead = await chips.request<FileReadCapability>('file:read')
    this.imageDecoder = await chips.request('image:decode')
    
    // 订阅事件
    this.sub = chips.subscribe('file:changed', this.onFileChanged)
  }
  
  async openPhoto(path: string) {
    // 使用能力
    const data = await this.fileRead.execute({ path })
    const image = await this.imageDecoder.execute({ data })
    this.display(image)
  }
}
```

#### 新 Bridge 的优势：

1. **类型安全**：
   - TypeScript 定义所有能力接口
   - 编译期检查参数和返回值

2. **权限清晰**：
   - 每个能力显式声明需要的权限
   - 用户可以看到插件请求了什么能力

3. **可扩展**：
   - 新增能力只需实现 `Capability` 接口
   - 不需要修改 Bridge 核心

4. **可调试**：
   - 每个能力请求都有 trace
   - 可以监控哪个插件使用了哪些能力

5. **性能优化**：
   - 能力句柄可以缓存
   - 资源访问可以流式传输
   - 批量操作可以优化

#### Rust 侧实现：

```rust
// Cordis 服务提供能力
trait ChipsCapability: Send + Sync {
    fn id(&self) -> &str;
    fn permissions(&self) -> &[Permission];
    fn schema(&self) -> &Schema;
    
    async fn execute(
        &self,
        params: Value,
        context: &ExecutionContext
    ) -> Result<Value>;
}

// 能力注册
impl CapabilityRegistry {
    fn register<C: ChipsCapability>(&mut self, capability: C) {
        self.capabilities.insert(capability.id(), Box::new(capability));
    }
}

// Bridge 转发
#[neon::export]
async fn chips_request_capability(
    capability_id: String,
    plugin_id: String,
    cx: FunctionContext
) -> Result<JsObject> {
    // 1. 检查插件权限
    let plugin = plugin_registry.get(&plugin_id)?;
    let capability = capability_registry.get(&capability_id)?;
    
    if !plugin.has_permissions(capability.permissions()) {
        return Err(PermissionDenied);
    }
    
    // 2. 返回能力句柄（包含 execute 方法）
    Ok(create_capability_handle(cx, capability))
}
```
