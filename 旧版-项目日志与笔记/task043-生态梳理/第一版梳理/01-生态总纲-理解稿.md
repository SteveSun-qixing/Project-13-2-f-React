## 0. 一句话

**薯片生态是一个可安装到所有主流平台的统一软件底座与插件生态：核心与插件只写一份代码，承载所有领域的软件；开发者只写业务，用户只装一个环境，内容属于用户。**

---

## 1. 生态定位

### 1.1 它是什么

一个与操作系统同层的"软件环境"。

- 操作系统负责驱动硬件；薯片负责承载软件与内容。
- 原生系统往下退，薯片往上长——用户在薯片上生活。
- 它不生产某一款软件，它生产"软件的土壤"。

### 1.2 三个视角

| 视角 | 薯片是什么 |
|---|---|
| 对操作系统 | 只有一个软件 |
| 对用户 | 一个会生长的环境：装一个，得到整个软件世界；内容随处可开、可分享、可组合 |
| 对开发者 | 一份代码、五端运行；只写业务、不碰平台；开箱即合规 |

### 1.3 类比与超越

微信小程序证明了"一个主程序 + 无数插件 + 一套能力 + 一套规范"的模型可行。
薯片把同一个模型，从一家公司的花园，扩展为**开放、可安装、全平台、全品类的软件环境**：

- 宿主不是聊天软件，是系统本身；
- 能力不是某公司的 API，是全平台的公共能力池；
- 范围不只是轻量工具，而是 Office、浏览器、图像创作、游戏在内的全量软件；
- 平台不只是微信自己的平台，而是所有主流操作系统。

### 1.4 边界（不是什么）

- 不是卡片工具生态——卡片/箱子是它的原生内容格式，不是它的全部。
- 不是兼容层——它提供能力，不只是抹平差异。
- 不是桌面项目——桌面/启动器是未来可能承载的产品之一，按平台单独立项制定需求。
- 不只是框架——框架解决"怎么开发"，它解决"软件怎么存在、怎么运行、怎么分发、怎么跨端"。

### 1.5 命名

"Host"是当前称呼，之后可能更换更合适的词。本文暂用"底层系统 / 底座"。

## 2. 发展方向与目标

### 2.1 方向

> 做一个可安装到所有主流平台的统一软件底座与插件生态——核心和插件都只写一份代码，承载所有领域的软件；开发者只写业务，用户只装一个环境。

展开为"两个统一 + 一个开放"：

- **统一底座**：软件共通能力（接口、模块、库、框架、服务）在底层沉淀一次。
- **统一形态**：所有软件都是插件——安装、组合、替换、分发。
- **开放生态**：官方与第三方同构；软件与内容自由流动、生长。

### 2.2 目标（六条）

1. **一份代码，五端运行。** Windows / macOS / Linux / Android / iOS。
2. **能力在底层沉淀完全。** 窗口与表面、文档与文件、媒体与图形、网络与存储、权限与更新——大部分软件会用到的东西，底座全有。
3. **承载全领域软件。** 从笔记到 Office、浏览器、开发工具、Agent、媒体创作、游戏，全部能跑，且无需往底座"打补丁"。
4. **软件即插件。** 安装、启停、组合、替换、市场分发；官方与第三方同规范、同工具、同门禁。
5. **体验统一。** 一套视觉、一套交互、一套文案、一套无障碍标准。
6. **内容属于用户。** 原生格式与通用文档平等共存；文件化、无数据库、可迁移。

### 2.3 验收标准（五条）

- 新软件里，**重复造轮子的代码趋近于零**——只剩业务。
- 新软件**第一天就五端可用**，而不是"先做一个平台"。
- **陌生开发者零源码依赖**，只靠文档、SDK、脚手架就能做出高质量插件。
- **跨领域压力测试全部通关**：Office、浏览器、Agent、视频剪辑、游戏……每个都不需要改底座。
- **内容穿越软件**：软件更替之后，用户数据仍然完整可用。

## 3. 哲学理念

### 3.1 总纲

> **对外：声明式、语义化、自适应的平台抽象。**
> **对内：一切皆插件、副作用可逆、作用域隔离、事件溯源的动态可组合。**
> **感受：厚而无感——底无所不包，用无所限制。**

### 3.2 支柱一：平台抽象

核心命题：**应用表达"应该是什么"，系统负责"怎么做"。** 由此带来三个效果——软件依赖接口而非实现、语义而非像素、状态而非命令；系统演进时可以统一替换实现，而软件无需重写。

- **意图优先（声明式）**：描述"是什么"，不描述"怎么画、怎么活"。
- **语义化**：API 表达角色与意图（打开文档、请求全屏、常规材质），不暴露像素、坐标、平台控件与具体库。
- **自适应**：布局、外观、行为由系统结合设备形态、窗口、输入方式、环境特征决定；开发者声明关系与意图。
- **控制反转**：框架调用开发者，而不是开发者驱动框架每一步；生命周期、渲染、布局、动画、资源管理由平台托管。
- **契约稳定**：软件依赖接口契约；系统更新替换实现而不变契约——**系统一更新，所有软件自动获得新行为**。
- **状态驱动**：状态是唯一事实来源，界面是状态的函数；单向数据流、显式依赖。
- **组合构建**：复杂由简单组合、修饰、包装而成；修饰是变换而非属性设置。

### 3.3 支柱二：动态可组合

核心命题：**生态里不存在不可替换的部件。** 一切由插件拼装，"飞机在空中换零件"。

- **一切皆插件**：软件、能力、界面、服务，全部以同一套插件机制存在；官方与第三方同构。
- **无特权核心**：特权收敛到不可再小的程度（路由、注册、事件、生命周期、权限），其余全部以可装、可换、可撤的机制存在。
- **副作用可逆**：插件对系统的任何修改（监听、注册、资源、句柄）都被记录并在卸载时完整撤销——"可逆"是框架纪律，不是实现者的自觉。
- **作用域隔离**：同一进程内可有多个作用域（工作区、文档、会话、Agent、账号），各自挂载插件与权限——"多个人格共处一室"。
- **事件溯源**：会话状态以只追加的类型化事件日志为唯一真源；可回放、可审计、可崩溃恢复。
- **组合优于特判**：遇到新需求先问"这是哪些基元的新组合"，而不是"往底座加一个特例"。

### 3.4 厚而无感

核心命题：**底层无所不包，使用无所限制，感受无形无感。** 它管的全是"底"，从不碰"上"。

- 管能力，不管创作；管默认，不管选择；管结构，不管行为；管治理，不管审批。
- **每一条限制都被底座翻译成一条能力或一个默认**：
  - "不许直接读文件" → "给你文档句柄与受控 URL"
  - "必须做权限校验" → "权限是身份的一部分，机制自动裁决"
  - "必须遵循视觉规范" → "组件默认就长对了"
  - "必须处理跨端差异" → "API 语义统一，差异已被吸收"
  - "必须做安全隔离" → "隔离就是默认的运行环境"
- 三个检验：新人零内部知识可开发；用户说不出"我在用平台"；新软件类型永远不需要向平台"申请支持"。
- 裁判问题：每设计一个机制，问"它是在铺路，还是在立规矩？" 立规矩的，重新设计成铺路的。

### 3.5 价值观原则（四组）

**A. 价值——为什么做**

1. **简单至上**：用户侧一切必须简单到理所当然；复杂全部藏在底层；一切设计争议由"是否让用户更简单"裁决。
2. **用户主权**：内容属于用户——文件、开放格式、无数据库、无账号绑架；随时能带走，所以敢留下。
3. **长期主义**：为十年设计；内容的寿命长于软件的寿命；不留临时实现、不留兼容包袱。

**B. 结构——怎么组织**

4. **厚底薄上**：共通能力沉到底层，上层只写业务；底越厚，上越薄，生态越省力。
5. **一切皆插件**：所有软件以插件形态存在；生态的生长机制。
6. **边界清晰**：内容与软件分离、前端与后端分离、逻辑与视觉分离。
7. **统一即品质**：一个底座、一套组件、一套视觉、一套交互、一种语言；用户看不到"拼接感"。
8. **开放与可替换**：没有不可替换的部件；标准公开、谁都可以实现、谁都可以离开。

**C. 秩序——怎么稳定**

9. **隔离与最小权限**：默认无权、按需申请、运行审计；安全是默认，不是补丁。
10. **鲁棒优先**：失败被隔离、有回退、可观测；系统默认假设"会出错"，并因此更可信。
11. **契约优先**：接口、事件、清单、格式、行为全部契约化；先立约、再实现。
12. **单一事实源**：每个事实只有一处权威；重复就是漂移的开始。
13. **平台无关**：跨端是天性而非补丁；核心不认识任何平台。

**D. 进化——怎么变强**

14. **复利复用**：每个能力全生态只实现一次；有成熟开源就用开源。
15. **组合优于特判**：底座只变厚于基元，不变胖于特例。
16. **体验即完成**：完整状态、键盘等价、动效克制、文案说人话、无障碍不妥协——这些是"完成"的定义，不是"优化项"。
17. **运行时托管为默认，自带为例外**：平台提供运行时；有特殊需要的软件可以自带库与代码——允许，但受底座契约约束，并自行负责一致性。

## 4. 产品思路

1. **一个软件，多个入口。** 产品族是"一个软件的不同入口"，不是一组软件。
2. **薄壳应用。** 绝大多数产品是薄壳：智能在底座，产品负责业务编排与体验。
3. **独立入口体验。** 每个插件都可以有自己的快捷方式、窗口与身份，用户感知像独立软件，实际共享底座。
4. **数据皆文件。** 不用数据库；数据是用户可携带、可备份、可用任何工具打开的文件。
5. **一后端多前端。** 同一能力可以有多种前端实现；前端自由组合。
6. **官方与第三方同构。** 同规范、同工具、同门禁；"官方"是质量背书，不是特权通道。
7. **两个内容世界平等。** 原生内容（卡片/箱子）与外来文档（docx、psd、代码仓库等）平等共存：前者是"视图与编排"的格式，后者必须原样存在、外部工具可开。
8. **自带为例外。** 游戏、专业工具、浏览器这类有特殊需要的软件，允许自带引擎与代码。
9. **产品族五类**：
   - 生产力：卡片编辑引擎（做卡片的工具）、笔记、Office 衍生
   - 消费：卡片查看器族（卡片/图片/视频/音乐/阅读/万能文件）
   - 治理：生态设置面板、安装器、资源管理器
   - 网络：社区客户端、社区平台服务器、个人服务器、社区网页版
   - 工具链：SDK、脚手架、命令行、软件制作器（愿景）

## 5. 架构设计

### 5.1 总原则：逻辑架构是宪法，物理实现可换届

所有架构陈述必须区分三层，不可混写：

1. **逻辑不变式**（稳定）：分层职责、依赖方向、唯一通道、契约体系。
2. **技术选型**（可复审）：语言、框架、组件库、Shell 技术。
3. **实现状态**（瞬时）：此刻做到哪一步，只作注记。

### 5.2 结构：微内核 + 厚服务 + 唯一通道

- **内核（薄）**：中心路由、服务注册、事件总线、生命周期、权限判定、调用上下文、熔断、审计。内核是唯一"知道全局"的组件。
- **服务域（厚）**：内容与文件、运行治理、系统环境、体验基础——每个动作契约化（输入/输出/权限/超时/错误/幂等）。
- **Bridge（唯一门）**：插件访问系统的唯一通道；对外形状与物理传输解耦。
- **调用链条**：应用 → 类型客户端（SDK/Hooks）→ Transport → 内核 → 服务 → 平台层。任何绕过都是违宪。

### 5.3 平台抽象的实施

- **语义化能力 API**：插件只看到"打开文档、请求全屏、提交作业、新建会话"这样的意图。
- **自适应**：响应式单位（cpx，屏幕宽度归一化）、断点、安全区、输入方式、能力快照。
- **平台托管**：外观、布局、动效、无障碍由平台接管；插件声明意图。
- **诚实降级**：能力差异可查询、可降级；不假装处处一样，不空实现假成功。

### 5.4 动态可组合的实施

- 插件注册与卸载的全生命周期治理；副作用可逆。
- 作用域模型覆盖工作区、文档、会话、账号。
- 会话事件日志为唯一真源（可回放、可恢复、可审计）。
- **能力生长路径三条**：模块插件（可移植）、官方能力包（平台签名、独立仓库）、壳扩展（平台集成）。
- **基元方向**（待细化）：表面、文档、作业、流、句柄、权限——新软件由基元组合，而非平台开特例。

### 5.5 平台运行时

- **三块构成**：表现运行时（组件、令牌、布局、动效）＋ 能力运行时（服务与模块）＋ 契约运行时（SDK、类型、桥接客户端、错误模型）。
- **默认托管，自带为例外**：平台提供运行时；特殊软件自带。
- **语义 API 是契约，具体库是实现**：插件依赖语义，不依赖某个库；实现可替换。
- **版本治理与兼容承诺**：第一版之后"契约稳定"是平台第一纪律。
- **效果**：系统一更新，所有软件自动获得新行为——"写一次"从空间（五端）扩展到时间（跨版本）。

### 5.6 跨端五律

1. **逻辑可移植，绑定只发生在壳里。**
2. **能力必须诚实**：可查询、可降级、正式 unsupported。
3. **原生能力只属于平台**（签名内置），插件只带可移植载荷（JS/WASM）。
4. **契约单源、多语言生成、金标验证**：绝不手抄多份。
5. **信任与性能分级**：从不受信内容到平台原生能力，明确分级与准入——同一个框架承载计算器与视频剪辑。

### 5.7 隔离与安全

- 默认无权、按需声明、运行审计。
- 身份来自物理通道，不信任载荷自报。
- 资源句柄化、受控 URL；不向插件暴露绝对路径。
- 工作区隔离：用户态与开发态严格分离。
- 准入流水线：清单校验 → 来源判定 → 启动握手 → 权限快照 → 沙箱注入 → 运行时审计 → 会话清理。

## 6. 内容体系

### 6.1 四级内容

基础卡片（原子）→ 复合卡片（可保存的最小单位）→ 箱子（引用、摘要与布局的容器）→ 社区（网络公共层）。

### 6.2 四个分离

1. 实体与引用分离；2. 数据与代码分离；3. 布局与数据分离；4. 内容与软件分离。

### 6.3 关键立场

- 卡片/箱子是**原生内容格式**（视图与编排），不是生态全部。
- 外来文档**平等共存**：可被查看、编辑、管理、分享，但不改装、不封装。
- **标签替代目录**：内容是"资源池 + 筛选视图"。
- **内容属于用户**：开放格式、无数据库、可迁移。

## 7. 体验设计

- **统一即品质**：一套视觉、一套交互、一套文案、一套无障碍标准；所有软件像同一个产品。
- **高级感**：世界级对标；克制用色、完整细节、动效服务内容。
- **量化标准**：即刻反馈 150–250ms；动效 180–240ms（iOS 曲线）；三态完整；错误永远有"下一步"；键盘与鼠标完全等价；`prefers-reduced-motion` 是红线。
- **语义化样式**：设计令牌 + 语义样式；外观可被平台替换。
- **响应式单位**：cpx（屏幕宽度归一化为固定份数，运行时换算）。
- **文案**：简体中文直写；用户语言优先（技术细节进日志）；术语统一；不用 emoji。
- **跨版本**：平台更新视觉语言，所有软件自动焕新。

---

## 8. 生态与治理

- **开发者体验**：只写业务；SDK、规范、脚手架开箱合规；预览与工具链缩短反馈循环。
- **生态机制**：应用市场、社区、官方与第三方同构。
- **质量治理**：客观验收（测试全绿 + 真实启动），不靠自我声明；契约校验、质量门禁。
- **文档治理**：单一事实源；写文档前先核代码；发现缺口先开工单；归档不删除。
- **工程纪律**：无临时/简化/占位实现；无 TODO；第一版前不背兼容包袱。
- **协作纪律**：分支与提交由用户管理。
