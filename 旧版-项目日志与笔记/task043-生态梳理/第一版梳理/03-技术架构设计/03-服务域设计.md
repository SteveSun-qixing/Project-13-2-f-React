# 03 · 服务域设计

> 【不变式】服务域是平台能力的公共池——"厚底层"的实体。任何多个插件都可能重复实现的能力，都必须沉淀到服务域或模块能力，而不是留给应用。

---

## 1. 定位

- 服务域对外表现为一组 `namespace.action` 路由（如 `document.session.open`）；
- 服务域是**能力的归口**，不是可执行体的划分：一个服务域可由多个实现组成，也可随平台版本重写；
- 服务域之间**不得直接调用**，一律经内核路由；
- 服务域不认识插件，只提供能力。

## 2. 服务设计规则

1. **每动作契约化**：输入 schema、输出 schema、权限、超时、幂等、错误码、流式声明，缺一不可。
2. **句柄优先**：跨边界传递资源/文档时使用句柄与租约，不暴露路径（见 04 篇"句柄"）。
3. **写事务化**：写操作必须原子提交、可恢复、可撤销；不得出现半写状态。
4. **失败归一**：一切失败返回 `StandardError`；不得抛出底层异常。
5. **能力诚实**：依赖平台能力时先查快照；不支持时返回正式错误，禁止空实现。
6. **无状态优先**：有状态服务必须声明状态归属与恢复机制（事件溯源或持久化）。
7. **最小权限**：服务动作的权限按动作粒度声明，不按服务粒度粗放授权。

## 3. 服务域清单

### A. 文档与内容域

| 服务域 | 职责 |
|---|---|
| `document` | **通用文档会话**：打开/读取/写入/保存/观察/转换/对比；工作副本与原子提交 |
| `content` | 生态原生内容：卡片、箱子的解析、打包、元数据、语义操作 |
| `resource` | 资源解析与访问：受控 URL、资源句柄、缓存与失效 |
| `archive` | 容器与压缩：ZIP Store 读写、包裹格式、完整性校验 |
| `serializer` | 序列化：YAML / JSON / 二进制编解码与 schema 校验 |
| `index` | 索引与检索：标签、全文、元数据查询 |

### B. 系统与环境域

| 服务域 | 职责 |
|---|---|
| `file` | 文件系统访问、工作区文件操作（扫描/新建/重命名/删除） |
| `platform` | 平台信息、能力快照、屏幕、电源、剪贴板、通知、全局快捷键、托盘 |
| `transfer` | 打开、保存、导出、分享、在文件夹中显示 |
| `association` | 文件关联、URL 协议注册、默认处理器治理 |
| `network` | 网络访问：HTTP、WebSocket、下载、协议适配（含 WebDAV 等） |
| `credential` | 凭证与密钥：加密存储、会话注入、审计 |
| `config` | 配置与偏好：分层覆盖、变更通知、快照 |
| `log` | 日志、诊断、导出 |

### C. 运行与治理域

| 服务域 | 职责 |
|---|---|
| `plugin` | 插件安装、启用、停用、卸载、会话管理 |
| `module` | 模块能力的注册、发现、调用、作业调度 |
| `surface` | 表面：窗口/页面/卡片/弹层的创建、状态与生命周期 |
| `command` | 命令：菜单、快捷键、命令面板、工具栏的**唯一来源** |
| `control` | 治理聚合：健康检查、指标、诊断、审计查询 |

> **注**：新设计不再保留 `theme` / `i18n` 服务域——视觉归表现运行时（L8），界面文案简体中文直写。

## 4. 关键服务域详解

### 4.1 `document`（通用文档会话）

**【设计】这是平台承载"所有编辑类软件"的核心服务**，取代旧体系"卡片服务垄断编辑"的模型。

核心动作面：

```
document.session.open      → { sessionId, handle }
document.session.read      → 分块/区间读取
document.session.write     → 增量写入（进入工作副本）
document.session.watch     → 变更订阅（内部变更 + 外部变更检测）
document.session.persist   → 原子提交到磁盘
document.session.checkpoint→ 检查点（崩溃恢复）
document.session.close     → 释放句柄与租约
document.convert           → 格式转换（经模块能力）
document.compare           → 版本对比与差异
```

规则：

- **工作副本模型**：编辑在副本上进行，提交原子换入；外部工具看到的永远是完整文件（外部共存）；
- **外部变更检测**：文件被其它软件修改时产生 `document.external-change` 事件，由应用决定合并/重载；
- **两种文档世界**：生态原生格式（卡片/箱子）与通用文档（docx 等）走同一会话模型，差异由处理器（模块/内置）承担；
- **无路径暴露**：应用拿到的只有句柄；持久化位置由平台管理。

### 4.2 `content`（原生内容）

- 卡片与箱子的格式语义（解析、打包、封面、结构、标签）；
- 不承担"所有文档编辑"——它是 `document` 的一个内容类型实现；
- 渲染与布局的运行时链路（见 11 篇）。

### 4.3 `surface`（表面）

- 表面的创建、状态、能力（见 04 篇"表面"）；
- 平台映射：桌面=窗口，移动=页面/卡片，Web=页面，无头=离屏画布；
- 表面能力集按端查询与降级（全屏、置顶、尺寸约束、沉浸模式）。

### 4.4 `plugin` 与 `module`（运行与能力）

- `plugin`：安装 → 校验 → 暂存 → 激活 → 会话 → 停用 → 卸载（全程可逆）；
- `module`：capability + method 的能力注册与调度；作业（job）的创建、进度、取消、恢复。

### 4.5 `platform` / `transfer` / `association`（系统集成）

- 三个服务域共担"平台集成语义面"：能力、流转、关联；
- 一切壳级能力（通知、托盘、快捷键、分享、打开方式）都在此收敛，应用不直接触碰壳；
- 移动端无对应能力时以能力快照如实降级（如无系统托盘 → unsupported）。

## 5. 能力扩展机制（三条生长路径）

| 路径 | 形态 | 适合 | 原生代码 | 分发 |
|---|---|---|---|---|
| 模块插件 | capability + method，沙箱执行（JS/WASM） | 第三方与官方的通用无界面能力 | 否 | 用户可装 |
| 官方能力包 | 平台签名、随平台版本分发、可含原生实现 | 编解码、GPU、格式引擎、系统深度能力 | 是 | 随平台 |
| 壳扩展 | 只存在于壳与 PAL 内 | 系统集成、平台特有能力 | 是 | 随壳 |

**【设计】判定规则**：先问"能否用可移植载荷实现"→ 能则模块插件；再问"是否跨插件共用且需要原生"→ 是则官方能力包；再问"是否平台特有"→ 是则壳扩展。**不允许**第四个答案（往核心塞一次性特例）。

## 6. 服务版本与兼容

- 服务随平台版本演进；每个服务域有独立版本号；
- 契约版本协商在客户端运行时完成（见 06 篇）；
- 弃用流程：标注 → 双实现期（仅平台内部）→ 移除；**对插件**不承诺跨主版本兼容，但承诺"不静默破坏"（提前公告 + 确定性错误）。
