## 一、生态定位与终极愿景

1. **软件级生态系统**（Prompt 4）：运行在操作系统之上，类似微信小程序生态；整个生态只有一个底层软件（薯片主机），所有上层软件都是插件。
2. **双重构成**（Prompt 220/221）：
   - **软件生态**：把普通人会用到的所有软件重新做一遍，做到世界级最好——免费、无广告、开源、简洁、美观、易懂好用；覆盖视频播放器、图片查看器、电子书阅读器、PS 类工具、视频剪辑、文本编辑器、笔记工具等。
   - **卡片生态**：把所有信息都用卡片保存，图片、文字、视频都放在同一载体，让**信息结构脱离程序保存**；统一用卡片保存、分享、查看。
3. **操作系统级野心**（Prompt 215）：做成操作系统级别的生态，覆盖所有应用软件市场，达到苹果生态的级别，覆盖移动端与桌面端。
4. **全平台通用**（Prompt 240/244）：像微信小程序那样，插件与核心主机只写一份代码，在 Linux、Windows、macOS、Android、iOS 全部可用；"不惜一切代价"。
5. **软件帝国**（Prompt 185/190）：目标不是"做一套组件库"，而是提供最高质量的应用框架，支撑"把所有软件重做一遍"的野心。
6. **开发体验对标 SwiftUI**（Prompt 182/190/913）：在薯片生态开发应用要像苹果 SwiftUI 一样轻松，做出 UI、交互、质量统一的应用。
7. **核心理念**（Prompt 4/17）：让复杂内容像打开图片一样简单——双击 `.card` 即开，可嵌入网页或其他软件，可分享直接使用。

## 二、内容与卡片生态理念

1. **一切信息皆卡片**（Prompt 178/220/221）：图片、文字、视频、链接等所有信息统一保存在卡片中。
2. **可嵌套**（Prompt 41/136/172）：卡片可层层嵌套；箱子可层层嵌套（箱子中放箱子显示封面）。
3. **卡片文件约定**（Prompt 226）：
   - ZIP 只打包不压缩（零压缩率）；"只要技术满足，就没有最大安全上限"。
   - 上传下载**完全还原**：什么信息都不能改动，连 ZIP 的创建时间、修改时间也不能变。
   - **空壳卡片是正常卡片类型**（资源全部以网络 URL 保存，卡内无本地文件）。
   - 卡片本身没有权限管理（像图片、Word 文件一样）。
4. **资源链路**（Prompt 203-205/225-226）：
   - 用户设备侧处理：客户端模块把卡片资源上传对象存储、替换链接、再上传卡片。
   - **浏览器只有查看能力**；上传、下载统一由客户端模块负责，各应用插件与它对接。
   - 下载时按文件名等信息**还原卡片根相对路径**。
   - 网页端可直接用网页版卡片查看器传入卡片文件查看；上传下载属于客户端能力。
5. **箱子模型**（Prompt 94-99/107）：
   - 箱子 = 元数据与结构 + 布局插件（**布局即箱子的前端**）。
   - 统一记录 URL，**不区分内部/外部、不区分三种类型、不再建同名文件夹**。
   - Host 负责寻找全部资源；**布局插件按需向 Host 申请**（含封面），动态加载，不一次性全量。
   - **卡片与箱子同构**：架构、链路、接口统一，尽可能共用（Prompt 136-139/149-150）。
6. **chips:// 内部协议**（Prompt 41）：以 `/` 层级、`#` 内容、`@` 属性、`list` 列举；理念是"**上层不处理底层复杂逻辑**"，由 Host 资源模块统一解析（该形态后演进为受控 URL / 资源句柄体系）。

## 三、架构哲学

1. **核心架构原则**（Prompt 4）：中心路由（一切服务通信过内核）、桥接隔离（插件只经 Bridge 访问系统）、底层厚上层薄、平台无关（PAL）、一切皆插件（独立仓库 + 统一打包）。
2. **最好的架构**（Prompt 72/84/139）：模块解耦、高度复用、平台化、系统化；为未来长期拓展、稳定发展、鲁棒性设计；让生态内所有软件完美配合。
3. **平台自动适配**（Prompt 135）：Host 底层自动处理 Win/Mac/Linux/Web/Android/iOS 全部差异，为上层提供统一环境（窗口、文件、上传下载及未来一切所需）；不留临时版、快速版。
4. **无兼容包袱**（反复出现）：第一版未发布，不做兼容性重构、不留回退机制、旧实现直接清理（Prompt 18/33/72/84/99）。
5. **模块插件**（Prompt 68-71/84）：
   - 纯无界面能力模块（工具属性、类似函数），安装到 Host，扩展 Host 能力、解耦未来功能。
   - 模块之间可相互调用；可有工作流模块；不区分模块职责类型。
   - 模块是"能力的积木"。
6. **原子化积木**（Prompt 239，最完整的表达）：
   - 所有功能拆成原子化模块，适配庞大生态；开发者只做最简开发，直接调用生态内的库、组件、模块。
   - **同一底层模块被不同软件复用**（专业工作站级 PS 与小白相册编辑共用一个底层实现，各自只调用其中一部分）。
   - 支持模块化扩展：新动画库可做成 mod 包直接引入；新模块与现有模块协同。
   - 核心难点是"**如何划分原子积木**"，同时保证各种类型的拓展。
7. **内核能力路由**（Prompt 133-134/159/162/175/232）：应用把需求（查看图片/视频、打开文件）交给内核，**内核自动寻找有对应能力的插件并传递资源**；应用只写最上层业务。
8. **编辑态例外**（Prompt 42/48/79）：编辑引擎为复杂交互与数据操作，需要就近装配单卡渲染、不套整卡 iframe；Host 提供的渲染链路在架构上与其一致。
9. **一条链路**（Prompt 149-150）：卡片与箱子共用同一条链路与接口，只在文件格式层区分，**不为箱子再开一套管线**。
10. **接口颗粒度**（Prompt 31）：Host 给应用提供较底层、较宽松的总接口（如允许编辑引擎直接处理文件），不细化到每个处理方法；其他类似场景同理。（后演进为 `file.session` 等统一契约，但"只给工具、不给限制、应用专注业务"的理念保留。）

## 四、产品理念

1. **世界最好、免费、无广告、开源、简洁、美观、易懂好用**（Prompt 219/220/221）。
2. **对标世界最好**（Prompt 166/167/169/219）：每个领域找世界最好产品对标——电子书对标 Thorium；设置界面参考主流软件表单布局；颜色提取参考豆瓣/QQ 音乐；播放器世界级。
3. **人机界面指南**（Prompt 215）：对标苹果 HIG 编写薯片生态自己的 HIG（一节一文档）；只写方向性与原则性外观（外观后来统一由平台风管）。
4. **消费型应用克制**（Prompt 219）：视频/图片/电子书/音乐播放器只做查看与使用，不做管理功能。
5. **起始首页独立设计**（Prompt 234）：每个软件一套简约起始首页，不共用一个总首页。
6. **客户端优先**（Prompt 227-228）：社区客户端是主要入口，网页版只供路人临时查看。
7. **系统级文件打开治理**（Prompt 231）：像操作系统一样提供"默认查看器 + 全部支持该格式的应用"选择；生态设置面板提供"文件打开方式"页；平时用户无需选择。

## 五、视觉与交互设计理念

1. **视觉语言**（Prompt 206）：有质感、有层次、有高级感、简约素雅；**纸片卡片的生命感**；彩虹折射点缀；类似苹果液态玻璃但**不透明**，边缘有细细的彩色反射。
2. **图标**（Prompt 233）：统一设计风格；色彩丰富、五颜六色；整体充满生机。
3. **社区界面**（Prompt 113/128）：极简；以个人页为中心（头图 + 网格作品）；磨砂质感背景 + 淡淡七彩光晕随机飘动；封面轻微立体感与随机浮动；动画细腻灵动、丝滑、有果味。
4. **极简交互**（Prompt 160/219）：无内容时只有一句居中提示；平时操作按钮隐藏，点击中部才出现。
5. **拖动质感**（Prompt 57/347）：像手机上调整应用图标一样丝滑；拖动时保留空位、插入时移除空位；删除区为淡红色小圆角矩形弹窗，滚动时不遮挡。
6. **响应式**（Prompt 128/168）：移动端上下堆叠；编辑面板适应窄窗口与移动端比例。
7. **显示规则**（Prompt 125/129）：任意比例的卡片封面对角线长度恒定、区域中心居中、名字统一在同一高度；图片打开时缩放到合适尺寸（最长边为高取窗口 80%，为宽取窗口 80%）。
8. **禁止卡片套卡片**（Prompt 168）：列表式、标题划分，不嵌套多层卡片。
9. **简洁优雅**（Prompt 160/219）：工具按钮克制；参考世界最好阅读器的界面与交互。
10. **宣传片**（Prompt 220-222）：对标苹果/微软风格；工业设计稿级镜头描述；"哪怕多写 10 倍代码，只要能提高 1% 画面质量"。

## 六、开发者体验理念

1. **复杂度留在底层**（Prompt 185）：上层应用代码尽可能简洁与少；常用功能都在系统底层，应用安装后直接调用；全生态统一交互与前端风格。
2. **像 SwiftUI 一样简单**（Prompt 182/190）：开发应用像苹果 SwiftUI 一样轻松，做出 UI、交互、质量统一的应用。
3. **前端框架定位**（Prompt 182-184）：不只做组件库，而是完整前端框架与开发框架；吸收 View/Stack/Grid/Form/List 声明式布局概念；以 Web 技术栈为底层；考虑未来对其他 Web 项目的兼容与快速吸收同化。
4. **开源优先与许可**（Prompt 100/155/157/159）：使用 MIT/Apache 等宽松协议；不宽松的宁可自己写；吸收开源项目时可用中间层包装，对外屏蔽内部实现。

## 七、工程协作方法与工作纪律

1. **一节一个文档**（反复出现）；**文档即代码**（Prompt 109）；文档要全面详细、可直接用于实际开发。
2. **写文档前必须重新核对代码与真实技术细节**（Prompt 112/286/582）。
3. **单一事实源**（反复出现）：生态通用/对外公开信息 → `生态共用技术文档`；项目内部信息 → 项目自己的文档。
4. **工单机制**（Prompt 23/315）：问题单独开工单，编号顺延，中文描述，**只描述问题不写解决方案**；文档与代码不符必须提工单。
5. **执行纪律**（Prompt 32/129）：直接完成所有任务，不每完成一点就汇报；完全按计划实施，不做多余的事。
6. **子代理并行**（Prompt 186-188/196-201/229/1186/1212）：可大量使用子代理并行推进；任务说明要非常详细；提前一个任务给子代理发送任务；大任务拆小任务用小数点编号（如 015.01）。
7. **无兼容纪律**：不要版本兼容处理、不要旧版回退机制。
8. **不要人事管理、商业分析、时间规划**（Prompt 4/11/88）。

## 十、总纲（从历史 Prompt 提炼的一句话）

> **把复杂度留在底层，把简单留给用户与开发者；一切皆插件、一切皆卡片；软件重做到世界最好，内容脱离程序保存；一个底座，全平台运行。**

## 附：高频反复出现的要求（可视为长期红线）

1. 不做兼容性设计、不留回退机制、不留旧版代码。
2. 最好的架构、最好的软件工程、最干净整洁优雅的代码。
3. 写文档前先核对代码；文档与代码不符先开工单。
4. 单一事实源：生态通用信息进 `生态共用技术文档`，项目内部信息留项目内。
5. 一节一个文档；文档即代码，要能直接指导开发。
6. 不允许临时版、简化版、快速版开发。
7. 官方与第三方、卡片与箱子、Host 与服务器：**能统一就统一，不能统一再拆**。
8. 用户侧体验无感：迁移、重构、更新都不能改变用户体验。
