# 3. 迁移总原则

1. **以需求和架构意图为源，不以旧代码形态为源**：旧提交提供行为、接口、测试、文档和局部架构调整证据；实际实现必须贴合当前重构后的目录、Provider、Scene、SDK、Host 服务和社区 Web 插件宿主。
2. **功能迁移与架构融合并行**：旧主工作区提交中的 `CardViewerSource`、`document.window` 事件、Host `cardSource` 启动、社区 Web 插件路由、源 `.card` 渲染缓存和模块插件化上传等架构调整都要迁移为当前新架构的一部分，不能只补用户界面表层功能。
3. **以后续提交覆盖前序方案**：`d3c6d0b0` 已替代 `6e6b20fb` 中旧 `card_pipeline_jobs/runCardPipeline` 主链路，迁移时保留“异步化、队列化、缓存化”的需求，不恢复旧 pipeline 主实现。
4. **统一来源模型**：卡片查看器入口统一收口到结构化 `cardSource`，避免继续扩散 `targetPath`、`fileOpenMode`、`webDocumentUrl`、`htmlUrl`、`communityHtmlUrl` 等平行私有字段。
5. **查看器壳层只做壳层能力**：封面/内容切换、返回按钮、顶部信息和 action slot 属于查看器壳层；卡片正文和箱子页面仍由 Host/SDK 正式文档链路承载。
6. **社区 Web 不复制桌面 Host**：社区 Web 插件宿主只实现浏览器侧 session、entry、bootstrap、resource-open-plan、surface 映射和高度同步；公共 Host WebShell 能力若要对外发布，另开正式任务。
7. **上传链路两端分工清晰**：用户设备侧模块插件负责解包、资源扫描、资源外置、YAML/cover HTML 改写和重新打包；服务器负责上传会话、对象存储、源文件保存、渲染缓存和公开访问控制。
8. **文档先核对后更新**：真正改动公共契约前，必须重新核对 Host/SDK/manifest/测试/运行链路，不能直接照搬旧工作区文档。
9. **源码一比一对照开发**：迁移实现时必须逐项打开旧主工作区对应提交的源码、测试和文档，按旧入口、旧状态流、旧错误处理、旧测试断言、旧架构职责调整和旧验收命令建立对照表，再把每个行为与架构意图映射到当前新架构落点。禁止只根据提交说明或记忆开发。
