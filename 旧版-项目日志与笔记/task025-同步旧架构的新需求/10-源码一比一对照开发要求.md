# 10. 源码一比一对照开发要求

## 1. 基本要求

迁移开发时必须一比一对照旧主工作区源码开发。这里的“一比一”不是直接复制旧代码，也不是把旧架构合并进当前 worktree，而是要求每个功能点和架构调整都必须以旧源码、旧测试、旧文档和旧运行链路为完整证据来源，逐项确认后再按新架构重写。

禁止只看 commit message、迁移计划摘要或历史记忆就开始实现。

## 2. 对照对象

每个迁移子任务至少核对以下来源：

- 旧主工作区对应 commit 的源码 patch；
- 旧主工作区对应测试文件和测试断言；
- 旧主工作区同步修改过的文档；
- 旧功能涉及的 `manifest.yaml`、`package.json`、脚本和验证命令；
- 旧提交中涉及的公共类型、启动参数、Host/SDK/Bridge 事件、服务边界、缓存模型、模块插件能力等架构调整；
- 当前 worktree 中同领域的新架构源码、测试、manifest 和正式运行链路。

## 3. 对照记录格式

每个子任务实施前，应在对应任务记录中写出对照表：

| 旧源码或旧行为 | 旧证据 | 新架构落点 | 迁移方式 | 验证 |
|---|---|---|---|---|
| 旧文件、旧函数、旧接口或旧交互 | commit、文件、测试或文档 | 当前文件、服务、SDK API、组件或文档 | 重写、归档、替代、弃用 | 单测、集成、构建、validate、人工验收 |

对照表必须覆盖：

- 入口参数；
- 数据结构；
- 架构职责与边界变化；
- 状态流；
- 错误处理；
- 权限口径；
- 资源生命周期；
- UI 文案和 i18n key；
- 主题 token 与布局约束；
- 测试断言；
- 文档落点。

## 4. 开发规则

1. 旧源码能说明“功能应该做什么”，不能决定“新架构代码应该长什么样”。
2. 旧源码也能说明“旧提交已经想把架构调整到哪里”，这些架构意图必须被吸收、替代、归档或登记工单，不能因为旧目录结构落后而直接忽略。
3. 旧实现中绕过 Host、Bridge、SDK、主题、多语言、模块服务或 Web 插件宿主的做法，必须改写为当前正式链路。
4. 旧实现中的临时兼容字段如果已经被新来源模型替代，只允许作为迁移输入识别，不允许写成新的主口径。
5. 旧测试中覆盖的用户行为、错误场景和架构边界必须在新架构测试中等价覆盖。
6. 旧代码中已经被后续提交替代的方案，以后续提交为准；被替代方案只能作为历史原因参考。
7. 如果旧源码能力在当前新架构没有正式落点，必须先登记工单，不得写临时实现。

## 5. 完成门禁

每个迁移子任务完成时必须能回答：

- 旧源码中哪些文件被逐项核对过；
- 旧测试中哪些断言已迁移为新架构测试；
- 旧提交中的哪些架构调整已经融合到当前新架构；
- 哪些旧实现被明确归档或不迁移；
- 新实现使用了哪些 Host / SDK / Bridge / module / surface 正式入口；
- 哪些公共契约或项目文档已同步更新；
- 哪些验证命令已通过。
