# 11. 架构融合迁移要求

## 1. 定位

旧主工作区 `develop` 的新增提交虽然整体建立在旧架构上，但其中有些代码已经表达了新的架构调整。本任务必须把这些架构调整迁移过来，并与当前 worktree 的重构架构融合。

融合迁移的意思是：

- 迁移旧提交中已经验证过的公共类型、启动协议、事件协议、服务边界、缓存模型、模块插件能力和测试口径；
- 保留当前 worktree 已经完成的 AppRuntime、Scene、surface、command registry、Host L1-L9、SDK 类型封装、主题和多语言架构；
- 对旧提交中的单体入口、临时字段、旧 pipeline、旧查看页和旧目录组织做职责重映射或归档处理。

## 2. 架构融合映射

| 旧架构调整 | 融合后的新架构落点 | 处理要求 |
|---|---|---|
| `CardViewerSource` 来源模型 | `Chips-SDK/src/types/card-viewer.ts`、`Chips-CardViewer/src/types/viewer-source.ts`、Host `launchParams.cardSource`、社区 Web 插件路由 | 作为统一来源模型迁移；本地文件使用 `kind: "local-file"` 和 `documentKind`，不新增 `local-card/local-box` 平行类型。 |
| `document.window.onResize` 与 iframe 文档类型标记 | `Chips-SDK/src/api/document.ts`、`Chips-CardViewer/src/components/CardWindow.tsx` | 在当前 ready/error/node-error/resource-open 基础上增强，不覆盖当前已存在事件面。 |
| Host `card.open` 和文件关联传参调整 | `Chips-Host/packages/card-open-service`、`Chips-Host/src/main/core/file-association.ts` | `.card/.box` 主入口传 `cardSource`；旧 `targetPath/fileOpenMode` 只作为旧输入识别。 |
| `ViewerSourceProvider` | 当前 `AppRuntimeProvider` 和 viewer-source 解析工具 | 迁移来源解析、封面读取和错误降级职责，不复制旧 Provider 结构。 |
| `ViewerStage` | 当前 `scene-registry`、`AppShell`、`DocumentFileScene`、`HostedDocumentScene` | 迁移舞台选择和 cover/content 模式切换职责，不新增平行舞台运行时。 |
| `ViewerChrome` | 当前 `CardViewerShell`、Scene action slot、command registry | 迁移返回、标题、日期、查看封面/查看内容动作；文案使用 i18n key，图标使用正式 IconDescriptor 或组件库图标能力。 |
| `ViewerCoverSurface` | 当前 `Chips-CardViewer/src/components` 新封面组件 | 迁移比例校验、面积归一、标题展示、点击返回正文和 resize 发布；样式必须走主题 token。 |
| 社区 `DocumentPluginRoutePage` 和 `HostedPluginSurface` | `Chips-CommunityPlatformServer/packages/web` 当前 Web 插件宿主 | 迁移 document 模式、插件 chrome/action、surface resize 和 `cardSource` 注入；不恢复旧社区查看页。 |
| 源 `.card` 与渲染缓存模型 | 社区服务器数据层、对象存储、worker 和 API | 以源文件永久保存、view/cover 缓存可重建为最终架构；旧 pipeline 归档。 |
| CommunityUploader 模块插件 | `Chips-ModulePlugin/Chips-CommunityUploader-Plugin` | 用当前模块插件脚手架和模块能力契约实现，不跨仓直连 Host 内部服务。 |

## 3. 分类规则

每个旧提交、旧文件和旧测试都必须被分类：

- 融合迁移：架构意图正确，按当前新架构实现。
- 职责重映射：旧文件不能保留，但其职责迁入当前 Provider、Scene、SDK、Host 服务或社区 Web 宿主。
- 被后续提交替代：以后续提交作为最终口径。
- 归档不迁移：旧实现不再作为正式链路，但按规则保留历史材料。
- 需要工单：当前新架构没有正式落点，或公共契约、脚手架、SDK、Host 能力缺失。

## 4. 门禁

子任务不能只以“页面看起来一致”作为完成标准。每个子任务完成前必须确认：

- 旧主工作区对应源码、测试和文档已经逐项打开核对；
- 功能行为和架构调整都有明确的新架构落点；
- 当前 worktree 已有的新架构文件没有被旧结构覆盖；
- Host/SDK/Bridge/manifest/测试/文档的公共口径一致；
- 旧临时链路已经归档、不迁移或仅作为旧输入识别；
- 验证命令覆盖本轮改动的实际风险范围。
