# 12. 主工作区架构调整融合矩阵

## 1. 定位

本节专门记录主工作区 `develop` 新提交中已经出现的架构调整，并定义它们迁移到当前重构 worktree 时的融合方式。

这里的融合不是合并分支、不是复制旧文件，也不是恢复旧架构目录；而是把旧源码中已经验证过的架构意图、接口边界、数据模型、事件协议和测试断言转译为当前 worktree 的正式架构实现。

后续开发必须做到：

- 每个架构调整都有旧源码证据；
- 每个旧源码职责都有当前新架构落点；
- 每个融合动作都有验证命令或测试断言；
- 每个不迁移项都有原因，必要时按工单规则登记；
- 每个公共契约变化都不能只停留在本任务日志，代码核对后要同步到 `生态共用技术文档/`。

## 2. 融合执行流

1. 打开主工作区 `develop` 对应提交的源码、测试、文档和 manifest。
2. 按功能行为、架构职责、公共契约、临时旧实现四类拆分旧改动。
3. 对每个架构职责建立新架构落点，优先落到当前 worktree 已有的 Host L1-L9、SDK 类型、AppRuntime、Scene、surface、模块插件、社区 API 和 worker 链路。
4. 如果旧提交中的实现绕过 Host、Bridge、SDK、主题、多语言或模块服务，只迁移需求和测试，不迁移绕过方式。
5. 如果旧提交中的架构调整已经被后续提交替代，以后续提交为准，前序方案只作为历史依据。
6. 如果当前新架构没有正式承载点，先登记 `项目日志与笔记/问题工单.md`，不得写临时实现。

## 4. 开发记录要求

每个实施记录必须追加一张对照表，至少包含：

| 对照项 | 旧源码证据 | 当前新架构落点 | 处理结果 | 验证 |
|---|---|---|---|---|
| 功能行为 | commit + 文件 + 测试 | 当前文件或服务 | 已融合、已替代、已归档、不迁移、需工单 | 命令或测试名 |
| 架构职责 | commit + 文件 + 文档 | Host/SDK/Bridge/AppRuntime/module/API | 已融合、已替代、已归档、不迁移、需工单 | 命令或测试名 |

如果一个旧源码文件同时包含有效需求和旧架构退化，必须拆开记录：有效需求融合，旧架构退化不迁移。

## 5. 最终收口

任务完成前需要逐项确认：

- `develop` 新提交中的架构调整已经全部分类；
- 当前 worktree 没有被旧架构目录覆盖；
- 旧 pipeline、旧查看页、旧单体入口等不再作为正式主链路；
- 新实现的公共契约已同步或计划同步到 `生态共用技术文档/`；
- 实施记录能追溯到每个旧源码文件、测试断言和验证命令。
