# 工单094-组件库冻结技术栈与质量门禁覆盖漂移

## 背景

用户要求检查当前 `Chips-ComponentLibrary` 是否可以完美实现生态设计手册中关于主题系统和组件库的目标。按工作区规则，先核对了设计原稿、生态共用组件库与主题系统文档，再检查组件库真实代码、包结构、契约、测试和质量门禁。

## 证据

1. 生态共用文档与组件库技术文档冻结的技术基线是 `React + Ark UI + Style Dictionary + Tamagui (Core)`，并声明 Ark UI 负责交互原语、可访问性与状态机基础，Tamagui Core 负责 token/runtime 语义层。
2. 当前 `Chips-ComponentLibrary/package.json` 的根级依赖只有 `react`，`npm ls @ark-ui/react @zag-js/core @zag-js/react @tamagui/core` 输出为空，未安装冻结口径中的 Ark UI、Zag.js 或 Tamagui Core 正式依赖。
3. 当前组件实现集中在 `packages/components/src/index.js`，主要使用 React、自研 `useInteractiveState`、自研键盘与状态逻辑，以及 `@chips/primitives` / `@chips/a11y` 辅助函数；真实实现并非基于 Ark UI / Zag 状态机封装。
4. `packages/adapters/tamagui-core` 当前是自研 token resolver / token map adapter，包名体现 Tamagui Core 适配意图，但没有实际依赖或调用 `@tamagui/core`。
5. `packages/theme-contracts/src/validator.js` 强制要求每个组件契约都存在 `iframe.requiredSandbox === true`；这导致普通组件如 `button`、`input`、`tabs` 等 contract 也带有 iframe 字段，与生态共用文档中“iframe 高级组件附加契约仅适用于 `CardCoverFrame`、`CompositeCardWindow`”的分层不一致。
6. 当前 `npm run verify` 和 `npm run quality:gate` 均可通过，说明已有 token、contract、类型、单元、a11y、性能基线，但 a11y 脚本主要调用 `validateComponentA11y(...)` 校验规则对象，并未通过真实 DOM/浏览器交互验证所有组件的键盘可完整操作、焦点可见和顺序正确。
7. 当前测试主要覆盖导出存在、纯函数、contract 文件、浅层 React element props 和部分状态逻辑；没有覆盖完整真实浏览器行为，例如 Dialog focus trap / restore、Menu roving focus、Select 选项导航语义、SplitPane pointer capture 与卸载清理、跨主题真实渲染差异等。

## 复现步骤

1. 进入 `Chips-ComponentLibrary`。
2. 执行 `npm run verify`，确认当前验证通过。
3. 执行 `npm run quality:gate`，确认当前发布门禁通过。
4. 执行 `npm ls @ark-ui/react @zag-js/core @zag-js/react @tamagui/core`，确认冻结技术栈核心依赖为空。
5. 检查 `packages/components/src/index.js`，确认组件行为主要由自研状态与键盘逻辑实现。
6. 检查 `packages/theme-contracts/src/validator.js`，确认所有组件 contract 都被强制要求 iframe 字段。
7. 检查 `packages/components/tests/a11y-stage9.test.mjs`，确认 a11y 门禁未通过真实 DOM 或浏览器交互执行完整键盘与焦点验证。

## 期望行为

- 组件库实现口径应与冻结技术栈一致：如果正式采用 Ark UI / Zag.js / Tamagui Core，则需要引入依赖并按文档分层封装；如果当前自研实现才是正式方向，则必须更新生态共用文档和组件库技术文档，取消已经冻结但未落地的依赖口径。
- 普通组件 contract 不应强制携带 iframe 高级组件字段；iframe 附加契约应仅适用于 `CardCoverFrame`、`CompositeCardWindow` 等高级 iframe 组件。
- 质量门禁应补齐真实组件渲染与交互测试：至少覆盖 contract part 与真实渲染一致性、键盘完整操作、焦点顺序与恢复、主题切换后 DOM/CSS 变量生效、语言切换、关键组件浏览器级回归。
- 通过门禁后，组件库才能被称为“符合生态冻结目标的正式实现”，而不仅是“当前基线可运行且浅层门禁通过”。

## 2026-08-02 复核补充

本次在评估“继续优化现有组件库”与“基于 shadcn/ui 二次开发重构”两条路线时，重新核对了当前代码、包声明、测试和发布门禁。原工单记录的冻结技术栈漂移仍然存在，并新增以下可复现证据：

1. 根 `tsconfig.json` 已启用 `allowJs + checkJs + strict + noEmit`，但 `scripts/run-typecheck.mjs` 只对 `.js/.mjs` 逐文件执行 `node --check`，不调用 TypeScript 编译器。直接执行 `npx tsc -p tsconfig.json --noEmit` 失败，共报告 3886 个 TypeScript 诊断，因此当前 `quality:gate` 中的 `typecheck: passed` 只能证明 JavaScript 语法可解析，不能证明严格类型安全。
2. `scripts/run-lint.mjs` 只检查 `TODO/FIXME`、行尾空格和文件末换行，未运行 ESLint 或等价语义规则；无法覆盖 React Hooks、未使用符号、不安全类型和可达性等问题。
3. `quality:coverage` 实际验证 71 个 component contract 与 quality matrix/fixture 的集合完整性，未收集语句、分支或函数代码覆盖率。
4. `test:perf` 主要在 Node.js 中测量排序、过滤、虚拟窗口纯函数，以及对空 `style.setProperty()` 目标的主题变量写入；未测量 React render/commit、浏览器 layout/paint、真实主题切换可见完成时间或包体。
5. 根 `build` 只执行 `build:tokens`；组件包直接把 `src` 作为 `main/exports`，没有组件代码与声明的正式构建、按包出口验收、tree-shaking 验证或安装产物测试；`@chips/primitives` 也未公布 types/exports。
6. 当前 `@chips/components` 的主实现仍集中在单个 16999 行 `packages/components/src/index.js`，且严格 TypeScript 错误大量集中在该文件；这与可独立演进、按组件发布和高解耦目标仍有明显距离。
7. 当前存储位置在 `已解决或废弃工单/`，但工单本身与总表状态均为“待处理”，存储归类与状态不一致。本次不自行移动历史工单，待用户处理时一并收口。

### shadcn/ui 路线判断

- shadcn/ui 是开发时源码分发系统与可视化默认配方，不是可直接替代 Chips L10 的运行时无头组件包。其当前组件包含 Tailwind 布局、尺寸、圆角、颜色和动效类，主要公开 `data-slot/data-variant/data-size`，不提供 Chips 正式 `data-scope/data-part/data-state`、六级主题解析、必需 token 诊断、Host/SDK/Bridge 和 Card Runtime 契约。
- 本轮建议不以 shadcn/ui 进行全量二次开发重构，也不引入第三套并行运行时栈。应保留已有 Chips contract/token/theme/i18n/Host 边界，先就工单094由用户决定“真正落地已冻结的 Ark UI/Zag.js/Style Dictionary/Tamagui Core”或“正式改定自研路线并同步全部文档”。
- 可以借鉴 shadcn/ui 的每组件独立源文件、compound composition、registry schema、CLI `dry-run/diff/view`、私有 registry 和 AI 开发工作流；若未来引入 Base UI/Radix/React Aria 任一底座，必须另立架构选型工单，通过 Chips adapter 重新输出契约，不得直接复制 shadcn 视觉类到 L10。
