## 5. 初始研究与参考对象

开发电子书基础卡片时重点参考了两个既有基础卡片：

### 5.1 音乐基础卡片

研究点：

1. 资源型基础卡片如何保存内部资源路径。
2. 查看态如何通过 `openResource(...)` 发出资源打开意图。
3. 如何构造结构化业务 payload 给目标应用插件。
4. 编辑器如何处理主资源、封面、歌词等多资源引用。
5. `collectResourcePaths(...)` 如何收集被配置引用的内部资源。
6. 替换资源时如何通过 `deleteResource(...)` 登记旧资源删除。
7. `basecardDefinition` 如何把 view/editor/schema/validate/collectResourcePaths 收口成统一入口。

结论：

1. 电子书卡片不能硬编码 `Chips-BookReader` 或 `Chips-PhotoViewer` 插件 ID。
2. 电子书卡片只负责表达“打开资源”的意图和业务上下文。
3. Host `resource.open` 负责路由，目标应用插件只消费 `launchParams.resourceOpen.payload`。
4. `chips.book-card` payload 应像音乐卡片 payload 一样成为稳定业务对象。

### 5.2 网页基础卡片

研究点：

1. ZIP 网页包如何通过宿主链路导入卡片根目录。
2. 网页包入口文件如何表达。
3. `resource_paths` 如何保存压缩包内全部资源。
4. 替换网页包时旧资源如何删除。
5. 查看态如何以入口文件为根，解析内部相对资源。

结论和后续修正：

1. 网页卡片不是只保存 `index.html`。
2. 网页卡片必须保存压缩包内通过安全校验后的全部网页文件。
3. `index.html` 只是入口文件，用于查看态打开网页包。
4. `importArchiveBundle(...)` 应提供通用目录导入能力，网页卡片通过 `entryFile: "index.html"` 表达入口约束。
5. 电子书图片包通过 `include` 过滤图片资源，不传 `entryFile`。

## 7. `BookCard` 配置模型

配置模型在 `Chips-BaseCardPlugin/book-BCP/src/schema/card-config.ts` 中定义。

核心字段：

1. `card_type: "BookCard"`
2. `theme?: string`
3. `source_type: "ebook" | "image-sequence"`
4. `book_file: string`
5. `book_format: string`
6. `book_name: string`
7. `book_author: string`
8. `cover_image: string`
9. `image_sequence: BookImageItem[]`
10. `image_sort_basis: "filename" | "entry-time"`
11. `resource_paths: string[]`

`BookImageItem` 字段：

1. `id`
2. `file_path`
3. `file_name`
4. `mime_type`
5. `sort_key`
6. `source_entry_path`
7. `entry_time`

配置归一规则：

1. `card_type` 固定归一为 `BookCard`。
2. 内部资源路径必须是卡片根目录相对路径。
3. 丢弃绝对路径、`..`、空路径、`blob:`、`data:` 或宿主临时 URL。
4. `resource_paths` 由 `book_file`、`cover_image`、`image_sequence[*].file_path` 和显式 `resource_paths` 去重合并得到。
5. `source_type` 不可信时根据 `image_sequence` 推断。
6. `image_sort_basis` 只允许 `filename` 或 `entry-time`。
7. `book_format` 归一为小写格式，例如 `markdown` 归一为 `md`。

校验规则：

1. `card_type` 必须为 `BookCard`。
2. `source_type` 必须为 `ebook` 或 `image-sequence`。
3. `image_sort_basis` 必须为 `filename` 或 `entry-time`。
4. 普通电子书有 `book_file` 时必须记录 `book_format`。
5. 图片包卡片不能同时保留普通电子书文件。
6. `image_sequence` 中每张图片必须有稳定 ID、资源路径和文件名。

7. 尝试通过以下规则定位封面：

## 10. 图片包导入链路的演进

### 10.1 初版

`a07225c0...` 临时提交中，`book-BCP` 已包含 ZIP 工具和图片包导入测试，用于读取 ZIP 中央目录、条目时间、图片文件和排序信息。

初版满足了图片包业务需求的基本形态：

1. 支持 ZIP/CBZ。
2. 过滤图片资源。
3. 丢弃非图片。
4. 按文件名或条目时间排序。
5. 首图作为默认封面。
6. 配置保存图片序列。

### 10.2 架构复核后的问题

继续核对网页基础卡片和编辑引擎资源桥后，发现图片包解包不应由 `book-BCP` 私自完成。

原因：

1. 压缩包解包涉及文件系统写入，必须由 Host/EditingEngine 资源桥承担。
2. 插件不能直接写卡片根目录。
3. 网页基础卡片、电子书基础卡片和未来资源包卡片都需要类似能力。
4. 如果每个插件自行解包，会形成多套安全校验、路径清洗、系统噪声处理和冲突处理逻辑。
5. 用户明确要求考虑生态长期拓展，不能做临时分叉。

因此后续把图片包资源保存职责迁移到正式宿主链路：

`book-BCP editor -> importArchiveBundle(...) -> EditingEngine EditorHost -> Host zip service / file service -> card root`

`book-BCP` 只消费宿主返回的最终资源路径和元数据。

### 10.3 最终链路

电子书图片包导入最终调用：

```ts
importArchiveBundle({
  file,
  preferredRootDir: stripFileExtension(file.name),
  include: {
    mimeTypes: ["image/*"],
    extensions: [".jpg", ".jpeg", ".png", ".gif", ".webp", ".bmp", ".avif", ".svg", ".tif", ".tiff"],
  },
  stripSingleRootDir: true,
  excludeSystemArtifacts: true,
})
```

最终行为：

1. 不保存 ZIP/CBZ 原文件。
2. 解包目录由宿主创建。
3. 目录名以压缩包名为前缀，宿主追加短 ID 避免冲突。
4. 只保留图片资源。
5. 非图片进入 `discardedEntries`。
6. `__MACOSX`、`.DS_Store`、`._*` 等系统噪声被排除。
7. 不安全路径被丢弃。
8. `entries[*].resourcePath` 是最终卡片根目录相对路径。
9. 配置只保存宿主返回的最终路径，不自行推测路径。
10. 图片排序可使用 `entries[*].modifiedTime`。
11. `modifiedTime` 缺失或不可区分时稳定回退文件名排序。

## 11. 通用 `importArchiveBundle(...)` 契约

本次最关键的架构收口之一，是把 `importArchiveBundle(...)` 定义成无业务模式的通用目录导入契约。

最终请求字段：

1. `file`
2. `preferredRootDir?`
3. `entryFile?`
4. `include?`

## 17. `BookCardOpenPayload`

正式 payload 形状：

```ts
interface BookCardOpenPayload {
  kind: "chips.book-card";
  version: "1.0.0";
  cardType: "base.book";
  mode: "ebook" | "image-sequence";
  resources: {
    book?: BookCardOpenResource;
    images?: BookCardOpenResource[];
  };
  display: {
    title: string;
    author?: string;
  };
}
```

`BookCardOpenResource` 字段：

1. `resourceId`：目标应用实际读取的正式资源标识。
2. `relativePath`：卡片根目录相对路径，用于匹配、日志和显示。
3. `fileName`：用户可读文件名。
4. `mimeType`：资源 MIME。

消费规则：

1. `mode = "ebook"` 时，书籍阅读器优先读取 `resources.book`。
2. `mode = "image-sequence"` 时，图片查看器按 `resources.images[]` 的顺序建立图片队列。
3. Host 只透传 payload，不解释业务字段。
4. 目标应用不能要求上游硬编码自身插件 ID。

公共文档已写入：

`生态共用技术文档/协议与契约/10-资源打开契约.md`

## 23. 当前最终链路

### 23.1 普通电子书

链路：

1. 用户在 `book-BCP` 编辑器上传电子书。
2. 编辑器识别格式。
3. EPUB/EPUB3 尝试解析标题、作者、封面。
4. 主电子书通过 `importResource(...)` 保存为卡片根目录资源。
5. EPUB 封面如存在，也通过 `importResource(...)` 保存为卡片根目录资源。
6. 编辑器更新 `BookCard` 配置。
7. `collectResourcePaths(...)` 返回主书籍文件和封面。
8. 查看态展示封面、书名、作者、格式。
9. 用户点击卡片。
10. 查看态调用 `openResource(...)`。
11. Host `resource.open` 根据 MIME/扩展名命中 `Chips-BookReader`。
12. Host 启动阅读器并透传 `chips.book-card` payload。
13. 阅读器读取 `payload.resources.book`。
14. 阅读器根据格式加载 EPUB 或虚拟书籍。

### 23.2 ZIP/CBZ 图片包

链路：

1. 用户上传 ZIP/CBZ。
2. `book-BCP` 调用 `importArchiveBundle(...)`。
3. EditingEngine/Host 解包到卡片根目录子文件夹。
4. Host 只保留图片。
5. 非图片、目录、系统噪声、不安全路径进入 `discardedEntries`。
6. `book-BCP` 从 `entries` 生成 `image_sequence`。
7. 按 `image_sort_basis` 排序。
8. 第一张图片作为默认封面。
9. 配置中不保存原 ZIP/CBZ。
10. 查看态展示封面、书名、格式和图片数量。
11. 用户点击卡片。
12. 查看态以第一张图片为主资源调用 `openResource(...)`。
13. payload 中传递完整 `resources.images[]`。
14. Host `resource.open` 命中 `Chips-PhotoViewer`。
15. 图片查看器建立图片队列。
16. 用户可按顺序浏览图片。

### 23.3 网页 ZIP 包

链路：

1. 用户在 `webpage-BCP` 上传网页 ZIP。
2. `webpage-BCP` 调用 `importArchiveBundle({ entryFile: "index.html" })`。
3. EditingEngine/Host 校验入口文件。
4. 保存压缩包内全部通过安全校验的文件。
5. 配置记录 `bundle_root`、`entry_file`、`resource_paths`。
6. 查看态用入口文件加载网页，并用 `<base href>` 支持内部相对资源。

## 24. 架构决策总结

1. `book-BCP` 只做电子书卡片业务建模、编辑 UI、查看 UI 和 payload 构造。
2. 压缩包实际解包、路径安全、冲突处理、资源写入都归宿主链路。
3. `importArchiveBundle(...)` 是通用目录导入能力，不含业务模式。
4. Host 负责资源打开路由，不解释业务 payload。
5. SDK 负责类型封装，不承载主实现。
6. 目标应用插件通过 manifest 声明 `resource-handler` 和 `file-handler`。
7. 图片查看器通过 payload 建立图片队列，不要求上游调用特定插件。
8. 书籍阅读器通过统一加载层承接可阅读格式。
9. 私有与重型格式不做临时解析，拆分正式工单。
10. 公共信息写生态共用技术文档，项目内部实现写项目文档，过程记录写项目日志。

## 31. 后续修复：编辑器拖拽导入与查看态视觉优化

日期：2026-05-02

### 31.1 编辑器主上传框拖拽导入失败

现象：

1. 用户在编辑引擎中打开电子书基础卡片编辑器。
2. 将电子书文件拖动到编辑面板里的“上传电子书或图片包”文件框。
3. 文件没有稳定进入电子书导入链路。

原因：

1. `book-BCP` 编辑器上传框原先只依赖隐藏的 `input[type=file]` 的 `change` 事件。
2. 编辑引擎中直接把文件拖放到上传区域时，浏览器默认 drop 行为不会自动触发该 input 的 `change`。
3. 主上传区域和封面上传区域都缺少显式 `dragenter/dragover/drop` 处理。

处理：

1. 在 `Chips-BaseCardPlugin/book-BCP/src/editor/panel.tsx` 中新增拖放文件读取逻辑。
2. `dragenter` 与 `dragover` 阶段阻止默认行为，并根据 busy 状态设置 `dropEffect`。
3. `drop` 阶段从 `dataTransfer.files` 或 `dataTransfer.items` 中读取第一个文件。
4. 主上传框 drop 后复用既有 `handleMainFile(...)`，因此普通电子书和 ZIP/CBZ 图片包仍走同一正式导入链路。
5. 封面上传框 drop 后复用既有 `handleCoverFile(...)`。
6. 新增 `data-role="main-dropzone"` 与 `data-role="cover-dropzone"`，用于测试和运行时定位。
7. 在 `tests/unit/editor-panel.test.tsx` 中新增“拖拽 PDF 到主上传区域可以导入”的测试。
