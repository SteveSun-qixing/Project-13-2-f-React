# 工单093：书籍阅读器私有与重型文档格式正式解码器缺口

## 背景

`base.book` 电子书基础卡片会保存多种电子书资源。当前 Host 资源打开路由与 `Chips-BookReader` manifest 已能把 MOBI、AZW/AZW3、DJVU、DOC、DOCX 识别为电子书启动目标，阅读器也能消费 `chips.book-card` payload。

但这些格式需要专门的正式解码器，不能用临时解析、简化转换或未批准第三方库在应用内绕过。

## 证据

- `Chips-BookReader/manifest.yaml`
  - 已声明 MOBI、AZW/AZW3、DJVU、DOC、DOCX 的资源处理能力。
- `Chips-BookReader/src/utils/book-reader.ts`
  - `SUPPORTED_BOOK_EXTENSIONS` 与 `SUPPORTED_BOOK_MIME_TYPES` 已识别这些格式。
  - `READER_RENDERABLE_FORMATS` 当前只包含 EPUB/EPUB3、PDF、TXT/Markdown、FB2、RTF。
- `Chips-BookReader/src/domain/book/virtual-book.ts`
  - `loadReadableBook(...)` 对未接入正式解码器的格式会抛出明确错误。
- 当前生态技术选型
  - 没有已冻结的 MOBI/AZW/AZW3、DJVU、DOC、DOCX 跨平台解码依赖。
  - 没有 Host 公共文档解码或转换服务可供阅读器调用。

## 影响范围

- `Chips-BookReader` 无法在应用内渲染 MOBI、AZW/AZW3、DJVU、DOC、DOCX 正文。
- `base.book` 可以保存并打开这些格式，但用户会看到“尚未接入正式解码器”的错误。
- 后续搜索、摘要、转换、预览等能力如果要读取这些格式，也缺少统一底层能力。
- 如果各业务仓私自引入解析器，会造成格式支持矩阵、错误处理、安全策略和跨平台行为分叉。

## 复现步骤

1. 在电子书基础卡片中上传 `.mobi`、`.azw3`、`.djvu`、`.doc` 或 `.docx`。
2. 在查看态点击卡片。
3. Host 按 MIME 或扩展名命中 `Chips-BookReader`。
4. 阅读器读取 `chips.book-card` payload 并识别目标格式。
5. 阅读器加载层提示该格式尚未接入正式解码器，正文无法渲染。

## 期望行为

1. 生态冻结正式文档解码架构，明确以下责任归属之一：
   - 阅读器内置跨平台格式解码器；
   - Host 提供公共文档解码/转换服务；
   - 独立文档解码模块提供统一能力，再由阅读器消费。
2. 针对 MOBI/AZW/AZW3、DJVU、DOC、DOCX 分别补齐：
   - 格式结构解析；
   - 元数据读取；
   - 文本章节提取；
   - 图片和内嵌资源读取；
   - 错误报告；
   - 文件安全边界；
   - 跨平台测试样本。
3. 阅读器继续复用统一 `ReadableBook` 输出结构，不为每种格式散落独立 UI。
4. 共享技术文档记录正式支持矩阵、解码责任边界、权限要求和测试资源要求。
5. 每个格式都需要单元测试、启动链路测试和真实样本渲染验证。

## 暂行处理

- `Chips-BookReader` 已完成 EPUB/EPUB3、PDF、TXT/Markdown、FB2、RTF 的正式阅读链路。
- MOBI/AZW/AZW3/DJVU/DOC/DOCX 当前只作为可识别电子书启动目标进入阅读器。
- 对未接入正式解码器的格式，阅读器给出明确错误。
- 不引入未批准第三方库，不调用系统私有命令，不编写简化版格式解析器。
