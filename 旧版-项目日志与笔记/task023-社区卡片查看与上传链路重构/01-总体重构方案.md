# 社区卡片查看与上传链路总体重构方案

## 1. 最新决策

- 决策时间：2026-05-24
- 方案状态：替代早期“网页端直接读取远程 `.card` / Web Host Runtime 渲染”的方案。
- 架构方向：继续沿用当前社区服务器整体架构，不改成微服务架构。
- 主链路：`.card` 永久保存，服务器异步渲染网页查看缓存，用户访问缓存。

本任务不再要求开发 Web Host Runtime。社区网页端不直接解析 `.card`，而是打开服务器已经渲染好的查看缓存。渲染缓存只作为派生产物存在，不是卡片内容源文件；缓存失效或删除后，系统必须能基于永久保存的 `.card` 重新渲染。

## 2. 核心原则

1. `.card` 是社区卡片的唯一源文件，必须永久保存。
2. 官方本地上传器在用户设备上处理资源外置、链接替换和重新打包。
3. 社区服务器接收并保存处理后的 `.card`。
4. 社区服务器后台 Worker 异步生成网页查看缓存。
5. 封面缓存与完整查看缓存分离，封面只处理 `.card/cover.html` 和 `.card/cardcover/`。
6. 网页查看入口打开渲染缓存，不在用户浏览器里解析 `.card`。
7. 渲染缓存保存 30 天；每次成功访问后续期为“最后一次访问后 30 天”。
8. 超过 30 天无人访问的渲染缓存由清理任务删除；源 `.card` 不删除。
9. 缓存删除后再次访问时，系统重新入队渲染并生成新的缓存。
10. 渲染缓存必须版本化：源文件、渲染器、插件、主题、语言等关键输入变化时，不复用旧缓存。

## 3. 目标链路总览

```text
官方本地上传器
  -> 登录社区账号
  -> 读取本地 .card
  -> 上传卡片内资源到资源服务器
  -> 替换 .card 内部资源链接
  -> 重新打包处理后的 .card
  -> 上传处理后的 .card 到社区服务器

社区 API
  -> 校验上传会话、资源归属与 .card 结构
  -> 保存 .card 到永久源文件存储
  -> 写入 cards 元数据
  -> 创建渲染任务

社区 Worker
  -> 拉取永久 .card 源文件
  -> 使用服务器端正式 Host 渲染能力生成完整网页查看产物
  -> 单独提取 .card/cover.html 与 .card/cardcover/ 生成封面缓存
  -> 写入渲染缓存 / 封面缓存对象存储
  -> 更新 render cache 记录

用户查看
  -> 访问 /cards/:cardId
  -> open-view 返回 viewUrl / renderStatus
  -> viewUrl 校验权限并触摸缓存 TTL
  -> 缓存存在则 302 到渲染缓存入口
  -> 缓存缺失则触发重新渲染
  -> 列表封面通过 /api/v1/cards/:cardId/cover 独立续期
```

## 4. 本轮落地状态

当前 `Chips-CommunityPlatformServer` 已经从旧上传转换链路切换到源文件 + 渲染缓存链路：

1. `POST /api/v1/upload-sessions`、资源 presign、`POST /api/v1/upload-sessions/:uploadId/card` 已落地；
2. 网页兼容 `POST /api/v1/upload/card` 也改为保存处理后的 `.card` 源文件并入队渲染；
3. `.card` 源文件保存到 `chips-card-files/{userId}/{cardId}/source.card`，并记录 bucket/key/sha256；
4. 新增 `upload_sessions`、`upload_session_resources`、`card_render_jobs`、`card_render_caches`；
5. `community-web` 完整查看缓存与 `community-cover` 封面缓存分开生成、保存和续期；
6. `GET /api/v1/cards/:cardId/view` 命中缓存时续期并 302，缺失时创建渲染任务并返回 `202`；
7. `GET /api/v1/cards/:cardId/cover` 使用独立封面缓存，缺失时返回可嵌入的准备中 HTML；
8. Worker 使用 `ccps:card-render:queue` 和 `card_render_jobs` 生成缓存，并清理过期缓存；
9. 旧 `CardPipelineQueueService`、`runCardPipeline`、`card_pipeline_jobs` 正式源码已归档，迁移 `0003_drop_legacy_card_pipeline.sql` 删除旧表。

重构保持现有 API + Worker + PostgreSQL + Redis + S3 架构，不拆成微服务。

## 5. 上传链路

### 5.1 官方本地上传器职责

官方本地上传器以无界面模块插件形态提供 `community.card.publish/publish` job 能力，负责：

1. 登录社区账号；
2. 创建上传会话；
3. 解包并校验 `.card`；
4. 扫描卡片内部资源；
5. 向社区服务器申请资源上传目标；
6. 将资源直传到资源服务器 / 对象存储；
7. 将 `.card` 内部资源引用替换为正式资源 URL；
8. 移除已经外置的大体积资源；
9. 重新打包处理后的 `.card`；
10. 提交处理后的 `.card` 和资源 manifest；
11. 展示发布结果、渲染状态和社区入口。

官方本地上传器不负责服务器渲染、缓存保存、权限最终判断和对象存储长期密钥管理。

### 5.2 社区服务器职责

社区服务器负责：

1. 鉴权；
2. 创建上传会话；
3. 签发资源上传目标；
4. 接收处理后的 `.card`；
5. 校验 `.card` 文件结构、ZIP 路径安全、metadata、structure、content；
6. 校验资源 manifest 与本次上传会话一致；
7. 校验对象存储中资源存在、大小与摘要匹配；
8. 保存 `.card` 到永久源文件存储；
9. 写入 `cards` 元数据；
10. 创建渲染任务。

社区服务器不再把“上传成功”绑定为“HTML 已生成”。上传成功只表示源 `.card` 已经保存，网页查看缓存由 Worker 后续生成。

## 6. 渲染缓存链路

### 6.1 缓存定位

渲染缓存是从 `.card` 源文件派生出来的网页查看产物。它可以是 HTML 目录、静态资源目录、渲染 manifest 与封面产物的组合，但数据库和接口上统一称为 `renderCache`，避免把某一种具体格式变成源文件概念。

`.card` 源文件是长期可信数据；渲染缓存是可以删除、重建、失效和重新生成的派生数据。

当前缓存分为两个 profile：

- `community-web`：完整卡片查看缓存；
- `community-cover`：独立封面缓存，只包含 `.card/cover.html` 和 `.card/cardcover/` 所需文件。

### 6.2 缓存生成

触发缓存生成的场景：

1. 新卡片上传并校验通过；
2. 用户访问时发现缓存不存在；
3. 用户访问时发现缓存版本与当前渲染器 / 插件 / 主题不匹配；
4. 管理后台手动要求重新渲染；
5. 系统升级后批量重建热门卡片缓存。

渲染任务必须异步执行。上传接口只保证 `.card` 源文件保存成功，不同步等待渲染完成。

### 6.3 缓存访问与续期

用户查看时必须先经过社区受控 view endpoint：

```text
GET /api/v1/cards/:cardId/view
```

该 endpoint 负责：

1. 校验卡片权限；
2. 查找当前有效渲染缓存；
3. 如果缓存可用，更新 `lastAccessedAt` 与 `expiresAt = now + 30 days`；
4. 返回 302 到渲染缓存入口，或返回可嵌入的受控查看 URL；
5. 如果缓存缺失，创建渲染任务并返回 `202 rendering`；
6. 如果渲染失败，返回结构化错误和重试状态。

为了降低数据库写入压力，缓存续期可以采用合并写入策略：同一缓存短时间内多次访问只记录一次续期，再由后台批量刷新 `lastAccessedAt` 和 `expiresAt`。

封面访问必须先经过社区受控 cover endpoint：

```text
GET /api/v1/cards/:cardId/cover
```

该 endpoint 使用与 view 相同的权限与续期规则，但只查找 `community-cover` 缓存。封面缓存缺失时创建 `cover_miss` 任务，并返回可嵌入的准备中 HTML，避免列表 iframe 直接显示 JSON。

### 6.4 缓存清理

清理任务周期性扫描：

```text
render_cache.expires_at < now
```

清理步骤：

1. 将缓存记录标记为 `deleting`；
2. 再次读取记录确认没有被访问续期；
3. 删除对象存储中的缓存目录；
4. 如使用 CDN，发起对应路径清理或确保 CDN TTL 不超过缓存生命周期策略；
5. 将记录标记为 `deleted` 或写入删除时间。

清理任务只删除渲染缓存，不删除 `.card` 源文件、资源服务器中的正式卡片资源和内容元数据。

## 7. 查看链路

### 7.1 open-view

`GET /api/v1/cards/:cardId/open-view` 返回卡片详情页打开所需轻量信息：

1. 卡片标题、封面、作者；
2. 源文件状态；
3. 当前渲染缓存状态；
4. 独立封面入口 `coverUrl`；
5. `viewUrl`；
6. `renderStatusUrl`；
7. 如果缓存已可用，返回 `viewState = cache_ready`；
8. 如果缓存缺失或正在生成，返回 `viewState = rendering`。

前台不直接暴露长期渲染缓存裸地址，而是进入 `viewUrl`，由后端完成权限判断和 TTL 续期。

### 7.2 前台展示状态

社区前台应区分：

1. `source_missing`：源 `.card` 不存在或损坏，卡片不可恢复；
2. `source_ready`：源 `.card` 已保存；
3. `rendering`：渲染缓存生成中；
4. `cache_ready`：渲染缓存可打开；
5. `render_error`：渲染失败，可显示错误并允许拥有者重试；
6. `cache_expired`：缓存已清理，系统重新排队生成。

用户看到的是“正在准备查看内容”或“渲染失败”，不应再出现“必须生成 htmlUrl 才算卡片 ready”的旧语义。

## 8. 保留原架构的模块边界

继续使用当前总体架构：

1. Fastify API：认证、用户、房间、上传会话、内容元数据、open-view、view endpoint、后台接口；
2. PostgreSQL：用户、房间、卡片、上传会话、渲染任务、渲染缓存记录；
3. Redis：队列、短期锁、续期合并缓冲、认证辅助状态；
4. Worker：渲染任务消费、缓存生成、过期缓存清理、可选索引任务；
5. S3 / MinIO / 对象存储：源 `.card`、外置资源、完整渲染缓存、封面缓存、头像、其他封面。

架构优化重点是职责收口和队列分工，不做微服务化拆分。

## 9. 与旧方案的关系

本目录归档中的“直接转发 `.card` 给网页端 CardViewer”方案保留为历史记录，不再作为当前实施目标。

当前正式目标是：

```text
.card 永久源文件
  + 服务器异步渲染缓存
  + 访问续期 30 天
  + 过期缓存删除
  + 沿用当前社区服务器架构
```
