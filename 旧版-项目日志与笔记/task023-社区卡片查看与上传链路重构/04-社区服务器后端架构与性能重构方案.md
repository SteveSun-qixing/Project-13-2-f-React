## 3. 目标架构

继续使用当前总体形态：

1. Fastify API 进程；
2. PostgreSQL；
3. Redis；
4. Worker 进程；
5. S3 / MinIO / 对象存储；
6. Nginx / Edge；
7. 社区 Web 前台；
8. Admin 后台。

不拆微服务。重构重点是让现有模块职责更清晰：

```text
Fastify API
  -> 认证、上传会话、内容元数据、open-view、view endpoint、后台接口

Worker
  -> 渲染任务消费、渲染缓存生成、过期缓存清理、可选索引任务

PostgreSQL
  -> cards、upload_sessions、card_render_jobs、card_render_caches

Redis
  -> 渲染队列、短期锁、访问续期合并、认证辅助状态

S3 / MinIO
  -> 永久 .card 源文件、外置资源、完整查看缓存、封面缓存
```

## 4. 原架构问题与本轮处理

本轮重构前社区服务器实际问题：

1. 上传后直接进入旧 pipeline，上传、资源替换、HTML 转换和数据库状态强绑定；
2. `.card` 源文件没有作为永久主文档保存；
3. `htmlUrl` 被当作卡片可查看的主入口；
4. 渲染产物没有独立缓存生命周期；
5. 没有最后访问后 30 天续期和清理机制；
6. Worker 的职责是“上传后转换完成才 ready”，不是“源文件 ready 后异步生成可重建缓存”；
7. 列表和打开热路径需要继续避免读取大 JSONB。

本轮已处理：

1. 源 `.card` 保存到 `chips-card-files` 并记录 bucket/key/sha256；
2. 上传会话、资源 presign、处理后 `.card` 提交接口已落地；
3. 完整查看缓存 `community-web` 和封面缓存 `community-cover` 已分离；
4. `card_render_jobs` / `card_render_caches` 替代旧 `card_pipeline_jobs`；
5. `view` 与 `cover` endpoint 命中缓存时续期到最后一次访问后 30 天；
6. Worker 负责渲染缓存生成和过期缓存清理；
7. `open-view` 不再依赖 `htmlUrl` 判断是否可打开；
8. 旧 pipeline 正式源码已归档，迁移删除旧表。

## 5. 目标模块职责

### 5.1 Fastify API

职责：

- 认证、鉴权、统一错误；
- 上传会话创建；
- 资源上传目标签发；
- 处理后 `.card` 提交；
- `.card` 结构预检和 manifest 校验；
- 保存源 `.card` 到对象存储；
- 写入 `cards` 元数据；
- 创建渲染任务；
- `open-view` 返回轻量打开信息；
- `view` endpoint 权限校验、缓存续期、302 或 202；
- `render-status` 状态查询；
- 后台管理接口。

API 不在请求内执行渲染，不同步等待 Worker 完成。

### 5.2 Worker

职责：

- 消费渲染任务队列；
- 从 `chips-card-files` 拉取源 `.card`；
- 使用服务器端正式 Host 渲染能力生成网页查看产物；
- 只加载查看所需插件模块；
- 富文本只加载 renderer，不加载 editor；
- 上传完整查看产物到 `chips-card-render-cache`；
- 上传封面产物到 `chips-card-cover-cache`；
- 更新 `card_render_caches`；
- 扫描并删除过期渲染缓存；
- 处理失败重试和死信记录。

Worker 继续复用现有 `worker.ts` 入口，任务语义已经从“上传转换”改成“渲染缓存任务”。

### 5.3 PostgreSQL

职责：

- 保存内容元数据；
- 保存上传会话；
- 保存资源 manifest；
- 保存渲染任务；
- 保存渲染缓存生命周期字段。

打开热路径只读取轻量列，不读取完整 metadata / structure / manifest。

### 5.4 Redis

职责：

- 渲染任务队列；
- 渲染任务短锁；
- 缓存访问续期合并；
- 登录失败计数和 refresh token 吊销等现有认证辅助状态。

热门卡片每次访问都直接写 PostgreSQL 会造成写放大，因此建议：

```text
view endpoint -> Redis 记录 cacheId 最近访问时间
后台 flush -> 批量更新 card_render_caches.lastAccessedAt / expiresAt
```

第一阶段也可以直接写 PostgreSQL，但必须保留升级为合并写入的设计。

### 5.5 对象存储

逻辑 bucket：

```text
chips-card-files
chips-card-resources
chips-card-render-cache
chips-card-render-cache-private
chips-card-cover-cache
chips-card-cover-cache-private
chips-avatars
chips-covers
```

职责：

- `chips-card-files`：永久 `.card` 源文件；
- `chips-card-resources`：外置资源；
- `chips-card-render-cache` / `chips-card-render-cache-private`：完整查看 30 天访问续期缓存；
- `chips-card-cover-cache` / `chips-card-cover-cache-private`：封面 30 天访问续期缓存；
- `chips-avatars` / `chips-covers`：现有用户和封面资源。

## 6. 查看热路径性能

### 6.1 缓存命中

```text
GET /cards/:cardId
  -> open-view 轻量查询
  -> iframe/navigate 到 /api/v1/cards/:cardId/view
  -> 权限校验
  -> render cache hit
  -> touch 续期
  -> 302 到对象存储 / CDN 缓存入口
```

性能目标：

- `open-view` 不读取大 JSONB；
- `view` 只读权限字段和缓存索引；
- 缓存静态内容由对象存储 / CDN 承担流量；
- 访问续期写入要合并，避免热门卡片每次请求都写数据库。

封面热路径独立于完整查看缓存：

```text
GET /api/v1/cards/:cardId/cover
  -> 权限校验
  -> community-cover cache hit
  -> touch 续期
  -> 302 到封面缓存入口
```

列表页只加载封面缓存，不触发完整查看缓存下载。

### 6.2 缓存未命中

```text
GET /api/v1/cards/:cardId/view
  -> 权限校验
  -> render cache miss
  -> 去重创建 render job
  -> 返回 202 rendering
  -> 前台轮询 render-status
  -> 渲染完成后再次进入 view
```

性能目标：

- 同一版本键只有一个活跃渲染任务；
- 热门卡片缓存过期后不会形成并发渲染风暴；
- 用户触发的 miss 任务优先级高于后台批量任务。

## 7. 上传热路径性能

```text
官方上传器
  -> 资源直传对象存储
  -> 提交处理后的 .card
  -> API 流式接收并保存源文件
  -> 创建内容记录
  -> 异步触发渲染
```

要求：

- 大资源不经过社区 API；
- `.card` 源文件保存使用流式写入；
- 上传会话有 TTL、并发限制、大小限制；
- 资源 manifest 校验不读取不必要大对象；
- 上传成功不等待渲染完成。

## 8. 缓存版本与失效

渲染缓存版本键：

```text
rendererVersion
renderProfile
themeId
locale
sourceCardSha256
```

当前 renderProfile：

- `community-web`：完整查看缓存；
- `community-cover`：封面缓存。

当前 `card_render_caches` 表保留了 `pluginVersionManifest` 与 `themeVersion` 字段，便于后续接入插件和主题版本感知；但本轮真实生效的 `cacheVersion` 由 `rendererVersion`、`renderProfile`、`themeId`、`locale`、`sourceCardSha256` 组成，不把暂未采集的插件版本自动写入版本键。

失效场景：

1. 源 `.card` 更新；
2. 渲染器版本升级；
3. 激活主题 ID 变化；
4. 语言或渲染 profile 变化；
5. 管理后台强制重渲染；
6. 缓存超过最后访问后 30 天。

失效后旧缓存不再被 open-view 选中。旧对象可以立即删除，也可以由清理任务统一删除，但不能继续作为当前查看入口。

## 10. 对象存储与 CDN 策略

### 10.1 源 `.card`

- 永久保存；
- 公开卡片可以允许受控下载；
- 私有卡片必须鉴权或短时签名；
- 删除卡片时才删除源 `.card`。

### 10.2 外置资源

- 由上传器直传；
- URL 写入 `.card`；
- 私有卡片需要同步设计资源权限，不能只保护 `.card`；
- 删除卡片时按资源 manifest 清理。

### 10.3 渲染缓存

- 放在 `chips-card-render-cache`；
- 按 `{cardId}/{cacheVersion}/` 隔离；
- `Cache-Control` 可使用较长静态缓存，但 CDN TTL 必须和删除策略配合；
- 如果业务要求“30 天后不可继续从 CDN 命中”，需要在删除时 purge CDN 或设置 CDN TTL 不超过清理周期。

## 11. 安全边界

上传安全：

- ZIP path traversal 防护；
- entry 数量、单文件大小、总展开大小限制；
- manifest 和对象存储 Head 校验；
- 资源 URL 来源校验；
- 用户配额与并发限制；
- 本地上传器不保存对象存储长期密钥。

渲染安全：

- Worker 渲染任务有超时和内存限制；
- 临时目录必须在任务结束后清理；
- cover.html 和卡片内容不得直接注入社区 DOM；
- 插件只加载正式 renderer 能力；
- 渲染产物上传前做路径安全校验。

查看安全：

- 私有卡片 view endpoint 必须鉴权；
- 无权访问按 404；
- 不向前台返回私有缓存长期裸 URL；
- 删除、封禁、可见性变化必须立即使 view endpoint 失效。

## 12. 部署演进

### 12.1 第一阶段

保持当前 Compose 形态：

```text
server
worker
web
admin
postgres
redis
object storage
nginx
```

调整职责：

- `server`：上传会话、源文件保存、view endpoint；
- `worker`：渲染缓存生成与清理；
- `nginx`：缓存对象访问、Range、静态缓存头策略。

### 12.2 第二阶段

仍不拆微服务，但可以拆 Worker 职责进程：

```text
worker-render
worker-cleaner
worker-index
```

这样可以让渲染任务和清理任务互不阻塞，同时继续使用同一代码库、同一数据库和同一部署体系。

## 14. 关键验收标准

服务器：

- 上传成功后源 `.card` 永久保存；
- 渲染缓存可以删除并重新生成；
- 普通 API 不在请求内执行渲染；
- `open-view` 不依赖 `htmlUrl`；
- `view` endpoint 每次成功查看都会让缓存续期到 30 天后；
- 清理任务只删除过期渲染缓存。

性能：

- 公开缓存内容由对象存储 / CDN 承担流量；
- 大资源上传不经过社区 API；
- 热门卡片不会因续期产生过量数据库写入；
- 同一缓存版本不会并发重复渲染。

前台：

- 缓存 ready 时直接查看；
- 缓存 missing 时显示准备中；
- 渲染失败有明确错误态；
- 缓存清理后再次访问可重新生成。
