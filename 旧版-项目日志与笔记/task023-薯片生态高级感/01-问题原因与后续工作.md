# 薯片生态高级感：问题原因与后续工作

> 日期：2026-05-26
> 文档性质：任务分析与后续方案，不是正式公共契约。
> 关联背景：task022 已完成组件库、主题系统、AppRuntime、命令系统、脚手架和应用迁移等大规模重构后，当前 UI 与前端框架仍缺少统一的高级感。
> 关联工单：`工单114-前端框架视觉产品化与高级感闭环缺口`

> 2026-05-26 追加执行口径：本轮实施计划已收窄为“先升级主题包、再把应用私有控件替换为组件库已有正式组件”。组件库尚未提供的产品级壳层或领域组件不在本轮实现范围内，只登记到 `缺少的组件.md`，详见 `02-实施计划-主题包升级与组件替换.md`。

## 1. 总结判断

task022 解决的是“生态前端是否统一、能否运行、能否接入主题、能否通过契约验证”的问题；task023 要解决的是“生态视觉是否成熟、统一、有产品感、能否稳定复用和验收”的问题。

当前 UI 没有高级感，不是因为 task022 完全失败，而是因为 task022 的主要交付物集中在架构、运行时、组件契约、主题注入、质量脚本和迁移链路。它让生态从“散”变成“可治理”，但还没有把薯片生态沉淀成一套产品级视觉语言。

高级感不是给按钮加一点阴影、给背景加渐变、把圆角调大就能得到。它需要主题包、组件库、应用壳层、页面结构、动效节奏、图标字体、真实素材、视觉回归和人工验收共同闭环。

## 2. 当前已具备的基础

### 2.1 主题与组件职责边界已经正确

生态设计已经明确：组件库只提供结构、状态与交互，不承载视觉样式；真正生效的颜色、字体、圆角、阴影、边框、动效与图标由主题包提供。

这说明当前不能把“缺少高级感”简单归因给组件库。组件库的职责是把每个组件的结构、状态、part、a11y、键盘交互和 token 接口点暴露出来；视觉质量最终要由主题包和应用组合体系承担。

### 2.2 主题运行时链路已经有正式方向

Host 主题链路已经要求从已启用主题插件读取主题，注入完整主题 CSS、解析后的变量、`data-chips-theme-id` 和 `data-chips-theme-version`，应用壳层通过 `ChipsThemeProvider` 或等价运行时从 Host 当前主题初始化。

这给高级感建设提供了基础：只要主题包和应用壳层做对，应用窗口、卡片窗口、iframe 内容和原生窗口背景可以共享同一套视觉来源。

### 2.3 组件 contract 与 token 覆盖已经变多

组件库已经覆盖大量正式组件和 token 命名，包括文本、图标、基础控件、输入控件、选择控件、媒体控件、复杂 compound 组件、命令消费组件、表单、数据网格、树、工作台、系统 UX、布局原语和卡片运行时组件。

这意味着高级感的下一步不是从零造控件，而是基于这些已有 contract，把主题视觉、应用壳层和真实应用样张做深。

## 3. 为什么现在仍然不高级

### 3.1 默认主题只是功能型浅色基线，不是高级视觉语言

`ThemePack/Chips-default` 当前视觉规范定位是“简约 / 清透 / 克制 / 易读 / 工具型”。这是一套合理的功能型浅色基线，但不是完整的品牌级高级视觉系统。

它当前更强调可读、克制、浅色、工具型、基础可访问性和控件可用性。这样的主题天然会显得干净、稳定，但也容易显得普通、平、缺少记忆点。

后续如果要“高级感”，必须先定义薯片生态官方视觉目标，例如：

- 是专业工具型的高级感；
- 是卡片内容创作型的高级感；
- 是媒体沉浸型的高级感；
- 是阅读/知识管理型的高级感；
- 还是统一品牌主题下按场景变体分化。

在目标未冻结前，只靠调 CSS 很容易变成局部审美叠加。

### 3.2 主题 CSS 仍偏基础控件皮肤，没有形成应用级视觉系统

默认主题当前的 CSS 主要完成以下工作：

- 全局背景、文字、基础半径、基础间距、基础阴影、focus ring；
- 图标字体落地；
- 按钮、输入、弹层、表单、反馈、布局容器等组件的基础状态；
- `hover / active / focus / disabled / error / loading` 等可用状态。

这些能力能让组件“像一个统一组件库”，但还不足以让应用“像一个高级产品”。高级应用还需要：

- 页面级背景和内容区层级；
- 专业工具壳层；
- 顶栏、侧栏、状态栏、命令区、检查器、资源区的层次关系；
- 媒体、阅读、编辑器、设置面板等不同场景的视觉组织；
- 图标、文本、密度、留白和动效之间的一致节奏；
- 真实窗口尺寸下的构图样张。

### 3.3 应用仍保留大量私有视觉系统

虽然应用已经接入部分组件库和主题运行时，但多个应用仍有自己的私有 CSS 体系，例如：

- `--photo-viewer-*`
- `--video-player-*`
- 旧 `--chips-color-*`
- 应用私有阴影、圆角、字体、渐变、透明浮层；
- `transition: all`
- `outline: none`
- 旧式硬编码 `box-shadow / border-radius / background / font-family`

这会造成一个很典型的现象：每个应用看起来都“还行”，但放到一起不像同一个生态。主题 Provider 已经在，但应用仍然在局部维护自己的皮肤。

这不是要禁止所有应用 CSS。问题在于应用 CSS 应该只做业务布局 glue code 和少量场景组合，而不应该长期维护自己的基础色板、阴影系统、控件状态和壳层视觉。

### 3.4 缺少产品级壳层组件

当前组件库已经有很多基础组件，但“高级感”主要来自可复用的产品壳层和组合模式，而不是单个按钮。

目前缺少或尚未产品化的关键壳层包括：

- `ChipsAppShell`
- `ChipsWorkbenchShell`
- `ChipsMediaShell`
- `ChipsReaderShell`
- `ChipsSettingsShell`
- `ChipsCommandDock`
- `ChipsStatusBar`
- `ChipsActivityBar`
- `ChipsInspectorField`
- `ChipsPropertyGrid`
- `ChipsResourcePanel`
- `ChipsTaskProgressCenter`

没有这些高层组件，应用开发者就会继续在各自项目里写页面框架、面板、浮层、工具条和状态栏。结果就是基础控件统一了，但产品界面仍然不统一。

### 3.5 质量门禁能证明“正确”，不能证明“高级”

当前质量门禁主要覆盖：

- token 是否存在；
- contract 是否匹配；
- 类型是否通过；
- 单元测试是否通过；
- a11y 和部分性能是否达标。

这些门禁很重要，但它们不评价：

- 页面是否有视觉层次；
- 应用之间是否像同一生态；
- 暗色主题是否真的有质感；
- 主题切换是否有完整截图验证；
- 真实素材下是否好看；
- 同一页面在不同窗口尺寸是否构图稳定；
- 文案、图标、密度和动效是否协调。

所以当前出现“测试通过但不高级”是正常结果。因为我们还没有把视觉质量变成可验证对象。

### 3.6 缺少真实应用样张和验收矩阵

高级感必须看真实窗口、真实素材、真实流程。

当前缺少面向第一版发布的视觉样张矩阵，例如：

- 设置面板首页、插件治理页、主题治理页、诊断页；
- 图片查看器打开真实图片、空态、错误态、命令浮层；
- 视频播放器打开真实视频、控制条、侧栏、字幕/音轨面板；
- 阅读器打开真实书籍、目录、阅读面板、设置面板；
- 富文本编辑器编辑状态、预览状态、保存反馈；
- 编辑引擎工作台、画布、检查器、资源面板、卡片窗口；
- 卡片查看器、复合卡片窗口、基础卡片 iframe；
- 默认主题、暗色主题和未来专业主题的并排对照。

没有这些样张，就无法定义“高级感达标”。

## 4. 接下来需要做什么

task023 不应该从“修某个页面颜色”开始，而应该按视觉产品化链路推进。

### 4.1 第一阶段：冻结高级感目标与验收样张

目标：先定义什么叫“薯片生态的高级感”。

需要完成：

1. 编写 `01-高级视觉目标定义`：
   - 官方默认主题的气质；
   - 暗色主题的气质；
   - 专业工具场景的气质；
   - 媒体/阅读/编辑场景是否需要场景化壳层。
2. 建立视觉关键词到工程指标的映射：
   - 层次；
   - 密度；
   - 留白；
   - 边界；
   - 阴影；
   - 动效；
   - 图标；
   - 字体；
   - 内容构图；
   - 状态反馈。
3. 选定第一批真实样张页面：
   - 设置面板；
   - 图片查看器；
   - 视频播放器；
   - 阅读器；
   - 富文本编辑器；
   - 编辑引擎；
   - 卡片查看器。
4. 形成验收标准：
   - 默认主题截图；
   - 暗色主题截图；
   - 空态、加载、错误、成功、禁用、选中、焦点状态；
   - 桌面窗口常用尺寸；
   - 真实素材。

### 4.2 第二阶段：主题包视觉语言升级

目标：让主题包从“控件皮肤”升级为“产品视觉系统”。

需要完成：

1. 扩展 `ref/sys` 色彩：
   - 页面背景；
   - 画布背景；
   - 内容区背景；
   - 侧栏背景；
   - 工具栏背景；
   - 浮层背景；
   - 玻璃/半透明表面；
   - 选中、悬停、拖拽、drop-target 等状态。
2. 扩展阴影与边界 token：
   - 平面边界；
   - 浮层阴影；
   - 媒体控制浮层；
   - 阅读内容纸面；
   - 工作台面板分隔。
3. 扩展字体与图标 token：
   - 标题、正文、说明、数值、代码、元信息；
   - Toolbar 图标、导航图标、状态图标、强调图标；
   - Material Symbols 轴值在不同场景下的默认策略。
4. 扩展 motion token：
   - 页面切换；
   - 面板打开/关闭；
   - 菜单和命令面板；
   - 媒体控制条显隐；
   - 拖拽反馈；
   - reduced motion 降级。
5. 更新默认主题和暗色主题：
   - 两者必须同步补齐；
   - 不在单包内混合 light/dark；
   - 每个 themeId 只承载一种正式外观。

### 4.3 第三阶段：组件库补齐产品级壳层

目标：减少应用私有页面框架，让高级感可以复用。

建议优先补齐：

1. `ChipsAppShell`
   - 顶部/侧边/内容/状态区域；
   - 命令入口；
   - 全局错误、加载和通知槽位。
2. `ChipsWorkbenchShell`
   - 活动栏；
   - 资源区；
   - 编辑区；
   - 检查器；
   - 底部状态栏；
   - 面板尺寸与分隔规则。
3. `ChipsMediaShell`
   - 沉浸画布；
   - 控制条；
   - 侧边信息面板；
   - 时间轴；
   - 快捷操作区。
4. `ChipsReaderShell`
   - 阅读背景；
   - 内容纸面；
   - 目录/书签/设置面板；
   - 阅读进度和浮动控制。
5. `ChipsSettingsShell`
   - 设置导航；
   - 分组页面；
   - 治理列表；
   - 详情区；
   - 诊断状态。
6. 表单与检查器增强：
   - `ChipsInspectorField`;
   - `ChipsPropertyGrid`;
   - `ChipsKeyValueEditor`;
   - `ChipsResourcePicker`;
   - `ChipsFileDropZone`;
   - `ChipsTaskProgressCenter`。

这些组件必须保持组件库边界：只提供结构、状态、a11y 和主题接口点，不硬编码业务视觉。

### 4.4 第四阶段：应用私有样式治理

目标：把应用从“各自好看”迁移到“生态统一”。

需要对每个应用建立样式迁移清单：

1. 搜索私有 token：
   - `--photo-viewer-*`
   - `--video-player-*`
   - `--chips-color-*`
   - `--rte-*`
   - 其他应用私有基础视觉变量。
2. 搜索硬编码视觉值：
   - `box-shadow`;
   - `border-radius`;
   - `background`;
   - `linear-gradient`;
   - `font-family`;
   - `transition: all`;
   - `outline: none`。
3. 分类处理：
   - 属于通用视觉能力的，上沉到主题 token；
   - 属于通用结构的，上沉到组件库壳层；
   - 属于真实业务素材的，保留在应用层；
   - 属于历史临时样式的，迁移或归档。
4. 应用迁移顺序建议：
   - 先迁移设置面板，因为它最能代表生态治理界面；
   - 再迁移图片/视频/阅读器，因为它们需要场景化壳层；
   - 再迁移富文本和编辑引擎，因为它们需要工作台壳层；
   - 最后迁移卡片查看器和卡片 iframe 样式，保证卡片内容与应用窗口一致。

### 4.5 第五阶段：视觉质量门禁

目标：让高级感可验证。

需要建立：

1. 主题矩阵预览：
   - 所有正式组件；
   - 所有关键状态；
   - 默认主题和暗色主题；
   - 不同密度。
2. 真实应用截图：
   - 每个重点应用至少 3 到 5 个关键状态；
   - 使用真实素材；
   - 覆盖常用窗口尺寸。
3. 视觉回归阈值：
   - 截图对比；
   - 布局溢出检测；
   - 文本遮挡检测；
   - 空白/未加载检测。
4. 主题切换验证：
   - 当前主题；
   - 切换后主题；
   - iframe 刷新；
   - 原生窗口背景；
   - 应用根节点数据属性。
5. 人工设计评审清单：
   - 层次是否清晰；
   - 密度是否合理；
   - 控件是否像同一系统；
   - 图标是否统一；
   - 动效是否克制；
   - 暗色主题是否不是简单反色；
   - 真实内容是否比空态更好看。

## 5. 不应该做什么

### 5.1 不要做临时视觉补丁

不要为了短期看起来高级，直接在应用里加私有渐变、厚阴影、大圆角、模糊背景或大量透明浮层。

这会让生态更不统一，也会让主题系统失去意义。

### 5.2 不要把视觉职责塞回组件库

组件库是 L10 Headless。它可以补结构、状态、part、slot、contract、a11y 和键盘行为，但不应该把某个主题的视觉写死在组件实现中。

### 5.3 不要只做默认主题

默认主题和暗色主题必须同步升级。生态规则已经明确一个主题包只承载一种外观，暗色外观必须作为独立 `themeId` 交付。

### 5.4 不要用测试通过代替视觉验收

contract、token、typecheck、unit test 通过，只能证明工程可用。高级感必须通过真实截图、真实素材、真实状态和人工设计评审来验收。
