# 工单121：社区卡片完整回下载与源文件直传契约缺口

## 背景

目标社区体验要求用户把本地制作完成的 `.card` 像 Word 文档、图片一样上传到社区，网页可以直接查看，之后也可以从网页下载保存完整卡片文件。

当前卡片上传与查看主链路已经具备上传会话、资源预签名、源 `.card` 私有保存、view/cover 渲染缓存和网页插件宿主。但核对现有代码与契约后发现，完整回下载与低性能服务器友好的源文件直传还没有形成正式闭环。

## 证据

1. 公共 API 契约明确把“社区内 `.card` 回下载”列为当前不在契约范围内的内容：`生态共用技术文档/协议与契约/09-社区平台API契约.md`。
2. 当前 `cards` 表保存了 `source_card_bucket`、`source_card_key`、`source_card_sha256`，但 `CardService.toDTO` 只暴露 `sourceCardSha256`、`viewUrl` 和 `renderStatusUrl`，没有源文件下载入口：`Chips-CommunityPlatformServer/packages/server/src/db/schema/cards.ts`、`Chips-CommunityPlatformServer/packages/server/src/services/card.service.ts`。
3. `cards.ts` 只有详情、open-view、status、render-status、view、cover、私有缓存代理、更新、删除和列表路由，没有 `download` / `source` / attachment 响应路由：`Chips-CommunityPlatformServer/packages/server/src/routes/cards.ts`。
4. 当前上传会话只给资源文件预签名，处理后的 `.card` 仍通过 `POST /api/v1/upload-sessions/:uploadId/card` multipart 进入 API 进程，再由服务器上传到 `chips-card-files`：`Chips-CommunityPlatformServer/packages/server/src/routes/upload.ts`、`Chips-CommunityPlatformServer/packages/server/src/services/upload-session.service.ts`。
5. `Chips-CommunityUploader-Plugin` 会在用户设备上把资源外置、改写 URL、删除已外置资源并重新打包处理后的 `.card`，因此服务器当前保存的发布源文件可能是“网页发布态处理包”，不是用户最初上传的全填充离线原始包：`Chips-ModulePlugin/Chips-CommunityUploader-Plugin/src/publisher.ts`。

## 影响范围

- 社区网页“下载完整卡片文件”的用户体验；
- 公开卡片和私有卡片的下载权限、签名 URL、审计和限流；
- 上传链路的数据面流量，尤其弱服务器处理大 `.card` 的压力；
- CommunityUploader、社区 API、对象存储 bucket 结构、数据库模型与公共 API 契约；
- “网页查看态处理包”和“用户原始完整包”之间的长期语义边界。

## 复现步骤

1. 上传一个包含本地图片、音频或视频资源的 `.card`；
2. 使用 CommunityUploader 正式发布链路时，观察上传模块会把资源 PUT 到预签名 URL，并把 `.card` 内部引用改成公开 URL 后重新打包；
3. 查看社区服务端 `cards` 记录，确认只保存一组 `source_card_bucket/key/sha256`；
4. 查看 `GET /api/v1/cards/:cardId` 与 `GET /api/v1/cards/:cardId/view`，确认只有查看缓存入口，没有源 `.card` 下载入口；
5. 若直接把当前 `source.card` 暴露为下载文件，用户拿到的可能是带 CDN URL 的处理包，而不是原始完整离线包。

## 期望行为

- 社区应区分至少两种卡片源：
  - 原始完整包：用户本地保存/上传的完整 `.card`，用于回下载、备份、迁移和离线打开；
  - 发布处理包：资源已外置、URL 已改写、面向网页渲染和缓存生成的 `.card`。
- 上传会话应支持源 `.card` 预签名直传到私有对象存储，API 只负责签发、提交、Head 校验、记录元数据和排队校验/渲染，不承担大文件数据面中转。
- 下载接口应返回用户期望的“完整卡片文件”，并按权限、作者设置、未来授权策略和审计要求控制访问。
- 对旧的仅保存处理包的记录，应有明确迁移或重新上传策略，不把处理包伪装成完整离线包。

## 暂行处理

本轮只登记缺口，并在上传链路调查笔记与 task-027-使用体验调查报告中给出推荐方案，不改动生产接口和数据结构。后续实施前需要先冻结公共契约，再同步修改 CommunityUploader、社区服务端、数据库迁移、网页端下载入口和验证用例。

## 需要协作方

- 社区服务器维护方
- CommunityUploader 模块维护方
- Host / SDK 卡片打包与校验能力维护方
- 对象存储与部署维护方

# 工单123：网络资源卡片渲染队列依赖 sourceCardSha256 导致查看缓存永不生成

## 背景

- 按 task027 新决策，网络资源卡片上传时不强制计算 SHA-256（P2-11），`card-transfer` complete 阶段把 `cards.sourceCardSha256` 置为 null；
- 但社区渲染缓存链路（`CardRenderCacheService`）的入队、版本号、缓存匹配、Worker 渲染都强依赖 `sourceCardSha256`；
- 本地实机验证：通过 `community.card.transfer/upload` 上传卡片后，`render-status` 一直为 `rendering`，`card_render_jobs` 无任务，网页查看缓存永不生成。

## 证据

- `card-render-cache.service.ts:183`：`if (!card || !card.sourceCardSha256 || ...) return null;` —— 无 SHA-256 直接不入队；
- `card-render-cache.service.ts:413` / `:529`：`renderViewJob` / `renderCoverJob` 要求 `sourceCardSha256`；
- `card-render-cache.service.ts:50`：`createCacheVersion` 用 `card.sourceCardSha256 ?? 'missing-source'` 生成缓存版本；
- `card-render-cache.service.ts:238` / `:246`：`findReadyCache` 按 `sourceCardSha256` 匹配已有缓存；
- `card-transfer.ts:374`：complete 设置 `sourceCardSha256: null`。

## 影响范围

- `card-transfer` 上传链路生成的卡片渲染缓存；
- 网页查看缓存与封面缓存生成；
- `card_render_jobs` / `card_render_caches` 的 SHA-256 依赖。

## 复现步骤

1. 启动本地服务端（API + Worker）；
2. `chipsdev module invoke` 调用 `community.card.transfer/upload` 上传 .card；
3. 轮询 `GET /api/v1/cards/{cardId}/render-status`，观察一直 `rendering`；
4. 查 `card_render_jobs`，无任务被创建。

## 期望行为

- 网络资源卡片用自身版本标识（sourceCardKey 对象键 / 版本 ID）作渲染缓存键；
- 无 SHA-256 也能入队并生成查看/封面缓存；
- 旧链路（有 SHA-256）行为不变。

## 暂行处理

- 已修复：渲染缓存链路支持无 SHA-256 的网络资源卡片，用 `sourceCardKey` 派生稳定版本标识。

## 需要协作方

- 社区服务器渲染缓存维护方
- task027 传输链路维护方

## 当前状态

- 已处理（见 task027 阶段修复记录）

# 工单125：应用插件渲染进程访问社区 HTTP API 的 CORS 链路缺口

## 背景

- 开发薯片社区客户端（`com.chips.community-client`，type: app）时，客户端核心职责是浏览社区内容（用户主页、卡片、箱子等），需要调用社区服务器 HTTP API；
- 社区服务器生产环境 CORS 只允许 `BASE_URL` 同源或 `!origin`（无 Origin 头）请求（`packages/server/src/app.ts:46-59`）；
- 应用插件运行在 Host 渲染进程，页面通过 `file://` 或 `chips-render://` 协议加载；渲染进程 `fetch` 社区 API 时，请求会携带非空 Origin（`file://` 或 `chips-render://...`），生产环境会被 CORS 拒绝；
- SDK / Host 当前没有正式的网络请求封装或网络代理 Bridge，应用插件访问外部 HTTP API 缺少统一正式链路。

## 证据

- `Chips-CommunityPlatformServer/packages/server/src/app.ts:54`：`if (!origin || origin === env.BASE_URL)`，生产只放行同源或空 Origin；
- `Chips-Host/src/main/electron/render-document-protocol.ts`：`chips-render` 注册为 standard+secure 协议，渲染进程页面拥有独立 origin；
- `Chips-SDK/src/types/client.ts`：`Client` 域名 API 中没有 network/http 请求能力；
- `生态共用技术文档/协议与接口标准/05-系统接口标准.md`：服务域总表中没有网络请求域；
- 社区 Web 前端通过同源 `/api` 代理（Vite/Nginx）访问，不跨域；桌面客户端没有同源代理。

## 影响范围

- 薯片社区客户端等所有需要访问外部 HTTP API 的应用插件；
- 社区平台 API 契约的"客户端"消费场景；
- Host 渲染进程对外部网络资源的正式访问链路。

## 复现步骤

1. 以 `NODE_ENV=production`、`BASE_URL=https://www.chipscard.space` 启动社区服务器；
2. 在应用插件渲染进程 `fetch('https://www.chipscard.space/api/v1/discover/cards')`；
3. 观察请求因 CORS 被拒绝（Origin 非空且不等于 BASE_URL）。

## 期望行为

- 建立应用插件渲染进程访问外部 HTTP API 的正式链路，二选一（或组合）：
  - 社区服务器生产 CORS 放行薯片 Host 客户端来源（如 `chips-render://` 或空 Origin 的客户端请求）；
  - Host 提供正式网络请求能力（如 `network.request` 域），由 Host 主进程代理，绕开渲染进程 CORS 限制；
- 对应 SDK 类型化封装、权限模型、CSP 基线同步收口；
- 更新社区平台 API 契约与系统接口标准。

## 暂行处理

- 本轮薯片社区客户端开发使用社区服务器开发模式（`NODE_ENV=development`，CORS 全放行）联调；
- 生产部署依赖本工单收口后正式链路，不在客户端内自建临时网络桥；
- 客户端 CSP `connect-src` 在开发阶段放行社区 API 来源，正式链路收口后按 Host 统一基线调整。

## 需要协作方

- 社区服务器维护方（CORS / 客户端来源放行）
- Host 维护方（网络请求能力与权限模型）
- SDK 维护方（类型化封装）

## 修复说明（2026-08-05）

已在社区服务器侧收口客户端访问链路：

1. **CORS 放行客户端来源**：`Chips-CommunityPlatformServer/packages/server/src/app.ts` 生产模式新增放行：
   - Origin 以 `chips-render:` 开头的薯片 Host 客户端来源；
   - `null` Origin（file:// 页面加载的客户端）；
   - `CORS_EXTRA_ORIGINS` 环境变量白名单（逗号分隔）中的来源；
