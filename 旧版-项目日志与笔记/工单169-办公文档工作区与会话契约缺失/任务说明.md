# 工单169：办公文档工作区与会话契约缺失

## 工单信息

- 工单编号：工单169
- 日期：2026-09-01
- 发现阶段：Chips-Word 新建、打开与保存链路复核
- 问题类型：Host / SDK 工作区公共契约缺口、Office 文档会话缺口
- 状态：已处理（2026-09-02）

## 背景

产品要求 Word、Slide、Sheet、PDF 应用插件创建的新文件直接保存在当前薯片工作区，并参考编辑引擎的正式创建与保存链路。复核代码后确认，编辑引擎当前正式工作区和自动保存能力只覆盖 `.card` 与 `.box`，生态尚未提供可供 Office 原格式文档复用的工作区定位、文件登记或文档会话契约。

本问题与工单165的“GenOffice 能力迁移边界”及工单168的“Word 移植残留”相关，但阻断点属于 Host / SDK 公共能力，不能在单个 Word 插件内部解决。

## 证据

1. `Chips-SDK/src/api/workspace.ts` 的 `WorkspaceApi` 只有 `scan(rootPath)`；SDK 不提供获取当前 Host 工作区根路径的正式方法。
2. `WorkspaceFileView.type` 只有 `card | box | folder`。`Chips-Host/packages/workspace-service/src/workspace-service.ts` 扫描时只登记卡片、箱子和文件夹，普通 `.docx/.pptx/.xlsx/.pdf` 文件会被忽略。
3. `Chips-SDK/src/api/document.ts` 的文档类型只覆盖 `card | box`；SDK 和 Host 没有 Office 文档的 `session.open/create/update/persist/close` 契约。
4. `Chips-EditingEngine/src/services/workspace-service.ts` 新建卡片时依赖 `launchParams.workspacePath` 和 `client.card.session.init(...)`；该链路不能用于原生 `.docx` 文件。
5. `Chips-EditingEngine/技术文档/01-编辑引擎vNext架构说明.md` 与 `生态共用技术文档/协议与接口标准/06-Chips-Host对外接口基线.md` 明确把 Host 会话、自动保存与工作区扫描限定在卡片和箱子。
6. `Chips-Word` 目前只能通过 `client.platform.saveFile(...)` 让用户选择路径，再调用 `client.file.write(...)` 写入 DOCX；新建文档无法确定当前薯片工作区，也无法进入 Host 托管的自动保存、冲突处理和会话生命周期。
7. `Chips-Word/vendor/docx-engine/src/blank.ts` 已有可生成合法空白 DOCX 的 `buildBlankDocx(...)`，因此 Word 引擎本身具备新建能力；阻断发生在工作区和正式持久化契约层。

## 影响范围

- Chips-Word、Chips-Slide、Chips-Sheet、Chips-PDF 的新建、首次保存、自动保存和最近文件链路；
- Chips-EditingEngine 工作区文件树对 Office/PDF 文件的展示、打开、重命名、删除和拖拽；
- Chips-Host 工作区服务、资源打开服务和应用启动上下文；
- Chips-SDK 的 workspace/document API、类型、测试与公开文档；
- 后续 Office 文档恢复、冲突检测、保存失败重试与多窗口一致性。

## 复现步骤

1. 启动 Chips-Word，检查起始页与命令系统，当前只有“打开”，没有正式“新建 Word 文档”动作。
2. 尝试在插件内创建空白 DOCX：`buildBlankDocx(...)` 可以生成并解析合法字节，但 SDK 无法取得当前薯片工作区根路径，因此不能确定创建目标。
3. 调用 `client.workspace.scan(<工作区>)`，观察返回类型和 Host 实现只包含 card、box、folder，普通 DOCX 不进入工作区文件树。
4. 检查 SDK document/card/box API，确认不存在 Office 文档会话。
5. 打开零字节 `.docx`，旧实现会把空字节直接交给 JSZip，并暴露 `End of data reached... Corrupted zip?`；这通常也是把“空文件占位”错误当成新 Word 文档后的直接表现。

## 期望行为

1. Host / SDK 提供正式的当前工作区上下文读取能力，应用插件无需接收硬编码路径，也不得推断 `~/.chips-host`。
2. `workspace.scan` 与对应类型契约支持正式登记普通文档，至少覆盖 DOCX、PPTX、XLSX 和 PDF，并定义文件 ID、MIME、扩展名、创建/修改时间及打开处理器信息。
3. 明确 Office 原格式文档的会话模型：新建、打开、脏状态、持久化、另存为、保存失败、冲突、关闭和恢复；确定哪些能力由 Host 托管，哪些由应用插件负责序列化。
4. Word 新建时调用 `buildBlankDocx(...)` 生成合法 OOXML，不允许通过创建零字节 `.docx` 作为占位；创建成功后文件立即位于当前薯片工作区并进入工作区索引。
5. Slide、Sheet、PDF 复用同一套工作区与文档会话契约，不分别实现路径拼接、文件命名和自动保存旁路。
6. 补充 Host、SDK、编辑引擎和四个办公插件的契约测试及端到端测试。

## 暂行处理

- `Chips-Word` 已为零字节和非 ZIP 数据增加 DOCX 容器预检，界面不再暴露 JSZip 英文底层异常。
- 不在 Word 内硬编码工作区路径，不用 `file.list` 绕过 `workspace.scan`，不把 Office 文件伪装成 `.card`，不自行复制 card session 形成第二套运行时。
- 在本工单收口前，不将“弹出系统另存为对话框”描述为“保存到薯片工作区”，也不宣称四个办公插件已完成正式工作区接入。

## 需要协作方

- Chips-Host 工作区、应用启动、资源打开与会话服务维护方
- Chips-SDK workspace/document/file API 维护方
- Chips-EditingEngine 工作区维护方
- Chips-Word、Chips-Slide、Chips-Sheet、Chips-PDF 维护方

## 处理结果

1. Host 新增 `office.document.create/open/read/write/get/persist/close` 会话服务，统一通过 PAL 文件能力读写；`create` 立即将合法初始字节落盘到当前工作区 `documents/`，未知扩展名以 `binary` 保存。
2. SDK 新增 `client.office`，统一归一化 Bridge 中的 Buffer、ArrayBuffer 与 Uint8Array；同步路由清单、Host schema 与 `office.read/office.write` 权限。
3. `workspace.getContext` 返回 Host 工作区根路径；`workspace.scan` 登记所有普通文件并提供扩展名、MIME、分类、文档类型和大小；`file.detectType` 与资源打开服务共用统一 MIME 表。
4. Chips-Word 新建使用 GenOffice `buildBlankDocx` 生成合法 OOXML，打开本地文件使用 Office `open/read`，保存使用 `write/persist`，关闭时释放会话；不再把零字节文件或系统另存为路径作为新建文档。
5. Chips-Slide 新建使用引擎 `createBlankPptx` 生成合法 OOXML，打开/保存本地 PPTX 复用 Office 会话；新增 `com.chips.slide.file.new` 与起始页新建入口。
6. Chips-Sheet 新建使用 `client.office.create` 立即写入工作区 `documents/`；本地 XLSX/XLSM 打开、保存与另存为复用 Office 会话，CSV 保留文件通道。
7. Chips-PDF 本地打开、保存与另存为复用 Office 会话，远程资源及 Web 下载继续使用资源/下载回退链路。
5. Office `write` 未传 `offset` 时替换完整字节，传入 `offset` 时执行区间写入，避免保存较短文档时残留旧文件尾部。

验证：Host 构建通过；Host Office/工作区/MIME/资源打开定向测试通过；编辑引擎测试和构建通过；SDK 105 个 Vitest 测试通过；Chips-Word 33 个测试通过；Chips-Ui 33 个测试通过；Slide、Sheet、PDF 类型检查通过。SDK 后续 CLI scaffold 阶段仍有既有 Card Viewer Smoke 中文文案断言失败，与本工单改动无关。
