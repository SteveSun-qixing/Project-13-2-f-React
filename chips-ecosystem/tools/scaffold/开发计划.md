## 一、目标与范围

在 `chips-ecosystem/tools/scaffold/` 交付四类插件角色（`basecard` / `boxlayout` / `app` / `service`）的模板清单与纯函数生成器，作为 `@chips/sdk/scaffold` 的实现来源（[02.08-02-SDK-API规范·八、脚手架](../../../薯片生态文档库/05-接口与契约/02.08-02-SDK-API规范-八、脚手架（@chips-sdk-scaffold）.md)）：

1. `listScaffoldTemplates()`：返回四条模板记录，`files` 与生成结果逐项一致；
2. `createScaffoldPlan(options)`：纯函数，只产出文件计划（路径 + 内容）与结构化 manifest，不写磁盘、不联网、不安装依赖；
3. 参数校验：角色合法性、插件 ID 反向域名文法与命名空间、显示名、目标目录；失败抛 `ScaffoldError`（`code: SDK_INVALID_SCAFFOLD_OPTIONS`），不产生部分计划；
4. 生成结果可直接 `install` / `build` / `test` / `pack`：包含构建配置（平台 vendor 外部化 + R4 红线守卫）、包级测试配置与测试、README；
5. 模板单测：生成 → 结构断言 → 清单校验（含落盘往返验证）。

范围外：文件写入、依赖安装与 `.cpk` 打包（由 `@chips/cli` 执行）；`@chips/sdk` 导出边界（`scaffold` 子路径的转发，由 SDK 包负责）；平台侧的清单/包校验实现（由 CLI 与内核负责）。

## 二、公开面与不变式

| 导出 | 位置 | 说明 |
|---|---|---|
| `createScaffoldPlan(options)` | `src/generator.ts` | 纯函数生成器，返回 `IScaffoldPlan` |
| `listScaffoldTemplates()` | `src/generator.ts` | 四角色模板清单，顺序固定 `basecard`、`boxlayout`、`app`、`service` |
| `SCAFFOLD_TEMPLATE_ROLES` | `src/generator.ts` | 角色枚举常量 |
| `ScaffoldError` / `isScaffoldError` | `src/errors.ts` | 校验失败错误；SDK 边界转换为 `ChipsError` |
| `IPluginManifest` 等类型 | `src/types.ts` | 与 SDK API 规范 §8.3 形状一致 |

不变式：

1. 生成器无副作用、无 IO；同一输入字节级可复现（覆盖式 YAML/JSON 发射器）；
2. 校验失败不产生部分计划；调用方不得落盘半个工程；
3. `manifest.yaml` 是唯一权威清单，`version` 与 `package.json` 一致；生成文件引用一律为包内相对路径且位于 `assets/` 内；
4. 四个角色只生成各自的专有字段（`cardTypes` / `layouts` / `ui` / `healthCheck`），禁止跨角色字段；
5. 两个入口（`dist/index.js` 与 `render.js`）默认导出对象，职责分离；`service` 不产出渲染入口与 UI 资源；
6. 渲染代码只从 `@chips/ui` 取组件与 Design Tokens、从 `@chips/sdk` 取类型；禁止硬编码视觉数值与第二套组件库；
7. 平台提供物（`react`、`react-dom`、`@chips/ui`）与全部构建期依赖放 `devDependencies`，第三方依赖精确版本，内部依赖 `workspace:*`。

## 四、四角色模板差异（与 SDK API 规范 §8.2、§8.5 对齐）

公共文件（全部角色）：`manifest.yaml`、`package.json`、`tsconfig.json`、`README.md`、`vite.shared.ts`、`vite.main.config.ts`、`vitest.config.ts`；渲染角色另有 `vite.render.config.ts`。

| 角色 | 主进程入口源码 | 渲染入口源码 | 角色文件 | 测试 |
|---|---|---|---|---|
| `basecard` | `src/main.ts`（`mainPlugin`，默认导出） | `src/render.tsx`（`renderPlugin`，默认导出） | `src/config.ts`、`src/index.ts`、图标、卡片配置 schema | `tests/config.test.ts` |
| `boxlayout` | `src/main.ts`（`mainPlugin`，默认导出） | `src/render.tsx`（`renderPlugin` + `attachRuntime`） | `src/config.ts`、`src/index.ts`、图标、布局配置 schema | `tests/render.test.ts`（jsdom） |
| `app` | `src/index.ts`（`IAppPlugin` 默认导出） | `src/ui/AppView.tsx`（窗口根组件 + `ChipsProvider`） | 启动器图标 | `tests/app.test.ts` |
| `service` | `src/index.ts`（`IServicePlugin` 默认导出） | 无 | 自身配置 schema | `tests/service.test.ts` |

构建配置与《构建与打包》§5.5 一致：主进程入口 `node18` 自包含单文件 → `dist/index.js`；渲染入口 `chrome118`、外部化平台 vendor 五条 URL 并重写路径 → 包根 `render.js`；两份配置共用 `vite.shared.ts` 的红线守卫。

## 五、测试策略与验收命令

- 结构断言：四角色文件清单与模板记录一致；路径为相对 POSIX 且互不重复；`manifest` 引用资源全部存在；`tsconfig` 只继承不重复定义；README 含插件标识、包名与产物说明。
- 清单校验：`manifest.yaml` 解析后通过 `manifest-validate`（角色专有字段、ID 文法、asset 路径、healthCheck 时长）。
- 静态检查：全部 `.ts` / `.tsx` 生成内容经 TypeScript 编译器 API 转译（语法级）；JSON 资产可解析；无占位标记与未替换变量。
- 落盘往返：计划写入系统临时目录后，磁盘上的 `manifest.yaml` 仍通过清单校验，`package.json` 版本与 manifest 一致。
- 确定性：同一选项两次生成结果字节级一致。

```bash
pnpm --filter @chips/scaffold run test
pnpm --filter @chips/scaffold run test:coverage
pnpm --filter @chips/scaffold run typecheck
pnpm --filter @chips/scaffold run build
pnpm --filter @chips/scaffold run lint
```

## 六、依赖与集成

- 上游：文档库 02.08（脚手架契约）、02.02（SDK 导出面）、03.01~03.06 与 07~10（角色接口）、02.03（插件包格式）、06.02（构建契约）。
- 下游：`@chips/sdk/scaffold` 转发本包；`@chips/cli` 的 `chips plugin create` 消费 `createScaffoldPlan` 并落盘；`@chips/gates` 的入口校验脚本用于打包前置检查。
- 生态依赖：生成结果的完整 `install/build/test` 依赖 `@chips/sdk` 与 `@chips/ui` 两个包的实际构建产物；两包未就绪时只可验证到结构、清单与语法层（见开发日志）。

## 七、风险与遗留

1. `工单001`：模板文件清单与构建契约的口径冲突。本包按「生成结果必须可构建」补齐 vite 配置与 README，并同步修订 SDK API 规范 §8.2；入口校验脚本的落位（`tools/scripts/` 与 `tools/gates/`）与 `render.js` 忽略规则仍待主代理收口，收口前生成包的 `build` 不含入口校验步骤（由 `chips plugin pack` 的安装同源校验覆盖）。
2. `工单002`：应用窗口根环境挂载责任。`app` 模板按 `@chips/ui` 指南 §3.1 在窗口根组件挂载 `ChipsProvider` 一次，与 `examples/plugins/hello` 暂行处理一致。
3. `@chips/sdk`、`@chips/ui` 尚未产出 `dist/` 时，无法执行生成工程的真实 `build` 与 `vitest`；两包就绪后必须回归四角色生成工程的 install/build/test（验收命令见 §五）。
