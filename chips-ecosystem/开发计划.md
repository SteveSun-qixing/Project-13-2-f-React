## 一、目标

把 `chips-ecosystem/` 完善为可安装、可构建、可检查的 pnpm + Cargo 双工作区：根清单聚合全部标准脚本，工具链配置全仓统一，各平台包具备占位清单（标准脚本 + 合规 workspace 依赖），并产出可提交的 `pnpm-lock.yaml`。

## 二、范围

交付物：

1. 根 `package.json`：`private`、`packageManager: pnpm@9`，聚合 `dev/build/test/lint/typecheck/test:coverage/test:contract/test:e2e/docs:check/package/clean`；`devDependencies` 精确锁定仓库级工具链（只放仓库级工具，业务/运行时依赖下沉到包）。
2. `pnpm-workspace.yaml`：`packages/*`、`plugins/*`、`plugins/*/*`、`tools/*`、`tests/*`、`examples/plugins/*`（`tests/*` 为 `@chips/perf`、`@chips/e2e`、`@chips/contract-tests` 的工作区成员入口）。
3. `tsconfig.base.json` + 根 `tsconfig.json`（solution：`files: []`，引用由各包落地后登记）。
4. 根 `Cargo.toml`：`members`、`[workspace.package]`、`[workspace.dependencies]`、release profile。
5. ESLint 扁平配置 `eslint.config.mjs`（R4 导入拦截、`import-x/no-cycle`、TS 类型感知、`packages/ui` 与 `packages/antd` 例外、根 `vitest.config.ts` 的 `allowDefaultProject`）、`.prettierrc.json`、`.prettierignore`。
6. `.editorconfig`、`rustfmt.toml`、`clippy.toml`。
7. `.gitignore`（构建产物零入库）、`README.md` 更新。
8. `packages/{bridge,sdk,host,ui,antd,native,cli}/package.json`（标准脚本 + `workspace:*` 依赖；`core-rust` 为纯 Rust 目录，不建 Node 清单）；工具包与测试包清单同步纳入精确版本与标准脚本口径。
9. `pnpm-lock.yaml`（本机联网生成）。
10. 各包清单依赖合规收口：根清单只保留仓库级工具（移除 `electron` 与 `yaml`）；`rimraf` 下沉到使用它的包（`bridge`/`sdk`/`cli`）；`tools/contract-gen` 的 `engines.node` 与工具包第三方版本统一为 Node >= 18 基线与精确版本。

不做：不改旧仓库；不改 `薯片生态文档库/`；不写业务源码；不创建临时/简化实现。

## 三、接口与依赖

- 唯一包管理器 `pnpm@9`（Node >= 18 LTS），唯一 Rust 工作区根 `Cargo.toml`。
- 内部依赖只允许 `workspace:*`；第三方 Node 依赖精确版本；Rust 第三方依赖只在 `[workspace.dependencies]` 声明。
- 包依赖方向：`ui → antd`、`sdk → bridge`、`host → bridge + ui`、`cli → sdk + bridge`；其余包与 tools 不越界。
- 聚合脚本语义与失败面：`build` = Cargo release + 各包 build；`test` = Cargo + 各包 test；`lint` = ESLint + Prettier + rustfmt + clippy；`typecheck` = `tsc -b`。

## 四、关键决策与依据

1. 目录结构沿用 W0 骨架与《重构大计划/02-仓库映射与新工作区》（`packages/{core-rust,native,bridge,host,sdk,ui,antd,cli}`、`plugins/<族>/<插件>`、`tools/{scaffold,contract-gen,gates}`）。

3. ESLint 采用扁平配置：现行 ESLint 9 已不支持 `.eslintrc`；规则内容（R4 拦截组、`packages/ui` 特例、`import-x/no-cycle`、TS/React 规则）与规范一致，文档中的 `.eslintrc.js` 示例需后续同步。

5. TS 编译采用项目引用：`tsconfig.base.json` 提供全仓严格选项，根 `tsconfig.json` 为 solution 文件；各包 tsconfig 由对应 W1 包任务创建并登记引用。
6. Cargo `members` 直接声明目标 crate 位置；在 `packages/core-rust/crates/*` 与 `packages/native` 落地前，Cargo 命令会因成员清单为空而报错，属 W1 内核/绑定任务的落地顺序，不是配置缺陷（见风险 R1）。

## 一、目标

在 `chips-ecosystem` 根运行 `pnpm lint`（第一步 `eslint .`）从实测 246 errors / 72 文件收敛到只剩 `packages/cli` 的 63 条（该目录由在途智能体独占，不修、只登记移交清单），其余 183 条逐条真实修代码。

## 二、口径判定（先判定，后动手）

- 根 `eslint .` 的失败**不是**构建产物混入：根 `eslint.config.mjs` 已 ignore `dist/coverage/target/release/test-results/playwright-report/fixtures/归档/*.node/*.cpk`，实测错误全部落在 `src/`、`tests/`、`test/` 源文件。
- 根级 246 条与包级 `pnpm --filter <pkg> lint` 通过的差异根源：根配置对 `**/*.{ts,tsx,mts,cts}` 启用 `tseslint.configs.recommendedTypeChecked`（类型感知规则面），包内配置只启用 `recommended`（非类型感知）。《TypeScript 编码规范·十一、ESLint 配置》权威 extends 清单本就含 `recommended-requiring-type-checking`，即根口径才是规范口径；包内配置缺类型感知层属工具链口径缺口（与工单 010 的 prettier 忽略面问题同型，本任务不改配置、只把代码修到规范口径，缺口登记开发日志遗留）。
- 结论：183 条全部按真实代码质量问题逐条修实现/测试代码；不放宽规则严重级、不删规则、不用 `eslint-disable` 压错误（确属生成代码的不可避免场景未发现）。

## 三、清单与修复策略（按规则族）

实测分布（完整清单落盘 `/tmp/lint-root-errors.txt` 与 `/tmp/lint-root-errors.json`）：

| 包                     | 错误数 | 主要规则                                                                                                                                                                                                                                                                      |
| ---------------------- | ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| packages/host          | 97     | `require-await`×59、`unbound-method`×9、`only-throw-error`×9、`no-unnecessary-type-assertion`×6、`explicit-function-return-type`×6、`prefer-promise-reject-errors`×2、`no-unsafe-assignment`×2、`no-redundant-type-constituents`×2、`no-base-to-string`×1、`no-unused-vars`×1 |
| packages/bridge        | 63     | `no-unsafe-argument`×33、`require-await`×22、`no-base-to-string`×3、`explicit-function-return-type`×2、其余单条                                                                                                                                                               |
| packages/sdk           | 20     | `require-await`×7、`unbound-method`×7、`no-unnecessary-type-assertion`×2、其余单条                                                                                                                                                                                            |
| tools/contract-gen     | 4      | `unbound-method`×2、`no-unnecessary-type-assertion`×2                                                                                                                                                                                                                         |
| packages/cli（范围外） | 63     | 含 1 条致命 Parsing error，整体移交                                                                                                                                                                                                                                           |

修复策略：

1. `require-await`：实现接口的 fake/port 方法去掉多余 `async`，返回类型保持 `Promise<T>` 语义（`return Promise.resolve(...)` 或直接返回既有 Promise）；纯同步 lambda 去掉 `async`。
2. `no-unsafe-argument` / `no-unsafe-assignment`（多在 bridge 测试对 `reject(error)` 断言）：消除 `any` 传播源，给测试夹具显式类型或收窄断言参数类型。
3. `unbound-method`：断言/引用方法处改箭头函数包裹或属性存在性检查，不改变行为。
4. `only-throw-error` / `prefer-promise-reject-errors`：抛出/拒绝值统一改为 Error 实例（复用各包既有 ChipsError/领域错误类型），核对调用方捕获逻辑同步收紧。
5. `no-base-to-string`：字符串化前显式序列化（`JSON.stringify` 或取字段），保持错误消息可读且为简体中文语境。
6. `no-unnecessary-type-assertion`：删除冗余断言。
7. `explicit-function-return-type`：补显式返回类型。
8. `no-redundant-type-constituents`：修正联合类型（`T | unknown` → `unknown` 或按真实意图收窄）。
9. `no-unused-vars`：删除或按 `_` 前缀约定处理（root 配置 argsIgnorePattern 为 `^_`，未使用变量需实际移除）。
