## 截至 2026-09-20 现状核验：判定面结构

- 取数面：`src/docs/sources.ts` 是全包唯一写「文档库相对路径 + 章节标题」的位置 —— 能力来源 1 条
  （《04-能力契约规范》§6.2 R19 全表）、权限来源 1 条（《08-权限系统设计》§4.1）、事件保留域 1 条 + 标准事件声明
  文件 10 个分册、错误码来源 21 条（另给出 6 个按域精确比对的关键来源常量）、四角色 `ROLE_SOURCES`
  共 12 个章节选择器、SDK 两个来源（§2.1 包入口、§2.2 主入口导出清单）、帧协议来源
  （《05-渲染引擎设计》§九 + `9.2 消息封套` / `9.3 消息清单与约束` 两个子章节常量 + 两个方向标记字面量）。
- 解析面：`markdown.ts` 章节定位 / 表格解析（代码块内不参与、支持 `\|` 转义）/ 行内码与围栏块提取；
  `docs/ts-declarations.ts` 用 TypeScript 编译器 API 归一声明，只取不带注释的 `getText()`，
  因此注释改动不进快照、成员名与可选性、类型、顺序改动必然进差异；
  所有解析未命中都显式抛出（含文件与章节），不静默跳过。
- 实现面：`code/bridge.ts` 读 `BUILTIN_CAPABILITIES` / `BUILTIN_PERMISSIONS` / `BRIDGE_ERROR_CODES` /
  `BRIDGE_ERROR_RETRYABLE` / `KERNEL_INVALID_TRANSITION` / `EVENT_ERROR_CODES` / `STANDARD_EVENTS`；
  `code/host.ts` 读 `PAL_ERROR_CODES` 与 `RESOURCE_ERROR_HTTP_STATUS` 的键集合。
  两者均为**源码相对路径直读**（W1 过渡，头注钉明包入口发布后 `code/bridge.ts` 是唯一需改的位置）。
- 判定面：`check/` 六个模块统一返回 `ContractViolation[]`（空列表即一致），每条带机器可判定 `code`、
  可定位 `subject` 与简体中文 `message`，按 `code` / `subject` 排序保证多次运行输出稳定。
- 产物面：`snapshots/` 四个快照（`event-contracts.json` 30 811 B、`role-interfaces.json` 37 322 B、
  `sdk-exports.json` 7 390 B、`frame-protocol.json` 10 420 B）随包提交；
  `reports/contract/contract-report.{json,md}` 由自定义报告器在 `onTestRunEnd` 写出，含 `gate: "G8"`、
  `snapshotMode`、汇总计数与逐用例清单。
- 装配面：`vitest.config.ts` 为 `environment: 'node'`、`include: ['tests/**/*.test.ts']`、
  `reporters: ['default', <包内 src/reporter.ts>]`、`testTimeout` / `hookTimeout` 30 s；
  `tests/helpers.ts` 以进程内缓存把文档模型与两侧登记表各装载一次（缓存不影响判定结果）。

## 2026-09-20 修复波次 FIX-CONTRACT：解析器与检查器收口（→ 46/46）

- 起点事实：`pnpm --filter @chips/contract-tests test` 10 个用例失败（共 9 个测试文件 / 46 用例）。
- 修正一（解析器，文档侧取数）：
  - `src/docs/errors.ts` 明确「登记表优先」口径 —— 章节内含表头为「错误码 / code」列的表时，
    该表即该来源的权威码集，正文散句引用的他域错误码不进入来源域；无此类表时才按整节正文提取；
    同一错误码可被多处引用（`BRIDGE_TIMEOUT` 同时出现在 Bridge §9.2 与能力调用 §11.3），
    故注册表按来源保留分域视图，另给出全库去重升序并集用于「不得自造错误码」判定。
  - `src/docs/sources.ts` 的章节选择器与文档库现行拆分件对齐（路径 + `level` + 标题前缀 + 报告标注），
    修正后「来源缺失」与「来源为空」不再混同。
  - `src/docs/ts-declarations.ts` 的归一面收敛为只依赖 `getText()`（不含注释），杜绝注释改动污染快照。
- 修正二（检查器，判定口径）：`src/check/errors.ts` 按实现完整度分档判定 ——
  拥有完整实现域的登记表（Bridge 通道、事件、资源协议）要求**集合逐项一致**；
  部分实现域（权限拒绝、权限登记内核常量、Bridge 资源控制、PAL）要求实现侧是对应文档域的**子集**
  （内核生命周期常量对照《01-薯片内核设计》§九 码表）；实现侧任何登记码必须在文档注册表内（红线 11）；
  Bridge 通道错误码的 `retryable` 与文档表逐项一致。
- 修正三（实现侧两处漂移收口）：`packages/bridge/src/protocol/capability-contracts.ts`（能力与权限映射登记表）
  与 `packages/bridge/src/protocol/events.ts`（标准事件与可见性登记表）两处实现侧数据与本波次窗口内落盘，
  与文档权威表逐项对齐。方向可核实：只读 `git diff --name-only` 显示文档库被改动的 7 个文件中
  **不含**《04-能力契约规范》《05-事件契约规范》《08-权限系统设计》，即判定基准未动、实现侧向文档收口，
  符合 G8「契约类文档与实现必须同一变更内一致，不一致视为缺陷」的取向。
- 修正四（帧协议闭合与文档侧唯一改动）：《05-渲染引擎设计》§9.3「消息清单与约束」表补入
  `host:init` 行（方向 `父 → 子`，触发时机「通道建立后父帧下发初始装载载荷」，约束「每个渲染会话仅一次；
  封套 `sessionId` / `frameId` 必须与通道登记一致（§9.6）」）——
  该行在《05-测试规范》§5.3 中本属必测消息，代码块已声明而清单表缺行，导致「代码块有、表必须收录」的
  双向闭合判定失败。快照 `snapshots/frame-protocol.json` 随之显式更新（现含 2 处 `host:init`：
  消息声明与联合类型投影），更新方式为 `pnpm run test:contract:update`（`CHIPS_CONTRACT_SNAPSHOT_UPDATE=1`），
  非静默覆盖。
- 修正五（偏差夹具与用例）：`tests/deviations.test.ts` 的注入断言随上述口径重写，
