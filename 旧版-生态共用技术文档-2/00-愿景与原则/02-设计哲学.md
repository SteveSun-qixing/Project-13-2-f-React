## 一、原子化模块理念

### 1.1 原子化的定义

**原子化（Atomicity）** 是指每个功能模块都是不可分割的最小单元，具有以下特征：

1. **最小职责**：每个模块只做一件事，并且做好
2. **清晰边界**：模块有明确的输入和输出
3. **独立演进**：模块可以独立开发、测试、部署
4. **可组合性**：模块可以自由组合形成复杂功能

### 1.2 原子化设计原则

#### 原则 1：单一职责

```typescript
// ❌ 反模式：职责过多
class FileManager {
  read() { /* 读取 */ }
  write() { /* 写入 */ }
  parse() { /* 解析 */ }
  render() { /* 渲染 */ }  // 职责过多！
  format() { /* 格式化 */ }
}

// ✅ 正确：单一职责
class FileReader {
  read() { /* 读取 */ }
}

class FileWriter {
  write() { /* 写入 */ }
}

class CardParser {
  parse() { /* 解析 */ }
}

class CardRenderer {
  render() { /* 渲染 */ }
}
```

#### 原则 2：接口隔离

```typescript
// ❌ 反模式：胖接口
interface Plugin {
  render(): void;
  edit(): void;
  executeBackground(): void;  // 不需要的操作
}

// ✅ 正确：接口隔离
interface RendererPlugin {
  render(props: RenderProps): RenderResult;
}

interface EditorPlugin {
  edit(props: EditProps): EditResult;
}

interface ServicePlugin {
  execute(): void;
}
```

#### 原则 3：组合优于继承

```typescript
// ❌ 反模式：继承导致紧耦合
class ImageCard extends BaseCard {
  // ...
}

class VideoCard extends BaseCard {
  // ...
}

// ✅ 正确：组合形成功能
class Card {
  constructor(
    private renderer: RendererPlugin,
    private editor?: EditorPlugin
  ) {}
  
  render() {
    return this.renderer.render(this.props);
  }
}
```

### 1.3 原子化的边界划分

原子化的关键在于**正确划分边界**。边界过粗会导致模块臃肿，边界过细会导致碎片化。

#### 边界划分准则

| 准则 | 描述 | 示例 |
|------|------|------|
| 业务边界 | 按业务领域划分 | Card 模块、Box 模块 |
| 能力边界 | 按能力类型划分 | 渲染能力、编辑能力 |
| 数据边界 | 按数据结构划分 | 元数据、配置、资源 |
| 生命周期边界 | 按运行阶段划分 | 初始化、运行、销毁 |

#### 边界划分示例

```
薯片生态模块划分：

├── document/
│   ├── card/           # 卡片领域
│   │   ├── parser/     # 解析能力
│   │   ├── renderer/   # 渲染能力
│   │   ├── validator/  # 验证能力
│   │   └── serializer/ # 序列化能力
│   │
│   └── box/            # 箱子领域
│       ├── parser/     # 解析能力
│       ├── renderer/   # 渲染能力
│       └── layout/     # 布局能力
│
├── platform/
│   ├── file/           # 文件操作
│   ├── network/        # 网络操作
│   └── clipboard/      # 剪贴板操作
│
└── security/
    ├── auth/           # 认证
    ├── permission/      # 权限
    └── crypto/         # 加密
```

## 二、能力导向设计

### 2.1 能力导向的定义

**能力导向（Capability-oriented）** 是指以「能力」为核心组织系统接口的设计方式：

- **能力** = 一组相关的操作及其数据的集合
- **能力封装** = 将一组相关操作和数据绑定在一起
- **能力组合** = 通过组合能力构建复杂系统

### 2.2 能力模型

```
┌─────────────────────────────────────────────────────────────┐
│                       Capability                              │
│  ┌─────────────────────────────────────────────────────┐  │
│  │                  File Capability                      │  │
│  │                                                      │  │
│  │  ┌───────────┐  ┌───────────┐  ┌─────────────────┐ │  │
│  │  │   read   │  │  write    │  │     list       │ │  │
│  │  │          │  │           │  │                │ │  │
│  │  │ params:   │  │ params:   │  │ params:        │ │  │
│  │  │   path    │  │   path    │  │   directory   │ │  │
│  │  │  encoding │  │  content  │  │  recursive    │ │  │
│  │  │           │  │           │  │               │ │  │
│  │  │ result:   │  │ result:   │  │ result:       │ │  │
│  │  │ content   │  │ bytes     │  │ entries       │ │  │
│  │  │ metadata  │  │           │  │               │ │  │
│  │  └───────────┘  └───────────┘  └─────────────────┘ │  │
│  │                                                      │  │
│  │  Permissions: file.read, file.write                  │  │
│  │  Schema: defined                                     │  │
│  └─────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────┘
```

### 2.3 能力定义规范

```typescript
// 能力接口定义
interface Capability {
  // 能力标识符
  readonly id: string;
  readonly version: string;
  
  // 动作定义
  readonly actions: Record<string, ActionDefinition>;
  
  // 权限要求
  readonly permissions: string[];
  
  // 生命周期
  initialize?(): Promise<void>;
  destroy?(): Promise<void>;
}

// 动作定义
interface ActionDefinition<P = unknown, R = unknown> {
  // 参数 schema
  readonly params: Schema;
  
  // 返回值 schema
  readonly result: Schema;
  
  // 权限要求
  readonly permissions: string[];
  
  // 超时时间（ms）
  readonly timeout?: number;
  
  // 是否幂等
  readonly idempotent?: boolean;
  
  // 处理器
  handle(params: P, context: Context): Promise<R>;
}
```

### 2.4 能力组合

```typescript
// 组合能力构建复杂功能
class DocumentService {
  constructor(
    private file: FileCapability,
    private card: CardCapability,
    private renderer: RenderCapability
  ) {}
  
  async openAndRender(path: string) {
    // 1. 读取文件
    const content = await this.file.read({ path });
    
    // 2. 解析为卡片
    const card = await this.card.parse({ content });
    
    // 3. 渲染展示
    return await this.renderer.render({ card });
  }
}
```

### 2.5 能力与权限

能力天然与权限关联：

```typescript
// 权限是能力的子集
interface Permission {
  readonly capability: string;  // 所属能力
  readonly action: string;     // 具体动作
  readonly level: 'read' | 'write' | 'admin';
}

// 插件声明需要的权限
const manifest = {
  permissions: [
    'file.read',
    'file.write',
    'card.parse',
    'card.render',
  ],

```

## 三、平台性思维

### 3.1 平台性定义

**平台性（Platform Thinking）** 是指将系统设计为支持第三方扩展和协作的基础设施。

### 3.2 平台设计原则

#### 原则 1：开放但安全

```
┌─────────────────────────────────────────────────────────────┐
│                    Platform Architecture                       │
│                                                              │
│   ┌─────────────────────────────────────────────────────┐   │
│   │                   Host Platform                      │   │
│   │   ┌─────────┐ ┌─────────┐ ┌─────────────────────┐ │   │
│   │   │ Kernel  │ │ Services │ │  Plugin Runtime     │ │   │
│   │   └─────────┘ └─────────┘ └─────────────────────┘ │   │
│   │          │         │                │               │   │
│   │          └─────────┼────────────────┘               │   │
│   │                    │                                │   │
│   │            ┌───────▼───────┐                        │   │
│   │            │   Bridge API  │                        │   │
│   │            │  (window.     │                        │   │
│   │            │   chips.*)    │                        │   │
│   │            └───────────────┘                        │   │
│   └─────────────────────────────────────────────────────┘   │
│                         │                                   │
│          ┌──────────────┼──────────────┐                  │
│          ▼              ▼              ▼                   │
│   ┌────────────┐  ┌────────────┐  ┌────────────┐         │
│   │  Plugin A  │  │  Plugin B  │  │  Plugin C  │         │
│   └────────────┘  └────────────┘  └────────────┘         │
└─────────────────────────────────────────────────────────────┘
```

#### 原则 2：契约优于实现

```typescript
// 定义稳定的契约
interface CardRenderer {
  // 稳定的契约接口
  render(props: RenderProps): Promise<RenderResult>;
  cleanup(): void;
}

// 契约可以由多个实现提供
class ImageCardRenderer implements CardRenderer { ... }
class VideoCardRenderer implements CardRenderer { ... }
class PdfCardRenderer implements CardRenderer { ... }
```

#### 原则 3：扩展优于修改

```typescript
// ❌ 反模式：修改核心代码
class CoreService {
  process(data) {
    // 原始逻辑
    // 新增逻辑（污染核心）
  }
}

// ✅ 正确：扩展点模式
class CoreService {
  private processors: Processor[] = [];
  
  // 扩展点
  addProcessor(processor: Processor) {
    this.processors.push(processor);
  }
  
  process(data) {
    let result = data;
    for (const processor of this.processors) {
      result = processor.process(result);
    }
    return result;
  }
}
```

### 3.3 平台稳定性

平台必须保持稳定，不能因为第三方插件而破坏：

| 稳定性维度 | 实现方式 |
|------------|----------|
| API 稳定性 | 语义化版本控制、废弃流程 |
| 性能稳定性 | 资源配额、隔离执行 |
| 安全稳定性 | 权限校验、沙箱隔离 |
| 升级兼容性 | 向后兼容、平滑迁移 |

## 四、可扩展性优先

### 4.1 可扩展性维度

| 维度 | 描述 | 实现方式 |
|------|------|----------|
| 功能扩展 | 新增功能 | 插件机制 |
| 类型扩展 | 新增类型 | 类型注册 |
| 渲染扩展 | 新增渲染器 | 渲染器注册 |
| 存储扩展 | 新增存储后端 | 适配器模式 |

### 4.2 扩展点设计

#### 渲染器注册

```typescript
// 渲染器注册表
class RendererRegistry {
  private renderers: Map<string, CardRenderer> = new Map();
  
  register(type: string, renderer: CardRenderer) {
    this.renderers.set(type, renderer);
  }
  
  get(type: string): CardRenderer | undefined {
    return this.renderers.get(type);
  }
  
  render(type: string, props: RenderProps): Promise<RenderResult> {
    const renderer = this.get(type);
    if (!renderer) {
      throw new Error(`No renderer for type: ${type}`);
    }
    return renderer.render(props);
  }
}
```

### 4.3 扩展性原则

1. **开放扩展点**：系统应该提供清晰的扩展点
2. **文档化扩展点**：每个扩展点必须有完整文档
3. **版本化扩展点**：扩展点 API 必须版本化管理
4. **测试扩展点**：扩展点必须有测试覆盖

### 5.3 可观测性设计

```typescript
// 所有关键操作都必须可观测
interface Observable {
  subscribe(event: string, handler: Handler): Unsubscribe;
  emit(event: string, data: unknown): void;

class CardService implements Observable {
  async parse(path: string): Promise<Card> {

    }
  }
}
```

## 六、容错与恢复

### 6.1 防御性编程

```typescript
// ❌ 不防御
function processCard(data: unknown) {
  const card = data as Card;  // 假设输入总是正确的
  return card.id;
}

// ✅ 防御性
function processCard(data: unknown): Result<string, ProcessError> {
  // 1. 验证输入
  const validation = cardSchema.validate(data);
  if (!validation.success) {
    return Result.failure({
      code: 'INVALID_CARD_DATA',
      message: 'Invalid card data',
      details: validation.errors,
    });
  }
  
  const card = validation.data;
  
  // 2. 验证业务规则
  if (!card.id) {
    return Result.failure({
      code: 'MISSING_CARD_ID',
      message: 'Card must have an id',
    });
  }
  
  return Result.success(card.id);
}
```

### 6.2 熔断与降级

```typescript
// 熔断器
class CircuitBreaker {
  private failures = 0;
  private lastFailure = 0;
  private state: 'closed' | 'open' | 'half-open' = 'closed';
  
  async execute<T>(operation: () => Promise<T>): Promise<T> {
    if (this.state === 'open') {
      if (Date.now() - this.lastFailure > this.timeout) {
        this.state = 'half-open';
      } else {
        throw new CircuitOpenError();
      }
    }
    
    try {
      const result = await operation();
      this.onSuccess();
      return result;
    } catch (error) {
      this.onFailure();
      throw error;
    }
  }
  
  private onSuccess() {
    this.failures = 0;
    this.state = 'closed';
  }
  
  private onFailure() {
    this.failures++;
    this.lastFailure = Date.now();
    if (this.failures >= this.threshold) {
      this.state = 'open';
    }
  }
}
```

### 6.3 资源清理

```typescript
// 确保资源总是被清理
class CardEditor implements Disposable {
  private resources: Disposable[] = [];
  
  async load(id: string) {
    const subscription = this.events.subscribe(id, handler);
    this.resources.push(subscription);
    
    const card = await this.cardService.get(id);
    this.resources.push(card);
    
    return card;
  }
  
  dispose() {
    // 确保所有资源被清理
    for (const resource of this.resources) {
      resource.dispose();
    }
    this.resources = [];
  }
}

// 使用 try-finally 或 using
async function main() {
  const editor = new CardEditor();
  try {
    await editor.load('card-123');
    // 使用 editor...
  } finally {
    editor.dispose();
  }
}
```

### 7.3 缓存策略

```typescript
// 多级缓存
class CardCache {
  // L1: 内存缓存（最快）
  private memory = new Map<string, Card>();
  
  // L2: 磁盘缓存
  private disk = new DiskCache();
  
  // L3: 远程缓存
  private remote = new RemoteCache();
  
  async get(id: string): Promise<Card | null> {
    // L1
    if (this.memory.has(id)) {
      return this.memory.get(id);
    }
    
    // L2
    const disk = await this.disk.get(id);
    if (disk) {
      this.memory.set(id, disk);
      return disk;
    }
    
    // L3
    const remote = await this.remote.get(id);
    if (remote) {
      await this.disk.set(id, remote);
      this.memory.set(id, remote);
      return remote;
    }
    
    return null;
  }
}
```

## 八、持续演进

### 8.1 API 演进策略

| 阶段 | 策略 | 时长 |
|------|------|------|
| 实验期 | `@internal` 标记，可随时破坏 | 1-2 个版本 |
| 稳定期 | 正式 API，保证兼容性 | 至少 6 个月 |
| 废弃期 | 警告提示，提供迁移路径 | 至少 2 个版本 |
| 移除期 | 删除旧 API | - |

### 8.2 向后兼容

```typescript

// 迁移助手
class MigrationHelper {
  migrate<V1, V2>(
    data: V1,
    transformers: Array<Transformer<V1 | V2>>

    let current: unknown = data;

    }
    
    return current as V2;
  }
}
```

## 九、总结

设计哲学是薯片生态的灵魂：

1. **原子化模块**：最小单元、独立演进、可组合
2. **能力导向**：以能力为核心、清晰边界、权限关联
3. **平台性思维**：开放安全、契约优于实现、扩展优于修改
4. **可扩展性优先**：预留扩展点、清晰契约、版本管理
5. **状态可观测**：显式优于隐式、不可变优于可变
6. **容错恢复**：防御性编程、熔断降级、资源清理
7. **性能意识**：延迟初始化、批量操作、多级缓存
8. **持续演进**：版本管理、向后兼容、渐进迁移

遵循这些设计哲学，我们能够构建一个**稳定、可扩展、易维护**的生态系统。
