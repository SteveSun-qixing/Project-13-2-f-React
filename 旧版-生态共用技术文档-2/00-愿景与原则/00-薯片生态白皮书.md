## 一、薯片生态愿景

### 1.1 使命

**让复杂内容像打开图片一样简单。**

薯片生态致力于构建一个运行在操作系统之上的软件级生态系统，通过原子化模块和统一协议，让用户可以像操作本地文件一样轻松创建、编辑、分享和消费各类数字内容。

### 1.2 愿景

**成为数字内容领域的"操作系统级"基础设施。**

- **对用户**：薯片主机是唯一需要安装的软件，所有功能以插件形式按需获取，像使用本地软件一样使用生态内的所有工具
- **对开发者**：遵循统一协议和 SDK，通过标准接口与系统交互，专注于业务逻辑实现，无需关心底层实现
- **对生态**：模块可插拔、能力可组合、平台可扩展，形成持续演进的数字内容处理平台

### 1.3 核心价值主张

| 价值维度 | 描述 |
|----------|------|
| **极简体验** | 双击即用，无需学习。薯片文件（`.card`、`.box`）可以直接打开，嵌入网页分享后他人可直接使用 |
| **原子化设计** | 每个功能都是独立可替换的最小单元，用户按需安装，生态按需演进 |
| **跨平台统一** | 同一套协议、同一套文件格式、统一的开发者体验，覆盖桌面和移动所有主流平台 |
| **生态互联** | 所有插件通过统一协议通信，任何插件可以调用任何其他插件的能力，实现真正的能力组合 |
| **隐私优先** | 所有数据由用户本地管理，无云端强依赖，用户完全掌控自己的数字资产 |

## 二、产品定位与差异化

### 2.1 市场定位

薯片生态定位于**数字内容管理与协作平台**，填补以下市场空白：

1. **本地优先 vs 纯云端**：不依赖云端服务，数据完全本地存储，同时支持按需同步
2. **深度定制 vs 通用工具**：高度可定制的模块化架构，满足不同垂直场景需求
3. **开发者友好 vs 封闭生态**：开放的插件协议，任何开发者都可以为生态贡献插件

### 2.2 竞品对比

| 维度 | 薯片生态 | Notion | Obsidian | VS Code Extension |
|------|----------|--------|----------|-------------------|
| 架构模式 | 操作系统级插件生态 | Web 应用 | 本地优先 | 编辑器插件 |
| 内容格式 | 统一卡片格式 | 数据库格式 | Markdown | 代码 |
| 平台覆盖 | 桌面+移动 | Web | 桌面 | 桌面 |
| 插件开放性 | 完全开放 | 部分开放 | 社区插件 | VS Code 市场 |
| 数据控制 | 用户完全掌控 | 云端优先 | 本地优先 | 代码仓库 |
| 扩展方式 | 原子化插件 | 模板+集成 | 插件+社区 | 插件 |

### 2.3 核心差异化

1. **操作系统级入口**：薯片主机在操作系统层运行，所有插件共享同一运行时
2. **统一内容格式**：`.card` 和 `.box` 作为标准内容格式，任何平台、任何插件都认识
3. **原子化模块**：每个功能都是独立插件，可以单独安装、更新、卸载
4. **本地优先架构**：不强制云端依赖，同时支持灵活的同步选项

## 三、生态架构

### 3.1 核心分层架构

```
┌─────────────────────────────────────────────────────────────┐
│                      User Applications                        │
│        (Chips-EditingEngine, Chips-CardViewer, etc.)         │
└─────────────────────────────────────────────────────────────┘
                              │
┌─────────────────────────────────────────────────────────────┐
│                        Plugin Layer                           │
│     (App Plugins, Card Plugins, Layout Plugins, Module Plugins)│
└─────────────────────────────────────────────────────────────┘
                              │
┌─────────────────────────────────────────────────────────────┐
│                    Bridge Layer (window.chips.*)               │
│         (Capability-based API, Permission Control)            │
└─────────────────────────────────────────────────────────────┘
                              │
┌─────────────────────────────────────────────────────────────┐
│                     Host Services Layer                       │
│     (File, Resource, Config, Window, Plugin, Card, Box...)   │
└─────────────────────────────────────────────────────────────┘
                              │
┌─────────────────────────────────────────────────────────────┐
│                      Cordis Runtime                          │
│         (Module Loader, Service Registry, Event Bus)         │
└─────────────────────────────────────────────────────────────┘
                              │
┌─────────────────────────────────────────────────────────────┐
│                  Rust Core (Native Module)                   │
│    (ZIP, Crypto, Resource Manager, Platform Abstraction)     │
└─────────────────────────────────────────────────────────────┘
                              │
┌─────────────────────────────────────────────────────────────┐
│                     Electron Shell                            │
│           (Main Process, Renderer Process, IPC)               │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 核心技术选型

| 技术领域 | 选型 | 理由 |
|----------|------|------|
| 桌面运行时 | Electron 28+ | 成熟的跨平台 Web 运行时 |
| 核心语言 | Rust | 高性能、内存安全、跨平台 |
| 前端框架 | React 18+ | 生态完善、组件丰富 |
| 组件库 | fork antd 5.x | 功能完整、主题定制灵活 |
| 插件框架 | Cordis | 原子化模块、动态组合 |
| 跨语言桥接 | N-API | 高性能、稳定 |

### 3.3 十二层架构

| 层级 | 名称 | 职责 |
|------|------|------|
| L1 | PAL | 平台能力抽象 |
| L2 | Host Kernel | 路由、注册表、事件、生命周期 |
| L3 | Host Services | 16 个核心服务域 |
| L4 | Plugin Runtime | 插件加载、隔离、会话、权限 |
| L5 | Bridge Transport | `window.chips.*` IPC 传输 |
| L6 | Runtime Client | 协议编解码、错误归一、重试 |
| L7 | UI Hooks | 面向页面的能力调用接口 |
| L8 | Declarative UI | View/Stack/Grid/Form/List 语义原语 |
| L9 | Unified Rendering | Normalize/Validate/Resolve/Commit |
| L10 | Component Layer | 组件库（fork antd） |
| L11 | Theme System | Design Tokens、主题配置 |
| L12 | App/Page Domain | 页面状态、业务流程 |

## 四、核心能力体系

### 4.1 卡片系统（Card）

卡片是薯片生态的**最小不可分割内容单元**，必须作为复合卡片的组成部分。

#### 卡片文件结构

```
my-card.card/                 # 零压缩率 ZIP
├── .card/                   # 元数据目录
│   ├── metadata.yaml        # 卡片元数据（ID、名称、创建时间、标签）
│   ├── structure.yaml       # 结构定义（包含的基础卡片列表）
│   └── resources.yaml       # 资源清单
├── content/                 # 内容目录
│   └── *.yaml               # 各基础卡片配置文件
└── assets/                  # 资源目录
    ├── cover.html           # 封面定义
    └── ...                  # 图片、视频等资源
```

#### 卡片类型

| 类型 | 说明 | 示例 |
|------|------|------|
| 复合卡片 | 可独立存储的最小单元 | 用户创建的工作卡片 |
| 基础卡片 | 不可独立存储，必须在复合卡片内 | 文本卡片、图片卡片、视频卡片 |

### 4.2 箱子系统（Box）

箱子是卡片的容器，负责组织和展示多个卡片。

#### 箱子文件结构

```
my-box.box/                  # 零压缩率 ZIP
├── .box/                    # 元数据目录
│   ├── metadata.yaml        # 箱子元数据
│   ├── structure.yaml       # 卡片列表（URL + 摘要）
│   └── content.yaml         # 布局配置
└── assets/                  # 箱子自身资源
    └── ...
```

#### 箱子特点

- **引用模式**：箱子只记录卡片引用和摘要，不存储卡片内容
- **布局驱动**：卡片展示方式由布局插件决定
- **动态加载**：消费时按需加载卡片内容

### 4.3 内容层次结构

```
基础卡片 → 复合卡片 → 箱子 → 房间 → 空间 → 社区
```

| 层级 | 描述 |
|------|------|
| 基础卡片 | 不可分割的内容单元（文本、图片、视频等） |
| 复合卡片 | 可独立存储的卡片单元（.card 文件） |
| 箱子 | 卡片的容器（.box 文件） |
| 房间 | 用户在空间内的组织单位 |
| 空间 | 对应物理存储设备 |
| 社区 | 网络上的公共平台 |

## 五、插件系统

### 5.1 角色驱动模型

薯片生态的插件**不分类，只分角色**：

| 角色 | 描述 | 运行时特征 |
|------|------|-----------|
| `renderer` | 内容渲染器 | 提供渲染接口，被其他组件调用 |
| `editor` | 内容编辑器 | 提供编辑接口，响应用户交互 |
| `service` | 后台服务 | 无 UI，持续运行提供服务 |
| `daemon` | 守护进程 | 无 UI，随系统启动运行 |

### 5.2 插件类型

| 类型 | 说明 | 典型插件 |
|------|------|----------|
| 应用插件 | 拥有独立窗口的完整应用 | 编辑引擎、查看器 |
| 卡片插件 | 基础卡片的渲染和编辑组件 | 图片卡片、视频卡片 |
| 布局插件 | 箱子的展示方式定义 | 列表布局、网格布局 |
| 模块插件 | 无界面的能力模块 | 视频处理、图片处理 |

### 5.3 插件包格式

- **格式**：`.cpk`（本质是零压缩率 ZIP）
- **隔离**：每个插件在独立 iframe 或进程运行
- **热插拔**：支持不重启软件安装、更新、卸载插件

### 6.3 中心路由原则

所有模块的通信必须经过薯片内核作为中转站，模块之间不能直接通信。

```
┌─────────┐         ┌─────────┐         ┌─────────┐
│ 模块 A  │ ──────> │  内核   │ ──────> │ 模块 B  │
└─────────┘         └─────────┘         └─────────┘
```

## 九、治理与演进

### 9.1 架构演进机制

- 所有重大架构变更必须通过 RFC 流程
- 每个决策必须有 ADR 记录
- 代码与文档必须同步更新

### 9.2 版本兼容性策略

- 遵循语义化版本（SemVer）
- API 变更必须经过弃用流程
- 提供平滑迁移指南

### 9.3 安全与隐私

- 所有插件运行在受控沙箱中
- 权限声明与实时校验
- 用户数据完全本地存储

## 十、总结

薯片生态是一个宏大而清晰的愿景。我们追求：

1. **像操作系统一样的基础设施**：用户只需安装一个软件，按需添加功能
2. **像打开文件一样的简单**：双击 `.card` 文件即可使用
3. **像搭积木一样的灵活**：原子化模块，任意组合

这需要：
- **坚定的架构原则**：中心路由、插件隔离、能力导向
- **完善的文档体系**：从愿景到实现，从规范到示例
- **持续的迭代演进**：小步快跑，持续交付价值

薯片生态，让复杂内容像打开图片一样简单。
