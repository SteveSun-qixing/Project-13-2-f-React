> **版本**：v1.0.0

> **适用范围**：薯片生态从零重构/全新开发

## 一、设计哲学

### 1.1 核心设计理念

薯片生态的架构设计遵循以下核心理念：

#### 1. 厚底层、薄上层

```
┌─────────────────────────────────────────────────────────────┐
│                        Upper Layer (薄)                     │
│         应用插件 ────── 业务编排 ────── UI 交互              │
└─────────────────────────────────────────────────────────────┘
                              │
┌─────────────────────────────────────────────────────────────┐
│                      Core Layer (厚)                         │
│   内核 │ 服务域 │ 插件运行时 │ Bridge │ Cordis │ Rust Core │
└─────────────────────────────────────────────────────────────┘
```

**原则**：
- 通用能力尽量固化在底层
- 上层只做业务编排，不重复实现底层能力
- 底层稳定，上层灵活

#### 2. 一切皆插件

**原则**：
- 每个功能都是独立可替换的最小单元
- 插件可以随时安装、更新、卸载
- 插件之间通过标准接口通信，互不依赖

#### 3. 能力导向设计

**原则**：
- 以「能力（Capability）」为核心组织接口
- 每个能力代表一个完整的业务语义单元
- 能力内部可自由重构，不影响 API 契约

### 1.2 设计哲学来源

| 来源 | 启发 | 应用 |
|------|------|------|
| Unix 哲学 | 透明、组合、管道 | 模块化、中心路由 |
| 微内核架构 | 最小核心、最大服务 | Cordis 运行时 |
| 响应式设计 | 声明式、状态驱动 | React + Declarative UI |
| Capability Security | 最小权限、运行时校验 | Bridge 权限模型 |

## 二、架构红线

架构红线是**不可违反**的原则，任何情况下都必须遵守。

### 2.1 绝对禁止

| 红线编号 | 规则 | 违反后果 |
|----------|------|----------|
| R-001 | 禁止跨服务直接 import 调用 | 架构腐化、循环依赖 |
| R-002 | 禁止插件直接访问系统 API | 安全风险、隔离失效 |
| R-003 | 禁止硬编码样式 | 视觉不一致、维护困难 |
| R-004 | 禁止绕过 Bridge 调用 Host 能力 | 权限绕过、安全漏洞 |
| R-005 | 禁止在渲染层直接发起系统调用 | 架构混乱、难以追踪 |
| R-006 | 禁止跨语言直接调用（除 N-API） | 类型不安全、内存风险 |

### 2.2 绝对要求

| 要求编号 | 规则 | 违反后果 |
|----------|------|----------|
| R-101 | 所有系统能力调用必须经过内核路由 | 服务解耦失效 |
| R-102 | 所有插件必须通过 window.chips.* 访问能力 | 隔离失效 |
| R-103 | 所有 API 必须有类型定义 | 类型不安全 |
| R-104 | 所有服务必须定义输入/输出 schema | 接口不一致 |
| R-105 | 所有测试必须通过才能合并 | 质量退化 |

## 三、架构原则

### 3.1 分层原则

#### 依赖方向原则

```
允许: Ln → Ln-1 或 Ln → 公共契约层
禁止: Ln → Lm (m < n-1) 跨层跳跃
```

**示例**：
- ✅ L7（UI Hooks）调用 L6（Runtime Client）
- ✅ L7（UI Hooks）调用 L5（Bridge Transport）通过公共契约
- ❌ L12（App Domain）直接调用 L3（Host Services）

#### 层职责边界

| 层级 | 只允许依赖 | 禁止依赖 |
|------|-----------|----------|
| L1 (PAL) | OS/Electron 原生能力 | 业务插件 |
| L2 (Host Kernel) | PAL | 应用页面代码 |
| L3 (Host Services) | Kernel | 插件 UI |
| L4 (Plugin Runtime) | Kernel+Services | 业务域实现细节 |
| L5 (Bridge Transport) | Runtime | 页面业务状态 |
| L6 (Runtime Client) | Bridge Transport | 组件渲染实现 |
| L7 (UI Hooks) | Runtime Client | Transport 细节 |
| L8 (Declarative UI) | UI Hooks + Component Layer | Host 服务细节 |
| L9 (Unified Rendering) | Declarative UI + Theme | Host 路由逻辑 |
| L10 (Component) | Theme (接口) | 视觉硬编码 |
| L11 (Theme) | Theme Package | 业务逻辑 |
| L12 (App Domain) | L7-L11 | L1-L5 细节 |

### 3.2 服务原则

#### 中心路由原则

所有服务间调用必须经过内核路由：

```typescript
// ✅ 正确：通过内核路由
const result = await kernel.invoke('file.read', { path: '/path' });

// ❌ 错误：直接调用
const result = await fileService.read('/path');
```

#### 服务注册原则

每个服务必须：
1. 声明服务名称和版本
2. 定义所有动作的 schema
3. 注册到内核路由
4. 导出类型定义

```typescript
// 服务注册示例
export const fileService = {
  name: 'file',
  version: '1.0.0',
  
  actions: {
    read: {
      schemaIn: fileReadSchema,
      schemaOut: fileReadResultSchema,
      permission: 'file.read',
      timeoutMs: 30000,
    },
    // ...
  },
  
  async initialize(kernel: Kernel) {
    kernel.register(this);
  },
};
```

### 3.3 插件原则

#### 插件隔离原则

每个插件必须运行在隔离环境中：

| 隔离级别 | 适用场景 | 隔离机制 |
|----------|----------|----------|
| iframe 隔离 | 卡片渲染 | 独立 origin、CSP 限制 |
| 进程隔离 | 应用插件 | 独立 BrowserWindow |
| 权限隔离 | 所有插件 | 运行时权限校验 |

#### 插件通信原则

插件间通信必须通过 Host 能力：

```typescript
// 插件 A 调用插件 B 的能力
// ✅ 正确：通过 Host 路由
const result = await window.chips.invoke('plugin-b:render', { ... });

// ❌ 错误：直接 import
import { PluginB } from 'plugin-b';  // 禁止！
```

### 3.4 错误处理原则

#### 错误归一化

所有错误必须归一化为标准格式：

```typescript
interface StandardError {
  code: string;           // 错误码
  message: string;         // 人类可读消息
  details?: unknown;       // 详细信息
  retryable?: boolean;    // 是否可重试
  source?: string;        // 错误来源
  timestamp: number;      // 错误时间
}
```

#### 错误码规范

| 前缀 | 来源 | 示例 |
|------|------|------|
| `BRIDGE_` | Bridge 层 | `BRIDGE_TIMEOUT`, `BRIDGE_INVALID_PARAMS` |
| `SERVICE_` | 服务层 | `SERVICE_NOT_FOUND`, `SERVICE_UNAVAILABLE` |
| `FILE_` | 文件服务 | `FILE_NOT_FOUND`, `FILE_PERMISSION_DENIED` |
| `PLUGIN_` | 插件系统 | `PLUGIN_INVALID`, `PLUGIN_PERMISSION_DENIED` |

### 3.5 性能原则

#### 性能预算

| 指标 | 目标值 |
|------|--------|
| 冷启动时间 | < 2s（Phase 2）/ < 1s（Phase 4）|
| 渲染帧率 | 60fps |
| 单次渲染提交（p95） | < 32ms |
| 长任务占比 | < 5% |
| 内存峰值 | < 500MB |

#### 性能优化策略

1. **懒加载**：按需加载代码和资源
2. **缓存**：多级缓存策略（内存、本地、CDN）
3. **虚拟化**：大列表强制虚拟滚动
4. **增量更新**：避免不必要的全量渲染

## 四、技术选型标准

### 4.1 选型决策框架

引入新技术前必须评估：

| 评估维度 | 权重 | 评估问题 |
|----------|------|----------|
| 功能匹配 | 30% | 是否满足核心需求？ |
| 维护状态 | 25% | 社区活跃度？长期维护？ |
| 性能影响 | 20% | 包体增加？运行时开销？ |
| 安全风险 | 15% | 已知漏洞？攻击面？ |
| 许可兼容 | 10% | 许可证是否允许商业使用？ |

### 4.2 技术栈决策

| 技术领域 | 当前选型 | 决策依据 |
|----------|----------|----------|
| 桌面运行时 | Electron 28+ | 跨平台成熟度、Web 兼容性 |
| 核心语言 | Rust | 性能、安全、跨平台 |
| 前端框架 | React 18+ | 生态完善、组件丰富 |
| 组件库 | fork antd 5.x | 功能完整、易于定制 |
| 插件框架 | Cordis | 原子化模型、动态组合 |
| 构建工具 | pnpm + Turborepo | 性能、monorepo 支持 |
| 包管理器 | pnpm | 性能、磁盘优化 |

### 4.3 禁止引入

以下情况**禁止引入**新技术：

1. 缺乏长期维护保障的开源项目
2. 安全漏洞未修复的库
3. 许可证不兼容的库（如 GPL）
4. 与现有技术栈严重冲突的库
5. 性能不达标的库

## 五、权衡原则

### 5.1 常见权衡场景

| 权衡场景 | 决策原则 |
|----------|----------|
| 性能 vs 可维护性 | 优先性能关键路径，可维护性用于非关键路径 |
| 简洁 vs 功能 | 优先简洁，复杂功能通过组合实现 |
| 灵活 vs 稳定 | 核心稳定，边缘灵活 |
| 通用 vs 专用 | 核心通用，垂直场景专用 |
| 标准化 vs 效率 | 协议标准化，实现可优化 |

### 5.2 决策记录

所有重大权衡必须记录：

1. **问题**：描述需要权衡的问题
2. **选项**：列出所有可行方案
3. **权衡**：分析各方案的利弊
4. **决策**：选择方案及理由
5. **后果**：决策的后果和风险

## 六、质量标准

### 6.1 代码质量

| 标准 | 要求 |
|------|------|
| TypeScript | strict 模式全开 |
| ESLint | 无 error |
| Prettier | 格式一致 |
| 禁止 any | 仅白名单例外 |

### 6.2 测试质量

| 测试类型 | 覆盖率要求 |
|----------|-----------|
| 单元测试 | > 80% |
| 集成测试 | 关键路径全覆盖 |
| E2E 测试 | 核心用户路径 |

### 6.3 文档质量

| 文档类型 | 要求 |
|----------|------|
| API 文档 | > 90% 覆盖率 |
| 代码注释 | 关键逻辑注释 |
| 更新要求 | 代码变更同步更新文档 |

## 七、安全原则

### 7.1 安全设计

| 原则 | 实现 |
|------|------|
| 最小权限 | 插件仅请求必要权限 |
| 纵深防御 | 多层安全检查 |
| 零信任 | 所有请求都需要验证 |
| 默认安全 | 安全配置开箱即用 |

### 7.2 安全检查清单

- [ ] 所有用户输入验证
- [ ] 所有权限校验
- [ ] 所有敏感数据加密
- [ ] 所有通信 TLS 加密
- [ ] 所有日志脱敏
