# ADR-006: 卡片与箱子统一文档链路

## 状态

**已接受** - 2026-09-19

## 背景

薯片生态中存在两种核心内容载体：

1. **卡片（Card）**：不可分割的最小内容单元，可独立存储
2. **箱子（Box）**：卡片的容器，包含多个卡片引用和布局配置

历史上，卡片和箱子采用不同的处理链路：
- 卡片有独立的渲染引擎和 SDK
- 箱子有独立的解析器和布局系统
- 两种格式的元数据格式不一致
- 渲染 API 不统一

这种分裂导致：
1. 开发成本倍增
2. 文档链路复杂
3. 用户体验不一致
4. 代码复用困难

## 决策

建立 **卡片与箱子统一文档链路**，实现：

- 统一的元数据格式
- 统一的资源解析流程
- 统一的渲染接口
- 统一的 SDK 封装

### 统一文件格式

无论 `.card` 还是 `.box` 文件，都采用相同的 ZIP 结构：

```
*.{card,box}/
├── _meta/                      # 统一元数据目录
│   ├── metadata.yaml           # 统一元数据格式
│   ├── structure.yaml          # 统一结构定义
│   └── resources.yaml          # 统一资源清单
├── content/                    # 内容目录
│   ├── *.yaml                 # 各条目配置文件
│   └── ...
└── assets/                     # 资源目录
    ├── cover.html              # 封面定义
    └── ...
```

### 统一元数据格式

```yaml
# _meta/metadata.yaml
document:
  id: "card_abc123"            # 统一 ID 格式
  type: "card" | "box"         # 类型标识
  version: "1.0"
  
identity:
  name: "我的卡片"
  description?: "卡片描述"
  tags: ["工作", "重要"]
  
timestamps:
  created: "2026-01-01T00:00:00Z"
  modified: "2026-01-02T00:00:00Z"
  
cover:
  ref: "./assets/cover.html"
  aspectRatio: "16:9"
```

### 统一 SDK 接口

```typescript
// 统一文档 SDK
class UnifiedDocument {
  // 打开文档
  static async open(path: string): Promise<UnifiedDocument>;
  
  // 保存文档
  async save(): Promise<void>;
  
  // 获取元数据
  getMetadata(): DocumentMetadata;
  
  // 获取结构
  getStructure(): DocumentStructure;
  
  // 获取资源
  async getResource(ref: ResourceRef): Promise<Resource>;
  
  // 渲染
  async render(options: RenderOptions): Promise<RenderResult>;
  
  // 验证
  validate(): ValidationResult;
}

// 具体类型
class CardDocument extends UnifiedDocument {
  getContent(): Content[];
  addContent(content: Content): void;
}

class BoxDocument extends UnifiedDocument {
  getEntries(): Entry[];
  getLayout(): LayoutConfig;
}
```

## 后果

### 优势

1. **开发效率**：一套代码处理两种文档类型
2. **一致性**：用户在不同文档间有统一的使用体验
3. **可扩展**：新文档类型可以复用统一链路
4. **测试简化**：统一测试套件覆盖所有文档类型
5. **SDK 简化**：开发者只需学习一套 API
6. **维护成本降低**：减少重复代码

### 劣势

1. **迁移成本**：现有卡片和箱子格式需要迁移
2. **复杂性增加**：统一模型需要处理更多边界情况
3. **学习曲线**：需要理解统一模型的设计理念

### 风险

1. **迁移失败**：旧版本文档可能无法正确迁移
2. **性能影响**：统一链路可能比专用链路性能略低

## 替代方案

### 方案 1：保持分离

**优点**：
- 实现简单
- 无需迁移

**缺点**：
- 代码重复
- 维护成本高
- 体验不一致

**结论**：不采用。长期成本过高。

### 方案 2：渐进式统一

**优点**：
- 风险可控
- 可逐步迁移

**缺点**：
- 过渡期复杂
- 需要维护两套代码

**结论**：不采用。过渡期成本过高。

## 实现细节

### 文件格式迁移

```typescript
// 迁移脚本
async function migrateLegacyDocument(
  input: LegacyCard | LegacyBox
): Promise<UnifiedDocument> {
  // 1. 检测类型
  const type = detectType(input);
  
  // 2. 转换元数据
  const metadata = convertMetadata(input.metadata);
  
  // 3. 转换结构
  const structure = convertStructure(input.structure);
  
  // 4. 转换资源
  const resources = convertResources(input.resources);
  
  // 5. 生成新格式
  return new UnifiedDocument({ metadata, structure, resources });
}
```

### 向后兼容

- 旧格式 `.card` 和 `.box` 仍可正常打开
- 首次打开时自动迁移到新格式
- 提供命令行工具进行批量迁移
