# ADR-007: 桌面端与移动端分离策略

## 状态

**已接受** - 2026-09-19

## 背景

薯片生态的长期目标是覆盖桌面和移动两大平台：

- **桌面端**：macOS、Windows、Linux
- **移动端**：iOS、Android（未来规划）

桌面端和移动端在以下方面存在显著差异：

| 维度 | 桌面端 | 移动端 |
|------|--------|--------|
| 输入方式 | 键鼠 | 触控 |
| 屏幕尺寸 | 大屏、可调 | 小屏、固定 |
| 多窗口 | 支持 | 不支持/受限 |
| 后台运行 | 支持 | 受限 |
| 系统集成 | 深度 | 有限 |
| 硬件能力 | 统一 | 多样 |

## 决策

采用 **桌面端与移动端分离策略**：

- **核心层共享**：Rust 核心、Cordis 运行时、文件格式保持一致
- **前端层分离**：各自平台独立的 React 前端实现
- **适配层独立**：平台适配层（PAL）各自实现

### 共享层设计

#### 1. Rust 核心（完全共享）

```rust
// chips-core/src/
pub mod document;      // 文档解析（.card, .box）
pub mod resource;      // 资源管理
pub mod plugin;        // 插件运行时
pub mod security;      // 安全验证

// 完全跨平台复用
```

#### 2. 服务层（完全共享）

```typescript
// Host Services（TypeScript）
// - card-service: 卡片操作
// - box-service: 箱子操作
// - plugin-service: 插件管理
// - config-service: 配置管理
// 所有服务共享，仅 Bridge 适配不同
```

#### 3. Bridge 层（平台适配）

```typescript
// Bridge Transport (平台特定)
interface PlatformBridge {
  // 桌面端
  desktop: {
    invoke(action: string, params: unknown): Promise<unknown>;
    on(event: string, handler: Function): void;
  };
  
  // 移动端
  mobile: {
    invoke(action: string, params: unknown): Promise<unknown>;
    addListener(event: string, handler: Function): void;
  };
}
```

### 分离层设计

#### 桌面端独立实现

| 模块 | 技术栈 | 说明 |
|------|--------|------|
| 前端框架 | React 18+ | 响应式布局 |
| 窗口管理 | Electron BrowserWindow | 多窗口支持 |
| 系统集成 | Electron APIs | 托盘、快捷键 |
| 文件系统 | Node.js fs | 完整文件系统 |
| 原生对话框 | Electron dialog | 文件选择器等 |

#### 移动端独立实现

| 模块 | 技术栈 | 说明 |
|------|--------|------|
| 前端框架 | React Native 0.72+ | 原生渲染 |
| 导航 | React Navigation | 页面导航 |
| 系统集成 | React Native APIs | 权限、相册 |
| 文件系统 | react-native-fs | 沙箱文件系统 |
| 原生对话框 | 原生组件 | ActionSheet 等 |

## 后果

### 优势

1. **平台最优**：每个平台使用最适合的技术和交互方式
2. **性能优化**：移动端无需 Electron Overhead
3. **维护分离**：平台团队可独立迭代
4. **核心共享**：文档格式、服务逻辑完全复用
5. **生态统一**：同一套插件系统在不同平台运行

### 劣势

1. **开发成本**：需要维护两套前端代码
2. **一致性挑战**：不同平台的 UI 可能不一致
3. **测试成本**：需要分别测试两个平台
4. **技术栈分裂**：需要 Electron + React Native 两套技术

### 风险

1. **体验分裂**：用户在不同平台体验差异大
2. **功能差异**：某些功能可能无法跨平台
3. **同步复杂性**：跨平台数据同步可能复杂

## 替代方案

### 方案 1：完全统一

**优点**：
- 一套代码
- 体验一致

**缺点**：
- 移动端性能差（Electron 不适合移动）
- 无法使用原生特性

**结论**：不采用。移动端必须使用原生技术。

### 方案 2：渐进式分离

**优点**：
- 风险可控
- 可逐步迁移

**缺点**：
- 过渡期复杂
- 需要维护桥接层

**结论**：部分采用。先确定架构，长期渐进分离。

## 实现计划

### Phase 1: 桌面端优先
- 完成桌面端 Electron 实现
- 验证核心共享层设计

### Phase 2: 移动端规划
- 设计移动端架构
- 实现 React Native 版本
- 验证核心共享

### Phase 3: 同步机制
- 实现跨平台数据同步
- 处理冲突场景
