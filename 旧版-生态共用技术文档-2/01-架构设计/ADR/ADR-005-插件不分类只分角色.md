# ADR-005: 插件不分类只分角色

## 状态

**已接受** - 2026-09-19

## 背景

传统插件系统往往采用分类方式管理插件，如「工具类」「内容类」「界面类」等。这种分类方式存在以下问题：

1. **边界模糊**：很多插件同时具备多种特性，难以归类
2. **扩展困难**：新功能出现时，分类体系需要重构
3. **语义不清**：分类名称无法准确描述插件能力
4. **权限耦合**：分类与权限体系难以对齐

薯片生态采用**角色驱动**的插件管理方式，插件通过声明其承担的「角色」来定义自身能力。

## 决策

采用 **插件不分类只分角色** 的设计理念：

### 角色模型

```
┌─────────────────────────────────────────────────────────────┐
│                    Plugin Manifest                           │
│  ┌─────────────────────────────────────────────────────┐    │
│  │  roles:                                              │    │
│  │    - renderer: true     # 声明渲染角色               │    │
│  │    - editor: true       # 声明编辑角色               │    │
│  │                                                     │    │
│  │  capabilities:           # 声明提供的能力            │    │
│  │    - card-renderer       # 卡片渲染能力              │    │
│  │    - image-processor     # 图片处理能力             │    │
│  └─────────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────────┘
```

### 核心角色定义

| 角色名称 | 描述 | 运行时特征 |
|-----------|------|-----------|
| `renderer` | 内容渲染器 | 提供渲染接口，被其他组件调用 |
| `editor` | 内容编辑器 | 提供编辑接口，响应用户交互 |
| `service` | 后台服务 | 无 UI，持续运行提供服务 |
| `daemon` | 守护进程 | 无 UI，随系统启动运行 |

### 角色组合

插件可以同时承担多个角色：

```yaml
# 示例：图片查看器插件
manifest:
  name: chips-image-viewer
  version: 1.0.0
  
  roles:
    renderer: true    # 可以被其他插件调用渲染图片
    editor: true     # 提供图片编辑功能
    service: false   # 不提供后台服务
  
  capabilities:
    - image-render
    - image-edit
    - image-filter
```

### 角色与 Manifest 字段映射

| 角色 | 必需字段 | 可选字段 |
|------|----------|----------|
| renderer | `entry.render` | `permissions` |
| editor | `entry.editor` | `permissions` |
| service | `entry.service` | `lifecycle.autoStart` |
| daemon | `entry.daemon` | `lifecycle.runAtStartup` |

### Manifest Schema

```typescript
interface PluginManifest {
  // 基本信息
  id: string;                    // 插件唯一标识
  name: string;                  // 插件名称
  version: string;               // 语义化版本
  description?: string;          // 描述
  author?: AuthorInfo;           // 作者信息
  
  // 角色声明
  roles: {
    renderer?: boolean;
    editor?: boolean;
    service?: boolean;
    daemon?: boolean;
  };
  
  // 能力声明
  capabilities: string[];
  
  // 入口点
  entry: {
    main?: string;               // 主入口
    render?: string;             // 渲染入口
    editor?: string;             // 编辑入口
    service?: string;            // 服务入口
    daemon?: string;             // 守护进程入口
  };
  
  // 权限声明
  permissions: string[];
  
  // 依赖声明
  dependencies?: {
    plugins?: Record<string, string>;
    capabilities?: Record<string, string>;
  };
  
  // 元数据
  metadata?: {
    icon?: string;
    screenshots?: string[];
    homepage?: string;
    repository?: string;
  };
}
```

## 后果

### 优势

1. **语义清晰**：角色直接描述插件的功能角色
2. **灵活组合**：插件可以自由组合角色，适应复杂场景
3. **易于扩展**：新角色可随时添加，不影响现有结构
4. **权限对齐**：角色与权限声明自然对应
5. **运行时决策**：Host 根据角色决定插件的加载和管理方式
6. **职责单一**：每个角色对应明确的职责边界

### 劣势

1. **设计复杂度**：需要仔细设计角色边界和组合规则
2. **文档要求高**：需要清晰的文档说明各种角色组合的预期行为
3. **迁移成本**：现有分类插件需要适配新的角色模型

### 风险

1. **角色膨胀**：如果角色设计不当，可能导致角色数量失控
2. **组合冲突**：某些角色组合可能产生预期外的行为

## 替代方案

### 方案 1：传统分类方式

**优点**：
- 概念简单
- 易于理解

**缺点**：
- 边界模糊
- 扩展困难
- 无法表达复杂插件

**结论**：不采用。无法满足薯片生态插件的多样性需求。

### 方案 2：标签系统

**优点**：
- 灵活性高
- 易于扩展

**缺点**：
- 语义模糊
- 难以标准化

**结论**：不采用。缺乏角色系统的结构化优势。

## 角色行为规范

### renderer 角色

```typescript
// 渲染入口导出
interface RenderPlugin {
  // 渲染配置
  config: {
    supportedTypes: string[];    // 支持的 MIME 类型或扩展名
    priority: number;           // 渲染优先级
  };
  
  // 渲染函数
  render(props: RenderProps): Promise<RenderResult>;
  
  // 可选：清理函数
  cleanup?(): void;
}

// 渲染生命周期
// 1. Host 调用 render(props)
// 2. Plugin 返回 RenderResult (HTML/CSS/JS)
// 3. Host 将结果嵌入 iframe
// 4. 插件卸载时调用 cleanup()
```

### editor 角色

```typescript
// 编辑入口导出
interface EditorPlugin {
  // 编辑配置
  config: {
    targetTypes: string[];       // 可编辑的类型
    priority: number;
  };
  
  // 编辑器组件
  Editor: React.ComponentType<EditorProps>;
  
  // 验证函数
  validate?(data: unknown): ValidationResult;
  
  // 转换函数
  serialize?(state: EditorState): unknown;
  deserialize?(data: unknown): EditorState;
}
```

### service 角色

```typescript
// 服务入口导出
interface ServicePlugin {
  // 服务配置
  config: {
    autoStart?: boolean;         // 是否自动启动
    singleton?: boolean;         // 是否单例
  };
  
  // 服务接口
  provide(): ServiceInterface;
  
  // 生命周期
  start?(): Promise<void>;
  stop?(): Promise<void>;
}
```
