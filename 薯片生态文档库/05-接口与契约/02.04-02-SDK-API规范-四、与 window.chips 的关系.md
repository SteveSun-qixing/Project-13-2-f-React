## 四、与 `window.chips` 的关系

- `window.chips` 由 preload 经 `contextBridge` 注入，是插件访问平台能力的唯一运行时入口；其方法面与 `IChipsBridge` 完全一致（[Bridge API 规范](./01-Bridge-API规范.md)）。
- SDK 不注入、不替换、不扩展 `window.chips`；`chips` 与 `ChipsBridge` 只做调用转发。
- SDK 主入口附带 `Window.chips` 全局声明（`readonly chips: IChipsBridge`）。插件导入 SDK 后可直接使用 `window.chips`，不得重复 `declare global`，也不得给 `Window` 添加其他平台对象。
- 主进程插件（如服务插件）不使用 `window.chips`：入口函数接收 Cordis 注入的 `Context`，通过 `ctx.provide` / `ctx.inject` / `ctx.on` / `ctx.emit` 使用服务与事件；出站能力与资源访问经 `ctx.bridge`（`IAppBridge` / `IServiceBridge`，[Bridge API 规范](./01-Bridge-API规范.md) 第 2.6 节、[核心接口规范](./03-核心接口规范.md)）。
- 渲染进程插件使用 `chips` 客户端；`window.chips` 是同一对象的底层入口，两者行为等价。Bridge 层文档为贴近协议形状可直接使用 `window.chips`。
- 禁止引用 preload 内部模块、`ipcRenderer`、`process`、`require` 等原始对象，禁止自建 IPC 通道。
