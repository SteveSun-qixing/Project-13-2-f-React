## 七、投递保证

全部标准事件与插件自有域事件的投递保证均为**至多一次（at-most-once）**：

| 通道 | 保证 | 丢失场景 |
|---|---|---|
| 内核总线（`ctx.emit` / `event:publish`） | 至多一次 | 无订阅者、插件已卸载、进程崩溃 |
| 桥接转发（主 → 渲染） | 至多一次 | 无订阅、窗口销毁、渲染进程未处理 |
| 持久化与重放 | 不提供 | 事件不写磁盘、不排队、不补发 |
| 确认与重试 | 不提供 | 发布请求成功不代表已投递 |

顺序与异常：

| 场景 | 保证 |
|---|---|
| 同一发布者、同一事件 ID | 按发布顺序投递 |
| 桥接转发 | 每个窗口通道内先进先出 |
| 跨发布者、跨进程 | 不保证顺序；需要因果顺序时在 payload 中携带逻辑序号自行处理 |

- 单个监听器抛出异常不中断派发，其余监听器继续执行；首个错误在派发完成后返回发布者，事件系统不重试。
- 嵌套派发深度上限 64，超限返回 `KERNEL_EVENT_DEPTH_EXCEEDED`。
- 监听器不得执行阻塞调用；耗时工作必须转交后台任务。
- 需要可靠传递的场景使用能力请求或由子系统自建确认机制，不得把关键业务建立在事件必达的假设上。

机制细节见《[09-事件系统设计](../01-架构设计/01-子系统设计/09-事件系统设计.md)》第六节。
