## 二、角色契约：`IServicePlugin`

### 2.1 接口定义

```typescript
interface IServicePlugin {
  /** 启动服务；由平台在 starting 阶段调用，返回后本插件进入 active。 */
  start(ctx: IServiceContext): Promise<void>;

  /** 停止服务；由平台在 stopping 阶段调用，必须先于 Fork 撤销完成。 */
  stop(): Promise<void>;

  /** 健康检查；声明 healthCheck 时由平台按周期调用。 */
  health?(): Promise<boolean>;

  /** 接收文件关联投递；manifest 声明 fileAssociations 时必须实现。 */
  handleFile?(uri: string): Promise<void>;
}
```

### 2.2 方法参考

| 成员 | 签名 | 平台调用时机 | 失败处理 |
|---|---|---|---|
| `start` | `start(ctx: IServiceContext): Promise<void>` | `starting` 阶段，每次激活调用一次 | 抛出或超时按激活失败处理：回收 Fork，插件转 `failed`，返回 `KERNEL_APPLY_FAILED` |
| `stop` | `stop(): Promise<void>` | `stopping` 阶段，`Fork.dispose()` 之前 | 抛出或超时不阻断撤销；记录 `KERNEL_DISPOSE_FAILED`，插件仍完成停用 |
| `health` | `health?(): Promise<boolean>` | 声明 `healthCheck` 后按 `interval` 周期调用 | 返回 `false`、抛出或超过 `timeout` 均按本次不健康处理（第五节） |
| `handleFile` | `handleFile?(uri: string): Promise<void>` | 声明 `fileAssociations` 后收到文件打开请求时调用 | 拒绝不中断服务；记录诊断并按 `APP_OPEN_FILE_FAILED` 语义上报（第 7.5 节） |

规则：

- 全部方法都必须在导出对象上可直接调用；平台以对象方法形式调用，插件不得要求调用方自行绑定 `this`。
- `start` 内登记的副作用（服务、能力、订阅、定时器）全部归属插件 Fork；`start` 失败的副作用由平台回收。
- `stop` 必须幂等：重复调用为 no-op；不得抛出异常中断清理链。
- `health` 必须无副作用、幂等、只读；不得在其中执行阻塞或耗时操作，也不得依赖周期性初始化。
- `handleFile` 的 `uri` 口径与 [07-应用插件接口](./07-应用插件接口.md) §3.4 一致（已归一的受管引用）；文件关联只决定路由，不代表授权。
- 超时阈值取内核常量（`apply` 30s、`stop` 10s、Fork 强撤 30s），超时以 `KERNEL_LIFECYCLE_TIMEOUT` 上报（[01-薯片内核设计](../01-架构设计/01-子系统设计/01-薯片内核设计.md)）；本文不重复数值。

### 2.3 入口模块

- 入口模块默认导出一个实现 `IServicePlugin` 的对象；模块顶层只允许声明，不允许产生副作用（定时器、订阅、文件访问等全部放入 `start`）。

```typescript
export default new ClockService();
```

- 平台在激活时对同一导出对象调用 `start`；停用后再次启用会重新调用 `start`，插件不得假设实例字段仍保留上次激活的状态（跨激活状态必须落配置或插件私有数据目录）。
- 激活期间，服务与能力注册在 `start` 成功返回后对外生效（[02-Bridge三层设计](../01-架构设计/01-子系统设计/02-Bridge三层设计.md) 4.2）；`start` 抛出时本次激活的全部注册随 Fork 回收。

### 2.4 角色约束

- 服务插件无 UI：不得创建窗口、不得渲染内容、不得注册 `capabilities.cardTypes` / `capabilities.layouts` / `ui` 字段。
- 服务插件运行在主进程：禁止直接访问 Node.js / Electron / 系统 API，禁止创建子进程；系统能力一律经 `ctx.bridge` 或内核服务获取。
- 服务插件无 UI，不得申请仅 `app` 可持有的窗口类、菜单类、托盘类、快捷键类、对话框类与外部打开类权限（`window:control`、`dialogs:use`、`shell:external` 等）；角色适用性以[08-权限系统设计](../01-架构设计/01-子系统设计/08-权限系统设计.md) 5.3 为准。

### 2.5 执行载体

服务插件的代码加载与进程形态由平台统一管理（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §5.1、§5.3）：

| 形态 | 规则 |
|---|---|
| 受管模块加载器（ModuleLoader） | 主进程插件的唯一加载路径：只允许插件作用域 `chips-resource://` 与平台白名单模块（`@chips/sdk` 类型、平台提供物）；**禁止 `node:*`、`electron`、裸路径与任意第三方原生模块**；加载器是完整性门禁，加载失败即插件启用失败 |
| 工具进程（Electron Utility Process） | 需要进程级隔离或重计算的服务逻辑在工具进程中执行；工具进程由壳提供、内核调度，崩溃按崩溃隔离与恢复策略处理，不影响主进程与其它插件（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §9） |

- 服务插件不得自行创建进程、线程或原生插件；`node:*` 与 `electron` 模块在受管加载器下不可解析，引用即加载失败。
- 服务插件的网络、文件与系统访问一律经 Bridge 能力或内核服务，进程形态不改变权限判定与审计。
