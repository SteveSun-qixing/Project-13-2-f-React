## 四、执行与结果

### 4.1 调用校验

`command:invoke` 在派发前按顺序校验，任一步失败即拒绝并写审计（`action: 'deny'`）：

1. 命令存在（`COMMAND_NOT_FOUND`）；
2. 调用上下文与 `scope` 匹配（`COMMAND_SCOPE_MISMATCH`）；插件调用方的上下文以会话实际绑定为准，输入中的 `context` 被忽略；
3. 调用方持有 `command:execute`（`BRIDGE_PERMISSION_DENIED`）；
4. `when` 求值后 `visible=true` 且 `enabled=true`（`COMMAND_STATE_INVALID`，`details.reason` 给出原因）；
5. `payload` 通过 `paramsSchema` 校验（`COMMAND_ARGS_INVALID`，`details.cause` 为 [04-能力契约规范](./04-能力契约规范.md) §5.4 的校验错误结构）；
6. 目标可执行：main 目标要求 owner 应用实例处于 `active`，否则 `COMMAND_OWNER_NOT_RUNNING`（隐式启动策略见 §4.4）。

### 4.2 派发

| 目标 | 派发方式 |
|---|---|
| `platform` | 调用平台内建处理器，等待 settle |
| `main` | 调用 owner 应用实例的 `handleCommand(commandId, payload)`，等待 settle（[07-应用插件接口](./07-应用插件接口.md) §3.3） |
| `ui` | 向注册会话投递标准事件 `command:invoked`，不等待处理完成 |

`command:invoked` 载荷：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `invocationId` | string | 是 | 调用唯一标识（ULID） |
| `commandId` | string | 是 | 命令 ID |
| `handlerId` | string | 是 | ui 目标的本地处理器标识 |
| `source` | CommandSource | 是 | 触发来源 |
| `payload` | unknown | 否 | 调用参数 |
| `context` | ICommandContext | 是 | 求值上下文（`appId` / `surfaceId` / `documentId`，缺省为 null） |

可见性：命令 owner 插件（含其注册会话）与平台；其他插件不可订阅。

### 4.3 结果

- `main` / `platform` 目标：处理完成返回 `status: 'completed'`；处理函数抛出时归一为 `COMMAND_EXECUTION_FAILED`（`details.cause` 保留原错误码），实例状态不变。
- `ui` 目标：分发成功后立即返回 `status: 'dispatched'`；执行结果由应用 UI 自行处理，平台不等待、不回传。
- 需要等待、进度与产物的自动化调用（典型为 CLI）使用 CLI 任务通道（[CLI 完整参考](../06-开发与运维/07-CLI完整参考.md)）；命令系统不提供轮询接口。
- 派发与收口都写审计（§6.2）；`command:invoked` 的投递保证为至多一次，处理方必须幂等容忍重复派发。

### 4.4 隐式启动

- `command:invoke` 不隐式启动应用。main 目标在 owner 未运行时返回 `COMMAND_OWNER_NOT_RUNNING`，调用方按正式启动链路启动应用实例后再调用。
- 平台侧调用方（CLI、系统入口、平台组件）的"启动并投递"由 CLI/平台启动契约承载：先走正式启动链路（启动来源 `command`），再调用 `command:invoke`；插件调用方无此通道。
