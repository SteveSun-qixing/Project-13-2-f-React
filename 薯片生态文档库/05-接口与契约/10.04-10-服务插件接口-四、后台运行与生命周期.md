## 四、后台运行与生命周期

### 4.1 状态与主链路

```text
installed ──enable──▶ starting ──start() 成功──▶ active
                          │                        │
                          │ start() 失败            ├── healthCheck 周期 health()
                          ▼                        │        └── 连续不健康 ──┐
                       failed ◀────────────────────┴── 运行崩溃 / 超配额 ────┤
                          │ retry（显式）                                    │
                          ▼                                                 │
                       starting                                             │
                                                                          ▼
active ──disable──▶ stopping ──stop() + Fork.dispose()──▶ installed    failed
```

| 阶段 | 平台动作 | 插件职责 | 失败结果 |
|---|---|---|---|
| `starting` | 生成会话权限快照、创建 Fork、调用 `start(ctx)` | 完成异步初始化、注册服务与能力 | Fork 回滚，插件 `failed`，`KERNEL_APPLY_FAILED` |
| `active` | 路由服务与能力调用、周期健康检查 | 响应调用、维持健康、遵守配额 | 不健康熔断；连续失败停用 |
| `stopping` | 摘除路由、调用 `stop()`、`Fork.dispose()` | 停止接收、落盘状态、释放自有资源 | `stop` 失败记录 `KERNEL_DISPOSE_FAILED`，停用照常完成 |
| `installed` | 写入启用偏好 | 无运行副作用 | — |
| `failed` | 保留清单与最后错误 | 无运行副作用 | 需显式重试 |

### 4.2 激活

1. 平台完成依赖解析与权限快照生成后创建插件 Fork。
2. 调用 `start(ctx)`；插件在此时完成初始化并调用 `provide` / `inject` / `on` / `registerCapability` / `effect`。
3. `start` 成功返回后，服务与能力注册对外生效，插件状态置为 `active`，发布 `plugin:enabled`。
4. `start` 抛出：平台捕获异常、回收本次 Fork 的全部副作用，插件转 `failed`；依赖它的插件保持 `pending`，待其恢复后自动继续（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) 4.3）。

### 4.3 运行

- `active` 期间接受服务注入消费、能力调用与事件投递；平台按 `healthCheck` 周期调用 `health()`。
- 平台施加软配额：消息频率、后台任务并发、内存占用；超配额按「限频 → 暂停后台任务 → 停用」逐级降级（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) 5.5）。
- 调用超时、取消与并发策略由 Bridge 统一收口；插件不得自建超时后继续写入（[02-Bridge三层设计](../01-架构设计/01-子系统设计/02-Bridge三层设计.md) 8）。

### 4.4 停用

- 触发来源：用户停用、依赖级联停用、卸载前置、健康检查连续失败、平台退出。
- 顺序固定为：摘除路由 → 调用 `stop()` → `Fork.dispose()` 逆序撤销空闲副作用 → 状态置 `installed`。
- `stop` 内禁止新的 `provide` / `inject` / `on` / `registerCapability`；停止期间进行的调用按超时或取消收口。
- 停用必定完成：`stop` 失败或超时由内核按策略强制撤销；失败只记录错误与审计，状态仍进入 `installed`（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) 4.4）。
- 停用不删除插件文件、配置与授权；再次启用不重新安装。

### 4.5 更新

- 服务插件更新走蓝绿替换：新 Fork 执行 `start()`，成功注册服务后原子切换服务代际，旧 Fork 进入 draining 并调用 `stop()`（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) 6.2、6.3）。
- 切换窗口内新旧两个实例短暂并存：`start` / `stop` 必须各自只管理本代际资源，禁止使用进程级单例或全局可变状态承载业务状态。
- 服务名与能力 ID 在更新前后保持不变；消费方经级联重建获得新代际，插件不得要求消费方重启。
- 新版本 `start` 失败时平台回滚到旧代际，插件保持 `active`。

### 4.6 启动恢复与后台常驻

- 平台启动时清理上次中断残留，对启用偏好集合按依赖拓扑序逐个启用；单个插件失败被隔离，不阻塞其它插件（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) 4.6）。
- `runtime.background: true` 的服务由平台在启动恢复阶段按启用偏好自动启用，运行不依赖任何界面会话；推荐常驻服务显式声明。
- `runtime.background: false` 或缺省时，平台不为该服务提供后台常驻保障：启动恢复阶段不主动启用，由用户或依赖链显式启用。
- 平台退出时对所有 `active` 服务调用 `stop()` 后统一撤销。

### 4.7 并发与长任务

- `start`、`stop`、`health` 与 `execute` 都运行在主进程调度模型中，禁止执行阻塞调用、同步文件 IO 与长循环。
- 需要周期或长时运行的处理必须使用取消令牌：在 `start` 中创建 `AbortController`，把 `abort()` 登记进 `effect` 清理与 `stop()`。

```typescript
const controller = new AbortController();
const timer = setInterval(() => {
  void pumpQueue(controller.signal);
}, 5_000);
ctx.effect(() => {
  clearInterval(timer);
  controller.abort();
});
```

- 并发策略由能力注册项决定（`parallel` / `serial`），插件不得假设同一能力的 `execute` 串行执行。
