## 三、握手与消息封套

### 3.1 协议字面量（唯一名字来源）

- 协议字面量：**`chips-cli-carrier/1`**（代码常量 `CARRIER_PROTOCOL`，`@chips/bridge` 协议分件）。
- 版本演进只走字面量版本号递增（`/2`、`/3`…）与握手协商；**禁止特性探测**：客户端不得在握手失败后改发旧版本帧试探，服务端不得按字段形状猜测版本（纪律平移自 `packages/host/src/renderer/frame-protocol.ts:17` 与 `packages/host/src/shared/card-window-init-surface.ts:62-66` 的在册先例）。
- `chips-frame/1` 与 `chips-card-window-init/1` 是宿主内部通道名，与本契约无继承关系，禁止混用（§1.4 第 2 条）。

### 3.2 握手帧

连接建立后的**首帧固定为握手请求**，不是封套帧；双向帧形状冻结如下（代码类型同名落于 `@chips/bridge` 协议分件）：

- 请求（CLI → 宿主）：`ICarrierHandshakeRequest = { protocol, clientId, bearerToken }`
  - `protocol`：客户端声称的协议字面量（v1 恒为 `chips-cli-carrier/1`）；
  - `clientId`：CLI 每次进程调用随机生成的进程实例标识（非空字符串，仅用于诊断关联，**不参与授权判定**，负载自报身份不构成信任输入）；
  - `bearerToken`：与发现文件 `bearerToken` 字段同值（§2.4）。
- 成功响应（宿主 → CLI）：`ICarrierHandshakeSuccess = { protocol, negotiated, hostVersion, instanceId }`
  - `negotiated`：恒等于请求 `protocol` 的字面量回显；`protocol` 字段保留线格式原样（供失败面统一解析）；
  - `hostVersion`：宿主语义版本字符串（诊断呈现用，不参与判定）；
  - `instanceId`：必须与发现文件 `instanceId` 一致（§2.4）；不一致时 CLI 按 `carrier_unavailable` 定性并关闭连接（错位登记防御）。
- 失败响应（宿主 → CLI）：`ICarrierHandshakeFailure = { protocol, negotiated: null, error: IChipsError }`
  - `error.code` 恒为 `CLI_TARGET_UNAVAILABLE`，`error.details.reason` 取 §5.3 词表（`protocol_mismatch` / `token_invalid`）；
  - 失败响应送达后服务端关闭连接。
- 类型收口：`ICarrierHandshakeResponse = ICarrierHandshakeSuccess | ICarrierHandshakeFailure`。

### 3.3 握手超时与前置约束

- 握手超时常量：**`CARRIER_HANDSHAKE_TIMEOUT_MS = 5000`**（`@chips/bridge` 协议分件冻结）。CLI 建连后 5 秒内未收到成功握手响应，按 `handshake_timeout` 定性走 §5.4；宿主侧对建连后 5 秒内未发握手首帧的连接直接关闭（双向 fail-closed）。
- 该常量与帧协议握手（《05-渲染引擎设计》05.09 段）、启动等待 30 秒（`packages/cli/src/constants.ts:11`）分属三层预算，互不挪用。
- 握手完成前，服务端不解析、不路由、不做任何权限判定；握手完成即登记承载会话（§4.3）。

### 3.4 消息封套：复用 Bridge 请求/响应形状

承载链路**直接复用** Bridge 线封套形状（权威形状定义：《02-Bridge三层设计》§7.2，代码源 `packages/bridge/src/protocol/ipc.ts:42-51`；宿主 IPC 适配层同构视图 `packages/host/src/protocol/wire.ts:12-37`）：

```ts
type ICarrierRequest = IBridgeRequest; // { requestId, capabilityId, input?, traceId? }
type ICarrierResponse = IBridgeResponse; // { requestId, ok: true, result } | { requestId, ok: false, error }
```

- `capabilityId` 槽承载 **`routeId`**（§5.1 在册路由名），服务端按路由表派发；这只是槽位复用，**不等于** `cli.*` 进入 Bridge 能力注册表（§4.4 禁令）。
- `error` 形状复用 `IChipsError`（`packages/bridge/src/protocol/errors.ts`），承载链路上的传输层/握手层错误按 §5.3 收敛。
- `requestId` 由 CLI 侧生成、单连接内唯一，服务端逐帧回显用于关联；别名类型 `ICarrierRequest` / `ICarrierResponse` 的唯一导出源是 `@chips/bridge` 协议分件（再导出别名，不重定义）。

### 3.5 序列化约束（《02》§7.3 纪律平移）

1. 序列化收敛 **JSON**（UTF-8）：承载链路是跨进程独立 VM 链路，不适用结构化克隆；文本禁止裸换行（§2.1 帧分界前提）。
2. 字段名一律 camelCase；时间字段一律 epoch 毫秒整数。
3. 可选字段语义为「省略 = 缺省值」，禁止显式 `null` 表达缺省（`ICarrierHandshakeFailure.negotiated: null` 是判别式联合的定值，不属于缺省表达）。
4. 错误对象只携带已登记码、简体中文消息与非敏感 `details`；禁止泄漏输入原文、凭证与内部堆栈（`IChipsError` 在册纪律）。

### 3.6 连接模型与并发

- Electron 单实例锁（`packages/host/src/main/main.ts:68`）保证发现文件指向的宿主实例每 OS 用户唯一，端点全用户唯一。
- **一次 CLI 进程调用 = 一条连接 = 一个服务端承载会话**：握手 → 串行请求/响应（`cli.task.*` 轮询臂在同一条连接内逐帧串行，天然无并发争用）→ 用完即关。无跨调用连接复用、无多路复用长连、无服务端推送帧。
- 多 CLI 并发各自独立连接，服务端每连接独立会话与在途表，互不可见。
