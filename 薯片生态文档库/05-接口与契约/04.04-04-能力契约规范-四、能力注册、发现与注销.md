## 四、能力注册、发现与注销

### 4.1 注册主体与时机

| 注册主体 | 能力来源 | 时机 | 失败处理 |
|---|---|---|---|
| 平台服务域 | 内置能力（第 6.2 节全表） | 平台启动阶段注册 | 校验失败终止平台启动 |
| 服务插件 | 已登记的第三方能力 | 服务插件 `start` 成功后，由其激活入口提交注册 | 该插件启用失败，状态置 `failed`（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) 第 4.3 节） |

- 只有 `service` 角色插件可以注册能力；`basecard` / `boxlayout` / `app` 不得注册能力（R1、[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) 第 2.3.4 节）。
- 内容处理服务能力不在此注册：其登记见第八节，形态为 Cordis 服务而非 Bridge 能力（第 2.2 节）。
- 服务插件侧的注册入口签名见 [10-服务插件接口](./10-服务插件接口.md)；注册请求由插件运行时代为提交，插件不得直接接触注册表。
- 注册项结构（`ICapabilityRegistration`：`capability` / `owner` / `timeoutMs` / `concurrency` / `maxQueue`）与注册表接口（`ICapabilityRegistry`）以 [02-Bridge三层设计](../01-架构设计/01-子系统设计/02-Bridge三层设计.md) 第 4.1 节为准，本文不重复。

### 4.2 注册校验

每次注册必须在写入注册表前完成以下校验；任一项失败都原子拒绝，不产生部分注册：

| # | 校验项 | 失败错误码 |
|---|---|---|
| 1 | `id` 符合第三节文法与命名规则 | `BRIDGE_CAPABILITY_CONFLICT` |
| 2 | `id` 在能力契约登记内，且登记绑定的提供方与注册上下文 `owner` 一致 | `BRIDGE_CAPABILITY_CONFLICT` |
| 3 | `id` 未被其他提供方占用；内置 ID 由平台服务域持有 | `BRIDGE_CAPABILITY_CONFLICT` |
| 4 | `id` 与任何权限 ID 不相同（R3） | `BRIDGE_CAPABILITY_CONFLICT` |
| 5 | `schema` 符合第五节子集且可离线编译 | `BRIDGE_INVALID_SCHEMA` |
| 6 | `permissions` 每项为已注册的基础权限 ID，且已在提供方 manifest 声明 | `PERMISSION_NOT_DECLARED` / `PERMISSION_UNKNOWN` |
| 7 | `owner` 已处于 `active` 状态 | `KERNEL_INVALID_TRANSITION`（owner 未 active 属内核生命周期状态错误，`PLUGIN_PERMISSION_DENIED` 只表示权限拒绝） |

校验项 2「登记绑定」与校验项 7「owner 激活」的内核 API 承载为 [`Bridge::grant_capability_id` 与 `Bridge::activate_provider`](./03-核心接口规范.md)（《核心接口规范》第 5.5 节）；注册与注销的具体 API 映射见 4.4。

### 4.3 发现

| 发现面 | 消费者 | 机制 |
|---|---|---|
| 编译期 | 插件开发者 | 内置能力：`@chips/sdk` 导出 `ICapabilityContracts`（第 2.3 节）与本文第 6.2 节全表；第三方 Bridge 能力：提供方随插件发布的能力契约（第九节）；内容处理服务能力：提供方契约包按第八节登记发布，不经 Bridge 发现面。`capabilityId` 与输入/输出类型在编译期检查 |
| 静态预期 | 安装与启用流程 | manifest 的 `permissions` 与 `dependencies` 声明调用预期；安装与启用阶段校验权限与依赖是否存在、是否匹配（[08-权限系统设计](../01-架构设计/01-子系统设计/08-权限系统设计.md) 第 5.3 节） |
| 运行时 | 任意调用方 | Bridge 不提供能力枚举 API（`IChipsBridge` 方法面固定）；能力缺失以 `BRIDGE_CAPABILITY_NOT_FOUND` 判定，不可重试 |
| 平台工具 | 插件管理界面、诊断与文档生成 | 平台内部只读能力编目（下）。 |

```typescript
interface ICapabilityDescriptor {
  id: string;
  owner: string;
  permissions: readonly string[];
  schema: JSONSchema;
  builtin: boolean;
  state: 'active' | 'draining';
}

interface ICapabilityCatalogFilter {
  owner?: string;
  domain?: string;
  builtin?: boolean;
}

interface ICapabilityCatalog {
  get(capabilityId: string): ICapabilityDescriptor | undefined;
  list(filter?: ICapabilityCatalogFilter): readonly ICapabilityDescriptor[];
}
```

编目是注册表的只读视图，**不通过 `window.chips` 暴露给插件**；其权威实例位于 Bridge 核心，主进程 TS 适配层只读查询。编目的内核侧只读面为 `Bridge::has_capability`（存在性，draining 在册语义见第十节）与 `Bridge::capability_state`（`state` 字段，返回类型 `CapabilityState` 是 `active` / `draining` 的 Rust 侧权威枚举），登记于 [03-核心接口规范](./03-核心接口规范.md) 第 5.8 节。

### 4.4 注销与在途调用

| 触发 | 处理 |
|---|---|
| 服务插件 `stop` / 停用 / 卸载 | 插件运行时在 `stop` 前提交注销；注销幂等 |
| 服务插件崩溃 / Fork dispose | 随 Fork 逆序撤销，注册项一并摘除 |
| 平台退出 | 全部注册项随 Bridge 关闭注销 |
| 蓝绿更新代际切换 | 旧代际注册项进入 `draining`，新代际接管（第 9.3 节、第十节） |

- 注销后停止接受新调用（`BRIDGE_CAPABILITY_NOT_FOUND`）；在途调用按 [02-Bridge三层设计](../01-架构设计/01-子系统设计/02-Bridge三层设计.md) 第 8 节收口，调用方收到结果或 `BRIDGE_CANCELLED`。
- 注销完成后，同一 ID 只能由原 `owner` 重新注册；其他提供方不得抢占，重注册校验与首次注册一致。
- 注销是幂等操作：对已注销 ID 重复注销为 no-op，不产生错误。

**触发 → 内核 API 映射**（行为承诺的可执行面；接口签名与失败码以 [03-核心接口规范](./03-核心接口规范.md) 第 5 节为唯一发布处）：

| 触发表触发 | `chips-bridge` 内核 API | 规范小节 |
|---|---|---|
| 服务插件 `stop` / 停用 / 卸载 | 单能力注销 `Bridge::unregister(capability_id)`；提供方整体停用 `Bridge::deactivate_provider(owner)`（批量注销其全部能力并在途按取消收口） | 核心接口规范 第 5.1、5.5 节 |
| 服务插件崩溃 / Fork dispose | 插件运行时随 Fork 逆序撤销调用 `Bridge::deactivate_provider(owner)`，注册项一并摘除 | 核心接口规范 第 5.5 节 |
| 平台退出 | `Bridge::shutdown()`：取消全部在途、拒绝新请求，全部注册项随关闭注销 | 核心接口规范 第 5.7 节 |
| 蓝绿更新代际切换 | 旧代际 `Bridge::begin_draining(capability_id)` + 新代际 `Bridge::takeover_register(registration)`；状态查询 `Bridge::capability_state(capability_id)` | 核心接口规范 第 5.8 节 |

- 「同一 ID 只能由原 `owner` 重新注册」的内核承载：注册期原 owner 绑定校验由 `Bridge::register` 统一执行（绑定不随注销移除）；蓝绿切换中的同 owner 定义覆盖唯一入口是 `Bridge::takeover_register`，跨 owner 一律 `BRIDGE_CAPABILITY_CONFLICT` 拒绝（第 9.3 节）。
- 「draining 后拒绝新调用、在途完成或按超时收口、在途清零进入已注销」的编排触发方（哪个生命周期节点调用映射表中的切换 API）属宿主与插件运行时职责，内核不自行编排。
- 上表 API 与 `Bridge::activate_provider` / `Bridge::grant_capability_id` / `Bridge::open_session` / `Bridge::close_session`、`invocation_context`（审计面）同属契约发布面；未在《核心接口规范》第 5 节登记的成员（如 `is_shutdown`）为非契约面，不得成为生态内必需依赖。
