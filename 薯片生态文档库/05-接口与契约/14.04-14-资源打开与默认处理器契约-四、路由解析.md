# 资源打开与默认处理器契约

> 版本：v1.0.0
> 日期：2026-09-19
> 状态：正式版
> 适用范围：资源打开路由的权威契约：打开来源与打开请求模型、manifest 处理器声明与 `primary` / `fallback` 层级、路由解析顺序与投递授权、启动载荷 `resourceOpen` 与业务载荷约定、默认处理器偏好 `platform.fileOpen.defaults` 与槽位治理接口、未安装/停用/卸载的降级与回收、与文档/条目/封面链路的关系；资源 URI 语法、句柄与权限判定本身不在此定义。

## 四、路由解析

### 4.1 解析顺序

对每个打开请求，路由按以下顺序解析（`resolveHandler` 是唯一解析实现）：

```text
输入归一（§2.3）
   │
   ▼
[1] 匹配等级                 M1 精确 MIME ＞ M2 主类型通配 ＞ E1 扩展名
   │
   ▼
[2] 用户偏好覆盖              platform.fileOpen.defaults 按
   │                          mime:<精确> → mime:<主类型>/* → ext:<扩展名> 查找；
   │                          有效偏好直接改选其插件（不改变等级判定）
    ▼
[3] 组内排序                  同等级内：primary 先于 fallback →
   │                          安装顺序（先安装优先）→ 插件 ID 字典序升序
   ▼
[4] 选定处理器                有效偏好命中时取偏好插件；
   │                          否则取排序后的首个候选
   │
   ├─ 命中 app     → 投递至应用实例（§4.3）
   ├─ 命中 service → 经 handleFile 投递（§4.3）
   └─ 无候选       → 未命中降级（§4.6）
```

匹配等级定义：

| 等级 | 判定 | 示例 |
|---|---|---|
| M1 | 声明的 `mimeTypes` 精确包含请求 MIME | 请求 `image/png` 命中声明 `image/png` |
| M2 | 声明的 `mimeTypes` 包含主类型通配 `<主类型>/*` | 请求 `image/tiff` 命中声明 `image/*` |
| E1 | 声明的 `extensions` 包含请求扩展名 | 请求 `.png` 命中声明 `.png` |

规则：

- 高等级优先：存在 M1 候选时不再考查 M2 与 E1；无 M1 时考查 M2；M1 与 M2 均无时才考查 E1。
- 同一插件在多个等级命中时只作为该插件的最佳等级候选，不重复计入。
- 请求 MIME 为 `application/octet-stream`（无法判定）时跳过 M1 与 M2，直接按 E1 匹配；扩展名同时缺席时无候选，走 §4.6。
- 解析是确定性函数：同样输入与同样插件状态必须得到同样结果，禁止随机、时间或会话因素参与排序。

### 4.2 用户偏好覆盖

用户偏好（§6.1）在匹配等级之后、组内排序之前应用：

1. 按 `mime:<精确 MIME>` → `mime:<主类型>/*` → `ext:<扩展名>` 顺序在 `platform.fileOpen.defaults` 中查找第一个存在的键。
2. 该键指向的插件处于 `active` 状态，且在此次候选集合中拥有任一等级命中，则以该插件为选定处理器；其匹配等级取该插件自身的最佳等级。
3. 指向的插件已停用、`failed`、已卸载或未声明任何命中候选时，忽略该偏好项，进入常规排序（偏好记录保留，§7.2）。
4. 偏好只改选插件：不能把未声明命中候选的插件变成候选，不能改变该插件自身的匹配等级判定，不能跳过角色与权限判定与投递授权。

### 4.3 投递

选定处理器后按角色投递：

| 角色 | 插件未启用 | 无实例 | 已有实例 |
|---|---|---|---|
| `app` | 按启动流程请求启用；启用失败以错误上报，不尝试下一候选 | 创建实例并调用 `launch`，`ctx.args` 为 `IResourceOpenLaunchArgs`（§5.1） | `active`：投递 `openFile(uri)`；`launching`：随 `launch` 完成后排队投递；`exiting`：拒绝并记诊断（[07-应用插件接口](./07-应用插件接口.md) §6.2） |
| `service` | 按文件关联路由请求启用后投递（[10-服务插件接口](./10-服务插件接口.md) §7.5） | 服务无实例概念：启用后调用 `handleFile(uri)` | 调用 `handleFile(uri)`；无窗口、无 `windowId` |
| `shell` | 不适用 | 不适用 | 平台解析底层真实路径并交操作系统默认程序打开 |
| `external` | 不适用 | 不适用 | 交系统浏览器打开 |

规则：

- `resource:open` 等待投递完成：新建实例等待 `launch` settle，已运行实例等待本次 `openFile` settle；处理器抛错按原错误码（`APP_LAUNCH_FAILED`、插件错误码）拒绝调用方。
- 处理器启动失败不再改投其他候选：打开意图只执行一次，避免不可预期的二次行为；失败写入诊断与审计（[07-应用插件接口](./07-应用插件接口.md) §8.3）。
- 平台壳层入口（`os-association`、`drop`）无调用方时，投递失败由平台记录诊断、写审计并给出用户可见提示。
- 投递顺序与多文件语义以 [07-应用插件接口](./07-应用插件接口.md) §6.2 为准：同批文件按到达顺序逐个投递，前一次 settle 后再投递下一次。

### 4.4 投递授权

打开投递常涉及接收方原本无权访问的作用域（文档作用域、他人插件作用域、系统关联的临时路径）。平台在投递前登记**投递授权**：

1. **授权对象**：接收方实例会话（`app` 的应用实例或 `service` 的当前激活代际）。
2. **授权范围**：本次打开的主资源 URI，加业务载荷 `resources.*` 引用的全部资源（封面、歌词、字幕、图片序列等）；平台在解析阶段归一收集为授权清单，未列入清单的 URI 不获授权。
3. **生效与失效**：投递前登记；接收方实例退出、投递被终止或资源失效时注销；授权不跨实例、不跨会话复用。
4. **权限边界**：只授读取，不授写入；接收方仍须在 manifest 声明 `resources:read` 基础权限，投递授权只替代作用域限定值的逐项用户确认——用户打开动作即授权，与 `dialog:open` 临时作用域同级（[04-资源管理设计](../01-架构设计/01-子系统设计/04-资源管理设计.md) §5.4）。
5. **可审计**：授权清单、每次跨作用域访问与失败均写入审计（[08-权限系统设计](../01-架构设计/01-子系统设计/08-权限系统设计.md) 第八节）；授权不写入 `permissions.yaml`（非持久授权）。

### 4.5 结果模型

```typescript
/** 投递模式。 */
export type ResourceOpenMode = 'app' | 'service' | 'shell' | 'external';

/** 打开结果。 */
export interface IResourceOpenResult {
  readonly mode: ResourceOpenMode;
  /** mode 为 app / service 时命中处理器插件 ID。 */
  readonly pluginId?: string;
  /** mode 为 app 且实例主窗口已创建时的窗口 ID（[07-应用插件接口](./07-应用插件接口.md) §4.4）。 */
  readonly windowId?: number;
  /** 命中槽位键（mime:<mime> / ext:<ext>）；shell / external 模式缺席。 */
  readonly slot?: string;
  /** 归一后的资源视图，供日志与诊断。 */
  readonly resolved: {
    readonly uri: string;
    readonly mimeType: string;
    readonly extension?: string;
    readonly fileName?: string;
  };
}
```

- `resolved` 是平台归一结果，只用于日志、诊断与展示；接收方实际读取入口以启动载荷 `resourceOpen.uri` 为准（§5.2）。
- 结果不携带真实路径与底层来源信息。

### 4.6 未命中降级

无任何候选处理器时按确定性顺序降级：

```text
无候选
  ├─ External 作用域引用（http(s) / webdav 来源）
  │     → mode: external，交系统浏览器打开
  ├─ Directory 来源（工作区、目录态文档、插件、临时作用域）
  │     → mode: shell，交操作系统默认程序打开
  │           └─ 系统打开不可用或失败 → RESOURCE_HANDLER_MISSING
  └─ Archive 成员（归档态 .card / .box / .cpk 内部资源）、Memory 字节
        → RESOURCE_HANDLER_MISSING（无底层真实路径，不可回退系统打开）
```

规则：

- 降级是路由的正式组成部分，不是错误兜底；`shell` 与 `external` 结果正常返回。
- `shell` 模式由平台内部完成路径解析与系统调用，不经过 `shell:openExternal` 能力，不要求调用方持有 `shell:external` 权限（调用方表达的是「打开该资源」，不是「用系统程序打开」）。
- 回退失败返回 `RESOURCE_HANDLER_MISSING`；`os-association` 来源下平台提示「没有可以打开该文件的处理器」并引导安装，同时写诊断与审计。
- 兜底处理器内部的呈现策略（如不支持格式的信息卡、下载引导）属处理器应用自身策略，平台不感知、不介入；平台只保证路由与回退确定。

### 4.7 失败语义

| 失败点 | 表现 | 调用方（`in-app`） | 壳层来源 |
|---|---|---|---|
| 输入不合法 | `BRIDGE_INVALID_INPUT` | 拒绝调用 | 记诊断 |
| 无 `resources:read` | `BRIDGE_PERMISSION_DENIED` | 拒绝调用 | 不适用 |
| 作用域越权 | `RESOURCE_PERMISSION_DENIED` | 拒绝调用 | 记诊断并提示 |
| 无候选且不可回退 | `RESOURCE_HANDLER_MISSING` | 拒绝调用 | 提示并引导安装 |
| 处理器启用失败 | 内核错误码（如 `KERNEL_DEPENDENCY_MISSING`） | 拒绝调用 | 记诊断并提示 |
| `launch` 失败 | `APP_LAUNCH_FAILED` | 拒绝调用 | 记诊断并提示 |
| `openFile` / `handleFile` 失败 | 插件错误码或 `APP_OPEN_FILE_FAILED` | 拒绝调用 | 记诊断并提示 |
| 路由超时 | `BRIDGE_TIMEOUT` | 拒绝调用 | 记诊断并提示 |

- 处理器启动失败后**不**自动改投其他候选；用户可经「文件打开方式」调整默认处理器后重试（§六）。
- 全部失败写审计；诊断不得包含文件内容、凭证或未脱敏路径（[04-能力契约规范](./04-能力契约规范.md) §10.4）。
