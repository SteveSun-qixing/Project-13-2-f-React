## 二、传输与端点发现

### 2.1 传输形态（Q1 裁定）

1. POSIX 平台使用 **Unix domain socket**，Windows 平台使用 **named pipe**（`\\.\pipe\…`）；两端统一收敛于 Node `node:net` 原语（`path` 型 server/client）。宿主实例监听就绪后一侧常开监听，每个宿主实例恰好一个承载端点。
2. **禁止** localhost TCP、stdio 子实例、文件信令轮询与广播/知名端口/进程枚举作为承载传输形态（立项评估 §① 方案 B/C/D 否决，理由随第八节裁定入册于 §1.4 第 4 条）。
3. **帧分界**：一条连接上的帧序列为**换行分隔 JSON**（每行一个完整 JSON 文本帧，行间以单个 `\n` 分隔；序列化文本内不得出现裸换行，即 `JSON.stringify` 缺省形状）。首帧固定为握手帧（§3.2），握手完成后的每帧为一个封套请求或封套响应（§3.3）。
4. 端点文件权限保护（UDS socket 文件 `0600`、所在目录 `0700`）与 bearer token 共同构成传输面鉴权，细则见 §4.2。
5. macOS `sun_path` 104 字节上限与陈旧 socket 清理为**规范必项**，细则见 §2.3 与 §2.5；Windows named pipe 无 POSIX 权限语义，pipe ACL 为「实现许可的额外校验」非规范必项（§1.4 第 3 条）。pipe 实例随句柄关闭回收，无文件系统残留清理义务。

### 2.2 端点落点与单一派生源（Q2 裁定）

承载端点生命周期 = 宿主实例生命周期 = 用户级（每 OS 用户一个宿主实例，§3.5）。端点文件与发现文件落点由 `<userData>` 派生：

| 对象 | 落点（字段级规范） |
|---|---|
| 发现文件 | `<userData>/chips-carrier.json` |
| 承载端点（POSIX） | `<userData>/chips-carrier.sock`（darwin/linux；超长缩短形态见 §2.3） |
| 承载端点（win32） | `\\.\pipe\chips-carrier-<H>`，`H` = `SHA-256(UTF-8(userData))` 十六进制摘要的前 16 位小写字符（pipe 名是机器全局的，散列保证多用户并发不互踩） |

- `<userData>` 为宿主实例的 Electron `app.getPath('userData')` 值（`packages/host/src/main/main.ts:99`），与插件安装根同根（`packages/host/src/main/production-assembly.ts:201` 的 `join(userDataPath, 'chips-plugins')` 前例）。
- **跨平台 `userData` 布局推导规则**（本文档为该规则的字段级唯一权威）：宿主应用名取发行配置 `productName: Chips`（[02.06 §6.1](../06-开发与运维/02.06-02-构建与打包-六、Electron 应用打包与签名.md)），Electron 缺省 `userData` 布局为——darwin：`~/Library/Application Support/Chips`；linux：`$XDG_CONFIG_HOME`（未设置时 `~/.config`）`/Chips`；win32：`%APPDATA%\Chips`。宿主若显式 `setPath('userData', …)` 覆写，以覆写值为其 `userData` 根，发现文件记录中的 `socketPath` 仍由 §2.3 纯函数从该根派生。
- **单一派生源条款**：上述布局规则在代码面的唯一共享实现为 `@chips/bridge` 协议分件（`packages/bridge/src/protocol/carrier.ts`）导出的纯函数 **`deriveCarrierEndpoints(userdataRoot: string): ICarrierEndpoints`**，宿主与 CLI 双侧消费同一实现并由契约测试锁双侧一致。本波（波 0）冻结其名称与形状：

```ts
export interface ICarrierEndpoints {
  readonly userdataRoot: string;
  readonly discoveryFile: string;   // <userdataRoot>/chips-carrier.json
  readonly socketPath: string;      // POSIX 形态或 win32 pipe 名，按上表
}
export function deriveCarrierEndpoints(userdataRoot: string): ICarrierEndpoints;
```

- 纯函数约束：无 IO、无时钟、无全局状态；同输入字节级同输出；不做存在性判断（文件在不在是消费方的事）。**禁止** CLI 侧复刻 Electron 命名逻辑的第二份散落推导；实现落波 1，波 0 只冻结类型与常量形状供后续波消费。

### 2.3 `sun_path` 上限与缩短形态（规范必项）

1. darwin 上 `bind` 的 socket 路径 UTF-8 字节数受 `sockaddr_un.sun_path` 104 字节上限约束（linux 为 108，按同一规则一并处理）。
2. `deriveCarrierEndpoints` 的冻结算法：先按 §2.2 固定形态派生；若 POSIX 平台派生结果 UTF-8 字节数超限，socket 文件名缩短为 `chips-c-<H>.sock`（`H` 同 §2.2 的 16 位散列，缩短名自身仅 29 字节）。
3. 若缩短后仍超限（`userdataRoot` 本身过深），**承载端点 fail-closed**：宿主照常启动、不监听承载、不写发现文件，并把该状态计入 `report()` 诊断面；CLI 侧按无承载定性（§5.4）。禁止为绕过上限在 `deriveCarrierEndpoints` 之外引入第二份路径推导。

### 2.4 发现文件记录形状

发现文件为一个 UTF-8 JSON 文档（单帧、无换行要求），字段冻结如下（camelCase、epoch 毫秒）：

| 字段 | 类型 | 规范 |
|---|---|---|
| `protocol` | `string` | 恒为 `chips-cli-carrier/1`（§3.1），CLI 读出不匹配即按 `protocol_mismatch` 处理（§5.3） |
| `instanceId` | `string` | 宿主每次承载实例启动随机生成的实例标识；发现文件与握手响应中的 `instanceId` 必须一致（§3.2） |
| `socketPath` | `string` | `deriveCarrierEndpoints` 输出的承载端点值 |
| `pid` | `number` | 宿主进程 PID（陈旧双判据之一，§2.5） |
| `startedAt` | `number` | 承载实例启动时刻，epoch 毫秒整数（陈旧双判据之二，§2.5） |
| `bearerToken` | `string` | CSPRNG 32 字节的小写 hex 64 字符；每承载实例启动重新生成，不落日志（§4.2、§2.8-脱敏） |

- 严格形状：未知字段拒绝（CLI 读出含未知顶层字段时按无效记录视同陈旧、走 §5.4 定性）；字段缺失或类型不符同理。
- 文件权限 `0600`；其所在 `userData` 目录要求 `0700`（POSIX）。win32 无 POSIX 权限语义，边界如实按 §1.4 第 3 条登记。
- 代码面记录类型：`ICarrierDiscoveryRecord`（`@chips/bridge` 协议分件，波 0 冻结）。

### 2.5 写删与陈旧治理

1. **原子写**：宿主写发现文件采用同目录临时文件 + `rename` 替换（临时文件名 `chips-carrier.json.tmp-<instanceId>`），CLI 读到的永远是完整记录。
2. **bind 前清理**：宿主启动监听前，若 `socketPath` 已有残留（`EADDRINUSE`）且按判据 3 判定陈旧，删除后重试 bind；判定不陈旧（真并发宿主存在，理论上被单实例锁排除）则承载面 fail-closed 并诊断留痕。
3. **陈旧双判据**：PID 不存在，或 PID 存在但该进程创建时间晚于记录 `startedAt`（PID 复用），判定记录陈旧。两判据必须同时实现，防 PID 回收窗口的假活。
4. **清理权**：陈旧清理只属于宿主启动序（写新记录前）与停机序（§2.5-5）；CLI 读出陈旧或连接失败时**不得**删除登记文件——CLI 无判据完备性（拿不到进程创建时间），删除权归写入方是原子治理的前提。CLI 侧的对应定性是 §5.4。
5. **停机顺序**：关闭监听（拒新连接；在途连接按 §5.4 取消收口）→ 删除 socket 文件 / 关闭 pipe 实例 → 删除发现文件。先断入站再毁地址，防「文件在、端点亡」的中间态被新客户端读取。

### 2.6 环境变量覆盖面（Q4 裁定）

| 变量 | 语义 | 严格错误语义（比照 `CHIPS_TRUST_ROOTS_FILE` 先例，`packages/cli/src/artifacts/trust-roots.ts:1-20`） |
|---|---|---|
| `CHIPS_CARRIER_SOCKET` | 显式给出承载端点路径（POSIX socket 路径或 win32 pipe 名），命中即跳过发现文件读取与按需拉起（§5.2），直连该端点后仍必须完成握手与 token 校验（token 从发现文件读取；发现文件不存在时握手以 `carrier_unavailable` 失败收口） | 空串按未设置处理；非绝对路径（win32 下非 `\\.\pipe\` 前缀）返回 `CLI_PATH_INVALID`（退出码 5），`details.env` 登记变量名 |
| `CHIPS_CARRIER_DISABLE` | 置 `1` 时为确定性离线条：完全跳过发现、连接与拉起，所有需要承载的路由按现行无承载回退链定性（发现阶段 → 3；平台操作面 → 6），供 e2e/CI 巩固 `no-carrier` 套件语义 | 值非 `1` 且非空串返回 `CLI_ARGUMENT_INVALID`（退出码 2），`details.env` 登记变量名；空串按未设置处理 |

- 两变量是承载域唯一正式注入通道（dev/e2e 零污染），命名与语义在 §2.7 环境变量表登记（[07.02 §2.7](../06-开发与运维/07.02-07-CLI完整参考-二、调用约定.md)）。
- 两变量都不进发现文件、不影响 §2.2 派生纯函数；`CHIPS_CARRIER_SOCKET` 只覆盖端点，不提供 token 旁路。

### 2.7 与运行标记的关系

运行标记 `<workspace>/.chips/state/host-state.json`（《07-CLI 完整参考》§3.2）是工作区状态面，**承载链路不依赖该标记**（07.03 §3.2.2 在册口径的承载域落点）：发现文件的判据是 PID+`startedAt` 双判据与 bearer token，与运行标记的存在与否、内容正误无因果关系。

### 2.8 承载面数据边界

1. `bearerToken` 禁止出现在 CLI 结果信封、日志、操作日志与诊断快照中（《07-CLI 完整参考》§2.8 脱敏纪律的承载域扩展：`token` 键名规则天然覆盖）。
2. 发现文件与 socket 路径可出现在诊断 `details.path`（比照 trust-roots 注入面 `details.path` 先例），文件内容中的 token 不可。
