# 资源打开与默认处理器契约

> 版本：v1.0.0
> 日期：2026-09-19
> 状态：正式版
> 适用范围：资源打开路由的权威契约：打开来源与打开请求模型、manifest 处理器声明与 `primary` / `fallback` 层级、路由解析顺序与投递授权、启动载荷 `resourceOpen` 与业务载荷约定、默认处理器偏好 `platform.fileOpen.defaults` 与槽位治理接口、未安装/停用/卸载的降级与回收、与文档/条目/封面链路的关系；资源 URI 语法、句柄与权限判定本身不在此定义。

## 一、定位与边界

### 1.1 定位

本文定义**资源打开路由**：把「打开某个资源」的意图解析为具体处理器（专用或兜底），并把资源与上下文投递给该处理器的唯一机制。生态中一切打开动作共用这条路由：

- 平台壳层接收的系统文件关联与拖放；
- 应用插件发起的应用内打开；
- 查看态渲染帧内的用户点击；
- 由路由统一承担处理器发现、优先级匹配、默认处理器偏好、启动载荷组装与未命中回退。

核心原则：

1. 打开必须经资源打开路由；调用方不得硬编码目标插件 ID，不得自行实例化或调用其他插件（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §8.4）。
2. 平台只提供路由机制，不内置任何具体格式的处理器；格式能力全部由插件以 manifest 声明提供（[架构原则](../00-愿景与原则/01-架构原则.md) §1.2）。
3. 路由解析与投递不读取资源字节；内容访问仍按资源协议与权限判定（[06-资源协议规范](./06-资源协议规范.md)、[08-权限系统设计](../01-架构设计/01-子系统设计/08-权限系统设计.md)）。
4. 第一版前无兼容义务：旧版 `resource-handler` / `file-handler` 能力串、`@fallback` 后缀、`capabilityFallbacks` 与 `targetPath` 均不进入新架构（[ADR-010](../01-架构设计/ADR/ADR-010-大爆炸重构策略.md)）。

### 1.3 术语

| 术语 | 定义 |
|---|---|
| 资源打开路由（open route） | 平台主进程组件：打开意图归一、处理器解析、用户偏好应用、投递与回退；`resource:open` 能力入口与平台壳层入口都汇聚到它 |
| 打开意图（open intent） | 打开一个资源的目标：`view`（查看）或 `edit`（编辑） |
| 处理器（handler） | 声明 `fileAssociations` 并以 `openFile` / `handleFile` 接收打开投递的 `app` / `service` 插件 |
| 专用处理器（primary） | 声明 `tier: primary`（缺省）的处理器；专用查看器、编辑器使用该层级 |
| 兜底处理器（fallback） | 声明 `tier: fallback` 的处理器；通用查看器使用该层级，只在同槽位无更高优先候选时接管 |
| 槽位（slot） | 路由的匹配单元：MIME 槽位 `mime:<mime>` 或扩展名槽位 `ext:<ext>`；默认处理器偏好与槽位视图都以槽位为粒度 |
| 默认处理器（default handler） | 某槽位当前生效的处理器：有效用户偏好优先，否则按匹配等级、层级与安装顺序解析 |
| 投递授权（delivery grant） | 平台为接收方实例登记的临时只读访问项，覆盖本次打开涉及的资源引用；随实例会话失效（§4.4） |
| 业务载荷（payload） | 发起方随打开透传的结构化上下文；平台不解释其业务语义 |
