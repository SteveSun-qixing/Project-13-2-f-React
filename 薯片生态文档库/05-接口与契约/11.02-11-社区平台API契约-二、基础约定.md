## 二、基础约定

### 2.1 端点与版本前缀

- 前台 API 前缀：`/api/v1`；后台 API 前缀：`/admin/api/v1`；版本前缀属于路径，不接受请求头版本协商。后台端点级契约见第十一节。
- 生产环境只允许 HTTPS（见第九节）；本地开发允许 `http://127.0.0.1:<port>`。
- 端点地址由客户端设置提供，默认 `https://www.chipscard.space`；客户端不得写死备用域名。

### 2.2 数据格式

| 项 | 规则 |
|---|---|
| 请求 / 响应 | JSON，`Content-Type: application/json; charset=utf-8` |
| 头像与房间封面上传 | `multipart/form-data`（仅这两个入口允许字节进入 API 进程） |
| 时间 | RFC 3339 UTC，例如 `2026-09-19T08:00:00.000Z` |
| 服务端实体 ID | UUID v4，例如 `id` / `userId` / `roomId` / `uploadId` |
| 文件级 ID | 10 位 Base62：`cardFileId` 取自 `.card/metadata.yaml` 的 `card_id`，`boxFileId` 取自 `.box/metadata.yaml` 的 `box_id` |
| JSON 字段命名 | 统一 camelCase；字段说明中标注其来源文件字段（如 `coverRatio` ← `cover_ratio`） |

### 2.3 响应信封

除 `GET /api/v1/health` 外，全部接口使用统一信封。

成功（对象）：

```json
{ "data": { } }
```

成功（列表）：

```json
{
  "data": [],
  "pagination": {
    "page": 1,
    "pageSize": 20,
    "total": 100,
    "totalPages": 5
  }
}
```

失败：

```json
{
  "error": {
    "code": "COMMUNITY_VALIDATION_ERROR",
    "message": "字段 pageSize 必须在 1 到 100 之间",
    "details": { "field": "pageSize" },
    "retryable": false
  }
}
```

- `error.code` 只取第七节登记的业务码；`error.message` 为简体中文、面向用户，不携带堆栈、对象键、真实路径与原始输入；诊断细节放 `error.details`。
- `error.retryable` 为提示字段；缺省时客户端按第七节表内 `retryable` 判定。
- 无正文成功的状态码为 `204`，不得返回空 JSON 对象。

### 2.4 请求追踪

- 请求可携带 `X-Request-Id`（32–128 个可见 ASCII 字符）；服务端必须原样回显，未携带时由服务端生成并回显。
- 错误响应的 `error.details.traceId` 为服务端日志关联标识；客户端把它记入诊断信息，不向用户展示。

### 2.5 健康检查

`GET /api/v1/health` 不使用统一信封：

```json
{
  "status": "ok",
  "timestamp": "2026-09-19T08:00:00.000Z",
  "version": "0.1.0",
  "apiVersion": "v1"
}
```

- 无需认证；失败时返回 `503` 与 `status: "degraded"`，`details` 列出不可用组件（`database` / `redis` / `storage`）。
- 客户端启动与故障排查使用该接口判断服务端可用性与 API 版本；`version` 为服务端实现版本。
