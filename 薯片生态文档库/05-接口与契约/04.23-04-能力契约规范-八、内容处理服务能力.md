## 八、内容处理服务能力

### 8.1 定位与边界

- 内容处理服务能力（下称内容处理能力）是由 `service` 角色插件通过 `ctx.provide` 注册、承载具体格式算法的 Cordis 服务能力：图像编解码与缩放、视频抽帧与转码、Office / PDF 引擎（含受保护文档的加密容器识别与口令解密）、媒体元数据、字体度量、HTML 渲染导出等。
- 内容处理能力**不注册为 Bridge 能力**、不进入第 6.2 节 R19 全表、不经过 Bridge 权限判定、schema 校验与审计（第 2.2 节服务边界）；消费方经 `ctx.inject` 注入后按提供方契约的类型化接口调用；格式转换链路编排归 `content-file-conversion.convert`（本节登记项），通用文件处理会话、跨格式通用编排与受控提交归 [15-文件处理契约](./15-文件处理契约.md)。
- 本节是内容处理能力的**唯一登记处**：能力 ID、归属官方服务插件、原子操作、输入/输出要点、权限映射与错误码族。逐项字段级 schema、格式选项语义与支持矩阵随提供方契约包发布，本节只登记、不复制。
- 与文档链路的分工：`.card` / `.box` 的解析、渲染与写入仍归文档解析器、渲染引擎与文档服务；内容处理能力不得实现第二解析器、第二渲染管线与文档写口（R8）。文档可作为转换来源，但必须经 `document:*` 与平台渲染链路消费（[15-文件处理契约](./15-文件处理契约.md) §2.4）。

### 8.2 标识与命名空间

内容处理实现不注册为 Bridge 能力，由 `service` 角色插件通过 Cordis 服务提供；本节规定其登记标识与命名空间：

```text
content-capability-id = service "." operation
service               = "content-" 1*( lowercase / digit / "-" )   ; 内容处理服务名，本节登记分配
operation             = 1*( lowercase / digit / "-" )
```

- 全部小写，点号 `.` 为唯一分隔符；恰为两段（服务名与操作名），禁止三段及以上；禁止空白、冒号、下划线、大写与中文；ID 不携带版本号。
- 与 Bridge 能力 ID（`<domain>:<action>[:<target>]`）与权限 ID 在字面与命名空间上互相隔离：内容处理能力一律使用点号形式（如 `content-image.normalize`），冒号形式一律无效；旧模块能力 ID（`converter.*`、`image.*`、`cover.*`、`community.*`）与旧 Host 动作（`resource.convertTiffToPng`、`resource.extractVideoFrame`、`office.*`）不得复用，一律作废（[09-官方插件与应用目录](../03-插件开发/09-官方插件与应用目录.md) §6.2）。
- 服务名沿用内核服务文法 `^[a-z][a-z0-9]*(-[a-z0-9]+)*$` 并统一使用 `content-` 前缀；每个能力 ID 绑定唯一服务名与唯一提供方插件；同一作用域内服务名唯一，不得并存第二实现，替换实现须经平台评审（[15-文件处理契约](./15-文件处理契约.md) §2.3、[01-薯片内核设计](../01-架构设计/01-子系统设计/01-薯片内核设计.md) §5.1）。
- 官方服务插件使用 `chips.service.*` 命名空间；内容处理服务的插件 ID 由[09-官方插件与应用目录](../03-插件开发/09-官方插件与应用目录.md)按本节登记分配并回写（R20）。提供方不得自造服务名、操作名或插件 ID。
- 同一标识不得同时以 Bridge 能力与 Cordis 服务两种形态登记并对外提供两套契约（第 2.2 节）。

### 8.3 登记项与描述符

提供方在发布前按本节提交登记项，平台校验后落入 8.4 表；登记项同时以描述符形式随提供方契约包发布，供 [15-文件处理契约](./15-文件处理契约.md) §4.2 的提供方选择消费：

```typescript
interface IContentCapabilityDescriptor {
  id: string;                       // <service>.<operation>，8.2 文法
  service: string;                  // Cordis 服务名（content- 前缀）
  provider: string;                 // 官方服务插件 ID（chips.service.*，按官方插件目录登记）
  operations: readonly string[];    // 服务方法名（原子操作）；每个能力 ID 恰好一个操作
  sourceFormats: readonly string[]; // 接受的规范化来源格式（如 tiff、docx、mp4）
  targetFormats: readonly string[]; // 产出的规范化目标格式
  streaming: {
    readonly input: boolean;
    readonly output: boolean;
  };
  maxInlineInputBytes: number;      // 一次性输入上限（字节）；超出必须流式或拒绝
  contractPackage: string;          // 提供方契约包（如 chips.service.content-image/contracts）
}
```

- 描述符是登记项的一部分；`sourceFormats` / `targetFormats` / `operations` / `streaming` / 输入上限由文件处理服务只读消费，不做运行时探测式回退（[15-文件处理契约](./15-文件处理契约.md) §4.2）。
- 原子操作通用约束：
  1. 纯处理：不获取资源句柄、不读写路径、不接触权限系统、不产生用户可见副作用；输入与输出为结构化克隆兼容值，二进制用 `Uint8Array`。
  2. 取消与超时：实现必须响应调用方 `AbortSignal` 并在安全点检查取消；内存、并发与后台时长受提供方软配额与平台配额约束（[01-薯片内核设计](../01-架构设计/01-子系统设计/01-薯片内核设计.md) §二.8）。
  3. 渲染复用：需要渲染的操作（卡片 → HTML、HTML → PDF / 图片、Office 页面渲染）必须复用平台渲染链路与受控渲染接口，禁止自建离屏渲染栈、禁止直接依赖 Electron（R8、[05-渲染引擎设计](../01-架构设计/01-子系统设计/05-渲染引擎设计.md)）。
  4. 不解析文档：不得解析或渲染 `.card` / `.box`；文档作为来源时经 `document:*` 与平台渲染链路消费（[15-文件处理契约](./15-文件处理契约.md) §2.4）。
  5. 安全：不得直接访问 Node.js / Electron / 系统 API；不得以内联 base64 兜底二进制；输出不得包含输入原文、凭证材料与内部路径。

计数：14 项内容处理能力、5 个内容处理服务（`content-image`、`content-media`、`content-converter`、`content-office`、`content-file-conversion`）。

受保护 Office 文档（口令加密）的处理链：

1. 识别：`content-office.inspect` 判定来源是否为加密容器（OLE/CFB 保护容器）并返回容器类型；该能力只识别、不解密，无口令参数。
2. 解密：确认加密后由消费方收集口令并调用 `content-office.decrypt`；口令只作为单次调用参数。
3. 明文产物：`decrypt` 返回一次性内存字节，不落盘、不缓存、不发布事件；消费方把明文交给后续渲染 / 转换步骤。
4. 不提供加密（re-encrypt）能力：保存解密后的文档时产物为**未加密**文档；消费方必须在交互中明确告知用户这一行为（是否覆盖原文件由调用方经受控提交决定）。

- 表中"权限映射"为调用侧所需 Bridge 权限：服务注入不经过 Bridge 权限判定，故均为无；提供方实现内部若访问受保护对象，必须使用自身会话的 Bridge 能力与权限并在 manifest 中声明，不得借用消费方权限（[08-权限系统设计](../01-架构设计/01-子系统设计/08-权限系统设计.md) §5.4）。
- 支持矩阵、格式选项与流式能力由提供方契约定义；文件处理服务按描述符选择提供方，不支持组合返回 `FILE_PROCESS_TARGET_UNSUPPORTED`（[15-文件处理契约](./15-文件处理契约.md) §3.5）。

### 8.5 调用与权限边界

- 消费方在 manifest `dependencies` 中声明提供方插件与版本范围；提供方未激活时不注入，直连调用点按 `KERNEL_SERVICE_NOT_FOUND` 收口，经编排链消费时归一为 `FILE_PROCESS_PROVIDER_MISSING`（[15-文件处理契约](./15-文件处理契约.md) §4.2）。
- 渲染进程不得直接注入内容处理服务：UI 一律经应用主逻辑或文件处理契约消费（[15-文件处理契约](./15-文件处理契约.md) §2.3）。
- 受保护 Office 文档的识别与解密由 Office 应用主逻辑直接消费（`inspect` → 口令交互 → `decrypt`），不进入 `file-processing` 通用会话；口令交互属应用交互，平台只提供原子能力，不提供口令收集、缓存与重试机制。
- 注册与注销随提供方 Fork；蓝绿更新时服务代际原子切换，会话不迁移，在途操作按取消收口（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §6.2）。
- 内容处理能力不提供 `window.chips` 访问面，不进入 Bridge 能力编目与能力族；提供方、描述符与支持矩阵经[09-官方插件与应用目录](../03-插件开发/09-官方插件与应用目录.md)与提供方契约查看。

### 8.6 错误码

- 内容处理能力抛出的错误统一为 `ChipsError`（`code` / `message` / `details` / `retryable`），`message` 简体中文；调用方按 `code` 分支。
- 错误码族按能力域登记：`IMAGE_*`、`VIDEO_*`、`MEDIA_*`、`CONVERTER_*`、`OFFICE_*`、`FONT_*`；码形为 `<DOMAIN>_<REASON>`，完整逐项码随提供方契约发布。代表性码：
  - `IMAGE_*`：`IMAGE_INPUT_UNSUPPORTED`、`IMAGE_DECODE_FAILED`、`IMAGE_ENCODE_FAILED`、`IMAGE_EMPTY`、`IMAGE_ANALYSIS_FAILED`；
  - `VIDEO_*`：`VIDEO_INPUT_UNSUPPORTED`、`VIDEO_DECODE_FAILED`、`VIDEO_FRAME_EXTRACTION_FAILED`；
  - `MEDIA_*`：`MEDIA_PARSE_FAILED`、`MEDIA_METADATA_UNAVAILABLE`；
  - `CONVERTER_*`：`CONVERTER_INPUT_UNSUPPORTED`、`CONVERTER_RENDER_FAILED`、`CONVERTER_OUTPUT_TOO_LARGE`；
  - `OFFICE_*`：`OFFICE_INPUT_UNSUPPORTED`、`OFFICE_INSPECT_FAILED`、`OFFICE_DECRYPT_FAILED`、`OFFICE_DECRYPT_WRONG_PASSWORD`、`OFFICE_CONVERT_FAILED`、`OFFICE_RENDER_FAILED`；
  - `FONT_*`：`FONT_PARSE_FAILED`、`FONT_METRICS_FAILED`。
- 提供方不得定义或复用 `BRIDGE_*`、`FILE_*`、`RESOURCE_*`、`DOCUMENT_*` 前缀；与第 11.4 节各域错误码不得重名。
- 经编排链传播时由 [15-文件处理契约](./15-文件处理契约.md) §6.3 归一为 `FILE_PROCESS_TRANSFORM_FAILED` / `FILE_PROCESS_PREVIEW_FAILED`，原始码与服务名写入 `details.cause`；直连服务消费方按原码分支。
- `details` 不得包含输入原文、凭证材料（含 `content-office.decrypt` 口令）、堆栈与内部路径。
- 口令只存在于单次调用的参数与实现内存中：不写日志、不写审计、不写错误 `details`、不写缓存、不落盘；调用结束后不保留引用。口令错误统一为 `OFFICE_DECRYPT_WRONG_PASSWORD`（`retryable: true`，供消费方重新收集口令），来源不是加密容器时 `OFFICE_DECRYPT_FAILED`；`inspect` 失败为 `OFFICE_INSPECT_FAILED`。

### 8.7 登记维护

- 新增、变更或注销内容处理能力必须走 RFC 与评审（[03-变更与决策管理](../07-工程管理/03-变更与决策管理.md)）；能力 ID、服务名与提供方一经登记不得重命名，移除按注销流程收口。
- 破坏性变更（删除或重命名能力 ID、收紧或改变输入语义、改变错误码含义）以新 ID 或平台主版本发布，与第 10.2 节同口径。
- 替换能力的实现提供方须经平台评审：同一作用域内服务名唯一、同一能力 ID 同时只有一个生效提供方。
- 本节登记表、提供方契约与 [15-文件处理契约](./15-文件处理契约.md) 的描述符消费、[08-官方应用功能总览](../08-产品与交互/08-官方应用功能总览.md) 的应用依赖必须同 PR 更新；官方服务插件 ID 登记回写[09-官方插件与应用目录](../03-插件开发/09-官方插件与应用目录.md)；登记项计数变化时同步更新本规范第 1.2 与第十三节。
