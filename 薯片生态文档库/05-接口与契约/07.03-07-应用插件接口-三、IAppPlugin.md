## 三、IAppPlugin

### 3.1 方法总表

| 方法 | 必需 | 调用时机 | 说明 |
|---|---|---|---|
| `launch(ctx)` | 是 | 应用实例创建时，恰好一次 | 完成实例初始化；resolve 表示启动完成 |
| `handleCommand(command, args)` | 否 | 实例 `active` 且收到命令 | 处理运行中投递的命令 |
| `openFile(uri)` | 否 | 实例 `active` 且收到文件打开请求 | 处理运行中投递的文件 |

入口绑定：插件模块入口（`dist/index.js`）默认导出实现 `IAppPlugin` 的对象；模块顶层只允许声明，不得产生副作用（订阅、定时器、文件访问全部放入 `launch`）。平台在启动实例时调用 `launch(ctx)`；`handleCommand` / `openFile` 需要在使用前从 `launch` 保存的 `IAppContext` 引用访问实例面（§4.6）。包内入口约定见 [03-插件包格式](../04-文件格式规范/03-插件包格式.md) §2.4，构建约定见 [01-快速开始](../03-插件开发/01-快速开始.md)。

### 3.2 launch(ctx)

```typescript
launch(ctx: IAppContext): Promise<void>;
```

语义：

- 平台创建应用表面（见 §6.1）后调用，每个应用实例恰好一次。
- `IAppContext` 是实例上下文，只在该实例生命周期内有效；实例退出后平台不再使用该对象调用插件。
- `launch` 必须处理 `ctx.args`（启动意图的完整载体）；运行中到达的意图不再回放给 `launch`（见 §6.2）。
- `launch` 中不得执行长时间阻塞操作；耗时初始化应交由后台任务，就绪后经事件或配置通知 UI。
- `launch` resolve 后实例进入 `active`，平台发布 `app:launched`；抛出或拒绝即启动失败（见 §8.3）。

典型用途：读取自身配置并应用到主窗口、注册 `beforeExit`、订阅标准事件、准备数据模型；窗口内容由应用 UI（渲染进程）负责，`launch` 不直接操作 DOM。

### 3.3 handleCommand(command, args)

```typescript
handleCommand?(command: string, args: unknown): Promise<void>;
```

语义：

- 平台在实例 `active` 时投递命令；只有 `launch` 已完成、实例可用时才可能被调用（实例状态见 §6.4）。
- 实例面（`ctx.config`、`ctx.window` 等）经 `launch` 保存的 `IAppContext` 访问；平台不向 `handleCommand` 传递上下文。
- `command` 由命令提供方定义，建议采用 `<domain>:<action>` 形式；平台按插件 ID 路由，不解释命令语义。
- `args` 为 JSON 可序列化值，由应用自行校验；参数非法时抛出 `APP_COMMAND_ARGS_INVALID`。
- 未实现 `handleCommand` 的插件收到命令时，平台不调用插件并返回 `APP_COMMAND_UNSUPPORTED`；已实现但命令不受支持时由插件抛出同一错误码。
- 命令投递不保证幂等，平台不自动重试；需要串行处理时由应用自行排队。

### 3.4 openFile(uri)

```typescript
openFile?(uri: string): Promise<void>;
```

语义：

- 实例面（`ctx.config`、`ctx.window` 等）经 `launch` 保存的 `IAppContext` 访问；平台不向 `openFile` 传递上下文。
- `uri` 只接受已归一的受管引用：`chips-resource://`，或由平台在投递前按 [06-资源协议规范](06-资源协议规范.md) §2.6 归一为受管作用域的 `file://`（目录态真实文件）；裸绝对路径、包内相对路径、`http(s)://` 与 `webdav://` 一律拒绝并返回 `APP_URI_INVALID`。远程内容须先经资源或网络能力落地后再投递。
- 文件关联只决定路由，不代表授权；文件内容访问仍受权限判定（[08-权限系统设计](../01-架构设计/01-子系统设计/08-权限系统设计.md)），越权调用返回 `BRIDGE_PERMISSION_DENIED`，应用应向用户提示并引导授权。
- 多文件时平台按传入顺序逐个调用，前一次 settle 后才调用下一次。
- 单个文件失败不阻断后续文件投递；平台记录诊断并继续。
- 未实现 `openFile` 的插件收到文件请求时，平台不调用插件并返回 `APP_OPEN_FILE_UNSUPPORTED`。

### 3.5 调用方约束

`launch` / `handleCommand` / `openFile` 只由平台调用。插件之间禁止直接调用彼此的角色方法（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §8.4）。
