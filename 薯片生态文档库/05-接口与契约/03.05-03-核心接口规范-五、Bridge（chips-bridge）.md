## 五、Bridge（chips-bridge）

Bridge 内核持有能力注册表与调用收口逻辑；三层职责、权限判定、Schema 校验与并发策略见 [02-Bridge三层设计](../01-架构设计/01-子系统设计/02-Bridge三层设计.md)。本节（5.1–5.9）是 `chips-bridge` 契约发布面的唯一清单：宿主与生态内消费者只依赖本节登记的成员；未在本节登记的 `pub` 成员为非契约面，不构成生态内必需依赖（见 5.7 面边界条目）。

### 5.1 注册

```rust
/// 能力描述：注册与静态发现所需的元数据。
pub struct CapabilityDescriptor {
    /// 能力 ID：`<domain>:<action>[:<target>]`。
    pub id: String,
    /// 输入的 JSON Schema。
    pub schema: serde_json::Value,
    /// 执行该能力所需权限 ID 的并集。
    pub permissions: Vec<String>,
}

/// 并发策略。
#[derive(Debug, Clone, Copy, PartialEq, Eq, Default)]
pub enum Concurrency {
    /// 同一能力可并发执行。
    #[default]
    Parallel,
    /// 同一能力 ID 全局串行，队列上限为 `max_queue`。
    Serial,
}

/// 能力输入信封：`json` 走 schema 校验；`bin` 承载 `x-chips-binary` 字段的字节。
pub struct CapabilityInput {
    pub json: serde_json::Value,
    pub bin: BTreeMap<String, Vec<u8>>,
}

/// 能力输出信封；`bin` 表与 `json` 中声明为 `x-chips-binary` 的字段一一对应。
pub struct CapabilityOutput {
    pub json: serde_json::Value,
    pub bin: BTreeMap<String, Vec<u8>>,
}

/// 能力执行的取消与截止信息；对应 TS 侧 `ctx.signal` / `ctx.deadline`。
pub struct CapabilityContext {
    /// 取消信号；会话销毁、能力注销、Bridge 关闭与超时触发。
    pub signal: CancelToken,
    /// 执行截止时刻。
    pub deadline: std::time::Instant,
}

/// 能力执行器：Rust 能力与 TS 能力共用该抽象。
#[async_trait]
pub trait CapabilityExecutor: Send + Sync {
    /// 执行能力；`input.json` 已通过 Schema 校验；错误必须归一为 `ChipsError`。
    /// 实现必须响应 `ctx.signal` 并在 `ctx.deadline` 前收口。
    async fn execute(
        &self,
        ctx: &CapabilityContext,
        input: CapabilityInput,
    ) -> Result<CapabilityOutput, ChipsError>;
}

/// 能力注册项；对应 02-Bridge三层设计 4.1 的注册项：
/// `ICapability` 的元数据抽为 `CapabilityDescriptor`，执行部分抽为 `CapabilityExecutor`。
pub struct CapabilityRegistration {
    pub descriptor: CapabilityDescriptor,
    /// 提供方标识：平台服务域 ID 或服务插件 ID（反向域名）。
    pub owner: String,
    /// 调用超时（毫秒），默认 30000。
    pub timeout_ms: u64,
    pub concurrency: Concurrency,
    /// 串行队列上限，默认 32。
    pub max_queue: usize,
    pub executor: Arc<dyn CapabilityExecutor>,
}

impl Bridge {
    /// 注册能力；失败时提供方启用失败。
    pub fn register(&self, registration: CapabilityRegistration) -> Result<(), ChipsError>;

    /// 注销能力；在途调用按超时/取消收口。幂等：对未注册或已注销 ID 重复注销为
    /// no-op（《能力契约规范》§4.4）。
    pub fn unregister(&self, capability_id: &str) -> Result<(), ChipsError>;
}
```

注册校验（注册期一次性完成，热路径不再重复）：ID 格式合法且全局唯一；`schema` 可离线编译；`permissions` 均在权限词表内且已在提供方 manifest 声明；`owner` 已激活。失败码：`BRIDGE_CAPABILITY_CONFLICT`、`BRIDGE_INVALID_SCHEMA`、`PERMISSION_NOT_DECLARED`、`PERMISSION_UNKNOWN`、`KERNEL_INVALID_TRANSITION`（`owner` 未激活，[04-能力契约规范](./04-能力契约规范.md) §4.2 校验项 7）；内核已 `shutdown` 后注册返回 `BRIDGE_CANCELLED`。能力 ID 与任何权限 ID 不得相同（[02-Bridge三层设计](../01-架构设计/01-子系统设计/02-Bridge三层设计.md) §4.2、§4.3）。「`owner` 已激活」与「ID 已登记且绑定 `owner`」两项前置由 5.5 的 `activate_provider` / `grant_capability_id` 承载；同原 owner 在蓝绿代际切换中的定义覆盖使用 5.8 的 `takeover_register`（`register` 本身对同 owner 同定义幂等、对定义不一致的重复注册拒绝）。

### 5.2 调用

```rust
/// 一次能力调用请求。
pub struct BridgeRequest {
    /// 调用唯一标识（UUID v4），由 preload 生成。
    pub request_id: String,
    pub capability_id: String,
    /// 已由适配层解析的会话。
    pub session: SessionId,
    /// 输入信封；`json` 的 Schema 校验在 `request` 内完成，`bin` 直接透明传递。
    pub input: CapabilityInput,
}

/// 执行器可见的调用上下文。
pub struct InvocationContext {
    pub request_id: String,
    pub capability_id: String,
    pub owner: String,
    pub session: SessionId,
    pub plugin_id: PluginId,
    /// 追踪 ID，与事件、权限审计一致。
    pub trace_id: String,
    /// 取消令牌；取消、超时、会话销毁时触发。
    pub cancel: CancelToken,
    /// 执行截止时刻；与 `CapabilityContext.deadline` 同源。
    pub deadline: std::time::Instant,
}

impl InvocationContext {
    /// 派生执行器可见的能力上下文（取消信号与截止时刻同源）。
    pub fn capability_context(&self) -> CapabilityContext;
}

impl Bridge {
    /// 完成会话校验、注册表命中、权限判定、Schema 校验与并发准入后执行能力。
    pub async fn request(&self, request: BridgeRequest) -> Result<CapabilityOutput, ChipsError>;

    /// 取消会话全部在途调用；幂等。
    pub fn cancel_session(&self, session: SessionId);
}
```

`InvocationContext` 的主进程只读取入口为 `Bridge::invocation_context`（5.7）。

| 阶段 | 行为 | 失败码 |
|---|---|---|
| 会话校验 | 会话不存在或已关闭立即拒绝 | `BRIDGE_SESSION_UNKNOWN` |
| 注册表命中 | 未注册能力拒绝 | `BRIDGE_CAPABILITY_NOT_FOUND` |
| 权限判定 | 会话快照未覆盖能力权限拒绝 | `BRIDGE_PERMISSION_DENIED` |
| Schema 校验 | 输入不合法拒绝，不填充默认值 | `BRIDGE_INVALID_INPUT` |
| 并发准入 | 会话在途超限、串行队列溢出 | `BRIDGE_SESSION_BUSY`、`BRIDGE_QUEUE_OVERFLOW` |
| 执行 | 超时触发 `cancel` 并丢弃迟到结果 | `BRIDGE_TIMEOUT` |
| 取消 | 会话销毁、能力注销、Bridge 关闭 | `BRIDGE_CANCELLED` |
| 归一 | 未识别异常 | `BRIDGE_INTERNAL` |

- 超时不保证无副作用；插件不得仅凭超时假定"未执行"（[02-Bridge三层设计](../01-架构设计/01-子系统设计/02-Bridge三层设计.md) §8.1）。
- Bridge 不自动重试、不去重执行；`request_id` 只用于关联与丢弃迟到结果。
- 完整触发条件与 `retryable` 取值见 [02-Bridge三层设计](../01-架构设计/01-子系统设计/02-Bridge三层设计.md) §9.2。

### 5.3 TypeScript 适配层示例

适配层完成会话解析、IPC 编解码与能力执行编排；授权判定与 Schema 校验始终在 Rust 侧（[02-Bridge三层设计](../01-架构设计/01-子系统设计/02-Bridge三层设计.md) §2.1）。

```typescript
// packages/host/src/main/native-bridge.ts：chips-native.node 的类型视图（与 8.6 节导出表一致）
export interface INativeBridgeRequest {
  requestId: string;
  capabilityId: string;
  sessionId: number;
  input: unknown;
  /** 二进制信封：`x-chips-binary` 字段的字节表（键与 input 中引用名一致）。 */
  bin?: Record<string, Uint8Array>;
}

  readonly signal: AbortSignal;
  readonly deadline: number;
}

  descriptor: {
    id: string;
    schema: Record<string, unknown>;
    permissions: string[];
  };
  owner: string;
  timeoutMs: number;
  concurrency: 'parallel' | 'serial';
  maxQueue: number;
  handler: (input: unknown, ctx: INativeCapabilityContext) => Promise<unknown>;
}

export interface INativeBridge {
  bridgeRegister(registration: INativeCapabilityRegistration): void;
  bridgeUnregister(capabilityId: string): void;
  bridgeRequest(request: INativeBridgeRequest): Promise<unknown>;
  bridgeCancelSession(sessionId: number): void;
```

```typescript
import type { ICapability, IBridgeRequest, IBridgeResponse } from '@chips/bridge';
import { ChipsError, isChipsError } from '@chips/bridge';
import type { INativeBridge } from './native-bridge';

/** 注册一个由 TS 实现的能力；执行由 Rust 侧发起并经回调返回。 */
export function registerCapability(bridge: INativeBridge, capability: ICapability): void {
  bridge.bridgeRegister({
    descriptor: {
      id: capability.id,
      schema: capability.schema,
      permissions: capability.permissions,
    },
    owner: 'chips.official.host',
    timeoutMs: 30_000,
    concurrency: 'parallel',
    maxQueue: 32,
    handler: (input: unknown, ctx: INativeCapabilityContext): Promise<unknown> =>
      capability.execute(input, ctx),
  });
}

/** 处理一次渲染进程的能力请求。 */
export async function dispatchBridgeRequest(
  bridge: INativeBridge,
  request: IBridgeRequest,
  sessionId: number,
): Promise<IBridgeResponse> {
  try {
    const result = await bridge.bridgeRequest({
      requestId: request.requestId,
      capabilityId: request.capabilityId,
      sessionId,
      input: request.input,
      bin: request.bin,
    });
    return { requestId: request.requestId, ok: true, result };
  } catch (error) {
    return { requestId: request.requestId, ok: false, error: normalizeError(error) };
  }
}

function normalizeError(error: unknown): ChipsError {
  if (isChipsError(error)) {
    return error;
  }
  return new ChipsError({
    code: 'BRIDGE_INTERNAL',
    message: '桥接内部错误',
    retryable: false,
  });
}
```

### 5.4 内核实例与构造

```rust
impl Bridge {
    /// 创建空的 Bridge 内核实例。
    pub fn new() -> Self;
}
```

- `Bridge` 为 `Clone` 句柄：克隆共享同一内部状态（同一注册表、同一会话表）；`Default` 与 `new` 等价；`Debug` 输出仅含关闭标志与注册表 / 会话 / 在途调用的聚合计数，不携带注册内容与权限明细。
- `chips-native` 绑定层以进程级单例持有内核实例（`OnceLock<Bridge>`），5.3 适配层的全部导出作用于同一实例；生态内消费者不得另建并行实例分裂注册表权威。

### 5.5 提供方激活与能力 ID 登记

```rust
/// 提供方类别（[02-Bridge三层设计](../01-架构设计/01-子系统设计/02-Bridge三层设计.md) §4.2 注册触发者）。
pub enum ProviderKind {
    /// 平台服务域：内置能力保留标识的持有方。
    PlatformService,
    /// 服务插件：经平台评审登记后注册能力。
    ServicePlugin,
}

/// 提供方登记：激活状态与 manifest 声明的权限集合。
pub struct ProviderRegistration {
    /// 提供方标识：平台服务域 ID 或服务插件 ID（反向域名）。
    pub id: PluginId,
    /// 提供方类别。
    pub kind: ProviderKind,
    /// manifest 声明的权限 ID 集合（安装时提交的申请集合）。
    pub permissions: Vec<String>,
}

impl Bridge {
    /// 登记并激活提供方：激活后其能力方可注册；`permissions` 为 manifest
    /// 声明的申请集合。
    ///
    /// 失败：权限声明引用未注册权限 ID → `PERMISSION_UNKNOWN`；内核已关闭
    /// 后 → `BRIDGE_CANCELLED`。重复激活同 ID 以最新声明覆盖（授权变更重建，
    /// [08-权限系统设计](../01-架构设计/01-子系统设计/08-权限系统设计.md) §7.6）。
    pub fn activate_provider(&self, registration: ProviderRegistration) -> Result<(), ChipsError>;

    /// 停用提供方：注销其全部能力并在途调用按取消收口；幂等。
    ///
    /// 对应 [02-Bridge三层设计](../01-架构设计/01-子系统设计/02-Bridge三层设计.md) §4.2：
    /// 服务插件 `stop` 前、平台退出时。
    pub fn deactivate_provider(&self, owner: &str);

    /// 登记第三方能力 ID 并绑定提供方（登记前置，
    /// [04-能力契约规范](./04-能力契约规范.md) §9.1）。
    ///
    /// 由平台评审流程经适配层调用；绑定不可转让、不可改绑。
    /// 失败：ID 文法非法、内置保留 ID、改绑他人登记 ID、登记提供方与 owner
    /// 不一致 → `BRIDGE_CAPABILITY_CONFLICT`；提供方未激活 →
    /// `KERNEL_INVALID_TRANSITION`；内核已关闭后 → `BRIDGE_CANCELLED`。
    pub fn grant_capability_id(&self, capability_id: &str, owner: &str) -> Result<(), ChipsError>;
}
```

三者是 5.1 注册校验「`owner` 已激活」「ID 已登记且绑定 `owner`」的唯一内核承载；消费者限定为主进程（宿主装配层 / 平台评审流程经适配层），插件侧不得获得直接触发这三个动作的任何路径（插件的申请集合与 ID 登记经 manifest 声明与安装评审流程表达，[02-Bridge三层设计](../01-架构设计/01-子系统设计/02-Bridge三层设计.md) §4.1「注册表是平台内部结构」）。

### 5.6 会话生命周期

```rust
impl Bridge {
    /// 登记会话快照：`request` 按 `granted_permissions` 执行权限判定；
    /// 授权变更后重新调用即按新快照重建
    /// （[08-权限系统设计](../01-架构设计/01-子系统设计/08-权限系统设计.md) §7.6）。
    ///
    /// 同一会话 ID 重复登记覆盖旧快照；失败：内核已关闭后 → `BRIDGE_CANCELLED`。
    pub fn open_session(
        &self,
        session: SessionId,
        plugin_id: PluginId,
        granted_permissions: Vec<String>,
    ) -> Result<(), ChipsError>;

    /// 关闭会话：拒绝该会话全部新调用（`BRIDGE_SESSION_UNKNOWN`）并取消其
    /// 在途调用；幂等。
    ///
    /// 清理时机（窗口销毁、插件停用、应用退出）以
    /// [02-Bridge三层设计](../01-架构设计/01-子系统设计/02-Bridge三层设计.md) §7.4 为准。
    pub fn close_session(&self, session: SessionId);
}
```

`cancel_session`（5.2）只取消在途、会话保持可用；`close_session` 同时拒绝后续调用。会话由适配层按来源解析后登记与关闭，不接受负载自报的 `pluginId`（三层 §7.4）。

### 5.7 关闭与审计只读面

```rust
impl Bridge {
    /// 关闭 Bridge：取消全部在途调用并拒绝新请求；幂等。
    ///
    /// 对应 [02-Bridge三层设计](../01-架构设计/01-子系统设计/02-Bridge三层设计.md) §8.2
    /// 取消来源之「Bridge 关闭」（平台退出）；全部注册项随关闭注销
    /// （[04-能力契约规范](./04-能力契约规范.md) §4.4 触发表）。
    pub fn shutdown(&self);

    /// 读取在途调用的完整上下文（供主进程适配层权限审计与事件追踪）；
    /// 不在途时返回 `None`。
    pub fn invocation_context(
        &self,
        session: SessionId,
        request_id: &str,
    ) -> Option<InvocationContext>;
}
```

- `invocation_context` 是审计记录 `traceId` / `requestId` / `sessionId` / `pluginId` 字段（[08-权限系统设计](../01-架构设计/01-子系统设计/08-权限系统设计.md) §8.2，运行时判定全量留痕）的内核唯一出口；`trace_id` 与事件、权限审计共用同一 ID 空间约定（5.2）。返回值携带活跃 `CancelToken`，属主进程平台内部面：**`chips-native` 禁止将其本体或 `cancel` / `deadline` 字段转发到 JS 插件侧**；主进程审计面若需绑定承载，扩展导出按 §8.6 规则另行登记。
- 面边界（非契约面）：`Bridge::is_shutdown` 等仅供 crate 自身集成测试使用的 `pub` 成员不属契约发布面，生态内其它 crate、绑定层与宿主不得依赖（关闭后的行为判定以 `BRIDGE_CANCELLED` 与各入口拒绝码为准）；确有需要纳入时另走 RFC。

### 5.8 蓝绿代际切换与状态查询

```rust
/// 能力生命周期状态（[04-能力契约规范](./04-能力契约规范.md) §10.1 状态机；
/// 对应 §4.3 编目 `ICapabilityDescriptor.state` 的 Rust 侧权威取值）。
pub enum CapabilityState {
    /// 能力可调用。
    Active,
    /// 蓝绿更新的旧代际：拒绝新调用；在途调用完成或按超时收口。
    Draining,
}

impl Bridge {
    /// 使能力进入蓝绿更新的 `draining` 状态（§4.4 触发表「蓝绿更新代际切换」、
    /// §10.1 状态机）：新调用一律按 `BRIDGE_CAPABILITY_NOT_FOUND` 拒绝；
    /// 在途调用（含串行队列等待者）不强杀，完成或按超时收口；在途清零后
    /// 注册项自动进入「已注销」。
    ///
    /// 幂等：对未注册、已注销或已处于 draining 的 ID 均为 no-op；失败：
    /// 内核已关闭后 → `BRIDGE_CANCELLED`。
    pub fn begin_draining(&self, capability_id: &str) -> Result<(), ChipsError>;

    /// 蓝绿更新的代际接管注册（§4.4 触发表、§9.3「蓝绿更新的代际接管」：
    /// 唯一允许的同 ID 覆盖）。
    ///
    /// 注册校验与首次注册完全一致（§4.4「重注册校验与首次注册一致」）；
    /// 差异仅在于允许同一原 owner 对已占用 ID 做定义覆盖：接管成功后注册表
    /// 原子指向新代际，旧代际已准入在途调用持旧注册项快照完成或按超时收口，
    /// 新调用一律由新代际处理。跨 owner 接管按 `BRIDGE_CAPABILITY_CONFLICT`
    /// 拒绝。
    pub fn takeover_register(&self, registration: CapabilityRegistration) -> Result<(), ChipsError>;

    /// 能力生命周期状态只读查询（§4.3 编目 `state`、§10.1）；未注册时返回 `None`。
    pub fn capability_state(&self, capability_id: &str) -> Option<CapabilityState>;

    /// 注册表存在性只读快照（§4.3 编目只读面的内核单点实例，供适配层诊断，
    /// 不暴露枚举面）：处于 draining 且尚未收口的注册项仍在册返回 `true`，
    /// 在途收口完成后返回 `false`（§10.1）。
    pub fn has_capability(&self, capability_id: &str) -> bool;
}
```

- `unregister`（5.1）与 `begin_draining`（本节）分属「停用/卸载」与「代际切换」两条通道，不得互相替代：前者在途按取消收口，后者在途善终。
- 切换触发时机（哪个生命周期节点调用 `begin_draining` / `takeover_register`）属宿主与插件运行时编排职责（§4.4 触发表、[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §6.2 原子切换点），内核不自行编排。

### 5.9 策略常量

| 常量 | 值 | 含义与权威出处 |
|---|---|---|
| `DEFAULT_TIMEOUT_MS` | `30_000` | 调用超时默认值（毫秒），注册项 `timeout_ms` 的缺省（[02-Bridge三层设计](../01-架构设计/01-子系统设计/02-Bridge三层设计.md) §8.1） |
| `DEFAULT_MAX_QUEUE` | `32` | 串行队列上限默认值，等待数达上限返回 `BRIDGE_QUEUE_OVERFLOW`（三层 §8.3） |
| `SESSION_IN_FLIGHT_LIMIT` | `64` | 同一会话对同一能力的在途调用上限，超限返回 `BRIDGE_SESSION_BUSY`（三层 §4.1、§8.3） |
| `SCHEMA_CACHE_CAPACITY` | `256` | 共享 schema 编译缓存上限条数（摘要键 LRU 淘汰，三层 §6.2） |
| `MAX_VALIDATION_ISSUES` | `16` | `BRIDGE_INVALID_INPUT` 单次聚合返回的校验错误条数上限，超出截断并置 `truncated`（[04-能力契约规范](./04-能力契约规范.md) §5.4） |

常量自 crate 根路径重导出（`chips_bridge::DEFAULT_TIMEOUT_MS` 等），是上述数值在 Rust 侧的唯一权威来源；消费者引用常量，不复写字面量。
