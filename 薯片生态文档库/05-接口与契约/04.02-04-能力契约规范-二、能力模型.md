## 二、能力模型

### 2.1 `ICapability`

```typescript
type JSONSchema = Readonly<Record<string, unknown>>;

interface ICapabilityContext {
  readonly signal: AbortSignal;      // 调用方取消信号（会话销毁、能力注销、Bridge 关闭）
  readonly deadline?: number;        // 绝对截止时刻（Unix 毫秒）；缺省按注册项 timeoutMs
}

interface ICapability<TInput = unknown, TOutput = unknown> {
  id: string;                      // <domain>:<action>[:<target>]
  execute(input: TInput, ctx: ICapabilityContext): Promise<TOutput>;
  schema: JSONSchema;              // 输入的 JSON Schema（第五节）
  permissions: string[];           // 执行所需基础权限 ID 集合
}
```

| 字段 | 类型 | 必填 | 语义 |
|---|---|---|---|
| `id` | `string` | 是 | 能力 ID，文法与命名规则见第三节；全局唯一（内置 ID 为保留标识） |
| `execute` | `(input: TInput, ctx: ICapabilityContext) => Promise<TOutput>` | 是 | 能力实现；收到的 `input` 已通过 schema 校验，实现不得假设调用方做过业务级校验；必须响应 `ctx.signal` 并在 `ctx.deadline` 前收口 |
| `schema` | `JSONSchema` | 是 | **输入**的 JSON Schema；只描述结构约束，不描述业务规则 |
| `permissions` | `string[]` | 是 | 执行所需基础权限 ID 的并集；空数组表示纯计算能力，无额外权限要求（仍受会话有效性约束） |

不变量：

1. `TInput` / `TOutput` 只存在于编译期；跨 Bridge 传输的值必须是结构化克隆兼容值（[02-Bridge三层设计](../01-架构设计/01-子系统设计/02-Bridge三层设计.md) 第 7.3 节）。二进制字段使用 `Uint8Array` 并由 `x-chips-binary` 标记（第 5.3 节），值经二进制信封的 `bin` 表承载（第 2.4 节）。
2. 输出不做运行时 schema 校验；输出契约由本节类型与第七节的 `ICapabilityContracts` 表维护。
3. 能力 ID 与任何权限 ID 不得相同（R3）。
4. 能力实现必须响应取消并释放已占用资源（[02-Bridge三层设计](../01-架构设计/01-子系统设计/02-Bridge三层设计.md) 第 8.2 节）：`ctx.signal` 触发后立即停止后续步骤并释放已占用句柄；无法即时中止的实现必须在 `ctx.deadline` 前返回，由 Bridge 按 `BRIDGE_TIMEOUT` 收口。

完整实现示例：

```typescript
import type { ICapability, JSONSchema } from '@chips/sdk';

interface IFileReadInput {
  path: string;
  encoding?: 'utf-8' | 'base64';
}

interface IFileReadOutput {
  content: string;
  encoding: 'utf-8' | 'base64';
}

interface IFileReader {
  readText(path: string, encoding: 'utf-8' | 'base64'): Promise<string>;
}

const fileReadInputSchema: JSONSchema = {
  type: 'object',
  additionalProperties: false,
  required: ['path'],
  properties: {
    path: { type: 'string', minLength: 1 },
    encoding: { type: 'string', enum: ['utf-8', 'base64'], default: 'utf-8' },
  },
};

export function createFileReadCapability(
  reader: IFileReader,
): ICapability<IFileReadInput, IFileReadOutput> {
  return {
    id: 'file:read',
    permissions: ['filesystem:read'],
    schema: fileReadInputSchema,
    async execute(input: IFileReadInput): Promise<IFileReadOutput> {
      const encoding = input.encoding ?? 'utf-8';
      const content = await reader.readText(input.path, encoding);
      return { content, encoding };
    },
  };
}
```

### 2.2 能力与服务的边界

| 维度 | 能力（Capability） | 服务（Service） |
|---|---|---|
| 所在层 | Bridge | Cordis 内核 |
| 消费方式 | `window.chips.request(capabilityId, input)` | `ctx.inject` / `ctx.provide` |
| 权限判定、schema 校验、审计 | 全部经过 | 不经过 |
| 适用场景 | 需要权限、校验、审计或跨渲染进程的调用 | 主进程内类型化、低开销的请求-响应 |
| 生命周期 | 随提供方 Fork 注册与注销（第十节） | 随 Fork |

同一功能不得同时以服务与能力两种方式对外提供两套契约；跨插件调用需要权限或审计时必须使用能力（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) 第 8.4 节）。

### 2.4 二进制信封

能力调用输入与输出统一使用**二进制信封**承载二进制数据；信封是 Bridge 调用消息的固定形状，不是新的能力模型：

```typescript
interface ICapabilityEnvelope<TJson> {
  json: TJson;                                   // 结构化 JSON 部分，走能力 schema 校验
  bin: Record<string, Uint8Array>;               // 二进制表：键为 json 中引用名（如 data 字段的键），值为字节
}
```

规则：

1. schema 中声明为 `x-chips-binary` 的属性，其值在信封 `bin` 表中以同名键承载；`json` 中对应位置为字符串键引用（调用方与实现都经 SDK 封装访问，不手写该引用）。
2. 输入与输出都允许携带二进制字段；输出二进制同样经 `bin` 表回传，不做运行时 schema 校验（第 2.1 节不变量 2）。
3. Rust 侧对应 `CapabilityInput { json, bin: BTreeMap<String, Vec<u8>> }`（[03-核心接口规范](./03-核心接口规范.md) 第 5 节）；Neon 边界二进制只做一次拷贝。
4. 禁止以内联 base64 字符串字段承载二进制；文本编码是显式的接口语义（如 `file:read` 的 `encoding` 选项），不属于二进制信封的兜底路径。
5. 单次信封二进制上限以各能力 schema 的 `x-chips-binary` 数值为准；超限调用返回 `BRIDGE_INVALID_INPUT`，大资源改用流式接口（第 7.2 节）。
