## 六、服务插件注册能力

### 6.1 注册调用

能力注册只能在 `start()` 执行期间调用；平台以 `start` 成功返回作为提交点，统一对外发布注册（[02-Bridge三层设计](../01-架构设计/01-子系统设计/02-Bridge三层设计.md) 4.2）。

```typescript
import type { ICapability } from '@chips/sdk';

interface ITranslateInput {
  text: string;
  target: string;
}

interface ITranslateOutput {
  text: string;
}

const translateCapability: ICapability<ITranslateInput, ITranslateOutput> = {
  id: 'translate:run',
  permissions: ['network:http'],
  schema: {
    type: 'object',
    additionalProperties: false,
    required: ['text', 'target'],
    properties: {
      text: { type: 'string', minLength: 1, maxLength: 4096 },
      target: { type: 'string', pattern: '^[a-z]{2}(-[A-Za-z]{2})?$' },
    },
  },
  // translateViaBridge：插件内部实现，经 ctx.bridge 调用已登记能力访问网络；
  // 实现必须响应 ctx.signal 并在 ctx.deadline 前收口（[04-能力契约规范](./04-能力契约规范.md) 2.1）。
  execute: async (input, ctx) => translateViaBridge(input, ctx.bridge, ctx.signal),
};

ctx.registerCapability(translateCapability, {
  timeoutMs: 30_000,
  concurrency: 'serial',
  maxQueue: 16,
});
```

> 示例能力 ID `translate:run` 的登记提供方为 `chips.service.translate`（第三方能力登记规则见 [04-能力契约规范](./04-能力契约规范.md) 第八节）；未登记 ID 不得出现在插件包中。

| 注册选项 | 默认值 | 说明 |
|---|---|---|
| `timeoutMs` | `30000` | 单次调用超时；超时返回 `BRIDGE_TIMEOUT`（`retryable: true`） |
| `concurrency` | `'parallel'` | `'serial'` 时该能力全局 FIFO；队列超限返回 `BRIDGE_QUEUE_OVERFLOW` |
| `maxQueue` | `32` | `'serial'` 时的等待队列上限 |

### 6.2 注册期校验

| 校验项 | 规则 | 失败错误码 |
|---|---|---|
| ID 格式 | `<domain>:<action>[:<target>]`；必须已在能力注册表登记 | `BRIDGE_CAPABILITY_CONFLICT` |
| 唯一性 | 全局唯一；不得占用平台保留 ID | `BRIDGE_CAPABILITY_CONFLICT` |
| 形状分离 | 能力 ID 不得与任何权限 ID 相同（R3） | `BRIDGE_CAPABILITY_CONFLICT` |
| schema | 离线可编译；禁止远程 `$ref`、网络加载与自定义脚本 | `BRIDGE_INVALID_SCHEMA` |
| 权限词表 | `permissions` 每项均为已注册基础权限 ID，且已在提供方 manifest 声明 | `PERMISSION_NOT_DECLARED` / `PERMISSION_UNKNOWN` |

- 任一校验失败导致 `start` 失败，本次激活整体回滚；插件不得在运行期补注册。
- 不访问受保护对象的纯计算能力声明空权限数组，权限判定直接通过；二进制输入输出经 `x-chips-binary` 字段与二进制信封承载（[04-能力契约规范](./04-能力契约规范.md) 2.4）。
- 第三方能力 ID 的登记规则与登记流程见[04-能力契约规范](./04-能力契约规范.md)；未登记 ID 不得出现。

### 6.3 运行语义与代际

- 注册生效后，其它插件按 ID 经 `request` 调用，链路与内置能力完全一致：权限判定、schema 校验、超时、审计一律适用（[02-Bridge三层设计](../01-架构设计/01-子系统设计/02-Bridge三层设计.md) 4.4）。
- 调用方身份是调用它的插件：判定使用调用方的会话权限快照；能力实现内部再发出的调用使用服务插件自己的快照，权限不借用、不传递。
- 能力注册随提供方 Fork：`stop` / 更新 / 崩溃时自动注销，注销后在途调用按超时或取消收口。
- 注册表不提供枚举 API；能力不可用只能通过 `BRIDGE_CAPABILITY_NOT_FOUND` 判定。
- 同一服务的同一能力 ID 必须跨版本稳定：ID 变更视为破坏性变更，依赖它的插件必须同步升级（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) 6.4）。

### 6.4 实现约束

- `execute(input, ctx)` 收到的 `input` 已通过 schema 校验；实现仍须执行业务级与资源级二次校验（如路径安全、URI 作用域）。
- `execute` 必须异步、不得阻塞调度模型；必须响应 `ctx.signal` 并在 `ctx.deadline` 前收口，取消时释放已占用资源（[04-能力契约规范](./04-能力契约规范.md) 2.1）。
- `execute` 不得假设调用方身份，不得从输入读取身份字段。
- 能力实现的错误是调用方可见的业务错误：抛出结构化 `ChipsError`，`message` 使用简体中文；未归一异常由 Bridge 转为 `BRIDGE_INTERNAL`。
- 能力实现不得直接访问系统 API、不得创建子进程、不得携带原生可执行载荷（R11、R17）。

### 6.5 旧「module」能力调用面的处置

旧 `@chips/sdk` 的 `module.*` 调用面对应旧「模块插件」角色；该角色在新架构中不存在（R1；[09-官方插件与应用目录](../03-插件开发/09-官方插件与应用目录.md) §6.2），`module.apiVersion` / `runtime` / `activation` / `methods` 清单字段全部作废。旧调用面不提供兼容层，按下表迁移；新插件禁止导入或依赖该调用面。

| 旧调用面（历史 API） | 新对应 | 说明 |
|---|---|---|
| `module.listProviders` | 无对应 | 能力注册表不提供枚举 API（6.3）；提供方发现经插件目录、安装清单与能力契约登记完成（[04-能力契约规范](./04-能力契约规范.md) §3.2、§八），运行期不按提供方枚举 |
| `module.resolve` | 无对应 | 不解析提供方：Bridge 能力按能力 ID 直接 `request`，Cordis 服务按服务名 `ctx.inject` / `ctx.get`；不可用分别收口为 `BRIDGE_CAPABILITY_NOT_FOUND` / `KERNEL_SERVICE_NOT_FOUND` |
| `module.invoke` | Bridge 能力调用或 Cordis 服务调用 | 渲染进程经 `window.chips.request`，主进程经 `ctx.bridge.request`；服务消费经 `ctx.inject` 与类型化服务接口；开发联调命令为 `chips dev service invoke`（[CLI 完整参考](../06-开发与运维/07-CLI完整参考.md) §4.7） |
| `module.job.get` / `module.job.cancel` | 无平台级作业面 | 长任务由消费方服务契约建模：会话式操作（如 [15-文件处理契约](./15-文件处理契约.md) 的进度与 `cancel()`）或挂到 Fork 的取消令牌任务；取消经 `AbortSignal` 与会话取消收口 |
| provider 记录（`runtime: 'worker'`、`activation`、`methods`、`inputSchema` / `outputSchema`） | 能力契约登记项与 Cordis 服务 | schema 归能力注册（`ICapability.schema`）与内容处理能力描述符，不提供运行期 provider 记录查询（[04-能力契约规范](./04-能力契约规范.md) §8.3） |

规则：

- SDK 主入口导出清单不含 `module` 族（[02-SDK-API规范](./02-SDK-API规范.md) §2.2）；旧封装随 SDK 清理，不保留别名、不提供迁移包装。
- 旧模块能力 ID 与 Bridge 能力/内容处理能力的替代关系以 [04-能力契约规范](./04-能力契约规范.md) §8.4、[09-官方插件与应用目录](../03-插件开发/09-官方插件与应用目录.md) §6.2 为准；本处只登记调用面处置，不重复登记能力归属。
