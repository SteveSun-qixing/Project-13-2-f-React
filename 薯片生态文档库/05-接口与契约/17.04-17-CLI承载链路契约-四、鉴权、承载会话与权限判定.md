## 四、鉴权、承载会话与权限判定

### 4.1 威胁模型（规范条款，如实划界）

- **信任域 = 当前 OS 用户**。同用户下的任何进程即「本机自身」——这是所有本地 IPC 体系（docker.sock、SSH agent、VS Code IPC）的共同边界，本契约不假装超越它。
- 防御目标：
  1. 不同 OS 用户 / 越权进程不得触达承载端点（§4.2 第一道）；
  2. 同机自动化或脚本不得**在宿主会话内**取得超出目标插件授权记录的能力——由 §4.4 权限判定门承载，不由传输层承载；
  3. 防对发现文件的离线伪造与同名端点抢占（§4.2 第二道 bearer token）。
- **不防御（在册条款，后续文档与实现不得宣称相反）**：同用户恶意进程读取 `0600` 发现文件并伪装握手——它已能以该用户身份直接执行任何用户命令与读写该工作区全部数据，承载链路不为其增加新攻击面，也不为封堵它承担密码学义务（§1.4 第 1 条 ed25519 互鉴否决的同源理由）。

### 4.2 传输面鉴权（进门）

| 道     | 机制                                                                                                                                                    | 规范等级                                                                              |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 第一道 | OS 文件权限：发现文件与 socket 文件 `0600`、所在 `userData` 目录 `0700`（POSIX），挡不同用户                                                            | 必项                                                                                  |
| 第二道 | bearer token：发现文件内实例级随机令牌（§2.4），握手帧携带，服务端**常量时间比较**（`node:crypto.timingSafeEqual`；长度不等路径同样不得早退暴露时序差） | 必项                                                                                  |
| 第三道 | 对端凭据：POSIX `SO_PEERCRED` / `LOCAL_PEERCRED` + pid/uid 校验（同机他用户凭据直接拒）                                                                 | **实现许可的额外校验**，非规范必项；Windows 侧对应 pipe ACL 查询，按 §1.4 第 3 条挂账 |

- token 校验失败：握手失败响应 `reason = token_invalid`（§5.3），关闭连接。
- 本道只解决「谁能进门」；进门后每一次路由调用仍必须过 §4.4 判定链，**任何门不得因前一门通过而跳过**。

### 4.3 承载会话（Q7 裁定：统一会话注册表 `carrier` 判别片）

- 宿主 Bridge 会话以 `ISessionSource`（`packages/bridge/src/protocol/session.ts:9-12`，现仅 `{ windowId, frameId }` 窗口形态）为来源判别。承载连接无窗口，裁定采**扩判别片**形态：`ISessionSource` 演进为 `kind: 'window' | 'carrier'` 判别式联合，carrier 片登记进**统一会话注册表**（`packages/host/src/runtime/capability/session.ts` 纳管）。
- 强制红线：不重复实现第二套会话表（`packages/host/src/runtime/capability/router.ts:8-9` 在册纪律）。carrier 会话复用既有 onClosed 清理联动（订阅与句柄释放链，`packages/host/src/runtime/host-runtime.ts:259-274`）与诊断快照面统一。
- 会话生命周期：握手成功即登记，连接关闭即关闭；关闭时拒绝新调用并取消该连接在途请求（§5.4「CLI 先死」行为体）。
- **carrier 会话不天然持资源句柄**：与文档/资源租约面（工单036 `chips-resource` 句柄租约）正交——只有当被派发的路由处理显式打开资源时，句柄才进句柄中心并挂在该会话上；连接关闭的句柄回收走既有会话关闭联动，不另造。
- 授权快照来源 = 目标插件授权记录（§4.4），快照覆盖纪律沿用 `open_session` 的会话快照裁定口径（`项目日志与笔记/RFC-chips-bridge契约发布面裁定/RFC-chips-bridge契约发布面裁定.md` §4.1 #9 行）。
- 形状冻结说明：`ISessionSource` 的 carrier 判别片代码形状改动落**波 1**（宿主侧接线波），本波只冻结契约语义，避免为冻结而预改 host 消费面（波 0 零行为实现）。

### 4.4 进门后的权限判定（不可绕过）

1. 承载链路上每个 `cli.command.*` / `cli.task.*` / `command:invoke` 调用的权限判定**复用既有运行时判定链三门**：会话登记校验 → 路由/能力存在性 → 运行时权限判定（能力路由权限门 `packages/host/src/runtime/capability/router.ts:80-99` 同族语义 + 《08-权限系统设计》[链路三运行时判定](../01-架构设计/01-子系统设计/08.07-08-权限系统设计-七、链路三：运行时判定.md)）。
2. 唯一事实源 = 目标插件授权记录：CLI 预检面（`packages/cli/src/plugin-cli/execute.ts:136-154` 读 `platform.pluginInfo` 授权记录）与服务端判定共用同一记录，两侧判定不得漂移。
3. 权限拒绝按既有域码在封套内返回（如 `CLI_PERMISSION_DENIED`，退出码 4 现行链消化），不新增承载专属码。
4. **独立服务路由表 + 禁入 Bridge 能力注册表**：carrier 服务端路由表与 Bridge 能力注册表在两处（文档与代码）都不存在包含关系；把 `cli.*` 点名进能力注册表会污染《04-能力契约规范》编目与 R19 权限映射，禁止。能力 ID 命名面 `cli:task-*`（`packages/core-rust/crates/chips-bridge/src/naming.rs:100-104`）是**插件 Bridge 消费面**（服务插件 SDK 消费），与本契约的服务路由面正交，两表各走各的门。
5. §5.8 头注「插件不得直接调用内核路由」的反向承诺由本章守住：宿主不得借承载链路绕过自己的权限门。
