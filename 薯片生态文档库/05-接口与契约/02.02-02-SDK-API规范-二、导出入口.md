## 二、导出入口

### 2.1 包入口

`@chips/sdk` 声明三个公开入口，全部通过 `package.json` 的 `exports` 暴露：

| 入口 | 用途 | 使用阶段 |
|---|---|---|
| `@chips/sdk` | 类型、客户端封装、辅助函数、全局声明 | 插件运行时代码 + 开发期代码 |
| `@chips/sdk/testing` | Mock Bridge、断言辅助 | 仅测试代码 |
| `@chips/sdk/scaffold` | 脚手架模板与生成器 | 仅 `@chips/cli` 与构建脚本 |

规则：

- 未在 `exports` 中声明的子路径一律不可导入；禁止 `@chips/sdk/src/**`、`@chips/sdk/dist/**` 等穿透路径。
- 插件运行时代码只允许导入主入口；`testing` 与 `scaffold` 不得出现在插件运行时依赖图中。
- 三个入口均无默认导出，全部为命名导出。

`@chips/sdk/testing` 的导出为：`createMockBridge`、`installMockBridge`、`uninstallMockBridge`、`assertChipsError`，以及 `IMockBridge`、`IMockBridgeOptions`、`IMockResourceInit`、`IMockCall`；`@chips/sdk/scaffold` 的导出见第八节。主入口不导出这两组开发期工具。能力契约的清单、schema 与权限映射以 [能力契约规范](./04-能力契约规范.md) 为权威，SDK 只导出对应 TS 类型，不维护第二份清单。角色接口文档与能力契约规范中标注为 SDK 导出的类型名，一律由 SDK 导出且不在插件内重复定义。

口径约定：`documentId` 取值＝文档稳定标识（`card_id` / `box_id`），跨会话、跨重命名稳定，与 `document:changed` 事件同口径（[11-文档服务设计](../01-架构设计/01-子系统设计/11-文档服务设计.md) §3.3）；SDK 类型与服务端实现使用同一口径。

### 2.3 类型转发规则

- `@chips/bridge` 是 Bridge 协议类型的唯一来源；SDK 以 `import type` 转发，不复制定义、不改变形状。
- 同一类型在 SDK 与 `@chips/bridge` 中重名时，以转发来源的声明为准。
- 插件不得越过 SDK 直接导入 `@chips/bridge` 获取类型（依赖矩阵见 [代码组织规范](../02-开发规范/01-代码组织规范.md)第 4.2 节）。

### 2.4 声明合并（服务类型扩展）

主进程插件为 `Context` 上注入的服务补充类型时使用模块声明合并，合并在插件的类型入口声明一次，服务名必须与实际 `provide` 名称一致（[核心接口规范](./03-核心接口规范.md)）：

```typescript
import type { ISummaryService } from './summary-service';

declare module '@chips/sdk' {
  interface Context {
    readonly summary: ISummaryService;
  }
}
```

- 合并只扩展编译期类型，不产生运行时行为；`ctx.summary` 与 `ctx.get('summary')` 等价。
- 不得借声明合并覆盖 SDK 已有成员；同名成员的签名必须与 SDK 兼容。
- 声明合并只用于主进程插件；渲染进程代码不使用 `Context`。
