## 四、IAppContext

### 4.1 字段总表

| 字段 | 类型 | 说明 |
|---|---|---|
| `appId` | `string` | 应用插件 ID，即 manifest `id`；与 `app:launched` / `window:created` 事件中的 `appId` 一致 |
| `surface` | `AppSurface` | 生效的表面形态，取值见 §5.2 |
| `launcher` | `IAppLauncherInfo \| null` | 生效的启动器信息；manifest 未声明 `ui.launcher` 时为 `null` |
| `args` | `IAppLaunchArgs` | 本次启动参数，见 §4.3 |
| `window` | `IAppWindow \| null` | 平台创建的主窗口句柄；`tray` 表面为 `null` |
| `lifecycle` | `IAppLifecycle` | 生命周期钩子，见 §4.5 |
| `bridge` | `IAppBridge` | 主进程出站能力与资源访问，见 §4.6 |
| `config` | `IAppConfig` | 自身命名空间配置访问，见 §4.6 |
| `logger` | `IAppLogger` | 平台日志流，见 §4.6 |
| `inject` | 方法 | 声明服务依赖并注入回调，见 §4.6 |
| `on` / `once` / `emit` | 方法 | 内核事件订阅与发布，见 §4.6 |
| `effect` | 方法 | 登记自定义清理，见 §4.6 |
| `exit` | 方法 | 请求结束本应用实例；幂等 |

规则：

- `IAppContext` 是内核 `Context` 在应用实例维度的受控视图，由实例字段与平台访问面两部分组成；未列出的成员即不可用，插件不得访问全局对象扩展访问面。
- 平台在每次启动时构造新对象；实例退出后该对象失效，其上登记的订阅、注入回调与清理自动撤销；再次启动得到新对象。
- 字段均为只读；实例字段不得跨实例缓存复用。

### 4.2 标识、surface 与 launcher

- `appId` 是应用在平台内的唯一标识，用于启动器、文件关联、窗口事件与诊断日志的关联。
- `surface` 是 manifest `ui.surface` 的生效值，决定主窗口形态与应用管理行为（§5.2）。
- `launcher` 是启动器信息的生效值，字段缺省按 §5.3 补齐；为 `null` 表示该应用没有启动器入口，仍可经文件关联与命令启动。

### 4.3 IAppLaunchArgs

| 字段 | 类型 | 说明 |
|---|---|---|
| `source` | `AppLaunchSource` | 启动来源：`launcher`（启动器）、`file-association`（文件关联）、`command`（命令）、`deep-link`（深链接） |
| `files` | `readonly string[]` | 需要打开的文件 URI 列表；无文件时为空数组 |
| `command` | `string?` | `source` 为 `command` 时的命令标识 |
| `commandArgs` | `unknown?` | `source` 为 `command` 时的命令参数 |
| `url` | `string?` | `source` 为 `deep-link` 时的深链接 URL |

不变量：

| `source` | `files` | `command` / `commandArgs` |
|---|---|---|
| `launcher` | 空数组 | 不出现；`url` 不出现 |
| `file-association` | 1 个及以上 | 不出现；`url` 不出现 |
| `command` | 空数组 | `command` 必有；`commandArgs` 可选；`url` 不出现 |
| `deep-link` | 空数组 | `url` 必有；`command` 不出现 |

- `source` 为 `file-association` 时，`launch` 负责处理全部初始文件；平台不会对它们额外调用 `openFile`（§6.2）。
- `source` 为 `command` 时，`launch` 负责处理初始命令；平台不会额外调用 `handleCommand`。
- `source` 为 `deep-link` 时，`launch` 负责处理初始深链接；运行中到达的深链接经 `app:opened-with-url` 事件投递（[05-事件契约规范](05-事件契约规范.md) §4.7）。

### 4.4 IAppWindow

| 成员 | 签名 | 说明 |
|---|---|---|
| `id` | `readonly number` | 窗口 ID，与 `window:created` / `window:closed` 的 `windowId` 同值 |
| `close` | `() => Promise<void>` | 关闭窗口；主窗口关闭可能触发实例退出（§6.3） |
| `focus` | `() => Promise<void>` | 聚焦并置前窗口 |
| `setTitle` | `(title: string) => Promise<void>` | 设置窗口标题；`desktop` 表面忽略该调用 |
| `setSize` | `(width: number, height: number) => Promise<void>` | 设置窗口内容尺寸（像素） |

规则：

- 句柄只代表 manifest 声明的表面窗口，由平台按 R17 安全基线创建；属免权限范围（[08-权限系统设计](../01-架构设计/01-子系统设计/08-权限系统设计.md) §4.4）。
- 窗口已关闭后调用返回 `APP_WINDOW_CLOSED`。
- 运行中额外创建窗口，以及聚焦、关闭、改变非自身窗口状态，一律经 `window:create` / `window:focus` / `window:close` / `window:setState` 能力（契约见 [04-能力契约规范](04-能力契约规范.md)）；应用不得绕过能力直接创建系统窗口。
- `tray` 表面的 `window` 为 `null`，应用按需经 `window:create` 创建窗口。

### 4.5 IAppLifecycle 与退出

```typescript
export type AppExitReason = 'user' | 'platform' | 'shutdown' | 'failure';

export interface IAppLifecycle {
  beforeExit(handler: (reason: AppExitReason) => Promise<void> | void): ISubscription;
}
```

`beforeExit` 语义：

- 退出流程开始时（§6.3 第 2 步）被调用，每个实例每轮退出恰好一次；用于保存未保存状态、刷新配置、释放业务资源。
- 不可取消退出：钩子只能做收尾，不能阻止实例结束（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §4.4）；钩子抛出异常或超时被平台捕获并记录，退出继续。
- 实例退出时自动撤销全部 `beforeExit` 订阅；返回的 `ISubscription` 仅用于提前撤销。
- 其他生命周期信号经标准事件获取：`window:closed`、`app:launched`、`app:exited`（见 §7.2）。

`exit(code?)` 语义：

- 请求平台结束本应用实例；平台按退出流程执行（§6.3）。
- 幂等：实例处于退出中或已退出时重复调用直接返回成功。
- `code` 可选，随 `app:exited` 的 `exitCode` 透出；缺省时不携带。
- 实例退出后再次启动会创建新实例并重新调用 `launch`；插件本身保持 `active`。

退出原因对照：

| reason | 触发 |
|---|---|
| `user` | 用户关闭主窗口（`surface: window` 且 `runtime.background` 为 `false`）或应用调用 `exit()` |
| `platform` | 平台停用、卸载或更新该插件时要求实例退出 |
| `shutdown` | 平台整体退出 |
| `failure` | 实例异常崩溃，由平台回收 |

### 4.6 平台访问面

`IAppContext` 的访问成员与 `IServiceContext`（[10-服务插件接口](10-服务插件接口.md) §3.5-§3.8）语义一致，差异只在角色与生命周期边界：

| 成员 | 说明 |
|---|---|
| `bridge.request<T>(capabilityId, input)` | 主进程出站能力调用，走完整 Bridge 链路（存在性 → 权限 → Schema → 路由 → 错误归一） |
| `bridge.resource(uri)` | 资源句柄访问，URI 统一为 `chips-resource://` 等形式（R13） |
| `config.get/snapshot/set/reset/watch` | 自身命名空间 `plugins.<appId>` 的类型化配置访问；`key` 为相对键 |
| `logger.debug/info/warn/error` | 平台日志流，按插件隔离；插件日志免权限（R19），写入失败不抛出 |
| `inject(dependencies, callback)` | 声明服务依赖并在就绪后注入回调；消费其他插件的服务须在 manifest `dependencies` 声明提供方（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §7.1） |
| `on` / `once` / `emit` | 内核事件面：标准事件与插件自有域事件；`emit` 不跨进程 |
| `effect(cleanup)` | 登记平台未内建追踪的清理（定时器、连接器等）；必须幂等且不抛出 |

规则：

- `bridge` 是 `IAppBridge = Pick<IChipsBridge, 'request' | 'resource'>`：主进程不存在 `window.chips`，事件订阅使用 `ctx.on` / `ctx.once`，不使用 `bridge.subscribe`（[01-Bridge-API规范](01-Bridge-API规范.md) §2.6）。
- 实例上登记的订阅、注入回调与清理随实例退出自动撤销；插件不得依赖进程存活期的手工回收。
- 访问 `platform` 命名空间的配置不使用 `ctx.config`，必须经 `ctx.bridge.request('config:get' | 'config:set', { namespace: 'platform', ... })` 并持带命名空间限定值的 `config:read` / `config:write`。
- 访问面不包含 `provide` 与 `registerCapability`：应用不对外提供接口，可复用的能力由 `service` 角色插件承载（§10.1）。
- 访问面之外的内核结构（全局对象、平台内部状态、Node.js / Electron API）不可访问（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §5.3）。
