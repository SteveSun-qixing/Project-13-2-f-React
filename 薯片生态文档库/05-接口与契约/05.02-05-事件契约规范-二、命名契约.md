## 二、命名契约

### 2.1 事件 ID 结构

事件 ID 由领域段与动作段构成，两段之间只允许一个冒号：

```
<domain>:<action>

domain = [a-z][a-z0-9-]*
action = [a-z][a-z0-9-]*

校验正则：^[a-z][a-z0-9-]*:[a-z][a-z0-9-]*$
```

| 段 | 含义 | 约束 |
|---|---|---|
| `<domain>` | 事件所属领域或插件命名空间 | 小写字母、数字、连字符；首字符必须为字母 |
| `<action>` | 已经发生的动作 | 小写字母、数字、连字符；通知型事件使用过去式动词短语（`changed`、`loaded`、`failed`） |

规则：

1. 只允许一个冒号；禁止点号、斜杠、空格、大写字母与空段。
2. 事件 ID 描述"已发生的事实"，不使用命令式或进行时动词（`do`、`loading` 等）。
3. 每个事件 ID 只有一个 payload 形态；同名事件不得在不同场景复用不同结构。
4. 事件 ID 在订阅与发布入口校验；非法 ID 返回 `EVENT_ID_INVALID`。
5. 内核内部事件使用 `internal:*` 域，不属于公开契约，见 4.11。

### 2.2 平台保留域

保留域只允许平台发布；插件发布保留域事件一律拒绝（`EVENT_PUBLISH_DENIED`）。保留域与事件清单：

| 域 | 发布方 | 事件清单 |
|---|---|---|
| `plugin` | 插件运行时 | 4.1（7 个） |
| `document` | 文档解析 / 渲染链路 | 4.2（4 个） |
| `file` | 资源管理 | 4.3（1 个） |
| `resource` | 资源管理 | 4.4（2 个，含 `resource:opened`） |
| `config` | 配置系统 | 4.5（1 个） |
| `security` | 权限与审计 | 4.6（1 个） |
| `permission` | 权限系统 | 4.6（2 个） |
| `window` | 窗口管理 | 4.7（3 个） |
| `app` | 应用运行时 | 4.7（3 个，含 `app:opened-with-url`） |
| `sync` | 同步引擎 | 4.8（6 个） |
| `command` | 命令注册表 | 4.9（4 个） |
| `tray` | 托盘 | 4.10（1 个） |
| `shortcut` | 快捷键 | 4.10（1 个） |
| `transfer` | 传输 | 4.10（3 个） |
| `internal` | 内核 | 4.11（不公开） |

### 2.3 插件自有域

- 插件自定义事件的 `<domain>` 取插件自有命名空间，默认与插件 ID 末段一致（如 `chips.official.editor` 使用 `editor`）。
- 命名空间由内核在插件加载时登记并去重；未取得命名空间的插件发布对应事件被拒绝（`EVENT_PUBLISH_DENIED`）。
- 插件只能发布与订阅自有命名空间内的事件，不得占用保留域（2.2）。
- 插件自有域事件默认不跨进程；确需跨进程时先按变更流程登记为标准事件。
- 插件自有域内的事件 ID 与 payload 由插件自行维护，但必须遵守 2.1 与第 3.4 节载荷约束。

### 2.4 稳定性

- 本文登记的事件 ID、payload 形态与触发语义一经发布即为稳定契约；修改走《[变更与决策管理](../07-工程管理/03-变更与决策管理.md)》的变更流程，并同步更新本文与《[09-事件系统设计](../01-架构设计/01-子系统设计/09-事件系统设计.md)》。
- 新增标准事件必须先登记（本文第四节）再实现；未登记事件不转发、不跨进程。
- 事件 ID 不复用：不再发布的事件保留登记，新语义使用新 ID。
