## 九、版本与 ABI 边界

### 9.1 版本模型

| 版本对象 | 位置 | 规则 |
|---|---|---|
| 平台统一版本 | `PLATFORM_VERSION`、全部 `@chips/*` 包与 Rust crate | 同一版本号同步升版，禁止版本漂移（[代码组织规范](../02-开发规范/01-代码组织规范.md) §3.4） |
| 绑定 ABI 版本 | `CORE_ABI_VERSION`、`coreAbiVersion` | 导出函数名、参数顺序、返回形状或句柄类型发生任何不兼容变化时递增 |
| 插件版本 | 各插件 manifest `version` | 独立语义化版本，不随平台版本 |
| 文档 `chip_standards_version` | `.card` / `.box` 的 `metadata.yaml` | 独立门禁，规则见 [06-文档解析器设计](../01-架构设计/01-子系统设计/06-文档解析器设计.md) §7 与 [04-版本与迁移规范](../04-文件格式规范/04-版本与迁移规范.md) |

- 版本起点 `0.1.0`，Phase 4 发布 `1.0.0`；第一版发布前不承诺任何兼容（[ADR-010](../01-架构设计/ADR/ADR-010-大爆炸重构策略.md)）。
- Rust crate 通过 `version.workspace = true` 继承工作区版本；`chips-native` 不得单独定版。
- 文档 `chip_standards_version` 与核心 ABI 无关：平台升级不影响已支持 `chip_standards_version` 的文档解析。

### 9.2 ABI 边界

**ABI 即本文登记的 JS 导出面**，包括：

1. 8.6 节的全部导出函数名、参数顺序与返回形状；
2. `JsBox<T>` 的 JS 可见行为（不透明句柄、可由对应释放函数或 GC 释放）；
3. `ChipsError` 同构对象的字段与语义；
4. `CORE_ABI_VERSION` 的取值。

不属于 ABI、不得依赖：

- Rust 类型的内存布局、结构体字段、`enum` 判别值；
- crate 之间的 Rust 函数签名与泛型实例化；
- `JsBox` 内部对象的大小、对齐与析构时机；
- 子系统错误枚举的 Rust 变体形态（只保证 `code` 字符串）。

规则：

1. `chips-native.node` 必须与 `host-electron` 同源构建；启动时比对 `coreAbiVersion()` 与编译期常量，不一致立即终止启动并提示重建，禁止降级运行。
2. Node-API 目标版本随 Neon 主版本固定（Neon 1.x 默认 `napi-8`）；升级 Neon、Node 或 Electron 主版本必须重新构建并复跑契约测试。
3. 任何导出面变更必须在同一变更中完成：更新本文、更新子系统文档、递增 `CORE_ABI_VERSION`、更新契约测试（[05-测试规范](../02-开发规范/05-测试规范.md)）。
4. `.cpk` 插件包永不携带原生可执行载荷（R11）；插件不感知 ABI 版本，只使用 `ctx` 与 `window.chips`。
5. 原生产物按平台与架构构建，输出到 `packages/host-electron/native/`，不入库（[代码组织规范](../02-开发规范/01-代码组织规范.md) §7.1）。

### 9.3 变更流程

导出面变更属于重大变更：RFC → 评审 → ADR 记录 → 实施 → 质量门禁 → 文档同步（[01-架构原则](../00-愿景与原则/01-架构原则.md)、[03-变更与决策管理](../07-工程管理/03-变更与决策管理.md)）。绑定层的内部实现优化（不改变导出面）不需要 RFC，但必须通过基准与契约测试。
