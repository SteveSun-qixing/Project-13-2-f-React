## 一、定位与边界

### 1.1 定位

- 本文是薯片生态**承载链路（carrier link）**的唯一权威定义：`chips <插件命令路径>`（《07-CLI 完整参考》§3.10）执行 `service` / `app` 目标时，CLI 进程与宿主（`@chips/host`）承载环境之间的传输、发现、握手、鉴权、路由派发与错误定性，全部遵循本文。
- 本文补齐工单039 登记的两项架构缺口：宿主侧 `cli.command.*` / `cli.task.*` / `command:invoke` 服务路由无正式承载通道（缺口 A 的传输层），跨进程发现与握手协议未定义（缺口 B）。消费端（CLI 请求方封装与回退定性）与错误码表均已在册且钉死，本文**零新码族、零消费端语义改动**，只定义中间「协议 + 服务端契约」层。
- 三仓消费者与唯一类型源：
  - **`@chips/bridge`**（`packages/bridge/src/protocol/carrier.ts`）：本文全部字面量、封套别名、握手帧类型、承载登记文件记录类型、`reason` 词汇表常量与 `deriveCarrierEndpoints` 纯函数的**唯一代码来源**；
  - **宿主**（服务端，`packages/host/src/carrier/`，波 1 落地）与 **CLI**（请求方组装，波 2 落地）双侧只消费 `@chips/bridge` 协议分件，禁止任何一方复刻第二份封套、字面量或路径推导实现（工单024 `ChipsError` 四份分叉的同族红线）。
- 架构红线不破：Host 是唯一运行时承载；服务间调用走内核路由；`cli.*` 路由是平台内部服务路由（《07-CLI 完整参考》§5.8 头注），本文只是其传输层，不改变其「CLI 与 SDK 消费；插件不得直接调用内核路由」的定性。

### 1.3 术语

| 术语 | 定义 |
|---|---|
| 承载链路 | 本文定义的 CLI 进程 ↔ 宿主承载环境的跨进程请求-响应链路（传输 + 发现 + 握手 + 鉴权 + 路由面的合称）。 |
| 承载端点 | 宿主实例监听请求的本地 IPC 地址：POSIX 为 UDS socket 路径，Windows 为 named pipe 名。 |
| 承载登记文件（发现文件） | 宿主在监听就绪后写入的 JSON 登记 `<userData>/chips-carrier.json`，供 CLI 发现端点并完成握手校验。 |
| 承载会话 | 一条通过握手的连接在统一会话注册表中的登记形态（§4.3），生命周期等于连接期。 |
| 路由 ID（`routeId`） | §5.1 在册服务路由名（如 `cli.task.create`），复用封套 `capabilityId` 槽传输（§3.3）。 |
| bearer token | 承载登记文件与握手帧携带的实例级随机令牌，实现一致性校验（§4.2），不是身份凭证。 |
| 发现阶段失败 | CLI 在建立可用承载会话之前失败（无发现文件、连接不上、握手不过、拉起不成），按现行回退链定性（§5.4）。 |
| 在途承载丢失 | 已建立承载会话后连接中途断开（宿主崩溃/重启），在途请求按 §5.4 收口。 |

### 1.4 裁定背景与否决记录（冻结条款）

以下裁定随本契约冻结，后续实现与文档不得与之相悖：

1. **ed25519 进程互鉴明确否决**。CPK 信任链（`packages/cli/src/artifacts/cpk-validate.ts:419-488` 验签闭包 + `CHIPS_TRUST_ROOTS_FILE` 注入面）保护的是**插件制品完整性**，不是**进程身份**；宿主侧不存在可分发的宿主公钥信任根（内嵌注册表缺位为工单028 在册账），CLI 侧也无「宿主发行密钥 → 信任根表」的正式登记链路。补齐两链的成本远超承载域收益，且同用户进程可读取宿主私钥文件，密码学互鉴在此只产生虚假安全感。若未来引入 OS keychain 或代码签名核验，另走 RFC 再议。
2. **`chips-frame/1` 与 `chips-card-window-init/1` 不入本协议**。两者语义是宿主内部窗口装载与渲染内容通道，信任方向（宿主自有 RenderHost、插件不可见不可订阅）与本契约「外部独立进程入站」相反。本协议只复用其**纪律先例**：版本字面量为唯一名字来源、升级走版本号协商、禁止特性探测式分支、握手令牌一次性下发（`packages/host/src/renderer/frame-protocol.ts:17、:250-255`；`packages/host/src/shared/card-window-init-surface.ts:62-66、:70-75`）。
3. **Windows named pipe ACL 加固为非规范必项**（Q9 裁定）：v1 只兑现 POSIX `0600/0700`；Windows 侧权限加固属「实现许可的额外校验」，边界随工单039 挂账至 Windows 门禁面立项（工单028 密钥材料面同族登记纪律）。
4. **不为 CLI 造旁路宿主实例**（Q1 裁定 C 方案否决理由，架构级）：stdio 子实例与 Electron 单实例锁（`packages/host/src/main/main.ts:68` `requestSingleInstanceLock`）和 §5.8 唯一命令索引承诺直接冲突（双份索引即第二套）。「按需启动」的解作用在连接模型上（§5.2），不在传输层造第二实例。
5. **「拉起后宿主是否自动退出」不入 v1**（Q6 裁定）：《07-CLI 完整参考》§3.2.2 已定调运行标记不是承载前置（07.03 §3.2.2），宿主存续语义与本契约正交。
