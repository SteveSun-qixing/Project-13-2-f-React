## 二、插件加载与生命周期

### 2.1 插件加载失败应该怎么排查？

按"状态 → 阶段 → 错误码"三步排查：

1. 查看插件记录 `state` 与 `lastError`（`IPluginRecord`，[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §3.3）；订阅 `plugin:failed` 获取归一错误（`payload.error`）。
2. `pending` 表示依赖未满足（`KERNEL_DEPENDENCY_MISSING` / `KERNEL_DEPENDENCY_VERSION`）；`failed` 表示激活失败或运行崩溃（`KERNEL_APPLY_FAILED`、`KERNEL_INJECT_FAILED`、`KERNEL_PLUGIN_PANICKED`）。
3. 安装期失败看 `CPK_*` 与 `PERMISSION_*` 错误码；日志与调试入口见 [07-调试与发布](./07-调试与发布.md)、[04-故障排查手册](../06-开发与运维/04-故障排查手册.md)。

### 2.2 为什么插件一直停在 pending？

- `pending` 表示启用请求已受理，但依赖未满足；平台不执行任何插件代码（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §3.1、§4.3）。
- 常见原因：`dependencies` 中的插件未安装、未启用，或已安装版本不在声明的版本范围内。
- 依赖全部就绪后自动继续激活；也可对该插件执行停用来取消等待。

### 2.3 为什么插件无法停用或卸载？

- `active` / `stopping` 状态卸载会被拒绝（`KERNEL_INVALID_TRANSITION`），必须先停用（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §4.5）。
- 存在 `active` 依赖者时，停用默认拒绝、卸载始终拒绝（`KERNEL_DEPENDENCY_CONFLICT`），返回依赖者列表。
- 需要级联停用时由调用方显式请求，平台按逆拓扑序先停用依赖者；内置插件只能停用、不可卸载。

### 2.4 一个插件可以同时实现多个角色吗？

不可以。一个插件只有一个角色，`manifest.type` 是单值；禁止在运行期按分支在多个角色间切换。需要多角色能力时拆分为多个插件，用 `dependencies` 组合，通过服务 / 能力 / 事件通信（[ADR-005](../01-架构设计/ADR/ADR-005-插件不分类只分角色.md)、[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §7.4）。

### 2.5 插件之间如何通信？

只有三条合法通道（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §8.1）：

- 服务：`ctx.provide` / `ctx.inject`，进程内、类型化、低开销的请求-响应；
- 能力：Bridge `request`，带权限判定、Schema 校验与审计，可跨上下文；
- 事件：`ctx.on` / `ctx.emit` 与 `chips.subscribe`，只做通知，不承担请求-响应语义。

禁止跨插件 `import`、直接对象引用、通过全局变量或全局单例交换数据。

### 2.6 为什么不能在插件模块顶层写订阅或定时器？

入口模块顶层只允许声明，订阅、定时器、窗口、文件访问必须放入 `start` / `launch`（[10-服务插件接口](../05-接口与契约/10-服务插件接口.md) §2.3、[07-应用插件接口](../05-接口与契约/07-应用插件接口.md) §3.1）。顶层副作用不被 Fork 追踪，停用 / 卸载后会残留，视为插件缺陷。

### 2.7 插件停用后还有回调或资源残留怎么办？

- 停用顺序为"摘除路由 → 角色停止入口 → `Fork.dispose()` 逆序回收"；事件订阅、定时器、服务、能力、资源句柄、UI 注入都必须纳入 Fork 追踪（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §4.4、§5.4）。
- 平台未内建追踪的资源用 `ctx.effect(cleanup)` 登记；`dispose` / `cleanup` 必须幂等且不得抛出。
- 停用必定完成：`stop` 失败只记录 `KERNEL_DISPOSE_FAILED`，不阻断撤销，状态仍回到 `installed`。

### 2.8 更新插件需要重启平台吗？

不需要。更新走蓝绿替换：校验新版本 → 新 Fork 激活 → 服务代际原子切换 → 旧 Fork draining 后销毁（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §6.2）。`service` 在 `start` 成功注册后切换；`basecard` / `boxlayout` 后续渲染使用新版本；`app` 已打开窗口保持旧版本直到关闭，避免丢失未保存状态；新版本激活失败时回滚旧版本。

### 2.9 插件崩溃会影响其它插件或平台吗？

不会扩散。激活失败回收副作用并转 `failed`；运行崩溃由调用边界捕获，不向平台核心传播；依赖该插件的插件保持 `pending`，故障恢复后自动继续。同一插件在窗口期内重复失败会进入熔断，停止自动重试，需用户显式重试（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §9.2、§9.3）。

### 2.10 为什么停用插件后卡片 / 箱子显示"内容不可用"？

`basecard` 停用会注销 `cardTypes`、`boxlayout` 停用会注销 `layouts`，使用该类型或布局的已打开视图被销毁并显示内容不可用提示；数据已持久化在文件中，不会丢失。重新启用后恢复渲染，无需重新安装（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §2.3.1、§2.3.2）。

### 2.11 如何观察插件的加载与状态变化？

订阅标准事件 `plugin:installed`、`plugin:uninstalled`、`plugin:loaded`、`plugin:enabled`、`plugin:disabled`、`plugin:unloaded`、`plugin:failed`：主进程用 `ctx.on`，渲染进程用 `window.chips.subscribe`。payload 字段与触发时机以 [05-事件契约规范](../05-接口与契约/05-事件契约规范.md) §4.1 为准。

### 2.12 平台启动时会自动启用哪些插件？

平台按启用偏好集合、依赖拓扑序逐个启用：上次退出为 `active` 的重新启用；`starting` / `stopping` 残留回滚为 `installed` 后按偏好处理；`failed` 启动时不自动重试；单个插件失败被隔离，不阻塞后续插件（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §4.6）。
