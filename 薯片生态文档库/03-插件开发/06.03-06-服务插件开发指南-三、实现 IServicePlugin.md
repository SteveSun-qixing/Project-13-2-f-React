## 三、实现 `IServicePlugin`

### 3.1 入口模块

入口模块的形状如下（完整实现见第九节）：

```typescript
import type { IServiceContext, IServicePlugin } from '@chips/sdk';

class ImageConvertService implements IServicePlugin {
  public async start(ctx: IServiceContext): Promise<void> {
    // 初始化、配置读取、服务注册、能力注册、副作用登记
  }

  public async stop(): Promise<void> {
    // 幂等清理
  }

  public async health(): Promise<boolean> {
    // 只读健康探针
    return true;
  }
}

export default new ImageConvertService();
```

规则（E10 2.3）：

- 入口模块默认导出一个实现 `IServicePlugin` 的对象；模块顶层只允许声明，不允许产生副作用（定时器、订阅、文件访问等全部放入 `start`）。
- 平台以对象方法形式调用三个方法，插件不得要求调用方自行绑定 `this`；类实例字段在 `start` 中重新初始化，不得假设保留上次激活的状态。
- 停用后再次启用会重新调用 `start`；跨激活状态必须落配置或插件私有数据目录。

### 3.2 `start(ctx)`：初始化与注册

`start` 是唯一的激活入口，平台在 `starting` 阶段创建插件 Fork 后调用它；`start` 成功返回后，服务与能力注册对外生效并发布 `plugin:enabled`（E10 4.2）。

在 `start` 内按顺序完成：

1. 重新初始化实例状态（激活标志、缓存、代际标识）。
2. 通过 `await ctx.config.get(...)` 读取自身配置，并用 `ctx.config.watch(...)` 订阅变更。
3. 用 `ctx.provide(...)` 注册 Cordis 服务，或用 `ctx.registerCapability(...)` 注册 Bridge 能力（同一功能只选一种，E4 2.2）。
4. 创建定时器、连接器、观察者等自定义副作用，并用 `ctx.effect(cleanup)` 包装登记。
5. 使用 `ctx.logger` 输出启动日志（保持轻量，不得阻塞）。

失败处理：`start` 抛出或超时按激活失败处理——平台回收本次 Fork 的全部副作用，插件转 `failed`，返回 `KERNEL_APPLY_FAILED`；依赖它的插件保持 `pending`，待其恢复后自动继续（E10 2.2、4.2）。超时阈值取内核常量（`apply` 30s、`stop` 10s、Fork 强撤 30s），超时报 `KERNEL_LIFECYCLE_TIMEOUT`，插件不自行定义超时数值（[01-薯片内核设计](../01-架构设计/01-子系统设计/01-薯片内核设计.md)）。

### 3.3 `stop()`：幂等清理

- 平台在 `stopping` 阶段摘除路由后调用 `stop()`，随后执行 `Fork.dispose()` 逆序撤销剩余副作用（E10 4.4）。
- `stop` 必须幂等：重复调用为 no-op；不得抛出异常中断清理链。
- `stop` 内禁止新的 `provide` / `inject` / `on` / `registerCapability`；停止期间进行的调用按超时或取消收口。
- `stop` 失败或超时由内核按策略强制撤销，只记录 `KERNEL_DISPOSE_FAILED`，停用照常完成（状态仍进入 `installed`）。
- `stop()` 与 `effect` 清理可以并存，但不得重复释放同一资源导致二次副作用。

### 3.4 `health()`：只读探针

- 仅在声明了 `healthCheck` 时被平台按周期调用；实现 `health()` 但未声明 `healthCheck` 时平台不调用它（E10 5.1）。
- 必须无副作用、幂等、只读；不得在检查中建立连接或读写文件，也不得依赖周期性初始化。
- 返回 `false`、抛出或超过 `timeout` 均按本次不健康处理；详细熔断规则见本文第六节。
