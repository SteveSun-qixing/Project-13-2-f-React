## 一、定位与边界

### 1.1 定位

本文是官方插件与应用身份的**唯一登记处**。任何使用 `chips.official.*`、`chips.basecard.*`、`chips.layout.*`、`chips.service.*` 命名的插件，必须先在本目录登记 ID、角色与职责边界，再进入接口设计与实现；本目录之外的命名不视为官方插件。

官方与第三方使用完全相同的接口、清单、生命周期、权限与打包链路，官方不享有特权（[ADR-005](../01-架构设计/ADR/ADR-005-插件不分类只分角色.md)；白皮书"一切皆插件"）。本目录只回答"官方有哪些插件、用什么 ID、各自负责什么、依赖谁、处于什么阶段"。

## 二、命名空间与 ID 分配

### 2.1 官方命名空间

官方插件 ID 为反向域名，全局唯一、发布后不得变更（[02-插件清单规范](./02-插件清单规范.md) §3.1、R20）：

| 命名空间 | 角色 | 用途 | 示例 |
|---|---|---|---|
| `chips.official.*` | `app` | 官方应用插件 | `chips.official.editor` |
| `chips.basecard.*` | `basecard` | 官方基础卡片插件 | `chips.basecard.richtext` |
| `chips.layout.*` | `boxlayout` | 官方箱子布局插件 | `chips.layout.grid` |
| `chips.service.*` | `service` | 官方服务插件 | `chips.service.file-processing` |

- 源码目录名取插件 ID 末段 kebab-case，包名 `@chips/plugin-<目录名>`（[代码组织规范](../02-开发规范/01-代码组织规范.md) §3.2）。
- 一个插件只有一个角色、只使用对应命名空间；需要多角色能力时拆成多个插件并以 `dependencies` 组合（R1、[插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §2）。
- 旧式 ID（`com.chips.*`、`chips-official.*`、`chips.module.*`、带 `.blp` 后缀的布局 ID）一律作废，不得用于新插件、新代码与新文档；对应关系见 §八。

### 2.2 卡片类型 ID 与布局类型 ID

- **卡片类型 ID**：`capabilities.cardTypes[].id`，与 `.card` 的 `card_type`、`structure.yaml` 条目 `type` 同值；取值以 [卡片文件格式](../04-文件格式规范/01-卡片文件格式.md) 各类型 Schema 的正式标识为准（如 `base.richtext`、`base.image`），未登记类型由插件定义并随插件发布（04 §6.10）。
- **布局类型 ID**：`chips.layout.<name>`，与箱子 `active_layout_type`、`layout_configs` 键同值（[02-插件清单规范](./02-插件清单规范.md) §7.3、R20）。
- 卡片类型 ID、布局类型 ID、插件 ID 是三个独立命名空间：同值不得互相兼任；历史别名（如 `RichTextCard`）只读取归一、不回写、不作为新写入值（[02-插件清单规范](./02-插件清单规范.md) §7.2）。

### 2.3 平台自身标识

平台能力提供方的 owner 为 `chips.official.host`（[核心接口规范](../05-接口与契约/03-核心接口规范.md) §3.5）。它是 Host 身份标识，不是插件：不进入插件目录、不安装、不启用、不更新，也不参与插件 ID 唯一性判定。

### 2.4 教学示例与官方分发的边界

文档中的教学示例 ID（如 `chips.basecard.hello`、`chips.service.clock`、`chips.service.hello`、`chips.official.translate-app`、`chips.official.markdown-card`）不是官方分发清单的一部分：示例插件位于 `examples/plugins/`，与官方插件使用同一套接口但不随平台分发（[代码组织规范](../02-开发规范/01-代码组织规范.md) §3.3）。其中 `chips.official.markdown-card` 因命名空间错误不作为正式 ID，正式 Markdown 卡片插件 ID 为 `chips.basecard.markdown`（见 §4.3）。

## 三、版本策略

### 3.1 三类版本与门禁

| 版本 | 权威位置 | 官方插件的执行口径 |
|---|---|---|
| 平台版本 | 仓库根 workspace 版本（`package.json` 与 `Cargo.toml` 一致） | 平台统一版本从 `0.1.0` 起步，Phase 4 发布 `1.0.0`（[代码组织规范](../02-开发规范/01-代码组织规范.md) §3.4） |
| 插件版本 | 包根 `manifest.yaml` 的 `version` | 与源码 `package.json` 一致；语义化版本独立演进，可单独发布与更新（[调试与发布](./07-调试与发布.md) §7.1、§7.3） |
| 文档格式版本 | `.card` / `.box` 的 `chip_standards_version` | 随平台版本发布，与插件版本互不推导（[04-版本与迁移规范](../04-文件格式规范/04-版本与迁移规范.md) §二） |

- `engines.chips` 声明插件可运行的平台版本范围；安装校验、启用、平台更新后重启自检与插件更新四处都校验，不满足返回 `CPK_ENGINE_UNSUPPORTED`（[02-插件清单规范](./02-插件清单规范.md) §3.6；[更新与分发规范](../06-开发与运维/06-更新与分发规范.md) §3.3）。
- `source: builtin` 的官方插件必须签名；内置插件不可卸载、只能停用（[插件包格式](../04-文件格式规范/03-插件包格式.md) §六；[插件体系](../01-架构设计/01-子系统设计/03-插件架构设计.md) §3.3）。

### 3.2 升级语义与预发布

- `MAJOR`：接口行为、配置 schema、数据契约或依赖契约的不兼容变更；`MINOR`：向后兼容新增；`PATCH`：向后兼容修复（[调试与发布](./07-调试与发布.md) §7.3）。
- `0.x` 阶段按预发布语义执行：破坏性变更升 `MINOR` 并同步迁移步骤；预发布使用 `-alpha.N`、`-beta.N`、`-rc.N`，不进入稳定渠道（[调试与发布](./07-调试与发布.md) §7.2）。
- 禁止同一版本号两种语义、禁止降版、禁止双读字段与别名映射等兼容层（[调试与发布](./07-调试与发布.md) §7.5；ADR-010）。

### 3.3 布局配置 schema 版本

- 布局插件的 `capabilities.layouts[].schemaVersions` 声明其支持渲染与编辑的 `schema_version` 取值集合；平台打开箱子时按此校验，兼容性变更放宽上限、破坏性变更收窄下限并让旧配置确定性降级（[02-插件清单规范](./02-插件清单规范.md) §7.3）。
- 平台不做运行时配置迁移；迁移工具与兼容边界见 [04-版本与迁移规范](../04-文件格式规范/04-版本与迁移规范.md) §六。

## 四、基础卡片插件（basecard）

### 4.1 原则

- 每个基础卡片插件至少登记一项 `capabilities.cardTypes`；卡片类型的注册与注销由平台在启用 / 停用流程中按清单执行，插件不得运行时动态增删（[02-插件清单规范](./02-插件清单规范.md) §7.2）。
- 基础卡片插件只提供查看渲染、编辑渲染、配置校验、内容初值、资源路径收集与可选导出；不写文档字节、不访问真实路径、不自建窗口（[基础卡片插件接口](../05-接口与契约/08-基础卡片插件接口.md)；R8、R17）。
- 基础卡片插件不申请窗口与系统集成类权限；界面在平台容器内渲染（[02-插件清单规范](./02-插件清单规范.md) §6.3）。

### 4.3 维护规则

- 卡片类型的新增属于插件包变更：类型 ID 全局唯一、发布后不得更名；跨插件重复注册时后注册方启用失败，不覆盖既有注册（[02-插件清单规范](./02-插件清单规范.md) §7.2）。
- 停用卡片插件后，该类型已打开视图销毁并提示内容不可用，文档数据保留不丢失（[02-插件清单规范](./02-插件清单规范.md) §7.2）。
- 已收口：`@chips/sdk/scaffold` 文档示例统一使用 `chips.basecard.markdown`；正式 ID 以本目录为准。

## 五、箱子布局插件（boxlayout）

### 5.1 原则

- 每个布局插件至少登记一项 `capabilities.layouts`，每项必须提供 `configSchema` 与 `schemaVersions`；布局 ID 与 `active_layout_type`、`layout_configs` 键同值（[02-插件清单规范](./02-插件清单规范.md) §7.3）。
- 布局插件不读取条目文件、不解析 YAML、不创建非受管 iframe；条目内容经帧运行时下发，激活经 `openDocument` 转发（[箱子布局插件接口](../05-接口与契约/09-箱子布局插件接口.md) §2、§6）。
- 布局切换只改变呈现方式，不修改箱子数据；箱子引用未安装布局时按 `RENDER_PLUGIN_MISSING` 降级占位（[箱子文件格式](../04-文件格式规范/02-箱子文件格式.md) §10.3；[02-插件清单规范](./02-插件清单规范.md) §7.3）。
- 查看态视觉遵守[官方布局视觉细则](../08-产品与交互/07-官方布局视觉细则.md)；呈现规则差异由各插件 `configSchema` 与插件文档定义。

### 5.2 登记表

| 插件 ID | 布局名称 | 职责 | 依赖 | 能力与权限 | 状态 | 对应文档 |

## 七、应用插件（app）

### 7.1 原则

- 应用插件使用 `ui.surface` 声明表面（`window` / `desktop` / `tray`），由平台创建表面窗口；运行中额外窗口经 `window:create`（[应用插件接口](../05-接口与契约/07-应用插件接口.md) §5.2）。
- 应用插件只消费平台链路与能力：不解析 `.card` / `.box`、不拼帧、不读写文档字节、不直接访问系统 API（R2、R8、R17）。
- 打开路由以处理器声明表达：专用查看器 / 编辑器为 `primary`，万能文件查看器为 `fallback`（[资源打开与默认处理器契约](../05-接口与契约/14-资源打开与默认处理器契约.md) §3）。
- 应用插件之间不互相调用、不 `import` 彼此实现；需要协作时经服务、能力与事件（[插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §8）。

## 九、目录维护规则

1. **先登记后设计**：新增官方插件（含官方同步插件、官方内容处理服务）必须先在本文登记 ID、角色与职责，再进入接口设计与实现；未登记 ID 不得出现在清单、代码与文档中（R20、R3 同口径）。
2. **ID 变更受控**：插件 ID、卡片类型 ID、布局类型 ID 发布后不得变更；确需变更走变更与决策管理流程并同步本目录（[变更与决策管理](../07-工程管理/03-变更与决策管理.md)）。
3. **单一事实源**：本目录登记"是什么"；接口、schema、交互与算法分别由对应权威文档定义。禁止在本目录复制其他文档的完整签名、字段表与权限表；发现重复定义时收敛为一处定义 + 一处引用。
4. **状态同步**：设计文档入库、设计被取代或废弃时，同步更新状态列与对应文档列；目录中不存在"未定义状态"的条目。
5. **与旧资产解耦**：旧仓库与旧文档只作为行为证据与对应关系来源；不得把旧 ID、旧字段、旧角色作为新设计的输入（ADR-010）。
6. **示例不冒充官方**：`examples/plugins/` 下的示例插件不在本目录登记；需要示例 ID 的文档必须使用示例命名空间（`chips.example.*`）或明确标注"示例、非官方分发"。

## 十、约束与自检清单

### 10.1 约束

- 一个插件只有一个角色，使用唯一命名空间；禁止一包多角色、运行期切换角色行为（R1）。
- 官方应用不得成为第二解析器或第二渲染管线；查看器与资源管理器不解析 `.card` / `.box`，编辑引擎不拼帧（R8）。
- 官方插件访问系统能力只经 `window.chips` / `ctx.bridge`；主进程插件只经受管模块加载器加载（R2、R17）。
- 官方插件界面统一 React + `@chips/ui` + antd，文案简体中文直写；禁止第二组件库与硬编码样式（R4、R5；[React 组件开发规范](../02-开发规范/03-React组件开发规范.md)）。
- 官方插件不申请未使用权限；`basecard` / `boxlayout` 不申请窗口与系统集成类权限（[02-插件清单规范](./02-插件清单规范.md) §6.3）。

### 10.2 自检清单

- [ ] 新插件 ID 是否落在四类官方命名空间之一，且与角色匹配？
- [ ] 插件 ID、卡片类型 ID、布局类型 ID 是否已在本文登记，未使用旧式 ID？
- [ ] 卡片类型 ID 是否与 `.card` 的 `card_type`、`structure.yaml` 条目 `type` 同值？布局 ID 是否与 `active_layout_type`、`layout_configs` 键同值？
- [ ] `manifest.yaml` 是否与本文的角色、职责、依赖一致，并与源码 `package.json` 版本一致？
- [ ] `engines.chips` 是否声明平台版本范围，且当前平台版本落在范围内？
- [ ] 布局插件是否提供 `configSchema` 与 `schemaVersions`，`configSchema` 是否随包发布并位于 `assets/`？
- [ ] 应用插件的处理器声明是否符合 `primary` / `fallback` 层级，未抢占其他专用处理器？
- [ ] 是否存在未登记的官方插件、示例 ID 冒充官方 ID、旧 ID 残留？
- [ ] 新增或更新后是否同步本目录状态列与对应文档列，并运行文档链接检查（0 坏链）？
