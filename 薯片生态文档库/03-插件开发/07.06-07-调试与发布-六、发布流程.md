## 六、发布流程

### 6.1 流程总览

```text
[1] 定稿：功能完成、测试通过、宿主内冒烟验证
      │
      ▼
[2] 版本：按第七节规则确定版本号；更新 manifest.yaml 与 package.json
      │
      ▼
[3] 构建：pnpm --filter <插件包名> run build
      │
      ▼
[4] 打包：pnpm --filter <插件包名> run package（内部调用 chips plugin pack）
      │
      ▼
[5] 校验：chips plugin validate <产物>，与安装同源；失败回到 [3]
      │
      ▼
[6] 签名：按来源渠道签名（发布链路执行；builtin 必须）
      │
      ▼
[7] 变更说明：随分发材料提供（不进入 .cpk）
      │
      ▼
[8] 投递：随平台内置 / 用户安装 .cpk / 插件市场
      │
      ▼
[9] 安装验证：在干净环境完成一次真实安装、启用与权限确认，确认冒烟用例通过
```

### 6.2 版本

- 插件版本的唯一权威位置是 `manifest.yaml` 的 `version`，源码 `package.json` 必须一致；由打包校验强制。
- 版本号的选择规则与升级含义见第七节；已发布版本的语义不可修改。
- 0.x 阶段（Phase 4 发布 `1.0.0` 前）破坏性变更升 `MINOR`，但必须在变更说明中显式列出。

### 6.3 变更说明

发布版本必须提供变更说明（发布说明），至少包含：

1. 版本号与日期；
2. 变更分类：新增 / 修复 / 破坏性变更；
3. 破坏性变更清单与影响范围（存在破坏性变更时必须显式列出，不提供运行时兼容行为，[04-能力契约规范](../05-接口与契约/04-能力契约规范.md) §9.2）；
4. 权限变化：新增或移除的权限项及原因（更新界面会重新确认权限变化，[08-权限系统设计](../01-架构设计/01-子系统设计/08-权限系统设计.md) §6.4）；
5. 依赖变化：`dependencies` 的范围调整；
6. 产物校验值：安装摘要 `sha256:`。

变更说明不随 `.cpk` 携带：包根白名单不允许清单之外的文档（[03-插件包格式](../04-文件格式规范/03-插件包格式.md) §2.3）。生态层面的变更治理与发布说明规范见 [03-变更与决策管理](../07-工程管理/03-变更与决策管理.md)。

### 6.4 投递渠道

| 渠道 | 来源 | 说明 |
|---|---|---|
| 随平台内置 | `builtin` | 官方插件；随平台版本分发，必须签名，不可卸载 |
| 用户安装 | `user` | 分发单位是单个 `.cpk`；安装后不自动启用，首次启用时完成授权确认 |
| 插件市场 | `user`（安装时由市场投递 `.cpk`） | 规划中的分发渠道；投递单位与安装校验不变，市场侧规则随发布链路定义 |

- 安装、更新、卸载均以 `.cpk` 为单位；任何投递方式都不改变安装校验与权限流程。
- 分发材料至少包含：`.cpk`、版本号、变更说明、安装摘要。

### 6.5 更新约束

- 更新走蓝绿替换，不重启平台、不中断调用（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §6.2）。
- 新版本必须满足全部已安装依赖者的版本范围，否则更新被拒绝并列出不满足的依赖者。
- 权限集合变化必须重新确认；拒绝则取消更新，旧版本继续运行。
- 降级默认拒绝；平台不提供旧版本回退安装（[04-版本与迁移规范](../04-文件格式规范/04-版本与迁移规范.md) §5.1）。
- 更新中断后平台启动时清理暂存目录并回滚旧版本。

### 6.6 发布检查清单

- [ ] `manifest.yaml` 与 `package.json` 版本一致且按第七节选定。
- [ ] `pnpm lint`、`pnpm typecheck`、`pnpm test` 通过。
- [ ] `chips plugin validate` 通过（含签名校验）。
- [ ] 包内无原生载荷、`node_modules/`、测试、源码、sourcemap、嵌套归档。
- [ ] 声明权限与能力调用一致，限定值收窄到必要范围。
- [ ] 依赖范围正确，更新不破坏已安装依赖者。
- [ ] 变更说明包含破坏性变更与权限变化。
- [ ] 在干净环境真实安装并完成一次启用、授权与冒烟验证。
