## 四、打包为 .cpk

### 4.1 打包前检查

- `manifest.yaml` 与源码 `package.json` 的 `version` 一致（打包工具强制校验，不一致按 `CPK_MANIFEST_INVALID` 拒绝）。
- `pnpm lint`、`pnpm typecheck`、`pnpm test` 全部通过；质量门禁以 [05-CICD与质量门禁](../06-开发与运维/05-CICD与质量门禁.md) 为准。
- 入口齐备：`dist/index.js` 全部角色必需；`render.js` 为 `basecard` / `boxlayout` / `app` 必需、`service` 禁止。
- 静态资源只放在 `assets/`；manifest 中的文件引用为包内相对 POSIX 路径且目标位于 `assets/` 内。
- 不存在以下内容：原生可执行载荷、`node_modules/`、测试文件、源码、sourcemap（`*.map`）、锁文件、嵌套归档、隐藏文件。
- 平台共享依赖（React、`@chips/ui`）已外部化，未随包重复打包。

### 4.2 命令

```bash
# 构建（插件包内 build 脚本产出单文件 ESM 入口与静态资源）
pnpm --filter @chips/plugin-hello-basecard run build

# 打包（package 脚本内部调用 @chips/cli）
pnpm --filter @chips/plugin-hello-basecard run package

# 直接调用 CLI：在插件目录内打包，输出到插件 dist/
pnpm exec chips plugin pack --out dist/

# 指定目录打包
pnpm exec chips plugin pack --dir examples/plugins/hello-basecard --out dist/

# 与安装完全同源的校验（不安装）
pnpm exec chips plugin validate dist/hello-basecard-1.0.0.cpk
pnpm exec chips plugin validate examples/plugins/hello-basecard
```

不使用 CLI 的工具链必须遵守同样的归档约束：

```bash
# 在构建暂存目录内执行；输出到插件的 dist/ 目录
zip -r -0 -X ../dist/<名称>-<版本>.cpk . -x '.*' -x '*/.*'
```

`-0` 表示 ZIP Store（不压缩），`-X` 去除额外文件属性；不得对暂存目录再加一层包裹目录。

### 4.3 产物结构

```text
hello-basecard-1.0.0.cpk (ZIP Store)
├── manifest.yaml            # 包根唯一权威清单（必需）
├── dist/                    # 构建产物目录（必需）
│   └── index.js             # 插件模块入口（必需）
├── render.js                # 渲染入口（basecard / boxlayout / app 必需；service 禁止）
├── assets/                  # 静态资源目录（按需）
│   └── icons/
│       └── hello.svg
└── signature.json           # 签名文件（可选；见第五节）
```

| 角色 | `render.js` | `assets/` 用途 |
|---|---|---|
| `basecard` | 必需 | 卡片类型图标、模板、样式 |
| `boxlayout` | 必需 | 布局图标、样式 |
| `app` | 必需 | 启动器图标、窗口与界面资源 |
| `service` | 禁止 | 仅数据文件，禁止任何 UI 资源 |

包根只允许 `manifest.yaml`、`dist/`、`render.js`、`assets/`、`signature.json` 五个条目；输出命名为 `<名称>-<版本>.cpk`，`.cpk` 不进入版本库。归档要求、白名单与体积限制的完整规则见 [03-插件包格式](../04-文件格式规范/03-插件包格式.md) §2、§4。

### 4.4 校验

`chips plugin validate` 与安装执行同一套校验，五个阶段依次判定，任一失败立即终止：

```text
[1] 归档校验    ZIP 可读、Store、无加密、无重复、CRC、路径安全、限额
      │
      ▼
[2] 结构校验    根目录白名单、角色布局、入口存在、无原生载荷、无嵌套归档
      │
      ▼
[3] 清单校验    manifest schema、ID / 版本 / 角色、路径引用、与包内容一致
      │
      ▼
[4] 签名校验    按来源渠道执行（builtin / user / development）
      │
      ▼
[5] 摘要与落盘  sha256 安装摘要 → 暂存目录 → 原子替换 → 注册表 installed
```

| 错误码 | 开发者处置 |
|---|---|
| `CPK_ARCHIVE_INVALID` | 重新用 `-0` 打包；确认无加密、无 ZIP64、无重复路径、无嵌套归档 |
| `CPK_LAYOUT_INVALID` | 删除包根白名单外条目与隐藏文件；核对角色布局 |
| `CPK_MANIFEST_MISSING` / `CPK_MANIFEST_INVALID` | 检查清单位置、语法、字段与路径引用；确认与 `package.json` 版本一致 |
| `CPK_ENTRY_MISSING` | 补全 `dist/index.js` 与角色要求的 `render.js`；确认是 UTF-8 文本 ESM |
| `CPK_NATIVE_PAYLOAD` | 移除原生载荷；Rust 能力属于平台，服务依赖必须打包进入口 |
| `CPK_PATH_UNSAFE` | 修正路径穿越、绝对路径、符号链接与非法字符 |
| `CPK_LIMIT_EXCEEDED` | 压缩资源、精简成员；限额不可申请放宽 |
| `CPK_SIGNATURE_REQUIRED` / `CPK_SIGNATURE_INVALID` | 按来源渠道补签名或修复签名文件（第五节） |

安装摘要定义为 `hash = "sha256:" + SHA-256(整个 .cpk 文件字节)`，写入插件注册表用于完整性校验与更新比对。校验全部通过前不落盘；安装失败必须清理临时目录，注册表不产生记录。
