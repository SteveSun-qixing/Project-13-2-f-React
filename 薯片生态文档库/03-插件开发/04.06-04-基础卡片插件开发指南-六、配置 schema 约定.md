## 六、配置 schema 约定

### 6.1 配置位置与 `card_type`

与呈现相关的可调参数放在内容配置（`content/{10 位 Base62 编号}.yaml`）的 `config` 字段中；`config` 是不透明映射，解析器不解释其语义，插件读取时必须回退默认值：

```yaml
# content/a1B2c3D4e5.yaml
card_type: base.richtext
content_format: markdown
content_source: inline
content_text: |
  薯片生态文档库
markdown_capabilities:
  commonmark: true
  gfm: true
  math: true
  highlight: true
  underline: true
  superscript: true
  subscript: true
config:
  fontSize: 16
  lineHeight: 1.6
```

`card_type` 必须写 04/01 的正式类型标识（如 `base.richtext`）；历史别名由 manifest `capabilities.cardTypes[].aliases` 声明、平台读取时归一为正式 `id`，不得作为新写入值（[08-基础卡片插件接口](../05-接口与契约/08-基础卡片插件接口.md) §6.2）；`card_type` 与 `.card/structure.yaml` 条目 `type`、插件 manifest 的 `capabilities.cardTypes[].id` 三者一致（R20、格式文档 §5.3）。

### 6.2 `configSchema`

卡片类型通过 `capabilities.cardTypes[].configSchema` 声明 JSON Schema（2020-12 方言）：

1. 文件为包内相对路径且位于 `assets/` 内；缺失或非法时插件启用失败。
2. 顶层必须为 `type: object`；字段约束、默认值与未知字段策略由插件定义，建议 `additionalProperties: false`。
3. 禁止远程 `$ref` 与外部网络解析；允许文档内 `#/...` 引用。
4. 该文件只描述卡片内容配置；插件自身设置使用 `assets/schemas/config.schema.json`，两者不是同一文件（[10-配置系统设计](../01-架构设计/01-子系统设计/10-配置系统设计.md)）。

### 6.3 `validateConfig` 与 schema 的关系

`configSchema` 与 `validateConfig` 是同一规则的两处实现：平台用 schema 做通用校验，插件用函数补充需要业务逻辑的检查。判定不得比 schema 宽松，且 `validateConfig` 必须是纯函数：同步、无副作用、不抛异常、不访问能力与全局状态；没有配置语义的类型恒返回 `true`。

### 6.4 校验时机

| 时机 | 执行方 | 行为 |
|---|---|---|
| 解析 | 文档解析器 | 不校验插件配置，只保证内容根映射与不透明值可用 |
| 编辑变更 | 插件编辑器 | 可实时提示，允许中间非法态 |
| 回流 / 保存前 | 编辑链路 | 执行 `configSchema` 与 `validateConfig`，任一失败拒绝回流并给出简体中文提示 |
| 创建 / 导入 | 编辑链路 / 应用插件 | 按 schema 校验初始配置 |
| 导出 | 导出链路 | 不强制校验；插件在 `export` 内按自身规则回退或拒绝 |
