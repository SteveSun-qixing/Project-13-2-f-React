## 五、打包与发布

### 5.1 安装 .cpk 被拒有哪些常见原因？

安装校验按"归档 → 结构 → 清单 → 签名 → 摘要"执行，失败返回对应错误码（[03-插件包格式](../04-文件格式规范/03-插件包格式.md) §5、§8）：

- `CPK_ARCHIVE_INVALID`：非 ZIP、成员未 Store 压缩、加密 / ZIP64、CRC 失败、重复路径、嵌套归档；
- `CPK_LAYOUT_INVALID`：包根出现白名单外条目、角色布局不符、隐藏文件；
- `CPK_MANIFEST_MISSING` / `CPK_MANIFEST_INVALID`：缺少或多份 `manifest.yaml`、schema 失败、路径引用非法、版本不一致；
- `CPK_ENTRY_MISSING`：角色要求的入口缺失或不是文本 ESM；
- `CPK_NATIVE_PAYLOAD` / `CPK_PATH_UNSAFE` / `CPK_LIMIT_EXCEEDED` / `CPK_SIGNATURE_REQUIRED` / `CPK_SIGNATURE_INVALID`。

打包前先运行 `chips plugin validate <包>` 可提前复现全部判定。

### 5.2 为什么提示 CPK_NATIVE_PAYLOAD？

包内检测到原生可执行载荷：平台按扩展名（`.node`、`.dll`、`.so`、`.dylib`、`.exe`、`.wasm` 等）与文件魔数双重判定，命中任一即拒绝（[03-插件包格式](../04-文件格式规范/03-插件包格式.md) §5.2）。Rust 能力属于平台；服务插件的 JS 依赖必须打包进 `dist/index.js`，不得随包携带原生模块。

### 5.3 为什么提示包根有包裹目录或白名单外文件？

`.cpk` 归档根必须直接是包根，包根只允许 `manifest.yaml`、`dist/`、`render.js`、`assets/`、`signature.json` 五类条目；源码、测试、锁文件、`.map`、隐藏文件、第二份清单都会触发 `CPK_LAYOUT_INVALID`（[03-插件包格式](../04-文件格式规范/03-插件包格式.md) §2.2、§2.3）。打包时不得对暂存目录再加一层父目录。

### 5.4 为什么提示入口缺失或入口非法？

- `basecard` / `boxlayout` / `app` 必须有 `dist/index.js` 与 `render.js`；`service` 必须有 `dist/index.js` 且禁止 `render.js`（[03-插件包格式](../04-文件格式规范/03-插件包格式.md) §2.4、§3.1）。
- 两个入口都必须是 UTF-8 文本 ESM 模块：`dist/index.js` 承载主进程纯函数与角色入口，`render.js` 承载渲染方法；单个入口文件不超过 8 MiB。

### 5.5 为什么 manifest 里的图标路径报 CPK_MANIFEST_INVALID？

manifest 中所有文件引用必须是包内相对 POSIX 路径且目标位于 `assets/` 内，禁止前导 `/`、`..`、盘符与任何 URI scheme（`file://`、`chips-resource://`、`http(s)://`）；引用缺失或越界即拒绝，`details.pointer` 指向具体字段（[03-插件包格式](../04-文件格式规范/03-插件包格式.md) §2.6）。运行时由平台解析为插件作用域资源，插件不得自行拼接。

### 5.6 打包提示版本不一致怎么办？

插件源码 `package.json` 的 `version` 必须与 `manifest.yaml` 的 `version` 一致，由打包工具强制校验；不一致返回 `CPK_MANIFEST_INVALID`（[03-插件包格式](../04-文件格式规范/03-插件包格式.md) §7.1、[04-版本与迁移规范](../04-文件格式规范/04-版本与迁移规范.md) §2.1）。

### 5.7 如何本地验证 .cpk？

```bash
pnpm exec chips plugin pack --out dist/
pnpm exec chips plugin validate dist/<名称>-<版本>.cpk
```

`validate` 与安装使用同源校验，覆盖归档、结构、清单与签名（开发来源跳过签名校验）；手动打包必须使用 `zip -r -0 -X`（Store、不压缩），并保证归档根直接是包根（[03-插件包格式](../04-文件格式规范/03-插件包格式.md) §7）。

### 5.8 插件必须签名吗？

按来源渠道：`builtin` 必须签名，缺失或无效拒绝安装；`user` 当前阶段可选，未签名时安装界面必须明确展示"未签名发布者"并经用户确认，不得静默安装；`development` 不检查签名。信任根未注册的 `keyId` 视为签名无效（[03-插件包格式](../04-文件格式规范/03-插件包格式.md) §6.3）。

### 5.9 .cpk 的体积与成员限制是多少？

`.cpk` 不超过 50 MiB；文件成员不超过 512 个；单文件不超过 16 MiB；`manifest.yaml` 不超过 256 KiB；单个入口文件不超过 8 MiB；路径长度不超过 180 字符；目录深度不超过 8 层。任一超限返回 `CPK_LIMIT_EXCEEDED`，不产生部分落盘（[03-插件包格式](../04-文件格式规范/03-插件包格式.md) §4）。

### 5.10 服务插件的包布局有什么特殊要求？

`service` 禁止 `render.js` 与任何 UI 资源（图片、字体、样式、图标）；`assets/` 只允许数据文件；`runtime.background` 为可选字段（缺省 `false`，常驻服务建议显式声明 `true`）；第三方依赖必须打包进 `dist/index.js`，包内不得出现 `node_modules/`；入口经受管模块加载器加载，禁止 `node:*` 与 `electron`（[03-插件包格式](../04-文件格式规范/03-插件包格式.md) §3.2、[02-插件清单规范](./02-插件清单规范.md) §4.3）。

### 5.11 安装完成后为什么插件没有自动启用？

安装只产生 `installed` 状态，不自动启用；依赖缺失或版本不满足也不阻止安装，只在启用时阻塞。首次启用时平台展示授权界面，用户确认后插件才进入 `starting`（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §4.2、§4.3）。

### 5.12 为什么降级安装被拒绝？

同一插件 ID 安装的目标版本必须高于已安装版本，降级一律确定性拒绝、不覆盖已安装版本；同 ID 更新走蓝绿替换流程（[04-版本与迁移规范](../04-文件格式规范/04-版本与迁移规范.md) §5.1、[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §6.2）。
