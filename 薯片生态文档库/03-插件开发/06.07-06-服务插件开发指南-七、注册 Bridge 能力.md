## 七、注册 Bridge 能力

### 7.1 登记前置

- 只有 `service` 角色插件可以注册能力；`basecard` / `boxlayout` / `app` 只能消费能力（E4 8.1）。
- 第三方能力实行**登记前置**：提供方在发布前向平台提交能力契约（ID、提供方、输入 schema、输出类型、所需基础权限、用途），经评审登记后，ID 与提供方绑定；插件激活注册时按登记记录校验 ID 与 `owner`（E4 8.1、4.2）。
- 能力 ID 文法为 `<domain>:<action>[:<target>]`，全小写；`domain` 由平台统一登记分配，插件不得自造；能力 ID 不得与任何权限 ID 相同（R3）。
- 能力 ID 发布后保持稳定：ID 变更视为破坏性变更，依赖它的插件必须同步升级。

### 7.2 注册调用

能力注册只能在 `start()` 执行期间调用；平台以 `start` 成功返回作为提交点，统一对外发布注册（E10 6.1）。以下注册调用摘自第九节的完整示例，能力对象的构造见 9.4：

```typescript
// createWebpCapability 的完整实现见第九节 9.4；第二个参数返回当前生效的默认质量
ctx.registerCapability(createWebpCapability(ctx, () => this.defaultQuality), {
  timeoutMs: 30_000,
  concurrency: 'serial',
  maxQueue: 16,
});
```

### 7.3 注册选项

| 选项 | 默认值 | 说明 |
|---|---|---|
| `timeoutMs` | `30000` | 单次调用超时；超时返回 `BRIDGE_TIMEOUT`（`retryable: true`） |
| `concurrency` | `'parallel'` | `'serial'` 时该能力全局 FIFO；队列超限返回 `BRIDGE_QUEUE_OVERFLOW` |
| `maxQueue` | `32` | `'serial'` 时的等待队列上限 |

### 7.4 注册期校验

任一项失败都原子拒绝，`start` 失败、本次激活整体回滚；插件不得在运行期补注册（E4 4.2）。

| # | 校验项 | 失败错误码 |
|---|---|---|
| 1 | `id` 符合文法与命名规则 | `BRIDGE_CAPABILITY_CONFLICT` |
| 2 | `id` 在能力契约登记内，且登记绑定的提供方与注册上下文 `owner` 一致 | `BRIDGE_CAPABILITY_CONFLICT` |
| 3 | `id` 未被其他提供方占用；内置 ID 由平台服务域持有 | `BRIDGE_CAPABILITY_CONFLICT` |
| 4 | `id` 与任何权限 ID 不相同（R3） | `BRIDGE_CAPABILITY_CONFLICT` |
| 5 | `schema` 符合 E4 第五节子集且可离线编译（顶层 `object`、`additionalProperties: false`、无远程 `$ref`） | `BRIDGE_INVALID_SCHEMA` |
| 6 | `permissions` 每项为已注册基础权限 ID，且已在提供方 manifest 声明 | `PERMISSION_NOT_DECLARED` / `PERMISSION_UNKNOWN` |
| 7 | 提供方已处于 `active` 状态 | `KERNEL_INVALID_TRANSITION`（owner 未 active 属内核状态错误；`PLUGIN_PERMISSION_DENIED` 只表示权限拒绝） |

- 纯计算能力（编解码、格式转换等）声明空权限数组，权限判定直接通过（E10 6.2）。
- schema 只描述结构约束，关键字白名单与二进制扩展见 E4 第五节；示例中的 `x-chips-binary` 上限单位为字节。

### 7.5 运行语义与代际

- 注册生效后，其它插件按 ID 经 `request` 调用，链路与内置能力完全一致：权限判定、schema 校验、超时、审计一律适用。
- 调用方身份是调用它的插件：判定使用调用方的会话权限快照；能力实现内部再发出的调用使用服务插件自己的快照，权限不借用、不传递（E10 6.3）。
- 能力注册随提供方 Fork：`stop` / 更新 / 崩溃时自动注销，注销后在途调用按超时或取消收口。
- 注册表不提供枚举 API；能力不可用只能通过 `BRIDGE_CAPABILITY_NOT_FOUND` 判定。
- 同一能力 ID 跨版本保持稳定；代际切换期间旧代际进入 `draining`，新代际接管。

### 7.6 实现约束

- `execute` 收到的 `input` 已通过 schema 校验；实现仍须执行业务级与资源级二次校验（如路径安全、URI 作用域）。
- `execute` 必须异步、不得阻塞调度模型；不得假设调用方身份，不得从输入读取身份字段。
- 能力实现的错误是调用方可见的业务错误：抛出结构化 `ChipsError`，`message` 使用简体中文、按 `<DOMAIN>_<REASON>` 命名错误码；未归一异常由 Bridge 转为 `BRIDGE_INTERNAL`。
- 输入与输出必须是结构化克隆兼容值；不得返回函数、类实例、DOM 对象或 `Error` 实例。
- 能力实现不得直接访问系统 API、不得创建子进程、不得携带原生可执行载荷（R11、R17）。
- 同一功能不得同时以服务与能力两种方式对外提供两套契约（E4 2.2）：需要权限判定、schema 校验、跨上下文或审计时使用能力；主进程内类型化、低开销的请求-响应使用服务。
