## 三、常见调试场景

### 3.1 插件不加载

按固定顺序定位，不要跳步：

1. 包与清单：先运行 `chips plugin validate <目录或 .cpk>`，排除安装阶段错误（见 §4.4）。
2. 发现与遮蔽：确认当前来源（`development` > `user` > `builtin`）与生效版本。
3. 状态：安装只产生 `installed`，不自动启用；只有 `active` 状态接收渲染请求、能力调用与服务调用。
4. 依赖：`pending` 表示依赖未满足，插件代码尚未执行（`KERNEL_DEPENDENCY_MISSING` / `KERNEL_DEPENDENCY_VERSION`）。
5. 激活失败：状态 `failed` 时，在插件管理界面读取该插件记录中的 `lastError`（`IPluginRecord`，[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §3.3）；结合 `plugin:failed` 事件（payload 为归一 `ChipsError`）还原失败点。
6. 生命周期事件：`plugin:loaded` / `plugin:enabled` / `plugin:disabled` / `plugin:unloaded` / `plugin:failed` 用于还原时间线（[05-事件契约规范](../05-接口与契约/05-事件契约规范.md) §4.1）。

| 症状 | 常见原因 | 处置 |
|---|---|---|
| 安装被拒（`CPK_*`） | 包结构、清单、路径或体积不符 | 按 §4.4 对照错误码修复后重新打包 |
| 已安装但从不生效 | 未启用；或启用偏好未写入 | 在插件列表中启用；排查启动恢复记录 |
| 长期停留 `pending` | 依赖缺失或版本范围不满足 | 安装依赖或调整 `dependencies.version`（§7.4） |
| `failed`：`KERNEL_DEPENDENCY_CYCLE` / `KERNEL_DEPENDENCY_DUPLICATE` | 依赖成环或重复声明同一依赖 | 拆分依赖、去重（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §7.2） |
| `failed`：`KERNEL_APPLY_FAILED` | 角色激活入口抛错（`start` / 注册 / `launch`） | 检查入口默认导出是否实现角色接口、`start` / `launch` 内部异常与日志 |
| `failed`：`KERNEL_INJECT_FAILED` | `inject` 回调抛错 | 修复注入回调；注入回调必须是同步函数且不缓存跨代际引用 |
| `failed`：`KERNEL_PLUGIN_PANICKED` | 主进程插件任务 panic | 消除未捕获异常；失败副作用已被回收 |
| 再次启动未自动重试 | `failed` 不参与启动恢复；有限次自动重试后进入熔断 | 修复原因后由用户显式重试（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §9.3） |
| 列表可见、渲染无效果 | 插件非 `active`，或注册内容与清单/内容不匹配 | 核对 `cardTypes` / `layouts` / 启动器与文件关联 |
| 现象不是最新代码 | 来源遮蔽，或旧 Fork 处于 draining | 确认生效来源与版本；等待代际切换完成 |

模块顶层产生副作用（订阅、定时器、文件访问）属于明确禁令：主进程入口只允许声明，副作用全部放入 `start` / `launch`（[10-服务插件接口](../05-接口与契约/10-服务插件接口.md) §2.3、[07-应用插件接口](../05-接口与契约/07-应用插件接口.md) §3.1）。

### 3.2 权限被拒

权限判定链路：`manifest.permissions`（申请）→ 用户授予 → 启用时生成会话快照 → 调用时以「能力所需权限 ∩ 会话快照 ∩ 限定值/目标」判定（[08-权限系统设计](../01-架构设计/01-子系统设计/08-权限系统设计.md) §4）。

| 错误码 | 场景 |
|---|---|
| `BRIDGE_PERMISSION_DENIED` | 能力调用被拒（含未授予、已撤销、超出限定值、用户拒绝） |
| `RESOURCE_PERMISSION_DENIED` | 资源作用域或路径安全判定失败 |
| `PLUGIN_PERMISSION_DENIED` | 启用、能力注册阶段的**权限**拒绝；生命周期状态错误使用内核码（如 owner 未 active 时注册能力返回 `KERNEL_INVALID_TRANSITION`） |
| `RENDER_RESOURCE_DENIED` | 渲染帧资源代理请求越权 |
| `PERMISSION_NOT_DECLARED` | 能力所需权限未在提供方 manifest 声明 |
| `PERMISSION_UNKNOWN` / `PERMISSION_INVALID` / `PERMISSION_ROLE_NOT_ALLOWED` | 安装校验阶段的权限 ID 与角色问题 |

`IPermissionDeniedDetails` 的 `reason` 直接对应处置方式：

| `reason` | 含义 | 处置 |
|---|---|---|
| `not_granted` | 未授予（默认拒绝） | 在「设置 → 插件 → 权限」中授予，或引导用户完成首次启用确认 |
| `revoked` | 已撤销 | 由用户重新授予；撤销后会话快照立即失效 |
| `out_of_scope` | 目标超出限定值 | 收窄调用目标，或调整 manifest 中的限定值 |
| `user_rejected` | 用户拒绝了本次授权 | 按用户操作中断；不得自动重试弹窗 |
| `policy` | 策略禁止 | 检查角色适用性与权限组合是否被允许 |

高频编码错误：

1. 能力 ID 与权限 ID 混用（R3 红线）：能力 `file:write` 需要的是权限 `filesystem:write`，两者不能互相声明。
2. manifest 未声明权限：能力调用必然被拒；服务插件注册能力时还会返回 `PERMISSION_NOT_DECLARED`。
3. 限定值写死绝对路径：路径限定必须使用目录变量（如 `${userDocuments}`），否则安装校验按 `PERMISSION_INVALID` 拒绝。
4. 把权限拒绝当业务失败静默吞掉：必须给出可操作提示（文案参考 [08-权限系统设计](../01-架构设计/01-子系统设计/08-权限系统设计.md) §9.3）。
5. 对 `retryable: false` 的错误做自动重试：权限拒绝不会因重试恢复，重试只会放大失败。

### 3.3 渲染异常

渲染错误统一为 `ChipsError`（`RENDER_` 前缀），粒度为帧：单帧失败不影响兄弟帧与整个会话。渲染错误的用户可见表现与重试入口见 [05-渲染引擎设计](../01-架构设计/01-子系统设计/05-渲染引擎设计.md) §11。

| 错误码 | 触发 | 检查点 |
|---|---|---|
| `RENDER_PLUGIN_MISSING` | 找不到匹配角色的插件 | 插件是否 `active`；`cardTypes` / `layouts` 注册 ID 与文档中 `card_type` / `active_layout_type` 是否一致 |
| `RENDER_PLUGIN_FAILED` | 插件渲染方法抛错 | 帧内 console 输出；未收窄的坏数据；未释放的副作用 |
| `RENDER_FRAME_TIMEOUT` | 握手或首帧超时（默认 5s） | 入口是否 ESM、渲染入口是否存在、首屏是否同步提交、模块顶层是否阻塞 |
| `RENDER_RESOURCE_DENIED` | 帧内资源越权或被拒 | 资源 URI 的作用域与授权；是否统一使用 `chips-resource://` |
| `RENDER_SCHEMA_UNSUPPORTED` | 插件 / 能力 / schema 与内容要求不匹配 | 内容结构与插件 `configSchema`；插件版本策略与能力声明是否满足内容要求（文档格式版本问题由解析链路返回 `DOCUMENT_VERSION_*`） |
| `RENDER_DOCUMENT_INVALID` | 文档解析校验失败 | 文档格式与 `chip_standards_version`；用文档校验流程复现（[06-文档解析器设计](../01-架构设计/01-子系统设计/06-文档解析器设计.md)） |
| `RENDER_SESSION_DISPOSED` | 会话已释放仍被调用 | 调用方生命周期；`dispose()` 后不得再使用会话 |
| `RENDER_PROTOCOL_VIOLATION` | 帧消息违规 | 是否创建非受管 iframe、发送协议外消息 |

渲染调试要点：

- 渲染帧固定为 `sandbox="allow-scripts"` 的 iframe；父帧与子帧不得互相读取 DOM、注入脚本（[05-渲染引擎设计](../01-架构设计/01-子系统设计/05-渲染引擎设计.md) §四）。
- 渲染入口的 `renderView` 必须同步完成首次 DOM 提交；更新必须覆盖式呈现，不得叠加多份内容；返回的 `Dispose` 必须幂等。
- 插件抛出的异常由帧运行时隔离并按 `RENDER_PLUGIN_FAILED` 降级；插件应保留结构化日志线索后交还异常，不要吞错。
- 编辑态就近渲染运行在应用窗口渲染进程：可经 `window.chips` 访问能力与资源，但同样禁止访问 Node.js / Electron API。
- 帧的高度由帧运行时测量，插件不得固定容器宽度、不得请求改变外层尺寸。

查看态容错骨架：

```typescript
import type { BaseCardView } from '@chips/sdk';

/**
 * 查看态渲染的容错骨架：容器内容一次性替换；失败时保留结构化线索并交还帧运行时降级。
 *
 * 完整的 IBaseCardPlugin 实现见《04-基础卡片插件开发指南》。
 */
export function renderCardContent(basecard: BaseCardView, container: HTMLElement): () => void {
  try {
    const element = document.createElement('div');
    element.dataset.cardId = basecard.card.card_id;
    element.dataset.nodeId = basecard.node_id;
    element.textContent = basecard.card.name;
    container.replaceChildren(element);
  } catch (error) {
    console.error('卡片渲染失败', error, { nodeId: basecard.node_id });
    throw error;
  }

  return () => {
    container.replaceChildren();
  };
}
```
