## 二、调试工具与手段

### 2.1 调试链路总览

```text
插件源码（src/）
      │ pnpm --filter <插件包名> run build
      ▼
开发目录（目录根 = .cpk 解包后的包根）
      │ 平台发现：来源 development
      ▼
开发宿主（Electron 壳 + React 渲染层）
      │ 启用：Fork 创建 → 角色激活入口 → active
      ▼
观测面
  ├── 日志：主进程角色 logger / 渲染侧宿主开发者工具
  ├── Bridge 追踪：traceId / requestId / 判定结果
  └── 事件：plugin:* 生命周期、permission:* 授权与拒绝
      │ 修复源码
      ▼
重新构建入口 → 热重载（复用蓝绿替换流程）→ 回到 active
```

### 2.2 开发态加载

开发态允许以目录形式加载插件，目录根布局与 `.cpk` 解包后的包根完全一致（[03-插件包格式](../04-文件格式规范/03-插件包格式.md) §2.7）：

1. 平台按来源优先级发现插件：`development` > `user` > `builtin`；同一 ID 在多个来源出现时，高优先级来源生效并遮蔽其它来源，遮蔽不删除文件（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §4.1）。
2. 目录态跳过归档校验与签名校验，仍执行 manifest、入口、原生载荷、路径安全与角色布局校验。
3. 目录态只用于开发与调试；禁止以目录态分发或安装，发布单位始终是单个 `.cpk`。

自检命令（与安装完全同源，不产生安装）：

```bash
pnpm exec chips plugin validate examples/plugins/hello-basecard
```

调试期间最常见的行为偏差来源是来源遮蔽：开发目录中的旧版本会一直覆盖已安装版本。确认当前生效来源与版本后再判断现象。

### 2.3 日志

按运行位置选择日志通道：

| 运行位置 | 通道 | 要点 |
|---|---|---|
| 主进程（`app` / `service` 的业务逻辑） | 角色上下文日志流：`IAppContext.logger` / `IServiceContext.logger` | `debug` / `info` / `warn` / `error`；结构化细节放 `fields`；平台自动附加 `pluginId`、`pluginVersion`、`timestamp`、`level`、`traceId`；免权限（R19），按插件命名空间自动归属（[07-应用插件接口](../05-接口与契约/07-应用插件接口.md) §4.6、[10-服务插件接口](../05-接口与契约/10-服务插件接口.md) §3.6） |
| 渲染进程（卡片帧、布局帧、应用窗口 UI） | 宿主开发者工具的 console | 遵守 `no-console`：仅 `console.warn` / `console.error`（[02-TypeScript编码规范](../02-开发规范/02-TypeScript编码规范.md) §11）；生产构建不得保留调试输出 |

规则：

- `message` 面向开发者、使用简体中文；`fields` 只允许字符串、数字、布尔与 `null` 标量；错误对象经 `error` 参数传入。
- 禁止记录凭证值、文件内容、用户数据与资源字节；禁止在发布路径同步写日志。
- 日志免权限（R19）：按插件命名空间自动归属，写入失败不抛出、不中断业务；排查时按 `pluginId` 过滤。
- 日志文件位置、级别调整与导出方法见 [04-故障排查手册](../06-开发与运维/04-故障排查手册.md)。

完整示例（主进程诊断日志）：

```typescript
import { ChipsError } from '@chips/sdk';
import type { IAppContext } from '@chips/sdk';

/**
 * 记录一次能力调用失败的诊断信息。
 *
 * code 与 details 是唯一可依赖的定位依据；message 只用于面向用户的提示，
 * 不得作为分支条件（见《01-Bridge-API规范》1.3）。
 */
export function logBridgeFailure(
  ctx: IAppContext,
  capabilityId: string,
  error: unknown,
): void {
  if (error instanceof ChipsError) {
    ctx.logger.error('能力调用失败', error, {
      capabilityId,
      code: error.code,
    });
    return;
  }

  ctx.logger.error('能力调用出现未归一异常', error, { capabilityId });
}
```

### 2.4 Bridge 调用追踪

Bridge 是插件访问平台能力的唯一通道，一次调用的定位信息由平台在追踪中记录：

| 信息 | 来源 | 用途 |
|---|---|---|
| `capabilityId` | 调用参数 | 确认能力 ID 拼写与登记状态 |
| `code` | `ChipsError.code` | 唯一的分支与检索依据 |
| `details` | `ChipsError.details` | 结构化违例位置（输入校验）或权限判定明细 |
| `traceId` / `requestId` | 平台追踪与事件日志 | 关联一次调用在判定链上的全部记录 |
| `pluginId` / `pluginVersion` | 会话绑定 | 区分插件与版本 |

规则：

- 渲染侧没有 `window.chips.context()`；事件封套不携带 `traceId`，追踪信息只进入日志与 Bridge 追踪（[05-事件契约规范](../05-接口与契约/05-事件契约规范.md) §3.3）。
- Bridge 不提供能力枚举 API：能力是否可用只能以 `BRIDGE_CAPABILITY_NOT_FOUND` 判定（[01-Bridge-API规范](../05-接口与契约/01-Bridge-API规范.md) §7.4）。
- `BRIDGE_INVALID_INPUT` 的 `details` 为 `IInvalidInputDetails`（`capabilityId` / `errors[].pointer` / `truncated`，[04-能力契约规范](../05-接口与契约/04-能力契约规范.md) §5.4）。
- `BRIDGE_PERMISSION_DENIED` 的 `details` 为 `IPermissionDeniedDetails`（[08-权限系统设计](../01-架构设计/01-子系统设计/08-权限系统设计.md) §9.2）。
- 追踪的开启方式、输出位置与过滤方法由 [03-调试指南](../06-开发与运维/03-调试指南.md) 给出。

渲染侧可在开发期订阅自身权限拒绝事件，直接观察判定结果；`security:audit` 仅平台可读，插件不可订阅：

```typescript
import { useEffect } from 'react';
import type { ISubscription } from '@chips/sdk';

type PermissionDenyReason =
  | 'not_granted'
  | 'revoked'
  | 'out_of_scope'
  | 'user_rejected'
  | 'policy';

interface IPermissionDeniedPayload {
  pluginId: string;
  permission: string;
  capabilityId?: string;
  reason: PermissionDenyReason;
  traceId: string;
}

function isPermissionDeniedPayload(value: unknown): value is IPermissionDeniedPayload {
  if (typeof value !== 'object' || value === null) {
    return false;
  }
  const candidate = value as Record<string, unknown>;
  return (
    typeof candidate.pluginId === 'string' &&
    typeof candidate.permission === 'string' &&
    typeof candidate.traceId === 'string' &&
    (candidate.reason === 'not_granted' ||
      candidate.reason === 'revoked' ||
      candidate.reason === 'out_of_scope' ||
      candidate.reason === 'user_rejected' ||
      candidate.reason === 'policy')
  );
}

/** 开发期诊断：把本插件的权限拒绝输出到宿主控制台；发布前移除或改为界面提示。 */
export function usePermissionDeniedDiagnostics(pluginId: string): void {
  useEffect(() => {
    const subscription: ISubscription = window.chips.subscribe(
      'permission:denied',
      (payload: unknown) => {
        if (isPermissionDeniedPayload(payload) && payload.pluginId === pluginId) {
          console.warn('权限被拒', payload.permission, payload.reason, payload.traceId);
        }
      },
    );

    return () => {
      subscription.dispose();
    };
  }, [pluginId]);
}
```

### 2.5 开发宿主热更新

开发宿主由 `pnpm dev` 启动（Electron 壳 + 渲染层热更新 + Rust 增量编译，[01-代码组织规范](../02-开发规范/01-代码组织规范.md) §8.1）。插件改动的生效链路：

```text
[1] 修改插件源码
      │
      ▼
[2] 重新构建入口：pnpm --filter <插件包名> run build
      │
      ▼
[3] 平台重载插件：复用蓝绿替换流程
      新 Fork 激活 → 服务代际原子切换 → 旧 Fork draining → 旧入口销毁
      │
      ├── 失败 → 清理暂存目录；旧版本继续运行，插件保持 active
      ▼
[4] 插件保持 active，调用方不中断（切换窗口内最多两个 Fork 并存）
```

规则：

- 热重载与正式更新是同一条替换路径：运行期插件目录只读，更新经暂存目录原子替换（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §6.2、§6.4）。
- 更新中断（崩溃 / 断电）后，平台启动时清理暂存目录并回滚到旧版本。
- 新版本必须满足全部已安装依赖者的版本范围，否则更新被拒绝；权限集合变化必须重新确认。
- 热重载失败不回退到"半新半旧"：失败后运行的仍是旧版本，插件保持 `active`。
- draining 有超时上限，超时后强制 `dispose()` 旧 Fork 并记录诊断；排查残留副作用时先区分新旧代际。
- 触发方式、观察入口（开发宿主 DevTools、追踪面板）见 [03-调试指南](../06-开发与运维/03-调试指南.md)。

### 2.6 宿主外验证

不启动平台也可以验证调用逻辑与错误分支：`@chips/sdk/testing` 提供与 `IChipsBridge` 同形状的 Mock（`createMockBridge` / `installMockBridge` / `uninstallMockBridge`），可挂载能力桩、触发事件、准备资源夹具并读取调用记录 `calls`（[02-SDK-API规范](../05-接口与契约/02-SDK-API规范.md) §7）。

Mock 只模拟调用结果，不执行权限判定与 schema 校验；权限与校验类问题必须在真实宿主中复现。测试编写约定见 [05-测试规范](../02-开发规范/05-测试规范.md)。
