## 五、崩溃与恢复

### 5.1 故障分类与隔离

| 故障 | 发生位置 | 隔离方式 | 恢复 |
|---|---|---|---|
| 激活失败 | 启用期入口（`start` / 注册 / `launch`） | 捕获异常并 `dispose()` 已产生副作用，状态置 `failed` | 有限次自动重试；超过阈值转人工 |
| 运行时异常 | 主进程插件逻辑 | 插件调用边界捕获，不向平台核心传播 | 记录诊断；连续失败触发熔断 |
| UI 崩溃 / 帧失联 | 渲染进程 / iframe | 进程与沙箱隔离，只影响该窗口或卡片 | 标记会话 `error`，已渲染帧保留，用户"重新打开" |
| 健康检查失败 | `service.health()` | 熔断：停止转发调用 | 连续失败 → 停用并置 `failed` |
| 资源超限 | 任意插件 | 配额降级：限频 → 暂停后台任务 → 停用 | 恢复后重新启用 |
| 调用超时 / 死锁 | 服务与能力调用 | 超时返回 `ChipsError`（含 `retryable`） | 调用方可重试；平台熔断 |

规则：单个插件 `failed` 不阻塞平台启动与其它插件启用；依赖故障插件的插件保持 `pending`，故障恢复后自动继续（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) 9.2）。

### 5.2 恢复路径

| 场景 | 恢复动作 |
|---|---|
| 插件 `failed`（激活失败） | 修复后显式重试：`failed → starting`；插件副作用已回收，无需手工清理 |
| 插件 `pending`（依赖未就绪） | 依赖安装/更新到满足范围后自动继续激活 |
| 上次退出中断残留 `starting` / `stopping` | 平台启动时清理并回滚为 `installed`，按启用偏好重新启用 |
| 平台启动批量启用 | 按依赖拓扑序逐个启用；单个失败被隔离，不阻塞后续 |
| 服务代际替换（蓝绿更新） | 新 Fork 注册服务后原子切换；旧 Fork draining 超时强制 `dispose`；失败则回滚新 Fork，插件保持 `active` |
| 渲染帧崩溃 | 帧失联标记会话 `error`；用户重开；重试重走完整链路（解析缓存可命中，不跳阶段） |
| 插件卸载残留 | 停用必定完成；`dispose()` 逆序回收，失败记录 `KERNEL_DISPOSE_FAILED` 但不阻断 |

### 5.3 崩溃循环保护

- 同一插件在窗口期内重复激活失败 → 进入熔断：停止自动重试，保持 `failed`，等待用户显式重试。
- 运行期崩溃先隔离，再按内核策略有限重启；超过阈值转人工处理。
- 熔断状态与重试记录进入审计日志，供插件开发者在开发态排查（[03-调试指南](./03-调试指南.md)）。
- 排查步骤：1) 从审计与日志确认熔断触发次数与时间窗口；2) 读取最后一次 `lastError` 与 `plugin:failed`；3) 修复根因后显式重试；4) 重试前确认不处于 `stopping` 或依赖未就绪状态。

### 5.4 数据安全

- 插件崩溃不得损坏用户数据：文件写入经平台能力完成，采用临时文件 + 原子替换。
- 停用、卸载与更新不删除用户创建的卡片与箱子文件；归档来源不就地改写。
- 资源句柄、流与缓存随会话与作用域注销完全释放；进程退出时仍有未释放句柄会写入警告日志与审计条目。
- 崩溃后不得以"恢复"为由直接改写用户文件；修复写回必须经编辑链路与 `validate`。
