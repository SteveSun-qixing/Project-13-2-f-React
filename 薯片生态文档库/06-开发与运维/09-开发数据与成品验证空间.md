### 1.3 总原则

1. **开发数据不是用户数据**：开发工作区与用户工作区在数据、插件记录、日志上完全隔离，开发数据不得写入用户工作区。
2. **开发数据不是交付物**：开发数据不得作为发布证据；交付必须经 `document:export` 产生合规归档并在正式链路中验证。
3. **样例必须可校验**：进入验证链路的每个样例都能追溯到正式生成链路，并通过当前解析器 `validate`。
4. **敏感材料零入库**：凭证、真实用户隐私与真实绝对路径不进入仓库、文档、样例、日志与诊断导出。

## 二、开发数据目录清单

### 2.1 工作区保留目录 `<workspace>/.chips/`

保留目录由平台在工作区首次打开时创建，整棵子树不扫描、不进文件树、不可搜索（[13-工作区设计](../01-架构设计/01-子系统设计/13-工作区设计.md) §3.1、§3.2）：

| 条目 | 内容 | 归口 | 删除与重建 |
|---|---|---|---|
| `.chips/workspace.json` | 工作区标记文件（`format`、`schemaVersion`、创建信息） | 平台绑定 | 缺失按"未初始化"处理并重建；格式非法返回 `WORKSPACE_VERSION_UNSUPPORTED` |
| `.chips/config.workspace.json` | 工作区层配置（显式覆盖项） | 配置系统 | 不随开发数据交付；经 `chips config reset` 或删除文件恢复默认 |
| `.chips/plugins/<pluginId>.json` | 工作区层插件配置 | 配置系统 | 插件卸载时一并删除 |
| `.chips/backup/` | 迁移与修复前备份 | 配置系统 | 保留最近一次，仅供人工恢复，平台不回读 |
| `.chips/logs/` | 工作区级日志与诊断导出 | 平台日志 | 按日志策略清理；诊断导出必须标注工作区类型且脱敏 |
| `.chips/state/instance.lock` | 实例锁（实例 ID、PID、心跳） | 工作区生命周期 | 失效锁可被接管；正常关闭释放 |
| `.chips/state/cleanup.json` | 未完成临时物与恢复登记 | 启动恢复 | 启动或 `chips doctor --fix` 清理 |
| `.chips/state/host-state.json` | CLI 运行标记（`running` / `pid` / `startedAt`） | CLI `chips start` / `chips stop` | 可随时删除重建；不是实例状态权威（[07-CLI完整参考](./07-CLI完整参考.md) §3.2） |
| `.chips/cache/` | 可重建派生缓存（缩略图、树索引、封面缓存） | 平台 | 容量默认上限 512 MiB、LRU 淘汰；删除不影响任何文档与配置 |

约束：

- 凭证材料不进入工作区：凭证存储位于用户级 `<user-config-dir>/credentials/`，工作区配置只保存 `credential://` 引用，保留目录不设 `credentials/` 子目录。
- 保留前缀 `.chips-*`（保存临时物 `.chips-save-<随机>`、导出暂存 `.chips-export-<随机>`、解包工作目录 `.chips-unpack-<随机>`）与 `.chips/` 同等保护；插件经 `file:*` / `resources:write` 触碰保留路径一律返回 `WORKSPACE_RESERVED_PATH` 并记录审计（[13-工作区设计](../01-架构设计/01-子系统设计/13-工作区设计.md) §6.3）。

### 2.2 平台用户数据目录 `<userData>`

`<userData>` 即 Electron `app.getPath('userData')`，与配置系统的用户级目录为同一位置（[03-调试指南](./03-调试指南.md) §2.1、[10-配置系统设计](../01-架构设计/01-子系统设计/10-配置系统设计.md) §3.2）：

| 路径 | 内容 | 归口 |
|---|---|---|
| `<userData>/config.user.json` | 用户层配置（显式覆盖项） | 配置系统 |
| 平台安装级目录（macOS `/Library/Application Support/Chips/`；Windows `%PROGRAMDATA%\Chips\`） | 平台层配置 `config.platform.json`（安装资源） | 配置系统 |
| `<userData>/credentials/` | 凭证材料（密钥、令牌、口令） | 凭证能力独占 |
| `<userData>/backup/` | 用户级配置迁移与修复前备份 | 配置系统 |
| `<userData>/plugins/<pluginId>.json` | 用户层插件配置 | 配置系统 |
| `<userData>/plugins/<pluginId>/` | 插件私有数据目录（属于免授权范围；写入仍需 `resources:write`） | 插件自身 |
| `<userData>/security/permissions.yaml` | 授权记录（平台独占写入） | 权限系统 |
| `<userData>/logs/audit/audit-YYYY-MM-DD.jsonl` | 审计日志（append-only，常规留存 ≥ 180 天、高风险 ≥ 365 天） | 权限系统 |
| `<userData>/logs/trace/trace-YYYY-MM-DD.jsonl` | 调试追踪（仅开发诊断，不进入审计留存） | 平台日志 |
| `<userData>/updates/staging/<版本>/` | 平台更新下载暂存（原子替换前） | 更新子系统 |
| `<userData>/dev/workspace/` | 开发工作区（§2.3） | 开发链路 |
| 平台用户数据目录内的插件安装目录 | `.cpk` 安装落盘位置（`user` 来源）；工作区不保存插件安装产物 | 插件系统 |

平台主日志位置与平台相关（macOS `~/Library/Logs/Chips/main.log`；Windows `%USERPROFILE%\AppData\Roaming\Chips\logs\main.log`），字段与检索方式以 [03-调试指南](./03-调试指南.md) §2.1 为准。

### 2.3 开发工作区

| 项 | 规则 |
|---|---|
| 默认路径 | `${userData}/dev/workspace` |
| 路径选择 | `--workspace` → `CHIPS_WORKSPACE` → 默认路径；仅开发构建接受（[07-CLI完整参考](./07-CLI完整参考.md) §2.2、§4.1） |
| 目录结构 | 与用户工作区同构：用户文件区 + 保留目录 `<workspace>/.chips/`（§2.1） |
| 数据性质 | 夹具与临时数据；不承诺保留、可随时删除重建、不参与同步、不作为交付物 |
| 插件记录 | 插件注册表在平台用户数据目录，与工作区无关；两个工作区共用同一份注册记录（同一渠道内） |
| 插件来源 | `development` 来源（开发目录或启动参数指定的插件目录）只在开发构建与开发工作区可用；用户工作区不加载、不展示、不记录 |
| 日志 | 开发工作区日志只写开发数据目录，不混入用户日志；诊断导出标注"开发"并脱敏 |
| Electron 状态 | Electron `userData`（Cache、Local Storage、Session Storage 等）位于平台级 `<userData>`，不嵌套进开发工作区；不得入库 |

依据：[13-工作区设计](../01-架构设计/01-子系统设计/13-工作区设计.md) §7.1–§7.4、[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §4.1。

### 2.4 旧 `.chips-host-dev/` 数据映射与处置

历史生态工作区根下的 `.chips-host-dev/` 是旧架构的开发工作区，实测清单：约 88 MiB，含 20 个目录态 `*.card/`、22 个 `*.box`、`ChipsNotes/`（含 `测试.box` 与插件私有目录 `.chips-notes-runtime/`）、`documents/`（2 个 `.docx`）、`config.json`、`credentials.enc.json`、`host-logs.jsonl`（126 行）、`host-state.json`、`plugin-runtime.json`、`plugins.json`、`route-manifest.json`、`route-descriptor-manifest.json`、`plugins/`（36 个插件副本，约 70 MiB）、`electron-user-data/`（约 1.8 MiB）、`.chips-editing-engine/box-sessions/`、`.music-player-artwork-cache/`。

映射与处置：

| 旧条目 | 新架构落位 | 处置 |
|---|---|---|
| `*.card/`、`*.box`、`ChipsNotes/`、`documents/` | 开发工作区用户文件区 `<userData>/dev/workspace/` | 不迁移；按开发工作区规范重新生成 |
| `config.json`（含读取位置等插件键，键名内含历史绝对路径） | 分层配置：`<user-config-dir>/config.user.json`、`.chips/config.workspace.json`、`.chips/plugins/*.json` | 不迁移；配置键按新命名空间重建 |
| `credentials.enc.json` | `<user-config-dir>/credentials/`（凭证能力独占） | 不迁移、不复制、不作为凭据来源；按敏感数据边界处理，禁止入库 |
| `host-logs.jsonl`、`host-state.json` | 平台日志三流（主日志 / 审计 / 追踪）与 `.chips/state/` | 不迁移 |
| `plugin-runtime.json`、`plugins.json`、`route-manifest.json`、`route-descriptor-manifest.json` | 插件注册表与路由（内核维护，运行时重建） | 不迁移 |
| `plugins/`（36 个插件副本） | `user` 来源安装目录（平台用户数据目录）；开发态联调用 `development` 来源 | 不迁移；经 `chips dev plugin install` 重新安装 |
| `electron-user-data/` | 平台级 `<userData>` | 不迁移；不得混入交付 |
| `.chips-editing-engine/`、`.music-player-artwork-cache/` | 插件私有数据目录 `<userData>/plugins/<pluginId>/` 或 `.chips/cache/` | 不迁移；按可重建数据处理 |
| `.DS_Store` 等系统生成物 | 不扫描、不进文件树、不入库 | 不迁移 |

结论：`.chips-host-dev/` 全部数据不迁移；确需样例时，按第四节索引选择合规来源并按第五节准入规则重新校验或重新生成。历史目录若需从仓库工作区移除，必须移入就近 `归档/`，禁止直接删除。

## 三、敏感数据边界与清理规则

### 3.1 敏感数据边界（红线）

1. **凭证材料**：只存于 `<user-config-dir>/credentials/`；配置、备份、日志、诊断导出、`config:changed` 事件、样例与测试夹具一律不得出现凭证材料，只允许 `credential://<pluginId>/<name>` 引用形式。
2. **真实绝对路径与用户名**：台账、样例元数据、文档正文与 TSV 证据不得复制运行数据中的历史绝对路径（如旧 `config.json` 的插件键、日志片段）；文档中只写 `${userData}`、`<workspace>` 等变量形式。
3. **用户隐私**：不得把用户工作区内容复制为样例；样例必须是脱敏、合成或已授权素材，且登记素材来源。
4. **Electron 状态**：`Cache`、`Local Storage`、`Session Storage`、`blob_storage` 等可能包含登录态与站点数据，视为敏感数据，不得入库、不得作为验证证据。
5. **日志与审计**：审计日志 append-only，插件无读写接口；普通日志、调试追踪与诊断导出不得含凭证与用户文件内容，导出必须标注工作区类型（用户 / 开发）并脱敏。
6. **保留区与跨工作区**：保留区只由平台组件访问；跨工作区访问不自动授权，旧作用域注销后句柄一律 `invalidated`。
7. **内容引用**：样例与夹具不得持久化 `data:` / `blob:` 与裸绝对路径，引用形式限于[06-资源协议规范](../05-接口与契约/06-资源协议规范.md) §2.2 的合法集合。

### 3.2 清理规则

| 对象 | 可清理性 | 方式 | 影响 |
|---|---|---|---|
| `<workspace>/.chips/cache/` | 可随时清理 | 删除目录或 `chips doctor --fix` | 仅丢失可重建缓存；文档与配置不受影响 |
| `.chips/state/cleanup.json` 登记的临时物 | 可清理 | 启动恢复或 `chips doctor --fix` | 清理崩溃残留临时物 |
| `.chips/state/host-state.json` | 可随时清理 | `chips stop` 删除；手动删除后在下次 `chips start` 重建 | 仅丢失脚本运行标记，不影响实例、文档与配置 |
| 保留前缀临时物 `.chips-save-*`、`.chips-export-*`、`.chips-unpack-*` | 仅平台清理 | 启动恢复、保存/导出收敛流程、`chips doctor --fix` | 不触碰用户文档 |
| 开发工作区整体 | 可整体清空重建 | 删除 `${userData}/dev/workspace` 后由 `chips dev` 重新初始化 | 丢失本机联调夹具；不承诺保留 |
| `<userData>/updates/staging/<版本>/` | 由更新流程管理 | 更新完成或失败回滚后清理 | 无 |
| `<userData>/logs/trace/` | 可清理 | 按调试需要删除 | 丢失调试追踪，不影响审计 |
| `<userData>/logs/audit/` | 不可手工删除 | 由平台按留存期清理（常规 ≥ 180 天、高风险 ≥ 365 天） | 影响可追溯性 |
| `backup/`（用户级 / 工作区级） | 保留最近一次 | 仅人工恢复使用，平台不回读 | 覆盖前先另存可保留更早备份 |

必须避免的清理动作：

- 不删除、不改写用户文档与已安装插件目录；插件与配置的移除只走 `chips plugin uninstall` 与 `chips config reset` 等正式命令。
- 不手工编辑 `.chips/workspace.json`、`config.workspace.json`、`security/permissions.yaml`。
- 仓库内资产（历史样例、脚本、文档）的移除遵循归档政策移入就近 `归档/`；运行时数据的清理按本表执行，两者不混用。

### 3.3 清理后自检

`chips doctor` 检查项固定为：工作区标记与保留目录、工作区可写性、平台数据目录、插件注册表、日志目录、更新渠道配置、承载运行时依赖；`--fix` 只处理可安全重建项（缓存、崩溃残留临时物、缺失的保留目录骨架），不触碰用户文档与已安装插件（[07-CLI完整参考](./07-CLI完整参考.md) §3.8）。

## 五、成品验证空间用途与准入

### 5.1 用途与执行环境

成品验证空间用于以真实用户形态完成交付物的人工端到端验收与缺陷复现：

- 验证对象：平台构建产物（含安装包）与发布渠道 `.cpk` 插件（`stable` / `beta` / `rc` / `alpha` / `builtin`）。
- 验证场地：正式渠道 + 用户工作区形态（`${userDocuments}/Chips` 或专用用户工作区），不得用开发工作区替代；开发工作区的崩溃与性能数据不得作为用户工作区的质量证据。
- 验证输入：本文件第四节索引的样例，以及经准入登记的新样例；示例配置必须由插件 schema 默认值或用户显式覆盖产生，不得随发布产物分发。
- 验证记录：按第六节模板形成记录并归档；记录中不得包含凭证、隐私与真实绝对路径。

### 5.2 与自动化测试、开发联调的区别

| 维度 | 自动化测试 | 开发联调 | 成品验证 |
|---|---|---|---|
| 入口 | `pnpm test` / `pnpm test:contract` / Playwright E2E | `pnpm dev`、`chips dev run`、`chips dev service invoke` | 正式安装包 + 用户工作区 |
| 插件来源 | 测试夹具与 Mock | `development` 来源 | `stable` / `beta` / `rc` / `alpha` / `builtin` |
| 数据 | `tests/fixtures/` 固定夹具 | 开发工作区临时数据 | 成品验证空间样例（复制到用户工作区） |
| 结论用途 | 门禁与回归 | 开发诊断 | 发布验收与缺陷复现 |

### 5.3 准入规则

样例进入成品验证空间必须同时满足：

1. **来源合规**：经正式链路产生（`document:export` 导出归档态或目录态、`chips plugin pack` 打包、`document:save` 受控写入），禁止手工拼装归档或使用第三方打包器改写成员顺序与压缩方式。
2. **版本可识别**：`chip_standards_version` 主版本与平台支持的文档格式主版本一致；次版本高于平台时只作为警告验证项；版本不满足的样例不得作为验收输入（[04-版本与迁移规范](../04-文件格式规范/04-版本与迁移规范.md) §5.1）。
3. **校验通过**：样例经 `document:open` 解析校验与 `validate` 通过，资源清单与实际成员、摘要一致；`Invalid` 样例只能作为错误处理验证的负面输入并单独标注。
4. **脱敏**：不含真实凭据、真实用户隐私与真实绝对路径；引用形式合法。
5. **素材授权**：媒体样例为自有、合成或已授权素材，并登记来源与许可；未获授权的历史素材仅限本机、不得再分发。
6. **登记齐全**：每个样例登记名称、形态、体积、覆盖插件与能力、生成方式、校验状态与维护人，并并入 §4.1 索引。
7. **体量受控**：大体积媒体与含第三方内容的样例不入库，仅在本地验证空间保留；可入库的小体积合规夹具放入 `tests/fixtures/`。
8. **插件版本明确**：验证插件使用发布渠道产物或 `builtin`；`development` 来源产物不得作为发布验证对象，也不得进入任何发布渠道。

### 5.4 准入流程

```text
样例来源（正式链路产物 / 历史样例重校验 / 合成素材）
        │
        ▼
[1] 版本与格式校验：document:open + validate + 资源清单核对
        │ 失败 → 拒绝准入（仅可作负面样例并单独标注）
        ▼
[2] 敏感检查：凭证 / 隐私 / 绝对路径 / 第三方授权
        │ 失败 → 脱敏处理或拒绝准入
        ▼
[3] 体量判定：入库（tests/fixtures/）或本地验证空间保留
        ▼
[4] 登记：名称、形态、体积、覆盖插件与能力、生成方式、校验状态、维护人
        ▼
[5] 并入 §4.1 索引；按第六节模板执行验证并归档记录
```
