## 三、Rust 内核调试

内核是 Cordis 运行时的 Rust 实现，状态由内核命令循环独占写入、其余路径只读快照（[01-薯片内核设计](../01-架构设计/01-子系统设计/01-薯片内核设计.md) 第 10 章）；调试时对状态与锁的干扰必须最小。

### 3.1 调试构建与符号

1. 使用 debug profile 构建（含符号；`[profile.release]` 的 LTO 产物不可用于断点调试）：

```bash
cargo build --workspace
```

2. 确认绑定产物已更新：`packages/host/native/chips-native.node` 的修改时间与本次 `cargo build` 一致（复制规则见 [01-代码组织规范](../02-开发规范/01-代码组织规范.md) 第 7.1 节）。
3. 启动壳应用：`pnpm dev`（根脚本聚合方式见 [01-代码组织规范](../02-开发规范/01-代码组织规范.md) 第 8.1 节）。

### 3.2 断点调试（lldb / VS Code）

1. 取得 Electron 主进程 PID：开发态启动日志输出 `process.pid`；macOS 可用 `pgrep -f Electron` 辅助确认。
2. 附加调试器（macOS）：

```text
$ lldb -p <主进程 PID>
(lldb) breakpoint set --func-regex 'chips_parser::'
(lldb) breakpoint set --func-regex 'chips_bridge::'
(lldb) continue
```

3. 命中后查看调用栈与变量；内核为单写多读 + Tokio（[01-薯片内核设计](../01-架构设计/01-子系统设计/01-薯片内核设计.md) 第 10 章），异步路径需查看全部线程：

```text
(lldb) thread backtrace all
(lldb) frame variable
(lldb) process continue
```

4. VS Code（CodeLLDB）附加配置：

```json
{
  "version": "0.2.0",
  "configurations": [
    {
      "name": "附加到 Electron 主进程（Rust）",
      "type": "lldb",
      "request": "attach",
      "pid": "${command:pickProcess}"
    }
  ]
}
```

5. 断点纪律：不得在持有内核锁的位置长时间停留（会阻塞命令循环）；优先使用条件断点（以插件 ID、能力 ID 为条件），不用全量停点。
6. 纯 Rust 路径更快：单元测试用 `cargo test -p <crate> -- --nocapture` 观察日志；需要断点时用 Rust Analyzer 的 Debug 入口或 `cargo test --no-run` 后对测试二进制附加调试器。

### 3.3 Rust 日志

- 内核与绑定使用 `log` 宏输出（[ADR-003](../01-架构设计/ADR/ADR-003-Rust核心加Node-Native-Module架构.md) 调试章节）；模块级别用 `RUST_LOG` 控制。
- 落地位置：平台主日志（第 2.1 节）。服务调用、事件发布等热路径禁止逐次 `info` 日志，避免违反内核性能约束（[01-薯片内核设计](../01-架构设计/01-子系统设计/01-薯片内核设计.md) 第 11.1 节）。
- 推荐在阶段边界（插件应用前后、依赖解析结果、Fork 撤销失败）记录结构化字段：

```rust
use log::{debug, error};

impl PluginManager {
    /// 在插件应用的阶段边界输出可检索的日志。
    async fn apply_with_log(&self, id: &PluginId) -> Result<(), KernelError> {
        debug!(plugin_id = id.as_str(), "开始应用插件");
        match self.apply_one(id).await {
            Ok(()) => {
                debug!(plugin_id = id.as_str(), "插件应用完成");
                Ok(())
            }
            Err(error) => {
                error!(plugin_id = id.as_str(), code = error.code(), "插件应用失败");
                Err(error)
            }
        }
    }
}
```

启动命令：

```bash
RUST_LOG=chips_cordis=debug,chips_bridge=trace pnpm dev
```

### 3.4 panic 定位

1. 启用栈输出：`RUST_BACKTRACE=full pnpm dev`；崩溃后在平台主日志中检索 `panicked at` 行。
2. 插件代码的 panic 由内核边界捕获（同步回调 `catch_unwind`、异步任务经任务句柄，[01-薯片内核设计](../01-架构设计/01-子系统设计/01-薯片内核设计.md) 第 9.3 节）：表现为插件进入 `failed`、发布 `plugin:failed` 事件并返回 `KERNEL_PLUGIN_PANICKED`。按 `plugin:failed` 的 `pluginId` 打开该插件栈修复；内核与其他插件不受影响。
3. 进程无日志直接退出：优先怀疑 Neon 绑定层 panic（跨 FFI 的 panic 会终止进程，[04-Rust编码规范](../02-开发规范/04-Rust编码规范.md) 第 14.2 节）。用 lldb 复现并执行 `thread backtrace all` 定位，修复方式是把绑定层改为 `JsResult` / `throw_error` 返回错误，而不是捕获 panic。
4. `KERNEL_DISPOSE_FAILED` 表示撤销阶段有副作用失败但流程继续（[01-薯片内核设计](../01-架构设计/01-子系统设计/01-薯片内核设计.md) 第 9.2 节）：在平台主日志检索该错误码，定位失败 Fork 对应的插件与资源。

### 3.5 并发问题定位

- 症状：界面卡顿、插件状态不一致、事件乱序。
- 步骤：
  1. `CHIPS_TRACE=plugin` 观察插件加载/停用是否长时间不推进；
  2. lldb `thread backtrace all` 检查是否有线程在持锁状态下调用插件代码或执行阻塞 IO（违反 K-4 与 [01-薯片内核设计](../01-架构设计/01-子系统设计/01-薯片内核设计.md) 第 10.3 节）；
  3. 阻塞型调用（文件 IO、图像处理）应经 `spawn_blocking`；确认为实现缺陷后按内核并发红线修复，不在调用侧加锁掩盖。
