## 三、质量门禁清单

### 3.2 覆盖率门禁（G6）

- 口径：总体 > 80%；Rust 核心（`chips-*` crates）与共享层（`@chips/ui`、`@chips/bridge`）> 90%（R18、《测试规范》第一节）。
- 四个统计维度（行、函数、分支、语句）分别判定：总体各维度 > 80%，核心与共享层各维度 > 90%（《测试规范》10.2 节）。
- 命令：测量为 `pnpm run test:coverage`（TS 为 vitest + v8，Rust 为 cargo-tarpaulin）；判定唯一执行面为 G6 `node tools/gates/check-coverage.mjs`（工单 011/017 裁决合并双执行面），`pnpm report:coverage` 只做测量聚合与报告渲染、判定委托 G6 获得，两侧不再各自判定。
- 报告：输出到 `coverage/`（lcov + html + Rust XML）；报告随流水线归档，并进入发布记录。
- 排除项按《测试规范》8.1 节的 vitest 配置执行；扩大排除范围属于豁免，按第六节登记，禁止为提升数字自行放宽。
- 新增代码不得拉低整体覆盖率；覆盖率下降即失败，不设"先合入再补测试"通道。

### 3.3 性能门禁（G7）

| 指标     | Phase 2（放宽） | Phase 4 起（正式） | 测量口径                                                            |
| -------- | --------------- | ------------------ | ------------------------------------------------------------------- |
| 冷启动   | < 2 s           | < 1 s              | 进程启动到主界面可交互                                              |
| 渲染帧率 | ≥ 30 fps        | ≥ 60 fps           | 标准滚动场景持续 10 s 的平均帧率                                    |
| 空闲内存 | < 500 MB        | < 500 MB           | 空闲 5 分钟后平台 RSS                                               |
| 打开卡片 | < 100 ms        | < 100 ms           | `RenderEngine.open()` 调用到会话 `ready`（《05-渲染引擎设计》10.1） |
| 打开箱子 | < 200 ms        | < 200 ms           | 同上                                                                |

解析器基准（criterion，PR 必跑，《06-文档解析器设计》9.2/9.5 节）：

| 基准                | 阈值                                |
| ------------------- | ----------------------------------- |
| 10 MB 卡片全量解析  | ≤ 100 ms                            |
| metadata 解析与校验 | ≤ 5 ms（打开总预算 ≤ 10 ms）        |
| 10 000 条目解析     | ≤ 100 ms（打开箱子总预算 ≤ 200 ms） |

- 渲染帧率臂两列比较算子为 ≥：工单045 修口（2026-09-21）——60Hz 参考机均值上限恰为 60.00，算子翻正 ≥，数值与协议零改；系权威文本措辞缺陷修口，不构成放宽门禁。
- 测量协议：夹具固定入库、环境固定、每指标多轮取中位数；与预算比较，不与历史浮动比较。
- 放宽值只适用于 Phase 2；Phase 4 起按正式基线执行。
- 变更导致超阈值必须在同一变更内优化，或以数据证明调整预算；禁止以"后续优化"推迟（《01-架构原则》4.2）。
- 平台级预算在 main 合并与 tag 流水线执行；PR 执行解析器基准与稳定子集。

### 3.4 契约一致性门禁（G8）

| 契约         | 比对对象                                                    | 权威                                                            |
| ------------ | ----------------------------------------------------------- | --------------------------------------------------------------- |
| 核心导出面   | Neon 导出函数名、参数、返回形状、错误码；`CORE_ABI_VERSION` | 《03-核心接口规范》                                             |
| 能力契约     | 内置能力注册表的 ID、schema 与权限映射                      | 《04-能力契约规范》                                             |
| 事件契约     | 事件 ID、payload 与触发时机                                 | 《05-事件契约规范》                                             |
| 插件角色接口 | 四种角色接口、SDK 类型导出、`.cpk` 入口默认导出形状         | 《02-SDK-API规范》、07-10 接口规范                              |
| 帧协议       | 帧消息封套、消息清单、方向与 `protocol` 值                  | 《05-渲染引擎设计》§9、《测试规范》5.3                          |
| 文档格式     | 解析器 schema 与格式文档字段；目录态/归档态夹具一致性       | 《01-卡片文件格式》、《02-箱子文件格式》、《06-文档解析器设计》 |
| manifest     | 清单校验实现与字段、角色规则                                | 《02-插件清单规范》                                             |

- 命令：`pnpm run test:contract`（TS 侧角色接口快照、帧协议与契约断言）+ `cargo test -p chips-native`（核心导出面与 `CORE_ABI_VERSION`）；必须在构建 `chips-native.node` 之后执行。
- 判定：全部断言通过，且快照比对无未审阅差异；导出面不兼容变更必须递增 `CORE_ABI_VERSION`，并作为重大变更走 RFC → 评审 → ADR（R16）。
- 产物：契约测试报告与快照差异清单输出到 `reports/contract/`，随流水线工件归档；差异必须由 PR 显式更新快照并说明理由，禁止静默覆盖。
- 契约类文档与实现必须同一 PR 更新；不一致视为缺陷，不得合并。
- 自动化只判定可机器比对的部分；文档同 PR 由 PR 门禁与评审共同保证，禁止以"文档后补"合并。

### 3.5 架构与安全门禁（G9、G10）

- 依赖方向必须符合《01-代码组织规范》4.2 的依赖矩阵；ESLint `import/no-cycle` 与 Rust 编译器的无环约束必须通过。
- R4：`@chips/antd` 仅 `packages/ui` 可用；`antd`、`antd/*`、`@mui/*`、`@chakra-ui/*` 的 `no-restricted-imports` 拦截必须生效。
- 插件不得直接 import 其他插件、平台包源码或 Node/Electron API；违反即失败。
- `unsafe fn` 必须有 `# Safety` 章节，`unsafe` 块必须有 `// SAFETY:` 注释；无理由的 `#[allow(clippy::...)]` 由 G2 与评审共同判定拒绝。
- 依赖安全：`cargo audit` 与 `pnpm audit` 无已知高危漏洞；新增依赖的选型审查随 PR（《01-架构原则》3.1）。
- Electron 安全基线必须保持：`nodeIntegration: false`、`contextIsolation: true`、`sandbox: true`，生产环境禁止关闭 `webSecurity`（R17、《超大型工程管理体系》6.3）。
- 插件系统能力只经 Bridge 调用且可审计；资源统一经 `chips-resource://` 访问，受限、可审计（《超大型工程管理体系》6.3）。

### 3.6 文档门禁（G12）

- 命令：`pnpm run docs:check`（[01-代码组织规范](../02-开发规范/01-代码组织规范.md) §8.1 标准脚本）：检查文档库相对链接、README 索引收录、四行文档头、公开 API 文档覆盖率与 ADR 状态。
- 判定：相对链接 0 坏链；README 索引收录 `薯片生态文档库/` 下全部正式文档且无失效条目；每份文档四行文档头齐全并含结尾"文档结束"；公开 API 文档覆盖率 > 95%（《01-架构原则》4.3、《超大型工程管理体系》6.4）；重大决策均有 ADR，状态为已接受或已废弃。
- 产物：坏链清单与 API 文档覆盖率报告输出到 `reports/docs/`（`links.json`、`api-coverage.json`），随流水线工件归档并进入发布记录；失败时输出逐条定位行。
- 代码、接口、格式、规范变更必须在同一 PR 内更新对应文档；不一致视为缺陷（R16）。
- 阶段出口前该阶段涉及的文档同步完成；发布说明与文档更新同 PR；发布记录中的文档状态可复核（第五节）。

### 3.7 生成工程门禁（G13）

- 命令：`pnpm run gates:generated-project`（`node tools/gates/check-generated-project.mjs`，GATE ID `generated-project`）。该脚本是 `tools/gates/gates-all.mjs` 串行聚合的第五项：聚合现为五项（docs、contracts、boundaries、coverage、generated-project），`gates:all` 逐项串行执行、任一失败即聚合退出码 1。
- 对象与段次：从 `tools/scaffold/src` 现场转译装载脚手架生成器（不依赖 `dist` 新鲜度，与模板内容编辑解耦），对四角色模板（`basecard` / `boxlayout` / `app` / `service`）各生成一份工程到临时沙箱，依次执行四类结构性段次：脚手架自校验（内存 manifest 过 `validateManifest`）、`manifest.yaml` 与 `package.json` 落盘实形圆整校验、可机检编译段（`.ts` / `.tsx` 语法级编译诊断、JSON 产物解析、包内相对引用存在性）、清洁度断言（占位回填、无未收口标记、无旧脚手架身份与沙箱绝对路径泄露、无绝对路径裸直读、文件集合齐备）。判据全部取结构性判定（键集、文件集合、语法诊断、清洁度正则），不快照模板字面内容，与并发的模板演进互不踩踏。
- 判据层编号（违规）：
  - `GP001` / `GP010`（脚手架 validate 层）：`GP001` = `createScaffoldPlan` 抛错；`GP010` = 内存 manifest 校验失败。
  - `GP011` / `GP012`（`manifest.yaml` 落盘实形层）：`GP011` = 落盘 manifest 解析失败或实形校验失败；`GP012` = 落盘 manifest 丢失计划的顶层键（发射器与计划不一致）。实形解析优先经脚手架包根解析其 `yaml` devDependency（真 `yaml` 包），不可解析时兜底改用内置子集解析器（只覆盖 `emitYaml` 输出文法：两级缩进块、`- ` 序列、`[]` / `{}`、行内标量与双引号转义）并以 `GP090` 警告留痕；报告统计 `parser: yaml | subset` 为口径唯一留痕。
  - `GP013`（`package.json` 形状层）：`version` 与 manifest 不一致、出现 `dependencies` 键（平台提供物红线）、`scripts.build` / `scripts.test` 缺失或为空、JSON 解析失败。
  - `GP020` / `GP021` / `GP022`（可机检编译段）：`GP020` = 语法级编译诊断；`GP021` = JSON 产物解析失败；`GP022` = 包内相对引用悬空。
  - `GP030` ~ `GP033`（清洁度层）：`GP030` = 未回填的模板占位符（`{{大写标识}}` 形态）；`GP031` = 未收口标记（TODO / FIXME / XXX）；`GP032` = 旧脚手架身份泄露（`app-standard`、`chips-scaffold-*`、`chipsdev`）或沙箱绝对路径泄露到正式工程文本；`GP033` = 生成源码存在绝对路径裸直读引用。
  - `GP040`（文件集合层）：计划缺失模板声明文件、计划出现模板清单之外的文件、核心文件缺失（`manifest.yaml`、`package.json`、`tsconfig.json`、`README.md`）、生成文件内容为空。
  - `GP050`（e2e 开关臂）：真跑段失败，见下。
  - 警告编号：`GP090`（`yaml` 包不可解析、改用内置子集解析器）、`GP091`（工作区根缺 `tsconfig.base.json`，e2e 段 typecheck 预期落空）。
- e2e 开关臂（`GP050`）：真装真跑重型段挂显式开关——`CHIPS_SCAFFOLD_E2E=1` 环境变量或 `--e2e` 参数才触发（比照宿主 app-smoke 的 `CHIPS_HOST_SMOKE=1` 惯例）；建 pnpm 工作区沙箱真装依赖后，逐生成工程按其 `package.json` 在册脚本执行 `typecheck` / `build` / `test`（该工程未声明对应脚本则跳过该步）。常跑段不触发该臂、不计入本门禁常跑判据；常跑段实测耗时约 0.4~0.5 s，e2e 臂在任务 #226 验收实测 22.4~22.7 s（随依赖缓存与机器浮动）。
- 收口现状（截至 2026-09-23）：门禁本体在册、常跑段四类段零违规（合缝波 #233 现场复跑：EXIT=0、`e2e=skipped`、单轮实耗约 0.4 s）。e2e 开关臂在 #226 验收阶段首次真开抓出三条模板面真缺陷（`basecard` 的 `validateConfig` 具名再导出指向无该导出的模块、`boxlayout` 的 `renderPlugin` 缺必填成员、生成工程缺 DOM 测试环境），当时维持候裁绿状态、不计入常跑段判据；三条缺陷已由工单055 修口波 #229（提交 `9958c8a03`）修口收口，开关臂随修口翻正通过（#233 现场 `--e2e` 真跑复测：EXIT=0、`e2e=passed`、实耗约 29 s，install 与逐工程 typecheck/build/test 全链绿）。聚合闸与常跑判据按设计仍不含 e2e 真跑臂，该臂只在显式验收时开启。
- 编号消歧（在册判例）：脚本与聚合报告显示标题为「生成工程门禁（G1）」，该 `G1` 指《旧功能覆盖矩阵-Chips-Host-Chips-Scaffold-2026-09-20》§五的缺口编号（矩阵缺口 G1/G3/G5/G6 同理）；矩阵缺口编号与本表门禁编号同号不同义（本表 G1 为 Rust 格式门禁）。引用本门禁一律使用本表编号 G13 或全称「生成工程门禁」，不得以裸 `G1` 指代。
- 退出码：0 通过；1 存在违规；2 用法或环境错误；3 工具内部错误（与 `gates-all.mjs` 聚合同一口径）。
- 产物：报告默认写入 `reports/generated-project/`，统计字段为 `roles / files / tsChecked / manifests / e2e / parser`；`e2e` 取值 `skipped | passed | failed`，未开开关臂时常跑通过即为 `pass`。
