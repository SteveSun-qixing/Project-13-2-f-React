## 二、版本基线

### 2.1 工具链版本要求

| 工具 | 版本要求 | 核验命令 | 权威来源 |
|---|---|---|---|
| Rust（rustc / cargo） | >= 1.75；edition 2021 | `rustc --version` | [04-Rust编码规范](../02-开发规范/04-Rust编码规范.md) §1.1 |
| rustfmt | 随 Rust 工具链 | `cargo fmt --version` | 同上 §1.2 |
| clippy | 随 Rust 工具链 | `cargo clippy --version` | 同上 §1.3 |
| Node.js | >= 18 LTS | `node --version` | [《超大型工程管理体系》](../07-工程管理/01-超大型工程管理体系.md) §9.1；[05-测试规范](../02-开发规范/05-测试规范.md) CI 固定 `node-version: 18` |
| pnpm | 主版本 9（>= 9） | `pnpm --version` | [01-代码组织规范](../02-开发规范/01-代码组织规范.md) §8.2 `"packageManager": "pnpm@9"` |
| Electron | >= 27，内置 Chromium >= 118、Node 18 | `pnpm --filter @chips/host exec electron --version` | [ADR-002](../01-架构设计/ADR/ADR-002-Electron作为桌面端壳.md) §版本要求 |
| TypeScript | >= 5 | `pnpm --filter @chips/host exec tsc --version` | [ADR-003](../01-架构设计/ADR/ADR-003-Rust核心加Node-Native-Module架构.md) §构建配置 |
| Neon | 1.x | 构建时由 Cargo 解析 | [ADR-003](../01-架构设计/ADR/ADR-003-Rust核心加Node-Native-Module架构.md) §构建配置 |
| 测试工具 | vitest（TS 单元/集成）、@playwright/test（Electron E2E）、criterion（Rust 基准）、cargo-tarpaulin（Rust 覆盖率） | `pnpm --filter @chips/sdk exec vitest --version` 等 | [05-测试规范](../02-开发规范/05-测试规范.md) §六、§八、§十 |

工具链版本只在三处固定：workspace 清单（`Cargo.toml`、`package.json`）、CI 工作流、本文。三处必须一致，不得由开发者在本地私自降级。服务端产品运行时与框架基线（§2.4）同受本条约束。

### 2.2 与管理体系基线的核对

[《超大型工程管理体系》](../07-工程管理/01-超大型工程管理体系.md) §9.1 给出的基线为：rustc >= 1.75、Node.js >= 18 LTS、pnpm >= 9、Electron >= 27。本文落地值与基线的对应关系：

- Rust：workspace `rust-version = "1.75"`，与基线一致；CI 与本地工具链不得低于 1.75。
- Node.js：与基线一致（>= 18 LTS；CI 固定 18）。
- pnpm：根清单固定 `pnpm@9`，与基线一致。
- Electron：与基线一致（>= 27，Chromium >= 118、Node 18 由 Electron 27 提供）。
- 其余构建与测试工具由各 workspace 包在 `devDependencies` 中固定，规则见 [05-测试规范](../02-开发规范/05-测试规范.md)。

以上取值互不冲突。任一处升级（Rust 最低版本、Node 主版本、pnpm 主版本、Electron 主版本）必须作为同一次变更同步更新 workspace 清单、CI 工作流与本文。

### 2.4 服务端产品运行时与框架基线（canonical）

服务端产品指 `chips-ecosystem/server/community/`（社区平台服务器）与 `chips-ecosystem/server/personal/`（个人服务器）两个平台进程之外、经 HTTP 与传输协议接入的部署单元（顶层目录骨架见[代码组织规范](../02-开发规范/01-代码组织规范.md) §二）。本节 canonical 均为现役实况升格登记，不引入新选型。

| 项 | canonical 口径 | 证据（现役实况，格式＝路径:行号） |
|---|---|---|
| Node 运行时 | **Node.js >= 20**：服务端产品本地联调、包级 `engines.node` 与 CI 判定下限统一为 20；生产镜像基础层锚定 `node:20-alpine` | [服务端部署与运维](./08-服务端部署与运维.md) §二：`08.02` §2.1 表「本地联调 Node.js >= 20」（`08.02:20`）、约束 2 镜像基础层（`08.02:25`）；旧两仓根清单 engines 实测同值 `"node": ">=20.0.0"`（`Chips-CommunityPlatformServer/package.json:25`、`Chips-PersonalServer/package.json:25`） |
| Web 框架 | **Fastify 4**（主版本 4，现役版本锚定 `^4.26.2`） | 旧两仓服务端包 dependencies 实测同值 `"fastify": "^4.26.2"`（`Chips-CommunityPlatformServer/packages/server/package.json:32`、`Chips-PersonalServer/packages/server/package.json:25`）；框架形态权威（只定名未定版本）：[社区平台设计](../01-架构设计/01-子系统设计/14-社区平台设计.md) §2.2（`14-社区平台设计.md:115`）、[个人服务器设计](../01-架构设计/01-子系统设计/15-个人服务器设计.md) §二（`15.02:18`、`15.02:42`） |

注记：

1. 与 §2.1 通用基线的关系：通用基线 Node >= 18 继续覆盖平台包、插件与工具链面（`chips-ecosystem/package.json:9` `"node": ">=18"`）；服务端产品面按 20 收紧，是「通用下限＋服务端收紧」的分层口径，不是互相冲突的双口径。
2. 差异归档理由：旧两仓均无 `.nvmrc`（两仓根与 `packages/` 层级实测零命中），除上述两档外不存在第三口径；部署权威（`08.02` §2.1）与两旧仓 engines 实测同为 20，故服务端 canonical 依现役实况多数写定为 `>= 20`（当前在役 LTS 版本线 22 / 24 均满足该下限）。
3. 同步义务：依 §2.1「三处固定」，服务端包 `engines.node >= 20` 须在包清单、CI 工作流与本文三处一致登记，随服务端目录落盘同步履行。
4. 升级策略：Node 镜像基础层（现 `node:20-alpine`；Node 20 上游维护窗口已止于 2026-04）与 Fastify 主版本（Fastify 5 及 `@fastify/*` 插件族配套大版本）的升版均属技术决策，须按[技术选型标准](../00-愿景与原则/01.04-01-架构原则-三、技术选型标准（Technology Selection Criteria）.md)与[决策流程](../00-愿景与原则/01.07-01-架构原则-六、决策流程（Decision Process）.md)核对，涉及基础架构或长期运行时依赖时履行 RFC → ADR 后方可变更；本文只登记现役口径，不预设升版时间表。`@fastify/*` 插件族与主框架同代锁定（实测：`@fastify/cookie ^9.3.1`、`@fastify/cors ^9.0.1`、`@fastify/helmet ^11.1.1`、`@fastify/jwt ^8.0.1`、`@fastify/multipart ^8.3.0`、`@fastify/swagger ^8.14.0`、`@fastify/swagger-ui ^4.0.0`，`Chips-CommunityPlatformServer/packages/server/package.json:21-27`；PS 侧同代子集 `Chips-PersonalServer/packages/server/package.json:19-22`），新服务端包起步沿用同代组合。
