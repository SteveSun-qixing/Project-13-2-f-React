# 更新与分发规范

> 版本：v1.0.0
> 日期：2026-09-19
> 状态：正式版
> 适用范围：薯片平台更新与分发的权威规范：平台更新（更新源与渠道、更新包签名链与信任根、版本比较与防降级、原子替换与失败恢复、灰度与暂缓、离线更新包、重启边界）、插件分发（`.cpk` 来源、市场协议契约、`engines.chips` 兼容门禁、安装包与内置插件首启引导）、版本回退声明、与构建/CICD 的衔接、供应链安全与审计、约束与自检清单。

---

## 一、定位与边界

### 1.1 定位

本规范定义薯片平台**自更新**与**插件分发**的正式契约：

- 平台更新：把新版本平台安全、可验证地交付到用户设备，并在失败时保持原状；更新源、渠道、签名链、版本门禁、灰度与暂缓、离线更新与重启边界以本文为准。
- 插件分发：`.cpk` 的三类安装来源、插件市场与平台之间的协议契约（仅契约，市场服务端由社区实现）、插件更新与平台版本的兼容门禁以本文为准。
- 内置插件：安装产物内的内置插件布局（`builtin-plugins/` 与 `index.json`）、首启内置插件引导（校验、装载、启用、自检与修复）与首启引导边界以本文 §3.4、§3.5 为准。
- 本规范不提供任何插件可调用的更新接口：平台自动更新是平台组件行为，不属于能力总表（[04-能力契约规范](../05-接口与契约/04-能力契约规范.md) 明示"平台自动更新的插件接口"在范围外）。

平台更新实现归属主进程平台组件（更新器）；插件更新实现归属插件管理链路（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §6.2 蓝绿更新）；内置插件引导归属插件管理子系统与平台首启流程（§3.4、§3.5）。

交付阶段：插件分发链路（`.cpk` 安装/更新、签名与信任根）随 Phase 3 落地；平台更新器与市场协议契约随 Phase 4（"安全加固、代码签名与发布安全配置、v1.0 发布"）落地；`.cpk` 签名与信任根的实现阶段标注同时以[《插件包格式》](../04-文件格式规范/03-插件包格式.md) §6.3 为准，阶段口径依据[《开发流程与阶段计划》](../07-工程管理/02-开发流程与阶段计划.md) §六、§七。

### 1.3 术语

| 术语 | 定义 |
|---|---|
| 更新源（update source） | 按渠道提供平台更新索引与更新包的 HTTPS 服务端点；平台编译期固定。 |
| 渠道（channel） | 发布的终点与更新索引的命名空间：`stable`、`beta`（用户可切换），`rc`、`alpha`（内部验证）。 |
| 更新索引（update index） | 某渠道某平台架构下描述最新可更新版本的 JSON 文档（`chips-update-index-v1`）。 |
| 更新包（update package） | 平台安装产物（macOS `.zip`、Windows NSIS `.exe`、Linux AppImage）；更新索引指向的交付实体。 |
| 签名链（signature chain） | 更新包字节 → `sha256` → `contentHash` → Ed25519 签名 → `keyId` → 信任根注册表。 |
| 信任根（trust root） | 平台编译期内嵌的 `trust-roots.json`，登记官方发布公钥；与 `.cpk` 共用同一注册表。 |
| 防降级（anti-downgrade） | 只接受严格高于已安装版本的更新；相等为 no-op，更低确定性拒绝。 |
| 原子替换（atomic replace） | 新版本先完整暂存并校验，再以重命名/安装事务替换旧版本；失败保持旧版本可用。 |
| 灰度（staged rollout） | 更新索引声明发布百分比，客户端按稳定哈希决定本轮是否参与。 |
| 暂缓（hold） | 索引声明 `paused` 时，客户端暂停该渠道的自动更新，不改变已安装版本。 |
| 离线更新包 | 完整安装包；用户手动下载并经摘要与签名校验后按平台安装流程安装。 |
| 市场（market） | 社区实现或官方运营的插件分发服务；与平台之间只经本规范定义的协议契约交互。 |
| 重启边界（restart boundary） | 平台更新的生效需要应用重启；插件更新不需要（蓝绿替换）。 |
| `engines.chips` | 插件 manifest 声明的平台版本范围门禁字段。 |
| 安装包（installer package） | 平台安装产物（macOS `.dmg`、Windows NSIS `.exe`、Linux AppImage / `.deb`）；承载应用、信任根与内置插件包（§3.4）。 |
| 内置插件（builtin plugin） | 随平台安装产物分发的官方插件（`source: builtin`）：必须签名、不进入用户安装区、不可卸载、只能停用；引导规则见 §3.4、§3.5。 |
| 内置插件装载区 | 用户数据目录内由插件管理子系统管理的平台区域，按插件 ID 与版本归档内置插件解包后的文件；不是用户插件安装区。 |
| 首启内置插件引导 | 首次启动与平台版本变化后首次启动执行的内置插件校验、装载、启用与自检修复流程（§3.5）。 |

### 1.4 基本约束

1. 平台更新与插件更新是两条独立链路：平台更新不经过插件接口，插件更新不经过安装器（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §6.1、§6.2）。
2. 一切更新与安装产物必须先校验、后生效：摘要与签名校验不通过时不得进入暂存目录，更不得替换或安装。
3. 第一版发布前不做兼容性设计与回退机制（R7、[ADR-010](../01-架构设计/ADR/ADR-010-大爆炸重构策略.md)）：不提供旧版本回退安装，不保留旧接口加载路径（§四）。
4. 更新源只使用 HTTPS；不提供任何"跳过校验"开关；TLS 证书校验始终开启（[04-资源管理设计](../01-架构设计/01-子系统设计/04-资源管理设计.md) §8.3）。
5. 渠道是发布终点，不是校验捷径：任何渠道的产物都必须通过全部门禁与产物校验（[05-CICD与质量门禁](../06-开发与运维/05-CICD与质量门禁.md) §5.4）。
