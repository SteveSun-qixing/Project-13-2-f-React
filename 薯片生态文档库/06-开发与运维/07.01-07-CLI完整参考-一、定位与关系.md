## 一、定位与关系

### 1.1 两个入口

`chips` 是薯片平台唯一的正式命令行工具，由 `@chips/cli` 提供，随平台发行包安装并在系统 PATH 暴露 `chips`；生态 Monorepo 内统一用 `pnpm exec chips` 调用工作区内的同一版本（[01-快速开始](../03-插件开发/01-快速开始.md) §3.1、[01-代码组织规范](../02-开发规范/01-代码组织规范.md) §3.3）。

| 入口 | 受众 | 作用域 | 典型用途 |
|---|---|---|---|
| `chips <命令>` | 终端用户与运维脚本 | 用户工作区（默认 `${userDocuments}/Chips`，[13-工作区设计](../01-架构设计/01-子系统设计/13-工作区设计.md) §七） | 插件安装与启停、打开文件、平台更新、诊断、执行插件命令 |
| `chips dev <子命令>` | 插件开发者 | 开发工作区（默认 `${userData}/dev/workspace`） | 开发宿主运行、服务能力联调、开发工作区插件管理 |

两个入口共用同一可执行文件、同一命令索引、同一参数解析与同一错误模型；数据、插件记录、日志与 Electron 运行态严格隔离，互不可见（[13-工作区设计](../01-架构设计/01-子系统设计/13-工作区设计.md) §7.1）。用户侧命令经平台运行时承载链路执行（链路的传输、发现、握手与鉴权契约权威：[17-CLI承载链路契约](../05-接口与契约/17-CLI承载链路契约.md)）；开发侧命令由 CLI 自身执行或委托开发宿主（`@chips/host` 的 dev 模式）。

### 1.2 命令树

```text
chips
├── help [命令]                      # 帮助；也可在任意命令后追加 --help
├── （裸命令 / --interactive）        # 交互式 TUI
├── start | stop | status            # 工作区运行标记与状态
├── config list | set | reset        # 配置（用户层 / 工作区层）
├── logs                             # 日志导出与跟踪
├── plugin create | pack | validate | install | uninstall | list | info | enable | disable
├── open <路径>                      # 文件关联打开
├── update check | install           # 平台更新
├── doctor                           # 诊断
├── completion <bash|zsh|fish>       # shell 补全脚本
├── <插件命令路径> [参数] [选项]      # 已启用插件的 CLI 命令（§五）
└── dev
    ├── help | （裸命令 / --interactive）
    ├── run                          # 开发宿主运行当前插件工程
    ├── service invoke               # 在开发宿主中调用服务能力
    ├── start | stop | status | config | logs | plugin | open | doctor   # 开发工作区管理
    ├── completion <bash|zsh|fish>
    └── <插件命令路径> [参数] [选项]  # 开发工作区中的插件命令
```

### 1.3 与运行时命令系统的关系

运行时命令系统（命令记录、注册与发现、执行与结果、冲突与错误码）的唯一权威是 **[13-命令系统契约](../05-接口与契约/13-命令系统契约.md)**；CLI 命令入口是该系统的命令行侧消费入口，二者关系如下：

| 维度 | 运行时命令系统（13-命令系统契约） | CLI 命令入口（本文 §五） |
|---|---|---|
| 载体 | 菜单、托盘、工具栏、快捷键、命令面板与 CLI 执行器（13 §5.1） | `chips` 进程的命令行入口 |
| 记录 | 平台命令注册表中的命令记录（`ICommandDefinition` / `ICommandView`） | manifest `cli.commands[]` 入口声明 |
| 消费 | 各入口经 `command:list` / `command:invoke` | CLI 经 `cli.command.*` 发现 + `command:invoke` 派发 |
| 处理入口 | 应用实例的 `handleCommand(command, payload)` | 与运行时命令同一记录、同一处理入口 |
| 生命周期 | 随应用实例与会话自动清理（13 §3.5） | 入口声明随插件安装、启用、禁用、卸载派生 |

规则：

1. CLI 入口的 `commandId` 必须指向 [13-命令系统契约](../05-接口与契约/13-命令系统契约.md) 登记的命令记录；CLI 与 UI **共享同一记录、同一校验、同一审计**（13 §5.7）。
2. CLI 的 `app` 目标执行按 13 §4.4 的"启动并投递"：先按正式启动链路启动 owner 应用实例并等待目标命令注册，再以 `source: 'cli'` 调用 `command:invoke`；命令的唯一执行入口是 `handleCommand`，应用不得在 `launch` 中重复执行 CLI 命令。
3. CLI 侧不复刻 Scope、Conditions、放置（placement）、快捷键与命令事件模型；这些概念只属于运行时命令系统。CLI 入口之间的路径冲突与固定命令根保留规则由本文定义，不改变命令记录本身（13 §5.7、§7.1）。
4. CLI 入口另有派生标识 `entryId`（`<pluginId>.cli.<commandPath 点分>`，§5.1），只用于 CLI 命令索引、帮助与补全；它不进入运行时命令注册表，也不作为运行时命令的引用。

### 1.4 与 cli-command / cli-task 的关系

CLI 命令扩展由两个契约组成，二者都只在 CLI 语境生效：

| 契约 | 内容 | 权威位置 |
|---|---|---|
| `cli-command` | 插件 CLI 命令的声明、发现与解析：manifest `cli.commands`、平台服务路由 `cli.command.list` / `cli.command.get` / `cli.command.resolve`、SDK `client.cliCommand` | 本文 §五、§5.8 |
| `cli-task` | `app` 目标执行时的任务生命周期与进度上报：服务路由 `cli.task.create` / `bindInvocation` / `get` / `progress` / `complete` / `fail` / `cancel`、SDK `client.cliTask` | 本文 §5.7、§5.8 |

- `service` 目标是同步能力调用，不创建 `cli-task`；长耗时工作不得阻塞调用，由服务插件自行提供任务化能力（[01-Bridge-API规范](../05-接口与契约/01-Bridge-API规范.md) §3.2）。
- `cli-task` 只承载命令行任务的进度与终态，不是应用业务状态机；应用业务进度仍由应用自身管理。
- `cli.command.*` 只发现 **CLI 入口**，不替代运行时命令的 `command:list`；两者数据源独立：入口声明来自 manifest，命令记录来自运行时注册表。
- 命令发现索引是只读派生结果：插件安装、启用、禁用、卸载后自动重建，CLI 与补全不得缓存后自行推断（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §三、§4.3）。

### 1.5 边界与不提供的能力

- 工程任务（构建、测试、静态检查、E2E）走 pnpm 脚本，CLI 不提供替代实现；CLI 只提供插件产物命令（`plugin create/pack/validate`）与开发宿主命令。
- 不提供主题、多语言、组件库相关命令（R5 已废弃相关体系）。
- 不提供 MCP 入口、插件代码热挂载入口与绕过 Bridge 的直连入口。
- 不提供平台更新的插件接口：`update` 是用户侧平台自更新入口，插件更新独立于平台更新（[06-更新与分发规范](./06-更新与分发规范.md) UD-1）。
- 不提供"任意历史版本安装"入口：平台与插件均不做降级安装（[06-更新与分发规范](./06-更新与分发规范.md) §四）。
