# CI/CD 与质量门禁

> 版本：v1.0.1
> 日期：2026-09-23
> 状态：正式版
> 适用范围：薯片生态全部代码仓库的持续集成阶段划分、质量门禁判定、产物校验、发布自动化与门禁失败/豁免规则；门禁数值一律引用《架构原则》与《超大型工程管理体系》，本文只做引用、执行与判定。

## 二、CI 流程

### 2.1 五阶段模型

```
[1] 提交校验 ──▶ [2] 检查 ──▶ [3] 测试 ──▶ [4] 构建 ──▶ [5] 产物校验
      │              │             │             │              │
   分支/提交      静态门禁       测试门禁      发布形态产物    同源校验
   信息/任务    与安全门禁     与性能门禁      与打包        契约与摘要
      │              │             │             │              │
      └──────────────┴─────────────┴─────────────┴──────────────┘
                任一阶段失败 → 阻断合并 / 阻断发布
```

| 阶段       | 内容                                                                                         | 对应门禁           |
| ---------- | -------------------------------------------------------------------------------------------- | ------------------ |
| 1 提交校验 | 分支命名（`task-NNN-名称`、`hotfix-名称`）、提交信息类型与格式、PR 模板与任务关联            | 《Git 工作流规范》 |
| 2 检查     | Rust 格式与 Clippy、ESLint、Prettier、类型检查、依赖审计                                     | G1-G4、G9、G10     |
| 3 测试     | 单元、集成、契约测试、文档测试、E2E、覆盖率、解析器基准                                      | G5-G8              |
| 4 构建     | Rust release、`chips-native.node`、TS 包、Electron 三端产物、`.cpk`                          | —                  |
| 5 产物校验 | `.cpk` 同源校验、文档 `validate`、版本一致性、契约文档同步、文档门禁、生成工程门禁、摘要登记 | G8、G11、G12、G13  |

- 检查与测试阶段允许构建调试形态产物作为输入（契约测试需要 `chips-native.node`）；构建阶段的产物是发布形态产物。
- 阶段按顺序执行、失败即停；不允许用前一阶段的成功替代后一阶段的判定。

### 2.2 触发规则

| 触发                  | 流水线                       | 要求                                                     |
| --------------------- | ---------------------------- | -------------------------------------------------------- |
| PR → main             | 五阶段全量                   | 全部门禁通过才具备合并资格；未通过禁止合并               |
| push → main           | 五阶段全量                   | 作为主线健康基线；失败必须立即修复                       |
| tag `v*`（打在 main） | 五阶段全量 + 签名 + 渠道发布 | 产物校验通过才允许发布；流程见第五节                     |
| Hotfix 分支           | 五阶段全量                   | 与常规分支同等门禁，不降级（《Git 工作流规范》第十三节） |

- 平台级性能预算（冷启动、帧率、空闲内存）在 main 合并与 tag 流水线执行；解析器基准在 PR 执行（《06-文档解析器设计》9.5 节）。
- 同一分支新的推送取消该分支未完成的旧流水线；main 与 tag 的流水线不得取消。

### 2.3 流水线定义（示例）

以下 YAML 只描述阶段、命令与判定语义，不绑定托管平台；仓库工作流配置必须与之等价。

```yaml
# 薯片生态 CI 流水线（概念示意）
pipeline:
  triggers:
    pull_request: [main]
    push: [main]
    tag: ['v*']

  stages:
    - stage: 提交校验
      steps:
        - name: 提交信息
          run: pnpm exec commitlint --from origin/main --to HEAD
        - name: 分支命名
          run: |
            case "$CI_BRANCH" in
              main|task-[0-9][0-9][0-9]-*|hotfix-*) ;;
              *) echo "分支命名不符合规范"; exit 1 ;;
            esac

    - stage: 检查
      steps:
        - name: Rust 格式
          run: cargo fmt --all -- --check
        - name: Rust 静态检查
          run: cargo clippy --workspace --all-targets -- -D warnings
        - name: TypeScript 静态检查
          run: pnpm exec eslint . && pnpm exec prettier --check .
        - name: 类型检查
          run: pnpm typecheck
        - name: 依赖审计
          run: cargo audit && pnpm audit

    - stage: 测试
      steps:
        - name: Rust 测试
          run: cargo test --workspace && cargo test --workspace --doc
        - name: TypeScript 测试
          run: pnpm -r run test
        - name: 契约测试
          run: pnpm run test:contract
        - name: 覆盖率（TS vitest + Rust tarpaulin）
          run: pnpm run test:coverage
        - name: E2E（关键场景）
          run: pnpm exec playwright test tests/e2e
        - name: 解析器基准
          run: cargo bench -p chips-parser

    - stage: 构建
      steps:
        - name: Rust release 与 Neon 绑定
          run: cargo build --workspace --release
        - name: 平台包与插件构建
          run: pnpm -r run build
        - name: 安装包与 .cpk 打包
          run: pnpm -r run package

    - stage: 产物校验
      steps:
        - name: .cpk 校验
          run: pnpm exec chips plugin validate dist/<名称>-<版本>.cpk
        - name: 文档夹具校验
          run: cargo test -p chips-parser
        - name: 版本一致性
          checks:
            - 平台包版本一致（package.json 与 Cargo.toml workspace）
            - tag 与平台版本一致
            - 插件 package.json 与 manifest.yaml 一致（chips plugin validate 判定）
            - chip_standards_version 合法（文档 validate 判定）
        - name: 文档门禁
          run: pnpm run docs:check
        - name: 生成工程门禁
          run: pnpm run gates:generated-project
        - name: 产物摘要
          checks:
            - 计算并登记每个产物的 sha256
            - .cpk 安装摘要重打包一致（同一提交）
```

### 2.4 缓存与确定性

- 缓存只用于加速，不参与判定：Node 依赖缓存键为 `pnpm-lock.yaml`，Rust 缓存键为 `Cargo.lock`；缓存未命中必须回退全量执行。
- 同一提交在相同输入下，检查、测试与产物校验必须产生相同结论；`.cpk` 安装摘要必须稳定。
- 测试用例不得访问外部服务，外部依赖必须 Mock（《测试规范》第十二节）；只有依赖安装允许访问包源。

### 2.5 本地钩子与 CI 的关系

- `pre-commit`、`commit-msg`（《Git 工作流规范》第十四节）只提供快速反馈，不构成门禁。
- CI 是唯一权威判定；本机通过不得作为跳过 CI 或豁免失败的理由。
