# 服务端部署与运维

> 版本：v1.0.0
> 日期：2026-09-19
> 状态：正式版
> 适用范围：薯片生态服务端产品（社区平台服务器、个人服务器）的部署与运维权威规范：环境与拓扑、域名/HTTPS/证书/CSP/CORS、对象存储、容器化与进程管理、配置与密钥管理、备份恢复、日志监控、升级回滚、服务器连接与口令管理、故障清单与自检清单；不覆盖服务端产品的 API 契约、数据模型与业务模块实现。

## 五、容器化与进程管理

### 5.1 镜像与构建上下文

1. 服务端产品的镜像构建上下文是**生态工作区根目录**（Compose 中 `context: ../..`），因为服务镜像需要生态内其他仓库的构建产物（见下）。
2. 社区平台服务器服务镜像包含独立的生态工件构建阶段，构建并复制 Host 运行时、默认主题、基础卡片插件、布局插件与内容处理插件，然后才构建服务端产品自身；前端镜像（`web` / `admin`）独立构建。
3. 个人服务器服务镜像是自包含的：只安装服务端与前端，不包含生态工件，不做服务端渲染。
4. 生产镜像必须打版本标签并保留上一版本的镜像（回滚依赖，见 §9）；禁止以 `latest` 或未标记镜像定义生产发布。
5. 构建产物中的数据库迁移 SQL 与元数据必须随服务端构建一并复制进镜像（`copy-server-runtime-assets` 链路），保证容器内可直接执行迁移。

### 5.2 服务清单与依赖

| 服务 | 镜像来源 | 依赖 | 重启策略 |
|---|---|---|---|
| `postgres` | `postgres:16-alpine` | — | `unless-stopped` |
| `redis` | `redis:7-alpine` | — | `unless-stopped`（仅社区） |
| `minio` | `minio/minio` | — | 仅本地模式启动 |
| `server` | 服务镜像 | PostgreSQL、Redis 健康；桶可初始化 | `unless-stopped` |
| `worker` | 服务镜像（切换命令） | PostgreSQL、Redis 健康、`server` 已启动 | `unless-stopped`（仅社区） |
| `web` / `admin` | 前端镜像 | — | `unless-stopped` |
| `nginx` | `nginx:alpine` | `server`、`web`、`admin` | `unless-stopped` |

1. 基础设施容器必须配置健康检查（`pg_isready`、`redis-cli ping`、MinIO 健康端点），应用容器用 `depends_on.condition` 等待健康状态。
2. 所有容器加入同一内部 bridge 网络；不创建 host 网络容器。
3. 数据卷固定：PostgreSQL 数据卷、Redis 数据卷（社区）、MinIO 数据卷（本地）；生产数据卷必须位于持久磁盘并对齐备份策略（§7）。

### 5.3 端口边界

1. 生产只发布 `80` 与 `443`。
2. `postgres`、`redis`、`minio`、`server`、`worker` 一律不发布到公网；如需本机调试，主机端口必须绑定回环地址（`127.0.0.1:<port>:<port>`）。
3. 禁止通过主机防火墙"先放开再依赖认证"的方式暴露基础设施端口。

### 5.4 启动顺序与就绪判定

服务端产品启动顺序固定，容器内自动执行，不依赖人工步骤：

```text
API：数据库迁移 → 连接 Redis → 初始化对象存储桶 → 初始化管理员账号 → 监听端口
Worker：数据库迁移 → 连接 Redis → 初始化对象存储桶 → 初始化渲染集成 → 重新入队滞留任务 → 首次缓存清理 → 消费循环
```

1. 数据库迁移失败时进程不得监听端口；部署方以健康检查失败处理。
2. Worker 启动时把超过 30 分钟仍处于处理中的任务重新入队，避免单次崩溃造成任务永久滞留。
3. 就绪判定：
   - API：`curl -fsS https://<主站入口>/api/v1/health` 返回 `status: ok`；
   - Worker：容器运行中且日志出现消费循环启动信息；
   - 对象存储：公开桶 `HeadBucket` 与最小上传/下载验证通过。

### 5.5 渲染 Worker

1. Worker 无 HTTP 端口，**禁止**用端口探活；存活判定用容器状态 + 日志 + 队列积压。
2. 队列与状态：任务经 Redis 队列进入，在 PostgreSQL 任务表中锁定；成功后写入缓存记录，失败按最大尝试次数重试，超限置为失败并记录错误。
3. 关键参数（默认值）：并发 `CARD_RENDER_WORKER_CONCURRENCY=1`、最大尝试 `2`、队列阻塞超时 `5s`、缓存上传并发 `8`、缓存保留 `30` 天。
4. 提高并发前必须核对对象存储带宽与数据库连接数；渲染缓存目录上传并发与消费并发同时升高会争抢带宽。
5. Worker 与 API 必须使用**不同的**服务端集成工作目录，禁止共享（共享会导致启动时互相清理插件目录）。

### 5.6 容器项目命名与端口错开

1. 每个服务端产品的 Compose 文件必须声明唯一的顶层 `name`（如个人服务器固定 `cps`）。
2. 同机部署多个服务端产品时，主机端口类变量（`*_HOST_PORT`）必须显式错开，且不得与 Nginx 的 80/443 冲突。
3. 部署目录名不得作为唯一区分手段：项目名缺失时 Compose 默认使用目录名，两个都位于 `deploy/` 的项目会互相识别为同一项目并重建对方容器。

### 5.7 容器运行策略

1. 生产环境所有容器 `restart: unless-stopped`；不配置无限重启风暴保护以外的额外守护进程。
2. 应用容器必须以非特权方式运行在镜像自带用户下；不挂载 Docker Socket，不使用 `privileged`。
3. 容器内不安装运维工具，不进行现场修改；任何变更通过重新构建镜像完成。
4. 数据卷只挂载必要目录；证书与 Nginx 配置以只读方式挂载。

### 5.8 Nginx 配置管理

1. Nginx 配置与证书在部署目录内版本化维护（`deploy/nginx/`、`deploy/certs/`），不通过 `docker cp` 现场修改。
2. 每次修改配置后必须执行 `nginx -t`，通过后再 reload；校验与 reload 命令见 §3.2。
3. 配置模板中的域名、上游名称与证书路径必须与 Compose 服务名一致（`server`、`web`、`admin`）。
4. 修改反向代理规则后必须回归验证：静态资源缓存头、SPA HTML 不缓存、API 健康检查、上传大小限制。
