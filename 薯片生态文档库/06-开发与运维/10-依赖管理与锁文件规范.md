- 漏洞与许可证审计的判定与处置（第六节）；

### 1.3 基本口径

1. Node 生态唯一包管理器是 pnpm 9，Rust 生态唯一包管理器是 Cargo；禁止 npm、yarn 与任何第二包管理器混用（[01-开发环境配置](./01-开发环境配置.md) §7.1）。
2. 依赖安装只在仓库根执行；根清单是依赖图的唯一入口，子包目录不独立安装、不保留独立锁文件。
3. 每个生态只保留一份锁文件；锁文件是构建、CI 与发布的唯一安装快照。
4. 依赖变更必须经声明、锁定、审计、测试四步齐全后合并；缺失任一步视为缺陷（R16）。

## 二、依赖声明规则

### 2.1 声明形式总表

| 对象 | 唯一合法声明 | 示例 | 说明 |
|---|---|---|---|
| 内部 Node 包 | `workspace:*` | `"@chips/ui": "workspace:*"` | 由工作区解析为本地包；禁止写死版本号 |
| 内部 Rust crate | `path` 依赖 | `chips-core = { path = "../chips-core" }` | 仅限 workspace 成员之间 |
| 第三方 Node 包 | 精确版本 | `"yaml": "2.8.2"` | 不带 `^`、`~`、`*`、`latest` 与预发布后缀 |
| 第三方 Rust crate | `[workspace.dependencies]` 语义化区间 | `serde = { version = "1", features = ["derive"] }` | crate 内以 `workspace = true` 引用 |
| 平台提供物 | 构建外部化 | `react`、`react-dom`、`@chips/ui` | 由帧运行时提供，不进入随包依赖 |
| 平台构建产物 | 构建流程生成 | `chips-native.node` | 不入库、不作为依赖声明 |

### 2.2 工作区协议

- 内部包一律使用 `workspace:*`（pnpm）；禁止 `workspace:^`、`workspace:~` 与具体版本混写。
- 内部 Rust crate 一律使用 `path` 依赖；包名对应的版本字段由 `[workspace.package]` 统一提供，禁止在 crate 内单独声明版本。
- 禁止路径与链接依赖：`file:`、`link:`、`portal:`、绝对路径、`npm link`、`pnpm link`、把一方包源码复制或 vendor 进其他包（[01-代码组织规范](../02-开发规范/01-代码组织规范.md) §3.4、§4.3）。
- 禁止 git、URL、tarball 形式的依赖；第三方依赖只从 npm registry 与 crates.io 解析（镜像使用见 §5.4）。
- 一方工程新增或迁出时，必须同步更新 `pnpm-workspace.yaml` 与根 `Cargo.toml` 的成员清单（[01-代码组织规范](../02-开发规范/01-代码组织规范.md) §8.3）。

### 2.3 版本范围

- 第三方 Node 包声明精确版本；升级是显式动作，必须走 §3.3 流程。
- 第三方 Rust crate 在 `[workspace.dependencies]` 声明语义化区间（如 `"1.35"`、`"0.9"`）；禁止 `*`；精确解析结果由 `Cargo.lock` 承载（[04-Rust编码规范](../02-开发规范/04-Rust编码规范.md) §1.1）。
- 预发布版本（`-alpha.N`、`-beta.N`、`-rc.N`）只用于平台自身包与插件版本；第三方依赖不使用预发布版本，安全修复确需使用时必须在评估记录中写明依据。
- `optionalDependencies` 不得用于按平台或环境掩盖缺失依赖；平台差异由构建流程与能力探测承担。
- 内部包版本号由平台统一版本规则提供，不参与依赖声明（[01-代码组织规范](../02-开发规范/01-代码组织规范.md) §3.4）。

### 2.4 依赖类别

| 类别 | 用途 | 边界 |
|---|---|---|
| `dependencies` | 会被打包内联的纯 JS 运行时依赖 | 插件引用必须可被打包为单文件入口（R11） |
| `devDependencies` | 构建、测试、类型与工具依赖 | 不得被运行时代码引用 |
| `optionalDependencies` | — | 本生态不使用 |

- 同一包不得同时出现在 `dependencies` 与 `devDependencies`。
- 平台提供物（`react`、`react-dom`、`@chips/ui`）不得进入插件 `dependencies`；插件渲染入口必须按 [02-构建与打包](./02-构建与打包.md) §5.5 外部化。
- 原生模块与 Node-API 载荷禁止作为插件依赖（R11）；平台核心绑定 `chips-native.node` 由平台构建流程生成并随平台分发。
- 根清单只允许仓库级开发工具进入 `devDependencies`（如 ESLint、Prettier、TypeScript、commitlint）；禁止业务依赖与运行时依赖进入根清单。
- 依赖声明必须与实际使用一致：未使用的依赖必须移除；使用而未声明的依赖（含类型包与构建工具）必须补齐。

### 2.5 声明操作

```bash
# 新增/升级第三方 Node 依赖（先完成选型评估，见第七节）
pnpm --filter @chips/ui add <包名>@<精确版本>

# 新增/升级内部 Node 依赖
pnpm --filter @chips/host add @chips/bridge@workspace:*

# 移除
pnpm --filter @chips/ui remove <包名>
```

- 命令在仓库根执行；`--filter` 指定唯一目标包，禁止在子包目录执行 `pnpm add` / `pnpm install`。
- 依赖声明只改 `package.json` / `Cargo.toml`；锁文件由包管理器生成，禁止手工编辑（§3.1）。
- Cargo 第三方依赖只编辑 `[workspace.dependencies]`，crate 内引用声明 `workspace = true`；内部 `path` 依赖随 crate 划分变更同步更新。

## 三、锁文件策略

### 3.1 唯一快照

- 仓库根维护且只维护两个锁文件：`pnpm-lock.yaml` 与 `Cargo.lock`。
- 两个锁文件必须提交到版本库，禁止写入 `.gitignore`；禁止在子包目录保留第二份锁文件。
- 锁文件只由 pnpm 与 Cargo 生成；禁止手工编辑、禁止脚本拼装、禁止用删除重建代替正常更新。
- 锁文件变更必须与产生它的清单变更同 PR；锁文件中的每个变更条目都必须能追溯到本次变更意图。
- 历史仓库存量锁文件在迁移时移入就近 `归档/`，不得复制进新仓库作为安装依据。

### 3.2 冻结安装

| 场景 | 命令 | 语义 |
|---|---|---|
| 本地安装 | `pnpm install` | 允许按清单更新锁文件 |
| 本地校验 | `pnpm install --frozen-lockfile` | 清单与锁文件不一致时报错 |
| CI 安装 | `pnpm install --frozen-lockfile` | 唯一安装方式；禁止 `--no-frozen-lockfile` |
| CI Rust 构建与检查 | `cargo build --locked`、`cargo test --locked`、`cargo clippy --locked` | 锁文件漂移时报错 |
| CI 依赖图与审计 | `cargo metadata --locked` | 依赖图检查与许可证元数据提取 |

- 冻结安装失败即判定清单与锁文件未同步，必须回本地执行 `pnpm install` / `cargo update` 后提交锁文件，不得在 CI 放宽冻结。
- 锁文件完整性不得关闭：pnpm 的 integrity 哈希与 Cargo 的 checksum 校验必须开启；禁止 `--no-verify-store-integrity`、`--ignore-checksums` 等绕过方式。

### 3.3 升级流程

常规升级（有计划）：

1. 评估：新增依赖按第七节完成评估；存量依赖升级核对变更日志、许可证与 MSRV 兼容。
2. 单包升级：

```bash
# Node：升级到指定精确版本
pnpm --filter @chips/ui add <包名>@<精确版本>

# Rust：升级到指定版本
cargo update -p <crate> --precise <版本>
```

3. 依赖图检查：`pnpm why <包名>` / `cargo tree -i <crate>` 确认影响面与重复版本。
4. 本地验证：`pnpm install --frozen-lockfile`、`pnpm lint`、`pnpm typecheck`、`pnpm test`、`pnpm build`，范围与改动匹配。
5. 同 PR 提交清单与锁文件；PR 描述写明升级原因、版本差与验证结论。

批量升级：

- 在定期统一窗口执行；禁止在功能 PR 顺带批量升级依赖。
- 破坏性升级（semver major）按 [03-变更与决策管理](../07-工程管理/03-变更与决策管理.md) 分级：影响基础架构、长期运行时依赖或公共协议的走 RFC → 评审 → ADR。

安全修复：

- 允许针对单个受影响包优先升级，附带 CVE/GHSA 编号与影响面结论。
- 无可用修复版本时按第六节处置，并登记技术债务清单。

工具链联动：

- pnpm 主版本或 `lockfileVersion` 变更、Rust 工具链升级，必须同步更新 workspace 清单、CI 工作流与 [01-开发环境配置](./01-开发环境配置.md) §2.2 三处后整体重装。

### 3.4 CI 校验

CI 在检查阶段对依赖执行以下校验：

```bash
pnpm install --frozen-lockfile             # 冻结安装
pnpm dedupe                                # 收敛可收敛的重复解析
git diff --exit-code pnpm-lock.yaml        # 锁文件必须无差异
cargo build --locked                       # Rust 锁文件冻结
cargo tree -d                              # 重复版本检查
pnpm audit --prod --audit-level high       # Node 运行时漏洞审计
cargo audit                                # Rust 漏洞审计
```

- 判定：任一命令失败即阻断合并，处理与豁免按 [05-CICD与质量门禁](./05-CICD与质量门禁.md) 第六节；禁止在 CI 中修改锁文件。
- 重复解析、重复版本与审计结果纳入 G9 架构红线与 G10 依赖安全的判定范围（[05-CICD与质量门禁](./05-CICD与质量门禁.md) §3.5）。
- CI 缓存键固定为 `pnpm-lock.yaml` 与 `Cargo.lock`；缓存未命中必须回退全量安装（[02-构建与打包](./02-构建与打包.md) §8.1）。

## 四、重复依赖与体积治理

### 4.1 重复依赖判定与收敛

Node：

- 定位：`pnpm why <包名>` 查看引入链与实例数。
- 收敛：`pnpm dedupe` 在兼容范围内统一为单一版本。
- 判定：收敛后 `pnpm-lock.yaml` 必须无差异；仍存在重复时逐条评估——同一主版本可安全收敛的必须收敛，跨主版本共存必须记录原因、影响与消除计划。
- React 与 `@chips/ui` 是单实例红线：帧内只允许一份 React 实例，插件构建必须外部化，出现内联副本即缺陷（[02-构建与打包](./02-构建与打包.md) §5.4、R4）。

Rust：

- 定位：`cargo tree -d` 列出重复 crate。
- 收敛：版本与 features 统一在 `[workspace.dependencies]` 声明；`resolver = "2"`；禁止同一 crate 的多个版本长期共存。
- 上游依赖锁定不同主版本而无法收敛时，必须登记技术债务清单，并在依赖升级时优先消除。

### 4.2 体积治理

- 限额引用：`.cpk` 文件与解包总量 50 MiB、单文件 16 MiB、入口 8 MiB 等以 [03-插件包格式](../04-文件格式规范/03-插件包格式.md) 第四章为唯一权威；入口校验以 [02-构建与打包](./02-构建与打包.md) §5.6 为准。
- 新增运行时依赖必须在评估中给出打包增量估算，并判断与限额的余量；判断不通过的不得引入。
- 构建产物大小纳入发布前产物校验；超限即阻断发布，不得放宽限额。
- 减小体积的合法手段：按需导入（禁止整库 barrel 导入）、tree-shaking、把渲染依赖限制在渲染入口、资源拆分与懒加载（首屏不受影响）。
- 重复打包防线：`dist/index.js` 必须完全自包含且无模块引用；`render.js` 只允许平台 vendor URL；入口校验脚本不通过不得打包（[02-构建与打包](./02-构建与打包.md) §5.6）。
- 体积治理不得引入额外的压缩或打包工具链；构建链以 [02-构建与打包](./02-构建与打包.md) 为准。

### 4.3 清理

- 未使用依赖与废弃包由发现方在同一 PR 移除清单与锁文件，不保留"以后可能用"的依赖。
- 移除后执行冻结安装与全量门禁，确认类型、测试与构建脚本不存在隐式引用。

## 五、Cargo 与 pnpm 双生态

### 5.1 职责边界

- pnpm 管理 TypeScript/JavaScript 工作区：`packages/*`、`plugins/*`、`tools/*`、`examples/plugins/*`。
- Cargo 管理 Rust workspace：`packages/core-rust/crates/*`，产物为 `chips-native.node`。
- 双生态不交叉声明：Rust 不依赖 npm 包；TS 不把 `chips-native.node` 声明为依赖，绑定由构建流程复制（[02-构建与打包](./02-构建与打包.md) §4.3）。
- 平台统一版本由根 `package.json` 与 `Cargo.toml` 的 `[workspace.package] version` 共同承载，两者必须一致，由 CI 版本一致性校验判定（[05-CICD与质量门禁](./05-CICD与质量门禁.md) §2.3）。

### 5.2 第三方 crate 集中登记

- 所有第三方 crate 只在 `[workspace.dependencies]` 声明一次；crate 内使用 `workspace = true`。
- features 在登记处声明，禁止 crate 内分叉 features；需要条件启用时用 crate 自身 `[features]` 组合，不引入第二版本。
- `rust-version`（MSRV）与 `edition` 由 `[workspace.package]` 统一；升级依赖不得突破 MSRV。
- `[profile.*]` 只在 workspace 根声明（[02-构建与打包](./02-构建与打包.md) §4.1）。

### 5.3 双生态锁定

- 同一提交必须同时提供两个锁文件；缺少任一个视为依赖变更不完整。
- 构建与测试必须使用 `--locked`；发布构建必须能在冷缓存环境用锁文件复现。
- 依赖安装是唯一允许访问外部网络的构建环节；构建、测试与产物校验不得访问外部服务（[05-CICD与质量门禁](./05-CICD与质量门禁.md) §2.4）。

### 5.4 镜像与代理

- 默认来源为 npm registry 与 crates.io。
- 镜像配置只作用于本机用户配置与环境变量，不得写入仓库文件；镜像导致的锁文件差异不得提交（[01-开发环境配置](./01-开发环境配置.md) §6.3）。
- 代理必须同时覆盖 pnpm、Cargo 与 Git，避免部分流量直连造成来源不一致。

### 5.5 Neon 绑定与原生载荷

- `chips-native.node` 由平台构建流程生成并随平台分发；不执行 `electron-rebuild`，Electron 打包配置固定 `npmRebuild: false`（[02-构建与打包](./02-构建与打包.md) §4.2）。
- 插件不得声明原生依赖、不得携带原生载荷；需要系统能力时经 Bridge 申请（R11、R17）。

## 六、漏洞与许可证审计

### 6.1 审计命令与频率

```bash
pnpm audit --prod --audit-level high          # Node 运行时依赖漏洞
cargo audit                                   # Rust 依赖漏洞
pnpm licenses list --prod --json              # Node 许可证清单
cargo metadata --locked --format-version 1    # Rust 依赖与许可证元数据
```

- 频率：每个 PR 的检查阶段执行漏洞审计；main 合并与 tag 流水线重复执行；许可证清单在同一阶段校验。
- Dependabot 等自动升级提案必须走 §3.3 流程，不得直接合并自动生成的锁文件变更。

### 6.2 漏洞判定

- 合并门禁：`cargo audit` 与 `pnpm audit` 无已知高危漏洞（G10）。
- 中低危漏洞必须登记技术债务清单并给出处置版本与时点；到期未处理按门禁失败处理。
- 无修复版本时的处置：升级替代包、移除功能或经 RFC 变更方案；禁止长期挂账。
- 审计结论写入 PR；豁免按 [05-CICD与质量门禁](./05-CICD与质量门禁.md) 第六节登记，禁止无痕豁免。

### 6.3 许可证判定

运行时依赖与随包内联依赖使用同一清单：

| 结论 | 许可证 |
|---|---|
| 允许 | MIT、Apache-2.0、BSD-2-Clause、BSD-3-Clause、ISC、0BSD、Unlicense、CC0-1.0 |
| 逐一评估 | MPL-2.0 等弱 copyleft；评估其文件级义务不影响平台再分发后方可引入 |
| 默认禁止 | GPL、LGPL、AGPL、SSPL、BSL 及任何与平台分发不兼容或无法确认的许可证；确需引入走 RFC 并经用户确认 |

- 依赖必须提供可识别的许可证标识（`license` 或 `license-file`）；缺失即禁止引入。
- 平台核心 Rust crate 的发布许可固定为 `MIT OR Apache-2.0`（`[workspace.package] license`），第三方 crate 许可证不得与之冲突。
- 第三方参考资产的许可随附（版权声明、`NOTICE`、附加许可目录）按 [11-第三方参考资产清单](../02-开发规范/11-第三方参考资产清单.md) 执行。
- 许可证清单纳入 CI 输出并归档；新增依赖的许可证结论必须在评估记录与 PR 中写明。

### 6.4 供应链完整性

- 锁文件完整性校验必须开启（§3.2），禁止任何绕过方式。
- 依赖来源只允许 npm registry 与 crates.io（§5.4）。
- 依赖的安装生命周期脚本（postinstall 等）必须在评估中说明用途与风险。
- `.cpk` 安装侧的签名与信任根校验以 [03-插件包格式](../04-文件格式规范/03-插件包格式.md) 第六章为准，插件依赖不得绕开平台签名链。

## 七、引入第三方库评估流程衔接

### 7.1 分工

- 评估标准本体（用途、许可证、维护状态、包体影响、安全风险、跨端兼容性）与关键依赖确认以 [架构原则](../00-愿景与原则/01-架构原则.md) §3.1 为唯一权威。
- 第三方参考资产（源码快照、移植、素材）的引入、处置与登记以 [11-第三方参考资产清单](../02-开发规范/11-第三方参考资产清单.md) 为准。
- 本文负责评估通过之后的落地约束：声明、锁定、审计、体积与清理，与第二至六节配合执行。

### 7.2 落地步骤

1. 必要性判定：现有平台能力、内部包或标准库能实现的不引入第三方库。
2. 评估执行：按 [架构原则](../00-愿景与原则/01-架构原则.md) §3.1 六项逐项给出结论；许可证不明或安全风险无法收口的直接拒绝。
3. 分级决策：改变基础架构、成为长期运行时依赖或影响公共协议的，先记录方案等待确认，并走 RFC → 评审 → ADR（[03-变更与决策管理](../07-工程管理/03-变更与决策管理.md)）。
4. 声明落地：按 §2.1 选择声明形式；第三方 Node 包精确版本，第三方 crate 进 `[workspace.dependencies]`。
5. 锁定与审计：同 PR 更新锁文件；通过 §3.4 的 CI 校验与第六节审计。
6. 体积确认：给出打包增量估算与限额余量结论（§4.2）。
7. 记录归档：评估结论与引入理由写入 PR；许可证与审计结果随流水线归档。
8. 淘汰复查：依赖不再使用或被更优方案替代时，于同一 PR 移除声明、锁文件条目与相关配置。

### 7.3 禁止情形

- 未完成六项评估即引入（红线 17）。
- 以"临时引入""后续替换"为由引入未评估依赖。
- 评估记录缺失、许可证不明或漏洞未处置即合并。
- 通过包别名、重复包名或私有 fork 绕过评估与审计。

## 八、约束与自检清单

### 8.1 强制规则

1. 唯一包管理器：pnpm 9（Node）与 Cargo（Rust）；禁止 npm、yarn 混用。
2. 内部依赖只用 `workspace:*`（pnpm）与 `path`（Rust workspace 成员）；禁止 `file:`、`link:`、`portal:`、`npm link`、路径依赖与源码复制。
3. 第三方 Node 依赖精确版本；第三方 Rust crate 只登记在 `[workspace.dependencies]` 并使用语义化区间。
4. 平台提供物不进入随包依赖；插件构建必须外部化 React 与 `@chips/ui`。
5. 依赖安装只在仓库根执行；子包不保留独立锁文件。
6. `pnpm-lock.yaml` 与 `Cargo.lock` 必须提交、禁止手工编辑、必须与清单变更同 PR。
7. CI 一律 `pnpm install --frozen-lockfile` 与 `cargo --locked`；禁止在 CI 修改锁文件。
8. 升级必须单包、可追溯、带验证；禁止在功能 PR 混入无关依赖变更。
9. 重复依赖必须用 `pnpm why` / `cargo tree -d` 核查并收敛；React 与 `@chips/ui` 保持单实例。
10. 新增运行时依赖必须给出体积影响结论；入口与包体限额不得放宽。
11. 漏洞审计无高危、许可证在允许清单内，是合并门禁的一部分。
12. 第三方引入必须完成六项评估并留痕；关键依赖必须走 RFC → 评审 → ADR。
13. 依赖来源只允许 npm registry 与 crates.io；镜像只作用于本机，不得改变提交的锁文件。
14. 未使用依赖必须移除，使用而未声明的依赖必须补齐。
15. 依赖变更必须同 PR 更新受影响文档（R16）。

### 8.2 自检清单

- [ ] 内部依赖均使用 `workspace:*` 或 `path`，无 `file:`、`link:`、路径依赖与源码复制
- [ ] 第三方 Node 依赖为精确版本；第三方 crate 集中在 `[workspace.dependencies]`
- [ ] 插件未把 React、`@chips/ui`、`@chips/sdk` 或原生载荷写入随包依赖
- [ ] 依赖变更命令在仓库根执行，无子包安装与子包锁文件
- [ ] `pnpm-lock.yaml` 与 `Cargo.lock` 已随清单变更同 PR 更新，无手工编辑
- [ ] 本地 `pnpm install --frozen-lockfile` 与 `cargo build --locked` 通过
- [ ] `pnpm dedupe` 后锁文件无差异；`cargo tree -d` 无未记录重复版本
- [ ] `pnpm audit --prod --audit-level high` 与 `cargo audit` 无高危
- [ ] 许可证清单对照允许清单全部通过，无缺失许可证字段的依赖
- [ ] 新增依赖的评估记录与体积影响结论已写入 PR
- [ ] 未使用依赖已移除，锁文件同步收敛
- [ ] 受影响文档已同步更新

|---|---|

| 依赖变更文档同步 | G12 |
