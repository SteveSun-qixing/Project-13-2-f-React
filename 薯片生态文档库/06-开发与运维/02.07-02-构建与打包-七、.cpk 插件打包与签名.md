## 七、`.cpk` 插件打包与签名

包内归档结构、包根白名单、体积限额、安装校验流程与错误码以[03-插件包格式](../04-文件格式规范/03-插件包格式.md)为唯一权威；本节定义构建侧如何产出合规输入、如何打包与签名。

### 7.1 打包前置条件

插件源码目录（以 `examples/plugins/hello-basecard/` 为例，`dist/` 与 `render.js` 为构建产物）：

```text
plugins/hello-basecard/
├── manifest.yaml
├── package.json
├── tsconfig.json
├── vite.main.config.ts
├── vite.render.config.ts
├── vite.shared.ts
├── src/
│   ├── main.ts              # 主进程纯函数 → dist/index.js
│   ├── render.tsx           # 渲染方法 → render.js
│   └── index.ts             # 拆分导出（非构建入口）
├── assets/
│   └── icons/
│       └── hello.svg
├── dist/                    # 构建产物：index.js 与打包输出的 .cpk（不入库）
└── render.js                # 构建产物（不入库）
```

打包前必须同时满足：

1. `manifest.yaml` 的 `version` 与 `package.json` 的 `version` 完全一致（由 CLI 强校验，不一致返回 `CPK_MANIFEST_INVALID`）。
2. `dist/index.js` 与角色要求的 `render.js` 存在、为 UTF-8 文本 ESM，并通过 5.6 的入口校验。
3. 包内不出现 `node_modules/`、源码、测试文件、sourcemap、锁文件与原生载荷（[03-插件包格式](../04-文件格式规范/03-插件包格式.md) §2.1、§4）。
4. manifest 内所有文件引用为包内相对路径且目标位于 `assets/`（[03-插件包格式](../04-文件格式规范/03-插件包格式.md) §2.6）。
5. `render.js` 不自行拼接作用域 URI，资源经平台解析为 `chips-resource://<plugin-scope>/assets/...`。

### 7.2 打包与校验命令

```bash
# 标准链路：构建 → 打包 → 与安装同源校验
pnpm --filter @chips/plugin-hello-basecard run build
pnpm --filter @chips/plugin-hello-basecard run package
pnpm --filter @chips/plugin-hello-basecard exec chips plugin validate dist/hello-basecard-1.0.0.cpk

# 在插件目录内直接调用（CLI 从当前目录收集 manifest.yaml、dist/、render.js、assets/）
pnpm exec chips plugin pack --out dist/
pnpm exec chips plugin validate dist/hello-basecard-1.0.0.cpk

# 归档检查：全部成员必须为 Stored
unzip -v dist/hello-basecard-1.0.0.cpk

# 确定性验证：连续两次打包摘要必须一致
shasum -a 256 dist/hello-basecard-1.0.0.cpk
```

不使用 CLI 的手工等价打包（第三方工具链必须遵守同样约束，[03-插件包格式](../04-文件格式规范/03-插件包格式.md) §7.2）：

```bash
cd <构建暂存目录>
zip -r -0 -X ../dist/<名称>-<版本>.cpk . -x '.*' -x '*/.*'
```

规则：

- `.cpk` 输出到插件 `dist/`，命名固定 `<名称>-<版本>.cpk`；`.cpk` 不进入版本库。
- `validate` 与安装校验同源，必须通过后才可签名与分发。
- 校验失败按[03-插件包格式](../04-文件格式规范/03-插件包格式.md) §8 的错误码定位；不得跳过校验直接手工修复归档。

### 7.3 签名与信任根

签名文件、`contentHash` 构造规则与来源渠道校验语义已在[03-插件包格式](../04-文件格式规范/03-插件包格式.md) §6 冻结；本节定义密钥生命周期与发布链路。

密钥生成（Ed25519）：

```bash
# 私钥（PKCS#8 PEM，只进入发布密钥库）
openssl genpkey -algorithm ED25519 -out chips-official-2026.pem

# 公钥（登记进信任根注册表）
openssl pkey -in chips-official-2026.pem -pubout -out chips-official-2026.pub.pem

# 提取 32 字节原始公钥并 Base64 编码（写入信任根注册表）
openssl pkey -pubin -in chips-official-2026.pub.pem -outform DER | tail -c 32 | base64
```

签名打包（私钥经文件路径注入，禁止出现在命令行参数、环境变量明文与日志中）：

```bash
CHIPS_SIGNING_KEY_FILE=/run/secrets/chips-official-2026.pem \
  pnpm exec chips plugin pack --out dist/ \
    --sign --key-id chips-official-2026
```

信任根注册表由平台编译期内嵌，位于 `packages/host-electron/resources/trust-roots.json`：

```json
{
  "format": "chips-trust-roots-v1",
  "keys": [
    {
      "keyId": "chips-official-2026",
      "algorithm": "ed25519",
      "publicKey": "<32 字节公钥的 Base64>",
      "source": "builtin"
    }
  ]
}
```

渠道与签名要求（完整语义见[03-插件包格式](../04-文件格式规范/03-插件包格式.md) §6.3）：

| 来源渠道 | 签名要求 | 缺失时 | 无效时 |
|---|---|---|---|
| `builtin` | 必须签名 | `CPK_SIGNATURE_REQUIRED`，拒绝安装 | `CPK_SIGNATURE_INVALID`，拒绝安装 |
| `user` | 可选 | 安装界面展示“未签名发布者”，用户确认后继续 | `CPK_SIGNATURE_INVALID`，拒绝安装 |
| `development` | 不检查 | 不检查 | 不检查 |

`user` 渠道的第三方发布者公钥由用户在平台信任管理中登记；未登记的 `keyId` 一律视为签名无效。

密钥生命周期：

| 阶段 | 规则 |
|---|---|
| 生成 | 每个发布主体、每个用途一把密钥；私钥只在密钥库生成，不得导出到个人设备 |
| 登记 | 公钥以 `keyId` 写入信任根注册表并随平台版本发布；`keyId` 全局唯一，不得复用 |
| 使用 | 仅发布流水线可读取私钥；本地与开发构建一律不签名 |
| 轮换 | 新增 `keyId` 并保留旧公钥，旧包签名继续有效；禁止用新密钥覆盖旧 `keyId` |
| 撤销 | 从信任根移除 `keyId` 即撤销；走变更流程并在发布说明中公告 |

### 7.4 发布规则

- 签名后的 `.cpk` 不得修改任何字节；任何内容变化必须重新构建、重新打包、重新签名。
- 发布时必须记录：安装摘要（`sha256:` + 文件字节摘要）、包内 `contentHash`、`keyId`；记录随发布说明归档。
- `builtin` 渠道强制签名；未签名包不得静默安装，必须产生可见提示与用户确认记录。
- 签名有效不得作为跳过归档、结构、清单与载荷校验的理由（[03-插件包格式](../04-文件格式规范/03-插件包格式.md) §6.3）。
- 插件源码与 `.cpk` 分开产出：源码随仓库版本控制，`.cpk` 作为发布制品进入分发渠道。
