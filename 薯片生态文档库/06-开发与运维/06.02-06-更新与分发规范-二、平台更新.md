## 二、平台更新

### 2.1 更新源与渠道

更新源在平台编译期固定为按渠道分根的 HTTPS 端点，客户端不从配置或用户输入接受任意 URL：

```
<update-root>/
├── stable/
│   ├── mac-arm64/index.json
│   ├── mac-x64/index.json
│   ├── win-x64/index.json
│   ├── win-arm64/index.json
│   └── linux-x64/index.json
├── beta/                     # 结构同 stable
├── rc/                       # 内部验证；不进入公开更新源
└── alpha/                    # 内部验证；不进入公开更新源
```

| 渠道 | 更新源 | 用户可选 | 版本形态 | 依据 |
|---|---|---|---|---|
| `stable` | 正式更新源 | 是（默认） | `MAJOR.MINOR.PATCH` | [05-CICD与质量门禁](../06-开发与运维/05-CICD与质量门禁.md) §5.4 |
| `beta` | 公测更新源 | 是（显式切换） | `-beta.N` | 同上 |
| `rc` | 候选验证源 | 否（仅候选验证分发） | `-rc.N` | 同上 |
| `alpha` | 内部验证源 | 否（仅内部构建） | `-alpha.N` | 同上 |

规则：

1. 用户可见的更新通道由平台策略键 `platform.update.channel` 决定，取值 `stable` / `beta`，默认 `stable`；该键只在平台层文件有效（`x-chips-policy: true`），只由用户在设置界面修改（[10-配置系统设计](../01-架构设计/01-子系统设计/10-配置系统设计.md) §2.3、§4.2）。
2. 预发布版本只进入对应预发布渠道，不进入 `stable`；`stable` 索引不得包含任何预发布标识（[04-版本与迁移规范](../04-文件格式规范/04-版本与迁移规范.md) §3.1）。
3. `rc` / `alpha` 产物不进入公开更新源：由内部验证流程以离线更新包（§2.6）或候选验证分发安装，验证结论回写发布记录。
4. 切换通道只影响后续更新检查，不触发"降级到该通道最新版本"：目标版本仍必须严格高于已安装版本（§2.3）。
5. 更新检查频率：启动后延迟 30s 首次检查，此后每 6 小时一次；用户可手动触发检查；单次检查与下载都不得阻塞应用启动与文档操作。

### 2.2 更新包格式与签名链

更新索引 `<update-root>/<channel>/<platform>-<arch>/index.json`：

```json
{
  "format": "chips-update-index-v1",
  "channel": "stable",
  "platform": "mac",
  "arch": "arm64",
  "version": "1.0.1",
  "published_at": "2026-09-19T02:11:04.000Z",
  "paused": false,
  "rollout": { "percent": 100, "seed": "2026-09-19-stable-1" },
  "package": {
    "name": "Chips-1.0.1-mac-arm64.zip",
    "url": "https://<update-host>/stable/mac-arm64/packages/Chips-1.0.1-mac-arm64.zip",
    "size": 148529432,
    "sha256": "6f1c9b0e72d5a441e08c6a7b4c2d9f0e7a5b3c1d8e6f4a2b0c9d7e5f3a1b8c6d"
  },
  "signature": {
    "format": "chips-signature-v1",
    "keyId": "chips-official-2026",
    "algorithm": "ed25519",
    "contentHash": "sha256:6f1c9b0e72d5a441e08c6a7b4c2d9f0e7a5b3c1d8e6f4a2b0c9d7e5f3a1b8c6d",
    "signature": "<Base64（对 contentHash 的 UTF-8 字节签名）>"
  },
  "notes_url": "https://<update-host>/releases/1.0.1"
}
```

| 字段 | 必需 | 说明 |
|---|---|---|
| `format` | 是 | 固定 `chips-update-index-v1`；不匹配即视为响应非法 |
| `channel` / `platform` / `arch` | 是 | 必须与请求的渠道、平台、架构一致；不一致视为响应非法 |
| `version` | 是 | 语义化版本；比较规则见 §2.3 |
| `published_at` | 是 | 发布时刻 RFC 3339 UTC |
| `paused` | 是 | `true` 表示该渠道暂缓自动更新（§2.5） |
| `rollout.percent` | 是 | 0–100；100 表示全量 |
| `rollout.seed` | 是 | 灰度种子；与设备稳定标识计算是否命中（§2.5） |
| `package.name` / `url` / `size` / `sha256` | 是 | 更新包文件名、HTTPS 地址、字节数、字节摘要（小写十六进制，无前缀） |
| `signature` | 是 | 与 `.cpk` 同构的签名块（[03-插件包格式](../04-文件格式规范/03-插件包格式.md) §6.1） |
| `notes_url` | 否 | 发布说明地址；展示用，不参与校验 |

签名链与校验规则：

1. `contentHash` = `sha256:` + 更新包**文件字节**的 SHA-256（小写十六进制）；与 `.cpk` 的 `contentHash` 构造不同，仅此一处差异，其余字段与语义完全一致。
2. 签名是对 `contentHash` 的 UTF-8 字节做 Ed25519 签名（Base64），与 `.cpk` 签名体系一致（[02-构建与打包](../06-开发与运维/02-构建与打包.md) §7.3）。
3. 客户端**必须从实际下载的字节重算** `sha256` 与 `contentHash`，不得信任索引字段作为签名输入；重算结果与签名块校验不一致时拒绝该更新包。
4. `keyId` 必须在平台编译期内嵌的信任根注册表中登记（`packages/host/resources/trust-roots.json`）；未登记的 `keyId` 视为签名无效。
5. 签名校验不替代平台代码签名与公证：macOS 产物必须通过 Developer ID 签名与公证校验（`codesign` / `spctl` / `stapler`），Windows 产物必须通过 Authenticode 与时间戳校验（`signtool verify /pa`）（[02-构建与打包](../06-开发与运维/02-构建与打包.md) §6.4）。
6. 更新索引只用于发现与展示；任何索引字段（名称、大小、说明、`paused` 除外）都不能替代对更新包的独立校验。
7. 密钥生命周期（生成、登记、使用、轮换、撤销）与 `.cpk` 共用同一套规则（[02-构建与打包](../06-开发与运维/02-构建与打包.md) §7.3）；轮换新增 `keyId` 并保留旧公钥，撤销从信任根移除并公告。

### 2.3 版本比较与防降级

1. 版本比较按[《版本与迁移规范》](../04-文件格式规范/04-版本与迁移规范.md) §3.2 的语义化版本优先级执行。
2. 判定矩阵：

| 索引版本 vs 已安装版本 | 判定 | 动作 |
|---|---|---|
| 更高（含正式版本高于预发布、预发布序号更高） | 可更新 | 进入灰度判定与下载流程 |
| 相等 | no-op | 不下载、不提示；记录检查时间 |
| 更低 | 降级 | 确定性拒绝并记录诊断；提示"当前版本高于该通道最新版本"（切换通道后的常见结果） |
| 索引版本低于平台支持的最低可升级版本 | 不适用 | 该索引不参与更新；提示重新安装最新版本 |

3. 防降级是刚性规则：任何渠道、任何来源（索引、离线包、命令行参数）都不得安装低于已安装版本的平台版本。
4. 预发布通道（`beta`）中可以出现"预发布版本高于已安装正式版本"的更新；切回 `stable` 后若正式版本低于已安装的预发布版本，按"更低"拒绝，等待正式版本号追平。
5. 版本比较使用版本核心三段数字与预发布标识，构建元数据不参与比较。

### 2.4 原子替换与失败恢复

```
[1] 检查与判定（§2.3）
        ▼
[2] 下载到 <userData>/updates/staging/<版本>/（临时目录）
        │ 失败 → 删除临时目录，保留旧版本，记录诊断
        ▼
[3] 校验：大小、sha256、contentHash、Ed25519 签名、keyId 信任根、平台代码签名
        │ 任一失败 → 更新包标记 invalid 并删除，暂停该版本的本次更新，提示用户
        ▼
[4] 暂存完成，向用户提示"更新已就绪，将在重启后完成"
        │ 用户选择"立即重启"或"退出时安装"
        ▼
[5] 收敛运行态：编辑会话 flush → 文档会话释放 → 同步会话中止 → 插件调用静默 → 应用退出
        ▼
[6] 替换（按平台）：macOS 替换 .app 包；Windows 运行 NSIS 静默升级；Linux 替换 AppImage
        │ 失败 → 恢复更新前状态，标记该版本 apply-failed，提示用户
        ▼
[7] 新版本首次启动自检：版本一致、核心与渲染进程可用、插件注册表加载成功
        │ 失败（连续 2 次）→ 恢复更新前状态，标记该版本 boot-failed，暂停该渠道自动更新并提示
        ▼
[8] 自检通过：清理暂存目录与上一版本备份，更新记录写入审计
```

规则：

1. **原子性**：步骤 [6] 是替换事务，任一失败必须回到更新前状态；"新版本首次启动自检通过"之前，更新不算完成。
2. **失败恢复与"版本回退"的区别**：失败恢复是"更新未完成、回到更新前状态"，不是版本回退功能；平台不提供用户主动降级安装（§四）。
3. **防循环**：同一版本在同一设备上 `apply-failed` / `boot-failed` 后不再自动重试该版本；只有更高版本出现时才再次尝试。失败原因必须写入审计并在界面说明。
4. **磁盘空间**：下载前检查可用空间（至少为更新包的 2 倍）；不足时提示用户清理，不自动删除用户文件。
5. 暂存目录与备份使用平台保留前缀与平台用户数据目录；崩溃后启动扫描并清理未完成暂存，保留可用版本。
6. macOS 与 Windows 的安装事务必须由更新器执行，任何步骤都不得要求用户手工替换文件；Linux 包管理器（`deb`）安装走系统包管理器，平台只负责提示与跳转。
7. 更新过程中的所有外部网络访问只来自更新器（平台组件），不经插件、不经资源代理。

### 2.5 灰度与暂缓

1. 灰度由索引的 `rollout.percent` 与 `rollout.seed` 控制：客户端以"设备稳定标识 + seed"的哈希取模 100，结果小于 `percent` 才参与本轮更新。
2. 设备稳定标识必须是平台生成的非隐私标识（安装时生成、存于用户数据目录），不得使用硬件序列号、MAC 地址或用户账号。
3. 灰度按版本生效：同一版本调整 `percent` 不需要新版本号，但必须更新索引并记录发布记录；已参与用户的更新不因百分比调低而撤回。
4. 暂缓（`paused: true`）：客户端停止该渠道的自动更新检查下载与提示，已下载未安装的暂存包保留但不安装；暂停原因与恢复由发布方经索引控制，客户端不提供本地"接受已暂缓版本"的绕过入口。
5. 用户侧"暂缓此版本"：用户可对某个具体版本选择"暂缓本次更新"，效果是跳过该版本（直到更高版本出现或用户手动检查时重新提示）；该选择记录在用户数据目录，不改变渠道设置。
6. 灰度与暂缓都不允许跳过签名、摘要与门禁校验。

### 2.6 离线更新包

1. 离线更新包是完整安装产物（macOS `.zip`、Windows `.exe`、Linux AppImage / `deb`），与在线更新包**字节相同**，由同一发布流水线产出并登记摘要。
2. 离线安装流程：

```
[1] 用户从发布页面获取安装包与 SHA256SUMS.txt（含签名块说明）
        ▼
[2] 平台"从文件安装更新"入口选择安装包
        ▼
[3] 校验：文件字节 sha256、Ed25519 签名与 keyId 信任根、平台代码签名
        │ 失败 → 拒绝并提示具体失败项
        ▼
[4] 版本判定：必须严格高于已安装版本（§2.3）
        │ 降级 → 拒绝
        ▼
[5] 按 §2.4 步骤 [5]–[8] 执行收敛、替换与首次启动自检
```

3. 离线包安装同样受灰度与暂缓之外的防降级、签名与代码签名约束；离线安装不受 `paused` 限制（用户显式动作），但发布方应在发布说明中标注暂缓原因。
4. 受管环境（无网络、企业分发）可以批量分发离线包与 `SHA256SUMS.txt`；平台提供校验命令入口（`tools/scripts/checksums.mjs verify`，[02-构建与打包](../06-开发与运维/02-构建与打包.md) §6.6）。
5. 离线包不提供"静默安装"：必须由用户显式发起并经校验后执行。

### 2.7 更新过程中的插件影响与重启边界

| 事实 | 规则 |
|---|---|
| 平台更新必须重启 | 平台版本是整体交付物（Rust 核心、Bridge、渲染进程、插件接口），替换进程内代码不可行；更新始终以重启为边界（[ADR-002](../01-架构设计/ADR/ADR-002-Electron作为桌面端壳.md)） |
| 插件更新不需重启 | 插件经蓝绿替换在运行中生效，与平台更新无关（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §6.2） |
| 运行中插件 | 平台更新前必须收敛运行态：编辑会话 flush、文档写入完成、在途能力调用结束、插件调用静默；更新器触发应用退出流程（`reason: 'shutdown'`，[07-应用插件接口](../05-接口与契约/07-应用插件接口.md) §4.5） |
| 插件状态 | 插件注册表、启用状态与授权记录位于用户数据目录，重启后原样恢复；平台版本变化后按 `engines.chips` 门禁（§3.3）重新判定，不满足的插件进入 `failed` 并提示升级 |
| 用户数据 | 平台更新不改写用户文档；文档格式变更随平台版本发布时必须交付迁移工具（[04-版本与迁移规范](../04-文件格式规范/04-版本与迁移规范.md) §七） |
| 更新失败 | 保持旧版本可启动、可回退到更新前状态（§2.4），不产生"半更新"状态 |
