## 三、插件分发

### 3.1 `.cpk` 安装来源

| 来源 | 渠道标识 | 入口 | 签名要求 | 说明 |
|---|---|---|---|---|
| 本地文件 | `user` | 拖入应用、文件选择、文件关联 | 可选；缺失时安装界面明确展示"未签名发布者"并经用户确认 | 第三方与个人分发 |
| 开发目录 | `development` | 启动参数指定的插件目录、开发工作区 | 不检查 | 仅开发构建；不签名、禁止分发（[03-插件包格式](../04-文件格式规范/03-插件包格式.md) §2.7、§6.3） |
| 插件市场 | `user` | 市场界面、`chips://` 深链接跳转 | 按市场登记信息校验；签名仍按 `user` 渠道规则执行 | 下载后走与本地文件完全相同的安装校验链 |
| 平台内置 | `builtin` | 随平台版本发布 | 必须签名 | 不参与用户侧分发（[02-构建与打包](../06-开发与运维/02-构建与打包.md) §7.4）；安装包布局与首启引导见 §3.5、§3.6 |

规则：

1. 无论来源如何，安装一律执行与安装同源的校验链：归档 → 结构 → 清单 → 签名 → 摘要（[03-插件包格式](../04-文件格式规范/03-插件包格式.md) §五）；市场下载不得跳过任何一步。
2. 安装摘要（`sha256:` + 文件字节摘要）写入插件注册表并作为更新比对依据（[03-插件包格式](../04-文件格式规范/03-插件包格式.md) §5.2）。
3. 安装只登记，不自动启用；首次启用逐项确认权限，拒绝不阻断启用（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §4.2、§4.3）。
4. 同 ID 更新走蓝绿替换；降级默认拒绝，权限集合变化必须重新确认（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §6.2、§6.4）。

### 3.2 市场协议契约

本节只定义**平台与市场之间的交互契约**；市场服务端的实现、部署与运营由社区服务承担，不在文档库范围内。协议基于 HTTPS + JSON，接口版本固定前缀 `/v1`。

| 操作 | 请求 | 响应 | 说明 |
|---|---|---|---|
| 发现 | `GET /v1/plugins?query=&type=&page=&pageSize=` | `{ items: MarketPluginEntry[], page, pageSize, total }` | 搜索与列表；`type` 取四类角色 |
| 详情 | `GET /v1/plugins/{pluginId}` | `MarketPluginDetail`（含版本列表） | 单个插件详情 |
| 下载 | `GET /v1/plugins/{pluginId}/{version}/download` | `.cpk` 字节流 | 也可返回受保护的直链；下载结果必须与登记的 `sha256` 一致 |
| 更新检查 | `POST /v1/updates/check` | `{ updates: MarketUpdateEntry[] }` | 请求体携带已安装插件 `{ pluginId, version }[]` 与平台信息（版本、OS、架构） |
| 安装回调 | `POST /v1/installations` | `204`（无正文） | 上报 `{ pluginId, version, installDigest, source, result, occurredAt }`；尽力而为，失败不得影响安装结果 |

```typescript
interface MarketPluginEntry {
  pluginId: string;
  version: string;                 // 该条目展示的最新版本
  type: 'basecard' | 'boxlayout' | 'app' | 'service';
  name: string;                    // 简体中文显示名
  description?: string;
  author?: string;
  license?: string;
  size: number;                    // .cpk 字节数
  sha256: string;                  // .cpk 字节摘要，小写十六进制
  keyId: string | null;            // 签名 keyId；null 表示未签名
  engines: { chips: string };      // 平台版本范围（§3.3）
  platforms: Array<'mac' | 'win' | 'linux'>;
  publishedAt: string;             // RFC 3339 UTC
}

interface MarketUpdateEntry {
  pluginId: string;
  version: string;                 // 可更新到的最高版本
  sha256: string;
  keyId: string | null;
  engines: { chips: string };
}
```

契约规则：

1. **签名优先**：市场登记信息（`sha256`、`keyId`）只用于展示与下载前快速校验；安装前仍以本地重算的摘要与签名校验为准。市场不能使未签名包"变成已签名"。
2. **来源白名单**：平台只接受编译期或用户显式配置的市场端点；不跟随市场返回的任意第三方下载地址（`download` 直链必须与市场端点同域或在其声明白名单内）。
3. **隐私最小化**：更新检查只上报插件 ID/版本与平台信息；不上报用户文件、工作区路径、插件配置、凭证或使用行为。安装回调只含安装结果元数据。隐私边界以[《同步引擎设计》](../01-架构设计/01-子系统设计/07-同步引擎设计.md) §8 的同类原则为准（最小化、可审计、不默认上传）。
4. **无登录要求**：平台不提供 OAuth/登录流程（[04-能力契约规范](../05-接口与契约/04-能力契约规范.md) 范围外能力）；需要账户的市场由市场自身以凭证 + `http` 能力组合实现，平台只保存 `credential://` 引用。
5. **失败不阻断**：市场不可达、响应非法或超时时，插件管理与已安装插件不受影响；错误归一为 `ChipsError`，错误码见 §3.4。
6. **下载事件**：下载过程发布 `transfer:progress` / `transfer:completed` / `transfer:failed`；用户可取消（`transfer:cancel`）（[04-能力契约规范](../05-接口与契约/04-能力契约规范.md)、[05-事件契约规范](../05-接口与契约/05-事件契约规范.md)）。
7. 市场协议不做服务发现与认证协商：端点必须固定 HTTPS，证书校验始终开启。

### 3.3 插件更新与平台版本兼容门禁（`engines.chips`）

1. manifest 增加 `engines` 字段：

```yaml
engines:
  chips: ">=1.0.0 <2.0.0"     # 语义化版本范围，语法见 04-版本与迁移规范 §4
```

2. 字段语义：`engines.chips` 声明插件可运行的平台版本范围；范围语法、运算符与匹配规则完全采用[《版本与迁移规范》](../04-文件格式规范/04-版本与迁移规范.md) §四。
3. 门禁时机与判定：

| 时机 | 判定 | 不满足时 |
|---|---|---|
| 安装校验 | 当前平台版本必须落在范围内 | 拒绝安装，`CPK_ENGINE_UNSUPPORTED` |
| 启用 | 同安装判定（平台可能在安装后升级） | 拒绝启用，插件停留 `installed`，提示"需要平台版本 X–Y" |
| 平台更新后重启自检 | 逐个已启用插件复核 | 不满足的插件进入 `failed`，提示升级插件；不阻塞平台运行 |
| 插件更新 | 新版本范围必须覆盖当前平台版本 | 拒绝更新，返回结构化错误并提示"该版本不支持当前平台" |

4. 平台版本即[《版本与迁移规范》](../04-文件格式规范/04-版本与迁移规范.md) §2.1 的平台统一版本；不使用独立平台代号。
5. 插件更新还必须满足依赖者版本范围与权限变化确认（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §6.4）；`engines.chips` 是独立于依赖门禁的**平台侧**门禁，两者都通过才允许更新。
6. 市场更新检查（§3.2）必须携带平台版本，市场返回的条目必须已按 `engines` 过滤；平台在下载后再本地复核一次，不信任市场过滤结果。

### 3.4 安装包与内置插件

内置插件（`source: builtin`）随平台安装产物分发：不进入用户插件安装区，也不参与市场与用户侧安装链路；其文件位于壳资源目录，随平台更新整体替换（§2.4）。安装产物布局三端同构，以 macOS 为例（`Chips.app/Contents/Resources/` 对应 Windows / Linux 应用资源目录）：

```text
<应用资源目录>/
├── frame/                          # 渲染帧资源（[02-构建与打包](./02-构建与打包.md) §6.1）
├── trust-roots.json                # 信任根注册表（§2.2）
└── builtin-plugins/
    ├── index.json                  # 内置插件清单（随平台版本生成）
    ├── chips.official.settings-<版本>.cpk
    └── …                           # 每个内置插件一个已签名 .cpk
```

`index.json` schema：

```json
{
  "format": "chips-builtin-plugins-v1",
  "platformVersion": "1.0.0",
  "plugins": [
    {
      "pluginId": "chips.official.settings",
      "version": "1.0.0",
      "file": "chips.official.settings-1.0.0.cpk",
      "sha256": "<.cpk 文件字节摘要，小写十六进制>",
      "enabledByDefault": true
    }
  ]
}
```

规则：

1. 每个内置插件必须是已签名 `.cpk`（`builtin` 渠道，[03-插件包格式](../04-文件格式规范/03-插件包格式.md) §六）；`enabledByDefault` 声明默认启用集合，生态设置面板（`chips.official.settings`）必须为默认启用。
2. 内置插件集合由发布流水线按[官方插件与应用目录](../03-插件开发/09-官方插件与应用目录.md)生成、构建、签名并汇总；`index.json` 与包文件同批生成，禁止手工编辑（[05-CICD与质量门禁](./05-CICD与质量门禁.md) §5.3、§5.4）。
3. 安装器只负责放置应用与内置插件包，不执行任何插件安装、启用或业务逻辑（壳零业务，[17-跨端Shell与平台抽象设计](../01-架构设计/01-子系统设计/17-跨端Shell与平台抽象设计.md) SB-2）；三端首启行为一致。
4. 内置插件不写入用户安装区、不参与用户侧分发、不可卸载，只能停用（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §4.1、§4.5）；用户安装同 ID 插件时按来源优先级遮蔽（`development` > `user` > `builtin`，同上 §4.1）。
5. 安装产物内的 `builtin-plugins/` 不进入 asar 打包（`extraResources` 明文安装，[02-构建与打包](./02-构建与打包.md) §6.1），使平台可校验、解包并按需重装。
6. 三端安装器只放置产物（macOS 为 DMG 拖入 Applications，Windows 为 NSIS 安装，Linux 为 AppImage / `deb`），不执行插件安装、启用或自检脚本；这些步骤统一在安装后的首次启动由平台执行，平台差异不进入插件引导逻辑（§3.5）。

### 3.5 首启引导与内置插件自检

首次启动，以及平台版本变化后的首次启动，按固定顺序执行内置插件引导：

```text
[1] 解析内置插件目录与 index.json
     │ 目录或清单缺失/非法 → 记录诊断并跳过引导，不阻塞启动
     ▼
[2] 逐个校验：归档与结构 → 清单 → Ed25519 签名与信任根 → 重算 sha256 与 index 比对 → engines.chips 门禁
     │ 任一项失败 → 该插件跳过并写审计（不安装、不启用），继续下一个
     ▼
[3] 装载：校验通过的插件解出到内置插件装载区（用户数据目录内由插件管理子系统管理的平台区域，按插件 ID 与版本归档）
     │ 注册表登记 source = builtin、状态 installed
     ▼
[4] 按 enabledByDefault 与启用偏好生成启用序列（依赖拓扑序），逐个启用；单个失败隔离，不阻塞其余
     ▼
[5] 自检与修复：以注册记录与 index.json 比对为第一层；记录缺失、版本不一致或不一致项从安装产物重新校验并替换
     ▼
[6] 首启引导：平台在首个会话中以欢迎入口提示打开设置面板；面板向导按[生态设置面板设计](../08-产品与交互/05-生态设置面板设计.md) §7 执行
```

规则：

1. 内置插件启用走标准启用流程：首次启用授权按[08-权限系统设计](../01-架构设计/01-子系统设计/08-权限系统设计.md) §6.2 逐项确认，未授权权限保持默认拒绝；首启不产生任何隐式授权。
2. 内置插件装载与自检是平台组件行为：不向插件暴露接口、不新增 Bridge 能力、不发布插件可订阅的专用事件。
3. 失败隔离：单个内置插件校验失败、装载失败或启用失败只影响该插件（跳过或 `failed`），平台启动继续；失败写入审计与诊断，设置面板提供重试入口（重试从安装产物重新校验，不改变用户数据与授权）。
4. 自检只做必要重算：以注册记录与 `index.json` 比对为第一层，不逐次重算全部包摘要；仅对记录缺失、版本不一致或校验不一致的条目重算 `.cpk` 摘要与签名。
5. 自检与重装不覆盖用户状态：用户对内置插件的停用与授权记录保留；重装只恢复文件与注册记录。
6. 平台更新替换安装产物内的 `builtin-plugins/` 后，内置插件版本以产物为准并走蓝绿替换语义（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §6.2）；注册记录不得保留指向旧包内路径的条目。
7. 首启引导与内置插件引导相互独立：引导被跳过或窗口关闭不影响内置插件的安装与启用；引导完成状态存于设置面板自身配置命名空间（[生态设置面板设计](../08-产品与交互/05-生态设置面板设计.md) §7.1）。
8. 错误码：内置插件校验失败沿用 `CPK_*`（含 `CPK_SIGNATURE_REQUIRED`、`CPK_SIGNATURE_INVALID`、`CPK_ENGINE_UNSUPPORTED`，§3.6、[03-插件包格式](../04-文件格式规范/03-插件包格式.md) §八）；自检或重装失败只记录诊断与审计，不改变平台启动结果。

### 3.6 插件分发错误码

新增（归口：更新与分发）：

| 错误码 | 含义 | 可重试 |
|---|---|---|
| `CPK_ENGINE_UNSUPPORTED` | `engines.chips` 范围不满足（安装 / 启用 / 更新任一环节） | 否（升级平台或插件） |
| `UPDATE_INDEX_INVALID` | 更新索引格式、字段或渠道/平台/架构不匹配 | 是（重新检查） |
| `UPDATE_PACKAGE_INVALID` | 更新包大小、摘要或签名校验失败 | 否（安全事件，记录审计） |
| `UPDATE_APPLY_FAILED` | 替换事务失败，已恢复更新前状态 | 是（等待更高版本） |
| `UPDATE_BOOT_FAILED` | 新版本首次启动自检失败，已恢复更新前状态 | 是（等待更高版本） |
| `UPDATE_DOWNGRADE_REJECTED` | 目标版本低于已安装版本 | 否 |
| `MARKET_UNREACHABLE` | 市场端点不可达或超时 | 是 |
| `MARKET_RESPONSE_INVALID` | 市场响应不符合协议契约 | 是（记录诊断） |

- 安装链路错误沿用 `CPK_*`（[03-插件包格式](../04-文件格式规范/03-插件包格式.md) §八）；传输错误沿用 `transfer:*` 事件与资源域错误码。
- 所有错误统一为 `ChipsError`（`code` / `message` / `details?` / `retryable?`），`message` 为简体中文；`details` 不含凭证、私钥与用户文件内容。
- 新增错误码的用户展示与排查条目随实现同步登记到[《故障排查手册》](./04-故障排查手册.md)。

### 3.7 文件关联注册与回收

系统文件关联（`.card`、`.box` 及各插件声明的扩展名）由平台在**启用时注册、停用/卸载时回收**；安装器不参与关联注册（§3.4 规则 3，壳零业务）。

| 阶段 | 行为 | 失败处理 |
|---|---|---|
| 启用 | 平台读取 manifest `fileAssociations`，经壳层注册到系统（macOS `CFBundleDocumentTypes` 等价声明、Windows 注册表、Linux desktop entry） | 记录诊断与审计；不阻断启用 |
| 停用 | 撤销该插件声明的全部关联 | 记录诊断；不阻断停用 |
| 卸载 | 撤销关联并清理系统关联缓存 | 记录诊断；卸载结果不受影响 |
| 首启自检 | 与内置插件自检同链路核对关联状态，缺失或指向旧路径时按当前已启用集合重建 | 记录诊断；不阻塞启动 |

规则：

1. 同一扩展名存在多个声明者时按[14-资源打开与默认处理器契约](../05-接口与契约/14-资源打开与默认处理器契约.md) 的 `tier`（`primary` > `fallback`）与用户偏好决定默认处理器；注册冲突不得静默覆盖用户显式选择。
2. 关联注册只引用已安装插件的稳定标识与启用状态，不写入安装临时路径；平台更新后由首启自检重建。
3. 冲突与回收必须幂等：重复启用、停用后再启用、卸载后重复回收均不产生残留关联。
4. 关联行为属平台壳层能力，不新增 Bridge 能力、不向插件暴露接口；插件只能声明 `fileAssociations`（[02-插件清单规范](../03-插件开发/02-插件清单规范.md)）。
5. 关联变更写入审计（插件 ID、扩展名、动作、结果），失败详情不含用户文件内容。
