## 三、用户侧命令 `chips`

### 3.1 帮助与交互式界面

#### 3.1.1 `chips help [命令]`

```bash
chips help                # 输出内置命令树与当前工作区已启用插件命令路径
chips help plugin install # 输出指定命令的用法、参数与示例
```

- 帮助内容来自 CLI 固定命令树与 `cli.command.list` 索引；`chips help <插件命令路径>` 展示声明的 `title`、`description`、`examples`、参数与选项（§5.1）。
- 退出码 0；未知命令帮助返回 `CLI_COMMAND_NOT_FOUND`（退出码 3）。

#### 3.1.2 裸命令与 `--interactive`

```bash
chips                 # 交互式终端中进入 TUI；非交互环境输出提示并返回 0
chips --interactive   # 显式进入 TUI；非交互环境返回 1
```

TUI 契约：

- 只展示固定命令与 `cli.command.list` 的当前索引，不读取插件源码、不绕过平台运行时。
- 界面为纯终端字符界面：顶部命令框（`chips > …`）、动态交互区、底部提示栏三段；不使用彩色前景/背景与闪烁样式；进入时使用备用屏幕并隐藏光标，退出恢复。
- 键盘操作：`↑/↓` 移动，`←/→` 调节/移动光标，`Space` 切换多选，`Enter` 确认或执行，`Backspace` 删除片段或退回上级，`Ctrl+C` 清空命令或请求取消当前执行，`Ctrl+\` 退出。
- 参数控件由声明的 `ui.control` 驱动：`select`（互斥列表）、`multiSelect`（多选后逗号连接）、`toggle`（布尔多选）、`stepper` / `slider`（数值滑块）、`pathInput` / `pasteBox` / `textarea`（输入框）。
- 执行时把最终 token 交回**同一**传统 CLI 执行器：最长前缀匹配、`--plugin` 消解、参数解析、路径校验、任务等待与结果输出完全一致；TUI 不定义第二套执行语义，不提供历史命令搜索与回放。
- 执行中 `Ctrl+C` 对声明 `job.cancelOnInterrupt: true` 的命令复用正式取消链路；结果面板展示成功/失败/取消、退出码、耗时与错误摘要，`R` 重跑上一条，`Enter` 返回构建界面。

### 3.2 工作区运行标记

#### 3.2.1 `chips start`

```bash
chips start
```

- 确保当前用户工作区已初始化，并写入运行标记 `<workspace>/.chips/state/host-state.json`：

```json
{ "running": true, "pid": 51234, "startedAt": "2026-09-19T02:11:04.000Z" }
```

- 幂等：标记已存在时覆盖刷新并返回同一形状；不启动图形界面，不拉起窗口。
- 输出：`{ "running": true, "pid": …, "startedAt": … }`；退出码 0。

#### 3.2.2 `chips stop`

```bash
chips stop
```

- 删除运行标记并输出 `{ "running": false }`；标记不存在时为幂等空操作，同样退出 0。
- 运行标记只是状态与脚本检查入口，插件命令的承载链路不依赖该标记（§3.10）。

#### 3.2.3 `chips status`

```bash
chips status
```

```json
{
  "workspace": { "path": "/Users/chips/Documents/Chips", "kind": "user" },
  "state": { "running": true, "pid": 51234, "startedAt": "2026-09-19T02:11:04.000Z" },
  "platformVersion": "0.1.0"
}
```

- 读取工作区标记与工作区标识；不读取系统进程表，不承诺端口、资源占用或连接数。
- `state.running` 为标记值；脚本需要真实实例状态时以平台实例锁与诊断输出为准（[13-工作区设计](../01-架构设计/01-子系统设计/13-工作区设计.md) §2.4、§7.3）。

### 3.3 配置

```bash
chips config list [--layer <user|workspace>]
chips config set <键> <值> [--layer <user|workspace>]
chips config reset <键> [--layer <user|workspace>]
```

- 层级与物理载体以 [10-配置系统设计](../01-架构设计/01-子系统设计/10-配置系统设计.md) §2.2 为准：`user` 层写 `<user-config-dir>/config.user.json`，`workspace` 层写 `<workspace>/.chips/config.workspace.json`；默认 `workspace`。
- 键空间：`platform.*` 与 `plugins.<pluginId>.*`；`platform` 层与 `plugin` 层不可写，传入即 `CONFIG_SCOPE_INVALID`。
- `<值>` 先按 JSON 解析（对象、数组、数字、布尔、`null`），失败时按字符串；写入前按 schema 校验，未注册键返回 `CONFIG_KEY_UNKNOWN`，类型不符返回 `CONFIG_VALUE_INVALID`。
- `reset` 移除该层覆盖；层内已无覆盖时幂等成功；插件卸载时用户层与工作区层插件文件一并清理（[10-配置系统设计](../01-架构设计/01-子系统设计/10-配置系统设计.md) §3.1）。

示例：

```bash
chips config list
chips config set platform.log.level debug
chips config set plugins.chips.official.editor.autoSaveDebounceMs 800
chips config reset platform.log.level
```

- 输出为生效配置或 `{ "ok": true }`；配置错误码退出码为 1，参数层非法为 2（§2.5）。

### 3.4 日志

```bash
chips logs [-n <行数>] [-l <级别>] [-f|--follow]
```

| 选项 | 默认 | 含义 |
|---|---|---|
| `-n, --lines <行数>` | 100 | 读取末尾行数 |
| `-l, --level <级别>` | 全部 | 过滤 `error` / `warn` / `info` / `debug` 及以上级别 |
| `-f, --follow` | 关 | 跟踪输出；`Ctrl+C` 结束跟踪并返回 0 |

- 来源为当前工作区与平台日志（[04-故障排查手册](./04-故障排查手册.md) §2.1）：平台主日志、调试追踪、工作区日志与 CLI 操作日志；字段规范与关联键见同文档 §2.2。
- `--follow` 输出增量行；非交互环境不输出动画控制字符。

示例：

```bash
chips logs -n 200 -l warn
chips logs --follow
```

### 3.5 插件管理

#### 3.5.1 `chips plugin create`

```bash
chips plugin create --role <app|basecard|boxlayout|service> --id <插件ID> --name <显示名> [--dir <目录>]
```

| 参数 | 必需 | 说明 |
|---|---|---|
| `--role` | 是 | 插件角色四选一：`app` / `basecard` / `boxlayout` / `service` |
| `--id` | 是 | 反向域名插件 ID（R20）；发布后不得变更 |
| `--name` | 是 | 非空简体中文显示名 |
| `--dir` | 否 | 目标目录；默认 `./<插件 ID 末段>` |

- 模板与文件计划来自 `@chips/sdk/scaffold`：生成器是纯函数，只产出路径与内容，不写盘、不联网、不安装依赖；落盘由 `@chips/cli` 完成（[02-SDK-API规范](../05-接口与契约/02-SDK-API规范.md) §8.1、§8.3）；四角色模板文件清单见同文档 §8.2。
- 生成结果必须直接通过 manifest 校验与插件包格式校验；生成内容包含 `manifest.yaml`、`package.json`、`tsconfig.json`、角色入口源码、`assets/` 与 README。
- `theme`、`module` 角色不存在，传入返回 `CLI_ARGUMENT_INVALID`（退出码 2）。

示例：

```bash
pnpm exec chips plugin create \
  --role app \
  --id chips.example.hello-world \
  --name "你好世界" \
  --dir examples/plugins/hello-world
```

```text
已创建 app 角色插件：chips.example.hello-world
目标目录：examples/plugins/hello-world
生成文件：manifest.yaml、package.json、tsconfig.json、src/index.ts、src/ui/AppView.tsx、assets/icons/app.svg
下一步：pnpm install 建立工作区链接，然后执行 chips dev run 启动开发宿主
```

#### 3.5.2 `chips plugin pack`

```bash
chips plugin pack [--dir <目录>] [--out <目录>] [--sign --key-id <密钥ID>]
```

| 参数 | 必需 | 默认 | 说明 |
|---|---|---|---|
| `--dir` | 否 | 当前目录 | 插件工程目录；读取 `manifest.yaml`、`dist/index.js`、`render.js` 与 `assets/` |
| `--out` | 否 | `<dir>/dist` | `.cpk` 输出目录 |
| `--sign` | 否 | 关 | 生成 Ed25519 签名；需要 `CHIPS_SIGNING_KEY_FILE` |
| `--key-id` | `--sign` 时必需 | — | 签名密钥标识，必须已登记信任根（[03-插件包格式](../04-文件格式规范/03-插件包格式.md) §6） |

- 打包前置校验、归档布局、ZIP Store、摘要、体积限额与错误码以 [03-插件包格式](../04-文件格式规范/03-插件包格式.md) §2、§四、§八为唯一权威；打包前强校验 `package.json` 与 `manifest.yaml` 的 `version` 一致（不一致返回 `CPK_MANIFEST_INVALID`）。
- 输出命名固定 `<名称>-<版本>.cpk`；同一输入两次打包必须字节级可复现（[02-构建与打包](./02-构建与打包.md) §1.3）。

示例：

```bash
pnpm exec chips plugin pack --out dist/

CHIPS_SIGNING_KEY_FILE=/run/secrets/chips-official-2026.pem \
  pnpm exec chips plugin pack --out dist/ --sign --key-id chips-official-2026
```

```text
已生成 dist/hello-world-0.1.0.cpk
  manifest: chips.example.hello-world@0.1.0（app）
  成员数: 4
  归档大小: 30.6 KiB（ZIP Store）
  安装摘要: sha256:8a3f0c1d…
  校验: 通过
```

#### 3.5.3 `chips plugin validate`

```bash
chips plugin validate <目录或 .cpk 路径>
```

- 与安装完全同源的五阶段校验：归档 → 结构 → 清单 → 签名 → 摘要；任一阶段失败立即终止并保留阶段输出（[03-插件包格式](../04-文件格式规范/03-插件包格式.md) §五）。
- 目录态要求包根形态（目录根布局与 `.cpk` 解包后的包根完全一致，[03-插件包格式](../04-文件格式规范/03-插件包格式.md) §2.7）：跳过归档与签名校验，仍执行 manifest、入口、路径安全与角色布局校验；检测到根级 `package.json` 即判定为源码工程目录，按 `CPK_LAYOUT_INVALID` 拒绝并提示先执行 `chips plugin pack` 校验产物。
- 签名阶段的信任根注入走环境变量 `CHIPS_TRUST_ROOTS_FILE`（开发/验证期唯一正式命令面通道，§2.7）：指向信任注册文件后按注册表验证签名；未注入或 `keyId` 未注册时签名包按 `CPK_SIGNATURE_INVALID` 拒绝。
- 通过时输出 `结果: valid` 并退出 0；不通过时输出失败的阶段与 `CPK_*` 错误对象，退出 1；路径不可读返回 `CLI_PATH_*`，退出 5。

示例：

```bash
pnpm exec chips plugin validate dist/hello-world-0.1.0.cpk

CHIPS_TRUST_ROOTS_FILE=/keys/trust-roots.json \
  pnpm exec chips plugin validate dist/hello-world-0.1.0.cpk
```

```text
归档校验: 通过（全部成员 Stored）
结构校验: 通过（app 布局）
清单校验: 通过
签名校验: 已跳过（development 来源）
结果: valid
```

#### 3.5.4 `chips plugin install`

```bash
chips plugin install <目录 | .cpk | manifest.yaml>
```

- 安装到当前渠道的插件注册表（位于平台用户数据目录，[13-工作区设计](../01-架构设计/01-子系统设计/13-工作区设计.md) §7.2）；只登记为 `installed`，**不自动启用**（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §4.2）。
- 安装校验链与 `plugin validate` 同源；`user` 来源未签名时输出“未签名发布者”提示：交互终端等待确认，非交互环境必须带 `--yes` 显式确认（缺少时返回 `CLI_ARGUMENT_INVALID`，不挂起），拒绝则不安装；`development` 来源仅开发入口可用。
- 同一插件 ID 再次安装即替换旧安装副本，不追加重复记录；版本比较与降级拒绝规则见 [04-版本与迁移规范](../04-文件格式规范/04-版本与迁移规范.md) §5.1。
- 输出：`{ "pluginId": "…", "version": "…", "type": "…", "state": "installed" }`；失败按 `CPK_*` / `PLUGIN_*` 返回，退出 1。

示例：

```bash
pnpm exec chips plugin install examples/plugins/hello-world/dist/hello-world-0.1.0.cpk
```

#### 3.5.5 `chips plugin list` / `chips plugin info`

```bash
chips plugin list [--role <basecard|boxlayout|app|service>] [--source <builtin|user>]
chips plugin info <pluginId>
```

- `list` 输出已发现与已安装插件记录，字段：`id`、`version`、`role`、`name`、`source`、`state`（`discovered` / `installed` / `active` / `disabled` / `failed`）、`enabled`；来源优先级与遮蔽规则见 [03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §4.1。
- `info` 输出单插件详情：`installPath`、`manifestPath`、权限申请与授权状态、依赖、`lastError`。
- 插件不存在返回 `PLUGIN_NOT_FOUND`（退出码 6）。

#### 3.5.6 `chips plugin enable` / `chips plugin disable` / `chips plugin uninstall`

```bash
chips plugin enable <pluginId>
chips plugin disable <pluginId>
chips plugin uninstall <pluginId>
```

- `enable`：首次启用进入逐项授权，拒绝某项授权不阻断启用（该项保持未授权）；成功输出 `state: active` 与新状态（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) §4.3）。
- `disable`：停止实例并级联停用依赖方；数据保留在文件中；输出 `state: disabled`。
- `uninstall`：移除入口、文件与注册记录；用户文档内容与插件配置文件按 [10-配置系统设计](../01-架构设计/01-子系统设计/10-配置系统设计.md) §3.1 清理规则处理；输出 `{ "ok": true }`。
- 三者在目标不存在与状态非法时分别返回 `PLUGIN_NOT_FOUND`（6）与 `PLUGIN_*`（1）。

### 3.6 打开文件

```bash
chips open <路径>
```

- 触发平台文件关联链路：`.card` / `.box` 走文档打开链路；已声明 `fileAssociations` 的应用插件经 `launch`（`source: 'file-association'`）接收文件，服务插件经 `handleFile` 接收（[07-应用插件接口](../05-接口与契约/07-应用插件接口.md) §3.4、[10-服务插件接口](../05-接口与契约/10-服务插件接口.md) §2.2）。
- 无插件处理器且系统可打开时，按 `shell:openExternal` 语义交给系统默认程序；路径非法或目标不可用返回 `FILE_ASSOCIATION_TARGET_INVALID`（退出码 5）。
- 输出：`{ "path": "…", "handler": { "pluginId": "…", "kind": "app|service" } }`，或 `{ "path": "…", "handler": { "kind": "shell" } }`。

示例：

```bash
chips open ~/Documents/Chips/旅行日记.card
```

### 3.7 平台更新

```bash
chips update check [--channel <stable|beta>]
chips update install [--channel <stable|beta>] [--json]
```

- 渠道与版本判定以 [06-更新与分发规范](./06-更新与分发规范.md) §2、§3 为唯一权威：用户可选 `stable` / `beta`；`rc` / `alpha` 不进入公开更新源；防降级为刚性规则，任何来源都不得安装低于已安装版本。
- `check` 输出：`currentVersion`、`latestVersion`、`channel`、`updateAvailable`、`publishedAt`、`notesUrl`；未配置更新源时 `updateAvailable: false` 并输出原因。
- `install` 执行下载 → 摘要 → contentHash → 签名 → 信任根完整校验 → 原子替换；失败回滚到更新前状态并返回 `UPDATE_*`（退出码 1）；无可用更新时返回 `{ "installed": false, "reason": "up-to-date" }`，退出 0。
- 更新以重启为边界；CLI 安装前要求编辑会话已经 flush 与收敛（UD-10）。

示例：

```bash
chips update check
chips update install
```

### 3.8 诊断

```bash
chips doctor [--fix] [--verbose]
```

- 检查项固定为：工作区标记与保留目录、工作区可写性、平台数据目录、插件注册表、日志目录、更新渠道配置、承载运行时依赖。
- 输出：

```json
{
  "workspace": { "path": "…", "kind": "user" },
  "checks": [
    { "id": "workspace.marker", "status": "ok", "detail": "标记与保留目录有效", "fixable": false },
    { "id": "cache.tmp", "status": "warn", "detail": "存在 2 个崩溃残留临时物", "fixable": true }
  ]
}
```

- `--fix` 只处理可安全重建项（缓存、崩溃残留临时物、缺失的保留目录骨架），不触碰用户文档与已安装插件；无法修复项保留在输出中。
- `--verbose` 增加逐项检查细节；存在 `error` 级检查项时退出 1，否则退出 0。

### 3.9 Shell 补全

```bash
chips completion bash
chips completion zsh
chips completion fish
```

- 输出注册到 `chips` 的补全脚本；脚本每次补全调用私有入口 `chips __complete ...`，该入口读取当前工作区 `cli.command.list` 索引并合并固定命令树。
- 插件安装、启用、禁用、卸载后，下一次 Tab 补全即反映最新索引；不需要重装补全脚本或重启平台。
- `__complete` 只输出换行分隔候选，不作为插件命令根开放；成功请求按 §2.8 记录 `source: completion` 操作日志，索引读取失败时静默返回空候选（退出码 0）。

### 3.10 插件命令调用

```bash
chips <命令路径> [参数] [选项]
chips --plugin <pluginId> <命令路径> [参数] [选项]
```

执行规则：

1. CLI 在需要时按需启动本次命令所需的短生命周期承载环境；用户不需要先执行 `chips start`。
2. `service` 目标经平台能力注册表与调用链路调用声明能力，等待响应；校验、权限、Schema 与路由与插件调用完全一致。
3. `app` 目标按 [13-命令系统契约](../05-接口与契约/13-命令系统契约.md) §4.4 的“启动并投递”执行：确保实例运行并等待入口级 `commandId` 注册后，以 `source: 'cli'` 调用 `command:invoke`；声明等待任务的命令创建 `cli-task` 并轮询至终态（§5.3.2）。
4. 进度：TTY 下 CLI 把去重后的 `progress` 以原地刷新行写 stderr（含 `percent` 显示百分比，含 `stage` 显示阶段名）；非交互环境默认不输出进度，`CHIPS_CLI_JOB_PROGRESS=1` 时按行写入 stderr。
5. `Ctrl+C` 对声明 `job.cancelOnInterrupt: true` 的命令调用 `cli.task.cancel` 并等待取消终态，随后按退出码 8 结束。

示例（§5.9 的应用插件声明 `translate file` 后）：

```bash
chips translate file ./README.md --to zh -o ./dist/README.zh.md --json
```

- 输出形状、human 摘要与产物提取规则见 §2.4 与 §5.4。
