## 五、Bridge 调用追踪

### 5.1 通道与追踪位置

| 通道 | 方向 | 追踪位置 | 关注点 |
|---|---|---|---|
| `bridge:request` | 渲染 → 主 | preload、主进程适配层、Bridge 核心、Host 执行 | 阶段推进与错误码（第 5.2、5.4 节） |
| `bridge:resource` | 渲染 → 主 | preload、主进程句柄表 | 句柄打开/释放、作用域与权限 |
| `event:control` | 渲染 → 主 | preload、主进程转发器 | 订阅计数与回执错误 |
| `event:<eventId>` | 主 → 渲染 | 主进程转发器 | 下行投递（第七章） |

通道定义见 [02-Bridge三层设计](../01-架构设计/01-子系统设计/02-Bridge三层设计.md) 第 7.1 节；`bridge:request` 的处理阶段（会话解析 → 注册表 → 权限 → Schema → 并发与超时 → 执行 → 取消 → 归一）见该文档第 2.3 节。

### 5.2 Bridge 追踪字段

`CHIPS_TRACE=bridge` 开启；`phase` 取值即调用链阶段名，`outcome` 记录该阶段结论。

| 字段 | 类型 | 含义 |
|---|---|---|
| `requestId` | string | 一次调用的唯一标识（preload 生成，UUID v4），用于关联与丢弃迟到结果 |
| `traceId` | string | 全链路追踪 ID（`InvocationContext.traceId`） |
| `sessionId` | string | 来源会话；解析失败时为空并伴 `BRIDGE_SESSION_UNKNOWN` |
| `windowId` | number | `webContents.id` |
| `channel` | string | `bridge:request` / `bridge:resource` / `event:control` |
| `direction` | string | `in`（渲染 → 主）/ `out`（主 → 渲染） |
| `capabilityId` / `operation` | string / null | 能力 ID；资源链路为 `open` / `release` |
| `phase` | string | `session` / `registry` / `permission` / `schema` / `concurrency` / `execute` / `cancel` / `normalize` |
| `outcome` | string | `allow` / `deny` / `ok` / `error` / `timeout` / `cancelled` |
| `errorCode` | string / null | `BRIDGE_*` 或 Host 业务错误码 |
| `retryable` | boolean | 与错误同源（[02-Bridge三层设计](../01-架构设计/01-子系统设计/02-Bridge三层设计.md) 第 9.2 节） |
| `durationMs` | number | Bridge 收到请求到返回结果的耗时（超时口径见该文档第 8.1 节） |

记录样例（一次权限拒绝）：

```json
{"timestamp":"2026-09-19T10:20:31.480Z","category":"bridge","requestId":"r-5c02","traceId":"t-3b91","sessionId":"s-7f2a","windowId":3,"pluginId":"chips.official.editor","pluginVersion":"1.0.0","channel":"bridge:request","direction":"in","capabilityId":"file:read","operation":null,"phase":"permission","outcome":"deny","errorCode":"BRIDGE_PERMISSION_DENIED","retryable":false,"durationMs":2,"details":null}
```

### 5.3 单次调用定位步骤

1. 复现操作，记录时间、插件 ID 与调用能力 ID。
2. 按 `capabilityId` + 时间窗口过滤追踪文件（命令见第 2.5 节）。
3. 取命中记录中的 `requestId`，聚合该调用的全部记录：

```bash
jq -c 'select(.requestId == "r-5c02")' \
  "$HOME/Library/Application Support/Chips/logs/trace/trace-2026-09-19.jsonl"
```

4. 找到首个 `outcome != "ok"` 的记录，读其 `phase` 与 `errorCode`，按第 5.4 节处理。
5. 涉及权限与审计的调用，用 `traceId` 在审计文件中取 `reason`、`missing`、`target` 等字段（命令见第 2.5 节）。
6. 需要观察封套原文时，在主进程 `ipcMain.handle('bridge:request', …)` 断点查看（第 4.1 节）。

### 5.4 常见错误码与诊断动作

完整错误码定义见 [02-Bridge三层设计](../01-架构设计/01-子系统设计/02-Bridge三层设计.md) 第 9.2 节；完整排查清单见 [04-故障排查手册](./04-故障排查手册.md)。下表只给定位动作。

| 错误码 | 诊断动作 |
|---|---|
| `BRIDGE_SESSION_UNKNOWN` | 检查窗口/帧在会话登记之后创建；确认来源 frame 与 `sessionId` 绑定；对照会话解析规则（[02-Bridge三层设计](../01-架构设计/01-子系统设计/02-Bridge三层设计.md) 第 7.4 节）。 |
| `BRIDGE_CAPABILITY_NOT_FOUND` | 核对能力 ID 拼写与大小写；确认提供方（平台域或服务插件）已激活且注册成功；内置能力对照 [04-能力契约规范](../05-接口与契约/04-能力契约规范.md)。 |
| `BRIDGE_PERMISSION_DENIED` | 读 `details.missing` 与 `reason`：`not_granted` 查 manifest `permissions` 声明与用户授权；`out_of_scope` 查限定值（路径前缀、域名通配）；对照 [08-权限系统设计](../01-架构设计/01-子系统设计/08-权限系统设计.md)。 |
| `BRIDGE_INVALID_INPUT` | 读 `details.errors[].pointer` 与 `keyword`，修正调用输入；对照能力 schema（[04-能力契约规范](../05-接口与契约/04-能力契约规范.md)）；schema 不填充默认值，缺省语义由能力实现定义。 |
| `BRIDGE_CAPABILITY_CONFLICT` / `BRIDGE_INVALID_SCHEMA` | 注册期错误：查能力 ID 是否与既有或保留 ID 重复、schema 是否可离线编译；提供方启用会失败，按 [03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) 处理。 |
| `BRIDGE_TIMEOUT` | 检查 Host 执行器是否阻塞（文件 IO、图像处理应经 `spawn_blocking`）或等待未就绪资源；超时不保证无副作用，不得仅凭超时假定"未执行"。 |
| `BRIDGE_CANCELLED` | 调用来自身会话销毁、能力注销或 Bridge 关闭；对照会话时间线（[01-Bridge-API规范](../05-接口与契约/01-Bridge-API规范.md) 第 4.2 节）确认生命周期。 |
| `BRIDGE_SESSION_BUSY` / `BRIDGE_QUEUE_OVERFLOW` | 会话在途调用超 64 或串行队列超 32：检查插件批量调用节奏，必要时把能力注册改为串行或分批（[02-Bridge三层设计](../01-架构设计/01-子系统设计/02-Bridge三层设计.md) 第 8.3 节）。 |
| `BRIDGE_INTERNAL` | 未归一异常；详情写平台主日志，用 `requestId` 在平台主日志检索对应记录，按 Host 缺陷修复。 |
