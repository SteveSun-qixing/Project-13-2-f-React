## 二、日志与追踪基线

### 2.1 平台日志流与位置

平台日志是主进程、内核与插件日志的统一去处，字段由平台自动附加 `pluginId`、`pluginVersion`、`timestamp`、`level`、`traceId`（[10-服务插件接口](../05-接口与契约/10-服务插件接口.md) 第 3.6 节）。三种输出相互独立：

| 输出 | 位置 | 内容 |
|---|---|---|
| 平台主日志 | 路径见 [ADR-002](../01-架构设计/ADR/ADR-002-Electron作为桌面端壳.md)（macOS `~/Library/Logs/Chips/main.log`、Windows `%USERPROFILE%\AppData\Roaming\Chips\logs\main.log`） | 主进程、内核、插件与渲染诊断 |
| 审计日志 | `<userData>/logs/audit/audit-YYYY-MM-DD.jsonl` | 权限判定、授予与撤销（字段见 [08-权限系统设计](../01-架构设计/01-子系统设计/08-权限系统设计.md) 第 8.2 节） |
| 调试追踪 | `<userData>/logs/trace/trace-YYYY-MM-DD.jsonl` | Bridge、事件、渲染、资源、插件与启动追踪（本文定义） |

`<userData>` 即 Electron `app.getPath('userData')`；macOS 为 `~/Library/Application Support/Chips`，Windows 为 `%APPDATA%\Chips`。调试追踪按日切分、异步追加，仅供开发诊断，不进入审计留存。

查看命令示例：

```bash
# 实时查看平台主日志（macOS）
tail -f ~/Library/Logs/Chips/main.log

# 只查看追踪中的错误记录（需 jq）
jq -c 'select(.errorCode != null)' \
  "$HOME/Library/Application Support/Chips/logs/trace/trace-2026-09-19.jsonl"
```

### 2.2 调试开关

| 开关 | 取值 | 默认值 | 作用 |
|---|---|---|---|
| `CHIPS_LOG_LEVEL` | `error` / `warn` / `info` / `debug` / `trace` | 开发构建 `debug`，发布构建 `info` | 平台主日志级别 |
| `CHIPS_TRACE` | `startup,plugin,bridge,event,render,resource` 逗号组合 | 开发构建开启除 `resource` 外的全部类别；发布构建关闭 | 调试追踪类别 |
| `RUST_LOG` | 模块路径过滤，如 `chips_cordis=debug,chips_bridge=trace` | 空 | 覆盖内核 Rust 侧日志级别 |
| `RUST_BACKTRACE` | `1` / `full` | 空 | panic 栈输出（第 3.4 节） |

启动示例（macOS / Linux）：

```bash
CHIPS_LOG_LEVEL=debug CHIPS_TRACE=bridge,event pnpm dev
```

Windows PowerShell：

```powershell
$env:CHIPS_LOG_LEVEL = 'debug'
$env:CHIPS_TRACE = 'bridge,event'
pnpm dev
```

### 2.3 追踪记录公共字段

追踪文件每行是一条 JSON 记录，公共字段如下；各章只补充专属字段，不重复本表。

| 字段 | 类型 | 含义 |
|---|---|---|
| `timestamp` | string | 记录时刻，ISO 8601 UTC |
| `category` | string | `startup` / `plugin` / `bridge` / `event` / `render` / `resource` |
| `traceId` | string | 全链路追踪 ID，与事件日志、审计一致 |
| `pluginId` / `pluginVersion` | string | 适用时的插件身份 |
| `sessionId` / `windowId` | string / number | 适用时的会话与窗口；`windowId` 为 `webContents.id` |
| `phase` | string | 记录对应的处理阶段；Bridge 取值见第 5.2 节 |
| `outcome` | string | `allow` / `deny` / `ok` / `error` / `timeout` / `cancelled` |
| `errorCode` | string / null | 失败时的错误码，成功为 `null` |
| `durationMs` | number | 该阶段或整体耗时（毫秒） |
| `details` | object / null | 结构化诊断；不得包含字节内容与平台外敏感路径 |

### 2.4 记录读取纪律

- 追踪文件与审计文件均为 JSON Lines；用 `jq` 过滤后需要原始行号时先 `jq -c` 再配合 `cat -n`。
- 日志与追踪异步写入，崩溃前的最后若干条可能缺失；按时间窗口检索时向前放宽 2 秒。
- 生产用户问题定位优先使用审计与平台主日志；调试追踪需用户显式开启（第 2.2 节默认值）。

### 2.5 traceId 与关联链

- 一次用户操作或外部触发产生一个 `traceId`；事件发布、能力调用、资源访问与审计记录共用该 ID（[03-核心接口规范](../05-接口与契约/03-核心接口规范.md) 第 5.2 节 `InvocationContext.traceId`、[09-事件系统设计](../01-架构设计/01-子系统设计/09-事件系统设计.md) 第 9.4 节）。
- `traceId` 不进入事件 payload，也不作为订阅 handler 参数（[05-事件契约规范](../05-接口与契约/05-事件契约规范.md) 第 3.2 节）；查看入口是追踪文件与审计文件。
- 关联步骤：以操作时间 + `pluginId` + `capabilityId`/`eventId` 在追踪文件中检索 → 命中记录取 `traceId` → 用 `traceId` 检索审计文件与其余类别记录，重建完整链路。

```bash
# 先按能力 ID 与插件定位记录
jq -c 'select(.category == "bridge" and .capabilityId == "file:read"
  and .pluginId == "chips.official.editor")' \
  "$HOME/Library/Application Support/Chips/logs/trace/trace-2026-09-19.jsonl" | tail -5

# 再按 traceId 关联审计
rg '"traceId":"t-3b91"' \
  "$HOME/Library/Application Support/Chips/logs/audit/audit-2026-09-19.jsonl"
```
