## 五、发布自动化

### 5.1 触发与前置

```
tag v{版本}（main 上的发布提交）
        │
        ▼
[1] 门禁重跑    五阶段全量，结论必须与 main 一致
        │
        ▼
[2] 版本校验    tag 与三类版本一致
        │
        ▼
[3] 构建与打包  三端安装包与 .cpk（同一提交重新构建）
        │
        ▼
[4] 签名        受保护发布环境；私钥不离开密钥库
        │
        ▼
[5] 产物校验    .cpk 同源校验 + 文档校验 + 摘要登记
        │
        ▼
[6] 记录与发布  发布记录（提交/版本/摘要/签名/门禁报告）→ 渠道
```

- 只有通过全部阶段的产物可进入渠道；PR 构建产物不得用于发布。
- 发布失败（任何阶段）必须递增版本号重新发布；禁止移动、删除或重打已推送的 tag（《Git 工作流规范》第八节）。

### 5.2 版本

- 三类版本的权威位置：平台版本（workspace 统一版本）、插件版本（`manifest.yaml`）、文档格式版本（`chip_standards_version`）（《04-版本与迁移规范》第二节）。
- 平台发布时全部平台包统一升版；插件独立升版、独立发布；文档格式版本随平台版本发布（《04-版本与迁移规范》第七节）。
- 版本号变更与代码在同一 PR 完成；发布流水线只做一致性校验，不代替人工升版。
- 预发布 `-alpha.N`、`-beta.N`、`-rc.N` 只进入对应预发布渠道，不进入稳定渠道（《04-版本与迁移规范》3.1 节）。

### 5.3 签名

- `.cpk` 签名文件固定为包根 `signature.json`：`format`、`keyId`、`algorithm`（`ed25519`）、`contentHash`、`signature`；`contentHash` 按《03-插件包格式》6.2 节计算。
- 私钥只存在于发布环境的密钥库；PR 与常规分支流水线禁止访问；签名在受保护环境中执行。
- 渠道签名要求：`builtin` 必须签名；`user` 可选，未签名必须在安装界面提示；`development` 不检查且禁止分发（《03-插件包格式》6.3 节）。
- 签名校验不替代归档、结构、清单与载荷校验；`keyId` 未在信任根注册表登记即视为签名无效（《03-插件包格式》第六节）。
- 安装包签名（macOS、Windows）的密钥生命周期与信任根分发由《02-构建与打包》与《07-调试与发布》定义；发布流水线校验签名结果后才允许进入渠道。

### 5.4 渠道

| 渠道 | 内容 | 版本形态 |
|---|---|---|
| stable | 正式发布 | `MAJOR.MINOR.PATCH` |
| rc | 发布候选 | `-rc.N` |
| beta | 公测 | `-beta.N` |
| alpha | 内部验证 | `-alpha.N` |
| builtin（插件来源） | 平台内置插件 | 随平台版本发布，必须签名 |
| user（插件来源） | 用户安装的官方/第三方插件 | 独立版本；签名可选但必须提示 |
| development（插件来源） | 本地开发目录或调试包 | 不签名、禁止分发 |

- 渠道是发布终点，不是校验捷径：任何渠道都必须通过全部门禁与产物校验。
- development 产物不得进入 stable/rc/beta/alpha 或 builtin/user；目录态禁止分发（《03-插件包格式》2.7 节）。

### 5.5 发布记录

每次发布必须生成可复核、不可静默修改的发布记录，至少包含：

| 字段 | 内容 |
|---|---|
| 提交 | 发布提交 SHA |
| 版本 | 平台版本、插件版本与 `chip_standards_version` |
| 产物清单 | 每个产物的名称、sha256、`.cpk` 安装摘要 |
| 签名 | `keyId` 与签名校验结果 |
| 门禁报告 | 五阶段结果与覆盖率、性能数据 |
| 变更说明 | 本次发布的新增、修复与破坏性变更 |
| 豁免 | 无豁免；如存在记录在案的豁免，必须列出并注明偿还任务 |

- 发布记录随发布说明归档；发布说明与文档更新同 PR（R16、《03-变更与决策管理》）。
- 发布记录与产物摘要共同构成发布追溯链：从渠道产物可回溯到提交、门禁报告与签名。
