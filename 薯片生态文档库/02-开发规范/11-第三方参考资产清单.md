## 一、定位与边界

### 1.1 覆盖范围

本文登记 `OpenSourceProjectHandlingFolder/` 目录留存的 10 组第三方参考资产快照，以及它们与生态内工程（`Chips-*`、`Chip-*`）的处置关系：

- DPlayer 源码（DPlayer-master）与官方 wiki（DPlayer-master-wiki）；
- FlexLayout（FlexLayout）；
- GenOffice（GenOffice）；
- MusicPlayer（MusicPlayer-main）；
- iconMaker（iconMaker）；
- miniPaint（minipaint）；
- open-file-viewer（open-file-viewer）；
- Thorium Reader 源码（thorium-reader-develop）与官方 wiki（thorium-reader-repowiki）。

每个资产组的完整参数（用途、来源、许可证、处置、吸收位置、风险与限制、维护状态）见 §二；引入新资产、升级版本与移除资产的操作规则见 §三至 §五。

W5 起本文另设**源码移植随行运行时依赖登记**（§2.12 uvf G-3 判例、§2.13 office 三域臂）：随某源码移植资产一并进入插件运行时的第三方依赖，逐项登记许可证、用途、包体与结论；该节是 §1.2「运行时依赖清单以各包 `package.json` 为准」口径的许可复核例外位——清单只登记许可与选型结论，版本仍以包管理清单为单一事实源。

### 1.2 边界

- 本文只登记第三方参考资产本身及其处置关系，不复制通用依赖选型标准：选型评估项目、评分规则与关键依赖确认规则以[《架构原则》三、技术选型标准](../00-愿景与原则/01.04-01-架构原则-三、技术选型标准（Technology Selection Criteria）.md)为唯一权威，本文只规定参考资产特有的登记流程与合规要求。
- 平台与插件运行时的依赖清单不在本文维护：以各包 `package.json` / `pnpm-lock.yaml`（Cargo 侧 `Cargo.lock`） 为准，本文只登记"参考资产 → 工程依赖"的对应关系与已公开的许可与风险结论。
- 第三方插件（生态外开发者提交的插件）的权限与包内容评审不属于本文范围，见《权限系统设计》十。
- 用户提供的字体、图标、示例素材等设计资产的来源登记不在本文范围，其许可要求与本文 §四一致。

### 1.3 术语

- **参考资产**：为解决特定技术问题而获取的第三方源码、文档或工具，不一定进入交付产物。
- **快照**：存放于 `OpenSourceProjectHandlingFolder/` 的本地副本，包含上游许可证文件；快照是评估与对照材料，不构成正式运行时依赖。
- **处置**：对参考资产的处理决定，分四档——仅参考、思路吸收、源码移植、运行时依赖；判定与义务见 §3.2。
- **吸收位置**：参考资产被参考、改写或引入的生态内真实文件或工程。

| @tiptap/\*（core/react/extensions/pm） | 不引入 | 生态编辑引擎须唯一（裁决 3 明确统一 = Milkdown）；tiptap 与 milkdown 同为 ProseMirror 内核封装，并行引入即第二套编辑引擎，分层资产（schema/序列化/能力对照）无法复用；§2.13 登记外裁决行同步终局化 |
| 自研 ProseMirror 直接封装 | 不引入 | schema/输入规则/IME/序列化/表格 GFM 全套自维护成本高，无长期收益；Milkdown 的 remark 双向管线（mdast ↔ ProseMirror）与预设体系正是该问题的成熟解，符合「最有利于生态长期发展」准则 |
| slate.js / lexical 等其它编辑器框架 | 不引入 | 与裁决 3 相左；非 ProseMirror 内核，数据模型自成一体，Markdown 双向保真需自建，且与 rich-text-editor 应用臂、office word 域的统一引擎口径冲突 |
| 沿用 W4 契约基线表单（TextArea） | 不保留 | 基线形制是缺位期的官方契约形态，非终态；裁决 3 收口缺位后编辑臂升级为真编辑器（本节登记的触发事件） |

同源边界（本节登记的适用约束，消费方必须遵守）：

1. Markdown 唯一持久化不变：编辑态以 Milkdown remark 管线序列化回 Markdown 源文，不落编辑器内部 HTML；
2. 查看态 ↔ 编辑态同源：两态共用同一 `content_text` 与同一能力对照面（`markdown_capabilities` 声明 × 渲染链支持面）；渲染链（`chips.service.markdown`）暂无承载的扩展语法（`==高亮==` / `++下划线++` / `^上标^` / `~下标~` / `$数学$`）编辑态**不得**引入富渲染臂，双态统一按纯文本呈现 + 能力降级提示，待渲染链扩展臂统一收口，防止双态漂移；
3. file 来源正文：帧内读取通道缺位不变，编辑器不得以不可读正文回写覆盖 `content_file`（08 §4.3 变更分流纪律）。

升级与登记同步义务：`@milkdown/kit` 升版须重跑本节许可证核验并更新版本行（《3.5》）；后臂（rich-text-editor 应用、office word 域）启用时按各自消费面补充用途行，不新开 RA 编号。

## 三、引入与登记流程

### 3.1 触发条件

出现以下任一情形时，必须完成本节流程并在本文登记：

1. 引入新的第三方源码、工具、文档或素材作为参考资产；
2. 对已有资产组作出新的处置（例如从"仅参考"升级为"源码移植"或"运行时依赖"）；
3. 升级已登记的运行时依赖或源码移植来源版本；
4. 移除、替换或停止追踪已登记资产。

### 3.2 处置判定与义务

| 处置 | 判定 | 义务 |
|---|---|---|
| 仅参考 | 只阅读其文档或源码以获得思路，不复制代码、不引入依赖 | 快照落位；登记来源、版本与许可证；产物不含其任何代码或素材 |
| 思路吸收 | 借鉴设计或交互思路，由生态自行实现；可能复用可独立授权的素材 | 快照落位；登记；复用素材须逐文件核对许可并在资产目录单独署名 |
| 源码移植 | 复制或改写其源码进入生态工程（含 `vendor/` 搬运） | 保留上游版权与许可证声明；记录改写边界；通过正式构建链路参与产物；登记吸收位置到文件级 |
| 运行时依赖 | 经包管理器正式引入并进入运行时 | 完成《架构原则》三 §3.1 全部评估项；版本以包管理清单为准；登记包名与版本范围；升级须重评 |

- 判定必须落到唯一档位；同一资产的不同部分可按不同档位处置（如 GenOffice 引擎层"源码移植"、其 AI 能力"不适用"），但必须逐项写清。
- 关键依赖（改变基础架构、成为长期运行时依赖、影响公共协议）必须先记录方案并等待用户确认（《架构原则》三 §3.1）。

### 3.3 评估要求

1. 选型评估：按《架构原则》三 §3.1 执行全部评估项目与评分规则；结论写入登记行或吸收评估文档，不得只写"已评估"。
2. 来源与版本固定：记录上游仓库 URL、快照版本（tag / 版本号 / commit），无版本号资产的必须记录获取时间与来源渠道；快照未附来源的（见 RA-06）在补齐前不得再分发。
3. 许可证核验：检查许可证原文、`NOTICE`、附加许可目录（如 `ee/`）、内嵌第三方库与素材的独立声明，结论写入登记行的"许可证"字段。
4. 安全与跨端：核对已知漏洞、依赖链深度与桌面三端兼容性；结论并入选型评估记录。
5. 快照落位：参考资产快照统一存放 `OpenSourceProjectHandlingFolder/`，许可证文件随快照保留，禁止删除或改写。

### 3.4 登记步骤

1. 完成 §3.3 评估并确定处置档位；
2. 快照与许可证文件落位；
3. 在本文 §二追加登记：总览表追加一行（编号顺延 `RA-`），并新增该组的字段明细；
4. 在梳理表分片登记节点（覆盖状态、建议动作、证据到文件与行号）；
5. 由主代理更新文档库 README 索引与新增文档登记表（子智能体不得并发改写）；
6. 运行链接检查，确认 0 坏链。

### 3.5 升级与移除

- 升级：运行时依赖升级须重跑选型评估并更新登记行版本；源码移植升级须比对上游差异、更新移植边界说明并重跑消费方测试。
- 移除：禁止直接删除快照；按归档政策移入就近 `归档/`，在登记行标注处置变化与取代者，并同步吸收位置的代码与文档。

## 四、许可证合规要求

### 4.1 通用义务

1. 保留上游版权声明、许可证全文与免责条款，随源码与分发产物一并保留；
2. 不得移除、改写或替换上游版权头；改动源码时按许可证要求标注变更；
3. 再分发二进制或打包产物时，随附对应许可证与 `NOTICE`（若上游提供）；
4. 许可证兼容性结论必须写入选型评估记录；存在疑问时按《架构原则》六决策流程处理。

### 4.2 按许可证类型的要求

| 许可证 | 要求 |
|---|---|
| MIT | 保留版权声明与许可证文本；允许修改与再分发 |
| BSD-3-Clause | 保留版权声明、许可证文本与免责条款；不得以作者或组织名义为衍生品背书 |
| Apache-2.0 | 保留 `LICENSE` 与 `NOTICE`；对修改文件作显著变更声明；商标不随许可授予；附加许可目录（如 `ee/`）不得纳入 |
| GPL / LGPL / AGPL | 默认禁止进入插件产物与平台分发物；确需引入必须提 RFC 并经用户确认，且隔离为独立进程或可选依赖；已登记的未启用链路（`libredwg-web`）不得启用 |

### 4.3 素材与文档

- 图片、字体、音频、示例数据按各自许可证单独登记，不随源码许可证自动覆盖；测试素材（音频、样例）一律不得随产物分发。
- wiki 与文档快照随仓库许可证使用，引用时必须标注"仅存档理解、不作为依据"，且不得作为实现依据（见 RA-02、RA-10）。

### 4.4 产物随附基线

- 源码移植产物的许可证随附以 `Chips-Office/vendor/`（`LICENSE`、`NOTICE`、`LICENSE-UNICODE.txt`）、`chips-ecosystem/plugins/apps/universal-file-viewer/src/engine/LICENSE.open-file-viewer`（W5 迁移后随引擎目录随附）、`Chips-BookReader` 移植代码的 BSD 版权头为基线样例；
- 新增源码移植资产时，许可证随附方式必须与上述基线一致。

## 五、禁止事项

| 编号 | 禁止事项 | 正确做法 |
|---|---|---|
| 01 | 未经评估与登记引入第三方参考资产或依赖 | 按 §三 完成评估、处置判定与登记 |
| 02 | 移除、改写上游版权声明与许可证文本 | 原样保留，变更另附说明 |
| 03 | 未经处置判定把快照源码复制进产物 | 先判定处置档位；源码移植须保留声明并登记吸收位置 |
| 04 | 把参考快照当作正式运行时依赖 | 运行时依赖一律经包管理器正式引入并登记 |
| 05 | 以 wiki / 文档快照作为实现依据 | 回到当前源码或正式文档核对 |
| 06 | 将 GPL / LGPL / AGPL 依赖引入插件产物或平台分发物 | 默认禁入；确需引入走 RFC 与用户确认并隔离 |
| 07 | 使用上游商标、品牌名与 Logo | 使用生态自有品牌命名与素材 |
| 08 | 引入来源不可追溯的代码或素材（无 URL、无许可证） | 补齐来源与许可后再登记 |
| 09 | 测试素材（音频、样例图片、示例数据）随产物分发 | 交付物剔除测试素材，仅在快照保存 |
| 10 | 登记行与实际实现不一致（吸收位置、版本、处置漂移） | 资产变化时同步更新本文、梳理表与实现 |
| 11 | 以第三方参考资产为由绕过前端样式、Token 与组件库约束 | 样式与组件一律遵守《统一视觉规范》《@chips/ui 共享层使用指南》 |

## 六、约束与自检清单

### 6.1 约束

1. 登记册穷尽：`OpenSourceProjectHandlingFolder/` 下每组资产在 §二有且仅有一条登记；新增、升级、移除时同轮更新。
2. 单一事实源：资产的上游、版本、许可证、处置与吸收位置只在本文 §二定义一次；其他文档引用本文，不复制登记参数。
3. 证据可定位：每条"吸收位置"必须指向真实存在的工程路径；维护状态结论必须注明观测时点与依据。
4. 吸收位置与代码一致：登记前重新核对当前代码；发现漂移时以代码为准更新登记并记录差异。
5. 登记与梳理表同步：本文变更必须跟随梳理表分片与新增文档登记（第 5 步由主代理执行）。

### 6.2 自检清单

- [ ] 新增资产已按 §3.3 完成选型评估、来源固定与许可证核验？
- [ ] 处置档位唯一且义务已履行（版权头、声明、登记、随附）？
- [ ] 登记总览与字段明细已同步，编号顺延且路径真实？
- [ ] 吸收位置在当前代码中真实存在，无漂移？
- [ ] 许可证文件、`NOTICE`、附加许可目录与内嵌第三方库均已核对？
- [ ] GPL 系链路未被启用，测试素材未进入交付物？
- [ ] 升级 / 移除已更新本文与吸收位置，快照按归档政策处理？
- [ ] 链接检查 0 坏链，梳理表分片已登记？
