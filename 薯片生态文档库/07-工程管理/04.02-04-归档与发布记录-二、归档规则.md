## 二、归档规则

### 2.1 总则与触发

归档是"内容退役"的正式动作：被替代、被废弃、工程冻结、任务结束或失败尝试留存时执行。归档不改变内容本身，只改变落位并补充说明。

三条硬规则：

1. **禁止删除**：任何文件、目录与历史内容都不得直接删除；
2. **就近归档**：退役内容移入离它最近的 `归档/` 目录（§2.2）；
3. **有据可查**：每个归档单元必须留下归档说明与索引记录，写明退役原因与替代者。

补充规则：

- 归档内容只读：不得在归档目录内继续开发、修改既有文件或新增业务内容；后续补充只能追加归档说明中的时间线条目。
- 归档不作为技术依据：现行文档、代码与测试不得引用归档内容作为契约、字段、错误码或数值来源；历史说明中引用归档时，必须标注"仅存档、不作为依据"。
- 归档是永久状态：内容移入归档后不再迁出现役目录；确需恢复使用时，复制或重写为新资产，不把归档目录改回现役。

### 2.2 位置与目录约定

| 归档位置 | 适用对象 | 示例 |
|---|---|---|
| 工作区根 `归档/` | 跨项目历史单元：工程已不存在的整仓归档、平台级废弃体系、失败移植尝试、工作区级历史材料 | `归档/ThemePack/`、`归档/Chips-ComponentLibrary/` |
| 工程内 `<工程>/归档/` | 仍在经营的工程内部的局部退役内容 | 插件集合内的单个旧插件、旧页面、旧脚本 |
| 文档库 `<分区>/归档/` | 被取代或并入的正式文档 | `薯片生态文档库/02-开发规范/归档/01-Rust编码规范-已并入04.md` |
| `项目日志与笔记/归档/` | 任务目录整体或部分退役、误登记材料 | 被废弃的排查笔记、误登记的任务材料 |

就近判定顺序：

1. 退役内容所属工程仍存在 → 该工程内 `归档/`；
2. 所属工程已不存在 → 工作区根 `归档/`；
3. 文档被取代或并入 → 所在分区的 `归档/`；
4. 任务过程材料退役 → `项目日志与笔记/归档/`。

粒度与边界：

- 一个可独立说明的目录或文件为一个归档单元；禁止在归档目录内嵌套多重无语义层级。
- 工程内 `归档/` 与工作区根 `归档/` 平级协作：工程级单元进工程归档并登记到工作区总索引；跨工程与无主单元进工作区根归档。
- 文档库 `归档/` 不参与分区索引收录（[01-代码组织规范](../02-开发规范/01-代码组织规范.md) 第 2.4 节）。

### 2.3 命名

- 归档单元目录名保留原名，不重命名、不规范化；目录名含日期、版本或批次前缀时原样保留（如 `2026-04-10-统一文档窗口`），保证历史引用与检索一致。
- 归档说明文件固定名 `归档说明.md`；工作区根 `归档/README.md` 是总索引，只做索引与时间线，不替代单元说明。
- 文档库归档文件命名：`<原编号>-<名称>-<处置标注>.md`；处置标注取 `已并入NN`、`已废弃`、`已替代`，标注必须与归档依据一致。
- 禁止归档命名使用"临时""最终版""最新"等无判定意义的词；禁止用空格或全角符号替换原有分隔符。

### 2.4 索引

索引分三层，互为对照：

1. **工作区总索引** `归档/README.md`：登记全部工作区级归档单元与工程级归档单元的映射；每次归档动作必须更新。登记字段固定：

   | 字段 | 内容 |
   |---|---|
   | 归档时间 | `YYYY-MM-DD` |
   | 源路径 | 工作区根相对路径 |
   | 归档单元 | 单元名与目标归档位置 |
   | 原因 | 被替代 / 已废弃 / 失败尝试 / 工程冻结 / 任务结束 / 误登记 |
   | 替代者 / 去向 | 取代该内容的现役工程、文档，或"无" |
   | 元信息状态 | 有说明 / 缺说明 |

2. **工程内索引** `<工程>/归档/README.md`：该工程归档单元不少于一个时必须存在，登记字段同上；工程内归档动作同时更新工程索引与工作区总索引。
3. **文档库归档**：归档文档在原分区 `归档/` 内成组存放，文件名保留处置标注；不进入 README 分区索引，被取代关系记录在处置标注与归档说明中。

反向索引：单元内 `归档说明.md` 记录来源路径与替代者，与正向索引互为对照；任何一侧缺失即视为归档未完成。

### 2.5 元信息（归档说明.md）

每个归档单元必须有一份 `归档说明.md`，字段固定：

| 字段 | 必填 | 内容 |
|---|---|---|
| 归档时间 | 是 | `YYYY-MM-DD` |
| 归档单元 | 是 | 单元名与工作区根相对来源路径 |
| 归档原因 | 是 | 被替代 / 已废弃 / 失败尝试 / 工程冻结 / 任务结束 / 误登记 |
| 替代者 | 是 | 取代该内容的现役工程、文档或"无" |
| 依据 | 是 | ADR 编号、裁决条目或任务编号 |
| 内容摘要 | 是 | 该单元是什么、最后可用状态，不超过三句 |
| 状态 | 是 | `保留` / `已替代` / `待处置` |
| 迁移映射 | 条件 | 执行过归档迁移时写目标归档单元与迁移时间 |

- 状态只用三值：`保留`（仍作历史参考）、`已替代`（已有替代者）、`待处置`（去向未定）；不存在"可删除"状态（§1.3）。
- 已有的有效说明不得改写，只能在其后追加时间线条目（追加时间、追加事由、追加内容）。
- 批量归档中，每个单元各有一份说明；禁止用一个批次说明替代单元说明。

### 2.6 归档动作流程

```
[1] 判定：触发原因 → 就近位置（§2.2）→ 归档单元粒度
        ▼
[2] 移动：以保留历史的移动方式（git mv）移入目标归档目录，不复制、不改内容
        ▼
[3] 说明：新建或更新 归档说明.md（§2.5），已有说明只追加
        ▼
[4] 索引：更新工程索引与工作区总索引（§2.4），追加登记行
        ▼
[5] 引用：全仓检索旧路径，更新全部引用方；引用归档时标注"仅存档、不作为依据"
        ▼
[6] 复核：链接检查 0 坏链、索引与实际目录一致、无悬空引用、无内容改动
```

执行纪律：

- 归档动作与说明、索引、引用更新必须同批提交；禁止先移动后补说明。
- 批量归档按单元逐个执行；一个提交只处理同一归档目标下的单元。
- 归档前必须检索旧路径引用（文档、代码、脚本、索引）；无法确认引用方时不得移动。
- 归档复核以 §七 自检清单为准，未通过不得标记归档完成。

### 2.7 归档与旧版文档库的区别

`旧版-生态共用技术文档/`、`旧版-生态设计原稿/`、`旧版-项目日志与笔记/` 是冻结的旧版文档库整体，不是归档单元：它们按 [ADR-010：大爆炸重构策略](../01-架构设计/ADR/ADR-010-大爆炸重构策略.md) 保持冻结状态，不参与 §五 迁移，也不得在其内部执行归档动作；其中仍有效的内容按对口权威文档迁入新库后，原件保留原处。
