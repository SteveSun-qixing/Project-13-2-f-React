## 三、发布记录制度

### 3.1 记录定义与落位

1. 发布记录是每次发布的追溯凭证：从渠道产物可回溯到提交、产物摘要、签名、门禁报告与变更说明（[05-CICD与质量门禁](../06-开发与运维/05-CICD与质量门禁.md) §5.5、[06-更新与分发规范](../06-开发与运维/06-更新与分发规范.md) 第六节）。
2. 落位：`项目日志与笔记/发布记录/`。发布记录是过程材料（R10），不进入文档库，也不作为技术契约的发布位置。
3. 命名：`V<版本>-<渠道>.md`（如 `V0.01-alpha.md`、`V1.0.0-stable.md`）。同一版本的多个平台、多个批次写在同一个文件内，以"发布批次"分节；版本号语法与渠道取值引用权威文档（§3.2），本文不另立。
4. 索引：`项目日志与笔记/发布记录/README.md` 必须存在，按发布先后维护以下字段：

   | 版本 | 渠道 | 发布日期 | 提交 | 状态 | 记录 |
   |---|---|---|---|---|---|

   状态取值：`已发布` / `已暂缓` / `已撤回` / `失败恢复`；状态变化只能新增行或追加记录，不删除历史行。

5. 服务端发布（社区平台、个人服务器）在同一目录登记，额外字段（镜像摘要、迁移范围、回滚窗口）按 [08-服务端部署与运维](../06-开发与运维/08-服务端部署与运维.md) 第九节执行。

### 3.2 记录字段与权威来源

发布记录逐项填写；每一项的定义与判定以权威文档为准，本文只规定"必须记录"：

| 记录项 | 记录要求 | 权威来源 |
|---|---|---|
| 版本号 | 平台版本、本次包含的插件版本清单、`chip_standards_version`；三者与发布 tag 一致 | [04-版本与迁移规范](../04-文件格式规范/04-版本与迁移规范.md) 第二节 |
| 提交 | 发布提交 SHA 与附注标签 `v{major}.{minor}.{patch}` | [06-Git工作流规范](../02-开发规范/06-Git工作流规范.md) |
| 产物清单 | 每个产物的名称、平台/架构、字节数、`sha256`；`.cpk` 另记安装摘要 | [06-更新与分发规范](../06-开发与运维/06-更新与分发规范.md) §5.2、[02-构建与打包](../06-开发与运维/02-构建与打包.md) 第九节 |
| 校验和 | 摘要清单的生成与 `verify` 结果；记录中的摘要与摘要清单逐字节一致 | [02-构建与打包](../06-开发与运维/02-构建与打包.md) §6.6、§9.4 |
| 签名 | 安装包代码签名与公证结果、`.cpk` 的 `keyId`/算法/校验结果、更新索引签名结果 | [02-构建与打包](../06-开发与运维/02-构建与打包.md)、[03-插件包格式](../04-文件格式规范/03-插件包格式.md) 第六节 |
| 渠道与分发 | 渠道、发布时间、灰度 `rollout` 与 `paused` 快照、离线包分发位置 | [05-CICD与质量门禁](../06-开发与运维/05-CICD与质量门禁.md) §5.4、[06-更新与分发规范](../06-开发与运维/06-更新与分发规范.md) §2.1 |
| 门禁报告 | 五阶段结论、覆盖率与性能数据；存在豁免时列出豁免项与偿还任务 | [05-CICD与质量门禁](../06-开发与运维/05-CICD与质量门禁.md) 第五节 |
| 变更说明 | 新增、修复与破坏性变更；重大变更引用 RFC / ADR 编号 | [03-变更与决策管理](./03-变更与决策管理.md) |
| 迁移 | 涉及文档格式或用户数据时的迁移工具、说明与验证结果；无则写"无" | [04-版本与迁移规范](../04-文件格式规范/04-版本与迁移规范.md) 第六、七节 |
| 回滚与失败恢复 | 按 §3.4 记录 | 本文 §3.4、[06-更新与分发规范](../06-开发与运维/06-更新与分发规范.md) §2.4 |
| 归档去向 | 发布记录与摘要清单的保存位置、产物不入库与重建命令 | 本文 §3.5、[01-代码组织规范](../02-开发规范/01-代码组织规范.md) 第七节 |

- 预发布渠道（`rc` / `alpha`）的验证结论必须回写对应发布记录（[06-更新与分发规范](../06-开发与运维/06-更新与分发规范.md) §2.1）。
- 灰度比例调整不产生新版本号，但必须追加发布记录（同上 §2.5）；暂停与恢复同样追加。
- 记录中的数值一律引用权威文档的数值，禁止转述或自造（[03-变更与决策管理](./03-变更与决策管理.md) 第七节）。

### 3.3 校验和与追溯链

1. 摘要的生成入口唯一：摘要清单工具（`tools/scripts/checksums.mjs`，[02-构建与打包](../06-开发与运维/02-构建与打包.md) §6.6）；发布记录中禁止手抄摘要而不经核对。
2. 一致性三元组：发布记录摘要 = `release/SHA256SUMS.txt` = 更新索引 `package.sha256`；`.cpk` 安装摘要另行与 `contentHash` 对照。任一不一致即发布缺陷，阻断发布（[05-CICD与质量门禁](../06-开发与运维/05-CICD与质量门禁.md) §4.5）。
3. 追溯链方向：渠道产物 → 摘要清单 → 发布记录 → 发布提交 → 门禁报告与 ADR / RFC。链条各节点必须可独立定位。
4. 确定性：同一提交、同一输入重新构建必须得到相同摘要；记录中出现摘要变化即说明产物不可复现，按缺陷处理，禁止带漂移发布。

### 3.4 回滚与失败恢复记录

平台不提供用户主动降级安装（[06-更新与分发规范](../06-开发与运维/06-更新与分发规范.md) 第四节），因此"回滚"在发布记录中只对应三类事件：

| 事件 | 触发 | 必须记录 |
|---|---|---|
| 更新失败恢复 | 安装替换失败 `apply-failed`、新版本首次启动自检失败 `boot-failed` | 版本、平台/架构、失败阶段、诊断摘要、恢复动作（回到更新前状态）、暂停的渠道、修复版本与关闭条件 |
| 发布撤回 / 暂缓 | 发现阻断缺陷，索引置 `paused: true` 或下调 `rollout` | 时间、索引变更内容、原因、已更新设备影响范围、恢复条件与恢复时间 |
| 服务端回滚 | 服务端发布验证失败，回退到上一版本 | 按 [08-服务端部署与运维](../06-开发与运维/08-服务端部署与运维.md) 第九节登记：回滚原因、时间、影响与验证结果 |

纪律：

- 失败恢复与撤回事件在发布记录内追加"失败与恢复"节，不覆盖原始发布字段。
- 失败恢复不是版本回退：禁止把"回到更新前状态"记为"降级安装"。
- 同版本 `apply-failed` / `boot-failed` 后不自动重试；修复必须发布更高版本，并登记修复版本与失败版本的对应关系。
- 发布失败重发必须递增版本号；禁止移动、删除或重打已推送的 tag（[05-CICD与质量门禁](../06-开发与运维/05-CICD与质量门禁.md) §5.1）。

### 3.5 修订纪律与生命周期

1. 记录只增不改：已写入字段不得修改；信息变化以追加条目表达（追加时间、追加事由、追加内容）。
2. 发布记录永久保留、不清理；对应产物不入库，按记录中的重建命令重新生成。
3. 渠道停止分发（版本下线）时，在索引中追加状态并注明最后分发时间，不删除记录。
4. 一个版本存在多次撤回 / 恢复时，全部事件按时间顺序记录；索引状态取最新事件。
5. 记录的任何引用（摘要清单、门禁报告、签名结果）必须能在产物目录或 CI 工件中定位；引用失效即视为记录缺陷。
