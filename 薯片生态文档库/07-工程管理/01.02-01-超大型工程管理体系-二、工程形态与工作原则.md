## 二、工程形态与工作原则

### 2.1 工程形态

| 维度 | 事实 |
|---|---|
| 代码规模 | 预计 50 万行以上，随插件生态持续增长 |
| 技术栈 | Rust（核心）+ Neon（Native Module）+ Electron（壳）+ React（界面）+ Cordis（插件运行时） |
| 子系统 | 10 个以上核心子系统：内核、Bridge、插件系统、渲染引擎、资源管理、文档解析、权限、事件、配置、同步 |
| 外部依赖 | Electron、Rust 生态、Node.js 生态、fork antd |
| 平台 | macOS / Windows / Linux / Android / iOS 五端共享 `.card` / `.box` 格式、Rust 核心与 Bridge 接口；实现优先级与阶段见[《薯片生态白皮书》](../00-愿景与原则/00-薯片生态白皮书.md) |
| 交付形态 | 三端安装包 + `.cpk` 插件包 + `.card` / `.box` 内容文件 |

### 2.2 工程挑战与对应机制

| 挑战 | 机制 |
|---|---|
| 架构复杂度（多层次、跨语言） | 四层文档体系（第三章）+ ADR 决策记录（第八章） |
| 依赖管理（单仓、跨语言、循环依赖） | Monorepo + 依赖矩阵 + 循环依赖门禁（[代码组织规范](../02-开发规范/01-代码组织规范.md)） |
| 质量保证 | 质量门禁（第六章），数值唯一登记在本文与[《架构原则》](../00-愿景与原则/01-架构原则.md) |
| 文档同步 | 文档与代码同一 PR 更新；不一致视为缺陷（第七章） |
| 变更管理 | RFC → 评审 → ADR → 实施 → 质量门禁 → 文档同步（第七章） |
| 知识传承 | ADR 永久记录、技术债清单、过程材料与正式文档分离（第八章） |

### 2.3 工作原则

1. **文档先行**：先有原则，再有设计，最后写代码。
2. **决策可追溯**：每个重大决策都有 RFC 与 ADR。
3. **门禁强制**：门禁不通过不得合并、不得进入下一阶段。
4. **单一事实源**：同一事实只写一处，其余文档引用。
5. **文档即代码**：文档与代码同 PR 维护，准确到可复刻实现。
6. **无兼容包袱**：第一版发布前不做兼容层、弃用周期与回退机制。
