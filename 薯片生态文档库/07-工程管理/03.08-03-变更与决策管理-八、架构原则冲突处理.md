## 八、架构原则冲突处理

### 8.1 流程

```
[1] 识别冲突    需求或实现与《架构原则》的设计哲学、红线、选型标准、质量基线冲突
        │
        ▼
[2] 重审需求    是否必须？能否在原则内实现？
        ├── 能 ──→ 调整需求或方案，按变更分级继续
        └── 不能
        ▼
[3] 修订原则    RFC → 评审 → ADR；更新《架构原则》文本与版本头
        │
        ▼
[4] 全库同步    同一变更内同步全部引用该原则的文档、契约、门禁与实现
        │
        ▼
[5] 复核        门禁通过、冲突消除、无临时绕过残留
```

### 8.2 规则

- 冲突未决期间不得开工：禁止"先按冲突方案实施、后补评审"。
- 禁止在代码、配置或文档中留下原则的临时绕过；发现即按缺陷修复（[01-架构原则](../00-愿景与原则/01-架构原则.md) 第 6.2 节）。
- 修订原则必须记录 ADR，并在同一变更内核对全库引用：术语、规则编号、示例与门禁读数不得出现第二套口径。
- 质量、性能与安全基线的调整同样走本流程。
- POC 阶段的简化实现不属于冲突，但 POC 代码与结论不得直接进入正式交付路径；进入 Phase 1 后必须完整实现（[01-架构原则](../00-愿景与原则/01-架构原则.md) 第 2.6 节）。
- 发现既有文档或实现与原则冲突时：能立即修正的按缺陷同 PR 修正；确认为架构缺口的按工单流程登记，不得静默保留。
