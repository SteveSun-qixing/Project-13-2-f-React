## 九、阶段准入与准出规则

### 9.1 通用准入规则

进入任一阶段必须同时满足：

1. 上一阶段已准出并留下可复核记录（Phase 0 为起点，无此要求）；
2. 本阶段所依赖的接口、契约与设计文档已发布，且与当前实现一致；
3. 工具链与 CI 可用，构建与测试可在干净环境复现；
4. 无未闭环的 P0/P1 技术债（技术债管理与清单见[03-变更与决策管理](./03-变更与决策管理.md)）；
5. 本阶段所需的能力与权限已在能力总表登记（Phase 1 起，R19）。

### 9.2 通用准出规则

准出任一阶段必须同时满足：

1. 交付物齐全，DoD 全项通过，逐项留存证据（测试与基准报告、门禁记录、评审结论）；
2. 质量门禁全量通过，且与本阶段对应的档位一致（第十章）；
3. 文档与代码在同一变更内同步完成（R16）；
4. 不存在 TODO、占位实现与临时简化；POC 代码不进正式链路；
5. 无未闭环的 P0/P1 技术债；
6. 阶段产物可作为下一阶段的可运行基线，且已在干净环境验证。

### 9.3 阶段准入/准出对照

| 阶段 | 准入前提 | 准出标志 |
|---|---|---|
| Phase 0 | 无（起点） | 文档库 + Monorepo 骨架 + POC 全部通过 |
| Phase 1 | Phase 0 准出 | 最小原型可演示，接口与契约一致 |
| Phase 2 | Phase 1 准出 | 子系统完整，覆盖率 >80%，Phase 2 档性能达标 |
| Phase 3 | Phase 2 准出 | 核心插件日常可用，CLI 与开发者文档就绪 |
| Phase 4 | Phase 3 准出 | 迁移工具 + 三端验证 + v1.0 发布 |
| Phase 5 | Phase 4 准出 + 所有者决策 | 移动端交付并通过门禁（暂不排期） |

### 9.4 阻塞与例外处理

1. **POC 不通过**：不得进入 Phase 1；调整方案后重新验证，方案变更走 RFC → 评审 → ADR（R16）。
2. **门禁不达标**：在同一变更内修复；确需调整基线时，必须以数据证明并走变更流程，不得以"后续优化"推迟（架构原则 §4.2）。
3. **文档与实现不一致**：视为缺陷，在同一变更内修复（R16）。
4. **发现架构缺口、组件或链路缺失**：登记问题工单并继续推进不受影响的部分，不得以临时实现绕过。
