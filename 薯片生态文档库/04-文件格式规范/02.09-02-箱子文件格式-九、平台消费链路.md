## 九、平台消费链路

### 9.1 平台统一解析

用户实际消费箱子时，由平台负责处理寻找所有卡片文件：

```text
打开 .box
  → 校验包结构（四个必需文件、内嵌引用目标、包内无 .box）
  → 读取 metadata.yaml / structure.yaml / content.yaml
  → 按 structure.yaml 的 url 逐项解析卡片资源
    （本地文件定位 / 网络访问 / 凭证注入 / 缓存命中 / 失败状态归一）
  → 生成箱子运行时数据模型（摘要条目 + 布局配置 + 资源）
  → 按 active_layout_type 装载对应布局插件并交给布局插件渲染
```

- "寻找"不仅包括本地文件定位，也包括网络访问、凭证注入、缓存命中、失败状态归一等运行时能力。
- 平台生成箱子运行时数据模型后，把资源和状态统一反馈给布局插件。
- 平台内部有统一的卡片信息读取模块；整个生态如果需要卡片的状态、标准化元数据、封面等信息，都统一向这个模块请求，由它返回正式结构，不允许箱子、查看器、布局插件各自再定义第二套卡片信息读取逻辑。
- 布局插件不直接扫描磁盘，不直接自行维护一套查找卡片的逻辑；文件系统、网络、凭证、资源定位和失败处理都属于平台职责。

### 9.2 首屏与按需取数

首屏渲染优先使用：

1. `metadata.yaml`
2. `structure.yaml` 的摘要字段
3. `content.yaml`
4. `assets/` 中的布局资源

平台不要求一次性解析全部卡片，只在布局插件申请时动态获取：

1. 详细元数据；
2. 封面资源；
3. 预览资源；
4. 卡片入口资源；
5. 自定义运行时字段。

### 9.3 条目摘要与封面

- 箱子的默认浏览态是**条目摘要态**：直接渲染卡片封面、名称和摘要，而不是默认展开整张卡片。
- 布局插件在显示条目封面时，应优先调用平台受控封面渲染接口，由平台返回标题、封面地址和比例等信息；布局插件不应把封面资源推断逻辑作为自己的默认职责。
- 条目引用的如果是箱子，平台继续复用目标箱子的 `.box/cover.html` 正式封面入口；嵌套箱子在浏览态显示封面，不就地展开。

### 9.4 条目激活

- 用户点击封面后，由平台中的专门条目激活模块负责决定如何打开对应卡片，并打开新的窗口显示卡片正式查看内容。
- 布局插件只发起正式打开请求，不自行实现新窗口逻辑，也不自行拼接卡片文件路径。

### 9.5 失败归一

- 单个条目定位失败、网络不可达、凭证缺失或目标失效时，由平台归一为条目失败态/离线提示；条目在布局中显示封面占位或失败态，不阻断整箱打开，也不影响其他条目。
- 条目状态变化通过正式接口反馈给布局插件，布局插件不自行探测文件与网络。
