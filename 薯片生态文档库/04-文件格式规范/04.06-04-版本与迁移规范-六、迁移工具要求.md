## 六、迁移工具要求

### 6.1 定位与范围

- 迁移工具是 Phase 4 交付物：把旧版生态的用户数据文件迁移为当前格式（R7、ADR-010）；
- 输入：旧版 `.card` / `.box` 文件（目录态或归档态），不依赖旧版运行时；
- 输出：符合当前 `chip_standards_version` 的合规 `.card` / `.box`；
- 不迁移插件配置与平台配置：配置迁移机制见 [10-配置系统设计](../01-架构设计/01-子系统设计/10-配置系统设计.md) §八；
- 迁移工具不是兼容层：它独立于解析器与渲染器运行，迁移逻辑不得进入解析器（[06-文档解析器设计](../01-架构设计/01-子系统设计/06-文档解析器设计.md) §7.3）；
- 与两态转换的关系：迁移只负责**版本升级**（旧 `chip_standards_version` → 当前版本），不负责形态转换；导入归档 → 工作区目录态、目录态 → 归档导出与另存由 `document:export` 承担（[11-文档服务设计](../01-架构设计/01-子系统设计/11-文档服务设计.md) §4.7），正式流程与落位规则见[13-工作区设计](../01-架构设计/01-子系统设计/13-工作区设计.md)。需要升级的两态文档先迁移、再转换（或先转换、再迁移），两步都属于显式用户操作，任何一步都不得改写输入文件。

### 6.2 功能要求

1. **只读源文件**：绝不修改、移动或删除输入文件；
2. **显式发起**：迁移由用户显式调用；平台不得自动改写用户文件；
3. **迁移到当前格式**：迁移目标固定为当前 `chip_standards_version`；不输出旧版本文件，不猜测缺失的转换语义，缺少所需转换能力时按 §6.6 报错；
4. **原子输出**：单个输出先写临时文件，校验通过后原子重命名；失败时不得留下半成品；
5. **逐文件独立**：单个文件失败不影响其它文件继续迁移；
6. **输出必检**：每个输出必须通过文档 `validate`；状态为 `Invalid` 的输出禁止交付，`ValidWithWarnings` 必须记录全部警告；
7. **资源完整性**：重新计算并写回资源清单的 `hash` 与 `size`；源资源缺失或不匹配时该文件迁移失败并记录诊断；
8. **未知字段显式报告**：无法映射的字段统一列入报告的 `droppedFields`，不得静默丢弃；
9. **幂等**：输入已是当前 `chip_standards_version` 时报告为 `skipped`，不重写、不报错；
10. **确定性报告**：文件按路径排序，逐文件状态与统计字节级稳定，便于复核与审计。

### 6.3 命令

```bash
# 迁移旧版数据到当前格式
chips migrate <源目录> --out <输出目录> --report <报告文件>

# 只读扫描并生成报告，不产生输出
chips migrate <源目录> --dry-run
```

退出码：

| 退出码 | 含义 |
|---|---|
| `0` | 全部文件迁移成功或跳过 |
| `1` | 存在失败文件（报告给出逐文件原因） |
| `2` | 参数、环境或输出目录错误，未开始迁移 |

### 6.4 报告格式

```json
{
  "tool": "chips-migrate",
  "chipStandardsVersion": { "from": "0.9.0", "to": "1.0.0" },
  "files": [
    {
      "source": "旧数据/我的卡片.card",
      "status": "migrated",
      "chipStandardsVersion": { "from": "0.9.0", "to": "1.0.0" },
      "output": "迁移结果/我的卡片.card",
      "resources": { "checked": 12, "mismatched": 0 },
      "droppedFields": ["metadata.legacyId"],
      "warnings": []
    },
    {
      "source": "旧数据/损坏.box",
      "status": "failed",
      "error": {
        "code": "DOCUMENT_ARCHIVE_INVALID",
        "message": "归档损坏，无法读取"
      }
    }
  ],
  "totals": { "total": 2, "migrated": 1, "skipped": 0, "failed": 1 }
}
```

### 6.5 完整性验证

- 每个输出在交付前必须完成两重验证：`validate` 结构校验 + 资源清单的哈希与尺寸全量核对；
- 验证不通过的文件按失败处理，不得混入成功统计；
- Phase 4 交付 Definition of Done 包含：迁移工具稳定、逐文件报告可复核、抽样与全量数据完整性验证通过（R7）。

### 6.6 迁移错误码

| 错误码 | 含义 | 可重试 |
|---|---|---|
| `MIGRATION_SOURCE_UNKNOWN` | 输入文件无法识别为可迁移的旧版格式 | 否 |
| `MIGRATION_STEP_MISSING` | 缺少从输入版本迁移到当前格式所需的转换步骤 | 否 |
| `MIGRATION_FAILED` | 迁移执行失败（含资源读取与写入错误） | 是 |
| `MIGRATION_VALIDATION_FAILED` | 输出未通过 `validate` 或资源完整性核对 | 否 |
| `MIGRATION_OUTPUT_CONFLICT` | 输出路径已存在且未显式允许覆盖 | 否 |
