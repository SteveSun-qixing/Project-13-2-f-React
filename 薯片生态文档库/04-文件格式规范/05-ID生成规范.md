# ID生成规范

> 版本：v1.0.0
> 日期：2026-09-19
> 状态：正式版
> 适用范围：`.card` / `.box` 四类文件级标识（`card_id`、`box_id`、内容节点 ID、条目 `entry_id`）的字符集与长度、生成算法要求、生成责任与时机、机器标识口径、冲突检测与处理、校验规则、隐私与不可枚举要求，以及与文件名和迁移的关系；不覆盖插件 ID、能力与权限 ID、运行时标识与服务端实体 ID。

---

## 一、定位与边界

1. 本规范是四类文件级标识的**生成与校验权威**：字符集、长度、随机性、作用域唯一性、冲突处理与隐私口径只在此处定义；字段出现位置与字段级 schema 仍以[《01-卡片文件格式》](./01-卡片文件格式.md)、[《02-箱子文件格式》](./02-箱子文件格式.md)为准，本规范不重复字段表。
2. 覆盖范围与类型归属（四类 ID 共用同一字符集与生成算法）：

| 类型 | 文件字段与位置 | 作用域（唯一性范围） |
|---|---|---|
| 卡片 ID（`card_id`） | `.card/metadata.yaml` 的 `card_id`（[01-卡片文件格式](./01-卡片文件格式.md) §四） | 文档级稳定标识，`documentId` 的取值来源 |
| 箱子 ID（`box_id`） | `.box/metadata.yaml` 的 `box_id`（[02-箱子文件格式](./02-箱子文件格式.md) §四） | 同上（箱子） |
| 内容节点 ID | `.card/structure.yaml` 的 `structure[].id`，对应 `content/{id}.yaml`；渲染视图与写入接口中命名为 `node_id` / `nodeId` | 单张卡片内唯一 |
| 条目 ID（`entry_id`） | `.box/structure.yaml` 的 `entries[].entry_id` | 单个箱子内唯一 |

3. 不属于本规范（各自权威位置）：
   - 插件 ID、基础卡片类型 ID、布局类型 ID、错误码分层：R20（[01-架构原则](../00-愿景与原则/01-架构原则.md) 附录）；
   - 能力 ID 与权限 ID：[04-能力契约规范](../05-接口与契约/04-能力契约规范.md)；
   - 资源作用域 ID、事件 ID（ULID）、Bridge 调用 ID（UUID v4）、同步范围 ID 等运行时标识：各自协议与子系统设计；
   - 服务端实体 ID（社区平台 / 个人服务器的内容实体 ID，UUID v4）：[11-社区平台API契约](../05-接口与契约/11-社区平台API契约.md)、[12-个人服务器API契约](../05-接口与契约/12-个人服务器API契约.md)；
   - `documentId` 不是独立 ID 类型，是 `card_id` / `box_id` 的统一别名（[11-文档服务设计](../01-架构设计/01-子系统设计/11-文档服务设计.md) §3.1）；服务端 API 中的 `cardFileId` / `boxFileId` 即两份 metadata 中的 `card_id` / `box_id`（[11-社区平台API契约](../05-接口与契约/11-社区平台API契约.md) §二）。
4. 红线：四类 ID 必须是**随机、不透明、不可枚举**的标识串，不承载任何业务、时间、设备或序列语义；生成只允许发生在平台受控链路中（§四）。

## 二、字符集与长度

1. 统一口径：全部四类 ID 固定为 **10 个字符**，字符集为 Base62（`0-9`、`a-z`、`A-Z`），格式文法为：

```
^[0-9A-Za-z]{10}$
```

2. 大小写敏感：`a` 与 `A` 是不同字符；ID 在存储、序列化、比较与匹配全过程中按原样处理，禁止大小写归一化，禁止不区分大小写的比较（唯一例外是节点 ID 的文件系统等价查重，见 §七.2.5）。
3. 一律按字符串处理：允许前导 `0`、允许以数字开头；禁止把 ID 解析为数值、参与数值运算或作为排序键。顺序由 `structure` / `entries` 数组声明顺序决定（[01-卡片文件格式](./01-卡片文件格式.md) §5.3、[02-箱子文件格式](./02-箱子文件格式.md) §5.7）。
4. 禁止在 ID 内加入任何结构：不得有类型前缀、分隔符（`-`、`_`）、校验位、版本号或字符集之外的字符。
5. 空间规模：62¹⁰ = 839,299,365,868,340,224（约 8.39×10¹⁷）。该空间是四类 ID 共用的全局空间，不区分设备、工作区或文档。
6. 跨文件系统命名安全（因节点 ID 直接进入文件名，见 §九.1）：
   - 字符集只含 `A-Za-z0-9`，是 FAT / NTFS / APFS / ext4 等文件系统的安全字符集；
   - 同一卡片内两个节点 ID 不得仅在字母大小写上不同（在大小写不敏感文件系统上会映射为同一路径）；生成与校验必须按大小写不敏感等价口径查重。

## 三、生成算法要求

### 3.1 随机性（强制）

1. 随机源必须是操作系统熵源的密码学安全随机数生成器（CSPRNG）：Rust 核心使用 OS 随机接口（`getrandom` 族）；TypeScript 侧使用 Web Crypto 的 `crypto.getRandomValues`；禁止 `Math.random`、时间种子伪随机、线性同余等可预测来源。
2. 随机取值必须在 62 字符集上**均匀无偏**：每字符独立、等概率。以字节随机数映射到 62 个索引时必须使用拒绝采样或等价的去偏映射；例如仅接受 `b < 248`（248 = 4 × 62）的字节并取 `b % 62`，拒绝 248–255 后重取。禁止直接 `byte % 62`（256 不能被 62 整除，产生取模偏差）。
3. 不得混入任何可推导成分：时间戳、自增计数、机器 / 设备标识、进程信息、用户信息、路径与内容摘要一律不得参与 ID 的生成或派生。
4. 正式链路不得提供可配置随机种子；生成实现必须支持在测试中注入确定性随机源以产生可复现夹具，夹具不得进入正式文档、正式包或发布产物。

### 3.2 唯一性（质量口径与碰撞概率）

1. 唯一性由**随机空间 + 作用域查重 + 冲突检测**共同保证，不使用中心化发号服务、共享注册表或文件锁。
2. 随机生成的碰撞概率按生日界估算：`P ≈ 1 − e^(−n²/(2·62¹⁰))`。参考量级：
   - 单文档内 n = 10⁴（节点 / 条目数）：P ≈ 6×10⁻¹¹；
   - 平台累计 n = 10⁶：P ≈ 6×10⁻⁷；
   - 全生态累计 n = 10⁹：P ≈ 0.6（极端量级，依赖 §六 的冲突检测兜底）。
3. 生成方必须在目标作用域内查重后再接受 ID：节点 ID 与所在卡片的节点集合、条目 ID 与所在箱子的条目集合、`card_id` / `box_id` 与当前受控写口已知的文档标识集合；命中即丢弃并重新生成，不覆盖、不改写既有 ID。
4. 生成是纯内存行为：生成失败不得产生半成品文件或半开窗口；落盘的原子性由文档服务受控提交保证（[11-文档服务设计](../01-架构设计/01-子系统设计/11-文档服务设计.md) §五）。

## 四、生成责任与时机

| ID | 生成方 | 生成时机 | 禁止 |
|---|---|---|---|
| `card_id` / `box_id` | 文档服务（Rust 核心受控写口） | 新建文档、复制为新文档、文件建卡（外部文件成为新文档） | 编辑引擎、插件与外部调用方指定、覆盖或拼装 ID；编辑引擎不得自行拼装 `.card` / `.box` 字节（[01-编辑引擎产品与交互设计](../08-产品与交互/01-编辑引擎产品与交互设计.md) §6.3） |
| 内容节点 ID | 编辑链路 | 节点插入时生成，随 `document:write` 的 `structure` + `content` 一次提交 | 插件不得自行生成或复用；结构替换与内容成员变更必须在同一次保存中一致（[12-编辑引擎设计](../01-架构设计/01-子系统设计/12-编辑引擎设计.md) §6.2） |
| `entry_id` | 编辑链路 | 条目插入时生成，随 `entries` / `structure` 模型切片提交 | 插件不得生成或复用；用户不得手工指定 |

1. 生成责任只属于上表生成方；应用插件、基础卡片插件、布局插件、服务插件与外部脚本等其余角色不得生成、复制或改写四类 ID。
2. 保持 ID 不变的操作：编辑、保存、导出、导入、另存、重命名、移动、两态转换与迁移；这些操作只改变形态、位置或文件名（[01-卡片文件格式](./01-卡片文件格式.md) §4.3、[13-工作区设计](../01-架构设计/01-子系统设计/13-工作区设计.md) §3.3）。
3. 必须重新生成的操作：新建文档、复制产生新文档实体、文件建卡（[01-编辑引擎产品与交互设计](../08-产品与交互/01-编辑引擎产品与交互设计.md) §6.3、[02-拖动与拖放交互规范](../08-产品与交互/02-拖动与拖放交互规范.md) §六）。
4. 归档导入保持源文档内部标识；文件名冲突只追加 `-2` / `-3` 后缀，不改 ID（[13-工作区设计](../01-架构设计/01-子系统设计/13-工作区设计.md) §3.3）。
5. 复制为新文档时，`card_id` / `box_id` 重新生成；卡片内部节点 ID 随内容引用整体保留（作用域是卡片，不产生跨文档冲突），但必须重新执行格式与作用域校验。
6. 已删除的节点 / 条目 ID 不回收、不复用；新插入一律生成新 ID。

## 五、机器标识与跨机生成

1. **本生态不使用机器标识**：四类 ID 不包含、不由机器标识派生，也不依赖配置中心、机器标识获取接口或节点注册表。旧版《ID生成规范》中的雪花算法变体（时间戳 + 机器标识 + 序列号）与 `IDGenerator.getMachineId()` 方案随平台抽象层（PAL）归档而整体废弃，不进入新架构。
2. 设计理由：
   - 隐私：文件级 ID 会在社区 / 个人服务器 API 中作为对外字段出现，设备指纹与生成时间不得被 ID 泄露；
   - 架构：新架构不提供机器标识获取面（[03-插件架构设计](../01-架构设计/01-子系统设计/03-插件架构设计.md) 的加载与执行模型不含机器身份）；
   - 安全：随机空间的碰撞概率与设备无关，跨机生成不需要协调。
3. 跨机 / 跨进程语义：任意设备、任意进程、任意工作区独立生成，互不通信；不要求时钟同步、不要求全局序列、不要求在线。跨机重复由 §六 的检测与确定性拒绝兜底。
4. 禁止：把主机名、MAC、安装 ID、设备指纹、用户账号或工作区路径混入 ID 或作为随机种子；禁止为"避免碰撞"引入中心发号服务、共享文件锁或注册表。

## 六、冲突检测与处理

### 6.1 生成时（作用域查重）

1. 节点 ID：在卡片模型的节点集合内查重，并叠加大小写不敏感等价查重（§二.6）；冲突即重新生成。
2. 条目 ID：在箱子模型的条目集合内查重；冲突即重新生成。
3. `card_id` / `box_id`：在当前受控写口已知的文档标识集合内查重；冲突即重新生成。

### 6.2 打开、导入与会话（确定性拒绝）

| 场景 | 判定与结果 |
|---|---|
| 同一会话内两个不同 `source` 解析出相同稳定标识 | 后到的打开请求返回 `DOCUMENT_ID_CONFLICT`，确定性拒绝，不静默合并（[11-文档服务设计](../01-架构设计/01-子系统设计/11-文档服务设计.md) §3.1、§十） |
| 导入的文档与工作区已有文档解析出相同稳定标识 | 导入流程中止并提示用户（重复副本），不自动重编号、不覆盖（[13-工作区设计](../01-架构设计/01-子系统设计/13-工作区设计.md) §3.3） |
| 箱子条目引用目标缺失或语法非法 | 由解析链按 `ENTRY_TARGET_MISSING` / `ENTRY_SOURCE_INVALID` 诊断处理，属于引用校验，不属于 ID 冲突处理（[06-文档解析器设计](../01-架构设计/01-子系统设计/06-文档解析器设计.md) §八） |

### 6.3 处理纪律

1. 已保存、已导出的 ID 不得为消除冲突自动重写；冲突处理只允许"拒绝 + 提示用户显式处理"（复制为新文档、重新创建或迁移），禁止静默替换 ID。
2. 解析器不发明标识：读取到非法 ID 时记录诊断并按要求降级或失败，不得自动重新生成 ID（[06-文档解析器设计](../01-架构设计/01-子系统设计/06-文档解析器设计.md) §五）。
3. 迁移工具不得擅自重新编号（§九.2）。

## 七、校验规则

### 7.1 格式校验

1. 四类 ID 一律按 `^[0-9A-Za-z]{10}$` 精确匹配：长度、字符集、大小写全部精确；拒绝空串、Unicode 归一化后的相似字符与全 / 半角变体。
2. 校验只在既有校验点执行，不新增第二套校验器：写入链在 `document:write` / `document:save` 校验（[11-文档服务设计](../01-架构设计/01-子系统设计/11-文档服务设计.md) §四），解析链在打开与 `validate` 校验（[06-文档解析器设计](../01-架构设计/01-子系统设计/06-文档解析器设计.md) §三、§八）。

### 7.2 语义校验

1. `card_id` / `box_id`：metadata 必填且格式合法；缺失或非法返回 `DOCUMENT_METADATA_INVALID`（致命，打开失败）。
2. 节点 ID：`structure[].id` 格式合法、卡内唯一、与 `content/{id}.yaml` 一一对应；缺失对应内容文件记录 `STRUCTURE_CONTENT_MISSING` 诊断，单个节点失败不阻塞其余节点。
3. 条目 ID：`entry_id` 格式合法、箱内唯一；非法或重复返回 `DOCUMENT_STRUCTURE_INVALID`。
4. 引用一致性：节点 ID 与内容文件名必须一致；结构替换与内容成员变更必须在同一次保存中一致（[12-编辑引擎设计](../01-架构设计/01-子系统设计/12-编辑引擎设计.md) §6.2、[11-文档服务设计](../01-架构设计/01-子系统设计/11-文档服务设计.md) §四）。
5. 大小写等价：节点 ID 集合按大小写不敏感口径必须无重复（§二.6）。
6. 稳定标识跨会话稳定：`documentId` 与 metadata 中的 `card_id` / `box_id` 同口径，禁止在会话层重新分配（[11-文档服务设计](../01-架构设计/01-子系统设计/11-文档服务设计.md) §3.1）。

### 7.3 错误码归属

ID 相关错误码不新增：metadata 字段问题用 `DOCUMENT_METADATA_INVALID`，结构字段问题用 `DOCUMENT_STRUCTURE_INVALID`，稳定标识冲突用 `DOCUMENT_ID_CONFLICT`；诊断复用解析链既有诊断码，不另立一套。

## 八、隐私与不可枚举

1. 四类 ID 都是随机不透明串，不含任何业务、时间、顺序、设备与用户信息；不得从 ID 推断创建时间、创建者、设备、文档内容或相互顺序。
2. 不可枚举（强制）：单次猜测命中概率为 62⁻¹⁰ ≈ 1.19×10⁻¹⁸；即使攻击者发起 10⁹ 次猜测，累计命中概率约 1.2×10⁻⁹。生成算法不得引入可缩小猜测空间的成分（时间戳、计数器、前缀、字典词）。
3. 服务端暴露与鉴权：文件级 ID 会出现在社区 / 个人服务器 API 的对外字段中（`cardFileId` / `boxFileId`）；对象键由服务端构造，客户端不得构造、拼接或猜测（[11-社区平台API契约](../05-接口与契约/11-社区平台API契约.md) §二、§五、[16-卡片传输协议](../05-接口与契约/16-卡片传输协议.md) §三）。ID 的随机性用于防猜测与防枚举，不替代服务端鉴权与授权；ID 不得作为访问凭证。
4. 界面与检索纪律：
   - ID 不作为用户可读名称：面向用户的展示一律使用 `name`（[01-卡片文件格式](./01-卡片文件格式.md) §4.3）；条目界面不显示 `entry_id`（[07-官方布局视觉细则](../08-产品与交互/07-官方布局视觉细则.md) §四）；
   - 平台与对外 API 不提供按 ID 前缀、模糊匹配或批量枚举的入口；按 ID 查询仅限平台内部精确匹配；
   - ID 可出现在日志、诊断与错误 `details` 中用于定位，但不得与用户身份、路径等信息组合成可枚举索引。

## 九、与文件名和迁移的关系

### 9.1 与文件名

1. 节点 ID 是**唯一进入文件名的 ID**：`content/{id}.yaml`（[01-卡片文件格式](./01-卡片文件格式.md) §6.1、§9.2），因此受 §二.6 的文件系统安全与大小写等价约束。
2. `card_id`、`box_id`、`entry_id` 不进入承载文件名：`.card/`、`.card`、`.box` 的名称部分与重命名只由用户可读名决定，平台不把 ID 写入文件名（[13-工作区设计](../01-架构设计/01-子系统设计/13-工作区设计.md) §3.3）。
3. ID 不作为资源寻址手段：资源与条目目标一律使用统一 URL / 包内相对路径模型（[02-箱子文件格式](./02-箱子文件格式.md) §三），不得用 ID 拼接路径或 URL。

### 9.2 与迁移

1. 迁移是**版本升级**，不是 ID 转换（[04-版本与迁移规范](./04-版本与迁移规范.md) §6.1）；合法 ID 在迁移中全程保持：`card_id` / `box_id` 不变，节点 ID 与 `content/{id}.yaml` 的对应关系不变，`entry_id` 与条目引用不变。
2. 迁移与导出 / 导入不得重新编号；迁移输出必须通过 `validate`，ID 不合法或无法在保持语义的前提下映射时按迁移失败报告，不静默生成替身 ID（[04-版本与迁移规范](./04-版本与迁移规范.md) §6.6）。
3. 外部文件进入生态的两种语义：归档导入保持源标识；文件建卡属于"新文档"，生成新 ID（[02-拖动与拖放交互规范](../08-产品与交互/02-拖动与拖放交互规范.md) §六）。
4. 网络资源卡片的 `card_id` 与卡片结构在改写 / 还原过程中不得改变（[16-卡片传输协议](../05-接口与契约/16-卡片传输协议.md) §4.1）；箱子引用网络卡片时只记录 URL、不记录认证信息，也不得借此改写自身或目标标识（[02-箱子文件格式](./02-箱子文件格式.md) §十一）。

## 十、约束与自检清单

### 10.1 约束（禁止事项）

- 禁止非受控链路生成、指定、覆盖或复用四类 ID；插件不得生成节点 ID 与条目 ID，不得拼装含 ID 的文档字节。
- 禁止可预测随机源、取模偏差与可配置种子（正式链路）。
- 禁止在 ID 中嵌入时间、序列、设备、用户、路径或业务语义。
- 禁止把 ID 数值化、大小写归一化、按前缀匹配或作为排序键。
- 禁止新增中心发号服务、机器标识依赖、全局注册表或共享锁。
- 禁止解析器、迁移工具与导入流程自动重写既有 ID。
- 禁止把 ID 作为访问凭证，或在用户界面中作为用户可读名称 / 主要标识展示。

### 10.2 自检清单

- [ ] 四类 ID 是否都为 10 位 Base62（`^[0-9A-Za-z]{10}$`），且全程大小写精确处理？
- [ ] 生成是否使用 OS 熵源 / Web Crypto，且映射无偏（拒绝采样）？
- [ ] 是否在作用域内查重（节点 / 条目 / 已知稳定标识），并包含节点 ID 的大小写不敏感等价查重？
- [ ] `card_id` / `box_id` 是否只在新建、复制为新文档、文件建卡时生成，其余操作保持？
- [ ] 节点 ID 是否只由编辑链路生成、随同一次 `document:write` 提交，插件未参与生成？
- [ ] 是否完全没有机器标识、时间戳、序列号等可推导成分与中心发号依赖？
- [ ] 冲突是否返回 `DOCUMENT_ID_CONFLICT` / `DOCUMENT_METADATA_INVALID` / `DOCUMENT_STRUCTURE_INVALID`，没有静默合并或自动重写？
- [ ] 迁移、导入、导出与重命名是否保持 ID 不变，输出是否通过 `validate`？
- [ ] 界面是否只展示 `name`，未展示 ID、未提供 ID 搜索或前缀匹配入口？
