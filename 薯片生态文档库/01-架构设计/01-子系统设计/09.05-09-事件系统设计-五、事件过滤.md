## 五、事件过滤

过滤遵循"**发布路径尽可能简单、过滤成本放在订阅侧**"的原则，分五层：

### 5.1 命名过滤（总线内）

- 只做精确 ID 匹配，不做通配符、正则或谓词求值。
- 事件 ID 非法（不符合 `<domain>:<action>`）在注册或发布时直接拒绝。

### 5.2 来源过滤（总线内）

- 保留域事件只能由平台发布；插件自有域事件只能由该插件发布；发布者身份按调用上下文记录，不取自调用参数。
- 该层同时承担防伪：`file:changed`、`security:audit` 等平台事件不可能来自第三方插件。

### 5.3 权限门控（Bridge 订阅入口）

事件契约可以为事件声明订阅权限与可见性规则：

- **静态门控**：`subscribe` 时按调用插件会话的授权判定；缺少权限时回执 `EVENT_SUBSCRIBE_DENIED`，订阅不建立。主进程侧插件订阅由内核按同一契约判定。
- **动态可见性**：按 payload 键前缀等规则逐事件判定。例如 `config:changed` 的 `platform.*` 事件对持有 `config:read` 的插件可见，`plugins.<pluginId>.*` 只对该插件与平台可见（见《[10-配置系统设计](./10-配置系统设计.md)》）；`security:audit` 仅对平台与官方审计界面可见（见《[08-权限系统设计](./08-权限系统设计.md)》）。
- 平台内部订阅不受插件权限限制。

### 5.4 桥接路由过滤（Bridge 转发器）

- **白名单**：仅转发事件契约登记的事件；`internal:*` 与插件自有域事件不转发。
- **按需转发**：主进程维护每个窗口、每个事件的订阅计数；计数为 0 的事件不做序列化、不占用 IPC；计数从 0 变为 1 时才启用转发（惰性转发）。
- **错误回执**：订阅未登记事件时回执 `EVENT_NOT_REGISTERED`，不静默丢失。
- **应用可见性规则**：动态可见性不满足的事件不投递给该订阅者。

### 5.5 内容过滤（订阅侧）

- 过滤条件由订阅者在 `handler` 内判定；SDK 可以提供类型守卫与过滤辅助函数，但过滤逻辑不进入内核发布路径。
- 高频事件（如 `sync:progress`）必须由发布方限流，并在事件契约中标注最小发布间隔；发布速率配额在发布入口计量（6.5）；订阅方不得依赖逐条投递做关键状态计算。
- 禁止在发布路径调用订阅者谓词做预过滤：发布开销必须与监听器数量线性，且每个监听器只调用一次。
