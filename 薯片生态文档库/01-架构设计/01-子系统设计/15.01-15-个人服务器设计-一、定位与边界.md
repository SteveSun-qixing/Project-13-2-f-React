## 一、定位与边界

### 1.1 定位

个人服务器是薯片生态的**单用户内容服务器**：一台服务器对应一个创作者，卡片与箱子的公开作品直接属于服务器本身，访客无需账号即可浏览；作品的查看与封面渲染产物由客户端渲染后上传，服务器只负责接收、存储、发布与展示，不执行渲染。

定位由三句话组成：

1. **单用户**：没有账号体系、没有注册登录、没有个人主页、没有房间与发现、没有管理后台；写权限只由服务器管理令牌约束（§5.2）。
2. **客户端渲染**：渲染发生在薯片客户端（Host 传输引擎与内容转换服务）；服务器没有 Worker、没有渲染队列、没有渲染缓存 TTL，也不重建任何产物（§四）。
3. **同构协议**：与社区平台共用 `.card` / `.box` 文件格式、`card-transfer` 控制面、对象存储直传、可逆恢复清单与下载计划；个人服务器只做能力裁剪，不发明第二套上传或下载协议（§七）。

个人服务器不是平台运行时的一部分：它不实现任何插件角色、不经 `window.chips` 与 Bridge、不参与工作区扫描与平台同步；它是客户端显式发布动作的服务端终点（[《插件架构设计》](./03-插件架构设计.md)、[《工作区设计》](./13-工作区设计.md)）。

### 1.2 产品范围

| 类别 | 内容 |
|---|---|
| 必做 | 单用户作品主页：展示全部公开卡片与箱子，按创建时间倒序；卡片查看页：加载客户端上传的查看产物；箱子查看页：服务器生成的极简只读文档；客户端发布说明页：向创作者说明发布流程；渲染产物上传链路：上传会话支持 `includeRenderArtifacts` 两种模式；管理令牌保护的写接口；部署与本地开发脚本 |
| 明确不做 | 多用户、注册登录、头像、角色；房间、发现、搜索；管理后台；服务端渲染（HeadlessHostShell、Worker 队列、渲染缓存 TTL 清理）；浏览器内上传与打包 |

规则：

1. 浏览器端只读：网页不提供上传、打包或编辑入口；发布与渲染一律在客户端完成（§3.4）。
2. 未上传渲染产物的卡片照常出现在主页网格中，打开时显示"尚未渲染"提示（`status = pending`，§3.2）。
3. 展示单位统一称为"作品"：卡片与箱子是同一种发布结果的两个内容类型。

### 1.3 术语

| 术语 | 定义 |
|---|---|
| 个人服务器 | 本文的服务器产品；单用户内容服务器，由社区平台裁剪而来（无多用户与无服务端渲染）。 |
| 作品 | 服务器内的一张卡片或一个箱子；分为公开（`public`）与私密（`private`）两种可见性。 |
| 管理令牌（`API_TOKEN`） | 保护全部写接口与传输控制面的唯一凭证；由部署环境配置（§5.2）。 |
| 上传会话 | `card-transfer` 控制面的一次发布事务；承载对象预签名、完成校验与发布（协议语义见《卡片传输协议》）。 |
| 渲染产物 | 客户端渲染生成的查看产物与封面产物 HTML 目录；以 `render-file` / `cover-file` 角色上传（§4.3）。 |
| 网络资源卡片 | 资源以对象存储 URL 外置的 `.card` 交付形态；个人服务器只接收此形态（[《卡片文件格式》](../../04-文件格式规范/01-卡片文件格式.md)）。 |
| 产物缓存版本（`cacheVersion`） | 一次发布对应一个缓存版本，由服务器在会话创建时确定（个人服务器取会话 ID）；产物对象键以它为中层前缀（§4.3）。 |
| 逻辑桶 | 由服务端定义的存储桶名（如 `chips-card-render-cache`）；桶角色与用途见[《卡片传输协议》](../../05-接口与契约/16-卡片传输协议.md) §6.2。 |
| 物理桶 | 对象存储中的真实桶；未启用单物理桶模式时与逻辑桶一一对应。 |
| 单物理桶模式 | 可选部署形态：全部逻辑桶映射到同一个物理桶，逻辑桶名作为对象键前缀（§6.3）。 |
| 恢复清单（restore manifest） | 客户端生成并由服务器持久化的原始路径、网络 URL 与 ZIP Store 条目映射；用于完整离线卡片的下载恢复，结构以《卡片传输协议》为准。 |
