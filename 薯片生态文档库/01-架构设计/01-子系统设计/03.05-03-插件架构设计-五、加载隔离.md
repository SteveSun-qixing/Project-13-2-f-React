## 五、加载隔离

### 5.1 隔离层次

| 层次 | 隔离对象 | 机制 | 越界 / 失效结果 |
|---|---|---|---|
| 进程 | 平台进程与各 UI | Electron 主进程 / 渲染进程；主进程插件经 ModuleLoader 受管加载；工具进程承载需隔离的服务；`nodeIntegration: false`、`contextIsolation: true`、`sandbox: true`（R17） | 单个窗口或工具进程崩溃不影响平台与其它插件 |
| 上下文 | 每个插件的 Context | Cordis 子 Context + `inject` 白名单 | 一个插件的 Context 异常不污染其它插件 |
| 副作用 | 每个插件的 Fork | 副作用追踪 + `dispose()` 逆序回收 | 停用 / 卸载后无残留 |
| 资源 | `chips-resource://` 作用域 | 作用域解析 + 路径安全校验（[04-资源管理设计](04-资源管理设计.md)） | 越权访问被拒绝 |

### 5.2 进程隔离与执行载体

- 平台主进程承载 Cordis 运行时、Bridge 能力、`service` 的调度与 `app` 的主逻辑；插件代码在主进程内运行，因此加载器与调用边界必须捕获插件异常（§9.2）。
- **主进程插件执行载体是受管模块加载器（ModuleLoader）**：只允许加载插件作用域的 `chips-resource://` 模块与平台白名单模块（`@chips/sdk` 类型与平台提供物）；禁止 `node:*`、`electron`、裸路径（如 `fs`、`path`）与任意文件路径。加载器是**完整性门禁**：加载前校验模块来源与完整性摘要，越界加载或校验失败一律拒绝，本次启用失败且不执行任何插件代码。
- **执行形态（2026-09-21 落文，RFC-插件执行通道与ModuleLoader裁定，随通道波 1 交付）**：受管加载器以 ESM 钩子链承载（`module.register` 的 resolve/load 双钩，通道波 0 已在 Electron 40.8 真进程实测该机制于主进程可行），完整性门禁在双钩侧各自生效——resolve 侧做作用域与白名单裁决，load 侧做包级摘要复算与 8 MiB/UTF-8/ESM 形态校验；激活撤销后对同一模块的再装载经 URL nonce 强制重求值，不复用陈旧模块实例。工程实现见 `packages/host/src/loader/module-loader.ts`。
- **服务插件的进程级隔离由工具进程（Electron Utility Process）承担**，作为正式执行形态登记：需要隔离的服务逻辑在工具进程中执行，进程由壳提供、内核调度；工具进程崩溃按 §9 的崩溃隔离与恢复处理，不影响主进程与其它插件。
- `app` 插件的 UI 运行在独立窗口（BrowserWindow）的渲染进程；窗口必须按 R17 安全基线创建，生产环境禁止关闭 `webSecurity`。
- `basecard` / `boxlayout` 的渲染在渲染引擎管理的 iframe 沙箱中执行；沙箱注入、资源代理与通信协议见 [05-渲染引擎设计](05-渲染引擎设计.md)。
- 插件不得创建子进程、不得加载原生可执行载荷（R11）；系统能力一律经 Bridge 获取。

### 5.3 上下文隔离

每个插件拥有独立 Context，只能访问：

1. 通过 `ctx.inject` 声明并由内核注入的服务；
2. `ctx` 提供的受控 API（事件、生命周期、服务注册、`ctx.task`）；
3. Bridge 的 `request` / `subscribe` / `resource` 三个方法（形状与语义见 [02-Bridge三层设计](02-Bridge三层设计.md)）；
4. `@chips/ui`（UI 组件与令牌）与 `@chips/sdk`（类型、脚手架、测试辅助）；
5. ModuleLoader 放行的插件作用域 `chips-resource://` 模块与平台白名单模块（§5.2）。

禁止：

- 跨插件 `import` 或直接持有其它插件的对象引用；
- 加载 `node:*`、`electron`、裸路径与任意文件路径模块；ModuleLoader 在加载前拒绝；
- 读写全局对象、修改平台内部状态；
- 访问 Node.js / Electron / 操作系统 API；
- 注册未经声明的服务、申请未声明的权限、访问未授权的资源作用域。

### 5.4 Fork 与副作用

- Fork 在启用时创建，是插件全部副作用的撤销单元；插件 Context 由内核按加载请求创建（默认挂载在平台根 Context 下），只继承平台公共能力，不继承其它插件的私有状态（[01-薯片内核设计](01-薯片内核设计.md) §3.2）。
- 必须纳入 Fork 追踪的副作用至少包括：事件订阅、定时器、服务注册、能力注册、资源句柄、后台任务（`ctx.task`）、UI 注入。
- 停用时按创建逆序 `dispose()`；`dispose()` 必须幂等，且不得抛出异常中断清理链。
- 未被 Fork 追踪的副作用视为插件缺陷；内核可检测并审计（[01-薯片内核设计](01-薯片内核设计.md)、[09-事件系统设计](09-事件系统设计.md)）。

### 5.5 资源与配额隔离

- 插件资源经 `chips-resource://` 的插件作用域访问（如 `chips-resource://plugin-001/icon.png`），作用域限定在插件自身包内；路径穿越、绝对路径与越作用域访问被拒绝（[04-资源管理设计](04-资源管理设计.md)、[06-资源协议规范](../../05-接口与契约/06-资源协议规范.md)）。
- 平台对插件施加四类软配额：**内存、任务数、消息速率、后台时长**；计量点、默认值与状态机由内核唯一定义（[01-薯片内核设计](01-薯片内核设计.md) 6.9），本文不重复数值。
- 超限按“**限流 → 暂停 → 停用**”逐级降级：先拒绝新增调用与事件发布，持续越界再暂停后台任务与新调用，仍不收敛则停用；降级、恢复与停用动作必须产生审计记录。
- 任务数与后台时长以 `ctx.task` 登记的活跃任务及运行时长计量；消息速率在 Bridge 调用入口与事件发布入口计量。
