## 六、存储设计

### 6.1 逻辑桶

桶角色与默认桶名的唯一登记在[《卡片传输协议》](../../05-接口与契约/16-卡片传输协议.md) §6.2；个人服务器实际启用的桶：

| 逻辑桶 | 用途 | 访问 | 键布局（前缀） |
|---|---|---|---|
| `chips-card-resources` | 卡片内嵌资源与网络资源卡片对象 | 按作品可见性策略（§6.2） | `cards/{cardId}/versions/{versionId}/...` |
| `chips-card-files` | 发布态完整 `.card` 源文件副本（服务器保留） | 私有（预签名访问） | `cards/{cardId}/versions/{versionId}/...` |
| `chips-box-files` | 发布态 `.box` 源文件 | 私有（预签名访问） | `boxes/{boxId}/versions/{versionId}/box.box` |
| `chips-card-render-cache` | 公开卡片查看产物 | 公开读 | `{cardId}/{cacheVersion}/...` |
| `chips-card-render-cache-private` | 私密卡片查看产物 | 私有（受控代理） | `{cardId}/{cacheVersion}/...` |
| `chips-card-cover-cache` | 公开卡片封面产物 | 公开读 | `{cardId}/{cacheVersion}/...` |
| `chips-card-cover-cache-private` | 私密卡片封面产物 | 私有（受控代理） | `{cardId}/{cacheVersion}/...` |
| `chips-covers` | 箱子封面等非卡片封面资源 | 公开读 | `boxes/{boxId}/cover/...` |

规则：

1. 桶命名全小写、连字符分隔（S3 规范）；服务端启动时自动创建缺失的桶并写入公开读策略（仅公开桶）。
2. 个人服务器不启用头像桶（`chips-avatars`）：头像属于多用户形态；其余桶角色按产品需要启用。
3. 逻辑桶是服务端的稳定命名空间；部署者不得手工改桶名或在桶间搬运对象（会破坏入口记录）。

### 6.2 公开读策略与可见性路由

1. 启动初始化对公开桶写入公开读对象策略（`arn:aws:s3:::<bucket>/*`）；私有桶不写公开策略。
2. 私有桶对象只能经两种路径访问：服务器受控代理（私有产物，支持 Range）与预签名 GET（箱子源文件下载，短有效期）。
3. **可见性路由（强制）**：卡片与箱子的资源访问必须按作品可见性策略决定（《卡片传输协议》§6.5）。公开作品的资源可走公开桶直链；私密作品的资源与网络资源卡片不得继续依赖公开桶匿名直链，正式实现必须把私密资源路由到私有存储或受控访问路径。
4. 公开桶的对象 URL 是长期可访问的：公开读策略 + CDN 域名构成公开分发面，不参与鉴权（§9.2）。

### 6.3 单物理桶模式

当部署设置 `S3_BUCKET_NAME` 时进入单物理桶模式：

1. 全部逻辑桶（含私有桶）映射到同一物理桶，对象键变为 `{逻辑桶名}/{原对象键}`；启动初始化只创建该物理桶并对它写入公开读策略。
2. `S3_ENDPOINT` 必须使用对象存储的**通用端点**，不得使用 bucket 专属端点：专属端点会把物理桶名写进对象键，导致 CDN 访问路径与实际键不一致（典型表现为 CDN 404）。
3. 公开资源的对外地址由 `S3_PUBLIC_URL`（推荐专用 CDN 域名）拼接逻辑桶名与对象键构成；未配置时开发态回退 `S3_ENDPOINT`，非开发态回退 `${BASE_URL}/cdn/{逻辑桶名}`。
4. **隐私约束（强制）**：单物理桶模式下私有对象与公开对象处于同一物理桶且该桶为公开读，私密性只由对象键不可枚举保证。因此单物理桶模式只允许部署"全部内容公开"的个人服务器；需要私密作品时必须使用独立私有桶的默认部署（不设置 `S3_BUCKET_NAME`）。该约束属于部署门禁，违反即视为配置错误（§9.3）。

### 6.4 对象大小、数量与残留

| 项 | 设计 |
|---|---|
| 单文件大小 | 由部署参数 `MAX_CARD_SIZE_MB` / `MAX_BOX_SIZE_MB` 声明；会话创建与预签名阶段按上限拒绝超限声明，`complete` 阶段校验实际对象大小与声明一致 |
| 传输模式 | `capabilities.multipart` 由部署声明：未启用时单对象一次预签名 `PUT`；服务器必须在协议校验中拒绝超限对象并给出上限 |
| 会话对象数 | 由会话与对象清单记录；`complete` 逐对象校验（《卡片传输协议》§3.6） |
| 预签名有效期 | 不超过会话剩余有效期；具体时长由服务器在预签名响应中给出 |
| 残留对象 | 会话过期、取消或发布失败可能留下未被作品引用的对象；由部署侧对象存储生命周期规则兜底清理，服务器不扫描、不回收（《卡片传输协议》§6.6） |

### 6.5 存储权威与可重建性

- 对象存储是**字节权威**：源文件、资源、产物只能从对象存储恢复；服务器不从客户端重新生成产物（客户端可重新发布，但那是一次新的发布事务）。
- 数据库是**元数据权威**：可见性、状态、标题、对象位置、产物入口、恢复清单只在数据库中；对象存储无法反推这些信息。
- 两侧必须成对备份与恢复（§8.3）；不存在"只备份数据库即可重建"的路径。
- 个人服务器的渲染产物**不是可重建缓存**：没有 Worker 与服务端渲染链路，产物丢失后只能由客户端重新发布生成（§8.3）。
