## 四、生命周期流程

### 4.1 发现

插件来源按优先级从高到低：

1. `development`：开发目录（开发工作区或启动参数指定的插件目录）；
2. `user`：用户插件目录（安装落盘位置）；
3. `builtin`：随平台分发的内置插件（含按需加载的平台服务插件，如同步引擎）。

规则：

- 发现只解析 `manifest.yaml` 的必要字段，不执行任何插件代码。
- 同一 ID 在多个来源出现时，高优先级来源生效，其余来源被遮蔽；遮蔽不删除文件。
- 同一来源内同 ID 出现多个版本时，取版本最高者，其余记录为冲突并报告。
- 发现结果写入注册表（`discovered`）；内置插件在平台首次启动时直接进入 `installed` 并按默认启用集合写入启用偏好。
- 插件查询与列表经插件管理能力提供，支持按角色与 ID 过滤（能力契约见 [04-能力契约规范](../../05-接口与契约/04-能力契约规范.md)）。

### 4.2 安装

```
用户 / 插件市场 / CLI 提供 .cpk
        │
        ▼
[1] 包结构校验：ZIP Store、根目录 manifest.yaml、入口存在、无原生载荷、无路径穿越
        │
        ▼
[2] manifest 校验：必填字段、ID 反向域名、语义化版本、角色合法、runtime.targets
        │
        ▼
[3] 来源校验：签名与来源渠道（development 来源跳过签名校验）
        │
        ▼
[4] 版本与冲突检查：同 ID 更新走替换流程（§6.2）；降级默认拒绝
        │
        ▼
[5] 权限解析：校验权限 ID、限定值与角色适用性，登记权限申请集合（默认未授权）
        │
        ▼
[6] 原子落盘：先写临时目录，校验通过后重命名进插件目录
        │
        ▼
[7] 写注册表：状态 = installed，发布生命周期事件
```

规则：

- 安装不自动启用；用户或平台在安装完成后引导启用。
- **安装只登记权限申请，不产生授权**：授权交互在首次启用时逐项展示与接受；拒绝任一权限不阻断启用，该权限保持未授权、运行时调用被拒绝（[08-权限系统设计](08-权限系统设计.md) 6.2）。
- 授权记录由权限系统独占写入；安装校验失败时 `.cpk` 不落盘、不注册。
- 依赖缺失或版本暂不满足不阻止安装，仅在启用时阻塞（§7.2）；版本范围不可满足（互斥）在启用时返回显式冲突。
- `.cpk` 的结构、体积限制、签名与完整校验清单见 [03-插件包格式](../../04-文件格式规范/03-插件包格式.md)。
- 安装失败不得留下半成品：临时目录必须清理，注册表不产生记录。

### 4.3 启用

对单个插件的启用流程：

1. 状态检查：必须为 `installed`（`pending` 表示已受理，见第 4 步）。
2. 首次启用授权：首次启用时逐项展示权限申请（插件名与版本、权限说明、风险级别、解析后的限定值），用户接受后写入授权记录；拒绝的条目保持未授权，**不阻断启用**（[08-权限系统设计](08-权限系统设计.md) 6.2）。
3. 会话快照：平台按授权记录生成该插件的会话快照（[08-权限系统设计](08-权限系统设计.md)）；运行时判定以快照为准，未授权、已撤销或超出限定值的调用被拒绝。
4. 依赖解析：按 §7.2 解析直接依赖，确保全部依赖处于 `active` 或可被同时启用；暂不满足则转入 `pending` 并等待依赖就绪，范围不可满足（互斥）则返回显式冲突并进入 `failed`。
5. 创建 Fork：`ctx.plugin(pluginModule)`，Context 只暴露允许面（§5.3），插件副作用从此刻起全部纳入 Fork 追踪；服务注册进入暂存代际（[01-薯片内核设计](01-薯片内核设计.md) 5.2）。
6. 角色激活入口：
   - `basecard`：注册 `cardTypes`；
   - `boxlayout`：注册 `layouts`；
   - `app`：注册启动器与文件关联；
   - `service`：调用 `start(ctx)`，完成服务与能力注册。
7. 状态置为 `active`：暂存代际一次原子发布并触发依赖方级联重建，随后发布 `plugin:loaded` 生命周期事件。

失败处理：

- 任一步骤失败：回收已产生的副作用（`dispose()`），状态转为 `failed`，记录结构化 `ChipsError`。
- 单个插件启用失败不影响平台与其它插件；依赖它的插件保持 `pending`，待其恢复后自动继续。
- 平台启动时的批量启用按依赖拓扑序执行，逐个隔离错误（§4.6、§9.2）。

### 4.4 停用

1. 依赖者检查：存在 `active` 依赖者时默认拒绝（`KERNEL_DEPENDENCY_CONFLICT`）；调用方显式请求级联停用时，按逆拓扑序先停用依赖者，平台在执行前展示受影响的插件列表（内核规则见 [01-薯片内核设计](01-薯片内核设计.md) §6.4、§7.5）。
2. 摘除路由：从插件注册表、能力路由、启动器与文件关联中移除该插件，停止接收新调用。
3. 执行角色停止入口：
   - `service`：调用 `stop()`；
   - `app`：关闭其全部窗口（关闭前由应用处理未保存状态）；
   - `basecard` / `boxlayout`：注销类型与布局。
4. `Fork.dispose()`：按创建逆序回收全部副作用（事件订阅、定时器、服务、能力、资源句柄、UI 注入）。
5. 状态置为 `installed`，写入启用偏好，发布生命周期事件。

规则：

- 停用不删除插件文件、配置与授权；再次启用不重新安装。
- 停用必定完成：`stop` 回调失败不阻断撤销，清理超时由内核按策略强制撤销；失败只记录错误与审计，状态仍进入 `installed`（[01-薯片内核设计](01-薯片内核设计.md) §6.4）。
- 停用后插件目录中的代码不再被调用；`dispose()` 必须幂等，重复停用不产生副作用。

### 4.5 卸载

1. 前置检查：状态必须为 `installed` 或 `failed`；`active` / `stopping` 必须先停用，否则返回 `KERNEL_INVALID_TRANSITION`。
2. 依赖者检查：存在任何已安装的依赖者时拒绝卸载（`KERNEL_DEPENDENCY_CONFLICT`），返回依赖者列表，用户须先处理依赖者。
3. 撤销该插件的全部权限授予。
4. 删除插件配置与缓存；删除方式遵循 [10-配置系统设计](10-配置系统设计.md)。
5. 删除插件目录与注册表记录。
6. 发布生命周期事件。

规则：

- 内置插件（`source: builtin`）不可卸载，只能停用。
- 卸载永不删除插件经平台能力创建的卡片、箱子等用户文件。
- 卸载后同 ID 再次安装，视为全新安装（不恢复旧配置）。

### 4.6 启动恢复

平台启动时的恢复顺序：

1. 加载注册表，清理上次中断残留的 `starting` / `stopping` 痕迹（回滚为 `installed`）。
2. 对启用偏好集合执行依赖解析，得到拓扑序。
3. 按拓扑序逐个启用；单个失败被隔离，不阻塞后续插件。
4. 依赖失败的插件保持 `pending`，其依赖恢复后自动继续激活。

| 上次退出状态 | 本次启动行为 |
|---|---|
| `installed` | 保持 `installed` |
| `pending` | 不恢复等待，按当前依赖重新判定 |
| `active` | 重新启用 |
| `starting` / `stopping` | 回滚为 `installed` 后按启用偏好处理 |
| `failed` | 启动时不自动重试；运行期失败按 §9.3 的重试与熔断策略处理 |
| 启用偏好中存在但已被遮蔽 / 删除 | 清理偏好并记录诊断 |
