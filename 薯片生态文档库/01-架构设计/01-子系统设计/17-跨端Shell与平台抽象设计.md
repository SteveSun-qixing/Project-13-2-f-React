# 跨端 Shell 与平台抽象设计

> 版本：v1.0.0
> 日期：2026-09-19
> 状态：正式版
> 适用范围：薯片平台壳（Shell）与平台核心（Host Core）的职责边界、平台抽象层（PAL）的分面与端口模型、桌面 Electron 壳 / 无头壳 / 移动壳（Phase 5，Tauri 2）差异对照、能力可用性与降级语义、无头宿主形态、浏览器宿主边界（不在本架构范围），以及 Linux / Android / iOS 的阶段安排；不覆盖 Bridge 调用契约、内核机制、渲染链路与各子系统内部实现。

---

## 一、定位与边界

### 1.1 定位

薯片平台采用**一核多壳**：平台核心（Host Core）与壳（Shell）分离，同一套内核、Bridge、解析、资源、文档与插件机制运行在桌面、无头与（Phase 5）移动三种宿主形态上。

本文是壳与平台抽象层设计的唯一权威：

- 壳与平台核心的职责边界与唯一交互面；
- 平台抽象层（PAL）的分面、端口模型与旧 PAL 口径的收口；
- 壳能力矩阵、能力可用性与降级语义；
- 桌面 Electron 壳、无头壳与移动壳（Phase 5，Tauri 2）的差异对照；
- 无头宿主形态与各平台的阶段安排。

### 1.2 术语

| 术语 | 定义 |
|---|---|
| 壳（Shell） | 面向一个具体运行形态与操作系统的宿主外壳：进程载体、窗口系统接入、平台差异适配、打包与更新；分桌面壳、无头壳、移动壳三类 |
| 平台核心（Host Core） | 壳无关的运行时整体：Rust 核心（Cordis 内核、Bridge 内核、文档解析、资源管理）、平台服务域、渲染引擎宿主侧与插件治理；不包含任何 Electron / Tauri / 操作系统特有代码 |
| 平台抽象层（PAL） | 壳内部的平台差异抽象层；以端口形式向平台核心提供系统能力，是平台内唯一允许出现平台特判的位置 |
| PAL 端口（port） | PAL 的一个能力分面接口；一个端口最多支撑一个能力域，其方法语义与对应能力动作一一对应 |
| 壳能力矩阵（capability matrix） | 壳在构建期与启动期声明的"哪些分面可用"的内部矩阵；只供能力注册层消费，不通过 Bridge 暴露 |
| 宿主进程 | 承载平台核心与插件的进程：桌面为 Electron 主进程，无头为 Node.js 进程，移动为 Tauri 宿主进程 |
| 能力域（capability domain） | Bridge 能力 ID 的域段（`window` / `dialog` / `file` / `resource` / `document` 等）；总表权威为[04-能力契约规范](../../05-接口与契约/04-能力契约规范.md) |

## 二、总体结构

### 2.1 一核多壳

```text
┌──────────────────────────────────────────────────────────────┐
│ 插件与内容（同一套文件格式、角色接口与 Bridge 契约，零平台分支） │
└───────────────────────────────┬──────────────────────────────┘
                                │ Bridge（唯一门，R2）
┌───────────────────────────────▼──────────────────────────────┐
│ 平台核心 Host Core（壳无关）                                   │
│  Cordis 内核 · Bridge 内核 · 文档解析 · 资源管理 · 文档服务      │
│  渲染引擎（宿主侧） · 权限 / 事件 / 配置 · 插件治理             │
└───────────────────────────────┬──────────────────────────────┘
                                │ PAL 端口（平台内部，不向插件暴露）
┌───────────────────────────────▼──────────────────────────────┐
│ 壳 Shell                                                      │
│  桌面 Electron 壳 · 无头 Node 壳 · 移动 Tauri 2 壳（Phase 5）  │
└───────────────────────────────┬──────────────────────────────┘
                                │ 系统 API
┌───────────────────────────────▼──────────────────────────────┐
│ 操作系统（macOS / Windows / Linux / Android / iOS）            │
└──────────────────────────────────────────────────────────────┘
```

规则：

1. 壳差异只允许存在于壳层；平台核心与插件不得感知壳形态（R2、[架构原则](../../00-愿景与原则/01-架构原则.md) 第 2.3 节）。
2. 桥接契约、能力 ID、权限 ID、错误码与文件格式跨壳完全一致；同一插件在任意壳上的行为差异只能来自能力可用性（第五节）。
3. 工具进程（Electron Utility Process）不是壳形态，而是壳提供给内核的隔离执行载体（[03-插件架构设计](./03-插件架构设计.md) 第 5.2 节）。

### 2.2 壳形态

| 壳形态 | 运行形态 | 交互表面 | 阶段 |
|---|---|---|---|
| 桌面壳 | Electron 主进程 + 窗口渲染进程 + 工具进程 | 多窗口、菜单、托盘 | Phase 0-4（macOS / Windows 优先，Linux Phase 4 三端验证） |
| 无头壳 | Node.js 进程（无窗口系统） | 无交互表面；可提供离屏帧宿主 | 随平台核心提供（服务端渲染、批处理与 CI） |
| 移动壳 | Tauri 2 宿主 + 系统 WebView | 全屏表面 | Phase 5（架构预留，暂不排期） |

- **Web 不是壳形态**：平台不提供 `web` 插件运行时，浏览器页面运行形态不在插件运行目标内（[04-能力契约规范](../../05-接口与契约/04-能力契约规范.md) 第 6.4 节）。**浏览器侧应用插件宿主不在本架构范围**：插件运行目标只有 `host`（桌面壳 / 无头壳 / Phase 5 移动壳）；旧社区平台的浏览器宿主链路（`plugin-sessions` 插件会话 API、`resource-open-plan`、`entry` / `bootstrap` 引导与 Web Runtime）不迁移、不保留，平台不定义浏览器侧插件会话契约。如需重新评估浏览器宿主，必须走 RFC → 评审 → ADR（R16、[03-变更与决策管理](../../07-工程管理/03-变更与决策管理.md)），不得把旧链路当作既有设计继续演进。五端共享只体现在文件格式、Rust 核心与 Bridge 接口按平台无关设计。
- 新增壳形态属于重大变更：RFC → 评审 → ADR 记录 → 门禁 → 文档同步（R16）。

### 2.3 进程与代码归属

| 壳 | 代码归属 | 进程结构 |
|---|---|---|
| 桌面壳 | `packages/host/`（`@chips/host`）：主进程、preload、窗口渲染进程、PAL 适配 | Rust 核心以 `chips-native.node` 经 Neon 运行在主进程内；窗口渲染进程运行 React 壳与 RenderHost；需隔离的服务由工具进程承载 |
| 无头壳 | 平台核心的无头入口与无头 PAL 适配；不加载 Electron | 单 Node.js 进程运行核心与插件；渲染需求由离屏帧宿主提供（第七节） |
| 移动壳 | Phase 5 引入的移动宿主包与移动 PAL 适配（Kotlin / Swift） | Tauri 2 宿主进程 + 系统 WebView；Rust 核心经移动绑定（JNI / Swift FFI，Phase 5 架构预留） |

- 壳与 PAL 类型是平台内部类型：不得由 `@chips/sdk` 导出，也不得出现在 `window.chips` 方法面上。
- 平台包划分以[代码组织规范](../../02-开发规范/01-代码组织规范.md) 第 3.1 节为准；新增平台包必须先走 RFC → ADR。

### 2.4 启动与退出顺序

启动：

1. 壳进程启动，构造 `IPalHost`（壳信息、能力矩阵、端口集合）；
2. 壳自检：矩阵中声明的可用分面必须有对应端口实现；缺端口、多端口或声明不一致终止启动；
3. 启动平台核心：内核 → 解析器 / 资源管理器 / 文档服务 → Bridge 按矩阵注册内置能力；注册校验失败终止平台启动（[02-Bridge三层设计](./02-Bridge三层设计.md) 第 4.2 节）；
4. 创建窗口渲染进程、注入 preload（`window.chips`）与自定义协议处理器；
5. 按启用偏好执行插件启动恢复，拓扑序逐个启用（[03-插件架构设计](./03-插件架构设计.md) 第 4.6 节）。

退出（逆序）：

1. 停用插件并完成 Fork 撤销；`app` 角色先关闭窗口并由应用处理未保存状态；
2. 释放窗口 / 表面、会话与资源句柄；注销事件订阅；
3. Bridge 关闭并注销全部能力；核心进入停机，工具进程退出；
4. 壳退出进程；强制退出时按内核 stop 超时与强制撤销策略收口。

## 三、壳与平台核心边界

### 3.1 职责划分

| 事项 | 壳负责 | 平台核心负责 |
|---|---|---|
| 进程与生命周期 | 进程创建与单实例、退出信号、工具进程托管、崩溃上报 | 内核生命周期、插件状态机、崩溃隔离与重启策略 |
| 系统能力实现 | 窗口、对话框、通知、剪贴板、菜单、托盘、快捷键、电源、外部打开、HTTP 传输、文件系统与目录变量解析 | 能力语义、输入 schema、权限判定、资源级二次约束（路径安全、域名核对）、审计 |
| 平台差异 | 全部平台特判（PAL 端口实现）；Linux 桌面环境差异同属壳 | 禁止 `process.platform`、禁止 `import` Electron / Tauri / 系统模块、禁止平台名分支 |
| 权限与安全 | 不绕过判定；按物理通道传递会话来源；窗口按 R17 安全基线创建 | 会话有效性 → 权限 → schema 三步判定；PathGuard、临时作用域、审计 |
| 业务逻辑 | 禁止实现任何插件业务 | 平台机制与平台服务；业务全部在插件 |
| 打包与更新 | 签名、安装事务、桌面自更新器（Phase 4）、移动商店分发 | 版本门禁、更新链路契约与迁移规则 |
| 界面 | 窗口容器、窗口级系统 UI；不含业务界面 | 渲染引擎与 React 壳在窗口渲染进程承载业务界面 |

### 3.2 唯一交互面

- **核心 → 壳**：只经 PAL 端口调用，取消与截止时间经端口参数如实传播。
- **壳 → 核心**：只经能力注册、平台服务调用（内核路由）、会话身份转发与事件总线发布。
- 壳内部通道（preload IPC、工具进程通道、更新器通道、自定义协议处理器）一律不得触达插件内容；插件访问平台的唯一运行时入口是 Bridge 的 `request` / `subscribe` / `resource`（[01-Bridge-API规范](../../05-接口与契约/01-Bridge-API规范.md)）。
- 壳不得实现第二个能力注册表、第二套权限判定或第二套 schema 校验；不得绕过 Bridge 直接调用能力实现。

### 3.3 边界红线

| 编号 | 红线 |
|---|---|
| SB-1 | 平台核心零平台特判：不得出现 Electron / Tauri / Kotlin / Swift API 引用与平台名字符串分支 |
| SB-2 | 壳零业务：不得实现插件业务逻辑，不得为某个插件增设专用通道或特判 |
| SB-3 | 插件零壳感知：插件不得按平台名、壳名或窗口环境分支；只能按能力调用结果降级 |
| SB-4 | 唯一门不变：壳内部通道不得暴露给插件内容；preload 只暴露 `IChipsBridge` 方法面 |
| SB-5 | 禁止伪造能力成功：分面缺失或环境不可用时不注册能力或返回正式域错误码，不得空实现假成功 |
| SB-6 | 壳不得放宽或替代权限判定；用户选择不产生文件系统授权（[04-能力契约规范](../../05-接口与契约/04-能力契约规范.md) 第 7.7 节） |
| SB-7 | PAL 端口错误必须归一为已登记错误码；未识别异常归一为 `BRIDGE_INTERNAL`，不得向插件泄露内部路径与堆栈 |
| SB-8 | 壳的窗口创建必须满足 R17：`nodeIntegration: false`、`contextIsolation: true`、`sandbox: true`，生产环境禁止关闭 `webSecurity` |

### 3.4 路径与目录变量

- 目录变量（如 `${userDocuments}`、`${userData}`）由壳解析为具体路径，经 `system:info.paths` 只读暴露；权限申请与限定值一律使用目录变量形式，禁止裸绝对路径（[04-能力契约规范](../../05-接口与契约/04-能力契约规范.md) 第 6.1 节）。
- 平台路径映射（平台级 / 用户级目录）以[配置系统设计](./10-配置系统设计.md) 第 3.2 节为准；工作区默认目录、Linux `~/.config/chips` 等平台差异只在壳与配置服务中实现。
- 路径安全校验（PathGuard）、作用域匹配与受控提交在平台核心（[04-资源管理设计](./04-资源管理设计.md)、[11-文档服务设计](./11-文档服务设计.md)）；壳不得自行放宽。

## 四、平台抽象层（PAL）

### 4.1 定位与放置

- PAL 是壳内部的**平台差异唯一收敛点**：所有系统调用与平台特判收敛到端口实现，平台核心只依赖端口契约。
- PAL 不是插件 API：不经 `window.chips` 暴露，不由 `@chips/sdk` 导出，不参与能力注册表的插件可见面。
- PAL 与平台统一版本同源发布（[代码组织规范](../../02-开发规范/01-代码组织规范.md) 第 3.4 节）；端口契约变更属于平台内部 ABI 变更，必须同步更新本文与端口契约测试。
- Bridge 不提供能力枚举 API，插件无法也不应探测壳能力矩阵（[02-Bridge三层设计](./02-Bridge三层设计.md) 第 4.4 节）。

### 4.2 端口模型

```typescript
type ShellKind = 'desktop' | 'headless' | 'mobile';
type PlatformId = 'macos' | 'windows' | 'linux' | 'android' | 'ios';

interface IShellInfo {
  readonly shell: ShellKind;
  readonly platform: PlatformId;
  readonly osVersion: string;
  readonly arch: string;
  readonly appVersion: string;
  readonly locale: string;
  readonly paths: Readonly<Record<string, string>>;
}

interface IPalCapabilityMatrix {
  readonly window: boolean;
  readonly dialog: boolean;
  readonly notification: boolean;
  readonly clipboard: boolean;
  readonly menu: boolean;
  readonly tray: boolean;
  readonly shortcut: boolean;
  readonly power: boolean;
  readonly systemInfo: boolean;
  readonly transfer: boolean;
  readonly shellOpen: boolean;
  readonly http: boolean;
}

interface IPalPorts {
  readonly storage: IPalStoragePort;
  readonly window?: IPalWindowPort;
  readonly dialog?: IPalDialogPort;
  readonly notification?: IPalNotificationPort;
  readonly clipboard?: IPalClipboardPort;
  readonly menu?: IPalMenuPort;
  readonly tray?: IPalTrayPort;
  readonly shortcut?: IPalShortcutPort;
  readonly power?: IPalPowerPort;
  readonly system?: IPalSystemPort;
  readonly transfer?: IPalTransferPort;
  readonly shellOpen?: IPalExternalPort;
  readonly http?: IPalHttpPort;
}

interface IPalHost {
  readonly info: IShellInfo;
  readonly matrix: IPalCapabilityMatrix;
  readonly ports: IPalPorts;
  /** 无头壳在需要服务端渲染时提供离屏帧宿主；桌面与移动壳不使用该字段。 */
  readonly render?: IPalRenderHost;
}
```

端口方法即对应能力动作的唯一下沉实现位置，以窗口端口为例（`windowId` 统一为 `number`，即 Electron `webContents.id`，权威口径见 [04-能力契约规范](../../05-接口与契约/04-能力契约规范.md) §7.4）：

```typescript
interface IPalWindowPort {
  create(options: WindowCreateOptions): Promise<{ windowId: number }>;
  list(): Promise<readonly WindowSummary[]>;
  focus(windowId: number): Promise<void>;
  close(windowId: number): Promise<void>;
  resize(windowId: number, size: WindowSize): Promise<void>;
  move(windowId: number, position: WindowPosition): Promise<void>;
  setTitle(windowId: number, title: string): Promise<void>;
  setState(windowId: number, state: WindowState): Promise<void>;
}
```

规则：

1. 方法集合与能力动作一一对应，不得添加第二语义；能力参数校验与权限判定在调用端口之前完成，端口只做系统适配与资源级约束。
2. 所有可能阻塞的端口方法接收 `{ signal, deadline }`，实现必须响应取消与截止；调用方会话结束、能力注销或 Bridge 关闭时端口调用一并收口。
3. 端口实现不得持有插件对象、不得回调插件、不得访问数据库式的平台内部状态；端口只依赖操作系统与其自身进程资源。
4. 端口的错误必须抛出已登记错误码的 `ChipsError` 同构对象（第三节 SB-7）。

### 4.3 分面到能力域的映射

| 旧 PAL 分面（旧版《平台抽象层设计》《Host 服务域设计》《跨端 Host 目标技术架构》） | 新架构归宿 | 说明 |
|---|---|---|
| `environment` / `platform` | `system:info` + 壳能力矩阵（内部） | 平台信息只读；矩阵不经 Bridge 暴露；旧 `platform.getCapabilities()` 快照作废 |
| `surface` / `window` | `window:*` | 桌面为窗口语义；移动壳内部映射为全屏表面；`tab` / `route` / `modal` / `sheet` 不作为能力 |
| `storage` / `fs` | `file:*` + 资源挂载与句柄 | 文件语义（`file:*`）与资源语义（`chips-resource://`）分属两套契约，不得互相替代 |
| `selection` / `dialog` | `dialog:*` | 用户选择不产生文件系统授权 |
| `transfer` / `shell` | `transfer:*`、`shell:openExternal` | 传输与外部打开分列，权限各自独立 |
| `association` | 资源打开与默认处理器契约 + manifest `fileAssociations` / `deepLinks` | 属打开路由与壳注册，不新增能力（[14-资源打开与默认处理器契约](../../05-接口与契约/14-资源打开与默认处理器契约.md)、[应用插件接口](../../05-接口与契约/07-应用插件接口.md)） |
| `device` / `screen` / `power` | `power:query`、`power:prevent-sleep`；屏幕枚举不提供 | 电池、充电、空闲与睡眠抑制为能力；多显示器由壳内部处理 |
| `systemUi` | `notification:send`、`clipboard:*`、`menu:set`、`tray:set`、`shortcut:*` | 五域独立注册、独立权限 |
| `background` | `power:prevent-sleep` + manifest `runtime.background` | 后台常驻属插件声明与内核调度，不新增壳能力 |
| `ipc`（named pipe / unix socket / shared memory） | 不迁移 | 插件访问面唯一门是 Bridge；壳内部进程通信不属公共契约 |
| `offscreenRender` | 无头壳离屏帧宿主（内部） | 不登记插件能力；复用同一渲染链路（第七节） |
| 旧 legacy 别名（`window` / `fs` / `dialog` / `clipboard` / `shell` / `platform` / `screen` / `tray` / `notification` / `shortcut` / `power` 服务名） | 全部作废 | 新架构使用能力 ID 与能力域，不保留别名与双轨 |

旧 Host 20 个服务域不逐项迁移：其中 `theme` / `i18n` 已随 ADR-006 废弃；`surface` / `window` 归一为 `window:*`；`file` / `resource` / `card` / `box` / `zip` / `serializer` 归入[资源管理设计](./04-资源管理设计.md)、[文档解析器设计](./06-文档解析器设计.md)、[文档服务设计](./11-文档服务设计.md)与文件处理契约；`command` 归[命令系统契约](../../05-接口与契约/13-命令系统契约.md)；服务域清单与能力域的完整对照以 01-16 子系统设计文档与[04-能力契约规范](../../05-接口与契约/04-能力契约规范.md)为准，本文不复制。

### 4.4 壳能力矩阵与平台标识

- 能力矩阵在构建期与启动期由壳按真实实现生成：分面缺失为 `false`，已实现为 `true`；**同一壳形态在不同平台或桌面环境下的矩阵可以不同**（例如 Linux 无托盘宿主时 `tray` 为 `false`），矩阵不由平台名字符串推断。
- 矩阵只供 Bridge 内置能力注册层消费：分面为 `false` 的能力域整体不注册（第五节）。
- `ShellKind` 与 `PlatformId` 是平台内部标识；对插件可见的平台标识只有 `system:info.platform`（取值即 `PlatformId` 字符串），其输出契约以[04-能力契约规范](../../05-接口与契约/04-能力契约规范.md) 第 7.14 节为准。

### 4.5 端口实现约束

| 编号 | 约束 |
|---|---|
| PAL-1 | 一个能力动作只有一个端口方法作为下沉实现，禁止在能力实现内直接调用 Electron / Tauri / 系统 API |
| PAL-2 | 端口不得假设调用来自可信输入；能力实现已做业务级校验，端口仍须做系统级约束（如窗口 ID 有效性、资源可解码性） |
| PAL-3 | 端口不得反向调用插件、不得发布业务事件；事件只由核心事件总线按[事件系统设计](./09-事件系统设计.md)投递 |
| PAL-4 | 端口返回结构必须结构化克隆兼容；句柄类对象只在核心侧存在，端口只传标识 |
| PAL-5 | 端口实现不得记录凭证明文与用户内容；诊断信息只写日志（[配置系统设计](./10-配置系统设计.md) 敏感配置边界） |

## 五、能力可用性与降级

### 5.1 三层判定

| 层次 | 判定对象 | 机制 | 失败表现 |
|---|---|---|---|
| 构建期 | 壳与平台组合是否存在该分面实现 | 壳实现完整性由构建与契约测试保证 | 构建产物不包含该分面 |
| 启动期 | 当前环境矩阵 | 壳生成能力矩阵；Bridge 按矩阵注册内置能力 | 注册校验失败终止启动；不可用能力不注册 |
| 运行期 | 环境是否可用（系统权限、硬件、桌面环境限制） | 端口返回正式域错误码 | 插件按错误码降级 |

### 5.2 不可用语义

| 情形 | 平台行为 | 插件可见结果 |
|---|---|---|
| 分面缺失（如无头壳的窗口分面） | 该能力域全部 ID 不注册 | `BRIDGE_CAPABILITY_NOT_FOUND`，`retryable: false` |
| 分面存在但当前环境不可用（通知权限被拒、无电池设备、剪贴板被系统禁用） | 能力仍注册，实现返回域错误码 | `NOTIFICATION_UNAVAILABLE`、`POWER_INFO_UNAVAILABLE`、`CLIPBOARD_UNAVAILABLE` 等；重试语义按错误码表 |
| 系统限制导致操作失败（全局快捷键被占用、托盘图标不可解码） | 返回域错误码 | `SHORTCUT_CONFLICT`、`SHORTCUT_REGISTER_FAILED`、`TRAY_ICON_INVALID`、`TRAY_SET_FAILED` 等 |
| 用户取消（对话框、系统选择器） | 返回正常取消结果 | `canceled: true`，不是错误（[04-能力契约规范](../../05-接口与契约/04-能力契约规范.md) 第 7.7 节） |
| 壳与核心内部异常 | 归一为通道级错误 | `BRIDGE_INTERNAL`，`retryable: false`，诊断写宿主日志 |

- 错误码的完整表与 `retryable` 取值以[04-能力契约规范](../../05-接口与契约/04-能力契约规范.md) 第十节为唯一权威，本文只列代表性条目。
- 禁止以空实现、静默忽略或返回假数据模拟能力可用（SB-5）。

### 5.3 插件侧降级规则

1. **不按平台名分支**：`system:info.platform` 只用于诊断与文案判断，不得用于功能分支；凡出现"平台不支持则走另一套逻辑"的实现即为缺陷。
2. **按调用结果降级**：`BRIDGE_CAPABILITY_NOT_FOUND` 表示该能力在当前宿主不可用；域错误码表示操作失败，按 `retryable` 决定是否重试。
3. **用户可见降级必须显式**：隐藏不可用入口或给出简体中文提示，禁止静默失败与永久转圈。
4. **不得缓存跨宿主的能力结论**：可用性由本次运行的宿主决定；插件不得把一次调用失败写入持久配置作为长期开关。
5. **权限不因降级放宽**：能力可用时必须经 Bridge 完整判定，降级路径不得绕过注册表、权限与审计。

### 5.4 平台侧过滤规则

- 表面过滤：移动壳不提供 `desktop` / `tray` 表面，无头壳不启动任何交互表面；平台在启用与启动阶段按矩阵过滤 `ui.surface`，不向用户暴露必然失败的启动入口（[应用插件接口](../../05-接口与契约/07-应用插件接口.md) 第 5.2 节）。
- 能力过滤：菜单、托盘、快捷键、对话框、外部打开与电源抑制类能力只在具备分面的壳注册；仅 `app` 角色可持有对应权限（[04-能力契约规范](../../05-接口与契约/04-能力契约规范.md) 第 6.3 节）。
- 过滤不得跳过权限判定与审计；过滤结果属于诊断信息，不构成新的插件 API。

### 5.5 明确不做

| 事项 | 结论 | 依据 |
|---|---|---|
| 屏幕枚举与多显示器管理 | 不提供能力；窗口定位坐标由壳按当前显示器在内部处理 | 内置能力总表无 `screen` 能力；旧 PAL `device.screen` 不迁移 |
| 能力快照 / 能力枚举 API | 不提供；Bridge 方法面固定，无枚举入口 | [02-Bridge三层设计](./02-Bridge三层设计.md) 第 4.4 节 |
| `web` 插件运行时 | 不提供；浏览器页面不是插件运行目标 | [04-能力契约规范](../../05-接口与契约/04-能力契约规范.md) 第 6.4 节 |
| 浏览器侧应用插件宿主（`plugin-sessions` / Web Runtime） | 不提供；不在本架构范围，插件运行目标只有 `host`；重新评估走 RFC → ADR | 本文 §2.2；旧社区平台链路只作历史证据 |
| named pipe / unix socket / shared memory 插件面 | 不提供；壳内部进程通信不是公共契约 | 旧 PAL `ipc` 分面不迁移 |
| 主题系统与多语言系统 | 已废弃；视觉由 `@chips/ui`、Design Tokens 与 antd 主题定制承担，文案简体中文直写 | [ADR-006](../ADR/ADR-006-主题系统与多语言系统.md) |
| 插件可调用的平台更新接口 | 不提供；平台更新是平台组件行为 | [06-更新与分发规范](../../06-开发与运维/06-更新与分发规范.md) 第 1.1 节 |

## 六、壳差异对照

### 6.1 总表

| 维度 | 桌面壳（Electron） | 无头壳 | 移动壳（Phase 5，Tauri 2） |
|---|---|---|---|
| 宿主进程 | Electron 主进程 | Node.js 进程 | Tauri 2 宿主进程 + 系统 WebView |
| 平台核心绑定 | Rust / Neon（`chips-native.node`） | Rust / Neon | Rust 核心 + JNI（Android）/ Swift FFI（iOS），Phase 5 引入 |
| 交互表面 | 多窗口（`ui.surface`：`window` / `desktop` / `tray`） | 无 | 全屏表面；`desktop` / `tray` 不提供 |
| 渲染宿主 | 可见窗口渲染进程（React 壳 + RenderHost + 帧） | 默认无；服务端渲染时提供离屏帧宿主 | 系统 WebView 内 RenderHost（同一帧协议） |
| 文件与目录 | 完整文件系统（PathGuard 与限定值约束） | 完整文件系统（服务/容器路径） | 应用沙箱目录 + 系统文档授权 |
| 对话框 | `dialog:open` / `dialog:save` | 不注册 | 系统文档选择器；导出走系统分享或文件流程 |
| 通知 | `notification:send`（系统通知） | 不注册 | 本地通知（系统策略约束） |
| 剪贴板 | `clipboard:read` / `clipboard:write` | 不注册 | 可用（系统策略约束） |
| 菜单 | `menu:set`（应用菜单 / 托盘菜单） | 不注册 | 不注册（系统 UI 提供应用级入口） |
| 托盘 | `tray:set` | 不注册 | 不适用 |
| 全局快捷键 | `shortcut:register` / `shortcut:unregister` | 不注册 | 不注册 |
| 电源 | `power:query` / `power:prevent-sleep` | 不注册（保活由部署层承担） | `power:query` 可用；`power:prevent-sleep` 不注册 |
| 系统信息 | `system:info` | `system:info` | `system:info`（`platform` 为 `android` / `ios`） |
| 外部打开 | `shell:openExternal` | 不注册 | `shell:openExternal`（系统浏览器 / 应用） |
| HTTP | `http:request` | `http:request` | `http:request` |
| 传输 | `transfer:download` / `transfer:cancel` | `transfer:*`（服务端拉取） | `transfer:*`（沙箱路径） |
| 工具进程 | Electron Utility Process | 无（进程即隔离单位） | Phase 5 由 Tauri sidecar / 系统服务决定 |
| 更新 | 平台自更新器（Phase 4） | 部署层镜像更新 | 应用商店机制，平台不实现自更新 |
| 窗口事件 | `window:created` / `window:closed` / `window:focused` | 不产生 | 按全屏表面生命周期发布同一组事件 |

- 表中"不注册"均表示对应能力域不进入 Bridge 注册表，调用返回 `BRIDGE_CAPABILITY_NOT_FOUND`；"可用"与"系统策略约束"表示能力注册，运行时失败按域错误码返回。
- 跨壳不变：能力 ID、权限 ID、错误码、事件名、文件格式与插件 `.cpk` 完全一致。

### 6.2 桌面壳（Electron）

- 主进程承载 Rust 核心（Cordis 运行时、Bridge、解析器、资源管理器）与 Bridge TS 适配层；preload 经 `contextBridge` 暴露 `window.chips`；窗口渲染进程运行 React 壳、RenderHost 与渲染帧（[05-渲染引擎设计](./05-渲染引擎设计.md) 第三节）。
- 窗口、菜单、托盘、快捷键、对话框、通知、剪贴板、电源、外部打开、自定义协议与离屏能力由桌面 PAL 实现；自定义协议处理器按 `protocol.handle` 现行口径实现（[ADR-002](../ADR/ADR-002-Electron作为桌面端壳.md) 现状注记）。
- 需进程级隔离的服务逻辑由工具进程承载，进程由壳提供、内核调度（[03-插件架构设计](./03-插件架构设计.md) 第 5.2 节）。
- 平台自更新器属壳组件，更新源、签名链与回滚以[06-更新与分发规范](../../06-开发与运维/06-更新与分发规范.md)为准。
- 安装器（macOS DMG、Windows NSIS、Linux AppImage / `deb`）属壳组件，只放置应用、信任根与内置插件包，不执行插件安装、启用或自检；内置插件引导与自检属平台首启流程（[06-更新与分发规范](../../06-开发与运维/06-更新与分发规范.md) §3.4、§3.5），三端共用同一实现。
- Linux 桌面环境差异（托盘宿主、全局快捷键、通知服务）只影响能力矩阵；同一二进制不按发行版分支。

### 6.3 无头壳

见第七节。

### 6.4 移动壳（Phase 5，Tauri 2）

- 采用 Tauri 2 作为移动壳：宿主进程 + 系统 WebView（Android WebView / WKWebView），平台抽象以 Kotlin（Android）与 Swift（iOS）实现，Rust 核心经 JNI / Swift FFI 复用（[ADR-003](../ADR/ADR-003-Rust核心加Node-Native-Module架构.md) 现状注记）。
- 交互表面为全屏：`window:*` 的能力语义映射到全屏表面的创建、聚焦、尺寸与关闭；多窗口语义不提供。
- 文件访问在应用沙箱与系统文档授权内；目录变量解析到沙箱文档目录；PathGuard、作用域与受控提交规则不变。
- 系统策略约束的能力（通知、剪贴板、后台执行）在系统拒绝时按域错误码返回；平台不得在系统权限未授予时伪造成功。
- 移动端不实现桌面自更新器；分发与更新走移动应用商店机制（[06-更新与分发规范](../../06-开发与运维/06-更新与分发规范.md) 不覆盖商店分发，本节为边界声明）。
- 移动端技术栈与移植方案在 Phase 5 启动时按 R16 走 RFC → 评审 → ADR 定案；当前口径为 Tauri 2 + Kotlin / Swift PAL，[ADR-007](../ADR/ADR-007-桌面端与移动端分离策略.md) 正文的 React Native 预选不再作为实现方向，ADR-007 按本口径修订。

## 七、无头宿主形态

### 7.1 定位与用途

无头宿主（Headless Host）是薯片平台的无交互运行形态：同一平台核心、同一 Bridge、同一插件体系，不创建窗口与系统 UI。用途：

- 服务端渲染：社区平台服务器的 Worker 从私有桶读取 `.card` / `.box` 源文件，经平台渲染链路生成查看缓存与封面缓存后写回对象存储（[服务端部署与运维](../../06-开发与运维/08-服务端部署与运维.md) 第 2.2 节）。
- 批处理与 CI：批量转换、校验、导出与自动化任务。
- 平台自动化：不需要用户界面的后台任务。

个人服务器**不做服务端渲染**，不使用无头宿主的渲染形态（[个人服务器设计](./15-个人服务器设计.md) 第七节）。

### 7.2 进程与入口

- 进程：单一 Node.js 进程，内嵌 Rust 核心（Neon）；不加载 Electron、不创建窗口系统连接。
- 入口：平台核心的无头入口；启动后完成与桌面壳相同的核心初始化与能力注册，但按无头矩阵跳过交互分面。
- 隔离：单实例进程；进程崩溃按内核崩溃隔离与恢复策略处理；不提供多实例协调（多副本由部署层编排，见第 7.5 节）。
- 插件：`service` 角色按启用偏好正常加载与运行；`app` / `basecard` / `boxlayout` 的交互与渲染入口只在具备表面与帧宿主时可用（第 7.4 节）。

### 7.3 能力矩阵

| 分面 | 无头可用性 | 说明 |
|---|---|---|
| 文件 `file:*`、资源 `resource:*`、文档 `document:*` | 可用 | 服务端渲染与批处理的基础链路 |
| 配置 `config:*`、凭证 `credential:*`、事件 `event:publish`、HTTP `http:request` | 可用 | 平台机制与网络访问 |
| 传输 `transfer:*` | 可用 | 服务端拉取远端资源 |
| 系统信息 `system:info` | 可用 | 日志、诊断与目录变量解析 |
| 窗口 `window:*`、对话框 `dialog:*`、通知 `notification:send`、剪贴板 `clipboard:*`、菜单 `menu:set`、托盘 `tray:set`、快捷键 `shortcut:*` | 不注册 | 无交互表面与系统 UI |
| 电源 `power:*`、外部打开 `shell:openExternal` | 不注册 | 保活由部署层承担；无可打开的系统界面 |

### 7.4 渲染形态

- 默认形态**无渲染帧宿主**：不提供帧运行时，需要交互帧的能力与功能在当前形态不可用（`BRIDGE_CAPABILITY_NOT_FOUND`）。
- 服务端渲染形态启用**离屏帧宿主**：不显示窗口、不创建可见表面，帧的创建、资源代理注入、握手、高度测量与释放完全复用[05-渲染引擎设计](./05-渲染引擎设计.md)的同一链路与同一帧协议。
- 离屏帧宿主是平台渲染引擎在无头壳中的宿主实现，不是第二条渲染管线：禁止任何服务、插件或转换流程自建离屏渲染栈（[文件处理契约](../../05-接口与契约/15-文件处理契约.md) 第 2.3 节）；产物写回、缓存与清理属服务端产品链路（[服务端部署与运维](../../06-开发与运维/08-服务端部署与运维.md) 第 2.2 节）。
- 离屏渲染不向插件暴露新能力：渲染调度由平台内部驱动，插件仍经角色接口参与内容渲染。

### 7.5 部署与运维衔接

- 无头宿主由部署层（Docker Compose / 进程管理器）保活、重启与升级；平台自更新器与商店分发不适用于无头形态。
- 资源限额（CPU、内存、并发）由部署层与内核软配额共同承担：内核软配额以[薯片内核设计](./01-薯片内核设计.md)为准，部署容量参数以服务端文档为准。
- 日志与诊断按[日志与诊断](../../06-开发与运维/03-调试指南.md)与部署规范落盘；无头宿主不产生窗口级日志。

## 八、平台阶段安排

### 8.1 桌面三端与 Linux

- macOS / Windows：Phase 0-3 实现与验证，Phase 4 发布验证。
- Linux：自 Phase 0 起保持平台无关设计，Phase 4 随桌面三端完成验证（R6、R7）；安装产物为 `Chips-<版本>-linux-x64.AppImage` 与 `.deb`（[构建与打包](../../06-开发与运维/02-构建与打包.md) 第六节）。
- Linux PAL 适配（目录约定、大小写敏感、托盘/快捷键/通知的桌面环境差异）在 Phase 3-4 收口，以能力矩阵表达可用性，不按发行版分支。
- 桌面三端共用同一桌面壳与同一套能力契约；平台差异只体现在 PAL 实现与矩阵。

### 8.2 Android 与 iOS（Phase 5，架构预留）

1. 移动端为 Phase 5 架构预留、暂不排期；启动需所有者决策（[开发流程与阶段计划](../../07-工程管理/02-开发流程与阶段计划.md) 第八节）。
2. 启动前按 R16 完成 RFC → 评审 → ADR：定案移动壳技术栈（当前口径为 Tauri 2）、Rust 核心移动绑定（JNI / Swift FFI）与移动能力清单，并同步修订 ADR-007。
3. 实现顺序为 Android 优先、iOS 随后（R6）。
4. 复用要求：`.card` / `.box` 文件格式零改动复用；Rust 核心、Bridge 接口与插件角色接口复用；移动特有系统能力（如 `mobile:*`）必须先登记进能力总表再使用（R19）。
5. 验收要求：安装、启动、核心功能与权限链通过移动端质量门禁；不支持的能力返回正式错误码，不伪造成功。
6. 分发与更新走移动应用商店机制，不实现桌面自更新器。

### 8.3 无头与 Web

- 无头壳随平台核心提供，不单独排期；服务端渲染、批处理与 CI 按需消费。
- Web 不提供插件运行时与浏览器侧应用插件宿主、不排期；只作为共享语义的降级实现方向（第五节、§2.2）。

## 九、约束与不变量

| 编号 | 约束 |
|---|---|
| SL-1 | 一核多壳：文件格式、Rust 核心与 Bridge 接口平台无关；壳差异不得进入插件可见面 |
| SL-2 | 平台核心零平台特判，壳零业务；平台差异只在 PAL 端口实现中 |
| SL-3 | 平台核心与插件不得 `import` Electron / Tauri / Kotlin / Swift / Node 系统模块；ModuleLoader 门禁不放行 |
| SL-4 | 壳与核心之间只有两条内部方向：端口调用（核心 → 壳）与能力注册 / 平台服务 / 会话身份 / 事件（壳 → 核心） |
| SL-5 | PAL 类型属平台内部类型，不由 `@chips/sdk` 导出、不出现在 `window.chips` |
| SL-6 | 能力可用性只以注册表为准：不可用能力不注册，调用返回 `BRIDGE_CAPABILITY_NOT_FOUND` |
| SL-7 | 环境级不可用必须返回正式域错误码并保持 `retryable` 语义，不得空实现假成功 |
| SL-8 | 插件不得按平台名或壳名分支；降级只按调用结果与错误码，且必须用户可见 |
| SL-9 | 壳过滤表面与能力不改变权限判定、schema 校验与审计；用户选择不产生文件系统授权 |
| SL-10 | 窗口与工具进程安全基线按 R17；生产环境禁止关闭 `webSecurity`，渲染帧固定 `sandbox="allow-scripts"` |
| SL-11 | 平台路径与目录变量只由壳解析；PathGuard、作用域与受控提交在核心，壳不得放宽 |
| SL-12 | 无头壳默认无帧宿主；服务端渲染复用同一渲染链路与帧协议，禁止第二渲染管线或自建离屏栈 |
| SL-13 | 移动壳为 Phase 5 架构预留；未实现平台不得写成已交付，移动特有绑定与能力先登记后使用 |
| SL-14 | 移动壳技术栈与桌面自更新边界以本文与 Phase 5 ADR 为准；商店分发不受桌面更新器覆盖 |
| SL-15 | 新增壳形态、新增平台包或 PAL 端口契约破坏性变更：RFC → 评审 → ADR → 门禁 → 文档同步 |
| SL-16 | 旧 PAL 分面、legacy 别名与旧 Host 服务域不迁移、不建兼容层；能力 ID 与能力域是唯一标识 |
| SL-17 | 插件运行目标只有 `host`：不提供浏览器侧应用插件宿主与 Web Runtime；重新引入必须走 RFC → 评审 → ADR 并同步修订本文与 ADR-007 |

## 十、自检清单

- [ ] 平台核心是否零平台特判，平台差异是否全部收敛到 PAL 端口？
- [ ] 壳是否零业务逻辑、零权限判定、零 schema 校验？
- [ ] 插件可见面是否只有 Bridge 三方法；PAL 类型是否未进入 SDK 与 `window.chips`？
- [ ] 能力矩阵是否按真实实现生成；缺失分面是否表现为不注册而不是假成功？
- [ ] 不可用能力与不可用环境是否分别返回 `BRIDGE_CAPABILITY_NOT_FOUND` 与正式域错误码？
- [ ] 插件降级是否只依据调用结果，且对用户可见、不按平台名分支？
- [ ] 无头壳的能力矩阵是否与第七节一致；离屏渲染是否复用同一渲染链路与帧协议？
- [ ] 移动壳与无头壳是否未把未交付能力写成已交付；移动特有绑定与能力是否先登记后使用？
- [ ] 是否未引入浏览器侧插件宿主、Web Runtime 或插件会话 API；插件运行目标是否只含 `host`？
- [ ] Linux 差异是否只体现在 PAL 实现与能力矩阵，未按发行版分支？
- [ ] 是否未引入旧 PAL 分面、legacy 别名、能力快照或任何兼容层？
