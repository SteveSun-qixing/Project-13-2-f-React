## 六、插件加载、停用与卸载

> 内核只处理状态机、依赖与生命周期；清单校验、包读取与安装由插件管理层完成（[03-插件架构设计.md](03-插件架构设计.md)）。内核接收的 `LoadRequest` 已包含插件 ID、版本、依赖声明与 `PluginRunner`。

### 6.1 插件代码适配层

```rust
use async_trait::async_trait;

/// 插件代码的执行抽象；TypeScript 插件由 Neon 适配层实现。
#[async_trait]
pub trait PluginRunner: Send + Sync {
    /// 执行插件 apply（Starting 阶段）；返回前副作用必须已登记到 `ctx` 对应 Fork。
    ///
    /// 超时上限 30s（`LIFECYCLE_APPLY_TIMEOUT`），超时按 6.7 强制撤销并报
    /// `KERNEL_LIFECYCLE_TIMEOUT`。
    async fn apply(&self, ctx: &Context, config: &PluginConfig) -> Result<(), KernelError>;

    /// 插件停用回调（Stopping 阶段）；正常清理由 Fork 撤销负责。
    ///
    /// 超时上限 10s（`LIFECYCLE_STOP_TIMEOUT`），超时后不再等待并进入强制撤销（6.7）。
    async fn stop(&self, ctx: &Context) -> Result<(), KernelError>;
}
```

`PluginConfig` 是插件命名空间生效值的只读视图：内核在插件进入 `Starting` 时向配置系统取一次快照并传入 `apply`，apply 期间不可变；定义与变更传播见 [10-配置系统设计.md](10-配置系统设计.md) 2.5。

### 6.2 状态机

内核状态与插件管理层状态（[03-插件架构设计.md](03-插件架构设计.md) 第三节）一一对应；`Resolving` 是内核内部子阶段，不对外暴露。

```
  Pending ──load──▶ Resolving ──就绪──▶ Starting ──成功──▶ Active
                        │                   │                │
                        │ 缺失/版本暂不满足   │ 应用失败/超时   │ disable
                        ▼                   ▼                ▼
                Pending（等待依赖）         Failed          Stopping
                                                               │ 撤销完成
                                                               ▼
                                                           Installed

  Resolving ──版本范围不可满足（互斥）──▶ Failed（KERNEL_DEPENDENCY_VERSION，见 7.4）
```

`Failed` 与 `Installed` 均可通过 `enable` 返回 `Resolving`；仅 `Installed`／`Failed` 可 `unload` 至 `Removed`（终态）。

状态与迁移：

| 内核状态    | 对应管理层状态 | 含义                         | 允许迁移到                                                                                  |
| ----------- | -------------- | ---------------------------- | ------------------------------------------------------------------------------------------- |
| `Pending`   | `pending`      | 启用请求已受理，等待依赖满足 | `Resolving`、`Installed`（取消）                                                            |
| `Resolving` | （内部子阶段） | 解析依赖、版本与拓扑序       | `Starting`、`Pending`（缺失/版本暂不满足）、`Failed`（成环／版本互斥）、`Installed`（取消） |
| `Starting`  | `starting`     | 执行 `PluginRunner.apply`    | `Active`、`Failed`（经 Fork 回滚）、`Installed`（取消）                                     |
| `Active`    | `active`       | 运行中                       | `Stopping`、`Failed`（任务 panic）                                                          |
| `Stopping`  | `stopping`     | 正在撤销副作用               | `Installed`（撤销失败只上报，不阻断停用）                                                   |
| `Installed` | `installed`    | 已停用，登记保留、零副作用   | `Resolving`（重新启用）、`Removed`                                                          |
| `Failed`    | `failed`       | 加载或运行失败，副作用已回滚 | `Resolving`（重试）、`Removed`                                                              |
| `Removed`   | （注销）       | 内核登记已移除               | 终态                                                                                        |

- 非法迁移返回 `KERNEL_INVALID_TRANSITION`；`unload` 只接受 `Installed` 与 `Failed`，`Active`／`Stopping` 的卸载请求必须先在插件管理层完成停用。
- 依赖缺失或版本暂不满足不是失败：插件停留在 `Pending`，依赖就绪后自动继续 `Resolving`；版本范围不可满足（互斥）是显式冲突，进入 `Failed`（7.4）。

### 6.3 加载流程

```
load(request)
  │
  ├─ 1. Pending → Resolving
  ├─ 2. 依赖解析：拓扑排序（7.2）、环检测（7.3）、缺失与版本检查（7.4）
  ├─ 3. 按拓扑序对未激活插件逐个执行 Starting：
  │      a. 创建插件 Fork（挂载到目标 Context）
  │      b. PluginRunner.apply(ctx, config)（超时上限 30s，见 6.7）
  │      c. 注册服务（写入暂存代际）、订阅事件、登记任务（全部进入插件 Fork）
  │      d. → Active：暂存代际一次原子发布并触发级联重建（5.2、5.4）
  │      e. 发布 plugin:loaded（结构化 payload）
  ├─ 4. 应用失败或超时：dispose 插件 Fork 回滚（暂存代际一并丢弃）→ Failed，返回错误
  ├─ 5. 缺失依赖或版本不可满足：停留在 Pending 或进入 Failed，见 7.4
  └─ 6. 全部完成：返回成功
```

应用与回滚：

```rust
impl PluginManager {
    /// 应用单个插件；失败或超时时回滚插件 Fork 并进入 Failed。
    async fn apply_one(&self, id: &PluginId) -> Result<(), KernelError> {
        self.mark(id, PluginState::Starting)?;
        let fork = self.forks().create_plugin_fork(id)?;
        let context = self.contexts().context_of(fork)?;
        let runner = self.runners().get(id)?;
        let config = self.configs().get(id)?;

        let applied = tokio::time::timeout(
            LIFECYCLE_APPLY_TIMEOUT,
            runner.apply(&context, &config),
        )
        .await;
        let failure = match applied {
            Ok(Ok(())) => None,
            Ok(Err(_)) => Some(KernelError::ApplyFailed { id: id.clone() }),
            Err(_) => Some(KernelError::LifecycleTimeout {
                id: id.clone(),
                phase: LifecyclePhase::Apply,
            }),
        };

        if let Some(error) = failure {
            self.audit().record_apply_failure(id, &error);
            // 强制撤销：丢弃暂存代际，触发任务取消并按强撤上限等待退出（6.7）。
            let rollback = self.forks().dispose(fork);
            self.mark(id, PluginState::Failed)?;
            rollback?;
            return Err(error);
        }

        // 进入 Active：暂存代际一次原子发布，随后触发依赖方级联重建。
        self.services().publish_staged(fork)?;
        self.mark(id, PluginState::Active)?;
        self.rebuild_dependents(fork)?;

        let payload = serde_json::json!({
            "pluginId": id,
            "version": self.versions().get(id)?.to_string(),
            "role": self.roles().get(id)?,
        });
        self.events().emit(&Event::new("plugin:loaded", payload), &context)?;
        Ok(())
    }
}
```

加载规则：

1. 加载顺序 = 依赖拓扑序；若 A 依赖 B，则 B 的 apply 必然先于 A。
2. 插件若消费其他插件提供的服务，必须声明对该提供方的依赖；未声明时不保证顺序。
3. apply 期间允许异步等待，但内核命令循环在等待期间继续处理其他命令。
4. 同一插件的重复 `load` 幂等：已 `Active` 直接返回成功，`Failed` 则先重试（`Failed → Resolving`）。
5. 加载事务性：失败时通过 Fork 撤销已产生的一切副作用（含暂存代际），不留部分注册。
6. apply 超时上限 30s，超时按 6.7 强制撤销并返回 `KERNEL_LIFECYCLE_TIMEOUT`；插件进入 `Failed`。
7. `plugin:loaded` 的 payload 为结构化对象 `{ pluginId, version, role }`，与 [05-事件契约规范.md](../../05-接口与契约/05-事件契约规范.md) 一致。

### 6.4 停用与卸载流程

```
disable(id)
  ├─ 1. 依赖者检查：存在 Active 依赖者且未显式级联 → 拒绝（KERNEL_DEPENDENCY_CONFLICT）
  ├─ 2. Active → Stopping
  ├─ 3. PluginRunner.stop(ctx)（可选回调；超时上限 10s，见 6.7）
  ├─ 4. dispose 插件 Fork：服务摘除、监听撤销、任务取消
  ├─ 5. 显式级联时按逆拓扑序停用依赖者
  └─ 6. → Installed

unload(id)
  ├─ 1. 依赖者检查：存在依赖者 → 始终拒绝，须先卸载依赖者
  ├─ 2. 仅接受 Installed／Failed；否则拒绝（KERNEL_INVALID_TRANSITION）
  ├─ 3. 从依赖图与登记表移除
  └─ 4. → Removed
```

停用规则：

1. 停用存在 `Active` 依赖者的插件默认拒绝；显式级联时先按逆拓扑序停用依赖者（[03-插件架构设计.md](03-插件架构设计.md) 第七节）。
2. `stop` 回调失败不阻断撤销：记录错误后继续 Fork 撤销，最终仍进入 `Installed`。
3. `stop` 超时（上限 10s）不阻断撤销：不再等待回调，直接进入强制撤销（6.7），上报 `KERNEL_LIFECYCLE_TIMEOUT`，最终仍进入 `Installed`。
4. `Stopping` 期间拒绝新的服务注册与事件订阅。
5. 插件被停用后，其服务条目全部摘除，消费方注入回到 `Waiting`，期间服务解析返回 `KERNEL_SERVICE_NOT_FOUND`（7.5）。

### 6.5 热更新（蓝绿替换）

更新由插件管理层发起（[03-插件架构设计.md](03-插件架构设计.md) 6.2），内核提供 Fork 与代际原语：

1. 以新版本创建新插件 Fork 并执行 `Starting`；旧 Fork 继续 `Active`，服务代际暂不切换。
2. 新 Fork 进入 `Active` 时，暂存代际一次原子发布，即为代际切换点；注册表与路由指向新版本（5.2）。
3. 旧 Fork 进入 draining：拒绝新调用并等待进行中的调用结束；超时后强制 `dispose`。
4. 插件状态始终为 `Active`，不产生 `Stopping → Starting` 的插件级迁移。
5. 任一步失败：dispose 新 Fork，旧 Fork 继续运行，插件状态保持 `Active`。

约束：

- 更新窗口内最多两个 Fork（旧、新）并存；代际切换后旧 Fork 不再处理新调用。
- 服务名与能力 ID 在更新前后不变；消费方通过级联重建（5.4）获得新代际。
- 新版本必须满足所有依赖者的版本范围，否则更新请求被拒绝。
- draining 上限与强制撤销时机由插件管理层按角色决定：`app` 角色在旧窗口全部关闭前只冻结、不强制撤销；其它角色按上限强制撤销（[03-插件架构设计.md](03-插件架构设计.md) 6.3）。内核只提供撤销原语，不感知角色。

### 6.6 失败回滚

- 应用阶段失败必须回滚到插件加载前的状态：dispose 插件 Fork、丢弃暂存代际、清除服务与监听、停止已启动任务。
- 回滚使用第四章的 Fork 机制，不引入独立的回滚逻辑。
- 结果与原因以终止状态（`Failed` 或 `Pending`）与错误码对外呈现；审计记录包含插件 ID、阶段与首个错误。

### 6.7 生命周期超时与强制撤销

生命周期超时常量由内核唯一定义，其它文档引用本节，不自行书写数值：

| 常量                         | 值  | 适用阶段                          |
| ---------------------------- | --- | --------------------------------- |
| `LIFECYCLE_APPLY_TIMEOUT`    | 30s | `PluginRunner.apply`              |
| `LIFECYCLE_STOP_TIMEOUT`     | 10s | `PluginRunner.stop`               |
| `FORK_FORCE_DISPOSE_TIMEOUT` | 30s | Fork 强制撤销时等待任务退出的上限 |

策略：

1. **apply 超时**：中止等待并按失败处理——dispose 插件 Fork 回滚（暂存代际一并丢弃），插件进入 `Failed`；调用方收到 `KERNEL_LIFECYCLE_TIMEOUT`（`details` 含插件 ID 与阶段 `apply`）。
2. **stop 超时**：不再等待回调，直接进入 Fork 强制撤销；插件仍进入 `Installed`，`KERNEL_LIFECYCLE_TIMEOUT` 记入审计。
3. **强制撤销**：对 Fork 内全部任务触发取消信号，等待退出至多 `FORK_FORCE_DISPOSE_TIMEOUT`；仍未退出时中止等待、不再阻塞生命周期，继续撤销其余副作用。
4. **可观测**：超时记录插件 ID、阶段、实际耗时与在途任务数；连续超时计入崩溃重启窗口（6.8）。
5. **协作式取消**：任务必须周期性检查取消信号并在取消时释放已占用资源（10.4）；拒绝响应取消视为插件缺陷。

### 6.8 崩溃重启与熔断

- 运行期异常与任务 panic 被隔离后按受控重启处理：同一插件在 10 分钟滚动窗口内最多自动重启 3 次。
- 每次重启按指数退避调度：首次 1s，其后 2s、4s，单次间隔上限 30s。
- 超过上限进入 `Failed` 并停止自动重启，等待用户显式启用（`enable`）后重置窗口计数。
- 崩溃重启复用 `Failed → Resolving → Starting` 迁移（6.2）；插件停用或卸载时清零窗口计数。
- 重启、熔断与恢复动作全部写审计；插件管理层策略与此一致（[03-插件架构设计.md](03-插件架构设计.md) 9.3）。

注（审计承载口径裁定注记，2026-09-23，任务 #167 升级③ 主智能体裁定批准落文）：本条「重启、熔断与恢复动作全部写审计」在内核现实现（chips-cordis）中的承载现状为——崩溃首因写入插件记录诊断字段 `last_error` / `last_failure`（`plugin.rs` `PluginRecord` 字段，由 `service.rs` `fail_plugin_inner` 在失败收敛段写入，经 `kernel.rs` `plugin_last_error` 对外提供只读诊断）；重启与熔断动作以 `plugin.rs` `crash_window` 滚动窗口计数承载（每次崩溃与激活失败经 `register_crash_attempt` 计入，窗口内有效计数经 `kernel.rs` `plugin_crash_attempts` 公开观测，`crash_restart_exhausted` 给出熔断判定，显式 `enable` 重置与停用、卸载清零由 `reset_crash_window` 与状态迁移钩子 `apply_crash_window_lifecycle_hook` 执行）；自动重启沿 `Failed → Resolving → Starting` 在册迁移收敛、激活成功后复用在册事件 `plugin:loaded`（与常规加载同发射点，`command.rs` `finish_activation`）。事件面不设独立 restart 类事件名，禁止自造事件名或审计事件种类（与工单046 段四 RFC `DecisionObserver` 不复用 cordis 事件总线的红线一致）。

### 6.9 插件软配额与超限降级

内核定义插件软配额与计量点；插件、服务与插件管理层文档引用本节，不自行定义阈值。

| 配额     | 计量点                                                                                            | 默认值    |
| -------- | ------------------------------------------------------------------------------------------------- | --------- |
| 内存     | 插件 Fork 存活期内登记的插件对象、任务缓冲与句柄占用，按 5s 采样估算                              | 256 MiB   |
| 任务数   | 同一插件 Fork 内活跃 `ctx.task` 任务计数（`Effect::Task` 登记与撤销）                             | 32        |
| 消息速率 | 插件每秒发出的 Bridge 能力调用与事件发布合计（1s 滑动窗口；在 Bridge 调用入口与事件发布入口计数） | 200 次/秒 |
| 后台时长 | 插件在无用户交互下连续后台运行时长（任务运行时长累加，任务退出即回落）                            | 10 分钟   |

超限状态机：**限流 → 暂停 → 停用**。

```
正常 ──超限──▶ 限流：拒绝新增调用与事件发布并告警；回落即恢复
                  │ 持续超限或反复越界
                  ▼
              暂停：暂停后台任务与新调用，保留插件状态；配额稳定回落即恢复
                  │ 仍不收敛
                  ▼
              停用：Active → Stopping → Installed；上报 KERNEL_QUOTA_EXCEEDED 并写审计
```

规则：

- 软配额不因单次越界直接停用：默认先限流，仅在持续或反复越界时升级。
- 默认值以内核常量为准；策略性调整经平台配置 schema 登记后生效（[10-配置系统设计.md](10-配置系统设计.md)）。
- 降级、恢复与停用全部写审计；恢复不绕过崩溃重启窗口（6.8）。
- 配额计量不得阻塞发布与调用热路径；采样与判定在命令循环外完成。
