## 九、并发写入与原子性

### 9.1 单写者模型

- 平台以单实例运行（由壳层保证），Rust 核心位于 Electron 主进程，是该用户配置文件与工作区配置文件的唯一写入者。
- 渲染进程与插件经 Bridge `bridge:request` 提交写入，在主进程内串行化，天然避免多进程写竞争。
- 宿主层不与外部编辑器共享写锁；外部修改的检测与处理见 9.5。

### 9.2 写入提交管线

```
插件 / 设置类插件
    │ chips.request('config:set', { namespace, key, value, scope })
    ▼
Bridge 层：能力注册表 · 权限判定 · 输入 schema 校验
    │ IPC bridge:request（渲染进程 → 主进程）
    ▼
宿主层：原生模块封装
    │ Neon 调用
    ▼
Rust ConfigStore：
    1. 解析调用方命名空间、目标命名空间与目标层
    2. 值 schema 校验与策略锁定检查
    3. 更新目标层键集，重新解析生效值
    4. 生成文件内容 → 临时文件 → fsync → 原子替换
    5. 切换内存快照
    6. 发布 config:changed
    ▼
Bridge 事件桥（event:*）→ 订阅方
```

### 9.3 原子替换

- 在目标文件同一目录创建临时文件，写入完整内容后 `flush` 并 `fsync`。
- 用平台原子替换覆盖目标：Unix 使用 `rename(2)`；Windows 使用 `MoveFileExW(MOVEFILE_REPLACE_EXISTING)`。
- Unix 上替换后对目录执行 `fsync`，确保目录项落盘。
- 任一步骤失败时保留旧文件，内存快照不切换，返回 `CONFIG_WRITE_FAILED`。

### 9.4 内存快照与写队列

- 读路径全部命中内存快照，无磁盘 I/O；快照通过 `ArcSwap` 整体切换，读取无锁。
- 每个配置文件对应一个异步互斥锁与一个提交队列；同层批量操作（如多键 `config:reset`）合并为一次落盘。
- 落盘成功后才切换快照，保证内存视图与磁盘状态一致（write-through）。
- 同键并发写入按队列到达顺序执行，最后一次成功提交的值为准；不同键的写入互不丢失。
- **`config:set` 不用于高频状态**：每次成功写入都可能触发落盘与 `config:changed`。频率约束建议：同一键写入间隔不低于 1s，单插件写入不超过 10 次/秒；播放进度、编辑光标、实时指标等高频变化必须保留在内存并经事件或方法调用传播，不进入配置。超过建议频率的写入记录审计告警，用于发现设计错误而非限流。

### 9.5 外部修改

- 平台对每个配置文件挂文件监视（去抖后比对内容摘要）。
- 外部修改合法且通过校验时，采纳为新基线，重算生效值，按键发 `config:changed`（`origin: external`）。
- 外部修改不可解析或未通过校验时，进入保护状态：保留该文件，平台对该文件的写入返回 `CONFIG_EXTERNAL_MODIFIED`，内存继续使用旧快照。
- 调用方对受保护文件执行同层 `config:reset` 可丢弃外部内容并按当前 schema 重建该文件，从而解除保护。

### 9.6 失败与崩溃恢复

- 崩溃只会发生在旧文件完整或新文件完整两种状态之间，不存在半写文件。
- 启动时若发现临时件残留，直接丢弃；目标文件不可解析时按 9.5 的保护流程处理。
