## 七、依赖与组合

### 7.1 `dependencies` 声明

```yaml
id: chips.app.image-editor
type: app
dependencies:
  - id: chips.basecard.image
    version: ^1.0.0
  - id: chips.service.image
    version: ^1.0.0
```

规则：

- 只声明直接依赖，不声明传递依赖；传递关系由解析器推导。
- 每个条目由 `id`（插件 ID）与 `version`（语义化版本范围）组成，只允许一个已安装版本满足范围。
- `dependencies` 表达插件包之间的依赖；消费其他插件提供的服务时，必须声明对该提供方插件的依赖，并用 `ctx.inject` 表达服务注入（[01-薯片内核设计](01-薯片内核设计.md) §6.3）。
- 依赖目标可以是任意角色；`app` 依赖 `basecard` / `service` 是最常见的组合（§7.5）。
- 清单字段的完整说明与校验规则见 [02-插件清单规范](../../03-插件开发/02-插件清单规范.md)。

### 7.2 依赖解析

解析器接口：

```typescript
export interface IPluginResolver {
  /** 返回满足依赖关系的启用顺序（被依赖者在前） */
  resolveEnableOrder(pluginIds: readonly string[]): Promise<readonly string[]>;
  /** 返回安全的停用顺序（依赖者在前） */
  resolveDisableOrder(pluginIds: readonly string[]): Promise<readonly string[]>;
}
```

算法步骤：

1. 收集目标插件的直接依赖，构建有向图（边 A → B 表示 A 依赖 B）；同一依赖重复声明直接拒绝（`KERNEL_DEPENDENCY_DUPLICATE`）。
2. 环检测：出现环时拒绝启用，返回 `KERNEL_DEPENDENCY_CYCLE` 并列出环路径。
3. 缺失检查：依赖的插件不存在或未安装，启用请求转入 `pending`，记录 `KERNEL_DEPENDENCY_MISSING`。
4. 版本检查：已安装版本不在声明范围内时区分两种情况——存在可满足范围的候选版本则保持 `pending` 等待更新；候选集合与范围无交集（互斥）则拒绝启用，返回显式 `KERNEL_DEPENDENCY_VERSION` 冲突，`details` 附双方范围与候选版本列表，插件进入 `failed`。
5. 拓扑排序：被依赖者在前，得到启用顺序；反向得到停用顺序。
6. 对 `pending` 插件，在依赖全部就绪后自动继续激活（§4.3）。

解析由内核 `PluginManager` 执行，错误码与状态语义以 [01-薯片内核设计](01-薯片内核设计.md) §6、§7 为准。

### 7.3 依赖就绪与级联

- 被依赖插件故障（`failed`）时，依赖它的插件不自动停用：已启用的保持 `active`，尚未启用的保持 `pending`；服务条目摘除，依赖者调用返回 `KERNEL_SERVICE_NOT_FOUND`，被依赖插件恢复后按拓扑序重建注入、服务可继续使用（[01-薯片内核设计](01-薯片内核设计.md) §7.5）。
- 停用被依赖插件：默认拒绝；显式级联时按逆拓扑序停用依赖者（§4.4）。
- 卸载存在依赖者的插件：始终拒绝（`KERNEL_DEPENDENCY_CONFLICT`），用户须先卸载依赖者（§4.5）。
- 被依赖插件更新时必须满足依赖者版本范围（§6.4）。
- **依赖版本互斥是显式冲突**：候选版本集合与声明范围无交集时返回 `KERNEL_DEPENDENCY_VERSION`（附双方范围与候选版本），不再静默 `pending`（[01-薯片内核设计](01-薯片内核设计.md) §7.4）。

### 7.4 多角色拆分规则（R1）

1. 一个插件只有一个角色；禁止多角色合并。
2. 需要多角色能力时拆分为多个插件，用 `dependencies` 组合（ADR-005）。
3. 拆分判据：
   - UI 边界：需要独立窗口与启动器 → `app`；需要嵌于宿主视图的渲染 → `basecard` 或 `boxlayout`。
   - 数据格式边界：定义卡片类型 → `basecard`；定义箱子布局 → `boxlayout`。
   - 复用边界：能力被多个角色或多个插件消费 → `service`。
   - 生命周期边界：需要后台常驻 → `service`；随用户操作启动 → `app`。
4. 拆分后的插件之间只通过服务 / 能力 / 事件通信（§8），不得共享代码内部状态。
5. 拆分后每个包独立版本化、独立热更新。

示例：图片卡片、图片编辑应用与图像服务拆分为三个插件：

```yaml
# 基础卡片插件：只定义卡片类型
id: chips.basecard.image
type: basecard

# 图像服务插件：无界面能力提供方
id: chips.service.image
type: service

# 应用插件：依赖卡片类型与服务
id: chips.app.image-editor
type: app
dependencies:
  - id: chips.basecard.image
    version: ^1.0.0
  - id: chips.service.image
    version: ^1.0.0
```

### 7.5 组合模式

| 组合 | 说明 |
|---|---|
| `service` + `app` | 应用消费后台服务（索引、同步、图像处理） |
| `service` + `basecard` | 卡片渲染与编辑消费通用能力（解码、转换、模板） |
| `basecard` + `app` | 编辑器类应用处理卡片类型；经服务或能力通信 |
| `app` + `app` | 应用间协作（如查看器被资源管理器调起打开文件） |

- 组合中的一切调用经 §8 的三条合法通道；拆分不产生任何直接引用。
