## 二、三层模型

### 2.1 分层与职责

```text
┌──────────────────────────────────────────────────────────────┐
│ 插件层（渲染进程）                                             │
│ 插件业务代码 · window.chips（preload 注入，Bridge 层暴露面）    │
│ 只做：发起请求、订阅事件、创建资源句柄、处理结果               │
└──────────────────────────────────────────────────────────────┘
                 ↕ IPC（contextBridge + ipcRenderer）
┌──────────────────────────────────────────────────────────────┐
│ Bridge 层（主进程 + 渲染进程 preload 薄壳）                     │
│ 会话解析 · 能力注册表 · 权限判定 · JSON Schema 校验            │
│ 路由与执行 · 超时/取消/并发 · 事件通道 · 错误归一              │
└──────────────────────────────────────────────────────────────┘
                 ↕ 内核路由（服务调用）+ Neon（Rust ↔ Node.js）
┌──────────────────────────────────────────────────────────────┐
│ Host 层（能力提供方）                                          │
│ 平台服务域（文件/窗口/图像/通知/资源/文档…）· 服务插件          │
│ 只做：能力实现与系统 API 封装                                  │
└──────────────────────────────────────────────────────────────┘
```

| 层 | 组成 | 职责 | 明确不负责 |
|---|---|---|---|
| 插件层 | 插件业务代码、调用点 | 声明调用意图；按 `ChipsError.code` 处理结果 | 身份声明、授权判断、越权输入（全部视为不可信） |
| Bridge 层 | 渲染进程 preload 传输壳 + 主进程 Bridge 核心 | 会话解析、注册表、权限判定、schema 校验、路由、超时/取消/并发、事件通道、错误归一 | 业务实现；UI；Cordis 服务注册与生命周期（属内核） |
| Host 层 | 平台服务域、服务插件 | 能力实现；系统 API 封装；资源级二次约束（路径安全、域名白名单核对） | 不重复权限判定与 schema 校验；不反向调用插件 |

实现分工：

- Bridge 核心（注册表、权限判定、schema 校验、路由）属于 Rust 核心能力，经 Neon 供 Electron 主进程调用（[ADR-003](../ADR/ADR-003-Rust核心加Node-Native-Module架构.md)）。
- 主进程 TS 适配层负责 `ipcMain` 通道注册、会话注册表（webContents ↔ 会话）与 IPC 编解码，不承载授权逻辑。
- 渲染进程 preload 仅做转发、订阅登记、错误还原与**快速失败预检**；预检使用会话权限快照（经 `session:permissions` 下行同步，见 7.4），不构成安全边界。

### 2.2 层间规则

1. **单向调用**：插件层 → Bridge 层 → Host 层。Host 层不得反向调用插件层，只能通过事件通道推送（见[09-事件系统设计](./09-事件系统设计.md)）。
2. **无旁路**：插件不得直接 `import` Node/Electron/系统模块，不得直接使用 `ipcRenderer`，不得自建 IPC 通道或 `file://` 直载资源。
3. **身份不可自报**：调用方身份（插件 ID、会话、权限）只由 Bridge 层按 IPC 来源解析；请求负载中即使携带身份字段也仅作诊断，不参与授权。
4. **渲染进程不可信**：插件层输入一律按不可信处理；会话有效性、权限、schema 三步校验全部在 Bridge 层完成。
5. **平台内部调用同链路**：平台自身调用能力（含服务插件）同样经过注册表、权限判定与 schema 校验，不得绕行。
6. **事件投递单向、发布走能力**：事件只从 Host 侧事件总线推送到插件（`event:<eventId>`）；插件发布事件必须经能力 `event:publish` 走 `bridge:request` 链路（受权限判定与 schema 校验），不存在独立的发布通道。

### 2.3 完整调用流程（能力调用）

1. 插件调用 `window.chips.request(capabilityId, input)`。
2. preload 生成 `requestId`，构造 `IBridgeRequest`，执行 `ipcRenderer.invoke('bridge:request', request)`。
3. 主进程 Bridge 适配层按 `event.sender` / `event.senderFrame` 解析来源会话；无法解析则返回 `BRIDGE_SESSION_UNKNOWN`。
4. Bridge 核心查能力注册表；未命中返回 `BRIDGE_CAPABILITY_NOT_FOUND`。
5. 权限判定（第五节）；不通过返回 `BRIDGE_PERMISSION_DENIED`。
6. JSON Schema 校验（第六节）；不通过返回 `BRIDGE_INVALID_INPUT`。
7. 并发与超时策略生效（第八节），组装调用上下文 `ctx`（会话、权限、`signal`、`deadline`），经内核路由交给 Host 实现。
8. Host 执行 `capability.execute(input, ctx)`，返回结果或抛出错误。
9. Bridge 层归一错误（第九节），编码 `IBridgeResponse` 返回。
10. preload 还原结果：`ok` 为真时 resolve `result`；`ok` 为假时以 `ChipsError` reject。

```text
插件层                        Bridge 层（主进程）                    Host 层
────────                      ─────────────────────                  ────────
chips.request(id, input)
    │  生成 requestId
    └──── bridge:request ────►┌──────────────────────────────┐
                              │ 1 会话解析（来源帧 → 会话）   │
                              │ 2 注册表命中                  │
                              │ 3 权限判定（capability.       │
                              │   permissions ⊆ 会话快照）    │
                              │ 4 Schema 校验（预编译）       │
                              │ 5 并发与超时策略              │
                              └──────────────┬───────────────┘
                                             │ execute(input, ctx)
                                             ▼
                                       能力实现（服务域）
                                             │
    ┌──────────────── IBridgeResponse ◄───────┘
    │  ok=false → ChipsError
    │  ok=true  → result
    └──► resolve / reject
```

### 2.4 事件订阅流程

1. 插件调用 `window.chips.subscribe(eventId, handler)`；preload **同步**登记本地订阅并返回 `ISubscription`。
2. 同一窗口内该 `eventId` 的本地订阅计数由 0 变为 1 时，preload 挂载 `ipcRenderer.on('event:<eventId>', …)` 监听，并经 `event:control` 向主进程发起 subscribe。
3. 主进程转发器校验事件已在事件契约登记、且订阅者具备订阅权限；失败时经 `event:control` 回执 `EVENT_NOT_REGISTERED` 或 `EVENT_SUBSCRIBE_DENIED`。
4. 登记确认前到达的事件负载先缓冲，确认后按序派发；回执失败时丢弃缓冲并移除监听，该订阅不再收到投递。
5. Host 侧事件总线发布事件后，转发器按窗口订阅计数投递 `event:<eventId>`（计数为 0 的窗口不做序列化、不占用 IPC）。
6. 单个 handler 抛出的异常被 preload 捕获并记录，不影响其他订阅者与后续投递。
7. `dispose()` 使该订阅失效（幂等）；本地计数归零时移除监听并经 `event:control` 发起 unsubscribe。
8. 会话销毁时，Bridge 层一次性清理该会话全部订阅与转发标记。

### 2.5 资源访问流程

资源存在两条正式路径，作用域解析与权限判定一致：

**句柄路径（生命周期控制与失效感知）**

1. 插件调用 `window.chips.resource(uri)`，preload 基于会话权限快照做同步预检：URI 非法或明显越权立即抛出 `ChipsError`，不返回句柄。
2. 预检通过返回懒打开的代理句柄；首次 `metadata()` 触发 `bridge:resource` 的 `open` 操作。
3. 主进程再次执行解析、作用域与会话校验、权限判定（纵深防御），分配句柄 ID 并写入句柄表。
4. 字节由 `chips-resource://` 协议处理器按 Range 提供（不经 IPC）；句柄负责失效感知与生命周期。
5. `release()` 归还租约；会话结束强制释放全部句柄。

**协议路径（交给渲染引擎加载）**

```text
<img src="chips-resource://card-001/image.jpg">
    → Chromium 网络层
    → 主进程 chips-resource:// 协议处理器
    → 会话解析 + 权限判定 + 路径安全
    → 资源管理器（缓存/流式）
    → 响应数据流
```
