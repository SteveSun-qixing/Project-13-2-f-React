## 八、事件总线

> 本节只定义内核总线的数据结构与派发规则；事件作用域模型、跨进程桥接与标准事件清单见 [09-事件系统设计.md](09-事件系统设计.md) 与 [05-事件契约规范.md](../../05-接口与契约/05-事件契约规范.md)。

### 8.1 事件模型与监听表

内核总线是唯一事件源与投递中枢；事件名、信封、广播语义与投递保证在 [09-事件系统设计.md](09-事件系统设计.md) 定义，本节给出内核侧的数据结构与派发原语。

- 事件名规范：两段式 `<domain>:<action>`，`<domain>` 与 `<action>` 均为小写字母开头、后接小写字母/数字/连字符；只允许一个冒号，禁止点号。校验正则：`^[a-z][a-z0-9-]*:[a-z][a-z0-9-]*$`。插件自有域取插件 ID 末段；内核在发布入口校验，不符合即拒绝。
- 事件信封：内核在发布入口补全 `id`（ULID）、`source`（按调用上下文重写，插件不可伪冒）与 `timestamp`；监听器只接收 `payload`。
- 事件载荷：`serde_json::Value`，经 Neon 边界与 TypeScript 侧同构。
- 监听表以事件名分桶；桶以写时复制快照发布，一经发布不再修改。

```rust
/// 事件载荷。
pub type EventPayload = serde_json::Value;

/// 事件信封。
pub struct Event {
    /// 事件实例唯一 ID（ULID）。
    pub id: String,
    /// 事件名：`<domain>:<action>`。
    pub name: EventName,
    /// 发布者身份：平台组件 ID 或插件 ID。
    pub source: String,
    /// 发布时刻，Unix 毫秒（UTC）。
    pub timestamp: u64,
    /// 追踪 ID；无追踪上下文时为 `None`。
    pub trace_id: Option<String>,
    /// 载荷。
    pub payload: EventPayload,
}

/// 监听器；Rust 订阅者在发布线程内同步调用，返回值只表达成败。
pub struct ListenerEntry {
    /// 退订令牌；内核 `off(token)` 的匹配键，也是插件可见订阅句柄的底层标识。
    pub token: ListenerToken,
    /// 归属 Fork；撤销该 Fork 自动退订。
    pub owner: ForkId,
    /// 是否只触发一次。
    pub once: bool,
    /// 存活标记；供 once 与退订做幂等判定。
    pub alive: Arc<AtomicBool>,
    /// 处理函数；监听器只接收载荷。JS 插件监听器由 Neon 适配层包装为
    /// “入队后立即返回”的转发器（见 8.3）。
    pub handler: Arc<dyn Fn(&Context, &EventPayload) -> Result<(), KernelError> + Send + Sync>,
}

/// 事件总线：监听表为写时复制快照。
pub struct EventBus {
    listeners: RwLock<Arc<HashMap<EventName, Arc<Vec<ListenerEntry>>>>>,
}
```

### 8.2 订阅与退订

- `on(name, handler, options?)`：登记监听器并返回退订句柄；`options.once` 首次投递后自动退订，`options.prepend` 前插到同优先级监听器之前；副作用登记到当前作用域 Fork。
- 退订：内核原语为 `off(token)`（幂等）；插件可见面是 `IEventSubscription.dispose()`，语义等价于 `off(token)`，token 即订阅句柄（订阅接口形状见 [09-事件系统设计.md](09-事件系统设计.md) 2.5）。
- Fork 撤销自动批量退订；退订顺序与注册顺序相反。
- 快照语义：一次投递使用发布开始时的监听器快照；投递期间新增或退订的监听器不影响本次投递，下一次发布生效。
- `once` 监听器以原子标记保证在并发与重入场景下只触发一次。
- 插件卸载过程中不再接收任何事件，包括其自身发布的事件。

### 8.3 派发原语

事件总线只有**同步广播**一种分发模式：内核不提供并行、串行、短路、环绕等模式，也不存在决策型事件（需要返回值、决策或拦截时使用 Cordis 服务或 Bridge 能力）。Rust 订阅者在发布线程内同步调用；JS 插件监听器经 Channel 异步投递——`emit` 的语义是**入队成功**，不等待 JS 执行。语义与 [09-事件系统设计.md](09-事件系统设计.md) 2.4 一致。

```rust
thread_local! {
    static EVENT_DEPTH: Cell<usize> = Cell::new(0);
}

/// 事件派发深度上限，防止监听器递归发布导致栈溢出。
const MAX_EVENT_DEPTH: usize = 64;

impl EventBus {
    /// 同步广播；无监听器时直接返回，不分配。
    ///
    /// Rust 订阅者在发布线程内同步调用；JS 插件监听器已由 Neon 适配层包装为
    /// Channel 入队转发器，返回 `Ok(())` 表示入队成功。
    /// 单个监听器错误不中断派发；首个错误在派发完成后返回给发布者。
    pub fn emit(&self, event: &Event, cx: &Context) -> Result<(), KernelError> {
        let listeners = {
            let table = self
                .listeners
                .read()
                .map_err(|_| KernelError::LockPoisoned)?;
            match table.get(&event.name) {
                Some(bucket) => Arc::clone(bucket),
                None => return Ok(()),
            }
        };

        let depth = EVENT_DEPTH.with(|cell| {
            let next = cell.get() + 1;
            cell.set(next);
            next
        });
        if depth > MAX_EVENT_DEPTH {
            EVENT_DEPTH.with(|cell| cell.set(depth - 1));
            return Err(KernelError::EventDepthExceeded {
                event: event.name.clone(),
            });
        }

        let mut first_error: Option<KernelError> = None;
        for listener in listeners.iter() {
            if let Err(error) = (listener.handler)(cx, &event.payload) {
                first_error.get_or_insert(error);
            }
        }

        EVENT_DEPTH.with(|cell| cell.set(depth - 1));
        first_error.map_or(Ok(()), Err)
    }
}
```

派发规则：

1. 同步广播：发布线程按注册顺序（FIFO）依次调用监听器；`prepend` 监听器排在常规位置之前。
2. 跨语言投递：JS 插件监听器不阻塞发布线程。Neon 适配层把 JS 回调包装为向 Channel 入队的转发器：`emit` 返回表示"全部监听器已调用 / 已入队"，不等待 JS 执行；入队失败（通道关闭、会话销毁）写审计。
3. 顺序保证：同一发布者、同一事件按 FIFO 调用与入队；不同发布者之间不保证顺序。
4. 快照隔离：派发基于发布时刻的监听器快照；派发期间不持有写锁。
5. 可重入：允许监听器内再次发布事件，嵌套派发深度优先；深度超过 64 返回 `KERNEL_EVENT_DEPTH_EXCEEDED`。
6. 错误隔离：单个监听器出错不影响其余监听器；首个错误返回发布者，事件系统不重试。JS 侧异常在 Node.js 线程捕获并写审计，不进入 `emit` 返回路径。
7. 至多一次投递：进程内、尽力而为；不持久化、不重放。
8. 监听器不得执行阻塞调用；耗时工作必须经 `ctx.task` 转交后台任务。

### 8.4 与 Bridge 事件的关系

事件总线只有一条：内核总线是唯一事件源与投递中枢。Cordis 事件是内核进程内的事件面；Bridge 事件是内核总线向渲染进程的跨进程投影，只承载公开事件的单向副本，白名单、按需转发与窗口会话清理见 [09-事件系统设计.md](09-事件系统设计.md) 第七节。内核不感知 IPC，不实现第二套订阅注册表。
