## 二、配置模型

### 2.1 配置键与命名空间

一条配置由**命名空间**与**键**组成，完整键为 `<namespace>.<key>`：

- 命名空间只有两类来源：
  - `platform`：平台注册的公共命名空间（当前唯一），由平台维护。
  - `plugins.<pluginId>`：插件命名空间，`pluginId` 为反向域名，每个插件一个。
- 键为命名空间内的相对路径：段字符集为小写字母、数字、连字符，用点分隔，不允许空段。
- 能力调用显式携带 `namespace` 与 `key`（见 11.3）；配置系统内部与事件使用完整键。
- 未在 schema 中注册的键不可读写（见第四节）。

键示例：

```
platform.window.defaultWidth
platform.log.level
plugins.chips.official.editor.fontSize
```

### 2.2 配置层级

配置分为四个层级：

| 层级 | 标识 | 语义 | 物理载体 |
|---|---|---|---|
| 平台层 | `platform` | 安装与管理链路写入的基线配置与策略 | `<platform-config-dir>/config.platform.json` |
| 用户层 | `user` | 用户级偏好；插件在用户级的自身配置 | `<user-config-dir>/config.user.json`、`<user-config-dir>/plugins/<pluginId>.json` |
| 工作区层 | `workspace` | 当前工作区的覆盖；插件在工作区级的自身配置 | `<workspace>/.chips/config.workspace.json`、`<workspace>/.chips/plugins/<pluginId>.json` |
| 插件层 | `plugin` | 插件包声明的默认值，插件键的最低优先层 | 插件包内 `assets/schemas/config.schema.json` 的默认值 |

### 2.3 覆盖规则

生效值按层由高到低解析，命中即返回：

| 键空间 | 覆盖顺序（高 → 低） |
|---|---|
| `platform.*` | 工作区层 → 用户层 → 平台层文件 → 平台 schema 默认值 |
| `plugins.<pluginId>.*` | 工作区层插件文件 → 用户层插件文件 → 插件层默认值 |

约束：

- 插件层默认值只作用于该插件命名空间，不参与 `platform` 命名空间解析；平台层不参与 `plugins.*` 解析。
- 插件对自身命名空间的读写免权限；读写 `platform` 命名空间需要带命名空间限定值的 `config:read` / `config:write`（见 [权限系统设计](./08-权限系统设计.md)）。
- 其他插件的命名空间对任何插件不可见、不可写（对应限定值不可申请），越权返回 `CONFIG_NAMESPACE_DENIED`。
- 策略键（schema 标记 `x-chips-policy: true`）只在平台层文件有效，其他层写入一律拒绝，返回 `CONFIG_POLICY_LOCKED`。
- 同层写入与现值相同的值视为空操作：该键不产生磁盘变更与事件。
- 工作区切换时，工作区层（含工作区插件文件）整体重新加载并重新解析生效值。

### 2.4 生效值解析示例

平台层文件 `config.platform.json`：

```json
{
  "schemaVersion": 1,
  "values": {
    "platform.update.channel": "stable",
    "platform.window.defaultWidth": 1200
  }
}
```

用户层文件 `config.user.json`：

```json
{
  "schemaVersion": 1,
  "values": {
    "platform.window.defaultWidth": 1400
  }
}
```

工作区层文件 `config.workspace.json`：

```json
{
  "schemaVersion": 1,
  "values": {
    "platform.window.defaultWidth": 1600
  }
}
```

解析结果：

| 配置键 | 生效值 | 生效层 | 是否默认 |
|---|---|---|---|
| `platform.window.defaultWidth` | `1600` | `workspace` | 否 |
| `platform.update.channel` | `"stable"` | `platform` | 否 |
| `platform.log.level` | `"info"` | `platform` | 是 |

`platform.log.level` 未出现在任何文件中，生效值来自平台 schema 默认值，`isDefault` 为 `true`。

移除工作区层覆盖后，`platform.window.defaultWidth` 回落到 `1400`（用户层）；再移除用户层覆盖后回落到 `1200`（平台层文件）。

### 2.5 `PluginConfig`（插件配置视图）

`PluginConfig` 是插件命名空间生效值的只读快照，是插件运行期看到的配置视图，也是内核 `apply(ctx, config)` 的 `config` 参数形态：

```typescript
interface PluginConfig {
  /** 完整键 → 生效值；键含命名空间前缀（`plugins.<pluginId>.<key>`）。 */
  readonly values: Readonly<Record<string, unknown>>;
  /** 读取单个键的生效值；未定义且无默认值时返回 undefined。 */
  get<T = unknown>(key: string): T | undefined;
}
```

规则：

- **内容**：该插件命名空间（`plugins.<pluginId>.*`）下按 2.3 覆盖解析后的生效值，包含插件 schema 声明的默认值；不包含其它命名空间与其它插件的键。
- **加载时机**：插件进入 `starting` 时，内核向 `ConfigStore` 取一次快照并传入 `PluginRunner.apply(ctx, config)`；apply 期间视图不可变，保证同一插件实例看到一致的配置。
- **变更传播**：落盘成功后配置系统发布 `config:changed`（第六节）；插件订阅事件更新自身缓存，或按需经 `config:get` / `config:snapshot` 读取最新值；`PluginConfig` 快照不随事件自动改写。
- **不是第二个事实源**：`PluginConfig` 只是 `ConfigStore` 的只读投影，不含写入能力；写入只能经 Bridge 能力（插件）或 Cordis 服务（主进程平台代码）完成。
- Rust 侧对应形态为 `ConfigStore` 产出的命名空间视图；内核生命周期约束见 [01-薯片内核设计](01-薯片内核设计.md) 6.1。
