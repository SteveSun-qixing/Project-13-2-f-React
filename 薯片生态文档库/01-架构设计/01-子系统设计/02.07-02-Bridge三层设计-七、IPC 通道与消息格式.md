## 七、IPC 通道与消息格式

### 7.1 通道总表

| 通道                  | 方向      | 模式                                    | 负载                                                   | 用途                                          |
| --------------------- | --------- | --------------------------------------- | ------------------------------------------------------ | --------------------------------------------- |
| `bridge:request`      | 渲染 → 主 | `ipcRenderer.invoke` / `ipcMain.handle` | `IBridgeRequest` → `IBridgeResponse`                   | 能力调用（含 `event:publish`）                |
| `bridge:resource`     | 渲染 → 主 | `ipcRenderer.invoke` / `ipcMain.handle` | `IResourceControlRequest` → `IResourceControlResponse` | 资源句柄打开与释放                            |
| `event:control`       | 渲染 → 主 | `ipcRenderer.invoke` / `ipcMain.handle` | `IEventControlRequest` → `IEventControlResponse`       | 订阅计数变更与错误回执                        |
| `event:<eventId>`     | 主 → 渲染 | `webContents.send` / `ipcRenderer.on`   | `IEventEnvelope`                                       | 公开事件下行                                  |
| `session:permissions` | 主 → 渲染 | `webContents.send` / `ipcRenderer.on`   | `ISessionPermissionsUpdate`                            | 会话权限快照同步下行；供 preload 快速失败预检 |

通道名固定，不得由插件自定义或拼接；`event:<eventId>` 中的 `eventId` 必须匹配事件契约中的登记 ID。资源字节不经 IPC：由 `chips-resource://` 协议处理器按 Range 提供（[04-资源管理设计](./04-资源管理设计.md)第 4.4 节）。

上表为**插件可见通道**全集。另有两条**宿主内部通道**（宿主自有壳进程↔主进程 IPC，非插件能力、不经 `window.chips` 链路、对插件不可见）不属上表口径，登记指向如下；本节只登记指向，消息形状、封套与错误面的定义权威各归[05-渲染引擎设计](./05-渲染引擎设计.md) §2.3（分件 05.02）对应段落，不在此重复定义：

| 通道                       | 承载世界                                                                           | 鉴权口径                                                          | 权威记载                                                                                    |
| -------------------------- | ---------------------------------------------------------------------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `document-view:request`    | 宿主窗口 preload 第二个独立 contextBridge 世界（`__chipsHostViewChannel`）↔ 主进程 | 两端均平台自身代码（工单035 裁定一），不走插件权限判定            | 《05-渲染引擎设计》§2.3「视图构建执行位与取视图通道承载」与「通道在壳进程侧的物理载体」两段 |
| `card-window-init:request` | 卡片窗口壳第三个独立 contextBridge 世界（`__chipsCardWindowInit`）↔ 主进程         | 同上；窗口身份只由主进程 `event.sender.id` 取证，渲染侧自报即闸拒 | 《05-渲染引擎设计》§2.3「卡片窗口装载输入投递」段                                           |

### 7.2 消息类型定义

```typescript
interface IBridgeRequest {
  requestId: string;
  capabilityId: string;
  input?: unknown;
}

type IBridgeResponse =
  | { requestId: string; ok: true; result: unknown }
  | { requestId: string; ok: false; error: ChipsError };

type ResourceControlOperation = 'open' | 'release';

interface IResourceControlRequest {
  requestId: string;
  operation: ResourceControlOperation;
  uri: string;
}

type IResourceControlResponse =
  | { requestId: string; ok: true; metadata: IResourceMetadata | null }
  | { requestId: string; ok: false; error: ChipsError };

interface IEventControlRequest {
  controlId: string;
  action: 'subscribe' | 'unsubscribe';
  eventId: string;
}

type IEventControlResponse =
  { controlId: string; ok: true } | { controlId: string; ok: false; error: ChipsError };

interface IEventEnvelope {
  eventId: string;
  payload: unknown;
  emittedAt: number;
}

interface ISessionPermissionsUpdate {
  sessionId: string;
  grantedPermissions: string[];
  permissionVersion: number;
}
```

| 字段                 | 说明                                                                              |
| -------------------- | --------------------------------------------------------------------------------- |
| `requestId`          | preload 生成（`crypto.randomUUID()`）；同一会话内唯一；用于关联响应与丢弃迟到结果 |
| `controlId`          | preload 生成；同一会话内唯一；订阅控制请求的关联键                                |
| `emittedAt`          | 事件产生时间，Unix epoch 毫秒                                                     |
| `ok`                 | 判别字段；不允许同时出现 `result` / `metadata` 与 `error`                         |
| `metadata`           | `open` 成功时返回资源元数据；`release` 成功时为 `null`                            |
| `grantedPermissions` | 会话权限快照的当前授权集合，主进程在授权变更后推送                                |
| `permissionVersion`  | 授权版本号，单调递增；preload 据此丢弃迟到推送                                    |

### 7.3 序列化约束

- 跨 IPC 的值必须是结构化克隆兼容类型：JSON 值、`Uint8Array`、`ArrayBuffer`。
- 能力调用在 Host 侧以 `{ json, bin }` 信封表达（3.6）：`bin` 段只承载 `x-chips-binary` 字段的字节；跨 IPC 时二进制随结构化克隆一次到达，不做 base64 编解码。
- 禁止传输：函数、类实例、`Symbol`、DOM 对象、`Error` 实例（错误统一用 `ChipsError` 同构普通对象）。
- 字段名一律 camelCase；时间戳一律 Unix epoch 毫秒；`undefined` 字段按结构化克隆语义保留，接收方必须以可选字段处理。
- 单条消息应保持较小体积；大资源必须经 `chips-resource://` 协议路径，大小限制与分块策略见[04-资源管理设计](./04-资源管理设计.md)与[06-资源协议规范](../../05-接口与契约/06-资源协议规范.md)。
- preload 只转发 `IChipsBridge` 方法可产生的消息，禁止透传任意通道与任意负载。

### 7.4 会话解析与绑定

会话由插件运行时在创建窗口/表面时向 Bridge 层登记，绑定关系保存在主进程：

| 字段                 | 类型                   | 说明                                                                                             |
| -------------------- | ---------------------- | ------------------------------------------------------------------------------------------------ |
| `sessionId`          | `string`               | 会话唯一标识                                                                                     |
| `pluginId`           | `string`               | 反向域名插件 ID                                                                                  |
| `windowId`           | `number`               | Electron `webContents.id`                                                                        |
| `frameId`            | `number`               | 主框架 routing id，用于区分同一窗口内的子框架                                                    |
| `grantedPermissions` | `ReadonlySet<string>`  | 权限快照，授权变更时由权限系统更新，并经 `session:permissions` 推送同步到 preload 供快速失败预检 |
| `openedDocuments`    | `ReadonlySet<string>`  | 会话已打开的卡片/箱子文档，用于资源作用域判定                                                    |
| `state`              | `'active' \| 'closed'` | 会话状态                                                                                         |

规则：

- 每次调用按来源（`webContents` + frame）解析会话；解析失败即拒绝，不接受负载自报的 `pluginId`。
- 会话关闭后拒绝全部新调用（`BRIDGE_SESSION_UNKNOWN`），在途调用取消并丢弃结果。
- 会话清理时机：窗口销毁、插件停用、应用退出；清理时同时释放资源句柄与事件订阅。
- 权限快照同步通道 `session:permissions` 是单向推送：主进程在授权变更后按 `permissionVersion` 递增推送；preload 只用于快速失败预检，权威判定仍在主进程（5.3）。

### 7.5 事件通道

- 投递使用 `event:<eventId>` 单通道单事件，避免通用信道带来的过滤泄漏。
- 事件模型与内核一致：总线只有广播一种分发模式，Rust 订阅者在发布线程内同步调用，JS / 渲染侧监听器异步投递（`emit` 语义 = 入队成功，不等待 JS 执行）；同一发布者、同一事件按 FIFO 投递（[01-薯片内核设计](./01-薯片内核设计.md) 第八节）。
- 主进程转发器只向已登记该事件的窗口推送；白名单、按需转发、可见性过滤与投递语义见[09-事件系统设计](./09-事件系统设计.md)，事件负载契约见[05-事件契约规范](../../05-接口与契约/05-事件契约规范.md)。
- `event:control` 的回执错误码（`EVENT_NOT_REGISTERED`、`EVENT_SUBSCRIBE_DENIED`）由事件系统定义；收不到确认的订阅一律不建立。
- 资源句柄失效通知以事件 `resource:invalidated` 经 `event:resource:invalidated` 投递，payload 为 `{ uri, reason }`；事件契约登记见[05-事件契约规范](../../05-接口与契约/05-事件契约规范.md)。
- 事件负载必须在推送前完成序列化约束检查；禁止携带其他会话的私有数据。
