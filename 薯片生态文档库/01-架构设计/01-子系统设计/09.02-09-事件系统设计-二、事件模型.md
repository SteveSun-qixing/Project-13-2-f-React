## 二、事件模型

### 2.1 发布/订阅

发布者向总线发布事件，总线将事件投递给所有匹配的监听器。模型规则：

- **发布者与订阅者互不感知**：发布者只描述事实，不指定接收者，也不等待处理结果。
- **一对多、多对多**：同一事件可以被任意数量的订阅者接收；同一订阅者可以订阅任意数量的事件。
- **订阅必须显式**：没有订阅者的事件被安全丢弃，不报错、不缓存、不重放。
- **精确匹配**：总线只按事件 ID 精确匹配，**不支持通配符、正则或前缀订阅**。需要按域观察时，逐个订阅该域内的具体事件（标准事件数量可控）。
- **广播语义**：总线只有广播一种分发模式，不定义决策型事件。Rust 订阅者在发布线程内同步调用；JS 插件监听器（主进程插件）经 Neon Channel 异步投递，`emit` 的语义是**入队成功**（不等待 JS 执行）；同一发布者、同一事件按 FIFO 调用与入队（与 [01-薯片内核设计](./01-薯片内核设计.md) 第八节一致）。跨进程投递为异步转发（见第七节）。

### 2.2 事件命名

事件 ID 由领域与动作两段构成：`<domain>:<action>`，整名文法 `^[a-z][a-z0-9-]*:[a-z][a-z0-9-]*$`。

| 段 | 规则 | 示例 |
|---|---|---|
| `<domain>` | 小写字母、数字、连字符（`^[a-z][a-z0-9-]*$`）；表示事件所属领域或插件命名空间 | `file`、`document`、`editor` |
| `<action>` | 小写字母、数字、连字符（`^[a-z][a-z0-9-]*$`）；通知型事件使用过去式动词短语 | `changed`、`loaded`、`failed` |

规则：

1. **分隔符唯一**：只使用一个冒号分隔两段；禁止点号、通配符、斜杠、空格、大写字母。
2. **平台保留域**：`internal`、`plugin`、`document`、`file`、`config`、`security`、`window`、`app`、`sync`、`resource`、`permission`、`tray`、`shortcut`、`transfer`、`command`。保留域事件只能由平台发布，标准事件清单见第八节。
3. **插件自有域**：插件自定义事件的 `<domain>` 取插件 ID 末段（如 `chips.official.editor` 使用 `editor`），注册时由内核登记去重；插件事件不得占用平台保留域。
4. **卡片与箱子统一域**：不设 `card:*`、`box:*` 事件域；卡片与箱子的差异通过 `document:*` 事件的 `kind` 字段表达（统一链路原则）。
5. **内核内部域**：`internal:*` 仅供内核自身使用，不属于公开契约，永不跨进程转发。
6. **渲染帧内部消息不占事件命名空间**：`frame:*`、`host:*` 是渲染引擎与 iframe 之间的 postMessage 消息类型（见《[05-渲染引擎设计](./05-渲染引擎设计.md)》），不是总线事件，不得作为事件订阅。

每个事件 ID 只能有一个 payload 形态；同名事件不得在不同场景复用不同结构。标准事件在[05-事件契约规范](../../05-接口与契约/05-事件契约规范.md)中登记后即为稳定契约，修改走变更流程（见《[变更与决策管理](../../07-工程管理/03-变更与决策管理.md)》）。

### 2.3 事件结构

内核中的事件由事件 ID 与 payload 两部分构成（内核结构见《[01-薯片内核设计](./01-薯片内核设计.md)》）：

```typescript
interface IEvent<TPayload = unknown> {
  id: string;          // 事件 ID，<domain>:<action>
  payload: TPayload;   // 事件负载，类型由事件契约定义
}
```

| 组成 | 说明 |
|---|---|
| `id` | 必须符合 2.2 的命名规则；内核在发布入口校验 |
| `payload` | 必须可结构化克隆（跨进程时）；不得携带凭证材料与未脱敏用户数据 |

**监听器只接收 `payload`**。发布者身份、发布时刻、追踪 ID 由内核在发布入口按调用上下文记录到事件日志与审计输出（见 9.4），不进入 payload，也不作为监听器参数；事件契约需要在负载中表达来源差异时，在 payload 中定义显式字段。

### 2.4 派发方式

标准事件统一采用**广播**：总线不提供并发、串行、环绕等其它派发模式，也不存在决策型事件；**决策与拦截使用 Cordis 服务调用或 Bridge 能力**，不得用事件实现。

| 订阅者位置 | 投递方式 | `emit` 返回语义 |
|---|---|---|
| Rust 订阅者（内核组件、Rust 服务） | 发布线程内同步调用（按注册顺序 FIFO） | 全部 Rust 监听器已调用完毕 |
| JS 插件监听器（主进程插件） | Neon Channel 异步入队，在 Node.js 线程执行 | 入队成功，不等待 JS 执行 |
| 渲染订阅者 | 桥接转发器异步 IPC（见第七节） | 入队成功，不等待渲染进程处理 |

- **快照隔离**：基于发布时刻的监听器快照；无监听器时零分配直接返回。
- **顺序**：同一发布者、同一事件按 FIFO 调用与入队；不同发布者之间不保证顺序（6.2）。
- **可重入**：允许监听器内再次发布事件，嵌套派发深度优先；深度上限 64，超限返回 `KERNEL_EVENT_DEPTH_EXCEEDED`。
- 派发规则与内核数据结构见《[01-薯片内核设计](./01-薯片内核设计.md)》第八节；投递保证与错误处理见第六节。

### 2.5 订阅接口

Context 暴露的事件方法形状如下（内核侧 `on` / `once` / `off(token)` 与监听表结构见《[01-薯片内核设计](./01-薯片内核设计.md)》）：

```typescript
type EventListener<TPayload> = (payload: TPayload) => void;

interface IEventSubscription {
  dispose(): void;   // 幂等；等价于内核 off(token)
}

on<TPayload>(event: string, listener: EventListener<TPayload>): IEventSubscription;

once<TPayload>(event: string, listener: EventListener<TPayload>): IEventSubscription;

emit<TPayload>(event: string, payload: TPayload): void;
```

`on` 注册的监听器是发布方的可逆副作用，由当前 Fork 追踪；退订统一通过返回的 `IEventSubscription.dispose()` 完成，不需要单独持有 token。

**示例：主进程插件订阅标准事件并发布自有事件**

```typescript
import type { Context, IEventSubscription } from '@chips/sdk';

interface IDocumentChangedPayload {
  uri: string;
  kind: 'card' | 'box';
}

interface IEditorDirtyPayload {
  uri: string;
}

/**
 * 插件入口：卡片文档变更时标记编辑状态。
 */
export function apply(ctx: Context): void {
  const subscription: IEventSubscription = ctx.on<IDocumentChangedPayload>(
    'document:changed',
    (payload) => {
      if (payload.kind !== 'card') {
        return;
      }
      ctx.emit<IEditorDirtyPayload>('editor:dirty', { uri: payload.uri });
    },
  );

  // 监听器随当前 Fork 自动退订；显式提前退订时调用 subscription.dispose()
  void subscription;
}
```
