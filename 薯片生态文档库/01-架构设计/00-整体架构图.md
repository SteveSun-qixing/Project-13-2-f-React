## 一、定位与阅读方式

### 1.1 本文是什么

- 文档库中**唯一**的全生态拓扑总览：用分层图、进程图与对照表回答"生态由哪些层、哪些子系统、哪些外部系统组成，彼此如何连接"。
- 全库阅读路径的起点：新读者从本文获得全景，再按第五节对照表进入各子系统权威文档。
- 架构讨论的共同坐标系：评审、拆任务、登记缺口时，用本文的层名与数据流名称对齐语境。

### 1.2 本文不定义什么

- 不定义接口、类型、字段、事件名、能力 ID、权限 ID、错误码与任何数值基线；这些只在各自权威文档中定义，对照表逐项给出落位。
- 不重复子系统内部设计（模块划分、状态机、算法与时序细节）；本文只给每个子系统一句定位与边界，细节经链接跳转。
- 命名、类型与冲突裁决以《本轮架构收口裁决》为最高依据，其次以文档库正式文档为准；本文与两者冲突时以两者为准。

## 二、全生态拓扑总览

### 2.1 六层总览

```text
                     用户 · 开发者 · 第三方插件作者
┌──────────────────────────────────────────────────────────────────────┐
│ 内容层   .card / .box —— 唯一事实源，脱离程序独立存在                   │
│          工作副本：目录态           交付/归档：ZIP Store 归档态          │
├──────────────────────────────────────────────────────────────────────┤
│ 插件层   官方与第三方插件同构，一个插件只有一个角色                      │
│          app（应用）· basecard（基础卡片）· boxlayout（箱子布局）         │
│          · service（服务）；分发单元 .cpk，唯一权威清单 manifest.yaml    │
├──────────────────────────────────────────────────────────────────────┤
│ 契约层   window.chips / IChipsBridge：request · subscribe · resource    │
│          能力契约 · 事件契约 · 资源协议 · 角色接口 · ChipsError           │
├──────────────────────────────────────────────────────────────────────┤
│ 平台层   Cordis 内核 · Bridge · 文档解析器 · 资源管理（统一文件系统）      │
│          渲染引擎 · 文档服务 · 编辑链路 · 工作区                          │
│          权限 · 事件 · 配置（同步引擎：可选、按需加载的平台服务插件）       │
├──────────────────────────────────────────────────────────────────────┤
│ 壳层     Electron 壳（桌面，当前：主进程 / 渲染进程 / preload）            │
│          工具进程（Electron Utility Process，壳提供、内核调度）            │
│          移动端 Phase 5（架构预留；技术栈预选 React Native）               │
├──────────────────────────────────────────────────────────────────────┤
│ 系统层   操作系统：文件 · 窗口 · 通知 · 剪贴板 · 快捷键 · 网络 · 电源 …     │
└──────────────────────────────────────────────────────────────────────┘

开发平面（纵向，服务开发期，不进入发布产物，见 §2.3）：
  @chips/sdk · @chips/cli（chips / chips dev）· @chips/ui + @chips/antd（fork）
  · 脚手架与示例 · 《薯片生态文档库》· CI/CD 与质量门禁

服务端与工具链（平台进程之外，经 HTTP 与传输协议接入，见 §2.4）：
  社区平台服务器 · 个人服务器 · 对象存储 · 只读 Web 前端 · 服务端部署与运维
```

分层规则（方向不可逆）：

1. 上层只能向下调用；下层不得调用上层；平台 → 插件只能经事件推送（[02-Bridge三层设计](./01-子系统设计/02-Bridge三层设计.md) §2.2）。
2. 层间只经相邻层契约通信，禁止跨层直连（[架构原则](../00-愿景与原则/01-架构原则.md) §2.3）。
3. 内容层不依赖任何程序：文件即数据层，程序只是读写工具（[白皮书](../00-愿景与原则/00-薯片生态白皮书.md) §4.6）。

### 2.2 运行时进程拓扑

```text
Electron 壳
├─ 主进程
│    Cordis 运行时（Rust，经 Neon 暴露）· Bridge 核心（注册表 / 权限判定 /
│    JSON Schema 校验 / 路由 / 超时 / 错误归一）· 平台服务域与 Host 能力实现
│    · 文档解析器 · 资源管理器 · 文档服务 · 插件加载（ModuleLoader 受管加载）
│    · 窗口 / 菜单 / 对话框 / 通知等壳能力适配
├─ 渲染进程（每个应用窗口一个）
│    React 应用（只从 @chips/ui 取材）· RenderHost（会话 / 帧树 / 测量 / 调度）
│    · 编辑链路（IEditSession / IPluginRuntime，就近渲染容器）
│    · 渲染帧（sandbox iframe：顶层卡片帧 / 顶层布局帧 / 条目帧）
├─ 工具进程（Electron Utility Process）
│    需要进程级隔离的服务插件执行与重计算任务；崩溃不影响主进程与其它插件
└─ preload（每个窗口）
     只暴露 window.chips 三个方法与订阅登记；不暴露 ipcRenderer / process 等原始对象
```

- 解析与资源 IO 全部在主进程；渲染、测量与帧管理全部在渲染进程；二者只经 Bridge 通信（[05-渲染引擎设计](./01-子系统设计/05-渲染引擎设计.md) §3）。
- 主进程插件在主进程内经受管模块加载器（ModuleLoader）运行；`service` 的进程级隔离由工具进程承担；`app` 的 UI 在独立窗口渲染进程；`basecard` / `boxlayout` 的渲染在 iframe 沙箱中执行（[03-插件架构设计](./01-子系统设计/03-插件架构设计.md) §5）。
- 安全基线（`nodeIntegration: false`、`contextIsolation: true`、`sandbox: true`、生产环境禁止关闭 `webSecurity` 等）以[架构原则](../00-愿景与原则/01-架构原则.md) R17 为唯一出处，本文不重复。

## 三、连接与边界说明

### 3.1 层间边界

| 边界 | 允许的连接 | 禁止的连接 |
|---|---|---|
| 内容层 ↔ 插件层 | 插件经文档服务受控读写文档内容，经资源管理与 `chips-resource://` 访问资源；解析只由平台解析器执行 | 插件接触文件字节、真实路径；插件自行解析或直写文档；出现第二写口 |
| 插件层 ↔ 契约层 | 渲染侧经 `window.chips` 的 `request` / `subscribe` / `resource`；主进程插件经 Cordis `ctx`（含 `ctx.bridge` 收窄面）与角色接口 | 绕桥访问 Node / Electron / 系统 API；跨插件 `import`；自建 IPC 通道 |
| 契约层 ↔ 平台层 | Bridge 完成会话解析、注册表命中、权限判定、schema 校验与超时策略后经内核路由交给 Host 实现；平台自身调用同链路 | 跳过注册表或权限判定；Host 反向调用插件（只可经事件通道） |
| 平台层 ↔ 壳层 | 壳实现窗口、菜单、托盘、快捷键、对话框、剪贴板与工具进程，经能力与 Bridge 暴露 | 插件感知壳差异；平台向插件泄漏壳细节或原始对象 |
| 壳层 ↔ 系统层 | 壳封装系统 API，归一为能力后经 Bridge 提供 | 平台业务层与插件直接触碰操作系统 API |
| 平台 ↔ 服务端 | `http:request`、凭证能力与传输链路；服务端经 HTTP 与预签名对象存储协作 | 服务端进入平台进程；服务端注册能力或接收平台事件；破坏客户端离线可用能力 |
| 开发平面 ↔ 运行时 | 只经正式接口、`.cpk` 与 `chips` 命令行；工具不得被 `packages/` 运行时依赖 | 工具、示例、测试夹具进入发布产物；插件打包第二套组件库 |

### 3.2 三个通信面与东西向

| 平面 | 方向 | 载体 | 契约 |
|---|---|---|---|
| 能力面 | 插件 → 平台（南向） | `request(capabilityId, input)` | [能力契约规范](../05-接口与契约/04-能力契约规范.md)、[Bridge API 规范](../05-接口与契约/01-Bridge-API规范.md) |
| 事件面 | 平台 → 插件（北向） | `subscribe(eventId, handler)`；主进程 `ctx.on` | [事件契约规范](../05-接口与契约/05-事件契约规范.md) |
| 资源面 | 双向 | `resource(uri)` → `IResourceHandle`；`chips-resource://` | [资源协议规范](../05-接口与契约/06-资源协议规范.md) |

- 南向与北向都是单向的：能力调用不反向调用插件；事件发布不等待插件执行结果（[02-Bridge三层设计](./01-子系统设计/02-Bridge三层设计.md) §2.2）。
- 插件发布事件不是独立通道：经能力 `event:publish` 走 `request` 链路，受权限判定与 schema 校验（[09-事件系统设计](./01-子系统设计/09-事件系统设计.md) §2.1）。
- 东西向（插件 ↔ 插件）只有三条合法路径：服务注入（`ctx.provide` / `ctx.inject`）、能力调用、事件订阅；绝不直接 `import`（[架构原则](../00-愿景与原则/01-架构原则.md) §2.1）。

### 3.3 外部出入口

| 出入口 | 路径 | 权威文档 |
|---|---|---|
| 文件关联 / URL Scheme 打开 | 操作系统 → 壳 → 资源打开与默认处理器路由 → 处理器插件（`app`）→ 渲染或编辑会话 | [资源打开与默认处理器契约](../05-接口与契约/14-资源打开与默认处理器契约.md) |
| 工作区打开与目录扫描 | 工作区绑定 → 资源作用域与文件监听 → 文件树与变更事件 | [13-工作区设计](./01-子系统设计/13-工作区设计.md) |
| 导入 / 导出 / 另存与两态转换 | 目录态 ↔ ZIP Store 归档态，经 `document:export` 与受控提交流程 | [13-工作区设计](./01-子系统设计/13-工作区设计.md)、[版本与迁移规范](../04-文件格式规范/04-版本与迁移规范.md) |

| 命令行 | `chips`（用户侧）与 `chips dev`（开发侧）；插件经 `cli.commands` 扩展 | [CLI 完整参考](../06-开发与运维/07-CLI完整参考.md) |

### 3.4 边界红线

以下任一条命中即为缺陷（依据见[架构原则](../00-愿景与原则/01-架构原则.md) §2 各条红线、R2、R8、R17）：

1. 插件访问系统能力绕开 Bridge（出现 `node:*`、`electron`、系统 API 或真实文件路径）。
2. 跨插件直接 `import` 或直接持有其它插件内部对象。
3. 解析、渲染、编辑器或应用插件自行读写文档字节（第二写口）。
4. 除文档解析器外存在第二处 `.card` / `.box` 解析实现（第二解析器）。
5. 除渲染引擎外存在第二套渲染帧 / 挂载 / 更新实现（第二渲染管线）。
6. 硬编码视觉值或引入第二组件库；业务代码越过 `@chips/ui` 导入。
7. 使用未登记的能力 ID、权限 ID、事件名或错误码。
8. 同一概念在第二处被定义或数值被转述（单一事实源破坏）；平台实现业务逻辑。
9. 服务端解析 `.card` / `.box` 或承载平台第二套解析、渲染管线。

## 四、关键数据流

### 4.1 打开与渲染（查看态）

```text
操作系统 / 应用内打开请求
  → 资源打开与默认处理器路由（14-资源打开与默认处理器契约）
  → 处理器插件（app）：launch / openFile
  → 渲染会话 open(request)：请求 → 解析 → 资源准备 → 插件渲染 → 组装 → 交付
      · 解析（主进程 Rust）：DocumentHandle → DocumentView（文档视图构建器）
      · 资源准备：注册资源作用域，生成引用映射（不预读字节）
      · 插件渲染：按 card_type / active_layout_type 选择插件，创建 sandbox 帧
      · 组装与交付：帧树 + 位姿 + 高度 + 错误边界，挂载到目标容器
```

- 卡片与箱子共用同一条链路：唯一分支点是 `DocumentKind`，分支后立即归一为 `DocumentView`（[05-渲染引擎设计](./01-子系统设计/05-渲染引擎设计.md) §2）。
- 解析细节以[文档解析器设计](./01-子系统设计/06-文档解析器设计.md)为准；资源作用域以[资源管理设计](./01-子系统设计/04-资源管理设计.md)为准。

### 4.2 能力调用（南向）

```text
插件 UI                preload                主进程 Bridge 核心            Host 实现
chips.request(id, input)
  → 生成 requestId → bridge:request(IPC)
                       → 1 会话解析（来源帧 → 会话）
                       → 2 能力注册表命中
                       → 3 权限判定（capability.permissions ⊆ 会话快照）
                       → 4 JSON Schema 校验
                       → 5 并发与超时策略 → 内核路由 → capability.execute(input, ctx)
  ← ok=true: resolve(result)
  ← ok=false: reject(ChipsError)     ← IBridgeResponse ← 结果或错误
```

- 主进程插件走同一判定链路：经 `ctx.bridge.request`（同进程直调 Bridge 核心），校验与审计不减少。
- 完整签名与错误码以 [Bridge API 规范](../05-接口与契约/01-Bridge-API规范.md) 为准；能力清单以[能力契约规范](../05-接口与契约/04-能力契约规范.md)为准。

### 4.3 事件通知（北向）

```text
Host 侧事件总线（内核 EventBus，广播语义）
  ├─ Rust 订阅者：发布线程内同步调用（FIFO）
  ├─ JS 主进程监听器：Neon Channel 异步入队（emit = 入队成功）
  └─ 渲染订阅者：event:<eventId> 异步 IPC 转发（按窗口订阅计数投递）
插件发布事件：经能力 event:publish 走 request 链路（受权限与 schema 校验）
```

- 订阅必须显式、精确匹配、无重放；退订经 `ISubscription.dispose()` 或 Fork 追踪（[09-事件系统设计](./01-子系统设计/09-事件系统设计.md) §2）。
- 事件命名、信封与全部标准事件以[事件契约规范](../05-接口与契约/05-事件契约规范.md)为准；未登记事件不得转发。

### 4.4 资源访问（句柄与协议）

```text
路径一：句柄（生命周期控制与失效感知）
  chips.resource(uri) → 同步预检 → 懒打开代理句柄
  → 首次 metadata() 触发 bridge:resource open（再次解析、作用域与会话校验、权限判定）
  → 分配句柄 ID；字节由 chips-resource:// 协议处理器按 Range 提供（不经 IPC）
  → release() 归还租约；会话结束强制释放全部句柄

路径二：协议（交给渲染引擎加载）
  <img src="chips-resource://…"> → Chromium 网络层
  → 主进程协议处理器 → 会话解析 + 权限判定 + 路径安全
  → 资源管理器（缓存 / 流式）→ 响应数据流
```

- 红线：**一切来源皆挂载、一切访问皆句柄**；插件不接触真实路径，来源差异止于 Provider（[04-资源管理设计](./01-子系统设计/04-资源管理设计.md) §2）。
- 写入只经 `resource:write`（限插件作用域与临时作用域）或文档服务的受控提交；句柄本身不提供写入方法（[资源协议规范](../05-接口与契约/06-资源协议规范.md)）。

### 4.5 文档写入与保存（唯一写口）

```text
document:open（建立文档会话，documentId = card_id / box_id，跨会话稳定）
document:write（模型切片替换：metadata / structure / content / entries；revision 推进）
document:save（两阶段提交：临时物与备份 → 原子替换；归档态执行 ZIP Store 重建；
               写后格式校验；失败按提交日志回滚 / 前滚，不产生半提交状态）
事件：document:opened / document:changed / document:saved / document:closed
```

- 写路径唯一：目录态与归档态的全部写入都经文档服务受控提交，纳入资源管理 WriteCoordinator 同一路径锁；不产生第二个写者（[11-文档服务设计](./01-子系统设计/11-文档服务设计.md) §2）。
- 外部修改检测与查看会话冻结语义见[11-文档服务设计](./01-子系统设计/11-文档服务设计.md) §7；两态转换与 `document:export` 见[13-工作区设计](./01-子系统设计/13-工作区设计.md) §4。

### 4.6 编辑回流（唯一时序）

```text
插件编辑器                 编辑链路                          文档服务            渲染会话
   │ change / getChange()    │                                │                  │
   │────────────────────────▶│ [1] 校验：configSchema → validateConfig             │
   │                         │ [2] document:write ────────────▶│ 模型替换          │
   │                         │◀────────────────────────────────│ { revision }     │
   │                         │ [3] 组装新 DocumentView（revision）                 │
   │                         │ [4] update(view, revision) ────────────────────────▶│
   │                         │ [5] markCommitted(revision)      │                  │
   │◀────────────────────────│                                │                  │
   │                         │ [6] 自动保存防抖 → document:save │ 两阶段提交        │
   │                         │◀───────────────── { source, digest }│ 发布事件        │
```

- 顺序固定且不可交换：**校验 → `document:write` → 会话 `update` → `markCommitted`**；不得跳过 `write` 直接 `update`，也不得在 `update` 失败时调用 `markCommitted`（[12-编辑引擎设计](./01-子系统设计/12-编辑引擎设计.md) §6）。
- 预览更新预算、合并窗口、串行队列与自动保存防抖取值以[12-编辑引擎设计](./01-子系统设计/12-编辑引擎设计.md) §6 为准，本文不重复数值。
- 编辑态就近渲染复用同一套插件接口与同一份解析结果，不是第二渲染管线（[05-渲染引擎设计](./01-子系统设计/05-渲染引擎设计.md) §8）。

|---|---|---|

| 唯一管线 | 一个解析器、一个渲染引擎、一条编辑回流；唯一分支点为 `DocumentKind` | R8、[05-渲染引擎设计](./01-子系统设计/05-渲染引擎设计.md) §2.1 |
| 一切皆插件 | 平台只提供能力与机制；应用、编辑器、查看器、资源管理器均为插件 | R1、[白皮书](../00-愿景与原则/00-薯片生态白皮书.md) §4 |
| 一切来源皆挂载、一切访问皆句柄 | 插件不接触真实路径；来源差异止于 Provider | R17、[04-资源管理设计](./01-子系统设计/04-资源管理设计.md) §1.5 |
| 前端唯一导入面 | 业务代码只从 `@chips/ui` 导入；antd fork 仅 ui 包内部使用；文案简体中文直写 | R4、R5、[ADR-008](./ADR/ADR-008-React加fork-antd前端技术栈.md) |

| 服务端边界 | 服务端不入平台进程、不注册能力、不解析 `.card` / `.box` | [15-个人服务器设计](./01-子系统设计/15-个人服务器设计.md) §2.3 |
| 开发平面隔离 | 工具与示例不进入发布产物；`tools/` 不被 `packages/` 运行时依赖 | [代码组织规范](../02-开发规范/01-代码组织规范.md) §2.2 |

### 6.2 自检清单

- [ ] 新增文档、插件或平台能力时，能指出它落在本文哪一层、与哪些层有连接？
- [ ] 所有跨层调用是否都经相邻层契约，而没有出现跨层直连或反向调用？
- [ ] 插件间耦合是否只用了服务注入、能力调用、事件订阅三条合法路径？
- [ ] 是否复用了统一的解析、资源、渲染、文档写入与编辑回流链路，没有新建并行管线或第二写口？
- [ ] 插件是否只经 `window.chips` / `ctx` 访问平台，没有接触 Node、Electron、系统 API 与真实路径？
- [ ] 能力、权限、事件、错误码是否都在权威文档登记，没有自造标识符？
- [ ] 视觉与文案是否只用 `@chips/ui` 与 Design Tokens，没有硬编码样式或第二组件库？
- [ ] 文档中的接口、字段与数值是否只引用权威文档，没有在本文或第二处重复定义？
- [ ] 服务端改动是否保持在平台进程之外，没有引入第二解析器或第二渲染管线？
- [ ] 工具与示例是否保持在开发平面内，没有进入发布产物或运行时依赖？
