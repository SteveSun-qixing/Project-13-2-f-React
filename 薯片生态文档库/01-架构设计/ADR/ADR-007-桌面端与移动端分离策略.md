# ADR-007: 桌面端与移动端分离策略

## 元数据

- **状态**: 已接受
- **日期**: 2026-09-19
- **影响范围**: 跨端架构

---

## 决策

双平台分离、三层统一架构。

---

## 平台划分

### 桌面端平台

```
技术栈：Electron + Rust + React
平台：macOS / Windows（优先），Linux（后续）
开发阶段：Phase 1-4
优先级：最高
```

### 移动端平台

```
技术栈：待定（建议 React Native）
平台：Android（次之），iOS（随后）
开发阶段：Phase 5（架构预留，暂不排期）
优先级：低
```

---

## 三层统一

### 第一层：文件格式统一

```
# .card 文件格式（完全统一）
my-card.card (ZIP Store)
├── .card/
│   ├── metadata.yaml
│   ├── structure.yaml
│   ├── cover.html
│   └── cardcover/            # 封面资源，可选
├── content/
│   └── {10位62进制ID}.yaml
├── {资源文件}                # 卡片根目录相对路径
└── {嵌套卡片}.card           # 可选

# .box 文件格式（完全统一）
Collection.box (ZIP Store)
├── .box/
│   ├── metadata.yaml
│   ├── structure.yaml
│   ├── content.yaml
│   ├── cover.html
│   └── boxcover/             # 箱子封面资源，可选
└── assets/                   # 箱子自有资源，可选
    ├── placeholders/
    ├── previews/
    └── layouts/
```

**保证**：
- 桌面端创建的 .card 可在移动端打开
- 移动端创建的 .box 可在桌面端打开
- 文件结构、schema 完全一致

---

### 第二层：Rust 核心复用

```rust
// Rust 核心可编译到移动端
pub struct CardParser;
pub struct ResourceManager;
pub struct CryptoEngine;
pub struct SyncEngine;

// 桌面端：通过 Neon
// Android：通过 JNI
// iOS：通过 Swift FFI
```

**可复用逻辑**：
- 文档解析（YAML/JSON）
- 资源管理
- 加密解密
- 数据同步

**不可复用**：
- UI 渲染
- 系统集成
- 平台特定功能

---

### 第三层：Bridge 接口统一

```typescript
// 统一的 Bridge 接口（R2）
interface IChipsBridge {
  request<TOutput>(capabilityId: string, input?: unknown): Promise<TOutput>;
  subscribe(eventId: string, handler: (payload: unknown) => void): ISubscription;
  resource(uri: string): IResourceHandle;
}

interface ISubscription {
  dispose(): void;
}

// 平台特定能力
// 桌面端
'desktop:window:create'
'desktop:tray:create'

// 移动端
'mobile:vibrate'
'mobile:camera:capture'

// 共有能力（实现不同）
'file:read'           // 桌面：完整文件系统，移动：沙箱
'notification:show'   // 桌面：系统通知，移动：推送通知
```

## 开发优先级

### Phase 1-4: 桌面端

开发内容：
- macOS / Windows 完整实现（Linux 后续）
- 完整插件生态
- 所有核心功能

移动端准备：
- Rust 核心设计考虑移动端兼容
- 文件格式设计考虑移动端需求
- Bridge 接口设计考虑跨平台抽象

### Phase 5: 移动端（架构预留，暂不排期）

开发内容：
- 选择技术栈（React Native）
- 移植 Rust 核心
- 开发移动端 UI
- 适配移动端特性

复用内容：
- 文件格式直接复用
- Rust 核心复用
- 插件逻辑部分复用

---

## 移动端技术栈（预选）

### React Native

**桥接方式**：

```
React Native (JavaScript)
    ↕
JSI (JavaScript Interface)
    ↕
C++ Turbo Module
    ↕
Rust 核心 (FFI)
```

**复用能力**：
- React 组件逻辑部分复用
- TypeScript 代码共享
- 业务逻辑复用

---

## 实施要求

### 桌面端开发

- 核心设计考虑移动端兼容性
- 文件格式保持平台无关
- Bridge 接口保持抽象

### 移动端开发（Phase 5，架构预留）

- 完整实现 Bridge 接口
- 编译 Rust 核心到移动端
- 实现移动端特定能力

## 现状注记

> 本节记录本 ADR 之后由正式文档落实或修订的口径，不修改上文原文。

1. 平台优先级统一为 macOS / Windows → Linux（桌面三端完成）→ Android → iOS（R6、[开发流程与阶段计划](../../07-工程管理/02-开发流程与阶段计划.md)）；Phase 5 移动端为架构预留、暂不排期。
2. 跨端能力示例改用已登记 ID：原文 `notification:show` 已统一为 `notification:send`；`file:read` 等保持有效；不得使用未登记 ID（[04-能力契约规范](../../05-接口与契约/04-能力契约规范.md)）。
3. JNI / Swift FFI 表述与[03-核心接口规范](../../05-接口与契约/03-核心接口规范.md)对齐：移动端绑定在 Phase 5 引入，当前只有 Neon / Node 绑定面；Rust 核心与 Bridge 接口自 Phase 0 起按平台无关设计。
4. `{10位62进制ID}` 统一写作 10 位 Base62 编号。
5. 同步引擎定位为可选、按需加载的平台服务插件形态；目录态不参与同步（[07-同步引擎设计](../01-子系统设计/07-同步引擎设计.md)）。
6. 浏览器侧应用插件宿主（旧社区平台的 `plugin-sessions` 插件会话 API、`resource-open-plan`、`entry` / `bootstrap` 引导与 Web Runtime）不在本架构范围：插件运行目标只有 `host`（桌面壳 / 无头壳 / Phase 5 移动壳）；如需再评估走 RFC → 评审 → ADR（[17-跨端Shell与平台抽象设计](../01-子系统设计/17-跨端Shell与平台抽象设计.md) §2.2、§5.5）。

**文档结束**
