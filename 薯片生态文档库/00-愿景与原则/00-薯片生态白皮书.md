# 薯片生态白皮书

> 版本：v3.0.0
> 日期：2026-09-19
> 状态：正式版
> 适用范围：定义薯片生态的使命愿景、核心概念、技术架构概览、核心原则摘要与发展阶段

---

## 一、使命与愿景

### 1.1 使命

**薯片生态 = 薯片平台 + 插件生态 + 内容生态。**

- **薯片平台**：运行在操作系统之上的软件平台，是所有插件与内容的唯一承载。
- **插件生态**：由基础卡片、箱子布局、应用、服务四类角色的插件组成。
- **内容生态**：由 `.card` 卡片与 `.box` 箱子构成，格式开放、脱离程序。

平台提供运行时、能力与规范；插件提供业务与体验；内容独立于程序长期存在。

### 1.2 两个目标

**软件生态：把常用软件重做一遍。**

用户只安装薯片平台，编辑器、阅读器、播放器、查看器、资源管理器、社区客户端等常用软件都以插件形式运行在平台内，共享同一套运行时、组件库、文件格式与权限系统。软件在统一平台上持续生长，而不是彼此隔离的孤岛。

**卡片生态：把信息保存为卡片，让信息脱离程序。**

信息以 `.card` 卡片文件保存：自包含内容、结构、资源与元数据；双击即开；可长期保存、自由流转；第三方工具可以读写。信息不再锁死在某个软件的数据孤岛中。

### 1.3 开放与社区友好

- 文件格式、接口协议与插件规范全部开放，任何第三方都可以实现、集成与扩展。
- 官方插件不享有特权：官方与第三方使用同一套接口、同一套生命周期。
- 支持第三方软件集成薯片卡片能力：博客、知识库、网站等可以嵌入、渲染与消费 `.card` 卡片。
- 生态以社区方式协作演进：重大变更走 RFC 评审，并以 ADR 记录决策。
- 本地优先：核心功能离线可用，用户数据保存在本地，平台不默认上传用户数据。

### 1.4 平台

薯片平台是全平台软件平台：

- 实现优先级：macOS / Windows → Linux（桌面三端完成）→ Android → iOS。
- 五端共享：`.card` / `.box` 文件格式、Rust 核心、Bridge 接口。
- 移动端为 Phase 5（架构预留）；桌面在 Phase 1-4 完成。
- 同一套文档与契约覆盖全部平台，平台层实现差异对插件透明。

## 二、核心概念

### 2.1 卡片（`.card`）

**定义**：自包含的知识单元文件，内容生态的最小交付单位。

- 卡片类型由基础卡片插件定义，渲染与编辑由对应插件提供。
- 卡片包内含内容、结构、资源与元数据，不依赖创建它的程序。
- 可被多个箱子引用，可嵌套组织。
- 结构遵循 [ADR-009](../01-架构设计/ADR/ADR-009-文件格式设计原则.md)：`.card/`（`metadata.yaml`、`structure.yaml`、`cover.html`、`cardcover/`）+ `content/{10 位 Base62 编号}.yaml` + 卡片根目录资源，发布态为 ZIP Store；字段与校验规则以[《卡片文件格式》](../04-文件格式规范/01-卡片文件格式.md)为准。

### 2.2 箱子（`.box`）

**定义**：组织卡片引用的容器文件。

- 箱子保存条目（entry）引用与布局（layout）配置，不内嵌被引用卡片实体；允许随包内嵌 `.card`（禁止内嵌 `.box`）。
- 布局由箱子布局插件定义，切换布局不改变引用数据。
- 结构遵循 [ADR-009](../01-架构设计/ADR/ADR-009-文件格式设计原则.md)：`.box/`（`metadata.yaml`、`structure.yaml`、`content.yaml`、`cover.html`）+ 可选 `boxcover/`、`assets/`，条目在 `structure.yaml`、布局在 `content.yaml`，发布态为 ZIP Store；引用模型与路径规则以[《箱子文件格式》](../04-文件格式规范/02-箱子文件格式.md)为准。

### 2.3 插件与四种插件角色

**插件**是扩展薯片平台的最小交付单元。插件不按功能分类，只按角色区分；一个插件只有一个角色（[ADR-005](../01-架构设计/ADR/ADR-005-插件不分类只分角色.md)）。

| 角色 | 标识 | 职责 |
|---|---|---|
| 基础卡片插件 | `basecard` | 定义卡片类型，提供渲染与编辑能力 |
| 箱子布局插件 | `boxlayout` | 定义箱子的呈现方式 |
| 应用插件 | `app` | 独立应用，拥有自己的窗口与界面 |
| 服务插件 | `service` | 后台服务，无界面，可注册能力 |

- 需要多角色能力时拆分为多个插件，用 `dependencies` 组合。
- 插件基于 Cordis：注册服务、依赖注入、事件、可逆副作用、热插拔。
- 插件经 Bridge 访问系统能力；包格式为 `.cpk`，`manifest` 是唯一权威清单。
- 插件与平台、插件与插件之间只通过服务、能力与事件通信。

### 2.4 薯片平台（Chips Platform）

**定义**：运行插件的底层平台，由以下部分构成。

- **Cordis 运行时**：插件加载、生命周期、服务注册与依赖注入、可逆副作用。
- **能力 Bridge**：插件与平台之间的能力通信层，负责注册、权限、校验与路由。
- **文档解析**：`.card` / `.box` 的解析与校验。
- **资源管理**：资源句柄、缓存、清理与统一访问。
- **渲染框架**：卡片与箱子的统一渲染链路。
- **权限 / 事件 / 配置系统**：最小权限、事件总线、分层配置。

平台只提供能力与机制，不实现业务逻辑。

## 三、技术架构概览

### 3.1 分层架构

```
┌──────────────────────────────────────────────────────┐
│ 插件生态层                                            │
│  应用插件 · 基础卡片插件 · 箱子布局插件 · 服务插件     │
└──────────────────────────────────────────────────────┘
                      ↕ Bridge（能力导向）
┌──────────────────────────────────────────────────────┐
│ 薯片平台层                                            │
│  Cordis 运行时 · Bridge · 文档解析 · 资源管理          │
│  渲染框架 · 权限系统 · 事件系统 · 配置系统             │
└──────────────────────────────────────────────────────┘
                      ↕ Neon（Rust ↔ Node.js Native Module）
┌──────────────────────────────────────────────────────┐
│ 壳与系统层                                            │
│  Electron 壳（主进程/渲染进程/preload） · 操作系统      │
└──────────────────────────────────────────────────────┘
```

### 3.2 技术栈

| 层 | 技术 | 说明 |
|---|---|---|
| 运行时 | Cordis（Rust 重实现） | `Context` / `Fork` / `provide` / `inject` / 事件 / 生命周期 |
| 能力层 | 能力导向 Bridge | 插件请求 `Capability`，Bridge 负责注册表、权限、校验、路由 |
| 核心 | Rust + Neon | Cordis 运行时、Bridge、文档解析、资源管理经 Neon 暴露给 Node.js |
| 壳 | Electron | 主进程承载平台，渲染进程运行 React，preload 暴露 `window.chips` |
| 前端 | React + `@chips/antd` + `@chips/ui` | fork antd 仅在 `@chips/ui` 内部使用；业务代码只从 `@chips/ui` 导入 |
| 视觉 | Design Tokens + antd 主题定制 | 视觉令牌经 `@chips/ui` 暴露；文案简体中文直写 |
| 资源协议 | `chips-resource://` | 统一、受限、可审计的资源访问 |

### 3.3 统一链路

卡片与箱子的解析、资源访问、渲染、打开、导出共用同一条链路与同一套接口；接口内部按文件格式（`.card` / `.box`）分支。禁止为卡片和箱子各写一套并行管线。

### 3.4 文件格式与插件包

- `.card` 与 `.box`：YAML + 目录结构 + ZIP Store（发布态不压缩归档）。
- 开发态为目录形式，发布态为单个文件，可由标准工具打开。
- `.cpk` 插件包：ZIP Store，根目录 `manifest.yaml` 为唯一权威清单。
- 规范细节见《卡片文件格式》《箱子文件格式》《插件包格式》《版本与迁移规范》。

## 四、核心原则摘要

完整原则与红线见[《架构原则》](./01-架构原则.md)，设计思想见[《设计哲学》](./02-设计哲学.md)。

### 4.1 一切皆插件

- 平台核心功能同样以插件形式实现：编辑器、查看器、资源管理器都是插件。
- 插件可安装、可替换、可卸载；卸载通过 Fork 反向清理，不留下副作用。
- 平台保持极小内核，生态决定最终体验。

### 4.2 平台不做业务

- 平台只提供能力与机制，不实现具体业务逻辑。
- 平台提供"文件读取"，但不知道如何"编辑文本"；提供"渲染框架"，但不知道如何"渲染某类卡片"。
- 业务逻辑全部在插件中，可快速迭代、可被第三方完全替换。

### 4.3 能力导向

- 插件请求能力（Capability），而不是调用平台函数。
- 能力 ID 使用 `<domain>:<action>[:<target>]`，权限 ID 使用 `<domain>:<scope>[:<qualifier>]`。
- 每个能力声明所需权限，Bridge 按能力声明与插件申请的交集判定。
- 能力可复用、可扩展、可审计。

### 4.4 开放

- 文件格式、协议与接口全部公开、有文档、无内部 API。
- 第三方可以读取、写入、渲染薯片卡片，可以集成薯片卡片能力。
- 官方插件与第三方插件使用同一套接口。

### 4.5 本地优先

- 核心功能离线可用；用户数据保存在本地。
- 平台不默认上传用户数据；云同步等能力由用户主动安装的插件提供。
- 所有资源经 `chips-resource://` 访问，权限受限、行为可审计。

### 4.6 统一链路

- 卡片与箱子共用同一条解析、资源、渲染、打开、导出链路。
- 编辑态可以界面就近渲染，但必须复用同一套插件接口与同一份解析结果。
- 禁止并行管线与旁路实现。

## 五、发展阶段

薯片生态采用大爆炸重构：旧版冻结，新库从零建立，不做兼容（[ADR-010](../01-架构设计/ADR/ADR-010-大爆炸重构策略.md)）。开发路线以阶段为唯一口径，不设日历排期；各阶段完成标准与质量门禁见《开发流程与阶段计划》。

| 阶段 | 目标 | 交付物 |
|---|---|---|
| Phase 0 | 文档与预研 | 全部文档库、Monorepo 骨架、Cordis/Neon/Bridge POC |
| Phase 1 | 核心平台 | Rust Cordis 运行时、Bridge、Electron 壳、React 壳、最小原型 |
| Phase 2 | 子系统 | 插件系统、渲染引擎、资源管理、文档解析、权限/事件/配置系统、覆盖率 >80% |
| Phase 3 | 官方插件与生态 | 应用插件重写（编辑引擎、查看器、资源管理器）、CLI、示例插件、开发者文档 |
| Phase 4 | 迁移与发布 | 用户数据迁移工具、性能与安全加固、桌面三端（macOS、Windows、Linux）验证、v1.0 发布 |
| Phase 5 | 移动端 | Android / iOS（架构预留，暂不排期） |

平台优先级为 macOS / Windows → Linux（桌面三端完成）→ Android → iOS；其中桌面三端在 Phase 4 完成验证，移动端为 Phase 5 架构预留。文件格式、Rust 核心与 Bridge 接口从 Phase 0 起即按平台无关设计，保证五端共享。

## 六、核心术语

| 术语 | 定义 |
|---|---|
| 薯片平台 / Chips Platform | 运行插件的底层平台 |
| 薯片生态 | 平台 + 插件生态 + 内容生态的总称 |
| Cordis | 插件框架，原子化服务 / 可逆副作用 / 依赖注入（Rust 重实现） |
| Context / ctx | 插件运行时上下文：服务注册、依赖注入、事件、生命周期 |
| Fork | Cordis 副作用追踪与撤销单元，`dispose()` 反向清理 |
| 服务（Service） | 通过 `ctx.provide` / `ctx.inject` 注册与消费的原子模块 |
| 能力（Capability） | Bridge 中的原子功能单元：`id` / `execute` / `schema` / `permissions` |
| Bridge | 插件与平台的能力通信层，三层：插件层 → Bridge 层 → Host 层（平台侧实现，仅作角色词） |
| 插件角色 | `basecard` / `boxlayout` / `app` / `service`，一个插件只有一个角色 |
| 基础卡片 | 最小知识单元的内容类型，由基础卡片插件定义 |
| 卡片 / `.card` | 自包含知识单元文件 |
| 箱子 / `.box` | 组织卡片引用的容器文件 |
| 条目（entry） | 箱子中的卡片引用记录 |
| 布局（layout） | 箱子的呈现方式，由箱子布局插件定义 |
| Design Tokens | 视觉令牌，样式唯一来源，经 `@chips/ui` 暴露 |
| `@chips/ui` | 共享 UI 层（组件、Hooks、Tokens），唯一导入面 |
| `@chips/antd` | fork antd，基础组件库，仅 `@chips/ui` 内部使用 |
| `@chips/sdk` | 类型定义、脚手架、测试辅助，不承载运行时 |
| ZIP Store | 不压缩的 ZIP 归档方式，可 mmap / 随机访问 |
| manifest | 插件清单，唯一权威配置 |
| 能力 ID | `<domain>:<action>[:<target>]` |
| 权限 ID | `<domain>:<scope>[:<qualifier>]` |
| `chips-resource://` | 统一资源访问协议 |
| 大爆炸重构 | 推倒重来、不做兼容、旧版冻结 |
