## 二、架构红线（Architecture Red Lines）

以下原则是**绝对不可违反的红线**。

### 2.1 服务必须走内核路由（No Direct Service Calls）

**原则**：插件之间不能直接 `import` 调用，必须通过 Cordis 服务注册和依赖注入。

**禁止**：
```typescript
// ❌ 禁止：插件 A 直接导入插件 B
import { ImageProcessor } from '@chips/plugin-image-processor';

class MyPlugin {
  process() {
    const processor = new ImageProcessor();  // 禁止
    processor.decode(data);
  }
}
```

**正确**：
```typescript
// ✅ 正确：通过 Cordis 依赖注入
class MyPlugin {
  constructor(ctx: Context) {
    // 声明依赖
    ctx.inject(['image'], (ctx) => {
      // ctx.image 由内核注入
      ctx.image.decode(data);
    });
  }
}
```

**理由**：
- 解耦：插件 A 不需要知道插件 B 的实现
- 可替换：可以替换 ImageProcessor 的实现
- 可测试：可以 Mock 依赖

---

### 2.2 插件访问系统能力必须走 Bridge（No Direct System Access）

**原则**：插件不能直接调用 Node.js API、Electron API、系统 API，必须通过 Bridge。

**禁止**：
```typescript
// ❌ 禁止：插件直接使用 Node.js API
import fs from 'fs';

class MyPlugin {
  readFile(path: string) {
    return fs.readFileSync(path);  // 禁止
  }
}
```

**正确**：
```typescript
// ✅ 正确：通过 Bridge 请求能力
class MyPlugin {
  async readFile(path: string): Promise<string> {
    return await chips.request<string>('file:read', { path });
  }
}
```

**理由**：
- 安全：权限可控、可审计
- 跨平台：Bridge 抽象了平台差异
- 可测试：可以 Mock Bridge

---

### 2.3 禁止跨层直连（No Layer Violations）

**原则**：严格遵守分层架构，上层可以调用下层，下层不能调用上层。

**架构层次**（从下到上）：
```
插件层（Plugin Layer）
    ↕ 只能向下调用
平台层（Platform Layer）
    ↕ 只能向下调用
系统层（System Layer）
```

**禁止**：
```typescript
// ❌ 禁止：平台层调用插件层
class ChipsPlatform {
  notifyEditor() {
    // 平台不能直接调用插件
    EditorPlugin.refresh();  // 禁止
  }
}
```

**正确**：
```typescript
// ✅ 正确：通过事件系统
class ChipsPlatform {
  notifyEditor() {
    // 平台发布事件，插件监听
    this.eventBus.emit('document:changed');
  }
}

class EditorPlugin {
  constructor(ctx: Context) {
    ctx.on('document:changed', () => {
      this.refresh();
    });
  }
}
```

---

### 2.4 SDK 不承载运行时实现（SDK is Not Runtime）

**原则**：`@chips/sdk` 只负责类型定义、脚手架、测试辅助，不承载平台运行时实现。

**SDK 的职责**：
- ✅ TypeScript 类型定义
- ✅ 插件开发脚手架
- ✅ 测试工具和 Mock
- ✅ 开发者工具

**SDK 不能做的**：
- ❌ 实现 Bridge 的主逻辑
- ❌ 实现 Cordis 运行时
- ❌ 实现文档解析

**理由**：
- SDK 和薯片平台的版本可能不同步
- SDK 是给开发者用的，薯片平台是给用户用的
- 职责分离，避免混乱

---

### 2.5 前端统一技术栈（Unified Frontend Stack）

**原则**：官方前端统一使用 React + fork antd + @chips/ui。

**强制要求**：
- ✅ 前端框架：React 18+
- ✅ 组件库：fork antd（唯一组件库）
- ✅ 共享层：@chips/ui
- ✅ 文案：简体中文直写（不使用 i18n key）
- ✅ 样式：Design Tokens + antd 主题定制
- ❌ 禁止引入第二套组件库（如 Material-UI、Chakra UI）
- ❌ 禁止硬编码样式（必须使用 Design Tokens）

**例外**：
- 第三方插件可以使用其他技术栈（自担风险）
- 但官方插件必须统一

**理由**：
- 视觉一致性
- 降低维护成本
- 更好的集成（统一 Design Tokens 与组件行为）

---

### 2.6 禁止临时实现（No Temporary Implementations）

**原则**：不做临时版、简化版、占位实现。每个功能都必须完整实现。

**禁止**：
```typescript
// ❌ 禁止
function parseCard(data: string) {
  // TODO: 暂时只支持 JSON，后续支持 YAML
  return JSON.parse(data);
}

// ❌ 禁止
class BridgeStub {
  // 临时实现，等 Rust 核心完成后替换
  async request(capability: string) {
    return mockCapability;
  }
}
```

**正确**：
```typescript
// ✅ 正确：完整实现
function parseCard(data: string, format: 'json' | 'yaml') {
  switch (format) {
    case 'json': return JSON.parse(data);
    case 'yaml': return yaml.parse(data);
  }
}
```

**理由**：
- 临时实现容易变成永久实现
- 技术债务累积
- 影响架构决策

**例外**：
- POC 阶段可以有简化实现
- 但进入 Phase 1 后必须完整实现

---

### 2.7 禁止兼容性包袱（No Compatibility Burden）

**原则**：薯片生态目前处于从零重构阶段，不需要考虑任何向后兼容。

**具体要求**：
- ❌ 不要为"可能的旧版本"预留接口
- ❌ 不要保留"已弃用但可能还有人用"的 API
- ❌ 不要因为"以后可能兼容"而引入复杂设计
- ✅ 直接使用最优架构
- ✅ 接口设计只考虑当前需求
- ✅ 后续版本通过迁移工具解决兼容性

**理由**：
- 现在处于重构阶段，没有历史包袱
- 为未来的兼容性设计是过度设计
- 保持架构的纯净和简洁
