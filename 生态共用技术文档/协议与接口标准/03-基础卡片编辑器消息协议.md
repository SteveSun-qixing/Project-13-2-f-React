# 基础卡片编辑器消息协议

> 版本：v1.0.0  
> 状态：冻结（2026-03-11）  
> 适用范围：`Chips-Host`、`Chips-SDK`、`Chips-EditingEngine`、所有基础卡片插件

## 1. 目标

基础卡片编辑器运行在 Host 所有权的 iframe 中。为保证编辑引擎、Host 与基础卡片插件之间的职责边界稳定，基础卡片编辑相关跨窗口通信统一使用本协议。

本协议解决以下问题：

- 基础卡片编辑器何时完成挂载；
- 编辑器如何把配置变更上报给宿主；
- 宿主如何在撤销/重做/回滚后把权威配置同步回编辑器；
- 编辑器运行时错误如何被宿主感知并上报。

## 2. 总体原则

- iframe 文档由 Host 生成并写入 `srcdoc`；
- 插件不直接访问 Node/Electron API；
- 应用层不直接 import 插件文件，也不自行拼接编辑器 HTML；
- 所有消息均以 `window.postMessage` 发送，宿主必须按 `contentWindow + origin` 严格过滤；
- `config` 为标准化后的插件编辑模型，不是原始 `content/*.yaml` 文本。

## 3. 事件清单

### 3.1 子 iframe -> 宿主

#### `chips.basecard-editor:ready`

表示编辑器 UI 已经完成首次挂载。

```ts
interface BaseCardEditorReadyPayload {
  nodeId: string;
  cardType: string;
  pluginId: string;
  protocolVersion: string;
}
```

#### `chips.basecard-editor:config-change`

表示用户在编辑器中产生了新的合法配置。

```ts
interface BaseCardEditorConfigChangePayload {
  nodeId: string;
  cardType: string;
  pluginId: string;
  config: Record<string, unknown>;
}
```

约束：

- 插件必须仅在本次配置通过本地校验后发送；
- 宿主收到后可做 dirty 标记、自动保存节流、预览刷新等处理；
- 该事件本身不代表已经成功保存到 `.card` 文件。

#### `chips.basecard-editor:config-synced`

表示编辑器已经接收并应用宿主下发的权威配置。

```ts
interface BaseCardEditorConfigSyncedPayload {
  nodeId: string;
  config: Record<string, unknown>;
}
```

#### `chips.basecard-editor:fatal-error`

表示编辑器运行时发生不可恢复错误。

```ts
interface BaseCardEditorFatalErrorPayload {
  code: string;
  message: string;
  details?: unknown;
}
```

### 3.2 宿主 -> 子 iframe

#### `chips.basecard-editor:sync-config`

宿主要求编辑器切换到新的权威配置。

```ts
interface BaseCardEditorSyncConfigPayload {
  config: Record<string, unknown>;
}
```

典型触发时机：

- 撤销 / 重做；
- 自动保存后，Host 对配置进行标准化并回写；
- 保存失败后回滚到最近一次成功状态；
- 外部命令导致当前节点配置被替换。

## 4. 生命周期建议

推荐顺序：

1. Host 调用 `card.renderBaseCardEditor({ cardFile, nodeId })`；
2. SDK/应用把返回的 `editor.body` 写入 iframe `srcdoc`；
3. 插件挂载完成后发送 `chips.basecard-editor:ready`；
4. 用户编辑时，插件发送 `chips.basecard-editor:config-change`；
5. 宿主保存成功或撤销/重做后，向 iframe 发送 `chips.basecard-editor:sync-config`；
6. 插件应用新配置后，发送 `chips.basecard-editor:config-synced`。

## 5. 错误处理

- 插件必须把不可恢复错误通过 `fatal-error` 上报，不得静默吞掉；
- 宿主收到后应中止当前编辑会话的自动保存队列，并向上层展示错误态；
- SDK 侧应将 `fatal-error` 规范化为标准错误对象 `{ code, message, details, retryable }`。

## 6. 兼容策略

当前生态尚未发布第一版，因此本协议按冻结稿直接执行：

- 不保留旧协议兼容层；
- 新接入的基础卡片插件与编辑引擎必须直接遵守本协议；
- 若协议需要修改，必须先走工单与共享文档更新流程。
