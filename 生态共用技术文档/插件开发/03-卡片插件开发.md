# 卡片插件开发

## 概述

卡片插件为基础卡片提供查看态渲染、编辑态渲染、配置归一、校验和资源引用收集能力。

当前正式链路有三类消费者：

- Host 通用查看链路：`card.render` 与 `client.card.compositeWindow.render(...)`
- Host 托管编辑器链路：`card.renderEditor` 与 `client.card.editorPanel.render(...)`
- 官方编辑引擎链路：`basecard.openSession/renderView/renderEditor/closeSession`

因此，卡片插件必须交付“一套正式插件导出”，由 Host 统一加载并服务不同宿主，而不是为不同宿主复制多套实现。

## 插件结构

卡片插件至少应包含以下模块：

- `manifest.yaml`
- `src/index.ts`
- `src/render/`
- `src/editor/`
- `src/schema/`
- `src/shared/`
- 测试目录与示例数据

推荐结构：

```text
src/
  index.ts
  render/
    view.tsx
    runtime.ts
  editor/
    panel.tsx
    runtime.ts
  schema/
    card-config.ts
  shared/
    utils.ts
    i18n.ts
  runtime-contract.ts
```

## manifest 配置

卡片插件的 `manifest.yaml` 必须满足以下要求：

- `type: card`
- `capabilities.cardTypes` 明确声明支持的基础卡片类型
- `entry` 指向构建产物入口，例如 `dist/index.mjs`

示例：

```yaml
id: chips.basecard.richtext
name: 富文本基础卡片插件
version: 0.1.0
type: card
entry: dist/index.mjs
capabilities:
  cardTypes:
    - base.richtext
permissions: []
```

约束：

- `capabilities.cardTypes` 是 Host 分发与基础卡片会话路由的统一依据。
- `capabilities.cardTypes`、卡片文件中的 `card_type` / `structure[].type` 与插件描述符 `cardType` 必须保持同一正式类型值，不引入别名归一逻辑。

## 正式导出契约

卡片插件入口必须导出以下能力：

```ts
export interface BasecardRenderContext {
  container: HTMLElement;
  config: Record<string, unknown>;
  themeCssText?: string;
  resolveResourceUrl?: (resourcePath: string) => Promise<string>;
  releaseResourceUrl?: (resourcePath: string) => Promise<void> | void;
}

export interface BasecardEditorContext {
  container: HTMLElement;
  initialConfig: Record<string, unknown>;
  onChange(next: Record<string, unknown>): void;
  resolveResourceUrl?: (resourcePath: string) => Promise<string>;
  releaseResourceUrl?: (resourcePath: string) => Promise<void> | void;
  importResource?: (input: { file: File; preferredPath?: string }) => Promise<{
    path: string;
    url?: string;
    name?: string;
    size?: number;
    mimeType?: string;
  }>;
  deleteResource?: (resourcePath: string) => Promise<void>;
}

export function renderBasecardView(ctx: BasecardRenderContext): (() => void) | void;
export function renderBasecardEditor(ctx: BasecardEditorContext): (() => void) | void;
export function getBasecardDescriptor(): {
  cardType: string;
  displayName: string;
  commitDebounceMs?: number;
};
export function createInitialBasecardConfig(baseCardId: string): Record<string, unknown>;
export function normalizeBasecardConfig(input: Record<string, unknown>, baseCardId: string): Record<string, unknown>;
export function validateBasecardConfig(config: Record<string, unknown>): {
  valid: boolean;
  issues: Array<{ path: string; message: string; code?: string }>;
};
export function collectReferencedResources(config: Record<string, unknown>): string[];
```

正式要求：

- `renderBasecardView` 与 `renderBasecardEditor` 必须是“挂载到容器并返回 cleanup”的纯函数。
- `normalizeBasecardConfig`、`validateBasecardConfig`、`collectReferencedResources` 是正式契约，不可省略。
- `commitDebounceMs` 由宿主会话层消费，用于统一提交节流。
- `collectReferencedResources` 必须返回卡片根目录相对路径。

## 查看态渲染开发

查看态的正式职责是：根据已归一配置把内容挂载到容器。

推荐实现方式：

1. 在 `render/view.tsx` 中创建视图结构。
2. 在 `render/runtime.ts` 中处理根节点挂载与清理。
3. 在 `src/index.ts` 中导出 `renderBasecardView`。

查看态约束：

- 不直接假定外层一定有边框、圆角或卡片壳层。
- 不自己解析插件清单、主题链或卡片文件结构。
- 内部资源路径按卡片根目录规则解析，不私自拼系统绝对路径。

## 编辑器开发

编辑器的正式职责是：把配置编辑 UI 挂载到给定容器，并通过 `onChange` 输出下一版配置快照。

推荐实现方式：

1. 在 `editor/panel.tsx` 中实现编辑器界面。
2. 在 `editor/runtime.ts` 中处理根节点挂载、尺寸与清理。
3. 在 `onChange` 前先完成插件内部必要的清洗。
4. 如需操作资源，通过宿主提供的 `resolveResourceUrl/releaseResourceUrl/importResource/deleteResource` 完成。

编辑器约束：

- 不直接调用文件写入或持久化接口。
- 不自己实现草稿会话、防抖提交和卡片切换逻辑。
- 不要求宿主必须把自己运行在特定 iframe 协议中。
- `importResource(...)` 必须接收 `{ file, preferredPath? }`，返回 `{ path }` 或包含补充信息的资源结果。
- `path` 必须始终是相对于卡片根目录的正式路径。

## 配置与资源

### 配置数据结构

每种卡片类型都应定义正式 schema。

推荐做法：

- 在 `schema/card-config.ts` 中声明类型；
- 在同文件中提供默认配置；
- 在 `runtime-contract.ts` 中集中实现：
  - `createInitialBasecardConfig`
  - `normalizeBasecardConfig`
  - `validateBasecardConfig`
  - `collectReferencedResources`

### 资源规则

- 卡片内部资源路径统一以卡片根目录为基准记录。
- 内部资源示例：`assets/example.png`
- 外部文件可记录绝对路径。
- 网络资源可记录 URL。
- `collectReferencedResources` 只返回卡片内部资源，不返回绝对路径与网络 URL。

## 与宿主链路的关系

### Host 通用链路

- Host 通过 `card.render/card.renderEditor` 加载插件。
- Host 负责生成正式 iframe 文档与事件协议。
- SDK `compositeWindow/editorPanel/coverFrame` 负责把这些文档交付给应用。

### 官方编辑引擎链路

- 编辑引擎通过 Host `basecard.*` 会话接口完成插件归一、校验和查看态 iframe 装配。
- `renderBasecardView` 被装载到单卡 iframe。
- `renderBasecardEditor` 由 Host `basecard.renderEditor` 包装成正式单卡编辑 iframe，再交给编辑引擎编辑面板装载。
- 编辑引擎壳层负责选中态、资源导入回写、自动保存和复合卡片装配。

重要边界：

- 普通应用和第三方集成不得自行扫描插件目录并直接 import 插件源码。
- 编辑引擎不是本地插件运行时权威方，Host 才是。

## 生命周期管理

卡片插件必须具备完整生命周期：

- 初始化阶段：创建 DOM、绑定事件、同步初始配置；
- 更新阶段：宿主重建或重新挂载后读取新配置；
- 销毁阶段：清理事件监听、定时器、编辑器实例和临时节点。

禁止事项：

- 把全局事件监听遗留在页面上；
- 依赖浏览器刷新才能释放状态；
- 把 cleanup 留成空实现或临时实现。

## 主题适配

- 基础卡片必须使用正式 `--chips-*` token，而不是写死颜色。
- 查看态与编辑态都必须适配同一套主题 token 体系。
- 插件不得依赖某个宿主私有主题注入细节。

## 错误处理

插件需要处理以下错误：

- 配置字段缺失或非法；
- 资源加载失败；
- 编辑器初始化失败；
- 富文本或嵌入内容清洗失败。

要求：

- 错误局部隔离在当前基础卡片范围内；
- 不抛出会让宿主整页崩溃的未处理异常；
- 对用户可见的错误信息应尽量可理解。

## 测试策略

卡片插件需要至少覆盖以下测试：

- 查看态挂载测试；
- 编辑态挂载测试；
- 配置归一测试；
- 配置校验测试；
- 资源引用收集测试；
- cleanup 与重复挂载稳定性测试；
- Host 通用链路集成测试；
- 编辑引擎基础卡片会话链路集成测试。
