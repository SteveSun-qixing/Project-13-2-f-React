# 卡片插件开发

## 概述

卡片插件为基础卡片提供渲染和编辑能力。每个基础卡片类型对应一个卡片插件，定义该类型卡片在查看器、通用 Host 托管编辑器，以及官方编辑引擎中的正式行为。

当前正式链路有两类消费者：

- Host 通用链路：通过 `card.render/card.renderEditor` 与 SDK `compositeWindow/editorPanel` 消费；
- 官方编辑引擎链路：通过 Host 已安装并启用的卡片插件入口模块导出的 `basecardDefinition` 消费同一组插件导出。

因此，卡片插件必须把“内容渲染/编辑能力 + 配置契约”写成可复用的正式导出，而不是把运行时假设写死在某一个宿主里。

## 插件结构

卡片插件至少应包含以下模块：

- `manifest.yaml`
- `src/index.ts`
- `src/render/`
- `src/editor/`
- `src/schema/`
- `src/shared/`
- 测试目录与示例数据

推荐结构：

```text
src/
  index.ts
  render/
    view.tsx
    runtime.ts
  editor/
    panel.tsx
    runtime.ts
  schema/
    card-config.ts
  shared/
    utils.ts
  lib/
    messages.ts
```

其中：

- `render/` 负责查看态内容挂载；
- `editor/` 负责编辑态内容挂载；
- `schema/` 负责默认值、类型定义与配置约束；
- `shared/` 负责富文本清洗、格式化等可复用逻辑；
- `lib/messages.ts` 是本地简体中文文案映射模块（key → 中文 + `formatMessage` 插值），界面文案简体中文直写，不再维护语言包。

官方基础卡片脚手架生成的标准工程结构如下：


生成工程默认不创建 `需求文档/`、`技术文档/`、`技术手册/`、`开发计划/` 这类过程性目录。长期公共契约应沉淀到生态共用技术文档，单个生成工程 README 只保存工程开发说明。

## manifest 配置

卡片插件的 `manifest.yaml` 必须满足以下要求：

- `type: card`
- `capabilities.cardTypes` 明确声明支持的基础卡片类型
- `entry` 指向构建产物入口，例如 `dist/index.mjs`
- 完整声明 `runtime.targets`
- 不声明仅应用插件可用的 `ui.surface`

示例：

```yaml
id: chips.basecard.richtext
name: 富文本基础卡片插件
version: 0.1.0
type: card
entry: dist/index.mjs
capabilities:
  cardTypes:
    - base.richtext
permissions: []
runtime:
  targets:
    desktop:
      supported: true
    web:
      supported: false
    mobile:
      supported: false
    headless:
      supported: true
```

约束：

- `capabilities.cardTypes` 是 Host 分发与编辑引擎描述符映射的统一依据；
- 若插件需要兼容 `RichTextCard -> base.richtext`、`ImageCard -> base.image` 这类别名，应在宿主描述符层处理，不应把别名判断散落在业务组件中。

## 正式导出契约

卡片插件入口必须导出以下正式能力：

```ts

    mimeType?: string;

}

  file: File;
  preferredPath?: string;
}

  path: string;
}

  file: File;
  preferredRootDir?: string;
  entryFile?: string;

    mimeTypes?: string[];
    extensions?: string[];

  stripSingleRootDir?: boolean;
  excludeSystemArtifacts?: boolean;
}

  sourcePath: string;
  resourcePath: string;
  fileName: string;
  mimeType?: string;
  size: number;
  compressedSize: number;
  crc32: number;
  offset: number;

  modifiedTime?: number;
}

  fileName?: string;
  mimeType?: string;

  entries: BasecardArchiveImportedEntry[];

  resourcePath: string;
  outputPath: string;
  overwrite?: boolean;
}

  sourceMimeType: "image/tiff";
  width?: number;
  height?: number;
}

  resourcePath: string;
  outputPath: string;

    height?: number;

  height: number;

  durationSeconds?: number;
}

  renderEditor?(ctx: BasecardEditorContext): (() => void) | void;

export const basecardDefinition: BasecardDefinition;
```

正式要求：

- 两个导出都必须是“挂载到容器并返回 cleanup”的纯函数；
- `basecardDefinition` 是官方编辑引擎进入正式运行时链路的唯一插件入口；
- `basecardDefinition.cardType` 必须与 `manifest.yaml` 中的 `capabilities.cardTypes[*]` 对齐；
- `basecardDefinition.icon` 必须输出正式 `IconDescriptor`，供编辑引擎卡箱库与其他运行时 UI 统一渲染；
- 插件静态身份图标存放在 `assets/icons/basecard-icon.svg/.png/.ico/.icns`，由正式工具链生成且每个基础卡片插件唯一，不进入 manifest、不属于系统入口链路；生成链路见 `生态共用技术文档/插件开发/01-插件开发规范.md` 的「图标资产」章节；
- 若插件需要在编辑引擎预览态屏蔽 iframe 内部指针交互，应通过 `previewPointerEvents = 'shielded'` 正式声明，而不是要求宿主按具体卡片类型写死特殊分支；
- 导出函数不得直接写文件、直接创建窗口或直接依赖宿主状态机；
- 编辑器导出必须允许被直接挂载到普通 DOM 容器，而不是假定自己必然运行在 Host 托管 iframe 中；
- 所有清理逻辑都必须在返回的 cleanup 中闭环。

## 查看态渲染开发

查看态渲染的正式职责是：根据配置把内容挂载到给定容器。

推荐实现方式：

1. 在 `render/view.tsx` 中创建纯 DOM 结构；
2. 在 `render/runtime.ts` 中处理插件自有样式注入、根节点挂载与清理；
3. 在 `src/index.ts` 中把 `renderBasecardView` 暴露给宿主。

查看态约束：

- 不直接假定外层一定有边框、圆角或卡片壳层；
- 内容宽度以宿主提供的容器为准；
- 颜色、边框、文本色使用 antd token 或苹果风格色值常量（`#f5f5f7` / `#1d1d1f` / `#0a84ff` 等，见 `生态共用技术文档/前端基础/02-统一视觉规范.md`），不再依赖主题 CSS 变量注入；
- 宿主可能把该导出挂载在 Host 生成的 iframe 文档中，也可能挂载在编辑引擎创建的单卡 iframe 中。
- 若查看态需要访问卡片内部文件资源，必须消费宿主提供的 `resolveResourceUrl/releaseResourceUrl`；应用层和基础卡片运行时不得把卡片根目录拼接成 `file://`，也不得把未解析的相对路径直接交给 iframe。只有远程 `http/https` 来源才可直接使用原始 URL。
- 若查看态需要把点击资源转交给外层容器统一打开，宿主可以额外提供 `openResource(...)` 这类可选回调；插件必须把它视为可选能力，缺失时优雅降级为静态显示。
- 当查看态需要让目标应用恢复结构化业务上下文时，可以把业务对象放入 `openResource(...).payload`；Host 只负责透传，不负责解释该对象。

## 编辑器开发

编辑器的正式职责是：把配置编辑 UI 挂载到给定容器，并通过 `onChange` 输出新配置。

推荐实现方式：

1. 在 `editor/panel.tsx` 中实现编辑器界面，使用 antd 控件 + 受控 State（`value` + `onChange` 模式，等价旧 `ChipsForm` 受控语义），面板根包 `ConfigProvider locale={zhCN} theme={appleTheme}`（`@chips/ui`）；
2. 在 `editor/runtime.ts` 中处理容器尺寸、根节点样式与清理；
3. 把局部输入节流、富文本清洗等逻辑收口在插件内部；
4. 通过 `onChange` 输出新的配置快照。

编辑器约束：

- 不直接调用 `CardService`、Bridge 写文件或其他持久化接口；
- 不把卡片切换、会话 flush、防抖提交职责写进插件；
- 不要求宿主必须提供 iframe 事件桥；
- 资源型编辑器应优先使用宿主提供的 `resolveResourceUrl/releaseResourceUrl/importResource/importArchiveBundle/deleteResource/convertTiffToPng/extractVideoThumbnail`；
- 卡片内部资源写回配置时只记录“相对于卡片根目录”的路径；
- 不得把 `blob:`、`data:`、系统绝对路径等运行时 URL 持久化成卡片内部正式资源路径；
- 若需要销毁逻辑，必须通过根节点 cleanup 或显式销毁函数闭环。

## 与宿主链路的关系

### Host 通用链路

- Host 通过 `card.render` 或 `card.renderEditor` 解析插件；
- Host 负责生成正式 iframe 文档与事件协议；
- SDK `compositeWindow/editorPanel` 负责把这些文档交付给应用。

### 官方编辑引擎链路

- 编辑引擎通过 `plugin.query({ type: 'card' })` 读取当前工作区已安装且已启用的卡片插件；
- 编辑引擎只会加载插件 `manifest.entry` 指向的构建产物，例如 `dist/index.mjs`；
- 插件入口模块必须导出 `basecardDefinition`，编辑引擎据此建立运行时描述符注册表；
- `renderBasecardView` 被挂载到编辑引擎自己创建的单卡 iframe；
- `renderBasecardEditor` 被直接挂载到编辑面板 DOM 容器；
- 编辑器会话、防抖提交、自动保存由编辑引擎运行时负责。

重要边界：

- 普通应用和第三方集成不得自行扫描插件目录并直接 import 插件源码；
- 官方编辑引擎允许根据 Host 运行时返回的已安装插件记录加载其构建产物入口，但不得回退到工作区源码扫描；
- 插件实现不能因为某个宿主的例外而破坏通用导出契约。

## 配置数据结构

每种卡片类型都应定义正式的配置 schema。

推荐做法：

- 在 `schema/card-config.ts` 中声明类型；
- 在同文件中提供默认配置；
- 在宿主描述符层完成最终归一与校验；
- 在插件内部只消费“已归一”的配置。

官方标准基础卡片脚手架默认提供以下通用配置基线，具体卡片类型可以在此基础上扩展自己的业务字段：

```ts
export interface BasecardConfig {
  card_type: 'base.example';
  theme?: string;
  title: string;
  body: string;
  locale?: string;
  resource_path?: string;
}
```

默认约束：

- `card_type` 必须与 `basecardDefinition.cardType` 和 `manifest.capabilities.cardTypes[0]` 对齐；
- `title/body` 是标准模板的内容字段，业务卡片可以替换或扩展为自己的配置字段；
- `locale/theme` 是历史保留的配置偏好字段（Host 契约字段），仅存于卡片配置数据中，插件 UI 不再消费，不承担任何主题/多语言运行时职责；
- `resource_path` 只允许卡片根目录内相对路径，不允许绝对路径、`file://`、`blob:`、`data:`、查询串、片段标识或 `..` 路径逃逸；
- `collectResourcePaths(config)` 必须返回配置中所有仍被引用的卡片根目录资源路径，并去重。

示例：

```ts
export interface BasecardConfig {
  card_type: 'RichTextCard';
  content_format: 'markdown';
  content_source: 'inline' | 'file';
  content_text?: string;
  content_file?: string;
  locale?: string;
  theme?: string;
}

export const defaultBasecardConfig: BasecardConfig = {
  card_type: 'RichTextCard',
  content_format: 'markdown',
  content_source: 'inline',
  content_text: '',
  locale: 'zh-CN',
  theme: '',
};
```

富文本基础卡片补充约束：

- 正式持久化内容只能是 Markdown，不得把编辑器运行时 HTML 直接写回配置；
- 纯文本字符数不超过 `200` 时保存到 `content_text`；
- 超过 `200` 时保存为卡片根目录 `.md` 资源文件，并在配置中写入 `content_file`；
- 编辑态悬浮工具框、选区状态等都属于运行时状态，不进入配置。

网页基础卡片补充约束：

- 正式类型标识为 `base.webpage`，运行时别名可以是 `WebPageCard`；
- 正式来源字段只允许两类：远程 `source_url`，或卡片根目录相对网页目录 `bundle_root + entry_file`；
- 当来源为网页 ZIP 包时，编辑器应通过 `importArchiveBundle({ entryFile: 'index.html' })` 让宿主先校验并解压，再把整个网页目录写入卡片根目录；
- `importArchiveBundle(...)` 是通用目录解包能力，不携带面向网页、图片或其他业务场景的开关字段；网页基础卡片的入口约束只通过 `entryFile: 'index.html'` 表达；
- 网页 ZIP 包的正式入口文件必须是 `index.html`；若压缩包只有一个顶层目录且其中存在 `index.html`，宿主会在导入时自动识别载荷根目录并把资源写入最终网页目录；
- 网页包正式配置应同时保存 `resource_paths`，用于宿主持久化阶段重建资源清单和删除旧网页资源；
- 网页基础卡片显示模式分为两类：
  - `fixed`：固定为宽:高 `7:16` 视口，并在窗口内滚动网页内容；
  - `free`：按网页内容高度展开，但最高不超过当前宽度的 `20` 倍；
- 网页基础卡片查看态必须把稳定视口信息传递给嵌入页：
  - 父层到网页的正式消息类型为 `chips:webpage-card:viewport`；
  - 网页包/同源网页应可消费 `window.__CHIPS_WEBPAGE_CARD_VIEWPORT__`、CSS 变量 `--chips-webpage-card-*`，并监听 `chips:webpage-card:viewport-change` 事件；
  - 若嵌入页希望跨源回传自身内容高度，应向父层发送 `chips:webpage-card:content-height`；
- 网页视口协议中的 `height` 表示传递给网页内部的稳定测量视口高度：
  - `fixed`：等于固定比例 `7:16` 对应的正式视口高度；
  - `free`：优先对齐宿主当前真实窗口高度，并限制不超过固定比例高度；父层最终展开后的长卡高度只用于宿主布局，不能再次回写给网页内部，否则会形成测量反馈。
- 网页视口协议中的 `baseHeight` 表示内容暂不可测或回退场景下的最小外层高度。
- 对网页 ZIP 包，官方查看态可注入稳定虚拟视口层，把常见 `vh/dvh/svh/lvh` 高度单位和 `window.innerHeight` 等读取尽量映射到协议视口高度，以降低 `free` 模式下长网页误判窗口高度的风险。
- 若远程网页因为 `X-Frame-Options`、`frame-ancestors` 或等效策略拒绝 iframe 嵌入，卡片查看态只显示正式错误提示，不做降级绕过。

音乐基础卡片补充约束：

- 正式类型标识为 `base.music`，运行时别名可以是 `MusicCard`；
- `audio_file` 是必填字段，且必须记录为相对于卡片根目录的路径；
- `album_cover`、`lyrics_file` 为可选字段；存在时也必须记录为相对于卡片根目录的路径；
- `production_team` 正式结构是数组，每个条目至少包含 `id`、`role`、`people[]`；
- 若编辑器在导入音频时解析到嵌入标题、歌手、专辑、封面或歌词，自动生成的封面与歌词资源仍必须通过 `importResource(...)` 写入卡片根目录，而不是只保留内存对象 URL；
- 对音频内嵌封面，插件不得只信任标签声明的 MIME；必须优先按真实图片字节头识别实际格式；
- 若真实封面格式为 TIFF，插件必须先把源封面作为卡片内部资源导入，再通过 `convertTiffToPng(...)` 生成正式 PNG 文件，并让配置只引用最终 PNG 路径；
- 查看态若拿到了宿主提供的 `openResource(...)`，点击音乐卡片时应通过它表达“打开音频资源”的意图，而不是在基础卡片内部直接启动播放器应用。
- 若音乐卡片希望播放器恢复封面、歌词和卡片级元数据，应把音乐基础卡片的正式播放上下文一起放入 `openResource(...).payload`，而不是让播放器自行猜测卡片目录结构。

评分基础卡片补充约束：

- 正式类型标识为 `base.score`，运行时别名可以是 `ScoreCard`；
- 正式配置至少包含 `style`、`score`、`total_score` 与可选 `locale/theme`；
- `style` 当前正式取值为 `stars`、`hearts`、`score`、`progress`；
- `stars` 与 `hearts` 固定为五分制，未获得的项以灰色状态展示，已获得的项以主题主色或错误色等可主题化色值展示；
- `stars` 与 `hearts` 的编辑器应通过五个可点击项设置 `score`，归一化后 `total_score = 5` 且 `score` 为 `0-5` 的整数；
- `score` 与 `progress` 的编辑器应提供两个数字输入字段：总分 `total_score` 与获得分数 `score`；
- `score` 不得小于 `0`，不得超过 `total_score`，`total_score` 不得小于 `1`；
- 查看态只展示评分数据，不访问资源、不打开其他应用、不承担持久化职责；
- 评分基础卡片查看态不应额外添加最外层卡片描边、背景色或阴影，装配层视觉由宿主与统一视觉规范负责。

电子书基础卡片补充约束：

- 正式类型标识为 `base.book`，运行时别名可以是 `BookCard`；
- 电子书基础卡片用于保存普通电子书资源或 ZIP/CBZ 图片包解包后的图片序列，阅读与图片查看能力由资源打开链路命中的应用插件承担；
- 正式配置至少包含 `source_type`、`book_file`、`book_format`、`book_name`、`book_author`、`cover_image`、`image_sequence`、`image_sort_basis` 与 `resource_paths`；
- 普通电子书文件必须作为卡片根目录相对资源保存到 `book_file`，支持格式可包括 EPUB/EPUB3、PDF、TXT/Markdown、MOBI、AZW/AZW3、FB2、DJVU 等；
- 上传 EPUB/EPUB3 时，编辑器可以解析 OPF 元数据并自动填写书名、作者和封面；解析不到时字段保持空字符串，由 UI 占位文案表达；
- ZIP/CBZ 图片包不得把原压缩包保存为卡片资源；必须通过 `importArchiveBundle(...)` 的 `include` 过滤规则解包后只保留可识别图片资源，非图片条目不进入配置和资源清单；
- 图片包资源应保存到以压缩包名为前缀的卡片根目录相对目录中；若宿主为了避免冲突追加短 ID，配置应以宿主返回的最终相对路径为准；
- 图片包导入时应传入 `stripSingleRootDir: true` 和 `excludeSystemArtifacts: true`，使常见单顶层目录包、`__MACOSX`、`.DS_Store`、`._*` 等系统噪声被通用解包层统一处理；
- 图片包排序依据为 `filename` 或 `entry-time`；当 ZIP 条目时间缺失或不可区分时，必须稳定回退文件名排序；
- 图片包默认把排序后的第一张图片写入 `cover_image`，用户上传自定义封面后可覆盖该引用；
- `collectResourcePaths` 必须返回 `book_file`、`cover_image`、`image_sequence[*].file_path` 与 `resource_paths` 中全部有效内部资源路径，并去重；
- 替换普通电子书、封面或图片包时，旧配置中不再被引用的内部资源必须通过 `deleteResource(...)` 登记删除；
- 查看态若拿到了宿主提供的 `openResource(...)`，普通电子书点击时以 `book_file` 为主资源，图片包点击时以排序后的第一张图片为主资源；传入 `openResource.resourceId` 与 `payload.resources.*.resourceId` 的值均应是卡片根目录相对路径，实际可读 URL 或 Host 托管资源标识由外层运行时归一到顶层 `resourceOpen.resourceId`；
- 电子书基础卡片传递的业务 payload 正式形状如下，Host 只透传，不解释业务字段：

```ts
interface BookOpenResource {
  resourceId: string;
  relativePath: string;
  fileName?: string;
  mimeType?: string;
}

interface BookCardOpenPayload {
  kind: 'chips.book-card';
  version: '1.0.0';
  cardType: 'base.book';
  mode: 'ebook' | 'image-sequence';
  resources: {
    book?: BookOpenResource;
    images?: BookOpenResource[];
  };
  display: {
    title: string;
    author?: string;
  };
}
```

## 资源引用

渲染组件可能需要引用卡片文件中的资源。

正式约束：

- 相对路径资源必须相对于卡片根目录解析，并通过 Host/Bridge/SDK 的 `resolveResourceUrl` 获取正式运行时 URL；Electron 桌面端可返回 `chips-render://card-root/...`，调用方不得自行构造 `file://` 基址或假定固定 URL scheme；
- 卡片内部资源路径统一从卡片文件根目录开始记录，不相对于 `content/`；
- 插件不直接假定自己拥有文件系统权限；
- 资源 URL 的生成由 Host 或宿主运行时完成，不由渲染组件私自拼系统绝对路径。

编辑态补充：

- Host 托管编辑器链路中，资源操作通过正式 `chips.card-editor:resource-*` 协议和 SDK `resources` 桥接完成；
- `importResource(...)` 返回的 `path` 必须是卡片根目录相对路径；
- `importArchiveBundle(...)` 是通用压缩包目录导入能力，只表达目录落位、入口文件、过滤规则、单根目录剥离和系统噪声排除，不接受面向具体卡片类型的开关字段；
- `entryFile` 表示“必须存在的入口文件”，适合网页包等入口型目录；未传 `entryFile` 时，宿主按 `include` 规则导入符合条件的文件集合；
- `include.mimeTypes/extensions` 是保留条目过滤规则；过滤不通过的条目进入 `discardedEntries`，不得写入配置引用；
- `entries` 返回每个最终导入条目的原始 ZIP 路径、最终卡片根目录相对路径、MIME、大小、CRC、压缩方式、目录标记和 `modifiedTime`；
- `discardedEntries` 返回目录、系统噪声、过滤不匹配和不安全路径等未导入条目，供编辑器日志、提示和后续审计使用；
- `convertTiffToPng(...)` 只允许输入卡片根目录内的相对资源路径，并返回最终 PNG 的相对路径；
- `extractVideoThumbnail(...)` 只允许输入卡片根目录内的视频相对资源路径，并返回最终封面图的相对路径；失败时编辑器不得撤销已经完成的视频导入；
- `releaseResourceUrl(...)` 用于释放 `blob:` 等临时资源 URL；
- 若宿主未提供资源桥接，而当前编辑器又必须依赖内部资源操作，应显式报错，不得私接文件系统。

标准脚手架中的资源桥接线如下：

- 查看态 `BasecardRenderContext` 可消费 `resolveResourceUrl/releaseResourceUrl/openResource`；
- 编辑态 `BasecardEditorContext` 可消费 `resolveResourceUrl/releaseResourceUrl/importResource/importArchiveBundle/deleteResource/convertTiffToPng/extractVideoThumbnail`；
- 编辑器导入资源时只能把宿主返回的 `path` 写回配置；
- 删除资源时先调用宿主 `deleteResource(resourcePath)`，成功后再清空配置引用；
- 查看态通过 `openResource(...)` 只表达资源打开意图，业务上下文放入 `payload`，Host 只负责透传；
- 任何运行时 URL 只能用于当前渲染会话，不得保存到配置文件。

## 生命周期管理

卡片插件必须具备完整生命周期：

- 初始化阶段：创建 DOM、绑定事件、同步初始配置；
- 更新阶段：由宿主重新挂载或推送新配置；
- 销毁阶段：清理事件监听、定时器、编辑器实例和临时节点。

禁止事项：

- 把全局事件监听遗留在页面上；
- 依赖浏览器刷新才能释放状态；
- 把 cleanup 留成空实现或未收口实现。

标准脚手架要求查看态和编辑态都支持重复挂载：

- 新挂载前先执行同一容器上一次保存的 cleanup；
- cleanup 必须卸载 React root，并清空由本次挂载创建的 DOM；
- 编辑态如修改 `html/body/container` 的内联尺寸或 overflow，应在 cleanup 中恢复原值；
- 查看态通过 Host 解析过资源 URL 时，应在 cleanup 中调用 `releaseResourceUrl(resourcePath)`。

## 主题适配

卡片插件视觉统一为苹果风格单一主题，不接入主题运行时。

正式要求：

- 颜色、边框、文本色统一来自 antd token（`theme.useToken()`）或苹果风格色值常量（`#f5f5f7` / `#1d1d1f` / `#0a84ff` / `#6e6e73` 等），查看态与编辑态使用同一套视觉（`ConfigProvider theme={appleTheme}`）；
- 查看态 `BasecardRenderContext.themeCssText` 作为宿主契约字段保留、不消费；插件只注入插件自有样式，不再渲染主题 CSS 与 token variables；
- 图标统一使用 `@ant-design/icons`，不打包任何字体图标体系；
- 用户可见文案简体中文直写，运行时不保留 i18n key（`src/lib/messages.ts` 集中管理中文文案映射）。

## 错误处理

卡片插件需要处理以下错误：

- 配置字段缺失或非法；
- 资源加载失败；
- 编辑器实例初始化失败；
- 富文本或嵌入内容需要清洗时的安全问题。

要求：

- 错误应局部隔离在当前基础卡片范围内；
- 不抛出会让宿主整页崩溃的未处理异常；
- 对用户可见的错误信息应尽量可理解。

## 测试策略

卡片插件需要至少覆盖以下测试：

- 查看态挂载测试；
- 编辑态挂载测试；
- 配置归一与校验测试；
- cleanup 与重复挂载稳定性测试；
- 在 Host 通用链路中的集成测试；
- 在编辑引擎本地运行时中的集成测试。

链路补充测试要求：

- 验证通过 SDK `compositeWindow/editorPanel` 调用时，插件在 Host 托管链路中行为正确；
- 验证通过编辑引擎本地运行时挂载时，单卡 iframe 预览与编辑器会话行为正确；
- 同一份插件导出在两条正式链路中的主题适配结果应保持一致。

其中 `verify` 必须串联 `lint/typecheck/test/build/validate/package`。生成工程的 `vitest.config.mts` 应对 `react` 与 `react-dom` 做别名和去重，避免 workspace 链接 `@chips/ui` 与 antd 时出现多份 React 实例。
