# 测试策略与质量门禁设计

> 文档状态：设计基线稿  
> 目标：定义 `Chips-SDK` 的测试层级与质量门禁，确保交付质量

---

## 1. 测试层级

### 1.1 单元测试

- 覆盖对象：
  - Core Client 逻辑（环境探测、错误归一、重试）。
  - 各能力域封装的参数校验与结果映射。
  - 工具函数（契约校验、性能采样等）。

### 1.2 契约测试

- 覆盖对象：
  - SDK 封装的动作名与 Host `route-manifest` 的一致性。
  - Host descriptor manifest 与 SDK `src/contracts/route-manifest.json` 的 `action/schemaIn/schemaOut/permission/timeoutMs/idempotent/retries` 元数据一致性。
  - SDK route manifest 中公开动作必须由 SDK Domain API wrapper 覆盖；Host 内部握手动作必须进入显式排除清单，禁止被误暴露成普通公共 SDK API。
  - 错误码映射是否保持原样（除包装外不更改语义）。

### 1.3 集成测试

- 覆盖对象：
  - 使用模拟 Host/Bridge 环境的 end-to-end 调用。
  - 在具备真实 Host 环境时，执行少量烟雾测试。

### 1.4 SDK Testing Helper

- `src/testing/index.ts` 是 SDK 的正式测试辅助入口，对外通过 `chips-sdk/testing` 导出。
- `createMockChipsHost()` 提供 Host simulator，覆盖调用记录、状态、事件总线、action handler、fault、delay 与权限拒绝。
- `createMockChipsClient()` 必须通过真实 `createClient()` 创建 SDK client；默认安装测试用 `window.chips`，用于覆盖 plugin Bridge 和 `platform.getLaunchContext()` 读取路径。
- 当测试需要 SDK timeout/retry 时，可使用 `installBridge: false` 让 client 走 custom transport。
- 测试辅助不得 import Host 主运行时实现，不得复制 KernelRouter、service registry 或 Runtime Client，只能模拟公开 action 与事件契约。

## 2. 测试用例规划

### 2.1 Core Client

- 环境探测：
  - `plugin` 环境（存在 `window.chips`）。
  - 浏览器环境（无 `window.chips`）。
  - Node 环境（无 `window`）。
- 错误归一：
  - 标准错误对象透传。
  - 原生 `Error` 与字符串包装。
- 重试策略：
  - 可重试错误的重试次数与退避间隔。

### 2.2 能力域封装

- `file/card/box/resource`：
  - 正常路径：基础操作成功。
  - 错误路径：文件不存在、格式错误等。
- 统一卡片显示链路：
  - 合法/非法 `mode`。
  - 事件协议触发与 origin 过滤。
- `theme/config/i18n/plugin`：
  - 各 API 功能行为。
  - 权限不足错误处理。

### 2.3 Testing Helper 用例

- `theme.getCurrent/apply`：通过 mock Bridge 调用真实 SDK API，并验证 `theme.changed` 事件。
- `i18n.getCurrent/setCurrent/translate/listLocales`：验证响应解包与 `language.changed` 事件。
- `platform.getLaunchContext()`：验证 mock Bridge 安装后走 preload 同形读取路径。
- `surface.open/list/getState`：验证 surface context fixture 与响应解包。
- `command.register/list/invoke/setState`：验证调用记录与 `command.*` 事件。
- 权限异常：通过 `setPermissionDenied()` 生成标准错误，验证 SDK 归一后的 `permission.required/granted/messageKey`。
- timeout/retry：通过 mock delay/fault 触发 SDK 超时与重试逻辑。

### 2.4 CLI Tooling 用例

- `chipsdev-r preview --json`：覆盖 `chips.config.mjs`、`manifest.yaml`、`runtime.targets`、`ui.surface` 与 Host mock/real Host 预览计划输出。
- `chipsdev-r component gallery --json`：覆盖组件库 contract、token 构建产物、组件矩阵和 quality/perf 摘要读取。
- `chipsdev-r theme inspect --json`：覆盖主题包 manifest、entry、contract、min functional set、主题 token 层级合成与 required token 覆盖诊断。
- `chipsdev-r quality gate --json`：覆盖项目状态、SDK route manifest、组件库 quality/perf 报告和主题检查摘要。
- `chipsdev-r assimilate scan/report --json`：覆盖外部 Web 项目框架识别、Host 能力风险、硬编码样式/文案、组件替换建议、manifest 建议和 report 迁移计划。
- `chipsdev-r diagnostics --json`：覆盖 route namespace/permission 摘要与前述报告汇总。
- `--out <file>`：至少覆盖一个报告命令的 JSON 落盘，确保人读输出与机器读报告可以同时消费。

## 3. 质量门禁

### 3.1 本地门禁

- `npm test`：Vitest Domain API / route manifest 契约测试与 CLI / 脚手架集成测试全部通过。
- `tests/run-cli-tooling-tests.cjs` 已纳入 `npm test`，用于锁定开发者报告命令的 JSON 结构与同化扫描行为。
- `npm run lint`：无 lint 错误。
- 性能基线脚本：封装层额外开销在阈值之内。

### 3.2 CI 门禁

- 在 CI 中执行：
  - 单元测试（覆盖率门槛）。
  - 契约漂移检测。
  - 性能基线采样（关键路径）。

### 3.3 发布前检查

- 所有测试通过。
- 契约漂移工单（如有）已闭环。
- 统一卡片显示链路 E2E 场景已通过。

---

## 4. 小结

本文件定义了 `Chips-SDK` 的测试层级、用例规划与质量门禁要求。实现时应优先建立测试基线，再逐步实现功能，以避免后补测试与质量滑坡。
