# 迁移总体架构设计

> 文档状态：待审核基线稿
> 设计原则：保留旧项目正确业务能力，替换旧底层运行方式，完全对齐新薯片生态正式架构

---

## 1. 项目定位

`Chips-EditingEngine` 在新生态中的定位不是独立桌面软件，而是运行在 `Chips-Host` 内部的编辑引擎应用插件：

- 类型：`type: app`
- 运行载体：`Chips-Host`
- 系统能力入口：`window.chips.*` / `chips-sdk`
- UI 基线：`@chips/component-library` + 主题系统 + 多语言系统

这意味着本项目只负责“编辑引擎业务编排与交互壳层”，不再承担主机、桥接主实现、原生窗口底层、文件系统底层等职责。

## 2. 迁移架构原则

### 2.1 中心路由与 Bridge 隔离

- 所有系统能力都必须经由 Host 路由与 Bridge。
- 本项目禁止直接调用 Node API、Electron 私有对象或 Host 私有模块。

### 2.2 底层厚、上层薄

- 文件解析、卡片渲染、窗口原生控制、主题广播、语言广播等公共能力尽量复用 Host。
- 编辑引擎聚焦业务编排：工作区状态、布局切换、工具窗口状态、命令和工作流。
- 文档写入优先复用 Host 提供的低层 `file.*` / `zip.*` 能力；不要求 Host 为每个编辑动作都提供一条细粒度业务 route。

### 2.3 契约优先

- 文件、窗口、主题、多语言、设置、插件、卡片链路全部以生态正式文档为准。
- 若文档与代码冲突，不得自行脑补第二套契约。

## 3. 目标分层

### L1 外部生态层

- `Chips-Host`
- `chips-sdk`
- `@chips/component-library`
- 生态主题、多语言、基础卡片、布局与模块插件

### L2 项目基础适配层

职责：封装生态公开能力，向业务域提供稳定适配接口。

建议模块：

- `bridge/`：对 `window.chips.*` 或 `chips-sdk` 的统一访问封装；
- `runtime/`：主题、多语言、日志、错误边界、事件总线适配；
- `contracts/`：项目内使用的类型、DTO、错误码映射。

### L3 核心业务域层

职责：承载编辑引擎正式业务能力。

建议模块：

- `workspace-domain/`
- `file-domain/`
- `card-package-domain/`
- `editor-domain/`
- `layout-domain/`
- `window-domain/`
- `settings-domain/`
- `command-domain/`
- `drag-domain/`

### L4 应用壳层与表现层

职责：React 页面结构、组件树、工具窗口壳层、布局容器、错误提示、加载态等。

## 4. 旧项目到新项目的重构边界

### 4.1 上层迁移总策略

- 迁移顺序改为“先复制旧项目上层正确实现，再替换底层依赖并完成重构”，不再以全新界面重新发明旧能力。
- 旧项目 `归档/Chips-Editor` 中已经被验证正确的布局语义、窗口模型、状态模型、工具面板职责、交互流必须优先保留。
- 新项目中已完成的 React 壳层、运行时 Provider、`card-package-domain`、Host / SDK 低层适配，定位为新生态底座；后续上层迁移必须建立在这层底座之上，而不是替代旧项目上层产品语义。
- 用户体验目标是“迁移后仍然像原来的编辑器”，差异仅允许出现在底层接口、运行时挂载方式、主题/i18n 接入与正式工程结构。

### 4.2 可迁移内容

- 业务规则；
- 用户工作流；
- 功能划分；
- 旧项目中已经稳定的窗口布局和状态语义；
- 测试场景；
- 旧项目中与具体运行时无关的状态模型和交互模型。

### 4.3 必须重写内容

- Electron 主进程与 preload；
- 旧版 connector 和本地 bridge；
- 旧版窗口、文件、主题、多语言直接实现；
- 任何依赖旧基础层的直连调用。

## 5. 迁移后的核心子系统

### 5.1 应用壳层系统

负责：

- Host 启动后应用初始化；
- 主题和语言上下文挂载；
- 工作区级错误边界和加载态；
- 布局路由与工具窗口容器。

### 5.2 工作区系统

负责：

- 当前工作区状态；
- 已打开文件集合；
- 当前激活对象；
- 脏状态、保存队列、会话上下文。

### 5.3 编辑系统

负责：

- 复合卡片编辑流程；
- 基础卡片编辑面板装载；
- 选中、锁定、顺序调整；
- 与撤销重做系统协同。

### 5.4 布局系统

负责：

- 无限画布和工作台两种正式布局；
- 工具窗口与主内容区协作；
- 布局切换时的状态恢复。

### 5.5 文件系统适配层

负责：

- 打开/新建/保存/导入/导出动作的 Host 调用封装；
- 文件对话框；
- 外部拖拽文件输入的识别和路由；
- 基于 `file.*` / `zip.*` 的文档级写入事务。

## 6. 当前首版架构决策

1. 继续以 React 作为新生态正式承载技术栈，但迁移方式不是重写旧产品，而是把旧项目上层模型和交互语义逐步映射到 React 壳层。
2. 先冻结 Host / SDK / file.* / zip.* / theme / i18n 等底层契约，再把旧项目的窗口系统、双布局、工具面板、卡片工作流迁入新仓库。
3. 旧项目上层 TypeScript 类型、状态模型、窗口管理语义优先保留并复制入新仓库，再做适配重构。
4. 先保证旧项目双布局与工具窗口主链路在 Host 内闭环，再补高级能力与体验微调。
5. 任何底层缺口一律通过工单推动生态修复，不在本项目内打补丁绕过。

### 5.6 卡片包治理系统

负责：

- `.card` 临时解压目录创建与清理；
- `metadata.yaml`、`structure.yaml`、`content/*.yaml` 的读写编排；
- 基础卡片新增、删除、重排；
- 编辑 / 查看模式切换持久化；
- 打包完成后的预览刷新与错误回滚。

该层是 EditingEngine 迁入新生态后的关键差异点：Host 只提供宽松、较底层的能力面，编辑引擎自身承担正式文件格式编排责任。
