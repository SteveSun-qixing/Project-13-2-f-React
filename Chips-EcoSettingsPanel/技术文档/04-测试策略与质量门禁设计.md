# 测试策略与质量门禁设计

## 1. 测试分层

### 1.1 单元测试

覆盖纯函数与视图模型映射：

- 菜单注册表排序与过滤
- Scene 注册表与 command metadata 稳定性
- 主题 / 插件 / 语言 DTO -> ViewModel 映射
- 权限、状态、按钮可用性判定
- 错误归一化与消息映射

### 1.2 组件测试

覆盖页面壳层与功能组件：

- 左侧菜单切换
- `AppRoot/AppProviders/AppRuntimeProvider/AppShell` 根组件结构
- 桌面侧栏导航与窄屏切换器是否消费同一套 command 入口
- 页面壳层和治理列表应断言组件库正式结构，例如 `navigation-split-view`、`data-grid`，并明确排除当前壳层已移除的 `toolbar`、`menu-bar`、`command-palette` 顶部命令区。
- 组件展示、主题诊断和预览质量页面应断言共享页面布局结构，例如 `settings-page-stack`、`settings-page-section`、`settings-card-grid`、`settings-summary-panel`、`settings-metric-card__value`，并明确排除旧的页面私有壳层 class。
- 设置面板私有 CSS 应通过测试明确排除旧蓝色导航色块、`settings-card-grid--bento`、`table/thead/tbody` 显示模型覆盖和旧硬编码字体 / 色值，确保业务层只承担布局、密度和组合样式。
- 列表空状态、加载态、错误态
- 操作按钮的可用/禁用条件
- 设置条目列表的详情入口是否存在，点击后是否进入带左上返回按钮的二级详情页，且治理详情不再渲染弹窗
- 组件展示页分组渲染
- 主题诊断页是否展示当前主题 Contract/resolve 诊断 view model
- 预览与质量页是否只展示正式 `chipsdev-r` 报告入口，不出现私有目录读取口径

### 1.3 集成测试

通过 mock Bridge / mock SDK 客户端验证：

- 安装主题 / 插件后页面状态刷新
- 主题切换后事件驱动更新
- 语言切换后的文案刷新
- 插件启用/停用/卸载的完整流程

### 1.4 端到端验证

在真实 Host 开发态至少验证：

1. 应用窗口可正常打开。
2. 主题安装、切换、卸载成功。
3. 语言切换后界面立即刷新。
4. 应用插件安装与停用成功。
5. 组件展示页能随主题变化刷新。

## 2.1 权限不足与 Host Smoke 基线

设置面板的权限测试使用 `chips-sdk/testing` 正式 mock Host，不在本项目内私造 Host/Electron/Bridge 运行时。

当前 028.05 后的权限与 smoke 覆盖要求：

- `runtime-permissions.test.ts` 使用 `setPermissionDenied(...)` 注入 SDK 标准 `PERMISSION_DENIED`，覆盖主题读取/写入、语言写入、插件治理、平台对话框、系统显示位置等关键路径；
- `settings-commands.test.tsx` 覆盖 `command.register` 与 `command.invoke` 被拒绝时 `useSettingsCommands()` 进入明确错误态，并保留 `PERMISSION_DENIED`；
- `runtime-hooks.test.tsx` 覆盖 `theme.apply` 和 `i18n.setCurrent` 被拒绝时不本地伪造主题/语言状态，列表仍以 Host 重新返回的数据为准；
- `host-smoke.test.ts` 通过 mock Host 执行设置面板正式 action 序列：Scene command 注册、主题切换、主题诊断、语言切换、应用插件查询、文件选择、快捷方式创建/删除、显示位置和 command invoke；
- `basic-flow.test.ts` 比对 `manifest.yaml`、`src/app/settings-permissions.ts` 与 SDK route manifest，防止权限清单与实际 action 消费漂移。

## 3. 回归清单

每次功能迭代后至少回归以下场景：

- 当前主题标识是否正确
- 当前语言标识是否正确
- AppRuntime 是否能从 Host launch context / surface context 派生当前 scene、surface、session 和 launchParams
- Scene 命令是否声明 i18n key、IconDescriptor、handlerId、Host command placement，不包含原始文案字段
- `manifest.yaml` 是否包含 `command.read`、`command.write`、`command.invoke`
- 列表排序和筛选是否稳定
- 当前设置面板插件是否被正确标识为不可停用/卸载
- 三类治理页是否保持正式设置条目列表布局且每条记录都有详情入口
- 治理列表是否继续通过 `ChipsDataGrid` 正式结构渲染行和单元格，列表是否只保留几个常用动作，完整字段、危险操作和低频操作是否进入二级详情页
- 设置详情页是否提供左上返回按钮，返回后保持当前 Scene 列表，不使用弹窗承载治理详情
- 组件展示页是否通过共享 `ShowcaseCardGrid` 保持 `hero / wide / standard` 卡片强调级别，主题诊断页和预览质量页是否通过共享 `SummaryPanel / CardGrid / MetricCard / CardDescription` 组织重复页面结构
- 私有样式是否仍以主题 token 与组件 contract 派生变量为基准，不恢复左侧菜单大面积蓝色按钮、表格显示模型覆盖或组件展示页旧 Bento class
- 三类治理页正常态是否不再出现错误边界红色外框
- 主题与插件安装失败时是否有可读反馈
- 组件展示页是否仍覆盖全部正式组件分组
- Host 事件订阅在页面重渲染后是否保持稳定且仍能刷新最新状态
- 主题诊断入口是否只调用 `theme.contract.get()` 与 `theme.resolve([])`
- 预览与质量入口是否保持为正式 `chipsdev-r` 命令清单，不读取私有文件路径
- 权限不足错误是否显示为统一 `SettingsPanelError`，并保留标准 `permission` 诊断字段
- 设置面板 Host smoke 是否仍只走 SDK/Bridge 正式 action 序列，不访问 Host 私有模块
