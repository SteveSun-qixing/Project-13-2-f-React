# 工单034：文档解析 Neon 导出面缺「源指纹」与「箱子布局配置」载体，`IDocumentParserPort` 无法完整对接

> 登记：W2 金链路刀2（任务 #89，TS 解析端口适配器契约先行）
> 日期：2026-09-21

## 一、问题

`packages/host/src/capabilities/document/ports.ts` 的 `IDocumentParserPort`（:124-139）要求解析端口提供两项数据面：

1. **源指纹**：`open()` 返回 `IDocumentParseOutcome.fingerprint: ISourceFingerprint`（:75，路径+尺寸+修改时间+归档 CRC 的成员指纹集合，`digest.ts` :19-33），`fingerprint(localPath)`（:134）为保存前基线复查的重取入口（`service.ts` :544 assertWritable、:727 rebuildAfterCommit 直接消费）。口径权威为《06-文档解析器设计》§5.4（目录态 = 尺寸+修改时间；压缩态 = 尺寸+CRC32+修改时间）。
2. **箱子布局配置切片**：`readPart(handle, { part: 'content' })`（不带 `nodeId`）是箱子 `.box/content.yaml` 布局配置的读取路径（`service.ts` :201 `ensureLayoutConfig` 直接消费；`ports.ts` :103-104 注明「箱子 `.box/content.yaml` 布局配置」）。

而 chips-native 文档解析域的冻结 Neon 导出表——《06-文档解析器设计》§12.1 十二项 + 《03-核心接口规范》§6.4 补 `buildDocumentView` 共 13 项（`openDocument / openCard / openBox / documentMetadata / documentStructure / documentContent / documentEntries / documentReadResource / documentValidate / buildDocumentView / documentClose / createCancelToken / cancelTokenCancel`，另见《03-核心接口规范》§8.6 导出总表「文档解析」行）——**没有任何一项返回数据源指纹或修订信息，也没有任何一项返回箱子布局配置**：

- Rust 侧两个载体均已存在且公开：`DocumentHandle::revision() -> DocumentRevision`（内含 `SourceFingerprint { kind, members: Vec<(PackagePath, MemberFingerprint{size, modified_millis, crc32})> }`，见 `crates/chips-parser/src/parser/mod.rs:333`、`src/model/mod.rs:575-582`、`src/source/mod.rs:57-86`）与 `DocumentHandle::layout_config()`（`crates/chips-parser/src/parser/mod.rs:240`，文档面注记见《06-文档解析器设计》§5.2 v1.0.1）。§12.1 明文「所有访问器函数与 Rust 方法一一对应」，但导出表未兑现这两项。
- `MetadataResult / StructureResult / ContentResult / EntriesResult` 统一信封为 `{ kind, value, diagnostics }`（§12.1），不携带指纹；`ValidationReport`（§6.5）与 `DocumentStatistics`（§3.7）亦无成员指纹字段。
- TS 侧无法在不违反架构红线的前提下自行补齐：源指纹口径权威在解析器 `DocumentSource::fingerprint()`（§4.1 / §5.4），归档态需要读 ZIP 中央目录（CRC32），宿主侧自行做 `.card`/`.box` 字节级解析违反工单015 口径与 `service.ts` 头注红线（「本模块不做任何 .card/.box 字节解析」）；资源端口 `listMembers` 只交付字节、不含修改时间与 CRC，且读资源字节违反「快速指纹不读取资源字节」（《11-文档服务设计》§5.5）。

顺带登记同表第三处口径空洞：`createCancelToken / cancelTokenCancel` 产出的 CancelToken 在 13 项导出中**没有传参位**（`openDocument(path, options?)` 的 `ParseOptions` 公开面（§6.1）不含 token 字段），§12.1 所述「解析线程在阶段边界检查取消标志」的传递通道在导出表上未闭合。

## 二、影响范围

- 金链路刀1（任务 #90，`packages/native` 13 导出落地）：照 13 项逐字落地后，刀2 适配器（`src/capabilities/document/adapters/native-parser.ts`）的 `fingerprint` 臂与箱子 `readPart('content')`（布局）臂无原生载体，`open()` 返回信封的 `fingerprint` 字段同样无源。
- 金链路刀4（组合根接线）与刀5（编辑回流）：`document:write` / `document:save` 的基线复查（`assertWritable`）与保存后句柄重建（`rebuildAfterCommit`）必然失败，W2 金链路闭环口径「打开→解析→渲染→内存编辑」在 write 一环断裂。
- 渲染路刀3（`buildDocumentView`）不受影响。
- serialize 臂的落盘序列化归属已由主智能体裁归 W3 chips-resource 波（《重构大计划/W2-开工波次计划.md》「金链路集成七刀定案」刀6），不在本工单范围；本适配器已按该裁决以登记码诚实失败实现。

1. 冻结导出表三处原文：《06-文档解析器设计》§12.1 表（v1.0.0，2026-09-19）、《03-核心接口规范》§6.4 表（13 行含 `buildDocumentView`）、§8.6 总表「文档解析」行——逐字核对无指纹/修订/布局访问器。
2. Rust 公开面：`chips-ecosystem/packages/core-rust/crates/chips-parser/src/parser/mod.rs` 的 `pub fn revision()`、`pub fn layout_config()`（行为测试 `crates/chips-parser/tests/pipeline_error_codes.rs`）。
3. 消费点：`packages/host/src/capabilities/document/ports.ts:75/:134`、`service.ts:175/:201/:222/:544/:727`。
4. 宿主指纹口径：`digest.ts` `ISourceFingerprint`/`computeQuickFingerprintDigest`、《11-文档服务设计》§5.5/§7.1、《06-文档解析器设计》§5.4。

## 四、复现步骤

1. 按 §12.1/§6.4 逐字实现 13 项 Neon 导出（刀1 口径）。
2. 以 `createNativeDocumentParserPort(module)` 构造适配器并调用 `fingerprint('/path/any.card')` 或 `readPart(handle, { part: 'content' })`（箱子句柄、不带 nodeId）。

## 五、期望行为（裁定请求）

按《03-核心接口规范》§8.6「导出表只增不改」规则增补两项文档解析域导出（命名按 §12.1 camelCase 规则自 Rust 访问器机械导出），并同步三处表（§12.1 / §6.4 / §8.6）与刀1 落地、`export-surface.json`、`.d.ts`：

1. `documentRevision(handle)` → `Promise<DocumentRevisionResult>`，JS 形状建议逐字冻结为
   `{ source: { kind: 'directory' | 'archive', members: ReadonlyArray<{ path: string; size: number; modifiedMillis: number | null; crc32: number | null }> }, chipStandardsVersion: string, indexDigest: string }`
   （`modifiedMillis`/`crc32` 对应 Rust `Option` → `null`；刀2 适配器 `native-parser.ts` 的 `INativeDocumentRevision` 类型视图已按此形状冻结，双源不漂移由 `tests/document-native-parser-adapter.test.ts` 的 §6.4 表锁与本文件比对锁定）。
2. `documentLayoutConfig(handle)` → `Promise<StructureResult 同形信封 { kind, value, diagnostics }>`（对应 `layout_config()`；卡片句柄误用按 §5.2 注记返回 `DOCUMENT_FORMAT_UNKNOWN`）。
3. CancelToken 传参通道：在 `openDocument/openCard/openBox` 的 `options`（或后续签名增补位）明确 token 传递语义，或明文注记「Neon 侧取消仅经宿主 signal 预检、在途取消暂不可达」。

## 六、暂行处理（刀2 本轮交付口径，非绕过实现）

- 适配器注入面 `INativeDocumentParserModule` 声明 = 13 项冻结名 + 上述两项按 §12.1 命名规则机械导出的待裁名（`documentRevision`、`documentLayoutConfig`），装载闸 `NATIVE_DOCUMENT_PARSER_REQUIRED_EXPORTS` 同口径 fail-closed：本单落地前，任何按 13 项旧表构建的产物在装载点即被判 `surface-mismatch` 并逐项点名缺位导出（防静默降级）。
- 适配器 `fingerprint` / `open().fingerprint` / 箱子布局臂全部经这两项导出取数，不引入任何宿主侧字节解析临时实现。
- `serialize` 臂按刀6 裁决以登记码 `BRIDGE_CAPABILITY_NOT_FOUND`（`@chips/bridge` 错误码表在册）诚实失败，不进入本工单。
- 本工单收口（两导出名入表 + 刀1 落地）后，刀4 组合根接线前无需改动本适配器签名；若裁定改名或改形状，仅需改 `adapters/native-parser.ts` 类型视图与映射单点。
