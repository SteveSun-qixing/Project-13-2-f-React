# 11 风险、决策和工单关系

## 1. 必须由用户确认的决策

| 编号 | 问题 | 本方案建议 | 原因 |
|---|---|---|---|
| D1 | 第一阶段 `antd + @chips/ui` 是否冻结为正式前端基线 | 建议确认 | 当前代码已采用，但共用文档仍是旧口径；不确认就不能继续扩展公共 API |
| D2 | 是否重新开放 Theme Package 安装 | 建议保留 Host Runtime + 轻量 Recipe，外部安装可开关 | 保留原始生态扩展能力，同时让普通作者不接触运行时细节 |
| D3 | 应用是否允许直接使用 antd 叶子组件 | 建议允许，生态组合经 `@chips/ui` | 避免为 100 个控件重复包一层，同时保持版本和主题统一 |
| D4 | 是否引入额外状态/表格/拖放库 | 建议按真实缺口逐项选型 | 未测量前增加依赖只会转移复杂度 |
| D5 | 是否采用 `app-minimal` 和 `app-standard` 双模板 | 建议采用 | 单一巨型模板导致简单应用背负工作台复杂度 |
| D6 | 应用默认是否继续支持多语言资源 | 建议默认中文、按需生成 locale | 去掉运行时样板不等于删除 key、a11y 和治理能力 |

## 3. 风险清单和控制措施

### R1：第一阶段迁移未完全收口

**表现**：active 仓库仍有旧 import、旧模板或被迁移过程中生成的临时文件。

**控制**：M0 建立 active/归档清单；每批 build 前执行残留审计、Manifest 对照和 `verify:workspace`；发现非本任务范围改动时保留并登记，不擅自覆盖用户文件。

### R2：为追求简单而误删正式能力

**表现**：将 i18n、主题、command、Bridge 等能力全部从 SDK/Host 删除，导致治理应用和跨平台 surface 失去正式入口。

**控制**：区分“应用默认不接线”和“Host/协议能力删除”。普通 app 走门面，治理 app 仍使用 typed API；公共能力删除必须另立架构决策。

### R3：`@chips/ui` 变成新的巨型组件库

**表现**：所有 antd 组件重新包装，加入业务页面、私有数据模型和一堆布尔 props。

**控制**：直接消费 antd 稳定叶子；只有跨应用重复或生态特有能力进入 `@chips/ui`；采用 compound/explicit variant；新增组件必须有质量矩阵和真实消费方。

### R4：第三方依赖把复杂度转移到 Host

**表现**：引入新的状态机、Portal、拖放或样式运行时，增加 CSP、包体和 Electron 差异。

**控制**：逐包选型，做许可证/维护/安全/包体/跨端实测；adapter 隔离；长期运行时依赖先征求用户确认；没有实际缺口不引入。

### R5：主题 Recipe 仍然泄漏 CSS 实现细节

**表现**：Recipe 最终变成 100 个 override 文件，作者仍需了解组件 DOM 私有结构。

**控制**：语义 token 优先；override 只允许登记的公共 token/part/state；编译器拒绝未知选择器；预览矩阵展示缺口；主题包禁止业务 CSS。

### R6：默认 Apple 主题和外部主题产生双轨

**表现**：`@chips/ui` hardcode 一套颜色，Theme Runtime 注入另一套 CSS，两个来源互相覆盖。

**控制**：单一主题解析入口；默认 Apple 也由同一 Recipe/生成配置产生；`ConfigProvider` 和 Host CSS 的优先级、scope、版本写入测试；应用不得私改 token。

### R7：文档再度漂移

**表现**：代码先改、文档最后补，社区开发者看到旧示例。

**控制**：M0 先建立公共文档差异表；脚手架模板 README 与正式共用文档使用同一最小示例；CI 检查示例可生成/可 typecheck；公共契约变更必须同步 issue、实现、测试和文档。

### R8：质量门禁名义通过

**表现**：静态扫描/契约矩阵显示绿色，但真实 Dialog、focus、surface 或 iframe 失败。

**控制**：Playwright、axe、Host run、Theme install、性能报告作为必选出口；每个失败保留 trace/screenshot/route log；禁止降低门禁替代修复。

## 4. 不做事项

- 不在应用中保留“暂时替代”的私有基础控件；确有缺口先建工单。
- 不将 `Chips-Host` 内部源码直接作为共享 npm 依赖。
- 不让主题包执行应用代码或直接调用 SDK。
- 不采用 `file:`、隐藏本地路径或手工补依赖解决工作区问题。
- 不以兼容旧大版本为理由保留双 API；当前尚未发布第一版，应直接收口干净方案。
- 不在本任务中创建分支、提交或修改无关用户变更。

## 5. 方案落地前的停线规则

出现以下情况，应停止写实现，先请用户或对应维护方确认：

1. D1/D2/D3 等架构决策没有结论；
2. Host、SDK、Manifest、脚手架或共用文档出现相互矛盾的公共字段；
3. 需要新增长期运行时依赖但没有完整选型报告；
4. antd 与产品需要的行为不等价，且改动会影响多个插件；
5. 真实 Host surface 或 iframe 链路无法复现，只有静态 mock；
6. 需要修改不在本阶段范围的用户工作区文件。
