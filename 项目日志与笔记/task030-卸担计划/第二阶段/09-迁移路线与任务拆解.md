# 09 迁移路线与任务拆解

## 1. 总原则

采用“契约先行、一个试点、按风险分批、每批真实验收”的顺序。第一阶段尚有并行修改和工单133/134，未收口前不能把所有应用一次性迁移到新的公共 API。

每个批次都必须保留用户管理的回滚点；本任务不创建、切换、合并或提交 Git 分支。

## 2. 阶段总表

| 阶段 | 内容 | 主要仓库 | 出口 |
|---|---|---|---|
| M0 | 决策、清点、公共文档收口计划 | 生态共用文档、工单134 | D1-D5 决策明确，停止项有 owner |
| M1 | `@chips/ui` runtime/app foundation | Chips-Ui、SDK、Scaffold | 最小应用入口和 mock Host 可运行 |
| M2 | App minimal 试点 | PhotoViewer | 真实 Host、Browser、测试和包全绿 |
| M3 | 标准应用壳和命令收口 | MusicPlayer、VideoPlayer、PhotoViewer、CardViewer | 4 个应用不再复制 Provider/命令框架 |
| M4 | 高复杂应用 | BookReader、RichTextEditor、CommunityClient、EcoSettingsPanel、EditingEngine、iconMaker | 分场景懒加载，权限/命令/错误全链路通过 |
| M5 | BCP/BLP/社区 Web | BaseCard、BoxLayout、CommunityPlatformServer web | iframe/document、a11y、资源、Browser 态通过 |
| M6 | Theme Recipe 与默认包 | Chips-Ui、Chips-SDK、Chips-Host、主题工程 | Recipe → Host install → surface 注入全绿 |
| M7 | 全量验收和发布准备 | 全工作区 | `verify:workspace`、质量报告、公共文档收口 |

## 3. M0：决策和清点

### 3.1 任务

1. 由用户确认 M0-D1 至 M0-D5；
2. 完成工单134 的公共文档差异清单；
3. 统计 active workspace 对 `@chips/ui`、antd、旧组件库、旧 theme/i18n 的引用；
4. 核对每个 app Manifest 的 `permissions`、`runtime.targets`、`ui.surface` 和实际 SDK action；
5. 核对 Host 的主题注入、command registry 和 surface 生命周期测试；
6. 固定本阶段 package 精确版本和 Node/npm 工具版本；
7. 确定 PhotoViewer 作为最小试点，EditingEngine 作为复杂工作台试点。

### 3.2 交付

- 决策记录；
- 应用/卡片/布局/主题依赖矩阵；
- 文档漂移清单；
- 不做事项和停止条件；
- 每个后续批次的输入/输出契约。

## 4. M1：`@chips/ui` 基础门面

### 4.1 代码任务

1. 补齐 `Chips-Ui/package.json` 的工作区统一元数据（工单133 剩余项）；
2. 新建 `src/app/`，实现 `mountChipsApp`、`defineAppConfig`、场景加载和默认 Provider 树；
3. 将 `ChipsProvider` 增强为 `client/launchContext/capabilities/platform` 正式上下文；
4. 将 command 本地注册和 Host registry adapter 分离，提供 register/unregister/invoke 生命周期；
5. 将 Apple theme、antd locale、popup container 和 global CSS 作为一个稳定 app preset；
6. 将 `StateBoundary`、`AppChrome`、`EmbeddedDocumentFrame` 补齐统一文案 key、错误对象、a11y 和清理逻辑；
7. 新增 `@chips/ui/testing`，统一 render helper 和 mock runtime，不让应用复制旧测试 Provider；
8. 清理根入口的非必要 barrel 导出，增加显式子路径 exports；
9. 为每一项 API 添加 `.d.ts`、README、单元测试和最小浏览器测试。

### 4.2 SDK/Host 联动

- SDK 增加 runtime capabilities 和 command typed adapter 所需类型；
- Host 明确 `command.register` handlerId/owner/session 行为；
- Host/SDK mock 增加 surface close、permission denied 和 theme fallback；
- 所有协议不一致先更新工单，不在 `@chips/ui` 私自兼容两种形状。

### 4.3 出口

一个手写 `App.tsx` 加一条 `mountChipsApp` 能在 Browser preview 和 Host window 渲染，且 command、错误、关闭清理测试通过。

## 5. M2：PhotoViewer 试点

### 5.1 迁移顺序

1. 保留 Manifest 能力、文件关联、权限和图片业务行为；
2. 用 `mountChipsApp` 替换 AppProviders/AppRuntimeProvider/AppShell 框架接线；
3. 把打开、保存、缩放、适配窗口等 command 改成统一 definitions/handlers；
4. 删除应用内重复 client、launch context、theme/i18n runtime；
5. 叶子 UI 直接消费 antd，跨场景壳消费 `@chips/ui`；
6. 更新单测、Playwright、CSP 和资源 URL 测试；
7. 运行正式 build/test/lint/typecheck/validate/package，记录 bundle 和 TTI 基线。

### 5.2 试点审查

- 业务行为和文件格式无变化；
- 应用源码没有 `window.chips`、旧组件库、旧主题 Provider 或私有基础控件；
- command 菜单、工具栏、快捷键、命令面板来自同一 registry；
- Host 权限拒绝和 Browser no-Host 态可理解；
- 失败后先修共享门面，不在 PhotoViewer 写特例。

## 6. M3：低风险应用批次

批次顺序：MusicPlayer → VideoPlayer → CardViewer。

每个仓库执行同一任务卡：

1. 依赖和 Manifest 对照；
2. 入口替换为 `mountChipsApp`；
3. 业务命令 definitions/handlers 分离；
4. 图片/媒体资源调用迁移为 SDK feature hook；
5. 统一播放/选择/加载/错误/空态；
6. 清理重复 CSS 中的全局颜色、字体、圆角；
7. 测试真实键盘、播放/暂停、资源释放和 surface close；
8. 单仓全绿后才进入下一仓库。

共享缺口（媒体控制、资源 URL、Panel header）必须回到 `@chips/ui`；仓库私有业务组件不得升格为公共组件。

## 7. M4：高复杂工作台批次

### 7.1 BookReader

- 先拆 readium/document domain 与 UI；
- 章节树、搜索、书签、偏好使用场景级 state；
- 阅读器内容 iframe/document 使用统一主题 CSS 注入；
- 通过动态 import 延迟加载搜索、偏好和大型目录；
- e2e 覆盖打开书籍、翻页、搜索、书签、关闭回收。

### 7.2 RichTextEditor

- SDK/BCP `importArchiveBundle` 类型漂移（工单132）必须先闭环；
- 编辑器命令、快捷键、selection 监听和资源导入必须按生命周期清理；
- 复杂菜单使用 compound command UI，不在 toolbar 中复制 handler；
- 真实浏览器验证粘贴、撤销/重做、资源和卡片保存。

### 7.3 CommunityClient / Community Web

- Browser 无 Host 与 Host surface 两种运行态明确分支；
- 社区 API server state 与本地 UI state 分离；
- 登录、上传、下载和路由错误不依赖桌面 Bridge；
- 统一图标、视觉、中文文案，保留网络 API 协议；
- Playwright 覆盖网络失败、权限和未登录重定向。

### 7.4 EcoSettingsPanel

- 它是治理应用，可以使用 theme/i18n/plugin manage 正式 API；
- 不能因为治理页面需要系统能力，就把治理逻辑下沉到 `@chips/ui`；
- 主题/语言/插件诊断页面只显示 Host/SDK 返回的标准快照；
- 命令注册、权限拒绝、主题切换和插件安装必须有 Host 集成测试。

### 7.5 EditingEngine / iconMaker

- 作为最高风险批次单独执行，不与小应用混批；
- 先拆资源、卡片、布局和编辑器 domain，再迁入口；
- 跨 iframe 的 BCP/BLP 主题、字体、图标和资源释放全链路验证；
- 性能记录大文档、长列表、拖动和重渲染基线。

## 8. M5：BCP、BLP 和 iframe 链路

1. BCP/BLP 不直接复刻 AppChrome，只消费 `@chips/ui` 的编辑面板、StateBoundary 和 EmbeddedDocumentFrame；
2. 卡片和布局 Manifest、资源权限、render/editor surface 语义保持正式协议；
3. 所有 iframe 文档注入完整 `theme.css`、字体、CSP 和必要 locale；
4. 确认 iframe 内 antd CSS-in-JS style 注入容器可用，不依赖父文档 style；
5. 真实 Host 打开卡片/箱子，执行 view/editor 切换、资源加载失败和关闭；
6. 归档目录不修改，现行目录若还有旧引用先登记工单再处理。

## 9. M6：Theme Recipe

1. 确认 Theme Runtime 继续保留或关闭外部主题入口；
2. 实现 Recipe schema、默认 Apple recipe、编译器和 validate；
3. 生成默认主题包，使用实际 Host `theme.install/apply/getAllCss` 链路联调；
4. 迁移主题预览矩阵和字体/icon 资源；
5. 记录构建产物 hash、token coverage、CSS/font bytes 和视觉快照；
6. 主题包作者文档与脚手架模板同批更新。

## 10. M7：全量收口

- 运行全工作区 `verify:workspace`；
- 逐仓执行正式 verify 脚本；
- 生成依赖、a11y、视觉、性能、Bridge 和 Manifest 报告；
- 闭环或明确阻断工单132、133、134 及迁移过程中新增工单；
- 将确认后的公共契约同步到 `生态共用技术文档/`，内部计划只保留过程和验收记录；
- 由用户决定提交、分支、合并和发布操作。

## 11. 批次停止条件

任一条件触发，停止当前批次并记录工单：

- 发现 Host/SDK/Manifest/文档契约不一致；
- 需要在应用内新建共享基础控件或私有 token 才能继续；
- antd 行为与原功能不等价且没有明确产品决定；
- 需要新增长期运行时依赖但尚未完成选型门；
- 真实 Browser/Host e2e、a11y 或性能门禁失败；
- 需要修改用户未授权的范围外仓库。
