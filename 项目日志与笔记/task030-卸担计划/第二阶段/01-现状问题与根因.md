# 01 现状问题与根因

## 1. 本次核对口径

本分析基于目标工作区 2026-08-08 的当前文件，而不是只引用旧任务说明。重点核对了：

- `Chips-Host/` 的 preload、runtime、主题和 Bridge 入口；
- `Chips-SDK/` 的 client、command、theme、i18n、testing 和 tooling；
- `Chips-Ui/` 当前共享层实现；
- `Chips-PhotoViewer/`、`Chips-EcoSettingsPanel/`、`Chips-EditingEngine/` 的 package、Manifest 和应用入口；
- `Chips-Scaffold/chips-scaffold-app/` 的模板、生成测试和 e2e；
- 第一阶段卸担计划、归档目录和共用技术文档。

工单134 已登记公共文档与代码基线漂移。下面将旧体系作为“问题证据”引用，不作为第二阶段新接口依据。

## 2. 当前真实链路

### 2.1 运行时链路

当前 Host 仍然拥有完整的插件运行时能力：

```text
PAL / Kernel / Services
  → Plugin Runtime / preload Bridge
  → 页面侧 chips-sdk Client
  → 应用 React 入口
  → antd + @chips/ui
```

Host 仍提供 `theme.*`、`i18n.*`、`surface.*`、`command.*` 等正式 route 和 Bridge 能力；当前部分新应用已经不再声明 `theme.read` 或 `i18n.read`，而是由 `@chips/ui` 的 Apple theme 与 antd 中文 locale 直接提供默认视觉和中文文案。也就是说，底层能力没有完全消失，但应用侧接线已经发生变化。

这正是“应用感觉臃肿”的一个关键原因：系统底层仍保留很多正式能力，应用侧却没有一个统一门面告诉开发者哪些能力必须用、哪些由平台默认处理、哪些只在治理应用中使用。

### 2.2 当前 `@chips/ui` 能力

`Chips-Ui/src/index.ts` 当前导出：

- `appleTheme` 与 `global.css`；
- `ChipsProvider/useChips`；
- 本地 `CommandProvider/useCommandRegistry/useCommandShortcuts`；
- `AppChrome`、`MenuBar`、`Toolbar`、`CommandPalette`；
- `EmbeddedDocumentFrame`、`PanelHeader`、`StateBoundary`。

这已经比每个应用各自维护 Provider、命令面板和嵌入容器好，但仍存在四个边界问题：

1. `ChipsProvider` 只接收一个已经由应用创建的 `client`，应用仍需自己处理 client 创建和入口注入；
2. `commands.tsx` 目前主要是本地注册和快捷键监听，尚未把 Host `command.register/unregister/invoke` 的权限、scope、handlerId 语义完整收口；
3. `appleTheme` 是共享事实源，但没有主题包编译输入、主题元数据、Host 注入和预览的统一作者入口；
4. 共享组件中仍能看到硬编码加载失败、空态、命令面板等文案，和原 Bridge command 的 `titleKey` 规范存在两种口径。

### 2.3 当前应用入口仍然偏重

脚手架 `app-standard` 虽然已经开始 antd 化，但仍保留：

```text
src/main.tsx
src/App.tsx
src/app/AppRoot.tsx
src/app/AppRuntimeProvider.tsx
src/app/AppShell.tsx
src/app/scene-registry.ts
src/commands/*
src/runtime/chips-client.ts
src/runtime/launch-context.ts
src/testing/*
```

这些文件中有一部分是框架实现，不是业务功能。若每个应用都复制、修改、测试它们，任何 Host/SDK/共享层改动都要在十余个应用中同步，复杂度自然回到应用侧。

目标不是粗暴删除所有文件，而是将其中的框架部分搬入可测试的共享门面，由脚手架只生成极薄的配置和业务入口。

## 3. 根因分层

| 根因 | 具体表现 | 结果 | 第二阶段处理 |
|---|---|---|---|
| 运行时能力没有门面化 | app 自己 create client、读 launch context、拼 Provider | 每个应用重复接线 | `mountChipsApp` + 默认运行时门面 |
| 公共 API 与实现边界不清 | `@chips/ui`、SDK、Host 都有 command/theme/i18n 相关代码 | 责任重叠、文档互相矛盾 | Host/SDK/UI/App 责任矩阵与 adapter 边界 |
| 组件成熟度被误解为“组件数量” | 有很多封装，但没有浏览器级行为、a11y、焦点和卸载测试 | 组件可用但不稳定 | 以 antd 作为成熟底座，自己只维护生态门面和适配器 |
| 主题系统把作者变成实现维护者 | 主题包需要掌握 token 层级、组件 CSS、字体、合同和构建顺序 | 主题开发繁琐，容易缺 token | Recipe 输入 + 编译生成 + 预览/矩阵门禁 |
| 状态、视觉、运行时混写 | 页面同时管理数据、命令、主题、窗口和组件样式 | 业务代码膨胀，难测试 | Provider 只持有环境状态，业务状态留在页面/领域层 |
| 规范存在双真相 | 归档后代码采用 antd，正式文档仍引用旧组件库 | 新开发者按错文档开发 | 工单134，M0 公共文档收口 |
| 校验偏文件级 | 通过导出扫描或静态契约，却未验证真实 Host surface | “门禁绿”不等于可运行 | 真实生成、浏览器、Host route、性能基线 |

## 4. 为什么社区成熟框架显得更稳定

成熟框架的优势不只是 API 简洁，而是把高风险行为长期放在同一个维护边界中：

- 键盘导航、焦点捕获与恢复、Portal、滚动锁定、弹层定位；
- disabled、loading、错误、受控/非受控状态的组合；
- 浏览器差异、ARIA 语义、事件清理和卸载；
- 多年的真实用户反馈和回归测试。

当前自研体系若自己实现这些行为，就必须同时承担“组件库、状态机、a11y 库、测试平台和发布维护者”的成本。单纯再写更多自研组件不会改变这个事实。

第二阶段因此采用以下边界：

1. antd 负责已经成熟且应用普遍需要的 UI 行为；
2. `@chips/ui` 只做主题配置、Host/Bridge 适配、应用壳、跨插件组合和生态特有组件；
3. 业务应用不再重复包装 antd，也不直接实现公共行为；
4. 只有 antd 明确缺失且被多个插件验证的能力，才进入 `@chips/ui` 的适配器或公共组件评审。

## 5. 主题包问题的本质

旧 ThemePack 的问题不是 token 体系本身没有价值，而是作者面对了错误的抽象层：

```text
作者想表达“蓝色、密度、圆角、字体”
却被要求处理“每个组件的状态选择器、CSS 文件顺序、字体复制、合同文件、Host 注入和构建产物”
```

因此第二阶段不采用“删掉所有主题能力”作为最终答案，而采用“双层主题”：

- 普通应用默认消费 `@chips/ui` 的已验证主题，不需要知道 Theme Runtime；
- 有视觉创作需求的主题作者使用 Theme Recipe，编译器生成 Host 所需的 CSS/token/Manifest/预览产物；
- Host 仍是主题选择、安装、作用域和注入的唯一运行时承载；
- 应用页面不得直接读取主题包文件或自行切换 CSS。

如果产品最终决定永远只提供单一 Apple 视觉，可以关闭“外部主题安装”，但仍保留 Recipe 编译和 token 诊断，避免 Apple 主题继续靠散落的硬编码维护。

## 6. 结论

需要卸掉的不是所有平台能力，而是把平台能力泄漏到每个应用和主题作者身上的负担。第二阶段的工作重心应从“继续补组件/补模板”转为：

1. 收口唯一正式链路；
2. 提供薄的应用门面；
3. 使用成熟 UI 底座承接高风险行为；
4. 用编译器把主题工程化细节自动化；
5. 用真实端到端门禁保证简化之后没有失去可靠性。
