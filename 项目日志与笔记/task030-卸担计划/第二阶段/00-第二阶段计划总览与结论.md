# task030 卸担计划第二阶段：平台收口与开发体验卸担

> 文档性质：项目日志与笔记中的内部方案，不替代生态公共契约。
>
> 基线日期：2026-08-08。
>
> 前置工单：工单134“第一阶段新前端基线与共享公共文档漂移”。

## 1. 先给结论

现在的问题不是某一个按钮、Provider 或主题文件写得太多，而是“平台边界没有被产品化”。Host、Bridge、SDK、组件/UI、主题和应用都具备一部分能力，但应用开发者仍然需要自己拼接这些能力；主题开发者仍然需要理解底层实现细节；质量门禁验证的是局部文件，而不是整条运行链路。

第一阶段的 `antd + @chips/ui` 迁移能有效减少旧自研组件、主题和 i18n 的维护成本，但它只解决了“换掉旧实现”，没有自动解决以下问题：

1. 应用入口仍暴露运行时 Provider、命令注册、启动上下文和测试接线；
2. `@chips/ui` 当前更像共享实现集合，还不是有稳定公共边界的应用开发门面；
3. antd 的默认能力与 Host 的 Surface、Bridge、权限、命令语义没有完全收口；
4. ThemePack 被归档后，应用虽然变简单了，但“主题包作为独立生态扩展”的链路也被一并切断；
5. 共享公共文档仍引用已归档的 `@chips/component-library`、旧主题 Provider 和旧 i18n hooks，造成正式口径漂移。

第二阶段的核心方案是：

```text
Host L1-L9（唯一运行时）
        ↓  Bridge / chips-sdk 正式协议
应用运行时门面（@chips/ui/app + 脚手架生成）
        ↓
@chips/ui（antd 稳定底座 + 共享视觉 + 壳层 + 适配器）
        ↓
应用只写业务状态、业务流程和页面组合
        ↓
Theme Recipe 编译器 → 可选 Theme Package → Host Theme Runtime 注入
```

也就是说：默认应用不再感知 Host 内部细节；普通主题作者不再编写百余份组件 CSS；组件稳定性主要交给成熟的 antd 和真实浏览器质量门禁；只有确实属于生态公共能力的部分，才继续进入 `@chips/ui` 或 Host。

## 2. 本阶段北极星

### 2.1 应用开发者的目标体验

一个普通应用只需要完成以下工作：

1. 用 CLI 生成 `manifest.yaml`、`app.config.ts`、入口和测试基线；
2. 在一个业务入口中声明场景和页面；
3. 通过 `useChips()` 使用已经注入的正式 SDK client；
4. 用 `defineCommands()` 声明命令元数据，用业务函数实现处理逻辑；
5. 直接组合 antd 或 `@chips/ui` 的稳定组件。

应用开发者不再手写 `AppProviders`、主题注入、环境 Provider、命令面板键盘监听、浏览器无 Host mock、窗口启动参数解析，也不直接访问 `window.chips`。

### 2.2 主题开发者的目标体验

主题开发者只需要提供：

- 色板、字体、密度、圆角、阴影、动效和图标策略；
- 少量有明确名称的组件变体覆写；
- 预览所需的主题元数据和资源。

编译器负责生成 token、CSS 变量、antd `ThemeConfig`、主题 Manifest、预览入口和完整性报告。主题包不再复制一套组件实现，也不再手工维护 100 个组件目录。

### 2.3 平台维护者的目标体验

Host 维护者只维护 Host 运行时、Bridge、权限、Surface、Theme Runtime 和正式服务；SDK 维护者只维护类型化封装、CLI、脚手架接入和测试辅助；`@chips/ui` 维护者只维护应用侧共享 UI 门面与适配器。三者各自有明确测试边界，不互相搬运行时实现。

## 3. 范围

### 3.1 必做

| 领域 | 第二阶段交付 |
|---|---|
| 公共契约 | 收口 Host、SDK、`@chips/ui`、应用、主题包的职责和示例；处理工单134 |
| 应用门面 | `mountChipsApp`、默认 Provider、启动上下文、命令、错误/加载边界和 Browser mock 的统一接线 |
| 脚手架 | `app-minimal` 与 `app-standard` 两种模板；生成后可直接 build/test/validate/package |
| 共享 UI | antd 作为成熟底座，`@chips/ui` 只包装生态特有的壳、Bridge 接线、主题入口和高频组合 |
| 组件质量 | 真实 DOM、键盘、焦点、弹层、滚动、卸载、a11y、性能测试；禁止把关键行为只测成静态快照 |
| 主题链路 | 设计并实现 Recipe 编译链；默认主题由共享层提供，可选 Theme Package 由 Host 管理 |
| 质量门禁 | 真实 `tsc`、ESLint、Vitest、Playwright、a11y 和渲染性能基线 |
| 迁移 | 以 PhotoViewer 为最小试点，再按风险分批迁移其余应用、BCP、BLP 和社区 Web |

### 3.2 不在本阶段直接做

- 不把 Host 运行时搬入 SDK 或应用。
- 不恢复旧 `Chips-ComponentLibrary` 的多包运行时，不在旧目录上继续开发。
- 不为了“像 SwiftUI”发明第二套 JSX/DSL 组件体系；先用成熟 antd + 组合门面实现同等的低样板体验。
- 不在没有选型报告、许可证核对、React 18 兼容性验证和跨端实测前新增长期运行时依赖。
- 不在公共契约未确认前直接修改共用技术文档正文；由工单134闭环后同步。

## 4. 必须先做的决策门

| 门 | 决策 | 默认建议 | 未通过时的处理 |
|---|---|---|---|
| M0-D1 | `antd + @chips/ui` 是否冻结为第一阶段之后的公共前端基线 | 通过 | 暂停公共 API 扩展，不能让新文档继续漂移 |
| M0-D2 | 是否保留 Host-owned Theme Runtime，并重新提供轻量 Theme Recipe/Package | 保留运行时，重做轻量作者体验 | 如果只要单一 Apple 视觉，则关闭外部主题安装入口，但仍保留 token 编译与诊断 |
| M0-D3 | 应用是否允许直接导入 antd 叶子组件 | 允许稳定叶子组件，生态能力必须经 `@chips/ui` | 若要求完全封装，则扩大 `@chips/ui` 适配面，不在应用内复制包装 |
| M0-D4 | 是否引入额外第三方运行时库 | 默认不引入；按领域实测后逐项批准 | 先用 React/antd 内建能力，不做临时替代 |
| M0-D5 | Manifest 是否由配置生成 | Manifest 仍为正式权威，配置仅生成类型和校验辅助 | 不允许出现两份可独立修改的权限/入口真相 |

## 5. 完成定义

本阶段不是“目录看起来更少”，而是同时满足：

1. 新建一个普通应用无需手写平台 Provider、主题运行时和命令键盘监听；
2. 应用业务代码不出现 `window.chips`、私有 token、自绘基础控件、私有 i18n formatter；
3. 共享 UI 的版本、导出边界、适配器和测试矩阵有正式文档；
4. 主题 Recipe 能从少量源文件生成可被 Host 安装、应用消费、预览和验证的完整产物；
5. 从 `chipsdev-r create` 到 Host `run` 的真实链路通过，而不是只通过关键字扫描；
6. 每项未收口的公共契约都有工单、责任人、前置条件和停止规则。
