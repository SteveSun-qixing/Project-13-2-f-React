# 04 应用开发卸担方案

## 1. 目标开发体验

应用开发者看到的工程应该是“业务项目”，而不是 Host 运行时的复制品。最小应用的入口目标如下：

```tsx
// src/main.tsx（目标形态）
import { createClient } from "chips-sdk";
import { mountChipsApp } from "@chips/ui/app";
import { App } from "./App";

mountChipsApp({
  client: createClient({ environment: "auto" }),
  render: <App />,
});
```

业务代码只表达：

```tsx
export function App() {
  return (
    <AppScene titleKey="photoViewer.title">
      <PhotoViewerPage />
    </AppScene>
  );
}
```

`AppProviders`、`AppRuntimeProvider`、主题、antd locale、命令面板、错误边界和测试 wrapper 都由 `@chips/ui/app` 提供。脚手架可以生成一个可读的入口，但不应要求每个应用维护相同的框架文件。

## 2. 两种模板，而不是一个巨型模板

### 2.1 `app-minimal`

适用于 PhotoViewer、VideoPlayer、MusicPlayer 等单主场景应用。生成内容：

```text
manifest.yaml
package.json
chips.config.mjs
index.html
src/main.tsx
src/App.tsx
src/app.config.ts
src/commands.ts
src/styles/app.css
tests/unit/app.test.tsx
tests/e2e/basic-flow.test.ts
README.md
```

要求：

- `src/main.tsx` 不超过 20 行；
- `src/App.tsx` 默认只保留一个业务页面插槽；
- `src/app.config.ts` 只配置应用显示信息、入口场景和命令，不复制 Manifest 权限；
- `src/commands.ts` 是可选文件，没有命令时不生成；
- 生成结果必须能直接 build/test/validate/package。

### 2.2 `app-standard`

适用于 EditingEngine、EcoSettingsPanel、BookReader 等多场景工作台。生成内容可以包含场景注册、共享壳、命令、mock 和 e2e，但所有框架实现从模板移入 `@chips/ui/app`，模板文件只负责应用差异：

```text
src/
├── main.tsx
├── App.tsx
├── app.config.ts
├── commands/
│   ├── definitions.ts
│   └── handlers.ts
├── scenes/
├── features/
├── domain/
├── styles/
└── testing/
```

不得再默认生成 `AppRuntimeProvider.tsx`、`theme-runtime.ts`、`i18n/locales.ts`、`render-with-chips.tsx` 等重复实现。若某个特殊应用确实需要治理级主题/i18n API，应显式启用 capability 并使用正式 SDK hook。

## 3. 应用配置与 Manifest

### 3.1 权威关系

- `manifest.yaml` 是 Host 安装、权限、入口和 Surface 语义的唯一权威；
- `app.config.ts` 是开发体验配置，用于生成类型、菜单和页面注册，不得独立修改权限；
- `chipsdev validate` 读取两者并检查 appId、entry、commandId、surface 和 capability 一致；
- CLI 生成 `src/generated/manifest-types.ts`，让业务代码可以获得类型提示但不能反向覆盖 Manifest。

### 3.2 建议的 `app.config.ts`

```ts
import { defineAppConfig } from "@chips/ui/app";

export default defineAppConfig({
  appId: "com.chips.photo-viewer",
  displayNameKey: "photoViewer.name",
  defaultScene: "viewer",
  scenes: {
    viewer: { render: () => import("./features/viewer/PhotoViewerPage") },
  },
});
```

规则：

1. `appId` 必须与 Manifest 相同；
2. `displayNameKey` 只引用应用文案资源，不写展示原文；
3. scene loader 使用动态 import，避免启动时加载所有重型页面；
4. 配置不可包含文件系统路径、权限绕过、任意代码字符串或 Host 私有 action；
5. CLI 在 build 前生成 scene registry，运行时不使用字符串反射。

## 4. 页面组合 API

采用组合优先的 React API：

```tsx
<AppScene.Root id="viewer">
  <AppScene.Header>
    <AppScene.Title titleKey="photoViewer.title" />
    <AppScene.Actions>
      <CommandButton commandId="photo.open" />
    </AppScene.Actions>
  </AppScene.Header>
  <AppScene.Content>
    <PhotoCanvas />
  </AppScene.Content>
</AppScene.Root>
```

规范：

- 复杂区域使用 compound components，不新增一串布尔 props；
- 视觉变体使用显式 `variant`，不以 `isX/isY/isZ` 组合隐式推导；
- Provider 只持有共享状态、actions 和 meta，页面通过 hook 消费；
- 组件优先接收 `children` 和清晰 slot，不用隐藏的 render prop 承载整个页面；
- 页面业务状态使用 React `useState/useReducer`；跨场景共享状态经评审后再引入 store；
- 派生值在 render 中计算，避免用 effect 复制状态；网络/Bridge 请求在事件处理器或明确的资源 hook 中触发；
- 频繁更新的临时值使用 ref，不将拖动、指针位置和播放时间全部放入全局 React state。

## 5. 状态和异步数据

### 5.1 状态归属

| 状态 | 归属 |
|---|---|
| 输入框草稿、面板开关、选择态 | 最近的业务组件或 feature hook |
| 跨 scene 文档选择、当前资源 | 应用 domain store；必须有明确 actions/selectors |
| Host launch context、capabilities、client | `@chips/ui` runtime Provider |
| 主题快照 | Host Theme Runtime + `@chips/ui` adapter |
| 命令注册状态 | `@chips/ui` command adapter + Host registry |
| 远程社区查询缓存 | 只有确有重复缓存需求时，评审后使用成熟 query 库 |

### 5.2 Bridge 请求约定

业务请求必须封装成 feature hook 或 domain service：

```ts
export function usePhotoResource(path: string | null) {
  const { client } = useChips();
  // hook 只负责请求生命周期、取消和标准错误，不负责渲染视觉。
}
```

要求：

- 组件卸载取消未完成请求或忽略过期响应；
- 多个互不依赖的只读请求使用 `Promise.all`；
- 权限错误展示标准错误状态，不捕获后静默返回空值；
- 资源 URL 必须在对应生命周期释放；
- 不在每个组件中重复写 `client.invoke("...")`。

## 6. 命令开发

### 6.1 定义和处理分离

```ts
export const commands = defineCommands({
  open: {
    commandId: "photo.open",
    titleKey: "photo.commands.open.title",
    shortcut: "Mod+O",
    menuPlacement: [{ menuId: "file", order: 10 }],
    handlerId: "photo.open",
  },
});

export const handlers = createCommandHandlers({
  "photo.open": async ({ client }) => {
    await client.platform.openFile({ mode: "file", allowMultiple: false });
  },
});
```

定义文件只写元数据，处理文件只写业务动作；UI 通过 `CommandButton`、`CommandPalette` 或 `AppChrome` 消费同一记录。

### 6.2 约束

- commandId 必须以应用 id/安全根段为前缀；
- handler 不通过 Bridge 传函数给 Host；
- `permission` 必须在 Manifest 声明；
- 快捷键冲突在 validate 阶段报错；
- 不为一个按钮再创建一套“按钮 onClick 命令”私有模型；
- 没有 Host 时可以执行本地 handler，但需要在测试中明确标记为 mock。

## 7. 多语言和文案

第一阶段默认使用 antd `zh_CN` 和应用静态中文文案。第二阶段要把“简单”与“不可治理”区分开：

- 组件库、Host command、错误和无障碍 label 继续使用稳定 key；
- 应用可以由 CLI 生成 `src/messages/zh-CN.ts`，默认只维护中文；
- 需要多语言的应用再生成其他 locale，不在所有应用强制复制空的 i18n runtime；
- 禁止 `formatMessage` 散落、默认文案和 command title 双写；
- `@chips/ui` 内置文案必须使用它自己的资源 key，并对外提供 locale 覆盖点。

这套方案保留治理能力，同时把普通应用从 Provider 和运行时管理中卸下来。

## 8. 样式和图标

- 默认视觉只来自 `@chips/ui` 的 ConfigProvider、CSS 变量和主题入口；
- 页面局部布局可以用 CSS，但颜色、字体、圆角、阴影、动效必须消费共享 token；
- 图标优先使用 `@ant-design/icons`，不手绘基础 SVG，不使用文本 glyph 冒充图标；
- 应用图标、插件 launcher 图标和界面运行时图标分开治理；
- `style` 仅用于运行时计算尺寸/位置，不用于复制共享 token；
- 所有弹层使用统一 `getPopupContainer`/portal 策略，确保 Electron window 和 iframe 中定位稳定。

## 9. 应用模板验证清单

每次修改模板必须：

1. 真实运行 `chipsdev-r create app --template app-minimal` 和 `app-standard`；
2. 检查没有未回填占位符、旧体系 import、旧目录和私有 token；
3. 运行 `npm run build`、`test`、`test:templates`、`test:e2e`；
4. 在 Host 打开生成应用，执行 command、文件选择、错误和 surface 关闭流程；
5. 抽样确认生成工程的业务开发者不需要修改框架 Provider 文件。
