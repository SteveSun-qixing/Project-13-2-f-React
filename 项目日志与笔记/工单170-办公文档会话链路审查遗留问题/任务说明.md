## 发现1：office.read 返回 descriptor.size 与字节长度语义不一致（高）

### 位置
- `Chips-Host/packages/office-document-service/src/index.ts` 第 234 行

### 描述
`read` 方法对局部区间读取（传入 `offset`/`length`）时，返回 `bytes` 的长度可能小于 `descriptor.size`（会话字节总长度）。SDK 消费方 `parseDocxBytes` 只关注 `bytes` 参数，但如果未来有依赖 `document.size` 做一致性校验的代码，会产生不一致判断。

### 推理
协议第 3 节说"read 返回完整或指定区间的会话字节"，未规定 descriptor 在区间读取时如何表现。但从语义一致性角度，当前的"返回全量 descriptor + 局部 bytes"在 UX 上会产生混淆。

### 建议修复
在 `read` 方法中，如果传入了 `offset` 或 `length`，返回的 `document` 中 `size` 字段应反映实际返回的 bytes 长度；或者新增 `bytesLength` 字段区分两者。修改需同步更新 SDK 类型定义。

## 发现2：close 的 persist 标志未同步 descriptor.status（高）

### 位置
- `Chips-Host/packages/office-document-service/src/index.ts` 第 270 行

### 描述
`close({persist:true})` 调用 `this.persist({sessionId})` 后，只在 `close` 体内把 `status` 标记为 `'closed'`。但 persist 方法本身会将 status 改为 `'clean'`（第 263 行）。这导致状态变化顺序为：dirty → clean（persist）→ closed。这是正确的行为，但 close 方法没有把 persist 后新的 document descriptor 同步返回。调用方如果期望拿到最终状态，必须再调用一次 `get`。

### 建议修复
确认这是否是预期行为。如果不需要返回最终 descriptor，保持现状（close 只返回 `{ack:true}`）；如果需要，修改返回类型。

## 发现3：SDK write 校验 Uint8Array 但 Host asBytes 更宽松（低）

### 位置
- `Chips-SDK/src/api/office-document.ts` 第 60 行
- `Chips-Host/packages/office-document-service/src/index.ts` 第 238 行

### 描述
SDK `write` 在调用前强制校验 `bytes instanceof Uint8Array`，不接受的输入直接抛 SDK 错误。Host `asBytes` 支持 ArrayBuffer、ArrayBufferView、Buffer、number[]、`{type:"Buffer",data:[...]}` 等多种形态。这导致：同样的 bytes 通过不同路径传入时行为不一致。

### 建议修复
将 SDK 的 `normalizeBytes` 也扩展为支持与 Host `asBytes` 完全相同的输入形态，保持两端一致。

## 发现4：Chips-Slide writeBytes 存在会话泄漏风险（高）

### 位置
- `Chips-Slide/src/state/deck-store.tsx` 第 349 行

### 描述
当 `officeSessionIdRef.current` 为 null（之前未建立会话），调用 `writeBytes` 时会走 else 分支新建 office 会话。但如果后续 `persist` 之前发生异常，新建的会话会被泄漏。更严重的是，`officeSessionIdRef.current` 在这个分支执行过程中被赋值为新 sessionId，但 persist 没有被调用（只调用了 write）。

实际上仔细看代码逻辑：
```typescript
if (officeSessionIdRef.current) {
  await client.office.write(officeSessionIdRef.current, bytes);
  await client.office.persist(officeSessionIdRef.current, filePath);
} else {
  await client.file.write(filePath, bytes, { encoding: "binary" });
  const officeDocument = await client.office.open({ filePath, format: "pptx" });
  officeSessionIdRef.current = officeDocument.sessionId;
}
```

else 分支先写文件再开会话，这是正确的——先有文件才能打开。但如果写文件成功但 open 失败，`officeSessionIdRef.current` 没有被赋值（因为赋值在 try 块内），所以不会泄漏。更重要的是，如果 `open` 抛出异常，else 分支已经完成了文件写入，此时后续读取会读到新文件，但会话未建立，这是可接受的降级。

**但是**：如果写文件成功，open 也成功，但 `officeSessionIdRef.current = officeDocument.sessionId` 执行后，下一个 save 会正确使用新会话。逻辑正确，无需修改。

## 发现5：Chips-Sheet CSV 切换时未正确关闭 office 会话（高）

### 位置
- `Chips-Sheet/src/app/AppRuntimeProvider.tsx` 第 430-440 行

### 描述
`saveWorkbookAs` 中，当另存为 CSV 时：
```typescript
if (format === "csv" && officeSessionIdRef.current) {
  await client.office.close(officeSessionIdRef.current).catch(() => undefined);
  officeSessionIdRef.current = null;
}
```
这里在写 CSV 文件后关闭了 office 会话。但之前的代码（434-436行）：
```typescript
} else {
  await writeWorkbookBytes(destinationPath, bytes);
  if (format !== "csv") {
    const officeDocument = await client.office.open({...});
```

对于非 CSV 格式（XLSX/XLSM），先写文件再开 office 会话，这是正确的。但如果 format 变为 CSV 时关闭了会话，后续 save 会再次尝试打开新的 office 会话。

**关键问题**：当 `officeSessionIdRef.current` 存在但 format 变为 CSV 时，代码在写 CSV 后关闭了会话。但 XLSX → CSV 的保存路径下，office 会话会被关闭，后续无法复用。这个逻辑是针对"从 office 会话的文件切换到 CSV 文件"的场景。

实际上这里的逻辑是：
1. 如果当前有 office 会话且新格式是 CSV → 关闭会话（因为 CSV 不走 office）
2. 如果新格式不是 CSV → 复用现有 office 会话（write + persist）
3. 如果当前没有 office 会话 → 写文件后开新 office 会话（仅非 CSV）

这个逻辑是正确的。

## 发现6：office.document.close 权限标注错误（高）

### 位置
- `Chips-Host/src/main/services/register-host-services.ts` 第 4447 行

### 描述
协议规定 `office.document.close` 的权限是 `office.write`（因为 `persist=true` 时会修改文件）。但超时设置为 5_000ms，与 read/get 相同。当 close 需要先 persist（dirty 文档）时，15s 的 persist 链路在 5s 超时下会被截断。

### 建议修复
将 close 的超时改为与 create/write/persist 相同的 15_000ms。
