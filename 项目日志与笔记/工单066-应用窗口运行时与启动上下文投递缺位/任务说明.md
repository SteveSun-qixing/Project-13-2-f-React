# 工单066：应用窗口运行时与启动上下文投递缺位

> 登记日期：2026-10-01
> 登记方：W5 photo-viewer 第③段迁移原子任务（`chips.official.photo-viewer`，派单行表 #3）
> 状态：开放
> 性质：宿主能力缺位登记（非本包缺陷）；本包四闸与 cpk 校验照常交付，窗口链路按诚实降级呈现。

## 一、背景

应用骨架（W5 三段式第②段，`tools/scaffold` app 模板）约定「应用窗口界面根组件 render.js 由平台窗口壳装载」（《03-应用插件开发指南》§十、`@chips/ui` §2.3：ChipsProvider 为「窗口运行环境根」）。图片查看器第③段迁移交付真实业务 UI 时确认：宿主侧尚无把插件 `render.js` 装入 `ui.surface: window` 表面窗口的运行时，初始启动上下文（`ctx.args.resourceOpen`）也没有主进程 → 窗口的投递通道。运行中投递不受影响（《14-资源打开与默认处理器契约》§5.5 规定 `resource:opened` 事件「UI 经 `chips.subscribe`」为正式面，已接）。

## 二、缺位明细与证据

1. **应用表面窗口装载的是诊断壳页，不是插件 render.js**
   - `packages/host/src/renderer/shell-window.ts:7-8` 头注：「本页只做诊断：验证 `window.chips` 方法面、IPC 调用链路与 `chips-resource://` 协议响应；不承载任何业务 UI（正式窗口界面由应用插件经 React + `@chips/ui` 提供）」。
   - 宿主 src 全量检索无「按插件加载 `render.js` / 装载 `IAppPlugin` 实例表面窗口」的编排（`host/src/main/app-launch.ts` 只承载宿主自身应用壳；`renderer/entries/frame.ts` 为基础卡片渲染帧通道，帧内明确不注入 `window.chips`，与 app 窗口分属两线）。
2. **初始启动上下文无投递通道**
   - 《07-应用插件接口》§4.3/§6.2：初始上下文随 `ctx.args.resourceOpen` 送达**主逻辑**；《14》§5.5：「新建实例不使用该事件：初始上下文随 `ctx.args.resourceOpen` 送达」——主逻辑到窗口 UI 的转投通道未定义、未交付。
   - 后果：应用 UI 挂载后无法得知「本次启动要打开什么」，只能等运行中 `resource:opened` 投递。图片查看器已按诚实降级呈现（空态文案「等待资源打开链路投递图片」+「打开图片」本地选择入口），不伪造初始查看内容。
3. **连带的宿主处理器缺位已在册**：`resource:open` 路由与 image 槽位处理器注册（工单063 ①）、`resource:read`/`file:write`/`dialog:*` 处理器（W4 宿主缺位勘查 64 项三态账「契约在册未实现」族）——本单不重复登记，只登记「窗口装载 + 初始上下文投递」这一结构性缺位。

## 三、影响范围

- 受阻：全部 `ui.surface: window` 应用（12 个 W5 app 骨架包）的「启动即看」链路——`chips dev run` 联调窗口只能见到诊断壳页或（未来接通装载后）无初始上下文的空态。
- 不受阻：应用包构建、四闸、cpk 五阶段校验；窗口内全部经 `window.chips` 正式面的能力调用（命令注册、`resource:opened` 订阅、`chips.resource(uri)` 句柄读取等在包内测试以假桥全链验证）。

## 四、复现步骤

1. `pnpm --filter @chips/plugin-photo-viewer run build && npx pnpm exec chips dev run --dir plugins/apps/photo-viewer`。
2. 观察表面窗口内容：为 `shell.html` 诊断页（或无 render.js 装载编排），非图片查看器界面。
3. 在包内测试注入假桥驱动 `AppView`（`tests/stage.test.tsx`）：`resource:opened` 运行中投递可建立查看态；初始 `ctx.args.resourceOpen` 无通道可达 UI，界面停留空态。

## 五、期望行为

1. 宿主交付应用窗口运行时：按 manifest `ui.surface` 创建表面窗口、装载插件 `render.js`（外部化 vendor 经 `chips-resource://platform/vendor/*` 提供）、注入 `window.chips` 方法面。
2. 定义并交付初始启动上下文投递通道（`ctx.args` → 窗口 UI；形态归宿主波裁定：preload 注入、启动查询参或受控事件面均可，但须过《01-Bridge-API规范》与安全基线），使《14》§5.1 的初始投递对 UI 可消费。
3. 交付后图片查看器按「初始上下文 → `resolveImageQueue` 建队」零改动回填（纯函数与订阅面已交付并测毕）。

## 六、暂行处理（零绕过）

- 界面以空态如实说明等待投递，不伪造初始查看内容、不轮询猜测、不经非正式通道（`window.location` 解析等）自造上下文。
- 运行中投递按《14》§5.5 正式面（`chips.subscribe('resource:opened')`）真实消费。
- 本单只登记不派单：归 W5 宿主窗口波统筹（与工单025/#85 帧执行通道、工单060~064 处理器族同波收口）。
