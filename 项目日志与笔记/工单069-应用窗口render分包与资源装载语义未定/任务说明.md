# 工单069：应用窗口 render.js 分包与按需资源的装载语义未定

> 登记日期：2026-10-01
> 登记方：W5 万能文件查看器壳重写臂原子任务（`chips.official.universal-file-viewer`，派单行表 #1 壳臂）
> 状态：开放
> 性质：宿主装载语义缺位登记（非本包缺陷）；与工单066（应用窗口运行时缺位）同波收口，本单登记其上的「分包与资源」具体维度。

## 一、背景

万能文件查看器是首个携带「重依赖引擎」的 W5 应用：壳臂交付后 `render.js` 消费引擎公开面（格式探测路由 → 18 格式插件），引擎内部以动态 `import()` 按格式懒加载 pdfjs/mermaid/three/xlsx/leaflet/hls/heic2any 等重依赖（RA-08 风险③红线）。构建实测：

- 若沿用 W5 各包 `vite.render.config.ts` 现行的 `inlineDynamicImports: true` 单文件形态，render.js 达 **19.25 MB**，直接违反《03-插件包格式》§五「单个文件超过 16 MiB」的 CPK 硬上限，`chips plugin pack` 无法出包；
- 因此本包已改为分包形态：render.js 为同步再导出门面（0.21 kB），主体与引擎核心在 `dist/AppView.js`（4.15 MB，CPK 布局允许 `dist/` 携带代码文件），重依赖按格式自然分包落 `dist/`（150 个 chunk，单文件最大 4.15 MB，全部 < 16 MiB），首屏不载重依赖。

分包形态在**包布局校验**侧全绿，但 render.js 对 `./dist/*` 的静态再导出与动态 `import()` 是否可解析，取决于尚未交付的应用窗口装载器如何为插件模块提供 base URL——该语义当前在册文档与宿主实现均未定义。

## 二、缺位明细与证据

1. **插件模块的相对导入 base URL 语义未定义**
   - `render.js` 门面含 `import { default as … } from "./dist/AppView.js"`；`dist/AppView.js` 内引擎插件按需 `import("./dist/<chunk>.js")`。
   - 《03-插件包格式》§二只约定 render.js 是「单一 ESM 文件」「由 SDK 构建产出」「在宿主文档（帧/应用窗口壳）内装载」，未约定装载器是否以包内 URL（如 `chips-resource://plugins/<id>/render.js`）为模块 base 解析相对导入；`packages/host/src/renderer/` 现仅有诊断壳页与卡片帧通道（工单066 证据），无插件 render.js 装载编排可对照。
   - 若未来装载器取文本 eval 而非 URL import，分包形态全部失效。
2. **pdf worker 的 `?url` 资产在分包构建下被内联为 data URL**
   - `src/domain/engine-plugins.ts:22` `import pdfWorkerSrc from "pdfjs-dist/build/pdf.worker.mjs?url"`，构建产物中该值收敛为 `data:text/javascript;base64,…`（约 1.4 MB，已计入 `dist/AppView.js`）。
   - Chromium 对 `new Worker("data:…")` 的支持面不稳定；pdf.js 失败时自动退回 fake worker（主线程解析），功能不中断但大 PDF 主线程成本上升。待窗口装载器提供包内资源 URL 语义后，应改回真实分发出（`dist/assets/pdf.worker.mjs` 资产 + 包内 URL）。
3. **包布局契约本身自洽**：`packages/cli/src/artifacts/cpk-validate.ts:299-327` 与 `packages/host/src/loader/validate.ts` 允许 `dist/` 子树携带代码文件、单文件 16 MiB 上限、根部仅 render.js 一个代码入口——分包形态与在册校验零冲突（本单不是布局规则缺陷）。

## 三、影响范围

- 受阻：万能文件查看器的分发态（`.cpk` 安装后）窗口装载；未来任何携带重依赖的应用（编辑器、薯片办公、社区客户端按需分包时同题）。
- 不受阻：本包四闸（test/typecheck/lint/build 全绿）、cpk 五阶段布局校验、包内假桥测试全链、渲染帧（basecard）链路（帧通道为单文件形态，不经本单）。

## 四、复现步骤

1. `npx pnpm@9 --filter @chips/plugin-universal-file-viewer run build` → 包根 render.js（0.21 kB）+ `dist/` 150 个分包；
2. 检索 `render.js`：静态再导出 `./dist/AppView.js`；
3. 对照工单066 复现步骤：宿主无 render.js 装载编排，分包解析语义无从验证。

## 五、期望行为

1. 应用窗口装载器（工单066 期望 1）落地时同时裁定：插件 render.js 以包内 URL 装载、相对导入以该 URL 为 base 解析、`dist/` 分包与资产可经同一 origin 取回（形态归宿主波裁定，须过安全基线与《03-插件包格式》）。
2. 裁定 pdf worker 资产形态：真实文件分发（`dist/assets/*` + 包内 URL）或维持 data URL 内联（二选一，写入《03-插件包格式》或工具链文档）。
3. 交付后本包按裁定零改动收口（分包形态已就位，仅需按需调整 worker 接线一行）。

## 六、暂行处理（零绕过）

- 本包保持分包构建（16 MiB 硬上限下的唯一合法形态），不在包内自造 loader 或运行时垫片；
- `resource:open` 打开臂、`resource:opened` 投递消费等窗口链路按诚实降级交付（与工单060~066 族一致），不假成功；
- 本单只登记不派单：归 W5 宿主窗口波统筹（工单066 同波）。
