# 工单 020：插件 `package` 命令 chips bin 解析漂移与目录态源码工程校验口径缺口

> 登记日期：2026-09-20
> 状态：开放
> 发现途径：task043 W2-P0-3 前置作业「cpk 夹具链」现状勘查（示例插件与脚手架模板的打包脚本链路）

---

## 一、问题

1. **`chips` bin 解析漂移**：示例插件与 `@chips/scaffold` 模板生成的插件 `package.json` 中，`package` 脚本一律写 `pnpm exec chips plugin pack --out dist/`，但插件的 `dependencies`/`devDependencies` 均不声明 `@chips/cli`。`pnpm exec` 在工作区 bin 解析不到 `chips` 时静默回退 PATH，命中仓库外的全局安装（本机实测为 `~/.volta/bin/chips`，一个与 workspace 版本口径不同的陈旧构建——它甚至不支持文档承诺的 `--version`）。这意味着「插件打包」正式脚本链在任何装有旧全局 chips 的机器上都会跑到错误的实现，在未安装的机器上直接失败。
2. **`plugin validate` 目录态与源码工程口径冲突**：《03-插件包格式》§7.2 与《07-CLI完整参考》§3.5.3 示例给出 `chips plugin validate examples/plugins/hello-basecard`（对**源码工程目录**执行同源校验）。实现中 `validateCpk` 目录态用 `collectDirectory` 收集全部文件并按**归档布局白名单**（`manifest.yaml`/`dist`/`render.js`/`assets`/`signature.json`）做 `validateLayout`，源码工程必然含 `package.json`、`src/`、`tsconfig.json` 等，文档示例命令必报 `CPK_LAYOUT_INVALID`。`plugin pack` 侧的同类漂移（§7.1「收集到暂存目录」未实现）已在本次夹具链作业中按文档修复（`packCpk` 增加包根白名单投影收集），`validate` 目录态未动，两处语义现在也不一致：pack 接受源码工程、validate 目录态不接受。

## 二、证据

- `tools/scaffold/src/templates/shared.ts:46`（模板 `package` 脚本）与 `examples/plugins/hello/package.json`（`"package": "pnpm exec chips plugin pack --out dist/"`）；两处的依赖清单均无 `@chips/cli`。
- 实测：`examples/plugins/hello` 目录内 `pnpm exec chips --version` → EXIT=1，输出 `unknown command: --version`（实际执行的是 `~/.volta/bin/chips`，`which chips` 证实）；workspace 正式入口 `node packages/cli/dist/bin.js --version` → EXIT=0，输出 `{ "chips": "0.0.0", "platform": null }`。
- 实测：`node packages/cli/dist/bin.js plugin pack --dir examples/plugins/hello --out /tmp/cpk-probe`（task043 修复前）→ EXIT=1，`CPK_LIMIT_EXCEEDED 目录深度超过上限：node_modules/...`，证明文档 §7.2「在插件目录内打包」链路此前在实现上不可用。
- `packages/cli/src/artifacts/cpk-validate.ts:554-563`：目录态直接 `collectDirectory` + `validateLayout`（`cpk-validate.ts:299-305` 白名单），源码工程目录（`package.json`/`src`）必触发 `CPK_LAYOUT_INVALID 白名单外条目`（对照 `packages/cli/tests/artifacts-cpk.test.ts` 「包根白名单外的条目拒绝」用例）。

## 三、影响

- 「插件打包」的官方推荐脚本链（含 `pnpm package` 根脚本触达全部插件）在 fresh clone 上不可复现，且更危险的是在装有旧全局 chips 的开发机上**静默跑错实现**——产出物口径由仓库外二进制决定。
- `validate` 与 `pack` 对「源码工程目录」的一接受一拒绝，文档、脚手架说明（"生成结果必须直接通过 manifest 校验与插件包格式校验"，§3.5.1）与实际行为三方漂移；用户按文档执行 `chips plugin validate <源码目录>` 必失败。
- W2-P0-3 之后的插件链 E2E 若走包脚本面打包，会直接暴露该断链。

## 四、期望行为（验收口径）

1. 示例插件与脚手架模板的 `package` 脚本链在 fresh clone 上仅凭 workspace 依赖即可执行到 workspace 版 `@chips/cli`（不依赖任何 PATH 回退/全局安装）；或 CLI 文档与模板统一改为一条明确的正式调用形态。`pnpm exec` 解析不到 workspace bin 时不得静默命中仓库外同名命令（至少需要可诊断的口径）。
2. 《03-插件包格式》§7.2/§3.5.3 与 `chips plugin validate` 目录态实现收敛为同一口径：要么目录态支持源码工程投影（与 `pack` 的收集投影一致），要么文档把该示例改称暂存目录形态；两处不得长期不一致。
3. 相关口径收口后，`examples/plugins/hello` 的 `build`/`package` 脚本与 `pnpm package` 根链路有在册用例证明端到端可用。
