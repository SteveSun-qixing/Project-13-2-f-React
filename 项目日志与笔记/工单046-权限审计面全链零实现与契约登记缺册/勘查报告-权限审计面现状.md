## ① 执行摘要（≤10 行）

1. 审计面整体处于「契约在册、实现近零」状态：《08.08》定义的记录格式、落盘、广播、留存、查询面、消费 UI 六要素中，仅事件契约登记面（三事件+payload）有真实实现挂点。
2. 宿主生产判定链路（`createHostCapabilityRouter` → `host-runtime`）的运行时放行/拒绝**零审计产出**；`@chips/bridge` 包内虽有 audit 钩子（`createBridgeRouter.options.audit`），但该路由器未被宿主生产链路使用，且其记录形状与契约不同型。
3. `IPermissionAuditEntry`（§8.2 十七字段）全仓 0 定义；`<userData>/logs/audit/` 落盘 0 实现；`permission:granted/denied`、`security:audit` 三事件**无任何生产者**（仅协议表+SDK 生成 ID+契约快照）。
4. 拒绝逐码面：PERMISSION 四码常量三方一致已收口（工单013 实证在案）；但 reason 五枚举中 `revoked`、`user_rejected` 全仓无产生位（Rust bridge 与宿主判定均固定 `not_granted`），其前置是链路二（授予/撤销交互与授权存储 `permissions.yaml`）整体未交付。
5. chips-resource（Rust）判定拒绝携带 out_of_scope/policy/not_granted 三类 reason，但 crate 无任何审计/日志回调挂点；chips-bridge crate 同样无挂点——**跨层审计采集钩子缺位是架构性缺口**，内核接线后会再次撞上。
6. 宿主 `host-trace.ts`（CHIPS_TRACE）已实现「JSONL 按日落盘+同序异步队列+失败隔离+flush 收口」完整形态，是审计写入器的直接可复用工程母型，但其头注明确「不进入审计留存」，语义（常开、留存策略、受限读取）必须独立承载。
7. 消费面：`05.05 §5.3/§5.4.2` 审计视图在 Chips-EcoSettingsPanel 与 `@chips/ui` 均无实现；且其依赖的「平台审计读取接口」「撤销/恢复能力」在《04-能力契约规范》能力表中**无登记条目**（契约层缺册）。
8. ULID（§8.2 id 字段）：Rust cordis 有生成器但 `pub(crate)` 不出 crate；TS 侧无 ULID 设施。
9. 归波建议：判定面审计挂点并入宿主整理波；Rust crate 审计 sink trait 与授权链二前置需独立立项/升单；能力契约登记缺口建议升新工单。
10. 口径歧义两处（见 §四）：免权限范围放行是否写审计；08.07 §7.2「按风险级别决定是否审计」与 08.08 §8.1「全量」表述不一。

## ③ 缺口清单与归波建议

**A. 可并入在途/近期波次的：**

1. **宿主判定面审计挂点**（#1/#2/#8）：给 `createHostCapabilityRouter` 增 `audit`/`onPermissionDecision` 注入位 + `host-runtime` 组合根接线 + 拒绝/放行发射 `permission:denied`/`security:audit`——改动面集中在 host runtime 两文件，可并入**宿主整理波**（与工单041 trace 波同族）。bridge 包内 router 的审计钩子可裁定为「与宿主统一判定面二选一收口」，避免双套判定长期并存（其现有测试 `router.test.ts:222-285` 已锁「写入失败不阻塞」语义可作验收母本）。
2. **chips-resource 段三捆绑**（#19）：段三波（工单036/044 残留合并波）在 Manager 收口处加一个 `DecisionObserver`（或等价 sink 回调）trait 挂点成本低、时机对。**注意**：本项结论以该 crate 并行波次落盘验收为准。

**B. 需独立立项「权限审计基础设施」的（建议 W3-P0-3 主体单）：**

- 契约同型 `IPermissionAuditEntry` 类型入 SDK/bridge 协议层（#3）；
- `<userData>/logs/audit/` JSONL 写入器（母型复用 host-trace 同序队列，常开、不受 CHIPS_TRACE 门控）+ 10MB 序号轮转 + 180/365 天留存清理（#4/#6/#12/#13/#15）；
- ULID 供给面（cordis `ulid.rs` 提公开面或独立设施）（#4）；
- traceId/requestId 横切传递（host-trace 头注已自认该缺口在册，#5）——**建议作为立项段一**，否则审计记录核心字段只能落空值；
- 平台审计读取接口+撤销/恢复能力的**能力契约登记**先行（见 C）。

**C. 建议升新工单的（契约/架构缺册类）：**

1. **跨层审计采集钩子无在册面**：`chips-bridge`、`chips-resource` 两 crate 均无拒绝出站信号（#19/#20），《08.08》未定义 crate 侧采集接口形态，Bridge 内核接线后必然复撞——属生态级架构缺口，符合 AGENTS 升单条件。
2. **《04-能力契约规范》缺「审计读取/撤销/恢复」能力条目**（#14/#7 前置）：05.05 §5.4.1 明文「撤销与恢复能力的登记归能力契约规范统一收口」，但能力表无册；08.08 §8.4 的「平台审计读取接口」同样无登记——契约漂移/缺册，登记后设置面板波才能开工。

**D. 消费方（05.05 审计视图）**：属 Chips-EcoSettingsPanel 仓库独立波次，本勘查仅确认消费位与依赖（读取接口+security:audit 增量+授权存储直读），不派单。

## ④ 与既有在册账的重叠/冲突提示

- **工单013（已收口）**：常量码表三方一致无回归；W3-P0-3「逐码」段的剩余面实际是 **reason 五枚举产生位**（#17）与错误→审计条目映射，不是码表本身——立项书应照此界定，避免与 013 重复验收。
- **工单042（已收口）**：Platform 免权限公开只读意味着资源侧存在**大量合规放行**（`chips-resource/src/permission.rs:219-221` read 恒 Allowed）；§8.1「判定（放行与拒绝）全量」若照字面实现，免权限范围（08.07 §7.2 `isSelfScope` 直通、Platform 只读、Document 会话内免重复校验）会刷屏审计流。**口径歧义①：免权限/直通放行是否入审计——须立项前裁定**（建议：免权限直通不产审计条目，仅产 grant/revoke/deny 与真正经过授予判定的 allow）。
- **口径歧义②**：08.07 §7.2 末行「判定结果允许时按风险级别决定是否审计（见 8.1）」与 08.08 §8.1「运行时判定（放行与拒绝）全量」表述冲突，落笔前需主智能体定一个权威口径。
- **W3-P0-1 段三 / 工单036/044**：chips-resource 在途（工作树可能脏），#19 结论以落盘验收为准；044 已登记「permission.rs:5 旧口径注释清理」与本勘查同文件重叠，波次协调时并轨。
- **工单041 修复波（CHIPS_TRACE）**：host-trace 是写入器母型但语义隔离（诊断≠审计，头注 :5-6 白纸黑字），复用应止于工程形态，不可复用其开关门控（审计须常开）。
- **宿主判定 vs bridge 包判定双套并存**（#2）：宿主自述判定为简化臂（无 qualifier 细粒度，session.ts:278-279），bridge 包评估器为完整臂但未接线——审计若挂在错误的判定面上会产生字段残缺记录，立项时先裁决统一判定面归属再谈审计。
