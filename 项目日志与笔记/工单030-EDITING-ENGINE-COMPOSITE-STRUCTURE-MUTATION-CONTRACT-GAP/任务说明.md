# 工单030：编辑引擎复合卡片结构编辑与锁定态契约调整闭环记录

## 1. 背景

`Chips-EditingEngine` 阶段三当前已经正式落地：

- 工作区文档会话；
- 工作区目录浏览；
- 设置中心；
- 基础卡片选中；
- 基础卡片编辑器挂载；
- `card.getBaseCard / card.renderBaseCardEditor / card.updateBaseCard` 基础配置编辑闭环；
- 自动保存、撤销 / 重做、编辑面板治理状态。

按迁移计划，下一步本应继续迁移旧项目中已经存在的以下核心能力：

1. 复合卡片内添加基础卡片；
2. 删除基础卡片；
3. 调整基础卡片顺序；
4. 查看模式 / 编辑模式（锁定态）切换。

在正式进入实现前，对生态共享文档、Host、SDK、当前项目文档进行了契约复核。

## 2. 旧项目基线要求

`归档/Chips-Editor/需求文档/02-功能需求.md` 明确给出：

### 2.1 FR-046 添加基础卡片

- 通过微内核生成 ID；
- 通过微内核 `card.add_base_card` 添加；
- 创建配置文件；
- 更新复合卡片结构；
- 自动保存；
- 触发 `base-card:added`。

### 2.2 FR-047 删除基础卡片

- 确认后通过微内核 `card.remove_base_card` 删除；
- 从复合卡片结构中移除；
- 删除配置文件；
- 自动保存；
- 触发 `base-card:removed`。

### 2.3 FR-048 调整基础卡片顺序

- 拖动基础卡片调整顺序；
- 通过微内核更新复合卡片结构；
- 自动保存新顺序；
- 触发 `base-card:reordered`。

### 2.4 FR-049 编辑模式切换

- 支持编辑模式 / 查看模式；
- 通过锁定按钮、快捷键、右键菜单切换；
- 切换状态需要保存。

这些都不是可选优化项，而是旧项目上层正确能力的一部分。

## 3. 当前生态正式能力复核结果

### 3.1 共享正式文档当前只闭环到“单个基础卡片配置编辑”

从以下正式文档可确认：

- `生态共用技术文档/架构设计/薯片生态-架构设计手册.md`
- `生态共用技术文档/插件开发/08-SDK使用指南.md`
- `生态共用技术文档/插件开发/03-卡片插件开发.md`

当前被共享文档明确冻结或公开的卡片正式能力主要是：

- `card.parse`
- `card.getBaseCard`
- `card.render`
- `card.renderBaseCardEditor`
- `card.updateBaseCard`
- `card.validate`

其中 `updateBaseCard` 的语义是：

- 针对已经存在的某个基础卡片节点；
- 回写该节点的标准化配置；
- 不涉及复合卡片结构级的新增、删除、重排；
- 不涉及查看模式 / 编辑模式或锁定态治理。

### 3.2 Host / SDK 当前未公开结构编辑或锁定态治理 route

核对结果：

- `Chips-Host/src/main/services/register-host-services.ts`
- `Chips-Host/src/main/services/register-schemas.ts`
- `Chips-SDK/src/contracts/route-manifest.json`

当前未发现以下正式接口：

- `card.addBaseCard`
- `card.removeBaseCard`
- `card.reorderBaseCard`
- `card.insertBaseCard`
- `card.setLockState`
- `card.setEditMode`
- `card.setViewMode`
- 其他等价的复合卡片结构写入或锁定态治理 route

### 3.3 Host 卡片服务当前也没有对应服务实现

核对：

- `Chips-Host/packages/card-service/src/card-service.ts`

当前 Host 卡片服务已具备：

- 读取卡片 AST；
- 渲染卡片；
- 读取指定基础卡片；
- 生成基础卡片编辑器 iframe；
- 回写指定基础卡片配置。

但未见：

- 新建基础卡片节点并更新 `.card/structure.yaml`；
- 删除基础卡片节点并同步删除内容文件；
- 以正式事务方式重排基础卡片顺序；
- 保存查看/编辑模式或锁定态。

## 4. 为什么这是阻断问题

编辑引擎不能直接采用以下方案继续推进：

1. 应用端私自解压 `.card` 包并改写 `.card/structure.yaml`；
2. 应用端自行决定新增节点 ID 生成、结构插入位置和内容文件命名规则；
3. 应用端私设 `locked`、`mode` 等字段写回元数据或结构文件；
4. 只做前端内存态拖拽排序和锁定按钮，而不走正式 Host 写入链路；
5. 自行约定未在共享文档中冻结的事件名或 SDK 调用方式。

上述做法都属于：

- 临时开发；
- 私有契约；
- 绕过 Host/SDK 正式边界；
- 会污染后续生态统一架构。

因此，在生态先补齐正式契约前，编辑引擎不能继续推进这条开发线。

## 5. 需要生态补齐的正式能力

建议先补齐并冻结以下能力，再恢复 EditingEngine 相关开发：

### 5.1 复合卡片结构编辑接口

至少需要明确：

- 添加基础卡片接口
  - 输入：`cardFile`、`baseCardType`、`pluginId?`、`insertPosition`
  - 输出：新增节点记录、更新后的结构摘要、必要时返回新的预览或节点信息
- 删除基础卡片接口
  - 输入：`cardFile`、`nodeId`
  - 输出：删除结果、更新后的结构摘要
- 重排基础卡片接口
  - 输入：`cardFile`、`nodeId`、`targetPosition` 或 `beforeNodeId/afterNodeId`
  - 输出：更新后的结构摘要

### 5.2 锁定态 / 查看-编辑模式治理接口

至少需要明确：

- 锁定态保存位置属于 metadata、structure 还是独立运行时状态；
- 查看模式 / 编辑模式是否是文档持久态；
- 正式 route 名称、输入输出模式；
- 预览 iframe 与编辑面板对模式切换的事件协作边界。

### 5.3 与当前已落地命令域的协作边界

需要明确：

- 结构编辑动作如何与自动保存协同；
- 结构编辑动作如何进入撤销 / 重做系统；
- 成功写回后如何刷新预览；
- 失败时如何回滚到权威状态；
- 是否需要新的共享事件或沿用现有回推链路。

## 6. 当前结论

本工单已按新的正式架构方向闭环：

- Host 不再为编辑引擎的每个结构动作补专用业务 route；
- 共享文档已冻结 `file.*` / `zip.*` 低颗粒度文档治理方案；
- 权限模型已支持 `file.manage` 这类命名空间超集权限；
- 卡片文件格式已正式定义 `metadata.yaml.editor_state.mode` 与结构写回规则；
- `Chips-EditingEngine` 已新增 `card-package-domain`，承接基础卡片新增、删除、重排与查看/编辑模式切换。

补充说明：

- 单个基础卡片配置编辑继续走 `card.updateBaseCard`，以复用 Host 已有插件序列化能力；
- 结构写入和模式切换走 `file.* + zip.*` 正式链路。
