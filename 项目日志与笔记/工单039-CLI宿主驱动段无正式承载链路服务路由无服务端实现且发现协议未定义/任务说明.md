- 编号：039

- 定性：架构级缺口（无正式服务通道可对接）。按仓库规矩停止实现宿主驱动段载体，不造临时通路、不以 stub 私有协议冒充正式链路。
- 日期：2026-09-21

## 一、背景与任务承诺

《07-CLI完整参考》对宿主驱动段（插件命令经承载环境执行）有如下正式承诺：

- §3.10.1「CLI 在按需启动本次命令所需的短生命周期承载环境；用户不需要先执行 `chips start`」
  （权威行号：薯片生态文档库/06-开发与运维/07.03-07-CLI完整参考-三、用户侧命令 chips.md:346）
- §3.10.2 `service` 目标经平台能力注册表与调用链路调用声明能力（同文件:347）
- §3.10.3 `app` 目标按 13-命令系统契约 §4.4「启动并投递」，以 `source: 'cli'` 调用 `command:invoke`（同文件:348）
- §5.8 平台内部服务路由表：`cli.command.list/get/resolve`、`cli.task.create/bindInvocation/get/progress/complete/fail/cancel`
  是「CLI 扩展的唯一服务路由集合；不得新增第二套命令索引或任务存储」
  （权威行号：薯片生态文档库/06-开发与运维/07.12-…-5.8 发现与任务服务路由.md:14-29）
- §2.4.5 结果信封、§2.5 退出码 6/7/8/9 的「有承载」语义均以承载链路真实存在为前提。

#122 的交付目标即打通并实测「宿主发现 → resolve → 执行 → 回包」的有承载路径。

## 二、缺口证据（均为本会话逐一核证的 文件:行号）

### 缺口 A：`cli.command.*` / `cli.task.*` / `command:invoke` 无任何服务端实现

1. CLI 与 SDK 只有**消费端**：
   - `chips-ecosystem/packages/cli/src/client/service-router.ts:58-134`（`cli.command.*` / `cli.task.*` 端口的请求方封装）
   - `chips-ecosystem/packages/sdk/src/client/cli-command-api.ts:8`（自述：「`cli.command.*` 属平台内部服务路由，只对注入服务传输的客户端」开放）
2. 宿主侧无接线：`packages/host/src` 全量 grep `cli.command.` / `cli.task.` / `command:invoke` 零命中；
   `packages/host/src/capabilities/` 仅有 `document` 一个域目录；`packages/host/src/runtime` 无任何 route 注册面。
3. 内核侧无实现：`packages/core-rust` grep `cli.command` / `cli.task` / `command:invoke` 服务实现零命中；
   唯一相关命中是 `packages/core-rust/crates/chips-bridge/src/naming.rs:100-104` 的 `cli:task-*` **能力 ID 命名注册**
   （插件 Bridge 面，服务插件消费，不是宿主/内核的服务路由 handler，也不对 CLI 进程开放）。
4. 全仓无 `@chips/cli` 消费者：`packages/*/package.json`、`tools/*/package.json` grep `"@chips/cli"` 仅命中其自身
   `name` 字段——不存在任何宿主/发行包装配 CLI 客户端的正式入口。

### 缺口 B：独立 `chips` 进程无宿主发现与传输通道（承载链路协议未定义）

1. 真实可执行入口从不做承载发现：`packages/cli/src/bin.ts:8` → `main(process.argv.slice(2))` 无选项；
   `packages/cli/src/main.ts:64-69` → 缺省走 `createLocalClient({})`。
2. 缺省 invoker 恒为离线拒绝：`packages/cli/src/runtime/local-client.ts:32-41`
   （无承载适配器时全部路由以 `CLI_TARGET_UNAVAILABLE` 拒绝）。
3. 注入面只有编程式端口：`IServiceRouterClientOptions.invoker` 注释自述「生产由 SDK 客户端（`@chips/sdk` 的
   `createClient({ bridge })` 目标）提供」（service-router.ts:33-34），而 SDK 的 bridge 客户端读取宿主渲染进程的
   `window.chips`（packages/sdk/src/client/chips-bridge.ts:143），外部 node 进程不可得。
4. 协议本身未落地：service-router.ts:9-10 明文——「其余平台操作……**在承载链路协议落地前**由承载适配器实现；
   缺失时相关命令返回 `CLI_TARGET_UNAVAILABLE`」。生态共用技术文档全库 grep「承载链路」仅三处引用性提及
   （07.01:21、07.02:147、07.03:64），**无任何文档定义该链路的传输形态、端点发现、握手与鉴权**。
5. 环境变量面无承载端点：《CLI 完整参考》§2.7 环境变量表（07.02:154-161）不含任何宿主发现/端点变量；
   工作区运行标记 `host-state.json` 只是状态标记，§3.2.2 明文「插件命令的承载链路不依赖该标记」（07.03:64）。

### 结论定性

CLI 侧消费端语义（发现分支、固定根先行定性、无承载→3/6 回退、信封/退出码）已完整实现且被离线测试
（`packages/cli/tests/**`、`tests/e2e/cli/tests/**`）钉死；但从真实 `chips` 进程出发，**有承载路径在
今天不可能到达**——既没有可对接的正式服务通道（缺口 A），也没有发现/传输协议（缺口 B）。

## 三、影响范围

- W2-P1-7 后段「宿主驱动段真进程实测」无法以不发明协议的方式落地：任何 e2e 载体要么给 CLI 进程
  新造一套端点注入通道（发明未在册协议=临时通路），要么在测试内 import 内部函数注入假 invoker
  （违反 tests/e2e/cli harness「禁止 import @chips/cli 内部函数走捷径、一律 spawn 真实可执行入口」纪律，
  且与 `packages/cli/tests/client-service-router.test.ts` 既有注入面单测重叠，无端到端增量）。
- §2.5 退出码 6（真目标不可用）、7/8（任务终态）、9（等待超时）的**有承载语义**目前只有 fake-client
  单元面覆盖，进程面不可实测；`CLI_TIMEOUT`、`job.cancelOnInterrupt` 真取消链路同理。
- §3.10 承诺的用户可感知行为（终端直接 `chips <插件命令路径>` 执行 service/app 目标）整体悬空。
- 对工单口径的澄清：任务书所提「`chips host <子命令>` 端到端回包」与权威文档冲突——v1.1.0 §2.3 明文
  「`host` 为历史二级入口名…`chips host ...` 返回 `CLI_COMMAND_NOT_FOUND`（退出码 3）」
  （07.02:55），且该面已由 `tests/e2e/cli/tests/cli-surface.test.ts:94` 与
  `packages/cli/tests/dispatch-command-not-found.test.ts:66-68` 双向钉死。**宿主驱动段的正式命令面是
  §3.10 `<插件命令路径>`，不是 `chips host *`**。后续派单表述应以文档为准。
