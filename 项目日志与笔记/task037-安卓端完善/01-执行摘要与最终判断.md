# 执行摘要与最终判断

## 1. 当前是否可以直接安装到 Android 手机

不可以。

这不是“尚未验证 APK”的保守表述，而是仓库中不存在 APK 产生链路：

- `Chips-Host/package.json` 主入口是 `dist/src/main/electron/app-entry.js`；
- Host 只导出 `desktop-host-shell` 和 `headless-host-shell`；
- `Chips-Host/src/main/shells/` 只有桌面与无头 Shell；
- PAL 只有 `node-adapter.ts`，没有 Android adapter；
- Bridge 生产链路依赖 Electron `ipcMain/ipcRenderer/contextBridge`；
- 安装器只有 `build:installer:macos`；
- 全仓没有 Gradle、AndroidManifest、APK、AAB、Capacitor、Cordova 或 React Native 工程；
- 正式共用文档明确写明 Web/Mobile Shell 尚未交付。

因此，现在没有可供 `adb install` 的产物，也没有可在模拟器中启动的 Android Activity。这不表示必须从零手写全部移动容器：Capacitor、Tauri 2 和 Node.js Mobile 都可以作为候选基础设施；但它们承载的是 Web 前端、Rust/原生后端或嵌入式 Node runtime，并不能把现有 Electron `BrowserWindow/ipc/contextBridge` 原样变成 Android 应用。

## 2. 当前成熟度

| 层级 | 状态 | 判断 |
|---|---|---|
| 跨平台类型与公共语义 | 部分完成 | 已预留 `HostKind=mobile`、`platform=android`、`fullscreen/sheet` |
| Kernel 路由/事件/权限模型 | 有较高复用价值 | TypeScript 逻辑清晰，但运行包仍依赖 Node 类型和模块解析 |
| Host Services | 桌面可用，未移动化 | 大量服务直接使用 `node:fs/path/os/crypto`，没有完全经过 PAL |
| Android Shell | 缺失 | P0 阻塞 |
| Android PAL | 缺失 | P0 阻塞 |
| Android Bridge | 缺失 | P0 阻塞 |
| 插件 Web surface | 设计预留 | 需要 Android WebView 宿主与隔离协议 |
| 模块插件 runtime | 不可直接复用 | 当前通过 Node `require/import(file://)` 执行 `.mjs/.cjs` |
| Android 构建发布 | 缺失 | P0 阻塞 |
| Android 测试 | 缺失 | 无设备 CI、仪器测试、E2E |

综合成熟度可评为：**契约预研阶段，而非 Android 可运行阶段。**

## 3. 最主要卡点

第一卡点不是前端响应式，也不是某个插件，而是 Host 自身的运行时承载。

现有 Host 架构虽然把 `PALAdapter` 注入 `HostCore`，但 `HostCore`、服务实现和模块 runtime 仍直接依赖 Node/Electron。Android 上既没有 Electron，也不能假设 Node 的文件路径、子进程、动态模块加载和长期后台进程存在。

第二卡点是移动 Bridge。Android WebView 不提供 Electron contextBridge。必须重新实现一个具有相同公共形状、但使用受控消息通道的 transport，并把 origin、surface、pluginId、session token、权限和消息配额绑定到原生侧。

第三卡点是文件与生命周期。Android 使用 `content://` URI、Storage Access Framework、应用沙箱和系统管理的进程生命周期。当前公共 API 大量以绝对文件路径为中心，Host 又假设可以长期后台运行，这两项都不能原样照搬。

第四卡点是插件真实性。正式源目录统计到 35 个 manifest：8 个 card、10 个 layout、7 个 module、10 个 app；其中只有 CardViewer 和 CommunityUploader 声明 `mobile: true`。但两者仍带 `os: darwin/win32/linux`，CommunityUploader 源码还导入 `node:path/node:os/node:url`。所以 `mobile: true` 目前不是运行证明。

## 4. 推荐路线

推荐建立：

`Android 原生 Shell -> Android PAL -> 可移植 Host Core -> WebView Bridge -> 插件 Web surface`

其中 Android Shell 可以优先评估 Capacitor 或 Tauri 2；如果目标是尽量保留当前 TypeScript/Node Host Core，应同时评估 Node.js Mobile。推荐先做两条有数据的技术原型：`Capacitor + Node.js Mobile` 与 `Tauri 2 + Rust/Android ports`，再根据现有 Host 服务兼容率、包体、启动、Bridge、安全和维护成本确定正式路线。

不推荐：

- 把现有 Electron 包直接套进 APK；
- 将所有插件改写成 React Native；
- 用单个高权限 `addJavascriptInterface` 向任意页面暴露全部能力；
- 为赶测试进度绕开 Host，直接在插件里调用 Android API；
- 先把所有 manifest 改成 `mobile: true` 再逐步修错误。

## 5. 可以立即开始的工作

1. 冻结 Android 架构 ADR 和最低 API/JDK/Gradle 版本；
2. 将 Host Core 中的 Node/Electron 直连做清单化并收敛到正式 port；
3. 建立 Android 工程和最小 Shell；
4. 实现可测试的 Android PAL 基础分面；
5. 实现安全 Bridge transport；
6. 先通过内置诊断 surface，再认证 CardViewer；
7. 形成 debug APK，开始模拟器与真机测试。

## 6. 不应立即做的工作

- 不应直接开发完整插件市场和热更新；
- 不应先适配全部插件；
- 不应承诺 Host 在 Android 后台永不退出；
- 不应在未解决模块插件执行模型前宣称五类插件均已支持；
- 不应把 `mobile: true` 当作验收条件，必须以设备测试报告和能力矩阵为准。
