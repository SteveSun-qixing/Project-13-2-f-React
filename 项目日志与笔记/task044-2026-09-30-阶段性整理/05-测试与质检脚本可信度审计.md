# 05 · 测试与质检脚本可信度审计

> task044 · 用户核心疑问「他们做的质量检测脚本、测试脚本能不能信任」的直接回答

## 一、总裁定：**部分可信——测试本体可信，质量数字与门禁聚合面不可信**

- **可信的部分**：3,516 个测试用例本体质量高——9,666 断言（2.75/用例）、`vi.mock` 全仓仅 7 处、零 `.only` 残留、零空壳测试；抽查均为真实行为断言（Electron 安全基线逐项钉死、markdown XSS 转义白名单、bridge 事件通道 58 断言用真实会话注册表、金链路 E2E 真进程真 Ed25519 签名）。
- **不可信的部分**：覆盖率门禁判的是 09-21 的过期快照且测量面缺 107 个源文件；门禁聚合有 3 条默认关闭的「逃生门」；gates:all 当前实测 FAIL；未提交的 4 个包测试全红。

## 四、fake-client 分析（tests/support/fake-client.ts）

457 行手写 `ICliClient` 替身，预置 `sha256:deadbeef` 等假值，被 8 个 CLI 测试引用。判定：**中等风险、未掩盖致命问题**——它只服务 CLI 表现层（端口-适配器架构下的合法替身），真实链路由 golden-chain E2E 补上（真 pnpm install + vite 双构建 + 真签名 + 五阶段 validate）。但生产 socket 的真实 IPC 仅在可被 env 关闭的 e2e 臂验证，**「单测全绿」不能独立证明真实链路**。

## 五、开发团队自查（09-22）交叉核对（B1）

自查评级：**诚实自查（B+），非粉饰**——全程亲跑留 EXIT 码、如实记录门禁红、自曝 20 条问题。但存在系统性盲区：覆盖率时效、G6 新鲜度、插件 id 命名空间、锁中毒惯用法全部漏检；且三项「重犯自己发现的问题」（双日志区、口径不一致、G9 红被当常态）。**自查可信但不可替代独立复核。**

## 六、修复建议（按优先级）

1. 修 4 个未提交包的红灯（依赖声明/类型/测试环境/实现），恢复工作区全绿。
2. G6 加输入新鲜度绑定（mtime 或 git commit 绑定），重跑 coverage 补全 107 个缺失文件。
3. check-entries 纳入 gates:all；e2e 臂在 CI 必跑；聚合输出标注逃生门状态。
4. 修复 gates 自测 1 例失败；门禁自测必须常绿。
5. 引入最小 CI（或本地 pre-commit 链），让门禁脱离「自产自检」闭环。
