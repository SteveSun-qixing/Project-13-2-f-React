# 工单035：渲染层视图构建端口与文档构建器输入形状漂移

> 登记：2026-09-21，金链路刀3（任务 #95，集成缝 1）勘查发现。
> 类型：文档-代码端口形状漂移（接口面）。
> 状态：已收口（2026-09-21，终关点达成——金链路刀5 双侧接线落地并验收：段A 主进程供给侧（任务 #108 交付、#110 接管复跑全绿）+ 段B 渲染消费臂与编辑回流（任务 #110），见第九节；裁定史见第八节）。
> （历史口径：登记时待处理，刀3 曾按「以文档为准实现、不改文档」落地暂行处理，见第六节。）

## 一、背景

《05-渲染引擎设计》§2.6 把 `DocumentViewBuilder` 的输入冻结为 **`DocumentHandle` + `SessionId`**
（执行位主进程 Rust 核心，无自有缓存、同句柄同修订输出确定）；《03-核心接口规范》§6.4 的
backing 导出 `buildDocumentView(handle, session: number)` 与该口径逐字对应。

渲染引擎端口（宿主 TS 侧，`packages/host/src/renderer/render-engine.ts` 的
`IDocumentViewBuilder`）实际消费形状为：

```
buildView(input: { source: string; documentId: string; kind: DocumentKind }): Promise<ICardRenderView>
```

两形状之间不存在直连通道：端口输入面没有句柄承载位、也没有数值会话承载位。

## 二、证据（逐项对表）

1. **输入侧**：§2.6 输入 = `DocumentHandle + SessionId`；端口输入 = `{source, documentId, kind}`
   （`render-engine.ts:97-103`）。`documentId`（十位 Base62 文本 ID——2026-09-21 任务 #105 审计勘正，原文笔误「11 字符」；权威三源：《05-ID生成规范》§二.1/§七.1、宿主 `validation.ts:26` 十位模式、Rust `is_base62_id`）与 `source`（URI 定位器）
   均不携带、也不可合规推导出主进程句柄。
2. **open 输出侧**：渲染管线在 `document:open` 之后调用 `buildView`
   （`render-engine.ts:223-229`），而 `IDocumentOpenOutput`
   （`capabilities/document/contract.ts`）有意只回 `{documentId, kind}`——句柄与数值会话
   都被文档服务刻意不暴露（§2.6 句柄生命周期归文档服务；`session-store.ts` 的记录级
   `handle/nativeSession` 只在主进程内部持有）。渲染层任何自取路径都会穿透该边界。
3. **会话形态漂移在册**：宿主会话标识 `sessionId: string` ↔ backing `session: number`（u64）
   的形态分叉已由《RFC-插件执行通道与ModuleLoader裁定》O3 与 W2 金链路定案记录
   （host 开发日志 2026-09-19），本端口漂移是其向视图构建域的延伸。
4. **返回侧窄化**：§6.6 冻结 `DocumentView = CardRenderView | BoxRenderView`；端口返回
   `ICardRenderView`（`frame-protocol.ts`），箱子渲染波开通前联合的另一支在渲染层无承载。

## 三、影响范围

- 刀3 交付的正式实现 `packages/host/src/renderer/document-view-builder.ts` 无法从端口输入
  直接凑出 §6.4 调用实参，必须引入可注入的会话解析入口做适配（见第六节暂行处理）。
- 刀4 组合根接线时，`DocumentViewSessionResolver` 是唯一能把端口 `{source, documentId, kind}`
  映射回文档服务会话记录（句柄 + 数值会话 + 受管作用域）的位置；该映射的口径（如何凭
  documentId/source 定位会话记录、string↔u64 归一在哪侧做）目前无文档权威定义，属刀4 起
  需裁决的空白。
- 箱子波（`BoxRenderView` 消费面）开通时端口返回类型必须随 §6.6 联合扩宽，现有
  `kind !== 'card'` 拒绝闸届时翻转；若文档侧对渲染端口另有裁定，以裁定为准。

## 四、复现步骤

只读勘查即可复现，无需运行：

1. 读《05-渲染引擎设计》§2.6 构建器输入定义与《03-核心接口规范》§6.4 导出表
   `buildDocumentView(handle, session: number)`；
2. 读 `packages/host/src/renderer/render-engine.ts` 的 `IDocumentViewBuilder` 端口形状与
   `document:open → buildView` 管线调用点；
3. 读 `packages/host/src/capabilities/document/contract.ts` 的 `IDocumentOpenOutput`（无
   handle/session 承载）与 `session-store.ts` 的 `IDocumentSessionRecord`（handle/nativeSession
   仅主进程内部字段）——确认渲染层不存在合规取数路径。

## 六、暂行处理（刀3 已落地，不阻塞）

- 构建器本体**以文档为准**逐字实现：每次 `buildView` 经注入的
  `DocumentViewSessionResolver`（刀4 组合根接线位）解析
  `{handle: INativeDocumentViewHandle, sessionId: number, managedScope: string}`，随后逐字调用
  `buildDocumentView(handle, sessionId)`；构建器零自有缓存、零状态（§2.6）。
- 端口形状不动（`render-engine.ts` 仅注释更新），漂移闭合责任上移至刀4 接线点；
  `sessionId` 触达 backing 前强制「非负安全整数」闸（u64 JS 侧传输硬边界，越界以
  `BRIDGE_INVALID_INPUT` 拒绝，不静默截断）。
- `kind !== 'card'` 输入在实现侧以 `BRIDGE_INVALID_INPUT` 诚实拒绝（箱子视图无承载）；
  backing 返回 `BoxRenderView` 判别在端口扩宽前视为绑定契约违约（`BRIDGE_INTERNAL`）。
- 测试面：`packages/host/tests/renderer-view-builder.test.ts` 以替身 resolver 注入固定绑定
  （42/card-7f3a），双轨套件（`renderer-engine`/`renderer-height`）同口径；resolver 的
  生产实现落地即本单裁定收口点。
