# 工单 003：能力 ID 文法（04.03 全小写）与 R19 canonical 表（camelCase）冲突

> 登记：W1-GATES（2026-09-19）
> 状态：待处理
> 影响：能力契约规范 §3.1 与 §6.2、`@chips/contract-gen` 的 `CAPABILITY_ID_PATTERN`、生成物 `CAPABILITY_IDS`、全部能力 ID 的注册与校验

---

## 一、背景

能力 ID 的权威文法在文档库内部不一致：命名规则章节要求全小写，而 R19 canonical 总表登记的能力 ID 含大写动作段（`window:setTitle`、`window:setState`、`shell:openExternal`）。`@chips/contract-gen` 已按 canonical 表实现（动作段允许大写），门禁无法同时满足两处口径。

## 二、证据

1. **全小写规则**：`薯片生态文档库/05-接口与契约/04.03-04-能力契约规范-三、能力 ID 与权限 ID 命名规则.md` §3.1
   - 文法 `action = 1*( lowercase / digit / "-" )`；
   - 规则 1：「全部小写，禁止空白、大写、下划线与中文；`:` 是唯一分隔符；能力 ID 为 2 段或 3 段，4 段及以上非法。」
2. **canonical 表含大写**：`薯片生态文档库/05-接口与契约/04.06-04-能力契约规范-六、权限映射（R19 全表）.md` §6.2 第 36、47 行
   - `window:create` / … / `window:setTitle` / `window:setState` → `window:control`；
   - `shell:openExternal` → `shell:external`。
3. **裁决亦含大写**：`项目日志与笔记/task043-生态梳理/本轮架构收口裁决.md` §四.2 明确新增 `window:setTitle` 等能力。
4. **生成器实现**：`chips-ecosystem/tools/contract-gen/src/parse.ts:20` `CAPABILITY_ID_PATTERN = /^[a-z][a-z0-9-]*:[a-z][A-Za-z0-9-]*$/`（动作段允许大写）；生成物 `packages/sdk/src/generated/capability-ids.ts` 已包含上述三个 ID。
5. **门禁表现**：`node chips-ecosystem/tools/gates/check-contracts.mjs` → 警告 `CONTRACT091 能力 ID 含大写字母：window:setTitle, window:setState, shell:openExternal`。

## 三、影响范围

- 能力注册校验（`PERMISSION_*` / `BRIDGE_CAPABILITY_*`）若按 04.03 实现，将拒绝 R19 已登记能力；
- 生成物与文档表单向比对无唯一文法依据；第三方能力评审、manifest 校验与 SDK 类型生成同样受影响。

## 四、复现步骤

1. 打开 `04.03` §3.1 与 `04.06` §6.2，对照文法与表中 ID；
2. 运行 `node chips-ecosystem/tools/gates/check-contracts.mjs`，观察 CONTRACT091；
3. 按 04.03 文法校验 `window:setTitle` 失败，按生成器文法校验通过。

## 五、期望行为

1. 明确唯一文法并同步修订冲突章节：若保留 canonical 大写动作段，则 04.03 §3.1 的文法应写为 `action = 1*( lowercase / uppercase / digit / "-" )` 并补充 camelCase 场景说明；若改为全小写，则需同步修改 R19 表、裁决与生成器实现。
2. 生成器实现、门禁判定与文档文法在同一次变更内保持一致。

## 六、暂行处理

- 门禁以警告 `CONTRACT091` 绕开该冲突，不阻断 `gates:all`；裁决后若统一为允许大写，删除该警告；若统一为小写，门禁升级为失败并同步生成器与夹具。
