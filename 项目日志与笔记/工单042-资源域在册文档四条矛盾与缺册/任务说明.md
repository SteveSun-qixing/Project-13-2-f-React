chips-resource 段一（寻址内核）按《06-资源协议规范》与《04-资源管理设计》双源实现时，发现四处在册文档互相矛盾或缺册，段一均以「登记不改文档、按更权威一方实现、留待裁决」处理。段二（Provider 挂载与写路径）直接依赖其中两条（ResourceStream 形状、Platform 权限口径），必须先行裁定落文，否则段二实现将再次踩「文档互斥」判例。

## 四条漂移与证据

1. **Platform 读取权限互斥**
   - 《04-资源管理设计》§5.3 作用域权限表：`Platform | 任意插件 | resources:read:platform | 禁止 | 只读、不可列举`（`薯片生态文档库/01-架构设计/01-子系统设计/04.05-04-资源管理设计-五、chips-resource--- 的解析与权限（管理器侧）.md` L67）。
   - 《06-资源协议规范》§4.3 作用域权限表：`Platform | 任意插件 | 免权限（公开只读） | 禁止 | 不可列举目录`（`薯片生态文档库/05-接口与契约/06.04-06-资源协议规范-四、权限模型.md` L60）。
   - 两表同行互斥（一为限定权限 ID、一为免权限）。《06》适用范围自称「`chips-resource://` 统一资源协议的权威契约：…权限模型…」，且《04》§5.1 自证「URI 语法规格…以《06-资源协议规范》为准」的从属口径。
   - 段一实现按《06》§4.3（免权限），`src/permission.rs` 判定矩阵与 `tests/error_code_lock.rs` reason 词表锁定在册。

2. **ChipsError 示例与实码 API 不符**
   - 《04-资源管理设计》§9.2（路径安全）示例代码使用 `ChipsError::ResourcePathInvalid(..)` 枚举变体。
   - 《核心接口规范》§3.3 落地的 `chips_core::ChipsError` 是单形结构体（`new / with_details / with_retryable`），全仓不存在 `ResourcePathInvalid` 变体（工单024 RFC 裁定后错误模型唯一化，`export class ChipsError`/单形结构体为终态）。
   - 示例若被段二/段三照抄将直接编译失败；属文档陈旧。

3. **`ResourceStream` 形状全册无定义**
   - 《04-资源管理设计》§3.2 `ResourceProvider::open_stream` 返回类型 `Result<ResourceStream, ChipsError>`，但 `ResourceStream` 的形状（方法、chunk 语义、结束信号、背压）在《04》《06》全部在册分件与《核心接口规范》中均未定义。
   - 口径源在《04》§七（大文件与流式读取）：chunk 拉取式、每次上限 256 KiB、调用方不拉取则 Rust 侧不推进（天然背压）、`RESOURCE_BUSY`（句柄正被流占用，§5.5 错误码表）。
   - 段一以在册抽象 trait（`next_chunk`）临时定义（`src/provider.rs`），README 声明「待文档补形」；段二三个内置 Provider（Directory/Archive/Memory）实现 `open_stream` 前必须补形定案。

4. **`details.reason = unicode` 无触发规则**
   - 《06-资源协议规范》§2.4 校验表「Unicode | NFC 规范化后校验与比较 | `unicode`」与 §7.3 reason 词表在册 `unicode` 一词（L87），但全部文档未给出任何**触发**该 reason 的拒绝规则——「规范化后校验与比较」本身是归一动作，不是拒绝条件。
   - 段一按词表保留成员、不产生该 reason（`tests/error_code_lock.rs` 词表锁定，实现零产生面），README 登记「待补规则」。

## 裁定（主智能体，2026-09-21）

1. **以《06-资源协议规范》为权威**（协议规范对权限模型的自述适用范围 + 《04》自身的从属句式）：Platform 作用域读取**免权限（公开只读）**。落文方向：《04.05》§5.3 表 Platform 行改「免权限（公开只读）」并加口径随《06》§4.3 的交叉引用；先核对《08-权限系统设计》4.4（免权限范围）同向无冲突后再改。实现零改动（段一已按此实现）。
2. **《04.09》§9.2 示例改实码 API**：`ChipsError::ResourcePathInvalid(..)` 改为 `chips-core` 单形结构体构造（域码表码 + `with_details`），文案与错误码值零改动，仅示例形态随实码。
3. **补形入《04.03》§3.2**：`ResourceStream` 定为拉取式流抽象——`next_chunk(&mut self) -> Result<Option<Chunk>, ChipsError>`（`None` = 流结束），`Chunk { offset, bytes }` 满足：非末块 `bytes.len() ∈ (0, 256*1024]`、`offset` 自 0 起严格等于前块累计、句柄被流占用期间其余读方法返回 `RESOURCE_BUSY`、调用方不拉取即天然背压。形状与段一 `src/provider.rs` 在册 trait 一致，文档吸收实现口径（同判例：§5.2 `ScopeRegistration.provider_id` 属可实现必需）。
4. **《06.02》§2.4 Unicode 行补触发规则**：百分号解码一次后的字节序列须为**合法 UTF-8 且不含非字符（U+nFFFE/U+nFFFF）、U+FFFE/U+FFFF 与替换字符 U+FFFD**，违反即 `RESOURCE_INVALID_URI` + `details.reason = unicode`；「NFC 规范化后校验与比较」维持归一语义（归一差异本身不构成拒绝）。《06.07》§7.3 词表同节注记联动。实现侧随动：段二波在 `path_guard` 落地该触发臂并把 `unicode` 从「在册不产生」翻为「有产生面」，纳入 `tests/error_code_lock.rs` 同型锁测。
