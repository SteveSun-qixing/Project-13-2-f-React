## 一、背景

薯片生态的富文本卡片（`chips.basecard.richtext`）采用「Markdown 唯一持久化」口径：卡片数据存 Markdown 源文，查看态需要一条「Markdown → 只读渲染结构」的解析/渲染链路。这条链路在生态目录里被登记为一个**内容处理服务插件** `chips.service.markdown`（服务名 `markdown`），由服务插件经 Cordis 服务对外提供，不注册 Bridge 能力。

本次 W4 开工前置勘查（旧三插件仓 → 新生态供给面逐仓映射）在核对 richtext 卡片族的端到端可迁性时发现：该服务在《09-官方插件与应用目录》长期停留在「待实现」状态，新生态没有任何实现面；更关键的是，**W4 开闸计划此前对它有零归属**——既没有波次承接，也没有工单登记，属于「文档在册、计划无主、代码无实现」的三不管缺口。richtext 卡片的迁移因此只能交付编辑面与数据面，查看链路无出口。

## 三、影响范围

- **直接阻塞**：`plugins/basecards/richtext` 的查看态端到端（W4-B 路 richtext 包）——按现有排程只能交付「非查看链」骨架，DOD 的「打开卡片渲染出内容」一环无出口。
- **间接影响**：`chips.service.file-processing`（09:175 行）与内容处理服务族的契约形态——若 markdown 服务先落地，可成为该族 Cordis 服务契约的首个样板；若继续挂空，W4-C 五模块（CardtoHTML / ColorPicker / FileConversion / HtmltoImage / HtmltoPDF）的服务化形态同样缺参照。
- **不阻塞**：三插件仓的其余 UI 供给面（layouts 10 包 / basecards 其余 8 包 / services 7 包）与本缺口无耦合；已派 #257 layouts 试点与未派 basecards 路均不受影响。
- **不做处置的代价**：richtext「Markdown 唯一持久化」的读侧长期由卡片私有实现承担，服务分层在第一个真实用例上就被绕过，后续每加一个 Markdown 消费方都重复一份实现。
