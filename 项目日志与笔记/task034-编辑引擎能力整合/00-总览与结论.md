# 00-总览与结论

## 1. 调查背景与目标

用户希望把编辑引擎的大部分接口和能力放到 Host，让编辑引擎成为「调用各种接口、调用各种能力」的套壳软件；这些能力应当是全生态共用的，未来其他软件（查看器、社区客户端、第三方工具）也可以直接使用。

本次调查回答三个问题：

1. 编辑引擎当前**已经通过 Host/Bridge/SDK 调用**了哪些能力？
2. 编辑引擎当前**自己实现**了哪些本应生态共用的能力（重复造轮子的部分）？
3. 这些能力应该以什么形态上移到 Host 及生态公共层？

## 2. 调查方法

- 阅读生态设计原稿：`14-编辑引擎设计.md`、`03-层次结构.md`、`02-架构原则.md`、`13-公共基础层设计.md`、`19-SDK与协议.md` 等；
- 阅读生态共用技术文档：`06-Chips-Host对外接口基线.md`、`13-命令系统契约.md` 等；
- 逐文件调查 `Chips-EditingEngine/src`（约 200 个源文件），确认每个能力点是否调用 SDK/Host；
- 核对 `Chips-Host/src/main/services/register-host-services.ts`（服务路由注册表）与 `Chips-SDK/src/api/*`（SDK 封装面）；
- 抽样其他应用（CardViewer、MusicPlayer、RichTextEditor、CommunityClient）对 Host 能力的消费情况，验证「全生态共用」的证据。

## 3. 总体结论

### 3.1 编辑引擎已正确接入了 Host 的「底层原语」能力

编辑引擎对 Host 的调用面集中在以下几类，形态正确（薄封装 + 统一 SDK client）：

- `file.*`（读写/stat/list/mkdir/delete/move/copy）
- `zip.*`（compress/extract/list）
- `resource.*`（resolve/readBinary/convertTiffToPng/extractVideoFrame）
- `config.*`（get/set）
- `plugin.query`（装载基础卡片插件与布局插件）
- `box.*`（pack/unpack/inspect/readMetadata/readLayoutDescriptor/normalizeLayoutConfig/renderCover/listLayoutDescriptors）
- `card.*`（readInfo/resolveResourceUrl/pack）
- `platform.*`（getLaunchContext/getPathForFile）
- `command.*`（命令注册，经 `@chips/ui` useCommandRegistry）

这部分占编辑引擎代码的约 15%，符合「应用只调用底层能力」的预期。

### 3.2 编辑引擎仍有大量「本应生态共用」的能力在本地自实现

以下能力目前是编辑引擎**本地实现**，生态内没有任何其他消费者可以复用（代码量合计约 1.1 万行）：

| 能力 | 本地实现位置 | 规模 | 应归属 |
|---|---|---|---|
| 卡片解包态文档读写/持久化/自动保存/资源生命周期 | `src/core/card-service.ts` | 1155 行 | **Host card 服务域（缺失）** |
| 卡片目录骨架初始化 | `src/core/card-initializer.ts` | 96 行 | Host card 服务域 |
| 箱子编辑会话/序列化/自动保存/条目管理 | `src/services/box-document-service.ts` | 1135 行 | **Host box 服务域（缺失）** |
| 编辑器资源会话（草稿/校验/防抖/资源队列） | `src/editor-runtime/*` | ~1200 行 | Host 编辑会话服务（缺失） |
| ZIP 目录导入（根探测/魔数/过滤/清理/回滚） | `src/editor-runtime/archive-import.ts` | 592 行 | Host 通用目录解包导入能力 |
| 封面生成/比例规范/图片封面 | `src/utils/card-cover.ts` | 147 行 | Host/共享模块 |

| 命令 undo/redo 历史 | `src/core/command-manager.ts` | 291 行 | Host/SDK 决策（当前悬空未接入） |
| 工作区文件树扫描/卡片箱子识别 | `src/services/workspace-service.ts` | 534 行 | Host 工作区/文件域 |

### 3.3 已确认的「重复实现」证据（同一能力多副本）

调查发现以下能力在生态内存在**两份以上独立实现**：

1. **MIME 猜测函数**：`card-service.ts guessMimeType`、Host `card-packer.ts guessMimeType`、`box-document-service.ts toMimeType`、`drag-drop-manager.ts detectFileType`、SDK `card.ts` 相关逻辑 —— 至少 4-5 处；
2. **相对资源路径规范化（normalizeResourcePath）**：编辑引擎 `card-service.ts`、`frame-host.tsx`、SDK `card.ts`、Host `card-service.ts`、`box-document-service.ts sanitizeAssetRelativePath`、`archive-import.ts` —— 至少 6 处；
3. **YAML 元数据序列化（metadata.yaml/structure.yaml 写盘）**：`card-service.ts persistCard`、`box-document-service.ts writeDocumentFiles`、`workspace-service.ts renameFile` —— 3 处；
4. **file:// URL 构造**：SDK `card.ts createFileUrl`、`box-document-service.ts createFileUrl` —— 2 处；
5. **默认封面 HTML 生成**：仅编辑引擎内部已做共享（`card-cover.ts`），但 Host 与生态无此能力，未来其他应用制作封面仍需重复；
6. **ID 生成**：编辑引擎 `generateId62` vs Host `createId` —— 2 处；
7. **封面比例规范化（normalizeCoverRatio）**：`card-service.ts`、`card-cover.ts` —— 2 处。

这些重复实现正是「能力未上移」的直接后果。

### 3.4 需要区分「生态决策已冻结」的两块

调查确认 task030 卸担计划已经做出正式决策（见 `生态共用技术文档/架构设计/15-主题系统设计.md`、`10-国际化架构设计.md` 的状态注记）：

- **主题系统（L11）已废弃**：全生态统一 antd `appleTheme` 单一苹果风格；编辑引擎 `theme-css.ts` 注释明确「不再读取 Host 主题」；
- **多语言系统已废弃**：全生态界面文案简体中文直写；编辑引擎 `messages.ts` 为本地中文文案表。

这两块**不是**本次「上移」的候选（已有正式废弃决策），报告仅在 01 篇中记录现状，不做翻案建议。若未来需要重新公共化，应单独发起决策。

### 3.5 上移方案的四类归属（已按用户 2026-08-11 决策定案）

依据 12 层架构（`生态设计原稿/03-层次结构.md`）与「底层厚上层薄」原则，编辑引擎本地自实现的能力按以下归属处理：

| 归属 | 形态 | 候选能力 |
|---|---|---|
| **A. Host 服务域（主进程，L2-L3）** | 新增/扩展服务动作，经内核路由对外 | 卡片文档编辑会话（card 域扩展）、箱子编辑会话（box 域扩展）、编辑会话资源协议（编辑器域）、ZIP 目录导入（资源域）、工作区扫描（文件域）、文档历史 undo/redo（会话服务） |
| **B. 共享功能模块（模块插件，无界面）** | 独立插件包，经 module.invoke 调用 | 封面生成与比例规范化、封面引用收集、文件类型识别、公共工具（MIME/路径规范化/ID/file URL） |
| **C. 共享组件层** | **不迁移**（用户决策） | 封面编辑面板、裁剪弹窗、封面模板、拖拽排序列表、文件树、窗口 chrome 壳、无限画布内核、窗口状态机——全部保留在编辑引擎页面域 |
| **D. 页面域保留（编辑引擎特有）** | 留在应用内 | 桌面编排（Dock、卡箱库、场景编排）、布局切换编排 |

> **决策记录（2026-08-11 用户确认）**：
> 1. 卡片文档域、箱子文档域、编辑器资源会话、封面体系、重复造轮子（MIME/路径规范化/YAML 序列化/file URL/ID/默认封面等）**全部工程化上移到 Host**；
> 2. undo/redo 历史栈**必须闭环**（作为 Host 会话服务的公共语义，不再是悬空实现）；
> 3. **取消**「无限画布/工作台作为独立布局插件」设计（该方向不再推进，画布与工作台留在编辑引擎页面域）；
> 4. **不迁移** C 类共享组件层（封面编辑面板/裁剪弹窗/模板、拖拽排序、文件树、窗口 chrome、画布内核、窗口状态机均保留在编辑引擎）；
> 5. **自动保存职责转移接受**：会话与自动保存由 Host 主进程管理，应用只订阅事件；
> 6. **内嵌卡片**：架构上允许（`box.session.addEmbeddedCard` 接口开放），一般默认使用链接引用；官方编辑引擎自身不提供内嵌操作入口；
> 7. **封面能力归属共享模块**（模块插件，无界面）；封面 UI 保留在编辑引擎；
> 8. **编辑态预览收敛程度 1**：保留编辑引擎本地装配层，但单卡 iframe 文档生成（CSP/资源基址/高度上报/交互代理）统一由 Host 提供，消灭双份实现；
> 9. 迁移过程必须同步做好**工程化拆分**：代码解耦成小模块、平台级/系统级规范、高质量实现（详见 09 篇第 6 章）。

详细方案与优先级见 [09-上移Host的方案与优先级.md](./09-上移Host的方案与优先级.md)。

## 4. 对「编辑引擎 = 套壳软件」目标的总体评价

**方向正确，且编辑引擎已经做到了一半**：

- 所有系统原语（文件、ZIP、资源转换、配置、插件、平台）都已走 Host，没有绕层直连；
- 渲染/显示链路（封面 iframe、箱子预览 iframe、基础卡片插件构建产物）复用 Host 托管链路；
- 唯一直接访问 `window.chips` 的代码点只有 `src/hooks/useChipsBridge.ts`（9 行），其余统一走 SDK client。

**剩下的一半**是：编辑引擎自己实现了**文档领域逻辑**（卡片/箱子/编辑会话/封面/导入），这些是生态未来的核心公共资产——查看器、社区客户端、第三方工具、未来的移动端编辑产品都需要同一套「文档读写、保存、资源生命周期」语义。这部分目前完全封闭在编辑引擎内部，任何新软件都无法复用，且已经出现了多处重复实现。

按 2026-08-11 已定决策，下一阶段将：**文档领域能力（卡片编辑会话、箱子编辑会话、编辑器资源会话、ZIP 目录导入、封面生成）工程化上移为 Host 公共服务/共享模块，undo/redo 历史闭环进会话服务，同步完成公共工具去重；编辑引擎保留页面域 UI（画布/窗口/封面面板等）与本地装配层（单卡协议统一走 Host 生成器）**。
