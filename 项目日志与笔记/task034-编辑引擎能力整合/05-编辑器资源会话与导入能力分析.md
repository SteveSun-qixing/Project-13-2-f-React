# 05-编辑器资源会话与导入能力分析

## 1. 现状

「编辑器资源会话」指：基础卡片编辑器（renderEditor）在 iframe 内编辑时，宿主侧提供资源解析、导入、删除、转换与 ZIP 目录导入的整套会话语义。当前存在**两套并行的协议与实现**：

### 1.1 Host/SDK 侧的正式编辑器资源桥（已有契约）

- SDK `card.editorPanel.render({ resources })` 支持本地桥接资源协议（`src/api/card.ts attachCardEditorResourceBridge`）：
  - `resolve` / `import` / `importArchiveBundle` / `delete` / `convertTiffToPng` / `extractVideoThumbnail` 六种动作；
  - 协议消息：`chips.card-editor:resource-request / resource-response / resource-release`；
  - `importArchiveBundle` 的请求/结果类型（`CardEditorArchiveImportRequest/Result`）已在 SDK 完整定义（根探测、entryFile、include 过滤、stripSingleRootDir、excludeSystemArtifacts、discardedEntries 分类）；
- 契约约束（`生态设计原稿/19-SDK与协议.md`）：`resourcePath` 一律使用相对卡片根目录路径；`import` 返回的 `path` 也是相对路径；`resources` 不进入 Host 正式 `card.renderEditor` 路由输入——**即 SDK 桥接层设计为「本地实现」**。

### 1.2 编辑引擎本地实现（完整业务逻辑在应用侧）

| 能力 | 位置 | 规模 |
|---|---|---|
| 编辑器 iframe 资源桥实现（消息监听、请求分发、30s 超时、错误归一） | `EditorHost.tsx` | 777 行中一部分 |
| 会话存储（source/draft/签名/dirty/校验/mount 计数/防抖提交） | `session-store.ts` | 390 行 |
| 待导入资源 blob URL 缓存与生命周期 | `EditorHost.tsx` + `frame-host.tsx` | 两处 |
| ZIP 目录导入全流程 | `archive-import.ts` | 592 行 |
| TIFF 转 PNG / 视频抽帧的会话编排（暂存、回写） | `EditorHost.tsx` | 委托 `client.resource.*` |

### 1.3 archive-import.ts 的核心逻辑（当前最完整、最值得上移的实现）

- **payload 根目录探测**：`resolveArchivePayloadRoot`（单一根目录剥离）/ `resolveGenericPayloadRoot`；
- **入口文件校验**：entryFile 存在性与类型检查；
- **内容过滤**：MIME 白名单 + 扩展名白名单（`include` 过滤）；
- **魔数嗅探**：`detectImageMimeType`（JPEG/PNG/GIF/WebP/BMP/AVIF/TIFF/SVG），不信任扩展名；
- **系统垃圾清理**：`__MACOSX`、`.DS_Store` 剔除；
- **暂存→移动→失败回滚**：先解压到临时目录，校验后移动到目标位置，失败清理；
- **结果结构化**：importedEntries/discardedEntries（directory/system-artifact/filter-mismatch/unsafe-path 分类）。

该逻辑与 `生态设计原稿/13-公共基础层设计.md` 中「目录解包能力应作为通用资源导入能力设计，通过过滤规则、入口文件和元数据返回表达不同业务需求」的正式方向完全一致，但当前实现封闭在编辑引擎应用内。

## 2. 问题与重复证据

1. **协议与实现割裂**：SDK 定义了 `importArchiveBundle` 契约，但执行者只能是编辑引擎应用（本地实现）；任何不包含编辑引擎代码的软件（查看器、社区、第三方）即使拿到契约也无法执行；
2. **ZIP 导入逻辑无法复用**：592 行高质量实现（根探测/魔数/过滤/回滚）封闭在应用仓；
3. **blob URL 资源缓存双份**：EditorHost 与 BasecardFrameHost 各有 pendingResourceImports 的 blob URL 缓存/释放逻辑；
4. **资源操作时序语义（节流窗口、删除登记、引用确认）** 在 card-service（卡片域）与 editor-runtime（会话域）之间分散。

## 3. 上移方案（建议）

### 3.1 目标形态一：Host 通用「资源导入」动作（最高优先）

在 `resource` 或新 `import` 服务域提供与 SDK `importArchiveBundle` 契约对齐的动作：

| 建议动作 | 职责 | 输入输出基线 |
|---|---|---|
| `resource.importArchive` | 解压 ZIP 到目标目录，执行根探测/过滤/清理/回滚 | 输入：zip 文件 + 目标根目录 + include 过滤 + entryFile + stripSingleRootDir + excludeSystemArtifacts；输出：rootDir/entryFile/resourcePaths/entries/discardedEntries |

- 输入输出类型直接复用 SDK `CardEditorArchiveImportRequest/Result`，一次收口两端；
- Host 主进程执行，天然具备文件系统权限与安全边界（路径逃逸校验收敛到 Host）；
- 编辑引擎 `archive-import.ts` 整体迁入 Host 后删除本地实现；EditorHost 只保留 30s 超时与消息分发（可继续用 SDK 桥或改为直接调用动作）。

### 3.2 目标形态二：Host 统一「编辑会话资源协议」服务

将 `resolve/import/delete/convertTiffToPng/extractVideoThumbnail` 的会话编排收口为 Host 动作（与 03 篇卡片编辑会话联动），应用侧不再需要维护 pendingResourceImports 队列：

- 资源 URL 解析统一走 `card.resolveResourceUrl`（持久资源）+ Host 会话暂存（待导入资源），blob URL 生命周期由 Host 会话管理；
- TIFF/视频帧转换的「暂存→引用→落盘」时序由 Host 会话控制；
- SDK `editorPanel.render({ resources })` 桥降级为「无 Host 会话时」的兼容形态或直接移除（当前无其他消费者，可一步收口）。

### 3.3 收益

- ZIP 导入、资源队列、转换编排成为生态公共能力，任何编辑器宿主（官方编辑引擎、第三方编辑器、未来移动端）直接复用；
- 消除 blob URL 缓存双份实现；
- SDK 契约与真实执行者不再割裂。

### 3.4 边界与风险

- 大文件导入（数百 MB ZIP）需要进度事件（可复用 module.job 任务模型）；
- 与 `zip.extract` 的区别要冻结：`zip.extract` 是原语（解到指定目录），`resource.importArchive` 是业务语义（根探测/过滤/清理/回滚）；
- 迁移时保持现有 592 行实现的测试（`tests/unit/archive-import` 相关）同步迁移，行为不得回退。
