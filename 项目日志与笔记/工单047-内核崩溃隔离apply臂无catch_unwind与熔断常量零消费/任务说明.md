# 工单047：内核崩溃隔离两缺口——apply 路径 panic 无 catch_unwind 致插件滞留 Starting、§6.8 崩溃重启熔断常量零消费

- 状态：开放
- 来源：2026-09-22 独立梳理审计（只读+文件整理批）新发现，主智能体重跑证据核证属实；建议并入 W3 P0-2（崩溃恢复面）验收
- 证据存档：`重构大计划/项目日志/2026-09-22-阶段性梳理/`（审计八件与梳理台账.db，findings 表）

## 一、背景与问题

《01-子系统设计/01-内核设计》§6.8（崩溃隔离与崩溃重启熔断）在册语义：插件运行体崩溃不得拖垮内核，判定/清理路径必须收敛到明确终态；崩溃重启须受「窗口内最大尝试数 + 指数退避」熔断常量约束。当前 chips-cordis 实码有两处与该在册语义不符：

### 缺口① apply 路径 Rust panic 无 catch_unwind，插件滞留 Starting

- 位置：`chips-ecosystem/packages/core-rust/crates/chips-cordis/src/command.rs:258-266`（`run_chain` 内 `tokio::time::timeout(apply_timeout, ticket.runner.apply(...))`），调用链起于 `command.rs:232-241`（`kernel.runtime().spawn(async move { ... })`）。
- 事实：`ticket.runner.apply(&ticket.context, &ticket.config)` 直接 await，无 `catch_unwind` 包裹。若 runner 的 `apply` 在 Rust 侧 panic（非返回 `Err`），行为链为：
  1. panic 使 `run_chain` 所在 spawned task 整体溃灭；
  2. `command.rs:234`（`send_state_reply`）、`:235-239`（`state.plugins.queued.remove`）、`:240`（`kernel.resume_pending()`）三处善后全部跳过；
  3. 等待 reply 的调用方只能靠超时侧兜底，插件状态机停在激活中（Starting），`queued` 集合残留，`resume_pending` 永不触发；
  4. 对照同文件超时臂 `ActivationOutcome::TimedOut` 与失败臂 `RunnerFailed` 均经 `finish_activation_command` 收敛——panic 臂是唯一不收敛出口。
- 影响：单个插件的 Rust panic 从「被隔离的失败判定」升级为「状态机滞留 + 队列残留 + 挂起恢复丢失」，违背 §6.8 崩溃隔离底线（架构底线速记「崩溃隔离」在册项）；W3 崩溃恢复验收（P0-2）必测面。
- 母型参照：cordis `EventSink` 面已有「catch_unwind 吞 panic」在册母型（见裁定F RFC 议题②登记），本缺口是判定/激活链上未覆盖的对应位。

### 缺口② §6.8 崩溃重启熔断常量已定义、零消费

- 位置：`crates/chips-cordis/src/constants.rs:46-55` 定义 `CRASH_RESTART_WINDOW`（600s）、`CRASH_RESTART_MAX_ATTEMPTS`（3）、`CRASH_RESTART_BACKOFF_INITIAL`（1s）、`CRASH_RESTART_BACKOFF_MAX`（30s）；`src/lib.rs:27-28` 仅 re-export。
- 事实：主智能体 2026-09-22 复跑 `grep -rn "CRASH_RESTART" crates/ --include="*.rs"` 排除定义/导出两文件后零命中——四常量在全 crate 无任何消费代码。
- 影响：§6.8 熔断语义（窗口内超限即停止重启、退避节奏）实码不存在，属「文档在册、常量占位、机制缺册」三态缺口；崩溃重启路径当前无界（若存在重启路径）或根本未实现，需与缺口①一并收口才可向 W3 P0-2 交付崩溃恢复验收。

## 二、期望行为（验收标准）

1. `run_chain` 的 apply 调用点具备 panic 捕获臂：panic 与 `Err` 一样收敛到 `ActivationOutcome` 既有在册失败语义（禁自造新变体/新错误码），善后三件套（reply/queued.remove/resume_pending）在 panic 臂同样执行，锁测覆盖「runner panic → 插件终态非 Starting、队列无残留、pending 恢复」。
2. §6.8 四熔断常量接入真实消费路径：窗口计数、超限拒重启、退避时长按常量取值，锁测覆盖三常量边界行为；若勘查结论为「崩溃重启机制整体未交付」，则按缺口如实升格描述并把机制交付纳入验收，禁止为消费而消费的装饰性引用。
3. `cargo test -p chips-cordis`、`cargo clippy -p chips-cordis --all-targets -- -D warnings`、`cargo fmt --check` 全 EXIT=0；既有用例零删减零放宽。
4. 文档面：修复后《01-内核设计》§6.8 描述与实码一致；若实现暴露文面歧义，以文档为准修实现并在本工单追加裁定注记。
