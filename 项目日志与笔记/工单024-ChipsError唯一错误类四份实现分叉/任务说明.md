# 工单024 —— 「全生态唯一错误类 `ChipsError`」事实上是四份互不兼容的实现（sdk / bridge / cli / host-preload）

> 登记日期：2026-09-20
> 来源：task043《契约-代码漂移审计-2026-09-20》面 1 第 5 条（W2 P0，需 RFC），并牵连该报告面 1 第 6、7 条与面 2 第 4 条（P1/P2 口径，留审计台账随本单一并裁定）；登记前已到代码复核。
> 性质：只登记问题，不含解决办法；归属裁定需 RFC（见第六节）。

## 一、背景

《02-SDK-API规范》§6.2（`薯片生态文档库/05-接口与契约/02.06-02-SDK-API规范-六、错误模型.md:29-44`）规定全生态只有一个错误类 `ChipsError`；`chips-ecosystem/packages/sdk/src/errors.ts:4` 的注释同样自述「全生态只有一个错误类」。审计发现该类在四个包中各有一份源码级实现，跨包传播时身份与守卫语义互不兼容。这是本轮审计判定的最严重架构级漂移（审计报告系统性结论 A）。

## 二、证据（文件:行号，均于 2026-09-20 复核）

1. 四处 `export class ChipsError`（grep 实测，源码面恰此四处）：
   - `chips-ecosystem/packages/sdk/src/errors.ts:38` —— `implements IChipsError`，构造入参 `IChipsErrorInit`（:11, :45）；
   - `chips-ecosystem/packages/bridge/src/protocol/errors.ts:23` —— `implements IChipsError`；
   - `chips-ecosystem/packages/cli/src/errors.ts:118` —— 不 implements 任何共享接口，构造入参 `IChipsErrorOptions`（:98, :127）且额外携带 `exitCode`（:137-138）；
   - `chips-ecosystem/packages/host/src/preload/chips-error.ts:27` —— `implements IChipsErrorShape`（本包私有形状）。
2. 守卫语义分叉（审计面 1 第 6 条）：SDK 侧 `isChipsError` 为结构判定、符合契约（`05/02.05:16` 规定「不读取原型链」，实现 `packages/sdk/src/errors.ts:62-68`）；bridge 侧 `packages/bridge/src/protocol/errors.ts:50-51` 为 `value instanceof ChipsError` —— 对本包类之外的任何 `ChipsError`（含跨 IPC 还原的普通对象）恒假。
3. 兜底策略分叉（审计面 1 第 7 条）：契约 `toChipsError` 为单参权威签名（`05/02.05:17`、`05/02.06:83-97`），host-preload 实现为三参 `(error, code, message)`（`packages/host/src/preload/chips-error.ts:78`，调用点 `packages/host/src/preload/bridge.ts:92` 注入 `BRIDGE_INTERNAL` 兜底码与文案）。
4. CLI 侧镜像（审计面 2 第 4 条）：`packages/cli/package.json:38-40` 声明依赖 `@chips/bridge` 与 `@chips/sdk`，同时自建 `IChipsErrorShape`（`packages/cli/src/errors.ts:90-95`）与私有 `ChipsError`（:118）。

## 三、影响范围

- 跨包 `instanceof` 与类型守卫语义不可靠：任何一处用 `instanceof` / bridge 侧 `isChipsError` 判定其它包抛出的 `ChipsError` 都得到假阴性；§6.4 归一链路（跨 IPC 普通对象在 preload 还原）在走 bridge 守卫的路径上漏判。
- 构造入参三形状并存（`IChipsErrorInit` / `IChipsErrorOptions` / `IChipsErrorOptions+exitCode` / `IChipsErrorShape`），错误对象跨层传递只能靠约定字段名对齐，无类型系统保障。
- 「SDK 只产生三个码」的收口口径（`05/02.06:75-81`）与 preload 三参兜底并行，形成第二套兜底策略。
- 涉及包：`@chips/sdk`、`@chips/bridge`、`@chips/cli`、`@chips/host`（preload），以及所有消费错误对象的插件与平台组件。

## 四、复现步骤

1. `chips-ecosystem` 内分别构建 sdk / bridge / cli / host。
2. 构造 `new (require('@chips/sdk').ChipsError)(...)`（或 import），在 bridge 上下文调用 bridge 侧 `isChipsError(err)` —— 得 `false`（bridge 判定为 `instanceof` 私有类，`packages/bridge/src/protocol/errors.ts:50`）。
3. 检索四处 `export class ChipsError`：`grep -rn "export class ChipsError" chips-ecosystem/packages/*/src` —— 四份实现即本单主体证据。

## 五、期望行为

全生态错误类收敛为单一事实源后，任何一层产生/还原的错误对象在其它任何层的守卫函数下得到一致的判定结果；`toChipsError` 的签名、兜底码策略与构造入参形状只有一份权威定义。

## 六、为何需要 RFC

唯一化涉及归属包裁定（类定义放 sdk、bridge 协议层还是独立底层包）、`@chips/bridge` 协议层与 `@chips/sdk` 的依赖方向、CLI 退出码扩展字段与 preload 还原链路的兼容策略——属跨包公共协议变更，按 AGENTS.md 架构红线需 RFC 裁定后再实施，故本单只登记问题与证据，处置随 RFC 走。
