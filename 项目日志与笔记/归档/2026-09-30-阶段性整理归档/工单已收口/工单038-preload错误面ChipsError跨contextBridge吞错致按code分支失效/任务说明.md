# 工单038 — preload 错误面 ChipsError 跨 contextBridge 吞错致按 code 分支失效

- 编号：038
- 状态：在册待收口（修复波归属：任务 #117，文件面 `packages/host/src/preload/**`）
- 登记日期：2026-09-21
- 登记来源：任务 #115（金链路刀7 E2E 真进程载体，验收证据 B）独立复现确认

## 一、问题

主进程 → 壳进程（preload）→ 渲染进程的跨桥错误语义在 contextBridge 处被吞没，共两处：

1. **ChipsError 跨桥降级为无信息 Error**：Bridge 线格式封套（wire envelope）本身完整到达壳进程，但经 `contextBridge` 暴露面回传渲染进程时，`ChipsError` 实例（`@chips/bridge` 自定义 Error 子类）在序列化边界上被克隆为原生 `Error`，`code` / `message` / `retryable` / `details` 全部丢失，渲染侧收到 `Error('')`（message 为空串）。凡按 code 分支的调用方（如金链路 E2E 的坏协议臂、 ghost 臂）无法区分错误类别。
2. **`window.chips.request('')` 预检拒绝被吞**：preload 侧对空 payload 的同步预检应拒绝（`BRIDGE_INVALID_INPUT` 语义），当前实现该拒绝发生在桥后异步链路内，且同样受 ① 影响——调用方拿不到可判定的错误对象，部分路径表现为 resolve。

## 二、影响

- 违反《RFC-ChipsError统一裁定》核心承诺：错误对象跨面传递保持 `code` 可分支、`retryable` 可判。渲染进程作为最重要的消费端目前只能拿到匿名 Error，统一错误码体系在「主进程→渲染进程」这一段断链。
- 金链路 E2E 真进程断言被迫放松：`golden-chain-w2.spec.ts` 错误臂目前只能断言「收到 Error」而不能断言 code，属文档-代码不一致的测试面侵蚀点。
- 插件与宿主 UI 在渲染侧的一切错误处理（重试提示、权限降级文案、能力缺失兜底）在该段全部退化，影响范围覆盖所有经 preload `window.chips` 的调用失败路径。

## 三、证据

- 复现载体：`chips-ecosystem/packages/host/tests/e2e-host/`（E2E 真进程 app-launch 链路，`CHIPS_E2E_REQUIRE_APP=1`），#115 交回记录证据 B；主智能体验收轮在真进程面独立复现确认（跨桥后 `err instanceof ChipsError === false`、`err.message === ''`、`err.code === undefined`，线封套字段在壳进程侧仍完整）。
- 桥面实现：`packages/host/src/preload/**`（contextBridge 暴露面）——自定义 Error 子类不经结构化克隆保留原型与自有属性，是 ① 的机理。
- 正确形态先例（仓库内已验证）：`chips-ecosystem/tests/e2e/fixtures/app/preload.cjs:26-28` ——先例做法是桥面把错误重建为纯数据对象（或经 `contextBridge` 暴露的工厂函数在目标世界重建 Error 实例），保留 `code`/`message`/`retryable`/`details` 全字段。
- 权威口径：`薯片生态文档库/05-接口与契约/RFC-ChipsError统一裁定`（按 code 分支为契约承诺）；《05-渲染引擎设计》§3.1 渲染进程安全基线要求错误语义可判定。

## 四、期望行为与验收

1. `window.chips.*` 任一调用失败时，渲染进程收到的错误对象携带完整语义：`code` 可分支、`message` 非空且与主进程侧一致、`retryable` 为布尔、`details` 可用；实现形态不限（纯数据错误对象或桥后重建的 Error 实例），但不得向渲染侧泄露 `ipcRenderer` / `invoke` 等原生通道（contextIsolation 与最小暴露面红线不动，参照 preload 双世界裁定 `__chipsHostViewChannel` 键集锁的口径）。
2. `window.chips.request('')`（及等价非法输入）在预检处即拒绝，拒绝对象可被调用方同步/立即 await 捕获，语义为 `BRIDGE_INVALID_INPUT`、`retryable: false`，不得 resolve。
3. `golden-chain-w2.spec.ts` 与 e2e-host 中因本缺陷放松的错误臂断言翻转为按 code 严格断言（不得留放松臂）。
4. 新增/改写定点测试锁定 ①②（桥后错误面字段级断言 + 预检吞错臂），套件的既有断言零改动零删除。
5. 验收闸：`packages/host` 的 `test` / `typecheck` / `lint` / `build:main` 全 0；`CHIPS_E2E_REQUIRE_APP=1` 定点 e2e-host 套件 0；既有 smoke（`CHIPS_HOST_SMOKE=1`）不回退。

## 五、暂行处理

- 不许诺时间线；刀7 全绿转正前本缺陷必须收口（E2E 断言质量依赖项）。

## 六、收口记录（修复波：任务 #117 · preload-038-agent，2026-09-21）

### 方案（修复形态定案）

桥面纯数据错误对象：`window.chips` contextBridge 挂载面的全部失败臂在跨界前归一为
`ChipsError.toPlain()` 同构普通对象（`code`/`message`/`retryable` 恒输出、`details` 有值时输出），
即《01-Bridge-API规范》§2.5「跨上下文传回的恒为普通对象」与《RFC-ChipsError统一裁定》§4.3
「`toPlain()` 为跨 IPC / contextBridge 唯一传输形态」的既有文档口径的兑现——文档本已正确，
本次是实现随文档。渲染侧判定走结构守卫 `isChipsError`（RFC §4.2 条 3 跨 Realm 唯一权威），
还原点 `ChipsError.fromPlain`；`instanceof ChipsError` 不再作为跨界形态依赖。

机理核实（Electron 40.8.0 `shell/renderer/api/electron_api_context_bridge.cc` 源码级）：
`Error` 族实例（含自定义子类）作为 Promise 拒绝值跨界命中 `IsNativeError()` 分支，被替换为
目标世界重建的匿名 `Error`（跨 context 读取 `message` 失败时消息一并清空 → 实测 `Error('')`），
自定义字段与原型全丢；纯数据对象走 `CreateProxyForAPI` 代理臂，自有可枚举字段完整保真。
同步抛出臂（`ProxyFunctionCallback` 异常臂）原生仅透 `message` 重建 `Error`——contextBridge
机制不承载自定义字段，属 Electron 平台边界；归一抛出值仍按同一口径送达，消息与主进程侧同源。
