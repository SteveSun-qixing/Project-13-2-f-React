# 工单 012：`chips-native` Neon 绑定层运行时函数缺少可离线执行/可度量的测试注入点

> 登记：W1-COV-NATIVE（2026-09-20）
> 状态：待处理
> 影响：`packages/native`（`chips-native`）Rust 行覆盖率门禁（W1 要求 >90%）、绑定层可测性口径

---

## 一、背景

W1 要求把 `chips-native` 的行覆盖率（行数口径）提升到 >90%。经补测后，crate 内可离线
执行的纯逻辑（指针转义 / `2^53` 边界 / 整数保型 / 非法 UTF-16 / 错误构造与归一形状 /
监听令牌翻译表 / 取消令牌状态 / 信封结构校验）已补齐真实单测，`chips-native` 由
140/617（22.7%）提升至 155/617（约 25.1%）。

但 `chips-native` 的主体可执行行是 Neon 导出函数与 `Context<'a>` 泛型辅助（类型映射、
错误映射、句柄持有、异步回投、模块注册）。《核心接口规范》§8.1 明确规定绑定层「不实现
业务逻辑，只做类型转换与错误归一」，即这些函数的职责本身就是 Node-API（napi）运行时
I/O 适配，不存在可与之分离的纯业务内核。这类函数需要一个真实的 napi `Env`（V8 isolate）
才能执行，而当前测试口径无法满足，导致其无法计入行覆盖。

## 二、证据

1. **测量口径为源码级插桩，只统计 test 二进制内实际执行的行。**
   `cargo tarpaulin --workspace` 在 Apple Silicon 走 LLVM 源码插桩：日志见
   `Generated: target/tarpaulin/profraws/chips_native-*.profraw`、
   `Mapping coverage data to source`。凡未在插桩进程内执行的行一律 0 覆盖。
2. **Neon `Context` 只能由 Node 生命周期构造，crate 内无离线注入点。**
   - `neon` 1.1.1 全仓不存在 `TestContext` / `MockContext` / 任何 mock/测试上下文；
   - 不存在 Rust 侧可调用的 `create_env`；`Cx::from_raw` 需真实 `sys::Env`（`unsafe`，
     由 Node 在模块注册/回调时提供）；
   - 因此 `FunctionContext` / `ModuleContext` / `Cx` 及 `Channel::new(cx)` /
     `Deferred` / `Root::new(cx, …)` / `JsBox` 均无法在 `cargo test` 内离线构造。
3. **Node 子进程执行不被归因。** 绑定层只能在 Node `require` 已构建的 `.node` 时运行；
   该运行发生在未被插桩的子进程内，`cargo test` + tarpaulin 无法把其计入 `chips-native`
   的 Rust 行覆盖（既有的 `scripts/check-types.mjs`、`check-abi.mjs` 与开发日志记录的
   「Neon 模块运行时冒烟」均验证了这一 Node 侧链路，但不进入 Rust 覆盖率）。
4. **逐文件残留（补测后仍为 0 或极低的均为 napi 运行时函数）：**
   - `abi.rs 0/7`：`register`（`ModuleContext`）、`core_version`/`core_abi_version`
     （`FunctionContext`）；
   - `cancel.rs 6/12`：`js_create_cancel_token` / `js_cancel_token_cancel`；
   - `handles.rs 0/78`：`JsServiceValue::from_js/to_js/Drop`、`JsCallback::new/
     dispatch_*/Drop`（全部 `Root`/`Channel`）；
   - `context.rs 32/140`：7 个 `js_context_*` 导出、`context_argument`/
     `string_array_argument`/`kernel_error`、`JsListenerSink::enqueue`；
   - `convert.rs 50/202`：`json_to_js` / `js_to_json` / `convert_js_value` /
     `convert_js_array` / `convert_js_object` / `is_plain_object` / `is_other_typed_array`；
   - `envelope.rs 35/89`：`bin_from_js` / `bin_to_js` / `json_with_bin_to_js` /
     `binary_bytes`；
   - `error.rs 24/66`：`throw_chips_error` / `chips_error_from_js`；
   - `runtime.rs 8/23`：`spawn_result` / `settle_json` / `id_to_js_number`。

## 三、影响范围

- `chips-native` 在「`cargo test` + 源码插桩」口径下无法逼近 90%；W1 Rust 覆盖率门禁对
  本 crate 的达成取决于绑定层是否有可离线执行/可度量的测试口径，而非纯逻辑是否补测；
- 与工单005（能力内核 `chips-bridge` 未交付）、工单011（G6 覆盖率门禁报告路径/阈值双
  事实源漂移）叠加：绑定层运行时函数的覆盖度量口径目前在生态内没有统一收口；
- 不影响运行期正确性：导出面在 Node 侧冒烟与 JS 类型/契约检查中已被验证。

## 四、复现步骤

1. `export PATH="$HOME/.cargo/bin:$HOME/.volta/bin:$PATH"`
2. `cd chips-ecosystem && cargo test -p chips-native`（45 通过 / 0 失败）。
3. `cd chips-ecosystem && pnpm test:coverage:rust`。
4. 观察 `packages/native/src/*` 逐文件 Tested/Total：纯逻辑文件已逼近可测上限，
   `abi.rs`/`handles.rs` 仍为 0，其余低覆盖文件的残留行全部是 §8.1 定义的 napi 运行时
   导出/辅助函数；在 `cargo test` 内尝试构造 `FunctionContext`/`Cx`/`Channel` 无可行入口。

## 五、期望行为（验收口径，不含解决方案）

1. 绑定层运行时函数应存在可被 CI 覆盖率管道归因的测试口径：要么在 crate 内可离线执行
   （受控 napi/引擎环境的正式测试基座），要么覆盖率度量管道能把「Node 加载 `.node` 驱动
   导出面」的执行计入 `chips-native` 的 Rust 行覆盖；二者取其一，由生态统一决策落地。
2. 在该口径收口前，`chips-native`（及后续所有 Neon 绑定 crate）的 >90% 行覆盖门禁应显式
   标注为受本工单约束的架构缺口，不得以空断言/无意义用例或调低阈值来凑数。
3. 验收证据：给出可复现的度量方式与 `chips-native` 逐文件行数，明确区分「纯逻辑可测」
   与「napi 运行时依赖本工单」两类残留。

## 六、暂行处理

- W1-COV-NATIVE 本轮：补齐并保留全部可离线执行的真实单测（convert/envelope/error/
  context/cancel/handles 纯逻辑层），不新增任何为凑覆盖率的空断言，不改动阈值/门禁/
  `tools/` 配置，不删改既有断言；
- 在 `packages/native/开发日志.md` 逐文件登记因本工单不可覆盖的函数清单与根因；
- 绑定层运行时函数的 Node 侧链路继续由 `check-abi.mjs`、`check-types.mjs` 与运行时冒烟
  兜底；Rust 行覆盖门禁对 `chips-native` 待本工单收口后再复测。
