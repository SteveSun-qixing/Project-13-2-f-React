# 工单 019：插件签名信任根无正式注册与注入链路

> 登记日期：2026-09-20
> 状态：已收口（2026-09-21 W2 #46，见同目录 `收口记录.md`）
> 发现途径：task043 W2-P0-3 前置作业「cpk 夹具链」——真实 Ed25519 签名正夹具在 CLI 正式命令面上无法完成签名阶段验收

---

## 一、问题

《03-插件包格式》§6.3 把「信任根注册表、密钥生成、签名工具与分发」归入发布链路并按《06-更新与分发规范》Phase 3/4 落地，但当前整条**校验消费面**没有任何正式挂点可以喂入信任根：

1. `chips plugin validate <.cpk>` / `chips plugin install <.cpk>` 的 user 渠道走到签名阶段时，`createLocalArtifacts` 的 `trustRoots` 恒为空对象——CLI 没有 `--trust-root` / `CHIPS_TRUST_ROOTS_FILE` / 配置文件任何一条注入路径，导致**任何结构合法的签名包在 CLI 面上必然 `CPK_SIGNATURE_INVALID`（`信任根未注册的 keyId`）**。
2. 引擎库面（`createLocalArtifacts({ trustRoots })` / `validateCpk({ trustRoots })`，`@chips/cli` 公开导出）支持注入，但只有编程调用可用；Host 装载器（W2-P0-3）与任何 CLI 用户都缺一层「信任根从哪里加载、按什么 schema 登记」的正式契约。
3. 本次夹具链作业已按签名口径落地了一个可作事实样例的信任配置形态（`chips-ecosystem/tests/e2e/fixtures/cpk/keys/trust-roots.json`：`{ version, trustRoots: { <keyId>: <SPKI PEM> } }`），但它属测试资产，不是生态正式契约；正式形态（文件位置、注册表归属、与渠道规则的结合方式）需要裁决。

## 二、证据

- `packages/cli/src/artifacts/cpk-validate.ts:478-484`：`trustRoots[keyId] === undefined` 即抛 `CPK_SIGNATURE_INVALID`；`packages/cli/src/artifacts/index.ts:79` 只透传构造期注入的 `options.trustRoots`。
- `packages/cli/src/commands/plugin.ts:223-252`：`plugin validate` 命令面无任何信任根参数；`packages/cli/src/runtime/local-client.ts:31` 缺省组装时 `trustRoots` 为空。
- 实测（workspace CLI 正式入口，正夹具）：
  `node packages/cli/dist/bin.js plugin validate tests/e2e/fixtures/cpk/packages/hello-0.1.0.cpk`
  → EXIT=1，`{ "code": "CPK_SIGNATURE_INVALID", "message": "信任根未注册的 keyId：chips-fixture-2026", "details": { "stage": "signature", ... } }`（归档/结构/清单三阶段均通过，仅签名阶段因无注册表而必败）。
- 对照：同一夹具经库面 `createLocalArtifacts({ trustRoots: { "chips-fixture-2026": <SPKI PEM> } })` 校验，五阶段全部通过、`signature:passed`（见 `tests/e2e/fixtures/cpk/generate-cpk-fixtures.mjs --check` 的校验矩阵，EXIT=0）。

## 三、影响

- W2-P0-3「Host 插件装载器 + 插件链 E2E（装载→能力→事件）」需要一条**可断言签名有效**的在用验收面；当前只能绕道库面注入，CLI 面上签名能力实质不可验证。
- `builtin` 渠道「必须签名」的门禁（§6.3）在缺少注册表面时无法端到端证明：既验不了真签名，也验不了拒真行为。
- 各消费方（CLI、Host 装载器、未来的更新链路）若各自私建信任根加载逻辑，将形成第二事实源，违背「签名与信任根判定语义冻结」的设计边界。

## 四、期望行为（验收口径）

1. 生态对「信任根注册表的加载来源与配置 schema」有唯一正式口径（CLI 命令面或平台配置目录，二者取其一并写入《03-插件包格式》§6.3 与《07-CLI完整参考》§3.5），Phase 3/4 之前也至少有开发态的可注入正式面。
2. `chips plugin validate <签名包>` 在按正式口径登记 keyId→公钥后，能对真实 Ed25519 签名包输出 `signature:passed` 并退出 0；未登记/不匹配时按 `CPK_SIGNATURE_INVALID` 拒绝且 `details.stage='signature'`。
3. W2-P0-3 装载器用例与 cpk 夹具链的签名正例不再依赖调用方私建的注入约定，统一消费第 1 条的正式口径。
