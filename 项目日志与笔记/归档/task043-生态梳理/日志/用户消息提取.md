声明式、语义化、自适应的平台抽象
（Declarative, Semantic, Adaptive Platform Abstraction）


如果只挑一个词，叫 平台抽象（Platform Abstraction）；如果从苹果文档语境，叫 自适应 UI / Adaptive UI；从架构角度，叫 控制反转 + 接口与实现分离。
SwiftUI 的哲学不是单一原则，而是一组相互支撑的技术与设计信念。它把界面开发从“命令式地创建、配置、同步、绘制和适配视图”，转为“声明意图、持有状态、组合语义、交给系统实现”。其核心可以这样阐述：


声明式与意图优先
开发者描述在给定状态下界面应该具有的结构、层次、语义和关系，不描述创建、布局、绘制、更新、销毁的具体过程。框架负责把声明转换为实际渲染树，并在状态变化时计算差异、执行更新。


状态是唯一事实来源，视图是状态的函数
界面不是被手动修改出来的，而是状态在某一时刻的投影。状态变化是界面变化的根本驱动力。框架追踪依赖、重新求值、比较差异，并以最小代价更新界面。开发者不再维护“视图与数据一致”这件事。


单向数据流与显式依赖
状态向下传递，事件向上反馈。绑定、观察、环境等机制形成显式依赖图。数据流方向明确，状态所有权清晰，减少隐式耦合、竞态和不可追踪的副作用。


组合优于继承，值语义优先
视图是轻量、可组合、可替换的声明单元。复杂界面由简单视图组合、修饰、包装而成。修饰符是变换，不是属性设置。值类型带来可预测性、隔离性、可测试性和更低的状态共享风险。


语义化 API 与契约稳定
API 表达角色、意图、层级、关系、材质、颜色、字体、间距等语义，不暴露具体像素、坐标和平台控件实现。开发者依赖的是接口契约，不是某一种实现细节。系统可以在契约不变的前提下替换实现。


自适应与平台托管
布局、外观、行为由系统结合设备形态、窗口尺寸、方向、尺寸类、安全区、输入方式、环境特征、可访问性、本地化、主题等因素决定。开发者声明关系与意图，系统计算几何、位置、样式和适配结果。


控制反转与关注点分离
框架控制生命周期、渲染、布局、动画、事件分发和资源管理；开发者控制状态与业务意图。内容、状态、布局、外观、动画、平台适配、可访问性彼此分离。框架调用开发者，而不是开发者手动驱动框架的每一步。


外观、行为与实现分离
标准控件、导航、标签、工具栏、材质、转场和视觉语言由系统设计系统提供。系统更新可以替换外观与行为的实现，而不改变应用依赖的接口。动态链接与稳定的运行时契约使旧应用也能获得新平台行为。自定义越多，自动适配越少；语义化标准越多，平台托管越多。


动画与交互内建
动画与状态变化绑定。开发者声明状态目标，系统负责插值、时间、曲线、转场、共享元素和中断处理。交互连续性和视觉一致性由框架统一保证，而不是由每个应用各自实现。


类型安全与声明式 DSL
Swift 的类型系统、结果构建器、属性包装器、不透明返回类型、泛型、协议、并发和观察机制，使声明式语法保持编译期检查、可组合、可扩展，同时隐藏复杂类型和实现细节。


跨平台与原生体验
同一套声明可以在不同平台和设备形态下由系统适配为符合平台惯例的原生体验。可访问性、本地化、动态字体、主题等作为环境语义参与，不是事后补丁。


即时反馈与迭代
预览、实时重载和编译期检查缩短反馈循环，使声明式开发可探索、可验证、可快速调整。开发者在描述意图的同时，能立即看到系统如何解释这些意图。


性能与一致性由框架保证
框架通过依赖追踪、差异计算、按需更新和渲染优化，减少手动同步带来的错误与性能负担。开发者不再维护视图树一致性，框架保证状态与界面一致。


哲学本质
SwiftUI 的哲学是：应用表达“应该是什么”和“为什么”，系统负责“怎么做”和“长什么样”。平台适配、外观实现、布局计算、动画过程和运行时行为被收回到系统层。应用依赖接口而非实现，依赖语义而非像素，依赖状态而非命令。因此，系统演进时可以统一替换实现，而符合语义化、自适应和平台托管原则的应用无需重写。


总结起来，SwiftUI 的哲学是：意图优先、状态驱动、组合构建、语义表达、控制反转、平台托管、契约稳定、系统实现。它不只是一个 UI 框架，而是苹果平台抽象哲学在界面层的体现。
拆开看，它其实是好几种技术设计的组合：


维度	技术名称	含义
UI 范式	声明式 UI	开发者描述“界面是什么”，不描述“怎么画”
API 设计	语义化 API	用角色、意图表达，如 .primary、.regularMaterial，而不是具体颜色和坐标
布局	自适应布局 / 响应式布局	用 Size Class、Safe Area、Trait 等让系统决定位置和尺寸
架构	控制反转 IoC	框架调用你的代码，而不是你手动控制所有流程
架构	关注点分离	内容、状态、表现、平台适配分开
渲染	系统控件 + 设计系统	导航栏、标签栏、按钮、材质由系统统一绘制
视觉	主题化 / Skinning	液态玻璃这类外观由系统替换，App 使用语义材质即可跟随
运行时	动态链接 + ABI 稳定	App 运行时调用系统框架，系统更新替换实现，旧 App 仍能工作
设计理念	平台一致性 / 原生体验	遵循 HIG，系统保证不同设备形态下的统一体验
所以，苹果能做到“系统一更新，很多 App 自动变”，本质不是远程改代码，而是：


开发者依赖的是接口契约，不是具体实现。系统更新替换了框架实现，但接口没变，所以 App 自动获得新行为。


比如：


TabView 是语义：“我要一个标签容器”，不是“在底部画一个栏”。


.regularMaterial 是语义：“我要一种常规材质”，不是“画一层半透明灰色”。


Auto Layout / SwiftUI 布局是语义：“放在安全区底部”，不是 y = 700。


这些都属于 面向意图编程（Intent-based Programming） 和 平台抽象。


一句话总结：


这叫“把平台适配和外观实现收进系统框架，开发者只描述意图”的设计。核心术语是：声明式 UI、语义化 API、自适应布局、控制反转、动态链接与平台抽象。

DeepSeek Harness 的设计哲学、架构特点与技术方法，共同指向一个核心目标：构建一个能够自我进化（Self-Evolving）的 Agent 运行时。其核心主张是 “一切皆插件”（Everything is a Plugin），旨在将传统 Harness 的固定结构彻底解耦，实现极致的灵活性与可扩展性。


🧠 设计哲学：一切皆插件
DeepSeek Harness 的设计哲学是对传统 Agent 框架的一次根本性重塑。它不满足于仅将工具作为插件，而是将模型适配器、工具注册表、会话日志，乃至 Agent 主循环（Agent Loop）本身全部设计为可插拔的组件。这意味着框架中不存在一个“不可修改的特权核心”，整个 Harness 就是由插件拼装而成，为 Agent 在运行过程中生成、替换自己的组件（即“自进化”）奠定了基础。


这一哲学的背后，是解决一个被忽视的根本问题：动态组合的可靠性。如果 Agent 要修改自己的运行时，那么修改后必须能够安全地“撤销”和“重组”。为此，DeepSeek 与北京大学合作发表了论文《一套处理时空可组合性的编程范式》，其核心正是 Cordis 元框架，它解决了两个关键难题：


时间可组合性 (Temporal Composability)：确保插件卸载时，其产生的所有副作用（如事件监听、资源占用）能被完整撤销，如同“后悔药”一般。


空间可组合性 (Spatial Composability)：解决组件间的动态依赖问题，当某个服务被替换或消失时，依赖它的组件能自动协调生命周期。


🏗️ 架构设计特点：基于 Cordis 的插件树
DeepSeek Harness 的架构建立在 Cordis 插件系统之上，形成了一棵可动态配置的“插件树”。


分层装配架构
运行实例并非写死的模块，而是通过 Profile、Bundle 和 Patch 逐层合成：


Profile：具名部署组合（如 Web、Headless），声明需要加载的 Bundle。


Bundle：可分发的配置层，包含配置行和对应的插件代码，提供通用能力（模型、工具、会话等）。


Patch：允许在部署时替换、插入或修改配置行，实现无需 Fork 源码的灵活定制。


三大核心机制
支撑这一架构的关键机制包括：


可逆副作用 (Reversible Effects)：这是 Cordis 的纪律性要求。插件对系统的任何修改（服务注册、事件监听）都会被记录，卸载时可逐层撤销，解决了传统插件框架常见的状态残留与“系统变脏”问题。


服务/事件协作 (Service/Event Collaboration)：插件间通过声明式的服务进行能力依赖，通过类型化事件进行跨插件协作和策略拦截。所有生命周期事件都是可监听的扩展点，为干预 Agent 行为提供了明确入口。


作用域与预设复用 (Scope & Preset)：通过 Scope 作用域隔离，同一进程内可以运行多个拥有不同人格、提示词和工具集的 Agent。Agent 的插件挂载在自己的 agent.ctx 中，实现了能力的精细化隔离与复用。


⚙️ 技术设计方法：面向长任务的可靠性
在“一切皆插件”的架构之上，DeepSeek Harness 针对长任务可靠运行的核心痛点，采用了系统化的设计方法。


可替换的 Loop 机制
为了应对不同场景，Harness 提供了多套执行机制，而非一个通用的 Loop：


基础 Agent Loop：驱动默认的轮次与步骤执行。


Goal Round：在当前会话中持续执行，保留完整的对话上下文。


Ralph Run：由多个独立的子 Agent 轮次组成，不继承父级对话历史，通过共享工作区和结构化交接报告传递信息，适合需要“重新开始”的复杂任务。


事件驱动的持久化状态
会话状态通过仅追加的、类型化的 SessionEvent 日志来管理，这是系统唯一的真源。这种事件溯源（Event Sourcing）设计使得会话完全可回放，为长任务审计、调试和从崩溃中恢复提供了坚实基础。


按需暴露的工具 Schema
模型理解的“外部世界”完全由 Harness 暴露的工具 Schema 定义。工具的名称、描述、参数和返回结果共同构成了模型的行动空间。Harness 可以按需动态暴露工具，而非一次性加载全部工具，有助于在长任务中控制上下文长度和保持模型焦点。


分层权限控制与多维验证
针对无人值守任务，Harness 设计了分层权限控制，例如在特定预设模式下可启用“自动批准”结合 LLM 分类器作为工具调用的唯一关口。同时，它强调多维验证体系，明确将“测试全部通过且应用正常启动”等客观标准作为任务完成的依据，而非仅依赖 Agent 的自我声明，以解决“验收失真”问题。


💎 总结
DeepSeek Harness 的设计是一场围绕 “动态可组合性” 的深度工程实践。它以 Cordis 元框架为基石，通过可逆副作用和作用域隔离确保了“一切皆插件”架构的可靠性；再以事件溯源日志和可替换的 Loop 机制等方法，将这种架构优势转化为面向长任务的实际工程能力。其最终愿景，是让 Agent 能够像飞机在空中更换零件一样，在不停止服务的情况下，安全地修改和进化自身的运行时。

## 三、进程与运行时架构


| 进程 | 内容 | 职责 |
|---|---|---|
| **主进程** | Node.js + Electron main + **Rust 核心（经 Neon）** | 内核、Bridge、解析、资源、文档服务、权限——平台本体 |
| **渲染进程** | React + 插件 UI + 渲染帧（iframe 沙箱） | 只做 UI 与业务表达，全部系统访问走 `window.chips` |
| **preload** | 薄壳 | 只做转发、订阅登记、错误还原、快速失败预检（不构成安全边界） |
| **工具进程**（按需） | 重计算任务 | 隔离重活，不阻塞主进程 |


**Rust 核心的并发模型**（内核红线 K-1～K-5）：


- 全部可变状态由**内核命令循环独占写入**；其余线程只读不可变快照；
- 调用插件代码时**不持有内核锁**，**不持锁 await**；
- 插件 panic 不得破坏内核状态、不得影响其他插件；
- 生产代码禁 `unwrap()` / `panic!`；`unsafe` 必须带 `# Safety` 说明。

## 四、内核：Cordis 运行时（Rust 重实现）


**定位**：插件运行机制的唯一下沉实现，不感知插件角色（四角色共用同一套加载/依赖/生命周期）。


| 组件 | 职责 | 不变量 |
|---|---|---|
| PluginManager | 状态机、依赖图、加载卸载事务 | 任一插件任一时刻只有一个状态 |
| ContextRegistry | Context 树、作用域、生命周期 | 子 Context 先于父销毁 |
| ForkRegistry | 副作用登记与逆序撤销 | 每个副作用只撤销一次，销毁后**零残留** |
| ServiceRegistry | 服务表、注入、代际 | 读路径不取写锁；写路径快照原子替换 |
| EventBus | 监听表、同步派发 | 派发期间不持写锁；无监听器零分配 |


**核心机制**：`Context`（作用域树）+ `Fork`（可逆副作用）+ `provide/inject`（服务注册与依赖注入）+ 拓扑排序与环检测（依赖解析）+ 级联重建（服务替换）。**一切副作用可逆，一切依赖可替换，一切状态可回放**——这是"动态可组合"的工程实现。

## 五、Bridge：能力架构（唯一门）


### 5.1 三层职责


| 层 | 职责 | 明确不负责 |
|---|---|---|
| 插件层 | 发起请求、订阅事件、创建句柄、按 `ChipsError.code` 处理结果 | 身份声明、授权判断（输入一律不可信） |
| Bridge 层 | 会话解析、能力注册表、权限判定、JSON Schema 校验、路由、超时/取消/并发、事件通道、错误归一 | 业务实现；Cordis 生命周期 |
| Host 层 | 能力实现、系统 API 封装、资源级二次约束（路径安全、域名白名单） | 不重复权限与校验；不反向调用插件 |


### 5.2 三条链路


1. **能力调用**：`chips.request(id, input)` → preload 生成 `requestId` → `bridge:request` → 会话解析 → 注册表 → 权限 → schema → 超时/并发 → 内核路由 → Host 执行 → 错误归一 → 返回。
2. **事件订阅**：Host 事件总线 → `event:<eventId>` 单向推送；插件发布事件必须走能力 `event:publish`，**没有独立发布通道**。
3. **资源访问**：`chips.resource(uri)` → `bridge:resource` → 句柄代理 → Resolver / Provider → `IResourceHandle`（读、区间、流、释放）。


### 5.3 关键机制


- **能力形状**：`id / execute / schema / permissions`——能力（做什么）与权限（能碰什么）是两个不同概念，各有一套 ID 体系。
- **身份不可自报**：调用方身份只由 Bridge 按 IPC 来源解析，请求里带的身份字段只作诊断。
- **渲染进程不可信**：会话有效性 → 权限 → schema 三步校验全部在主进程完成。
- **平台自身同链路**：平台内部调用同样过注册表、权限与校验，不绕行。
- **会话（Session）**是身份与限权单位：一个插件运行实例绑定一个渲染宿主即为一个会话，权限快照随之冻结。

- `manifest.yaml` 是唯一权威清单；`.cpk`（ZIP Store）分发；独立仓库、独立版本、独立发布。
- 启用即创建 Fork，停用即 `dispose()`；支持热插拔与不停机更新。
- 通信只有三条合法路径：**服务注入 / 能力调用 / 事件订阅**。

## 七、内容架构：五链一条线


卡片与箱子的**解析、资源、渲染、封面、编辑+写入**共用同一条链路、同一套接口；唯一分支点是 `DocumentKind`（`.card` / `.box`）。**禁止并行管线、禁止第二套解析器。**


| 链 | 权威设计 | 关键约束 |
|---|---|---|
| **解析链** | 06-文档解析器设计 | 只读；目录态与 ZIP Store 双模式；schema 校验；增量解析；错误修复不掩盖问题 |
| **资源链** | 04-资源管理设计（→ 统一文件系统） | 句柄制；一切皆挂载、差异止于 Provider；缓存只是优化不是事实源 |
| **渲染链** | 05-渲染引擎设计 | 只读投影；渲染帧 iframe 沙箱；资源代理注入；高度自适应；编辑态就近渲染 |
| **封面链** | 01/02-文件格式规范 | `cover.html` + `cardcover/` / `boxcover/`；条目卡渲染走封面视图（BoxCoverView） |
| **编辑+写入链** | 11-文档服务设计 | **唯一写口**：会话模型、内存修订、原子提交、ZIP Store 重建、外部修改检测 |


**数据契约**：`.card` / `.box` / `.cpk` 全部 ZIP Store（不压缩归档）、YAML 人类可读、字段与版本规则以《文件格式规范》为唯一权威；`chip_standards_version` 是版本闸门；第一版后破坏性变更走主版本 + 迁移工具，**不做运行时兼容层**。


**状态所有权**（内容架构最重要的纪律）：
- 解析器**只读**；
- 文档服务**唯一写口**（工作副本 → 校验 → 原子替换 → 崩溃恢复）；
- 渲染会话**只读投影**；
- 进入渲染帧的**只有已解析模型与资源句柄**，帧内不读文件；
- 缓存只加速，不拥有真相。

## 八、前端与 UI 架构


```
第三方/业务代码  ──只能从这里导入──▶  @chips/ui（共享层：组件 + 令牌 + 布局）
                                        │
                                        ▼
                                   @chips/antd（fork antd，仅 @chips/ui 内部使用）
```


- **唯一导入面**：业务代码只从 `@chips/ui` 导入；fork antd 不对外暴露。
- **视觉**：Design Tokens + antd 主题定制；禁止硬编码样式、禁止第二套组件库。
- **文案**：简体中文直写；主题系统与多语言系统已废弃（ADR-006），不得新增相关依赖。
- **渲染进**：插件 UI 运行在 iframe 沙箱，与平台通过帧协议通信；宿主负责编排、高度、生命周期与就近渲染。
- **状态**：插件自管自己的状态；跨插件共享只能经事件、服务与配置；持久化只能经文档服务与配置系统。

## 九、跨端架构


- **五端共享**：`.card`/`.box` 格式、Rust 核心、Bridge 接口契约、`@chips/ui` 语义（Web 端可降级实现）。
- **壳差异被吃掉**：窗口、菜单、文件对话框、通知、快捷键、剪贴板、托盘等由壳实现，插件永远只见 Bridge。
- **平台优先级**：macOS / Windows（Phase 1-4）→ Android（Phase 5）→ Linux → iOS；移动端架构预留、实现分离（ADR-007）。
- **能力探测与降级**：能力注册表声明可用性；插件按能力是否存在降级，而不是按平台名分支。

## 十、安全架构


**信任模型**：渲染进程不可信，插件输入不可信，网络内容不可信，用户文件中的数据不可信（解析即校验）。


| 层 | 机制 |
|---|---|
| 身份 | 会话由 Bridge 解析，插件不可自报 |
| 授权 | 权限声明 → 用户授予 → 运行时判定 → 审计；最小权限；路径/域名级限定 |
| 校验 | JSON Schema（能力输入）+ 文档 schema（内容）双闸门 |
| 资源 | `chips-resource://` 统一寻址；PathGuard 防目录穿越；外部资源内容类型必须匹配消费场景 |
| 包与供应链 | `.cpk` 签名与安装校验、体积限制；依赖引入必须过选型评估 |
| 审计 | 能力调用与敏感资源访问可追溯 |

## 十一、可靠性与性能架构


**错误模型**：统一 `ChipsError`（域前缀 + 稳定的 code + 可操作的建议），跨 Rust → Neon → Bridge → 插件全程归一，不丢语义、不泄露内部细节；错误必须可定位（故障排查手册按错误码组织）。


**可靠性**：
- 插件隔离：崩溃不扩散，可重启恢复；
- 写入原子性：临时文件 + 校验 + 原子替换；崩溃后可恢复（文档服务事务层）；
- 外部修改检测：版本戳/摘要对比，冲突显式暴露而不是静默覆盖。


**性能架构（基线即架构，不是优化项）**：


| 指标 | 基线 |
|---|---|
| 冷启动 | < 1 秒 |
| 渲染帧率 | > 60 fps |
| 空闲内存 | < 500 MB |
| 打开卡片 / 箱子 | < 100 ms / < 200 ms |


**架构级手段**：帧内不读文件、不持锁 await、SingleFlight 合并并发、流式与大文件句柄化、缓存分层、就近渲染、懒加载解析。**不达标必须改架构，不允许"后续优化"挂账。**


---


## 十二、架构治理与演进


- **契约治理**：每个概念只有一处权威（单一事实源）；契约变更走 RFC → 评审 → ADR → 门禁 → 文档同步。
- **无兼容包袱**：第一版前大爆炸重构（ADR-010）；第一版后契约稳定 + 迁移工具，禁止双轨与运行时兼容层。
- **文档治理**：四层文档体系；写文档先核代码；文档与实现不一致视为缺陷；归档不删除。
- **质量门禁**：Rust（clippy/fmt/覆盖率 > 80%）+ TS（ESLint/Prettier/strict/覆盖率 > 80%）+ 集成/契约测试全绿才算完成。


---


## 十三、架构不变式清单（全量红线速查）


| 域 | 不变式 |
|---|---|
| 承载 | 平台是唯一运行时承载；插件不碰 Node/Electron/系统 API |
| 通信 | 唯一门 Bridge；服务走内核路由；不跨层、不直连、不反向调用 |
| 身份 | 会话由 Bridge 解析；插件不可自报；三步校验在主进程 |
| 内核 | 单写者；不持锁 await；副作用可逆；崩溃隔离 |
| 内容 | 五链一条线；唯一分支 DocumentKind；解析只读、文档服务唯一写口、渲染只读投影 |
| 文件 | 一切皆挂载、一切皆句柄、差异止于 Provider |
| 前端 | `@chips/ui` 唯一导入面；fork antd 仅内部；中文直写；无硬编码样式 |
| 契约 | 单一事实源；RFC→ADR→门禁→文档同步 |
| 演进 | 无兼容包袱；破坏性变更主版本 + 迁移工具；归档不删除 |
| 质量 | 性能基线不挂账；门禁全绿；不做临时实现、不留 TODO |

## 结语


薯片生态的架构可以概括为**三句话**：


1. **一条竖线**：内容 → 插件 → 契约 → 平台 → 壳 → 系统，层层向下、界限分明；
2. **三个平面**：能力面（南向能力）、事件面（北向通知）、资源面（句柄化访问），互相正交、各有契约；
3. **一条链路**：从文件字节到屏幕像素再到修改落盘，全程同一条链、同一个模型、同一个写口。


内核薄到无感、契约硬如宪法、链路单而无歧、内容久而不死——这就是薯片生态架构设计要达到的形态。
