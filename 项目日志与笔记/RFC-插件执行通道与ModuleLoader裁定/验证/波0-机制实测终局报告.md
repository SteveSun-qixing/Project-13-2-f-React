## 二、M2（推荐面）三口径实测：全绿

钩子形态：`module.register(hooksUrl, { parentURL, data })`，resolve/load 双钩，钩子代码运行于**独立 worker 线程**（每口径独立最小 harness，夹具在各自 `fixtures/`）。

### M2-C1 白名单越界 specifier 真实抛拒且插件体零执行 —— **达成**

- 预期：`node:*`、`electron`、裸路径（`fs`）、作用域外路径（`../outside-scope/…`）在 resolve 钩抛拒；探针模块与越界目标均不被 import 求值。
- 实测：4 个越界入口全部以 `W0_WHITELIST_REJECT` 拒绝（钩子日志 `out/hook-events.jsonl` 计 4 条 reject 事件：`not-in-whitelist × 3` + `scope-escape × 1`）；`globalThis` 探针断言全缺（探针模块、四插件体、作用域外目标均零执行）；阳性对照 `plugin-good.mjs` 正常装载求值。
- 附带实测发现：`new vm` 无关——**Electron 40.8 下 `register()` 返回值为 `undefined`**（Node 语义应返回 MessagePort）：`port2` 端口消息通道在主进程不可用。机制不受影响（钩子照常执行、fs 日志通道权威），但**波 1 实现不得依赖 `register()` 返回端口做宿主↔钩子通信**，应以 `initialize(data)` 投递 + 共享文件/内存侧信道为准。
- 证据：`logs/w0_m2_c1.log`（13 项断言全 PASS，**EXIT=0**）、`m2/c1-whitelist-reject/out/result.json`。

### M2-C2 load 钩读字节复算包级哈希，篡改真实拒装且无半执行状态 —— **达成**

- 预期：注册表期望哈希按原始字节登记；磁盘内容被篡改后 load 钩复算 sha256 不合 → 抛拒；无任何部分求值。
- 实测：`W0_HASH_REJECT`（expected/actual 摘要在钩日志留痕，见 stderr）；`entry-tampered` 模块体与探针均未执行（`__W0_C2_TAMPERED_BODY_RAN__` / `__W0_C2_TAMPER_INJECTED__` 双缺）；阳性对照通过。
- 证据：`logs/w0_m2_c2.log`（5 项断言全 PASS，**EXIT=0**）、`m2/c2-hash-tamper/out/result.json`。

### M2-C3 同路径不同 nonce 穿透 ESM 缓存复加载，每次重新过门禁 —— **达成**

- 预期：`?nonce=` 查询串使每次激活为新缓存键；resolve/load 钩每次重新触发（含哈希门禁每次重新复算）。
- 实测：同 URL 二次 import 被缓存遮蔽（模块体执行计数停在 1，**证明问题真实存在**）；nonce-A/nonce-B 顺次穿透缓存、体执行 2/3 次；钩子调用计数：entry resolve 事件 5 次（每次 import 尝试均重新过 resolve 钩，含被缓存遮蔽的一次——**实测细化：同 URL 复 import 仍触发 resolve 钩，但不再触发 load/实例化，缓存遮蔽发生在实例化层**）、load 事件 allow 3 + reject 1；篡改后换 nonce → 复加载真实重新撞上哈希门禁被拒且无额外执行。
- 证据：`logs/w0_m2_c3.log`（7 项断言全 PASS，**EXIT=0**）、`m2/c3-nonce-reload/out/result.json`。

## 三、M1（备选面）机制可达性冒烟 —— **达成**（M2 全绿，按任务口径仅跑可达性证明；但冒烟本身已覆盖三口径形态）

- 形态：`node:vm` `SourceTextModule` + 宿主自控 linker（linker 即白名单+摘要门禁），`vm.createContext` 独立上下文（真隔离面，附带收益）。
- 实测（`logs/w0_m1_smoke.log`，6 项断言全 PASS，**EXIT=0**，`m1/smoke/out/result.json`）：
  - linker 对 `node:fs`/`electron`/裸 `fs` 三口全抛拒且上下文零污染（探针标记全缺）；
  - 源字节篡改（registry 摘要 vs 实际摘要不合）在入口实例化前即拒（`entry-hash`），linker 复算亦留 `hash-mismatch`；
  - 复加载天然无缓存：每激活新建实例、重过 linker，执行计数 1→2 递进。
- **M1 前置 flag 依赖成立**：无 flag 时 `SourceTextModule` 为 undefined，M1 在 Electron 主进程必须解决 flag 注入（下节）。

## 四、Electron 主进程支持度专测（E1）+ flag 注入终局

### E1（`logs/w0_e1.log`，9 项断言全 PASS，**EXIT=0**，`electron/e1-main-support/out/result.json`）

1. `module.register` 在**主进程（`process.type=browser`，非 utility process）**内可用，钩子链上真实完成 ESM 求值；钩子跑在 **Node worker 线程**（`wtIsMainThread=false, threadId=1`，非 Electron utility process），worker 内可读 `process.versions.node/electron`，fs 读写通道可用（门禁素材 `initialize(data)` 投递 + JSONL 日志实证）。
2. 与渲染沙箱配置的相互作用：`sandbox:true / nodeIntegration:false / contextIsolation:true` 窗口正常创建加载；主世界 `require/process/module` 全 undefined、无 `window.chips`、加载器标记零泄漏；沙箱 preload 仅有受限 require（`electron` 可取、`node:fs` 被拒）。**主进程侧注册钩子对渲染进程零影响**——宿主红线（R1）相容性实证：加载器驻主进程，插件代码经 window.chips.*/Bridge 之外的系统能力通路不因本机制扩大。
3. Electron 特异性负面发现（同 C1）：`register()` 返回 `undefined` → MessagePort/port2 通信面在 Electron 主进程**不可用**，波 1 设计须按此约束。
4. 操作学（工程注意）：Electron 主脚本在 `app.whenReady()` 之前抛错时进程**滞留不退出**（首轮实测「App threw an error during load」后 pid 存活），验证脚本因此必须内置 watchdog `app.exit` + 外部 `pgrep` 存活判据与 TERM 收口；本轮全部收口后 `pgrep` 零残留。

### flag 注入四模式实测（`logs/w0_flags_f1..f4.log`，各 EXIT=0）——**终局结论**

| 模式 | 注入方式 | 主进程 `vm.SourceTextModule` | 结论 |
|---|---|---|---|
| F1 基线 | 仅 `app.commandLine.appendSwitch('experimental-vm-modules')`（主脚本最早期调用） | **undefined**（boot 与 ready 后均无，`new` 抛 "not a constructor"） | **appendSwitch 对 vm-modules 不生效**——该 flag 属 Node 引导期选项，Node 主进程 realm 在 app ready 前已定；与 Node 早期文档口径一致，Electron 40.8 实测坐实 |
| F2 | argv 后置脚本名（`cli.js main.cjs --experimental-vm-modules`） | undefined（`execArgv=[]`） | 不生效（Electron 不把任意 Node flag 从 argv 转交自身主进程 Node 引导） |
| F3 | argv 前置脚本名（`cli.js --experimental-vm-modules main.cjs`） | undefined（`execArgv=[]`） | 不生效（同上） |
| F4 | **环境变量 `NODE_OPTIONS=--experimental-vm-modules`** | **function（boot 即可用）** | **唯一生效面**：进程启动前外部注入 |

即：若取 M1，Electron 主进程可行注入只有 `NODE_OPTIONS` 环境面（宿主启动器在 spawn/Electron 进程环境层设置），**不存在应用内运行期打开该 flag 的路径**。

## 五、三口径 × 两机制矩阵 + O2 终局建议

| 口径 | M2（module.register 双钩） | M1（vm.SourceTextModule + linker） |
|---|---|---|
| ① 白名单越界真实抛拒、插件体零执行 | **达成**（EXIT=0，13 断言全过） | 达成（冒烟内已覆盖，EXIT=0） |
| ② 哈希篡改真实拒装、无半执行 | **达成**（EXIT=0） | 达成（冒烟内已覆盖） |
| ③ nonce 穿透缓存复加载、每次重过门禁 | **达成**（EXIT=0，附 resolve/load 计数细化） | 天然满足（无全局缓存；冒烟证实递进执行+门禁重跑） |
| Electron 40.8 主进程支持度 | **可用**（browser 主进程 + worker 钩子；限制：register() 返回 undefined，MessagePort 面不可用） | 可用但**必须** `NODE_OPTIONS` 外置注入（appendSwitch/argv 三路实测全不生效） |

**O2 终局建议：维持 M2 为推荐实现面。** 依据：三口径在 Electron 40.8.0（Node 24.14.0）真主进程全绿；官方稳定 API、零启动 flag（H5 零违例）、非 experimental（H4 满足）；H1–H3 均有实测落位。M1 作为降级路径**真实存在**（NODE_OPTIONS 注入 + linker 冒烟全过），若取 M1 须由用户显式接受以下条款束：① `--experimental-vm-modules` experimental flag 进生产启动面（H4 违例）；② 注入只能是进程环境层 `NODE_OPTIONS`（H5 违例，且经宿主启动器/打包 Info.plist 环境等外置面承载）；③ 宿主主脚本在 whenReady 前异常会导致 Electron 进程滞留的运维约束（watchdog/TERM 收口纪律）。波 1 落地 M2 时的机制级设计约束（本实测直接产出）：a) 宿主↔钩子线程通信不依赖 `register()` 返回 MessagePort（Electron 下为 undefined）；b) 复加载 nonce 需保留于 URL 查询串（resolve 透传 query、load 按去 query 路径读字节）；c) 同 URL 不带 nonce 的复 import 仍会过 resolve 钩但被实例化层缓存遮蔽——蓝绿/卸载复加载**必须**换 nonce，实测已双向坐实。
