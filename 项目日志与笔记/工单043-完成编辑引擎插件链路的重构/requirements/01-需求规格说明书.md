# 工单043：编辑引擎基础卡片插件链路重构需求规格说明书

## 1. 文档目标

本文档定义“编辑引擎基础卡片插件链路重构”任务的正式需求边界，用于约束后续技术设计、开发实施、测试验收与文档更新。

本任务的唯一核心目标是：

- 用户在新设备上安装 Host；
- 安装编辑引擎应用插件；
- 在 Host 中安装任意符合正式规范的基础卡片插件；
- 编辑引擎无需重新构建、无需静态接入源码，即可正常使用这些基础卡片插件完成查看态装配与编辑态编辑。

## 2. 背景与问题

本节描述的是工单立项时的旧正式实现状态。

当前正式实现中，编辑引擎编辑态使用本地静态注册的基础卡片描述符与本地运行时：

- 编辑引擎在构建期静态注册基础卡片描述符；
- 编辑引擎直接 import 已接入基础卡片插件的 `renderBasecardView` 与 `renderBasecardEditor`；
- 编辑引擎本地完成配置初始化、规范化、校验、编辑会话、防抖提交与单卡装配；
- Host 继续承担通用 `CompositeCardWindow` 与 `editorPanel` 链路。

该方案的主要问题是：

1. Host 已安装基础卡片插件，不等于编辑引擎可立即使用；
2. 编辑引擎与 Host 同时承担基础卡片运行时职责，插件治理边界不清；
3. 编辑引擎与 Host 对同一插件存在双入口，增加了实现漂移风险；
4. 新增基础卡片类型时，编辑引擎必须重新改代码、重新发版，无法满足生态插件化目标。

## 3. 设计原则

本任务必须同时满足以下原则：

1. Host 是基础卡片插件的唯一正式发现者、加载者与运行时权威；
2. 编辑引擎只负责复合卡片编辑态的壳层编排，不再直接加载基础卡片插件源码；
3. 编辑引擎仍然保留“按基础卡片粒度拼接单卡并完成复合卡片渲染”的产品体验；
4. 正式能力颗粒度尽可能收粗，避免过细能力导致多点对齐和协议漂移；
5. 不做兼容性设计，不保留旧本地静态注册链路作为正式双路径；
6. 内部资源路径继续以卡片根目录为唯一正式记录口径；
7. 所有公开正式信息必须最终沉淀到生态共用技术文档与生态设计原稿；
8. 当前工单内部文档只保存任务过程所需的设计、计划与实施边界。

## 4. 目标用户与场景

### 4.1 目标用户

- 薯片官方编辑引擎终端用户；
- 安装第三方基础卡片插件的生态用户；
- 负责插件开发、Host 开发、编辑引擎开发的生态工程师。

### 4.2 核心场景

#### 场景 A：新设备冷启动

1. 用户安装 Host；
2. 用户安装编辑引擎应用插件；
3. 用户在 Host 中安装基础卡片插件；
4. 用户打开编辑引擎；
5. 编辑引擎可自动识别并使用已安装基础卡片插件。

#### 场景 B：安装新基础卡片插件后立即可用

1. 用户正在使用编辑引擎；
2. 用户在 Host 中安装新的基础卡片插件；
3. 编辑引擎刷新插件可用列表后，无需重新构建即可创建、渲染、编辑该类型基础卡片。

#### 场景 C：打开包含未知类型基础卡片的复合卡片

1. 用户打开一张包含多个基础卡片类型的复合卡片；
2. 编辑引擎通过 Host 识别每个基础卡片类型；
3. 已安装插件的基础卡片正常加载；
4. 未安装或无效插件的基础卡片给出正式降级与错误信息，但整张复合卡片仍可继续工作。

## 5. 功能性需求

### 5.1 插件发现与可用性

1. 编辑引擎必须从 Host 查询当前已安装且已启用的基础卡片插件。
2. 编辑引擎不得再依赖本地静态注册表决定“哪些基础卡片类型可用”。
3. 编辑引擎、Host、卡片文件与基础卡片插件必须统一使用正式基础卡片类型标识，例如 `base.richtext`，不得再保留旧类型别名归一逻辑。
4. 插件启用、禁用、卸载后，编辑引擎必须能感知最新状态。

### 5.2 单卡运行时会话

1. 编辑引擎打开一个基础卡片时，必须先向 Host 打开该基础卡片运行时会话。
2. 会话打开结果必须至少返回：
   - 会话标识；
   - 目标插件标识；
   - 归一化后的正式配置；
   - 当前校验结果；
   - 插件运行时能力声明。
3. 编辑引擎不得自行复制 Host 的基础卡片规范化与校验逻辑。
4. 编辑引擎在关闭节点、关闭卡片、切换卡片或卸载时，必须正确释放会话。

### 5.3 查看态装配

1. 编辑引擎必须继续按基础卡片粒度拼装复合卡片。
2. 每个基础卡片仍应保持独立失败隔离和独立尺寸测量。
3. 单卡查看态运行时由 Host 提供，编辑引擎负责：
   - 创建单卡容器；
   - 管理单卡选中态；
   - 汇总单卡高度；
   - 组织整张复合卡片布局；
   - 代理交互给无限画布。
4. 编辑引擎不得重新回退到“整张复合卡片由 Host 直接输出单个大 iframe”的编辑态主方案。

### 5.4 编辑态装配

1. 编辑引擎右侧编辑面板必须改为消费 Host 提供的基础卡片编辑器运行时。
2. 编辑引擎不得再直接 import 基础卡片插件源码。
3. 编辑态配置变更必须以 Host 输出的权威结果为准。
4. 编辑引擎仍负责编辑态壳层编排，包括：
   - 当前选中节点管理；
   - 编辑器容器切换；
   - 草稿同步；
   - 卡片级保存时机控制；
   - 错误显示与重试入口。

### 5.5 配置与资源

1. 基础卡片内部资源路径必须继续以卡片根目录为正式记录口径。
2. 编辑引擎不得自行决定插件资源路径规则。
3. Host 必须作为资源解析、导入、删除、临时 URL 释放的权威执行方。
4. 编辑引擎保存复合卡片时，必须能够获得每个基础卡片当前引用的内部资源集合，用于重建 `structure.yaml` 资源清单。
5. 不允许把 `blob:`、`data:`、系统绝对路径写回正式 YAML。

### 5.6 交互与主题

1. 单卡与编辑引擎壳层必须共享正式主题来源。
2. 编辑引擎无限画布中的滚轮、缩放、选中代理能力必须保留。
3. 单卡运行时切换为 Host 权威后，不得破坏当前正式的交互代理边界。
4. 多语言文案必须继续符合生态多语言系统要求。

### 5.7 错误与降级

1. 若插件不存在、插件未启用、插件运行失败、会话建立失败，编辑引擎必须给出正式错误提示。
2. 单卡错误不得拖垮整张复合卡片。
3. 编辑器加载失败时，不得影响预览链路。
4. 所有错误都必须具备明确错误码、错误边界与日志记录点。

## 6. 非功能性需求

### 6.1 架构要求

1. 不保留旧本地静态注册链路作为正式双路径。
2. 不允许编辑引擎在运行时扫描 Host 插件安装目录后直接 import 源码。
3. Host 与 EditingEngine 的职责边界必须清晰、单向、可审计。

### 6.2 稳定性要求

1. 编辑引擎切换节点、频繁编辑、频繁增删卡片时不得出现会话泄漏。
2. 资源 URL 必须可回收，避免长期编辑造成内存泄漏。
3. 插件异常退出或抛错时，必须被限定在单卡或单编辑器范围内。

### 6.3 性能要求

1. 新方案不得明显劣化当前编辑引擎的节点切换体验。
2. 单卡数量较多时，复合卡片装配仍应保持内容驱动高度和可接受响应速度。
3. Host 与编辑引擎之间的协议颗粒度必须控制在可维护范围内，不做过细 RPC 拆分。

### 6.4 工程要求

1. 不允许留 TODO、临时代码、占位实现。
2. 所有关键链路都必须有自动化测试。
3. 所有对外正式能力都必须同步更新共享技术文档与设计原稿。

## 7. 范围界定

### 7.1 本任务范围内

- Host 基础卡片插件权威运行时改造；
- EditingEngine 基础卡片查看态与编辑态链路重构；
- SDK / Bridge 正式能力扩展；
- 资源链路重新归口；
- 测试体系重建；
- 共享技术文档与设计原稿更新；
- 必要的脚手架、模板、开发文档同步。

### 7.2 本任务范围外

- 大版本兼容策略；
- 旧链路兼容适配器；
- 非基础卡片插件类型的整体治理重构；
- 无关业务功能的额外界面改版。

## 8. 验收标准

### 8.1 用户验收

以下条件全部满足时，本任务才算通过：

1. 在全新环境中仅安装 Host 与编辑引擎应用插件时，编辑引擎可启动；
2. 在 Host 中安装一个基础卡片插件后，编辑引擎无需重新构建即可识别该插件；
3. 用户可在编辑引擎中创建、查看、编辑该基础卡片类型；
4. 用户关闭并重新打开卡片后，内容、资源路径、布局和编辑结果保持正确；
5. 卸载或禁用插件时，编辑引擎能给出正式反馈，而不是静默失效；
6. 整个编辑态复合卡片仍由编辑引擎自己完成单卡拼接与整体渲染。

### 8.2 工程验收

1. 不存在本地静态 import 基础卡片插件源码的正式主链路；
2. Host 成为基础卡片插件唯一正式发现与加载入口；
3. EditingEngine 通过正式协议消费单卡运行时；
4. 共享技术文档与生态设计原稿同步完成更新；
5. 测试全部通过，且覆盖 Host、SDK、EditingEngine 三侧关键场景。

## 9. 当前落地结果

截至本轮实现完成，已落地结果如下：

1. Host 已成为基础卡片插件唯一正式发现、加载与会话运行时入口；
2. EditingEngine 编辑态已切换为“应用内装配复合卡片 + Host 托管单卡会话”；
3. SDK 已提供 `client.card.basecard.*` 正式调用入口；
4. 基础卡片内部资源路径与封面资源路径都已统一为“按卡片根目录记录”；
5. `structure.yaml` 资源清单可根据基础卡片引用资源与封面资源重新生成；
6. 共享技术文档、生态设计原稿与工单内部文档已同步更新。
