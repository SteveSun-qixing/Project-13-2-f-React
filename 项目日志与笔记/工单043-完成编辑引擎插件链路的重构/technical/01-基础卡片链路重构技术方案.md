# 工单043：编辑引擎基础卡片插件链路重构技术方案

## 1. 文档目标

本文档定义工单 043 的目标架构、正式协议、仓库影响面、实施约束与验证策略。

本方案不做兼容性设计，目标是将当前“编辑引擎本地静态注册基础卡片插件”的正式主链路，整体替换为“Host 权威插件运行时 + EditingEngine 负责单卡装配”的正式架构。

## 2. 当前实现分析

本节描述的是工单立项时的旧链路状态。

### 2.1 当前正式链路

当前仓库中的编辑引擎主链路具备以下特征：

1. `Chips-EditingEngine` 在本地静态注册 `BasecardDescriptor`；
2. 描述符直接 import 基础卡片插件源码；
3. `BasecardFrameHost` 本地挂载 `renderBasecardView`；
4. `EditorHost` 本地挂载 `renderBasecardEditor`；
5. `CardService` 本地依赖描述符完成配置归一与部分数据治理；
6. Host 继续提供通用 `card.render` / `card.renderEditor` 给查看器和第三方集成。

### 2.2 当前问题

当前实现存在以下结构性问题：

1. Host 已安装插件与 EditingEngine 可用插件不是同一事实来源；
2. EditingEngine 与 Host 同时持有插件运行时逻辑，职责重复；
3. 新插件需要修改 EditingEngine 源码，违背插件化目标；
4. 正式类型口径、配置归一、校验、资源收集逻辑存在双端漂移风险；
5. 用户在新设备上安装插件后，EditingEngine 不能自动获得完整能力。

## 3. 目标架构

## 3.1 架构总原则

目标架构采用以下边界：

- Host：基础卡片插件唯一正式发现者、加载者、运行时权威；
- EditingEngine：编辑态复合卡片壳层、单卡容器装配者、会话编排者；
- SDK / Bridge：Host 权威能力的类型化封装与协议入口；
- 基础卡片插件：只提供正式导出，不直接感知 EditingEngine 实现细节。

## 3.2 目标链路

### 3.2.1 查看态

1. EditingEngine 打开复合卡片；
2. EditingEngine 读取卡片结构与基础卡片数据；
3. EditingEngine 按基础卡片节点向 Host 打开单卡运行时会话；
4. Host 返回单卡会话信息与单卡查看态运行时入口；
5. EditingEngine 自己创建单卡容器并完成节点装配；
6. EditingEngine 汇总高度、错误态、选中态与交互代理；
7. 复合卡片整体仍由 EditingEngine 本地完成渲染。

### 3.2.2 编辑态

1. 用户选中某个基础卡片；
2. EditingEngine 打开或复用该基础卡片会话；
3. EditingEngine 请求 Host 提供该会话的编辑器运行时；
4. Host 负责插件加载、配置归一、校验与资源运行时；
5. EditingEngine 负责编辑器容器切换、卡片级保存与错误边界；
6. Host 通过统一事件向 EditingEngine 回传权威配置结果。

## 4. 正式协议设计

## 4.1 颗粒度原则

本任务不采用过细 RPC 方案。

不推荐公开以下高度细粒度动作作为正式主接口：

- `createInitialConfig`
- `normalizeConfig`
- `validateConfig`
- `collectResourcePaths`

原因：

1. 动作面过多，前后端对齐成本高；
2. 一处数据模型变更需要同步多个接口；
3. 插件实现与协议定义更容易漂移；
4. EditingEngine 会被迫理解过多插件内部语义。

## 4.2 建议的正式粗粒度能力

### 4.2.1 `basecard.openSession`

用途：

- 打开一个基础卡片运行时会话；
- 由 Host 统一完成插件查找、正式类型校验、初始配置补齐、配置规范化、校验与能力声明。

建议输入：

```ts
{
  cardType: string;
  baseCardId: string;
  cardId?: string;
  cardRootPath?: string;
  sourceConfig?: Record<string, unknown>;
  mode: 'view' | 'edit';
}
```

建议输出：

```ts
{
  sessionId: string;
  pluginId: string;
  resolvedCardType: string;
  displayName: string;
  normalizedConfig: Record<string, unknown>;
  validation: {
    valid: boolean;
    errors: Record<string, string>;
  };
  capabilities: {
    hasView: boolean;
    hasEditor: boolean;
    supportsResources: boolean;
    supportsInteractionDelegate: boolean;
  };
}
```

该接口收口以下职责：

- 创建默认配置；
- 配置归一；
- 配置校验；
- 正式类型校验；
- 插件可用性判断；
- 会话建立。

### 4.2.2 `basecard.renderView`

用途：

- 请求 Host 提供某个会话的单卡查看态运行时。

建议输入：

```ts
{
  sessionId: string;
  theme?: ThemeSnapshot;
  interactionPolicy?: 'native' | 'delegate';
}
```

建议输出：

```ts
{
  sessionId: string;
  pluginId: string;
  cardType: string;
  view: {
    title: string;
    body: string;
  };
}
```

说明：

- 这里不要求 Host 直接拼接整张复合卡片；
- Host 只负责单卡 view 运行时；
- EditingEngine 继续保留自己的单卡 iframe 装配层。

### 4.2.3 `basecard.renderEditor`

用途：

- 请求 Host 提供某个会话的单卡编辑器运行时。

建议输入：

```ts
{
  sessionId: string;
  theme?: ThemeSnapshot;
}
```

建议输出：

```ts
{
  sessionId: string;
  pluginId: string;
  cardType: string;
  editor: {
    title: string;
    body: string;
  };
}
```

说明：

- Host 负责插件加载、编辑器运行时与资源桥；
- `basecard.renderEditor` 是 Host 托管单基础卡片编辑器 iframe 的正式能力；
- 官方 EditingEngine 编辑面板当前正式实现为：使用 `basecard.openSession` 获得权威会话结果，再调用 `basecard.renderEditor` 装载单卡编辑 iframe。

### 4.2.4 `basecard.closeSession`

用途：

- 释放 Host 侧会话、资源句柄、事件监听、临时 URL 与运行时状态。

## 4.3 正式事件

建议单卡运行时统一使用以下事件：

- `chips.basecard:ready`
- `chips.basecard:change`
- `chips.basecard:height`
- `chips.basecard:interaction`
- `chips.basecard:error`

其中 `chips.basecard:change` 应直接返回权威结果：

```ts
{
  sessionId: string;
  cardType: string;
  pluginId: string;
  normalizedConfig: Record<string, unknown>;
  validation: {
    valid: boolean;
    errors: Record<string, string>;
  };
  referencedResources: string[];
}
```

这意味着 EditingEngine 不再单独调用 `normalize/validate/collectResourcePaths`。

## 5. 资源链路设计

## 5.1 原则

1. 资源路径继续统一按卡片根目录记录；
2. Host 是资源解析、导入、删除、释放的唯一权威；
3. EditingEngine 不再直接实现插件级资源逻辑；
4. 保存阶段重建 `structure.yaml` 资源清单时，以 Host 输出的 `referencedResources` 为准。

## 5.2 资源责任边界

### Host 负责

- 校验资源路径是否合法；
- 为编辑器提供 `resolve/import/delete/release` 运行时能力；
- 生成不冲突文件名；
- 管理 `blob:` URL 生命周期；
- 输出最终 `referencedResources`。
- Host 生成的基础卡片查看态与编辑态 `srcdoc` 文档，`img-src` 必须显式允许 `blob:`，用于承载编辑期未落盘资源与重新解析中的临时预览。

## 5.3 运行时事件可靠性约束

基础卡片查看态和编辑态 iframe 的事件订阅，必须以“运行时读取最新 `contentWindow`”作为正式实现约束，不能在 iframe 插入 DOM 前缓存 `contentWindow` 引用。

原因：

1. EditingEngine 会先注册事件，再把 Host 返回的 iframe 插入容器；
2. 若订阅时缓存到的是 `null`，后续 `ready` 之外的 `select / change / height / interaction / error` 事件都会丢失；
3. 事件丢失会直接导致基础卡片无法选中、编辑输入不回写、高度不刷新、交互代理失效。

正式要求：

1. SDK 的消息订阅器在每次收到 `message` 事件时，都要重新读取 `frame.contentWindow`；
2. EditingEngine 保存基础卡片数据时，必须以 Host 回传的权威标准化配置整体替换本地配置，不能把旧字段继续 merge 保留；
3. 所有基础卡片编辑器变更事件，都视为 Host 权威结果，不允许 EditingEngine 继续拼接旧架构残留字段。

### EditingEngine 负责

- 触发卡片级保存；
- 把会话输出的权威配置写回卡片数据结构；
- 在持久化时与 `CardService` 协作重建资源清单；
- 在关闭卡片、关闭节点时调用 `closeSession`。

## 6. 主题、多语言与交互

### 6.1 主题

- Host 单卡运行时必须继续消费同一主题快照；
- EditingEngine 壳层与单卡运行时必须共享统一主题来源；
- 不允许出现“单卡是 Host 主题，壳层是本地主题”两个事实来源。

### 6.2 多语言

- 单卡运行时文案应继续由 Host / 插件正式链路提供；
- EditingEngine 壳层文案继续使用自身多语言系统；
- 多语言边界必须清晰，不得在插件内部硬编码用户可见文案。

### 6.3 交互

- EditingEngine 继续负责无限画布的外层交互代理；
- Host 提供的单卡查看态运行时继续发出正式 `interaction` 载荷；
- EditingEngine 不得失去对节点选中、滚轮代理、缩放代理的掌控。

## 8. 实施策略

## 8.1 迁移策略

不做兼容性双正式链路。

实施时采用“先补 Host 单卡协议，再切 EditingEngine 主路径，最后清理旧链路”的单向迁移策略：

1. 在 Host / SDK 补齐正式单卡会话协议；
2. 在 EditingEngine 接入新协议并完成主链路切换；
3. 删除 EditingEngine 本地静态注册与本地插件 import 主路径；
4. 同步更新测试与共享文档。

## 8.2 风险点

1. 单卡协议过细导致实现漂移；
2. 会话与资源释放不完整导致泄漏；
3. Host 单卡运行时性能不达标；
4. 插件在 Host 运行态与 EditingEngine 当前假设不一致；
5. 文档、脚手架、测试未同步导致后续再漂移。

## 8.3 风险控制

1. 正式能力控制在会话级粗颗粒度；
2. 先建立契约测试与集成测试，再切主链路；
3. 会话生命周期统一建模；
4. 资源路径与引用集合由 Host 权威输出；
5. 所有公开正式变更同步更新共享文档。
