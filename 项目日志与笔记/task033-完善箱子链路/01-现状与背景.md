# 现状与背景

## 任务目标

在箱子布局页面内按需显示条目的卡片封面或完整卡片内容。文档库布局需要在右侧直接展示当前选中卡片的正式内容，而不是只显示封面后新开查看窗口。

## 现有能力

1. `Chips-Host` 的 `card.render` 已能解析 `.card`、分发基础卡片插件、组装复合卡片文档，并返回 Host 托管的 `documentUrl` 和渲染会话。
2. `Chips-SDK` 的 `client.card.compositeWindow.render` 已封装复合卡片 iframe、标准 sandbox、高度事件、错误事件和会话释放。
3. 箱子查看链路已是 `CardViewer -> client.document.window.render -> box.documentWindow.render -> Host 布局文档`。
4. 布局文档本质上是 Host 托管网页，CSP 和 sandbox 允许其挂载受控子 iframe。
5. 箱子会话已能用 `entryId` 解析包内嵌卡片与 `file:` 卡片。

## 当前断点

箱子布局 Runtime 当前只暴露：

- `listEntries`；
- `readEntryDetail`；
- `renderEntryCover`；
- `resolveEntryResource`；
- `readBoxAsset`；
- `prefetchEntries`；
- `openEntry`。

它没有从 `entryId` 到完整卡片文档的正式动作。`documentFile` 资源只是原始 `.card` 文档，无法直接在 iframe 中运行。

文档库布局因此只能在右侧调用 `renderEntryCover(entryId)`，点击后调用 `openEntry(entryId)`。这不是卡片渲染器缺失，而是箱子运行时与现有卡片渲染器之间的公共契约缺口。

## 边界约束

- 布局必须以 `entryId` 而不是 `cardId` 定位内容。同一卡片可被同一箱子多次引用，而 `entryId` 是当前箱子会话中的唯一引用身份。
- 布局不得获取或持久化 Host 临时解包路径、`file://` 地址、凭证或渲染会话 URL。
- 引用箱子的条目保持正式封面态，不在布局内递归展开子箱子。
- 完整卡片渲染可能继续包含多个基础卡片 iframe，必须懒加载并及时释放离屏或被替换的渲染会话。
- 网络 URL 的下载、凭证、缓存和重试仍属于 Host 文档解析边界，不下放给布局插件。

## 工单关系

本任务对应 `工单145-箱子布局缺少条目完整文档渲染契约`。公共契约、Host、SDK、脚手架、文档库布局和测试需在同一任务中收口。
