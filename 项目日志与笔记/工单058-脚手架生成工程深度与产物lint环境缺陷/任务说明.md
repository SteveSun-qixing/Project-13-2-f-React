## 一、背景

W4 插件迁移波的第一路（#257，grid 布局包）走生态正式命令生成工程形制，随后要「补旧功能面」并把包跑绿。落地的过程中撞到两处**不是业务代码问题、而是脚手架与仓库配置环境面**的缺陷：一处让新生成工程开箱 typecheck 全灭，一处让根聚合 lint 闸在新增插件包上必红。两者都会随 W4/W5 的每一个新插件包重复发生，属于「开闸第一包就该钉住」的坑。

## 二、证据（磁盘实读 + 真实退出码）

### 臂一：`deriveTsconfigExtends` 绝对路径回退少一级

- 事实源：`chips-ecosystem/tools/scaffold/src/validate.ts:182-186`

  ```ts
  export function deriveTsconfigExtends(targetDir: string): string {
    if (targetDir.startsWith('/') || /^[A-Za-z]:/.test(targetDir)) {
      return '../../tsconfig.base.json';   // 绝对路径无法推导深度 → 固定两级
    }
    const depth = targetDir.split('/').filter((segment) => segment.length > 0).length;
    return `${'../'.repeat(Math.max(depth, 1))}tsconfig.base.json`;
  }
  ```

  函数头注自述「约定 `targetDir` 为相对工作区根目录的路径（如 `plugins/hello`、`examples/plugins/hello`）」，并要求「调用方在落盘后核对」。
- 调用侧破约：`chips-ecosystem/packages/cli/src/commands/plugin.ts:152-158` 一带把 `--dir` 解析为**绝对路径**（`context.cwd` 拼接）后传入生成链 ⇒ 走固定两级回退分支。
- 触发条件：包目录深度 ≥3（如 `plugins/layouts/grid`，正确值应为 `../../../tsconfig.base.json`）。固定两级指向 `chips-ecosystem/packages/tsconfig.base.json`（不存在）⇒ 生成工程 `tsc --noEmit` 面报 TS1704（找不到文件）一类的连锁错，**开箱即全灭**。
- 本波实况：#257 在包内把 `plugins/layouts/grid/tsconfig.json` 的 `extends` 手工改为 `../../../tsconfig.base.json` 后四闸转 0；模板本体未改（`tools/**` 是该路的禁改面）。
- 规避口径（在册可用）：CLI 调用改传相对 `--dir plugins/<族>/<名>`，`validate.ts:185-186` 的按段数推导即正确（该分支有在册用例）。

### 臂二：插件渲染产物落包根，被根 eslint 判成 Node 环境

- 事实源：`chips-ecosystem/eslint.config.mjs:75-80`（本批前）对 `**/*.{js,mjs,cjs}` 一律 `globals: globals.node`；`tools/scaffold/src/templates/boxlayout.ts:648` 口径「构建以 `src/main.ts` 生成 `dist/index.js`、以 `src/render.tsx` 生成 `render.js`」——后者落**包根**且 `dist/` 之外的路径不在忽略面（`:60-72` ignores 仅 `**/dist/**` 等）。
- 后果：`plugins/layouts/grid/render.js`（打包产物，运行期使用 `ResizeObserver`/`IntersectionObserver`）在根配置下报 2 条 `no-undef`（87:19、120:19），根 `pnpm run lint`（`eslint . && prettier --check . && cargo fmt && cargo clippy`）在新增任何插件包时**必红**；而包内 `lint` 脚本只跑 `eslint src tests`，抓不到产物面 ⇒ **包内四闸全绿、聚合闸红**的错配窗口。
- 旁证：`examples/plugins/hello/render.js` 同为已入库打包产物（tracked），恰好未引用被缺省排除的浏览器全局，因此该缺陷在 W4 之前未暴露——属侥幸，不是无缺陷。

## 三、影响范围

- 每一个经 `chips plugin create` 生成、且放在 `plugins/<族>/<名>` 三级深度的插件工程（W4 三插件仓 26 包 + W5 应用仓全部）：不修正则每包都要人工补一次 `extends`，或按「相对 `--dir`」口径绕行——绕行属于使用约定，不消除模板缺陷。
- 每一次代码冻结期的根聚合 lint：不修正则每新增一个引用浏览器全局的渲染包就多两条红，容易被误判成业务代码问题。
- 不影响：任何既有包源码、协议面、覆盖率阈值、门禁值。

## 五、期望行为

1. 臂一：`deriveTsconfigExtends` 不再依赖调用方传相对路径的口头约定——两条路均可：①由 CLI 侧统一以工作区根为基准换算相对 `targetDir` 后传入（生成链单一事实源在 CLI）；②模板落盘后按真实目录深度回写 `extends`（生成器自检）。要求**两路择一后有一条锁测覆盖「三级深度插件目录生成物 typecheck 开箱可过」**，禁止只改注释。归属：`tools/scaffold` 与 `packages/cli` 的实施波。
2. 臂二：本批已在根配置按事实声明浏览器全局修口（`plugins/**/render.js` 与 `examples/plugins/**/render.js` → `globals.browser`）。仍待裁的模板侧议题：渲染产物是否应改为落 `dist/render.js`（与 `dist/index.js` 同侧、天然落在忽略面），该变更牵动 `.cpk` 打包成员表、`check-entries` 的入口解析与《05.06》示例面，属架构面口径 ⇒ **不自行改**，随工单001② 的 `render.js` 忽略面悬案一并请主/用户裁定。
3. 包内 `lint` 脚本是否应扩到产物面（`eslint src tests render.js`）以消除「包内绿、聚合红」错配，随本单裁定后统一。

## 六、暂行处理（处置前怎么办）

- W4 各插件波**必须**在建包后立刻核对 `tsconfig.json` 的 `extends` 层级（正确形：`plugins/<族>/<名>` → `../../../tsconfig.base.json`），并跑一次包内 `typecheck` 作为 M0 判据；不要把「手工修正」当成已修。
- 生成命令优先传相对 `--dir`（`plugins/<族>/<名>`），走有在册用例的推导分支。
- 闸口一律以 `~/.volta/bin/pnpm`（9.15.0）为准；PATH 上的 homebrew `pnpm` 8.15.9 不满足 `engines>=9`，其读数不入账。
- 不得通过给产物加 eslint 注释（`/* eslint-disable */`）或把 `plugins/**` 整面塞进 ignores 来「清红」——那是降断言，非处置。
