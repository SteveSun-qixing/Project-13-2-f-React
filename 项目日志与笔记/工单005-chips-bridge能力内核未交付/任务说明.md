# 工单 005：能力内核 `chips-bridge` crate 未交付，chips-native 能力执行导出面无实现载体

> 登记：W1-NATIVE（2026-09-19）
> 状态：处理中（2026-09-20：`chips-bridge` crate 主体已落位入库 fd4bb760 并派覆盖率补测；chips-native 四导出转发面派单在途，见《重构大计划/W2-开工波次计划.md》§四 在途派单 6）
> 影响：`packages/native`（chips-native ABI 完整性）、`packages/host`（`bridge:request` 链路）、`packages/bridge`（TS 过渡实现退场）、W1 门禁（契约测试）

---

## 一、背景

《核心接口规范》§8.6 规定 `chips-native` 的 ABI 导出面包含能力执行四函数（`bridgeRegister` / `bridgeUnregister` / `bridgeRequest` / `bridgeCancelSession`），§5 规定这四个导出转发 `chips-bridge` crate 的 `Bridge`（能力注册表、权限判定、schema 校验、路由与超时取消）。§2.2 规则 5 明确「绑定层只做类型转换与错误映射，业务逻辑全部位于子系统 crate」，因此绑定层不得自行实现注册表、权限判定或 schema 校验。

当前 Rust 工作区中 `chips-bridge` crate 不存在：`packages/core-rust/crates/` 仅有 `chips-core`、`chips-cordis`。`packages/bridge/`（TypeScript）是 Bridge 核心的过渡实现，其开发计划自述「最终架构中由 Rust 核心承载……后续可由 Neon 实现替换」。

结论：chips-native 的能力执行导出面在本轮无实现载体，且不得以绑定层业务代码兜底。

## 二、证据

1. `薯片生态文档库/05-接口与契约/03.02-03-核心接口规范-二、crate 划分与公开面.md:17`：`chips-bridge` 职责为「Bridge 内核（注册表、权限判定、Schema 校验、路由）」，主要公开类型 `Bridge` / `CapabilityRegistration` / `CapabilityExecutor`。
2. `薯片生态文档库/05-接口与契约/03.08-03-核心接口规范-八、Neon 绑定约定.md:141`：§8.6 导出总表 Bridge 域含 `bridgeRegister`、`bridgeUnregister`、`bridgeRequest`、`bridgeCancelSession`。
3. `薯片生态文档库/05-接口与契约/03.05-03-核心接口规范-五、Bridge（chips-bridge）.md:83-89`：`Bridge::register` / `Bridge::unregister` 签名与注册校验要求。
4. `薯片生态文档库/05-接口与契约/03.05-03-核心接口规范-五、Bridge（chips-bridge）.md:123-129`：`Bridge::request` / `Bridge::cancel_session` 签名及调用阶段失败码。
5. `薯片生态文档库/05-接口与契约/03.02-03-核心接口规范-二、crate 划分与公开面.md:32`：§2.2 规则 5「绑定层只做类型转换与错误映射，业务逻辑全部位于子系统 crate」。
6. `chips-ecosystem/packages/core-rust/crates/` 目录清单：仅 `chips-core`、`chips-cordis`，无 `chips-bridge`（`ls` 可复现）。
7. `chips-ecosystem/packages/bridge/开发计划.md:70-71`：TS bridge 风险条目自述「Bridge 核心在最终架构中由 Rust 核心承载……本包以同语义 TS 实现并提供 `ICapabilityInvoker` / 会话与事件注册表等接缝，后续可由 Neon 实现替换」。

## 三、影响范围

- `packages/native`：`abi/export-surface.json` 的 `blocked` 已登记四个 bridge 导出；`types/chips-native.d.ts` 不声明未注册函数（按 ABI 类型面必须与运行时一致的口径），能力执行函数在 native 侧暂缺。
- `packages/host`：主进程 `bridge:request` 链路当前只能使用 TS bridge，`chips-native.node` 无法承载能力路由。
- W1 门禁：本 crate 的契约测试（导出面三方一致）只能覆盖非 bridge 域；《核心接口规范》§8.6 导出面尚未闭合。

## 四、复现步骤

1. `ls chips-ecosystem/packages/core-rust/crates/`：输出仅 `chips-core`、`chips-cordis`。
2. `rg -n "pub struct Bridge|pub trait CapabilityExecutor" chips-ecosystem/packages/core-rust/`：无匹配。
3. 在 `packages/native/src/abi.rs` 的 `export_table!` 中尝试注册 `bridgeRequest`：无 `chips_bridge` 依赖可引用，也不得在绑定层内实现注册表与权限判定。

## 五、期望行为

1. 由对应任务交付 `chips-bridge` crate，提供《核心接口规范》§5.1/§5.2 的公开面与语义（注册校验、会话校验、权限判定、schema 校验、并发准入、超时取消、错误归一）。
2. `chips-native` 在 `export_table!` 同一入口追加四个 bridge 导出（导出表只增不改），并同步更新 §8.6、`abi/export-surface.json`、`types/chips-native.d.ts` 与契约测试。
3. 若主代理裁决调整 W1 顺序（例如先以 TS bridge 覆盖金链路、Rust bridge 排入后续波次），需在《核心接口规范》§8.6 与本工单同步标注阶段口径。

## 六、验收标准

- `cargo test -p chips-bridge` 通过；公开类型与方法与 §5 一致。
- `packages/native` 的 `abi/export-surface.json` ↔ `src/abi.rs` ↔ `types/chips-native.d.ts` 三方一致，且 bridge 四项从 `blocked` 移除。
- `node packages/native/scripts/check-abi.mjs` 通过且不再引用本工单。

- native 本轮不注册 bridge 导出：绑定层不承载 Bridge 业务逻辑；`abi/export-surface.json` 以 `blocked` 项引用本工单，`scripts/check-abi.mjs` 强制校验阻塞项引用的工单目录真实存在。
- 本工单登记后继续推进 native 其余导出面（元信息、Context、取消令牌）与类型映射/错误归一/线程约束/构建脚本/测试，并在 `packages/native/开发日志.md` 标注未收口口径。
