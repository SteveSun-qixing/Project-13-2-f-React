## 一、背景与收口对象

《能力契约规范》§4.4 共三条语义。前一轮收口（工单005 补测落地一，b4a9e21b）已修正「注销幂等」；本轮补齐任务指明的两条残口：

1. 同一能力 ID 重新注册绑定「原 owner」，非原 owner 抢注按文档口径拒绝；
2. 蓝绿 draining：旧代际进入 draining——拒绝新调用、在途调用有序收尾。

## 二、依据条文（原文摘录，逐字对齐）

《能力契约规范》§4.4（`薯片生态文档库/05-接口与契约/04.04-04-能力契约规范-四、能力注册、发现与注销.md`）：

> - 注销后停止接受新调用（`BRIDGE_CAPABILITY_NOT_FOUND`）；在途调用按 [02-Bridge三层设计] 第 8 节收口，调用方收到结果或 `BRIDGE_CANCELLED`。
> - 注销完成后，同一 ID 只能由原 `owner` 重新注册；其他提供方不得抢占，重注册校验与首次注册一致。
> - 注销是幂等操作：对已注销 ID 重复注销为 no-op，不产生错误。
>
> 触发表：「蓝绿更新代际切换 | 旧代际注册项进入 `draining`，新代际接管（第 9.3 节、第十节）」

§9.3 冲突处理（04.24 分件）：

> - 「蓝绿更新的代际接管 | 唯一允许的同 ID 覆盖：新代际注册后旧代际进入 `draining`，切换完成后旧代际注销不影响新注册」
> - 「注销后重新注册 | 仅允许登记绑定的提供方；注册校验与首次注册一致」
> - 「其他 owner 抢占已注销 ID | 拒绝，`BRIDGE_CAPABILITY_CONFLICT`（登记绑定不可转让、不可继承）」

§10.1 状态机（04.25 分件）：

> `未注册 ──注册成功──▶ active ──代际切换──▶ draining ──在途收口──▶ 已注销`
> draining 行：「拒绝新调用；在途调用完成或按超时收口」；不变量 4：「`draining` 是蓝绿更新的唯一过渡态，切换完成后同一 ID 只有一个生效代际」

§11.2 错误码（04.26 分件）：

> `BRIDGE_CAPABILITY_NOT_FOUND`——「调用未注册能力 ID；`draining` 后的新调用」（retryable: false）；`BRIDGE_CAPABILITY_CONFLICT`——注册冲突全集（retryable: false）。

《03-插件架构设计》§6.2/§6.3：原子切换点「新 Fork 注册服务，注册表与路由指向新版本」；「一次调用要么由旧版本处理，要么由新版本处理」。

《核心接口规范》03.05 §5.1/§5.2：`register`/`unregister`/`request`/`cancel_session` 签名与阶段失败码（本轮零改动，仅作约束核对）。

## 三、实现口径

### 3.1 语义一：原 owner 重注册绑定

- `CoreState` 新增 `owner_bindings: HashMap<String, String>`（能力 ID → 首次成功注册的提供方）。注册成功即写入；**不随 `unregister` / `deactivate_provider` 移除**（§9.3「登记绑定不可转让、不可继承」）。
- `check_registration_bindings` 在 owner 激活校验后统一执行绑定校验：绑定存在且与注册 `owner` 不一致 → `BRIDGE_CAPABILITY_CONFLICT`，`details.reason = "同一 ID 只能由原 owner 重新注册，其他提供方不得抢占"`。覆盖面：已注销 ID 被抢注、在册 ID 被抢注、draining 收口后被抢注、蓝绿接管被跨 owner 借用；内置 ID（无登记台账）此前无任何重注册约束面，本机制为其唯一约束；第三方 ID 与既有 `id_ledger` 双保险、口径一致。
- 错误码全部取 `error_codes.rs` 既有常量，未自造新码、未新增常量。

### 3.2 语义二：蓝绿 draining

- 注册项内增 `draining: AtomicBool`；公开新增两个动作入口 + 一个只读视图（均为增量，四个 ABI 转发面签名零改动）：
  - `Bridge::begin_draining(capability_id) -> Result<(), ChipsError>`：旧代际进入 draining。新调用在 `admit` 两段锁均按 `BRIDGE_CAPABILITY_NOT_FOUND` 拒绝（§11.2）；在途调用（含串行队列等待者）**不强杀**，完成或按超时收口（§10.1）；在途清零时经 `release_invocation` 自动摘除注册项并清理串行态（draining →在途收口→ 已注销）；无在途则即刻收口；对未注册/已注销/重复进入均 no-op 幂等（与 §4.4 幂等口径一致）。
  - `Bridge::takeover_register(registration) -> Result<(), ChipsError>`：§9.3「唯一允许的同 ID 覆盖」。注册校验与首次完全一致（复用 `precheck_registration` + `check_registration_bindings`，含 3.1 绑定校验，跨 owner 接管即被拒）；接管后注册表原子指向新代际，旧代际在途调用持旧 `Arc<Registration>` 快照在新槽位之下有序收尾（切换完成后的收尾不再引用注册表，天然满足「旧代际注销不影响新注册」）；新调用一律由新代际处理（§6.3 原子可见）。
  - `Bridge::capability_state(capability_id) -> Option<CapabilityState>`：§4.3 编目 `ICapabilityDescriptor.state`（`'active' | 'draining'`）的 Rust 侧权威只读面；`CapabilityState` 经 lib.rs 追加 re-export。
- `register` 与 `takeover_register` 共用内部 `register_with(registration, takeover)`：同 owner 同定义幂等路径**保留** draining 标记不被普通注册唤醒（§10.1：draining 只能经在途收口退出），接管路径安装为新代际 active。
- 原 `unregister`（stop/停用/卸载路径）行为不变：新调用 NOT_FOUND + 在途按取消收口（§4.4 第一条 + §8.2 取消来源，既有用例锁定），与 draining（代际切换路径，不取消）分属两条文档通道，不混用。
