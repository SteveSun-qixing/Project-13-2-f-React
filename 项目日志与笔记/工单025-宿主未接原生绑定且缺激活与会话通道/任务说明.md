## 一、背景

《03-核心接口规范》§5 规定宿主侧存在原生绑定适配层 `packages/host/src/main/native-bridge.ts`（`薯片生态文档库/05-接口与契约/03.05-03-核心接口规范-五、Bridge（chips-bridge）.md:153` 点名该文件为「chips-native.node 的类型视图」，`:192` 给出 `import type { INativeBridge } from './native-bridge';`），§8.1–§8.7 给出全部绑定约定；同文档 `:93` 规定能力注册校验包含「`owner` 已激活」，`:133-135` 规定调用会话不存在即返回 `BRIDGE_SESSION_UNKNOWN`。Rust 内核 `chips-bridge` crate 的注册与调用前置正是「提供方激活 + 会话登记」两步。

## 二、证据（文件:行号，均于 2026-09-20 复核）

2. `packages/host/src` 全目录 grep `chips-native|bridgeRequest|INativeBridge` 0 命中（本轮实测）——宿主从声明、导入到调用一律未接。

**绑定层与内核之间的激活/会话通道断链（审计面 3 第 3 条）**

3. `chips-ecosystem/packages/native/types/chips-native.d.ts:105-117`（本轮复核函数面）：绑定层对外只有 `bridgeRegister` / `bridgeUnregister` / `bridgeRequest` / `bridgeCancelSession` 四方法，与契约 `INativeBridge`（`05/03.05:181-186`）一致——接口形状本身没有提供方激活与会话登记通道。

## 三、影响范围

- 断链 + 能力缺位：§8.1–§8.7 的全部绑定约定没有落地宿主；即便装载 `chips-native.node`，注册因 owner 未激活被内核拒绝、调用因会话不存在返回 `BRIDGE_SESSION_UNKNOWN`——Bridge 三层（宿主 / 绑定 / 内核）在真实进程内不可端到端装配。
- 工单005 剩余面③「绑定层四导出运行时端到端覆盖」在该通道打通前也不可能达成；W3 集成层实测（TD-001 偿还动作）同样被此地基缺口阻塞。
- 涉及包：`@chips/host`（main 进程）、`chips-native`（Neon 绑定面形状）、`chips-bridge` crate（前置校验为既定内核语义）。

## 四、复现步骤

1. 构建 `chips-native`（`packages/native`，`check-abi` 等值门禁通过）。
2. Node 侧加载 `.node`，调用 `bridgeRegister({ descriptor, owner, ... })` —— 由于进程内没有任何 API 能先执行 `activate_provider(owner)`，注册按内核校验失败（owner 未激活）。
3. 跳过注册直接 `bridgeRequest({ requestId, capabilityId, sessionId, input })` —— 无任何通道产生有效 `sessionId`，内核按 `BRIDGE_SESSION_UNKNOWN` 拒绝。
4. 检索 `grep -rn "chips-native" chips-ecosystem/packages/host/src` —— 0 命中，宿主连绑定层都未装载。

## 五、期望行为

契约与代码收敛：宿主存在契约点名的适配层，且 `INativeBridge` 方法面（或其正式扩展）具备提供方可激活、会话可登记的完整通道，使「注册 → 会话 → 调用 → 取消」在真实进程内端到端可用；或在裁定后修订 §5 / §8 的接口形状与文件清单，使文档承诺与可实现面一致。
