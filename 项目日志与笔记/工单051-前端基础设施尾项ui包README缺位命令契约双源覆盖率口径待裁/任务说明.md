单源化候选方案（≥2，本波零改码，候主智能体裁定）：

- **方案 A（推荐）——UI 转 `import type` 转发 SDK 类型**：仿 `sdk/src/types/bridge.ts` 对 `@chips/bridge` 的转发先例（唯一来源、不复制定义）。改动面：`gates.config.json` `packages/ui.allowedInternal` 加 `@chips/sdk`、G9 边界白名单/《01-代码组织规范》§6.4 随动、ui `contract.ts` 收敛为运行时独有类型 + 转发行、运行时/组件 import 随动。风险：UI→SDK 新依赖边改变「共享层不依赖 SDK」的既有分层语义（sdk 依赖 bridge/scaffold），且渲染帧/vendor 外部化面需复核；触跨层契约发布面，**建议走 RFC 流程**后再实施。
- **方案 B——维持双源 + 机械一致性锁**：不动依赖边，在 `tests/contract`（或包内 `src/command/contract.test.ts`）新增「三面字段级一致性」快照锁（TS 类型互赋 +《13》表格对账），漂移即红。成本最低、零架构变更；缺点：双源事实仍在，字段漂移从「静默」变「触闸」。可作为 A 裁定前的过渡锁或 A 否决后的终态。
- **方案 C——抽取契约类型独立包（如 `@chips/contract`）**：三方同源。改动最大（新包、发布面、pnpm workspace、G1 表、构建链），超出当前尾项收口定位，仅备案不推荐。

推荐：短期 B（本波即可登记为候派单）、终态 A（需 RFC 与边界表裁定）。理由：B 不触红线即可消除「静默漂移」风险；A 才是真单源，但新依赖边涉分层语义，必须由主智能体/RFC 裁。
