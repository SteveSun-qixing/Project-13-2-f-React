## 二、缺陷与证据（均为 2026-09-21 进程面实测）

### 缺陷① `chips --version` 在构建产物上恒回退 `0.0.0`

- 文档：§2.1「`--version` 输出 `chips` 版本与平台版本并退出 0」。
- 实现：`packages/cli/src/version.ts` 以 `createRequire(import.meta.url)` 解析 `../../package.json`。该相对路径按 **src 布局**成立（`src/version.ts → packages/cli/package.json`）；编译产物为 `dist/version.js`，同一路径解析到 `packages/package.json`（不存在），`readVersion()` 落入 catch 分支返回 `'0.0.0'`。
- 实测：`node packages/cli/dist/bin.js --version` → stdout `{"chips":"0.0.0","platform":null}`，退出 0；而 `packages/cli/package.json` 的 `version` 为 `0.1.0`。包内单测（vitest 直跑 src）读到的恰是 `0.1.0`，两执行面口径分叉，单测无法暴露。
- 期望行为：构建产物上的 `--version` 输出与包清单一致（或将版本事实源统一到产物可解析的位置）。

### 缺陷② 无承载环境下「命令不存在」类失败返回 6 而非文档承诺的 3

- 文档：§2.3「`chips host ...` 返回 `CLI_COMMAND_NOT_FOUND`（退出码 3）」（`host` 属固定根保留集，判定不依赖任何索引）；§3.1.1「未知命令帮助返回 `CLI_COMMAND_NOT_FOUND`（退出码 3）」；§2.5 退出码 3 =「命令不存在或冲突」。
- 实现：`src/run.ts` `runEntry()` 在固定命令树 `matchBuiltinCommand` 未命中后，**先**调用 `client.cliCommand.list()`/`resolve` 做插件路径匹配，未先行判定「保留固定根 / `help <未注册命令>`」这两类无需索引即可定性的输入；无承载适配器时 `list()` 即抛 `CLI_TARGET_UNAVAILABLE`（`src/client/service-router.ts` `unavailable()`）。
- 实测（离线进程面）：
  - `chips host list` → 退出 6，`CLI_TARGET_UNAVAILABLE`（`details.route: cli.command.list`）；
  - `chips frobnicate xyz` → 退出 6，同上；
  - `chips help nosuchcmd` → 退出 6，`details.route: cli.command.resolve`。
- 边界说明：任意未知 token 在**有承载环境**时经索引正常返回 3，离线 6 尚可解释为「承载缺失先于索引判定」；但保留固定根与 `help <未注册命令>` 的 3 属**无需索引即可定性**的承诺，且离线进程同样应兑现。
- 期望行为：`runEntry()` 在进入插件分支前完成保留根（`host` 等 `FIXED_COMMAND_PATHS`/保留集，§2.3）与 `help` 目标未注册（§3.1.1）的先行判定，返回 `CLI_COMMAND_NOT_FOUND`（3），与承载环境无关。

### 缺陷③ `plugin pack` 第二次打包被自身上一次产物阻断

- 文档：§3.5.2「同一输入两次打包必须字节级可复现」；§7.2 标准脚本 `chips plugin pack --out dist/`（输出目录与默认输出目录同为 `<dir>/dist`）；《03-插件包格式》§2.2 嵌套归档禁令的对象是「包内成员」。
- 实现：`src/artifacts/cpk-pack.ts` `collectPackInput()` 收集包根白名单子树（`dist/`、`assets/`、`manifest.yaml`、`render.js`），不排除 `.cpk` 归档；`CPK_ARCHIVE_INVALID`「嵌套归档」守卫随即将**上一次打包落在 `dist/` 的自身输出**判为输入违规。
- 实测（进程面复现，对象为 `chips plugin create --role basecard` 脚手架工程离线 `pnpm install --offline` + `pnpm run build` 后的工程目录）：
  1. `chips plugin pack`（缺省 `--out` 即 `<dir>/dist`）→ 退出 0，生成 `dist/<名称>-<版本>.cpk`；
  2. 再次 `chips plugin pack` → 退出 1，`CPK_ARCHIVE_INVALID`，`details.file: dist/<名称>-<版本>.cpk`，错误文案「打包输入包含嵌套归档（通常是未清理的旧产物）」。
- 影响：脚手架模板 `package` 脚本（`chips plugin pack --out dist/`）与文档示例流程在**重复执行**时必红；「两次打包字节级可复现」的验收只能在 `--out` 指向工程外目录时达成。当前规避：`clean` 脚本清理 `dist/` 后重跑（文档未把「重打包前必须 clean」写成承诺）。
- 期望行为（裁决归工单方面）：`pack` 收集输入时排除本次输出目录内与 `<名称>-<版本>.cpk` 同族的本包历史产物（或明文规定输出目录不得位于输入白名单子树并由 CLI 先行拒绝），使 §7.2 标准脚本可重复执行。

## 三、影响范围

- 缺陷①：平台发行包内 `chips --version` 的版本事实源失真；契约测试与门禁若断言版本号将漂移。
- 缺陷②：用户脚本按 §2.5 以 `3` 判别「命令不存在」在离线进程面失效；E2E/集成测试无法按文档口径固化这三条断言。
- 缺陷③：CI 或开发者连续执行 `pnpm --filter <插件> run package` 必红一次；金链路 CLI 链「打包」步骤的可重复性受损。

## 四、复现步骤

环境：`chips-ecosystem/`（pnpm monorepo），`pnpm --filter @chips/cli run build` 已执行。

- ①：`node packages/cli/dist/bin.js --version` → 观察 `chips` 字段为 `0.0.0`。
- ②：`node packages/cli/dist/bin.js host list; echo $?` → `6` 与 `CLI_TARGET_UNAVAILABLE`；`node packages/cli/dist/bin.js help nosuchcmd; echo $?` → 同上（route 为 `cli.command.resolve`）。
- ③：临时目录内 `node <bin> plugin create --role basecard --id chips.e2e.repro --name 复现 --dir <ws>/generated/<slug>`（cwd 使 `--dir` 呈相对形态以命中模板 tsconfig 深度契约），镜像工作区 `pnpm install --offline` + `pnpm run build` 后，连续两次 `node <bin> plugin pack`（缺省 `--out`）→ 第二次退出 1。

## 五、期望行为汇总

1. 构建产物 `--version` 输出 `packages/cli/package.json` 的真实版本（§2.1）。
2. 保留固定根与未注册 `help` 目标在任意承载状态下先行返回 `CLI_COMMAND_NOT_FOUND`（退出码 3）（§2.3、§3.1.1）。
3. `plugin pack` 可重复执行且字节级可复现（§3.5.2、§7.2 标准脚本语义）。

### 8.1 修复位置（修实现，不改文档承诺）

- **缺陷①（`--version` 产物面回退 `0.0.0`）**：`packages/cli/src/version.ts` 的清单
  相对路径由 `../../package.json` 改为 `../package.json`——构建以 `src` 为
  `rootDir`、`dist` 为 `outDir` 且 `version.ts` 恒在两布局的根层，`../package.json`
  在 `src/version.ts` 与 `dist/version.js` 两个执行面同深解析到
  `packages/cli/package.json`；另加包名守卫（`name !== '@chips/cli'` 不采信版本），
  防止未来布局漂移再次静默读错清单。
- **缺陷②（未找到面 6/3 分叉）**：`packages/cli/src/run.ts` `runEntry()` 在固定树
  未命中后、插件分支之前新增**固定根先行定性**（`FIXED_COMMAND_ROOTS` 含历史保留名
  `host`，大小写不敏感，§2.3 判定不依赖任何索引）直接回 `CLI_COMMAND_NOT_FOUND`（3）；
  任意未知 token 进入插件分支后，**发现阶段**（`cli.command.list`）的承载缺失按
  「无已启用插件命令即无匹配」定性为 3（§2.3），匹配成功后的执行链路失败保持
  `CLI_TARGET_UNAVAILABLE`（6）不被吞；`packages/cli/src/commands/help.ts` 对
  `cli.command.resolve` 的发现失败同形定性为 3（§3.1.1「未知命令帮助返回
  `CLI_COMMAND_NOT_FOUND`」），其余失败原样透传。
- **缺陷③（重复打包自阻断）**：`packages/cli/src/artifacts/cpk-pack.ts` 输出目录
  先行计算并传入 `collectPackInput()`；新增**按输出目录归属**的历史输出排除——
  位于本次输出目录（缺省 `<dir>/dist` 或工程内显式 `--out`）顶层、与本包归档命名

  非扩展名一刀切：输出目录内的外来归档（如 `foreign-2.3.4.cpk`）、`assets/` 等非
  输出目录归档、以及 `--out` 指向工程外时 `dist/` 内的任何归档，仍按
  [插件包格式] §2.6 以 `CPK_ARCHIVE_INVALID`（1）拒绝。
