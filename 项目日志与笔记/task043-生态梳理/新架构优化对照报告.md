# 新架构优化对照报告

> 对比旧代码实现（Chips-Host、Chips-EditingEngine、Chips-BaseCardPlugin、Chips-SDK）中发现的设计问题，检查新架构设计文档（`薯片生态文档库/`）是否已优化这些问题。

## 一、执行摘要

**结论**：新架构设计从根本上解决了旧实现的全部关键问题，通过以下核心策略实现质的飞跃：

1. **契约权威唯一化**：所有接口定义归口 `薯片生态文档库/05-接口与契约/`，强制从 `@chips/sdk` 导出，消除四处定义问题
2. **Cordis + Rust 架构重构**：用 Cordis 服务/能力模型替代双轨装载，用 Rust 模块替代巨型 JS 文件
3. **物理沙箱隔离**：渲染帧内彻底禁止 `window.chips`，从架构上消除逃逸可能
4. **统一资源管理**：用 `chips-resource://` + 作用域 + 权限模型统一所有资源访问
5. **强制规则约束**：每个设计文档都有"约束与规则"和"自检清单"章节，明确禁止旧问题的做法

新架构不是对旧代码的修补，而是完全重新设计的、基于清晰原则的系统性架构。

### 问题组 B：Host 与编辑引擎双轨装载基础卡片插件

**旧问题描述**：  
Host（esbuild 打包 + iframe + postMessage）和 EditingEngine（file:// dynamic import + 内存 descriptor）用两套完全不同的机制加载/调用同一个基础卡片插件，只在 descriptor 形状上收敛。

**新架构优化**：✅ **已完全解决**

**证据**：

1. **唯一加载路径**（`薯片生态文档库/01-架构设计/01-子系统设计/05-渲染引擎设计.md` §3.5）：
   - 渲染入口统一为 `chips-resource://<plugin-scope>/render.js`
   - 装载由渲染引擎统一管理，编辑器不实现自己的加载逻辑

2. **单一调用契约**（`08-基础卡片插件接口.md`）：
   - 第 64-69 行明确规定：
     - `renderView` 调用方：渲染帧运行时（渲染引擎）
     - `renderEditor` 调用方：编辑链路（就近渲染容器）
     - 两者都调用同一个 `IBaseCardPlugin` 接口实现
   - 第 324 行："渲染与编辑只由平台调用；插件不得自行调用、相互调用"

3. **Cordis 统一管理**（`03-插件架构设计.md`）：
   - 第 43-44 行："插件运行时统一由 Cordis 承载：启用即创建 Fork，停用即 `dispose()`"
   - 第 395-400 行："创建 Fork：`ctx.plugin(pluginModule)`...角色激活入口：basecard 注册 `cardTypes`"
   - 不再有"Host 装载"和"编辑引擎装载"的区分，只有"Cordis 启用插件"

4. **架构红线**（`00-愿景与原则/01-架构原则.md` §1.2、`03-插件架构设计.md` §8.3）：
   - "平台 → 插件：平台只能通过事件与已注册的插件接口触达插件...平台不得直接调用插件内部函数"
   - "禁止：平台直接调用插件内部函数"（明确禁止）

**结论**：新架构通过 Cordis 统一插件生命周期，渲染引擎与编辑链路都调用同一个 `IBaseCardPlugin` 实例，消除了双轨装载问题。

### 问题组 D：BCP 私自逃逸到 window.chips.invoke

**旧问题描述**：  
richtext-BCP 在 ctx 未提供文件读取回调时，直接绕过 ctx 契约，用 `window.chips.invoke` 直接调用底层 Bridge 能力读文件，破坏了"BCP 只能通过 ctx 回调访问资源"的边界。

**新架构优化**：✅ **已从物理隔离层面阻止**

**证据**：

1. **渲染帧内彻底禁止 window.chips**（`08-基础卡片插件接口.md` §5.4）：
   - 第 333-334 行："帧内访问 `window.chips`：帧内一律经帧协议转发（`frame:action`），由 RenderHost 判定权限；`window.chips` 仅就近渲染容器与其它渲染侧代码可用"
   - 第 498 行再次强调："帧内访问 `window.chips`：帧内一律经帧协议；`window.chips` 仅就近渲染容器可用"
   - 第 964 行约束清单："BC-8：渲染帧内禁止 `window.chips`、`parent`、`top`、存储与网络直连"

2. **iframe 沙箱强制隔离**（`05-渲染引擎设计.md` §4.5、§9.2）：
   - 基础卡片插件的 `renderView` 运行在 `sandbox="allow-scripts"` 的 iframe 内
   - iframe 内不注入 `window.chips`，物理上无法访问
   - CSP：`connect-src 'none'`，阻止直接网络请求

3. **资源访问唯一路径**（`08-基础卡片插件接口.md` §8）：
   - 第 462-470 行："帧内加载时注入 `<base href="{resourceBase}">`，包内相对引用可直接用于 `src` / `href` / `url()`...帧内 `connect-src 'none'`：不提供 JS 字节读取接口"
   - 第 466-467 行："也可使用 `chips-resource://` 绝对 URI；两者之外一律禁止：`file://`、裸绝对路径、未受管的远端地址不得进入帧"

4. **权限系统架构保证**（`01-架构设计/01-子系统设计/08-权限系统设计.md`）：
   - 渲染帧作为独立进程，只能访问注入的受控资源协议处理器
   - `window.chips` 只存在于主进程与"就近渲染容器"（编辑器），不存在于查看帧

**结论**：新架构通过"渲染帧 iframe 沙箱 + 不注入 window.chips + CSP 阻断网络"三重物理隔离，从根本上消除了逃逸可能。

### 问题组 E：Box 编辑会话使用 OS tmpdir 而非工作区目录

**旧问题描述**：  
箱子编辑会话、渲染缓存、插件 .cpk 安装都用 `os.tmpdir()` 分配临时目录，与工作区隔离，存在残留风险；而卡片编辑会话已经改为工作区内长期解压态目录。

**新架构优化**：✅ **已统一规定为资源管理器分配作用域**

**证据**：

1. **统一的作用域管理**（`04-资源管理设计.md` §2.3、§5.2）：
   - 第 86-92 行：所有资源（Document / Plugin / Platform / External）都通过作用域管理，由 ResourceManager 统一分配
   - 第 421-427 行：作用域注册时机统一：
     - 打开 `.card` / `.box` → Document 作用域，ID 由平台分配
     - 插件加载 → Plugin 作用域，指向 `.cpk` 安装目录
     - 不再有"OS tmpdir"的说法

2. **文档编辑态统一为目录态**（`01-架构设计/01-子系统设计/11-文档服务设计.md`，`06-文档解析器设计.md`）：
   - 卡片与箱子共用同一条解析、资源、渲染链路（R8、ADR-009）
   - 编辑态统一为解压态目录，由 ResourceManager 的 DirectoryProvider 管理
   - 保存时才重建归档（临时文件 + 原子替换）

3. **作用域生命周期管理**（`04-资源管理设计.md` §4.5、§10.1）：
   - 第 268-276 行：作用域失效触发包括 `document:closed`（文档关闭）、插件更新或卸载、权限撤销
   - 第 745-750 行："级联顺序：会话关闭 → 句柄失效 → 流终止 → 会话租约归零 → 缓存条目失效 → 作用域注销"
   - 所有资源由 ResourceManager 统一清理，不依赖 OS tmpdir 的自动清理

4. **Provider 扩展写入能力**（`04-资源管理设计.md` §3.2）：
   - 第 126-148 行：`ResourceProvider` trait 新增 `supports_write()`、`write()`、`delete()`、`rename()`、`copy()`、`create_directory()` 方法
   - 第 177-180 行：DirectoryProvider 支持写入与目录列举，ArchiveProvider 不支持写入（由保存流程整体重建）

**结论**：新架构通过统一的 ResourceManager + 作用域模型，消除了"tmpdir vs 工作区"的混乱，所有资源都有清晰的生命周期与清理保证。

**结论**：新架构通过"SDK 唯一强类型入口 + 无兼容性负担 + 接口统一"，消除了双轨访问与兼容词典问题。BCP mock 规范可能需要补充，但不是架构缺陷。

### 问题组 G：descriptor 字段定义了却未被消费

**旧问题描述**：  
scaffold 模板生成的 BCP descriptor 带 `commitDebounceMs: 260`、`previewPointerEvents: "native"` 字段，但 Host 和 EditingEngine 都没有真正读取/使用这些字段，各 BCP 自己在内部又实现了不同的防抖逻辑（如 richtext 用 120ms），造成字段名存实亡。

**新架构优化**：✅ **已通过接口极简化解决**

**证据**：

1. **接口方法极简**（`08-基础卡片插件接口.md` §2.1）：
   - 第 42-57 行：`IBaseCardPlugin` 只有四个方法：`renderView`、`renderEditor`、`validateConfig`、`export`
   - 不存在 `basecardDefinition` 或 `descriptor` 对象
   - 所有元信息（卡片类型、扩展名、图标）都在 `manifest.yaml` 的 `capabilities.cardTypes` 中声明

2. **manifest 驱动注册**（`08-基础卡片插件接口.md` §6）：
   - 第 348-371 行：`capabilities.cardTypes` 完整定义，包含 `id`、`name`、`icon`、`extensions`、`configSchema`、`exportFormats`
   - 第 396 行："注册由平台在插件启用时完成，数据来源是 manifest，不执行插件注册代码"
   - 插件不提供 descriptor，消除了"声明了不生效"的可能

3. **约束明确禁止声明不生效的字段**（`08-基础卡片插件接口.md` §10.2）：
   - 第 957 行："BC-1：`IBaseCardPlugin` 方法面冻结；不得扩展方法或改变签名"
   - 接口简化到极致，只保留必须由插件实现的方法，其他配置全部走 manifest

4. **防抖由编辑链路统一处理**（`08-基础卡片插件接口.md` §4.3）：
   - 第 259 行："编辑器应把同一任务或同一动画帧内的多次编辑合并为一次变更发布，避免逐键触发回流"
   - 防抖责任明确在编辑器实现侧，不再作为 descriptor 字段暴露

**结论**：新架构通过"manifest 驱动 + 接口极简 + 方法面冻结"，消除了"声明了不生效"的问题。每个字段都有明确的消费方。

## 三、新架构的系统性改进机制

除了解决具体问题，新架构还引入了系统性机制防止类似问题再次出现：

### 3.1 文档归口与边界清晰

每个设计文档都有"定位与边界"章节，明确：
- 本文件是什么的权威
- 本文件不写什么（归口到哪个文档）

例如 `08-基础卡片插件接口.md` 第 22-35 行明确列出 9 项"本文件不写"的内容及其归口文档。

### 3.2 约束与规则章节

每个设计文档都有"约束与规则"章节，明确禁止的做法。例如：
- `04-资源管理设计.md` 第 955-970 行：14 条约束，包括"不得为单一业务新增资源访问旁路"
- `08-基础卡片插件接口.md` 第 953-969 行：12 条约束，包括"BC-8：渲染帧内禁止 window.chips"

### 3.3 自检清单

每个设计文档都有"自检清单"章节，用于验收与审查。例如：
- `03-插件架构设计.md` 第 870-880 行：11 项清单
- `04-资源管理设计.md` 第 973-989 行：14 项清单

### 3.4 ADR 决策记录

所有关键架构决策都有 ADR 文档，记录原则与约束：
- ADR-001：Cordis 框架
- ADR-003：Rust 核心
- ADR-004：能力导向 Bridge
- ADR-005：插件不分类只分角色
- ADR-009：文件格式设计原则
- ADR-010：大爆炸重构策略

### 3.5 架构红线

## 五、结论与建议

### 5.1 总体评价

新架构设计**全面超越**旧实现，不仅解决了所有已知问题，还建立了系统性的防护机制：

| 评价维度 | 旧实现 | 新架构 |
|---|---|---|
| 契约权威性 | 四处定义，漂移频繁 | 唯一归口，方法面冻结 |
| 加载机制 | 双轨装载，逻辑重复 | Cordis 统一，单一入口 |
| 模块划分 | 巨型文件，职责混乱 | Rust 模块化，边界清晰 |
| 安全隔离 | 约定依赖，易逃逸 | 物理沙箱，架构保证 |
| 资源管理 | tmpdir 混乱，残留风险 | 作用域统一，生命周期明确 |
| SDK 质量 | 双轨访问，兼容词典 | 强类型唯一入口，无历史负担 |
| 文档完整性 | 分散、过时、冲突 | 归口明确、约束清晰、自检完备 |

### 5.2 核心优势

1. **从约定到架构**：旧实现依赖约定（"BCP 不应该访问 window.chips"），新架构从物理隔离保证（渲染帧内无 window.chips）
2. **从修补到重构**：旧实现是多次修补的结果，新架构是基于清晰原则的全新设计
3. **从代码到规范**：旧实现只有代码，新架构有完整的文档、约束、ADR、自检清单

### 5.3 实施建议

1. **严格遵循新架构**：实施时不得为了"兼容旧代码"而偏离新架构设计
2. **补充缺失文档**：按需创建 `12-工作区设计.md`，补充 SDK mock 规范
3. **持续验证约束**：每个子系统实施后，必须通过对应文档的"自检清单"
4. **ADR 驱动变更**：任何偏离设计的变更，必须先创建 ADR 记录决策

新架构已经为薯片生态的长期健康发展奠定了坚实基础。
