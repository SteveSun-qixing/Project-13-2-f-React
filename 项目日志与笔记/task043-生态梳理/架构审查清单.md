## 审查原则（来自 01-架构原则.md）

每个设计决策必须回答以下问题：

### 核心问题

1. **为什么不能做成插件？**
   - 如果答案是"因为方便"或"因为常用" → **错误**
   - 只有"基础设施"才能在平台层，"业务能力"必须在插件层

2. **这是基础设施还是业务能力？**
   - **基础设施**（可以在平台）：Cordis 运行时、Bridge 能力路由、资源管理、权限系统、渲染引擎框架、事件系统、配置系统
   - **业务能力**（必须在插件）：文件转换、图片处理、文档编辑、特定卡片类型、特定布局、同步服务、搜索索引

3. **插件能否通过现有机制实现？**
   - 如果能通过"服务注册/发现"实现 → 必须用服务插件
   - 如果能通过"能力注册"实现 → 必须用能力注册
   - 如果需要新的平台机制 → 需要充分论证

#### 问题 1：文件转换服务 ❌ **已识别，待修正**

**错误设计**：将文件转换设计为"平台级 Cordis 服务"

**违反原则**：
- 违反 1.1 "一切皆插件"

- 其他插件通过 `ctx.inject(['file-converter'])` 消费

#### 问题 2：同步引擎 ✅ **已确认正确**

**审查结果**：同步引擎设计**正确**

**理由**：
1. 同步引擎是**框架/机制**，提供通用同步原语：变更检测、版本向量、冲突判定、增量同步协议
2. 具体远端存储、账户体系由**同步插件（service 角色）**实现
3. 架构清晰：平台提供机制，插件提供实现
4. 符合"平台不做业务"原则：平台不自带任何远端服务

**类比**：同步引擎 vs 同步插件 = 渲染引擎 vs 卡片插件

## 审查方法

### 对每个子系统设计文档

1. **阅读文档名称与定位**
   - 如果名称包含具体业务（如"图片处理"、"文本编辑"） → 🚨 红灯
   - 如果名称是抽象框架（如"渲染引擎"、"插件架构"） → ✅ 可能正确

2. **阅读核心职责**
   - 是否包含"提供 XXX 算法"？ → 🚨 业务能力
   - 是否包含"管理 XXX 框架"？ → ✅ 基础设施
   - 是否包含"编排 XXX 流程"？ → ✅ 基础设施

3. **检查代码示例**
   - 平台代码中是否包含具体业务逻辑？ → 🚨 违反原则
   - 平台代码中是否只负责路由/调度？ → ✅ 正确

4. **检查对外接口**
   - 接口是否暴露了具体业务方法（如 `convertImageToPng`）？ → 🚨 违反原则
   - 接口是否只暴露抽象能力（如 `request(capabilityId, input)`）？ → ✅ 正确

### 对每个 ADR 文档

1. **检查决策是否属于平台层**
   - 插件框架选择 → ✅ 平台决策
   - 前端技术栈 → ✅ 平台决策
   - 具体功能实现方式 → 🚨 不应该是 ADR

2. **检查是否过度设计**
   - 是否为"未来可能的兼容性"预留接口？ → 🚨 违反 2.7
   - 是否为"可能的扩展"增加复杂度？ → ⚠️ 需要评估

2. **服务插件角色明确化**：
   - 已在 `03-插件架构设计.md` 中定义服务插件通过 `ctx.provide` 注册服务供其他插件消费
