## 一、现状勘查结论

### 1.1 此前不存在任何真实 `.cpk` 夹具或其校验用例

- 全仓（`packages/host`、`tests/**`，本次改动前）对 `.cpk / packCpk / validateCpk` 的引用检索：`packages/host` 侧**零命中**——Host 插件链相关测试全部走内存清单/能力注册对象，从未装载过真实归档包。
- `tests/e2e/tests/` 仅有 `assertions / environment / fixtures / workspace` 四个测试文件，均与插件包无关。
- `tests/e2e/fixtures/` 既有先例是 `generate-fixtures.mjs`（cards/boxes JSON 夹具 + `--check` 逐字节比对模式），本次链完全沿用该先例口径。
- `chips-ecosystem/.gitignore:13` 的 `*.cpk` 通配此前无例外——即使生成真实包也会被吞没（工单018 同型缺陷），本次已加锚定例外（§四）。

### 1.2 唯一的示例插件工程与「生成不出真实包」的根因

- `examples/plugins/hello` 是仓库唯一插件示例工程（`manifest.yaml`：`chips.example.hello@0.1.0`，role app），已有 vite 双构建（`vite.main.config.ts`/`vite.render.config.ts`）。
- 勘查实测（本次修复前）：`node packages/cli/dist/bin.js plugin pack --dir examples/plugins/hello --out <tmp>` 直接 **EXIT=1 `CPK_LIMIT_EXCEEDED`**——`pack` 会把整个目录（含 `node_modules` 全部文件）作为打包输入，遍历在归档收集阶段即触发限额。
- 根因证据（修复前 HEAD 版本）：`packages/cli/src/artifacts/cpk-pack.ts:16,38` ——`packCpk` 直接 `collectDirectory(fileSystem, dir)` 全目录收集，未做《03-插件包格式》§7.1「收集到暂存目录」的包根白名单投影（`manifest.yaml | dist/ | render.js | assets/`）。规范要求的输入投影在实现中不存在，故任何真实工程都不可能 pack 成功。
- 结论：这不是夹具缺口，而是 `@chips/cli` pack 的真实缺陷。因属「确属缺陷」且不改公开命令签名，按工单授权在 `packages/cli/**` 范围内修复（§五之 1）。

### 1.3 CLI 校验面对信任根的缺口（不修，已提工单 019）

- `packages/cli/src/artifacts/cpk-validate.ts:478-484`：签名阶段查 `input.trustRoots[keyId]`，未注册即 `CPK_SIGNATURE_INVALID「信任根未注册的 keyId」`。
- 命令面 `packages/cli/src/commands/plugin.ts:195-201`（pack 的签名注入只有 `CHIPS_SIGNING_KEY_FILE`）至 `:223-252`（validate 子命令）均**无任何信任根注入参数/环境变量/配置文件通道**；运行时组装 `packages/cli/src/runtime/local-client.ts:31` 的 `createLocalArtifacts(options)` 也不透传 trustRoots。
- 即：CLI 命令面上，签名包 validate 恒失败。库面层 `createLocalArtifacts({ trustRoots })` 可注入——夹具验证矩阵走的就是这个唯一可用面。缺口登记为工单 019。

## 二、生成链（可重复 / 离线 / 确定）

### 2.1 链路与产物

```
examples/plugins/hello 源码
  └─ pnpm --filter @chips/plugin-hello run build        （vite，NODE_ENV 锁定 production）
       └─ node packages/cli/dist/bin.js plugin pack --dir examples/plugins/hello
            --out <tmp> --sign --key-id chips-fixture-2026
            CHIPS_SIGNING_KEY_FILE=keys/fixture-signing-private.pem
            （真实 PKCS8 Ed25519 私钥，node:crypto 签 contentHash UTF-8 字节）
                 └─ 负向变体（engine 内存重打包 / 字节翻转）
                      └─ tests/e2e/fixtures/cpk/packages/*.cpk + checklist.json
```

- 编排脚本：`chips-ecosystem/tests/e2e/fixtures/cpk/generate-cpk-fixtures.mjs`（约 370 行，无占位实现、无 TODO）。
- 故意用 `node packages/cli/dist/bin.js` 而非 `pnpm exec chips`：PATH 上存在陈旧全局 `chips`（`~/.volta/bin/chips`），生成链必须锁定本仓 CLI（关联工单 020 之 ①）。

### 2.2 确定性设计

| 维度 | 手段 |
|---|---|
| 归档字节 | ZIP Store（method 0）+ 固定 1980-01-01 DOS 时间戳 + 条目按路径字节序（CLI 既有保证） |
| 签名 | Ed25519 本身确定性（RFC 8032）；夹具密钥对为**入库的固定密钥**（`keys/*.pem`），非每次新生成 |
| 构建输出 | 子进程环境 `deterministicEnv`：`NODE_ENV=production` 强制 + 剔除全部 `VITEST*` 键（vitest 注入的 `NODE_ENV=test` 会改变 vite 产物字节，见 §五之 4） |
| 离线 | 全链仅本地文件与 workspace 依赖，无任何网络访问 |

### 2.3 命令

```bash
cd chips-ecosystem
# 生成（写入夹具）
node tests/e2e/fixtures/cpk/generate-cpk-fixtures.mjs
# 校验（重建 + 逐字节比对 + 多余文件扫描 + 五阶段矩阵）
node tests/e2e/fixtures/cpk/generate-cpk-fixtures.mjs --check
# 契约测试挂接（spawn 上述 --check）
pnpm --filter @chips/test-contract run test:contract   # tests/contract/tests/cpk-fixtures.test.ts
```

### 2.4 五阶段校验矩阵（`--check` 内嵌）

用 `@chips/cli` 库面 `createLocalArtifacts({ trustRoots: { 'chips-fixture-2026': <信任根公钥 PEM> } })`、channel `source: 'user'`，对**入库的夹具文件本身**逐个 validateCpk：正夹具要求 `valid` 且 signature 阶段 `passed`；三个负夹具要求精确命中错误码+阶段（§三）。任一不符即 `--check` 非零退出。

## 五、发现的缺陷与处置

1. **pack 无暂存投影（已修，授权范围内）**：`cpk-pack.ts` 以 `collectPackInput` 按包根白名单（`manifest.yaml`、`render.js`、`dist/`、`assets/`）投影收集；成员含嵌套归档扩展名（如残留旧 `.cpk`）时报 `CPK_ARCHIVE_INVALID「打包输入包含嵌套归档…」`。公开命令签名未动。配套测试改写入 `packages/cli/tests/artifacts-cpk.test.ts`（白名单投影用例 + 嵌套归档拒绝用例，替换旧的 `CPK_LAYOUT_INVALID` 全目录口径用例）。
2. **zip 归档错误缺 `details.stage`（已修，§八 合规）**：`zip.ts` 新增 `archiveError(detail, file?)` 统一抛 `CPK_ARCHIVE_INVALID` 且携带 `{ stage: 'archive', file }`；`readZipStore`/`findEndOfCentralDirectory` 全部抛出点改造。此缺陷是首跑验证矩阵时被 CRC 负夹具暴露的。
3. **CLI 存量测试漂移（已修）**：`packages/cli/tests/local-runtime.test.ts` 中「SDK 脚手架子路径未导出 → CLI_TARGET_UNAVAILABLE」用例已过期（`@chips/sdk` 现导出 `./scaffold`），改写为断言真实 SDK create 链路。修复后 CLI 全套 466/466 通过。
4. **vitest 环境污染确定性（已修，生成器侧）**：contract 测试内 spawn `--check` 时子进程继承 `NODE_ENV=test` 导致 vite 产物字节漂移、四个夹具全部「内容不一致」；生成器对 build/pack 子进程统一 `deterministicEnv`（强制 production + 剔 `VITEST*`），standalone 与 vitest 双环境一致通过。
5. **validate 目录态口径漂移（未修，提工单 020）**：`cpk-validate.ts:554-563` 目录态仍用全目录 `collectDirectory` 对归档白名单硬校验（§7.2 文档示例 `chips plugin validate <dir>` 在真实工程上恒 `CPK_LAYOUT_INVALID`）；pack 本次已按 §7.1 投影，validate 因涉 Host 三路智能体在途一致面、且属口径裁决而非缺陷修复，未动，登记工单 020 之 ②。
6. **信任根无 CLI 注入面（未修，提工单 019）**：见 §1.3。CLI 命令面上签名包 validate 实测 `EXIT=1「信任根未注册的 keyId：chips-fixture-2026」`——如实记录，夹具矩阵走库面。
7. **陈旧全局 CLI bin（未修，提工单 020 之 ①）**：`pnpm exec chips` 在 `examples/plugins/hello`（package.json `package` 脚本，无 @chips/cli 依赖声明）下会静默落到 `~/.volta/bin/chips` 旧版。生成链已绕开（绝对路径启动本仓 `dist/bin.js`）。
