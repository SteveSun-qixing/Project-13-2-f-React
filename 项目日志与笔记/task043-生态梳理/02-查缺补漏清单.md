## 1. P0 · 重构前置（先决决策与清洗）

### 1.1 命名与术语统一
- **问题**："Host / 薯片主机 / chips-host" 遍及所有文档、SDK、CLI、包名（`chips-host/*`）、权限串、事件名；"薯片平台"零出现。
- **影响**：文档与代码的第二套语言，越晚改成本越高。
- **待办**：① 建《术语表》主发布文档（薯片平台 / 薯片核心 / 薯片运行时 / 薯片内核 / 壳 / 插件宿主）；② 制定文档级更名清单（文档先改，代码随重构改）；③ 明确"Host"在代码中保留为角色词的范围。

### 1.2 平台运行时正式设计
- **问题**：现状是"每插件自带 antd + `@chips/ui`"（task030 决策）；新决策是"平台运行时为默认、自带为例外"，但交付机制、边界、版本治理全部空白。
- **影响**：决定"系统一更新所有软件自动变"能否成立；决定插件包形态与依赖模型。
- **待办**：新建《平台运行时设计》主发布文档：运行时构成（表现/能力/契约）、默认托管与自带例外规则、构建期外部化与运行时注入机制、版本协商与兼容承诺、语义 API 与实现的关系、跨端一致性。

### 1.3 跨语言契约单一源方案
- **问题**：完全空白。`04-数据交换协议` 只提了 Protobuf 原则，无 `.proto`、无生成约定、无 golden vectors；四语言（TS/Rust/Kotlin/Swift）将各自手写契约。
- **影响**：Rust Host Core 迁移的前置；不做则跨端必然分裂。
- **待办**：① 契约源选型（Protobuf / JSON Schema / 自研 DSL）；② 确定覆盖域（route descriptor、schema、StandardError、capability snapshot、manifest、Bridge envelope、句柄、生命周期状态）；③ 生成管线（TS/Rust/Kotlin/Swift）+ CI 无 diff 校验 + golden vectors。

### 1.4 组合基元最终集合
- **问题**：候选基元（表面/文档/作业/流/句柄/权限）未定；`DocumentHandle/ResourceHandle` 只有名字无契约；stream 原语完全缺失；job 分散（06/13/CLI）；作用域/事件溯源/可逆副作用全无。
- **影响**：所有能力 API 与插件契约的设计前提。
- **待办**：新建《能力基元设计》文档，定稿基元集合、各基元的公共契约位、与插件权限/作用域/审计的关系。

### 1.5 跨端能力矩阵与降级契约
- **问题**：无 per-platform 能力矩阵；PAL 能力快照仅 Desktop/Headless 有真实实现；无"等价行为/正式 unsupported"的契约化表达。
- **影响**：五端一致性与"能力诚实"的实现基础。
- **待办**：① 定义能力快照 schema（跨语言）；② 输出五端能力矩阵（含桌面/移动/Web/Headless 差异）；③ 定义降级与 unsupported 的公共语义。

### 1.6 第一版边界定义
- **问题**："第一版"在大量文档中被引用（不做兼容、不做回退），但从未定义它包含什么。
- **影响**：决定哪些缺口必须现在做、哪些可以后放；决定重构范围。
- **待办**：决策文档（本地创作+消费闭环？含哪几端？含社区？含市场？）。

### 1.7 文档真相收敛方案
- **问题**：三处真相（`生态设计原稿`、`生态共用技术文档`、task043 梳理稿）+ 大量 stale 文档（架构 05/06/07/08/09/11 泛化草稿、10/15 废弃、手册/19/20 部分过期）。
- **影响**：不收敛则每次查阅都有第二口径。
- **待办**：① 文档体系总图（哪类信息住哪一层、唯一主发布位置表）；② 归档/重写/吸收清单；③ 原稿与 task043 的迁移路径。

### 1.8 task030 残留清洗（文档与契约）
- **问题**：13 份以上契约/规范仍含 theme/i18n 正式字段或强制口径，其中两处硬伤：`08-箱子布局运行时契约`（强制 `theme.getAllCss/tokens` 注入）、`13-命令系统契约`（`titleKey` 必填）；另 SDK 仍暴露 `client.theme.*`、Host 仍挂 `theme/i18n` 服务。
- **影响**：新插件按错误契约开发；"第一版无兼容包袱"被破坏。
- **待办**：逐份修订清单（01/02/03/04/05/07/08/09 卡片/09 社区/10 个人/13/文件格式 01/文件格式 03 + 卡片业务/箱子业务），并决定 Host 内部 theme/i18n 服务是删干净还是明文保留。

### 1.9 Electron 绑定清洗（正式契约不得含平台实现语义）
- **问题**：`ui.window.chrome`（Electron 窗口语义）、`chips-render://` 协议、Electron PDF 打印模板、IPC 通道表、`window/shell/tray/ipc` legacy 子域、`getPathForFile` 等被写成正式公共契约。
- **影响**：与"跨端天性"直接冲突；移动/Web 无法实现。
- **待办**：定义"Shell 专属能力"的正式表达方式（声明位 + 降级语义），逐份清洗 01/03/05/06/07 与文件转换/箱子运行时契约。

## 4. 建议推进顺序（供排期参考）

1. **P0 决策批次**（先决）：命名落地 → 平台运行时设计 → 基元集合 → 契约单一源 → 能力矩阵 → 第一版边界 → 文档收敛方案。
2. **P0 清洗批次**（可并行）：task030 残留 + Electron 绑定清洗（文档与契约先行，代码随重构）。
3. **P1 骨架批次**：契约生成管线 → Rust Kernel → 服务化收口 → 基元落地 → 平台运行时实现。
4. **P1 平台批次**：Desktop 薄壳 → Android → iOS/Web/Headless → 工具链/门禁。
5. **P1 能力批次**：深度能力、转换、Office、脚手架修正。
6. **P2 生态批次**：市场、社区、视觉、文档收尾。
