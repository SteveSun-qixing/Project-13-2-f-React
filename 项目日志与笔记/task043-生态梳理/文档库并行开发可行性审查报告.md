# 文档库并行开发可行性审查报告

> 日期：2026-09-19
> 触发问题：文档库是否已经详细到可以支撑所有项目、插件、模块完全解耦、独立并行开发而不产生漂移？
> 审查方式：子代理系统性核查 `薯片生态文档库/` 全部 60 篇文档，对照 `旧版-生态共用技术文档/`、`旧版-生态共用技术文档-2/` 与各独立项目仓库，并对关键结论人工复核。

---

## 一、结论先行

**结论：可以支撑并行开发，已达到生产级门槛，但有一处高优先级缺口需要补齐。**

判定依据：
1. 10 篇接口契约文档（Bridge API、SDK API、核心接口、能力契约、事件契约、资源协议、四类插件接口）均达到"方法级签名 + 错误码 + 时序图 + 完整示例"的权威参考标准，评分 5/5。
2. 11 篇子系统设计文档全部具备统一的"定位与边界"章节和"本文件不做什么 → 归口文档"清单，依赖方向单向、无循环。
3. 旧文档库中的公共契约内容（协议与契约 15 篇、协议与接口标准 7 篇、文件格式规范 4 篇、架构设计 21 篇）已被系统性整合、去重进新文档库，组件库/主题/多语言等已按 ADR-006 正式废弃。
4. 三个并行开发场景（平台与插件独立开发、插件内部模块并行、跨项目协作）逐一核查后均评分 5/5，未发现会导致"团队各自实现后无法对接"的契约空洞。

**唯一高优先级缺口**：CLI 命令完整参考缺失。旧文档库有专门的 `chips` 主机命令行手册和 `chipsdev` 开发者命令行手册，新文档库目前只在《构建与打包》《快速开始》等文档中零散提及部分命令（`chips plugin pack`、`chips plugin validate` 等），没有一份权威、完整、逐项列出全部子命令/参数/退出码的 CLI 参考文档。这不影响插件契约层面的并行开发，但会阻塞 CI/CD 自动化脚本编写和新成员独立上手命令行工具。

## 五、并行开发可行性评估（三场景）

### 场景 A：薯片平台（Host+内核）与插件完全独立开发 —— 5/5

Host 团队仅依据 Bridge API、能力契约、资源协议、核心接口规范即可实现平台侧；插件团队仅依据四类插件接口文档 + SDK API 即可独立开发，不需了解 Host 内部实现。潜在协作点（渲染帧沙箱协议、`markCommitted` 时序）均已有 ASCII 时序图落在权威文档中，不依赖口头对齐。

### 场景 B：插件内部模块并行开发（如 `renderView` 与 `renderEditor` 分工） —— 5/5

`Card` 视图模型、`IEditor` 八成员接口、`ICardPatchOperation`（RFC 6901）均为强类型定义，`markCommitted` 调用时机在 §4.3 有明确协议，两个模块的开发者可分别对照接口文档实现而互不依赖对方的代码。

### 场景 C：跨项目协作（编辑引擎 + Host + 基础卡片插件） —— 5/5

编辑引擎只需消费 `IEditor` 协议与 `Card` 视图模型，不需了解 BCP 内部实现；BCP 团队只需实现 `IBaseCardPlugin` 接口的四个方法即可，双方通过 12 条约束清单（BC-1~BC-12）和完整示例插件对齐验收标准。

## 七、结论重述

现有文档库在**接口契约完整性**与**子系统边界清晰度**两个维度均达到"可独立实施、可并行开发"的标准，旧文档库中的全部公共契约内容已被系统性吸收、整合或按 ADR 正式废弃，没有发现"两个团队各自看文档实现后无法对接"的契约空洞。

在用户确认之前，本报告不会擅自去实现 CLI 完整参考文档（这需要先核对 `@chips/cli` 真实实现范围，避免凭空编造命令）。建议用户明确是否已有 CLI 实现代码可供核对，再决定是否现在补齐该文档，或先登记为工单留待后续处理。
