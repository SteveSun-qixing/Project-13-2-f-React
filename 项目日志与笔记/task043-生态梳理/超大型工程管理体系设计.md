## 一、超大型工程的定义与特征

### 1.1 薯片生态的规模特征

- **代码规模**：预计 50万+ 行代码
- **技术栈复杂度**：Rust + Electron + React + Native Module + 插件生态
- **开发周期**：2-3 年持续开发
- **团队规模**：可能扩展到多人协作
- **子系统数量**：10+ 核心子系统（内核、Bridge、插件系统、渲染引擎、资源管理...）
- **外部依赖**：Cordis、antd、Electron、Rust 生态、Node.js 生态
- **平台支持**：桌面三端 + 未来移动两端

### 1.2 超大型工程的核心挑战

1. **架构复杂度**：多层次架构（内核-Bridge-插件），跨语言（Rust-TypeScript）
2. **依赖管理**：monorepo 管理、版本同步、循环依赖
3. **质量保证**：测试覆盖、性能基线、兼容性验证
4. **文档同步**：代码与文档的一致性
5. **变更管理**：架构演进、接口变更、向后兼容
6. **知识传承**：设计决策、技术选型、架构权衡

```markdown
已接受 (2026-09-19)

## 决策
完整引入 Cordis，并进行薯片生态定制...

## 后果
### 优势
- 原子化模块问题得到解决
- 插件热插拔能力

### 劣势
- 需要用 Rust 重新实现
- 学习曲线

### 风险
- Cordis 上游更新可能不兼容

## 替代方案
1. 自研插件系统
2. 采用其他框架（如 VS Code Extension API）
```

## 三、工程流程规范（开发生命周期）

### 3.1 从零开发的标准流程

```
Phase 0: 准备阶段（2-4周）
  ├── 完成所有第一层文档（愿景与原则）
  ├── 完成所有第二层文档（架构设计）
  ├── 完成所有第三层文档（开发规范）
  ├── 搭建基础工程骨架（monorepo + 构建工具链）
  └── 技术预研与 POC 验证

Phase 1: 核心基础（8-12周）
  ├── Rust 核心实现（Cordis 运行时）
  ├── Bridge 基础实现
  ├── Electron 壳集成
  ├── 基础测试框架
  └── 最小可验证原型

Phase 2: 子系统开发（20-30周）
  ├── 插件系统完整实现
  ├── 渲染引擎完整实现
  ├── 资源管理完整实现
  ├── 主题系统实现
  ├── 多语言系统实现
  ├── 文档解析实现（卡片/箱子）
  └── 完整测试覆盖

Phase 3: 生态建设（持续）
  ├── 官方插件开发（编辑引擎、查看器...）
  ├── 开发者工具（CLI、调试工具）
  ├── 示例与教程
  └── 社区文档

Phase 4: 优化与发布（8-12周）
  ├── 性能优化
  ├── 安全加固
  ├── 兼容性测试
  ├── 文档完善
  └── Beta 测试
```

### 3.2 每个 Phase 的交付物（Definition of Done）

#### Phase 0 交付物

- [ ] 所有第一层文档已完成并评审
- [ ] 所有第二层文档（ADR + 子系统设计）已完成并评审
- [ ] 所有第三层文档（开发规范）已完成并评审
- [ ] Monorepo 骨架已搭建，CI/CD 已配置
- [ ] 技术选型 POC 已验证（Cordis + Electron + Rust Native Module）

#### Phase 1 交付物

- [ ] Rust Cordis 运行时可以加载插件
- [ ] Bridge 可以从 JavaScript 调用 Rust 能力
- [ ] Electron 可以启动并显示 React 界面
- [ ] 单元测试框架已就绪
- [ ] 最小原型可以演示"加载一个插件并调用其能力"

#### Phase 2 交付物

- [ ] 插件系统完整可用（加载、卸载、隔离、热插拔）
- [ ] 渲染引擎可以打开并显示 .card 和 .box 文件
- [ ] 资源管理可以处理本地文件和网络资源
- [ ] 主题系统可以切换主题
- [ ] 多语言系统可以切换语言
- [ ] 测试覆盖率 > 80%
- [ ] 性能基线达标（冷启动 < 2s）

#### Phase 3 交付物

- [ ] 至少 3 个官方插件已完成（编辑引擎、查看器、资源管理器）
- [ ] CLI 工具可用（创建插件、打包、验证）
- [ ] 插件开发文档完整
- [ ] 至少 5 个示例插件

#### Phase 4 交付物

- [ ] 性能基线达标（冷启动 < 1s，渲染 60fps）
- [ ] 安全审计通过
- [ ] 三端兼容性测试通过（macOS、Windows、Linux）
- [ ] 所有文档已完善
- [ ] Beta 测试完成，关键 bug 已修复

## 四、变更管理流程

### 4.1 架构变更流程（重大变更）

```
1. 提出变更
   ├── 创建 RFC 文档（Request for Comments）
   ├── 说明背景、动机、影响范围
   └── 提出至少 2 个替代方案

2. 评审变更
   ├── 技术评审（架构一致性、性能影响）
   ├── 风险评估（破坏性变更、迁移成本）
   └── 决策记录（接受/拒绝，理由）

3. 实施变更
   ├── 更新 ADR 文档
   ├── 更新相关设计文档
   ├── 更新开发规范（如需要）
   └── 更新 CHANGELOG

4. 验证变更
   ├── 通过所有质量门禁
   ├── 更新测试用例
   └── 更新文档
```

**重大变更定义**：
- 修改核心架构设计
- 修改公开 API 接口
- 修改文件格式规范
- 引入新的核心依赖
- 修改构建流程

### 4.2 API 变更流程（破坏性变更）

```
1. 弃用阶段（Deprecation）
   ├── 标记 API 为 @deprecated
   ├── 添加 console.warn 警告
   ├── 更新文档说明替代方案
   └── 至少保留 2 个版本周期

2. 迁移阶段（Migration）
   ├── 提供迁移指南
   ├── 提供自动化迁移工具（如可能）
   └── 示例代码更新

3. 移除阶段（Removal）
   ├── 发布 Breaking Change 通告
   ├── 更新 CHANGELOG
   └── 更新所有文档
```

### 4.3 文档变更流程

```
原则：代码与文档必须同步更新

- 修改代码 → 同一 PR 中更新相关文档
- 修改 API → 同一 PR 中更新 API 文档
- 修改架构 → 同一 PR 中更新 ADR 或设计文档
- 修改流程 → 同一 PR 中更新开发规范
```

## 五、知识管理与传承

### 5.1 设计决策记录（ADR）

**目的**：记录"为什么这样设计"，而不仅仅是"怎样设计"

**规则**：
- 每个重大决策必须有 ADR
- ADR 一旦接受，不能修改（只能新增 ADR 推翻旧决策）
- ADR 必须记录替代方案和权衡理由

### 5.2 架构审查会议（Architecture Review）

**频率**：每 2 周一次

**议题**：
- 审查新的 RFC 提案
- 评审架构变更
- 讨论技术债务
- 分享技术调研

**输出**：
- 会议纪要（记录决策和理由）
- 更新相关 ADR
- Action Items

### 5.3 技术债务管理

**记录位置**：`项目日志与笔记/技术债务清单.md`

**记录内容**：
- 债务描述
- 产生原因
- 影响范围
- 优先级（P0/P1/P2/P3）
- 偿还计划

**偿还原则**：
- 每个 Sprint 至少偿还 1 项 P0 债务
- 每个 Phase 结束前必须清零 P0/P1 债务

## 九、总结

超大型工程管理的核心是：

1. **文档先行**：代码之前先有设计，设计之前先有原则
2. **决策可追溯**：每个重大决策都有 ADR 记录
3. **质量门禁**：每个 Phase 都有明确的 Definition of Done
4. **持续演进**：架构可以演进，但必须通过 RFC 流程
5. **知识传承**：文档与代码同步更新，设计决策永久记录
