## 一、四类角色（R1）

| 角色 | `type` | 入口接口 | 核心职责 | 界面形态 |
|---|---|---|---|---|
| 基础卡片插件 | `basecard` | `IBaseCardPlugin` | 定义卡片类型：查看渲染、编辑渲染、配置校验、导出 | 嵌于宿主视图（iframe） |
| 箱子布局插件 | `boxlayout` | `IBoxLayoutPlugin` | 定义布局：布局渲染、布局编辑、配置校验 | 嵌于宿主视图（iframe） |
| 应用插件 | `app` | `IAppPlugin` | 独立窗口应用：启动器、文件关联、命令、文件打开 | 独立窗口（`ui.surface`） |
| 服务插件 | `service` | `IServicePlugin` | 后台常驻服务：注册服务与能力、健康检查 | 无 UI |

- `manifest.type` 是单一值；一个插件只有一个角色；需要多角色能力时拆成多个插件，用 `dependencies` 组合。
- 角色不是功能分类：任意领域的功能都可以分别以四种角色承载（ADR-005）。
- 内核不感知角色：四类角色共用同一套加载、依赖与生命周期机制。

### 1.1 基础卡片接口要点

- 定义 `capabilities.cardTypes`（类型 ID、名称、图标、扩展名）；
- `renderView(view: BaseCardView, container)`、`renderEditor(view, container): IBaseCardEditor`、`validateConfig(config)`、可选 `export(basecard, format)`；
- 补充成员：`createInitialContent()`（插入节点的内容初值来源）、`collectResourcePaths(basecard)`；
- `aliases`（manifest `capabilities.cardTypes[].aliases`）：别名 → 正式 ID 由插件声明、平台读取时归一。

### 1.2 布局接口要点

- 定义 `capabilities.layouts`（布局 ID、名称、图标、描述）；
- `renderLayout(view: BoxRenderView, container)`、`renderEditor(view, container): ILayoutEditor`、`validateConfig(config)`；
- 布局切换只改变呈现方式，不修改箱子数据。

### 1.3 编辑句柄拆分

- `IBaseCardEditor` 与 `ILayoutEditor` 分别定义，SDK 分别导出，不导出笼统 `IEditor`；
- 两者 `getChange()` 返回各自变更类型；调用方在视图关闭时释放编辑器实例。

## 二、清单、入口与包

### 2.1 manifest 与 `.cpk`

- `manifest.yaml` 是**唯一权威清单**（字段规范见 [插件清单规范](../../../薯片生态文档库/03-插件开发/02-插件清单规范.md)）；包内其它配置文件不得与其冲突。
- `.cpk` = ZIP Store（不压缩归档）：根目录 `manifest.yaml` + 构建产物目录 + 静态资源；包内不得携带原生可执行载荷（R11）。
- `service` 角色的 Node/JS 依赖必须随包携带或声明为平台提供的能力；包内不得出现 `node_modules/`。

### 2.2 双入口：`dist/index.js` + `render.js`

| 入口 | 路径 | 角色 | 职责 |
|---|---|---|---|
| 插件模块入口（主进程部分） | `dist/index.js` | 全部角色 | 只承载主进程可执行部分：注册转发、`validateConfig` / `createInitialContent` / `collectResourcePaths` 等纯函数；经受管模块加载器加载 |
| 渲染入口（渲染部分） | `render.js` | `basecard` / `boxlayout` / `app` | 承载 `renderView` / `renderEditor` / `renderLayout` / `export` 等渲染侧实现；SDK 构建产出的单一 ESM 文件 |

规则：

1. 两个入口都必须是 UTF-8 文本 ESM 模块，默认导出对象；
2. 职责不得越界：`dist/index.js` 不得含 DOM 渲染逻辑；`render.js` 不得含主进程注册、文件 IO 或平台服务逻辑；
3. `service` 角色只有主进程部分（`dist/index.js`），**不存在渲染部分**；
4. 除 `dist/` 与 `render.js` 外，包内任何位置不得出现 `.js` / `.mjs` / `.cjs` / `.ts` 代码文件；
5. 入口文件各自不超过 8 MiB；`render.js` 必须外部化平台共享依赖（React、`react-dom`、`@chips/ui`），不得内联第二套组件库或第二份 React。

### 2.3 `engines.chips` 门禁

- `engines` 仅允许 `chips` 一个键，值为合法且非空的版本范围；声明时当前平台版本必须落在范围内。
- `engines.chips` 是独立于 `dependencies` 的**平台侧**门禁：依赖门禁约束插件之间的版本关系，本字段约束插件与平台的版本关系，两者都通过才允许启用与更新。
- 不满足时安装 / 启用 / 更新拒绝，返回 `CPK_ENGINE_UNSUPPORTED`。

### 2.4 签名与信任根

- 签名文件固定为包根 `signature.json`；`signature` 为对 `contentHash` 的 Ed25519 签名（Base64），`keyId` 由发布方信任根注册表解析。
- 来源渠道：`builtin` 必须签名（缺失 `CPK_SIGNATURE_REQUIRED`）；`user` 可选（未签名须明确提示"未签名发布者"并经用户确认，不得静默安装）；`development` 跳过签名校验。
- 签名无效返回 `CPK_SIGNATURE_INVALID`；签名有效不得作为跳过归档、结构、清单与载荷校验的理由；信任根未注册的 `keyId` 视为签名无效。

## 三、生命周期

### 3.1 安装

```
包结构校验 → manifest 校验 → 来源校验（签名）→ 版本与冲突检查
  → 权限解析（登记申请集合，默认未授权）→ 原子落盘 → 写注册表（installed）
```

- 安装不自动启用；安装失败不得留下半成品（临时目录清理、注册表无记录）。
- **安装只登记权限申请，不产生授权**：授权交互在首次启用时逐项展示与接受。
- 依赖缺失或版本暂不满足不阻止安装，仅在启用时阻塞；版本范围互斥在启用时返回显式冲突。

### 3.2 启用

1. 状态检查（必须为 `installed`）；
2. **首次启用逐项授权**：展示插件名与版本、权限说明、风险级别、解析后的限定值；用户接受后写入授权记录；**拒绝任一项不阻断启用**，该权限保持未授权、运行时调用被拒绝；
3. 生成会话权限快照；
4. 依赖解析（拓扑序，满足或可同时启用）；
5. 创建 Fork，副作用纳入追踪；服务注册进入暂存代际；
6. 角色激活入口（注册类型 / 布局 / 启动器 / 调用 `start`）；
7. 进入 `active`：暂存代际一次原子发布，发布 `plugin:loaded`。

### 3.3 停用、卸载与启动恢复

- 停用：依赖者检查（存在 `active` 依赖者默认拒绝 `KERNEL_DEPENDENCY_CONFLICT`，显式级联按逆拓扑序）→ 摘除路由 → 角色停止入口 → `Fork.dispose()` → `installed`；停用不删除文件、配置与授权。
- 卸载：必须为 `installed` / `failed`；有已安装依赖者时拒绝；撤销授权、删除配置缓存与目录；内置插件不可卸载，只能停用；卸载永不删除用户文件。
- 启动恢复：清理中断残留（`starting` / `stopping` 回滚为 `installed`）；按启用偏好与拓扑序逐个启用，单个失败隔离；`failed` 启动时不自动重试。

## 四、加载隔离与执行载体

| 隔离层 | 机制 | 效果 |
|---|---|---|
| 进程 | 主进程 / 渲染进程 / 工具进程；`nodeIntegration: false`、`contextIsolation: true`、`sandbox: true` | 单个窗口或工具进程崩溃不影响平台与其它插件 |
| Context | 插件 Context 只暴露允许面 | 作用域与生命周期隔离 |
| Fork | 副作用追踪与逆序撤销 | 停用后零残留 |

### 4.1 受管模块加载器（ModuleLoader）

- **主进程插件执行载体是受管模块加载器**：只允许加载插件作用域的 `chips-resource://` 模块与平台白名单模块（`@chips/sdk` 类型与平台提供物）；
- **禁止** `node:*`、`electron`、裸路径（如 `fs`、`path`）与任意文件路径；
- 加载器是**完整性门禁**：加载前校验模块来源与完整性摘要，越界加载或校验失败一律拒绝，本次启用失败且不执行任何插件代码。

### 4.2 工具进程

- **服务插件的进程级隔离由工具进程（Electron Utility Process）承担**，作为正式执行形态登记；
- 工具进程由壳提供、内核调度，承载需隔离的服务逻辑与重计算；
- 工具进程崩溃按崩溃隔离与恢复策略处理，不影响主进程与其它插件。

## 五、热插拔与蓝绿更新

- 热插拔：启用即创建 Fork，停用即 `dispose()`；更新为蓝绿替换，平台不重启，插件保持 `active`。
- 蓝绿流程：新 Fork 加载 → 暂存代际原子切换（切换点）→ 旧 Fork draining（拒绝新调用、等待在途结束）→ 撤销旧 Fork；窗口内最多两个 Fork 并存。
- **`app` 角色差异**：更新只影响新启动的实例；已打开窗口保持旧版本直到全部关闭；窗口全关前旧 Fork **标记冻结、拒绝新调用、不强制撤销**，避免丢失未保存状态。
- **draining 上限仅适用于非 `app` 角色**：超时后强制 `dispose()` 旧 Fork 并记录诊断。
- 新版本必须满足所有依赖者的版本范围，否则更新请求被拒绝。

## 六、依赖与组合

- `dependencies` 声明插件间依赖与版本范围；解析包含环检测、拓扑排序、版本范围、缺失与显式版本互斥冲突处理。
- 缺失或版本暂不满足 → `pending` 等待依赖就绪，依赖恢复后自动继续激活。
- **版本范围互斥是显式冲突**：候选版本集合与声明范围无交集时拒绝启用，返回 `KERNEL_DEPENDENCY_VERSION`，`details` 附双方范围与候选版本列表，插件进入 `failed`；不再静默 `pending`。
- 多角色需求按下述组合：拆成多个单角色插件，用 `dependencies` 组合；禁止一个包注册多种角色或在运行期切换角色行为。

## 七、崩溃隔离与恢复

- 故障分类：加载失败、apply 失败、运行期异常、任务 panic、健康检查失败、超时；全部被隔离，不扩散。
- 崩溃循环保护：同一插件 10 分钟滚动窗口内最多自动重启 3 次，指数退避 1s / 2s / 4s（单次间隔上限 30s）；超限进入 `Failed`，等待用户显式启用后重置窗口计数。
- 服务插件按 `healthCheck` 周期调用 `health()`；连续不健康触发熔断与停用。
- 数据安全：崩溃不丢已提交数据（写入原子性由文档服务保证）；未保存的编辑器状态由编辑链路按错误提示重试或保留脏状态。

## 八、通信规则

三条合法路径：

1. **服务注入**：`ctx.provide` / `ctx.inject`（经内核路由，K-1）；
2. **能力调用**：Bridge `request`（受权限判定与审计）；
3. **事件订阅**：`subscribe` / `ctx.on`。

禁令：

- 禁止插件之间直接 `import` 或运行时加载对方代码；
- 禁止插件直接访问 Node.js / Electron / 系统 API；
- 禁止插件注册未登记的能力 ID 或自造权限 ID；
- 禁止绕过 Fork 追踪登记副作用。

## 九、施工自检

- [ ] 插件是否只有一个角色，入口是否按角色实现对应接口？
- [ ] `manifest.yaml` 是否为唯一权威，`engines.chips` 与签名是否通过门禁？
- [ ] 双入口职责是否分离，`render.js` 是否外部化平台共享依赖？
- [ ] 安装是否只登记申请，首次启用是否逐项授权、拒绝不阻断启用？
- [ ] 主进程插件是否只经受管模块加载器加载，未触碰 `node:*` / `electron` / 裸路径？
- [ ] `app` 更新是否窗口全关前只冻结不强制撤销？
- [ ] 依赖冲突是否显式返回 `KERNEL_DEPENDENCY_VERSION` 并附范围与候选版本？
- [ ] 崩溃重启是否遵守 10 分钟 / 3 次与指数退避？
