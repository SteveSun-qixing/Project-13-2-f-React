# 禁止事项与反模式

> 版本：v1.0.0
> 日期：2026-09-19
> 状态：正式版
> 适用范围：《施工规范套件》13 分册：薯片生态的红线速查与反模式说明；每条给出"为什么 + 正确做法 + 权威依据"，命中即缺陷，必须当场修正

---

## 一、总则

1. 本清单是写作与编码的最低红线；与[08-治理与不变式](./08-治理与不变式.md)的不变式清单配合使用。
2. 命中任一条即判定为缺陷：模块内可直接修正的当场修正；涉及跨模块契约的按 [10-审查方法与检查清单](./10-审查方法与检查清单.md) §七登记工单。
3. 禁止以"临时/先这样/后续优化"为理由放行任何一条。

## 二、红线速查表

| 编号 | 禁止事项 | 一句话判据 |
|---|---|---|
| 01 | 绕桥 | 插件代码出现 `node:*`、`electron`、系统 API 或真实文件路径 |
| 02 | 跨插件直调 | 出现跨插件 `import` 或直接实例化/调用其他插件内部对象 |
| 03 | 直写文件 | 解析、渲染、编辑器、应用插件自行读写文档字节 |
| 04 | 第二解析器 | 除《06-文档解析器设计》外存在第二处解析 `.card`/`.box` 的实现 |
| 05 | 第二渲染管线 | 除《05-渲染引擎设计》外存在第二套渲染帧/挂载/更新实现 |
| 06 | 硬编码样式 | 出现非 Design Tokens 的颜色、间距、字号、圆角字面量 |
| 07 | 第二组件库 | `import` antd、`@mui/*`、`@chakra-ui/*` 或 fork antd 直引 |
| 08 | TODO | 代码或文档出现 TODO、FIXME、"待补" |
| 09 | 占位实现 | 存在 stub、mock 替代正式实现（测试用 mock 除外） |
| 10 | 兼容层与双轨 | 出现别名映射、旧字段回退、新旧两套并行路径 |
| 11 | 自造能力/权限/错误码 | 使用未登记的能力 ID、权限 ID、错误码或事件名 |
| 12 | 单一事实源破坏 | 同一概念在第二处被定义或数值被转述 |
| 13 | 未归档删除 | 直接删除文件或内容，未移入就近 `归档/` |
| 14 | 凭印象结论 | 结论无文件路径、无行号、无核对过程 |
| 15 | 无证据结论 | 引用不存在或无法复现的"证据" |
| 16 | 自造性能指标 | 使用《架构原则》§4.2 之外的性能/覆盖率数值 |
| 17 | 引入未评估依赖 | 新增第三方依赖未做六项选型评估即引入 |

## 三、逐条说明

### 3.1 隔离与通信

#### 01 绕桥

- **为什么**：Bridge 是唯一的安全、权限、审计与跨端抽象边界；绕桥等于绕过权限判定与 schema 校验，跨端必然失效（R2、R17）。
- **正确做法**：系统能力一律经 `chips.request(id, input)`；句柄经 `chips.resource(uri)`；事件经 `subscribe`；主进程插件经 `ctx` 服务与能力，且只经受管模块加载器加载。
- **依据**：[02-Bridge三层设计](../../../薯片生态文档库/01-架构设计/01-子系统设计/02-Bridge三层设计.md)、[03-插件架构设计](../../../薯片生态文档库/01-架构设计/01-子系统设计/03-插件架构设计.md) §5。

#### 02 跨插件直调

- **为什么**：直接依赖使插件不可替换、不可热插拔，破坏 Cordis 依赖图与代际重建（架构原则 §2.1）。
- **正确做法**：通信只有三条合法路径——服务注入（`ctx.inject`）、能力调用、事件订阅；跨插件只在服务契约与能力契约上耦合。
- **依据**：[03-插件架构设计](../../../薯片生态文档库/01-架构设计/01-子系统设计/03-插件架构设计.md) §8、[架构原则](../../../薯片生态文档库/00-愿景与原则/01-架构原则.md) §2.1。

#### 03 直写文件

- **为什么**：文档服务是唯一写口；旁路写入绕过原子提交、ZIP Store 重建与外部修改检测，会造成数据损坏与"模型旧 + 资源新"（R8、裁决 B-7）。
- **正确做法**：文档内容经 `document:write` / `document:save` 受控提交；插件资源写入只经 `resource:write` 的插件作用域与临时作用域；归档重建纳入 WriteCoordinator 同一路径锁。
- **依据**：[11-文档服务设计](../../../薯片生态文档库/01-架构设计/01-子系统设计/11-文档服务设计.md) §2.1、[04-资源管理设计](../../../薯片生态文档库/01-架构设计/01-子系统设计/04-资源管理设计.md) §4.8。

### 3.2 内容链路

#### 04 第二解析器

- **为什么**：两套解析必然产生字段与版本判定漂移，内容"十年不死"失效；解析器只读是状态所有权的基础（R8）。
- **正确做法**：`.card`/`.box` 解析只走《06-文档解析器设计》；消费方使用 `DocumentView` 与解析句柄；插件专有字段按不透明值处理。
- **依据**：[06-文档解析器设计](../../../薯片生态文档库/01-架构设计/01-子系统设计/06-文档解析器设计.md)、[05-渲染引擎设计](../../../薯片生态文档库/01-架构设计/01-子系统设计/05-渲染引擎设计.md) §2.5。

#### 05 第二渲染管线

- **为什么**：编辑态就近渲染是复用同一插件接口与同一份解析结果的例外，不是第二条管线；第二管线会使查看态与编辑态行为分叉（R8、裁决 B-1/B-2）。
- **正确做法**：渲染帧统一由《05-渲染引擎设计》装载与更新；编辑态经 `IEditSession` 与 `IPluginRuntime` 门面就近渲染；应用插件不得自行创建 iframe 渲染栈。
- **依据**：[12-编辑引擎设计](../../../薯片生态文档库/01-架构设计/01-子系统设计/12-编辑引擎设计.md) §10、[05-渲染引擎设计](../../../薯片生态文档库/01-架构设计/01-子系统设计/05-渲染引擎设计.md) §8。

### 3.3 前端

#### 06 硬编码样式

- **为什么**：视觉一致性依赖统一的 Design Tokens 与 antd 主题定制；硬编码样式会随主题、密度、对比度变化而失配（R5）。
- **正确做法**：颜色、间距、字号、圆角、阴影一律使用 `@chips/ui` 暴露的 Design Tokens；需要定制时经 antd 主题 token。
- **依据**：[03-React组件开发规范](../../../薯片生态文档库/02-开发规范/03-React组件开发规范.md)、[架构原则](../../../薯片生态文档库/00-愿景与原则/01-架构原则.md) §2.5。

#### 07 第二组件库

- **为什么**：第二套组件库会引入第二套视觉语言、交互行为与包体负担，破坏统一体验与维护成本（R4）。
- **正确做法**：业务代码只从 `@chips/ui` 导入；fork antd 仅 `packages/ui` 内部使用；ESLint `no-restricted-imports` 拦截 `antd`、`antd/*`、`@chips/antd`（ui 包例外）、`@mui/*`、`@chakra-ui/*`。
- **依据**：[架构原则](../../../薯片生态文档库/00-愿景与原则/01-架构原则.md) R4、[ADR-008](../../../薯片生态文档库/01-架构设计/ADR/ADR-008-React加fork-antd前端技术栈.md)。

### 3.4 工程与文档

#### 08 TODO

- **为什么**：TODO 是未完成交付的标志，会累积成技术债并掩盖缺口（架构原则 §2.6、R16）。
- **正确做法**：当前任务范围内的功能必须完整实现；无法在本轮完成的能力必须写明阶段与依据（如工具进程、移动端），不得以 TODO 代替。
- **依据**：[架构原则](../../../薯片生态文档库/00-愿景与原则/01-架构原则.md) §2.6、[本轮架构收口裁决](../本轮架构收口裁决.md) §七。

#### 09 占位实现

- **为什么**：占位实现容易被当成正式实现长期存在，导致契约被绕过、测试失真（架构原则 §2.6）。
- **正确做法**：提供完整实现；测试替身只放在测试代码中并经正式 mock 接口（`@chips/sdk/testing`）注入。
- **依据**：[05-测试规范](../../../薯片生态文档库/02-开发规范/05-测试规范.md)、[02-SDK-API规范](../../../薯片生态文档库/05-接口与契约/02-SDK-API规范.md)。

#### 10 兼容层与双轨

- **为什么**：第一版前不存在兼容义务；双轨会让新旧两种事实并存，违反单一事实源并永久污染架构（ADR-010）。
- **正确做法**：直接使用最优架构；破坏性变更走主版本 + 迁移工具；禁止别名映射、旧字段回退、新旧并行路径。
- **依据**：[ADR-010](../../../薯片生态文档库/01-架构设计/ADR/ADR-010-大爆炸重构策略.md)、[04-版本与迁移规范](../../../薯片生态文档库/04-文件格式规范/04-版本与迁移规范.md)。

#### 13 未归档删除

- **为什么**：删除会丢失历史依据与决策上下文；归档保留可追溯性并避免引用悬空。
- **正确做法**：需要移除的内容移动到就近 `归档/` 目录，标注归档原因与取代者，并更新引用方路径。
- **依据**：[07-文档编写规范](../../../薯片生态文档库/02-开发规范/07-文档编写规范.md) §12.1、[本轮架构收口裁决](../本轮架构收口裁决.md) §七。

### 3.5 契约与事实源

#### 11 自造能力/权限/错误码

- **为什么**：未登记的 ID 无法进入权限映射、schema 校验与故障排查体系，等于私开旁路（R3、R19、R20）。
- **正确做法**：能力/权限先登记进《能力契约规范》R19 表；事件名遵守文法并登记《事件契约规范》；错误码按域分层并登记，跨层统一 `ChipsError`。
- **依据**：[04-能力契约规范](../../../薯片生态文档库/05-接口与契约/04-能力契约规范.md)、[05-事件契约规范](../../../薯片生态文档库/05-接口与契约/05-事件契约规范.md)、[架构原则](../../../薯片生态文档库/00-愿景与原则/01-架构原则.md) R3/R19/R20。

#### 12 单一事实源破坏

- **为什么**：两处定义必然漂移，修改需要多点同步，最终无人知道哪份为准（最终任务 核心原则 4）。
- **正确做法**：概念只在一处定义，其他文档引用；数值（性能基线、覆盖率、超时、配额）只引用权威文档；发现重复定义立即收敛。
- **依据**：[08-治理与不变式](./08-治理与不变式.md) §1.2、[03-变更与决策管理](../../../薯片生态文档库/07-工程管理/03-变更与决策管理.md)。

### 3.6 结论纪律

#### 14 凭印象结论

- **为什么**：凭印象得出的结论不可复现、不可审计，会把审查变成猜测（最终任务 核心原则 14/15）。
- **正确做法**：结论必须先核对文件、代码与运行链路；每条结论附路径与行号；不确定时继续核对而不是下判断。
- **依据**：[10-审查方法与检查清单](./10-审查方法与检查清单.md) §四、[最终任务](../最终任务：薯片生态完整文档库与最佳架构设计.md) §4。

#### 15 无证据结论

- **为什么**：无证据的结论无法验收，也无法在争议时裁决。
- **正确做法**：证据三要素齐全（路径 + 行号 + 片段）；否定性结论附检索命令与检索范围；引用归档内容必须标注"仅存档、不作为依据"。
- **依据**：[10-审查方法与检查清单](./10-审查方法与检查清单.md) §四、[11-旧资产对照方法](./11-旧资产对照方法.md) §4.3。

### 3.7 性能与依赖

#### 16 自造性能指标

- **为什么**：自创指标会导致门禁判定分裂、优化方向失焦（R18）。
- **正确做法**：只引用《架构原则》§4.2 与《05-CICD与质量门禁》的基线数值；不达标必须改架构或实现，禁止挂账。
- **依据**：[架构原则](../../../薯片生态文档库/00-愿景与原则/01-架构原则.md) §4.2、[05-CICD与质量门禁](../../../薯片生态文档库/06-开发与运维/05-CICD与质量门禁.md)。

#### 17 引入未评估依赖

- **为什么**：未评估依赖可能带来许可证、安全、维护与跨端风险，且可能悄悄改变基础架构（架构原则 §3.1）。
- **正确做法**：引入前完成六项评估（用途、许可证、维护状态、包体影响、安全风险、跨端兼容）；涉及基础架构、长期运行时依赖或公共协议时先记录方案等待用户确认。
- **依据**：[架构原则](../../../薯片生态文档库/00-愿景与原则/01-架构原则.md) §3.1、AGENTS 架构红线。
