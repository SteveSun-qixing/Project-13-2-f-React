## 一、第一性推导：架构不是选出来的，是推出来的

薯片生态的架构形态不是偏好选择，而是被四条不可动摇的约束推导出来的：

| 约束 | 推导 | 架构结果 |
|---|---|---|
| **五端运行**（macOS / Windows / Linux / Android / iOS） | 业务不能绑定任何平台 | **一核多壳**：Rust 核心 + 薄壳（Electron / Tauri / Web / Headless） |
| **内容十年不死** | 数据层不能是数据库 | **文件即数据层**：`.card` / `.box` 是唯一事实源；解析器只读、写入受控 |
| **无限插件且可替换** | 功能不能写死在平台里 | **一切皆插件 + 能力导向**：平台只提供机制与能力 |
| **体验统一且可组合** | 界面不能各自为政 | **单一共享层 + 五链一条线 + 单写者** |

四条约束之间的张力——安全 vs 可扩展、统一 vs 自由、长期稳定 vs 快速迭代——由**能力边界 + 契约治理**调和：

> **平台管边界，生态管内容。**

推论：

1. 平台必须小：内核薄到无感，功能全部下沉为插件与服务；
2. 契约必须硬：`window.chips`、角色接口、文件格式与事件是一等公民；
3. 链路必须单：卡片与箱子共用同一条链路、同一个写口；
4. 数据必须久：文件格式开放、人类可读、可被第三方工具读写。

## 二、全景分层架构

```
┌────────────────────────────────────────────────────────────────────┐
│ 内容层   .card / .box（事实源，脱离程序独立存在，ZIP Store）          │
├────────────────────────────────────────────────────────────────────┤
│ 插件层   应用 app · 基础卡片 basecard · 箱子布局 boxlayout · 服务 service │
│          （独立仓库、独立版本、独立发布；官方与第三方同构）              │
├────────────────────────────────────────────────────────────────────┤
│ 契约层   window.chips：request / subscribe / resource（唯一门）      │
│          IChipsBridge · ICapability · ISubscription · IResourceHandle│
├────────────────────────────────────────────────────────────────────┤
│ 平台层   Cordis 内核 · Bridge · 文档解析器 · 资源/文件系统 · 渲染框架  │
│          文档服务 · 权限系统 · 事件系统 · 配置系统 · 同步引擎          │
├────────────────────────────────────────────────────────────────────┤
│ 壳层     Electron（桌面，当前）· Tauri 2（移动，Phase 5）· Web · Headless│
├────────────────────────────────────────────────────────────────────┤
│ 系统层   操作系统（文件、窗口、通知、剪贴板、快捷键、网络…）             │
└────────────────────────────────────────────────────────────────────┘
        （纵向）开发平面：@chips/sdk · 脚手架 CLI · @chips/ui · 文档库
```

分层规则：

- 上层只能向下调用；下层不得调用上层，也不得反向调用插件（平台 → 插件只能经事件）；
- 每层只通过相邻层的契约通信，禁止跨层直连（[《架构原则》](../../../薯片生态文档库/00-愿景与原则/01-架构原则.md) §2.3）；
- 内容层不依赖任何程序：文件即事实源，程序只是读写工具。

## 三、南北向与东西向

### 3.1 南北向

- **南向是能力**：平台提供给插件的能力，经 `window.chips.request(capabilityId, input)` 请求；能力有 ID、schema 与权限声明，经 Bridge 注册、校验、路由与审计。
- **北向是事件**：平台推送给插件的通知，经 `subscribe(eventId, handler)` 订阅；事件只承载载荷，单向、不回头。
- 南向与北向都是单向的：能力调用不反向调用插件，事件发布不等待插件执行结果。

### 3.2 东西向

插件之间只通过三种方式耦合，绝不直接 `import`：

1. **服务注入**：经 Cordis `ctx.provide` / `ctx.inject`（内核路由，K-1 红线）；
2. **能力调用**：经 Bridge `request`（受权限判定与审计）；
3. **事件订阅**：经 `subscribe` / `ctx.on`（同步广播 + JS 经 Channel 入队）。

## 四、三个平面与一条链路

### 4.1 三个平面（互相正交、各有契约）

| 平面 | 方向 | 载体 | 契约 |
|---|---|---|---|
| 能力面 | 插件 → 平台（南向） | `request(capabilityId, input)` | 能力契约、Bridge API 规范 |
| 事件面 | 平台 → 插件（北向） | `subscribe(eventId, handler)` | 事件契约规范 |
| 资源面 | 双向 | `resource(uri)` → `IResourceHandle` | 资源协议规范 |

### 4.2 一条链路

从文件字节到屏幕像素再到修改落盘，全程同一条链、同一个模型、同一个写口：

```
文件字节 → 解析（只读）→ DocumentView → 渲染帧 → 用户编辑
   → 校验 → document:write → update(view, revision) → markCommitted
   → document:save（两阶段提交、原子替换）
```

- 唯一分支点是 `DocumentKind = 'card' | 'box'`，分支后立即归一为 `DocumentView`；
- 禁止并行管线、禁止第二套解析器、禁止第二个写口；
- 编辑态允许就近渲染，但必须复用同一套插件接口与同一份解析结果（R8）。

## 五、各层对施工的含义

| 层 | 施工者只能做什么 | 不能做什么 |
|---|---|---|
| 内容层 | 按文件格式规范读写 `.card` / `.box` | 发明目录、字段或引用形式 |
| 插件层 | 实现角色接口，经 `ctx` 与 `window.chips` 使用平台 | 直接 `import` 其他插件、直接访问 Node / Electron / 系统 API |
| 契约层 | 按 Bridge API、能力契约、事件契约、资源协议调用 | 绕过 Bridge 自建通道 |
| 平台层 | 按子系统设计实现机制与服务，注册能力 | 实现业务逻辑、把功能写死 |
| 壳层 | 实现窗口、菜单、对话框等平台差异，喂给 Bridge | 让插件感知壳差异 |
| 系统层 | 被壳层封装后经能力暴露 | 被插件直接触碰 |
