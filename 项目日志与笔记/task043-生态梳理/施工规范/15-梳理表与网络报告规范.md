# 梳理表与网络报告规范

> 版本：v1.0.0
> 日期：2026-09-19
> 状态：正式版
> 适用范围：《施工规范套件》15 分册：多维梳理表的 TSV schema、分片并发协议、边表与网络梳理报告要求、验收清单模板；所有子智能体的梳理输出必须遵循本规范

## 一、目标与产物

- 目标：把所有内容节点、文件、功能、概念、接口、链路、插件、模块连成一张可检索、可交叉验证的网络，最终达到"没有遗漏节点、没有孤立节点、没有未定义边界"（[最终任务](../最终任务：薯片生态完整文档库与最佳架构设计.md) §1、§2.3）。
- 产物：
  1. 分片梳理表：`梳理表/分片-<ID>.tsv`（每个子智能体一份，事实源）；
  2. 总表：`梳理表/总表.tsv`（主代理合并的派生只读表）；
  3. 边表：`梳理表/边表.tsv`（节点间关系）；
  4. 网络梳理报告：`项目日志与笔记/task043-生态梳理/网络梳理报告.md`（含节点/边/孤立节点/未闭合边界/交叉验证结论）；
  5. 验收清单：`项目日志与笔记/task043-生态梳理/验收清单.md`（模板见 §六）。

## 二、多维梳理表 schema

TSV 固定 9 列，表头逐字固定：

| 列 | 列名 | 取值 / 格式 | 说明 |
|---|---|---|---|
| 1 | 节点ID | `<来源码>-<5 位顺序号>` | 来源码：`OD`（旧文档库）、`OR`（旧仓库）、`ND`（新库）；号段由主代理预分配，禁止跨号段占用 |
| 2 | 来源类型 | `旧文档库` / `旧仓库` / `新库` | 三值之一，不得自造 |
| 3 | 旧路径或新路径 | 工作区根相对路径 | 旧资产写旧路径，新库写新路径；仓库文件写到文件级 |
| 4 | 主题 | 短语 | 该节点承载的主题/概念/功能名 |
| 5 | 维度标签 | 多值，半角分号分隔 | 取值见 §2.1，至少一个 |
| 6 | 新库对应 | 文档库相对路径（可多个，半角分号分隔） | 旧资产填写新库对应位置；新库节点填自身路径 |
| 7 | 覆盖状态 | `已覆盖` / `部分` / `缺失` / `冲突` | 四值之一；"正式废弃"计入 `已覆盖`，依据写在第 9 列 |
| 8 | 建议动作 | `直接修订` / `补设计` / `登记工单` / `归档处理` / `无需动作` | 五值之一 |
| 9 | 证据 | `路径:行号` 或 `路径:行号-行号`；多条用 `;` | 禁止与第 3 列重复互相引用，必须能独立定位 |

### 2.1 维度标签取值

`文件`、`功能`、`架构`、`抽象`、`插件`、`模块`、`链路`、`接口契约`、`入口`、`平台`、`生命周期`、`安全`、`性能`、`扩展`

- 可多选，用半角分号分隔（如 `功能;链路;接口契约`）；一个节点在多个维度可检索由多标签保证。
- 新增维度必须先在主代理处登记，禁止自造。
- 既有分片（`分片-INV*.tsv`）保留其原标签写法，由主代理在合并时归一到上表取值。

### 2.2 示例行（示意）

```tsv
OD-00001	旧文档库	旧版-生态共用技术文档/命令行工具/01-Chips-Host命令行使用手册.md	CLI 命令参考	文件;功能;入口	薯片生态文档库/06-开发与运维	缺失	补设计	旧版-生态共用技术文档/命令行工具/01-Chips-Host命令行使用手册.md:1-5
OR-00001	旧仓库	Chips-Host/src/main/index.ts	宿主主进程入口	架构;入口;生命周期	薯片生态文档库/01-架构设计/01-子系统设计/01-薯片内核设计.md	部分	直接修订	Chips-Host/src/main/index.ts:1-5
ND-00001	新库	薯片生态文档库/01-架构设计/01-子系统设计/12-编辑引擎设计.md	编辑链路	架构;链路;接口契约	薯片生态文档库/01-架构设计/01-子系统设计/12-编辑引擎设计.md	已覆盖	无需动作	薯片生态文档库/01-架构设计/01-子系统设计/12-编辑引擎设计.md:14-60
```

### 2.3 覆盖状态判定

| 状态 | 判定 |
|---|---|
| 已覆盖 | 新库有对应定义或正式处置；废弃须有 ADR/裁决依据并写入证据列 |
| 部分 | 新库有相关内容但缺少契约、字段、时序或失败路径 |
| 缺失 | 新库无任何对应；必须记录检索命令与检索范围 |
| 冲突 | 新库与旧资产或裁决互相矛盾；同轮必须给出裁决动作 |

## 三、分片协议（并发安全）

1. 目录：`项目日志与笔记/task043-生态梳理/梳理表/`。
2. 命名：`分片-<ID>.tsv`，`<ID>` 为子智能体标识（如 `A-03`、`B-11`）或既有分片标识（如 `INV1`）。
3. **一个分片只由一个子智能体写入；禁止并发写同一文件**（包含不得由他人追加、改写、格式化）。主代理只读分片。
4. 文件第一行为表头，与 §二 逐字一致；每行一条节点记录。
5. 编码与格式：
   - UTF-8（无 BOM）；LF 换行；
   - 制表符分隔；字段内禁止出现制表符与换行；
   - 多值用半角分号；字段内列举说明用顿号；
   - 证据列的多条证据用半角分号分隔。
6. 号段预分配：开工前由主代理分配 `OD/OR/ND` 顺序号号段，避免 ID 冲突；号段内顺序自增，不复用。
7. 去重规则：允许同一路径多行（不同主题/维度），但 `(来源类型, 路径, 主题)` 组合不得重复；发现重复由主代理合并。
8. 冻结与修订：分片一经交付即冻结；确需修订时新建 `分片-<ID>-r2.tsv` 追加，不覆盖原文件（归档不删除）。
9. 合并：主代理把所有分片按表头拼接为 `总表.tsv`；总表是派生只读产物，任何修正只能回到分片进行。
10. 既有分片兼容：`分片-INV*.tsv` 等既有分片保留原表头与原 ID；合并时由主代理做字段映射——来源归一为 `旧文档库`/`旧仓库`/`新库`，路径补全为工作区根相对路径，标签归一为标准取值，原证据保留。

## 四、边表与网络

边表固定 4 列，`梳理表/边表.tsv`：

| 列 | 列名 | 取值 / 格式 |
|---|---|---|
| 1 | 起点节点ID | 节点ID（存在于某个分片） |
| 2 | 关系类型 | `定义` / `引用` / `实现` / `归口` / `替代` / `依赖` / `覆盖` |
| 3 | 终点节点ID | 节点ID（存在于某个分片） |
| 4 | 证据 | `路径:行号`，多条用 `;` |

- 边只连接已登记节点；引用不存在的节点视为欠登记，必须补节点或撤边。
- 网络质量判据：
  - **无孤立节点**：每个节点至少有一条边；
  - **无未闭合边界**：`引用` 双向闭合、`归口` 有落点、功能节点有 `实现`/`覆盖` 边；
  - 同一条边不得重复登记（起点+关系+终点 唯一）。
- 边表同样遵守 §三 的分片与格式纪律；按分片写 `边表-<ID>.tsv`，由主代理合并。

## 五、网络梳理报告要求

`项目日志与笔记/task043-生态梳理/网络梳理报告.md` 必须包含以下章节，每章结论必须带证据（`路径:行号`）；"未发现"也必须写明检索范围与命令。

1. **节点统计**：按来源类型、维度标签、覆盖状态分别计数；总节点数 = 各分片节点数之和。
2. **边统计**：按关系类型计数；`引用` 边的双向闭合率。
3. **孤立节点**：列出全部无边节点、所在分片、证据与处置（补边/补设计/归档）。
4. **未闭合边界**：列出定义悬空、归口缺失、功能无实现来源、契约无接口的条目与处置。
5. **交叉验证结论**：
   - 文件视角 → 功能视角：每个功能是否有新架构设计；
   - 功能视角 → 文件视角：每个能力是否有实现来源；
   - 两条验证的不一致清单与处理结果。
6. **缺口与处置汇总**：`部分/缺失/冲突` 条目 → 处置（直接修订/补设计/工单编号）。
7. **验收对照**：引用 §六 验收清单的最终结论。

## 六、验收清单模板

`项目日志与笔记/task043-生态梳理/验收清单.md` 按以下六项逐条判定；结论只允许 `通过` / `不通过`，不通过必须给出证据与处置。

| 验收项 | 判定标准 | 证据 | 结论 |
|---|---|---|---|
| 能力域有文档 | 每个能力域在文档库中有唯一权威文档 | `<路径:行号>` | `<通过/不通过>` |
| 契约有接口 | 每个契约在 05-接口与契约或对应子系统文档中有完整接口 | `<路径:行号>` | `<通过/不通过>` |
| 接口有证据 | 每条接口结论可定位到真实文件与行号 | `<检索命令 + 路径:行号>` | `<通过/不通过>` |
| 缺口有处理 | 所有 `部分/缺失/冲突` 均有处置结果或工单编号 | `<差距表行 + 处置>` | `<通过/不通过>` |
| 可独立并行开发 | 关键契约具备签名、时序、错误码、示例，团队无需口头对齐 | `<契约文档:行号>` | `<通过/不通过>` |
| 无孤立节点 | 边表无孤立节点、无未闭合边界 | `<网络报告章节>` | `<通过/不通过>` |

### 6.1 完成判据

- 分片条目数 = 已判定条目数（清单穷尽，见 [11-旧资产对照方法](./11-旧资产对照方法.md) §4.3）；
- 无悬空的 S1/S2 发现；
- 总表、边表、网络报告、验收清单四件产物齐全且互相一致。

## 七、多维梳理库（SQLite，已建立）

多维梳理表以 SQLite 数据库为唯一实现，取代一次性表格，供任意维度查询与交叉验证。

- 数据库：`项目日志与笔记/task043-生态梳理/梳理表/薯片生态多维梳理.db`
- 工具：`项目日志与笔记/task043-生态梳理/工具/梳理库.py`
- 表：`nodes`（节点）、`dimensions`、`node_dimensions`（节点×维度）、`edges`（对应/已解决等关系）、`gaps`（缺口）、`docs`（新文档登记）
- 视图：`v_gaps`、`v_coverage_by_source`、`v_coverage_by_dimension`
- 受控维度：文件、功能、架构、抽象、插件、模块、链路、接口契约、入口、平台、生命周期、安全、性能、扩展、交互、视觉、运维、工程治理、规范质量、工具链、产品、数据、演进、服务端、前端、测试、合规、参考资产、网络、日志、无障碍、内容、版本；自由标签自动归并。

### 7.1 工具命令

```bash
python3 项目日志与笔记/task043-生态梳理/工具/梳理库.py import        # 导入全部分片（幂等）
python3 项目日志与笔记/task043-生态梳理/工具/梳理库.py stats         # 覆盖统计
python3 项目日志与笔记/task043-生态梳理/工具/梳理库.py gaps          # 未闭合缺口
python3 项目日志与笔记/task043-生态梳理/工具/梳理库.py query --dimension 平台 --status 缺失
python3 项目日志与笔记/task043-生态梳理/工具/梳理库.py orphans       # 孤立节点
python3 项目日志与笔记/task043-生态梳理/工具/梳理库.py export        # 导出 多维梳理表.csv
```

### 7.2 子智能体协议（必须遵守）

1. 开工前先 `query`/`gaps` 查看自己主题下的缺口与已有节点，避免重复设计。
2. 产出新文档后写三份分片（文件名中的 `<ID>` 用子智能体标识，例如 `D1`）：
   - `梳理表/分片-<ID>.tsv`：表头 `节点ID	来源	旧路径	主题	维度标签	新库对应	覆盖状态	建议动作	证据`；新增文档登记为一行 `已覆盖`。
   - `梳理表/登记-<ID>.tsv`：表头 `编号	文档名	路径	权威范围	依赖	状态	负责人`。
   - `梳理表/缺口处理-<ID>.tsv`：表头 `缺口ID	状态	新文档路径	说明`；把本次关闭的缺口标 `done`。
3. 收尾运行 `import`，确认 `stats` 中 `docs` 与自己登记的文档数一致。
4. 不得并发修改 `14-新增文档登记表.md`、`README.md`（由汇总组统一合并）。
5. 禁止把未验证的结论写入分片；证据列必须可定位。
