## 一、信任模型

以下四类对象一律视为**不可信**：

1. **渲染进程不可信**：会话有效性 → 权限 → schema 三步校验全部在主进程完成；preload 预检不是安全边界。
2. **插件输入不可信**：能力输入一律经 JSON Schema 校验；能力不能扩大自身声明的权限需求，插件不能通过调用参数扩大权限。
3. **网络内容不可信**：外部资源经资源代理注入，内容类型必须匹配消费场景；帧内 `connect-src 'none'`，不能直接发起网络请求。
4. **用户文件中的数据不可信**：解析即校验；文档 schema 与结构校验是内容进入平台的第一道闸门。

配套底线（R17）：Electron `nodeIntegration: false`、`contextIsolation: true`、`sandbox: true`；生产禁用关闭 `webSecurity`；插件只能经 Bridge 访问系统；资源统一经 `chips-resource://` 访问。

## 二、安全机制总览

| 层 | 机制 |
|---|---|
| 身份 | 会话由 Bridge 按 IPC 来源解析，插件不可自报；请求中的身份字段只作诊断 |
| 授权 | 权限声明 → 用户授予 → 运行时判定 → 审计；最小权限；路径 / 域名级限定；未决即默认拒绝 |
| 校验 | JSON Schema（能力输入，2020-12 方言）+ 文档 schema（内容）双闸门 |
| 资源 | `chips-resource://` 统一寻址；PathGuard 防目录穿越；作用域与句柄双重约束 |
| 包与供应链 | `.cpk` 签名与安装校验、体积限制；第三方依赖引入必须过选型评估 |
| 审计 | 能力调用与敏感资源访问可追溯；授予、撤销与判定全量留痕 |

## 三、权限词表与能力映射（唯一权威）

- **能力 → 权限映射唯一权威**：[能力契约规范](../../../薯片生态文档库/05-接口与契约/04-能力契约规范.md) §6.2（R19，canonical）与 [权限系统设计](../../../薯片生态文档库/01-架构设计/01-子系统设计/08-权限系统设计.md) §4。
- 能力表达"做什么"，权限表达"被允许访问什么范畴"；**能力 ID 与权限 ID 不得相同**（R3）。
- 权限 ID 文法：`<domain>:<scope>[:<qualifier>]`；全部小写；段数 2 或 3；限定值必须使用目录变量（如 `${userDocuments}`），不得写裸绝对路径。
- 内置域由平台统一维护，第三方插件不得新增域、scope 或 qualifier 文法；未注册权限安装校验返回 `PERMISSION_UNKNOWN`。

### 3.1 四条链路

1. **声明**：manifest `permissions` 只表达申请；安装与加载校验语法、注册表与角色适用性。
2. **授予**：首次启用逐项授权（拒绝任一项不阻断启用，该权限保持未授权）；敏感权限在目标首次调用时确认；授权记录由权限系统独占写入。
3. **判定**：Bridge 调用与资源访问前，按"会话权限快照 ∩ 能力所需权限 + 目标限定值匹配"判定；判定点唯一，不存在绕过入口。
4. **审计**：授予、撤销、放行与拒绝全量记录；插件无法关闭、修改或删除审计。

### 3.2 拒绝语义

- 运行时权限拒绝统一 `BRIDGE_PERMISSION_DENIED`；`PLUGIN_PERMISSION_DENIED` 只表示权限拒绝（启用、能力注册阶段的权限校验失败）。
- owner 未 `active` 等生命周期状态错误使用内核状态码（如 `KERNEL_INVALID_TRANSITION`），不得混用权限错误码。
- 拒绝信息只包含本次调用所需与缺失的权限，不暴露其他插件、其他会话的权限信息。

## 四、路径安全（PathGuard）

- 路径校验在服务端唯一入口为 **PathGuard**：任何快速路径都不得跳过解码与分段校验。
- 规则：**先解码一次 + NFC 规范化 + 分段校验**；不得信任 URL 解析器的路径折叠结果。
- 目录穿越防护：`..` 明文与编码形式、双重编码、绝对路径、UNC、ADS、`\0`、Unicode 规范化差异、符号链接逃逸、超长路径全部拒绝。
- 目录态来源 `canonicalize` 后再次验证仍在作用域根内；符号链接指向根外一律拒绝；归档条目必须是普通文件，拒绝符号链接、硬链接与设备。
- `chips-resource://` 协议处理器必须基于 `request.url` 原始字符串重新执行语法解析与 PathGuard；越权返回 403 并写审计。
- PathGuard 必须有独立单元测试覆盖编码绕过与符号链接逃逸；路径限定必须使用目录变量，不得写裸绝对路径。

## 五、审计

- 记录策略：授予、撤销、运行时判定（放行与拒绝）、权限集合变化**全量记录**；审计以异步追加执行，写入失败不阻塞调用但必须记录内部告警。
- 审计记录字段：`id`（ULID）、`timestamp`、`action`（`grant` / `revoke` / `deny` / `allow`）、`source`、`actor`、`pluginId` / `pluginVersion`、`sessionId`、`permission`、`qualifier`、`capabilityId`、`target`、`resourceUri`、`reason`、`traceId`、`requestId`。
- 判定耗时不计入能力执行的性能预算；审计与日志使用同一 `traceId` 口径，便于全链路定位。
- 留存、轮转与脱敏按权限系统设计执行；插件无任何审计豁免通道。

## 六、包签名与信任根

- 签名文件固定为包根 `signature.json`：`keyId` 由发布方信任根注册表解析；`signature` 为对 `contentHash` UTF-8 字节的 Ed25519 签名（Base64）。
- 来源渠道规则：

| 来源 | 签名要求 | 缺失时 | 无效时 |
|---|---|---|---|
| `builtin` | 必须签名 | `CPK_SIGNATURE_REQUIRED`，拒绝安装 | `CPK_SIGNATURE_INVALID`，拒绝安装 |
| `user` | 可选 | 明确展示"未签名发布者"，用户确认后继续 | `CPK_SIGNATURE_INVALID`，拒绝安装 |
| `development` | 跳过 | — | — |

- 未签名不得静默安装；必须产生可见提示与用户确认记录。
- 签名有效不得作为跳过归档、结构、清单与载荷校验的理由；信任根未注册的 `keyId` 视为签名无效。
- 安装校验顺序：归档 → 结构 → 清单 → 签名 → 摘要；失败不落盘。签名链、更新源与发布流程见 [更新与分发规范](../../../薯片生态文档库/06-开发与运维/06-更新与分发规范.md)。

## 七、可靠性

- **插件隔离**：崩溃不扩散；受控重启 10 分钟窗口内最多 3 次、指数退避；超限进入 `Failed` 等待显式启用。
- **写入原子性**：临时物 + `validate` + 原子替换；两阶段提交与提交日志支持崩溃恢复前滚 / 回滚（归档态无备份，只前滚或放弃）。
- **外部修改检测**：版本戳 / 摘要对比，冲突显式暴露而不是静默覆盖；`DOCUMENT_SOURCE_CHANGED` / `DOCUMENT_WRITE_CONFLICT` 确定性拒绝。
- **会话一致性**：外部修改时查看会话冻结并提示重载，禁止"模型旧 + 资源新"混用。
- **零残留**：一切副作用登记到 Fork，停用 / 卸载后零残留；撤销幂等。

## 八、性能基线

### 8.1 数值（唯一来源）

五项基线的**唯一来源**是 [架构原则](../../../薯片生态文档库/00-愿景与原则/01-架构原则.md) §4.2 与附录 R18；其他文档只允许引用，不得改写数值或另立口径：

| 指标 | 基线 | Phase 2 放宽 |
|---|---|---|
| 冷启动 | < 1 秒 | < 2 秒 |
| 渲染帧率 | > 60 fps | > 30 fps |
| 空闲内存 | < 500 MB | — |
| 打开卡片 | < 100 ms | — |
| 打开箱子 | < 200 ms | — |

覆盖率和静态检查口径同样以 R18 为准：总体 > 80%，Rust 核心（`chips-*` crates）与共享层（`@chips/ui`、`@chips/bridge`）> 90%；Clippy 无 warning；`unsafe` 必须有 `# Safety` 注释。

### 8.2 架构级手段

- 帧内不读文件、不持锁 `await`；
- SingleFlight 合并并发、流式与大文件句柄化、缓存分层；
- 就近渲染、懒加载解析、虚拟化与增量渲染；
- 解析限额（512 MiB / 1 万条等）作为可配置的安全防护默认值。

**不达标必须改架构，不允许"后续优化"挂账。**

## 九、错误模型

- 跨边界错误只有一个形状：`ChipsError { code, message, details?, retryable? }`（构造：`new ChipsError({ code, message, details?, retryable? })`；`IChipsError` 仅作结构别名）。
- `code` 规则：`<DOMAIN>_<REASON>`，全大写、下划线分隔；同一个 `code` 只有一个含义；域前缀按来源归一（`KERNEL_*`、`BRIDGE_*`、`DOCUMENT_*`、`RESOURCE_*`、`PERMISSION_*`、`EVENT_*`、Host 业务码）。
- `message` 为简体中文、面向用户；不携带堆栈、内部路径与原始输入；诊断细节放 `details`（JSON Pointer、字段名、目标等）。
- `retryable` 仅作提示：`true` 表示重新执行可能成功；`false` 不得自动重试。
- 跨 Rust → Neon → Bridge → 插件全程归一，不丢语义、不泄露内部细节；错误必须可定位，故障排查按错误码组织（[故障排查手册](../../../薯片生态文档库/06-开发与运维/04-故障排查手册.md)）。

## 十、施工自检

- [ ] 是否把渲染进程、插件输入、网络内容、用户文件数据一律按不可信处理？
- [ ] 权限词表与能力映射是否引用能力契约 §6.2 与权限系统 §4，没有自创权限 ID？
- [ ] 路径是否全部经 PathGuard，限定值是否使用目录变量？
- [ ] 授予、撤销与判定是否全量写审计，没有豁免通道？
- [ ] 签名缺失 / 无效是否按来源渠道确定性处理，未签名是否未静默安装？
- [ ] 性能数值是否只引用架构原则 §4.2 与 R18，没有自创指标？
- [ ] 错误是否归一为 `ChipsError`，`message` 是否不泄露内部细节？
