## 一、薯片生态是什么

**薯片生态 = 薯片平台 + 插件生态 + 内容生态。**

- **薯片平台（Chips Platform）**：运行在操作系统之上的软件平台，是所有插件与内容的唯一运行时承载；提供 Cordis 运行时、能力 Bridge、文档解析、资源管理、渲染框架、权限 / 事件 / 配置系统。平台只提供能力与机制，不实现业务逻辑。
- **插件生态**：由基础卡片（`basecard`）、箱子布局（`boxlayout`）、应用（`app`）、服务（`service`）四类角色的插件组成；一个插件只有一个角色；官方与第三方使用同一套接口、同一套生命周期，官方不享有特权。
- **内容生态**：由 `.card` 卡片与 `.box` 箱子构成；文件格式开放、YAML 人类可读、脱离创建它的程序独立存在。

两个产品目标：

1. **软件生态：把常用软件重做一遍。** 用户只安装薯片平台，编辑器、阅读器、播放器、查看器、资源管理器、社区客户端等常用软件都以插件形式运行在平台内，共享同一套运行时、组件库、文件格式与权限系统。
2. **卡片生态：把信息保存为卡片，让信息脱离程序。** 信息以 `.card` 自包含保存：内容、结构、资源与元数据齐全，双击即开、长期保存、自由流转，第三方工具可以读写。

架构三句话（完整推导见《01-架构总论（第一性推导与分层）》）：

1. **一条竖线**：内容 → 插件 → 契约 → 平台 → 壳 → 系统，层层向下、界限分明；
2. **三个平面**：能力面（南向能力）、事件面（北向通知）、资源面（句柄化访问），互相正交、各有契约；
3. **一条链路**：从文件字节到屏幕像素再到修改落盘，全程同一条链、同一个模型、同一个写口。

权威入口：[《薯片生态白皮书》](../../../薯片生态文档库/00-愿景与原则/00-薯片生态白皮书.md)、[《架构原则》](../../../薯片生态文档库/00-愿景与原则/01-架构原则.md)、[《设计哲学》](../../../薯片生态文档库/00-愿景与原则/02-设计哲学.md)、[文档库索引](../../../薯片生态文档库/README.md)。

## 二、本轮任务（task043）

### 2.1 任务定位

薯片生态文档库（`薯片生态文档库/`，8 分区 66 份正式文档）已经完成三轮编写与架构收口，但尚未对照历史资产做穷尽式的覆盖核对。本轮任务的目标是：

> 对照**旧版三套文档库**与**全部旧仓库**，穷尽式补齐新架构缺失的设计；用文件视角 × 功能视角交叉验证，保证整张生态网络没有遗漏节点、没有孤立节点、没有未定义边界。

旧版三套文档库指：

- `旧版-生态设计原稿/`：产品与架构设计原稿（卡片 / 箱子业务、模块化架构、公共基础层、插件系统等）；
- `旧版-生态共用技术文档/`：协议与契约、协议与接口标准、文件格式规范、架构设计、插件开发、命令行工具等正式旧文档；
- `旧版-生态共用技术文档-2/`：愿景与原则、架构设计、开发规范、工程结构、实施计划、协议与接口、插件开发、开发与运维、工具链、速查手册。

全部旧仓库指仓库根目录下的历史项目，例如 `Chips-Host/`、`Chips-EditingEngine/`、`Chips-BaseCardPlugin/`、`Chips-BoxLayoutPlugin/`、`Chips-SDK/`、`Chips-Ui/`、`Chips-Scaffold/`、`Chips-CardViewer/` 以及各官方应用插件仓库。旧版代码只作为功能与行为证据，不作为架构口径来源。

### 2.2 裁决优先

本轮所有断言、命名、类型、机制与冲突裁决以 [《本轮架构收口裁决》](../本轮架构收口裁决.md)（唯一施工依据）为准；文档库内的表述如与裁决冲突，按裁决修订。术语、数字、错误码、类型名一律以裁决为准。

### 2.3 方法：多维梳理表 + 多标签 + 网络式梳理

用梳理表把全部内容节点、文件、功能、代码、概念、接口、链路、插件、模块连成一张可检索、可交叉比对的网络。维度包括但不限于：

- 文件维度、功能维度、架构维度、抽象维度；
- 插件维度、模块维度、链路维度；
- 接口与契约维度、入口维度、平台维度；
- 生命周期维度、安全与权限维度、性能维度、未来扩展维度。

每个节点打多个标签（分号分隔），支持按任意维度检索与交叉验证。梳理表分片存放于 `../梳理表/`（已有 `分片-INV2.tsv`、`分片-INV6.tsv` 等），字段包含：节点 ID、来源、旧路径、主题、维度标签、新库对应、覆盖状态、建议动作、证据。

## 三、两个视角与交叉验证

### 3.1 文件视角：逐文件梳理

从文件出发，逐个文件、逐个目录、逐个仓库梳理内容，标记：

- 哪些文件的哪些代码共同组成了一个功能；
- 哪些文件的哪些代码共同组成了一个模块、插件、链路、接口、协议、入口；
- 每个文件、每段代码的角色、职责、边界与依赖。

### 3.2 功能视角：逐功能对照新架构

从功能出发，对照新一代架构设计，检查：

- 新架构是否完整覆盖了这个功能；
- 新架构是否为这个功能提供了清晰的抽象、职责、边界、接口、契约与链路；
- 设计是否足够干净、足够可扩展、足够支持独立并行开发；
- 是否存在功能遗漏、抽象错误、职责混乱、接口缺失、链路断裂、边界不清。

### 3.3 交叉验证

- 文件视角梳理出来的功能，必须在功能视角中找到对应的新架构设计；
- 功能视角中的每个能力，必须在文件视角中找到对应的实现来源；
- 两边不一致的地方，就是缺口、冲突、错误、待设计。

## 五、交付纪律

1. **不删文件**：禁止直接删除任何文件；需要移除的内容统一移动到就近 `归档/` 目录，并在索引中标注归档状态。
2. **无临时实现**：不做临时版、简化版、占位实现；不留下 TODO；确需分阶段的能力必须写明阶段与依据（如工具进程、移动端 Phase 5）。
3. **门禁全绿**：改动后使用各项目 `package.json` 中的正式脚本验证；文档库链接检查（`pnpm docs:check` 口径，工具见 `../工具/检查文档链接.py`）必须 0 坏链。
4. **单一事实源**：一个概念只存在于一处权威文档，禁止复制粘贴；跨文档依赖必须通过文档引用。术语、数字、错误码以《裁决》为准。
5. **证据化结论**：所有结论必须有证据（文件路径、行号、代码片段、文档引用）；禁止凭印象、禁止跳文件、禁止无证据结论。
6. **文档即代码**：文档要全面详细，说明要准确到"另一个团队可以完美理解、不产生误会、能按文档复刻"。
7. **发现问题直接解决**：直接补全设计、补全文档、修正架构、补齐抽象、补齐接口与契约；只有需要和其他模块、项目、团队沟通确认的事项，才按仓库 `AGENTS.md` 规则登记工单（只描述问题，不写解决办法，含问题描述、影响范围、证据、关联节点、验收标准）。
8. **不做兼容性设计**：第一版发布前不考虑兼容性重构，不留回退机制，不保留过时口径与兼容写法。

## 六、本施工规范套件的使用方式

本目录（`施工规范/`）是 30-40 个子智能体共享的规范套件：每个子智能体开工前先读本套件，而不是在提示词里重复设计规范、背景、目标与审查要求。

| 文档 | 用途 |
|---|---|
| [00-任务背景与目标](./00-任务背景与目标.md) | 本文：生态定义、任务、成果物与纪律 |
| [01-架构总论（第一性推导与分层）](./01-架构总论（第一性推导与分层）.md) | 架构为什么是唯一解、全景分层、南北向与东西向 |
| [02-运行时与内核](./02-运行时与内核.md) | 内核并发模型、生命周期、服务代际、事件、配额、崩溃重启 |
| [03-Bridge与能力体系](./03-Bridge与能力体系.md) | 唯一门、三条链路、信封、会话、能力注册与权限判定 |
| [04-插件体系](./04-插件体系.md) | 四角色、包与入口、安装授权、加载隔离、蓝绿、依赖、崩溃恢复 |
| [05-内容五链与数据契约](./05-内容五链与数据契约.md) | 解析 / 资源 / 渲染 / 封面 / 编辑写入五链与视图契约 |
| [06-前端与跨端](./06-前端与跨端.md) | `@chips/ui`、Design Tokens、帧沙箱、五端优先级 |
| [07-安全与可靠性性能](./07-安全与可靠性性能.md) | 信任模型、权限、PathGuard、审计、签名、性能与错误模型 |

使用规则：

1. **本套件只提炼要点并指向权威文档**，不替代权威文档；施工以文档库原文为准。
2. 遇到套件与文档库不一致：以《裁决》为最高依据，其次以文档库正式文档为准，并登记差异。
3. 涉及自己任务范围之外的文件不做改动；跨文档引用使用最终路径。
