# 运行时与内核

> 版本：v1.0.0
> 日期：2026-09-19
> 状态：正式版
> 适用范围：薯片内核（Cordis 运行时 Rust 实现）的并发模型、Context 与 Fork、服务模型与代际、生命周期与超时、事件总线、软配额与崩溃重启；术语与数值以《本轮架构收口裁决》和内核设计原文为准

## 一、定位

- 薯片内核是 Cordis 运行时的 Rust 实现，经 Neon 暴露给 Node.js，是**插件运行机制的唯一下沉实现**。
- 内核**不感知插件角色**：`basecard`、`boxlayout`、`app`、`service` 四类角色共用同一套加载、依赖与生命周期机制。
- 内核只负责：Context 树、Fork 与可逆副作用、服务注册与注入、插件状态机、依赖解析、事件派发、错误归一与隔离、线程与并发调度。
- 内核不负责：Bridge 能力注册表与权限判定、插件安装业务流程、资源句柄、文档渲染、文件格式——这些各有归口文档。

| 组件 | 职责 | 不变量 |
|---|---|---|
| PluginManager | 状态机、依赖图、加载卸载事务 | 任一插件任一时刻只有一个状态、至多一个注册生效的插件 Fork |
| ContextRegistry | Context 树、作用域、生命周期 | 子 Context 先于父销毁 |
| ForkRegistry | 副作用登记与逆序撤销 | 每个副作用只撤销一次，销毁后零残留 |
| ServiceRegistry | 服务表、注入、代际 | 读路径不取写锁；写路径快照原子替换 |
| EventBus | 监听表、同步派发 | 派发期间不持写锁；无监听器零分配 |

权威：[《薯片内核设计》](../../../薯片生态文档库/01-架构设计/01-子系统设计/01-薯片内核设计.md)。

## 二、并发模型与内核红线

### 2.1 单写多读

- **全部可变状态由内核命令循环独占写入**：所有状态变更经命令队列投递到命令循环，串行执行，天然避免竞态与乱序。
- 其余线程只读不可变快照：服务表与监听表以 `Arc` 快照发布，读路径只做一次读锁 + `Arc::clone`。
- 调用插件代码前必须释放内核锁；传入插件的是快照或句柄；**禁止在持锁状态下 `await`、执行阻塞调用或调用插件代码**。
- 阻塞型插件调用（文件 IO、图像处理）必须经 `spawn_blocking`；跨语言调用经 Neon Channel 投递到 Node.js 线程，内核线程不直接调用 JavaScript。

### 2.2 红线 K-1 ~ K-5

| 编号 | 规则 |
|---|---|
| K-1 | 服务间调用必须经内核解析与注入，禁止插件之间直接 `import` 调用 |
| K-2 | 一切副作用必须登记到 Fork；Context 销毁后零残留 |
| K-3 | 插件代码的错误与 panic 不得破坏内核状态，不得影响其他插件 |
| K-4 | 调用插件代码时不得持有内核锁；不得在持锁状态下 `await` |
| K-5 | 生产代码禁止 `unwrap()` 与 `panic!`；`unsafe` 必须附 `# Safety` 注释 |

## 三、Context 与 Fork

### 3.1 Context

- 根 Context 由内核启动时创建，平台服务（含 Bridge 服务）注册在根 Context；每个插件加载时创建一个插件 Context，父节点为加载请求指定的父 Context。
- 服务可见性：注册在 Context 上的服务对自身与全部后代可见；同名服务以最近祖先为准，子遮蔽父。
- Context 生命周期：`Created → Active → Disposing → Disposed`；销毁父 Context 前先销毁全部子 Context；`Disposing` 后拒绝新的 `provide` / `inject` / `on`；销毁幂等。

### 3.2 Fork 与可逆副作用

- Fork 是副作用追踪与撤销单元：每个 Context 持有一个作用域 Fork，每次插件加载创建一个插件 Fork，每次注入创建一个注入 Fork。
- 副作用类型：服务注册、事件监听、子 Fork、后台任务、定时器与自定义资源；内建能力必须走各自登记入口，不允许绕过追踪。
- **dispose 顺序固定**：子 Fork 后序 + 自身副作用 LIFO（后登记先撤销）；单个副作用撤销失败不中断流程。

### 3.3 任务 API：`ctx.task`

- `ctx.task(fn, { name?, signal? })` 返回可等待句柄（`join()` / `cancel()`），与内核 `Effect::Task` 一一对应。
- 任务登记到当前 Fork，随 Fork 撤销自动取消；活跃任务数计入插件软配额。
- 取消是**协作式**的：长任务必须周期性检查取消信号并在取消时释放已占用资源；拒绝响应取消视为插件缺陷。

## 四、服务模型与代际

### 4.1 服务定义

- 服务由 `ctx.provide` 注册、由 `ctx.inject` 消费；绑定完成后服务调用是直接方法调用，内核不在调用路径上。
- 服务名规范：`^[a-z][a-z0-9]*(-[a-z0-9]+)*$`；作用域内唯一。
- **服务不设独立版本号**：内核内置服务属于内核 ABI，随平台版本演进；插件间服务消费的兼容性由 `dependencies` 版本范围与能力契约版本共同约束。同一服务名同时只有一个生效代际，不提供多版本共存。

### 4.2 暂存代际与原子发布

1. **Starting 暂存**：插件 Fork 处于 `Starting` 期间，`provide` 只写入该 Fork 的**暂存代际**，对服务解析不可见，不触发级联重建；
2. **Active 原子发布**：插件进入 `Active` 时，暂存代际一次原子写入服务表（单次快照替换），同名条目代际 `generation + 1`，随后触发级联重建；
3. **回滚**：apply 失败或进入 `Active` 前被取消时，暂存代际随插件 Fork 一并丢弃，服务表与其它插件不受影响；
4. **Active 期间 provide** 立即原子发布并触发级联重建。

### 4.3 注入与级联重建

- 依赖全部可用时创建注入 Fork 并执行回调；任一依赖被替换、摘除、提供方停用或进入 `Failed` 时，撤销注入 Fork，注入回到 `Waiting`。
- **提供方 `Failed` 时依赖方保持 `Active`**：服务条目摘除，期间调用返回 `KERNEL_SERVICE_NOT_FOUND`；提供方恢复后按拓扑序重建。
- **反向依赖索引**以 `(ProviderFork/Generation, ServiceName)` 为键：只有确实消费了被替换代际的注入才重建。
- 重建顺序遵循依赖图拓扑序；**重建深度 ≤ 16**，超限中止本轮重建并上报 `KERNEL_REBUILD_OVERFLOW`，受影响注入保持 `Waiting`。

## 五、生命周期与超时

### 5.1 状态机

```
Pending ──load──▶ Resolving ──就绪──▶ Starting ──成功──▶ Active
                      │                   │                │
                      │ 缺失/版本暂不满足   │ 应用失败/超时   │ disable
                      ▼                   ▼                ▼
              Pending（等待依赖）         Failed          Stopping
                                                             │ 撤销完成
                                                             ▼
                                                         Installed
```

- `Resolving` 是内核内部子阶段，不对外暴露；版本范围互斥直接进入 `Failed`（`KERNEL_DEPENDENCY_VERSION`）。
- `Failed` 与 `Installed` 均可 `enable` 返回 `Resolving`；仅 `Installed` / `Failed` 可 `unload`。

### 5.2 生命周期超时（内核唯一定义）

| 常量 | 值 | 适用阶段 |
|---|---|---|
| `LIFECYCLE_APPLY_TIMEOUT` | 30s | `PluginRunner.apply` |
| `LIFECYCLE_STOP_TIMEOUT` | 10s | `PluginRunner.stop` |
| `FORK_FORCE_DISPOSE_TIMEOUT` | 30s | Fork 强制撤销时等待任务退出的上限 |

- apply 超时：回滚插件 Fork（含暂存代际），插件进入 `Failed`，返回 `KERNEL_LIFECYCLE_TIMEOUT`；
- stop 超时：不再等待回调，直接进入强制撤销，插件仍进入 `Installed`，超时记入审计；
- 强制撤销：触发全部任务取消并等待至多 30s，仍未退出则中止等待、继续撤销其余副作用。

### 5.3 热更新（蓝绿替换）

- 新版本创建新 Fork 执行 `Starting`，旧 Fork 继续 `Active`；新 Fork 进入 `Active` 时暂存代际原子发布，即为代际切换点。
- 旧 Fork 进入 draining：拒绝新调用并等待在途调用结束；超时后强制 `dispose`。
- **`app` 角色在旧窗口全部关闭前只冻结、不强制撤销**；draining 上限仅适用于非 `app` 角色。
- 更新窗口内最多两个 Fork 并存；任一步失败则 dispose 新 Fork，旧 Fork 继续运行。

## 六、事件总线

### 6.1 事件模型

- **事件总线只有同步广播一种分发模式**：不存在并行、串行、短路、环绕等模式，也不存在决策型事件（需要返回值或拦截时使用服务或能力）。
- 事件名规范：`^[a-z][a-z0-9-]*:[a-z][a-z0-9-]*$`（两段式，禁止点号）；插件自有域取插件 ID 末段；发布入口校验，不符合即拒绝。
- 事件信封由内核补全 `id`（ULID）、`source`（按调用上下文重写，插件不可伪冒）与 `timestamp`；监听器只接收 `payload`。
- 监听表以事件名分桶，写时复制快照发布；一次投递使用发布开始时的快照。

### 6.2 派发规则

- Rust 订阅者在发布线程内**同步调用**；JS 插件监听器经 Channel **异步投递**——`emit` 的语义是**入队成功**，不等待 JS 执行。
- 同一发布者、同一事件按 FIFO 调用与入队；不同发布者之间不保证顺序。
- 单个监听器错误不中断派发，首个错误返回发布者；事件系统不重试，至多一次投递。
- 嵌套发布深度超过 64 返回 `KERNEL_EVENT_DEPTH_EXCEEDED`。
- 退订原语为 `off(token)`（幂等）；插件可见面是 `IEventSubscription.dispose()`；Fork 撤销自动批量退订。

### 6.3 与 Bridge 事件的关系

事件总线只有一条：内核总线是唯一事件源与投递中枢。Bridge 事件是内核总线向渲染进程的跨进程投影，只承载公开事件的单向副本；插件发布事件必须走能力 `event:publish`，**没有独立发布通道**。

## 七、软配额与崩溃重启

### 7.1 软配额（内核唯一定义）

| 配额 | 计量点 | 默认值 |
|---|---|---|
| 内存 | 插件 Fork 存活期内对象、任务缓冲与句柄占用，按 5s 采样估算 | 256 MiB |
| 任务数 | 同一插件 Fork 内活跃 `ctx.task` 任务计数 | 32 |
| 消息速率 | 插件每秒发出的 Bridge 调用与事件发布合计（1s 滑动窗口） | 200 次/秒 |
| 后台时长 | 无用户交互下连续后台运行时长 | 10 分钟 |

超限状态机：**限流 → 暂停 → 停用**；不因单次越界直接停用，持续或反复越界才升级；降级、恢复与停用全部写审计；恢复不绕过崩溃重启窗口。

### 7.2 崩溃重启与熔断

- 运行期异常与任务 panic 被隔离后按受控重启处理：同一插件在 **10 分钟滚动窗口内最多自动重启 3 次**。
- 每次重启按指数退避：首次 1s，其后 2s、4s，单次间隔上限 30s。
- 超过上限进入 `Failed` 并停止自动重启，等待用户显式启用（`enable`）后重置窗口计数。
- 插件停用或卸载时清零窗口计数；重启、熔断与恢复动作全部写审计。

## 八、施工自检

- [ ] 可变状态是否只由命令循环写入，读路径是否只读快照？
- [ ] 调用插件代码时是否未持有内核锁、未持锁 `await`？
- [ ] 副作用是否全部登记到 Fork，dispose 后零残留？
- [ ] 服务是否在 `Active` 时一次原子发布，apply 失败是否丢弃暂存代际？
- [ ] 生命周期超时（apply 30s / stop 10s / 强撤 30s）与软配额降级是否按内核常量执行？
- [ ] 事件是否只有同步广播 + JS 经 Channel 入队，`emit` 是否只表示入队成功？
- [ ] 崩溃重启是否遵守 10 分钟 / 3 次与指数退避，超限是否进入 `Failed`？
