## 一、治理总则

### 1.1 本轮工作依据与效力顺序

| 顺序 | 依据 | 效力 |
|---|---|---|
| 1 | [本轮架构收口裁决](../本轮架构收口裁决.md) | 本轮唯一施工依据：命名、类型、机制与冲突裁决；文档库表述与之冲突时按裁决修订 |
| 2 | [薯片生态文档库](../../../薯片生态文档库/README.md)（正式文档） | 已落库的契约与设计；裁决已覆盖的部分以裁决为准 |
| 3 | [最终任务：薯片生态完整文档库与最佳架构设计](../最终任务：薯片生态完整文档库与最佳架构设计.md) 与 [基础要求、规范、理念](../架构的一部分基础要求，规范，理念.md) | 方法论、核心原则与不变式来源；不直接作为具体契约依据 |

- 裁决未覆盖的新冲突：按"最小改动 + 与裁决原则一致"处理，并在交付说明中列出（裁决 §七）。
- 功能方面与架构方面的口径冲突，按 [写作与协作原则](../06-写作与协作原则.md) §2.4 的优先级处理；最终以裁决为准。

### 1.3 契约变更流程：RFC → 评审 → ADR → 门禁 → 文档同步

重大变更固定五步（R16）：

1. **RFC**：背景、动机、方案、影响范围。
2. **评审**：架构一致性、性能影响、风险评估；结论写入评审记录，不进入 ADR 正文。
3. **ADR**：按 [03-变更与决策管理](../../../薯片生态文档库/07-工程管理/03-变更与决策管理.md) §4 的唯一模板记录决策、关键设计、约束、后果；正文一经接受不得修改，推翻需新建 ADR。
4. **门禁**：通过 [05-CICD与质量门禁](../../../薯片生态文档库/06-开发与运维/05-CICD与质量门禁.md) 的 G8（契约一致性）与 G12（文档覆盖率/坏链）等全部判定。
5. **文档同步**：受影响的正式文档与 README 索引同 PR 更新。

- 文档与实现不一致视为缺陷（R16）；变更分级、技术债管理以《变更与决策管理》为准，本文不复制其细节。

### 1.4 无兼容包袱

- 第一版发布前：完全推倒重来、旧版冻结，不做兼容性重构（ADR-010）；禁止双轨、兼容映射、回退机制与过时口径。
- 第一版发布后：契约稳定，破坏性变更走主版本 + 迁移工具；仍禁止运行时兼容层（[04-版本与迁移规范](../../../薯片生态文档库/04-文件格式规范/04-版本与迁移规范.md)）。
- 版本闸门：`chip_standards_version` 为严格三段式，禁止预发布；格式版本问题用 `DOCUMENT_VERSION_*`（R20）。
- 判据：任何"为兼容旧写法"而新增的分支、别名、字段 = 违规，按《禁止事项与反模式》处理。

### 1.5 文档治理

- 四层文档体系与文档分层以 [超大型工程管理体系](../../../薯片生态文档库/07-工程管理/01-超大型工程管理体系.md) 为准；正式文档只进 `薯片生态文档库/`，过程材料只在 `项目日志与笔记/`（R10）。
- 写文档先核对代码、清单与运行链路；不得依赖 README、脚手架模板文本或历史任务说明（AGENTS 开工顺序）。
- 归档不删除：需要移除的内容移动到就近 `归档/` 目录，并在引用方更新路径；被归档文档不作依据，只在历史说明中引用。
- 文档修订后保持文档头、章节编号与"相关文档"章节规范；新增/移动/改名/归档必须同步 README 索引与 [14-新增文档登记表](./14-新增文档登记表.md)。

### 1.6 质量门禁

- Rust：`cargo clippy` 无 warning、`cargo fmt` 通过；总体覆盖率 > 80%，`chips-*` crates > 90%；`unsafe` 必须带 `# Safety`。
- TypeScript：ESLint 无 error、Prettier 通过、`strict: true`；总体覆盖率 > 80%，`@chips/ui`、`@chips/bridge` > 90%。
- 集成测试、契约测试全绿；性能基线引用 [架构原则](../../../薯片生态文档库/00-愿景与原则/01-架构原则.md) §4.2，不得自创指标。
- 性能基线不挂账：不达标必须分析原因并改架构或实现，禁止"后续优化"式推迟。
- 完成定义：门禁全绿 + 文档同步 + 证据可核对，才算完成。

## 二、架构不变式清单（全量红线速查）

下表为全生态不可违反的不变式。文档名均指 `薯片生态文档库/` 内同名文档，完整路径见 [README](../../../薯片生态文档库/README.md)。

| 域 | 不变式 | 权威文档 |
|---|---|---|
| 承载 | 平台是唯一运行时承载；插件不碰 Node/Electron/系统 API，主进程插件只经受管模块加载器（ModuleLoader）加载（禁止 `node:*`、`electron`、裸路径） | [03-插件架构设计](../../../薯片生态文档库/01-架构设计/01-子系统设计/03-插件架构设计.md)、[01-Bridge-API规范](../../../薯片生态文档库/05-接口与契约/01-Bridge-API规范.md) |
| 通信 | 唯一门 Bridge（`request` / `subscribe` / `resource`）；服务走内核路由；不跨层、不直连、不反向调用 | [02-Bridge三层设计](../../../薯片生态文档库/01-架构设计/01-子系统设计/02-Bridge三层设计.md)、[01-薯片内核设计](../../../薯片生态文档库/01-架构设计/01-子系统设计/01-薯片内核设计.md) |
| 身份 | 会话由 Bridge 按 IPC 来源解析，插件不可自报；会话有效性 → 权限 → schema 三步校验全部在主进程完成 | [02-Bridge三层设计](../../../薯片生态文档库/01-架构设计/01-子系统设计/02-Bridge三层设计.md)、[08-权限系统设计](../../../薯片生态文档库/01-架构设计/01-子系统设计/08-权限系统设计.md) |
| 内核 | 单写者（内核命令循环独占写入）；不持锁 await；副作用可逆（Fork 零残留）；崩溃隔离；服务代际暂存原子发布 | [01-薯片内核设计](../../../薯片生态文档库/01-架构设计/01-子系统设计/01-薯片内核设计.md) §5、§6 |

| 文件 | 一切来源皆挂载、一切访问皆句柄；插件只经 `chips-resource://` 与句柄访问，不接触真实路径；document 挂载写入只经文档服务受控提交 | [04-资源管理设计](../../../薯片生态文档库/01-架构设计/01-子系统设计/04-资源管理设计.md)、[06-资源协议规范](../../../薯片生态文档库/05-接口与契约/06-资源协议规范.md) |

## 三、结语

薯片生态的架构可以概括为三句话（[基础要求、规范、理念](../架构的一部分基础要求，规范，理念.md) 结语）：

1. **一条竖线**：内容 → 插件 → 契约 → 平台 → 壳 → 系统，层层向下、界限分明；
2. **三个平面**：能力面（南向能力）、事件面（北向通知）、资源面（句柄化访问），互相正交、各有契约；
3. **一条链路**：从文件字节到屏幕像素再到修改落盘，全程同一条链、同一个模型、同一个写口。

内核薄到无感、契约硬如宪法、链路单而无歧、内容久而不死——治理与不变式的全部规则都服务于这一形态。
