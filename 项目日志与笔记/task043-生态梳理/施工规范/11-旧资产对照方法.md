# 旧资产对照方法

> 版本：v1.0.0
> 日期：2026-09-19
> 状态：正式版
> 适用范围：《施工规范套件》11 分册：三套旧文档库与全部旧仓库的对照流程、覆盖判定、差距表与"先穷尽清单再设计"纪律；含上一轮漏检 CLI 的案例复盘

---

## 一、目标与适用

1. 目标：保证新库对旧资产（旧文档库、旧仓库）的覆盖判定是**逐文件、可核对、无漏检**的，任何旧资产都有明确的覆盖状态与处置。
2. 适用：所有承担旧资产对照与补齐任务的子智能体；对照结果写入 `梳理表/分片-<ID>.tsv`（schema 见 [15-梳理表与网络报告规范](./15-梳理表与网络报告规范.md)）。
3. 纪律：**先穷尽清单，再设计**。清单未冻结前，不得开始覆盖判定与补设计。

## 三、对照流程（五步）

1. **旧资产逐文件清单**
   - 三套旧文档库：每个 `.md` 文件一行；
   - 旧仓库：文档目录逐文件 + 源码逐文件（排除构建产物）；
   - 每行填写：节点ID、来源类型、路径、主题、维度标签、证据（行数或关键行号）。
2. **主题归类**
   - 按主题维度聚合（如"编辑器接口""写入原子性""CLI 命令"），同一文件可属于多个主题（多标签）；
   - 归类只改变组织方式，不改变清单事实。
3. **新库覆盖判定**
   - 对每条旧资产在 `薯片生态文档库/` 中寻找对应定义或正式处置；
   - 覆盖状态取值：`已覆盖` / `部分` / `缺失` / `冲突`；
   - "正式废弃"计入 `已覆盖`，但必须在判定说明中写明依据（ADR 编号或裁决编号）；找不到依据的废弃视为 `缺失`。
4. **差距表**
   - 只列出 `部分` / `缺失` / `冲突` 三类；
   - 冲突必须在同一轮给出裁决或登记跨模块工单。
5. **直接补设计**
   - 缺口直接补：修改/新增文档、补契约、补接口、补链路；
   - 不走"待办清单"，不等待确认；仅跨模块才写工单（见 [10-审查方法与检查清单](./10-审查方法与检查清单.md) §七）。

## 四、案例复盘：为什么上一轮漏掉命令行（CLI）

### 4.1 事实链

1. 上一轮架构对照只覆盖了两类对象：
   - 新库自身（子系统设计与接口文档）；
   - 五个子系统的旧代码：`Chips-Host`、`Chips-EditingEngine`、`Chips-BaseCardPlugin`、`Chips-SDK`、`Chips-Scaffold`（证据：[新架构优化对照报告](../新架构优化对照报告.md) 结语"调研覆盖"）。
2. 旧文档库对照在该轮之后才补做，且采用**主题级归并**：如"架构设计 21 篇 → 已覆盖（去重重组为 11+10）"（证据：[文档库并行开发可行性审查报告](../文档库并行开发可行性审查报告.md) §四）。
3. 首轮对照因此漏掉 CLI：旧库有专门的两篇手册与一篇使用指南（证据：`旧版-生态共用技术文档/命令行工具/01-Chips-Host命令行使用手册.md`、`02-Chips-Dev开发者命令行手册.md`、`旧版-生态共用技术文档/开发与运维/03-命令行拆分与使用指南.md`），而新库只在《快速开始》《构建与打包》零散提及命令（证据：[文档库并行开发可行性审查报告](../文档库并行开发可行性审查报告.md) §一、§六）。
4. 同一方法缺陷还掩盖了其他旧资产，使它们从未获得逐条判定：
   - 平台抽象层：`旧版-生态共用技术文档/架构设计/02-平台抽象层设计.md`；
   - 日志系统：`旧版-生态共用技术文档/架构设计/09-日志系统架构设计.md`；
   - 服务器侧产品：`Chips-CommunityPlatformServer/`、`Chips-PersonalServer/`、`Chips-CommunityClient/` 及其旧契约 `旧版-生态共用技术文档/协议与契约/09-社区平台API契约.md`、`10-个人服务器API契约.md`。

### 4.2 根因

| 根因 | 表现 | 后果 |
|---|---|---|
| 以新库为主键审查 | 只审"新库里有什么" | 看不到新库里没有的东西，缺失天然不可见 |
| 旧仓库只取五处 | 其余 17 个旧仓库未进入对照 | 服务器侧、查看器、播放器等产品的旧设计无判定 |
| 主题级归并代替逐文件 | "架构设计 21 篇已覆盖"式结论 | 个别文件被大类掩盖，漏检无法被发现 |
| 无全量清单与覆盖矩阵 | 没有"每条旧资产 → 状态"的表 | 漏检既不可度量，也不可追责 |

### 4.3 补救纪律

1. **先穷尽清单，再设计**：清单冻结后才允许覆盖判定；清单本身可核对（路径级、行数级）。
2. **覆盖矩阵以旧资产为主键**：每条旧资产必须有且只有一个覆盖状态；禁止以主题大类状态代替文件级状态。
3. **双向交叉**：功能视角结论必须有旧资产来源（文件视角）支撑；找不到来源的功能按"凭空设计"处理。
4. **否定结论要留检索证据**：判定"新库缺失"时必须记录检索命令、检索范围与命中数。
5. **每轮收尾复核**：统计清单条目数、判定条目数，二者必须相等；不等即漏检。

## 五、防复发检查（开工前/收尾前）

### 开工前

- [ ] 两个基线清单（旧文档库文件、旧仓库文件）已冻结并记录数量
- [ ] 号段已由主代理分配，分片文件已建立且表头一致
- [ ] 本分片覆盖范围（仓库/目录）已写明，无重叠无遗漏

### 收尾前

- [ ] 清单条目数 = 已判定条目数
- [ ] 所有 `部分/缺失/冲突` 均有差距表行与处置
- [ ] 所有"正式废弃"判定均有 ADR/裁决依据
- [ ] 无"待判定"式悬空状态
- [ ] 案例复盘中的四类漏检对象（CLI、平台抽象层、日志系统、服务器侧产品）已有明确结论
