## 2026-09-16 · 阶段七：用户决策——平台运行时为主，自带库为例外

### 用户决策（重要）

> "大部分都是平台提供的运行时，只有软件自己有特殊需要的时候，才自己打包相关库和代码。这是允许的。"

### 我方理解与推论

- 正式原则：**运行时托管为默认，自带库为例外**（对标 iOS：UIKit/SwiftUI 由系统提供；游戏/专业工具可自带引擎）。
- 效果成立：平台更新 → 所有使用运行时的软件自动获得新外观/新行为（"系统一更新，所有软件自动变"成为生态真能力）。
- "写一次"升级为两个维度：**空间上五端运行 + 时间上跨版本受益**。
- 必然要求：
  1. 运行时是平台的正式表面（契约），实现可替换——antd 今天是实现，不是契约；插件应依赖语义 API 而非具体库（语义化原则在依赖层面的落地）。
  2. 版本治理与兼容承诺（第一版后契约稳定）。
  3. 交付机制：构建期外部化 + 运行时注入 + 跨端一致（具体机制待设计）。
  4. 例外路径规则：允许自带，但仍受底座契约（权限/生命周期/隔离/表面语义）约束；自带者失去自动外观更新；需要可被治理/识别。
- 既有决策调整：task030"每个插件各自打包 antd + @chips/ui"从"长期架构"降级为"开发期实现"，长期目标为平台运行时。

## 2026-09-16 · 阶段八：用户提出"厚而无感"哲学

### 用户原话

> "就是整个底层系统非常厚，但是看起来什么都管了，但是有感觉什么都没管，什么都没限制。"

### 我方提炼

- 命名提案：**厚而无感**——底层无所不包，使用无所限制，感受无形无感。
- 悖论解法：**"管"与"不管"分层**——管能力不管创作、管默认不管选择、管结构不管行为、管治理不管审批。它管的全是"底"，从不碰"上"。
- 核心机制：**禁令 → 能力的翻译**。每一条限制都被底座消化成一条能力或一个默认：
  - "不许直接读文件" → "给你文档句柄与受控 URL"
  - "必须做权限校验" → "权限是身份的一部分，机制自动裁决"
  - "必须遵循视觉规范" → "组件默认就长对了"
  - "必须处理跨端差异" → "API 语义统一，差异被吸收"
  - "必须做安全隔离" → "隔离就是默认的运行环境"
- 三个检验：新人零内部知识可开发 / 用户说不出"我在用平台" / 新软件类型永远不需要向平台"申请支持"。

## 2026-09-16 · 阶段九：命名讨论（底层系统叫什么）

### 用户问题

推荐这个"底层系统"叫什么？从技术角度讲应该叫什么？

### 我方建议（待用户决定）

- 技术类别：**应用运行时平台（Application Runtime Platform）**——运行时 + 服务 + 框架 + 治理四合一。
- 整体名称推荐：**薯片平台（Chips Platform）**。
- 分层命名：薯片核心（Chips Core，可移植核心）/ 薯片运行时（Chips Runtime，执行环境）/ 薯片内核（Chips Kernel，路由治理）/ 壳（Shell，平台适配）。
- 长期对外：当平台接管用户环境后，"薯片系统"是自然叫法；现阶段不宣称 OS。
- "Host/主机"降级为角色词（插件宿主），不再作为整体名称——理由：关系名非本质名、"主机"中文误导（硬件）、低估平台性、有歧义。
- 改名成本：文档正在重写，此刻是更名成本最低的时点。
