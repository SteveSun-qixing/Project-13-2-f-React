## 一、背景

新架构下旧「模块插件」角色不存在，其功能按《09-官方插件与应用目录》§6.2 归并为**内容处理服务插件**，而《04-能力契约规范》§8.4（分件 `薯片生态文档库/05-接口与契约/04.23-04-能力契约规范-八、内容处理服务能力.md`）已经把该族能力钉成 canonical 登记表：**13 项能力 / 4 个服务包**（`chips.service.content-image`、`content-media`、`content-converter`、`content-office`），加上《09》§6.1 在册的编排与会话服务 `chips.service.file-processing` 与富文本前置件 `chips.service.markdown`，构成本族的全部拆包面。

契约规范同时规定：**契约随插件发布**（《09》:177 行「以 Cordis 服务提供（不注册 Bridge 能力）；契约随插件发布」），且契约包落点在服务包目录内书写为 `contractPackage: chips.service.content-image/contracts`（《04.23》:52）。

## 二、证据（全部主智能体一手实读，真实路径与行号）

1. 契约落点口径：`薯片生态文档库/05-接口与契约/04.23-04-能力契约规范-八、内容处理服务能力.md:52`

   ```ts
   contractPackage: string;          // 提供方契约包（如 chips.service.content-image/contracts）
   ```

   同篇 `:64-84` 为 canonical 能力表（13 能力 / 4 服务，含输入→输出与错误码族），`:30` 钉死「内容处理能力一律使用点号形式，冒号形式一律无效」。

2. 随包发布口径：`薯片生态文档库/03-插件开发/09-官方插件与应用目录.md:177`（`chips.service.markdown` 行「契约随插件发布」），`:182-194` 为旧模块插件→新服务归属映射表（七包全部指向「内容处理服务」形态）。

3. **互斥事实**：打包与校验的包根白名单不含 `contracts/`。
   - `chips-ecosystem/packages/cli/src/artifacts/cpk-pack.ts:25`：`const PACK_ROOT_FILES: readonly string[] = ['manifest.yaml', 'render.js'];`（头注 `:21` 明写参与打包者为「`manifest.yaml`、`render.js` 与 `dist/`、`assets/` 子树」）
   - `chips-ecosystem/packages/cli/src/artifacts/cpk-validate.ts:95`：`const ROOT_WHITELIST = ['manifest.yaml', 'dist', 'render.js', 'assets', SIGNATURE_FILE];`
   ⇒ 放在包根 `contracts/` 的契约目录**既不会被 pack 进 `.cpk`，也会在 validate 侧成为不在白名单上的顶层目录**。

4. 并行路实证（同批两路交付物的相反选择，构成实际口径分叉）：
   - 任务 #268（`chips.service.colorpicker` 单包迁移，交付未入库）在报告登记：兄弟服务件把契约放 `contracts/`，而 pack 根白名单只含 `manifest.yaml`/`render.js`/`dist`/`assets`，**其契约不进 .cpk**；该路因此把 JSON Schema 改落 `assets/schemas/` 以自证可发布。
   - 在册母型 `chips-ecosystem/plugins/layouts/grid/`（提交 `420d57085`）同样把 schema 放 `assets/schemas/`，全仓 `plugins/**` 无 `contracts/` 目录先例（`find` 零命中）。

## 三、影响范围

- **本族全部服务包**：`content-image`（3 能力）／`content-media`（2）／`content-converter`（3）／`content-office`（5）／`file-processing`（编排会话）／`markdown`——契约发布链路不通，则消费方（`file-processing` 会话、编辑器导出面板、富文本查看链）拿不到机器可读契约，「按描述符选择提供方、不支持组合返回 `FILE_PROCESS_TARGET_UNSUPPORTED`」（《15-文件处理契约》§3.5）的机检无从落地。
- **门禁与脚手架面**：`tools/scaffold/src/templates/service.ts` 现仅心跳骨架（G2 缺口在册），模板不知道该输出 `contracts/` 还是 `assets/schemas/` ——在落点裁定前派 G2 单会固化错误形制。
- **已在途/已交付件**：#265（cardtohtml）、#266（htmltoimage+htmltopdf）、#268（colorpicker）三包均按 `assets/schemas/` 形制落地，与本条 4 的母型一致但**与《04.23》:52 的 `contracts` 书写不一致**；若裁定取 `contracts/`，需一次合流重形（含把非 canonical 包名并入 canonical 拆包，见 W4 §九 v0.1.4）。

## 四、期望行为

1. 契约落点有**单一权威口径**：要么裁定契约目录为包根 `contracts/` 并扩 `cpk-pack.ts:25` 与 `cpk-validate.ts:95` 两处白名单（同步《06-服务插件开发指南》§七与脚手架模板），要么裁定 `contractPackage` 字段值语义为「包内相对路径」并把权威书写翻正为 `assets/contracts/` 形（同步《04.23》:52 措辞与版本随动）。二者皆可接受，**不接受两口径并存**。
2. `chips plugin pack` 产出的 `.cpk` 成员集**实测包含**契约目录，且 `chips plugin validate` 对该成员集判绿；补一条锁测防回归（契约不进包 ⇒ 红）。
3. 脚手架 `service` 模板随裁定输出对应形制，并在《06》§七 与《02-插件清单规范》§8.1 留可核对文字。
