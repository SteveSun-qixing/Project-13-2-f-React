# 生产域名与对象存储部署说明

## 文档定位

- 本文档说明 `Chips-CommunityPlatformServer` 在生产环境绑定正式域名、HTTPS 与外部 S3 兼容对象存储的部署口径；
- 本文档以当前代码中的 `deploy/docker-compose.yml`、`deploy/nginx/nginx.conf`、`deploy/nginx/web.conf`、`deploy/nginx/admin.conf`、`packages/server/src/config/env.ts`、`packages/server/src/worker.ts`、`packages/server/src/services/card-render-cache.service.ts`、`packages/server/src/storage/buckets.ts`、`packages/server/src/storage/init.ts`、`packages/server/src/storage/s3.ts` 为准；
- 本文档只记录社区服务器自身部署细节，不替代对象存储厂商控制台、DNS 控制台或证书平台的操作文档。
- 最后核对时间：2026-05-24。

## 1. 域名入口

生产环境推荐使用单一主访问域名作为 `BASE_URL`，另一个域名只做跳转。

当前 `nginx.conf` 的正式口径为：

- `http://chipscard.space` -> `https://www.chipscard.space`
- `http://www.chipscard.space` -> `https://www.chipscard.space`
- `https://chipscard.space` -> `https://www.chipscard.space`
- `https://www.chipscard.space` 承载社区前台、后台与 API
- `https://file.chipscard.space` 承载对象存储公开资源

正式环境的 `BASE_URL` 必须与主访问域名完全一致：

```env
BASE_URL=https://www.chipscard.space
```

原因：

- 服务端生产 CORS 只允许 `BASE_URL` 同源请求；
- refresh token Cookie 在生产环境启用 `Secure`；
- 前台 `/api` 与 `/admin/api` 都按同源路径访问。

## 2. HTTPS 证书

当前 Nginx 容器从以下路径读取证书：

```text
Chips-CommunityPlatformServer/deploy/certs/chipscard.space_ca.crt
Chips-CommunityPlatformServer/deploy/certs/chipscard.space.key
```

证书必须覆盖：

- `chipscard.space`
- `www.chipscard.space`

证书私钥不进入 Git，`deploy/certs/*` 已由项目 `.gitignore` 排除。

## 3. 对象存储写入入口

服务端通过 S3 兼容协议写入对象存储。Docker 全栈模式下，容器内 `S3_ENDPOINT` 来自：

```yaml
S3_ENDPOINT: ${S3_RUNTIME_ENDPOINT:-http://minio:9000}
```

因此生产外部对象存储应在 `deploy/.env` 中配置：

```env
S3_RUNTIME_ENDPOINT=https://s3.ap-southeast-1.qiniucs.com
S3_ENDPOINT=https://s3.ap-southeast-1.qiniucs.com
S3_REGION=ap-southeast-1
S3_FORCE_PATH_STYLE=true
```

`S3_ENDPOINT` 保留给本地 Node 进程直接读取；`S3_RUNTIME_ENDPOINT` 保证 Docker 容器运行时也使用同一生产入口。

七牛云 S3 兼容写入必须使用与公开直连资源兼容的校验配置：

```ts
requestChecksumCalculation: 'WHEN_REQUIRED'
responseChecksumValidation: 'WHEN_REQUIRED'
```

原因：

- AWS SDK v3 在默认配置下会对 `fs.createReadStream(...)` 上传启用流式校验编码；
- 七牛云 S3 兼容接口会把这类请求里的 `content-encoding: aws-chunked` 持久化为对象元数据；
- 浏览器通过 `file.chipscard.space` 直连对象时可能误按 `aws-chunked` 解码，表现为新上传 HTML 或图片乱码、图片查看器无法正常显示；
- 当前代码在 `packages/server/src/storage/s3.ts` 的 `getS3Client()` 中统一设置上述配置，上传仍保持流式读取，不需要把大文件整体读入内存。

部署验证时，任意新上传的图片、HTML、CSS、JS 等公开对象响应头都不应再包含：

```text
content-encoding: aws-chunked
```

文本类资源应携带明确 charset，例如：

```text
content-type: text/html; charset=utf-8
```

## 4. 数据库结构部署口径

社区服务器业务上按用途保留多类逻辑 bucket：

- `chips-card-resources`
- `chips-card-files`
- `chips-card-render-cache`
- `chips-card-render-cache-private`
- `chips-card-cover-cache`
- `chips-card-cover-cache-private`
- `chips-avatars`
- `chips-covers`

当对象存储服务商为公开资源使用一个物理 bucket 时，设置：

```env
S3_BUCKET_NAME=chipscardspace
```

写入规则：

```text
逻辑 bucket: chips-card-render-cache
业务 key: card-1/cache-version/index.html
物理 bucket: chipscardspace
物理 key: chips-card-render-cache/card-1/cache-version/index.html
公开 URL: https://file.chipscard.space/chips-card-render-cache/card-1/cache-version/index.html
```

这样可以保持数据库中的 `coverUrl`、`viewUrl` 对应缓存入口、`entryUrl` 和前端资源路径稳定，同时满足单 bucket 部署要求。

当前 `chips-card-files`、`chips-card-render-cache-private`、`chips-card-cover-cache-private` 属于内部 bucket。单物理 bucket 模式下，当前代码仍会为这些内部 bucket 单独创建 bucket，不映射进 `S3_BUCKET_NAME`，以避免源 `.card` 和私有缓存被公开读策略覆盖。

私有逻辑 bucket 始终使用独立私有物理 bucket，不进入 `S3_BUCKET_NAME` 对应的公开物理 bucket：

```text
chips-card-files/{userId}/{cardId}/source.card
chips-card-render-cache-private/{cardId}/{cacheVersion}/index.html
chips-card-cover-cache-private/{cardId}/{cacheVersion}/index.html
```

`chips-card-files` 是永久 `.card` 源文件存储。渲染缓存删除、重建或过期清理都不得删除该源文件。

## 6. 公开资源入口

生产环境推荐使用对象存储服务商绑定的自定义 HTTPS 域名：

```env
S3_PUBLIC_URL=https://file.chipscard.space
```

七牛云侧需要保证该域名已绑定到空间或 CDN，并配置有效 HTTPS 证书。当前正式资源域名为：

```text
https://file.chipscard.space/
```

说明：

- 浏览器直接访问 `https://file.chipscard.space/...`，社区主站不承担资源代理流量；
- 对象实际写入七牛云单物理 bucket `chipscardspace`，公开路径仍带逻辑 bucket 前缀；
- Nginx 保留 `/cdn/` 到 `https://file.chipscard.space/` 的 301 跳转，用于把旧入口统一到正式资源域名。

## 7. 卡片渲染 Worker 部署

卡片上传接口当前不会在 API 请求进程内执行渲染。生产部署必须同时运行 API `server` 与卡片渲染 `worker`。

### 7.1 Compose 服务形态

`deploy/docker-compose.yml` 中的 `worker` 服务复用 `Dockerfile.server` 构建出来的同一镜像，并通过命令切换入口：

```yaml
command: ["node", "dist/worker.js"]
```

Worker 容器与 `server` 使用相同的 `.env`，并在 Compose 中覆盖：

```yaml
DATABASE_URL: postgresql://ccps_user:ccps_password@postgres:5432/ccps_db
REDIS_URL: redis://redis:6379
S3_ENDPOINT: ${S3_RUNTIME_ENDPOINT:-http://minio:9000}
CARD_RENDER_WORKER_CONCURRENCY: ${CARD_RENDER_WORKER_CONCURRENCY:-1}
```

`worker` 依赖 PostgreSQL、Redis 与 `server` 已启动。它不暴露公网端口。

### 7.2 Worker 启动顺序

`packages/server/src/worker.ts` 的正式启动顺序为：

1. 执行数据库迁移；
2. 连接 Redis；
3. 初始化对象存储 bucket；
4. 初始化 Host 集成层；
5. 重新入队超过 30 分钟仍处于 `processing` 的渲染任务；
6. 先执行一次过期缓存清理；
7. 按 `CARD_RENDER_WORKER_CONCURRENCY` 启动消费循环；
8. 每小时执行一次过期缓存清理。

Worker 从 Redis 队列 `ccps:card-render:queue` 取任务，在 PostgreSQL `card_render_jobs` 表中锁定任务，下载 `chips-card-files/{userId}/{cardId}/source.card`，然后按 `renderProfile` 生成缓存：

- `community-web`：生成完整查看缓存，写入 `chips-card-render-cache` 或 `chips-card-render-cache-private`；
- `community-cover`：生成封面缓存，写入 `chips-card-cover-cache` 或 `chips-card-cover-cache-private`。

缓存记录保存在 `card_render_caches`，命中访问会续期到最后一次访问后 30 天。失败时按配置重试，超过次数后任务置为 `failed`，缓存记录置为 `error`。

### 7.3 Worker 环境变量

与 Worker 直接相关的环境变量：

- `CARD_RENDER_WORKER_CONCURRENCY`
  - Worker 消费循环并发数，默认 `1`
- `CARD_RENDER_JOB_MAX_ATTEMPTS`
  - 单个任务最大尝试次数，默认 `2`
- `CARD_RENDER_QUEUE_POLL_TIMEOUT_SEC`
  - Redis `brpop` 阻塞等待秒数，默认 `5`
- `CARD_RENDER_CACHE_UPLOAD_CONCURRENCY`
  - 渲染缓存目录上传并发，默认 `8`
- `CARD_RENDER_CACHE_TTL_DAYS`
  - 查看缓存和封面缓存最后一次访问后的保留天数，默认 `30`
- `CARD_RENDERER_VERSION`
  - 渲染缓存版本键中的服务器渲染器版本，默认 `community-card-renderer-4`
  - `community-card-renderer-2` 起，社区 Web HTML 缓存必须把 Host 注入主题字体等根外本地文件资源复制进导出产物并改写为相对 URL；`community-card-renderer-3` 起，离线基础卡片 iframe 的相对资源基准 URL 必须由 Host 单卡运行时按当前文档 URL 归一；`community-card-renderer-4` 起，缓存产物必须包含视频/电子书基础卡片最新资源打开 payload，以确保卡片内部视频、电子书和图片序列点击事件能继续启动对应资源处理应用。升级该值可让旧缓存自然失效并重新生成。
- `UPLOAD_SESSION_TTL_MINUTES`
  - 官方上传会话过期时间，默认 `60`

## 8. Nginx 缓存口径

当前生产入口由外层 `deploy/nginx/nginx.conf` 统一承载。缓存口径如下：

- `/assets/`
  - 代理到 `web:80` 的 `/assets/`
  - 外层 Nginx 隐藏上游 `Cache-Control`
  - 写入 `Cache-Control: public, max-age=31536000, immutable`
- `/admin/assets/`
  - 代理到 `admin:80` 的 `/assets/`
  - 外层 Nginx 隐藏上游 `Cache-Control`
  - 写入 `Cache-Control: public, max-age=31536000, immutable`
- `/`
  - 代理到 `web:80`
  - 外层 Nginx 写入 `Cache-Control: no-cache`
- `/admin/`
  - 代理到 `admin:80`
  - Admin 镜像内 `deploy/nginx/admin.conf` 对 HTML fallback 写入 `Cache-Control: no-cache`
- `/api/` 与 `/admin/api/`
  - 代理到 `server:3000`
  - 外层 Nginx 不写入静态资源长缓存

前台与后台镜像内部的 `web.conf`、`admin.conf` 也对各自 `/assets/` 使用长缓存、对 HTML fallback 使用 `no-cache`。外层 Nginx 的 `/assets/` 与 `/admin/assets/` 独立 location 用于避免静态资源长缓存与 SPA HTML fallback 的 `no-cache` 在同一路径上冲突。

## 9. 部署验证

部署后至少验证：

```bash
curl -k --resolve www.chipscard.space:443:111.92.241.17 https://www.chipscard.space/api/v1/health
curl -k --resolve www.chipscard.space:443:111.92.241.17 -I https://www.chipscard.space/
curl -k --resolve www.chipscard.space:443:111.92.241.17 -I https://www.chipscard.space/admin/
```

若 DNS 已正式解析到服务器，可去掉 `--resolve`。

资源链路验证以新上传内容为准，检查返回的 view 缓存 URL / `coverUrl` 是否形如：

```text
https://file.chipscard.space/chips-card-render-cache/...
https://file.chipscard.space/chips-card-cover-cache/...
https://file.chipscard.space/chips-covers/...
```

公开渲染缓存走对象存储或 CDN 直链时，该公开域名必须保留对象存储的 `Range` / `206 Partial Content` 行为；视频、音频等浏览器媒体元素会依赖分段读取。

前台卡片打开不应依赖 `htmlUrl`。正式打开入口为：

```text
GET /api/v1/cards/{cardId}/open-view
GET /api/v1/cards/{cardId}/view
GET /api/v1/cards/{cardId}/cover
```

若卡片正文或封面缓存使用社区服务器受控代理入口，例如私有内容下的：

```text
GET /api/v1/cards/{cardId}/render-cache/{cacheVersion}/assets/content/videos/demo.mp4
```

需要额外验证视频类资源的分段读取能力：

```bash
curl -k -I -H "Range: bytes=0-1023" "https://www.chipscard.space/api/v1/cards/{cardId}/render-cache/{cacheVersion}/assets/content/videos/demo.mp4"
```

期望返回 `206 Partial Content`、`Content-Range` 与 `Accept-Ranges: bytes`。如果只返回整段 `200 OK` 或缺少 `Content-Range`，浏览器视频播放器可能能打开查看器会话，但 `<video>` 无法读取媒体元数据并显示“视频资源不可用”。

## 10. 生产端口边界

生产 Compose 默认只映射：

- `80`
- `443`

以下服务只在 Docker 网络内访问，不直接暴露公网端口：

- PostgreSQL `5432`
- Redis `6379`
- MinIO `9000 / 9001`
- 卡片渲染缓存 Worker 无 HTTP 监听端口

外部对象存储部署下，MinIO 服务仅作为本地开发/回退组件保留，不属于生产资源写入链路。
