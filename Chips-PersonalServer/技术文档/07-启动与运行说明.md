## 1. 运行架构总览

### 1.1 包职责

- `packages/server`
  - 社区服务器 API 主体；
  - 使用 Fastify 提供 REST API；
  - 使用 Drizzle ORM + PostgreSQL 持久化结构化数据；
  - 使用 Redis 处理认证失败计数、token 吊销名单等运行时状态；
  - 使用 MinIO / S3 兼容对象存储保存卡片资源、源 `.card`、view/cover 渲染缓存、头像与封面；
  - 启动时会初始化 Host 集成层，安装卡片插件、模块插件和主题插件。
- `packages/server/src/worker.ts`
  - 与 API 复用同一个服务端构建产物和 Docker 镜像；
  - 独立消费 Redis 中的卡片渲染缓存队列；
  - 从 `chips-card-files` 下载永久 `.card` 源文件；
  - 生成完整查看缓存 `community-web` 与封面缓存 `community-cover`；
  - 成功后写入 `card_render_caches` 并设置 30 天访问续期，失败按环境变量配置重试；
  - 周期清理最后访问后超过 30 天的渲染缓存，不删除源 `.card`。
- `packages/web`
  - 社区公开前台；
  - 使用 Vite 开发服务器运行；
  - 开发态通过 `/api` 代理到 `packages/server`。
- `packages/admin`
  - 社区管理后台；
  - 也是独立 Vite 前端；
  - 开发态通过 `/api` 与 `/admin/api` 代理到 `packages/server`。
- `deploy`
  - 存放 Docker Compose、Dockerfile 和 Nginx 反向代理配置；
  - 用于生产式或接近生产式的容器化运行。

### 1.2 两种正式运行模式

当前项目存在两条正式启动路径：

1. 本地开发分拆模式
   - Docker 只负责 PostgreSQL、Redis、MinIO；
   - `packages/server` 在本地 Node 进程中运行；
   - `packages/web` / `packages/admin` 在本地 Vite 进程中运行。
2. Docker 全栈模式
   - PostgreSQL、Redis、API、卡片渲染缓存 Worker、Web、Admin、Nginx 全部由 Compose 拉起；
   - 使用本地 MinIO 对象存储时再额外启动 MinIO；
   - 对外统一由 Nginx 暴露 `80` / `443` 端口。

本仓库当前最适合日常开发与联调的是第一种模式。

### 1.3 端口与访问入口

| 组件 | 默认端口 | 用途 | 说明 |
| --- | --- | --- | --- |
| API 服务 | `3000` | Fastify REST API | 根路径 `/` 不是前台首页 |
| 卡片渲染缓存 Worker | 无公网端口 | Redis 队列消费者 | 默认并发 `1`，处理查看缓存、封面缓存与缓存清理 |
| 社区前台 | `5173` | `packages/web` Vite 开发服务 | 默认推荐访问这里看社区页面 |
| 管理后台 | `5174` | `packages/admin` Vite 开发服务 | 独立后台入口 |
| PostgreSQL | 容器内 `5432` | 结构化数据存储 | Docker 基础设施，生产 Compose 默认不映射公网端口 |
| Redis | 容器内 `6379` | 认证与运行时缓存 | Docker 基础设施，生产 Compose 默认不映射公网端口 |
| MinIO S3 API | 容器内 `9000` | 对象存储 API | 本地对象存储模式使用，外部对象存储部署可不启动 |
| MinIO Console | 容器内 `9001` | MinIO 管理台 | 本地对象存储模式使用，生产 Compose 默认不映射公网端口 |
| Nginx | `80` | 全栈统一入口 | 仅 Docker 全栈模式使用 |

重要说明：

- `http://127.0.0.1:3000/` 不是社区前台页面，看到 `404` 是正常现象；
- API 是否启动成功，应通过 `http://127.0.0.1:3000/api/v1/health` 判断；
- 社区前台页面默认应访问 `http://localhost:5173/` 或显式绑定后访问 `http://127.0.0.1:5173/`。

## 2. 环境变量与基础依赖

### 2.1 基础依赖

- Node.js：`>= 20`
- npm：生态根工作区使用 `10.9.3`
- pnpm：`>= 9`
- Docker / Docker Compose：用于 PostgreSQL、Redis、MinIO 以及可选的全栈模式

### 2.2 依赖安装与工作区解析

生态根工作区的正式依赖入口是仓库根 `package.json` 与 `package-lock.json`。社区服务器的三个实际包：

- `Chips-CommunityPlatformServer/packages/server`
- `Chips-CommunityPlatformServer/packages/web`
- `Chips-CommunityPlatformServer/packages/admin`

已经纳入生态根 npm workspaces。刷新整个生态依赖时，在生态根执行：

```bash
npm install
```

社区项目保留 pnpm 启动命令作为本项目内部开发入口。`Chips-CommunityPlatformServer/.npmrc` 明确启用：

```ini
link-workspace-packages=true
```

`Chips-CommunityPlatformServer/pnpm-workspace.yaml` 覆盖：

```yaml
packages:
  - 'packages/*'
  - '../Chips-Host'
```

因此在 `Chips-CommunityPlatformServer` 内执行：

```bash
pnpm install
```

时，`@ccps/server` 的 `chips-host: 0.1.0` 会解析为 `link:../../../Chips-Host`，不应访问远端 registry。

当前服务端代码只直接 import `chips-host`。CardViewer、PhotoViewer、基础卡片插件、布局插件、模块插件和默认主题不再作为 `@ccps/server` 的 npm/pnpm `file:` 依赖安装；它们由 `HostIntegrationService` 按生态根目录中的源码或构建产物路径安装到临时 Host 工作区。这样 API 与 Worker 每次启动都会使用当前 `ThemePack/Chips-default/dist` 等正式产物，不再消费旧 `node_modules/.pnpm` 快照。

### 2.3 环境变量文件位置

服务端环境变量不是从仓库根自动扫描，而是由 `packages/server/src/config/env.ts` 显式读取：

```ts
dotenv.config({ path: path.resolve(__dirname, '../../../../deploy/.env') });
```

因此开发态正式环境文件位置是：

```text
Chips-CommunityPlatformServer/deploy/.env
```

不是：

- 仓库根 `.env`
- `packages/server/.env`

### 2.4 必要环境变量

当前 `deploy/.env` 至少需要保证以下变量有效：

- `PORT`
  - API 监听端口，默认 `3000`
- `HOST`
  - API 监听地址，默认 `0.0.0.0`
- `BASE_URL`
  - 外部访问基地址；
  - Swagger 与部分公开 URL 逻辑会用到
- `DATABASE_URL`
  - PostgreSQL 连接串
- `REDIS_URL`
  - Redis 连接串
- `S3_ENDPOINT`
  - MinIO / S3 兼容对象存储入口
- `S3_RUNTIME_ENDPOINT`
  - Docker Compose 运行时覆盖用入口；
  - 不直接由服务端读取，而是在 `deploy/docker-compose.yml` 中映射为容器内 `S3_ENDPOINT`；
  - 留空时 Docker 全栈模式默认使用 `http://minio:9000`；
  - 使用外部对象存储时应设置为外部 S3 兼容 API 入口。
- `S3_ACCESS_KEY`
  - MinIO 访问账号
- `S3_SECRET_KEY`
  - MinIO 访问密码
- `S3_REGION`
  - S3 区域，默认 `us-east-1`
- `S3_FORCE_PATH_STYLE`
  - 本地 MinIO 一般为 `true`
- `JWT_SECRET`
  - 长度必须至少 32 个字符
- `JWT_ACCESS_EXPIRES_IN`
  - Access Token 过期时间
- `JWT_REFRESH_EXPIRES_IN`
  - Refresh Token 过期时间
- `MAX_CARD_SIZE_MB`
  - 卡片上传大小上限
- `MAX_BOX_SIZE_MB`
  - 箱子上传大小上限
- `MAX_AVATAR_SIZE_MB`
  - 头像上传大小上限
- `CARD_RENDER_CACHE_UPLOAD_CONCURRENCY`
  - view/cover 渲染缓存目录上传对象存储的并发上限，默认 `8`
- `CARD_RENDER_WORKER_CONCURRENCY`
  - 卡片渲染 worker 并发循环数量，默认 `1`
- `CARD_RENDER_JOB_MAX_ATTEMPTS`
  - 单个渲染任务最大尝试次数，默认 `2`
- `CARD_RENDER_QUEUE_POLL_TIMEOUT_SEC`
  - worker 等待 Redis 渲染队列的阻塞超时时间，默认 `5`
- `CARD_RENDER_CACHE_TTL_DAYS`
  - ready 渲染缓存续期后的过期天数，默认 `30`
- `CARD_RENDERER_VERSION`
  - 渲染缓存版本组成部分，渲染器或输出契约变化时应升级
  - 当前默认值为 `community-card-renderer-4`；该版本要求 `card -> html` 导出产物离线化 Host 注入主题字体等根外本地文件资源，让基础卡片 iframe 内的相对资源基准 URL 可被 Host 单卡运行时归一为当前文档绝对 URL，并要求视频/电子书基础卡片缓存产物使用正式 `chips.video-card`、`chips.book-card` 资源打开 payload，从而保证评分图标字体、视频、电子书与图片序列都能在社区 Web 中继续走 `resource.open` 链路。
- `UPLOAD_SESSION_TTL_MINUTES`
  - 上传会话有效期，默认 `60`
- `ENABLE_SWAGGER`
  - 是否启用 `/api/docs`
- `HOST_ACTIVE_THEME_ID`
  - Host 集成层的激活主题

### 2.5 可选环境变量

- `S3_PUBLIC_URL`
  - 若设置，公开资源 URL 将优先使用这个前缀，生产环境推荐配置为对象存储自定义 HTTPS 域名；
  - 若不设置：
    - 开发态优先返回 MinIO 直连地址；
    - 非开发态回退到 `${BASE_URL}/cdn/...`
- `S3_BUCKET_NAME`
  - 若设置，表示将公开逻辑 bucket 写入同一个物理 bucket；
  - 写入对象 key 时会自动添加逻辑 bucket 前缀，例如 `chips-card-render-cache/{cardId}/{cacheVersion}/index.html`；
  - 公开 URL 仍保留逻辑 bucket 路径，确保前端和已发布 DTO 不需要知道物理 bucket 名称。
- `ADMIN_USERNAME`
  - 若设置，服务启动时会尝试初始化管理员账号
- `ADMIN_PASSWORD`
  - 配合 `ADMIN_USERNAME` 使用
- `HOST_CARD_PLUGIN_PATHS`
  - 覆盖默认卡片插件安装路径
- `HOST_THEME_PLUGIN_PATHS`
  - 覆盖默认主题插件安装路径
- `HOST_MODULE_PLUGIN_PATHS`
  - 覆盖默认模块插件安装路径

## 3. 服务端正式启动顺序

### 3.0 API 服务启动顺序

`packages/server/src/server.ts` 中的启动顺序是固定的：

1. 执行数据库迁移 `runMigrations()`
2. 连接 Redis `connectRedis()`
3. 初始化对象存储 bucket `initStorageBuckets()`
4. 初始化管理员账号 `initAdminAccount()`
5. 构建并启动 Fastify `buildApp()`

### 3.1 数据库迁移

- 迁移实现位于 `packages/server/src/db/migrate.ts`
- 使用 Drizzle migrator 执行 `packages/server/src/db/migrations`
- 若数据库未准备好，服务不会继续监听端口
- `@ccps/server build` 结束时会通过 `scripts/copy-server-runtime-assets.mjs` 把迁移 SQL 与 `meta/_journal.json` 正式复制到 `packages/server/dist/db/migrations`，保证 `node dist/server.js` 与正式 Docker 镜像都能直接运行迁移
- 当前项目未发布首版，不需要保留过往数据兼容；部署新结构时按当前迁移定义重置数据库后运行迁移，不编写旧数据迁移、回填或兼容方案

### 3.2 Redis 连接

- 连接实现位于 `packages/server/src/cache/redis.ts`
- 采用 `lazyConnect: true`，由 `connectRedis()` 显式触发
- Redis 主要用于：
  - 登录失败计数
  - 认证锁定
  - Refresh Token 黑名单 / 吊销状态
  - 卡片渲染缓存任务队列 `ccps:card-render:queue`

### 3.3 对象存储初始化

- 初始化逻辑位于 `packages/server/src/storage/init.ts`
- 启动时会确保以下公开读 bucket 存在并设置公开读策略：
  - `chips-card-resources`
  - `chips-card-render-cache`
  - `chips-card-cover-cache`
  - `chips-avatars`
  - `chips-covers`
- 启动时还会确保以下内部 bucket 存在，不设置公开读策略：
  - `chips-card-files`
  - `chips-card-render-cache-private`
  - `chips-card-cover-cache-private`

### 3.4 Host 集成层

Fastify 启动完成后，`buildApp()` 还会在 `onReady` 生命周期中初始化 Host 集成层。

Host 集成层的关键行为：

- 工作区位置按进程角色隔离：
  - API 进程：`Chips-CommunityPlatformServer/packages/server/.chips-server-host-server`
  - Worker 进程：`Chips-CommunityPlatformServer/packages/server/.chips-server-host-worker`
- 每次启动前会先清空并重建这个目录；
- 会启动 `HostApplication`；
- 会从生态仓库中默认安装这些插件：
  - `Chips-CardViewer`
  - `Chips-PhotoViewer`
  - `Chips-BaseCardPlugin/richtext-BCP`
  - `Chips-BaseCardPlugin/image-BCP`
  - `Chips-BaseCardPlugin/webpage-BCP`
  - `Chips-BaseCardPlugin/music-BCP`
  - `Chips-BaseCardPlugin/video-BCP`
  - `Chips-BaseCardPlugin/score-BCP`
  - `Chips-BaseCardPlugin/book-BCP`
  - `Chips-BaseCardPlugin/hyperlink-BCP`
  - `Chips-BoxLayoutPlugin/grid-BLP`
  - `Chips-ModulePlugin/Chips-CardtoHTML-Plugin`
  - `Chips-ModulePlugin/Chips-FileConversion-Plugin`
  - `ThemePack/Chips-default`
- 启动后会执行 `theme.apply`，应用 `HOST_ACTIVE_THEME_ID`

这意味着：

- 社区服务器开发态不是一个“纯后端 API”，它在内容处理链路上依赖本仓库里的 Host / 插件 / 主题资源；
- 如果这些本地插件目录不存在、未构建或路径配置错误，卡片处理相关能力会受影响；
- API 与 Worker 安装默认主题后，`packages/server/.chips-server-host-server/plugins/theme.theme.chips-official-default-theme/dist/tokens.json` 和 `packages/server/.chips-server-host-worker/plugins/theme.theme.chips-official-default-theme/dist/tokens.json` 应与 `ThemePack/Chips-default/dist/tokens.json` 保持一致。

### 3.5 卡片渲染缓存 Worker 启动顺序

`packages/server/src/worker.ts` 是正式后台 Worker 入口，启动顺序为：

1. 执行数据库迁移 `runMigrations()`
2. 连接 Redis `connectRedis()`
3. 初始化对象存储 bucket `initStorageBuckets()`
4. 初始化 Host 集成层 `hostIntegration.init()`
5. 把超过 30 分钟仍处于 `processing` 的滞留任务重新入队
6. 执行一次过期渲染缓存清理，并按小时周期继续清理
7. 按 `CARD_RENDER_WORKER_CONCURRENCY` 启动消费循环

Worker 处理队列时会：

- 通过 Redis `brpop` 从 `ccps:card-render:queue` 获取任务 ID；
- 在 PostgreSQL 的 `card_render_jobs` 中锁定 `queued` 任务；
- 从 `chips-card-files/{userId}/{cardId}/source.card` 下载永久 `.card` 源文件到专属临时目录；
- `community-web` 任务调用 Host 集成层生成完整网页查看缓存，并上传到 `chips-card-render-cache*`；
- `community-cover` 任务提取 `.card/cover.html` 与 `.card/cardcover/`，生成独立封面缓存并上传到 `chips-card-cover-cache*`；
- 成功后把任务置为 `succeeded`，写入 `card_render_caches.generatedAt / lastAccessedAt / expiresAt`；
- 失败时按 `CARD_RENDER_JOB_MAX_ATTEMPTS` 控制尝试次数，超过次数后把任务置为 `failed` 并写入缓存错误态。

## 4. 推荐本地开发启动方式

### 4.1 启动 Docker 基础设施

在项目根执行：

```bash
docker compose \
  -f Chips-CommunityPlatformServer/deploy/docker-compose.yml \
  --env-file Chips-CommunityPlatformServer/deploy/.env \
  up -d postgres redis minio
```

或者进入 `deploy` 目录执行：

```bash
cd Chips-CommunityPlatformServer/deploy
docker compose up -d postgres redis minio
```

检查状态：

```bash
docker compose \
  -f Chips-CommunityPlatformServer/deploy/docker-compose.yml \
  --env-file Chips-CommunityPlatformServer/deploy/.env \
  ps
```

期望至少看到：

- `ccps_postgres`
- `ccps_redis`
- `ccps_minio`

并且状态为 `Up` / `healthy`。

### 4.2 启动 API 服务

在仓库根执行：

```bash
pnpm --dir Chips-CommunityPlatformServer dev
```

这个命令实际会执行：

```bash
pnpm --filter @ccps/server dev
```

也就是：

```bash
tsx watch src/server.ts
```

### 4.6 一键本地启动脚本

项目提供正式本地开发一键启动脚本：

```bash

```

该命令会按顺序执行：

1. 使用 `deploy/docker-compose.yml` 与 `deploy/.env` 启动 PostgreSQL、Redis、MinIO；
2. 清理当前社区项目自己的旧 API、Worker、Web、Admin 开发进程；
3. 启动 API 并等待 `http://127.0.0.1:3000/api/v1/health` 返回成功；
4. 启动卡片渲染缓存 Worker，并等待 `CardRenderWorker` 进入消费循环；
5. 启动社区前台 `http://127.0.0.1:5173/`；
6. 启动管理后台 `http://127.0.0.1:5174/admin/`。


`stop:local` 只停止本地 Node/Vite 开发进程，不停止 Docker 基础设施。若需要连 PostgreSQL、Redis、MinIO 一起停止，可直接执行：

## 5. Docker 全栈启动方式

如果需要接近生产式的整体验证，可以直接拉起完整 Compose：

```bash
docker compose \
  -f Chips-CommunityPlatformServer/deploy/docker-compose.yml \
  --env-file Chips-CommunityPlatformServer/deploy/.env \
  up -d --build
```

这会启动：

- PostgreSQL
- Redis
- MinIO
- `server`
- `worker`
- `web`
- `admin`
- `nginx`

### 5.1 Docker 全栈模式访问入口

- 社区前台：
  - `http://localhost/`
- 管理后台：
  - `http://localhost/admin/`
- API 健康检查：
  - `http://localhost/api/v1/health`
- API 文档：
  - `http://localhost/api/docs`
- CDN 公开资源：
  - 本地 MinIO 回退口径为 `http://localhost/cdn/...`
  - 生产对象存储推荐使用 `S3_PUBLIC_URL` 指向的自定义 HTTPS 域名

### 5.2 全栈模式的反向代理关系

`deploy/nginx/nginx.conf` 当前路由关系为：

- `/api/` -> `server:3000`
- `/admin/api/` -> `server:3000`
- `/cdn/` -> 当前生产配置 301 跳转到对象存储自定义 HTTPS 域名；本地 MinIO 模式可改为代理到 `minio:9000`
- `/admin/assets/` -> `admin:80` 的 `/assets/`，外层 Nginx 强制写入 `public, max-age=31536000, immutable`
- `/assets/` -> `web:80` 的 `/assets/`，外层 Nginx 强制写入 `public, max-age=31536000, immutable`
- `/admin/` -> `admin:80`
- `/` -> `web:80`

缓存口径：

- `/assets/` 与 `/admin/assets/` 只承载 Vite hash 静态资源，使用长缓存；
- 前台 `/` 的 HTML fallback 由外层 Nginx 写入 `Cache-Control: no-cache`；
- 后台 `/admin/` 的 HTML fallback 由 Admin 镜像内 `deploy/nginx/admin.conf` 写入 `Cache-Control: no-cache`；
- `/api/` 与 `/admin/api/` 不由 Nginx 添加缓存头。

### 5.3 全栈模式的额外注意事项

- `Dockerfile.server` 不是只打包 `packages/server`；
- 它会先在独立的 `ecosystem-artifacts` 阶段正式构建：
  - `Chips-Host`
  - `Chips-BaseCardPlugin/image-BCP`
  - `Chips-BaseCardPlugin/richtext-BCP`
  - `Chips-BaseCardPlugin/webpage-BCP`
  - `Chips-BaseCardPlugin/music-BCP`
  - `Chips-BaseCardPlugin/video-BCP`
  - `Chips-BaseCardPlugin/score-BCP`
  - `Chips-BaseCardPlugin/book-BCP`
  - `Chips-BaseCardPlugin/hyperlink-BCP`
  - `Chips-ModulePlugin/Chips-HtmltoImage-Plugin`
  - `Chips-ModulePlugin/Chips-CardtoHTML-Plugin`
  - `Chips-ModulePlugin/Chips-FileConversion-Plugin`
  - `ThemePack/Chips-default`
- 随后服务镜像再消费这些已构建工件，而不是依赖宿主机预先提交的 `dist` 目录；
- 服务端正式 `dist` 还会额外并入数据库迁移资源，再复制进生产镜像；
- `server` 与 `worker` 复用同一个 `Dockerfile.server` 镜像，Compose 中的 `worker` 服务通过 `command: ["node", "dist/worker.js"]` 切换入口；
- `worker` 服务依赖 PostgreSQL、Redis 和 `server` 已启动，默认 `CARD_RENDER_WORKER_CONCURRENCY=1`。

因此 Docker 全栈模式要求整个生态仓库相对目录结构完整可用。

## 8. 常见问题与排障

### 8.1 打开 `http://127.0.0.1:3000/` 什么都没有

这是正常现象。

原因：

- `3000` 是 API 服务；
- 根路径 `/` 没有挂社区前台页面；
- 正确的 API 验证地址是 `/api/v1/health`；
- 正确的社区前台地址是 `5173` 或 Docker 全栈模式下的 `80`。

### 8.2 `5173` 只能用 `localhost`，不能用 `127.0.0.1`

原因：

- Vite 默认开发服务器并不总是对 `127.0.0.1` 暴露；
- 若需要明确通过 `127.0.0.1` 访问，请使用：

```bash
pnpm --dir Chips-CommunityPlatformServer/packages/web exec vite --host 0.0.0.0 --port 5173
```

### 8.3 API 没有监听，终端停在迁移或初始化阶段

优先检查：

1. PostgreSQL 是否启动
2. Redis 是否启动
3. MinIO 是否启动
4. `deploy/.env` 是否正确
5. `JWT_SECRET` 是否至少 32 位

### 8.3.1 `.card` 上传后一直处于处理中

优先检查：

1. Worker 进程或 Docker `worker` 服务是否正在运行
2. Redis 是否可连接
3. 对象存储中 `chips-card-files` 私有 bucket 是否可由 API 写入、由 Worker 读取
4. Host 集成层依赖的插件与主题是否已构建并可安装
5. `card_render_jobs` 中任务是否处于 `queued`、`processing`、`failed` 或 `succeeded`
6. `card_render_caches` 中对应 `community-web` 或 `community-cover` 缓存是否记录错误信息

### 8.4 启动时 Host 集成层报插件路径问题

优先检查：

- 生态仓库目录是否完整；
- `Chips-Host`、`Chips-BaseCardPlugin`、`Chips-ModulePlugin`、`ThemePack` 是否存在；
- 若使用自定义插件路径，`HOST_*_PLUGIN_PATHS` 是否指向真实文件或目录。

### 8.5 对象资源 URL 不是 `/cdn/...`

这是当前代码定义的结果，不一定是故障。

现有逻辑：

- 若设置了 `S3_PUBLIC_URL`，优先用它；
- 若是开发态且未设置 `S3_PUBLIC_URL`，优先返回 MinIO 直连地址；
- 若是非开发态且未设置 `S3_PUBLIC_URL`，回退到 `${BASE_URL}/cdn/...`

### 8.6 启动后 `.chips-server-host-*` 内容被重建

这是当前 Host 集成层的正式行为，不是误删。

现有逻辑：

- 每次 `HostIntegrationService.init()` 先删除当前进程角色对应的旧工作区；
- 再重建并重新安装插件、应用主题；
- 目的是保证社区服务器处理链路启动时拥有一致的 Host 运行环境。
- API 与 Worker 使用不同工作区，避免两个正式进程并发启动时互相清理插件目录。

## 10. 推荐使用结论

日常开发请优先采用以下口径：

1. 先启动 Docker 基础设施；
2. 再启动本地 API；
3. 涉及 `.card` 上传、查看缓存或封面缓存时启动 Worker；
4. 再启动本地社区前台；
5. 需要后台时额外启动本地 Admin；
6. 不要把 `3000` 当成社区首页；
7. 需要单端口统一入口时再切换到 Docker 全栈模式。
